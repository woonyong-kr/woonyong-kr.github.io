fork 가 메모리를 통째로 베끼지 않게 하기

PintOS 과제에서 COW 는 필수가 아니었습니다. fork 는 이미 동작했고, 테스트도 통과한 상태였습니다. 그런데 fork 경로를 따라가다 보니 이상한 그림이 보였습니다. 자식 프로세스 대부분이 복사받은 메모리를 쓰기도 전에 exec 으로 전부 버리고 있었습니다.

__do_fork()
  └─ supplemental_page_table_copy()
       ├─ uninit_copy()   initializer 만 복사
       ├─ anon_copy()     프레임 할당 + memcpy   ← 여기서 전체 페이지 복사
       └─ file_copy()     프레임 할당 + file_read

곧이어 자식이 exec() → 방금 복사한 메모리 전부 폐기

복사 비용은 전부 내는데, 그 복사본은 대부분 수명이 몇 밀리초입니다. 이 낭비를 없애는 방법이 Copy-on-Write 라는 것은 알고 있었습니다. 문제는 선택이었습니다. 남은 기간에 필수 과제(스왑 · mmap)를 다듬을 것인가, 구조를 바꾸는 확장에 들어갈 것인가. fork 는 모든 프로세스 생성이 지나는 길목이라, 여기 낭비는 시스템 전체의 낭비라고 판단했고 확장을 골랐습니다.

복사 시점을 “쓰는 순간” 으로 옮기다

fork 시점에는 아무것도 복사하지 않습니다. 부모와 자식이 같은 물리 프레임을 가리키게 하고, 양쪽 페이지를 모두 읽기 전용으로 내립니다.

fork 직후                          자식이 페이지 P 에 쓰기 시도
부모 ──┐                           부모 ──> [프레임 A]
       ├──> [프레임 A] (읽기 전용)
자식 ──┘                           자식 ──> [프레임 A'] (그 페이지만 복사)

누군가 쓰기를 시도하면 CPU 가 Page Fault 를 냅니다. 그때 그 페이지 하나만 복사하고, 쓴 쪽의 매핑을 새 프레임으로 바꿉니다. 복사 비용이 “전체를 즉시” 에서 “실제로 쓴 페이지만, 쓴 순간에” 로 바뀝니다.

폴트 하나에 의미가 세 개가 됐다

이 설계의 대가는 Page Fault 의 의미가 늘어나는 것입니다. 핸들러가 같은 폴트를 세 갈래로 판정해야 합니다.

Page Fault
 ├─ 잘못된 접근            → 프로세스 종료
 ├─ 스택 확장 요청         → 새 페이지 할당
 └─ COW 페이지에 쓰기      → ref_count 확인
      ├─ ref_count > 1    → 복사 후 매핑 교체
      └─ ref_count == 1   → 복사 없이 쓰기 권한만 복원

마지막 분기를 넣을지 한참 고민했습니다. 없어도 동작은 합니다. 그런데 공유자가 나 하나만 남았는데 복사하는 것은 COW 를 넣은 이유를 스스로 배반하는 일입니다. 그래서 프레임이 참조 수를 세도록 구조를 바꿨습니다. struct frame 에 추가한 것은 두 필드입니다.

OS 와 CPU 에게 서로 다른 말을 해 둔다

구현하며 가장 헷갈렸던 지점이라 당시 발표 자료에 문장으로 박아 뒀습니다.

SPT writable=true
  -> 원래 쓸 수 있는 page 라는 OS 의 판단

PML4/PTE_W=false
  -> 지금 CPU/MMU 에게는 쓰기를 막아 page fault 를 유도

OS 는 “이 페이지는 쓸 수 있다” 고 기억하고, CPU 에게는 “지금은 쓰지 마라” 고 말합니다. 이 어긋남이 만들어 내는 폴트가 복사의 트리거입니다. 폴트 경로는 vm.c 의 vm_handle_wp 에서 vm_handle_cow, vm_copy_cow_page 로 이어집니다.

참조 수는 답의 절반이었다

이렇게 프레임이 공유되기 시작하자 새 질문이 따라왔습니다. 공유된 페이지가 스왑으로 내려가면, 그 스왑 슬롯은 누가 언제 반납해야 하는가. 참조 수만으로는 풀리지 않는 이 문제는 다음 글에 이어집니다.

교육용 커널 위의 구현이라는 경계는 그대로입니다. 상용 커널의 COW 와 비교하면 huge page 나 NUMA 같은 차원이 통째로 없고, 검증도 과제 테스트 스위트(pintos/tests/vm) 범위 안입니다.
