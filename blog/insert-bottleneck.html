INSERT 는 왜 144배 느려졌나

PostgreSQL 비교의 후속입니다. “시료가 작다”는 피드백으로 규모를 1,000,000행으로 올렸더니, 이번엔 범위 조회가 아니라 INSERT 가 무너졌습니다.

INSERT (ops/sec)     10,000행     1,000,000행
MiniDB                ~400,000        2,751     ← 144배 하락

단서는 스케일 곡선에 있었습니다. 50k → 0.25초, 100k → 0.96초, 200k → 4.73초. 행 수가 2배면 시간이 4배 — O(N²)의 서명입니다.

gdb 를 붙였다

추측하지 않고, 실행 중인 삽입 프로세스에 gdb 를 붙여 스택을 샘플링했습니다.

#0  lock_acquire (lt=<g_lock_table>, row_id=152269, mode=LOCK_X)  lock_table.c:254
#1  exec_insert                                                    executor.c:273
#2  execute                                                        executor.c:1637

4회 샘플 중 4회가 lock 테이블의 체인 탐색 위에 있었습니다. 코드를 따라가니 결함이 두 건이었습니다.

결함 1 — 힙 체인 전체 재탐색

꼬리 페이지가 가득 찰 때마다(약 90행마다) 새 페이지를 할당하기 전에, 삭제된 슬롯을 재활용할 수 있는지 힙 체인 전체를 처음부터 다시 걷고 있었습니다. DELETE 가 한 번도 없었는데도요. 1M 행이면 페이지가 약 12,700장이고, 페이지 접근이 약 8천만 번 쌓입니다. 페이지 수 P 에 대해 O(P²)입니다.

결함 2 — REPL 경로의 lock 미해제

더 큰 쪽은 이겁니다. 서버 경로는 문장이 끝나면 보유 lock 을 전부 해제하는데(Strict 2PL autocommit), REPL 경로는 같은 실행 함수를 직접 부르면서 해제를 빠뜨렸습니다. 문장마다 X-lock 엔트리가 lock 테이블에 영구 누적되고, 해시 버킷 256개에 N 개가 쌓이면 lock 획득마다 체인을 N/256 개씩 걸어야 합니다. 총 O(N²).

같은 코드가 경로에 따라 다르게 동작하는 결함이라, 단위 기능 테스트로는 안 잡힙니다. 규모를 키운 실측이 아니면 나올 수 없는 종류였습니다.

두 결함을 각각 고쳤다

  1. 빈 슬롯 힌트 — “힙 어딘가에 재활용할 슬롯이 있을 수 있는가”를 bool 하나로 기억합니다. DELETE 때 켜지고, 전체 탐색이 허탕이면 꺼지고, DB 를 열 때는 원래 하던 꼬리 복원 순회에서 정확한 값으로 복원됩니다. 삭제 없는 순차 INSERT 는 재탐색을 아예 하지 않습니다.
  2. REPL 의 lock 해제 — 문장 실행 직후 lock_release_all() 호출 한 줄. 서버 경로와 같은 의미론이 됐습니다.

sanitizer(-Werror) 빌드 통과, ASAN 으로 삽입 · 삭제 · 슬롯 재활용 · 재열기 경로 무오류를 확인하고 다시 측정했습니다.

다시 측정

1,000,000행 (ops/sec)   개선 전      개선 후      PG (fsync=off)
INSERT                    2,751      591,429        10,919

삽입 스케일 곡선은 50k · 200k · 1M 에서 531k · 593k · 582k ops/sec — 선형으로 돌아왔습니다. Apple Silicon 로컬 재현에서는 835k ops/sec 로 더 좋았습니다.

결함 두 곳과 개선 폭을 정리하면 이렇습니다.

결함 1  힙 체인 전체 재탐색     페이지 12,700장을 반복해 걷기 → bool 힌트 하나
결함 2  REPL 의 lock 미해제     엔트리 1,000,000개 잔류       → 해제 호출 한 줄

INSERT 1,000,000행    2,751 ops/sec ───────────▶ 591,429 ops/sec

같은 MiniDB의 개선 전후는 2,751에서 591,429 ops/sec로 약 215배 차이였습니다. PostgreSQL과의 비교가 아니라, 위 두 O(N²) 결함을 수정하기 전후의 결과입니다.

이 측정이 남긴 것

PostgreSQL과의 배수는 성과가 아닙니다. WAL도 MVCC도 네트워크도 없는 엔진이 내구성 비용을 지불하지 않은 결과입니다. 남길 수 있는 것은 규모를 키운 측정에서 O(N²) 두 곳을 찾고, gdb 스택 샘플링으로 원인을 좁혀 같은 MiniDB의 스케일 곡선을 다시 확인한 과정입니다.

한계도 남습니다. 1M 행(약 52MB)도 여전히 캐시에 다 올라가는 규모라 디스크가 병목인 비교는 아니고, 단일 커넥션 합성 워크로드입니다. 전 과정은 저장소의 docs/benchmark-postgres.md 와 bench/ 스크립트로 재현할 수 있습니다.
