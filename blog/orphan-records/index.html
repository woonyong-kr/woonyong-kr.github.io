부모가 먼저 죽으면 남는 것들

과제 테스트가 전부 통과한 상태에서 찾은 커널 메모리 누수

  • 프로젝트
  • C

부모가 먼저 죽으면 남는 것들

wait 시스템 콜은 부모가 자식의 종료 코드를 읽는 통로입니다. 자식이 부모보다 먼저 끝날 수 있으므로, 종료 코드는 자식 스레드가 사라진 뒤에도 남아 있어야 합니다. 그래서 자식의 종료 정보를 스레드와 분리된 별도 레코드(child_status)로 커널에 보관합니다.

여기까지 만들면 과제 테스트는 전부 통과합니다. 그런데 질문이 하나 남았습니다.

부모가 자식보다 먼저 죽으면, 그 레코드는 누가 치우나.

정상 경로:  자식 종료 → 레코드에 기록 → 부모 wait → 부모가 레코드 회수
문제 경로:  부모 종료 → 자식들의 레코드를 아무도 안 가리킴
            자식이 나중에 종료 → 레코드 기록 → 읽을 사람 없음 → 영원히 잔류

테스트는 이 경로를 요구하지 않습니다. 잔류 레코드는 동작에 아무 증상을 만들지 않고, 커널 메모리만 조용히 샙니다. 프로세스가 수만 번 뜨고 지는 실제 시스템이라면 언젠가 커널이 메모리를 다 씁니다.

회수 경로를 추가했다

부모가 종료될 때 자식 레코드를 두 갈래로 처리합니다.

  • 이미 종료됐고 아무도 기다리지 않는 레코드는 그 자리에서 회수
  • 아직 실행 중인 자식은 고아 목록으로 옮겨, 자식이 종료될 때 자기 레코드를 스스로 정리

회수 순서도 고정했습니다. 페이지 테이블, 프레임, 파일 디스크립터를 정해진 순서로 해제해서 같은 자원을 두 번 반납하는 경로를 막았습니다.

이 버그의 성격

이 누수는 기다려서는 못 찾습니다. 에러도, 실패하는 테스트도 없기 때문입니다. 찾는 방법은 프로세스 생명주기를 표로 그려 놓고 “이 전이에서 이 자원은 누가 치우나” 를 전이마다 묻는 것뿐이었습니다.

나중에 데이터 파이프라인에서 “모든 검사가 통과하는데 검사 자체가 죽어 있던” 결함 2건을 찾았을 때, 같은 질문을 다시 하고 있다는 걸 알았습니다. 통과는 증명이 아닙니다. 통과가 무엇을 검사했는지까지 봐야 증명입니다.

구현 전에 만든 체크리스트

이 종류의 누수는 하나가 아니라는 걸 알고 있었기 때문에, 가상 메모리 과제를 구현하기 전에 “종료 시 무엇을 안 치우면 무엇이 새는가”를 표로 먼저 만들었습니다. 당시 분석 노트에서 그대로 옮깁니다.

| 빠진 정리                    | 결과                                  |
|------------------------------|---------------------------------------|
| resident frame 해제          | user pool frame 누수                  |
| swapped-out anon slot free   | swap slot 누수                        |
| dirty mmap write-back        | 파일 수정 내용 손실                   |
| uninit lazy aux 해제         | file reference / aux metadata 누수    |
| SPT entry 제거               | 종료한 process 의 page metadata 잔류  |

정리 순서도 코드에 이유가 있습니다. supplemental_page_table_kill 이 pml4_destroy 보다 먼저 와야 합니다 — 페이지별 정리가 PTE 의 dirty bit 와 프레임 연결을 봐야 하는데, PML4 가 먼저 사라지면 판단 근거가 사라지기 때문입니다.

교육용 커널이라 여기서 끝나는 것

회수 경로는 process.c 의 reparent_or_reap_children 에, SPT 정리가 PML4 해제보다 먼저 오는 순서는 같은 파일의 process_cleanup 에 있습니다.

물론 교육용 커널의 단순한 프로세스 모델 위의 이야기입니다. 실제 OS 의 좀비 프로세스와 reparenting(예: PID 1 입양)은 시그널까지 얽힌 더 넓은 문제입니다.
