LLM fallback을 붙이기 전에 정할 것

Kyro의 규칙 엔진은 카탈로그에 적힌 징후와 판별 신호만 다룹니다. 그렇다면 규칙이 잡지 못한 장애에는 LLM을 붙이면 될까. 프로젝트 중에는 이 질문을 설계로 정리했지만, 현재 저장소에서 모델 호출부터 후보 제한·근거 재평가까지 이어지는 구현은 확인하지 못했습니다.

따라서 아래 내용은 완료 기능 설명이 아니라 다음 단계에서 지키려던 경계입니다.

모델에게 결론을 맡기지 않는다

로그 전체를 넣고 원인을 자유롭게 쓰게 하면 답이 매번 달라질 수 있고, 카탈로그에 없는 원인을 그럴듯하게 만들 수도 있습니다. 구현한다면 규칙 엔진이 먼저 판단하고, 근거가 부족해 보류한 경우에만 모델을 호출하는 순서를 생각했습니다.

여기서 LLM은 최종 판정자가 아니라 후보를 넓히는 역할입니다. 모델이 높은 confidence를 내더라도 수집된 증거로 다시 확인하지 못하면 보류해야 합니다.

구현 전에 필요한 계약

설계대로 붙이려면 적어도 다음 항목을 코드와 테스트로 고정해야 합니다.

  • 응답을 자유 서술이 아닌 구조화된 후보 목록으로 제한할 것
  • 카탈로그에 존재하는 candidate_id만 받을 것
  • 모델이 본 근거와 최종 판정에 사용한 근거를 구분해 남길 것
  • 민감한 로그 원문과 비밀 값이 외부 모델로 넘어가지 않게 할 것
  • timeout·재시도·비용을 기록하고, 모델 호출 실패 시 규칙 결과를 바꾸지 않을 것

읽기 전용 MCP로 카탈로그를 조회하게 하는 구상도 같은 단계의 설계안입니다. 현재 k8s-ops 코드에는 이 경계를 강제하는 LLM adapter·도구 정의·평가 결과가 없으므로 구현됐다고 쓰지 않습니다.

확인해야 할 평가

규칙 카탈로그에서 파생한 합성 회귀 입력 116개는 LLM 품질 평가가 아닙니다. fallback을 구현한다면 카탈로그 생성 경로와 분리된 표본으로 다음을 따로 확인해야 합니다.

  • 규칙이 보류한 사례에서 유효한 후보를 얼마나 제안하는지
  • 카탈로그 밖 ID와 근거 없는 후보를 모두 거절하는지
  • 여러 모델과 반복 호출에서도 채택 결과가 얼마나 일관적인지
  • 실제 로그의 민감 정보가 프롬프트와 기록에 남지 않는지

이 표본과 실행 결과가 생기기 전까지는 “환각을 막았다”거나 “LLM 판정 품질을 검증했다”고 말할 근거가 없습니다.
