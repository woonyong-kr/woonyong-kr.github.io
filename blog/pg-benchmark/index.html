PostgreSQL 비교로 찾은 범위 조회 병목

직접 만든 SQL 엔진이 얼마나 느린지 궁금했습니다. PostgreSQL 16 과 같은 워크로드로 붙여 봤습니다.

측정 조건을 먼저 못 박았습니다. 조건 없는 비교는 자랑도 반성도 못 됩니다.

단일 커넥션 · 순차 실행 · 같은 행 수 · 같은 질의 · 3회 반복 중앙값
MiniDB: -O2 빌드 (sanitizer 제거)
PostgreSQL: fsync=off 를 주 비교로 (MiniDB 는 WAL 이 없어 fsync=on 비교는 불공정)

비교 수치는 성과로 세지 않았다

10,000행 기준으로 INSERT 와 점 조회는 MiniDB 가 크게 앞섰습니다. 그런데 이건 빠른 게 아니라 안 하는 게 많은 겁니다. WAL 이 없어 커밋이 메모리 쓰기일 뿐이고, TCP 대신 인프로세스이며, MVCC 오버헤드가 없습니다. 그래서 이 항목들은 성과로 세지 않았습니다.

눈에 들어온 건 진 항목이었습니다.

Range 1,000행 조회 (10,000행 테이블)
MiniDB 2,026 ops/sec  <  PG(fsync=off) 2,077 ops/sec

왜 졌는가

EXPLAIN 과 페이지 읽기 계측으로 추적하니 원인이 명확했습니다. B+Tree 를 만들어 놓고 범위 조회에 안 쓰고 있었습니다. 실행기는 id = X 점 조회에만 인덱스를 타고, id >= a 는 힙을 처음부터 훑고 있었습니다.

id = 5000          → INDEX_LOOKUP, 페이지 3장, 0.04ms
id >= 5000 LIMIT 1000 → TABLE_SCAN, 페이지 36장, 3.89ms

더 나쁜 건 규모였습니다. 힙 스캔은 O(테이블 크기)라 100,000행에서는 630 ops/sec 까지 떨어졌습니다. 데이터가 클수록 격차가 벌어지는 구조적 약점입니다.

고쳤다

리프 형제 포인터는 이미 있었습니다. 자료 구조는 준비돼 있는데 실행기가 안 쓰던 것뿐입니다.

  • 파서에 BETWEEN a AND b 를 추가하고, id 의 부등호 조건을 범위 술어로 승격
  • 플래너에 인덱스 범위 경로를 추가
  • B+Tree 에 범위 스캔 구현: 하한 키 리프까지 O(log N) 하강 후 형제 포인터 순회

기존 동작이 깨지지 않았는지 세 겹으로 확인했습니다. 힙 스캔 결과와 바이트 단위 동일 검증, ASAN · UBSAN 빌드에서 런타임 오류 0, 점 조회 · INSERT · 전체 스캔 회귀 없음.

같은 MiniDB의 개선 전후를 다시 측정 

Range 조회 (ops/sec)          10,000행    100,000행
개선 전 (힙 스캔)               2,531        630
개선 후 (인덱스 범위 스캔)       3,374      3,292
PostgreSQL (fsync=off)          2,077      1,706

힙 스캔은 규모에 무너지고(2,531 → 630), 인덱스 스캔은 둔감합니다(3,374 → 3,292). O(log N + 반환행)이라는 교과서 문장이 숫자로 확인됐습니다. 100,000행에서 4배 넘게 지던 항목이 1.9배 우위로 뒤집혔습니다.

세 경로의 성격 차이를 1,000,000행까지 늘려 보면 이렇습니다.

Range ×100 (ops/sec)      10,000행    100,000행    1,000,000행
인덱스 범위 스캔             3,374        3,292        3,218    ← 거의 평평
PostgreSQL (fsync=off)      2,077        1,706        1,630
힙 스캔                     2,531          630         73.9    ← 규모에 붕괴

힙 스캔이 규모에 무너지는 동안 인덱스 스캔은 비교적 일정했습니다. 여기서 성과로 볼 수 있는 값은 PostgreSQL과의 순위가 아니라, 같은 MiniDB에서 실행 경로를 바꾸기 전후의 차이입니다.

규모를 키우니 다른 곳이 무너졌다

“시료가 작다”는 피드백으로 규모를 1,000,000행으로 올렸습니다. 같은 MiniDB·합성·단일 연결 조건에서 인덱스 범위 스캔은 3,218 ops/sec, 기존 heap scan은 73.9 ops/sec였습니다. 약 43.5배 차이입니다.

1,000,000행 Range ×100    인덱스 범위 스캔 3,218  >  PG(fsync=off) 1,630  >  힙 스캔 73.9

대신 이번엔 INSERT 가 144배 느려져 있었습니다. gdb 스택 샘플링으로 O(N²) 두 곳을 특정해 고친 그 기록은 따로 정리했습니다.

정직하게 셀 수 있는 성과

이 비교에서 말할 수 있는 것은 측정으로 약점을 찾고, 원인을 코드로 좁힌 뒤, 같은 MiniDB의 개선 전후를 다시 확인했다는 점입니다. PostgreSQL보다 빨랐던 항목은 WAL·MVCC·네트워크 비용을 지불하지 않은 결과라 성과로 사용하지 않습니다.

한계도 그대로 남습니다. WAL 이 없어 크래시하면 복구할 수 없고, 단일 커넥션 합성 워크로드이며, 1M 행(약 52MB)도 캐시에 다 올라가는 규모라 디스크가 병목인 비교는 아닙니다. 측정 조건과 전 과정은 저장소의 docs/benchmark-postgres.md 와 bench/ 스크립트로 재현할 수 있습니다.
