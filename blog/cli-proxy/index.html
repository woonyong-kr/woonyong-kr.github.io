655개 함수와 열 개 회사 사이

다누리 엔진은 extern "C" 로 655개 함수를 내보냈습니다. 콘텐츠를 만드는 협업사는 열 곳. 엔진은 완성품이 아니라 개발 중인 물건이라 인터페이스가 계속 바뀌었고, 열 곳이 각자 엔진을 고치기도 했습니다.

콘텐츠가 이 655개를 직접 부르면 어떻게 될까요. 엔진이 바뀔 때마다 열 곳의 콘텐츠가 제각각 깨집니다. 실제로 병합 때마다 깨졌습니다. 누구의 잘못도 아니고, 구조가 그렇게 생긴 겁니다.

경계를 두 겹으로

그래서 사이에 층을 세웠습니다.

C++ 엔진 (655개 extern "C")
   ↓
C++/CLI 프록시 (CLIInterface)     ← 네이티브를 관리 코드로 번역
   ↓
C# 프레임워크 (JEngine)           ← 콘텐츠가 실제로 만나는 API
   ↓
콘텐츠 (협업사 10곳)

핵심 규칙은 하나입니다. C++ 엔진을 직접 부르는 코드는 콘텐츠에 없다. 콘텐츠에는 네이티브 호출(DllImport)이 한 건도 없고, 엔진과는 관리되는 C# 표면 — 프록시가 내놓는 타입과 생명주기 · 코루틴 · 이벤트로 이뤄진 프레임워크 API — 로만 만납니다.

네이티브 함수의 서명이 바뀌면 흡수하는 곳은 프록시와 프레임워크입니다. 열 곳의 콘텐츠는 바뀐 것을 모릅니다. 인터페이스가 하나로 통일됐다는 말은 이 뜻입니다.

소스는 중앙에서

계층만으로는 부족했습니다. 열 곳이 각자 고친 엔진 소스가 흩어지면 어느 것이 진짜인지 사라집니다. 소스를 한곳으로 모으고 버전을 중앙에서 관리한 이야기는 따로 정리했습니다.

확인할 수 있는 것과 없는 것

C# 프레임워크는 dx_framework 에 공개돼 있습니다. 프록시의 C++/CLI 소스와 엔진 본체는 ㈜코드쓰리의 것이라 공개하지 않습니다 — 엔진과 렌더러를 제가 만들었다고 말하지 않는 이유이기도 합니다. 저장소에는 프록시를 감싸는 방식의 재구성 예시만 두었습니다.

이 구조는 이후에도 반복됐습니다. Kyro 에서 LLM 의 제안을 카탈로그 원인 ID 로 제한한 것도, 복구 권한을 Draft PR 하나로 모은 것도 — 바뀌는 것과 바뀌면 안 되는 것 사이에 경계를 세우는 같은 일이었습니다.
