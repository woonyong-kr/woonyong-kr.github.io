자동 복구가 클러스터를 직접 바꾸지 못하게 한 이유

2026-08-02 · 프로젝트 · GitOps · Kubernetes

자동 복구가 클러스터를 직접 바꾸지 못하게 한 이유

자동 복구에 클러스터 쓰기 권한을 주면 데모는 단순해집니다. 대신 잘못된 변경이 생겼을 때 답하기 어려운 질문이 남습니다.

  • 무엇을 바꿨는지 어떻게 재구성하나
  • 잘못 바꿨을 때 어디로 되돌리나
  • 왜 그렇게 고쳤는지 누가 설명하나

권한을 넓히는 대신 좁혔다

에이전트는 클러스터에 아무것도 쓰지 못합니다. 할 수 있는 일은 사람이 검토할 변경 제안을 만드는 것까지입니다.

판정 --> 수정안 생성 --> GitHub Draft PR   (자동 merge 경로 없음)
                              │
                        사람이 검토 · merge --> GitOps 가 배포 --> 배포 후 재확인

코드에서 허용한 전달 경로는 Draft PR 하나입니다. 제안 내용과 승인 여부를 Git 이력으로 추적하고, 실제 반영은 사람이 결정하게 하려는 경계입니다.

경계를 코드로 박은 곳 세 군데

바꿀 수 있는 것의 목록. 수정안은 배포 설정의 허용된 scalar 필드만 바꿉니다. 승인 원문에서 허용된 구간만 바꾸고 나머지 바이트는 그대로 보존합니다. YAML 을 자유롭게 고치는 경로 자체가 없습니다.

기준 커밋 재검증. PR 을 만들기 직전에 대상 브랜치의 최신 커밋을 다시 확인합니다. 수정안을 계산할 때의 커밋과 다르면, 그 사이 저장소가 움직인 것이므로 만들지 않고 멈춥니다. 낡은 전제 위의 변경이 올라가는 걸 막는 장치입니다.

계약 테스트. 허용하지 않은 action과 전달 방식을 거부하고, 기준 커밋이 달라졌을 때 중단하는 조건을 테스트로 남겼습니다.

확인할 수 있는 것

  • PR 생성과 기준 커밋 재검증: src/services/gitops/scm-worker/github_provider.py — 생성 요청에 "draft": True 를 싣고, 응답의 draft 가 참인지 한 번 더 확인합니다
  • 허용 필드 패치: src/domains/gitops/source_patch.py
  • 로컬 산출물: .gitops/safe-pr/의 복구 변경 문서에 승인 근거(approval_ref)·되돌리기 패치(rollback_patch)·패치 해시(patch_sha256)가 붙습니다

한계

여기까지 확인한 것은 저장소 코드·manifest·계약 테스트입니다. 실제 GitHub App과 외부 Kubernetes 클러스터를 연결해 PR 생성부터 merge·배포·복구 확인까지 수행한 E2E 결과는 없습니다. Draft PR은 사람이 merge해야 하므로 복구 속도도 사람의 응답에 영향을 받습니다.
