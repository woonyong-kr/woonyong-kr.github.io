장애 원인 판정을 YAML로 분리한 이유

장애 원인을 코드 안의 조건문으로만 관리하면 후보 하나를 추가할 때마다 엔진을 함께 고쳐야 하고, 어떤 증거를 보고 판단하는지도 구현을 읽어야 알 수 있습니다. Kyro는 판정 지식과 실행 로직을 분리해 원인 후보와 필요한 증거는 YAML 카탈로그에, 규칙을 적용하는 방법은 Python 엔진에 두었습니다.

규칙은 증거가 있을 때만 후보를 만든다

예를 들어 컨테이너가 메모리 부족으로 종료됐다는 후보는 OOMKilled, 종료 코드 137, 관련 로그처럼 구분 가능한 신호가 있어야 점수를 얻습니다. 증거 파일이 존재한다는 사실만으로는 후보를 확정하지 않으며, 필요한 신호가 없으면 판단을 보류합니다.

현재 카탈로그는 YAML 파일 15개, 룰북 29개, 원인 후보 참조 87개로 구성됩니다. 고유한 candidate_id도 87개라 룰북 사이에 중복 등록된 후보는 없습니다. 데이터 모델은 후보 재사용을 지원하지만 현재 카탈로그가 그렇게 구성돼 있다는 뜻은 아닙니다. 이 숫자는 Kubernetes의 전체 장애 유형이나 실제 운영에서 확인한 원인 수가 아니라, 프로젝트 저장소에 정의된 범위입니다.

image_pull_backoff 룰북을 보면 ImagePullBackOff와 ErrImagePull은 Kubernetes에서 관찰한 징후입니다. 이 룰북의 원인 후보 5개 중 missing_image_pull_secret은 이벤트 메시지에서 unauthorized, authentication required, pull access denied 같은 문구를 찾습니다. 여기서 unauthorized는 장애 종류가 아니라 판별에 쓰는 증거 문구입니다. YAML의 signals는 자동 matcher 입력이고, checks는 사람이 후보를 검토할 때 볼 확인 목록입니다.

116개 입력은 정확도 평가가 아니라 회귀 점검이다

evals/build_golden_set.py는 같은 카탈로그를 읽어 합성 입력 116개를 만듭니다. 후보마다 판별 신호를 하나 넣은 긍정 입력 87개와, 룰마다 판별 신호를 넣지 않은 입력 29개입니다. evals/run_eval.py는 이 입력을 규칙 엔진에 넣어 후보 연결과 근거가 없을 때의 보류 동작을 확인합니다.

입력과 기대 결과가 같은 카탈로그에서 나오므로 이 결과를 실제 장애 정확도로 해석할 수는 없습니다. 확인할 수 있는 것은 카탈로그를 수정했을 때 loader·schema·matcher 연결이 깨지지 않는지, 신호가 없는 입력을 잘못 확정하지 않는지입니다.

실제로 끝까지 확인한 범위

프로젝트에서 증거 수집부터 원인 판정과 변경 제안까지 한 흐름으로 확인한 사례는 ImagePullBackOff입니다. 합성 입력 116개와 원인 후보 87개를 이 범위보다 넓은 실환경 검증 근거로 사용하지 않습니다.

규칙이 후보를 만들지 못했을 때 LLM을 어디까지 사용할지는 LLM fallback을 붙이기 전에 정할 것에 별도로 정리했습니다.
