열 개 회사의 소스를 한곳으로

다누리 과제에는 협업사가 열 곳 있었고, 엔진은 완성품이 아니라 개발 중인 물건이었습니다. 열 곳이 각자 필요한 부분을 고쳤고, 고친 소스는 각자의 저장소에 남았습니다.

병합할 때마다 어딘가의 콘텐츠가 깨졌습니다. 누구의 잘못도 아닙니다. 어느 것이 진짜 엔진인지 아무도 말할 수 없는 구조가 문제였습니다.

기술이 아니라 합의가 먼저였다

중앙 관리는 기술적으로 어려운 일이 아닙니다. 어려운 건 열 곳이 “내 수정본을 포기하고 중앙본을 따른다”에 동의하는 것입니다.

  • 관리자를 한 명씩 설득했습니다. 전체 회의 한 번으로 되는 일이 아니었습니다
  • 실무자 핫라인을 열었습니다. 엔진에 필요한 수정 요청이 관리자 결재를 거치지 않고 바로 들어오게 — 중앙 관리가 병목이 되면 다시 각자 고치는 시대로 돌아갑니다
  • 엔진 버전을 단일화했습니다. 통합된 소스만이 배포되는 엔진이고, 여기에 C++/CLI 프록시와 C# 프레임워크 계층이 더해져 콘텐츠가 엔진 변경에서 분리됐습니다

통합하는 사람이 관리하는 사람이 됐다

소스가 한곳에 모이자, 통합을 담당하는 사람이 전체 상황을 가장 잘 아는 사람이 됐습니다. 그렇게 신입인데 PM 을 제안받았습니다.

이 경험의 요지는 도구가 아닙니다. 여러 주체가 각자의 기준으로 움직일 때, 기준을 하나로 모으는 절차를 만드는 것 — 이후 위캔버스에서 3개 팀의 완료 기준을 맞춘 것도, 크래프톤 정글에서 검증 시나리오 116개로 규칙 엔진의 기준을 세운 것도 같은 일이었습니다.

숫자로 남기지 못한 것

당시의 병합 실패 횟수나 통합 후 감소치 같은 지표는 기록으로 남기지 못했습니다. 남은 것은 통합된 소스, 그 위의 공개된 프레임워크 코드, 그리고 PM 이라는 결과입니다.
