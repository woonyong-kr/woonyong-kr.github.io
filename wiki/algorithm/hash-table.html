해시 테이블

해시 테이블

한 줄 요약: 해시 테이블은 키를 해시 함수로 배열 인덱스로 바꿔 한 번에 자리를 찾아가는 구조다. 서로 다른 키가 같은 칸을 가리키는 충돌은 체이닝이나 개방 주소법으로 처리하고, 칸이 차면 더 큰 배열로 재해싱한다.

검색을 계산으로 바꾸는 해시 테이블

전화번호부에서 “김우녕”의 번호를 찾는다고 하자. 명단이 정렬되어 있지 않으면 첫 사람부터 차례로 이름을 대조해야 한다. 1만 명이 있다면 최악의 경우 1만 번 비교한다. 이름순으로 정렬된 명단에서도 이진 탐색을 사용하면 약 14번은 확인해야 한다. 어느 방식이든 데이터가 늘어나면 찾는 비용도 늘어난다.

이번에는 “이름을 넣으면 그 사람이 앉을 좌석 번호가 즉시 나오는 규칙”이 있다고 생각해 보자. 이 규칙이 김우녕을 327번 좌석으로 바꾼다면 명단을 훑지 않고 그 자리로 곧장 갈 수 있다. 데이터가 1만 개든 100만 개든 비교 횟수는 사실상 한 번이다.

이처럼 이름을 좌석 번호로 바꾸는 규칙이 해시 함수(hash function)이고, 좌석이 늘어선 배열이 해시 테이블(hash table)이다. 해시 테이블은 데이터가 어디 있는지 차례로 찾는 대신, 데이터가 있어야 할 자리를 계산한다.

이 구조를 이해하면 다음 내용을 함께 설명할 수 있다.

  • 파이썬 dict, 자바 HashMap, C++ unordered_map이 평균 O(1)에 동작하는 방식
  • 서로 다른 두 키가 같은 자리를 가리키는 충돌과 그 해결 방법
  • 데이터베이스 인덱스가 어떤 경우에는 해시를 쓰고 어떤 경우에는 B+Tree를 쓰는 이유
  • 캐시, 중복 제거, 집합(set) 연산을 빠르게 구현하는 방식

아래에서는 키가 배열의 어느 칸으로 가는지 계산하고, 충돌이 났을 때 체이닝과 개방 주소법이 어떻게 다르게 동작하는지 살펴본다.

키에서 버킷까지: 해시 테이블의 동작 흐름

이름표로 사물함을 정하는 규칙

100개짜리 사물함에 물건을 맡길 때마다 “이름의 글자 코드를 모두 더한 뒤 100으로 나눈 나머지”에 해당하는 칸에 넣는다고 하자. “cat”은 c(99) + a(97) + t(116) = 312이고, 312 % 100 = 12이므로 12번 칸에 들어간다. 나중에 “cat”을 찾을 때도 같은 계산을 하면 12번이 나온다. 전체 사물함을 뒤질 필요가 없다.

하지만 “act”도 같은 글자로 이루어져 합이 312이므로 12번 칸을 가리킨다. 이처럼 서로 다른 키가 같은 칸을 가리키는 일을 충돌(collision)이라고 한다. 가능한 키는 무한하지만 칸은 유한하므로 충돌은 피할 수 없다. 따라서 해시 테이블은 충돌을 처리하는 규칙을 함께 갖춰야 한다.

해시 테이블을 이루는 세 요소

  • 해시 함수(hash function): 키를 받아 배열 인덱스를 계산한다. 보통 해시값 % 배열크기를 사용한다. 같은 키에는 항상 같은 인덱스를 내놓고, 서로 다른 키는 가능한 한 여러 인덱스에 고르게 흩어지게 하는 편이 좋다.
  • 버킷 배열(bucket array): 실제 값을 담는 칸의 배열이다. 각 칸을 버킷이라고 한다.
  • 충돌 해결(collision resolution): 두 키가 같은 칸을 가리킬 때 처리하는 규칙이다. 대표적으로 체이닝과 개방 주소법이 있다.

키를 넣고 찾는 과정

키 "cat"과 값 5를 크기가 8인 테이블에 넣는다고 하자.

  1. 해시 함수가 "cat"을 정수로 바꾼다. 예를 들어 hash("cat") = 312라고 하자.
  2. 배열 크기로 나눈 나머지로 인덱스를 정한다. 312 % 8 = 0이므로 0번 버킷을 선택한다.
  3. 0번 버킷에 ("cat", 5)를 저장한다.

찾을 때도 hash("cat") % 8 = 0을 계산해 0번 버킷을 확인한다. 넣을 때와 찾을 때 같은 계산을 사용하므로 같은 자리에 도달한다.

충돌 해결 1: 체이닝(separate chaining)

체이닝은 각 버킷에 값 하나만 두지 않고 연결 리스트를 둔다. 같은 버킷을 가리키는 키들은 그 버킷의 리스트에 이어 붙인다.

%% 체이닝 충돌 해결
flowchart LR
  table["인덱스 &#124; 버킷<br/>0 &#124; 연결 리스트<br/>1 &#124; 비어 있음<br/>2 &#124; 연결 리스트<br/>3 &#124; 연결 리스트"]
  cat["cat: 5"]
  act["act: 9"]
  dog["dog: 7"]
  bird["bird: 2"]
  fish["fish: 4"]
  table_b0_e["table:b0:e"]
  cat_w["cat:w"]
  cat_e["cat:e"]
  act_w["act:w"]
  table_b2_e["table:b2:e"]
  dog_w["dog:w"]
  table_b3_e["table:b3:e"]
  bird_w["bird:w"]
  bird_e["bird:e"]
  fish_w["fish:w"]
  table_b0_e --> cat_w
  cat_e --> act_w
  table_b2_e --> dog_w
  table_b3_e --> bird_w
  bird_e --> fish_w

값을 찾을 때는 해당 버킷의 리스트만 따라가며 키를 비교한다. 충돌이 적으면 리스트가 짧아서 빠르지만, 키가 한 버킷에 몰리면 리스트가 길어져 탐색도 느려진다.

충돌 해결 2: 개방 주소법(open addressing)

개방 주소법은 별도의 리스트를 두지 않는다. 키가 가리킨 칸이 이미 차 있으면 정해진 규칙에 따라 다른 빈 칸을 찾아 저장한다. 가장 단순한 선형 탐사(linear probing)는 한 칸씩 옆으로 이동하며 빈자리를 확인한다.

"cat" → 0번 시도 → 비어 있음 → 0번에 저장
"act" → 0번 시도 → 차 있음 → 1번 시도 → 비어 있음 → 1번에 저장

찾을 때도 0번부터 한 칸씩 이동한다. 키가 일치하는 칸을 만나면 값을 찾은 것이고, 빈 칸을 만나면 해당 키가 없다고 판단한다. 모든 값이 배열 안에 있어 메모리 지역성(locality)이 좋지만, 한 구역이 차기 시작하면 그 주변까지 연이어 차는 군집(clustering)이 생길 수 있다.

부하율과 재해싱

부하율(load factor) = 저장된 원소 수 / 버킷 수

부하율이 1에 가까워질수록 빈 칸이 줄고 충돌이 늘어나 평균 탐색 길이도 길어진다. 그래서 부하율이 임계값을 넘으면 더 큰 배열을 만들고 모든 원소의 자리를 다시 계산해 옮긴다. 체이닝에서는 보통 0.75, 개방 주소법에서는 0.5 안팎을 임계값으로 사용하며, 새 배열은 보통 기존 배열의 2배 크기로 만든다. 이 과정을 재해싱(rehashing)이라고 한다.

재해싱할 때 단순히 값을 같은 위치로 복사할 수는 없다. 인덱스를 해시값 % 배열크기로 계산하므로 배열 크기가 바뀌면 나머지도 달라지기 때문이다. 크기 8에서 312 % 8 = 0이었던 키는 크기 16에서 312 % 16 = 8이 되어 다른 버킷으로 이동한다.

모든 원소를 다시 배치하는 한 번의 재해싱에는 O(n)이 든다. 그러나 배열을 2배씩 늘릴 때 이 비용을 전체 삽입 횟수에 나누어 보면 삽입 한 번의 평균 비용은 O(1)로 유지된다. 이를 분할 상환(amortized)이라고 한다. 일부 삽입에서 큰 비용이 발생해도 여러 삽입에 걸친 평균 비용은 낮게 유지된다는 뜻이다.

실제 시스템의 해시 테이블

  • 파이썬 dict와 집합 set, 자바 HashMap, C++ unordered_map은 모두 해시 테이블이다. 자바 8 이후 HashMap은 한 버킷의 체인이 너무 길어지면 연결 리스트를 균형 트리로 바꿔 최악의 탐색 비용을 O(log n)으로 제한한다.
  • 해시 함수가 좋지 않거나 공격자가 같은 버킷에 몰리는 키를 의도적으로 보내면 모든 키가 한 리스트에 쌓여 O(n)으로 퇴화할 수 있다. 이를 해시 DoS라고 한다. 실무의 해시 함수가 실행마다 무작위 시드를 섞는 이유다.

구현으로 확인하는 해시 함수·체이닝·탐색

해시 함수: 문자열을 인덱스로 바꾸기(C)

h * 33 + 글자를 반복해 키의 모든 글자를 섞은 뒤, 배열 크기로 나눈 나머지를 인덱스로 사용한다. 마지막 % table_size에서 큰 해시값을 유한한 수의 인덱스로 줄이기 때문에 충돌이 생긴다. 해시값의 범위와 실제 배열 인덱스의 범위가 다르다는 점을 구분해야 한다.

체이닝으로 넣기: 버킷 리스트 앞에 연결하기(C)

먼저 키의 인덱스를 계산한 뒤 해당 버킷 리스트의 맨 앞에 새 노드를 연결한다. 리스트의 앞에 넣기 때문에 충돌이 나더라도 삽입 자체는 O(1)이다. 같은 인덱스를 받은 키들이 하나의 리스트에 쌓이는 체이닝 구조가 이 코드에 드러난다.

체이닝으로 찾기: 계산한 버킷만 순회하기(C)

검색할 때는 전체 테이블이 아니라 키가 속한 버킷 리스트만 순회한다. 리스트 길이는 부하율의 영향을 받으므로 부하율을 낮게 유지하면 평균적으로 1~2번의 비교로 끝나 O(1)에 가까워진다. 해시 계산은 확인할 범위를 하나의 버킷으로 좁히고, 마지막 키 비교는 원하는 키가 맞는지 판별한다.

flowchart TD
  key["key &quot;cat&quot;"]

  index["인덱스 0"]

  open_addressing["개방 주소법<br/>옆 빈 칸 탐사"]

  hash --> hash_value
  hash_value --> index
  index --> bucket
  bucket --> chaining
  bucket --> open_addressing
  bucket --> rehash

언제 해시 테이블을 선택하는가

해시 테이블은 검색을 순서대로 뒤지는 작업에서 위치를 계산하는 작업으로 바꾼다. 해시 함수로 키를 배열 인덱스에 대응시키므로 삽입·검색·삭제는 평균 O(1)에 동작한다. 다만 무한한 키를 유한한 칸으로 줄이는 % 배열크기 계산 때문에 충돌이 생긴다. 체이닝은 같은 버킷의 키를 연결 리스트에 모으고, 개방 주소법은 배열 안에서 다른 빈 칸을 찾는다. 부하율이 높아지면 더 큰 배열로 재해싱하며, 한 번의 재해싱은 O(n)이지만 분할 상환한 삽입 비용은 평균 O(1)이다.

키로 값을 빠르게 넣고 찾거나 지우는 일이 중요하고 순서가 필요 없다면 해시 테이블이 적합하다. 반면 “범위 검색(10 이상 50 이하)“이나 “정렬된 순회”가 필요하면 키를 흩어 놓는 해시 테이블은 적합하지 않다. 이런 경우에는 순서를 유지하는 B+Tree가 더 알맞다. 평균 성능은 O(1)이지만 해시 함수가 좋지 않거나 부하율을 관리하지 않으면 최악에는 O(n)으로 느려질 수 있다. 해시 테이블은 순서를 유지하지 않는 대신 키의 위치를 빠르게 계산하는 자료구조다.
