MCP — 모델 컨텍스트 프로토콜 (Model Context Protocol)

MCP — 모델 컨텍스트 프로토콜 (Model Context Protocol)

확인 범위: 이 문서는 MCP의 역할과 구조, 기능, 통신 흐름 및 RAG·Function Calling과의 관계를 설명하는 개념 중심의 입문 자료이며, 포함된 FastMCP 코드는 동작 방식을 보여 주는 예시다. 실제 구현의 호환성·동작 여부나 전송 방식 선택은 사용 중인 코드와 버전을 확인하고 실행 기록 및 필요한 성능 측정을 통해 별도로 검증해야 한다.

한 줄 요약: MCP는 LLM 애플리케이션이 외부 도구·데이터 소스에 접근하는 방식을 표준화한 개방형 프로토콜이다.

MCP 구분

LLM은 텍스트를 생성할 수 있지만, 혼자서는 파일을 읽거나, DB를 조회하거나, API를 호출할 수 없다. 이 한계를 넘기 위해 “도구 사용(tool use)” 기능이 등장했다. 그런데 문제가 있다.

도구마다 연결 방식이 다르다. Slack API는 REST, 파일 시스템은 로컬 함수 호출, DB는 SQL 드라이버를 쓴다. LLM 앱이 도구 10개를 지원하려면 10가지 연동 코드를 각각 작성해야 한다. 도구 제공자도 LLM 앱마다 다른 인터페이스를 맞춰야 한다.

이 상황은 USB 이전의 주변기기 시장과 같다. 프린터는 병렬 포트, 마우스는 PS/2, 모뎀은 시리얼 포트를 썼다. USB가 등장하자 하나의 규격으로 모든 장치를 연결할 수 있게 되었다.

MCP는 LLM 생태계의 USB다. LLM 앱(호스트)과 외부 도구(서버) 사이의 통신 방식을 하나의 프로토콜로 통일한다. Anthropic이 2024년 11월에 공개했다.

MCP 구조

비유: 번역기가 있는 회의실

LLM을 회의 참석자, 외부 도구를 각국 대사관이라고 하자. 대사관마다 다른 언어를 쓰면 참석자는 각 언어를 모두 배워야 한다. MCP는 회의실에 배치된 표준 번역기다. 모든 대사관이 번역기의 규격에 맞춰 메시지를 보내면, 참석자는 번역기 하나만 이해하면 된다.

3계층 아키텍처: Host → Client → Server

MCP는 세 개의 역할을 정의한다.

  1. Host: LLM 애플리케이션 자체. Claude Desktop, IDE 플러그인, 커스텀 챗봇 등이 해당한다. 사용자와 직접 상호작용하는 계층이다.
  2. Client: Host 안에서 동작하는 프로토콜 커넥터. Server 하나당 Client 하나가 1:1로 연결된다. JSON-RPC 메시지를 주고받는 역할이다.
  3. Server: 외부 도구·데이터를 노출하는 경량 프로세스. 파일 시스템, DB, Slack, GitHub 등 각각이 하나의 Server가 된다.
  • Host (호스트)
  • Claude Desktop, IDE 등
  • Client A | | Client B | …
  • JSON-RPC | JSON-RPC
  • Server A | | Server B
  • 파일시스템 | | Slack

Host 하나가 여러 Client를 가질 수 있고, 각 Client는 하나의 Server와 통신한다. Server끼리는 직접 통신하지 않는다.

Server가 노출하는 세 가지 기능

MCP Server는 세 종류의 기능을 LLM에 제공한다.

  1. Tools (도구): LLM이 호출할 수 있는 함수. 파일 읽기, DB 쿼리 실행, API 호출 등 부수 효과가 있는 동작이다. LLM이 “이 함수를 실행해 달라”고 요청하면 Server가 실행하고 결과를 돌려준다.
  2. Resources (리소스): LLM이 읽을 수 있는 데이터. 파일 내용, DB 스키마, 설정 값 등이다. REST API의 GET 엔드포인트와 비슷하다. 읽기 전용이며 부수 효과가 없다.
  3. Prompts (프롬프트): 미리 정의된 프롬프트 템플릿. “코드 리뷰해 줘”, “이 파일 요약해 줘”처럼 자주 쓰는 작업 패턴을 Server가 제공한다.

통신 프로토콜: JSON-RPC 2.0

Client와 Server는 JSON-RPC 2.0 메시지를 주고받는다. 전송 계층은 두 가지를 지원한다.

  • stdio: Server를 자식 프로세스로 실행하고 표준 입출력으로 통신. 로컬 도구에 적합하다.
  • HTTP + SSE (Server-Sent Events): 원격 서버와 통신. 서버가 이벤트를 푸시할 수 있다.

메시지 흐름은 다음과 같다.

  • Client Server
  • initialize (요청)
  • →
  • initialize (응답: 지원 기능)
  • ←
  • initialized (알림)
  • →
  • tools/list (요청)
  • →
  • tools/list (응답: 도구 목록)
  • ←
  • tools/call (요청: 함수 실행)
  • →
  • tools/call (응답: 실행 결과)
  • ←

초기화 단계에서 서로의 프로토콜 버전과 지원 기능(capabilities)을 교환한다. 이후 Client가 필요할 때 도구 목록을 조회하고, LLM이 선택한 도구를 호출한다.

RAG와의 관계

RAG는 “검색한 문서를 프롬프트에 넣는다”는 패턴이다. MCP는 “도구와 데이터를 표준 방식으로 연결한다”는 프로토콜이다. RAG 파이프라인의 검색 단계를 MCP Server로 구현할 수 있다. 벡터 DB 검색을 MCP 도구로 노출하면, LLM이 필요할 때 직접 검색을 요청하는 구조가 된다.

Function Calling과의 차이

LLM API의 Function Calling(도구 사용)은 LLM이 “이 함수를 호출하고 싶다”는 의사를 표현하는 방식이다. MCP는 그 함수가 실제로 어디에 있고, 어떻게 호출하고, 결과를 어떻게 돌려받는지를 정의하는 프로토콜이다. Function Calling이 주문서라면, MCP는 주문서를 주방(서버)에 전달하는 배달 시스템이다.

정리

MCP는 LLM 앱과 외부 도구 사이의 통신을 표준화한 프로토콜이다. Host-Client-Server 3계층 구조로 동작하며, JSON-RPC 2.0 메시지를 주고받는다. Server는 Tools, Resources, Prompts 세 가지 기능을 노출한다. 하나의 프로토콜로 파일, DB, API 등 모든 외부 시스템을 연결할 수 있어서, LLM 생태계의 USB 역할을 한다.
