Prefill과 Decode 단계

Prefill과 Decode 단계

범위: 이 문서는 Prefill과 Decode의 일반적인 개념, 연산 특성 및 스케줄링 선택 기준을 설명하며, 코드와 연산량 계산은 본문에 제시된 예제 구조와 GPT_CONFIG_SMALL 설정에 한정된다. 특정 추론 엔진·버전의 실제 동작, compute-bound·memory-bound 여부, 지연 시간과 처리량 개선 정도를 판단하려면 해당 구현의 코드와 실행 기록, 하드웨어별 성능 측정이 별도로 필요하다.

한 줄 요약: LLM 추론은 프롬프트를 한 번에 처리하는 Prefill 단계와 토큰을 하나씩 생성하는 Decode 단계로 나뉘며, 각 단계의 병목이 다르다.

Prefill과 Decode 단계 필요성

LLM에 “서울의 인구는?”이라고 질문하면, 모델은 이 프롬프트를 읽고 “약 950만 명이다”라는 답을 한 토큰씩 생성한다. 이 과정은 내부적으로 두 단계로 나뉜다.

프롬프트를 읽는 단계와 답을 생성하는 단계는 연산 특성이 완전히 다르다. 프롬프트는 토큰 여러 개를 한 번에 병렬 처리할 수 있지만, 생성은 이전 토큰의 결과가 있어야 다음 토큰을 만들 수 있으므로 순차적이다. 이 차이를 무시하면 GPU 활용률이 낮아지고, 서빙 시스템의 처리량이 떨어진다.

Prefill과 Decode 단계 차이

Prefill 단계 — 프롬프트를 한 번에 처리한다

사용자가 보낸 프롬프트의 모든 토큰을 한 번에 Transformer에 통과시키는 단계다.

동작 순서:

  1. 프롬프트 토큰 전체를 임베딩한다. shape: (1, prompt_len, d_model).
  2. 각 Transformer 블록에서 모든 토큰의 Q, K, V를 동시에 계산한다.
  3. Causal mask를 적용해 attention score를 구한다.
  4. 각 블록의 K, V를 KV Cache에 저장한다.
  5. 마지막 토큰 위치의 logits로 첫 번째 생성 토큰을 뽑는다.

이 단계는 행렬 곱이 크다. prompt_len개 토큰 전체에 대해 (prompt_len, d_model) @ (d_model, d_model) 연산이 각 블록마다 Q, K, V, Output 네 번 일어난다. GPU의 연산 유닛을 꽉 채울 수 있으므로 compute-bound(연산 병목)다.

Decode 단계 — 토큰을 하나씩 생성한다

Prefill이 끝나면 KV Cache가 채워진 상태에서 토큰을 하나씩 이어 붙이는 단계다.

동작 순서:

  1. 직전에 생성한 토큰 하나를 임베딩한다. shape: (1, 1, d_model).
  2. 새 토큰의 Q, K, V를 계산한다. shape: 모두 (1, 1, d_model).
  3. 새 K, V를 KV Cache 뒤에 붙인다.
  4. 새 토큰의 Q와 캐시 전체의 K로 attention score를 구한다.
  5. 캐시의 V를 가중합해서 출력을 만든다.
  6. logits에서 다음 토큰을 샘플링한다.
  7. EOS가 나오거나 최대 길이에 도달할 때까지 1~6을 반복한다.

이 단계는 행렬 곱이 작다. Q projection은 (1, d_model) @ (d_model, d_model)이고 attention은 (1, d_model) @ (seq_len, d_model).T다. GPU 연산 유닛 대부분이 놀고, 대신 KV Cache를 메모리에서 읽어오는 시간이 지배적이므로 memory-bound(메모리 대역폭 병목)다.

Prefill과 Decode 단계 코드

책의 generate 함수 구조

이 코드는 KV Cache가 없다. 매 스텝마다 idx_cond 전체를 forward하므로 시퀀스가 길어질수록 중복 계산이 늘어난다. train.py의 generate() 함수는 temperature와 top-k 샘플링을 추가한 확장판이지만 같은 구조다.

KV Cache가 있는 추론 엔진의 흐름

Prefill에서 model.forward는 (1, prompt_len) 입력을 받아 (prompt_len, d_model) 크기의 K, V를 각 layer마다 캐시에 저장한다. Decode에서는 (1, 1) 입력만 넣고, attention 계산 시 캐시에서 과거 K, V를 읽어 사용한다.

연산량 비교 — 구체적 숫자

책의 테스트 설정(GPT_CONFIG_SMALL)을 기준으로 각 단계의 연산 규모를 비교한다.

설정: emb_dim=64, n_heads=4, n_layers=2, context_length=64

Prefill (prompt_len = 50 토큰):

  • Q projection: (50, 64) @ (64, 64) = 50 × 64 × 64 = 204,800 곱셈
  • K, V도 같은 크기 → Q+K+V = 614,400 곱셈
  • Attention score: (50, 64) @ (64, 50) = 50 × 64 × 50 = 160,000 곱셈
  • 이것이 layer 2개, head 4개 → 전체 약 620만 곱셈

Decode (1 토큰, 캐시에 50개 저장):

  • Q projection: (1, 64) @ (64, 64) = 4,096 곱셈
  • K, V projection: 같은 크기 → Q+K+V = 12,288 곱셈
  • Attention score: (1, 64) @ (64, 50) = 3,200 곱셈
  • layer 2개, head 4개 → 전체 약 12만 곱셈

Prefill은 Decode보다 약 50배 많은 연산을 하지만, GPU는 큰 행렬곱에서 효율이 높으므로 실제 시간은 50배 차이가 나지 않는다. 반면 Decode는 연산량이 작아 GPU 연산 유닛이 대부분 놀고, KV Cache를 메모리에서 읽는 대역폭이 병목이 된다.

왜 서빙 시스템은 두 단계를 따로 스케줄링하는가

Prefill과 Decode의 병목이 다르기 때문에, 서빙 엔진(vLLM, TensorRT-LLM 등)은 두 단계를 별도로 스케줄링한다.

  • Prefill 요청이 들어오면 GPU 연산을 집중 투입한다.
  • Decode 중인 요청은 메모리 대역폭만 쓰므로 여러 요청을 묶어 배칭한다.
  • Prefill과 Decode를 같은 배치에 섞으면 Prefill의 큰 행렬곱이 Decode 요청의 지연을 늘린다. 이를 interference(간섭)라 한다.

이 분리가 연속 배칭(continuous batching)과 함께 LLM 서빙 처리량을 크게 높이는 핵심이다.

정리

  • Prefill은 프롬프트 전체를 병렬로 처리하고 KV Cache를 채운다. compute-bound다.
  • Decode는 토큰 하나씩 생성하며 KV Cache를 읽는다. memory-bound다.
  • 책의 generate() 함수는 KV Cache 없이 매번 전체를 forward하므로 두 단계가 구분되지 않는다. 실제 추론 엔진은 이를 분리해 효율을 높인다.
  • 연결 문서: KV 캐시 메모리 계산, 연속 배칭
