페이지드 어텐션

페이지드 어텐션

확인 범위: 이 문서는 페이지드 어텐션의 일반 원리와 블록 크기 등 설계 선택의 기준을 설명하며, 제시된 코드는 특정 구현을 재현하거나 검증한 결과가 아닌 단순화된 개념 예시다. 실제 메모리 절감률과 동시 처리량, 커널 효율은 구체적인 구현·버전·실행 환경에서 코드와 실행 기록 및 성능 측정으로 별도 검증해야 한다.

한 줄 요약: 페이지드 어텐션은 KV 캐시를 고정 크기 블록으로 쪼개고, OS의 가상 메모리 페이징처럼 논리 블록과 물리 블록을 분리해 GPU 메모리 낭비를 줄이는 기법이다.

페이지드 어텐션 필요성

KV 캐시 메모리 계산에서 KV 캐시가 GPU 메모리의 주요 병목임을 봤다. 문제는 캐시의 할당 방식에 있다.

기존 서빙 시스템은 요청이 들어오면 그 요청의 최대 시퀀스 길이만큼 연속된 GPU 메모리를 미리 할당한다. 예를 들어 최대 길이가 2048 토큰이면 2048 토큰분의 KV 캐시 공간을 한 번에 잡는다. 실제로 생성되는 토큰이 100개뿐이어도 나머지 1948 토큰분은 비어 있다. 이것이 내부 단편화다.

여러 요청을 동시에 처리하면 각 요청의 연속 블록 사이에 빈 공간이 생긴다. 전체 GPU 메모리에 여유가 있어도 연속된 공간이 없어 새 요청을 받지 못한다. 이것이 외부 단편화다.

메모리 단편화에서 본 문제가 GPU 메모리에서 그대로 반복된다. OS는 가상 메모리 페이징으로 이 문제를 해결했다. 페이지드 어텐션은 같은 해법을 KV 캐시에 적용한다.

페이지드 어텐션 흐름

OS 페이징과의 대응

OS의 가상 메모리가 물리 메모리를 고정 크기 페이지(보통 4KB)로 나누듯, 페이지드 어텐션은 KV 캐시를 고정 크기 블록(보통 16토큰)으로 나눈다.

대응 관계:

  • OS 가상 페이지 → KV 캐시 논리 블록 (시퀀스 내 블록 번호)
  • OS 물리 프레임 → KV 캐시 물리 블록 (GPU 메모리 내 실제 위치)
  • OS 페이지 테이블 → 블록 테이블 (논리 블록 → 물리 블록 매핑)
  • OS 요구 페이징 → 토큰 생성 시점에 블록 할당

블록 단위 KV 캐시

기존 방식은 한 요청의 KV 캐시를 하나의 연속된 텐서로 할당한다. 페이지드 어텐션은 이를 블록 단위로 쪼갠다.

블록 크기가 4토큰이고, 한 요청이 현재 10토큰을 생성했다면:

%% 블록 테이블 매핑
flowchart LR
  logical0["논리 블록 0<br/>토큰 0~3의 K, V"]
  logical1["논리 블록 1<br/>토큰 4~7의 K, V"]
  logical2["논리 블록 2<br/>토큰 8~9의 K, V<br/>슬롯 2개 남음"]
  physical7["물리 블록 7<br/>GPU 메모리 실제 위치"]
  physical2["물리 블록 2<br/>GPU 메모리 실제 위치"]
  physical15["물리 블록 15<br/>GPU 메모리 실제 위치"]
  logical0 -->|매핑| physical7
  logical1 -->|매핑| physical2
  logical2 -->|매핑| physical15

물리 블록 7, 2, 15는 GPU 메모리에서 연속일 필요가 없다. 떨어진 위치에 있어도 블록 테이블이 매핑을 관리한다.

단편화 해결

%% 단편화 비교
flowchart TD
  legacy["기존 연속 할당 방식<br/>요청A [사용 10칸][내부 낭비 6칸] 요청B [사용 4칸][낭비 4칸]<br/>외부 단편화: 사이에 빈 공간이 있어도<br/>연속 공간이 아니면 새 요청 할당 불가"]
  paged["페이지드 어텐션 방식<br/>물리 블록: [A0] [B1] [A2] [빈] [B0] [A1] [빈] [빈]<br/>요청A 블록 테이블: 0→0, 1→5, 2→2<br/>요청B 블록 테이블: 0→4, 1→1<br/>내부 단편화: 마지막 블록만 (최대 block_size-1)<br/>외부 단편화: 없음 (비연속 할당)"]
  result["빈 블록은 위치와 무관하게 재사용<br/>새 요청은 연속 GPU 메모리를 요구하지 않음"]
  legacy -->|KV 캐시를 고정 크기 블록으로 분리| paged
  paged -->|논리 블록 → 물리 블록 매핑| result

내부 단편화는 각 요청의 마지막 블록에서만 발생한다. 블록 크기가 16토큰이면 최대 15토큰분만 낭비된다. 외부 단편화는 원리적으로 발생하지 않는다. 빈 블록이 어디에 있든 새 요청에 할당할 수 있다.

vLLM 논문에 따르면, 기존 시스템 대비 메모리 낭비를 6080% 줄인다. 같은 GPU 메모리로 24배 많은 요청을 동시에 처리할 수 있다.

어텐션 커널의 변경

KV 캐시가 비연속적이므로, attention 계산 시 블록 테이블을 참조해 물리 블록을 모아야 한다. 기존 attention 커널은 연속 메모리를 전제하므로 그대로 쓸 수 없다.

페이지드 어텐션 커널의 동작:

  1. 새 토큰의 Q를 계산한다.
  2. 블록 테이블에서 이 요청의 물리 블록 목록을 읽는다.
  3. 각 물리 블록의 K를 가져와 Q와 내적한다.
  4. softmax로 attention weight를 구한다.
  5. 각 물리 블록의 V를 가중합한다.

블록 단위로 K, V를 읽으므로 메모리 접근 패턴이 달라진다. GPU 메모리 대역폭을 효율적으로 쓰기 위해 블록 크기와 warp 크기를 맞추는 커널 최적화가 필요하다.

페이지드 어텐션 텐서 코드

책의 baseline — 연속 메모리 기반 generate

이 코드는 KV 캐시 자체가 없다. 매 스텝마다 전체 시퀀스를 다시 계산한다. 캐시가 있더라도 하나의 연속 텐서로 할당하는 것이 기본이다. 페이지드 어텐션은 이 연속 텐서를 블록으로 쪼갠다.

페이지드 어텐션 개념 코드 — 블록 테이블과 할당

블록 할당기는 OS의 물리 프레임 할당기와 같은 역할이다. 빈 블록 목록에서 하나를 꺼내 요청에 할당하고, 요청이 끝나면 반납한다.

블록 테이블 기반 KV 캐시 쓰기

토큰이 생성될 때마다 현재 블록에 빈 슬롯이 있으면 그 자리에 쓰고, 블록이 꽉 차면 새 블록을 할당한다. OS의 요구 페이징(demand paging)과 같은 원리다.

수치 예시 — 메모리 절약 효과

설정: max_seq_len=2048, block_size=16, d_model=4096, fp16 (2바이트)
요청 수: 10개, 실제 생성 길이: 각각 [50, 120, 30, 200, 80, 45, 150, 60, 90, 110]

기존 연속 할당:
  요청당 KV 메모리 = 2 × 2048 × 4096 × 2 = 33,554,432 바이트 = 32 MB
  10개 요청 총 = 320 MB

페이지드 어텐션:
  요청별 블록 수 = ceil(실제 길이 / 16)
  [4, 8, 2, 13, 5, 3, 10, 4, 6, 7] = 총 62 블록
  블록당 메모리 = 2 × 16 × 4096 × 2 = 262,144 바이트 = 256 KB
  총 = 62 × 256 KB = 15.5 MB + 마지막 블록 내부 단편화

절약: 320 MB → 약 16 MB (95% 절약)

실제 생성 길이가 최대 길이보다 훨씬 짧을 때 절약 효과가 극대화된다.

정리

페이지드 어텐션은 KV 캐시의 메모리 관리 문제를 OS 가상 메모리의 페이징 기법으로 해결한다. 연속 할당 대신 고정 크기 블록 단위로 캐시를 쪼개고, 블록 테이블로 논리-물리 매핑을 관리한다. 내부 단편화는 마지막 블록에서만 발생하고, 외부 단편화는 원리적으로 없다. 같은 GPU 메모리로 2~4배 많은 요청을 동시에 처리할 수 있다.
