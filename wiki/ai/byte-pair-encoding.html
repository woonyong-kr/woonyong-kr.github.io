바이트 페어 인코딩

한 줄 요약: BPE는 가장 자주 붙어 나오는 인접 쌍을 새 토큰으로 합치는 압축 알고리즘이다. 바이트(0~255)에서 출발하면 어떤 문자도 UNK 없이 표현되고, 병합과 복원이 결정적으로 맞물린다.

토크나이저와 BPE가 토크나이저 전체 흐름(왜 토큰화하는가, train, encode, tiktoken)을 다룬다면, 이 문서는 BPE 알고리즘 자체의 내부 동작에 집중한다. 즉 “왜 바이트에서 시작하는가”, “어떤 쌍을 먼저 병합할지 어떻게 결정하는가”, “병합된 토큰을 어떻게 다시 원문으로 복원하는가”를 코드 수준으로 본다.

바이트 페어 인코딩 구분

서브워드 토크나이저는 어휘를 만드는 방법이 필요하다. 사람이 “the”, “ing” 같은 토큰을 손으로 정하면 언어마다 새로 만들어야 하고, 학습 코퍼스의 통계도 반영하지 못한다.

문자 단위에서 출발하면 또 다른 문제가 생긴다. 유니코드 문자는 14만 자가 넘는다. 초기 어휘를 문자로 잡으면 학습에서 한 번도 본 적 없는 문자(이모지, 희귀 한자)가 입력으로 들어왔을 때 처리할 토큰이 없다. 이것이 OOV(Out-Of-Vocabulary) 문제다.

BPE는 두 문제를 동시에 푼다.

  • 병합 규칙을 코퍼스 빈도로 자동 학습한다. 사람이 어휘를 정하지 않는다.
  • 바이트(0~255)에서 출발한다. 모든 텍스트는 UTF-8로 인코딩하면 바이트 열이 되므로, 256개 바이트 토큰만 있으면 어떤 입력도 UNK 없이 표현된다.

바이트 레벨 BPE는 GPT-2부터 GPT-4까지 GPT 계열이 공통으로 쓰는 방식이다.

바이트 페어 인코딩 흐름

BPE는 데이터 압축 기법에서 왔다. 원리는 “가장 흔한 인접 쌍을 새 기호로 치환”이다. aaabdaaabac에서 aa가 가장 흔하면 Z=aa로 묶어 ZabdZabac로 줄인다. 토크나이저 BPE는 이 치환을 어휘 크기에 도달할 때까지 반복하고, 치환 순서(merge rule)를 저장한다.

토큰 ID 레이아웃 — 왜 바이트가 4번부터 시작하는가

밑바닥 LLM 책의 BPETokenizer는 ID 공간을 세 구역으로 나눈다.

  • 0~3: 특수 토큰 (<pad>, <unk>, <bos>, <eos>)
  • 4~259: 원본 UTF-8 바이트 256개 (BYTE_OFFSET = 4만큼 밀려 있음)
  • 260~: BPE 병합으로 새로 생긴 토큰
%% BPE 토큰 ID 공간
flowchart LR
  special["0..3<br/>특수 토큰<br/>&lt;pad&gt;"]
  bytes["4..259<br/>UTF-8 바이트 256개<br/>BYTE_OFFSET = 4<br/>OOV 방지 기본 어휘"]
  merge["260..vocab_size<br/>BPE merge 토큰<br/>학습 중 새로 생성<br/>merge rule 순서 저장"]
  special --> bytes
  bytes --> merge

바이트 구간이 항상 통째로 들어있는 것이 핵심이다. 어떤 문자열이 들어와도 최악의 경우 바이트 단위로는 반드시 표현되므로, UNK로 떨어지는 입력이 원리적으로 없다.

어떤 쌍을 먼저 병합하는가 — 결정성이 중요한 이유

가장 자주 나온 쌍을 고른다는 규칙만으로는 부족하다. 빈도가 같은 쌍이 여러 개면 어느 것을 먼저 합칠지 모호해진다. train과 encode가 같은 순서를 보장하려면 동점 처리(tie-break)가 결정적이어야 한다.

책은 세 단계로 순서를 못 박는다.

  1. 빈도가 높은 쌍 우선 (-counts[pair])
  2. 빈도가 같으면 코퍼스에 먼저 등장한 쌍 우선 (first_seen[pair])
  3. 그것도 같으면 토큰 ID가 작은 쌍 우선 (pair[0], pair[1])

이 순서가 고정되어야 train에서 만든 병합 순서와 encode에서 적용하는 순서가 정확히 일치한다. 순서가 흔들리면 같은 텍스트가 다른 토큰열로 인코딩된다.

복원(decode)은 왜 한 번에 모아서 디코딩하는가

병합 토큰은 내부에 “어떤 두 토큰을 합쳤는지”를 튜플로 기억한다. 복원은 이 튜플을 바이트가 나올 때까지 재귀로 펼친다. 펼친 바이트를 하나씩 decode하면 안 된다. 한글 “가”는 3바이트인데, 바이트를 하나씩 디코딩하면 깨진다. 바이트를 전부 모은 뒤 bytes(...).decode("utf-8")를 한 번만 호출해야 멀티바이트 문자가 온전히 복원된다.

바이트 페어 인코딩 코드

초기화 — 바이트 어휘 깔기

학습 전에도 어휘에는 항상 특수 토큰 4개와 바이트 256개가 깔려 있다. 이 256개가 OOV를 막는 안전망이다.

병합할 쌍 선택 — 결정적 동점 처리

min 키의 튜플이 동점 처리 규칙 전체다. 빈도가 같아도 항상 같은 쌍을 고르므로 train/encode 일관성이 보장된다.

쌍을 바이트로 펼치기 (복원)

병합 토큰 (105, 260)은 좌·우를 재귀로 펼쳐 결국 바이트 값들로 환원된다. decode()는 이렇게 모은 바이트를 한 번에 bytes(...).decode("utf-8")로 문자열로 만든다.

숫자로 따라가기 — “aaab”

min_frequency=1, 입력 "aaab"를 학습한다고 하자. a=97, b=98이므로 BYTE_OFFSET(4) 적용 시 a=101, b=102이다.

%% BPE aaab 병합과 복원 흐름
flowchart TD
  input["1. 초기 시퀀스<br/>&quot;aaab&quot;<br/>UTF-8 byte: [97, 97, 97, 98]<br/>offset 적용: [101, 101, 101, 102]"]
  first_pair["2. 첫 병합 쌍 선택<br/>(101, 101)<br/>new_id = 260"]
  first_merge["3. 왼쪽부터 겹침 없이 치환<br/>[260, 101, 102]"]
  second_pair["4. 동점 처리<br/>(260, 101)"]
  second_merge["5. 두 번째 병합<br/>new_id = 261<br/>[261, 102]"]
  decode["6. decode<br/>261 = (260, 101)<br/>260 = (101, 101)<br/>offset 제거 → [97, 97, 97, 98] → &quot;aaab&quot;"]
  input --> first_pair
  first_pair --> first_merge
  first_merge --> second_pair
  second_pair --> second_merge
  second_merge --> decode

병합은 “왼쪽부터 겹치지 않게” 적용되므로 aaa가 aa+a로 갈라지는 점에 주의한다. 같은 merge 순서를 encode에서 그대로 재생하면 동일한 토큰열이 나온다.

시퀀스 길이 변화 한눈에 보기

위 그림에서 encode 쪽은 [101,101,101,102]에서 [260,101,102], 다시 [261,102]로 줄어든다. decode 쪽은 261을 (260,101), (101,101)+101 순서로 펼친 뒤 102와 합쳐 원래 바이트열 [97,97,97,98]을 되찾는다.

정리

BPE는 최빈 인접 쌍을 새 토큰으로 병합하는 과정을 어휘 크기까지 반복하고, 그 순서를 merge rule로 저장하는 알고리즘이다. 바이트(0~255)에서 출발하므로 어떤 입력도 UNK 없이 표현되고, 동점 처리를 결정적으로 고정해 train과 encode의 결과를 일치시킨다. 복원은 병합 토큰을 바이트까지 재귀로 펼친 뒤 한 번에 UTF-8 디코딩한다.
