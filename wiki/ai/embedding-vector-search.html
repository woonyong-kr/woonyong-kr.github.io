임베딩 벡터 검색 (Embedding Vector Search)

임베딩 벡터 검색 (Embedding Vector Search)

한 줄 요약: 임베딩 벡터 검색은 질문과 문서를 같은 벡터 공간에 놓고, 방향이 가까운 문서 조각을 찾아 RAG의 근거로 쓰는 방법이다.

키워드 검색과 임베딩 검색의 차이

키워드 검색은 질문과 문서에 정확히 겹치는 단어가 있을 때 강하다. 사용자가 “비밀번호 초기화”라고 물었는데 문서에는 “계정 복구”라고 적혀 있으면 놓칠 수 있다. 두 표현의 의미는 비슷하지만 사용한 단어가 다르기 때문이다.

임베딩 검색은 텍스트를 숫자 벡터로 바꾼 뒤 벡터 사이의 가까움을 비교한다. 이때 사용하는 embedding model은 의미가 비슷한 문장의 벡터 방향이 가까워지도록 학습된 모델이다. 따라서 단어가 달라도 벡터가 가까우면 검색 결과에 포함될 수 있다. 다만 여기서 벡터의 가까움은 모델이 계산한 similarity score이며, 두 문장의 의미가 실제로 같다는 검증 결과를 뜻하지는 않는다.

검색을 구성하는 요소

embedding model은 텍스트를 고정 길이 벡터로 바꾼다. 질문과 문서를 비교하려면 둘을 같은 모델로 임베딩해 같은 벡터 공간에 놓아야 한다.

vector store는 문서 chunk의 벡터와 metadata를 저장한다. 작은 실험에서는 배열로 저장할 수 있고, 규모가 커지면 벡터 데이터베이스나 ANN index를 사용한다.

similarity score는 질문 벡터와 문서 벡터가 얼마나 가까운지를 나타낸다. 가까움을 계산하는 방법에는 cosine similarity, dot product, L2 distance 등이 있다. 계산된 점수를 기준으로 top-k를 적용하면 점수가 높은 문서 조각 몇 개를 반환할지 정할 수 있다.

임베딩 룩업도 텍스트를 계산 가능한 벡터로 바꾸지만 검색용 임베딩과 쓰임새가 다르다. 임베딩 룩업은 토큰 ID를 모델 내부 벡터로 바꾸는 계층이고, RAG의 임베딩 검색은 문장이나 문단 전체를 검색용 벡터로 바꾼다.

RAG에서 임베딩 벡터 검색이 동작하는 흐름

인덱싱 단계에서는 문서를 chunk로 나누고 각 chunk의 embedding을 vector store에 저장한다. 검색 단계에서는 사용자 질문을 같은 공간의 query embedding으로 바꾼 뒤, 저장된 벡터와의 유사도를 계산해 top-k chunk를 반환한다. 생성 단계에서는 질문과 검색된 chunk를 함께 프롬프트에 넣어 LLM 답변을 만든다.

검색 단계가 느려지면 RAG 전체 응답도 느려진다. 데이터가 많아졌을 때는 모든 벡터를 전부 비교하는 brute force 검색 대신 ANN approximate nearest neighbor 인덱스를 사용한다.
