추론 엔진 프레임워크 비교

한 줄 요약: 추론 엔진 프레임워크는 학습된 모델을 가변 길이·동시 요청·스트리밍·GPU 메모리 한계에 맞춰 실행하는 계층으로, 가중치 적재·KV cache·배칭을 맡는다.

추론 엔진 프레임워크는 학습된 모델을 실제 요청에 맞춰 빠르고 안정적으로 실행하기 위한 실행 계층이다.

추론 엔진 프레임워크 비교 혼동

LLM을 서비스로 쓰려면 model.generate()만으로는 부족하다. 실제 요청은 길이가 다르고, 동시에 들어오고, 스트리밍으로 나가고, GPU 메모리 한계 안에서 처리되어야 한다.

그래서 추론 엔진은 보통 다음 문제를 맡는다.

  • 모델 가중치를 어떤 형식으로 올릴지
  • KV cache를 어떻게 관리할지
  • prefill과 decode 요청을 어떻게 스케줄링할지
  • batching, streaming, quantization을 어디까지 지원할지
  • CPU, NVIDIA GPU, 다른 backend 중 어디에서 실행할지

이 문서는 엔진 이름을 외우는 문서가 아니라, 병목에 따라 어떤 계열을 먼저 볼지 정하는 기준이다.

운영 조건별 우선 검토 엔진

운영 조건이 다른 세 상황을 비교해 보자.

이렇게 보면 프레임워크 비교는 “무엇이 더 유명한가”가 아니라 “내 병목이 어디에 있는가”의 문제다.

비교 기준

  • vLLM
    • 강점: 페이지드 어텐션, 연속 배칭, LLM 서빙 스케줄링
    • 먼저 떠올릴 때: 많은 동시 요청, 긴 context, KV cache 메모리 낭비가 문제일 때
  • TensorRT-LLM
    • 강점: NVIDIA GPU에 맞춘 kernel, quantization, batching, parallelism 최적화
    • 먼저 떠올릴 때: NVIDIA GPU 환경에서 낮은 latency와 높은 throughput이 핵심일 때
  • ONNX Runtime
    • 강점: ONNX 모델 실행, Execution Provider 선택, 여러 배포 환경 호환성
    • 먼저 떠올릴 때: LLM 전용 스케줄링보다 모델 실행 portability가 더 중요할 때

추론 엔진 프레임워크 비교 적용 기준

  • 요청 처리량이 낮고 GPU 슬롯이 자주 빈다
    • batching과 scheduler가 강한 엔진을 먼저 본다.
  • KV cache 메모리가 먼저 꽉 찬다
    • cache 관리 방식과 paged/block 기반 할당을 본다.
  • NVIDIA GPU에서 한 모델을 최대한 빠르게 돌려야 한다
    • TensorRT-LLM 같은 GPU 최적화 런타임을 본다.
  • 모델을 여러 플랫폼에 배포해야 한다
    • ONNX export와 Execution Provider 지원을 먼저 확인한다.
  • API 서버, 인증, rate limit, 관측성까지 필요하다
    • 추론 엔진만으로 끝나지 않는다. 모델 서빙 API 설계와 운영 계층을 함께 본다.
