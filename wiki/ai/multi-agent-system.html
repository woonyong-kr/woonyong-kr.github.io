다중 에이전트 시스템 (Multi Agent System)

한 줄 요약: 다중 에이전트 시스템은 한 Agent가 모든 일을 맡는 대신 계획, 검색, 실행, 검토를 여러 Agent가 나눠 협업하는 구조이며, 역할 분리로 판단이 섞이는 문제를 줄이되 메시지와 비용, 지연을 새로 떠안는다.

하나의 Agent가 계획부터 검토까지 모두 맡으면 구조가 단순하고 실패 원인을 추적하기 쉽다. 그러나 작업이 커질수록 한 Agent 안에 서로 다른 역할과 판단 기준이 섞일 수 있다. 다중 에이전트 시스템은 계획, 검색, 실행, 검토를 여러 Agent에게 나눠 이 문제를 줄이는 협업 구조다.

역할 분리가 필요한 지점

한 Agent가 전체 순서를 정하면서 정보를 검색하고, 도구를 호출해 결과를 만든 뒤, 그 결과까지 스스로 검증하면 각 단계의 판단 기준을 분리하기 어려워진다. 다중 에이전트 구조에서는 계획 담당이 전체 순서를 잡고, 실행 담당이 실제 도구를 호출하며, 검토 담당이 결과가 조건을 만족하는지 확인할 수 있다.

역할을 나누면 각 Agent가 맡은 기준에 집중할 수 있지만, Agent가 많다고 항상 더 나은 것은 아니다. Agent 사이의 메시지 전달과 상태 공유가 필요해지고, 책임 소재가 흐려질 수 있다. LLM 호출과 도구 호출이 늘어 비용이 커지며, 결과를 주고받고 검토하는 과정에서 지연도 발생한다.

대표 패턴

  • supervisor-worker
    • supervisor가 목표를 하위 작업으로 나누고 worker에게 배분한다.
    • 여러 하위 작업을 병렬로 처리할 때 적합하다.
  • reviewer-executor
    • executor가 결과를 만들고 reviewer가 조건, 위험, 누락을 검사한다.
    • 코드 수정, 문서 생성, 도구 실행처럼 검증이 중요한 작업에 적합하다.
  • debate
    • 여러 Agent가 서로 다른 관점의 답을 제시한 뒤 마지막에 하나를 선택하거나 합의한다.
    • 판단 기준이 모호하거나 리스크를 평가해야 하는 문제에 적합하다.
  • specialist team
    • 검색 담당, 코드 담당, 테스트 담당, 보고 담당처럼 역할을 고정한다.
    • 같은 업무 절차가 반복되는 경우에 적합하다.

작업이 진행되는 흐름

이 흐름에서 supervisor는 모든 작업을 직접 수행하지 않는다. 사용자 목표를 하위 작업으로 나누고, 각 Agent의 결과를 병합하며, 결과 사이의 충돌을 해결한다. Research Agent가 근거와 후보를 전달하면 Executor Agent가 결과물을 만들고, Reviewer Agent가 조건과 누락, 위험을 점검한다. supervisor는 이 결과를 바탕으로 최종 요약과 다음 행동을 결정한다.

적용 여부를 판단하는 기준

작업이 짧고 도구 호출이 적으며, 실패 원인을 하나의 흐름에서 추적할 수 있다면 단일 Agent로도 충분하다. 병렬 처리나 별도 검토가 품질에 큰 이득을 주지 않는 경우에도 역할을 나눌 필요가 적다.

반대로 검색, 실행, 검토처럼 책임을 명확히 나눌 수 있고, 이를 분리해야 품질이 올라가는 작업에는 다중 Agent가 나을 수 있다. 여러 후보를 비교하거나 장시간 작업의 중간 산출물을 독립적으로 검증해야 할 때도 역할 분리의 이점이 생긴다.

다만 역할의 이름만 다르고 실제 책임이 겹친다면 Agent를 늘려도 판단 기준은 분리되지 않는다. shared memory에 확인되지 않은 추측이 계속 쌓이거나, 서로 다른 결론을 병합할 최종 책임자가 없는 구조도 피해야 한다. 추가된 비용과 지연 시간이 품질 향상보다 크다면 다중 에이전트 구조를 적용할 이유가 약하다.

운영할 때 생기는 위험

  • 비용 증가
    • Agent가 늘어나면 LLM 호출과 도구 호출도 늘어난다.
  • 지연 시간 증가
    • 결과를 순서대로 검토하는 구조는 처리 시간이 길어질 수 있다.
  • 책임 경계 흐림
    • 최종 결정권자가 없으면 Agent마다 다른 결론을 내놓을 수 있다.
  • 메모리 오염
    • 한 Agent의 추측이 shared memory에 들어가면 다른 Agent가 이를 사실처럼 사용할 수 있다.
  • 충돌 해결 실패
    • reviewer와 executor의 의견이 다를 때 어떤 판단을 우선할지 정한 규칙이 필요하다.

메모리와 평가

다중 Agent가 함께 작업할 때는 에이전트 메모리 시스템의 범위를 정해야 한다. 모든 Agent가 같은 기억을 읽게 할지, 역할마다 별도의 작업 메모리를 제공할지 결정해야 한다. 특히 확인되지 않은 추측이 shared memory를 통해 다른 Agent에게 전달되면 사실과 추론의 경계가 흐려질 수 있다.

에이전트 평가에서는 최종 답변만 확인해서는 각 역할의 수행 과정을 알기 어렵다. 각 Agent가 맡은 역할을 제대로 수행했는지, supervisor가 충돌을 어떻게 처리했는지, 불필요한 왕복이 있었는지를 trace로 확인해야 한다.
