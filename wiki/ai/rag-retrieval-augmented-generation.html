RAG — 검색 증강 생성 (Retrieval-Augmented Generation)

한 줄 요약: RAG는 LLM이 답변을 생성하기 전에 외부 문서를 검색해서 프롬프트에 끼워 넣는 기법이다.

RAG가 필요한 문제와 비용을 줄이는 자리

LLM만으로 질문에 답하려고 하면 세 가지 한계가 드러날 수 있다.

첫째는 **지식 단절(knowledge cutoff)**이다. 학습 이후에 발생한 사건은 학습 데이터에 들어 있지 않다. 예를 들어 “2025년 5월 환율”을 물었을 때, 그 시점이 학습 데이터가 끊긴 뒤라면 모델의 파라미터만으로 값을 알 수 없다.

둘째는 **할루시네이션(hallucination)**이다. 모델은 모르는 질문에도 그럴듯한 답을 생성할 수 있다. 파라미터에 기록된 패턴이 실제 사실과 일치하는지 모델 내부에서 검증하기는 어렵다.

셋째는 사적 데이터 접근 불가다. 회사 내부 문서, 개인 노트, 비공개 DB는 사전 학습에 포함되지 않는다. 이런 데이터를 파인튜닝으로 주입하는 방식은 비용이 들고, 데이터가 바뀔 때마다 다시 학습해야 한다.

RAG는 이 문제들을 다루기 위해 모델을 재학습하는 대신 외부 문서를 프롬프트에 제공한다. 질문이 들어오면 외부 저장소에서 관련 문서를 검색하고, 검색된 문서를 프롬프트에 붙여 LLM에 넘긴다. 그러면 모델은 기존 파라미터만 사용하는 것이 아니라 프롬프트에 포함된 문맥을 참고해 답변을 생성할 수 있다. 다만 이 구조가 항상 정확한 답을 보장하는 것은 아니다. 검색된 문서와 프롬프트가 답변의 근거가 되므로, 결과는 어떤 문서를 찾아 제공했는지에 영향을 받는다.

파인튜닝과 비교했을 때 RAG가 비용을 줄이는 자리는 여기에 있다. 지식이 바뀔 때마다 모델을 다시 학습하지 않고 외부 저장소의 문서를 바꿔 제공할 수 있기 때문이다.

RAG 구조: 검색, 증강, 생성

비유: 오픈북 시험

LLM 단독 사용은 클로즈북 시험에 비유할 수 있다. 머릿속 기억인 파라미터만으로 답하기 때문이다. RAG는 오픈북 시험에 가깝다. 문제를 받으면 먼저 교재에 해당하는 외부 문서에서 관련 페이지를 찾고, 그 페이지를 보면서 답을 쓴다.

3단계 파이프라인: 검색 → 증강 → 생성

이 비유에서 관련 페이지를 찾는 과정은 검색, 찾은 페이지를 문제와 함께 놓는 과정은 증강, 그 내용을 참고해 답을 쓰는 과정은 생성에 해당한다.

  1. 검색(Retrieval): 사용자 질문을 벡터로 변환하고, 문서 저장소에서 유사도가 높은 문서 조각(chunk)을 가져온다.
  2. 증강(Augmentation): 검색된 문서 조각을 프롬프트 앞에 삽입한다. “다음 문맥을 참고하여 답하시오”와 같은 지시문과 함께 구성한다.
  3. 생성(Generation): 증강된 프롬프트를 LLM에 입력하고, 모델이 문맥을 근거로 답변을 생성한다.

각 단계의 데이터 흐름을 항목으로 나타내면 다음과 같다.

  • 질문 벡터화 유사도 검색
  • 사용자 | → | Embedding | → | Vector Store
  • 질문 | | Model | | 문서 저장소
  • 검색된 chunk
  • 최종 답변 증강 프롬프트
  • 사용자 | ← | LLM | ← | Prompt
  • (GPT 등) | | 질문 + chunk

검색 단계의 임베딩과 유사도 검색

RAG의 검색 단계는 임베딩에 의존한다. LLM 학습에서 토큰 ID를 벡터로 바꾸는 임베딩과 원리는 같다. RAG에서는 문장이나 문단을 단위로 삼아 임베딩한다는 차이가 있다.

질문과 문서 조각을 같은 벡터 공간에 놓으면 두 벡터의 유사도를 비교할 수 있다. 가장 일반적인 측정 방법은 코사인 유사도(cosine similarity)다.

코사인 유사도가 비교하는 것

cosine_similarity = (A · B) / (|A| × |B|)

A = [1, 2, 3], B = [2, 4, 6]이라 하자.

A · B = 1×2 + 2×4 + 3×6 = 28 |A| = sqrt(1 + 4 + 9) = sqrt(14) ≈ 3.74 |B| = sqrt(4 + 16 + 36) = sqrt(56) ≈ 7.48

cosine_similarity = 28 / (3.74 × 7.48) ≈ 1.0

A와 B는 크기만 다르고 방향은 같다. 따라서 코사인 유사도는 1이다. 코사인 유사도는 벡터의 크기보다 방향을 비교한다. 이 방식에서는 문장 길이가 달라도 의미가 비슷한 문장의 벡터가 같은 방향을 가리키면 높은 유사도를 얻는다.

검색 단위를 만드는 청킹(Chunking)

문서 전체를 하나의 벡터로 만들면 세부 정보가 희석된다. RAG는 검색할 단위를 만들기 위해 문서를 일정 크기의 조각(chunk)으로 나눈다.

청킹 방식에 따라 보존되는 문맥과 필요한 비용이 달라진다.

  • 고정 길이 분할: 500토큰씩 잘라서 100토큰 겹침(overlap). 단순하지만 문장 경계를 무시할 수 있다.
  • 문장/문단 단위 분할: 마침표나 줄바꿈 기준으로 나눈다. 의미 단위를 보존한다.
  • 의미 기반 분할: 임베딩 유사도가 급격히 변하는 지점에서 자른다. 비용이 크다.

chunk가 너무 작으면 답변에 필요한 문맥이 부족할 수 있다. 너무 크면 관련 없는 내용까지 포함하고 LLM의 컨텍스트 윈도를 더 많이 사용한다. 실무에서는 200~1000토큰 범위를 자주 사용하지만, 이 범위가 모든 문서와 질문에 적합하다고 볼 수는 없다.

RAG 텐서 코드로 보는 파이프라인

다음 코드는 문서 임베딩, 검색, 프롬프트 증강이 어떻게 이어지는지 보여 주는 예시다. 실제 임베딩 모델 대신 랜덤 벡터를 사용하므로, 검색 품질이나 출력 결과를 검증하는 구현은 아니다.

1단계: 문서 임베딩과 벡터 저장

이 단계는 각 문서 조각을 벡터로 변환하고, 벡터들을 행렬로 모아 벡터 스토어를 구성한다. 실제 시스템에서는 FAISS, Chroma, Pinecone 같은 벡터 데이터베이스를 사용한다.

2단계: 질문으로 유사 문서 검색

이 단계는 질문을 벡터로 바꾸고, 벡터 스토어의 각 chunk와 코사인 유사도를 비교한 뒤 점수가 높은 chunk를 선택한다. 이것이 RAG의 R(Retrieval)이다. 다만 이 예시는 랜덤 벡터를 사용하므로, 코드 주석에 적힌 검색 결과가 의미 유사도에 따라 재현된다고 볼 수는 없다.

3단계: 프롬프트 증강과 생성

검색된 chunk를 지시문과 질문에 결합해 프롬프트를 만드는 과정이 A(Augmentation)다. 이 예시는 조립된 프롬프트를 출력할 뿐, 실제 LLM 호출은 수행하지 않는다. 해당 프롬프트를 LLM에 입력해 답변을 생성하는 과정이 G(Generation)에 해당한다.

전체 파이프라인 흐름

예제의 질문이 문서 검색을 거쳐 프롬프트로 조립되는 순서는 다음과 같다.

  • 질문: “트랜스포머 구조가 뭐야?”
    1. embed(query) | 질문 → 128차원 벡터
    1. retrieve() | 벡터 스토어에서 top-k chunk 검색
  • cosine sim | (4, 128) 행렬과 유사도 비교
    1. build_prompt | “[문맥] chunk1, chunk2 + [질문]”
  • 증강 조립
    1. LLM 생성 | GPT 등이 문맥 기반 답변 생성

이 가운데 예제 코드가 직접 보여 주는 범위는 임베딩용 벡터 구성, 유사도 비교, 프롬프트 조립까지다. 마지막 LLM 생성은 흐름을 설명하지만 실행하지 않는다.

기본 RAG를 다시 설명하는 기준

RAG는 검색(Retrieval), 증강(Augmentation), 생성(Generation)으로 이어진다. 질문과 문서를 같은 벡터 공간에 임베딩하고, 코사인 유사도로 관련 chunk를 찾은 뒤, 검색된 문맥과 질문을 하나의 프롬프트로 조립한다.

이 구조는 학습 이후의 정보나 사적 데이터를 모델 재학습 없이 제공하는 데 사용할 수 있다. 또한 모델이 외부 문맥을 참고하게 만들어 할루시네이션 문제를 다루려는 방식이다. 그러나 정확성은 자동으로 보장되지 않는다. 검색 단계가 관련 문서를 찾지 못하거나 제공된 문맥이 부족하면 생성 단계도 충분한 근거를 얻지 못한다.

이 문서가 다루는 범위는 검색 결과를 프롬프트에 넣는 가장 기본적인 RAG 구조다. 실제 시스템에서는 청킹 전략, 리랭킹(re-ranking), 하이브리드 검색(키워드 + 벡터) 등을 결합한다.

연결 문서:

  • 질문과 문서를 같은 벡터 공간에서 비교하는 검색 방식
  • 청킹, 검색, 프롬프트 조립을 단계별로 나누는 기준
  • Naive RAG — 검색 결과를 바로 프롬프트에 넣는 기본 구조
  • Advanced RAG — 재랭킹, 쿼리 변환 등 검색 품질 개선 기법
  • RAG가 의존하는 벡터 변환의 원리
  • RAG의 생성 단계를 담당하는 모델
