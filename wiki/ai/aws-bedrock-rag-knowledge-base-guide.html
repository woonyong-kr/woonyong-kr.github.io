Amazon Bedrock Knowledge Base와 RAG 실습 가이드

한 줄 요약: Bedrock Knowledge Base는 vector DB와 embedding, retrieval을 직접 구현하는 대신 S3 원문을 연결해 관리형 RAG 검색 계층을 구성한다. 이를 통해 모델이 기억에 의존해 답하는 방식과 외부 문서를 검색해 근거를 바탕으로 답하는 방식을 구분할 수 있다.

Bedrock Knowledge Base 실습에서는 RAG를 관리형 서비스로 구성한다. 직접 vector DB, embedding job, retrieval 코드를 모두 작성하지 않고 S3 원문을 연결하면, Bedrock이 embedding과 vector store 연동을 맡는다.

이 구성을 이해하려면 모델의 기억과 외부 문서 검색을 먼저 구분해야 한다. LLM은 학습 시점 이후에 나온 문서나 조직 내부 문서를 알지 못한다. 모든 문서를 프롬프트에 넣는 방식도 길이와 비용의 한계가 있다. RAG는 질문과 관련 있는 문서 조각만 검색해 프롬프트에 넣고, Knowledge Base는 이 검색 계층을 관리형으로 제공한다.

Bedrock Knowledge Base가 구성하는 RAG 흐름

Knowledge Base는 S3, embedding model, vector store, retrieval API를 하나의 흐름으로 연결한다.

이 흐름에서는 검색과 생성을 분리해서 봐야 한다. 검색 단계는 질문과 가까운 문서 조각을 찾으며, 답변을 생성하지 않고도 검색된 chunk만 확인할 수 있다. 생성 단계에서는 모델이 검색된 chunk를 근거로 자연어 답변을 만들고, citation을 통해 어떤 chunk를 참고했는지 확인한다.

1단계: Bedrock 접근과 리전 확인

먼저 Anthropic Claude 계열 모델과 Titan Text Embeddings v2 같은 embedding model에 접근할 수 있는지 확인한다. Bedrock 기능을 사용할 리전과 workshop 리전도 일치해야 한다. 모델 접근 권한은 리전별로 다를 수 있다.

2단계: Knowledge Base 만들기

새 Knowledge Base를 만들고 새 service role을 생성하거나 workshop이 제공한 role을 사용한다. Data source에는 S3 bucket 또는 workshop이 제공한 S3 경로를 연결한다.

Chunking은 기본 설정을 사용한다. 이 실습에서는 최대 chunk 크기를 300 token 수준으로 설정한다. Embedding model로는 Titan Text Embeddings v2를 선택하고, vector store는 quick create를 이용해 OpenSearch Serverless에 만든다. Vector store 생성에는 시간이 걸릴 수 있으므로 완료 상태를 확인한 뒤 다음 단계로 진행한다.

3단계: Data source sync

Knowledge Base를 만든 뒤 data source를 sync한다. Sync가 끝나야 검색할 chunk가 vector store에 들어간다.

Sync가 실패하면 S3 경로가 올바른지 먼저 확인한다. 이어서 service role에 S3 object 읽기 권한이 있는지, embedding model 접근 권한이 있는지, vector store 생성이 완료되었는지 살펴본다.

4단계: 검색만 먼저 테스트하기

Generate responses를 끄고 질문하면 모델의 답변 없이 검색된 chunk만 볼 수 있다.

처음에는 생성 결과보다 검색 결과를 먼저 확인하는 편이 좋다. 답변이 이상할 때 바로 생성 모델을 의심하지 않고, 질문과 관련된 chunk가 실제로 검색되었는지 분리해서 판단할 수 있기 때문이다.

다음 질문으로 검색을 시험할 수 있다.

  • What's the lead paint guidelines for homes sold?
  • 주택 판매 시 납 페인트 관련 가이드라인은 무엇인가?

5단계: 생성 답변 테스트하기

Generate responses를 켜고 Claude 3 Haiku 같은 빠른 모델을 선택한 뒤 같은 질문을 다시 입력한다. 이때 답변이 검색된 chunk를 근거로 삼는지, citation이 붙는지, 문서에 없는 내용을 만들어내지 않는지 확인한다.

검색과 답변 품질을 판단하는 방법

검색 결과가 질문에서 빗나간다면 chunk 크기가 너무 크거나 작을 수 있다. 질문 표현과 문서 표현의 차이가 크거나 원문 data source가 sync되지 않은 경우도 확인해야 한다.

답변은 자연스럽지만 근거가 약하다면 citation을 살펴본다. 그래도 원인을 판단하기 어렵다면 Generate responses를 끄고 retrieval 결과부터 다시 확인한다. 이 과정으로 검색 문제와 생성 문제를 나눠 볼 수 있다.

최신 문서가 검색되지 않는다면 S3에 문서를 올린 뒤 data source sync를 다시 실행했는지 확인한다. S3의 원문을 변경하는 것만으로는 검색 대상이 갱신되지 않을 수 있다.

Bedrock Knowledge Base와 직접 구현한 RAG 비교

RAG를 직접 구현하면 chunking, embedding, vector DB, retrieval, prompt assembly, citation 처리를 직접 설계한다. 자유도는 높지만 그만큼 확인해야 할 실패 지점도 많다.

Bedrock Knowledge Base는 이러한 구성 요소 사이에 AWS의 관리형 연결을 제공한다. 콘솔과 API로 빠르게 구성할 수 있지만, 검색과 답변의 품질을 조절하려면 chunking, embedding, vector store, retrieval의 역할을 이해해야 한다.
