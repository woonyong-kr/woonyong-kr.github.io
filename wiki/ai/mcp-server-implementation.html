MCP 서버 구현 (MCP Server Implementation)

한 줄 요약: MCP 서버 구현은 외부 시스템 기능을 Tool·Resource·Prompt로 감싸 Host가 표준 메시지로 발견·호출하게 만들어, 통합 코드를 앱에서 독립 프로그램으로 분리한다.

MCP 서버 구현은 외부 시스템의 기능을 Tool, Resource, Prompt로 감싸 Host가 표준 메시지로 발견하고 호출할 수 있게 만드는 작업이다.

MCP 서버 구현 혼동

LLM 앱에서 “GitHub 이슈를 찾아줘”, “이 DB schema를 읽어줘”, “테스트를 실행해줘” 같은 기능을 직접 붙이면 앱 안에 통합 코드가 계속 늘어난다. MCP Server로 분리하면 외부 시스템별 책임을 독립된 작은 프로그램으로 옮길 수 있다.

서버 구현에서 먼저 정할 것은 “무엇을 노출할지”다.

  • 읽기 자료
    • Resource
    • 예: 프로젝트 README, 설정 파일, DB schema
  • 실행 행동
    • Tool
    • 예: 검색, 테스트 실행, API 호출
  • 반복 절차
    • Prompt
    • 예: 코드 리뷰 요청, 장애 로그 분석 템플릿

MCP 서버 구현 사례

이 예시에서 readme는 읽기 전용 context이고, search_docs는 모델이 호출할 수 있는 행동이다. stdio transport를 쓰면 Host가 서버 프로세스를 실행하고 표준 입출력으로 JSON-RPC 메시지를 주고받는다.

구현 순서

  • Server 이름과 책임 범위 정리
    • 예: project-helper, database-reader, github-workflow
  • 노출할 능력 분류
    • Resource: 읽기 자료
    • Tool: 실행 행동
    • Prompt: 반복 작업 양식
  • 입력 스키마 좁히기
    • query: str, top_k: int처럼 필요한 값만 받기
  • 권한과 실패 처리 추가
    • 허용 경로, rate limit, timeout, 민감 작업 확인
  • Host 연결 설정
    • 로컬이면 stdio, 원격이면 HTTP 계열 transport 검토

MCP 서버 구현 적용 기준

  • 서버 하나가 너무 많은 일을 한다
    • 파일, DB, GitHub, 결제 같은 경계가 섞이면 서버를 나누는 편이 낫다.
  • Tool 설명이 모호하다
    • Agent가 잘못 고를 가능성이 높다. 이름, 설명, 입력 스키마를 좁힌다.
  • stdout에 로그를 쓴다
    • stdio 기반 서버에서는 JSON-RPC 메시지를 깨뜨릴 수 있으므로 stderr나 logging 사용.
  • 사용자 확인 없이 상태 변경 Tool을 실행한다
    • 삭제, 전송, 권한 변경은 human-in-the-loop가 필요하다.
