RAG 파이프라인 설계 — 검색 품질을 결정하는 단계별 선택을 미리 정하는 기준

확인 범위: 이 문서는 RAG 파이프라인의 단계 구분과 일반적인 선택·진단 기준을 설명하며, 포함된 코드는 흐름을 보여 주는 참조 구현이다. 구체적인 설정값의 적합성, 검색 품질·응답 속도·비용에 관한 판단은 실제 문서와 모델, 저장소, 버전 및 실행·성능 측정을 통해 별도로 검증해야 한다.

한 줄 요약: 팀 프로젝트에서 RAG를 쓰기로 정한 다음, 청킹·임베딩·검색·리랭킹·생성 각 단계에서 무엇을 어떻게 고를지 미리 정해 두는 설계 기준이다. 검색이 엉뚱한 문서를 가져오면 아무리 좋은 LLM도 틀린 답을 내므로, 답이 틀렸을 때 검색 실패인지 생성 실패인지 가려낼 수 있게 단계를 분리해 설계한다.

RAG 파이프라인 설계 혼동

팀 프로젝트에서 “사내 문서로 답하는 챗봇을 만들자, RAG로 가자”까지는 쉽게 정해진다. 문제는 그다음이다. RAG가 검색·증강·생성 세 단계라는 것을 알아도, 막상 구현하면 답이 엉뚱하게 나온다. 그리고 왜 틀렸는지 짚지 못한다.

문제 상황을 보자. 사용자가 “환불 기한이 며칠이야?”라고 물었는데 챗봇이 “환불은 불가능합니다”라고 답한다. 원인은 두 갈래다.

  • 검색이 환불 정책이 아니라 교환 정책 문서를 가져왔다 → 검색 실패
  • 검색은 맞는 문서를 가져왔는데 LLM이 문맥을 무시하고 엉뚱하게 답했다 → 생성 실패

이 둘을 구분하지 못하면 엉뚱한 곳을 고친다. 검색이 문제인데 프롬프트만 며칠씩 손보거나, 생성이 문제인데 임베딩 모델을 계속 바꾸는 식이다. RAG 파이프라인 설계는 각 단계를 독립적으로 고를 수 있게 분리해 두는 일이다. 그래야 “검색된 문서 목록”을 눈으로 찍어 보고 어느 단계가 깨졌는지 진단할 수 있다.

이 설계 기준이 없으면 다음을 판단할 수 없다.

  • 문서를 몇 글자씩 잘라야(청킹) 검색이 잘 되는지
  • top-k(검색해 올 문서 조각 개수)를 몇 개로 둘지, 많이 가져오면 왜 오히려 나빠지는지
  • 의미 검색(벡터)만으로 부족한 경우가 언제인지, 키워드 검색을 언제 섞어야 하는지
  • 이 문제가 RAG로 풀 일인지 미세조정으로 풀 일인지

핵심 질문은 하나다. 검색이 엉뚱한 문서를 가져오면 LLM이 아무리 좋아도 답은 틀린다. 그렇다면 각 단계를 어떻게 설계해야 맞는 문서가 위로 올라오고, 틀렸을 때 어디가 깨졌는지 알 수 있는가.

RAG 파이프라인 설계 구조

비유: 도서관 사서

질문에 답하는 사서를 떠올려 보자. 사서는 머릿속 지식만으로 답하지 않는다. 질문을 듣고(1), 어느 서가로 갈지 정하고(2), 그 서가에서 관련된 책 몇 권을 뽑고(3), 그중 진짜 쓸 만한 페이지를 골라(4), 그 페이지를 보며 답을 정리한다(5).

RAG 파이프라인의 각 단계가 이 동작 하나하나에 대응한다. 그리고 사서가 엉뚱한 답을 했을 때 원인은 둘 중 하나다. 책을 잘못 뽑았거나(검색 실패), 맞는 책을 보고도 엉뚱하게 읽었거나(생성 실패). 설계의 목표는 이 단계들을 분리해서, 어느 동작이 틀렸는지 따로 점검할 수 있게 만드는 것이다.

인덱싱 타임과 쿼리 타임을 나눈다

RAG에서 가장 먼저 잡아야 할 설계 구분은 “언제 일어나는 일인가”다. 파이프라인은 시점이 다른 두 덩어리로 갈린다.

  • 인덱싱 타임(indexing time, 오프라인): 사용자가 오기 전에 미리 한다. 문서를 잘라 임베딩하고 벡터 저장소에 넣는다. 한 번 또는 문서가 바뀔 때만 돈다.
  • 쿼리 타임(query time, 온라인): 사용자 질문이 들어올 때마다 돈다. 질문을 임베딩해 검색하고, 프롬프트를 만들어 LLM에 넘긴다. 응답 속도가 여기서 결정된다.

이 둘을 섞으면 안 된다. 청킹·임베딩처럼 무거운 작업을 쿼리 타임에 두면 사용자가 매 질문마다 기다린다. 이 구분은 데이터 파이프라인의 배치 적재(인덱싱)와 온라인 조회(쿼리)가 갈리는 것과 같은 구조다.

단계별 설계 결정

각 단계는 독립적으로 고를 수 있는 손잡이(knob)가 있다. 손잡이를 모르면 무엇을 돌려야 검색이 좋아지는지 알 수 없다.

  • 청킹(chunking): 문서를 몇 글자(토큰)씩 자를지, 조각 사이를 얼마나 겹칠지(overlap) 정한다.
    • 너무 작게 자르면: 한 조각에 담긴 문맥이 부족해, 검색은 됐는데 답에 필요한 정보가 잘려 나간다.
    • 너무 크게 자르면: 한 조각에 여러 주제가 섞여 임베딩 벡터가 뭉개지고, LLM 컨텍스트 윈도도 낭비된다.
    • 기준값: 실무에서 자주 쓰는 200~1000토큰 범위. 문장·문단 경계를 지켜 자르면 의미 단위가 보존된다.
  • 임베딩 모델(embedding model): 질문과 문서를 같은 벡터 공간에 넣는 모델을 고른다.
    • 인덱싱과 쿼리에 반드시 같은 모델을 써야 한다. 다른 모델로 만든 벡터는 같은 공간에 있지 않아 유사도가 무의미하다.
    • 다국어 문서면 다국어 임베딩 모델을, 도메인 용어가 많으면 해당 도메인 데이터로 학습된 모델을 고른다.
  • 검색 방식(retrieval): 의미 검색(dense, 벡터)만 쓸지 키워드 검색(sparse, BM25)을 섞을지 정한다.
    • 의미 검색은 “환불”과 “반품”처럼 표현이 달라도 뜻이 비슷하면 찾는다.
    • 키워드 검색은 제품 코드 A-1024, 함수명 fsync()처럼 정확히 일치해야 하는 고유명사에 강하다.
    • 둘을 합친 것이 하이브리드 검색(hybrid search)이다. 고유명사가 많은 도메인이면 섞어야 한다.
  • top-k: 검색해 올 조각 개수다. 많을수록 좋아 보이지만 아니다.
    • 적으면: 정답이 든 조각이 안 뽑힐 위험(재현율 하락).
    • 많으면: 관련 없는 조각이 프롬프트에 섞여 LLM이 헷갈리고(noise), 토큰 비용도 는다.
  • 리랭킹(re-ranking): 1차로 넉넉히 가져온 뒤(예: 20개), 정밀한 모델로 다시 순위를 매겨 상위 몇 개만 LLM에 넘긴다.
    • 임베딩 검색은 빠르지만 거칠다. 리랭커(cross-encoder)는 느리지만 질문-조각을 함께 보고 정밀하게 점수를 매긴다.
    • “넓게 뽑고 좁게 거른다”가 검색 품질을 올리는 핵심 패턴이다.

왜 chunk를 겹쳐서(overlap) 자르나?

문서를 토막 낼 때 칼로 자르듯 딱 끊으면, 경계에 걸친 문장이 두 조각으로 쪼개져 어느 쪽에서도 온전히 검색되지 않는다. 그래서 조각 끝과 다음 조각 시작을 일부 겹친다. 겹침이 늘면 안전하지만 조각 수가 늘어 저장·검색 비용도 는다.

총 토큰 T=10,000, 조각 크기 C=500, 겹침 O일 때 조각 수 N:

N = ceil( (T - O) / (C - O) )

겹침 0   : N = 10000 / 500          = 20개
겹침 100 : N = (10000-100)/(500-100) = 9900/400 ≈ 25개
겹침 250 : N = (10000-250)/(500-250) = 9750/250 = 39개

겹침이 0에서 250으로 늘면 조각 수가 20개에서 39개로 약 2배가 된다. 저장 벡터 수와 검색 시 비교 횟수도 그만큼 는다. 겹침은 경계 손실을 막는 보험이고, 비용은 조각 수 증가다. 보통 조각 크기의 10~20%(여기선 50~100토큰)가 균형점이다.

검색 실패와 생성 실패를 가른다

설계가 단계를 분리하는 진짜 이유가 여기 있다. 답이 틀렸을 때 다음 순서로 찍어 본다.

  • 먼저 “검색된 조각 목록”을 그대로 출력해 본다.
    • 정답이 든 조각이 목록에 없다 → 검색 실패. 청킹·임베딩·top-k·하이브리드를 손본다.
    • 정답이 든 조각이 목록에 있는데 답이 틀렸다 → 생성 실패. 프롬프트·LLM·디코딩을 손본다.

이 한 번의 출력으로 고쳐야 할 단계가 갈린다. 단계를 섞어 짜 두면 이 출력 자체가 불가능해, 진단이 추측으로 변한다.

RAG 파이프라인 설계 코드

아래는 사내 문서 RAG 챗봇의 참조 구현이다. 인덱싱 타임과 쿼리 타임을 파일로 나눠, 단계를 따로 점검할 수 있게 둔다. 코드 흐름이 곧 위 설계 단계 순서다.

이 코드가 하는 일: 인덱싱 타임에 문서를 겹쳐 자르고 임베딩해 저장소를 만든다.

# rag/index.py — build_index(): 인덱싱 타임 (오프라인, 문서가 바뀔 때만 실행)
def chunk(text: str, size: int = 500, overlap: int = 100) -> list[str]:
    # 끝과 시작을 overlap만큼 겹쳐 자른다 → 경계 문장 손실 방지
    step = size - overlap
    return [text[i:i + size] for i in range(0, len(text), step)]

def build_index(docs: list[str], embed) -> list[dict]:
    store = []
    for doc_id, text in enumerate(docs):
        for c in chunk(text):
            store.append({
                "doc_id": doc_id,          # 출처 추적용 메타데이터
                "text": c,                 # 원문 조각 (생성 단계에서 그대로 쓴다)
                "vec": embed(c),           # 인덱싱·쿼리에 같은 embed 사용
            })
    return store                           # 실제로는 FAISS·Chroma 등에 적재

기억할 것: 인덱싱은 쿼리 타임에 두지 않는다. 무거운 청킹·임베딩을 미리 끝내 두어야 사용자가 매 질문마다 기다리지 않는다. doc_id 같은 메타데이터를 함께 저장해야 답변에 출처를 붙일 수 있다.

이 코드가 하는 일: 쿼리 타임에 질문을 임베딩해 유사한 조각을 넉넉히 가져온다.

# rag/query.py — retrieve(): 쿼리 타임 1차 검색 (넓게 뽑는다)
import numpy as np

def cosine(a, b):                          # 방향만 비교 → 길이 달라도 의미 유사면 높다
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

def retrieve(query: str, store: list[dict], embed, fetch_k: int = 20) -> list[dict]:
    qv = embed(query)                      # 질문도 같은 모델로 임베딩
    scored = [(cosine(qv, item["vec"]), item) for item in store]
    scored.sort(key=lambda x: x[0], reverse=True)
    return [item for _, item in scored[:fetch_k]]   # 리랭킹 전이라 넉넉히(20개)

기억할 것: 1차 검색은 정답을 놓치지 않게 넓게(fetch_k=20) 뽑는다. 정밀하게 거르는 일은 다음 단계인 리랭킹에 맡긴다. “넓게 뽑고 좁게 거른다”의 앞 절반이다.

이 코드가 하는 일: 1차로 뽑은 조각을 정밀 모델로 다시 매겨 상위 몇 개만 남긴다.

# rag/rerank.py — rerank(): 쿼리 타임 2차 정밀 거르기 (좁게 남긴다)
def rerank(query: str, candidates: list[dict], cross_encoder, top_k: int = 3) -> list[dict]:
    # cross-encoder는 (질문, 조각)을 함께 입력받아 관련도를 직접 점수화한다
    # 임베딩 검색보다 느리지만 정밀하다 → 후보 20개에만 적용해 비용을 통제
    scored = [(cross_encoder.score(query, c["text"]), c) for c in candidates]
    scored.sort(key=lambda x: x[0], reverse=True)
    return [c for _, c in scored[:top_k]]   # LLM에는 정밀하게 추린 top_k(3개)만

기억할 것: 리랭킹이 “넓게 뽑고 좁게 거른다”의 뒤 절반이다. 느린 정밀 모델을 전체가 아니라 후보 20개에만 돌려, 품질은 올리고 비용은 묶는다. top-k를 작게(3) 두어 프롬프트에 잡음이 섞이는 것을 막는다.

이 코드가 하는 일: 진단을 위해 검색 결과를 먼저 찍고 나서 생성한다.

# rag/answer.py — answer(): 단계를 분리해 검색 실패/생성 실패를 가른다
def answer(query: str, store, embed, cross_encoder, llm) -> str:
    cands = retrieve(query, store, embed, fetch_k=20)
    contexts = rerank(query, cands, cross_encoder, top_k=3)

    # 진단 포인트: 정답 조각이 여기 없으면 '검색 실패', 있는데 답이 틀리면 '생성 실패'
    for c in contexts:
        print(f"[검색됨] doc={c['doc_id']} :: {c['text'][:40]}")

    block = "\n".join(f"- {c['text']}" for c in contexts)
    prompt = f"다음 문맥만 근거로 답하라. 문맥에 없으면 모른다고 답하라.\n\n{block}\n\n질문: {query}"
    return llm.generate(prompt)             # 문맥 밖 추측 금지 지시로 할루시네이션 억제

기억할 것: 검색 결과를 출력하는 한 줄이 진단의 핵심이다. 단계를 분리해 두었기에 이 출력이 가능하고, 이 출력으로 검색 실패와 생성 실패가 갈린다. 프롬프트에 “문맥에 없으면 모른다고 답하라”를 넣어, 검색이 비었을 때 LLM이 지어내지 못하게 막는다.

정리

RAG 파이프라인 설계는 “RAG로 가자” 다음에 오는 단계별 선택을 미리 정해 두는 일이다. 시점으로는 인덱싱 타임(청킹·임베딩·저장)과 쿼리 타임(검색·리랭킹·생성)을 나눈다. 무거운 작업을 인덱싱 타임으로 밀어야 응답이 빨라진다.

판단 기준 정리:

  • 청킹은 200~1000토큰에서 시작하고, 조각 크기의 10~20%를 겹쳐 경계 손실을 막는다. 겹침이 늘면 조각 수가 늘어 비용이 는다.
  • 임베딩은 인덱싱과 쿼리에 반드시 같은 모델을 쓴다. 다른 모델 벡터는 같은 공간에 있지 않다.
  • 고유명사·코드가 많으면 의미 검색에 키워드 검색을 섞는다(하이브리드).
  • “넓게 뽑고(fetch_k 크게) 좁게 거른다(리랭킹 후 top-k 작게)”가 검색 품질의 핵심 패턴이다.
  • 답이 틀리면 검색된 조각 목록부터 찍는다. 정답 조각이 없으면 검색을, 있으면 생성을 손본다.

연결 문서:

  • RAG
    • 이 설계가 전제하는 검색·증강·생성 3단계의 원리와 코사인 유사도를 먼저 잡는다.
  • 데이터 파이프라인
    • 인덱싱에 넣을 문서가 어디서 어떻게 정제돼 오는지, 그 앞단을 본다.
  • Fine tuning 전략
    • 지식을 검색으로 붙일지(RAG) 모델에 학습시킬지(미세조정) 가르는 결정 기준을 비교한다.
  • 임베딩 룩업
    • 청킹·검색이 의존하는 벡터 변환이 모델 안에서 어떻게 일어나는지 본다.
  • DB 인덱스
    • 벡터 저장소가 풀 스캔을 피해 빠르게 찾는 원리를, 익숙한 DB 인덱스와 비교해 본다.
