KV 캐시 메모리 계산

확인 범위: 이 문서는 KV 캐시 메모리의 일반적인 계산 원리와 MHA·GQA·MQA에 따른 차이를 설명하고, 본문에 제시된 설정과 가정으로 산출한 예시를 제공한다. 특정 모델·코드·하드웨어에서의 실제 메모리 사용량, 최대 동시 요청 수, 병목 및 절감 효과는 구현 세부사항과 버전, 실행 기록, 오버헤드 및 성능 측정을 별도로 확인해야 한다.

한 줄 요약: KV Cache 메모리는 2 × n_layers × seq_len × d_model × bytes_per_param으로 계산한다. 배치 크기와 컨텍스트 길이가 늘어나면 모델 파라미터보다 캐시가 먼저 GPU 메모리를 채울 수 있다.

KV 캐시 메모리를 계산해야 하는 이유

LLM 추론에서 모델 파라미터가 차지하는 메모리는 고정되어 있지만, KV Cache는 요청에 따라 동적으로 늘어난다. 요청마다 캐시가 할당되므로 동시에 처리할 수 있는 요청 수, 즉 배치 크기와 허용 가능한 컨텍스트 길이는 KV Cache가 차지하는 메모리의 영향을 받는다.

따라서 “왜 GPU 80GB인데 배치 4개밖에 처리하지 못하는가?”, “컨텍스트를 128K로 늘리면 메모리가 얼마나 더 필요한가?” 같은 질문에 답하려면 먼저 요청 하나의 KV Cache 크기를 계산해야 한다.

KV 캐시 메모리 계산

기본 공식

요청 하나의 KV Cache 메모리는 다음과 같이 계산한다.

KV Cache = 2 × n_layers × seq_len × d_model × bytes_per_param

각 항목은 다음을 뜻한다.

  • 2: Key와 Value 두 텐서를 저장한다.
  • n_layers: Transformer 블록 수다. 각 블록에는 별도의 K와 V가 있다.
  • seq_len: 프롬프트와 생성된 토큰을 합한 현재 시퀀스 길이다.
  • d_model: 모델의 임베딩 차원이다. 모든 head의 head_dim을 합한 값이다.
  • bytes_per_param: 파라미터 하나를 저장하는 바이트 수다. FP16은 2바이트, FP32는 4바이트다.

계산에 d_model을 사용하는 이유

멀티헤드 어텐션에서 각 head는 d_head = d_model / n_heads 차원의 K와 V를 갖는다. 모든 head의 차원을 합치면 다음과 같다.

n_heads × d_head = n_heads × (d_model / n_heads) = d_model

따라서 한 layer에서 토큰 하나에 해당하는 K 텐서의 크기는 (d_model,)이고, V 텐서도 같은 크기다.

책의 설정으로 직접 계산

이 테스트 설정은 모델이 작기 때문에 KV Cache도 작다. MultiHeadAttention._project_qkv()는 입력 (B, T, 64)를 W_key와 W_value로 투영한 뒤, _split_heads를 거쳐 (B, 4, T, 16) shape으로 나눈다. 4개 head와 16차원의 head_dim을 곱하면 64가 되며, 이는 d_model과 같다. 따라서 토큰 하나의 K 또는 V 크기도 d_model과 같다.

실제 모델 규모로 확장

같은 공식을 더 큰 모델 설정에 적용하면 다음과 같다.

배치 크기가 미치는 영향

요청 하나의 KV Cache 크기를 알면 배치 크기에 따른 전체 GPU 메모리를 다음과 같이 추산할 수 있다.

GPU 메모리 = 모델 파라미터 + KV Cache × batch_size + 기타(activation 등)

LLaMA-2 7B를 A100 80GB에서 서빙한다고 가정하면 계산은 다음과 같다.

  • 모델 파라미터 (FP16): 7B × 2 bytes = 14 GB
  • 기타 오버헤드: 약 2 GB
  • KV Cache 가용 메모리: 80 - 14 - 2 = 64 GB
  • KV Cache per request (seq_len=4096): 2 GB
  • 최대 동시 요청 수: 64 / 2 = 32개

컨텍스트를 32K로 늘린다고 가정하면 결과가 달라진다.

  • KV Cache per request: 2 × 32 × 32768 × 4096 × 2 = 16 GB
  • 최대 동시 요청 수: 64 / 16 = 4개

이 계산에서는 컨텍스트 길이가 8배로 늘어나면서 요청 하나의 KV Cache도 8배가 되고, 동시에 처리할 수 있는 요청 수는 8분의 1로 줄어든다. 실제 최대 동시 요청 수와 병목은 구현 세부사항과 오버헤드 등을 별도로 확인해야 한다.

MQA와 GQA가 메모리를 줄이는 방식

일반 MHA(Multi-Head Attention)는 모든 head에 별도의 K와 V를 둔다. KV Cache와 추론 최적화 문서에서 다룬 MQA와 GQA는 여러 Q head가 K와 V를 공유하도록 KV head 수를 줄인다. 그만큼 캐시에 저장할 K와 V의 전체 차원도 작아진다.

제시된 계산에서 GQA는 KV Cache를 MHA의 4분의 1로, MQA는 32분의 1로 줄인다. LLaMA-2 70B의 설정으로 제시된 n_kv_heads=8에서는 KV Cache가 MHA 대비 10분의 1 수준이 된다.

KV Cache shape 변환 흐름

Decode 단계에서 새 토큰 하나가 들어오면 K를 투영하고 head별로 나눈 뒤 기존 캐시에 이어 붙인다. 한 Transformer 블록 안에서 이 과정이 진행되는 shape은 다음과 같다.

%% KV Cache shape 변환 흐름
flowchart TD
  input["입력 x<br/>(B, 1, d_model)<br/>Decode 단계: 새 토큰 1개"]
  projection["K projection<br/>x @ W_K"]
  knew["k_new<br/>(B, 1, d_model)"]
  split["head 분리<br/>(B, 1, d_model)<br/>→ (B, n_heads, 1, d_head)"]
  concat["캐시에 concat<br/>k_cache: (B, n_heads, seq_so_far, d_head)<br/>+ k_new → seq_so_far+1"]
  score["Q @ K_cache.T / sqrt(d_head)<br/>scores: (B, n_heads, 1, seq_so_far+1)"]
  attend["softmax → attn_weights<br/>attn_weights @ V_cache<br/>→ (B, n_heads, 1, d_head)"]
  merge["head 결합<br/>(B, 1, d_model)"]
  input --> projection
  projection --> knew
  knew --> split
  split --> concat
  concat --> score
  score --> attend
  attend --> merge

함께 볼 내용

KV Cache 메모리는 2 × n_layers × seq_len × d_model × bytes_per_param으로 계산한다. 배치 크기나 컨텍스트 길이가 늘어나면 전체 캐시 메모리도 선형으로 증가한다. MHA 대신 GQA나 MQA를 사용하면 KV head 수가 줄어들어 캐시에 필요한 메모리도 감소한다.

이 계산을 실제 서빙 환경에 적용할 때는 모델 파라미터뿐 아니라 activation 등의 오버헤드를 함께 고려해야 한다. 관련된 추론 과정과 메모리 관리 방식은 페이지드 어텐션과 Prefill과 Decode 단계에서 이어서 살펴볼 수 있다.
