임베딩 차원 트레이드오프

임베딩 차원 트레이드오프

확인 범위: 이 문서는 임베딩 차원의 일반적인 역할과 비용·표현력의 트레이드오프, 선택 기준을 설명하고, 제시된 모델 구성과 코드 발췌를 통해 텐서 크기와 헤드 수 제약을 예시한다. 특정 코드·모델 버전의 실제 동작이나 성능을 검증한 실행 기록·측정 결과는 포함하지 않으므로, 구현 적합성과 성능 판단에는 별도의 코드 확인과 실행·측정이 필요하다.

한 줄 요약: 임베딩 차원 emb_dim은 토큰 하나를 표현하는 벡터의 길이다. 크면 표현력이 늘지만 파라미터·연산·과적합이 같이 커진다.

임베딩 차원이 필요한 이유

신경망이 토큰 ID를 처리하려면 먼저 정수 ID를 실수 벡터로 바꿔야 한다. 임베딩 룩업이 이 변환을 담당하며, 변환된 벡터의 길이가 임베딩 차원 emb_dim이다. emb_dim = 256이면 토큰 하나를 256개의 실수로 표현한다.

단어를 좌표 공간의 점으로 보면 차원의 의미를 이해하기 쉽다. 2차원에서는 단어가 평면 위의 점이 되고, 256차원에서는 256개 축을 가진 공간의 점이 된다. 축이 많을수록 단어 사이의 미묘한 의미 차이를 더 많이 담을 수 있지만, 각 축을 저장하고 계산하는 비용도 함께 든다.

이 문서에 제시된 모델 구성에서는 emb_dim이 임베딩의 출력 폭이 되고, 이후 어텐션, FFN, LayerNorm도 같은 폭의 텐서를 다룬다. 따라서 emb_dim을 바꾸면 임베딩 테이블뿐 아니라 뒤따르는 층의 텐서 크기와 연산 비용도 달라진다.

차원이 너무 작으면 서로 다른 단어가 비슷한 벡터로 뭉개져 표현력이 부족할 수 있다. 반대로 크게 잡으면 파라미터 수와 연산량이 늘고, 학습 데이터가 부족할 때 과적합할 수 있다. 임베딩 차원을 정할 때는 표현력만이 아니라 데이터 양과 연산 예산을 함께 고려해야 한다.

차원이 커질 때 달라지는 것

표현력과 비용

차원이 클수록 더 많은 의미 축을 담을 수 있다. 다만 이 변화는 임베딩 테이블과 모델 내부 가중치에 서로 다른 비율로 영향을 준다.

  • 임베딩 테이블은 vocab_size × emb_dim 크기이므로 emb_dim에 비례해 선형으로 증가한다.
  • 어텐션과 FFN의 내부 가중치는 emb_dim의 제곱에 비례해 증가한다.
  • 각 층이 emb_dim 폭의 행렬곱을 수행하므로, 차원이 2배가 되면 해당 행렬곱 비용은 대략 4배가 된다.

임베딩 파라미터 계산

임베딩 파라미터 수 = vocab_size × emb_dim

GPT-2 small 기준 대입: 50257 × 768 = 38,597,376 ≈ 38.6M

emb_dim을 768에서 1536으로 2배 키우면: 50257 × 1536 = 77,194,752 ≈ 77.2M

이 계산에서는 임베딩 파라미터만 약 38.6M 늘어난다. 어텐션과 FFN의 emb_dim^2 가중치는 임베딩 테이블보다 더 빠르게 증가한다. 따라서 차원을 키우면 표현할 수 있는 의미 축은 늘지만 비용도 커지며, 학습 데이터가 이를 뒷받침하지 못하면 과적합으로 성능이 떨어질 수 있다.

입력 임베딩과 출력 분류기 가중치를 공유하는 weight tying을 적용하면 vocab_size × emb_dim 파라미터를 한 번만 저장해 메모리를 아낄 수 있다.

헤드 수와의 제약

멀티헤드 어텐션은 전체 차원을 여러 헤드가 균등하게 나눠 사용한다. 각 헤드의 크기는 head_dim = emb_dim / n_heads이므로, 이 구성에서는 emb_dim이 헤드 수 n_heads로 나누어떨어져야 한다. 자세한 파라미터 계산은 멀티헤드 파라미터 수를 본다.

  • emb_dim = 256, n_heads = 8 → head_dim = 32 (정상)
  • emb_dim = 256, n_heads = 7 → 나누어떨어지지 않음 (불가)

문서에 제시된 크기 기준

  • 작은 학습용 모델: 64 ~ 256
  • GPT-2 small: 768
  • GPT-2 large 이상: 1280 ~ 수천

이 값들은 문서에 제시된 경험적 기준이다. 실제 선택에서는 모델의 다른 구성과 데이터 양, 연산 예산을 함께 살펴야 한다.

코드에서 확인하는 emb_dim

밑바닥 LLM 책의 예제 코드는 emb_dim을 설정 한 곳에서 관리한다.

임베딩층은 이 설정값으로 학습 가능한 테이블의 shape을 정한다.

nn.Embedding(vocab_size, emb_dim)은 (vocab_size, emb_dim) 모양의 학습 가능한 룩업 테이블을 만든다. 토큰 ID로 행을 고르면 길이가 emb_dim인 벡터가 나온다. 위치 임베딩도 같은 차원을 사용해야 두 벡터를 더할 수 있다.

입력 (batch, seq_len)의 각 토큰 ID는 (batch, seq_len, emb_dim)의 벡터 텐서로 변환된다. emb_dim을 키우면 마지막 축이 길어지고, 이 출력을 받는 이후 층의 연산량도 함께 커진다.

텐서 shape 변환

%% 임베딩 차원 shape 변환 흐름
flowchart LR
  input_ids["입력 토큰 ID<br/>(batch=2, seq_len=4)"]
  embedding_table["nn.Embedding(vocab_size, emb_dim)"]
  output_embeddings["출력 임베딩<br/>(batch=2, seq_len=4, emb_dim)"]
  input_ids --> embedding_table
  embedding_table --> output_embeddings

헤드 수 제약을 적용하는 코드

이 실험 코드는 emb_dim % n_heads == 0인 헤드 수를 선택한다. head_dim = emb_dim / n_heads가 정수가 되어야 각 헤드가 전체 차원을 균등하게 나눌 수 있으므로, 이 구성에서 차원과 헤드 수는 독립적으로 정할 수 없다.

선택할 때 확인할 질문

임베딩 차원 emb_dim을 선택할 때는 토큰을 표현할 충분한 폭이 필요한지, vocab_size × emb_dim 크기의 임베딩 테이블을 감당할 수 있는지, 어텐션과 FFN의 emb_dim^2 증가를 연산 예산이 허용하는지 확인한다. 데이터가 늘어난 모델 용량을 뒷받침할 수 있는지도 함께 살펴야 한다. 멀티헤드 어텐션을 사용한다면 emb_dim이 n_heads로 나누어떨어지는지도 확인한다.

연결 문서:

  • 토큰 ID를 벡터로 바꾸는 메커니즘
  • vocab size 쪽 트레이드오프
  • emb dim이 어텐션 파라미터에 미치는 영향
  • 위치 임베딩이 emb dim을 공유하는 방식
