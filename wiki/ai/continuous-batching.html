연속 배칭 — 생성이 끝난 자리에 새 요청을 바로 채우는 스케줄링

연속 배칭 — 생성이 끝난 자리에 새 요청을 바로 채우는 스케줄링

범위: 이 문서는 연속 배칭의 일반 원리와 정적 배칭과의 차이, Prefill·Decode 혼합 시 고려할 선택 기준을 설명하며, 제시된 스케줄러와 수치 비교는 동작을 단순화한 개념 코드와 예시 계산이다. 특정 구현·버전에서의 실제 동작이나 처리량·지연 개선 폭은 코드와 실행 기록, 성능 측정을 별도로 확인해야 한다.

한 줄 요약: 연속 배칭(Continuous Batching)은 배치 내 한 요청이 생성을 끝내면 즉시 대기 큐의 새 요청으로 교체해, GPU가 놀지 않게 만드는 이터레이션 단위 스케줄링 기법이다.

연속 배칭 문제

LLM 서빙에서 여러 요청을 동시에 처리하려면 배칭이 필요하다. 가장 단순한 방식은 정적 배칭(static batching)이다. 요청 N개를 모아 배치를 만들고, 모든 요청이 생성을 끝낼 때까지 기다린 뒤 다음 배치를 시작한다.

문제는 요청마다 생성 길이가 다르다는 것이다. 한 요청이 10토큰만 생성하고 다른 요청이 500토큰을 생성하면, 10토큰짜리 요청은 490스텝 동안 GPU 자원을 차지만 하고 실제 연산은 하지 않는다. 패딩 토큰을 채워 넣어도 GPU는 그 자리의 attention 계산을 수행한다.

정적 배칭 — GPU 활용의 낭비:

스텝:  1   50  100  150  200  250  300
요청A: ███████████████████████████████  (300 토큰)
요청B: ████░░░░░░░░░░░░░░░░░░░░░░░░░  (50 토큰, 이후 대기)
요청C: ██████████░░░░░░░░░░░░░░░░░░░  (100 토큰, 이후 대기)

█ = 실제 연산   ░ = GPU 낭비 (패딩 또는 대기)
새 요청은 A가 끝날 때까지 시작할 수 없다.

연속 배칭은 이 문제를 해결한다. 매 이터레이션(디코딩 스텝)마다 배치 구성을 점검하고, 끝난 요청을 빼고 새 요청을 넣는다.

연속 배칭 변화

이터레이션 단위 스케줄링

정적 배칭은 배치 단위로 스케줄링한다. 배치가 끝나야 다음 배치가 시작된다. 연속 배칭은 이터레이션 단위로 스케줄링한다. 매 디코딩 스텝마다:

  1. EOS를 생성한 요청 또는 최대 길이에 도달한 요청을 배치에서 제거한다.
  2. 빈 슬롯에 대기 큐의 새 요청을 삽입한다.
  3. 새 요청이 들어오면 해당 요청의 Prefill을 수행한다.
  4. 기존 요청은 Decode를 계속한다.
연속 배칭 — 슬롯 재활용:

스텝:  1   50  100  150  200  250  300
슬롯0: AAA AAA AAA AAA AAA AAA AAA  (요청A: 300 토큰)
슬롯1: BBB DDD DDD DDD FFF FFF ···  (B→50에서 끝, D→150에서 끝, F 시작)
슬롯2: CCC CCC EEE EEE EEE GGG ···  (C→100에서 끝, E→250에서 끝, G 시작)

모든 슬롯이 항상 실제 연산을 수행한다.

정적 배칭 vs 연속 배칭

정적 배칭: 배치 내 가장 긴 요청이 전체 처리 시간을 결정한다. 짧은 요청이 많을수록 GPU 낭비가 커진다.

연속 배칭: 각 요청이 독립적으로 시작하고 끝난다. GPU 슬롯은 항상 활성 요청으로 채워진다. 처리량(throughput)이 정적 배칭 대비 2~20배 높아진다.

Prefill과 Decode의 혼합

연속 배칭에서 한 가지 까다로운 점은 Prefill과 Decode가 같은 배치에 섞인다는 것이다. Prefill과 Decode에서 봤듯 두 단계의 연산 특성이 다르다.

  • Prefill: 프롬프트 전체를 한 번에 처리. 큰 행렬곱. compute-bound.
  • Decode: 토큰 하나씩 생성. 작은 행렬곱. memory-bound.

새 요청이 슬롯에 들어오면 그 요청은 Prefill을 해야 하고, 기존 요청은 Decode를 계속한다. 같은 GPU forward pass에서 두 종류의 연산이 섞이면 간섭(interference)이 발생한다. Prefill의 큰 행렬곱이 Decode 요청의 지연(latency)을 늘린다.

이를 완화하는 전략:

  • Chunked Prefill: 긴 프롬프트의 Prefill을 여러 이터레이션에 걸쳐 나눈다. 한 번에 처리하는 Prefill 토큰 수를 제한해 Decode 요청에 미치는 영향을 줄인다.
  • Prefill 분리 스케줄링: Prefill 전용 GPU와 Decode 전용 GPU를 분리한다. 규모가 큰 서빙 시스템에서 사용한다.

연속 배칭 스케줄러 — 개념 코드

핵심은 step() 안에서 매 이터레이션마다 슬롯 구성을 갱신하는 것이다. 완료된 요청을 빼고 새 요청을 넣어 GPU 슬롯이 항상 활성 상태를 유지한다.

수치 비교 — 처리량 차이

설정: 배치 크기 4, 요청 8개
생성 길이: [30, 200, 50, 150, 80, 120, 40, 180]

정적 배칭:
  배치1: [30, 200, 50, 150] → 200 스텝 (가장 긴 요청에 맞춤)
  배치2: [80, 120, 40, 180] → 180 스텝
  총 스텝: 380, GPU 유효 연산: 30+200+50+150+80+120+40+180 = 850 토큰·스텝
  GPU 총 연산: 4×200 + 4×180 = 1520 토큰·스텝
  활용률: 850/1520 = 55.9%

연속 배칭:
  슬롯은 항상 활성 요청으로 채워진다.
  총 850 토큰을 생성하되, 4슬롯이 거의 항상 활성이다.
  대략 850/4 = 213 스텝에 모든 요청 완료.
  GPU 활용률: ~100% (슬롯 전환 오버헤드 제외)

처리량 개선: 380/213 = 약 1.8배

요청 간 생성 길이 편차가 클수록 연속 배칭의 이득이 커진다.

정리

연속 배칭은 LLM 서빙에서 GPU 활용률을 극대화하는 이터레이션 단위 스케줄링 기법이다. 정적 배칭이 가장 긴 요청에 맞춰 전체 배치를 기다리는 반면, 연속 배칭은 매 스텝마다 완료된 요청을 빼고 새 요청을 넣는다. 페이지드 어텐션과 함께 사용하면 KV 캐시 메모리를 효율적으로 관리하면서 동시에 처리량도 높일 수 있다.
