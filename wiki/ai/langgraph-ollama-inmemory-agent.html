LangGraph와 Ollama Agent의 State, Tool, InMemorySaver 실행 흐름

LangGraph와 Ollama Agent의 State, Tool, InMemorySaver 실행 흐름

터미널 질문이 Ollama 답변으로 바뀌는 동안 LangChain, LangGraph, Tool executor, Checkpointer는 서로 다른 책임을 맡는다. return {"messages": [response]}가 기존 대화를 지우지 않는 이유, Tool 결과가 다시 LLM으로 들어가는 이유, 같은 thread_id에서 체크포인트가 누적되는 이유를 하나의 실행 흐름으로 연결한다.

이 문서의 기준 예제는 src/langgraph_agent_lab/의 StateGraph 학습 코드다. 학습용 FunctionMessage와 ChatMessage는 실무 권장안이 아니라 메시지 타입 비교를 위해 의도적으로 포함한 장치다.

LangChain, LangGraph, Ollama의 책임 경계

구성 요소책임직접 하지 않는 일

Checkpointer체크포인트 저장·조회·삭제다음 Node를 판단하는 Agent 로직

ChatOllama는 학습 예제에서 새로 만든 클래스가 아니다. langchain-ollama가 제공하며 LangChain의 BaseChatModel 규격을 구현한다. 공급자가 바뀌면 ChatOpenAI, ChatAnthropic처럼 다른 adapter를 사용할 수 있지만 invoke()와 Message 중심 호출 방식은 비슷하다.

ChatOllama(...)는 연결할 서버와 모델을 설정한 객체를 만든다. validate_model_on_init=True이면 초기화 중 서버에 모델 존재 여부를 확인할 수 있지만 답변 생성은 하지 않는다. bind_tools(TOOLS)는 Tool 이름·설명·입력 schema가 결합된 호출 객체를 반환한다. 이 시점에 schema를 Ollama로 전송하거나 Tool을 실행하지 않으며, 실제 모델 요청은 뒤의 model.invoke()에서 전송된다.

graph.invoke()에서 END까지

builder.compile()은 Node와 Edge 정의를 실행 가능한 Graph 객체로 확정한다. Checkpointer가 있다면 실행 중 State를 저장하는 기능도 이때 결합된다.

터미널 입력은 LLM에 바로 전달되지 않는다. graph.invoke()가 Graph 실행을 시작하고 START Edge부터 순서대로 Node를 실행한다.

Tool 사용 경로는 execute_tools가 끝난 뒤 agent_decide로 돌아가는 루프다.

Node는 작업 함수이고 Edge는 Node 사이의 실행 순서다. START와 END는 일반 함수 Node가 아니라 Graph의 진입점과 종료점을 나타낸다.

AgentState와 부분 업데이트

AgentState는 Graph 전체에서 공유할 수 있는 필드의 schema다. TypedDict는 런타임 객체를 새로 만드는 클래스라기보다 딕셔너리의 예상 키와 타입을 표현한다.

total=False는 선언된 필드를 모든 딕셔너리에서 매번 요구하지 않는다는 뜻이다. Node가 자신이 바꿀 필드만 반환하는 부분 업데이트와 잘 맞는다. 새 필드 추가를 금지하는 옵션은 아니다.

이 문장은 Python 관점에서는 키 하나를 가진 일반 딕셔너리 반환이다.

Python 딕셔너리 문법 자체가 기존 State를 갱신하지 않는다. LangGraph 실행기가 Node 반환값을 받고 AgentState의 reducer 규칙으로 기존 State와 합친다.

flowchart LR
  node["1 agent_decide<br/>부분 dict 반환"]
  runtime["2 LangGraph runtime<br/>State schema 확인"]
  reducer["3 add_messages<br/>기존·새 메시지 병합"]
  state["4 갱신된 AgentState<br/>다음 Node 입력"]
  checkpoint["5 Checkpointer<br/>superstep 저장"]
  node --> runtime --> reducer --> state --> checkpoint

messages에는 add_messages reducer가 붙어 있으므로 새 메시지가 기존 목록과 병합된다.

개념적으로는 다음 처리와 비슷하다.

새 Message ID라면 뒤에 추가되고, 기존 ID와 같으면 해당 메시지가 갱신된다. 일반 필드는 reducer가 없으므로 Node가 새 값을 반환하면 교체된다.

여러 SystemMessage가 있어도 모두 같은 메시지 타입이다. 고정·임시 구분은 LangChain의 별도 타입이 아니라 애플리케이션이 ID와 생명주기로 만든 정책이다.

RemoveMessage도 Node 반환 목록에 들어가지만 최종 대화 내용으로 남는 메시지는 아니다. add_messages reducer가 타입과 ID를 읽고 동일한 ID의 기존 메시지를 제거한다.

이 명령은 스레드 전체를 지우지 않는다. temporary_message_id와 일치하는 메시지 하나만 최신 State에서 제거한다. 과거 체크포인트까지 소급 삭제하지도 않는다.

FunctionMessage는 ToolMessage보다 오래된 형식이며 tool_call_id가 없다. 여러 Tool 요청과 결과를 정확히 짝지어야 하는 신규 코드에서는 ToolMessage가 적합하다. 현재 예제의 FunctionMessage와 ChatMessage는 Message 종류를 보여주기 위한 기록일 뿐이며 실제 감사 기능으로는 일반 로그나 별도 State 필드가 더 자연스럽다.

LLM 호출 결과와 Tool 요청

실제 LLM 호출은 invoke()가 있는 줄이다.

messages_for_model(state)는 AgentState 전체를 모델에 보내지 않는다. SystemMessage, 요약, 최근 대화처럼 모델이 읽어야 할 Message만 고른다. response는 LLM이 반환한 AIMessage이며 두 형태가 가능하다.

@tool schema와 실제 Python 실행

add_numbers, explain_langgraph_term 같은 Tool은 LangChain 기본 Tool이 아니라 학습 예제에서 선언한 사용자 정의 Tool이다.

@tool은 함수 이름, docstring, 매개변수 이름과 타입을 읽어 Tool schema를 만든다. LLM은 Python 구현을 직접 읽거나 실행하지 않는다. 아래 값은 add_numbers.args_schema.model_json_schema()가 만든 인자용 JSON Schema다. bind_tools()가 모델을 호출할 때 adapter가 이 값을 callable 이름과 함께 공급자별 바깥 Tool 형식으로 감싸므로, 아래 JSON 자체가 Ollama에 전송되는 전체 payload는 아니다.

Tool schema의 내부 JSON을 외울 필요는 없지만 이름, 설명, 타입은 정확해야 한다. 설명이 모호하면 LLM의 Tool 선택도 흔들린다.

Tool 이름으로 실제 객체를 찾기 위한 딕셔너리는 컴프리헨션으로 만든다.

일반 반복문으로 풀면 같은 의미다.

실제 Tool 실행은 LLM이 아니라 execute_tools Node가 맡는다.

성공과 실패는 모두 ToolMessage로 변환된다. tool_call_id는 어떤 요청에 대한 결과인지 연결한다.

Tool 실행 후 Graph는 agent_decide로 돌아간다. LLM은 ToolMessage를 읽고 매개변수를 고쳐 재호출하거나, 다른 Tool을 고르거나, 실패를 설명하거나, 결과가 충분하면 최종 답변을 만든다.

실무에서는 이 선택을 LLM 재량에만 맡기지 않는다. 프롬프트는 판단 기준을 안내하고 코드가 최대 횟수, 권한, 승인, timeout과 종료 조건을 강제한다.

조건 Edge와 최종 경로 기록

agent_decide는 AIMessage만 State에 추가한다. 다음 Node는 Node 반환값이 아니라 조건 Edge의 routing 함수가 결정한다.

isinstance(last_message, AIMessage)가 True라면 not True는 False이므로 오류 조건을 통과한다. AIMessage가 아니면 isinstance가 False, not False가 True가 되어 예외가 발생한다.

현재 MAX_TOOL_ROUNDS는 3이다. tool_rounds가 0, 1, 2이면 Tool 실행 경로로 갈 수 있고, 이미 3회 실행한 뒤 LLM이 다시 Tool을 요청하면 tool_limit_response로 이동한다.

routing 함수의 문자열 반환값은 조건 Edge 매핑의 키다.

왼쪽은 route_after_agent()의 반환값이고 오른쪽은 실제 Node 이름이다.

record_direct의 route 필드는 다음 Node를 정하지 않는다.

"tools" if used_tool else "direct"는 Python 조건 표현식이다. 앞에서 Tool을 사용한 뒤 최종 AIMessage가 나온 경우에는 route="tools", 처음부터 직접 답한 경우에는 route="direct"를 기록한다. 두 경우 모두 실제 다음 Node는 고정 Edge인 finalize_response다.

저장된 대화와 모델 Context의 차이

Checkpointer에 저장된 전체 messages와 LLM에 전달하는 Context는 같은 범위가 아니다.

현재 예제는 FunctionMessage와 ChatMessage를 State에 저장하지만 Ollama 입력에서는 제외한다. 요약을 만들었다고 원본 메시지가 자동 삭제되는 것도 아니다. 저장량을 줄이려면 별도의 RemoveMessage 또는 retention 정책이 필요하다.

최근 세 turn이라는 범위는 LangGraph 기본값이 아니라 학습 예제의 애플리케이션 정책이다.

실제 범위 계산은 HumanMessage index를 찾은 뒤 세 번째로 최근 사용자 입력부터 끝까지 자르는 방식이다. 따라서 그 사용자 입력 뒤에 이어진 AIMessage와 ToolMessage도 함께 남는다.

thread_id는 OS thread, 터미널 프로세스, LLM 인스턴스 ID가 아니다. Checkpointer에서 한 대화의 State와 체크포인트 이력을 찾는 논리적 ID다.

같은 thread_id로 여러 번 invoke()하면 이전 최신 State를 불러와 새 입력과 병합한다. 새로운 thread_id를 쓰면 새 대화를 시작하지만 이전 thread 기록은 메모리에 남는다.

config는 개념적으로 RunnableConfig 타입이다. configurable은 런타임별 설정을 담는 약속된 상위 키이고, Checkpointer는 그 안의 thread_id를 요구한다. 그 밖의 대표 상위 키에는 tags, metadata, run_name, max_concurrency, recursion_limit이 있다. 임의의 값을 아무 상위 위치에 넣는 방식이 아니라 각 Runnable과 Checkpointer가 약속한 키를 사용해야 한다.

interrupt()와 터미널 입력 대기

터미널의 input() 대기와 LangGraph interrupt()는 다르다.

interrupt() 안의 딕셔너리는 UI나 호출자에게 전달할 질문 정보다. LLM이 자동으로 답을 듣는 프롬프트가 아니다. 애플리케이션이 사용자 입력을 받아 같은 thread_id로 재개해야 한다.

Checkpointer가 중단 위치를 저장하고 있으므로 Graph 객체의 별도 인스턴스 ID를 전달할 필요는 없다. thread_id와 체크포인트 정보가 이어서 실행할 위치를 찾는다.

Superstep과 자동 체크포인트

Superstep은 현재 실행 가능한 Node 묶음을 실행하고 결과를 한 번에 State에 반영하는 단위다. 순차 Graph에서는 보통 Node 하나가 하나의 superstep이다. 병렬 Node들은 같은 superstep에 포함될 수 있다.

flowchart TD
  ready["1 실행 가능한 Node 결정"]
  run["2 같은 superstep의 Node 실행"]
  collect["3 부분 State 업데이트 수집"]
  merge["4 reducer로 State 병합"]
  route["5 Edge·routing 함수<br/>다음 Node 결정"]
  save["6 Checkpointer.put()<br/>State와 next 저장"]
  ready --> run --> collect --> merge --> route --> save

조건 Edge 함수는 Node가 아니므로 routing 함수 실행만을 위한 별도 체크포인트는 없다. Node 반환값을 State에 병합한 뒤 routing 함수가 그 갱신된 State를 읽고 다음 Node를 고른다. 그 결과가 같은 superstep 체크포인트의 StateSnapshot.next에 저장된다.

현재 예제처럼 별도 durability를 주지 않으면 기본 async 방식으로 각 superstep의 변경을 저장하면서 다음 단계를 실행한다. sync는 저장 완료 뒤 다음 단계로 넘어가고, exit는 Graph가 끝날 때만 변경을 영속화한다. 저장 시점 보장이 필요한 실행에서는 이 차이를 별도 정책으로 정한다.

순차 direct 경로의 논리적 이력은 입력과 START 예약 단계까지 포함하면 다음과 같다.

END는 실행 함수가 아니므로 END 전용 스냅샷을 별도로 하나 더 만들지 않는다. 마지막 Node가 끝난 체크포인트가 최신 State다.

get_state()는 최신 스냅샷을 조회하고 새 체크포인트를 만들지 않는다. get_state_history()는 해당 thread의 체크포인트 이력을 반환한다.

thread_id는 체크포인트 이력 묶음을, checkpoint_id는 그 안의 특정 스냅샷 하나를 식별한다. checkpoint_id 없이 조회하면 최신값을 선택하고, 과거 스냅샷의 config를 사용하면 해당 시점을 조회한다.

update_state()는 수동 State 변경을 새로운 체크포인트로 기록한다.

수동 업데이트는 메모리를 줄이는 기능이 아니다. 기존 이력 뒤에 새 체크포인트를 추가한다. as_node는 단순 라벨이 아니라 다음 실행 위치에도 영향을 줄 수 있으므로 중단된 Graph에서 사용할 때는 실제 실행 의미를 맞춰야 한다.

LangGraph와 Checkpointer 인터페이스

LangGraph는 무엇을 언제 저장할지 알지만 어디에 어떻게 보관할지는 Checkpointer 구현에 맡긴다.

대표 인터페이스의 책임:

사용자는 BaseCheckpointSaver 계약을 구현해 다른 저장소와 직렬화 정책을 만들 수 있다. LangGraph는 구체 저장소의 테이블이나 메모리 딕셔너리를 직접 알 필요가 없다. “LangGraph가 아무것도 모른다”기보다는 논리적 체크포인트 규격은 알고 물리적 저장 방법은 모른다는 구분이 정확하다.

InMemorySaver의 물리 저장과 State 크기

논리적으로 각 체크포인트는 그 시점의 전체 State 스냅샷이다. 학습 예제의 사용자 State 관점에서는 channel을 messages, turn, route 같은 필드별 값과 갱신 규칙으로 이해할 수 있다. LangGraph 내부에는 실행과 분기를 위한 제어 channel도 있으므로 State 필드와 모든 channel이 완전히 일대일이라는 뜻은 아니다. version은 channel 값의 특정 버전을 식별하는 값이고, blob은 직렬화된 실제 값이다. 현재 InMemorySaver 구현은 new_versions로 전달된 channel 값을 새 blob으로 저장하고, 변경되지 않은 channel은 체크포인트의 version 참조를 재사용한다.

AgentState의 TypedDict 클래스 정의 자체를 체크포인트마다 복사하지는 않는다. 하지만 messages처럼 큰 필드가 매번 변경되면 새로운 version이 계속 생긴다. 누적 목록 전체가 새 channel 값으로 직렬화될 수 있으므로 대화가 길어질수록 저장량도 빠르게 커질 수 있다.

저장량 관리 기준:

  • 오래된 대화는 요약한 뒤 필요하면 원본 Message 제거
  • 큰 Tool 결과는 파일·객체 저장소에 두고 State에는 ID와 요약만 저장
  • 사용이 끝난 thread는 delete_thread()로 정리
  • 학습용 FunctionMessage, ChatMessage 누적 제거
  • 영속 저장소에서는 retention과 삭제 정책 별도 설계

InMemorySaver에는 고정 용량이나 LRU 방식 자동 퇴출을 기대하면 안 된다. 프로세스가 살아 있는 동안 기록이 누적되고, 프로그램을 종료하면 전체 기록이 사라진다.

새 thread_id를 발급하는 것은 새 대화를 시작하는 동작일 뿐 이전 기록을 지우지 않는다. delete_thread(thread_id)는 해당 ID 아래의 모든 체크포인트와 write를 제거한다. Python 객체는 해제되지만 운영체제가 표시하는 프로세스 RSS가 즉시 같은 크기만큼 줄어들지는 않을 수 있다.

Desktop AI의 디스크 저장과 OS Swap

Desktop AI가 대화 기록을 디스크에 내리고 다시 읽는 모습은 가상 메모리와 비슷해 보이지만 책임 주체가 다르다.

실제 Desktop AI는 전체 기록을 SQLite나 서버 DB에 보관하고, 현재 질문에 필요한 최근 대화·요약·검색 결과만 RAM과 LLM Context에 올리는 형태가 일반적이다. 모델 가중치의 memory mapping이나 CPU/GPU offloading은 대화 체크포인트와 별개의 계층이다.

Python 문법과 LangGraph 동작 구분

학습 중 LangGraph 기능처럼 보이지만 Python 자체 문법인 표현들이 있다.

코드Python 의미LangGraph와의 관계
state["messages"][-1]list의 마지막 원소가장 최근 Message라는 Graph 불변식에 의존
isinstance(value, AIMessage)타입 확인Node 경계 검증에 사용
not TrueBoolean 반전, 결과 Falserouting 조건 표현에 사용
state.get("turn", 0)키가 없으면 기본값 0부분 State 안전 조회
list[ToolMessage]list 원소 타입 힌트런타임 강제보다 IDE·type checker 지원
"tools" if used else "direct"조건 표현식경로 기록값 계산
{tool.name: tool for tool in TOOLS}dict 컴프리헨션Tool 이름 lookup 구성
input().strip()앞뒤 공백 제거터미널 입력 정리
text.lower()영문 소문자 변환종료 명령 비교
try/exceptPython 예외 처리입력·Tool 경계 실패 처리

argparse의 action="store_true"도 LangGraph 문법이 아니다. 명령줄에 옵션이 존재하면 해당 Namespace 필드를 True로 저장하라는 argparse API 규칙이다.

터미널 루프의 Ctrl+D는 입력 스트림 종료를 나타내 EOFError, Ctrl+C는 KeyboardInterrupt를 발생시킬 수 있다. strip()은 앞뒤 공백만 제거하고 lower()는 영문을 소문자로 바꾼다. 따라서 /exit 안녕하세요는 /exit와 정확히 일치하지 않아 종료 명령이 아니라 일반 질문으로 처리된다. 이 입력 처리는 Graph가 아니라 바깥의 Python CLI 책임이다.

현재 예제에서 실무 코드로 바꿀 부분

학습 예제는 Message 타입과 Graph 흐름을 한 번에 관찰하기 위한 목적이 강하다. 실무 전환 시에는 다음 경계를 다시 잡는다.

  • FunctionMessage 감사 기록
    • 구형 function-calling 학습 목적
    • 일반 로그나 audit State 필드로 이동
  • ChatMessage(role="auditor")
    • 실제 감사 로직 없이 문장만 기록
    • 검증 함수와 구조화된 감사 결과로 교체
  • Tool 오류 문자열
    • raw 예외 노출 방지
    • error_type, retryable, 안전한 사용자 메시지로 구조화
  • Tool 재시도
    • LLM 지시만으로 통제하지 않음
    • timeout, retry 횟수, 승인, 권한을 Graph와 executor에서 강제
  • 전체 Message 누적
    • 요약과 저장량 정리 정책 분리
    • Checkpointer retention과 모델 Context selection을 별도 설계

디버깅 순서

  1. prepare_messages 반환 직후
    • 두 SystemMessage, 새 HumanMessage, turn 확인
  2. agent_decide의 response
    • AIMessage.content와 tool_calls 확인
  3. route_after_agent
    • tool_calls 유무와 tool_rounds 확인
  4. execute_tools
    • tool_name, tool_call["args"], ToolMessage.status 확인
  5. 두 번째 agent_decide
    • Tool 결과를 읽은 최종 AIMessage 확인
  6. graph.get_state(config)
    • 최신 values, next, checkpoint_id 확인
  7. graph.get_state_history(config)
    • superstep별 State 변화 확인
