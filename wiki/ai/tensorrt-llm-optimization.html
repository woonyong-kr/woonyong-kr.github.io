TensorRT-LLM 최적화

TensorRT-LLM 최적화

한 줄 요약: TensorRT-LLM은 NVIDIA GPU에서 LLM 추론을 빠르게 실행하기 위해 attention kernel, batching, KV cache, quantization, parallelism을 묶어 제공하는 추론 엔진이다.

서비스 추론에서 생기는 비용

PyTorch로 모델을 그대로 실행하면 개발하기는 쉽다. 그러나 서비스 추론에서는 layer마다 Python runtime과 framework dispatch를 거쳐 일반 purpose kernel을 반복해서 호출하므로 낭비가 생긴다. 모델이 커지면 병목도 단순한 연산량에 머물지 않는다. GPU 메모리 이동과 kernel launch부터 KV cache 관리와 batch scheduling까지 함께 영향을 준다.

TensorRT-LLM은 NVIDIA GPU에서 이런 비용을 줄이기 위한 추론 엔진이다. 모델 구조를 엔진이 이해할 수 있는 형태로 바꾸고, GPU에 맞춘 kernel과 runtime으로 실행한다. 모델 정확도를 높이는 학습 기법이 아니라, 이미 학습된 모델을 특정 하드웨어에서 더 싸고 빠르게 실행하기 위한 배포 계층이다.

병목에 따라 달라지는 최적화

optimized attention kernel은 attention 계산을 GPU에 맞게 최적화한다. 이 과정에서는 KV cache 읽기, softmax, value 가중합에서 발생하는 메모리 접근을 줄이는 일이 중요하다.

in-flight batching은 실행 중인 요청 묶음에 새 요청을 동적으로 섞는다. 요청을 고정된 batch로만 처리할 때 생기는 빈 슬롯 낭비를 줄이기 위한 방식이다.

paged KV cache는 KV cache를 블록 단위로 관리한다. 요청마다 필요한 cache 크기가 달라질 때 발생할 수 있는 메모리 단편화를 줄이는 데 초점을 둔다.

quantization은 FP8, INT8, INT4 계열처럼 더 낮은 비트 표현을 사용한다. 모델 실행에 필요한 메모리와 bandwidth를 줄이는 선택이다.

parallelism은 큰 모델을 여러 GPU에 나누는 방법이다. tensor, pipeline, expert parallelism 등을 사용할 수 있다.

모델을 요청 처리까지 연결하는 흐름

이 흐름에서는 무엇을 얼마나 빠르게 만들 것인지 먼저 판단해야 한다. latency가 문제라면 작은 batch와 kernel 최적화가 중요하다. throughput이 문제라면 in-flight batching과 KV cache capacity를 살펴본다. GPU 메모리가 문제라면 quantization과 parallelism을 먼저 검토한다.

일반 PyTorch 추론과의 차이

일반 PyTorch 추론에서는 framework가 layer별 연산을 순서대로 호출하고, 서빙에 필요한 batch 재구성이나 KV cache, streaming을 별도로 붙여야 한다. TensorRT-LLM은 GPU에 맞춘 실행 경로와 함께 이러한 서빙 기능을 제공한다. 따라서 두 방식의 차이는 모델 자체보다 추론과 요청 처리를 구성하는 배포 계층에서 드러난다.
