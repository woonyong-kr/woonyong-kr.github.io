Amazon Bedrock Agent, Flow, Guardrails 실습 가이드

한 줄 요약: Bedrock에서 Agent가 무엇을 판단하고 Lambda가 무엇을 실행하며 Flow와 Guardrail이 어디에 붙는지를 기준으로, 문서 검색을 넘어 도구 호출과 실행 순서 고정, 안전 경계까지 묶는 구조를 정리한다.

Bedrock Agent 실습은 Knowledge Base로 답변 근거를 찾는 단계를 넘어, LLM이 도구를 호출해 계산하거나 외부 데이터를 조회하게 만드는 과정이다. Flow는 여러 노드를 명시적으로 연결해 실행 순서를 고정하고, Guardrails는 모델 입출력의 안전 경계를 둔다.

이 문서는 Bedrock 실습 후반부의 판단 구조를 정리한다. 세부 콘솔 화면보다 “Agent가 무엇을 판단하고, Lambda가 무엇을 실행하고, Flow와 Guardrail이 어디에 붙는가”를 기준으로 읽는다.

Amazon Bedrock Agent 필요성

  • RAG만으로는 문서를 찾아 답할 수 있지만, 계산이나 업무 처리는 어렵다.
  • Agent는 질문을 보고 Knowledge Base를 조회할지, Lambda action을 호출할지 선택한다.
  • Flow는 Agent에게 모든 판단을 맡기지 않고, 입력과 조건, 프롬프트, Lambda, Agent 호출 순서를 그래프로 고정한다.
  • Guardrails는 금지 주제, 민감정보, 부적절한 내용, 근거 부족 답변을 제어하는 운영 안전장치다.

Amazon Bedrock Agent 흐름

Agent를 만들었다고 끝이 아니다. 수정한 뒤에는 Prepare를 다시 해야 테스트 런타임에 반영된다.

1단계: Agent 만들기

  • Agent
    • 이름: mortgage-processing-agent
    • service role: 새로 만들거나 workshop 제공 role 사용
    • model provider: Anthropic
    • model: Claude 3 Sonnet 계열
  • Instruction
    • 역할을 명확히 쓴다.
    • 예: 모기지 신청 처리, 대출 가능성 판단, 주택 정보 조회, Fannie Mae 관련 지침 참고.
  • 저장
    • 콘솔에서 Agent instruction을 입력한 뒤 반드시 Save를 누른다.
    • Save 없이 다음 단계로 가면 action group 추가나 prepare에서 설정이 빠질 수 있다.

2단계: Action Group 붙이기

Action group은 Agent가 호출할 수 있는 도구 묶음이다. Bedrock은 API schema를 보고 어떤 입력을 Lambda에 넘겨야 하는지 이해한다.

  • 대출 계산 action group
    • 이름: loan-calculation
    • Lambda: workshop이 만든 loan calculator 함수
    • API schema: S3의 loan_calculator.json
  • 부동산 정보 조회 action group
    • 이름: mls-lookup
    • Lambda: workshop이 만든 MLS lookup 함수
    • API schema: S3의 mls_lookup.json

3단계: Knowledge Base 연결

  • Agent에 앞서 만든 Knowledge Base를 연결한다.
  • instruction에는 “정책, FAQ, 가이드라인은 Knowledge Base를 근거로 답하라”는 식의 기준을 둔다.
  • Knowledge Base만으로 답할 질문과 action group이 필요한 질문을 나눠 테스트한다.

예시:

  • Knowledge Base 중심
    • What are the specific eligibility criteria for Fannie Mae-backed loans for single-family homes?
  • Knowledge Base와 도구 호출 결합
    • I make 70K per year. Can I afford to buy the property listed under MLS-5678. Do I qualify for any special programs for Fannie Mae backed loans?

4단계: Prepare와 Trace 확인

  • Agent 수정 후 Prepare를 누른다.
  • 테스트 창에서 질문을 던진다.
  • Show trace를 열어 확인한다.

Trace에서 봐야 할 것:

  • Agent가 Knowledge Base를 조회했는가
  • 어떤 action group을 골랐는가
  • Lambda 입력 파라미터가 맞는가
  • Lambda 결과를 최종 답변에 어떻게 사용했는가
  • 실패했다면 retrieval 실패인지 Lambda 실패인지 권한 실패인지 나뉘는가

5단계: Flow 만들기

Flow는 Agent의 자율 판단을 보완해 실행 그래프를 직접 만든다.

  • Flow
    • 이름: process-mortgage-application-flow
    • role: workshop이 제공한 Prompt Flow role 또는 새 role
    • encryption: 기본 AWS 관리형 key 사용
  • 기본 선 제거
    • 기본 Flow input에서 Flow output으로 바로 이어지는 선을 제거한다.
  • input type
    • Flow input의 output type을 Object로 맞춘다.
  • 노드
    • Lambda node
    • Condition node
    • Prompt node
    • Agent node

Flow는 “모델에게 알아서 해”보다 재현성이 높다. 업무 프로세스가 정해져 있으면 Flow가 유리하고, 사용자의 요청이 다양하면 Agent가 유리하다.

6단계: Guardrails 만들기

  • Guardrail
    • 이름: bedrock-ws-guardrails
    • 기본 차단 메시지: 모델이 답할 수 없음을 사용자에게 알려 주는 문장
    • encryption: 기본 AWS 관리형 key
  • 설정 영역
    • content filters
    • denied topics
    • word filters
    • sensitive information filters
    • contextual grounding
  • 연결
    • Agent나 테스트 대상 모델에 guardrail을 붙인다.
    • 차단되는 입력과 허용되는 입력을 둘 다 테스트한다.

Guardrail은 답변 품질을 높이는 장치가 아니라 운영 경계를 세우는 장치다. 금지 주제, 민감정보, 정책 위반 가능성을 줄이는 용도로 본다.

7단계: Multi-Agent Collaboration

워크숍 후반부의 multi-agent는 역할 분담을 이해하는 데 초점을 둔다.

  • intent classification agent
    • 사용자 요청의 종류를 분류한다.
  • technical specialist
    • 기술적 세부 질문을 맡는다.
  • policy specialist
    • 정책과 가이드라인 해석을 맡는다.
  • supervisor
    • 하위 agent를 조율하고 최종 응답을 만든다.

단일 Agent가 모든 역할을 갖는 것보다, 책임을 나누면 trace와 테스트가 쉬워진다. 대신 orchestration 비용과 복잡도는 늘어난다.

자주 막히는 지점

  • Agent가 수정한 내용을 반영하지 않는다
    • Save와 Prepare를 모두 했는지 확인한다.
  • Lambda action이 호출되지 않는다
    • instruction이 도구 사용 조건을 충분히 명확히 했는지 본다.
    • API schema S3 경로와 Lambda 권한을 확인한다.
  • Knowledge Base를 안 쓴다
    • Agent의 KB instruction이 약할 수 있다.
    • 질문이 문서 검색이 필요한 형태인지 확인한다.
  • Guardrail이 너무 많이 막는다
    • denied topic과 word filter가 과하게 넓은지 확인한다.
    • 차단 테스트와 정상 테스트를 분리한다.
