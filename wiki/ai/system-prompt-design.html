시스템 프롬프트 설계 (System Prompt Design)

한 줄 요약: 시스템 프롬프트 설계는 모델이 대화 전체에서 지킬 역할·경계·출력 규칙·안전 조건을 매 요청 작업 지시보다 위에 고정하는 일로, 사용자 요청이 바뀌어도 서비스의 금지 행동과 도구 사용 기준이 흔들리지 않게 만든다.

사용자 요청은 대화마다 달라지지만, 서비스의 역할과 금지 행동까지 그때마다 바뀌어서는 안 된다. 시스템 프롬프트 설계는 모델이 대화 전체에서 지켜야 할 역할, 경계, 출력 규칙, 안전 조건을 개별 작업 지시보다 상위의 기본 조건으로 정하는 일이다.

시스템 프롬프트가 필요한 이유

시스템 프롬프트는 답변 형식과 도구 사용 기준처럼 모든 요청에 공통으로 적용할 규칙을 고정한다. 학습 튜터 앱이라면 사용자가 “짧게 말해”라고 요청해도 최소한의 안전 설명과 근거 구분을 유지해야 한다. 코드 리뷰 Agent라면 사용자가 “그냥 고쳐”라고 해도 실제 파일을 수정하기 전에 변경 범위와 위험을 확인해야 한다.

이처럼 시스템 프롬프트는 “무슨 답을 만들지”보다 “어떤 방식으로 일할지”를 정한다. 실제 과업의 내용은 사용자 메시지와 검색 결과, 도구 결과가 채운다.

학습 튜터의 시스템 프롬프트 예시

이 예시는 역할뿐 아니라 설명 방식, 도구 사용 경계, 불확실한 내용을 다루는 기준까지 함께 정한다. 따라서 개별 요청이 달라져도 학습 튜터가 일하는 방식은 일관되게 유지할 수 있다.

규칙을 어디에 둘지 판단하는 기준

모든 요청에서 지켜야 하는 규칙은 시스템 프롬프트 후보가 된다. 이번 요청에만 필요한 조건이라면 사용자 프롬프트나 작업 지시로 충분하다.

출력 모양을 기계적으로 보장해야 할 때는 시스템 프롬프트만으로 부족할 수 있으므로 구조화 출력을 함께 검토한다. 외부 도구를 호출해야 한다면 도구 설명, 호출 조건, 권한 경계를 시스템 규칙에 넣고 실제 실행은 executor가 맡는다.

규칙이 많아져 서로 충돌한다면 우선순위와 예외 조건을 줄여야 한다. 그런 다음 테스트 질문을 사용해 규칙이 실제 출력에 어떻게 반영되는지 확인한다.

흔한 실패

역할만 정하고 금지 조건을 두지 않으면 행동의 경계가 모호해진다. “친절한 튜터”라고만 쓰는 경우에는 출처 없는 단정이나 과한 추측을 막기 어렵다.

출력 형식만 정하고 판단 기준을 빼면 모양은 맞아도 내용이 흔들릴 수 있다. JSON 형식은 지키더라도 어떤 값을 넣어야 하는지가 명확하지 않기 때문이다.

도구 권한을 구분하지 않으면 읽기 도구와 쓰기 도구의 위험이 같은 수준으로 취급된다. 도구를 사용하는 시스템 프롬프트에는 호출 조건뿐 아니라 권한 경계도 함께 명시해야 한다.
