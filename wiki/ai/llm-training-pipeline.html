LLM 구현 파이프라인

LLM을 바닥부터 구현할 때는 토크나이저, attention, Adam을 따로 외우기보다 “텍스트를 다음 token 예측 문제로 바꾸고, 틀린 예측을 줄이도록 모델을 고친다”는 한 흐름으로 먼저 연결해 두는 편이 낫다.

먼저 텍스트를 예측 문제로 바꾼다

모델은 문자열 자체를 계산하지 못하므로 토크나이저가 텍스트를 token ID로 바꾼다. 그다음 dataset과 dataloader는 token ID 열의 앞부분을 입력으로 자르고, 바로 다음 token을 정답으로 둔 여러 학습 예제를 만든다.

예를 들어 나는 오늘 다음에 공부한다가 오는 문장이라면, 입력은 앞 token들이고 정답은 한 칸 오른쪽으로 민 token들이다. 이 한 칸 차이가 모델이 “다음에 무엇이 올까”를 배우게 하는 기준이므로, tokenization과 batch 구성이 맞지 않으면 뒤의 Transformer와 optimizer를 아무리 잘 만들어도 학습이 어긋난다.

모델은 다음 token의 후보 점수를 만든다

입력 token ID는 embedding에서 벡터가 되고, 위치 인코딩이 더해져 순서 정보까지 갖게 된다. 이 벡터는 self attention, multi head attention, Transformer block을 지나면서 앞 token들을 참고해 다음 token의 후보 점수인 logits를 만든다.

여기서 logits는 아직 선택된 단어가 아니라 각 token이 다음 자리에 올 가능성을 비교하기 위한 점수다. 그래서 이 단계만으로는 모델이 맞게 배웠는지 알 수 없고, 바로 뒤에서 정답 token과 비교해야 한다.

틀린 예측을 손실로 바꾸고 다시 고친다

cross entropy loss는 모델이 낸 logits와 실제 다음 token을 비교해, 정답에 낮은 점수를 줬을수록 큰 손실을 만든다. 역전파는 이 손실을 줄이려면 embedding과 Transformer 안의 어떤 가중치를 어느 방향으로 바꿔야 하는지 계산하고, Adam 같은 optimizer가 그 계산을 반영한다.

한 번의 update가 곧바로 좋은 문장을 만드는 것은 아니다. 같은 흐름을 많은 batch에서 반복하면서 손실이 줄어드는지, 검증 데이터에서도 결과가 유지되는지, 과적합을 막는 장치가 필요한지를 함께 확인해야 한다.

학습한 모델은 한 token씩 이어서 만든다

생성할 때는 현재 prompt를 모델에 넣고 logits에서 다음 token 하나를 고른 뒤, 그 token을 prompt 끝에 붙여 다시 예측한다. 이 과정을 반복하면 문장이 길어지지만, 매번 이전 token 전체를 처음부터 다시 계산하면 느려진다.

KV cache는 attention이 이미 계산한 이전 token의 key와 value를 보관해 이 중복 계산을 줄인다. 따라서 학습 파이프라인을 이해한 뒤에는 “학습 때의 한 batch 예측”과 “서비스에서 한 token씩 생성하는 추론”이 같은 모델을 서로 다르게 사용하는 장면이라는 점을 구분할 수 있다.

막힌 단계에서 다시 찾는 순서

이 페이지는 모든 구현을 한 번에 대신하는 코드 문서가 아니라, 지금 어디가 막혔는지 찾는 지도다. 입력 shape가 맞지 않으면 tokenization과 dataloader를, attention 값이 이상하면 embedding과 Transformer block을, loss가 줄지 않으면 cross entropy와 optimizer를, 생성이 느리면 KV cache를 먼저 확인하면 된다.

실제 구현을 따라가려면 미니 GPT 노트북과 연결 노트를 함께 열면 된다. 이 문서를 다시 찾을 때는 “텍스트가 학습 batch와 다음 token 정답으로 바뀌는 곳은 어디인가?”와 “손실이 어떤 경로로 파라미터를 고치는가?”라는 두 질문으로 현재 단계를 찾으면 된다.
