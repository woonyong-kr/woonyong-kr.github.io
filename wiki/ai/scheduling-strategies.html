LLM 서빙 스케줄링 전략

한 줄 요약: LLM 서빙 스케줄링은 대기 요청 중 무엇을 이번 GPU 실행 step에 넣을지 정하는 정책으로, 처리량·지연·공정성을 함께 조절한다.

LLM 서빙 스케줄링은 대기 중인 요청 중 무엇을 이번 GPU 실행 step에 넣을지 정하는 정책이다.

LLM 서빙 스케줄링 전략 구분

LLM 추론 서버에는 요청이 계속 들어온다. 각 요청은 입력 길이, 생성 길이, 우선순위, 남은 토큰 수가 다르다. 단순히 먼저 온 요청부터 순서대로 처리하면 GPU가 비거나, 짧은 요청이 긴 요청 뒤에서 오래 기다리거나, 긴 prompt의 prefill이 짧은 decode 요청의 지연 시간을 밀어낼 수 있다.

스케줄러가 조절하는 핵심은 세 가지다.

  • 처리량
    • GPU 슬롯을 최대한 비우지 않는다.
  • 지연 시간
    • 한 요청이 첫 토큰을 받을 때까지의 시간과 전체 완료 시간을 줄인다.
  • 메모리
    • KV cache가 GPU 메모리를 넘지 않게 요청 수와 길이를 제한한다.

요청 큐가 다음처럼 쌓였다고 하자

요청 큐가 다음처럼 쌓였다고 하자.

모두 같은 방식으로 처리하면 A의 긴 prefill이 B의 짧은 응답까지 늦출 수 있다. 반대로 B 같은 짧은 요청만 우선하면 C 같은 긴 요청은 계속 밀릴 수 있다.

그래서 서빙 스케줄러는 매 step마다 이런 결정을 내린다.

자주 나오는 전략

  • 정적 배칭
    • 처음 묶은 batch가 끝날 때까지 구성을 바꾸지 않는다.
    • 구현은 단순하지만 긴 요청 하나가 batch 전체를 끌고 간다.
  • 동적 배칭
    • 실행 중에도 요청을 추가하거나 제거한다.
    • 요청 길이가 들쭉날쭉한 서비스 트래픽에 더 강하다.
  • 연속 배칭
    • decode iteration마다 끝난 요청을 빼고 새 요청을 넣는다.
    • 연속 배칭에서 상세 흐름을 본다.
  • chunked prefill
    • 긴 prompt prefill을 여러 조각으로 나눠 decode 지연을 줄인다.
    • Prefill과 Decode의 병목 차이와 연결된다.
  • 메모리 기반 admission
    • KV cache 여유가 있을 때만 새 요청을 받는다.
    • 페이지드 어텐션처럼 cache를 블록 단위로 관리하는 방식과 함께 본다.

정리

  1. 서빙 스케줄러는 매 GPU step마다 “어떤 decode를 유지하고, 새 prefill을 몇 토큰 넣고, 빈 슬롯에 무엇을 채울지”를 정해 처리량·지연·메모리를 동시에 조절한다.
  2. 긴 prompt의 prefill이 짧은 decode의 첫 토큰 지연을 밀어내는 것이 핵심 충돌이라, chunked prefill·연속 배칭이 이 충돌을 푼다.
  3. KV cache가 GPU 메모리를 넘지 않게 admission으로 요청 수·길이를 제한하는 것이 정적 배칭과 갈리는 지점이다.

직접 확인하려면 prompt 2000·생성 200 요청과 prompt 20·생성 20 요청을 같은 batch에 섞었을 때 어느 정책에서 짧은 요청의 첫 토큰 지연이 줄어드는지 따져 본다.
