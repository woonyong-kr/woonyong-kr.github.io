SFT 데이터 품질 — 명령어 튜닝의 성능을 결정하는 데이터 기준

SFT 데이터 품질 — 명령어 튜닝의 성능을 결정하는 데이터 기준

확인 범위: 이 문서는 SFT 데이터 품질의 일반 원리와 선택·점검 기준을 설명한다. 제시된 코드는 그 원리가 특정 구현에 어떻게 반영되었는지 보여주는 예시다. 코드의 실제 동작과 데이터·모델별 성능은 해당 코드, 라이브러리 버전, 실행 기록과 성능 측정을 별도로 확인해야 한다.

한 줄 요약: SFT(Supervised Fine-Tuning)에서는 데이터의 양뿐 아니라 개별 (지시, 답변) 쌍의 정확성, 형식 일관성, 다양성을 함께 살펴야 한다.

데이터 규모보다 먼저 품질을 보는 이유

명령어 튜닝은 사전학습된 모델에 (지시, 답변) 쌍을 보여주고 답변 구간의 다음 토큰 예측 loss를 최소화한다. 학습 메커니즘은 사전학습과 같은 cross-entropy지만 사용하는 데이터는 다르다. 이 문서에서 비교하는 사전학습 데이터는 수조 토큰 규모의 웹 텍스트이고, SFT 데이터는 수천~수만 건의 (지시, 답변) 쌍이다.

SFT 데이터의 규모가 상대적으로 작으면 개별 샘플이 모델 행동에 미치는 영향도 커진다. LIMA 논문(Zhou et al., 2023)은 1,000건의 고품질 데이터로 GPT-4 수준에 가까운 지시 수행 능력을 달성했다고 보고했다. 반면 이 문서에 정리된 비교에서는 5만 건의 저품질 데이터로 학습한 모델이 형식은 따르지만 답변의 정확성과 유용성은 떨어졌다.

이 결과는 LIMA가 제시한 “Superficial Alignment Hypothesis”와 연결된다. 이 관점에서 SFT는 새로운 지식을 대량으로 주입하기보다 사전학습에서 배운 능력을 적절한 응답 형식으로 꺼내도록 행동을 조정한다. 따라서 이 문서가 다루는 범위에서는 학습 예시가 정확하고 일관적인지가 데이터 건수만큼 중요하다.

사전학습과 SFT의 차이는 책 읽기와 고객 응대 연습에 비유할 수 있다. 사전학습이 수만 권의 책을 읽는 과정이라면, SFT는 고객 응대 매뉴얼의 예시를 따라 연습하는 과정에 가깝다. 매뉴얼이 길어도 잘못된 예시가 섞여 있으면 응대 품질이 떨어질 수 있다. 반대로 분량이 짧더라도 예시가 정확하고 일관적이면 필요한 행동을 익히는 데 도움이 된다. 이 비유는 품질의 중요성을 설명하기 위한 것이며, 특정 데이터 양이 언제나 충분하다는 뜻은 아니다.

품질을 판단하는 세 축

SFT 데이터는 정확성, 형식 일관성, 다양성의 세 축으로 살펴볼 수 있다.

  • 정확성 (Accuracy)
    • 답변의 사실이 맞는가
    • 코드가 실행 가능한가
    • 수학 풀이가 올바른가
    • 환각(hallucination)이 없는가
  • 형식 일관성 (Format Consistency)
    • 채팅 포맷 템플릿을 일관되게 따르는가
    • 역할 구분자(system, user, assistant)가 정확한가
    • 답변 길이와 스타일이 과업 유형에 맞는가
  • 다양성 (Diversity)
    • 지시 유형이 요약, 번역, 코드, 비교, 추론 등으로 충분히 다양한가
    • 입력 도메인이 한쪽으로 편향되지 않았는가
    • 답변 길이의 분포가 자연스러운가

세 축은 서로 다른 문제를 가리킨다. 사실이 맞아도 포맷이 흔들리면 모델이 일정한 응답 구조를 배우기 어렵다. 포맷이 일정해도 같은 패턴이 반복되면 다양한 입력에 대응하는 예시가 부족해진다.

데이터 양과 품질을 다룬 사례

이 문서에 정리된 연구와 데이터셋의 조건은 서로 같지 않다. 따라서 아래 결과만으로 모든 SFT에서 적은 데이터가 더 낫다고 일반화할 수는 없다. 각 사례는 고품질 수작업 데이터와 대규모 자동 생성 데이터가 어떤 장점과 한계를 보였는지 비교하는 근거로 읽어야 한다.

  • LIMA (Zhou et al., 2023)
    • 1,000건의 수작업 고품질 데이터
    • 65B LLaMA 기준 GPT-4(text)와 비교 가능한 응답 품질
    • “Superficial Alignment Hypothesis”를 제시하며 SFT가 사전학습에서 배운 능력의 표면적 형식을 조정한다고 설명
  • Alpaca (Taori et al., 2023)
    • GPT-3.5로 자동 생성한 52K 건의 instruction 데이터
    • 7B LLaMA를 빠르게 지시 수행 모델로 전환
    • 자동 생성 데이터의 유용성과 함께 환각 및 형식 불일치 문제를 제시
  • Dolly 2.0 (Databricks, 2023)
    • 직원이 수작업으로 만든 15K 건
    • 이 문서에 정리된 결과에서는 수작업 데이터가 자동 생성 데이터보다 답변 정확성에서 우위

이 사례들은 데이터 건수만 늘리는 전략의 한계를 보여준다. 다만 수천 건의 정확하고 다양한 데이터가 언제나 수만 건의 자동 생성 데이터보다 낫다고 단정하려면 동일한 모델, 과업, 평가 조건에서 별도 검증이 필요하다.

SFT 데이터가 표현되는 방식

밑바닥 LLM 책(Ch7)에서 사용하는 Alpaca 포맷은 세 필드로 구성된다.

instruction은 과업 지시, input은 처리할 데이터, output은 정답 답변이다. input은 비어 있을 수도 있다.

채팅 모델은 message 배열 형식을 사용한다.

두 형식은 구조가 다르지만 지시와 답변의 경계가 명확해야 하고 답변이 정확해야 한다는 기준은 같다.

데이터를 만들고 검수할 때 묻는 질문

먼저 지시만 읽고 무엇을 어떤 형식으로 답해야 하는지 알 수 있는지 확인한다. “이것에 대해 써라”처럼 대상과 형식이 드러나지 않는 지시는 모호하다. “다음 텍스트를 3문장으로 요약해라.”처럼 대상과 출력 조건을 함께 제시하면 판단 기준이 분명해진다.

답변은 지시의 조건과 맞아야 한다. 3문장 요약을 요청했는데 5문장으로 답하거나, 한국어를 요청했는데 영어가 섞이면 지시와 답변이 일치하지 않는다. 사실 오류도 따로 확인해야 한다. 코드에는 문법 오류가 없는지, 날짜·수치·인물 정보는 맞는지 살펴본다.

같은 유형의 지시에는 답변 스타일과 특수 토큰, 역할 구분자를 일관되게 적용한다. 동시에 같은 패턴의 (지시, 답변) 쌍이 불필요하게 반복되지 않는지도 확인한다. 반복이 많아지면 데이터 건수는 늘지만 다양성은 낮아질 수 있다.

코드에서 확인하는 데이터 품질 처리

밑바닥 LLM 레포의 src/finetune.py에는 NSMC(Naver Sentiment Movie Corpus) 감성 분류 데이터를 처리하는 make_sentiment_dataset이 포함되어 있다. 분류 과업을 위한 코드지만, 원본 읽기, 품질 필터, 분할로 이어지는 데이터 준비 흐름을 보여준다.

빈 입력과 잘못된 label 거르기

품질 필터는 if not text or label not in {"0", "1"}에 들어 있다. 빈 리뷰와 label이 손상된 행을 같은 조건에서 제외한다. make_sentiment_dataset은 남은 결과를 셔플한 뒤 val_ratio에 따라 train/val로 나눈다. SFT 데이터에 이 흐름을 적용할 때는 지시와 답변의 정확성, 포맷, 중복까지 과업에 맞게 더 세밀하게 검사해야 한다.

near-duplicate 제거하기

다양성을 낮추는 직접적인 요인 가운데 하나는 near-duplicate(거의 같은) 샘플이다. 밑바닥 LLM 책의 유틸리티는 단순 문자열 비교 대신 TF-IDF 벡터의 코사인 유사도로 샘플이 비슷한 정도를 계산한다.

analyzer="char"는 글자 단위 n-gram을 사용한다. 이 설정은 띄어쓰기나 어순이 조금 달라진 변형의 유사도를 계산하는 데 쓰인다. threshold를 1에 가깝게 올리면 더 비슷한 쌍만 중복으로 판정하고, 낮추면 더 느슨하게 묶는다.

제시된 조건에서는 key in ("input", "output")일 때만 뒤쪽 항목을 제거 대상으로 표시한다. 따라서 instruction 자체는 제거 대상에서 제외되고 input이나 output이 겹칠 때 뒤 항목을 버린다. 같은 지시라도 입력이 다르면 유효한 샘플일 수 있기 때문이다. 다만 이 코드가 실제 데이터에서 어떤 샘플을 제거하는지는 입력과 threshold를 사용해 별도로 확인해야 한다.

동일한 템플릿으로 토큰화하기

필터링을 통과한 데이터는 채팅 포맷 템플릿에 따라 토큰 시퀀스로 변환된다. 밑바닥 LLM 책은 Alpaca 스타일 프롬프트를 format_input으로 만들고 InstructionDataset에서 미리 토크나이징한다.

프롬프트는 고정 서문, ### Instruction, 선택적인 ### Input, ### Response 순서로 구성된다. 책의 실제 템플릿에는 개념 코드의 ### Instruction: 앞에 고정 서문이 한 줄 더 붙는다. InstructionDataset은 모든 샘플을 같은 format_input으로 직렬화해 형식이 샘플마다 달라지지 않도록 한다.

길이 제한과 loss 범위는 format_input이 아니라 collate 단계에서 처리한다.

이 구현은 loss 범위를 0/1 마스크로 제어하지 않는다. 첫 패딩(EOS) 뒤의 패딩 타깃을 -100(ignore_index)으로 바꾸고, PyTorch cross_entropy가 기본값인 ignore_index=-100을 무시하도록 한다. 자세한 메커니즘은 명령어 튜닝에서 다룬다.

allowed_max_length가 지정되면 inputs와 targets가 같은 길이에서 잘린다. 그 결과 답변 일부가 사라질 수 있으므로, 긴 답변 과업에서는 한도를 충분히 설정하거나 잘리는 샘플을 미리 제외해야 한다. 실제로 어떤 샘플이 잘리는지는 토큰화 결과와 설정값을 확인해야 한다.

배치 한 개의 shape는 다음 순서로 변한다.

  • 원본 토큰 리스트 (가변 길이)
  • 샘플 A: [t0 t1 t2] len=3
  • 샘플 B: [t0 t1 t2 t3 t4] len=5
  • EOS(50256) 추가 + batch_max_length(=6)까지 패딩
  • A: [t0 t1 t2 EOS P P] B: [t0 t1 t2 t3 t4 EOS] (each len=6)
  • inputs=padded[:-1], targets=padded[1:]
  • inputs : (B=2, T=5) ← 모델 입력
  • targets: (B=2, T=5) ← 한 칸 시프트, 둘째 패딩부터 -100
  • torch.stack → 디바이스 이동
  • (2, 5) 텐서 2개 → GPTModel → logits (2, 5, vocab)

품질 기준을 실제 데이터에 적용하기

SFT 데이터를 검토할 때는 먼저 지시와 답변이 정확한지 확인하고, 이어서 포맷이 일관적인지와 샘플 구성이 충분히 다양한지를 살펴본다. 코드 수준에서는 빈 필드와 잘못된 label을 걸러내고, near-duplicate를 점검하며, 토큰화 뒤 길이 제한으로 답변이 잘리지 않는지 확인할 수 있다.

LIMA, Alpaca, Dolly 2.0 사례는 고품질 수작업 데이터와 자동 생성 데이터의 특성이 다를 수 있음을 보여준다. 그러나 어느 정도의 데이터가 충분한지, 수작업 데이터가 자동 생성 데이터보다 나은지는 모델과 과업, 평가 조건에 따라 다시 검증해야 한다. 이 문서의 기준은 데이터 선택과 점검을 시작하는 틀이며 특정 데이터셋의 성능을 보장하는 결과는 아니다.
