GPU 메모리 관리

GPU 메모리 관리

범위: 이 문서는 GPU 메모리의 주요 소비원과 대략적인 산정 원리, 절약 기법의 선택 기준을 설명하는 개념 자료이며, 제시된 코드와 수치는 특정 설정에 따른 계산 예시다. 실제 메모리 요구량과 기법의 효과는 구체적인 구현·정밀도·옵티마이저·버전 및 실행 기록과 성능 측정을 통해 별도로 검증해야 한다.

한 줄 요약: LLM 학습 시 GPU 메모리는 모델 파라미터, 기울기, 옵티마이저 상태, 활성값(activation) 네 가지가 나눠 쓰며, 각각의 크기와 절약 기법을 알아야 OOM 없이 학습할 수 있다.

GPU 메모리 관리 구분

GPT 모델을 학습하려면 GPU 메모리에 모델 전체를 올려야 한다. 그런데 모델 가중치만 올리면 끝이 아니다. 역전파를 위한 기울기, Adam 옵티마이저의 내부 상태, 그리고 순전파 중간 결과(활성값)까지 모두 메모리를 잡아먹는다.

GPT-2 Small(124M 파라미터)을 FP32로 학습하면 가중치만 약 500MB인데, 실제로는 기울기 + 옵티마이저 상태까지 합쳐 가중치의 약 8배 메모리가 필요하다. 이 구조를 모르면 “왜 24GB GPU에서 7B 모델이 안 올라가는지” 판단할 수 없다.

GPU 메모리 관리 흐름

비유

GPU 메모리는 책상 위 작업 공간이다. 모델 파라미터는 교재, 기울기는 연습장, 옵티마이저 상태는 이전 풀이 기록 2권, 활성값은 현재 펼쳐놓은 중간 계산 메모지다. 교재만 보면 책상이 넉넉해 보이지만, 실제 공부할 때는 교재 한 권 크기의 4~8배 공간이 필요하다.

네 가지 메모리 소비원

%% GPU 메모리 소비원
flowchart TD
  memory["GPU 메모리 전체<br/>파라미터<br/>(Params) &#124; 기울기<br/>(Grads) &#124; 옵티마이저<br/>(Opt States) &#124; 활성값<br/>(Acts)<br/>고정 크기<br/>파라미터 수 x 바이트 &#124; 고정 크기<br/>파라미터 수 x 2 x 바이트 &#124; 가변 크기<br/>B x T에 비례"]

각 요소의 크기:

  • 모델 파라미터: 학습된 가중치. FP32이면 파라미터당 4바이트.
  • 기울기(Gradient): 역전파가 계산한 loss 미분값. 파라미터와 동일한 shape, 동일한 바이트.
  • 옵티마이저 상태: Adam은 파라미터당 1차 모멘트(m)와 2차 모멘트(v)를 유지한다. FP32 기준 파라미터당 8바이트 추가.
  • 활성값(Activation): 순전파 중간 출력. 역전파에서 기울기를 계산하려면 필요하다. 배치 크기(B)와 시퀀스 길이(T)에 비례해 증가한다.

FP32 기준 메모리 공식

%% FP32 학습 메모리 공식
flowchart LR
  params["파라미터<br/>P x 4B"]
  grads["기울기<br/>P x 4B"]
  adam_m["Adam m<br/>P x 4B"]
  adam_v["Adam v<br/>P x 4B"]
  fixed["고정 학습 메모리<br/>P x 16B"]
  activation["활성값 메모리<br/>배치 B, 길이 T에 따라 증가"]
  total["총 학습 메모리<br/>P x 16B + 활성값"]
  params --> fixed
  grads --> fixed
  adam_m --> fixed
  adam_v --> fixed
  fixed --> total
  activation --> total

총 학습 메모리 ≈ 파라미터 수 × (4 + 4 + 8) + 활성값 메모리 = 파라미터 수 × 16바이트 + 활성값

  • 파라미터: P × 4B
  • 기울기: P × 4B
  • Adam m: P × 4B
  • Adam v: P × 4B
  • 합계(고정): P × 16B

파라미터 수가 P일 때, 가중치만 보면 P × 4B이지만 학습에는 P × 16B가 필요하다. 가중치 대비 4배다.

왜 활성값이 가변인가?

활성값은 배치 크기(B)와 시퀀스 길이(T)에 비례한다. Transformer 한 블록의 활성값은 대략:

한 블록 활성값 ≈ B × T × D × (10~14) × bytes_per_element

여기서 D는 임베딩 차원이다. Attention score matrix는 B × H × T × T이므로 시퀀스 길이의 제곱에 비례한다. 이것이 긴 문맥에서 메모리가 폭발하는 원인이다.

GPU 메모리 관리 텐서 코드

파라미터 수 계산

id(parameter)로 중복을 방지한다. tie_embeddings=True이면 token embedding과 LM head가 같은 텐서를 공유하므로, 한 번만 세야 정확하다.

GPT-124M 급 메모리 산출

163M 파라미터 모델의 가중치는 0.65GB이지만 학습에는 2.6GB가 고정으로 필요하다. 여기에 활성값 메모리가 추가된다.

활성값 메모리 추정

배치 크기를 8에서 1로 줄이면 활성값이 1/8로 줄어든다. 이것이 작은 GPU에서 배치 크기를 줄이는 이유다.

shape 변환으로 보는 메모리 흐름

%% 활성값 shape 흐름
flowchart TD
  input["input_ids<br/>(B, T)<br/>거의 0"]
  embedding["tok_emb + pos_emb<br/>(B, T, D)<br/>B x T x D x 4 저장"]
  qkv["Q,K,V<br/>(B,H,T,d_k) x 3<br/>역전파용 저장"]
  scores["scores<br/>(B,H,T,T)<br/>T^2 비례"]
  context["context<br/>(B,T,D)<br/>저장"]
  ffn["FFN hidden<br/>(B,T,4D)<br/>저장"]
  repeat["Block 2~12<br/>같은 패턴 반복"]
  logits["logits<br/>(B,T,V)<br/>B x T x 50257 x 4"]
  backward["역전파<br/>저장 활성값 + dout<br/>기울기 계산 후 해제"]
  input --> embedding
  embedding --> qkv
  qkv --> scores
  scores --> context
  context --> ffn
  ffn --> repeat
  repeat --> logits
  logits --> backward

순전파에서 저장한 활성값을 역전파에서 소비한다. 저장하지 않으면 역전파를 할 수 없지만, 전부 저장하면 메모리가 부족하다. 이 딜레마가 그래디언트 체크포인팅의 동기다.

절약 기법 요약

  • 배치 크기 축소 + 그래디언트 누적: 활성값 메모리를 줄이면서도 큰 배치 효과를 유지한다.
  • 그래디언트 체크포인팅: 중간 활성값을 버리고 역전파 시 다시 계산한다. 메모리를 시간으로 교환.
  • 혼합 정밀도 학습: 파라미터와 활성값을 FP16/BF16으로 줄인다. 파라미터당 16B → 10B로 감소.
  • FSDP/ZeRO: 파라미터, 기울기, 옵티마이저 상태를 여러 GPU에 분할한다.
  • Flash Attention: attention score matrix를 메모리에 전부 올리지 않고 타일 단위로 계산한다. (B, H, T, T) 저장을 피한다.

정리

LLM 학습 시 GPU 메모리는 파라미터(P×4B), 기울기(P×4B), Adam 상태(P×8B), 활성값(∝B×T²)으로 나뉜다. 163M 모델도 FP32 학습에 약 10GB가 필요하다. 7B 모델이면 단순 계산으로 112GB 이상이 되어 단일 GPU로는 불가능하다. 그래서 그래디언트 누적, 그래디언트 체크포인팅, 혼합 정밀도 학습이 단독 GPU에서의 필수 기법이 되며, 그 이상은 분산 학습으로 넘어간다.
