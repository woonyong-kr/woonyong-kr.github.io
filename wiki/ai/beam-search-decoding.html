빔 검색 디코딩 — 여러 후보를 동시에 추적하는 텍스트 생성 전략

범위: 이 문서는 빔 검색의 일반 원리와 디코딩 전략의 선택 기준을 설명하며, 포함된 코드와 수치 비교는 구현 예시일 뿐이다. 특정 코드 경로의 실제 동작, 버전별 호환성, 실행 결과와 성능·품질에 관한 판단은 이 본문만으로 검증된 결과로 보지 않는다.

한 줄 요약: 빔 검색은 매 스텝마다 상위 k개 후보 시퀀스를 유지하면서 다음 토큰을 확장해, greedy보다 높은 전체 확률의 문장을 찾는 디코딩 전략이다.

빔 검색 디코딩 문제

디코딩 전략 문서에서 greedy 디코딩의 문제를 봤다. greedy는 매 스텝마다 확률이 가장 높은 토큰 하나만 고른다. 빠르지만, 각 스텝의 최선이 전체 문장의 최선이 아닐 수 있다.

예를 들어 “The dog”까지 생성한 상태에서:

스텝 3: "ran" (0.6) vs "quickly" (0.3)
스텝 4: "ran" 뒤 → "away" (0.2)  |  "quickly" 뒤 → "ran" (0.9)

greedy는 스텝 3에서 “ran”(0.6)을 고른다. 그 뒤 “away”(0.2)가 이어지면 두 스텝의 결합 확률은 0.6 × 0.2 = 0.12다. 반면 “quickly”(0.3) → “ran”(0.9) 경로는 0.3 × 0.9 = 0.27로 두 배 이상 높다. greedy는 이 경로를 영원히 찾지 못한다.

이상적으로는 모든 가능한 토큰 조합을 탐색하면 최적 시퀀스를 찾을 수 있다. 하지만 vocab_size가 50,257이고 길이가 T인 시퀀스의 조합 수는 50,257^T 이므로 전수 탐색은 불가능하다.

빔 검색은 이 사이에 서는 타협안이다. 모든 경로를 보진 않지만, 매 스텝마다 상위 k개(빔 폭) 후보를 유지하면서 탐색 범위를 넓힌다.

빔 검색 디코딩 계산

빔 폭 (Beam Width)

빔 폭 k는 매 스텝에서 동시에 추적하는 후보 시퀀스의 수다. k = 1이면 greedy와 같다. k가 클수록 더 넓은 탐색 공간을 보지만, 계산량도 k배 늘어난다.

동작 순서

빔 검색의 한 스텝을 구체적으로 풀어본다. 빔 폭 k = 2로 설정한다.

스텝 1: 시작 토큰 <BOS>에서 vocab_size개의 다음 토큰 확률을 구한다. 상위 k = 2개를 고른다.

빔 0: <BOS> → "The"   (log_prob = -0.5)
빔 1: <BOS> → "A"     (log_prob = -1.2)

스텝 2: 각 빔을 확장한다. 빔 0에서 vocab_size개, 빔 1에서 vocab_size개, 총 2 × vocab_size개의 후보가 생긴다. 이 중 상위 k = 2개를 고른다.

빔 0 확장: "The dog" (-0.5 + -0.8 = -1.3), "The cat" (-0.5 + -1.0 = -1.5), ...
빔 1 확장: "A dog"   (-1.2 + -0.6 = -1.8), "A small" (-1.2 + -0.9 = -2.1), ...

상위 2개 선택:
  빔 0: "The dog"   (누적 log_prob = -1.3)
  빔 1: "The cat"   (누적 log_prob = -1.5)

스텝 3 이후: 같은 과정을 반복한다. EOS 토큰이 나온 빔은 완료 후보에 넣고, 나머지 빔은 계속 확장한다. 모든 빔이 완료되거나 최대 길이에 도달하면 종료한다.

왜 log 확률을 쓰는가?

시퀀스의 결합 확률은 각 토큰 확률의 곱이다.

P(w_1, w_2, ..., w_T) = P(w_1) × P(w_2|w_1) × ... × P(w_T|w_1..w_{T-1})

확률 값은 0~1 사이이므로 곱할수록 매우 작아진다. 부동소수점 언더플로가 발생한다. log를 취하면 곱셈이 덧셈으로 바뀐다.

log P(w_1..w_T) = log P(w_1) + log P(w_2|w_1) + ... + log P(w_T|w_1..w_{T-1})

log 확률은 항상 음수(또는 0)이므로, 누적값이 0에 가까울수록 확률이 높은 시퀀스다.

길이 정규화 (Length Normalization)

log 확률은 음수이므로 토큰을 추가할수록 누적값이 작아진다. 빔 검색이 짧은 시퀀스를 편향적으로 선호하는 이유다. “Yes.”는 토큰 2개로 누적 log_prob이 -1.0인데, “The dog quickly ran across the yard.”는 토큰 8개로 -6.4일 수 있다. 숫자만 비교하면 “Yes.”가 이긴다.

길이 정규화는 누적 log 확률을 시퀀스 길이로 나눠 토큰당 평균 log 확률로 비교한다.

score = (1 / T^alpha) × sum(log P(w_t | w_1..w_{t-1}))

alpha는 길이 페널티 강도를 조절한다. alpha = 1.0이면 평균, alpha = 0이면 정규화 없음이다. 보통 0.6~0.8을 쓴다.

빔 검색 전체 흐름 다이어그램

  • 스텝 1 스텝 2 스텝 3
  • “The” “The dog” “The dog ran”
  • (-0.5) | (-1.3) | (-2.0)
  • “The cat” “The dog sat”
  • (-1.5) (-2.2)
  • “A” “A dog” (탈락: 상위 k 밖)
  • (-1.2)
  • “A small” (탈락)
  • 각 스텝에서 k × vocab_size 후보 중 상위 k개만 살아남는다.

빔 검색 디코딩 코드

빔 검색 생성 함수

GPT 모델의 generate() 함수(SW_AI-W13-gpt/src/train.py)는 greedy와 샘플링만 지원한다. 빔 검색은 여러 시퀀스를 병렬로 추적해야 하므로 별도 구현이 필요하다.

핵심 동작:

  • (1) 각 빔의 마지막 위치에서 logits를 구한다.
  • (2) log_softmax로 log 확률을 만든다. softmax → log 순서보다 수치적으로 안정적이다.
  • (3) 상위 beam_width개 토큰을 뽑아 기존 시퀀스에 붙인다.
  • (4) 전체 후보 중 누적 log 확률 상위 beam_width개만 다음 스텝으로 넘긴다.
  • (5) 최종적으로 길이 정규화된 점수가 가장 높은 시퀀스를 반환한다.

수치로 확인하기 — 그리디 vs 빔 검색

numpy로 간단한 예시를 만들어 그리디와 빔 검색의 차이를 확인한다.

이 예시에서는 매 스텝 최고 확률 토큰이 뒤이어 나오는 토큰과도 잘 맞아 그리디와 빔 검색이 같은 결과를 낸다. 실제 언어 모델에서는 1~2번째 스텝의 차선 토큰이 이후 스텝에서 훨씬 높은 확률을 유도하는 경우가 빈번하고, 이때 빔 검색이 그리디보다 나은 시퀀스를 찾는다.

디코딩 전략 비교

항목그리디샘플링(top-k/top-p)빔 검색
결정론적OXO
다양성낮음높음중간
품질 최적화지역 최적비보장근사 전역 최적
연산 비용O(V)O(V)O(k·V)
대표 용도번역(draft)창작, 대화번역, 요약, ASR

선택 기준은 단순하다:

  • 정확성이 최우선이면 빔 검색을 쓴다. 기계 번역, 음성 인식, 요약처럼 정답에 가까운 출력이 필요한 태스크다.
  • 다양성·창의성이 필요하면 샘플링(top-k, top-p)을 쓴다. 대화, 스토리 생성 등이다.
  • 속도가 최우선이면 그리디를 쓴다. 빔 검색 대비 k배 빠르고, 품질 차이를 감수할 수 있을 때 선택한다.

정리

빔 검색 디코딩은 매 스텝 상위 k개 후보를 유지하면서 누적 log 확률이 가장 높은 시퀀스를 찾는 알고리즘이다. 그리디의 지역 최적 문제를 완화하되, 전수 탐색보다 현실적인 비용으로 동작한다. 길이 정규화를 적용하지 않으면 짧은 시퀀스에 편향되므로 반드시 함께 사용한다.
