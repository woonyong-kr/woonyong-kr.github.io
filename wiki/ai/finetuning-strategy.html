Fine-tuning 전략

Fine-tuning 전략

범위: 이 문서는 Fine-tuning 필요 여부와 방식 선택에 관한 일반 원리와 판단 기준을 설명하며, 코드와 파라미터 계산은 제시된 작은 GPT 설정을 이해하기 위한 예시다. 특정 구현의 동작 여부, 라이브러리·모델 버전별 요구 자원, 실제 학습 가능성과 성능은 코드 확인과 실행 기록·측정을 통해 별도로 검증해야 한다.

한 줄 요약: 팀 프로젝트에서 LLM을 쓸 때 미세조정(Fine-tuning)이 필요한 상황인지 먼저 판단하고, 필요하다면 full fine-tuning·LoRA·QLoRA·head-only 중 비용 대비 효과가 가장 큰 방식을 고르는 결정 기준이다.

Fine-tuning 전략 문제

팀 프로젝트에서 “LLM을 쓰자”까지는 쉽게 정해진다. 문제는 그다음이다. 똑같이 LLM을 쓰더라도 길은 네 갈래로 갈린다.

  • 프롬프트만 잘 써서 상용 API(GPT 등)를 그대로 호출한다.
  • 모델 바깥에 문서를 검색해 붙여 준다. 이게 RAG다.
  • 모델 가중치 자체를 우리 데이터로 추가 학습한다. 이게 미세조정이다.
  • 위 방법을 섞는다.

이 갈림길에서 판단을 못 하면 두 가지 사고가 난다. 하나는 프롬프트로 충분한 문제에 GPU를 며칠씩 태워 미세조정하는 낭비다. 다른 하나는 반대로, 모델의 말투나 출력 형식을 꼭 고정해야 하는데 프롬프트만 붙들고 있다가 데모 품질이 들쭉날쭉해지는 실패다.

Fine-tuning 전략은 “언제 미세조정이 필요한가”, 그리고 “필요하다면 어떤 방식을 골라야 우리 GPU와 데이터로 감당이 되는가”를 미리 정해 두는 판단 기준이다.

이 기준이 없으면 full fine-tuning, LoRA(Low-Rank Adaptation), QLoRA(Quantized LoRA)가 각각 무슨 문제를 푸는 도구인지 구분하지 못한다. 세 단어가 전부 “모델을 학습시킨다”로 뭉뚱그려지면, 7B 모델을 노트북 GPU 한 장으로 어떻게 미세조정하는지 같은 현실적인 질문에 답할 수 없다.

Fine-tuning 전략 흐름

비유: 새 직원을 어떻게 쓸 것인가

이미 똑똑한 신입 직원(사전 학습된 LLM)을 데려왔다고 하자. 이 직원을 우리 일에 맞게 쓰는 방법은 세 가지다.

  • 일할 때마다 매뉴얼을 건넨다 → 프롬프트 엔지니어링. 직원 머릿속은 안 바뀐다. 매번 지시를 길게 줘야 한다.
  • 회사 자료실 열람권을 준다 → RAG. 필요할 때 문서를 찾아보게 한다. 최신 정보·사내 지식에 강하다.
  • 우리 회사 방식으로 재교육한다 → 미세조정. 직원의 판단 자체를 바꾼다. 한 번 들이면 매번 지시하지 않아도 우리 스타일대로 일한다.

재교육(미세조정)은 효과가 가장 깊지만 비용도 가장 크다. 그래서 “정말 재교육이 필요한 일인가”를 먼저 따져야 한다.

미세조정이 필요한 문제인가

미세조정은 “모델이 무엇을 아는가(지식)“보다 “모델이 어떻게 행동하는가(형식·문체·좁은 과업)“를 바꿀 때 효과가 크다.

  • 미세조정이 맞는 경우
    • 출력 형식을 고정해야 한다. 항상 같은 JSON 스키마, 같은 분류 라벨(긍정/부정)로 답해야 한다.
    • 도메인 말투·용어를 일관되게 써야 한다. 법률·의료 문체처럼 프롬프트로 매번 흉내 내기 번거로운 경우.
    • 과업이 좁고 라벨 데이터가 있다. 감성 분류, 의도 분류처럼 정답이 명확한 경우.
  • 미세조정이 과한 경우
    • 필요한 건 최신 정보나 사내 문서다 → RAG가 맞다. 지식은 검색으로 붙이는 게 싸고 갱신도 쉽다.
    • 범용 능력(요약, 번역, 코드 생성)이면 → 좋은 프롬프트 + 상용 API로 충분한 경우가 많다.

판단의 핵심은 하나다. 바꾸려는 것이 모델의 지식이면 RAG를, 모델의 행동 양식이면 미세조정을 먼저 검토한다.

결정 트리

미세조정으로 가닥이 잡혔다면, 이제 “어느 방식”인지를 고른다. 아래 흐름을 따라 내려간다.

%% Fine-tuning 방식 선택 결정 트리
flowchart TD
  problem["LLM이 필요한 문제"]
  knowledge["모델의 지식을<br/>바꿔야 하나?"]
  rag["RAG<br/>검색으로 문서 붙이기"]
  behavior["행동/형식/문체를<br/>고정해야 하나?"]
  prompt["프롬프트 + 상용 API"]
  data["라벨 데이터가<br/>충분한가?<br/>수천~수만 건 이상"]
  gpu["GPU 메모리가<br/>넉넉한가?"]
  full["full fine-tuning<br/>또는 head-only"]
  lora["LoRA<br/>어댑터만 학습"]
  qlora["QLoRA<br/>4bit 양자화 + LoRA"]
  problem --> knowledge
  knowledge --> rag
  knowledge --> behavior
  behavior --> prompt
  behavior --> data
  data --> gpu
  gpu --> full
  gpu --> lora
  lora --> qlora

기술 스택 판단의 기준값으로 적힌 “7B 이하 모델 + QLoRA, 학습 데이터 1만~10만 건”은 이 트리의 가장 오른쪽 경로다. 모델은 크게(7B) 쓰고 싶은데 GPU는 부족할 때, QLoRA로 메모리를 줄여 한 장으로 학습하는 선택이다.

미세조정 방식 스펙트럼: 무엇을 학습 가능하게 둘 것인가

방식의 차이는 결국 “전체 파라미터 중 몇 개를 실제로 갱신하는가”로 갈린다. 학습 가능한 파라미터가 적을수록 GPU 메모리와 학습 시간이 줄지만, 모델을 바꿀 수 있는 폭도 줄어든다.

  • full fine-tuning
    • 모든 가중치를 갱신한다. 표현력이 가장 크다.
    • 옵티마이저 상태(Adam은 파라미터당 추가 2배 메모리)까지 들고 있어야 해서 메모리를 가장 많이 쓴다.
  • LoRA
    • 기존 가중치는 얼려 두고, 작은 저랭크(low-rank) 행렬 한 쌍만 새로 학습한다.
    • 학습 파라미터가 전체의 약 1% 수준으로 줄어든다.
  • QLoRA
    • 얼린 가중치를 4비트로 양자화해 메모리에 올리고, 그 위에 LoRA를 얹는다.
    • 큰 모델을 작은 GPU 한 장에 올릴 수 있게 만드는 조합이다.
  • head-only (선형 프로빙)
    • backbone을 전부 얼리고 마지막 분류기 한 층만 학습한다. 가장 싸지만 표현력이 가장 좁다.

실제 서비스 모델과 학습용 작은 모델은 다르다

전략을 추상적으로만 두면 감이 안 온다. 두 기준을 분리해서 봐야 한다.

  • 실제 서비스 기준 (7B급 이상 오픈소스/상용 모델)
    • 파라미터가 수십억 개다. full fine-tuning은 GPU 여러 장(수십~수백 GB VRAM)을 요구한다.
    • 그래서 현실에서는 LoRA·QLoRA 같은 PEFT(Parameter-Efficient Fine-Tuning)가 사실상 기본이다.
  • 학습용 작은 모델 기준 (밑바닥 LLM의 작은 GPT)
    • 이 볼트의 기준 코드(SW_AI-W13-gpt)는 emb_dim=256, n_layers=6짜리 장난감 GPT다.
    • 파라미터가 수백만 개라 노트북에서도 full fine-tuning이 그냥 돈다.
    • 작아서 LoRA의 메모리 이득이 체감되지 않는다. 대신 “무엇을 얼리고 무엇을 학습하는가”라는 구조를 눈으로 확인하기에 좋다.

즉 LoRA·QLoRA가 “필수”가 되는 건 모델이 클 때다. 작은 모델로 개념을 익히고, 실제 7B 모델에 올릴 때 PEFT로 갈아탄다.

catastrophic forgetting과 학습률

어떤 방식을 쓰든 공통 함정이 하나 있다. 사전 학습 가중치는 막대한 텍스트로 오래 최적화된 값이다. 큰 학습률로 미세조정하면 이 값이 급격히 망가져, 모델이 원래 갖고 있던 언어 능력을 잊는다. 이를 catastrophic forgetting(파괴적 망각)이라 한다.

그래서 미세조정 학습률은 사전 학습보다 훨씬 작게 잡는다. 사전 학습이 1e-46e-4라면, 미세조정은 1e-55e-5 정도로 10배 이상 낮춘다. “미세”조정이라는 이름이 여기서 나온다.

Fine-tuning 전략 코드

full fine-tuning: 모든 파라미터를 학습 대상으로

밑바닥 LLM 과제의 분류 미세조정 모델은 GPT backbone 위에 분류기 한 층을 얹은 구조다. 별다른 설정을 하지 않으면 backbone과 분류기 모두 학습된다. 이것이 full fine-tuning이다.

이 코드가 하는 일: GPT backbone으로 문맥 벡터를 만들고, 마지막 유효 토큰의 hidden state를 분류기에 넣어 2-class 로짓을 낸다. self.gpt가 그대로 모듈로 등록돼 있어, 옵티마이저에 model.parameters()를 넘기면 backbone까지 전부 갱신된다.

head-only: backbone을 얼리면 분류기만 학습된다

같은 모델에서 backbone 파라미터의 requires_grad를 끄면, 역전파가 backbone까지 흐르지 않는다. 분류기 한 층만 학습되는 head-only 방식이 된다.

이 코드에서 기억할 것: requires_grad = False는 해당 파라미터를 학습에서 빼는 스위치다. full fine-tuning과 head-only의 코드 차이는 이 한 줄이다. 무엇을 얼리느냐가 곧 전략이다.

학습 루프는 방식과 무관하게 같다

방식을 바꿔도 학습 루프 자체는 그대로다. 달라지는 건 “어떤 파라미터가 갱신되느냐”뿐이다.

이 코드가 하는 일: forward로 loss를 구하고 backward로 기울기를 흘린 뒤 step으로 갱신한다. backbone을 얼렸다면 backward 단계에서 backbone에는 기울기가 쌓이지 않으므로, 같은 루프가 자동으로 head-only 학습이 된다.

왜 LoRA가 메모리를 줄이는가? — 학습 파라미터 수로 계산

방식별로 실제 갱신되는 파라미터 수를 밑바닥 LLM 기본 설정(emb_dim d=256, n_layers L=6, n_heads=8, ffn_mult=4)으로 대입해 본다.

Transformer 블록 하나의 파라미터 수(근사):

어텐션 QKV (qkv_bias=False) = 3 × d × d         = 3 × 256 × 256 = 196,608
어텐션 출력 투영            = d × d + d          = 65,536 + 256  = 65,792
FFN (d→4d→d)               = 2 × d × 4d + 5d     = 524,288 + 1,280 ≈ 525,568
LayerNorm 2개              = 2 × 2d              = 1,024
------------------------------------------------
블록 1개 ≈ 788,992 ≈ 0.79M
6개 블록 ≈ 4,733,952 ≈ 4.7M   ← backbone 학습 대상의 대부분

방식별 학습 파라미터 수:

full fine-tuning : 임베딩 + backbone(≈4.7M) + 분류기(514) ≈ 수백만 개 (거의 전부)
head-only        : 분류기만 = 256 × 2 + 2                = 514개
LoRA (rank r=8)  : q·v 투영에만, 블록당 2 × (2 × r × d)  = 2 × (2×8×256) = 8,192
                   6블록 합 = 49,152, + 분류기 514       ≈ 49,666개

대입 결과:

full fine-tuning ≈ 4,700,000개
LoRA  r=8        ≈    49,666개   (backbone의 약 1%)
head-only        ≈       514개

결론: LoRA는 기존 가중치를 얼린 채 블록당 작은 저랭크 행렬 한 쌍만 학습해, 학습 파라미터를 backbone의 약 1%로 줄인다. 학습 파라미터가 줄면 옵티마이저 상태(Adam은 파라미터당 추가 메모리 2배)도 그만큼 줄어, 큰 모델을 작은 GPU에 올릴 수 있게 된다. 이것이 7B 모델을 한 장으로 미세조정하는 방법의 출발점이다.

정리

미세조정 전략은 두 번의 판단으로 정리된다. 첫째, 바꾸려는 것이 모델의 지식이면 RAG를, 행동·형식·문체이면 미세조정을 고른다. 둘째, 미세조정이라면 GPU 여유와 모델 크기를 보고 full fine-tuning → LoRA → QLoRA → head-only 스펙트럼에서 감당 가능한 지점을 잡는다. 방식의 본질은 “전체 파라미터 중 무엇을 얼리고 무엇을 학습하느냐”이며, 코드에서는 requires_grad 한 줄과 옵티마이저에 넘기는 파라미터 목록으로 갈린다. 작은 모델에서는 full fine-tuning이 그냥 돌지만, 7B급부터는 LoRA·QLoRA가 사실상 기본이 된다. 어떤 방식이든 학습률을 사전 학습보다 낮춰 파괴적 망각을 피한다.
