PintOS 가상 메모리 구현 가이드

PintOS 가상 메모리 구현 가이드

PintOS 가상 메모리를 구현하기 전에 이해할 개념·코드·테스트 순서를 모은다.

전체 순서

1단계: 주소 변환 기준 잡기

알아야 할 질문:

  • 유저가 보는 주소와 실제 RAM 주소는 왜 다를까?
  • 0x401234 같은 주소는 page number와 offset으로 어떻게 쪼개질까?
  • CPU는 PML4, PDPT, PD, PT를 어떤 순서로 따라갈까?
  • PTE의 present, writable, user, accessed, dirty bit는 각각 무엇을 말할까?

읽을 문서:

2단계: PML4와 SPT를 구분하기

판단 기준:

  • PML4: CPU가 직접 보는 번역표
  • SPT: PintOS 커널이 보는 의미표
  • PML4 mapping 없음 + SPT 존재: 아직 RAM에 없지만 합법적인 page 가능

읽을 문서:

3단계: lazy loading을 이해하기

알아야 할 질문:

  • load_segment()는 왜 ELF 바이트를 즉시 읽지 않을까?
  • UNINIT page는 언제 ANON 또는 FILE page로 초기화될까?
  • 첫 page fault 때 aux에 담긴 정보는 어디에 쓰일까?

읽을 문서:

4단계: page fault를 정책 질문으로 바꾸기

알아야 할 질문:

  • CR2에는 어떤 주소가 들어 있을까?
  • PF_P, PF_W, PF_U는 각각 무엇을 알려줄까?
  • not-present fault와 protection fault는 어떻게 다를까?
  • write fault가 read-only page에 들어온 경우는 왜 살리면 안 될까?

읽을 문서:

5단계: claim으로 실제 메모리 붙이기

알아야 할 질문:

  • frame은 어디서 가져올까?
  • page->frame과 frame->page는 언제 연결할까?
  • pml4_set_page()는 어떤 VA와 어떤 KVA를 연결할까?
  • pml4_set_page()가 실패하면 방금 얻은 frame과 양방향 포인터를 어떻게 정리할까?
  • PTE 설치 후 swap_in()은 왜 page type별로 다른 함수를 호출할까?
  • UNINIT page의 swap_in() 안에서 callback이 실패하면 aux와 page type metadata는 누가 정리할까?

읽을 문서:

6단계: stack growth 경계 정하기

알아야 할 질문:

  • fault address와 유저 RSP가 얼마나 가까워야 할까?
  • USER_STACK 위로 올라가거나 너무 아래로 내려가면 왜 죽여야 할까?
  • 커널 모드에서 난 fault라도 유저 주소 접근일 수 있는가?

읽을 문서:

7단계: frame eviction과 swap 이해하기

알아야 할 질문:

  • frame table은 왜 필요한가?
  • accessed bit는 clock algorithm에서 어떻게 쓰일까?
  • dirty anonymous page와 dirty file-backed page는 어디로 내려가야 할까?
  • swap slot은 sector 단위로 어떻게 계산할까?

읽을 문서:

8단계: mmap과 file-backed page 이해하기

알아야 할 질문:

  • mmap 주소, 길이, offset은 어떤 조건을 만족해야 할까?
  • code/data/stack과 겹치는 mapping은 왜 거절해야 할까?
  • read-only mmap에 write가 들어오면 어디서 막아야 할까?
  • dirty file-backed page는 munmap() 또는 exit 때 언제 write-back해야 할까?

읽을 문서:

9단계: fork에서 주소 공간 의미 복사하기

알아야 할 질문:

  • lazy page는 자식에서도 lazy로 남겨야 할까?
  • 이미 resident한 page는 frame 내용을 복사해야 할까?
  • swapped-out page는 swap slot을 공유해도 될까?
  • COW를 구현한다면 writable bit와 write fault를 어떻게 해석해야 할까?

읽을 문서:

구현 순서

  1. SPT 자료구조와 spt_find_page(), spt_insert_page() 생성
  2. load_segment()의 lazy page 등록 완성
  3. vm_try_handle_fault()에서 SPT lookup과 claim 연결
  4. vm_do_claim_page()와 vm_get_frame()으로 실제 frame 연결
  5. stack growth 추가
  6. frame table, eviction, swap 추가
  7. mmap()과 file-backed page 추가
  8. fork()의 SPT copy 정리
  9. exit, munmap(), SPT kill에서 자원 해제 검증

코드에서 핵심 파일

  • page/frame/SPT 구조체
    • 파일: pintos/include/vm/vm.h
  • VM 공통 로직
    • 파일: pintos/vm/vm.c
  • anonymous page와 swap
    • 파일: pintos/vm/anon.c, pintos/include/vm/anon.h
  • file-backed page와 mmap
    • 파일: pintos/vm/file.c, pintos/include/vm/file.h
  • uninit page와 lazy initializer
    • 파일: pintos/vm/uninit.c, pintos/include/vm/uninit.h
  • page fault 진입점
    • 파일: pintos/userprog/exception.c
  • ELF loading과 fork/exit
    • 파일: pintos/userprog/process.c
  • page table helper
    • 파일: pintos/threads/mmu.c, pintos/include/threads/mmu.h

테스트로 보는 체크포인트

  • lazy-*, page-linear, page-parallel
    • 확인할 기능: lazy loading, SPT lookup, claim
  • pt-grow-*, pt-bad-addr, pt-write-code*
    • 확인할 기능: stack growth, invalid access, protection fault
  • swap-*, page-merge-*, page-shuffle
    • 확인할 기능: eviction, accessed bit, swap-in/out
  • mmap-read, mmap-write, mmap-clean, mmap-unmap
    • 확인할 기능: mmap 기본 동작과 write-back
  • mmap-bad-*, mmap-over-*, mmap-misalign, mmap-kernel
    • 확인할 기능: mmap 인자 검증과 overlap 검증
  • mmap-twice, mmap-shuffle, swap-file
    • 확인할 기능: 다중 mapping, page별 offset, file-backed page 격리
  • mmap-inherit, swap-fork
    • 확인할 기능: fork와 SPT copy

PintOS 가상 메모리 구현 쟁점

  • page fault가 났을 때 “죽일 fault”와 “살릴 fault”를 어떻게 구분할까?
  • PML4에 없는 page인데 SPT에는 있는 상태는 왜 정상일까?
  • struct page는 데이터 자체를 담는가, 데이터가 어디 있는지의 의미를 담는가?
  • anonymous page와 file-backed page는 swap-out 위치가 왜 다를까?
  • dirty bit는 file write-back과 swap-out 중 어느 판단에 쓰일까?
  • mmap()의 반환값이 단순 주소처럼 보여도 왜 mapping 객체 관리가 필요할까?
