fork -- 주소 공간 복제

fork — 주소 공간 복제

확인 범위: 이 문서는 fork의 일반 원리와 Linux·PintOS 구현을 구분해 설명하고, PintOS의 구현 흐름과 Project별 선택 기준을 개념적으로 정리한다. 제시된 코드 좌표, 버전별 동작, GDB 관찰 결과와 복제 비용·성능 판단은 해당 소스와 실제 실행 기록 및 측정으로 별도 검증해야 한다.

fork()는 부모가 멈춰 있던 실행 지점을 자식도 이어받게 만드는 복제 작업이다. 주소 공간, 레지스터, fd table을 맞춰 놓은 뒤 부모에게는 자식 TID를, 자식에게는 0을 돌려준다.

fork — 주소 공간 복제 상태

fork()는 호출한 프로세스(부모)의 주소 공간, 레지스터 상태, 파일 디스크립터 테이블을 통째로 복제하여 새로운 프로세스(자식)를 만든다. 부모는 자식의 TID를 받고, 자식은 0을 받는다. 복제가 완료되면 두 프로세스는 독립적으로 실행된다.

상세 설명

추상 개념

fork의 핵심 계약:

  1. 주소 공간 복제: 자식은 부모의 메모리 내용과 동일한 사본을 갖는다.
  2. 레지스터 복제: 자식은 부모가 fork를 호출한 시점의 레지스터 상태를 이어받는다.
  3. 반환값 구분: 부모의 fork()는 자식 TID를, 자식의 fork()는 0을 반환한다.
  4. fd 테이블 복제: 자식은 부모의 열린 파일을 공유한다 (같은 struct file, 같은 offset).

실제 OS (Linux)

Linux의 fork()는 내부적으로 clone() syscall을 호출한다. 현대 Linux는 기본적으로 **Copy-on-Write(COW)**를 적용한다:

  • 부모와 자식이 같은 물리 프레임을 공유하되 PTE를 read-only로 설정한다.
  • 어느 한쪽이 쓰기를 시도하면 page fault가 발생하고, 그때 프레임을 복사한다.
  • 이 덕분에 fork() + exec() 패턴에서 불필요한 메모리 복사를 피한다.

PintOS 구현

PintOS의 fork는 process_fork() (부모 측)과 __do_fork() (자식 측) 두 함수로 나뉜다.

부모 측: process_fork()

process_fork(name, if_)
  1. child_status 구조체 할당, 세마포어 2개 초기화
     - fork_sema: 자식 초기화 완료 대기용
     - wait_sema: wait() 대기용
  2. fork_args에 부모 포인터 + intr_frame 복사본 + cs 포인터 패킹
  3. thread_create(name, PRI_DEFAULT, __do_fork, args)
  4. sema_down(&cs->fork_sema)  ← 자식이 복제 완료할 때까지 블록
  5. cs->fork_success 확인 → 성공이면 tid 반환, 실패면 TID_ERROR

자식 측: __do_fork()

__do_fork(aux)
  1. fork_args에서 부모 포인터, intr_frame 꺼냄
  2. pml4_create()로 빈 페이지 테이블 생성
  3. process_activate(curr) → CR3 전환
  4-a. [VM 미적용] pml4_for_each(parent->pml4, duplicate_pte, parent)
       → 부모의 모든 유저 PTE를 순회하며 palloc + memcpy
  4-b. [VM 적용] supplemental_page_table_copy(&curr->spt, &parent->spt)
       → SPT 기반으로 lazy/swapped/file-backed 페이지까지 복제
  5. duplicate_fd_table(curr, parent) → file_duplicate()로 각 fd 복제
  6. duplicate_running_file(curr, parent) → 실행 파일도 복제
  7. if_.R.rax = 0  ← 자식의 fork 반환값을 0으로 설정
  8. sema_up(&cs->fork_sema)  ← 부모에게 "복제 완료" 알림
  9. do_iret(&if_) → 유저 모드 진입 (부모가 fork 호출한 바로 그 지점부터)

핵심 동기화: fork handshake

sequenceDiagram
    participant Parent as 부모
    participant Child as 자식

    Parent->>Parent: child_status 할당, fork_sema(0) 초기화
    Parent->>Child: thread_create(__do_fork)
    Parent->>Parent: sema_down(fork_sema) — 블록
    Note over Child: pml4 복제
    Note over Child: fd_table 복제
    Note over Child: RAX = 0
    Child->>Parent: sema_up(fork_sema)
    Note over Parent: fork_success 확인
    Parent->>Parent: return child_tid
    Child->>Child: do_iret → 유저 모드 (return 0)

이 handshake가 없으면 부모가 자식의 tid를 반환한 뒤 자식이 아직 복제 중인 상태에서 부모의 주소 공간이 변경될 수 있다. fork_sema로 순서를 보장한다.

QEMU 에뮬레이션

QEMU는 fork의 어떤 단계도 인지하지 않는다. fork는 순수히 OS 소프트웨어 동작이다.

  • 페이지 테이블 복제: pml4_create()가 palloc_get_page()로 새 물리 프레임을 할당 → QEMU는 guest physical memory 범위 내 메모리 접근일 뿐 fork인지 모른다.
  • memcpy(4 KB): 부모 프레임 → 자식 프레임 복사도 QEMU에게는 평범한 메모리 load/store 시퀀스다.
  • CR3 전환: process_activate()가 자식의 PML4 물리 주소를 CR3에 기록하면, QEMU TCG는 SoftMMU의 TLB를 flush하여 이후 주소 변환이 자식의 페이지 테이블을 따르게 한다.
  • sema_up/down: QEMU가 에뮬레이션하는 건 cli/sti 명령어(interrupt disable/enable)뿐이다. 세마포어 자체는 메모리 내 카운터 조작이므로 QEMU 입장에서 일반 명령어 실행과 동일하다.

에러 처리 흐름

fork 실패 시 자식은 goto error 경로로 빠진다:

flowchart TD
    A["__do_fork 시작"] --> B{pml4_create 성공?}
    B -->|No| E[goto error]
    B -->|Yes| C{SPT/PTE copy 성공?}
    C -->|No| E
    C -->|Yes| D{fd_table 복제 성공?}
    D -->|No| E
    D -->|Yes| F{running_file 복제 성공?}

    F -->|Yes| G["RAX=0, fork_success=true
    sema_up → do_iret"]

    E --> H["cs->exit_status = -1
    cs->exited = true
    cs->fork_success = false"]
    H --> I["sema_up(fork_sema)"]
    I --> J["thread_exit()"]

부모는 sema_down 이후 cs->fork_success를 확인하여, false이면 TID_ERROR를 반환한다. 이때 child_status 구조체는 부모가 list_remove + free로 정리한다(process.c:218-224).

duplicate_pte 콜백 (Project 2)

pml4_for_each는 부모의 4단계 페이지 테이블을 재귀 순회하며 present한 PTE마다 콜백을 호출한다. 커널 주소(is_kernel_vaddr)는 건너뛴다.

fork — 주소 공간 복제 값 추적

fork 시 복제되는 자원의 크기 예시:

자원크기계산
유저 페이지 10개40 KB10 x 4 KB (PGSIZE)
fd_table4 KBpalloc 1 page (PAL_ZERO)
child_status~80 bytesmalloc (세마포어 2개 + 상태 필드)
intr_frame 복사192 bytessizeof(struct intr_frame)

Project 2에서 fork의 시간 복잡도는 O(N)이다. N = 부모의 유저 페이지 수. 각 페이지마다 palloc + memcpy(4 KB)가 발생한다.

Linux vs PintOS fork 비교

항목Linux (do_fork/copy_process)PintOS (process_fork/__do_fork)

반환값 메커니즘copy_thread()에서 pt_regs.ax = 0_do_fork에서 if.R.rax = 0

signal 처리sighand 복제 또는 공유 (CLONE_SIGHAND)지원 없음

핵심 차이: Linux fork는 물리 메모리를 복사하지 않는다. 부모와 자식이 같은 frame을 공유하되 PTE를 read-only로 표시하고, 쓰기 시점에 COW fault로 분리한다. PintOS Project 2는 모든 페이지를 즉시 복사하므로 fork 비용이 O(N × 4 KB)다.

관찰 시나리오: fork 전후 메모리 비교

  1. b duplicate_pte — 첫 hit에서 p/x va (복제 대상 가상 주소)
  2. p/x *(uint64_t *)parent_page — 부모 frame의 첫 8바이트
  3. finish 후 p/x *(uint64_t *)newpage — 자식 frame의 첫 8바이트
  4. 두 값이 동일하면 memcpy 정상 → 이후 부모가 write해도 자식은 영향 없음 확인
