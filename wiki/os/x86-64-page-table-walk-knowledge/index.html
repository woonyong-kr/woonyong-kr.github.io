x86-64 페이지 테이블 워크

x86-64 페이지 테이블 워크 시작

0x8048123이라는 유저 가상 주소가 있다.

주소 변환과 메모리에서는 이 주소를 page base 0x8048000과 offset 0x123으로 나눴다. 그런데 x86-64 CPU는 page table에서 0x8048000이라는 key를 한 번에 찾지 않는다.

CPU는 주소의 비트를 네 조각으로 더 나눠서 다음 표들을 차례로 걷는다.

PML4 -> PDPE -> PDE -> PTE -> frame + offset

현대 x86-64에는 5단계 page table 옵션도 있다. 하지만 PintOS 학습에서는 PML4 -> PDPE -> PDE -> PTE 흐름을 먼저 정확히 잡는 것이 목적이다.

먼저 가상 주소 하나가 page table을 통과하는 과정을 다음 질문에서 시작한다.

가상 주소 한 개는 어떻게 4개의 page-table index와 1개의 offset으로 쪼개질까?

이 과정을 따라가면 PintOS의 구현과 page table에 필요한 메모리에 관한 질문도 함께 설명할 수 있다.

PintOS도 정말 4단계 page table을 쓰나? 512개를 넘으면 linked list처럼 next pointer로 이어 붙이나? page table 자체를 담는 4KB 메모리는 누가 가져오나?

x86-64 페이지 테이블 워크 필요성

운영체제 책에서는 “page table이 VA를 PA로 바꾼다”고 짧게 말한다. 하지만 디버깅할 때는 그 말만으로 부족하다.

실제로는 이런 질문을 해야 한다.

  • 현재 CR3가 가리키는 최상위 page table은 어디인가?
  • 이 VA의 PML4 index는 몇 번인가?
  • 중간 page table entry가 present가 아니면 어디서 page fault가 나는가?
  • 마지막 PTE에는 frame 주소와 permission bit가 어떻게 들어 있는가?
  • QEMU는 이 walk를 OS 정책으로 처리하나, 하드웨어 효과로 재현하나?

이 질문에 답할 수 있어야 page fault가 어느 단계에서 발생했는지 추적할 수 있다.

x86-64 페이지 테이블 워크 흐름

x86-64 4KB page, 4단계 page table 기준에서 가상 주소는 다음처럼 나뉜다.

bits 63..48  sign extension
bits 47..39  PML4 index   9 bits
bits 38..30  PDPE index   9 bits
bits 29..21  PDE index    9 bits
bits 20..12  PTE index    9 bits
bits 11..0   page offset 12 bits

여기서 bits 63..48은 새로운 table index가 아니다. 4단계 모드에서는 bit 47의 부호 확장(sign extension)처럼 맞아야 하는 canonical address 영역이다.

9비트 index 하나는 0..511 중 하나를 고른다. entry 하나가 8바이트라서 page table 한 장은 다음 크기가 된다.

512 entries * 8 bytes = 4096 bytes = 1 page

따라서 page table도 메모리 안에 있는 4KB짜리 배열이다. CPU는 VA의 비트 조각을 배열 index로 사용해 다음 table의 주소를 찾는다.

이 과정을 “주소를 헤더처럼 4단계로 잘라서 찾아간다”고 설명하면 큰 방향은 맞다. 다만 정확히는 header가 아니라 주소 비트 필드다. VA 안의 특정 bit 구간이 각각 배열 index 역할을 한다.

VA bits

[ PML4 index ][ PDPE index ][ PDE index ][ PTE index ][ offset ]
    9 bits       9 bits       9 bits      9 bits      12 bits

이 구조는 linked list가 아니라 4단계 트리다.

flowchart LR
    CR3["CR3 register"] --> PML4["PML4 page<br/>512 entries"]
    PML4 -->|"bits 47..39<br/>9-bit index"| PDPT["PDPT page<br/>512 entries"]
    PDPT -->|"bits 38..30<br/>9-bit index"| PD["PD page<br/>512 entries"]
    PD -->|"bits 29..21<br/>9-bit index"| PT["PT page<br/>512 entries"]
    PT -->|"bits 20..12<br/>9-bit index"| Frame["Data Frame<br/>4KB"]
    Frame -->|"bits 11..0<br/>12-bit offset"| Byte["최종 byte"]

  entry 1  -> 다른 PDPT page
  ...
  entry 511

  entry 0  -> PD page
  entry 1  -> 다른 PD page
  ...
  entry 511

  entry 0  -> PT page
  ...

  entry 0  -> data frame 4KB
  entry 1  -> data frame 4KB

따라서 512개가 넘을 때 page header의 next 주소로 이어지는 것은 아니다. 상위 단계의 다른 entry를 거쳐 다른 table page로 내려간다.

범위 계산

각 단계는 512개 entry 가운데 하나를 고른다. offset 12비트는 마지막 data page 안의 바이트 위치를 나타낸다.

9비트 = 2^9 = 512
12비트 = 2^12 = 4096 bytes = 4KB

그래서 4단계 page table이 표현할 수 있는 전체 가상주소 수는 다음과 같다.

512 * 512 * 512 * 512 * 4KB
= 2^9 * 2^9 * 2^9 * 2^9 * 2^12
= 2^48 bytes
= 256 TiB

이 계산은 실제 RAM이 256 TiB 있다는 뜻이 아니다. 그만큼의 가상주소 번호를 표현할 수 있다는 뜻이다. 실제 frame은 page fault가 나거나 mapping을 설치할 때 필요한 만큼만 붙는다.

각 table page가 담당하는 범위도 계산할 수 있다.

단위 커버하는 범위 이유
PTE entry 1개 4KB data frame 하나
PT page 1개 2MB 512 * 4KB
PD entry 1개 2MB PT page 하나가 맡는 범위
PD page 1개 1GB 512 * 2MB
PDPT entry 1개 1GB PD page 하나가 맡는 범위
PDPT page 1개 512GB 512 * 1GB
PML4 entry 1개 512GB PDPT page 하나가 맡는 범위
PML4 page 1개 256TiB 512 * 512GB

이 표에서 next pointer가 필요하지 않은 이유를 확인할 수 있다. page table page 하나가 꽉 차면 같은 레벨의 다음 page로 이어지는 것이 아니라, 상위 index가 바뀌면서 다른 하위 table page를 가리킨다.

가상 주소를 손으로 따라가기

다음 가상 주소가 page table을 통과하는 과정을 손으로 따라가 보자.

VA = 0x0000000008048123

비트 조각은 이렇게 나온다.

PML4 index = 0x000 = 0
PDPE index = 0x000 = 0
PDE index  = 0x040 = 64
PTE index  = 0x048 = 72
offset     = 0x123 = 291

각 table entry의 byte offset은 index에 8을 곱한다.

PML4E offset = 0   * 8 = 0x000
PDPE offset  = 0   * 8 = 0x000
PDE offset   = 64  * 8 = 0x200
PTE offset   = 72  * 8 = 0x240

마지막 PTE가 frame base 0x12345000을 가리키고 present라면 최종 주소는 다음처럼 계산된다.

PA = 0x12345000 + 0x123
   = 0x12345123

실제 운영체제

Linux와 Windows도 x86-64 하드웨어 위에서는 같은 page-table walk 원리를 사용한다. CPU는 CR3에서 시작해 page table entry의 present, writable, user, accessed, dirty 같은 bit를 검사한다.

다만 실제 하드웨어와 OS가 항상 4KB page만 쓰는 것은 아니다. huge page와 5단계 page table 같은 확장이 있을 수 있다.

실제 OS는 page table 외의 상태도 함께 관리한다.

  • Linux는 mm_struct, VMA, page cache, swap, copy-on-write, NUMA, huge page 같은 상태를 함께 관리한다.
  • Windows도 process address space, VAD, section object, prototype PTE, working set, pagefile 같은 구조를 함께 쓴다.

page-table walk는 하드웨어의 주소 번역 과정이다. 반면 fault를 처리해 실행을 계속할지 종료할지는 커널의 VM 정책이 결정한다.

PintOS는 이 현실을 교육용으로 줄여서 page table, supplemental page table, frame, swap/file-backed page를 직접 구현하게 만든다.

pml4e_walk(pml4, va, create)는 최종 PTE의 주소를 돌려준다.

  • create == false: 중간 table이 없으면 NULL을 반환한다.
  • create == true: 중간 table이 없으면 새 4KB page table을 할당해 연결한다.

따라서 pml4_set_page()가 새 mapping을 만들 때는 중간 table을 만들어도 되지만, pml4_get_page()가 단순 조회할 때는 없는 table을 만들면 안 된다.

이 PintOS 코드는 x86-64용이므로 PML4 -> PDPT -> PD -> PT의 4단계 page table을 쓴다. 실제 코드 이름도 그 구조를 반영한다.

단계 PintOS 매크로/함수 의미
PML4 PML4(va), pml4e_walk() 최상위 512개 entry 중 하나
PDPT PDPE(va), pdpe_walk() 다음 512개 entry 중 하나
PD PDX(va), pgdir_walk() 다음 512개 entry 중 하나
PT PTX(va) 최종 PTE 512개 중 하나
offset pg_ofs(va) 4KB frame 안의 바이트 위치

page table 자체를 저장할 4KB는 PintOS의 palloc_get_page()로 확보된다. 이 흐름은 유저 데이터 frame을 가져올 때처럼 PAL_USER를 붙이는 흐름과 구분해서 봐야 한다.

파일:

  • SW_AI-W11-pintos/pintos/threads/mmu.c

중간 table이 없고 create == true이면 새 page table page를 만든다.

uint64_t *new_page = palloc_get_page (PAL_ZERO);

반면 유저 데이터 frame은 VM 코드의 vm_get_frame()에서 보통 다음처럼 가져온다.

frame->kva = palloc_get_page (PAL_USER);

둘 다 4KB page를 얻지만 용도가 다르다.

가져오는 4KB 대표 호출 위치 용도
page table page pml4e_walk(..., create=true) 내부 PML4/PDPT/PD/PT 같은 하드웨어 page table 저장
user data frame vm_get_frame() 유저 VA 뒤에 붙을 실제 데이터 page

page table과 user page는 모두 4KB 메모리 page이지만 역할은 다르다. 하나는 주소 번역 표이고, 다른 하나는 사용자 데이터가 들어가는 frame이다.

루트 PML4 포인터는 어디에 있나

4단계 page table도 시작점이 필요하다. CPU가 아무 곳에서나 page table walk를 시작할 수는 없다.

PintOS에서 시작점은 PML4 page의 주소다. 각 유저 프로세스와 스레드의 struct thread 안에 그 주소를 가리키는 포인터가 저장된다.

파일:

  • SW_AI-W11-pintos/pintos/include/threads/thread.h

관련 필드는 다음과 같다.

uint64_t *pml4;

이 포인터 자체는 struct thread 안에 들어 있는 8바이트짜리 필드다. 포인터가 가리키는 대상은 pml4_create()가 할당한 4KB짜리 PML4 page다.

%% struct thread의 pml4 포인터와 PML4 page
flowchart LR
  thread["struct thread<br/>pml4: uint64_t *<br/>8-byte pointer field"]
  pml4["PML4 page<br/>4KB page table<br/>entry 0<br/>entry 1<br/>...<br/>entry 511"]
  thread --> pml4

프로세스가 새 주소 공간을 만들 때 PintOS는 다음 함수를 호출한다.

파일:

  • SW_AI-W11-pintos/pintos/threads/mmu.c
uint64_t *
pml4_create (void) {
    uint64_t *pml4 = palloc_get_page (0);
    if (pml4)
        memcpy (pml4, base_pml4, PGSIZE);
    return pml4;
}

이 함수의 동작 순서는 다음과 같다.

1. PML4 page로 쓸 4KB를 palloc_get_page(0)으로 얻는다.
2. 커널 기본 매핑인 base_pml4 내용을 복사한다.
3. 새 PML4 page의 kernel virtual address를 반환한다.
4. 그 반환값을 현재 thread의 curr->pml4에 저장한다.

예를 들어 process.c에서는 새 프로세스 주소 공간을 만들 때 다음처럼 쓴다.

curr->pml4 = pml4_create ();

이 주소 공간이 실제 CPU의 기준이 되려면 CR3에 올라가야 한다. PintOS는 스케줄링으로 다음 스레드가 실행될 때 주소 공간을 활성화한다.

schedule()
  -> process_activate(next)
      -> pml4_activate(next->pml4)
          -> lcr3(vtop(pml4))

pml4_activate()의 동작을 보여 주는 부분은 다음과 같다.

void
pml4_activate (uint64_t *pml4) {
    lcr3 (vtop (pml4 ? pml4 : base_pml4));
}

여기서 lcr3()는 CPU의 CR3 레지스터를 바꾼다. CR3는 현재 주소 변환의 루트, 즉 PML4 page의 물리 주소를 담는다.

루트 포인터의 관계는 다음처럼 이어진다.

thread_current()->pml4
  -> PML4 page의 kernel virtual address
  -> vtop(pml4)
  -> CR3에 들어가는 PML4 page의 guest physical address

이후 CPU는 현재 CR3에서 시작해서 PML4 index -> PDPT index -> PD index -> PT index -> offset 순서로 내려간다.

루트에도 메모리가 필요하지만, 포인터와 table 자체는 서로 다른 곳에 저장된다. 루트의 포인터 값은 struct thread 안의 필드에 있고, 포인터가 가리키는 PML4 table 자체는 별도의 4KB page에 있다.

QEMU

QEMU는 PintOS의 SPT, stack growth, mmap 정책을 모른다.

QEMU가 재현하는 것은 guest CPU의 page-table walk다. TCG 경로에서는 현재 guest CR3와 guest VA를 기준으로 page table entry 주소를 계산하고, present/permission bit를 검사한다.

대표 파일:

  • target/i386/tcg/system/excp_helper.c
    • mmu_translate()

QEMU 코드에도 같은 index 계산이 나온다.

((addr >> 39) & 0x1ff)
((addr >> 30) & 0x1ff)
((addr >> 21) & 0x1ff)
((addr >> 12) & 0x1ff)

각 index는 << 3으로 8바이트 entry offset이 된다.

entry address = table base + (index << 3)

entry가 present가 아니면 QEMU는 guest CPU의 page fault 효과를 만든다. 그 뒤 page_fault()에서 이 fault를 처리할지 결정하는 주체는 PintOS다.

QEMU 코드에는 PG_MODE_LA57 분기도 있다. 이 분기는 5단계 page table이 켜진 guest를 위한 경로다. PintOS를 이해할 때는 그 분기보다 addr >> 39, addr >> 30, addr >> 21, addr >> 12로 내려가는 4단계 흐름을 먼저 보면 된다.

x86-64 페이지 테이블 워크 코드

1. PintOS는 VA bit 조각을 index로 만든다

파일:

  • SW_AI-W11-pintos/pintos/include/threads/pte.h

shift와 mask를 적용하는 식은 다음과 같다.

PML4(va) = (va >> 39) & 0x1FF
PDPE(va) = (va >> 30) & 0x1FF
PDX(va)  = (va >> 21) & 0x1FF
PTX(va)  = (va >> 12) & 0x1FF

2. PintOS는 중간 entry에서 다음 table을 찾는다

파일:

  • SW_AI-W11-pintos/pintos/threads/mmu.c

pml4e_walk()는 PML4 entry에서 다음 table의 물리 주소를 꺼내고, ptov()로 커널이 접근할 수 있는 주소로 바꾼 뒤 다음 단계로 내려간다.

pte = pdpe_walk (ptov (PTE_ADDR (pml4e[idx])), va, create);

pgdir_walk()의 마지막 단계는 최종 PTE 주소를 계산한다.

return (uint64_t *) ptov (PTE_ADDR (pdp[idx]) + 8 * PTX (va));

여기서 8 * PTX(va)는 page table 배열에서 몇 번째 8바이트 entry를 선택하는지 나타낸다.

중간 table이 없는데 mapping을 새로 만들어야 하면 PintOS는 이 자리에서 table page를 만든다.

uint64_t *new_page = palloc_get_page (PAL_ZERO);
pdpe[idx] = vtop (new_page) | PTE_U | PTE_W | PTE_P;

이 코드는 다음 순서로 동작한다.

1. 새 4KB page table page를 얻는다.
2. 그 page의 kernel virtual address를 vtop()으로 guest physical address로 바꾼다.
3. 상위 entry에 "다음 table은 여기 있다"는 주소와 PTE_P/PTE_W/PTE_U flag를 기록한다.

다음 table로 내려가는 포인터는 C 구조체의 next 포인터가 아니라 page table entry의 주소 bit에 들어 있다.

3. pml4_get_page()는 present인 최종 PTE를 해석한다

파일:

  • SW_AI-W11-pintos/pintos/threads/mmu.c

관련 코드는 다음과 같다.

if (pte && (*pte & PTE_P))
    return ptov (PTE_ADDR (*pte)) + pg_ofs (uaddr);

이 반환값은 유저 VA 자체가 아니다. PintOS 커널이 같은 guest physical frame을 직접 볼 수 있게 만든 kernel virtual address다.

이 차이는 pml4 get page는 왜 커널 가상 주소를 돌려주나에서 uaddr = 0x8048123, PTE_ADDR = 0x12345000, KERN_BASE = 0x8004000000 값을 넣어 계산한다.

4. pml4_set_page()는 마지막 PTE에 frame을 연결한다

파일:

  • SW_AI-W11-pintos/pintos/threads/mmu.c

관련 코드는 다음과 같다.

*pte = vtop (kpage) | PTE_P | (rw ? PTE_W : 0) | PTE_U;

vtop(kpage)는 kernel virtual address가 가리키는 frame의 guest physical address를 얻는다. 거기에 present/writable/user bit를 합쳐 최종 PTE 한 칸을 만든다.

5. QEMU도 같은 bit 위치를 하드웨어처럼 걷는다

파일:

  • target/i386/tcg/system/excp_helper.c

QEMU의 64비트 page walk도 level별 entry 주소를 만든다.

level 4: (addr >> 39) & 0x1ff
level 3: (addr >> 30) & 0x1ff
level 2: (addr >> 21) & 0x1ff
level 1: (addr >> 12) & 0x1ff

present bit가 없으면 fault로 간다. 접근이 성립하면 accessed bit를 세우고, store 접근이면 dirty bit도 세우는 흐름이 이어진다.

최종 guest physical address는 page table entry의 주소 부분과 VA offset을 합쳐 만든다.

paddr = (pte & PG_ADDRESS_MASK & ~(page_size - 1)) | (addr & (page_size - 1));

이 주소는 host physical address가 아니다. Guest Physical Memory에서 다룬 것처럼 QEMU가 host process 안에서 backing하는 guest physical address다.

x86-64 페이지 테이블 워크 값 추적

1. VA를 index로 분해하기

입력:

VA = 0x0000000008048123

계산:

PML4 = (VA >> 39) & 0x1FF = 0x000 = 0
PDPE = (VA >> 30) & 0x1FF = 0x000 = 0
PDX  = (VA >> 21) & 0x1FF = 0x040 = 64
PTX  = (VA >> 12) & 0x1FF = 0x048 = 72
ofs  =  VA        & 0xFFF = 0x123 = 291

같은 계산을 4단계 탐색 과정으로 풀면 다음과 같다.

1. 현재 CR3가 가리키는 PML4 page를 본다.
2. PML4[0] entry를 읽는다.
3. 그 entry가 가리키는 PDPT page로 간다.
4. PDPT[0] entry를 읽는다.
5. 그 entry가 가리키는 PD page로 간다.
6. PD[64] entry를 읽는다.
7. 그 entry가 가리키는 PT page로 간다.
8. PT[72] entry를 읽는다.
9. 그 entry가 가리키는 frame base에 offset 0x123을 더한다.

여기서 PML4[0], PDPT[0], PD[64], PT[72]는 모두 8바이트 entry다.

2. index를 entry 주소 offset으로 바꾸기

entry 하나는 8바이트다.

PML4E byte offset = 0  << 3 = 0x000
PDPE byte offset  = 0  << 3 = 0x000
PDE byte offset   = 64 << 3 = 0x200
PTE byte offset   = 72 << 3 = 0x240

예를 들어 page table base가 0x0000000000200000이면 PTE 주소는 다음처럼 계산된다.

PTE address = 0x0000000000200000 + 0x240
            = 0x0000000000200240

이번에는 가상의 table base를 넣어 전체 주소를 이어 보자.

CR3가 가리키는 PML4 base = 0x100000

PML4E address = 0x100000 + (0  * 8) = 0x100000
PML4E value   = 0x200007
PDPT base     = 0x200000

PDPE address  = 0x200000 + (0  * 8) = 0x200000
PDPE value    = 0x300007
PD base       = 0x300000

PDE address   = 0x300000 + (64 * 8) = 0x300200
PDE value     = 0x400007
PT base       = 0x400000

PTE address   = 0x400000 + (72 * 8) = 0x400240
PTE value     = 0x12345067
frame base    = 0x12345000

final address = 0x12345000 + 0x123 = 0x12345123

각 entry 값의 낮은 12비트는 flag다. 따라서 base 주소를 얻을 때는 & ~0xFFF 또는 PintOS의 PTE_ADDR()로 이 부분을 잘라낸다.

3. 최종 PTE를 주소와 flag로 나누기

마지막 PTE 값이 다음과 같다고 하자.

PTE = 0x0000000012345067

낮은 12비트는 flag다.

frame base = PTE & ~0xFFF = 0x12345000
flags      = PTE &  0xFFF = 0x067

flag 해석:

0x001 PTE_P present
0x002 PTE_W writable
0x004 PTE_U user
0x020 PTE_A accessed
0x040 PTE_D dirty

최종 주소:

PA = frame base + offset
   = 0x12345000 + 0x123
   = 0x12345123

4. page fault는 어느 단계에서도 날 수 있다

다음 중 하나라도 present가 아니면 CPU는 최종 PA를 만들 수 없다.

PML4E not present -> #PF
PDPE  not present -> #PF
PDE   not present -> #PF
PTE   not present -> #PF

PintOS는 #PF를 받은 뒤 SPT를 보고 이 주소가 lazy load, stack growth, swapped-out page인지 판단한다.

정리

  • PintOS에서 보는 x86-64 4KB page 기준 VA는 9비트 index 네 개와 12비트 offset으로 나뉜다.
  • 각 page table은 512개의 8바이트 entry를 담는 4KB 배열이다.
  • 512개를 넘으면 linked list의 next로 이어지는 것이 아니라, 상위 단계의 다른 entry가 다른 하위 table page를 가리킨다.
  • 4단계 구조 전체는 512 * 512 * 512 * 512 * 4KB = 256TiB의 가상주소 번호를 표현할 수 있다.
  • PintOS의 PML4/PDPE/PDX/PTX 매크로는 이 index를 직접 계산한다.
  • PintOS도 x86-64용 4단계 page table을 쓴다.
  • page table 자체를 담는 4KB page는 pml4e_walk(..., create=true) 흐름에서 palloc_get_page(PAL_ZERO)로 만들어질 수 있다.
  • 유저 데이터 frame은 VM의 vm_get_frame()에서 palloc_get_page(PAL_USER)로 가져오는 별도 자원이다.
  • pml4e_walk()는 중간 table을 따라 최종 PTE의 주소를 찾는다.
  • pml4_set_page()는 최종 PTE에 frame 주소와 permission bit를 기록한다.
  • QEMU는 PintOS 정책을 모르고, guest CPU의 page-table walk와 #PF 효과를 재현한다.
  • 실제 OS와 최신 하드웨어에는 huge page, 5단계 page table 같은 확장이 있을 수 있으므로 이 문서의 계산은 PintOS 학습용 4단계 기본형에 해당한다.
