명령어 실행 사이클

명령어 실행 사이클

CPU는 전원이 켜진 동안 명령어를 읽고, 해석하고, 실행하는 루프를 계속 돈다. OS가 끼어드는 지점은 이 루프가 인터럽트나 예외로 꺾이는 순간이다.

명령어 실행 사이클 구조

CPU는 전원이 켜진 순간부터 꺼질 때까지 하나의 루프를 반복한다. fetch → decode → execute. 이 세 단계가 한 바퀴 도는 것이 하나의 명령어 실행 사이클이다. OS가 프로세스를 전환하든, 인터럽트를 처리하든, 결국 CPU가 하는 일은 이 사이클의 반복이다. OS를 이해하려면 이 사이클이 어떤 상태를 읽고, 어떤 상태를 바꾸는지 먼저 알아야 한다.

상세 설명

추상 개념 (CPU 하드웨어 규칙)

사이클의 각 단계는 다음과 같다.

Fetch: RIP(Instruction Pointer)가 가리키는 메모리 주소에서 명령어 바이트를 읽는다. x86-64는 가변 길이 명령어를 사용하므로, CPU는 첫 바이트(opcode)를 보고 나머지 길이를 판단한다.

Decode: 읽어 온 바이트를 opcode, operand, addressing mode로 분해한다. 현대 CPU는 이 단계에서 마이크로아키텍처 내부의 micro-op으로 변환하지만, OS 관점에서는 ISA 수준의 의미만 중요하다.

Execute: 분해된 명령어의 의미대로 연산을 수행한다. ALU 연산이면 레지스터 값이 바뀌고, 메모리 접근이면 load/store가 일어나며, 분기이면 RIP가 대상 주소로 변경된다. 실행 후 RIP는 다음 명령어를 가리키도록 갱신된다(분기가 아니면 현재 명령어 길이만큼 증가).

%% CPU 메인 루프
flowchart LR
  fetch["Fetch<br/>RIP에서 바이트 읽기"]
  decode["Decode<br/>opcode 분해"]
  execute["Execute<br/>ALU / 분기 / 메모리"]
  check["사이클 중단 지점<br/>인터럽트 검사: execute 완료 후"]
  fetch --> decode
  decode --> execute
  execute --> fetch
  execute -.-> check

이 사이클에서 OS와 관련된 핵심 이벤트가 끼어드는 지점이 있다.

이벤트발생 시점CPU 동작
인터럽트명령어 경계에서 전달RIP/CS/RFLAGS를 저장하고 IDT로 점프. CPL 또는 스택이 바뀔 때만 이전 SS:RSP도 저장
예외(#PF 등)execute 중현재 명령어 중단, 핸들러로 점프
syscall 명령execute 단계RCX=RIP, R11=RFLAGS, MSR_LSTAR로 점프

분기·호출·복귀와 syscall도 다음 RIP를 바꾸는 명시적 제어 이전이다. 그중 인터럽트와 예외는 정상적인 분기 명령 없이 제어를 handler로 넘길 수 있다. OS는 특히 비동기 인터럽트를 이용해 “유저 프로그램이 자발적으로 커널을 부르지 않아도” 제어권을 가져온다(선점 스케줄링의 기초).

실제 OS (Linux/Windows)

실제 OS에서 이 사이클 자체는 하드웨어가 처리하므로 OS가 개입하지 않는다. OS가 관여하는 것은 사이클이 중단되는 순간이다.

Linux의 경우, timer interrupt가 RIP를 커널의 인터럽트 핸들러로 바꾸면 scheduler_tick()이 현재 프로세스의 시간을 감소시키고, 시간이 다 되면 schedule()을 호출해 다른 프로세스의 RIP로 교체한다. 이것이 선점 스케줄링이다.

Windows도 동일한 원리로 작동하며, IRQL(Interrupt Request Level) 체계를 통해 인터럽트 우선순위를 관리한다.

핵심은 같다. CPU는 항상 fetch-decode-execute만 하고, OS는 인터럽트/예외를 통해 “어떤 명령어를 다음에 fetch할지”를 결정한다.

PintOS 구현

PintOS에서 이 사이클이 관찰되는 핵심 경로는 두 가지다.

1. 부팅 후 첫 명령어 실행

BIOS → bootloader → kernel.o의 start → main() 순서로 RIP가 이동한다. main()에서 thread_start() → schedule() → do_iret()을 통해 idle thread가 첫 번째로 실행된다. 이 전체 과정은 fetch-decode-execute 사이클이 RIP를 따라가는 것일 뿐이다.

2. Timer interrupt로 인한 스케줄링

%% PintOS timer interrupt와 schedule()
flowchart LR
  cpu_a["CPU<br/>Thread A 실행 중<br/>RIP=0x4000b0"]
  pit["i8254 PIT<br/>IRQ0<br/>100Hz"]
  pic["i8259 PIC<br/>인터럽트 신호"]
  save["CPU 상태 저장<br/>RIP/CS/RFLAGS push<br/>CPL·스택 전환 시 이전 SS:RSP도 push<br/>RIP ← IDT[0x20]"]
  handler["timer_interrupt()<br/>thread_tick()<br/>thread_ticks++<br/>≥4이면 yield 예약"]
  scheduler["schedule()<br/>intr_yield_on_return<br/>next = ready_list에서 최고 우선순위 선택"]
  cpu_b["CPU<br/>do_iret()<br/>RIP ← Thread B의 저장된 RIP<br/>Thread B 실행 시작"]
  cpu_a -->|"Thread A 실행 중"| pit
  pit -->|"IRQ0"| pic
  pic -->|"CPU로 전달"| save
  save -->|"timer interrupt handler"| handler
  handler -->|"intr_yield_on_return"| scheduler
  scheduler -->|"do_iret()"| cpu_b

결국 “다른 스레드를 실행한다”는 것은 CPU의 RIP를 다른 스레드의 저장된 RIP 값으로 교체하는 것이다. CPU는 여전히 fetch-decode-execute를 할 뿐이다.

QEMU 에뮬레이션

QEMU는 guest CPU의 fetch-decode-execute를 소프트웨어로 재현한다.

TCG(Tiny Code Generator) 모드에서의 흐름:

%% QEMU TCG에서 guest 명령어 실행
flowchart TD
  guest["Guest 코드 블록<br/>RIP 0x4000b0~0x4000c8"]
  tb["TB<br/>host native code"]
  reason["TB 끝 이유?"]
  next["다음 Guest 블록<br/>translate or 캐시 hit"]
  interrupt["QEMU 메인 루프<br/>인터럽트 주입"]
  mmio["device model<br/>MMIO 접근 처리"]
  guest -->|"translate"| tb
  tb -->|"execute"| reason
  reason -->|"분기/점프"| next
  reason -->|"인터럽트 대기"| interrupt
  reason -->|"MMIO 접근"| mmio
  next -->|"다음 블록"| guest
  interrupt -->|"env-&gt;eip 갱신"| guest
  mmio -->|"복귀"| guest

QEMU TCG는 guest PC를 매 명령 뒤 반드시 env->eip에 기록하지 않는다. Translation Block 내부에서는 다음 PC가 생성된 host code와 TB metadata에 암묵적으로 유지될 수 있고, TB exit·fault·interrupt·debug 경계에서 env->eip를 동기화한다. guest 인터럽트를 주입할 때는 동기화된 상태와 guest IDT를 사용해 handler 주소로 제어를 옮긴다. 이것은 실제 CPU의 상태 전이를 소프트웨어로 모사한 것이다.

KVM 가속 모드에서는 guest 명령어를 실제 CPU가 직접 실행하므로 fetch-decode-execute는 하드웨어가 수행하고, QEMU는 VM exit 시에만 개입한다.

모드fetch-decode-execute 수행자QEMU 개입 시점
TCGQEMU 소프트웨어매 TB(Translation Block)
KVM실제 CPU 하드웨어VM exit (I/O, pf 등)

명령어 실행 사이클 값 추적

x86-64 명령어의 길이 예시:

명령어바이트 수바이트 내용
nop190
mov $1, %rdi748 c7 c7 01 00 00 00
syscall20f 05
ret1c3

RIP = 0x00000000004000b0에서 mov $1, %rdi(7바이트)를 실행하면, 다음 fetch 시 RIP = 0x00000000004000b7이 된다.

PintOS의 TIME_SLICE는 4 tick이다. QEMU PIT(i8254)의 기본 주파수는 100 Hz이므로, 한 tick은 10ms다. 따라서 한 스레드가 연속 실행되는 최대 시간은 약 40ms(4 × 10ms)이며, 이 시간 동안 CPU는 수백만 번의 fetch-decode-execute 사이클을 수행한다.

100 MHz 기준 (단순 계산):
  40ms × 100,000,000 cycles/s = 4,000,000 cycles
  IPC 1 가정 시: ~4,000,000 instructions per time slice
