GDB 스텁 레지스터 읽기

확인 범위: 이 문서는 GDB Remote Protocol을 통해 QEMU가 유지하는 guest 레지스터 상태를 GDB에 전달하는 일반 흐름과 해석 기준을 설명한다. 제시된 레지스터 번호·구조체 필드·함수 경로·응답 크기·PintOS 출력·성능 관련 판단은 특정 QEMU·GDB 버전의 소스 코드나 실제 실행·측정으로 검증한 결과가 아니라, 적용 환경에서 별도 확인이 필요한 구현 예시다.

한 줄 요약: info registers를 치면 host CPU가 아니라 QEMU가 유지하는 guest 레지스터를 stub이 통역해 전달하는 과정.

GDB 스텁 레지스터 읽기 상태

QEMU의 GDB stub은 guest CPU의 레지스터를 호스트 GDB에게 읽혀주는 통역관이다. PintOS 디버깅에서 info registers를 치면, GDB는 실제 호스트 CPU 레지스터가 아니라 QEMU가 소프트웨어로 유지하는 CPUX86State 구조체의 필드를 읽는다. 이 과정은 GDB Remote Serial Protocol의 g 패킷을 통해 이루어진다.

상세 설명

추상 개념 (GDB Remote Protocol)

GDB와 QEMU는 TCP 소켓(보통 localhost:1234)으로 연결된다. GDB가 레지스터를 읽고 싶을 때의 프로토콜:

g 패킷은 “모든 레지스터를 한 번에 보내라”는 요청이다. QEMU는 CPUX86State 구조체에서 레지스터 값들을 순서대로 꺼내 hex 문자열로 인코딩해 응답한다.

실제 동작 흐름

QEMU 내부에서 GDB register read가 처리되는 경로:

%% GDB register read call flow
flowchart TD
  gdb_packet["1. GDB가 $g 패킷 전송"]
  handle_packet["2. gdb_handle_packet() 수신"]
  read_registers["3. 'g' 명령<br/>→ gdb_read_registers() 호출"]
  arch_dispatch["4. cpu_gdb_read_register()<br/>아키텍처별 구현으로 위임"]
  x86_read["5. x86_cpu_gdb_read_register()<br/>CPUX86State에서 값 복사"]
  hex_encode["6. 레지스터 값을 hex 문자열로 인코딩"]
  response["7. 응답 패킷 전송"]
  gdb_packet --> handle_packet
  handle_packet --> read_registers
  read_registers --> arch_dispatch
  arch_dispatch --> x86_read
  x86_read --> hex_encode
  hex_encode --> response

핵심: 호스트 CPU와 무관

에뮬레이션 모드(TCG)에서 QEMU가 guest 명령어를 실행할 때, guest 레지스터 값은 호스트 CPU의 실제 레지스터가 아니라 CPUX86State 구조체의 regs[] 배열에 저장된다. GDB가 읽는 것은 이 배열이다.

호스트 하드웨어 레지스터는 QEMU 프로세스 자체의 실행에 사용된다. 반면 guest RAX/RBX/RIP의 관찰 가능한 정본은 CPUX86State이고, TCG 실행과 GDB stub 읽기는 같은 guest 상태를 공유한다.

TCG 실행 경로에서는 guest 명령어가 번역 블록을 거쳐 host 코드로 실행되고, 그 결과가 CPUX86State.regs[]에 갱신된다. GDB의 레지스터 읽기 경로는 이 배열을 읽어 응답하므로, 실행 결과와 관찰 대상이 같은 guest 상태에 연결된다.

특수 레지스터 읽기

CR 레지스터(CR0, CR2, CR3, CR4)는 표준 g 패킷에 포함되지 않는다. QEMU의 x86 target description XML에서 별도 feature로 노출된다:

GDB 스텁 레지스터 읽기 값 추적

g 패킷 응답 크기 계산 (x86-64):

레지스터 그룹개수크기바이트 합
범용 (RAX-R15)168B128B
RIP18B8B
EFLAGS14B4B
세그먼트 (CS-GS)64B24B
기본 합164B
hex 인코딩 후328 chars

FPU/SSE 레지스터 포함 시 훨씬 커진다 (ST0-ST7: 80B, XMM0-XMM15: 256B).

TCP 소켓 통신이므로 GDB stepi 한 번에 최소 2 round trip 발생:

  1. s (step) → 실행 후 stop reply
  2. g (read regs) → 레지스터 덤프

이것이 QEMU GDB 디버깅이 느린 이유 중 하나다.
