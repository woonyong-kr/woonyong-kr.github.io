thread_tick()와 TIME_SLICE 검사

thread_tick()와 TIME_SLICE 검사

thread_tick()은 timer interrupt가 들어올 때마다 현재 스레드의 실행 시간을 세고, TIME_SLICE를 넘으면 인터럽트 복귀 시점에 yield를 예약한다.

타이머 인터럽트에서 스레드 전환까지

하드웨어는 time slice를 직접 알지 못한다. 하드웨어가 제공하는 것은 주기적인 타이머 인터럽트다. 타이머가 매 tick마다 CPU를 인터럽트하면 OS는 현재 스레드가 실행된 시간을 소프트웨어 카운터로 추적한다. 카운터가 임계값에 도달했을 때 OS가 재스케줄링을 요청하면서 time slice가 만들어진다.

PintOS에서는 timer_interrupt()가 매 타이머 인터럽트마다 thread_tick()을 호출한다. thread_tick()은 현재 스레드의 실행 통계를 갱신하고, 마지막으로 스케줄된 뒤 사용한 tick 수를 센다. 이 값이 TIME_SLICE = 4에 도달하면 intr_yield_on_return()을 호출한다.

이 호출은 즉시 context switch를 일으키지 않는다. 인터럽트 처리 중에는 yield만 예약하고, 실제 전환은 인터럽트 핸들러가 복귀할 때 일어난다. 새 스레드가 선택되어 schedule()이 실행되면 thread_ticks가 0으로 초기화되고 다음 time slice가 시작된다.

스레드가 자발적으로 양보하지 않아도 타이머 인터럽트는 OS에 제어권을 돌려준다. OS가 time slice 소진 여부를 검사해 다른 스레드를 실행할 수 있다는 점에서 이 과정은 **선점형 스케줄링(preemptive scheduling)**을 구성한다.

PintOS의 thread_tick() 구현

함수는 먼저 현재 스레드의 종류에 따라 실행 통계를 갱신한다.

조건증가 카운터의미
t == idle_threadidle_ticksCPU가 유휴 상태
t->pml4 != NULLuser_ticks유저 프로그램 실행 중
그 외kernel_ticks커널 스레드 실행 중

이 통계는 thread_print_stats()에서 출력되며 CPU 사용률을 대략적으로 파악하는 데 쓰인다.

통계를 갱신한 뒤에는 thread_ticks를 먼저 증가시키고 TIME_SLICE와 비교한다. thread_ticks는 현재 스레드가 마지막으로 스케줄된 이후 경과한 tick 수다. ++thread_ticks로 증가한 값을 비교하므로 4번째 tick에서 yield가 예약된다.

그 생명주기는 다음과 같다.

schedule() 호출
  -> thread_ticks = 0            (새 time slice 시작)

tick 1: thread_tick() -> thread_ticks = 1 -> 계속 실행
tick 2: thread_tick() -> thread_ticks = 2 -> 계속 실행
tick 3: thread_tick() -> thread_ticks = 3 -> 계속 실행
tick 4: thread_tick() -> thread_ticks = 4 -> intr_yield_on_return()
  -> 인터럽트 복귀 시 thread_yield()
  -> schedule()
  -> thread_ticks = 0            (다음 스레드의 새 time slice)

이 흐름을 함수와 조건 중심으로 나타내면 다음과 같다.

flowchart TD
    A["timer_interrupt()"] --> B["ticks++"]
    B --> C["thread_tick()"]
    C --> D{"t == idle_thread?"}
    D -- yes --> E["idle_ticks++"]
    D -- no --> F{"t->pml4 != NULL?"}
    F -- yes --> G["user_ticks++"]
    F -- no --> H["kernel_ticks++"]
    E --> I["++thread_ticks"]
    G --> I
    H --> I
    I --> J{"thread_ticks >= TIME_SLICE(4)?"}
    J -- yes --> K["intr_yield_on_return()"]
    J -- no --> L["return"]
    K --> L

tick 수와 시간 계산

PintOS에서 TIMER_FREQ는 100 Hz이므로 한 tick은 10 ms다. TIME_SLICE가 4 tick이므로 한 스레드가 time slice를 모두 사용하면 약 40 ms 동안 실행된다.

TIME_SLICE          = 4 ticks
1 tick              = 1 / TIMER_FREQ = 1/100 초 = 10 ms
time slice          = 4 * 10 ms = 40 ms

타이머가 초당 100번 발생하고 네 tick마다 time slice가 만료되므로, 한 스레드가 매번 time slice를 모두 소진한다는 조건에서는 초당 최대 25회의 선점을 계산할 수 있다.

TIMER_FREQ          = 100 Hz (초당 100 tick)
최대 선점 횟수      = 100 / 4 = 25 회/초

이 값은 스레드가 time slice를 끝까지 사용하는 경우에 대한 계산이다. 스레드가 자발적으로 yield하거나 I/O 대기로 block되면 그보다 일찍 전환될 수 있다.

Round-Robin 관점에서 보면 네 번째 tick에 yield가 예약되고, 인터럽트 복귀 뒤 다음 스레드의 time slice가 시작된다.

Thread A:  |==tick1==|==tick2==|==tick3==|==tick4==|  yield  |
Thread B:                                          |==tick1==|==tick2==|...
           t=0      t=10ms   t=20ms   t=30ms   t=40ms

thread_ticks: 1        2        3        4 -> yield

idle_ticks, user_ticks, kernel_ticks는 모두 unsigned long long이다. 입력 문서의 100 Hz 계산에 따르면 overflow까지 약 5.8 * 10^9 년이 걸리므로, PintOS가 실행되는 범위에서는 overflow를 걱정하지 않는다는 설명이다.

QEMU에서 보이는 경계

QEMU도 time slice를 알지 못한다. QEMU의 역할은 8254 PIT가 설정된 주기에 따라 IRQ0를 guest CPU에 전달하는 것이다. 그 뒤 PintOS가 인터럽트를 처리하면서 thread_ticks와 TIME_SLICE를 비교한다.

전체 경로는 다음과 같다.

  1. 호스트 타이머 만료 — QEMU의 PITChannelState에 등록된 timer_mod() 콜백이 호스트 이벤트 루프에서 발생
  2. IRQ0 raise — pit_irq_timer_update() → qemu_irq_raise(s->irq) → i8259 PIC에 IRQ0 전달
  3. guest interrupt 주입 — TB 실행 종료 시점에 cpu_exec() 루프가 pending interrupt를 확인, do_interrupt64()로 IDT 0x20(PIT) 벡터 처리
  4. PintOS handler 실행 — timer_interrupt() → thread_tick() → thread_ticks 비교 → 필요 시 intr_yield_on_return()

따라서 QEMU가 관찰하는 것은 guest instruction의 흐름이다. 어떤 스레드가 몇 tick을 실행했는지 세고 time slice 만료를 판단하는 일은 guest인 PintOS의 소프트웨어 로직이다.

TCG 모드에서는 TB 실행 도중의 인터럽트 검사가 TB 경계에서 이뤄진다. 입력 문서는 매우 긴 기본 블록에서 타이머 인터럽트 전달이 조금 지연되고 thread_ticks 갱신도 한두 tick 밀릴 수 있다고 설명한다. 다만 이 문서에는 지연 범위나 PintOS에 미치는 실질적 영향을 직접 측정한 결과가 제시되어 있지 않으므로, 영향이 없다고 검증된 사실로 해석해서는 안 된다.

Linux와 Windows에서 대응하는 개념

Linux의 CFS(Completely Fair Scheduler)는 PintOS처럼 고정 tick 수를 time slice로 사용하는 대신 가상 실행 시간(vruntime)을 기준으로 스케줄링한다. 그래도 scheduler_tick()이 매 tick마다 호출되어 현재 태스크의 vruntime을 갱신하고 resched_curr()로 재스케줄링을 요청한다는 점에서는, 주기적인 tick을 계기로 실행 상태를 갱신하고 재스케줄링을 요청하는 흐름을 비교할 수 있다.

Windows에서는 기본 time quantum이 스레드 우선순위와 시스템 유형에 따라 달라진다고 설명한다. 입력 문서가 제시한 값은 클라이언트 Windows에서 약 2 clock interval 또는 약 30 ms, 서버에서 약 12 clock interval 또는 약 180 ms다. 그러나 해당 수치의 Windows 버전, 설정 조건, 출처가 입력에 포함되어 있지 않다. 따라서 모든 Windows 환경에 적용되는 고정값이 아니라 이 문서가 제시한 제한적인 비교값으로 보아야 한다.

이 표의 Windows 수치와 세부 동작에도 입력 문서 안에서 별도의 근거가 제시되어 있지 않다. PintOS의 실행 흐름을 다른 스케줄러 용어와 대조하는 참고 범위로 사용하는 것이 적절하다.

GDB로 관찰할 지점

다음 스크립트는 thread_tick() 진입, time slice 만료 조건, 통계 카운터, schedule()의 리셋 지점을 각각 관찰한다. 입력 문서에는 실제 실행 결과가 포함되어 있지 않으므로, 아래 내용은 관찰 절차이지 검증 결과가 아니다.

thread_ticks 실시간 모니터링

(gdb) b thread_tick
(gdb) commands
  silent
  printf "thread_ticks=%d, thread=%s, pri=%d\n", thread_ticks+1, thread_current()->name, thread_current()->priority
  c
end

TIME_SLICE 만료 포착

(gdb) b thread.c:215 if thread_ticks+1 >= 4
(gdb) commands
  printf "TIME_SLICE expired! thread=%s, switching...\n", thread_current()->name
  bt 3
  c
end

idle vs user vs kernel tick 비율 확인

(gdb) b thread_print_stats
(gdb) commands
  printf "idle=%llu user=%llu kernel=%llu\n", idle_ticks, user_ticks, kernel_ticks
  c
end

schedule() 시점 thread_ticks 리셋 확인

(gdb) b thread.c:715
(gdb) commands
  silent
  printf "thread_ticks reset: prev=%s → next=%s\n", thread_current()->name, list_entry(list_front(&ready_list), struct thread, elem)->name
  c
end
