UNINIT Page — 지연 로딩을 위한 초기화 전 페이지

UNINIT Page — 지연 로딩을 위한 초기화 전 페이지

확인 범위: 이 문서는 demand paging과 UNINIT page의 일반 개념 및 설계상 선택 기준을 설명하고, 제시된 PintOS·Linux·QEMU 코드 경로와 동작은 특정 구현을 해석한 내용이다. 코드 좌표, 메모리 크기·절약량, 호출 순서와 GDB 관찰 결과는 해당 소스 버전과 실제 빌드·실행 기록을 대조해야 확정할 수 있다.

한 줄 요약: 모든 유저 페이지가 처음 태어나는 중간 상태로, 실제 접근(page fault) 시점에 ANON·FILE 등 최종 타입으로 변신해 lazy loading을 가능하게 한다.

UNINIT Page 상태

UNINIT page는 PintOS VM 시스템에서 lazy loading을 구현하기 위한 중간 상태 페이지 타입이다. 모든 유저 페이지는 처음 UNINIT 상태로 태어나며, 실제 접근(page fault)이 발생할 때 비로소 ANON, FILE 등 최종 타입으로 **변신(transmute)**한다. 이 디자인 덕분에 exec 시점에 전체 ELF를 메모리에 적재하지 않고, 필요한 페이지만 on-demand로 적재할 수 있다.

상세 설명

추상 개념 (Demand Paging 원리)

Demand paging의 핵심은 “약속만 해두고, 실제 물리 frame은 접근 시점에 할당”하는 것이다. UNINIT page는 이 약속을 데이터로 표현한 것이다:

  • 무엇을 적재할지 → vm_initializer *init (콜백 + aux 데이터)
  • 어떤 타입이 될지 → enum vm_type type (VM_ANON 또는 VM_FILE)
  • 어떻게 초기화할지 → page_initializer 함수 포인터

실제 OS (Linux)

Linux에서 유사한 개념은 VMA(Virtual Memory Area)다. mmap() 호출 시 VMA만 등록하고 물리 page는 할당하지 않는다. page fault 시 do_fault() → __do_fault()가 backing store에서 데이터를 읽어온다. PintOS의 UNINIT page는 이 VMA + fault handler 조합을 page 단위로 구현한 것이다.

uninit_new() (vm/uninit.c)

핵심: page->frame = NULL이므로 물리 메모리를 전혀 소비하지 않는다.

uninit_initialize() — 변신 시점

실행 순서:

  1. page_initializer() → struct page의 operations를 최종 타입으로 교체
  2. init() → 실제 데이터를 kva에 적재 (디스크에서 읽기 등)

순서가 중요한 이유: page_initializer가 page->anon 또는 page->file_page union 필드를 초기화한다. 이 작업이 먼저 완료되어야 init()에서 해당 필드를 참조할 수 있다.

uninit_destroy() — 미접근 페이지의 종료

이 함수가 호출되는 경우: 프로세스가 exit할 때 한 번도 fault되지 않은 페이지. 예를 들어, ELF의 .bss 영역이 크지만 프로그램이 일부만 사용한 경우.

QEMU 에뮬레이션

QEMU 관점에서 UNINIT page는 보이지 않는다. PML4에 매핑이 없으므로 guest가 해당 VA에 접근하면 QEMU의 softmmu가 pf를 발생시키고, PintOS의 page_fault handler가 실행된다. QEMU는 물리 frame이 할당된 후에야 해당 GPA→HVA 매핑을 인식한다.

UNINIT → fault → claim 과정에서 QEMU가 관여하는 지점은 정확히 2곳이다:

  1. #PF 발생: softmmu가 PTE walk에서 present=0을 발견 → exception vector 14 inject → PintOS page_fault() 실행
  2. claim 완료 후: pml4_set_page()로 PTE에 PFN이 기록되면, 다음 접근 시 softmmu가 이 PTE를 읽어 정상 변환 수행. QEMU의 소프트웨어 TLB에 새 엔트리가 캐시된다.

uninit_copy() — fork 시 UNINIT 페이지 복사

fork 시 부모의 UNINIT page를 자식에게 복사하는 것은 단순 memcpy가 아니다:

%% UNINIT page fork 복사
flowchart TD
  parent["부모 UNINIT page<br/>src-&gt;va<br/>src-&gt;uninit.type<br/>src-&gt;uninit.init<br/>src-&gt;uninit.aux"]
  deep_copy["lazy_load_arg deep copy<br/>새 lazy_load_arg를 malloc<br/>내용 복사<br/>file_reopen으로 file 포인터 독립화"]
  alloc["자식 UNINIT page 등록<br/>vm_alloc_page_with_initializer(type, va, writable, init, new_aux)"]
  child["자식 SPT<br/>새 UNINIT page<br/>독립된 aux<br/>독립된 struct file *"]
  parent --> deep_copy
  deep_copy --> alloc
  alloc --> child

file_reopen()이 핵심이다. 부모와 자식이 같은 struct file *을 공유하면, 한쪽이 close할 때 다른 쪽의 lazy load가 실패한다. 별도 파일 디스크립터를 만들어 독립적인 파일 접근을 보장한다.

GDB 관찰 스크립트

1. UNINIT page 생성 추적 — vm_alloc_page_with_initializer 진입:

(gdb) break vm/vm.c:199
(gdb) commands
  silent
  printf "alloc UNINIT: va=%p type=%d writable=%d\n", upage, type, writable
  continue
  end

2. uninit_initialize 변신 관찰 — fault 시 타입 전환:

(gdb) break vm/uninit.c:48
(gdb) commands
  printf "UNINIT→transmute: va=%p type=%d init=%p aux=%p\n", page->va, uninit->type, uninit->init, uninit->aux
  continue
  end

3. uninit_destroy 호출 확인 — 미접근 페이지 정리:

(gdb) break vm/uninit.c:65
(gdb) commands
  printf "UNINIT destroy (never faulted): va=%p aux=%p\n", page->va, page->uninit.aux
  continue
  end

aux가 NULL이 아닌데 free하지 않으면 메모리 누수다.

4. uninit_copy fork 추적 — 자식 UNINIT 생성:

(gdb) break vm/uninit.c:73
(gdb) commands
  printf "UNINIT copy: src_va=%p type=%d\n", src->va, src->uninit.type
  continue
  end

5. page_initializer 디스패치 확인 — anon vs file:

(gdb) break vm/uninit.c:56
(gdb) commands
  printf "page_initializer=%p (anon_init=%p file_init=%p)\n", uninit->page_initializer, anon_initializer, file_backed_initializer
  continue
  end

실제로 어떤 initializer가 호출되는지 확인한다.

6. 프로세스의 총 UNINIT page 수 세기:

(gdb) define count_uninit
  set $count = 0
  # SPT hash table 순회 필요 — 간접적으로 spt_kill에 breakpoint
  printf "UNINIT page count requires SPT traversal\n"
end

또는 vm_alloc_page_with_initializer hit 수를 세면 exec 시점의 UNINIT page 총 수를 알 수 있다.
