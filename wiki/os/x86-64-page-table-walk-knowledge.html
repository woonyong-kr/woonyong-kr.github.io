x86-64 페이지 테이블 워크

x86-64 페이지 테이블 워크 시작

0x8048123이라는 유저 가상 주소가 있다.

주소 변환과 메모리에서는 이 주소를 page base 0x8048000과 offset 0x123으로 나눴다. 그런데 x86-64 CPU는 page table에서 0x8048000이라는 key를 한 번에 찾지 않는다.

CPU는 주소의 비트를 네 조각으로 더 나눠서 다음 표들을 차례로 걷는다.

현대 x86-64에는 5단계 page table 옵션도 있다. 하지만 PintOS 학습에서는 PML4 -> PDPE -> PDE -> PTE 흐름을 먼저 정확히 잡는 것이 목적이다.

먼저 가상 주소 하나가 page table을 통과하는 과정을 다음 질문에서 시작한다.

가상 주소 한 개는 어떻게 4개의 page-table index와 1개의 offset으로 쪼개질까?

이 과정을 따라가면 PintOS의 구현과 page table에 필요한 메모리에 관한 질문도 함께 설명할 수 있다.

PintOS도 정말 4단계 page table을 쓰나? 512개를 넘으면 linked list처럼 next pointer로 이어 붙이나? page table 자체를 담는 4KB 메모리는 누가 가져오나?

x86-64 페이지 테이블 워크 필요성

운영체제 책에서는 “page table이 VA를 PA로 바꾼다”고 짧게 말한다. 하지만 디버깅할 때는 그 말만으로 부족하다.

실제로는 이런 질문을 해야 한다.

  • 현재 CR3가 가리키는 최상위 page table은 어디인가?
  • 이 VA의 PML4 index는 몇 번인가?
  • 중간 page table entry가 present가 아니면 어디서 page fault가 나는가?
  • 마지막 PTE에는 frame 주소와 permission bit가 어떻게 들어 있는가?
  • QEMU는 이 walk를 OS 정책으로 처리하나, 하드웨어 효과로 재현하나?

이 질문에 답할 수 있어야 page fault가 어느 단계에서 발생했는지 추적할 수 있다.

x86-64 페이지 테이블 워크 흐름

x86-64 4KB page, 4단계 page table 기준에서 가상 주소는 다음처럼 나뉜다.

여기서 bits 63..48은 새로운 table index가 아니다. 4단계 모드에서는 bit 47의 부호 확장(sign extension)처럼 맞아야 하는 canonical address 영역이다.

9비트 index 하나는 0..511 중 하나를 고른다. entry 하나가 8바이트라서 page table 한 장은 다음 크기가 된다.

따라서 page table도 메모리 안에 있는 4KB짜리 배열이다. CPU는 VA의 비트 조각을 배열 index로 사용해 다음 table의 주소를 찾는다.

이 과정을 “주소를 헤더처럼 4단계로 잘라서 찾아간다”고 설명하면 큰 방향은 맞다. 다만 정확히는 header가 아니라 주소 비트 필드다. VA 안의 특정 bit 구간이 각각 배열 index 역할을 한다.

이 구조는 linked list가 아니라 4단계 트리다.

flowchart LR
    CR3["CR3 register"] --> PML4["PML4 page<br/>512 entries"]
    PML4 -->|"bits 47..39<br/>9-bit index"| PDPT["PDPT page<br/>512 entries"]
    PDPT -->|"bits 38..30<br/>9-bit index"| PD["PD page<br/>512 entries"]
    PD -->|"bits 29..21<br/>9-bit index"| PT["PT page<br/>512 entries"]
    PT -->|"bits 20..12<br/>9-bit index"| Frame["Data Frame<br/>4KB"]
    Frame -->|"bits 11..0<br/>12-bit offset"| Byte["최종 byte"]

따라서 512개가 넘을 때 page header의 next 주소로 이어지는 것은 아니다. 상위 단계의 다른 entry를 거쳐 다른 table page로 내려간다.

범위 계산

각 단계는 512개 entry 가운데 하나를 고른다. offset 12비트는 마지막 data page 안의 바이트 위치를 나타낸다.

그래서 4단계 page table이 표현할 수 있는 전체 가상주소 수는 다음과 같다.

이 계산은 실제 RAM이 256 TiB 있다는 뜻이 아니다. 그만큼의 가상주소 번호를 표현할 수 있다는 뜻이다. 실제 frame은 page fault가 나거나 mapping을 설치할 때 필요한 만큼만 붙는다.

각 table page가 담당하는 범위도 계산할 수 있다.

이 표에서 next pointer가 필요하지 않은 이유를 확인할 수 있다. page table page 하나가 꽉 차면 같은 레벨의 다음 page로 이어지는 것이 아니라, 상위 index가 바뀌면서 다른 하위 table page를 가리킨다.

가상 주소를 손으로 따라가기

다음 가상 주소가 page table을 통과하는 과정을 손으로 따라가 보자.

비트 조각은 이렇게 나온다.

각 table entry의 byte offset은 index에 8을 곱한다.

마지막 PTE가 frame base 0x12345000을 가리키고 present라면 최종 주소는 다음처럼 계산된다.

sequenceDiagram
    participant CPU as CPU/MMU
    participant PML4 as PML4[0]
    participant PDPT as PDPT[0]
    participant PD as PD[64]
    participant PT as PT[72]
    participant MEM as Frame

    CPU->>PML4: CR3 + 0*8 = offset 0x000
    PML4-->>CPU: entry → PDPT base
    CPU->>PDPT: PDPT_base + 0*8 = offset 0x000
    PDPT-->>CPU: entry → PD base
    CPU->>PD: PD_base + 64*8 = offset 0x200
    PD-->>CPU: entry → PT base
    CPU->>PT: PT_base + 72*8 = offset 0x240
    PT-->>CPU: PTE → frame 0x12345000 | P|W|U
    CPU->>MEM: 0x12345000 + 0x123 = 0x12345123

실제 운영체제

Linux와 Windows도 x86-64 하드웨어 위에서는 같은 page-table walk 원리를 사용한다. CPU는 CR3에서 시작해 page table entry의 present, writable, user, accessed, dirty 같은 bit를 검사한다.

다만 실제 하드웨어와 OS가 항상 4KB page만 쓰는 것은 아니다. huge page와 5단계 page table 같은 확장이 있을 수 있다.

실제 OS는 page table 외의 상태도 함께 관리한다.

  • Linux는 mm_struct, VMA, page cache, swap, copy-on-write, NUMA, huge page 같은 상태를 함께 관리한다.
  • Windows도 process address space, VAD, section object, prototype PTE, working set, pagefile 같은 구조를 함께 쓴다.

page-table walk는 하드웨어의 주소 번역 과정이다. 반면 fault를 처리해 실행을 계속할지 종료할지는 커널의 VM 정책이 결정한다.

PintOS는 이 현실을 교육용으로 줄여서 page table, supplemental page table, frame, swap/file-backed page를 직접 구현하게 만든다.

pml4e_walk(pml4, va, create)는 최종 PTE의 주소를 돌려준다.

  • create == false: 중간 table이 없으면 NULL을 반환한다.

QEMU

QEMU는 PintOS의 SPT, stack growth, mmap 정책을 모른다.

QEMU가 재현하는 것은 guest CPU의 page-table walk다. TCG 경로에서는 현재 guest CR3와 guest VA를 기준으로 page table entry 주소를 계산하고, present/permission bit를 검사한다.

대표 파일:

  • target/i386/tcg/system/excp_helper.c
    • mmu_translate()

QEMU 코드에도 같은 index 계산이 나온다.

각 index는 << 3으로 8바이트 entry offset이 된다.

entry가 present가 아니면 QEMU는 guest CPU의 page fault 효과를 만든다. 그 뒤 page_fault()에서 이 fault를 처리할지 결정하는 주체는 PintOS다.

QEMU 코드에는 PG_MODE_LA57 분기도 있다. 이 분기는 5단계 page table이 켜진 guest를 위한 경로다. PintOS를 이해할 때는 그 분기보다 addr >> 39, addr >> 30, addr >> 21, addr >> 12로 내려가는 4단계 흐름을 먼저 보면 된다.

QEMU의 64비트 page walk도 level별 entry 주소를 만든다.

present bit가 없으면 fault로 간다. 접근이 성립하면 accessed bit를 세우고, store 접근이면 dirty bit도 세우는 흐름이 이어진다.

최종 guest physical address는 page table entry의 주소 부분과 VA offset을 합쳐 만든다.

이 주소는 host physical address가 아니다. Guest Physical Memory에서 다룬 것처럼 QEMU가 host process 안에서 backing하는 guest physical address다.

다음 중 하나라도 present가 아니면 CPU는 최종 PA를 만들 수 없다.

PintOS는 pf를 받은 뒤 SPT를 보고 이 주소가 lazy load, stack growth, swapped-out page인지 판단한다.

정리

  • PintOS에서 보는 x86-64 4KB page 기준 VA는 9비트 index 네 개와 12비트 offset으로 나뉜다.
  • 각 page table은 512개의 8바이트 entry를 담는 4KB 배열이다.
  • 512개를 넘으면 linked list의 next로 이어지는 것이 아니라, 상위 단계의 다른 entry가 다른 하위 table page를 가리킨다.
  • 4단계 구조 전체는 512 * 512 * 512 * 512 * 4KB = 256TiB의 가상주소 번호를 표현할 수 있다.
  • PintOS의 PML4/PDPE/PDX/PTX 매크로는 이 index를 직접 계산한다.
  • PintOS도 x86-64용 4단계 page table을 쓴다.
  • page table 자체를 담는 4KB page는 pml4e_walk(..., create=true) 흐름에서 palloc_get_page(PAL_ZERO)로 만들어질 수 있다.
  • 유저 데이터 frame은 VM의 vm_get_frame()에서 palloc_get_page(PAL_USER)로 가져오는 별도 자원이다.
  • pml4e_walk()는 중간 table을 따라 최종 PTE의 주소를 찾는다.
  • pml4_set_page()는 최종 PTE에 frame 주소와 permission bit를 기록한다.
  • QEMU는 PintOS 정책을 모르고, guest CPU의 page-table walk와 pf 효과를 재현한다.
  • 실제 OS와 최신 하드웨어에는 huge page, 5단계 page table 같은 확장이 있을 수 있으므로 이 문서의 계산은 PintOS 학습용 4단계 기본형에 해당한다.
