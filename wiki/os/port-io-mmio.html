Port I/O와 MMIO

Port I/O와 MMIO

확인 범위: 이 문서는 Port I/O와 MMIO의 일반 원리와 선택 기준을 설명하고 PintOS·Linux·Windows·QEMU의 구현 예를 비교한다. 다만 제시된 코드 경로와 동작은 특정 버전의 소스 및 실행 기록으로 검증한 결과가 아니다. 구현 세부, 장치별 주소와 호출 경로, 상대 성능에 관한 판단은 대상 버전의 실제 코드·실행 추적·성능 측정으로 별도 확인해야 한다.

CPU는 장치에 어떻게 접근하는가

CPU가 장치(device)의 상태를 읽거나 명령을 전달하려면 장치 레지스터에 접근해야 한다. 이 레지스터를 CPU의 주소 체계에 배치하는 방식에 따라 Port-mapped I/O(PMIO)와 Memory-mapped I/O(MMIO)로 나뉜다.

PMIO는 메모리와 분리된 I/O 주소 공간을 사용하며 in/out 명령어로 접근한다. MMIO는 장치 레지스터를 물리 메모리 주소에 매핑하고 일반 load/store 명령으로 접근한다. x86 아키텍처는 두 방식을 모두 지원한다. PintOS에서는 레거시 장치를 제어할 때 PMIO를 주로 사용한다.

%% CPU가 장치와 통신하는 두 경로
flowchart TD
  cpu["CPU<br/>in/out mov"]
  io_bus["I/O Bus<br/>(PMIO)"]
  memory_bus["Memory Bus<br/>(MMIO)"]
  pmio_devices["PIC PIT IDE<br/>0x20 0x40 0x1F0"]
  mmio_devices["VGA FB PCIe<br/>0xB8000 BAR"]
  cpu -->|in/out| io_bus
  cpu -->|mov| memory_bus
  io_bus --> pmio_devices
  memory_bus --> mmio_devices

Port-mapped I/O

x86 CPU에는 메모리 주소 공간과 별도로 64K 포트의 I/O 주소 공간(0x0000 ~ 0xFFFF)이 있다. CPU는 다음 전용 명령어로 이 공간에 접근한다.

명령어방향크기
in al, dxport → CPU8비트
in ax, dxport → CPU16비트
in eax, dxport → CPU32비트
out dx, alCPU → port8비트
out dx, axCPU → port16비트
out dx, eaxCPU → port32비트
insb/insw/inslport → memorybulk
outsb/outsw/outslmemory → portbulk

in/out은 특권 명령어다. EFLAGS.IOPL 필드(비트 12-13)가 현재 CPL 이상이어야 실행할 수 있다. 커널(CPL=0)은 항상 실행할 수 있다. 유저(CPL=3)는 IOPL=3이거나 TSS의 I/O Permission Bitmap에서 허용된 포트에만 접근할 수 있다.

Memory-mapped I/O

MMIO는 장치 레지스터를 물리 메모리 주소에 매핑한다. CPU는 일반 mov 명령과 같은 방식으로 해당 주소에 접근하지만, 메모리 컨트롤러는 요청을 RAM이 아니라 장치로 전달한다.

이 차이 때문에 MMIO 영역에는 메모리와 다른 접근 규칙이 필요하다.

  • MMIO 영역은 UC(Uncacheable) 또는 WC(Write-Combining)로 설정해야 한다. 캐시가 개입하면 장치가 최신 값을 받지 못할 수 있다.
  • 컴파일러가 메모리 접근을 제거하거나 합치지 못하도록 volatile 포인터를 사용해야 한다.
  • byte, word, dword, qword 크기로 접근할 수 있지만 실제 허용 크기는 장치마다 다르다.

MMIO는 메모리 명령의 다양한 주소 지정 방식을 사용할 수 있고 64비트 주소 공간을 활용할 수 있다. DMA와도 자연스럽게 통합된다.

특성PMIOMMIO
주소 공간별도 I/O 공간 (64K)물리 메모리 공간
명령어in/out (전용)mov, load/store (범용)
주소 크기16비트 (0~0xFFFF)32/64비트
캐시 이슈없음 (별도 버스)UC/WC 설정 필요
현대 사용레거시 장치PCIe, GPU, NVMe 등

운영체제의 I/O 추상화

Linux의 PMIO

Linux는 inb()/outb() 등의 인라인 함수로 포트에 접근한다. 드라이버를 초기화할 때는 request_region()으로 사용할 포트 범위를 예약한다. 현대 Linux에서 PMIO는 8259A PIC, 8254 PIT, PS/2 키보드 같은 레거시 장치에 남아 있다.

%% Linux PMIO 드라이버 흐름
flowchart TD
  probe["driver_probe()"]
  request["request_region(0x1F0, 8, &quot;ide0&quot;)<br/>포트 범위 예약"]
  select["outb(0x1F6, 0xA0 &#124; (drive &lt;&lt; 4))<br/>IDE drive select"]
  status["inb(0x1F7)<br/>status 읽기"]
  release["release_region(0x1F0, 8)<br/>해제"]
  probe --> request
  request --> select
  select --> status
  status --> release

Linux의 MMIO

Linux는 ioremap()으로 물리 주소를 커널 가상 주소에 매핑한 뒤 readl()/writel() 같은 접근자(accessor) 함수로 장치 레지스터를 읽고 쓴다. NVMe, GPU, NIC 같은 현대 PCIe 장치는 MMIO를 사용한다.

%% Linux MMIO 드라이버 흐름
flowchart TD
  probe["driver_probe()"]
  resource["pci_resource_start(pdev, 0)<br/>BAR0 물리 주소 획득"]
  map["pci_iomap(pdev, 0, size)<br/>ioremap + 자원 관리"]
  read["readl(base + REG_STATUS)<br/>MMIO 읽기 (volatile)"]
  write["writel(val, base + REG_COMMAND)<br/>MMIO 쓰기"]
  unmap["pci_iounmap(pdev, base)<br/>해제"]
  probe --> resource
  resource --> map
  map --> read
  read --> write
  write --> unmap

최신 드라이버는 devm_ioremap() / devm_request_region() 같은 devres 프레임워크도 사용한다. devres는 device lifecycle과 자원 해제를 연결해 메모리 누수를 방지한다. PintOS에는 이에 해당하는 자원 관리 프레임워크가 없다.

항목PintOSLinux
PMIO APIinb()/outb() (io.h 인라인)inb()/outb() (asm/io.h 인라인)
MMIO API직접 포인터 역참조 (vga.c)readl()/writel() (barrier 포함)
자원 예약없음 (충돌 검사 없음)request_region() / request_mem_region()
자동 해제없음devres (devm_*)
Memory barrier없음readl()에 rmb 내장, writel()에 wmb 내장
캐시 제어없음 (단일 MMIO 장치)ioremap_nocache() / ioremap_wc()

Windows는 READ_PORT_UCHAR()/WRITE_PORT_UCHAR()로 PMIO를, READ_REGISTER_ULONG()/WRITE_REGISTER_ULONG()로 MMIO를 추상화한다.

PintOS에서 두 방식 찾기

PintOS는 장치 제어에 PMIO를 주로 사용한다. include/threads/io.h에는 포트에 접근하는 인라인 함수가 다음과 같이 정의되어 있다.

16비트와 32비트 버전인 inw, outw, inl, outl도 제공한다. 여러 값을 옮기는 bulk 버전에는 insb, outsb 등이 있다.

장치포트용도파일
8259A PIC master0x20, 0x21ICW/OCW 초기화, EOI, 마스크threads/interrupt.c
8259A PIC slave0xA0, 0xA1ICW/OCW 초기화, 마스크threads/interrupt.c
8254 PIT0x40 (counter 0), 0x43 (control)타이머 주파수 설정devices/timer.c
IDE primary0x1F0-0x1F7, 0x3F6디스크 읽기/쓰기/상태devices/disk.c
IDE secondary0x170-0x177, 0x376두 번째 IDE 채널devices/disk.c
키보드 (PS/2)0x60스캔 코드 읽기devices/kbd.c
시리얼 (UART)0x3F8+ (COM1)디버그 출력, 입력devices/serial.c
VGA CRT0x3D4, 0x3D5커서 위치 설정devices/vga.c

PintOS에서 MMIO를 사용하는 사례는 VGA 텍스트 프레임버퍼다. 물리 주소 0xB8000을 커널 가상 주소 0x8004000000 + 0xB8000에 직접 매핑하고 포인터로 접근한다.

따라서 PintOS에서도 장치 설정과 상태 확인은 주로 PMIO로 처리하지만, 화면에 문자를 기록할 때는 MMIO를 사용한다.

QEMU는 접근을 어떻게 장치 모델로 전달하는가

QEMU는 PMIO와 MMIO를 모두 에뮬레이트하며 두 방식에 서로 다른 dispatch 경로를 사용한다. 여기서 설명하는 함수와 경로는 특정 버전에서 검증한 결과가 아니므로 실제 분석에서는 대상 QEMU 소스와 실행 추적을 함께 확인해야 한다.

PMIO dispatch

guest가 in/out 명령을 실행하면 TCG가 helper 함수를 호출한다.

%% QEMU PMIO dispatch 흐름
flowchart TD
  guest["guest: outb(0x43, 0x34)"]
  helper["TCG: helper_outb(env, port=0x43, val=0x34)"]
  address_space["address_space_write(&amp;address_space_io, port, ...)"]
  flatview["MemoryRegion 탐색 (flatview)"]
  pit_write["pit_ioport_write(opaque, addr=3, val=0x34, size=1)"]
  reset["PIT channel 0 재설정"]
  guest --> helper
  helper --> address_space
  address_space --> flatview
  flatview --> pit_write
  pit_write --> reset

QEMU는 PMIO를 위해 별도의 address_space_io를 관리한다. 각 장치 모델이 memory_region_init_io()로 포트 범위를 등록하면 I/O 명령은 해당 장치의 read/write 콜백으로 dispatch된다.

장치QEMU 소스등록 함수포트 범위
PIT (i8254)hw/timer/i8254.cpit_initfn()0x40-0x43 (4 ports)
PIC (i8259)hw/intc/i8259.cpic_initfn()0x20-0x21, 0xA0-0xA1
IDEhw/ide/piix.cpci_piix_ide_realize()0x1F0-0x1F7, 0x3F6
UART (16550)hw/char/serial.cserial_realize_core()0x3F8-0x3FF
PS/2 (KBD)hw/input/i8042.ci8042_realizefn()0x60, 0x64

MMIO dispatch

MMIO는 물리 주소를 기준으로 dispatch된다. guest가 해당 주소에 load/store하면 SoftMMU의 TLB에서 MMIO flag가 붙은 항목을 만나고 느린 경로(slow path)로 들어간다. 이후 io_readx()/io_writex()가 호출된다.

%% QEMU MMIO dispatch 흐름
flowchart TD
  guest["guest: mov [0xB8000], ax"]
  tlb["SoftMMU TLB lookup<br/>MMIO flag 발견"]
  write["io_writex()"]
  address_space["address_space_write(&amp;address_space_memory, 0xB8000, ...)"]
  region["MemoryRegion: vga-lowmem"]
  vga["vga_mem_write(opaque, addr, val, size)"]
  guest --> tlb
  tlb --> write
  write --> address_space
  address_space --> region
  region --> vga

MMIO 영역은 일반 RAM과 달리 SoftMMU TLB에 TLB_MMIO 플래그로 표시되어 매번 helper를 통과한다. 원문에서는 이 경로 때문에 MMIO 접근이 RAM 접근보다 수십 배 느리다고 설명하지만, 이 상대 성능은 대상 버전과 실행 환경에서 별도로 측정해야 한다.

특성PMIO 에뮬레이션MMIO 에뮬레이션
TCG 경로helper_outb/inb 직접 호출SoftMMU slow path
주소 공간address_space_ioaddress_space_memory
TLB 캐시해당 없음 (별도 helper)TLB_MMIO flag → 매번 slow path
상대 비용빠름 (helper 1단계)느림 (TLB miss + dispatch)

두 경로를 연속해서 보면 CPU 명령이 장치 모델의 동작과 반환값으로 이어지는 관계를 다음과 같이 나타낼 수 있다.

%% QEMU Port I/O 시퀀스
flowchart TD
  out_note["CPU: outb(0x43, 0x34)"]
  out_decode["QEMU TCG: out 명령 디코딩"]
  pit_write["Device Model: pit_ioport_write(port=0x43, val=0x34)"]
  in_note["CPU: inb(0x60)"]
  in_decode["QEMU TCG: in 명령 디코딩"]
  kbd_read["Device Model: kbd_read_data(port=0x60)"]
  pit_reset["pit_reset"]
  scancode["scancode"]
  al["al"]
  out_note --> out_decode
  out_decode --> pit_write
  pit_write --> pit_reset
  pit_reset --> in_note
  in_note --> in_decode
  in_decode --> kbd_read
  kbd_read --> scancode
  scancode --> al

GDB에서 I/O 경로 관찰하기

PintOS의 장치 I/O를 GDB로 관찰하려면 QEMU의 helper 함수에 breakpoint를 걸 수 있다. 다음 명령은 관찰 방법을 보여 주는 예이며, 실제 사용 가능 여부와 함수명은 대상 QEMU 빌드에서 확인해야 한다.

주소와 값으로 흐름 확인하기

PMIO와 MMIO의 차이는 실제 주소와 값의 흐름을 따라가면 더 분명해진다.

  • I/O 주소 공간 크기: 65536 포트 (0x0000 ~ 0xFFFF)
  • in/out 명령 단위: 1바이트(8비트), 2바이트(16비트), 4바이트(32비트)
  • PIT control word 예: outb(0x43, 0x34) → counter 0, LSB then MSB, mode 2(rate generator)
  • PIT 주파수: outb(0x40, count & 0xFF) + outb(0x40, count >> 8) — count = 1193180 / Hz
    • PintOS 기본 100 Hz: count = 1193180 / 100 = 11932 (0x2E9C)
  • PIC IRQ 리매핑: master ICW2 = 0x20 (벡터 32), slave ICW2 = 0x28 (벡터 40)
  • VGA framebuffer: 물리 0xB8000, 크기 = 80 columns x 25 rows x 2 bytes = 4000 bytes

PIT에서는 outb()가 제어 포트와 counter 포트로 값을 보낸다. PIC에서는 초기화 값이 IRQ의 벡터 범위를 정한다. VGA에서는 포트가 아니라 물리 주소 0xB8000에 매핑된 프레임버퍼를 수정한다. 같은 PintOS 안에서도 장치가 제공하는 인터페이스에 따라 PMIO와 MMIO의 접근 경로가 달라지는 셈이다.
