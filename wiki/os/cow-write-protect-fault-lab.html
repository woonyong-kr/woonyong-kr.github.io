COW write-protect fault는 언제 page copy로 살아나나

확인 범위: 이 문서는 COW write-protect fault를 page copy 또는 writable remap으로 처리하는 일반 원리와 판단 기준을 설명하고, 제시된 로컬 PintOS 구현의 함수·metadata·테스트 흐름을 구체적 사례로 다룬다. 코드 경로와 bit·주소 계산은 본문에 제시된 구현을 기준으로 하며, 실제 동작 여부와 실행 결과·성능은 해당 저장소 버전에서 테스트와 GDB로 별도 검증해야 한다.

COW write fault 시작

fork()는 부모 프로세스의 주소 공간을 자식에게 물려준다.

그러면 처음 배우는 사람은 보통 이렇게 묻는다.

부모가 가진 모든 4KB page를 자식에게 바로 복사해야 할까?

실제 OS는 보통 그렇게 하지 않는다. 대부분의 page는 fork 직후에 읽기만 하고, 실제로 쓰는 page는 일부일 수 있기 때문이다.

copy-on-write, 줄여서 COW는 이 낭비를 줄이는 방법이다. 이름 그대로 처음에는 복사하지 않고 공유하다가, 누군가 write하려는 순간에만 복사한다.

PintOS VM 테스트에는 이 생각을 직접 묻는 파일이 있다.

이 Lab의 질문은 이것이다.

child가 large[0] = '@'를 실행할 때, 왜 page fault가 실패가 아니라 “이제 복사할 시간”이라는 신호가 될 수 있을까?

COW write fault 문제

fork() 때 모든 page를 즉시 복사하면 이해하기는 쉽다.

하지만 많은 프로그램은 fork() 직후 곧바로 exec()을 하거나, 부모와 자식이 대부분의 page를 읽기만 한다.

이때 즉시 복사는 낭비가 된다.

COW는 이 문제를 page table permission으로 푼다.

이 말은 즉, COW에서 page fault는 단순한 사고가 아니다. 커널이 일부러 걸어 둔 read-only 장치가 첫 write를 알려 주는 신호다.

꼬리 질문

이 Lab은 다음 질문을 순서대로 따라간다.

  1. 왜 fork() 때 모든 page를 복사하지 않아도 될까?
  2. COW page는 왜 page table에서 잠깐 read-only처럼 보여야 할까?
  3. write-protect fault와 진짜 read-only page write는 어떻게 구분할까?
  4. PintOS의 vm_handle_wp()는 어떤 역할을 해야 할까?
  5. cow-simple은 같은 frame 공유와 write 뒤 분리를 어떻게 확인할까?
  6. QEMU는 COW를 알고 frame을 복사해 줄까?
  7. 숫자 0x12345005, error code 0x7을 넣으면 어떤 상황이 계산될까?
  8. GDB에서는 f->error_code, PTE, frame identity 중 무엇을 보면 될까?

COW write fault 흐름

COW는 “공유 read-only page”와 “진짜 read-only page”를 구분해야 한다.

상태PTE 관점커널 metadata 관점write가 오면

read-only mmap pagePTE_W=0 또는 lazy not-presentmapping writable 아님죽여야 함
COW shared pagePTE_W=0원래 writable, 지금은 공유 중복사 후 살릴 수 있음

핵심은 PTE_W=0만 보고 판단하면 안 된다는 점이다.

이 질문에 답하려면 page table 밖의 정보가 필요하다.

PintOS에서는 보통 SPT의 struct page, frame table, 또는 별도 COW metadata에 다음 의미를 저장한다.

실제 운영체제

Linux의 fork()는 COW를 적극적으로 사용한다.

부모와 자식의 page table entry가 같은 물리 page를 가리키게 하되, private writable page는 잠시 read-only처럼 만든다. 둘 중 하나가 write하면 CPU가 protection fault를 내고, Linux 커널은 VMA와 page metadata를 보고 COW 후보인지 판단한다. 맞으면 새 page를 할당하고 내용을 복사한 뒤 write를 허용한다.

Windows는 Unix식 fork()를 일반 프로세스 생성 API로 제공하지 않는다. 보통은 CreateProcess가 새 process와 address space를 만든다. 그래도 Windows에도 image section, mapped section, private page에서 copy-on-write 개념은 존재한다.

현실 OS는 PintOS보다 훨씬 복잡하다.

  • 같은 physical page를 여러 process가 참조할 수 있다.
  • page cache, shared mapping, private mapping, file mapping을 함께 다룬다.
  • 멀티코어에서 동시에 write fault가 들어올 수 있다.
  • page reference count, reverse mapping, TLB shootdown, locking이 필요하다.

PintOS에서는 이 큰 문제를 fork(), PTE writable bit, SPT metadata, vm_handle_wp()로 줄여서 학습한다.

PintOS

현재 로컬 PintOS 저장소에는 COW가 구현되어 있다. 읽을 지점은 네 군데다.

첫째, 테스트가 COW의 기대 동작을 고정한다.

  • PintOS 저장소 상대 경로 pintos/tests/vm/cow/cow-simple.c
  • PintOS 저장소 상대 경로 pintos/tests/vm/cow/cow-simple.ck
  • PintOS 저장소 상대 경로 pintos/tests/vm/cow/Rubric

cow-simple.ck는 fork 직후 두 frame identity가 같고, child write 뒤 달라져야 한다고 기대한다.

둘째, anon_copy()가 fork 시 resident anonymous page를 COW 공유로 바꾼다.

  • PintOS 저장소 상대 경로 pintos/vm/anon.c
    • anon_copy()

핵심은 같은 frame->kva를 부모와 자식에게 rw=false로 매핑하고, vm_frame_add_owner()로 공유 frame의 owner/ref_count를 늘리는 흐름이다.

셋째, page fault 경로가 present write fault를 COW 후보로 넘긴다.

  • PintOS 저장소 상대 경로 pintos/userprog/exception.c
    • PF_P/PF_W/PF_U를 not_present/write/user로 분해한다.
  • PintOS 저장소 상대 경로 pintos/vm/vm.c
    • vm_try_handle_fault()
    • vm_handle_write_protect_fault()
    • vm_handle_wp()

vm_handle_wp()는 SPT metadata의 page->writable을 보고 COW로 살릴 수 있는 page와 진짜 read-only page를 구분한다.

넷째, vm_handle_cow()가 공유 수에 따라 copy와 remap을 나눈다.

ref_count > 1이면 쓰기를 시도한 process만 새 frame을 받는다. ref_count == 1이면 더 이상 공유자가 없으므로 복사하지 않고 PTE writable만 복원한다.

마지막으로, PTE writable bit는 pml4_set_page()의 rw 인자로 조절된다.

  • PintOS 저장소 상대 경로 pintos/threads/mmu.c
    • pml4_set_page(pml4, upage, kpage, rw)
  • PintOS 저장소 상대 경로 pintos/include/threads/pte.h
    • PTE_P
    • PTE_W
    • PTE_U

pml4_set_page()는 rw가 true일 때만 PTE_W를 세운다.

현재 구현의 큰 흐름은 다음과 같다.

반대로 page->writable이 false이면 vm_handle_wp()는 false를 반환해야 한다. 그래야 pt-write-code나 read-only mmap write를 잘못 살리지 않는다.

이 구분이 흐려지면 0x7 COW fault와 pt-write-code, read-only mmap write를 같은 실패로 처리하거나, 반대로 모두 살려 버리는 오류가 생긴다.

QEMU

QEMU는 COW를 모른다.

QEMU가 하는 일은 x86 CPU처럼 page table permission을 검사하는 것이다.

  • target/i386/cpu.h
    • PG_RW_MASK
    • PG_ERROR_P_MASK
    • PG_ERROR_W_MASK
    • PG_ERROR_U_MASK
  • target/i386/tcg/system/excp_helper.c
    • PTE permission으로 PAGE_WRITE 가능 여부를 계산한다.
    • write가 허용되지 않으면 protection fault error code를 만든다.

QEMU의 page walk 흐름은 단순화하면 이렇다.

그 다음은 PintOS의 일이다.

QEMU는 “이 read-only page가 COW 후보인지, 진짜 read-only code인지”를 판단하지 않는다. QEMU는 write permission fault를 만들어 줄 뿐이고, 의미 해석은 guest OS인 PintOS가 한다.

COW write fault 값 추적

PTE bit 계산

PintOS의 pte.h 기준 주요 bit는 다음이다.

frame base가 0x12345000이라고 하자.

일반 writable user page는 다음처럼 보인다.

COW fork 직후에는 같은 frame을 보되 writable bit를 끈다.

child가 write하면 CPU 관점의 error code는 이렇게 읽힌다.

이 값은 demand paging의 not-present fault가 아니다. 이미 page는 있었다. 다만 write permission이 막혀 있었다.

COW 복사 뒤 계산

vm_handle_wp()가 child에게 새 frame 0x23456000을 할당했다고 하자.

그 뒤 같은 명령어 large[0] = '@'가 재실행된다.

그래서 child의 memcmp(buf, large, strlen(buf))는 달라지고, parent의 memcmp는 그대로 유지된다.

정리

  • COW는 fork() 비용을 줄이기 위해 page를 즉시 복사하지 않고 공유한다.
  • 공유 중인 writable page는 page table에서 임시 read-only처럼 보여야 첫 write를 fault로 잡을 수 있다.
  • COW write fault는 보통 PF_P=1, PF_W=1, PF_U=1인 protection fault다.
  • 같은 protection fault라도 code page나 read-only mmap write는 죽어야 하고, COW page만 vm_handle_wp()로 살아야 한다.
  • 현재 로컬 PintOS 구현은 page->writable로 COW 후보를 가르고, frame->ref_count로 새 frame 복사와 writable remap을 나눈다.
  • QEMU는 COW를 모른다. QEMU는 PTE permission을 보고 pf를 만들어 주고, 그 의미를 해석하는 것은 PintOS다.

COW write fault 관련 개념

  • SPT fork copy
    • fork()가 SPT page 의미를 자식에게 물려주는 흐름.
  • vm try handle fault() decision
    • PF_P/PF_W/PF_U가 fault 처리 분기로 바뀌는 지점.
  • Page Fault Error Code
    • 0x7 error code를 present write user fault로 읽는 법.
  • PTE bit
    • PTE_W가 write permission과 fault를 어떻게 만드는지.
  • TLB와 CR3
    • 부모와 자식의 address space 기준이 CR3로 분리되는 이유.
  • mmap read only Lab
    • COW와 달리 read-only file-backed mapping의 write를 죽여야 하는 기준.
