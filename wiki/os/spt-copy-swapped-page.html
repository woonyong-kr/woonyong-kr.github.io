Swapped Page 복사 (fork SPT copy)

Swapped Page 복사 (fork SPT copy)

한 줄 요약: fork 시 swap에 나가 있는 page는 slot을 즉시 복사하지 않고 자식에 같은 swap_idx를 복사한 뒤 참조 수를 올려, swap in이나 재eviction 때 참조 카운트로 기존 snapshot을 보호한다.

Swapped Page 복사 구조

fork() 시점에 부모의 SPT에는 resident page, UNINIT page와 더불어 swapped-out page가 섞여 있을 수 있다. 이 page는 RAM에 frame이 없고 swap disk의 특정 slot에 4096바이트가 저장되어 있다. 현재 PintOS 구현은 이 slot을 즉시 복사하지 않고, 자식 page에 같은 swap_idx를 복사한 뒤 swap_slot_ref()로 참조 수를 올린다. 이후 어느 쪽이 swap in하면 swap_slot_unref()로 참조를 줄이고, 다시 eviction될 때는 새 slot을 받아 나가므로 기존 slot의 snapshot을 덮어쓰지 않는다.

상세 설명

추상 개념 (fork와 swapped page의 문제)

fork 시점의 부모 주소 공간 상태 세 가지:

page 상태frame 존재?데이터 위치복사 전략
Resident (VM_ANON/VM_FILE)있음RAM frameframe 내용 memcpy
UNINIT (lazy)없음아직 없음aux 메타데이터 deep copy
Swapped-out없음swap disk slotswap_idx 복사 + slot ref count 증가

swapped page가 까다로운 이유는 데이터가 RAM에 없다는 점이다. resident page는 frame→kva로 memcpy하면 되지만, 현재 구현의 swapped page는 fork 시점에 바이트를 읽지 않고 swap_idx metadata와 slot ref count만 복사한다.

실제 OS (Linux)

Linux에서 fork는 COW(Copy-on-Write)를 사용하므로 swapped page도 즉시 복사하지 않는다. 부모의 swap entry를 자식의 page table entry에 복제하고 참조 카운트를 증가시킨다. 실제 복사는 어느 한쪽이 write를 시도할 때 COW fault에서 수행된다.

fork 시점:
  부모 PTE: swap entry (slot 5, refcount 1)
  → 자식 PTE: 같은 swap entry (slot 5, refcount 2)

한쪽 write 시:
  1. swap in → 임시 frame에 읽기
  2. 새 frame 할당 + 데이터 복사
  3. 원본 swap entry refcount 감소
  4. 새 page에 대한 독립 매핑 설치

PintOS 구현

현재 로컬 PintOS 구현의 swapped page 복사 전략은 slot 공유 + ref count다.

현재 전략: metadata copy + swap_slot_ref()

1. 부모 SPT 순회 중 swapped-out anon page 발견
2. 자식 SPT에 같은 VA의 VM_ANON page 생성
3. dst_page->anon = src_page->anon 으로 swap_idx/swapped 복사
4. swap_slot_ref(src_page->anon.swap_idx) 로 ref count 증가
5. 자식도 not-present swapped page 상태로 남음

이 전략은 fork 시점에 disk read/write가 없다. swap slot은 “변경 가능한 공유 버퍼”가 아니라 “여러 page metadata가 참조하는 snapshot”처럼 취급된다.

대안 전략: swap-in → memcpy → 자식 page 생성

1. 부모 slot에서 4096B를 임시 frame으로 읽기
2. 자식용 frame 또는 새 swap slot에 복사
3. 부모와 자식이 서로 다른 backing을 갖게 만들기

이 대안은 이해하기 쉽지만 fork 시점의 I/O가 커진다. 현재 코드는 Linux의 swap_map처럼 ref count를 두는 쪽을 택했다.

핵심 불변식: 같은 swap slot을 공유해도 된다. 단, slot은 ref count로 보호되어야 하고, swap in 후 다시 eviction되는 page는 기존 slot에 덮어쓰지 않고 새 slot을 받아야 한다.

QEMU 에뮬레이션

QEMU는 fork도 swap slot도 모른다. PintOS가 swap disk에 sector read/write를 보내면 QEMU IDE 모델이 호스트 파일(swap.dsk)의 해당 오프셋에서 I/O를 수행할 뿐이다. 현재 구현에서는 swapped page fork 자체가 disk I/O를 만들지 않고, 나중에 page fault로 swap in할 때 같은 slot의 섹터를 읽는 요청만 QEMU에 보인다.

Swapped Page 복사 값 추적

fork 시 swapped page 복사 비용 (현재 전략):

disk I/O: 0
metadata copy: dst_page->anon = src_page->anon
ref count: swap_slot_ref(src_page->anon.swap_idx)

나중에 한쪽이 page fault로 swap in할 때:

8 × disk_read = 4096B 복원
swap_slot_unref(slot)
ref_count가 0이면 bitmap slot 해제, 0이 아니면 다른 process를 위해 유지

예시 시나리오:

부모가 20개 page 중 5개가 swapped-out인 상태에서 fork하면:

Resident pages:  15 × memcpy = 15 × 4096B = 60 KB 메모리 복사
Swapped pages:   5 × swap_idx metadata copy + 5 × swap_slot_ref()
Fork 시 disk I/O: 0
Swap slot 소비:  부모 5 slots 그대로 공유
                 ref_count만 1에서 2로 증가

    B -->|"resident"| C[frame memcpy]
    B -->|"UNINIT"| D[aux deep copy]
    B -->|"swapped-out anon"| E[자식 VM_ANON page 생성]

  VA 0x8048000 → page A (resident, frame F1)
  VA 0x8049000 → page B (swapped, slot 3)
  VA 0x804A000 → page C (UNINIT)

Swap disk:
  slot 3 (sector 24..31): page B의 4096B

═══ fork 후 (부모 + 자식) ═══

부모 SPT:                         자식 SPT:
  VA 0x8048000 → page A (F1)        VA 0x8048000 → page A' (F2)
  VA 0x8049000 → page B (slot 3)    VA 0x8049000 → page B' (slot 3)
  VA 0x804A000 → page C (UNINIT)    VA 0x804A000 → page C' (UNINIT)

Swap disk:
  slot 3 (sector 24..31): 부모 page B와 자식 page B'가 함께 참조
  swap_ref_count[3] = 2

Swapped Page 복사 점검

  • 현재 구현에서 swapped page fork는 자식용 slot을 새로 복사하지 않는다.
  • 자식은 부모의 swap_idx를 metadata로 복사하고, swap_slot_ref()로 같은 slot의 참조 수를 올린다.
  • 공유 slot은 read-only snapshot처럼 다룬다. swap in은 slot을 읽고 swap_slot_unref()만 하며, slot 내용을 덮어쓰지 않는다.
  • 나중에 page가 수정되고 다시 eviction되면 anon_swap_out()이 새 slot을 할당하므로 부모/자식의 snapshot이 섞이지 않는다.
  • 이 문서는 독립 slot 복사 전략이 아니라 현재 로컬 PintOS의 ref count 기반 전략을 기준으로 읽는다.
