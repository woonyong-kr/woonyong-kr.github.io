swap-fork Lab (fork/exec 뒤 child별 swap 상태가 섞이지 않는가)

한 줄 요약: tests/vm/swap-fork는 부모의 swapped-out page 상속이 아니라, fork()→즉시 exec("child-swap")로 주소 공간을 갈아끼운 10개 child가 각자 anonymous page와 swap slot metadata를 child별 struct page·slot bitmap 소유권으로 독립 유지하는지를 압박하는 테스트다.

swap-fork 쟁점

Swap Lab (anonymous page가 디스크 슬롯으로 나갔다 돌아오는 법)에서는 한 프로세스의 anonymous page가 swap slot으로 나갔다 돌아오는 흐름을 봤다.

그 다음 질문은 프로세스가 여러 개일 때다.

같은 child-swap 프로그램을 10개 띄우면, 각 child의 anonymous page와 swap slot metadata는 서로 섞이지 않을까?

이 Lab은 tests/vm/swap-fork를 그 질문으로 읽는다.

중요한 주의점이 있다. 이 테스트는 “부모의 이미 swapped-out 된 page를 자식이 그대로 상속해 읽는지”를 직접 검증하는 테스트는 아니다. swap-fork.c의 child는 fork() 직후 곧바로 exec("child-swap")한다. 그래서 핵심은 다음에 가깝다.

꼬리 질문

  • swap-anon을 통과해도 왜 swap-fork에서 깨질 수 있을까?
  • child가 바로 exec()하는데 fork()의 SPT copy와 cleanup은 왜 여전히 중요할까?
  • 10개 child가 같은 유저 VA를 써도 왜 같은 struct page를 공유하면 안 될까?
  • anonymous page의 swap slot 번호는 process별 metadata와 어떻게 연결되어야 할까?
  • child exit 때 swapped-out page의 slot은 누가 해제해야 할까?
  • QEMU는 이 child별 slot 소유권을 알고 있을까?
  • 숫자를 넣으면 10개 child의 1MB anonymous 영역은 몇 page를 만든다고 볼 수 있을까?
  • GDB로 어디를 보면 SPT와 anon slot이 child별로 분리됐는지 확인할 수 있을까?

swap-fork 혼동

VM을 구현할 때 처음에는 한 프로세스만 보는 테스트가 쉽다.

하지만 실제 OS와 PintOS 테스트는 여러 프로세스를 동시에 실행한다.

두 child가 같은 가상 주소를 쓰더라도 같은 메모리를 뜻하지 않는다. 각 process는 자기 PML4, 자기 SPT, 자기 struct page 목록을 가진다.

이 말은 즉, swap slot metadata도 “전역 slot 번호”와 “어느 process의 어느 page가 그 slot을 소유하는가”를 함께 맞춰야 한다. slot bitmap만 맞고 struct page 소유권이 꼬이면 다음 문제가 생긴다.

버그증상
page metadata 공유한 child cleanup이 다른 child page를 destroy할 수 있음
slot double free아직 다른 page가 쓰는 slot을 free로 표시해 덮어씀
slot leakchild exit 뒤 slot이 free되지 않아 swap 공간이 줄어듦
exec cleanup 누락fork로 잠깐 받은 옛 주소 공간이 새 exec 주소 공간과 섞임
SPT copy 실패child가 exec까지 가기 전에 잘못된 주소 공간 상태로 죽음

swap-fork는 이런 생명주기 문제를 한 번에 압박한다.

swap-fork 흐름

swap-fork는 세 개의 생명주기를 분리해서 보면 된다.

생명주기무엇이 생기나언제 사라져야 하나
fork 직후 child의 임시 주소 공간부모에서 복사된 register, PML4, SPT 의미child가 exec()에 성공해 새 프로그램으로 바뀔 때
exec 뒤 child-swap 주소 공간새 ELF, 새 stack, 새 anonymous page 의미child가 exit(0)할 때
swap slot 소유권resident가 아닌 anonymous page의 backing slotswap-in 성공 또는 page destroy 때

처음 배우는 단계에서는 이렇게 잡으면 된다.

중요한 규칙은 두 가지다.

  1. 같은 VA라도 process가 다르면 다른 page다.
  2. 같은 slot을 두 live page가 동시에 소유하면 안 된다.

swap-fork.c는 child를 10개 만든다

swap-fork.c는 child를 10개 만든다.

각 child는 child-swap.c에서 1MB짜리 정적 배열을 page 단위로 건드린다.

테스트의 기대 출력은 child 10개가 모두 시작하고 parent가 정상 종료하는 것이다.

child 내부의 데이터 불일치는 출력으로 길게 나오지 않고 fail("data is inconsistent")나 parent의 wait() 실패로 드러난다.

실제 운영체제

Linux에서는 fork() 뒤 exec()가 흔한 프로세스 생성 흐름이다. fork() 직후에는 부모 주소 공간의 VMA와 page table 의미가 논리적으로 상속되고, 보통 copy-on-write로 실제 page copy를 늦춘다. execve()가 성공하면 이전 주소 공간은 버려지고 새 실행 파일 기준 주소 공간이 만들어진다.

anonymous page가 메모리 압박으로 내려가면 Linux는 swap entry와 page metadata를 통해 어느 page가 어디에 저장됐는지 추적한다. 여러 process가 같은 VA를 써도 각 process의 address space 기준으로 해석한다.

Windows는 Unix식 fork()를 일반 프로세스 생성 API로 제공하지 않는다. 보통 CreateProcess가 새 process와 address space를 만든다. 그래도 mapped section, private page, pagefile, working set 같은 구조를 통해 “process별 주소 공간”과 “backing storage”를 분리해서 관리한다.

현실 OS는 PintOS보다 훨씬 복잡하다. SMP, page cache, COW refcount, shared mapping, pagefile allocation, process teardown race까지 함께 다룬다. PintOS에서는 이 복잡도를 줄여 SPT, page, frame, swap slot의 소유권을 직접 구현하게 한다.

QEMU

QEMU는 swap-fork라는 테스트 이름도, child별 SPT도 모른다.

QEMU가 보는 것은 다음 정도다.

예를 들어 PintOS가 anonymous page를 slot 7에 쓴다고 하자.

QEMU의 hw/ide/core.c에서는 ide_sector_write()가 sector 번호를 얻고 blk_aio_pwritev()에 sector_num << BDRV_SECTOR_BITS를 넘긴다.

이 말은 즉, QEMU는 “child A의 page”라는 의미를 모르고, 단지 guest가 요청한 sector write/read를 수행한다. child별 소유권은 PintOS VM layer가 지켜야 한다.

정리

swap-fork는 단순히 “swap이 된다”만 묻지 않는다.

child가 fork()로 생기고 곧바로 exec()하면서 주소 공간 생명주기가 한 번 갈아끼워진다. 그 뒤 10개 child가 각자 anonymous page를 만들고, 메모리 압박 상황에서 page와 slot metadata가 독립적으로 유지되어야 한다.

따라서 이 테스트를 볼 때는 세 가지를 분리한다.

  • fork()의 SPT copy는 child가 exec까지 안전하게 가는 임시 주소 공간을 만든다.
  • exec()는 그 임시 주소 공간을 버리고 child-swap의 새 주소 공간을 만든다.
  • anonymous swap metadata는 child별 struct page와 slot bitmap 사이의 소유권을 끝까지 지켜야 한다.

QEMU는 이 정책을 모른다. QEMU는 page fault와 disk sector I/O를 하드웨어처럼 전달할 뿐이고, child별 SPT/slot 소유권은 PintOS 구현의 책임이다.

swap-fork 관련 문서

  • SPT fork copy
    • VM 이후 fork()가 present PTE뿐 아니라 SPT 의미를 복제해야 하는 이유.
  • swapped anon fork 질문
    • 부모의 swapped-out page를 child가 exec 없이 직접 읽는 별도 질문.
  • anonymous page swap slot
    • anonymous page가 swap slot 번호를 어디에 기억해야 하는지.
  • Swap Lab
    • anonymous page 한 장이 sector 8개로 나갔다 돌아오는 기본 실험.
  • Swap Disk QEMU Trace
    • PintOS slot/sector가 QEMU block backend offset으로 내려가는 흐름.
  • Frame Eviction Trace
    • 어떤 frame을 victim으로 골라 swap out하는지.
