스택 성장 경계 Lab

확인 범위: 이 문서는 스택 page fault를 성장 후보와 잘못된 접근으로 구분하는 일반 원리와 PintOS 구현 시의 선택 기준을 설명하고, 제시된 테스트·코드·GDB 관찰 지점을 검증 방법으로 연결한다. 다만 현재 Project 3 VM 코드가 skeleton 상태이므로, 특정 구현·버전의 실행 결과나 성능을 검증한 문서로 보아서는 안 된다.

한 줄 요약: 스택 page fault가 발생하면 fault_addr, 유저 rsp, USER_STACK, page base를 기준으로 “스택 성장 후보”와 “잘못된 포인터 접근”을 구분한다. 이 기준을 PintOS의 네 테스트(pt-grow-stack 등)로 직접 확인한다.

스택 성장 경계

PintOS VM 테스트는 스택 성장을 허용할 조건과 거부할 조건을 구체적인 접근 사례로 나누어 검증한다.

이 Lab의 목표는 네 테스트를 외우는 데 있지 않다. fault_addr, 유저 rsp, USER_STACK, page base 계산을 차례로 살펴보며 “스택 성장 후보”와 “잘못된 포인터 접근”을 구분하는 감각을 익히는 것이 목표다.

스택 성장 경계가 필요한 이유

스택은 실행 중 자동으로 확장될 수 있다. 그러나 아무 주소나 스택으로 인정하면 잘못된 포인터 접근까지 유효한 메모리 접근으로 처리되어 메모리 보호가 깨진다.

예를 들어 다음 두 접근은 겉으로는 모두 page fault를 일으킬 수 있다.

첫 번째는 push 같은 정상적인 스택 사용일 수 있다. 반면 두 번째는 현재 스택 포인터보다 한 페이지 아래를 갑자기 읽는다. PintOS 테스트 pt-grow-bad는 두 번째 접근을 스택 성장으로 처리하지 않는지 확인한다.

따라서 stack growth 구현의 핵심은 page fault를 많이 복구하는 것이 아니라, 복구해도 되는 fault만 정확히 선별하는 데 있다.

실제 운영체제와의 관계

Linux와 Windows도 실행 중 스택 확장을 처리하지만, 실제 판단 기준은 PintOS보다 훨씬 복잡하다.

Linux는 process address space의 VMA, stack limit, guard page, signal 처리, thread별 stack을 함께 고려한다. Windows는 thread stack에 reserved 영역과 committed 영역을 두고, guard page에 접근하면 다음 page를 commit하는 방식으로 확장한다.

현실의 OS도 결국 다음과 같은 공통 질문에 답해야 한다.

차이는 현실의 OS가 보안, 호환성, thread stack, page cache, 동시성까지 함께 다룬다는 점이다. PintOS는 이러한 복잡도를 줄이고, vm_try_handle_fault()와 vm_stack_growth()에 핵심 판단 기준을 직접 구현하도록 구성되어 있다.

QEMU의 역할

QEMU는 어떤 주소가 스택에 속하는지 판단하지 않는다.

QEMU의 역할은 x86 CPU처럼 guest virtual address에 대해 page walk를 수행하고, 번역에 실패하면 guest인 PintOS에 page fault를 전달하는 것이다.

스택 성장 경계 값 추적

1. page base 계산

page fault는 특정 바이트에 접근할 때 발생하지만, page table mapping은 page 단위로 설치된다. 따라서 vm_stack_growth()는 0x4747eff8이라는 바이트 주소 자체가 아니라, 그 주소가 속한 0x4747e000 page를 준비해야 한다.

2. 1MB stack limit의 범위 익히기

PintOS KAIST Project 3의 stack growth 기준은 최대 1MB를 전제로 설명된다.

따라서 후보 주소는 대략 다음 범위 안에 있어야 한다.

그러나 이 범위에 포함되더라도 현재 rsp와 지나치게 멀리 떨어진 주소라면 거부해야 한다.

3. rsp - 8과 rsp - 4096 비교

현재 유저 스택 포인터가 다음 값이라고 가정하자.

이 fault는 현재 스택 사용과 가까우므로 스택 성장 후보가 될 수 있다.

정리

  • 스택 성장은 모든 not-present page fault를 무조건 복구하는 기능이 아니다.
  • 판단의 핵심 입력은 fault_addr, user rsp, USER_STACK, stack limit, page base다.
  • pt-grow-stack과 pt-big-stk-obj는 정상적인 스택 성장을 확인한다.
  • pt-grow-bad는 현재 rsp보다 지나치게 먼 접근을 거부하는지 확인한다.
  • pt-grow-stk-sc는 syscall 내부에서 유저 스택 버퍼를 처음 건드리는 경우까지 확인한다.
  • QEMU는 page fault 이벤트와 guest CR2/error code를 제공하지만, stack growth 정책은 PintOS가 결정한다.
