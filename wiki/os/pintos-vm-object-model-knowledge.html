PintOS VM 객체 모델 — struct page, frame, operations가 나누는 책임

PintOS VM 객체 모델 — struct page, frame, operations가 나누는 책임

확인 범위: 이 문서는 PintOS VM의 page·frame·operations 책임 분리와 다형성·생명주기를 설명하는 개념 및 코드 해설이며, 제시된 구조체·함수·주소 계산은 특정 구현을 이해하기 위한 예시다. 실제 필드와 동작의 일치 여부, 버전별 차이, 실행 경로와 성능에 관한 판단은 대상 소스 코드와 버전, 실행 기록 및 측정 결과를 별도로 확인해야 한다.

한 줄 요약: PintOS VM은 struct page(가상 페이지 메타데이터), struct frame(물리 프레임), struct page_operations(타입별 동작 함수 테이블) 세 구조체로 가상 메모리를 관리한다. C 언어에서 union과 함수 포인터 테이블로 OOP의 상속과 다형성을 구현한 설계다.

PintOS VM 객체 모델 구분

PintOS VM 시스템에는 세 종류의 페이지가 있다. 아직 물리 메모리에 올라오지 않은 UNINIT 페이지, 파일과 무관한 Anonymous 페이지, 파일 내용을 담는 File-backed 페이지다. 이 세 종류는 swap in/out, 소멸, 복사 동작이 전부 다르다.

이 차이를 if-else로 처리하면 코드 곳곳에 타입 분기가 퍼진다. PintOS는 대신 C에서 “인터페이스 패턴”을 사용한다. struct page_operations에 함수 포인터를 넣고, 호출 시점에 페이지 타입을 몰라도 swap_in(page, kva) 매크로 하나로 올바른 함수가 실행되게 만든다.

이 객체 모델을 모르면 vm_do_claim_page()가 swap_in(page, frame->kva)를 호출할 때 실제로 어떤 함수가 실행되는지 추적할 수 없다.

PintOS VM 객체 모델 흐름

세 구조체의 역할

%% PintOS VM 객체 모델 — 클래스 UML
flowchart LR
  Page["struct page<br/>va : void*<br/>operations : page_operations*<br/>frame : struct frame*<br/>writable : bool<br/>hash_elem (SPT)"]
  Frame["struct frame<br/>kva : void*<br/>page : struct page*<br/>owners : list (COW)<br/>ref_count : size_t"]
  Ops["interface page_operations<br/>swap_in()<br/>swap_out()<br/>destroy()<br/>copy()<br/>type"]
  Uninit["struct uninit_page<br/>init / type / aux<br/>page_initializer"]
  Anon["struct anon_page<br/>swap_idx / swapped"]
  File["struct file_page<br/>file / ofs<br/>page_read_bytes"]
  Page -->|frame 참조<br/>COW에서는 N:1 가능| Frame
  Page -->|operations| Ops
  Page -->|union variant| Uninit
  Page --> Anon
  Page --> File

클래스 UML — struct page가 operations와 struct frame을 참조한다. 일반 claim은 page와 frame이 1:1이지만 COW 공유 중에는 여러 page가 한 frame을 가리키며, frame->page는 primary owner이고 실제 소유 집합은 owners/ref_count가 관리한다. union은 uninit_page/anon_page/file_page 중 하나를 보존한다.

  • struct page — 가상 페이지 하나의 메타데이터. SPT(Supplemental Page Table)의 해시 테이블에 hash_elem으로 들어간다. va로 검색하고, operations로 동작을 위임하고, frame으로 물리 메모리를 찾는다.
  • struct frame — 물리 프레임 하나. kva에 커널 가상 주소를 담고, frame table(전역 리스트)에 연결된다. 페이지 교체 시 vm_get_victim()이 이 리스트를 순회한다.
  • struct page_operations — 타입별 동작을 묶은 함수 포인터 테이블. UNINIT, ANON, FILE 각각이 자기만의 page_operations 인스턴스를 가진다.

union으로 타입별 데이터 분리

struct page 안에 union이 있다. 한 페이지는 한 시점에 하나의 타입이므로, 같은 메모리 공간을 uninit_page, anon_page, file_page 중 하나로 해석한다.

  • struct uninit_page — 초기화 함수(init), 최종 타입(type), 초기화 인자(aux), 타입별 초기화 함수(page_initializer)를 보관한다. page fault가 발생하면 이 정보로 실제 타입으로 변신(transmute)한다.
  • struct anon_page — swap slot 인덱스(swap_idx)와 swap 여부(swapped)만 저장한다. 파일과 연결이 없으므로 swap disk가 유일한 backing store다.
  • struct file_page — 원본 파일 포인터(file), 오프셋(ofs), 읽을 바이트 수(page_read_bytes)를 저장한다. evict 시 dirty면 파일에 writeback한다.

다형성: 매크로로 감춘 함수 호출

호출하는 쪽은 page가 UNINIT인지, ANON인지, FILE인지 알 필요 없다. swap_in(page, kva)를 호출하면 page->operations에 연결된 함수가 실행된다. UNINIT이면 uninit_initialize()가 실행되어 실제 타입으로 변신하고, ANON이면 anon_swap_in()이 swap disk에서 읽어오고, FILE이면 file_backed_swap_in()이 파일에서 읽어온다.

페이지 생명주기

%% PintOS VM 페이지 생명주기 — 상태 전이 UML
flowchart LR
  start["start"]
  Uninit["UNINIT<br/>(SPT 등록만,<br/>물리 프레임 없음)"]
  Resident["ANON / FILE<br/>(물리 프레임 적재 완료)"]
  Swapped["swap / file<br/>(디스크에 저장)"]
  start -->|vm_alloc_page_with_initializer| Uninit
  Uninit -->|swap_in / uninit_initialize| Resident
  Resident -->|swap_out / evict| Swapped
  Swapped -->|swap_in / 재접근 page fault| Resident

상태 전이 UML — 모든 struct page는 vm_alloc_page_with_initializer()로 UNINIT 상태에서 시작한다. page fault 시 swap_in()(= uninit_initialize())으로 ANON/FILE로 적재되고, swap_out()/evict로 swap·file 디스크에 내려갔다가 재접근 시 다시 적재된다.

  1. vm_alloc_page_with_initializer()가 struct page를 malloc하고 uninit_new()로 UNINIT 상태로 초기화한다. SPT에 등록만 하고 물리 프레임은 할당하지 않는다.
  2. 해당 가상 주소에 접근하면 page fault가 발생한다. vm_do_claim_page()가 물리 프레임을 할당하고 swap_in(page, frame->kva)를 호출한다.
  3. UNINIT page의 swap_in은 uninit_initialize()다. 이 함수가 최종 타입의 초기화 함수(anon_initializer 또는 file_backed_initializer)를 호출하여 operations를 교체하고 union 데이터를 채운다.
  4. 메모리가 부족하면 vm_evict_frame()이 swap_out(page)을 호출한다. ANON이면 swap disk에 쓰고, FILE이면 dirty일 때 파일에 writeback한다.

실제 OS와의 차이 (Linux vs PintOS)

C로 다형성을 구현해 가상 메모리를 관리한다는 발상 자체는 실제 OS도 같다. 다른 점은 구조체를 어떻게 쪼개느냐다.

  • Linux 기준
    • 물리 프레임 메타데이터는 struct page(최근 커널은 struct folio)가 담당한다. PintOS의 struct frame에 가깝다.
    • 가상 주소 영역은 struct vm_area_struct(VMA)가 담당한다. 시작·끝 주소, 권한, backing 파일을 한 영역 단위로 보관한다.
    • 타입별 동작은 struct vm_operations_struct의 함수 포인터(fault, map_pages 등)로 위임한다. PintOS의 struct page_operations와 같은 인터페이스 패턴이다.
    • 정리하면 Linux는 “물리(page) / 가상 영역(VMA) / 동작(vm_ops)“으로 나눈다.
  • Windows 기준
    • VAD(Virtual Address Descriptor)가 합법적인 가상 주소 영역과 권한을 관리하고, PFN database가 물리 page 상태와 소유를 추적한다.
    • PintOS의 page 단위 SPT는 영역 정책과 물리 frame bookkeeping을 학습용 구조로 더 직접 드러낸다.
  • PintOS 기준
    • struct page가 가상 페이지 메타데이터를, struct frame이 물리 프레임을, struct page_operations가 동작을 맡는다.
    • 한 struct page가 가상 페이지 하나(4KB)에 대응한다. Linux의 VMA처럼 영역 단위가 아니라 페이지 단위다.
    • union으로 UNINIT, ANON, FILE을 한 구조체에 담아 학습용으로 단순화했다.

핵심 차이는 관리 단위다. Linux는 가상 주소 “영역”을 VMA로 묶지만, PintOS는 가상 “페이지” 하나하나를 struct page로 관리한다.

이 모델은 하드웨어가 보지 못한다

이 객체 모델은 순수한 커널 소프트웨어 자료구조다. QEMU나 CPU/MMU는 struct page, struct frame, page_operations를 전혀 보지 못한다. 하드웨어가 주소 변환에 쓰는 것은 pml4_set_page()가 채운 페이지 테이블(PML4)뿐이다. 즉 이 세 구조체는 PML4보다 위 계층, 커널 안에만 존재한다. SPT와 PML4를 둘 다 두는 이유가 여기서 갈린다.

PintOS VM 객체 모델 코드

struct page 정의

operations가 const 포인터인 것에 주목한다. 한번 설정되면 런타임에 함수 테이블 자체를 수정하지 않는다. 타입 전환은 포인터가 가리키는 대상을 바꾸는 것이다.

struct frame과 소유자 관리

ref_count와 owners 리스트는 Copy-on-Write를 위한 필드다. fork 시 부모와 자식이 같은 frame을 공유하면 ref_count가 증가하고, 쓰기 시 COW 핸들러가 ref_count > 1이면 새 프레임에 복사한다.

vm_alloc_page_with_initializer() — UNINIT page 등록

이 함수는 물리 프레임을 할당하지 않는다. uninit_new()가 page->operations를 UNINIT용 함수 테이블로 설정하고, 최종 타입 정보를 uninit.type, uninit.page_initializer에 저장해둔다. 실제 메모리 적재는 page fault가 발생할 때까지 미룬다(lazy loading).

vm_do_claim_page() — 물리 프레임 할당과 mapping

swap_in(page, frame->kva) 한 줄이 핵심이다. UNINIT 페이지면 uninit_initialize()가 실행되어 anon_initializer() 또는 file_backed_initializer()를 호출하고, operations 포인터를 최종 타입의 함수 테이블로 교체한다. 이미 ANON/FILE 페이지면 swap disk나 파일에서 내용을 읽어온다.

위 코드는 성공 경로만 축약한 예시다. 실제 구현은 PTE 설치나 swap_in()이 실패하면 PTE, frame↔page 연결, owner 등록과 새 frame 할당을 역순으로 되돌려야 한다.

vm_type 비트 마스크

vm_type은 하위 3비트가 기본 타입(UNINIT/ANON/FILE)이고, 상위 비트는 마커 플래그다. VM_ANON | VM_MARKER_0은 “Anonymous 타입이면서 스택 페이지”를 의미한다. VM_TYPE() 매크로로 기본 타입만 꺼낸다.

정리

PintOS VM 객체 모델은 세 구조체로 책임을 나눈다. struct page는 가상 주소와 메타데이터를, struct frame은 물리 메모리를, struct page_operations는 타입별 동작을 담당한다. union과 함수 포인터 테이블로 C에서 다형성을 구현하여, 호출 시점에 페이지 타입을 분기하지 않고도 올바른 swap_in/swap_out/destroy가 실행된다. 모든 페이지는 UNINIT으로 시작하여 page fault 시 최종 타입으로 전환되며, 이것이 lazy loading의 구조적 기반이다.
