vm_try_handle_fault 판단 흐름 Trace

한 줄 요약: vm_try_handle_fault()는 pf를 즉시 종료해야 할 오류와 frame을 준비한 뒤 같은 명령어를 다시 실행할 수 있는 합법적인 fault로 구분한다. SPT hit, stack growth(rsp 근접), write-protect 순으로 검사해 claim(frame과 PTE 설치)을 시도할지 프로세스를 종료할지 결정한다.

먼저 짚어 볼 질문

PintOS의 page_fault()는 왜 프로세스를 바로 종료하지 않고 vm_try_handle_fault()에게 처리 가능성을 먼저 물을까?

page fault에는 성격이 다른 두 상황이 포함된다.

  • 잘못된 포인터로 허용되지 않은 주소에 접근한 경우
  • 허용된 주소이지만 운영체제가 아직 page를 준비하지 않은 경우

vm_try_handle_fault()는 이 둘을 구분하는 관문이다.

이 fault는 프로세스를 종료해야 할 오류인가, 아니면 page를 준비한 뒤 같은 명령어를 다시 실행할 수 있는 상황인가?

판단 기준

가상 메모리(VM)는 모든 page를 처음부터 RAM에 올려둘 필요가 없다는 생각을 바탕으로 한다.

대표적으로 실행 파일의 code page, mmap file-backed page, 스택 확장 과정에서 생기는 page는 처음에는 page table에 present mapping이 없을 수 있다. 이런 page를 살릴 수 있는지는 주소만 보고 단정할 수 없다. SPT나 스택 성장 규칙처럼 해당 주소가 합법적인 가상 주소 공간에 속한다는 근거가 있어야 하며, 그 근거가 확인되면 fault 시점에 frame과 page table entry를 준비할 수 있다.

반대로 0xdeadbeef 같은 무관한 주소를 스택 성장으로 인정하거나 read-only page에 대한 write를 demand paging으로 처리하면 메모리 보호가 깨진다.

따라서 VM page fault handler는 다음 순서로 판단해야 한다.

판단 구조

vm_try_handle_fault()는 CPU가 남긴 하드웨어 정보를 PintOS의 VM 정책에 맞는 판단으로 바꾸는 함수다.

입력은 다섯 가지다.

입력의미
ffault 시점의 register snapshot. 특히 rip, rsp, syscall 처리 중 발생한 fault인지 판단할 때 필요하다.
addrCR2에서 읽은 faulting virtual address
useruser context에서 발생한 fault인지 나타내는 값
write쓰기 접근 중 발생한 fault인지 나타내는 값
not_presentpage 부재로 발생한 fault인지 권한 위반인지 구분하는 값

판단 결과는 크게 네 갈래다.

갈래확인할 질문대표 결과
SPT hitSPT에 이 page의 의미가 이미 기록되어 있는가?vm_do_claim_page(page)
stack growthSPT에는 없지만 정상적인 스택 확장 접근인가?vm_stack_growth(addr)
write protectionpresent page에 write하다가 막힌 것인가?COW vm_handle_wp(page) 또는 실패
invalid access어느 경로에도 해당하지 않는가?false 반환 후 kill(f)

즉, vm_try_handle_fault()는 page fault handler 안에서 적절한 VM 처리 경로를 선택하는 작은 스케줄러처럼 볼 수 있다.

        alt SPT hit (page 발견)
            SPT-->>VM: struct page *page
            VM->>VM: write 권한 확인
            VM->>FRAME: vm_get_frame()
            FRAME-->>VM: struct frame *frame
            VM->>VM: page <-> frame 연결
            VM->>SWAP: swap_in(page, frame->kva)
            SWAP-->>VM: 내용 로드 완료

            PF->>PF: kill(f)

        alt COW 후보

            VM->>VM: vm_handle_wp(page) -> frame 복사

            PF->>PF: kill(f)

    PF-->>CPU: iretq -> 같은 명령어 재실행

판단하며 답할 질문

  • page fault 주소만으로 판단하기 어려운 이유는 무엇인가?
  • PF_P/PF_W/PF_U는 VM 관점에서 어떤 질문으로 바뀌는가?
  • page table에는 없지만 SPT에는 있는 page를 살릴 수 있는 이유는 무엇인가?
  • SPT에도 없는 접근을 stack growth로 인정하는 기준은 무엇인가?
  • present page에 대한 write fault를 not-present fault와 다르게 처리하는 이유는 무엇인가?
  • frame이 없다면 fault 처리는 어느 경로로 이어지는가?
  • QEMU는 이 정책에서 무엇을 알고 무엇을 모르는가?
  • GDB에서는 addr, page, f->rip, f->rsp 가운데 무엇을 확인해야 하는가?

fault_addr = 0x8048123

1. Lazy executable page

이를 분해하면 다음과 같다.

SPT에서 0x8048000 page를 찾았고 해당 page가 uninit executable-backed page라면 처리할 근거가 있다.

2. Stack growth 후보

fault_addr가 현재 user rsp에 가깝고 USER_STACK 아래의 허용 범위에 있다면, SPT에 없더라도 새 anonymous page를 만들 수 있다.

3. 종료해야 하는 접근

SPT에도 없고 허용된 스택 범위에도 없다면 이 접근을 살릴 근거가 없다. 이때 vm_try_handle_fault()는 false를 반환하고 page_fault()는 kill(f)로 진행한다.

4. 권한 위반

이를 분해하면 다음과 같다.

PF_P가 1이므로 page는 present 상태였다. 즉, page가 없어서가 아니라 접근 권한이 맞지 않아 발생한 fault다. copy-on-write 같은 정책이 구현되어 있지 않다면 demand paging처럼 vm_do_claim_page()로 처리해서는 안 된다.

실제 운영체제와의 연결

Linux와 Windows도 page fault를 언제나 crash로 취급하지는 않는다.

Linux는 fault 주소가 속한 VMA, 접근 권한, anonymous page와 file mapping 여부, copy-on-write 후보 여부 등을 판단한다. 합법적인 접근이면 page를 준비해 같은 명령어를 다시 실행할 수 있게 하고, 불법 접근이면 일반적으로 SIGSEGV로 이어진다.

Windows 역시 process address space의 region과 protection, guard page, section/file mapping, committed/reserved 상태 등을 바탕으로 처리한다. 유효한 접근이면 필요한 page나 mapping을 준비하고, 그렇지 않으면 access violation으로 이어진다.

현실의 OS와 PintOS가 공통으로 묻는 질문은 다음과 같다.

이 주소 접근은 원래 허용된 주소 공간의 일부인가?

다만 현실의 OS는 copy-on-write, shared mapping, page cache, NUMA, thread stack, 보안 정책까지 함께 다루므로 PintOS보다 훨씬 복잡하다.

PintOS

PintOS에서 vm_try_handle_fault()로 진입하기 직전의 흐름은 다음 파일과 함수에서 확인할 수 있다.

  • SW_AI-W11-pintos/pintos/userprog/exception.c
    • page_fault()
  • SW_AI-W11-pintos/pintos/vm/vm.c
    • vm_try_handle_fault()
    • vm_stack_growth()
    • vm_do_claim_page()
  • SW_AI-W11-pintos/pintos/include/vm/vm.h
    • struct supplemental_page_table
    • struct page

전체 흐름은 다음과 같이 정리할 수 있다.

SPT에 page가 있다는 사실은 그 주소를 처리할 VM metadata가 있다는 뜻이지, 모든 접근 방식이 허용된다는 뜻은 아니다. read-only mmap page에 대한 첫 접근이 write라면 PTE가 아직 없어 not_present == true일 수 있다. 그래도 SPT metadata의 writable == false를 확인해 claim을 거부해야 한다.

QEMU

QEMU는 vm_try_handle_fault()에 담긴 PintOS의 VM 정책을 알지 못한다.

QEMU는 x86 CPU처럼 guest virtual address를 guest physical address로 변환하고, 변환에 실패하면 guest인 PintOS에 pf를 전달한다.

관련 코드는 다음과 같다.

  • target/i386/cpu.h
    • PG_ERROR_P_MASK
    • PG_ERROR_W_MASK
    • PG_ERROR_U_MASK
    • EXCP0E_PAGE
  • target/i386/tcg/system/excp_helper.c
    • page walk 실패 시 TranslateFault에 error_code과 cr2를 담는다.
    • x86_cpu_tlb_fill()에서 env->cr[2] = err.cr2
  • target/i386/emulate/x86_mmu.c
    • translate_res_to_error_code()
    • x86_write_mem_ex()
    • x86_read_mem_ex()

예를 들어 QEMU의 emulation helper는 변환 실패를 error code로 바꿀 때 다음 기준을 사용한다.

이 값은 guest pf의 error code가 되고, PintOS는 같은 의미를 PF_P/PF_W/PF_U로 읽는다.

그러나 SPT hit를 살릴지, 스택 근처의 접근에 anonymous page를 만들지, 권한 위반을 거부할지는 모두 PintOS가 결정한다.

판단 코드

1. page_fault()가 판단 재료를 만든다

파일: SW_AI-W11-pintos/pintos/userprog/exception.c

핵심 흐름은 다음과 같다.

fault_addr는 접근에 실패한 주소이고 f->rip는 그 접근을 실행하던 명령어 주소다. 둘을 구분해야 준비할 page와 실행을 재개할 위치가 뒤섞이지 않는다.

2. 함수 시그니처와 최상위 분기

파일: SW_AI-W11-pintos/pintos/vm/vm.c (line 224)

먼저 vm_fault_addr_invalid(addr)로 주소 자체를 검증한다. 이 검사를 통과하면 not_present 여부에 따라 두 경로로 나뉜다.

  • !not_present → vm_handle_write_protect_fault(addr, write)
  • not_present → vm_handle_not_present_fault(f, addr, user, write)

3. 주소 유효성 검사

파일: SW_AI-W11-pintos/pintos/vm/vm.c (line 233)

NULL 포인터나 유저 프로세스의 커널 주소 접근은 살릴 수 있는 page fault로 취급하지 않는다.

4. Not-present fault의 두 단계 판단

파일: SW_AI-W11-pintos/pintos/vm/vm.c (line 239)

먼저 vm_claim_spt_page(addr, write)를 호출해 SPT에서 page를 찾아 claim한다. 실패하면 vm_should_grow_stack(f, addr, user)로 stack growth 후보인지 판단하고, 조건을 만족하면 vm_grow_stack_and_claim(addr)로 새 anonymous page를 만든다.

5. SPT 조회와 접근 권한

파일: SW_AI-W11-pintos/pintos/vm/vm.c (line 248)

spt_find_page()로 page를 찾는다. 결과가 NULL이면 false를 반환한다. page가 존재하지만 write && !page->writable이면 vm_handle_unwritable_spt_page(page)로 보내고, 그 밖의 경우에는 vm_do_claim_page(page)로 frame을 할당해 PTE를 설치한다.

6. Stack growth의 세 가지 조건

파일: SW_AI-W11-pintos/pintos/vm/vm.c (line 269)

stack growth 후보가 되려면 세 조건을 모두 만족해야 한다.

  1. fault_addr < USER_STACK — 스택 최상단보다 아래에 있어야 한다.
  2. fault_addr >= USER_STACK - STACK_MAX — 최대 스택 한계인 1MB 안에 있어야 한다.
  3. fault_addr >= rsp - 32 — 현재 스택 포인터에 가까워야 한다.

rsp 결정 규칙도 중요하다. user mode fault에는 f->rsp를 사용하고, syscall 처리 중 발생한 kernel mode fault에는 thread_current()->user_rsp를 사용한다. user_rsp 필드는 threads/thread.h line 153에 있다.

7. 스택 page 생성과 claim

관련 파일은 SW_AI-W11-pintos/pintos/vm/uninit.c와 SW_AI-W11-pintos/pintos/userprog/process.c이다.

11. Syscall 처리 중 발생한 fault와 user rsp

관련 파일은 SW_AI-W11-pintos/pintos/userprog/syscall-entry.S와 SW_AI-W11-pintos/pintos/include/threads/thread.h이다.

syscall_entry.S는 syscall 진입 시 user rsp를 if->rsp에 저장한다.

user mode에서 직접 발생한 page fault라면 f->rsp가 user stack pointer다. 반면 커널이 syscall 처리 중 user buffer에 접근하다 fault를 내면 CPU는 이미 kernel stack을 사용하고 있다. 이 경우에도 stack growth를 지원하려면 syscall 진입 시점의 user rsp를 thread 상태에 저장해 판단 기준으로 사용해야 한다.

struct thread의 user_rsp 필드(line 153)가 이 역할을 한다. vm_should_grow_stack()에서 user가 false이면 f->rsp 대신 thread_current()->user_rsp를 사용한다.

1. Fault address를 SPT key로 바꾸기

이 값은 user mode에서 write를 시도했지만 page가 없었다는 뜻이다. 해당 page가 SPT에 있으면 claim 후보이며, SPT에 없더라도 rsp 근처라면 stack growth 후보가 될 수 있다.

4. 테스트로 분기 익히기

현재 저장소의 VM에는 TODO가 많으므로, 이 목록은 현재 모두 통과한다는 실행 결과가 아니라 구현 후 확인할 판단표로 읽어야 한다.

정리

  • vm_try_handle_fault()는 pf를 PintOS의 VM 정책에 따라 분기한다.
  • 첫 관문인 vm_fault_addr_invalid()는 NULL과 커널 주소를 걸러낸다.
  • not_present == true이면 vm_handle_not_present_fault()가 SPT hit에 대한 claim을 먼저 시도하고, SPT miss일 때 stack growth 여부를 판단한다.
  • vm_claim_spt_page()는 SPT에서 page를 찾지만, write && !page->writable이면 vm_handle_unwritable_spt_page()로 거부한다.
  • vm_should_grow_stack()는 주소 범위와 rsp 근접 조건을 검사하며, kernel mode fault에는 thread->user_rsp를 사용한다.
  • not_present == false인 write fault는 vm_handle_write_protect_fault()가 처리하고, COW가 구현되지 않았다면 실패한다.
  • claim하려면 frame과 PTE를 준비한 뒤 swap_in()으로 page 내용을 채워야 한다.
  • QEMU는 x86 pf와 CR2/error code를 재현하지만 SPT와 stack growth 정책은 PintOS가 결정한다.
