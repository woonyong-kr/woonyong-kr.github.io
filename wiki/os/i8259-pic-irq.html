i8259 PIC

장치가 인터럽트를 일으켜도 CPU가 그 신호를 곧바로 처리하는 것은 아니다. i8259 PIC가 장치의 IRQ 라인을 받아 인터럽트 벡터로 바꾸고 CPU에 전달한다. CPU는 이 벡터를 사용해 IDT에서 실행할 핸들러를 찾는다.

i8259 PIC 구조

8259A Programmable Interrupt Controller(PIC)는 외부 장치와 CPU 사이에서 하드웨어 인터럽트를 중개한다. PIT나 IDE가 IRQ 라인을 올리면 PIC는 CPU의 INTR 핀을 assert한다. CPU가 interrupt acknowledge cycle로 응답하면 PIC가 벡터를 제공하고, CPU는 그 벡터에 대응하는 IDT 핸들러를 선택한다.

x86 PC는 8259A PIC 두 개를 Master와 Slave로 연결해 사용한다.

PICI/O 포트IRQ 라인기본 벡터리맵 후 벡터
Master0x20 (command), 0x21 (data)IRQ 0~70~70x200x27 (3239)
Slave0xA0 (command), 0xA1 (data)IRQ 8~158~150x280x2F (4047)

Slave PIC는 Master의 IRQ 2 라인에 cascade 연결된다. 따라서 Slave에 연결된 장치의 인터럽트는 Slave → Master IRQ2 → CPU 순서로 전달된다.

기본 설정에서는 IRQ 015가 인터럽트 벡터 015에 매핑된다. 이 범위는 divide error와 page fault 같은 CPU exception의 벡터와 충돌한다. OS는 초기화 과정에서 PIC를 다시 프로그래밍해 IRQ 015를 벡터 0x200x2F로 옮긴다.

주요 IRQ와 리맵된 벡터는 다음과 같다.

IRQ장치리맵 벡터
0PIT (Timer)0x20 (32)
1Keyboard0x21 (33)
2Cascade (Slave 연결)0x22 (34)
4Serial COM10x24 (36)
14Primary IDE0x2E (46)
15Secondary IDE0x2F (47)

장치가 신호를 발생시킨 뒤 핸들러가 처리를 마치고 PIC에 완료를 알리기까지의 흐름은 다음과 같다.

%% i8259 PIC IRQ 전달 흐름
flowchart TD
  device["장치 신호 발생"]
  irq_line["PIC IRQ 라인 활성화"]
  if_check["CPU<br/>현재 명령 완료 후<br/>EFLAGS.IF 확인"]
  idt["CPU<br/>IDT[vector] 참조"]
  handler["핸들러 실행"]
  eoi["EOI<br/>End of Interrupt<br/>PIC에 완료 통지"]
  remap["remap"]
  intr["intr"]
  device --> irq_line
  irq_line --> remap
  remap --> intr
  intr -->|"IF=1이면 수락"| if_check
  if_check --> idt
  idt -->|"핸들러 주소로 점프"| handler
  handler --> eoi

핸들러는 처리를 마친 뒤 PIC에 EOI(End of Interrupt)를 보내야 한다. EOI를 보내지 않으면 PIC가 해당 IRQ를 계속 처리 중인 것으로 간주하므로 같은 우선순위 이하의 인터럽트가 계속 차단된다.

Linux와 PintOS의 사용 방식

Linux는 부팅 초기에 8259A PIC를 사용하다가 APIC(Advanced PIC)를 감지하면 Local APIC와 I/O APIC로 전환한다. APIC는 멀티코어 환경에서 인터럽트를 특정 CPU 코어로 라우팅할 수 있다. 반면 8259A는 단일 CPU에만 인터럽트를 전달한다.

PintOS는 단일 CPU 환경이므로 8259A PIC만 사용한다. pic_init()은 먼저 두 PIC의 인터럽트를 모두 마스킹하고, ICW(Initialization Command Word)를 차례로 기록해 Master와 Slave의 연결 관계와 벡터 범위를 설정한 뒤 마스크를 모두 해제한다.

초기화 — pic_init() (interrupt.c:356)

각 ICW가 정하는 내용은 다음과 같다.

  • ICW1: 초기화 시작과 트리거 모드(edge/level)
  • ICW2: 벡터 오프셋, 즉 리맵 주소
  • ICW3: Master-Slave 연결 관계
  • ICW4: 8086 mode와 같은 동작 모드

EOI 전송 — pic_end_of_interrupt() (interrupt.c:391)

Slave 인터럽트에 해당하는 벡터 0x28~0x2F를 처리한 뒤에는 Master와 Slave 모두에 EOI를 보내야 한다. 이 코드는 현재 로컬 PintOS가 사용하는 Master→Slave 순서를 보여 준다. 일반적인 8259A cascade 운용에서는 Slave를 먼저 acknowledge하고 Master의 cascade IRQ를 나중에 acknowledge하는 Slave→Master 순서를 권장한다. 그러므로 이 코드를 하드웨어 전반의 권장 순서로 일반화해서는 안 된다. 구현을 바꿀 때는 실제 보드나 QEMU의 동작과 interrupt test로 확인해야 한다.

핸들러 등록 — intr_register_ext() (interrupt.c:289)

외부 인터럽트 핸들러는 인터럽트가 비활성화된 INTR_OFF 상태에서 실행된다. PIT 타이머 핸들러는 intr_register_ext(0x20, timer_interrupt, "8254 Timer")로 등록한다.

인터럽트 수신 — intr_handler() (interrupt.c:414)

벡터 0x20~0x2F의 외부 인터럽트가 들어오면 intr_handler()은 다음 순서로 처리한다.

  1. in_external_intr = true 설정
  2. yield_on_return = false 초기화
  3. timer_interrupt와 같은 등록된 핸들러 호출
  4. pic_end_of_interrupt()를 호출해 EOI 전송
  5. yield_on_return이 true이면 thread_yield() 호출

QEMU에서의 에뮬레이션

QEMU는 hw/intc/i8259.c에서 8259A PIC를 소프트웨어로 에뮬레이션한다. Guest OS가 outb(0x20, ...) 같은 명령으로 I/O 포트에 값을 쓰면 QEMU가 이를 가로채 가상 PIC의 상태를 갱신한다. hw/timer/i8254.c의 PIT가 타이머 만료 시 가상 PIC의 IRQ 0 라인을 raise하면 QEMU는 vCPU에 인터럽트를 주입한다.

PIT 타이머 인터럽트만 따라가면 IRQ 0이 Master PIC에 들어간 뒤 CPU와 IDT를 거쳐 timer_interrupt()로 이어지고, 핸들러가 EOI를 보내면서 처리가 끝난다.

%% i8259 PIC timer interrupt 전달 순서
flowchart LR
  pit["i8254 PIT"]
  pic_m["Master PIC"]
  cpu["CPU"]
  idt["IDT[0x20]"]
  handler["timer_interrupt()"]
  eoi["EOI<br/>outb(0x20, 0x20)"]
  pit -->|"IRQ 0 라인 활성화"| pic_m
  pic_m -->|"INTR 핀 assert"| cpu
  cpu -->|"EFLAGS.IF == 1 확인"| cpu
  cpu -->|"INTA cycle에서 vector 0x20 수신"| idt
  idt -->|"핸들러 주소로 점프"| handler
  handler -->|"ticks++ thread_tick()"| handler
  handler --> eoi
  eoi -->|"인터럽트 완료"| pic_m
