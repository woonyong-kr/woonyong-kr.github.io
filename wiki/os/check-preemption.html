check_preemption() 선점 판단

check_preemption() 선점 판단

확인 범위: 이 문서는 우선순위 선점의 일반 원리와 판단 기준을 설명하고, 제시된 PintOS 구현 및 Linux·Windows·QEMU 비교를 통해 적용 맥락을 정리한다. 다만 함수 위치와 호출 경로, 버전별 동작, 실행 빈도와 성능 수치 및 GDB 관찰 결과는 특정 소스 코드·버전·실행 기록으로 별도 검증해야 하며, 여기서는 실제 측정 결과로 확정하지 않는다.

check_preemption()은 ready_list 맨 앞의 스레드가 현재 스레드보다 우선순위가 높을 때, 지금 CPU를 양보해야 하는지 판단한다.

왜 깨워 놓기만 하면 부족한가

우선순위 스케줄러에서 새 스레드를 READY로 만들기만 하고 현재 스레드를 계속 실행시키면, 더 높은 우선순위 스레드가 리스트 앞에서 기다리게 된다. 이 순간 스케줄러의 약속, 즉 “가장 높은 우선순위의 READY 스레드가 CPU를 잡는다”가 깨진다.

check_preemption()은 이 약속이 깨졌는지 확인하는 작은 문턱이다. ready_list 맨 앞 스레드의 우선순위가 현재 스레드보다 높으면 thread_yield()로 CPU를 양보한다. 높은 우선순위 스레드가 생성되거나, BLOCKED에서 깨어나거나, 현재 스레드의 effective priority가 낮아진 직후에 이 검사가 필요하다.

우선순위 선점이 필요한 순간

Priority Preemptive Scheduling에서 핵심 불변식은 “CPU에서 실행 중인 스레드는 항상 시스템에서 가장 높은 우선순위를 가진 READY 스레드여야 한다”이다. 이 불변식이 깨지는 순간은 세 가지다:

  1. 새로운 높은 우선순위 스레드가 생성될 때 (thread_create)
  2. BLOCKED 스레드가 깨어나 READY가 될 때 (thread_unblock → sema_up)
  3. 현재 스레드의 우선순위가 낮아질 때 (thread_set_priority)

각 순간마다 “현재 스레드 우선순위 < ready_list 최고 우선순위”를 검사하고, 참이면 thread_yield()로 스케줄러를 호출해야 한다.

하드웨어는 이 판단을 하지 않는다. 하드웨어가 하는 선점은 타이머 인터럽트에 의한 시간 기반(time-slice) 선점뿐이다. 우선순위 기반 선점은 순수하게 OS 소프트웨어의 책임이다.

실제 OS (Linux/Windows)

Linux CFS(Completely Fair Scheduler)는 priority preemption 대신 vruntime 기반 선점을 사용한다. 새 태스크가 깨어나는 경로의 generic 진입점은 check_preempt_curr()이며, 커널 version의 fair scheduling class 구현은 wakeup 전용 판단(전통적으로 check_preempt_wakeup()으로 불린 로직)에 위임할 수 있다. 선점 필요 시 resched_curr()가 TIF_NEED_RESCHED를 설정하고, 실제 context switch는 안전한 스케줄 지점에서 발생한다.

Windows는 dispatcher를 통해 우선순위 기반 선점을 수행한다. 높은 우선순위 스레드가 ready 상태가 되면 KiDispatchInterrupt()가 현재 스레드를 즉시 밀어낸다.

PintOS 구현

PintOS의 check_preemption()은 threads/thread.c에 구현되어 있다:

핵심 설계 판단:

  • intr_context() 가드: 인터럽트 핸들러 안에서는 thread_yield()를 호출하면 안 된다. 현재 구현은 thread_yield()의 ASSERT(!intr_context())에서 먼저 실패한다. 인터럽트 선점은 intr_yield_on_return()을 설정하고 반환 경계에서 처리한다.
  • ready_list는 우선순위 내림차순: list_begin()이 항상 최고 우선순위 스레드를 가리킨다.
  • < 비교 (같으면 양보 안 함): 같은 우선순위면 현재 스레드가 time slice를 다 쓸 때까지 계속 실행한다.

refresh_priority() — donation 반영 후

check_preemption()은 단독으로 호출되기도 하지만, priority donation 해제 후 refresh_priority() → check_preemption() 체인으로 호출되는 경로가 중요하다.

donation → check_preemption 시나리오:

Thread A (base=31, effective=40, donation 받은 상태, RUNNING)
  lock_release()에서 donation 제거 후 refresh_priority(A) 호출
     → A.priority = max(31, donation_list_max)
     → 31 (donation_list 비면 base로 복귀)
     → check_preemption()
       → 31 < ready_list_front.priority(35)?
       → Yes → thread_yield() → A가 선점당함

QEMU 에뮬레이션

check_preemption()은 순수 OS 소프트웨어 로직이므로 QEMU 하드웨어 에뮬레이션이 직접 관여하지 않는다. QEMU가 하는 일은 check_preemption() 내부의 각 명령어(비교, 분기, 함수 호출)를 TCG Translation Block으로 번역하여 실행하는 것뿐이다.

그러나 선점의 결과인 context switch는 QEMU가 에뮬레이션하는 하드웨어 동작으로 이어진다:

  • thread_yield() → schedule() → thread_launch() 에서 iretq 실행 → QEMU helper_iret_protected()
  • 새 스레드의 %rsp 전환 → QEMU는 다른 guest 메모리 영역의 스택을 참조
  • process_activate() → lcr3() → QEMU CR3 레지스터 갱신 → softmmu TLB flush

QEMU-GDB 조합으로 선점이 발생하는 순간을 관찰할 수 있다.

GDB에서 선점 관찰 5단계:

  1. b check_preemption — 선점 판단 함수에 breakpoint
  2. hit 시 p thread_current()->priority — 현재 스레드 우선순위 확인
  3. p ((struct thread *)list_entry(ready_list.head.next, struct thread, elem))->priority — ready_list 최고 우선순위
  4. p thread_current()->name — 누가 양보당하는지 확인
  5. c 후 thread_yield에서 재정지 → schedule() → do_iret() 관찰

선점 빈도 프로파일링:

(gdb) set $preempt_count = 0
(gdb) set $no_preempt_count = 0
(gdb) break check_preemption
(gdb) commands
  silent
  if !list_empty(&ready_list) && thread_current()->priority < \
     ((struct thread *)list_entry(ready_list.head.next, struct thread, elem))->priority
    set $preempt_count = $preempt_count + 1
  else
    set $no_preempt_count = $no_preempt_count + 1
  end
  continue
  end
(gdb) # 테스트 실행 후
(gdb) printf "preempted: %d, not: %d\n", $preempt_count, $no_preempt_count

thread_yield() 내부 관찰:

  • b *thread_yield → hit 시 p thread_current()->status (THREAD_RUNNING)
  • n 진행 → list_insert_ordered 이후 ready_list에 현재 스레드가 삽입됨 확인
  • do_schedule(THREAD_READY) 호출 후 다음 thread_current()가 바뀜 확인

sema_up → check_preemption 체인 관찰:

  • b synch.c:129 (sema_up 내 check_preemption 호출 지점)
  • hit 시 bt — sema_up의 caller 확인 (lock_release? cond_signal?)
  • p sema->waiters — 깨어날 waiter 확인

donation 해제 → 선점 관찰:

  • b thread.c:818 (refresh_priority 진입)
  • hit 시 p t->priority (갱신 전), fin 후 p t->priority (갱신 후)
  • priority가 감소했으면 직후 check_preemption에서 선점 발생 예상

check_preemption() 선점 판단 값

  • PintOS 우선순위 범위: 0 (PRI_MIN) ~ 63 (PRI_MAX), 기본값 31 (PRI_DEFAULT)
  • ready_list 조회 비용: O(1) — list_begin()은 이미 정렬된 리스트의 첫 원소
  • thread_yield() 호출 시 현재 스레드는 ready_list에 우선순위 순서대로 재삽입: O(n)
  • 선점하지 않는 fast path: O(1) — list front 조회와 비교
  • 선점하는 경로/최악 비용: O(n) — thread_yield()가 현재 스레드를 ordered ready list에 재삽입
