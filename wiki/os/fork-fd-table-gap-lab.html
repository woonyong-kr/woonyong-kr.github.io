fork fd table gap Lab (중간 fd를 닫은 뒤 큰 fd가 복제되는가)

한 줄 요약: 중간 fd를 닫은 뒤 fork하면 자식이 더 큰 열린 fd를 쓸 수 있는지 확인하는 실험.

fork fd table gap 시작

부모가 fd 2, 3, 4를 열어 둔 뒤 fd 3만 닫고 fork()하면, 자식은 아직 열려 있는 fd 4를 쓸 수 있을까?

처음에는 “fd 4는 닫지 않았으니 당연히 자식에게도 보이겠지”라고 생각하기 쉽다.

하지만 이 저장소의 PintOS 구현에서는 close(3)이 next_fd를 3으로 낮추고, fork()의 fd table 복제가 fd < parent->next_fd 범위만 돈다. 그러면 fd 4는 아직 열려 있어도 복제 loop에 들어가지 않는다.

이 Lab은 그 경계를 숫자와 GDB 관찰로 확인하는 실험이다.

fork fd table gap 구분

fd table은 빈칸 없이 차곡차곡만 채워지는 배열이 아니다.

프로그램은 파일을 여러 개 열고, 중간 fd를 닫고, 다시 열고, 그 상태에서 fork()할 수 있다. 이때 커널은 “다음에 할당할 후보 번호”와 “현재 실제로 열려 있는 fd slot”을 구분해야 한다.

이 말은 즉, next_fd 같은 값은 편의를 위한 힌트일 수 있지만, fd table의 진실은 각 slot이 NULL인지 아닌지에 있다.

이 구분을 놓치면 다음 버그가 생긴다.

이 Lab은 reuse Lab (닫힌 fd 번호가 다시 쓰이는 순간)에서 남긴 질문을 실제 fork 경계로 끌고 내려간다.

꼬리 질문

  1. close(fd)는 fd table에서 무엇을 바꾸는가?
  2. process_close_file()은 왜 next_fd를 닫힌 번호로 낮추는가?
  3. fork()는 부모 fd table의 어느 범위까지 복제하는가?
  4. next_fd가 낮아져도 더 큰 fd slot은 살아 있을 수 있는가?
  5. 자식의 read(4, ...)는 어느 함수에서 실패하는가?
  6. 실제 OS에서는 이런 gap이 있으면 어떻게 처리해야 하는가?
  7. QEMU는 이 fd 복제 실패를 어떤 수준에서만 볼 수 있는가?

실제 운영체제

Linux의 fork()는 부모의 열린 fd entry를 자식 fd table에 복제한다. fd 번호 사이에 gap이 있어도 “열려 있는 fd”는 상속 대상이다.

예를 들어 Linux에서 fd 3을 닫고 fd 4가 살아 있으면, fork() 뒤 자식도 fd 4를 갖는다. 구현은 PintOS처럼 단순한 한 페이지 배열이 아니라 files_struct, fdtable, reference count, close-on-exec bit 같은 구조를 포함하지만, 학습자가 잡아야 할 원칙은 이것이다.

Windows는 Unix식 fork()가 기본 모델이 아니다. CreateProcess에서 handle 상속 여부를 정하거나 DuplicateHandle로 명시적으로 복제한다. 따라서 “fork가 fd table을 자동 복제한다”는 설명은 Linux/POSIX 계열에 맞는 설명이고, Windows에는 그대로 적용하면 안 된다.

PintOS

이 저장소의 PintOS 흐름은 다음과 같다.

실험에서 중요한 함수는 세 개다.

함수볼 질문
process_add_file()fd 2, 3, 4가 어떤 순서로 채워지는가
process_close_file()close(3) 뒤 next_fd가 어떻게 바뀌는가
duplicate_fd_table()fd 4를 복제 범위에 포함하는가

현재 구현에서는 process_add_file()이 fd 2부터 빈칸을 찾는다. 그래서 첫 세 번의 open()은 보통 2, 3, 4를 반환한다.

그 다음 process_close_file(3)은 fd_table[3]을 NULL로 만들고, 3 < next_fd이면 next_fd = 3으로 낮춘다.

마지막으로 duplicate_fd_table()은 fd < parent->next_fd 조건을 사용한다. parent->next_fd == 3이면 fd 2만 보고 loop가 끝난다.

QEMU

QEMU는 이 실패를 “fd 4 상속 실패”로 이해하지 않는다.

PintOS가 guest memory 안에서 struct thread의 fd_table 포인터 배열을 읽고 쓴다. QEMU는 그 메모리 load/store와 CPU 명령 실행을 재현한다.

자식의 read(4, ...)가 실패하면 흐름은 디스크 장치까지 내려가지 않는다.

즉 이 Lab에서 QEMU로 확인할 수 있는 것은 guest CPU/register/memory 상태다. fd 정책의 옳고 그름은 PintOS 커널 코드가 정한다.

정리

  • fd table의 진짜 상태는 fd_table[i] != NULL 여부다.
  • next_fd는 열린 fd의 최대 범위를 보장하지 않으면 복제 범위로 쓰기 위험하다.
  • 현재 PintOS 구현은 close(3) 뒤 next_fd = 3이 될 수 있고, duplicate_fd_table()은 fd 4를 보지 못할 수 있다.
  • 자식은 유저 변수 c == 4를 갖고 있어도 커널의 fd_table[4]가 비어 있으면 read(4, ...)에 실패한다.
  • Linux식 fork 상속 모델에서는 열린 fd entry가 기준이므로 gap 뒤의 fd도 상속되어야 한다.
  • QEMU는 이 fd 정책을 판단하지 않는다. QEMU는 PintOS가 실행하는 명령과 guest memory 변화를 재현할 뿐이다.
