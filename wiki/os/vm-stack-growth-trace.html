스택 성장 Page Fault → Frame 할당 전체 Trace

스택 성장 Page Fault → Frame 할당 전체 Trace

범위: 이 문서는 스택 성장 page fault가 frame 할당과 매핑으로 이어지는 일반 흐름과 판단 조건을 설명하되, 제시된 함수·코드 좌표·주소·상수·GDB 절차는 특정 구현을 전제로 한 추적 예시다. 실제 동작과 성능은 해당 코드와 버전의 실행 기록 및 측정으로 별도 검증해야 한다.

한 줄 요약: 유저 프로그램이 매핑된 스택 아래 주소를 건드리면 page fault가 나고, OS는 정당한 스택 성장으로 판단되면 새 anonymous page를 SPT에 등록·프레임 할당·매핑까지 설치한 뒤 명령을 재실행한다.

스택 성장 Page Fault → Frame 상태

유저 프로그램이 현재 매핑된 스택 영역 아래의 주소에 접근하면 page fault가 발생한다. OS는 이 fault가 정당한 스택 성장인지 판단하고, 정당하다면 새 anonymous page를 SPT에 등록한 뒤 물리 frame을 할당하여 매핑을 설치한다. 이 trace는 유저의 push rbp 같은 명령어에서 시작해 page fault → vm_try_handle_fault → vm_should_grow_stack → vm_stack_growth → vm_claim_page → do_iret 복귀까지의 전체 흐름을 추적한다.

시나리오

유저 프로그램에서 큰 지역 변수 배열을 선언하는 상황:

초기 스택: 1 페이지(0x47FFE000~0x47FFF000)만 매핑됨. buf[0]에 접근하면 0x47FFC000 근처에 fault 발생.

    GC-->>TF: true
    TF-->>PF: true

vm_should_grow_stack 판단 조건

세 가지 조건의 의미:

조건의미값 (기본)
fault_addr < USER_STACK유저 스택 영역 안USER_STACK = 0x47FFF000
fault_addr >= USER_STACK - STACK_MAX스택 최대 크기 초과 방지STACK_MAX = 1 MB = 0x100000
fault_addr >= rsp - 32RSP 근처 접근만 허용32 bytes 여유 (push 최대 크기)

rsp - 32 조건이 중요한 이유: push는 RSP를 8 감소시키고 쓴다. pusha(32-bit)는 32 bytes를 한 번에 push한다. 따라서 fault_addr이 rsp - 32 이상이어야 정당한 스택 접근이다. 이보다 훨씬 아래 주소에 접근하면 잘못된 포인터(segfault)로 판단한다.

vm_stack_growth 루프

이 루프는 현재 stack_bottom과 fault 주소 사이의 모든 페이지를 한 번에 SPT에 등록한다. 2 페이지 점프 시나리오에서도 중간 페이지를 빠뜨리지 않는다.

스택 성장 비용

단계시간 (대략)
pf 예외 진입 (CPU → 핸들러)~100 ns
vm_try_handle_fault 분기~50 ns
vm_should_grow_stack 판단~30 ns
vm_alloc_page × 2 (SPT hash 삽입)~200 ns
palloc_get_page (bitmap 검색)~100 ns
pml4_set_page (PTE 설치)~50 ns
do_iret 복귀~100 ns
합계~630 ns

비교: 정상 메모리 접근은 ~1 ns, TLB miss는 ~10 ns. 스택 성장은 정상 접근보다 ~630배 느리지만, 한 번 성장하면 이후 접근은 정상 속도다.

user vs kernel fault에서의 RSP 결정

fault 원인user 파라미터RSP 출처이유
유저 코드에서 직접 접근truef->rsp인터럽트 프레임에 유저 RSP 저장됨
syscall 핸들러 내 copy_to_userfalsecurr->user_rsp커널 모드에서 유저 포인터 접근, intr_frame은 커널 RSP

커널 모드에서 유저 포인터를 통해 스택 접근 시, f->rsp는 커널 스택을 가리키므로 사용할 수 없다. 대신 syscall 진입 시 저장해 둔 thread->user_rsp를 사용한다.
