QEMU TCG 번역 블록

QEMU TCG 번역 블록

확인 범위: 이 문서는 QEMU TCG의 Translation Block 번역·캐싱·체이닝·무효화 원리와 PintOS 환경에서의 영향 및 선택 기준을 개념적으로 설명한다. 제시된 소스 경로·구조체·함수·기본값·성능 수치·TB 크기 예시는 특정 QEMU 버전이나 실제 실행 기록으로 검증된 결과가 아니므로, 구현과 환경별 판단에는 해당 버전의 코드 확인과 실행·성능 측정이 필요하다.

한 줄 요약: guest 명령어를 host 명령어로 번역한 단위 Translation Block(TB) — 한 명령어씩 인터프리팅하지 않음.

QEMU TCG 번역 블록 구조

Translation Block(TB)은 QEMU TCG(Tiny Code Generator)가 guest 명령어를 host 명령어로 번역한 결과물의 단위다. QEMU는 guest 코드를 한 명령어씩 인터프리팅하지 않고, 일련의 guest 명령어를 묶어 host native 코드로 변환한 뒤 직접 실행한다. 이 “묶음”이 Translation Block이다. TB 단위의 변환과 캐싱이 QEMU가 순수 인터프리터 대비 10~100배 빠른 핵심 이유다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

실제 CPU는 fetch → decode → execute를 파이프라인으로 처리한다. QEMU는 이를 소프트웨어로 재현해야 하는데, 한 명령어씩 “fetch → decode → 호스트 코드 생성 → 실행”하면 너무 느리다. 대신 기본 블록(basic block) 단위로 한 번에 번역하고, 번역된 호스트 코드를 캐시에 보관하여 같은 코드가 다시 실행될 때 재활용한다.

기본 블록이란 분기 없이 순차적으로 실행되는 명령어 시퀀스를 말한다. TB의 경계는:

  • 시작: 분기의 목적지(jump target), 또는 인터럽트 복귀 지점
  • 끝: 분기 명령어(jmp, call, ret, 조건 분기), 또는 인터럽트/예외 발생 지점

TCG 번역 파이프라인

%% TCG 번역 파이프라인
flowchart TD
  guest["Guest x86-64 코드"]
  frontend["Frontend<br/>target/i386/tcg/translate.c<br/>guest 명령어 -&gt; TCG IR"]
  optimizer["Optimizer<br/>불필요한 연산 제거"]
  backend["Backend<br/>tcg/aarch64/ 또는 tcg/i386/<br/>TCG IR -&gt; host native 코드"]
  cache["Code Cache<br/>TB 저장"]
  guest --> frontend
  frontend --> optimizer
  optimizer --> backend
  backend --> cache

각 단계의 역할:

  1. Frontend — guest ISA 전용. x86-64의 가변 길이 명령어(1~15바이트)를 디코드하고, 의미를 TCG IR 연산(op)으로 표현한다. 예를 들어 mov rax, [rbx+8]은 “load 64bit from (rbx+8) into rax” TCG op이 된다.

  2. TCG IR — ISA 독립적인 중간 표현. 레지스터는 “TCG temp”라는 추상 변수로, 메모리 접근은 load/store op으로 표현된다. 약 150개의 op 종류가 있다.

  3. Backend — host ISA 전용. TCG IR을 호스트 CPU의 네이티브 명령어로 변환한다. macOS ARM64 위에서 PintOS를 돌리면, x86-64 guest 코드가 ARM64 host 코드로 변환된다.

TB 캐시와 체이닝

코드 캐시(Code Cache):

번역된 TB는 QEMU 프로세스의 메모리에 할당된 코드 캐시 영역에 저장된다. 기본 크기는 약 32MB다. 같은 guest PC(RIP)의 코드가 다시 실행되면 캐시에서 찾아 바로 실행한다. 캐시가 가득 차면 전체를 flush하고 처음부터 다시 번역한다.

TB 체이닝(Chaining):

TB A의 끝이 무조건 분기(jmp target)이고 target의 TB B가 이미 캐시에 있으면, TB A의 마지막에 TB B로 직접 점프하는 호스트 명령어를 패치한다. 이렇게 하면 QEMU의 메인 루프로 돌아가지 않고 TB → TB → TB로 연속 실행되어 오버헤드가 크게 줄어든다.

%% TB 체이닝
flowchart TD
  tb_a["TB A<br/>guest 0x400100~0x40010F<br/>... host 코드 ..."]
  tb_b["TB B<br/>guest 0x400110~0x40012A<br/>... host 코드 ..."]
  tb_c["TB C<br/>..."]
  tb_a -->|"jmp TB_B 직접 점프"| tb_b
  tb_b -->|"jmp TB_C 직접 점프"| tb_c

체이닝이 불가능한 경우(간접 분기, 인터럽트 검사 필요 등)에는 QEMU 메인 루프로 복귀한다.

TB 무효화

Guest OS가 코드 영역의 메모리를 수정하면(자기 수정 코드, JIT 등) 해당 guest 주소의 TB를 무효화해야 한다. QEMU는 guest 페이지 단위로 TB를 추적하여, 해당 페이지에 대한 쓰기가 발생하면 관련 TB를 모두 삭제한다.

PintOS에서는 자기 수정 코드가 없으므로 TB 무효화는 주로 page table 변경(CR3 전환, pml4_set_page 등) 시 발생한다.

실제 OS (Linux/Windows)

실제 OS에서 QEMU를 사용할 때, KVM이 활성화되면 TCG 대신 하드웨어 가상화(VT-x/AMD-V)를 사용한다. 이 경우 guest 코드가 실제 CPU에서 직접 실행되므로 TB 번역이 필요 없다. TCG는 KVM이 불가능한 환경(cross-architecture, 예: ARM 호스트에서 x86 guest)에서만 사용된다.

PintOS 개발 환경에서는:

  • x86-64 호스트: KVM 사용 가능 → TB 번역 없이 직접 실행
  • ARM64 호스트 (Apple Silicon Mac): KVM 불가 → TCG로 x86-64 → ARM64 번역

PintOS 구현

PintOS 자체는 TCG를 인식하지 못한다. PintOS 입장에서는 “실제 x86-64 CPU 위에서 돌아가는 것”과 동일하게 동작한다. 그러나 PintOS 개발자가 알아야 할 TCG 영향:

성능 차이:

  • TCG 모드에서 PintOS의 loops_per_tick 보정값이 실제 하드웨어와 크게 다르다.
  • timer_calibrate()가 측정하는 busy-wait 루프 속도는 TCG 번역 오버헤드를 포함한다.

디버깅 영향:

  • GDB로 PintOS를 디버깅할 때, breakpoint는 TB 무효화를 유발한다. breakpoint가 설정된 주소의 TB가 삭제되고, 해당 guest 명령어가 다시 번역될 때 breakpoint trap이 삽입된다.
  • single-step 모드에서는 TB 크기가 1 명령어로 제한되어 매우 느려진다.

CPUX86State와 TB의 관계:

TB를 실행하기 직전에 CPUX86State에서 guest 레지스터를 호스트 레지스터나 TCG temp에 로드하고, TB 실행이 끝나면 결과를 CPUX86State에 다시 저장한다.

QEMU 에뮬레이션

QEMU 소스에서 TB 관련 핵심 구조체:

TB 조회는 tb_lookup() → tb_htable_lookup()으로 guest PC + flags를 키로 해시 테이블에서 찾는다. 미스(miss)이면 tb_gen_code()로 새 TB를 번역한다.

QEMU TCG 번역 블록 값 추적

TB 크기 예시:

PintOS thread_yield() 함수의 TB:

guest 시작 주소: 0x800420B0 (커널 코드)
guest 명령어 수: 약 8~15개 (call까지)
guest 코드 크기: 약 30~60 바이트 (x86-64 가변 길이)
host 코드 크기: 약 100~300 바이트 (ARM64 고정 4바이트 명령어 기준)

변환 비율: guest 1바이트 → host 약 2~5바이트 (ISA와 상황에 따라 다름)

코드 캐시 크기:

기본 코드 캐시: 32 MB
평균 TB 크기 (host): ~200 바이트
캐시 가능 TB 수: ~160,000개
PintOS 전체 커널 코드: ~100 KB → TB ~수천 개
→ 캐시 부족 없음 (PintOS는 작은 OS)

번역 비용:

TB 번역 (cold): ~10~100 마이크로초
TB 실행 (cached): ~나노초 (네이티브에 가까움)
번역:실행 비율: 한 번 번역 → 수천~수만 번 재실행

flowchart TD
  main_loop["QEMU 메인 루프"]

  lookup -->|"Hit"| run_tb
  lookup -->|"Miss"| gen_code
  gen_code --> store_cache
  store_cache --> run_tb
  run_tb --> exit_reason

  direct_jump --> run_tb
  exit_reason -->|"인터럽트 검사 간접 분기"| main_loop
  exit_reason -->|"예외 발생"| exception
  exception --> main_loop
