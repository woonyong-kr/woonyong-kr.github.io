QEMU는 Syscall 번호를 해석하지 않는다

QEMU는 Syscall 번호를 해석하지 않는다

확인 범위: 이 문서는 SYSCALL의 CPU 상태 전환과 syscall 번호를 해석하는 OS 정책의 경계를 설명하는 개념 문서다. 제시된 QEMU·PintOS·Linux 코드 좌표와 GDB 출력, 실행 시간·주소·명령어 수 등의 수치는 특정 버전의 실제 소스나 실행 기록·성능 측정으로 검증한 결과가 아니라, 해당 구현을 판단할 때 별도로 확인해야 할 항목이다.

QEMU는 SYSCALL 명령어가 CPU에 일으키는 효과만 재현한다. RAX에 들어 있는 번호가 write인지 read인지 해석하는 일은 PintOS 커널의 몫이다.

숫자는 남겨 두고 의미는 커널이 붙인다

guest에서 SYSCALL 명령어가 실행되면 QEMU는 RCX, R11, RIP, 세그먼트처럼 CPU가 바꾸기로 정한 값만 바꾼다. RAX에 SYS_WRITE=10이 들어 있어도 QEMU에게는 그냥 64비트 정수다. 그 숫자를 write() 호출로 바꾸는 코드는 guest OS인 PintOS의 syscall_handler() 안에 있다.

하드웨어 효과와 OS 정책의 경계

SYSCALL 명령어의 하드웨어 동작

x86-64 SYSCALL 명령어는 CPU가 수행하는 고정된 하드웨어 절차다:

단계CPU 동작관여하는 레지스터/MSR
1RCX ← RIP (복귀 주소 저장)RCX
2R11 ← RFLAGS (플래그 저장)R11
3RIP ← LSTAR MSR (진입점 점프)IA32_LSTAR (0xC0000082)
4CS ← STAR[47:32], SS ← STAR[47:32]+8IA32_STAR (0xC0000081)
5RFLAGS &= ~SFMASKIA32_FMASK (0xC0000084)

이 5단계에서 RAX는 읽히지도, 수정되지도 않는다. CPU는 RAX에 무엇이 들어 있든 상관하지 않는다. RAX를 “syscall 번호”로 해석하는 것은 순전히 OS의 **소프트웨어 규약(ABI)**이다.

env->regs[R_EAX]를 읽는 코드가 없다. QEMU에게 RAX=10이든 RAX=9999든 동일하다. 둘 다 그냥 64비트 정수로 CPUX86State.regs[0]에 남아 있을 뿐이다.

실제 OS (Linux)

Linux도 동일한 구조다:

구성 요소위치역할
syscall 번호 정의arch/x86/include/generated/uapi/asm/unistd_64.h__NR_write = 1
syscall 테이블arch/x86/entry/syscall_64.csys_call_table[__NR_write] = __x64_sys_write
진입점arch/x86/entry/entry_64.Sentry_SYSCALL_64

Linux의 syscall 번호 체계는 PintOS와 다르다 (write가 Linux에서는 1, PintOS에서는 10). 이것은 OS 정책이기 때문에 하드웨어(또는 QEMU)와 무관하다.

GDB로 확인하기

QEMU GDB stub으로 syscall 경계를 직접 관찰할 수 있다:

(gdb) b *syscall_handler
(gdb) continue
... (유저가 write 호출)

Breakpoint hit at syscall_handler

(gdb) p/x $rax
$1 = 0xa                  ← 10 = SYS_WRITE

(gdb) p/x $rdi
$2 = 0x1                  ← fd = 1 (stdout)

(gdb) p/x $rsi
$3 = 0x804a020            ← buffer 주소 (유저 공간)

(gdb) p/x $rdx
$4 = 0xd                  ← length = 13 bytes

이 시점에서 QEMU는 “RAX=0xa, RDI=0x1, RSI=0x804a020, RDX=0xd”라는 숫자만 알고, PintOS는 이것을 “fd=1(stdout)에 13바이트를 쓰라”로 해석한다.

syscall 번호 값 추적

SYSCALL 명령어의 CPU 동작 시간 (실제 하드웨어):
  ~ 수십 ns (WRMSR로 설정된 진입점으로 점프)

QEMU TCG에서의 SYSCALL 처리:
  helper_syscall() 호출 → 레지스터 5개 변경 → 수 μs

PintOS syscall_handler() switch 문:
  20+ case 분기 → 해당 함수 호출 → 수천~수만 명령어

RAX 값 범위:
  QEMU가 처리 가능한 범위: 0 ~ 2^64-1 (어떤 값이든 무관)
  PintOS가 해석하는 범위: 0 (SYS_HALT) ~ 21 (SYS_DUP2)
  범위 밖이면: default 분기 → 아무 동작 없음

순서도 / 개념도

PintOS user wrapper는 syscall1(SYS_WRITE, fd) 계열에서 inline assembly로 RAX에 syscall 번호를 두고 RDI·RSI·RDX에 fd·buf·len을 배치한 뒤 syscall을 실행한다. 예를 들어 assembly의 핵심은 mov ... %rax; ... syscall이다. QEMU는 RAX의 10을 해석하지 않은 채 LSTAR에 등록된 syscall_entry(실행 예: 0x800420xxxx)로 제어를 옮긴다. syscall_entry가 intr_frame을 구성한 뒤 PintOS handler가 SYS_WRITE를 선택하며, fd=1이면 console putbuf() 경로를 탈 수 있다.

sequenceDiagram
    participant User as 유저 프로그램
    participant QEMU as QEMU (하드웨어)
    participant OS as PintOS (OS)

    User->>User: RAX ← SYS_WRITE(10)
    User->>User: RDI ← fd, RSI ← buf, RDX ← len
    User->>QEMU: SYSCALL 명령어

    Note over QEMU: RAX를 읽지 않음!
    QEMU->>QEMU: RCX ← RIP
    QEMU->>QEMU: R11 ← RFLAGS
    QEMU->>QEMU: RIP ← LSTAR MSR
    QEMU->>QEMU: CS/SS ← 커널 세그먼트

    QEMU->>OS: RIP가 syscall_entry로 이동

    Note over OS: RAX를 읽어서 해석
    OS->>OS: switch(f->R.rax)
    OS->>OS: case 10 → write()
    OS->>OS: 반환값 → f->R.rax
    OS->>QEMU: SYSRET / do_iret

    QEMU->>User: RIP 복원, CPL 3
