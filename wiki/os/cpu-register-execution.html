CPU 레지스터와 명령어 실행

한 줄 요약: RIP가 가리키는 명령어를 fetch·decode·execute하며 레지스터·메모리를 바꾸는 CPU 실행의 본질.

핵심 모델

CPU 실행의 본질은 RIP가 가리키는 명령어 바이트를 읽고(fetch), 해석하고(decode), 레지스터나 메모리를 변경하고(execute), 다음 RIP로 이동하는 반복이다. OS 관점에서 레지스터는 단순한 연산 임시 저장소가 아니라, 시스템 콜 인자 전달, 컨텍스트 스위치 상태 보존, 페이지 테이블 루트 지정 등 커널과 유저의 경계를 오가는 핵심 매개체다.

CPU 레지스터와 명령어 실행 쟁점

write(1, "hello", 5)를 호출했을 때, 숫자 1, 문자열 주소, 크기 5는 커널에 어떻게 전달될까?

처음에는 함수 호출처럼 보이지만, 시스템 콜 경계에서는 “C 함수 인자”보다 더 낮은 층의 약속이 중요해진다. 그 약속은 어떤 값을 어떤 레지스터에 넣을 것인가다.

CPU 레지스터와 명령어 실행 혼동

운영체제는 유저 프로그램을 믿지 않는다. 유저 프로그램이 커널 함수를 직접 호출하게 두면, 파일 시스템이나 메모리 보호 규칙을 우회할 수 있다.

그래서 CPU는 유저 모드에서 커널 모드로 넘어가는 제한된 문을 제공하고, 커널은 그 순간의 레지스터 값을 읽어 요청을 해석한다.

이 말은 즉, 시스템 콜을 이해하려면 함수 이름보다 먼저 다음을 봐야 한다.

  • RAX: 어떤 시스템 콜인가?
  • RDI, RSI, RDX: 첫 번째, 두 번째, 세 번째 인자는 무엇인가?
  • RIP: 유저 프로그램은 어디에서 커널로 들어왔는가?
  • RSP: 유저 스택은 어디였고, 커널 스택은 어디인가?
  • RFLAGS: 인터럽트 허용 같은 CPU flag는 어떤 상태였는가?

운영체제 관점에서 중요한 레지스터는 보통 다음이다.

레지스터의미
RIP다음에 실행할 instruction address
RSP현재 stack top
RBPstack frame 기준점
RAX반환값, syscall number
RDI/RSI/RDX함수 또는 syscall 인자
CR3현재 page table root
RFLAGSinterrupt enable 같은 CPU flag

시스템 콜 순간에는 이 레지스터들이 “요청서”가 된다.

유저 요청 직전 레지스터syscall 경계의 의미
RAXsyscall number, 예: SYS_WRITE
RDI, RSI, RDX첫 3개 인자, 예: fd, user buffer address, size
R10, R8, R9x86-64 Linux syscall ABI의 추가 인자
RIPsyscall instruction 다음의 복귀 위치
RSP유저 stack top

커널은 C 함수 이름을 직접 받지 않는다. 저장된 register snapshot의 RAX로 syscall을 고르고, 예를 들어 RAX == SYS_WRITE이면 그 ABI에 따라 RDI/RSI/RDX를 인자로 해석한다.

write(1, "hello", 5) 요청

문자열 "hello" 자체가 레지스터에 통째로 들어가는 것은 아니다. 레지스터에는 문자열이 놓인 유저 가상 주소가 들어간다.

flowchart LR

  registers["syscall 직전<br/>RAX=SYS_WRITE<br/>RDI=1<br/>RSI=0x401000<br/>RDX=5"]
  validate["커널<br/>RSI..RSI+4<br/>user pointer 검증"]

커널은 RSI를 포인터처럼 다루기 전에 반드시 “이 주소가 유저가 읽어도 되는 주소인가?”를 확인해야 한다. 그 다음 흐름은 유저 포인터 검증 (User Pointer Validation) Trace로 이어진다.

실제 운영체제

Linux와 Windows 모두 CPU architecture의 ABI와 privilege level 위에서 실행된다. 차이는 API 이름과 커널 내부 구조에 있지만, 공통 문제는 같다.

관점LinuxWindows
유저 APIwrite, read, mmap 같은 POSIX API와 syscall ABIWriteFile, ReadFile, VirtualAlloc 같은 Win32 API
커널 진입CPU의 syscall/interrupt/trap 계열 진입을 사용CPU의 kernel transition을 사용
저장되는 상태레지스터 snapshot, trap frame 계열 구조trap frame, thread context, handle/object 상태
복잡한 이유보안, SMP, signal, seccomp, ptrace, page cachehandle table, object manager, APC, SEH, 보안 모델

여기서 중요한 결론은 “실제 OS도 결국 레지스터를 저장하고 복원한다”는 점이다. 다만 실제 OS는 PintOS보다 훨씬 많은 CPU 기능, 보안 정책, 디버깅 기능을 함께 다룬다.

PintOS

PintOS에서 레지스터는 다음 상황에서 눈에 띈다.

  • interrupt 또는 syscall 진입 시 struct intr_frame
  • context switch 시 saved register와 stack pointer
  • user program 시작 시 RIP, RSP
  • syscall 인자 전달 시 RAX, RDI, RSI, RDX

대표 파일:

  • PintOS 저장소 상대 경로 pintos/include/threads/interrupt.h
    • struct gp_registers
    • struct intr_frame
  • PintOS 저장소 상대 경로 pintos/userprog/syscall.c
    • syscall_init()
    • syscall_handler()
  • PintOS 저장소 상대 경로 pintos/userprog/syscall-entry.S
    • syscall_entry
  • PintOS 저장소 상대 경로 pintos/threads/intr-stubs.S
    • intr_entry

시스템 콜 진입의 핵심

PintOS는 부팅 중 syscall_init()에서 CPU MSR을 설정한다.

MSR_LSTAR는 x86-64 long mode에서 syscall 명령이 커널 쪽 어디로 점프할지 담는 register다. 이 값 때문에 유저 프로그램의 syscall 명령은 PintOS의 syscall_entry로 들어온다.

syscall_entry.S는 CPU가 남긴 값과 유저 레지스터를 커널 스택에 push해서 struct intr_frame 모양으로 만든 뒤, 그 주소를 RDI에 넣고 syscall_handler()를 호출한다.

%% PintOS syscall entry flow
flowchart TD
  init["syscall_init()<br/>MSR_LSTAR = syscall_entry"]
  user["유저 프로그램<br/>syscall instruction"]
  cpu["CPU<br/>RCX/R11에 복귀 상태 보존<br/>RIP = MSR_LSTAR"]
  entry["syscall_entry<br/>커널 stack 전환<br/>register snapshot 구성"]
  handler["syscall_handler(f)<br/>f->R.rax로 분기<br/>인자 해석<br/>f->R.rax에 반환값 저장"]
  init -.->|진입점 설정| cpu
  user --> cpu
  cpu --> entry
  entry -->|RDI = &intr_frame| handler

syscall_handler()는 이 snapshot을 읽는다.

f->R.rax는 처음에는 syscall 번호이고, handler가 끝날 때는 반환값 위치가 된다. 이 한 줄이 RAX가 “요청 번호”와 “결과값”이라는 두 역할을 시간 순서로 갖는다는 증거다.

QEMU

QEMU에서 guest register는 host CPU register와 같은 것이 아니다. QEMU는 guest CPU state를 내부 자료구조로 들고 있고, TCG 또는 가속기를 통해 guest instruction의 효과를 host에서 재현한다.

확인할 QEMU 영역:

  • target/i386/cpu.h
    • CPUX86State
    • regs[], eip, eflags, cr[]
  • target/i386/tcg/emit.c.inc
    • gen_SYSCALL()
  • target/i386/tcg/system/seg_helper.c
    • helper_syscall()
  • target/i386/gdbstub.c
    • x86_cpu_gdb_read_register()
    • x86_cpu_gdb_write_register()

QEMU의 x86 CPU 상태는 대략 다음 식으로 읽으면 된다.

PintOS가 보는 RAX, RDI, RIP, CR3는 guest CPU 관점의 값이다. QEMU 내부에서는 env->regs[...], env->eip, env->cr[3] 같은 guest state로 표현된다.

QEMU GDB stub도 같은 guest state를 읽어 GDB에 보여준다.

%% GDB register read flow
flowchart LR
  guest["PintOS guest<br/>syscall_handler가<br/>register 의미 해석"]
  state["QEMU CPUX86State<br/>regs[] / eip / eflags / cr[]"]
  stub["QEMU GDB stub<br/>remote protocol로 직렬화"]
  gdb["GDB info registers<br/>RAX/RDI/RIP/CR3 표시"]
  guest -.->|동일 guest architectural state| state
  state --> stub
  stub --> gdb

중요한 구분이 있다. QEMU는 SYS_WRITE의 의미를 모른다. QEMU는 syscall 명령이 RCX, R11, RIP, segment state를 어떻게 바꾸는지 같은 CPU 동작을 재현한다. RAX == SYS_WRITE를 보고 파일에 쓰는 주체는 PintOS의 syscall_handler()다.

1. write(1, 0x8048123, 5)의 레지스터 값

%% write syscall 요청과 반환값
flowchart TD
  user["user code<br/>RAX=SYS_WRITE<br/>RDI=1<br/>RSI=0x8048123<br/>RDX=5"]
  syscall["syscall instruction<br/>CPU/QEMU는 CPL/RIP 전환<br/>번호 의미는 해석하지 않음"]
  entry["syscall_entry<br/>intr_frame snapshot 생성<br/>f->R.rax=SYS_WRITE"]
  handler["syscall_handler(f)<br/>번호와 인자 해석<br/>f->R.rax=write 결과"]
  restore["현재 local branch의 syscall-entry.S<br/>sysretq 복귀<br/>RAX=write 반환값"]
  user --> syscall --> entry --> handler --> restore

source 학습 문서의 do_iret() 복귀 설명은 이전/upstream 흐름을 전제로 한다. 현재 local branch의 실제 userprog/syscall-entry.S는 정상 syscall 끝에서 register를 pop한 뒤 sysretq를 실행한다. do_iret()의 iretq는 context switch, 초기 유저 진입, 인터럽트·예외 복원 경로에서 별도로 사용된다. RSI = 0x8048123은 문자열 자체가 아니라 guest virtual address다.

계산 항목값
guest virtual address0x8048123
4 KiB page base: RSI & ~0xFFF0x8048000
page number0x8048
page offset: RSI & 0xFFF0x123
5-byte 접근 범위0x8048123..0x8048127

커널은 0x8048000 page의 유효성과 RSI..RSI+4 전체 범위의 user 접근 권한을 확인해야 한다. 검증이 끝나면 물리 frame의 offset 0x123..0x127에 접근한다. 커널이 이 주소에서 5바이트를 읽으면 다음처럼 보일 수 있다.

VAbyteASCII
0x80481230x68h
0x80481240x65e
0x80481250x6cl
0x80481260x6cl
0x80481270x6fo

레지스터에는 문자열 전체가 아니라 시작 주소 RSI와 길이 RDX가 들어 있다. 같은 byte range도 명령, 정수, 문자열 중 무엇으로 해석할지는 consumer가 결정한다.

2. struct intr_frame 안의 offset 계산

struct gp_registers는 64비트 register 15개를 순서대로 담는다.

struct gp_registers는 64-bit field 15개이므로 15 × 8 = 120 bytes다. 선언 순서가 offset을 결정해 f->R.rsi는 8 × 8 = 64, f->R.rax는 14 × 8 = 112에 놓이고 다음 영역은 offset 120에서 시작한다. 이 구현의 struct intr_frame에서 주요 offset은 다음처럼 계산할 수 있다.

필드offset
f->R.r150
f->R.rsi64
f->R.rdi72
f->R.rdx88
f->R.rax112
f->vec_no136
f->error_code144
f->rip152
f->cs160
f->eflags168
f->rsp176
f->ss184

예를 들어 f = 0x80042000이라면:

필드f = 0x80042000일 때 주소

f->R.rdi0x80042048
f->R.rdx0x80042058

GDB의 x/gx 0x80042070은 f->R.rax, x/gx 0x80042098은 f->rip을 보여 준다. 이 방식으로 debug symbol의 구조체 해석과 raw memory를 교차 검증할 수 있다. 이 계산을 할 수 있으면 GDB에서 struct intr_frame을 신뢰하지 않고도 raw memory가 어떤 필드로 해석되는지 확인할 수 있다.

CPU 레지스터와 명령어 실행 GDB

PintOS GDB에서 syscall 인자 보기

syscall_handler에 멈췄다면 현재 CPU register와 저장된 user register를 구분해서 본다.

확인해야 할 질문:

  • f->R.rax가 syscall 번호인가?
  • f->R.rdi/rsi/rdx가 유저가 넘긴 인자인가?
  • f->rip는 syscall 이후 돌아갈 유저 코드 주소인가?
  • f->R.rsi가 가리키는 바이트가 실제 "hello"인가?

raw offset으로도 확인할 수 있다.

첫 줄은 f->R.rax, 둘째 줄은 f->rip와 같은 값을 보여야 한다.

QEMU GDB stub 관점에서 보기

QEMU GDB stub에 붙은 GDB의 info registers는 host macOS/Linux register가 아니라 guest register를 보여준다. 이 관찰 계층 자체는 QEMU GDB Stub은 어떤 상태를 보여주는가에서 따로 정리한다.

같은 이름의 RAX라도 관찰 위치에 따라 의미가 다르다.

Linux vs PintOS 레지스터 보존 비교

context switch에서 보존해야 할 레지스터 범위가 OS마다 다르다. System V ABI에서 callee-saved는 RBX, RBP, R12-R15이지만, 커널 내부에서는 모든 레지스터를 저장해야 하는 상황이 있다.

항목LinuxPintOS
유저→커널 진입 시 저장pt_regs 구조체에 15개 범용 + RIP/RSP/RFLAGS/세그먼트struct intr_frame에 15개 범용 + RIP/RSP/RFLAGS/세그먼트
context switch 저장callee-saved 레지스터만 (RBX, RBP, R12-R15) __switch_to_asmthread_launch()에서 모든 범용 레지스터를 intr_frame에 저장 후 do_iret()
switch 전환 단위task_struct, FPU/SSE state 포함struct thread, FPU state 없음
pt_regs / intr_frame 크기kernel version과 구성의 실제 struct pt_regs 확인192 bytes (0xC0, packed current local layout)
부동소수점XSAVE/XRSTOR로 별도 저장저장하지 않음 (유저 프로그램에서 FP 사용 시 손실)
세그먼트 레지스터FS/GS per-CPU, 나머지 고정ES/DS만 intr_frame에 저장

PintOS thread_launch()가 callee-saved만 저장하지 않고 모든 레지스터를 intr_frame에 기록하는 이유는, 스레드 전환을 do_iret()의 iretq로 통일하기 때문이다. Linux의 __switch_to_asm은 callee-saved만 스택에 push/pop하고 ret으로 돌아가는 더 가벼운 방식을 쓴다.

정리

  • CPU 실행은 RIP가 명령어 바이트를 가리키고, 실행 결과가 레지스터와 메모리에 반영되는 반복이다.
  • 시스템 콜에서는 레지스터가 커널 요청서가 된다.
  • PintOS는 syscall_entry.S가 struct intr_frame 모양의 snapshot을 만들고, syscall_handler()가 f->R.rax/rdi/rsi/rdx를 읽는다.
  • QEMU는 SYS_WRITE를 처리하지 않는다. QEMU는 guest CPU state와 syscall 명령의 하드웨어 의미를 재현한다.
  • GDB에서는 현재 register와 저장된 intr_frame field를 구분해야 한다.
