is_user_vaddr() — 유저 주소 범위 확인

한 줄 요약: is_user_vaddr()는 syscall로 전달된 주소가 PintOS의 유저 주소 범위에 속하는지 먼저 확인한다. 커널 주소가 이후의 매핑 검사와 메모리 접근으로 넘어가지 않게 막는 첫 번째 필터다.

syscall로 받은 주소를 왜 먼저 검사하는가

유저 프로그램은 syscall 인자로 포인터를 커널에 전달한다. 이 포인터가 유저 영역을 가리킨다는 보장은 없으므로, 커널은 실제로 주소를 사용하기 전에 범위와 매핑을 확인해야 한다. 그렇지 않으면 유저 프로그램이 커널 주소를 전달했을 때 커널 데이터가 읽히거나 덮어써질 수 있다.

PintOS의 is_user_vaddr()는 이 검증 과정에서 주소 범위만 판별한다. 주소가 NULL인지, 페이지가 실제로 매핑되었는지, 쓰기 가능한지까지 한 번에 보장하지는 않는다. 이런 조건은 뒤따르는 검증 단계가 맡는다.

하드웨어가 나누는 주소 공간

이 문서가 전제로 삼는 x86-64의 48비트 canonical address 공간은 상위 비트 패턴에 따라 다음과 같이 나뉜다.

영역주소 범위용도
Lower half0x0000_0000_0000_0000 ~ 0x0000_7FFF_FFFF_FFFF유저 공간
Non-canonical hole0x0000_8000_0000_0000 ~ 0xFFFF_7FFF_FFFF_FFFF사용 불가
Upper half0xFFFF_8000_0000_0000 ~ 0xFFFF_FFFF_FFFF_FFFF커널 공간

PTE의 U/S 비트(bit 2)는 하드웨어 수준에서 유저 접근과 커널 접근을 구분한다. 그러나 syscall을 처리하는 커널은 CPL 0에서 실행되므로, SMAP이 없는 환경에서는 U/S=0인 커널 페이지에도 접근할 수 있다. 따라서 유저가 넘긴 포인터를 커널이 직접 사용할 때는 하드웨어 권한 검사와 별도로 주소 범위를 걸러야 한다.

PintOS의 주소 경계와 구현

PintOS는 KERN_BASE를 유저 영역과 커널 영역의 경계로 사용한다.

is_user_vaddr()는 vaddr < KERN_BASE인지 판별하는 매크로다. 함수 호출 없이 비교식으로 평가되며, KERN_BASE 이상인 주소를 거부한다.

항목값
KERN_BASE0x80_0400_0000 (약 32.016 GiB)
유저 공간0x0 ~ 0x80_03FF_FFFF
유저 공간 크기약 32 GiB
USER_STACK0x4748_0000 (약 1.114 GiB)
비교 연산 비용1회 unsigned 비교 (1 cycle)

주소별 판정은 다음과 같다.

  • 0x0804_8000 (일반 유저 코드) → < KERN_BASE → 통과
  • 0x80_0400_0000 (KERN_BASE 정확히) → >= KERN_BASE → 거부
  • 0xFFFF_FFFF_FFFF_FFFF (커널 최상단) → >= KERN_BASE → 거부
  • NULL (0x0) → < KERN_BASE → 통과하지만, 별도 NULL 검사에서 거부

마지막 예시처럼 범위 검사 통과는 주소가 사용 가능하다는 뜻이 아니다. NULL도 수치상 KERN_BASE보다 작기 때문에 별도 검사가 필요하다.

syscall 검증 체인에서 맡는 단계

PintOS의 호출 흐름은 validate_user_addr() → try_claim_user_addr() → is_user_vaddr() 순서다. try_claim_user_addr()는 먼저 NULL을 거부하고, 이어서 is_user_vaddr()로 유저 주소 범위인지 확인한다. 그다음 PML4 walk으로 매핑을 확인하고, VM을 사용하는 경우 SPT lookup이나 stack growth 가능성을 판단한다. 검증에 실패하면 validate_user_addr()가 exit(-1)을 호출해 유저 프로세스를 종료한다.

  • try_claim_user_addr(addr, write, f)
  • addr == NULL? → false
  • is_user_vaddr(addr)? → false이면 return false ← 여기
  • user_page_accessible? → PML4 walk으로 매핑 확인
  • (VM) SPT lookup / stack growth

전체 흐름은 다음과 같다.

flowchart TD
    A["유저가 syscall(fd, buffer, size) 호출"] --> B["validate_user_addr(buffer)"]
    B --> C{"addr == NULL?"}
    C -- Yes --> FAIL["exit(-1)"]
    C -- No --> D{"is_user_vaddr(addr)?"}
    D -- No --> FAIL
    D -- Yes --> E{"PML4 walk → 매핑 존재?"}
    E -- Yes, accessible --> OK["주소 사용 허용"]
    E -- No --> F{"SPT/stack growth?"}
    F -- 성공 --> OK
    F -- 실패 --> FAIL

버퍼가 여러 페이지에 걸치면 시작 주소만 검사해서는 각 페이지의 매핑 상태를 알 수 없다. validate_user_buffer()는 페이지 경계를 따라 이동하면서 페이지마다 validate_user_addr()를 호출한다.

각 호출에서 is_user_vaddr()가 범위 필터로 먼저 동작하고, 이후 단계가 해당 페이지의 매핑과 접근 가능성을 확인한다. 이 문서에서는 페이지 단위 반복이 SPT lookup과 stack growth 판단도 페이지 단위로 수행해야 하기 때문이라고 설명한다.

커널 주소가 전달됐을 때의 방어 흐름

유저가 0xFFFF_8000_0000_0000을 buffer로 전달하면 is_user_vaddr(0xFFFF_8000_0000_0000)은 이 주소를 KERN_BASE와 비교한다. 주소가 0x80_0400_0000 이상이므로 결과는 false가 되고, 검증 경로는 exit(-1)로 프로세스를 종료한다.

이 범위 검사가 없다면 PML4 walk에서 커널 매핑을 찾은 뒤 커널 데이터를 유저 버퍼로 복사하는 경로로 이어질 수 있다. PTE의 U/S 비트는 CPL 3인 유저 코드의 커널 페이지 접근을 막지만, CPL 0인 커널 자체의 접근까지 막지는 않는다. 이 문서가 가정하는 SMAP 미사용 PintOS 환경에서 is_user_vaddr()가 필요한 이유다.

QEMU에서 보이는 하드웨어 경계

is_user_vaddr() 자체는 순수한 소프트웨어 비교이므로 QEMU가 별도로 개입하지 않는다. QEMU TCG의 SoftMMU는 guest PTE의 U/S 비트를 이용해 접근 권한을 에뮬레이션한다. guest가 CPL 3일 때 U/S=0인 커널 전용 페이지에 접근하면 pf를 주입하지만, CPL 0에서는 SMAP이 없으면 같은 페이지에 접근할 수 있다.

QEMU SoftMMU 검사CPL 0 (커널)CPL 3 (유저)
U/S=1 (유저 페이지)접근 허용접근 허용
U/S=0 (커널 페이지)접근 허용 (SMAP 없으면)pf 발생

따라서 유저가 syscall 인자로 커널 주소를 넘겼을 때 커널 모드의 접근은 하드웨어 수준에서 성공할 수 있다. 주소를 사용하기 전에 is_user_vaddr()로 차단해야 하는 경계가 여기서 생긴다.

검증 실패 경로는 QEMU GDB로 관찰할 수 있다. 다음 명령은 process_exit에서 종료 상태와 backtrace를 출력하고, syscall_handler에서 syscall 번호와 인자를 확인하도록 구성되어 있다.

; validate_user_addr 실패 시 exit(-1) 호출에 조건부 breakpoint
(gdb) b process_exit
(gdb) commands
  printf "exit status: %d\n", thread_current()->exit_status
  bt 5
  continue
end

; is_user_vaddr 판단 자체를 관찰 — syscall_handler 진입 시 인자 출력
(gdb) b syscall_handler
(gdb) commands
  printf "syscall_no=%ld, arg0=0x%lx, arg1=0x%lx\n", $rdi, $rsi, $rdx
  continue
end

이 문서의 주소 경계를 적용하면 arg0 또는 arg1이 0x80_0400_0000 이상일 때 커널 주소가 인자로 전달된 경우에 해당한다. 그 원인은 악의적인 입력일 수도 있고 유저 프로그램의 버그일 수도 있다.

Linux와 Windows 비교의 범위

다음 비교는 이 문서가 제시한 구현 설명을 기준으로 한다. Linux와 Windows의 모든 버전과 설정에서 동일하다고 일반화하거나, 여기 적힌 수치와 호출 관계가 실제 소스에서 검증되었다는 뜻은 아니다.

이 문서에서 Linux의 대응 개념은 access_ok()다. x86-64 Linux의 유저 공간 상한을 TASK_SIZE_MAX = 0x0000_7FFF_FFFF_F000으로 제시하며, copy_from_user()와 copy_to_user()가 유저 포인터를 다루는 과정에서 access_ok()를 통해 커널 주소를 사전에 거른다고 설명한다. 단순화한 구현은 다음과 같다.

Windows에서는 ProbeForRead()와 ProbeForWrite()가 같은 역할을 하며, 유저 공간 상한은 통상 0x0000_7FFE_FFFF_FFFF이라고 이 문서는 설명한다.

PintOS와 Linux의 차이는 단일 주소를 확인하는지, 주소와 크기로 범위를 확인하는지에서 먼저 드러난다.

항목PintOS is_user_vaddr()Linux access_ok()
검사 대상단일 주소주소 + 크기 범위
오버플로우 방지없음 (별도 NULL 검사)ptr + size 오버플로우 시 자동 실패
상한KERN_BASE (0x80_0400_0000)TASK_SIZE_MAX (0x7FFF_FFFF_F000)
하드웨어 보강없음SMAP/SMEP
호출 빈도매 페이지마다copy_from_user() 진입 시 1회

이 비교에서 PintOS는 페이지마다 범위와 매핑을 확인하고 SPT lookup 또는 stack growth를 판단한다. Linux는 VMA 기반이며 access_ok() 한 번으로 전달된 범위를 검사한다고 설명되어 있다.

SMAP과 SMEP가 보강하는 보호

이 문서에서는 최신 x86-64 CPU의 보강 기능을 다음과 같이 구분한다.

기능CR4 비트효과도입
SMEP (Supervisor Mode Execution Prevention)CR4.SMEP (bit 20)커널 모드에서 유저 페이지의 코드를 실행하면 pfIvy Bridge (2012)
SMAP (Supervisor Mode Access Prevention)CR4.SMAP (bit 21)커널 모드에서 유저 페이지를 읽기/쓰기하면 pfBroadwell (2014)

SMAP이 활성화된 Linux에서는 copy_from_user() 내부에서 stac(Set AC Flag)으로 유저 메모리 접근을 일시적으로 허용하고, 복사 후 clac(Clear AC Flag)으로 보호를 복원한다고 설명한다. 실제 복사에서 page fault가 발생하면 fixup_exception()을 거쳐 -EFAULT를 반환하는 흐름도 함께 제시한다.

PintOS는 CR4를 조작하는 코드가 없고 QEMU의 기본 CPU 모델(qemu64)에서도 해당 기능이 비활성화되어 있어 SMAP/SMEP를 사용하지 않는다고 이 문서는 전제한다. 이 전제에서는 is_user_vaddr()와 뒤따르는 PML4 검사가 소프트웨어 방어 흐름을 이룬다.

두 흐름을 나란히 놓으면 각 단계가 맡는 역할을 확인할 수 있다.

이 문서의 비교 기준에서는 Linux가 access_ok()와 SMAP, page fault fixup을 결합하고, PintOS는 is_user_vaddr()와 PML4 walk를 사용한다. 이는 각 검사가 전체 안전성을 단독으로 보장한다는 뜻이 아니라, 주소 사용까지 이어지는 방어 단계가 서로 다르다는 뜻이다.
