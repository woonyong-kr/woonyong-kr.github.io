Lazy UNINIT Page 복사 (fork SPT copy)

Lazy UNINIT Page 복사 (fork SPT copy)

한 줄 요약: fork로 SPT를 복제할 때 아직 frame이 없는 UNINIT(lazy) 페이지는 물리 복사 없이 init·aux·type 메타데이터만 옮기면 되지만, aux를 얕게 복사하면 부모·자식이 같은 포인터를 공유해 깨질 수 있다.

Lazy UNINIT Page 복사 상태

fork에서 부모의 SPT를 자식에게 복제할 때, UNINIT page는 아직 physical frame을 갖지 않은 “약속만 있는” 페이지다. 이 페이지는 frame을 복사할 필요가 없지만, 약속 자체를 정확히 복제해야 한다. 핵심 난이도는 uninit_page.aux 포인터가 가리키는 보조 데이터의 소유권 처리에 있다 — 얕은 복사(shallow copy)는 부모·자식이 같은 aux를 공유하게 되어, 한쪽이 먼저 fault → init → free(aux)하면 다른 쪽이 dangling pointer를 읽는 버그를 낳는다.

상세 설명

추상 개념 (Demand Paging과 Fork의 교차)

Demand paging 환경에서 fork가 호출되면, 부모의 가상 주소 공간에는 세 종류의 페이지가 섞여 있다:

상태frame 유무복사 전략
Resident (ANON/FILE)있음frame 할당 + memcpy
UNINIT (lazy)없음메타데이터(init, aux, type) 복제
Swapped (evicted)없음swap slot snapshot

UNINIT 페이지는 아직 한 번도 접근되지 않았으므로, 디스크 I/O나 frame 할당 없이 메타데이터만 복사하면 된다. 이 점에서 가장 가벼운 복사 경로다.

실제 OS (Linux)

Linux에서는 fork 시 COW가 기본이므로 lazy page에 해당하는 개념이 약간 다르다. mmap(MAP_PRIVATE)으로 매핑했지만 아직 접근하지 않은 페이지는 VMA(vm_area_struct)만 복제하고 PTE를 만들지 않는다. 자식이 접근하면 자식의 page fault handler가 독립적으로 파일에서 읽어온다. 핵심 원리는 동일하다 — 약속(VMA 메타데이터)만 복사하고, 물리 자원은 접근 시점에 할당.

PintOS 구현

PintOS에서 UNINIT page의 메타데이터는 struct uninit_page에 저장된다:

supplemental_page_table_copy()에서 UNINIT 페이지를 만나면:

  1. 자식 SPT에 같은 VA로 새 page 구조체를 생성한다
  2. uninit_new()로 초기화하되, 부모의 init, type, page_initializer를 그대로 전달한다
  3. aux는 반드시 deep copy해야 한다 — 같은 포인터를 공유하면 안 된다

aux가 가리키는 실제 데이터는 load_segment()에서 할당한 구조체다. 이 구조체에는 file 포인터, offset, read_bytes, zero_bytes 등이 담겨 있다. fork 시 이 구조체를 malloc + memcpy로 독립 복사본을 만들어야 한다.

/* 의사 코드: UNINIT 페이지 복사 */
if (page->operations->type == VM_UNINIT) {
    void *new_aux = malloc(sizeof(struct lazy_load_info));
    memcpy(new_aux, page->uninit.aux, sizeof(struct lazy_load_info));
    vm_alloc_page_with_initializer(
        page->uninit.type,     /* VM_ANON 또는 VM_FILE */
        page->va,
        writable,
        page->uninit.init,     /* lazy_load_segment */
        new_aux                /* deep-copied aux */
    );
}

PintOS 실제 코드: uninit_copy()

PintOS에서 UNINIT page 복사는 uninit_copy() (vm/uninit.c:73)가 담당한다. 이 함수는 page_operations.copy 가상 함수로 등록되어 supplemental_page_table_copy() → copy(dst, src_page) 매크로를 통해 호출된다:

핵심 포인트 3가지:

  1. malloc + memcpy: aux 구조체를 deep copy한다
  2. file_reopen(): file 포인터도 독립 객체로 복제한다 — 부모가 file_close()해도 자식 file이 살아 있다
  3. 실패 시 cleanup: file_reopen 실패 시 malloc한 메모리를 free하고 false 반환

QEMU 에뮬레이션

QEMU는 UNINIT page 복사에 직접 관여하지 않는다 — 이것은 순수 소프트웨어(커널) 로직이다. 다만 GDB로 fork 과정을 디버깅할 때 유용하다:

(gdb) break uninit_copy
(gdb) p src_page->va              # 복사 대상 VA
(gdb) p src_page->uninit.aux      # 부모 aux 주소
(gdb) finish
(gdb) # 자식 SPT에서 같은 VA의 page를 찾아 aux 주소가 다른지 확인

QEMU가 관여하는 시점은 자식이 이 UNINIT page에 처음 접근할 때다: MMU walk → present=0 → pf → uninit_initialize() → lazy_load_segment() → 디스크 I/O. 이 디스크 I/O가 QEMU의 IDE controller model을 통과한다.

aux 얕은 복사의 위험

fork 때 uninit_page.aux를 얕게 복사하면 부모와 자식이 같은 struct lazy_load_arg를 공유한다. 부모가 먼저 page fault를 만나 uninit_initialize()를 실행하고, lazy_load_segment()가 shared aux를 사용한 뒤 free(aux)하면 자식의 uninit.aux는 이미 해제된 주소를 가리키는 dangling pointer가 된다.

%% aux 얕은 복사와 깊은 복사 비교
flowchart LR
  shallow_parent["parent struct page<br/>uninit.aux"]
  shallow_child["child struct page<br/>uninit.aux"]
  shared_aux["shared struct lazy_load_arg<br/>file<br/>ofs<br/>page_read_bytes<br/>page_zero_bytes"]
  deep_parent["parent struct page<br/>uninit.aux"]
  deep_child["child struct page<br/>uninit.aux"]
  parent_aux["parent struct lazy_load_arg<br/>parent 전용 file<br/>parent 전용 offset/read/zero metadata"]
  child_aux["child struct lazy_load_arg<br/>malloc(sizeof(struct lazy_load_arg))<br/>memcpy(temp_aux, src_page-&gt;uninit.aux, sizeof(struct lazy_load_arg))"]
  shallow_parent --> shared_aux
  shallow_child --> shared_aux
  deep_parent --> parent_aux
  deep_child --> child_aux

깊은 복사에서는 parent와 child가 같은 init, type, page_initializer 값을 공유해도 된다. 하지만 aux와 그 안의 file lifetime은 각자 따로 가져야 하므로, 자식 쪽에는 malloc(sizeof(struct lazy_load_arg)), memcpy(temp_aux, src_page->uninit.aux, ...), file_reopen(temp_aux->file)로 만든 독립 복사본을 연결한다.

Lazy UNINIT Page 복사 값 추적

전형적인 fork 시나리오에서 UNINIT 페이지 수:

  • ELF 코드 세그먼트: 수십~수백 페이지 (프로그램 크기에 비례)
  • ELF 데이터 세그먼트: 수 페이지
  • exec 직후 fork하면 대부분의 페이지가 아직 UNINIT → 대부분이 이 경로

aux 구조체 크기: 일반적으로 24~32 bytes (file 포인터 8B + offset 8B + read_bytes 4B + zero_bytes 4B + …)

따라서 UNINIT 100 페이지를 fork해도 추가 메모리는 약 3,200 bytes에 불과하다. frame 할당(페이지당 4 KiB)에 비하면 무시할 수준이다.

aux 얕은 복사 vs 깊은 복사 시나리오

나쁜 구조에서는 child가 parent의 aux 포인터만 복사한다. 이후 parent page fault가 uninit_initialize() → lazy_load_segment(aux) → free(aux) 순서로 shared aux를 해제하면, child page fault 시점에는 child의 uninit_page.aux가 해제된 메모리를 가리킨다.

%% aux 얕은 복사 lifetime
flowchart TD
  parent_page["parent struct page<br/>uninit_page.aux"]
  child_page["child struct page<br/>uninit_page.aux"]
  shared_aux["같은 struct lazy_load_arg 공유"]
  step1["1. fork 시 child는 parent의 aux 포인터만 복사"]
  step2["2. parent page fault"]
  parent_fault["parent fault 경로<br/>uninit_initialize()<br/>lazy_load_segment(aux)<br/>free(aux)"]
  step3["3. child page fault"]
  uaf["child의 uninit_page.aux가 해제된 메모리를 가리킴<br/>dangling pointer, use-after-free 위험"]
  parent_page --> shared_aux
  child_page --> shared_aux
  step1 --> step2
  step2 --> parent_fault
  parent_fault --> step3
  step3 --> uaf

좋은 구조에서는 child 생성 시 malloc(sizeof(struct lazy_load_arg)), memcpy(temp_aux, src_page->uninit.aux, ...), file_reopen(temp_aux->file), vm_alloc_page_with_initializer(type, upage, writable, init, temp_aux) 순서로 독립 aux를 만든다. 이후 parent fault는 parent aux만, child fault는 child aux만 소비하고 해제한다.

%% aux 깊은 복사 lifetime
flowchart TD
  parent_page["parent struct page<br/>uninit_page.aux"]
  parent_aux["parent struct lazy_load_arg<br/>file, ofs, page_read_bytes<br/>page_zero_bytes<br/>file lifetime"]
  child_page["child struct page<br/>uninit_page.aux"]
  child_aux["child struct lazy_load_arg<br/>file, ofs, page_read_bytes<br/>page_zero_bytes<br/>file_reopen()으로 분리"]
  fork_steps["fork 시 child 생성 순서<br/>1. malloc(sizeof(struct lazy_load_arg))<br/>2. memcpy(temp_aux, src_page-&gt;uninit.aux, sizeof(struct lazy_load_arg))"]
  parent_fault["parent fault<br/>uninit_initialize()<br/>lazy_load_segment(parent aux)<br/>free(parent aux)"]
  child_fault["child fault<br/>uninit_initialize()<br/>lazy_load_segment(child aux)<br/>free(child aux)"]
  rule["rule"]
  parent_page --> parent_aux
  child_page --> child_aux
  fork_steps --> child_page
  parent_aux --> parent_fault
  child_aux --> child_fault
  parent_fault --> rule
  child_fault --> rule

판단 기준: init, type, page_initializer는 같은 함수/타입 값을 공유해도 되지만, aux와 aux->file lifetime은 parent와 child가 분리해서 가져야 한다.
