바이트와 명령어 해석

바이트와 명령어 해석

한 줄 요약: RIP가 가리킬 때 x86-64 디코더가 바이트를 명령어로 해석하는 방식 — 같은 바이트도 위치에 따라 코드가 됨.

바이트와 명령어 해석 차이

메모리의 바이트 시퀀스는 그 자체로 의미가 없다. CPU의 RIP가 해당 주소를 가리킬 때, x86-64 디코더가 그 바이트를 명령어로 해석한다. 같은 바이트 48 c7 c7 01 00 00 00이 RIP가 가리키면 mov $0x1, %rdi라는 명령어가 되지만, 데이터 영역에 있으면 그냥 7바이트 정수(0x000001c7c748)일 뿐이다. GDB의 x/i(instruction) 포맷과 x/x(hex) 포맷을 전환하면 이 차이를 직접 확인할 수 있다.

상세 설명

추상 개념 (x86-64 명령어 인코딩)

x86-64는 **가변 길이 명령어 집합(Variable-Length ISA)**이다. 한 명령어가 1바이트에서 15바이트까지 될 수 있다. CPU의 fetch 단계에서 RIP가 가리키는 주소부터 바이트를 읽고, 디코더가 prefix → opcode → ModR/M → SIB → displacement → immediate 순으로 파싱하여 명령어 경계를 결정한다.

필드크기예시
REX prefix0~1 byte48 = REX.W (64비트 피연산자)
Opcode1~3 bytesc7 = MOV imm32 to r/m
ModR/M0~1 bytec7 = mod=11 reg=000 r/m=111 → %rdi
Immediate0~8 bytes01 00 00 00 = 0x00000001

핵심: instruction fetch는 RIP에서 시작한다. 다만 RIP가 가리키기만 하면 충분한 것은 아니며, 해당 가상 주소가 present이고 현재 privilege에서 executable이어야 한다(NX 등 권한 검사 포함). 같은 물리적 바이트도 fetch 경로에서는 명령어로 디코딩되고, data load 경로에서는 정수·포인터·문자열의 바이트로 읽힌다.

x86-64 명령어 바이트 해석 예제

PintOS에서 실제로 만나는 명령어 패턴들:

syscall 명령어가 단 2바이트(0f 05)라는 점은 중요하다. QEMU TCG는 이를 target별 translator와 helper 경로로 구현하지만 helper 이름과 호출 단계는 QEMU version에 따라 달라질 수 있다. 현재 checkout에서 rg 'gen.*syscall|helper.*syscall' target/i386와 trace로 확인한다.

GDB에서 같은 바이트를 다르게 보기

(gdb) x/7bx 0x80042100        ← 바이트 단위로 보기
0x80042100: 0x48  0xc7  0xc7  0x01  0x00  0x00  0x00

(gdb) x/1i 0x80042100         ← 명령어로 보기
0x80042100: mov    $0x1,%rdi

(gdb) x/1gx 0x80042100        ← 8바이트 정수로 보기
0x80042100: ...                ← 명령어 7바이트 + 다음 바이트까지 읽음

x/7bx와 x/1i는 같은 7바이트 명령어 범위를 각각 raw byte와 instruction으로 본다. x/1gx의 giant word는 8바이트 단위이므로 다음 명령어의 첫 바이트까지 포함한다. 따라서 8번째 바이트를 확인하지 않고 정수값을 고정해서는 안 된다.

syscall_entry의 실제 바이트

PintOS syscall_entry(userprog/syscall-entry.S)의 첫 몇 줄을 바이트로 보면:

처음 17바이트가 3개의 명령어를 인코딩한다. CPU는 RIP를 기준으로 각 명령어의 끝을 파악하고 다음 명령어로 넘어간다. 만약 RIP가 두 번째 바이트(89)를 가리킨다면, 전혀 다른 명령어(mov)로 해석될 수 있다 — 이것이 “alignment 문제”다.

PintOS에서 바이트→명령어 해석이 중요한 순간

1. Page Fault 디버깅

page fault가 발생하면 f->rip에 fault를 일으킨 명령어 주소가 담긴다. 이 주소의 바이트를 명령어로 해석해야 “어떤 메모리 접근이 실패했는가”를 알 수 있다.

(gdb) p/x f->rip
$1 = 0x804a100

(gdb) x/1i 0x804a100
0x804a100: mov    (%rax),%rdx     ← RAX가 가리키는 주소를 읽다 실패

(gdb) p/x $rax
$2 = 0x0                          ← NULL 포인터 역참조!

2. 스택 프레임 추적 (backtrace)

bt 명령어는 스택의 return address를 명령어 주소로 해석하여 call chain을 보여준다. 스택이 깨지면 return address가 엉뚱한 바이트를 가리키고, x/i로 보면 의미 없는 명령어가 나온다 — 이것이 “stack corruption” 증상이다.

3. QEMU TCG Translation Block

QEMU의 TCG는 guest 코드 영역의 바이트를 읽어서 IR(Intermediate Representation)로 번역하고, 이를 호스트 코드로 컴파일한다. TCG가 바이트를 명령어로 해석하는 과정이 disas_insn()이다. 잘못된 RIP로 점프하면 TCG가 유효하지 않은 바이트를 디코딩하다 실패한다.

실제 OS (Linux)

Linux에서도 동일한 원리가 적용된다:

상황바이트→명령어 해석
objdump -d vmlinuxELF text section의 바이트를 명령어로 디스어셈블
perf recordIP(Instruction Pointer) 샘플의 바이트를 명령어로 매핑
kprobes타겟 주소의 첫 바이트를 int3(0xCC)로 교체하여 브레이크포인트 설정
dmesg + decode_stacktrace.shoops 메시지의 Code: 바이트를 명령어로 표시

Linux 커널 oops 메시지의 Code: 줄이 바로 바이트→명령어 해석의 전형적 예다:

Code: 48 89 e5 48 83 ec 10 48 8b 45 f8 48 8b 00 <48> 8b 00 ...

<48>이 fault 지점이고, 이후 바이트를 명령어로 디코딩하면 mov (%rax),%rax — RAX가 가리키는 주소의 접근 실패.

QEMU 에뮬레이션

QEMU TCG의 바이트→명령어 디코딩 개념 흐름(구체 함수명은 version별 확인):

1. RIP 주소에서 instruction fetch와 권한 검사를 수행

2. x86 translator가 prefix·opcode·피연산자를 파싱
   → prefix 판별 → opcode 판별 → 피연산자 파싱

3. target 동작을 TCG IR/helper 호출로 변환

4. Translation Block(TB)에 저장
   → 같은 주소를 다시 실행하면 TB 캐시에서 바로 실행

TB 캐시 무효화가 일어나는 경우: self-modifying code, CR3 변경, tb_flush() 호출.

바이트와 명령어 해석 값 추적

x86-64 명령어 길이 범위:
  최소: 1 byte (ret = 0xc3, hlt = 0xf4, nop = 0x90)
  최대: 15 bytes (prefix + opcode + ModR/M + SIB + disp32 + imm32)
  평균: ~4.5 bytes (일반적 x86-64 코드)

PintOS 커널 코드 크기 (대략):
  .text section ≈ 80~120 KB
  → 약 18,000~27,000개 명령어 (평균 4.5 bytes 가정)

QEMU TCG Translation Block:
  크기·종료 조건은 version과 build에 따라 달라짐
  → 현재 checkout의 translator 상수와 trace로 측정

syscall 명령어 바이트:
  0f 05 = 2 bytes
  이 2바이트가 user→kernel 전체 전환을 촉발

iretq 명령어 바이트:
  architecture primary opcode = cf
  현재 x86-64 assembler/object 출력 = 48 cf
  → 소스 표기만으로 단정하지 않고 object disassembly로 확인
