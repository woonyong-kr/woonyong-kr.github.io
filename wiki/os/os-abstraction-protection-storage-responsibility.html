OS 추상화, 보호, 저장 책임

확인 범위: 이 문서는 OS의 추상화·보호·저장 책임에 관한 일반 원리와 Linux·Windows·PintOS·QEMU의 역할을 개념적으로 비교한다. 제시된 코드 좌표, 주소·섹터 수치, GDB 명령과 동작 경로는 특정 구현·버전에 대한 실제 실행이나 성능 측정 결과가 아니므로, 적용 여부와 영속성·원자성 같은 판단은 대상 소스와 버전 및 실행 기록으로 별도 검증해야 한다.

한 줄 요약: 운영체제의 세 기둥 — 추상화·보호·저장 책임으로 OS의 핵심 역할을 요약.

OS 추상화, 보호, 저장 책임 변화

운영체제의 핵심 책임은 세 기둥으로 요약된다. 추상화(Abstraction)는 하드웨어의 복잡함을 프로그래머가 다룰 수 있는 인터페이스로 감싼다. 보호(Protection)는 프로그램이 서로의 메모리나 하드웨어를 함부로 건드리지 못하게 막는다. 저장소 계약(Storage Contract)은 데이터가 언제 영속적으로 기록되는지의 규칙을 정한다. 이 세 가지가 없으면 다중 프로그램 실행, 보안, 데이터 안전성 모두 보장할 수 없다.

상세 설명

추상 개념 (하드웨어 수준)

하드웨어는 거칠다. RAM은 물리 주소와 바이트 단위로 움직이고, 디스크는 섹터(보통 512 B) 단위로 읽고 쓰며, CPU는 권한 비트가 맞으면 어떤 명령어든 실행한다. 이 세 장치를 직접 다루는 프로그램은 모든 물리 주소를 외워야 하고, 섹터 오프셋을 직접 계산해야 하며, 실수로 다른 프로그램의 메모리를 덮어쓸 위험을 항상 감수해야 한다.

OS가 끼어드는 이유는 이 복잡함을 줄이고, 동시에 프로그램 간 격리를 강제하기 위해서다.

하드웨어 원소재OS가 제공하는 추상화보호가 필요한 이유
물리 RAM 주소가상 주소 공간프로세스 A가 B의 메모리를 읽으면 안 됨
디스크 섹터파일, 디렉터리, 오프셋파일 시스템 메타데이터가 깨지면 모든 파일 손실
CPU 명령어프로세스, 스레드, syscallhlt 같은 명령을 유저가 실행하면 시스템 정지

실제 OS (Linux/Windows)

Linux:

  • 추상화: VFS(Virtual File System)가 ext4, NFS, procfs를 모두 같은 open/read/write/close 인터페이스로 감싼다. 가상 메모리는 vm_area_struct로 프로세스별 주소 공간을 관리한다.
  • 보호: 커널 모드(ring 0)와 유저 모드(ring 3) 분리, 페이지 테이블의 user/supervisor 비트, seccomp으로 syscall 필터링.
  • 저장소: 페이지 캐시가 write()를 버퍼링하고, fsync()가 디스크 flush를 보장한다. ext4 저널링이 메타데이터 원자성을 제공한다.

Windows:

  • 추상화: Object Manager가 파일, 프로세스, 스레드, 레지스트리 키를 모두 handle로 관리한다. Memory Manager가 가상 주소 공간을 제공한다.
  • 보호: ACL(Access Control List) 기반 보안 모델. 커널/유저 분리는 동일하게 CPU ring에 의존한다.
  • 저장소: NTFS 저널링, FlushFileBuffers()가 fsync에 해당한다.

공통점: 두 OS 모두 CPU 하드웨어의 ring protection과 MMU page table을 보호의 기반으로 쓴다. 추상화 인터페이스의 이름은 다르지만, 해결하는 문제는 같다.

PintOS 구현

PintOS는 실제 OS의 세 기둥을 교육용으로 단순화한다.

추상화:

  • 가상 메모리: struct supplemental_page_table과 pml4로 프로세스별 주소 공간을 제공한다. 단, 프로세스 간 공유 메모리는 지원하지 않는다.
  • 파일 시스템: 단일 디렉터리, 파일 확장 없음(프로젝트 4 이전), struct inode와 struct file로 파일을 추상화한다.
  • 프로세스/스레드: struct thread가 프로세스와 스레드 역할을 겸한다. 멀티스레드 유저 프로세스는 지원하지 않는다.

보호:

  • 커널/유저 모드 분리: x86-64 CPL 0/3을 그대로 사용한다.
  • 유저 포인터 검증: is_user_vaddr(), pml4_get_page(), 또는 page fault 기반 검증으로 커널이 유저 주소를 확인한다.
  • 시스템 콜 경계: syscall 명령 → LSTAR MSR → syscall_handler()가 유일한 진입점이다.

저장소:

  • PintOS 기본 파일 시스템은 저널링이 없다. fsync도 기본 구현에서는 no-op이다.
  • 프로젝트 4(filesys)에서 버퍼 캐시와 디렉터리 확장을 구현할 수 있다.
  • 디스크 I/O는 disk_read()/disk_write()가 QEMU IDE 장치와 통신한다.

QEMU 에뮬레이션

QEMU는 세 기둥 중 어느 것도 “정책”으로 제공하지 않는다. QEMU는 하드웨어를 흉내낼 뿐이다.

  • 추상화: QEMU는 파일 시스템도 프로세스도 모른다. guest OS가 추상화를 제공한다.
  • 보호: QEMU는 CPL 비트, PTE user 비트, CR0 보호 모드 등 CPU 하드웨어 보호 메커니즘을 에뮬레이션한다. 하지만 “어떤 프로세스가 어떤 자원에 접근해도 되는가”라는 정책은 guest OS의 몫이다.
  • 저장소: QEMU BlockBackend은 guest의 disk_write() 요청을 호스트 파일 I/O로 변환한다. fsync 보장이나 저널링은 guest OS가 결정한다.

구분의 핵심: QEMU는 메커니즘(하드웨어 동작)을 재현하고, PintOS는 그 메커니즘 위에 정책(추상화, 보호, 영속성 규칙)을 세운다.

OS 추상화, 보호, 저장 책임 값 추적

보호 경계의 구체적 수치

KERN_BASE = 0x8004000000

유저 주소 범위: 0x0 ~ 0x8003FFFFFF  (약 512 GB)
커널 주소 범위: 0x8004000000 ~       (그 이상)

is_user_vaddr(0x400000) = true   (코드 영역)
is_user_vaddr(0x47480000) = true (USER_STACK 바로 아래)
is_user_vaddr(0x8004000000) = false (커널 시작)

디스크 추상화의 수치

물리 섹터 크기 = 512 바이트
PintOS BLOCK_SECTOR_SIZE = 512
파일의 논리적 offset 100을 읽으려면:
  sector = 100 / 512 = sector 0
  sector 내 offset = 100 % 512 = 100

유저는 read(fd, buf, 10)으로 바이트 단위 접근을 하지만, OS는 내부적으로 섹터 단위로 디스크에 요청한다.
