ELF 로더는 파일을 어떻게 실행 중인 메모리로 바꾸는가

확인 범위: 이 문서는 ELF 로더의 일반적인 역할과 파일 offset·가상 주소·페이지 경계를 해석하는 원리를 설명하고, 제시된 PintOS 코드베이스와 args-none 사례를 통해 구현 방식을 구체화한다. 코드 좌표·버전별 동작·GDB 관찰 결과·메모리 사용량 등 실제 구현이나 실행에 의존하는 판단은 본문의 코드와 명령을 해당 환경에서 직접 확인해야 하며, 제시된 스크립트와 시나리오는 그 자체로 검증 완료된 실행 기록이나 성능 측정 결과를 뜻하지 않는다.

한 줄 요약: 디스크의 실행 파일이 exec() 호출을 거쳐 CPU가 실행할 수 있는 코드로 바뀌는 ELF 로더의 적재 과정을 살펴본다.

ELF 로더 시작

exec("args-none")를 호출하면 디스크에 있던 실행 파일은 어떤 과정을 거쳐 CPU가 실행할 수 있는 코드가 될까?

처음에는 단순히 “프로그램 파일을 메모리에 복사한다”고 생각하기 쉽다. 그러나 운영체제가 실제로 처리해야 할 일은 단순 복사보다 구체적이다.

  • 파일에서 읽을 바이트의 범위를 정한다.
  • 그 바이트를 어느 유저 가상 주소에 배치할지 정한다.
  • 파일에서 읽을 부분과 0으로 채울 부분을 구분한다.
  • 코드 페이지에는 읽기·실행 권한을, 데이터 페이지에는 쓰기 권한을 부여하는 식으로 접근 권한을 정한다.
  • 마지막으로 CPU가 처음 실행할 RIP와 유저 스택 RSP를 정한다.

이러한 작업을 담당하는 코드가 로더(loader)다. PintOS에서는 userprog/process.c의 load()가 이 역할을 맡는다.

ELF 로더 구분

실행 파일은 이미 실행 중인 프로그램이 아니라 디스크에 저장된 바이트 묶음이다.

운영체제는 이 바이트 묶음을 읽고 다음 질문에 답해야 한다.

이 파일은 진짜 실행 파일인가?
어느 CPU용 파일인가?
어느 구간을 메모리에 올려야 하는가?
각 구간은 유저 가상 주소 어디에 보여야 하는가?
파일에는 없지만 실행 중에는 0으로 존재해야 하는 영역은 어디인가?
첫 명령어 주소는 어디인가?

이 질문에 답하지 못하면 CPU는 파일의 바이트를 명령어로 실행할 수 없다. 따라서 로더는 파일 형식의 약속을 프로세스 주소 공간의 약속으로 바꾸는 코드라고 할 수 있다.

ELF 로더 흐름

ELF를 처음 살펴볼 때는 섹션(section)보다 프로그램 헤더(program header)를 먼저 이해하는 편이 좋다.

PintOS 로더가 실행 과정에서 직접 사용하는 핵심 구조는 다음 두 가지다.

ELF header
  - 이 파일이 ELF인지
  - 64비트 x86-64용인지
  - entry point가 어디인지
  - program header table이 파일 어디에 있는지

Program header
  - 파일 offset 몇 번부터
  - 유저 가상 주소 몇 번에
  - 파일에서 몇 바이트를 읽고
  - 메모리에는 총 몇 바이트를 만들지
  - 쓰기 가능한지

전체 흐름은 다음과 같다.

flowchart TD
    A[exec → process_exec] --> B[load]
    B --> C[pml4_create + process_activate]
    C --> D[filesys_open → file_read ELF header]
    D --> E{magic/class/machine 검증}
    E -- 실패 --> F[return false]
    E -- 통과 --> G[program header 반복]
    G --> H{p_type == PT_LOAD?}
    H -- No --> G
    H -- Yes --> I[validate_segment]
    I --> J[load_segment: 페이지 단위 반복]
    J --> K[palloc_get_page PAL_USER]
    K --> L[file_read + memset 0]
    L --> M[install_page → pml4_set_page]
    M --> G
    G -- 모든 phdr 처리 --> N[setup_stack]
    N --> O["if_->rip = e_entry, if_->rsp = USER_STACK"]

여기서 핵심은 “파일 offset”과 “유저 가상 주소”가 서로 다른 번호라는 점이다.

file offset = 실행 파일 안에서 몇 번째 바이트인가
virtual address = 유저 프로세스가 실행 중에 볼 주소는 몇 번인가

로더는 서로 다른 이 두 주소 체계를 연결한다.

PintOS 테스트 바이너리 중 args-none을 보자

구체적인 적재 과정을 이해하기 위해 PintOS 테스트 바이너리 가운데 args-none을 살펴보자.

로컬에서 file로 파일 정보를 확인하면 다음과 같은 결과가 나온다.

args-none: ELF 64-bit LSB executable, x86-64, statically linked

이어서 objdump -f -p로 프로그램 헤더를 확인하면 대표적인 LOAD 항목을 다음과 같이 볼 수 있다.

LOAD off 0x0000000000001000 vaddr 0x0000000000400000 align 2**12
     filesz 0x0000000000004ef0 memsz 0x0000000000004ef0 flags r-x

이 내용을 로더의 관점에서 풀어 쓰면 다음과 같다.

파일의 0x1000 위치부터 0x4ef0 바이트를 읽어라.
그 내용이 유저 가상 주소 0x400000부터 보이게 하라.
이 구간은 읽기/실행 가능하고, 쓰기 가능하지 않다.
정렬 단위는 2**12 = 4096B = 0x1000이다.

다만 이 코드베이스의 PintOS는 PF_W만 확인해 writable을 정한다. 즉, ELF flag의 r-x 전체를 실제 운영체제처럼 세밀하게 적용하지는 않는다. 과제용 로더에서는 “쓰기 가능한가?”라는 조건만 page table 권한에 반영한다고 이해하면 된다.

CPU는 디스크의 0x1000 위치를 직접 실행하지 않는다. 대신 나중에 유저 가상 주소 0x400000 근처에서 명령어를 가져온다. 이 주소가 실제 프레임으로 번역되도록 page table을 구성하는 것이 로더의 핵심이다.

실제 운영체제

Linux에서는 execve() 계열 호출이 새 프로그램 이미지를 만든다. ELF 실행 파일의 경우 커널 로더가 program header를 읽고 코드·데이터·스택·mmap 영역을 포함한 프로세스 주소 공간을 구성한다.

실제 Linux는 PintOS보다 훨씬 많은 문제를 처리한다.

  • 동적 링커와 shared library
  • ASLR(address space layout randomization)
  • demand paging
  • copy-on-write
  • 파일-backed mapping
  • 권한, 보안 정책, credential 변화
  • 스레드와 signal 상태 정리

Windows는 ELF 대신 PE/COFF 형식의 실행 파일을 사용한다. 사용자는 일반적으로 CreateProcess 같은 Win32 API를 호출하며, 내부에서는 Windows loader가 image section, DLL, import table, relocation 등을 처리한다.

두 운영체제의 공통점은 분명하다. 실행 파일을 단순히 복사하는 것이 아니라 파일 형식의 메타데이터를 읽어 새 프로세스 주소 공간과 최초 실행 상태를 만든다.

PintOS

  • PintOS 저장소 상대 경로 pintos/userprog/process.c
    • process_exec
    • load
    • validate_segment
    • load_segment
    • setup_stack
    • install_page
  • PintOS 저장소 상대 경로 pintos/threads/mmu.c
    • pml4_set_page
  • PintOS 저장소 상대 경로 pintos/include/threads/vaddr.h
    • PGSIZE

PintOS의 load()는 현재 스레드에 사용할 새 PML4를 만들고 활성화한다.

t->pml4 = pml4_create()
process_activate(t)

그런 다음 실행 파일을 열고 ELF header를 읽는다.

filesys_open(argv[0])
file_read(file, &ehdr, sizeof ehdr)

검증 조건은 다음처럼 비교적 직접적이다.

magic      = 0x7f 'E' 'L' 'F'
class      = 64-bit
endian     = little-endian
type       = executable
machine    = x86-64
phentsize  = sizeof(struct Phdr)
phnum      <= 1024

검증을 통과하면 program header를 하나씩 읽는다. PintOS가 실제로 메모리에 적재하는 대상은 PT_LOAD segment다.

PT_LOAD
  -> validate_segment()
  -> file_page, mem_page, page_offset 계산
  -> read_bytes, zero_bytes 계산
  -> load_segment()

load_segment()는 이 작업을 페이지 단위로 반복한다.

한 페이지에 대해:
  page_read_bytes = min(read_bytes, PGSIZE)
  page_zero_bytes = PGSIZE - page_read_bytes
  kpage = palloc_get_page(PAL_USER)
  file_read(file, kpage, page_read_bytes)
  memset(kpage + page_read_bytes, 0, page_zero_bytes)
  install_page(upage, kpage, writable)

install_page()는 같은 유저 가상 페이지가 이미 매핑되어 있는지 확인한 뒤 pml4_set_page()를 호출한다.

결국 ELF 로더가 만드는 최종 결과는 단순한 “파일 바이트”가 아니라 유저 가상 페이지에서 물리 프레임으로 이어지는 page table mapping이다.

QEMU

QEMU는 PintOS 유저 프로그램의 ELF 의미를 해석하지 않는다.

args-none 같은 guest user executable은 PintOS 파일 시스템 안에 저장된 파일이다. QEMU가 이 파일의 program header를 읽어 RIP를 정하는 것은 아니다. 이 작업은 guest OS인 PintOS의 load()가 담당한다.

QEMU의 역할은 그보다 아래 계층에 있다.

PintOS file_read()
  -> PintOS filesys / inode / disk layer
  -> guest가 디스크 장치에 접근
  -> QEMU 장치 모델이 I/O를 처리
  -> PintOS가 받은 바이트를 guest memory에 복사
  -> PintOS가 page table entry를 guest memory에 기록
  -> guest CPU가 나중에 그 page table을 따라 instruction fetch

QEMU 코드에서 이 관점과 연결되는 위치는 다음과 같다.

  • system/physmem.c
    • address_space_read_full
    • address_space_write
    • address_space_rw
  • system/memory.c
    • memory_region_dispatch_read
    • memory_region_dispatch_write
  • include/system/memory.h
    • address_space_rw 선언과 설명

QEMU에도 ELF 관련 타입과 로더 코드가 있지만, 이는 QEMU가 특정 machine의 kernel image 등을 직접 적재할 때 사용하는 경로와 연결된다. PintOS 안에서 exec()로 실행되는 유저 프로그램 ELF는 QEMU가 아니라 PintOS가 해석한다.

ELF 로더 코드

PintOS의 ELF header 구조는 process.c에 직접 정의되어 있다.

struct ELF64_hdr {
    unsigned char e_ident[EI_NIDENT];
    uint16_t e_type;
    uint16_t e_machine;
    uint32_t e_version;
    uint64_t e_entry;
    uint64_t e_phoff;
    ...
};

Program header 역시 같은 파일에 정의되어 있다.

struct ELF64_PHDR {
    uint32_t p_type;
    uint32_t p_flags;
    uint64_t p_offset;
    uint64_t p_vaddr;
    uint64_t p_filesz;
    uint64_t p_memsz;
    ...
};

load()가 ELF header를 검증하는 조건은 다음과 같은 의미를 지닌다.

memcmp(ehdr.e_ident, "\177ELF\2\1\1", 7)
ehdr.e_type != 2
ehdr.e_machine != 0x3E
ehdr.e_phentsize != sizeof(struct Phdr)

이 코드는 PintOS가 파일이 x86-64용 ELF executable인지 직접 검사한다는 근거다.

PT_LOAD에서 핵심 값을 계산하는 부분은 다음과 같다.

file_page = phdr.p_offset & ~PGMASK;
mem_page = phdr.p_vaddr & ~PGMASK;
page_offset = phdr.p_vaddr & PGMASK;
read_bytes = page_offset + phdr.p_filesz;
zero_bytes = ROUND_UP(page_offset + phdr.p_memsz, PGSIZE) - read_bytes;

load_segment()는 파일의 바이트를 읽고 나머지를 0으로 채운 뒤 유저 페이지에 설치한다.

file_read(file, kpage, page_read_bytes);
memset(kpage + page_read_bytes, 0, page_zero_bytes);
install_page(upage, kpage, writable);

마지막으로 page table을 연결하는 코드는 pml4_set_page()다.

*pte = vtop(kpage) | PTE_P | (rw ? PTE_W : 0) | PTE_U;

이 코드는 다음 세 가지를 의미한다.

  • vtop(kpage): 커널 가상 주소로 보이는 frame을 page table entry에 기록할 물리 주소로 변환한다.
  • PTE_P: present, 즉 현재 매핑되어 있음을 표시한다.
  • PTE_W, PTE_U: 각각 쓰기 가능 여부와 유저 접근 가능 여부를 표시한다.

ELF 로더 값 추적

이제 구체적인 숫자를 대입해 보자.

args-none의 한 LOAD segment가 다음과 같다고 가정한다.

off    = 0x1000
vaddr  = 0x400000
filesz = 0x4ef0
memsz  = 0x4ef0
flags  = r-x

PintOS의 계산 결과는 다음과 같다.

PGSIZE      = 0x1000
PGMASK      = 0xfff

file_page   = 0x1000 & ~0xfff = 0x1000
mem_page    = 0x400000 & ~0xfff = 0x400000
page_offset = 0x400000 & 0xfff = 0x0

read_bytes  = 0x0 + 0x4ef0 = 0x4ef0
zero_bytes  = ROUND_UP(0x4ef0, 0x1000) - 0x4ef0
            = 0x5000 - 0x4ef0
            = 0x110

따라서 이 segment는 유저 가상 주소 0x400000부터 총 0x5000 바이트, 즉 5페이지를 차지한다.

page 0: VA 0x400000, 파일에서 0x1000부터 0x1000 바이트 읽음
page 1: VA 0x401000, 파일에서 다음 0x1000 바이트 읽음
page 2: VA 0x402000, 파일에서 다음 0x1000 바이트 읽음
page 3: VA 0x403000, 파일에서 다음 0x1000 바이트 읽음
page 4: VA 0x404000, 파일에서 0xef0 바이트 읽고 마지막 0x110 바이트는 0

여기서 기억할 점은 페이지 경계 때문에 “파일 크기”와 “메모리 크기”가 달라질 수 있다는 것이다.

이번에는 파일에는 데이터가 없지만 메모리에서는 0으로 초기화해야 하는 segment를 살펴보자.

off    = 0x0f00
vaddr  = 0x405f00
filesz = 0x0
memsz  = 0x524
flags  = rw-

PintOS의 계산 결과는 다음과 같다.

file_page   = 0x0f00 & ~0xfff = 0x0
mem_page    = 0x405f00 & ~0xfff = 0x405000
page_offset = 0x405f00 & 0xfff = 0xf00

read_bytes  = 0
zero_bytes  = ROUND_UP(0xf00 + 0x524, 0x1000)
            = ROUND_UP(0x1424, 0x1000)
            = 0x2000

이 segment는 0x405000부터 2페이지를 만들고 그 내부를 0으로 채운다. 실제로 의미 있는 영역은 0x405f00부터 0x524 바이트이지만, page table은 페이지 단위로 매핑되기 때문이다.
