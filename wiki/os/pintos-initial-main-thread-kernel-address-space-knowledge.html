PintOS 초기 main thread와 커널 주소 공간

PintOS 초기 main thread와 커널 주소 공간

한 줄 요약: PintOS의 main()이 호출될 때는 start.S가 임시 page table을 구성하고 paging을 이미 활성화한 상태다. 따라서 “가상 메모리가 없다”고 말하는 것은 정확하지 않다. 이 시점에 아직 없는 것은 SPT·demand paging·eviction으로 구성되는 유저 프로세스용 VM subsystem이다.

PintOS 초기 main thread의 역할과 차이

PintOS의 main()이 호출되는 시점에 “가상 메모리가 전혀 없다”고 보는 것은 잘못이다. start.S가 임시 page table을 구성하고 paging을 활성화한 뒤 main()을 호출하므로, 하드웨어 paging은 이미 활성화되어 있다. 다만 유저 프로세스용 VM subsystem인 SPT, demand paging, frame eviction은 아직 준비되지 않았다. main thread는 “운영체제 전체 메모리의 소유자”가 아니라 커널 초기화를 수행하는 최초의 실행 단위다.

상세 설명

추상 개념: CPU/MMU의 하드웨어 규칙

x86-64 CPU가 부팅 직후 long mode로 전환하려면 다음 두 조건이 필요하다.

  • CR3에 유효한 PML4의 물리 주소를 넣는다.
  • CR0.PG를 설정해 paging을 활성화한다.

그 뒤 CPU가 수행하는 모든 메모리 접근은 page table walk를 거친다. 물리 주소를 직접 사용하는 단계와 가상 주소를 사용하는 단계의 경계는 CR0.PG = 1이 되는 순간이다.

여기서 “가상 메모리”라는 표현은 다음 두 계층으로 나누어 이해해야 한다.

단계의미제공 주체
하드웨어 pagingCR3와 page table을 이용한 VA→PA 변환CPU/MMU
OS VM subsystempage fault, lazy loading, SPT, swap, eviction 정책OS 커널 코드

PintOS의 main()은 하드웨어 paging이 활성화된 환경에서 실행된다. 반면 VM subsystem은 부팅 과정의 훨씬 뒤에서 의미를 갖는다.

실제 OS와 비교: Linux와 Windows

Linux와 Windows도 부팅 초기에는 boot CPU가 임시 stack과 임시 page table을 사용한다.

항목LinuxWindows
초기 page tableearly_top_pgt → 정식 init_mm.pgd 전환HAL 초기 매핑 → 정식 PDE 전환
첫 실행 흐름start_kernel() → swapper(PID 0) → init(PID 1)KiSystemStartup() → System process
커널 스택per-CPU boot stack(16KB+), KASLR 적용 가능per-CPU ISR stack
SMPboot CPU가 AP를 start_secondary()로 깨움KeStartAllProcessors()
KPTI유저/커널 page table 분리(Meltdown 대응)KVA Shadow

세 운영체제의 핵심 모델은 같다. 커널은 먼저 실행에 필요한 최소한의 stack과 page table을 확보한 뒤 allocator, scheduler, VM subsystem을 차례로 초기화한다.

PintOS 구현 흐름

PintOS의 부팅 과정은 다음 네 단계로 나누어 추적할 수 있다.

%% PintOS 부팅 4단계 주소 체계 전환
flowchart LR
  loader["1. loader.S<br/>물리 주소 중심<br/>kernel image -&gt; RAM 복사<br/>PintOS allocator 없음"]
  start["2. start.S<br/>boot_pml4e -&gt; CR3<br/>CR0.PG = 1<br/>RSP = KERN_BASE + 0x1000"]
  main["3. main() 초반<br/>임시 kernel VA mapping<br/>thread_init()<br/>현재 RSP page를 initial_thread로 등록"]
  alloc["thread_init() 반환 뒤<br/>palloc_init(mem_end)<br/>malloc_init()"]
  paging["4. paging_init()<br/>base_pml4 direct map 구성<br/>정식 kernel address space 활성화"]
  loader --> start --> main --> alloc --> paging
단계주소 체계메모리 관리 상태핵심 파일
1. BIOS/loader물리 주소 중심PintOS allocator 없음loader.S
2. start.S임시 page table(boot_pml4e)allocator 없음start.S
3. main() 초반임시 kernel VA mappingthread/palloc/malloc 준비 중init.c
4. paging_init() 이후base_pml4 기반 direct mappage allocator와 kernel heap 사용 가능init.c, mmu.c

main thread가 등록되는 과정은 다음과 같다.

sequenceDiagram
  participant S as start.S (entry_64)
  participant M as main()
  participant T as thread_init()
  participant P as paging_init()
  S->>S: RSP = LOADER_KERN_BASE + 0x1000
  S->>M: call *%rax
  M->>M: bss_init(), read_command_line()
  M->>T: thread_init()
  T->>T: RSP를 pg_round_down()
  T->>T: initial_thread = running_thread()
  T->>T: init_thread(initial_thread, "main", PRI_DEFAULT)
  T->>T: initial_thread->status = THREAD_RUNNING
  T-->>M: return
  M->>M: palloc_init(mem_end), malloc_init()
  M->>P: paging_init(mem_end)
  P->>P: base_pml4 direct map 구성
  P->>P: pml4_activate(0)로 CR3 교체

자주 혼동하는 지점을 질문과 답으로 정리하면 다음과 같다.

질문답
main() 시점에 가상 메모리가 없는가?아니다. start.S가 임시 page table을 사용해 paging을 이미 활성화했다.
user VM은 있는가?없다. pml4, SPT, lazy loading 계층은 아직 준비되지 않았다.
main thread가 커널 메모리를 관리하는가?아니다. main thread는 초기화 코드를 실행하는 실행 단위일 뿐이다.
새 kernel thread는 별도 주소 공간을 받는가?아니다. 새 4KB page(struct thread + kernel stack)를 받지만 커널 공통 주소 공간은 공유한다.
새 user process는 별도 주소 공간을 받는가?그렇다. pml4_create()로 새 PML4를 만들고 user page mapping을 추가한다.

paging_init(mem_end)는 palloc_get_page()를 이용해 base_pml4를 확보한다. 이어서 물리 주소 범위 [0, mem_end)를 커널 가상 주소 범위 [KERN_BASE, KERN_BASE + mem_end)에 direct map하고, pml4_activate(0)으로 CR3를 교체한다.

QEMU 에뮬레이션의 경계

QEMU는 PintOS에서 정의한 “main thread”, “initial_thread”, “palloc”의 의미를 해석하지 않는다. QEMU가 재현하는 대상은 guest CPU에서 발생하는 하드웨어 수준의 효과다.

PintOS가 하는 일QEMU가 하는 일
start.S가 boot_pml4e를 CR3에 넣음helper_write_crN()으로 guest CR3 갱신
CR0.PG를 켜서 paging 활성화guest CPU state에 PG 비트를 반영하고 이후 VA→PA walk를 재현
thread_init()으로 initial_thread 등록guest instruction의 효과만 재현하며 struct thread의 의미는 알지 못함
paging_init()으로 base_pml4 구성guest가 사용하는 memory 바이트를 제공
process_activate()로 CR3 교체guest의 mov %cr3 효과를 재현

4KB thread page 메모리 배치

%% PintOS 초기 main thread 4KB page 레이아웃
flowchart TD
  top["0x8004001000<br/>RSP 시작 · kernel stack top"]
  stack["kernel stack<br/>return address · 저장 register · 지역변수<br/>높은 주소에서 낮은 주소로 성장"]
  thread["0x8004000000<br/>initial_thread<br/>struct thread · 약 200+ bytes"]
  top --> stack --> thread

struct thread이 실제로 끝나는 위치와 stack의 남은 크기는 구조체 크기와 실행 중인 stack 사용량에 따라 달라진다. 고정된 사실은 4KB page의 양 끝 주소와 두 영역이 같은 page를 공유한다는 점이다.

추적하는 주소는 커널 가상 주소다

0x8004000000은 물리 주소가 아니다. paging이 활성화된 뒤에는 page table이 이 VA를 PA로 변환한다. 초기에는 boot_pml4e가 임시 매핑을 제공하고, paging_init() 이후에는 base_pml4가 정식 direct map을 제공한다.

유저 모드에서는 침범할 수 없다

user mode에서 커널 page에 접근하면 page fault(protection fault)가 발생한다. 그러나 kernel mode는 다르다. kernel bug가 잘못된 pointer를 통해 0x8004000000 근처에 값을 쓰면 main thread의 struct thread나 stack을 손상할 수 있다. PintOS는 커널 내부를 하나의 신뢰 영역으로 취급하기 때문이다.
