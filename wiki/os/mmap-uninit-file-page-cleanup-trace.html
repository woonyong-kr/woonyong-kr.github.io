fault가 한 번도 나지 않은 mmap page는 누가 정리하나

한 줄 요약: 한 번도 fault가 발생하지 않은 UNINIT(FILE) page에는 frame도 dirty bit도 없어 write-back할 필요가 없다. 그러나 aux가 file reference와 offset을 들고 있으므로, cleanup을 끝내려면 free(page)가 아니라 uninit_destroy()가 aux와 file ownership을 정확히 한 번 정리해야 한다.

미사용 mmap page cleanup의 출발점

mmap()은 파일을 주소 공간에 연결한다. 하지만 lazy loading을 사용하면 mmap() 직후에도 실제 frame은 없을 수 있다.

위 코드에서 사용자가 p[4096]을 한 번도 읽지 않았다면 두 번째 page는 여전히 VM_UNINIT 상태일 수 있다.

여기서 다음 질문이 생긴다.

frame도 없고 dirty bit도 없는 UNINIT(FILE) page는 munmap() 또는 process exit에서 free(page)만 하면 될까?

짧게 답하면, 아니다.

미사용 mmap page cleanup이 필요한 이유

처음 배울 때는 munmap() 정리를 다음과 같이 생각하기 쉽다.

이 모델은 이미 fault가 발생해 frame이 연결된 page에는 어느 정도 들어맞는다. 하지만 lazy mmap()에는 이와 다른 상태가 존재한다.

이 page는 RAM에 올라온 적이 없으므로 파일에 write-back할 바이트도 없다. 그러나 aux가 heap에 할당되어 있고 그 안에 file_reopen()으로 얻은 file object가 들어 있다면, 이를 그대로 버릴 수는 없다.

즉, never-faulted page의 cleanup은 “디스크 write-back” 문제가 아니라 metadata ownership 문제다.

실패하는 구현은 대개 다음 두 유형 중 하나다.

잘못된 구현증상
uninit_destroy()가 아무것도 하지 않음never-faulted page의 aux와 file reference leak
uninit_destroy()와 region cleanup이 같은 file을 모두 닫음double close, use-after-free, 다음 page cleanup 실패

따라서 가장 먼저 “누가 파일을 닫는가”를 정해야 한다.

  1. never-faulted UNINIT(FILE) page에는 어떤 자원이 남아 있을까?

미사용 mmap page의 cleanup 흐름

mmap() page는 cleanup 시점에 다음 세 상태 중 하나일 수 있다.

상태page typeframemetadata 위치write-backcleanup 핵심
첫 fault 전VM_UNINIT, future VM_FILE없음page->uninit.aux없음aux와 file ownership 정리
resident file pageVM_FILE있음page->filedirty이면 필요file bytes write-back 뒤 page 정리
evicted file pageVM_FILE없을 수 있음page->fileeviction 때 처리했거나 다시 판단file metadata와 reference 정리

처음에는 이 세 상태를 다음과 같이 구분하면 된다.

aux와 page->file은 같은 개념이 아니다. mmap file page의 aux는 언제 struct file page로 옮겨야 하나에서 살펴봤듯이, aux는 첫 fault 전의 임시 작업 지시서이고 page->file은 첫 fault 이후에도 유지되는 metadata다.

cleanup의 기준은 다음 한 문장으로 정리할 수 있다.

파일 길이가 6000바이트이고 두 page를 매핑하는 경우

파일 길이가 6000바이트이고 두 page를 매핑한다고 가정하자.

첫 번째 page는 p[0] 접근으로 fault가 발생했다.

두 번째 page에는 한 번도 접근하지 않았다.

따라서 munmap(p)는 두 page를 같은 방식으로 처리해서는 안 된다.

여기서 중요한 점은 page 1의 SPT entry도 지워야 한다는 것이다. 그래야 munmap() 뒤에 같은 주소를 읽었을 때 SPT lookup이 실패하고 프로세스가 종료된다.

실제 운영체제에서는

Linux에서 close(fd)는 이미 만들어진 mapping을 즉시 없애지 않는다. 커널의 VMA와 file object reference가 mapping의 생명주기를 별도로 관리하기 때문이다. munmap(addr, length) 또는 process exit이 주소 범위를 없애면 VMA, PTE, page cache, file reference가 차례로 정리된다.

Windows에서도 MapViewOfFile()로 만든 view는 user handle을 닫는 것과 별도의 생명주기를 가진다. UnmapViewOfFile(base) 또는 process teardown이 view를 정리하고, 이후 section/file object reference count도 그에 맞춰 감소한다.

실제 OS는 PintOS보다 훨씬 복잡하다.

  • file mapping은 범위 단위의 VMA/view 및 page cache와 연결된다.
  • 같은 file page를 여러 process가 공유할 수 있다.
  • dirty write-back은 munmap() 순간에만 단순히 끝나지 않을 수 있다.
  • close/unlink/truncate와 mapping 사이에는 reference count와 locking이 필요하다.

그럼에도 초보자가 이해해야 할 핵심은 같다.

PintOS에서는

W09 PintOS skeleton에는 이 cleanup 책임을 보여 주는 단서가 이미 있다.

첫째, struct page는 type별 metadata를 union에 둔다.

둘째, uninit_new()는 aux를 page->uninit.aux에 저장한다.

셋째, uninit_destroy() 주석은 첫 fault가 한 번도 발생하지 않은 page가 process exit까지 남을 수 있음을 설명한다.

즉, 상황에 따라 uninit_destroy()를 빈 함수로 두어서는 안 된다. aux가 heap memory나 reopened file reference를 소유한다면 이 함수 또는 region cleanup이 해당 자원을 회수해야 한다.

page별 file 소유 설계

가장 단순한 방법은 page마다 file_reopen()을 별도로 소유하는 것이다.

이 방식은 각 page를 독립적으로 cleanup할 수 있다는 장점이 있다. 반면 mapping의 page 수만큼 file object가 생길 수 있다는 단점도 있다.

현재 W09 구현의 uninit_destroy()는 이미 이 방식을 따른다.

struct lazy_load_arg가 ANON과 FILE lazy page에 공통으로 사용되므로, page_get_type()로 분기하지 않고 aux의 file 필드가 NULL이 아닐 때 닫는다. executable lazy page도 page별 file_reopen()을 가지므로 이 cleanup이 올바르게 동작한다.

region이 file을 소유하는 설계

다른 방법은 mmap_region이 reopened file 하나를 소유하는 것이다.

이 설계에서는 page별 uninit_destroy()가 file을 닫아서는 안 된다. 마지막에 region이 한 번만 닫아야 한다.

이 방식은 range metadata와 file ownership을 한곳에서 관리할 수 있다는 장점이 있다. 대신 cleanup 순서를 더 엄격하게 지켜야 한다. page destroy가 region pointer를 참조한다면 page보다 region을 먼저 free해서는 안 된다.

어느 설계를 선택하든 지켜야 할 불변식은 같다.

process exit 순서

W09의 process_exit()은 VM 빌드에서 process_cleanup()을 먼저 호출한 뒤 fd를 닫는다.

이 순서에서는 SPT kill 시점에도 fd table의 file이 열려 있다. 그러나 mapping이 fd table의 file pointer에 직접 의존해서는 안 된다. mmap-close 테스트처럼 사용자가 fd를 먼저 닫더라도 mapping은 계속 살아 있어야 하기 때문이다.

mmap-close와 mmap-remove 테스트도 같은 조건을 요구한다.

따라서 결론은 분명하다.

미사용 mmap page cleanup 값 추적

다음 mapping을 살펴보자.

page별 metadata는 다음과 같이 나뉜다.

VA pagefile offsetread byteszero bytes접근 여부
0x10000000040960p[0] 접근으로 fault 발생
0x10001000409619042192접근 없음

p[0] = 'A' 후 munmap(p)라면 첫 번째 page는 dirty 상태일 수 있다.

그러나 두 번째 page에는 frame이 없다.

그렇더라도 두 번째 page의 aux는 정리해야 한다.

page별 file 소유 설계에서는 이 aux가 자신의 file을 닫는다.

region 소유 설계에서는 aux가 file을 닫지 않는다.

두 방식 가운데 하나만 선택해야 한다. 두 경로가 같은 reopened file pointer를 모두 닫아서는 안 된다.

정리

  • never-faulted UNINIT(FILE) page는 frame도 PTE도 없으므로 dirty write-back 대상이 아니다.
  • 그렇더라도 page->uninit.aux는 heap memory와 file reference를 들고 있을 수 있으므로 반드시 cleanup해야 한다.
  • destroy(page)는 현재 operation table을 따르므로, UNINIT page는 uninit_destroy()가 처리하고 fault 이후의 FILE page는 file_backed_destroy()가 처리한다.
  • file reference ownership은 page별 소유와 region 소유 중 하나로 일관되게 정해야 한다.
  • file_close()는 ownership을 가진 경로에서 정확히 한 번만 호출해야 한다.
  • process_exit()은 VM 빌드에서 SPT kill을 먼저 수행한다. 그러나 mmap-close 테스트처럼 fd가 먼저 닫히는 경우도 있으므로 mapping이 fd table의 file pointer에 의존해서는 안 된다.
  • QEMU는 aux leak이나 double close를 알지 못하며 page fault, dirty bit, IDE sector write 같은 하드웨어 효과만 재현한다.
