argv 문자열 → stack 배치

argv 문자열 → stack 배치

한 줄 요약: PintOS가 USER_STACK(0x47480000)에서 아래로 문자열 → padding → argv[argc]=NULL → argv 포인터 배열 → fake return address를 쌓고 RDI=argc·RSI=argv로 진입시키는 교육용 x86-64 배치를 다룬다.

argv 문자열 → stack 배치 상태

유저 프로그램이 실행될 때 main(int argc, char **argv)가 인자를 받으려면, 커널이 유저 스택에 인자 문자열과 포인터 배열을 미리 배치해 두어야 한다. x86-64에서 이 배치는 스택의 꼭대기(USER_STACK = 0x47480000)에서 아래로 자라며, 문자열 → word-align padding → argv 포인터 배열 → return address 순서로 쌓인다. 커널은 이 작업을 마친 뒤 RDI = argc, RSI = argv 주소로 레지스터를 설정하고 유저 모드로 점프한다.

상세 설명

PintOS 진입 규약과 System V ABI의 경계

아래 배치는 PintOS의 setup_initial_stack()과 lib/user/entry.c가 함께 정한 규약이다. RDI·RSI를 함수 인자에 쓰는 부분은 System V AMD64 함수 호출 규약과 같지만, Linux ELF의 프로세스 시작 규약과 동일하지 않다. Linux의 _start는 RSP가 가리키는 초기 스택에서 argc, argv, envp, auxv를 읽으며 fake return address를 전제하지 않는다.

핵심 규칙:

  • 문자열은 스택 꼭대기에서 아래로 복사한다 (역순: argv[argc-1] → argv[0])
  • 포인터 배열도 아래로 쌓는다 (역순: argv[argc-1] → argv[0])
  • 모든 포인터와 return address는 8바이트 정렬되어야 한다

실제 OS (Linux)

Linux에서는 execve() → do_execveat_common() → copy_strings() → create_elf_tables()가 이 작업을 수행한다. 추가로 auxiliary vector (AT_PHDR, AT_ENTRY 등)와 environment variables까지 스택에 배치한다. PintOS는 이 중 argv만 구현한다.

PintOS 구현

PintOS의 setup_initial_stack() (userprog/process.c:1077)이 이 배치를 담당한다.

단계 1: 문자열 복사 (역순)

argv[argi]를 스택에 복사한 뒤, 배열 원소를 새 스택 주소로 덮어쓴다. 이후 포인터 배열 단계에서 이 주소를 사용한다.

단계 2: word-align padding

& -8 = & 0xFFFFFFFFFFFFFFF8로 하위 3비트를 지워 8바이트 정렬한다. 문자열 끝이 8의 배수가 아니면 0~7바이트의 padding이 삽입된다.

단계 3: argv[argc] = NULL sentinel

C 표준은 argv[argc] == NULL을 보장한다.

단계 4: argv 포인터 배열 (역순)

단계 5: 레지스터 설정

단계 6: return address = 0

main()이 return하면 RIP = 0으로 점프해 page fault로 종료된다. 정상 경로에서는 exit() syscall로 종료하므로 이 return address가 쓰이지 않는다.

argv 문자열 → stack 배치 값 추적

args-multiple some arguments for you! (argc = 5) 예제:

역순이므로 실제 순서: you! → for → arguments → some → args-multiple

문자열 5개 총 크기 = 14 + 5 + 10 + 4 + 5 = 38바이트 stack_p = 0x47480000 - 38 = 0x4747FFDA

word-align: 0x4747FFDA & 0xFFF8 = 0x4747FFD8 (2바이트 padding)

QEMU 에뮬레이션

QEMU TCG 모드에서 setup_initial_stack()이 스택에 쓰는 memcpy/memset은 guest 가상 주소에 대한 softmmu store로 변환된다. 과정:

  1. memcpy(stack_p, argv[argi], size) → TCG가 guest VA(0x4747xxxx)에 대한 store 시퀀스로 번역
  2. softmmu TLB에 해당 VA의 매핑이 없으면 TLB miss → tlb_fill() → PML4 walk → setup_stack()에서 설치한 PTE 발견 → TLB 엔트리 캐시
  3. 이후 store는 TLB hit → host 메모리에 직접 기록
  4. word-align의 & -8 연산은 순수 레지스터 연산이므로 메모리 접근 없이 TCG IR and_i64로 처리

GDB에서 x/40xb 0x4747FFA0 같은 명령은 gdb stub이 softmmu를 통해 guest 메모리를 읽는 것이므로, guest CPU가 보는 것과 동일한 바이트를 확인할 수 있다.

관찰 시나리오

시나리오 1: 단일 인자 vs 다중 인자 스택 비교

목표: argc=1과 argc=5일 때 스택 소비량과 word-align padding 차이를 관찰한다.

절차:

  1. args-none (argc=1, 문자열 “args-none\0” = 10B) 실행, dump_argv_stack으로 레이아웃 확인
  2. args-multiple some arguments for you! (argc=5, 총 38B) 실행, 동일하게 확인
  3. 비교: padding 바이트 수, 총 소비 바이트, argv 포인터 배열 크기

예상 결과:

  • argc=1: 문자열 10B → padding 6B → NULL(8) + ptr(8) + ret(8) = 총 40B
  • argc=5: 문자열 38B → padding 2B → NULL(8) + ptr×5(40) + ret(8) = 총 96B
  • 인자 수가 늘면 포인터 배열이 8B×argc씩 선형 증가

시나리오 2: 128바이트 제한 경계에서의 동작

목표: LOADER_ARGS_LEN = 128 제한에 근접하는 인자를 넣어 경계 동작을 확인한다.

절차:

  1. 정확히 127바이트 인자 문자열(파일명 포함)을 구성해 실행 → 성공 확인
  2. 128바이트 초과 인자 구성 → parse_command_line() 실패 확인
  3. GDB에서 parse_command_line 반환값과 setup_initial_stack 호출 여부 추적

예상 결과:

  • 127B: 정상 실행, 스택 배치 완료
  • 128B+: strlcpy가 잘리거나 인자 파싱이 불완전 → 의도하지 않은 동작 가능
  • PintOS는 명시적 에러 처리가 없으므로, 잘린 인자로 실행될 수 있음
