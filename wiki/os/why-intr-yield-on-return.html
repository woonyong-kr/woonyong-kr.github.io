인터럽트 끝에서 yield하는 이유

인터럽트 끝에서 yield하는 이유

확인 범위: 이 문서는 인터럽트 문맥에서 스케줄링을 미루는 일반 원리와 PintOS의 yield_on_return 구현 흐름을 설명한다. 제시된 코드 순서, 수치 계산, QEMU·Linux·Windows 비교는 특정 코드·버전의 실행 기록이나 성능 측정으로 검증한 결과가 아니므로, 실제 적용 여부를 판단하려면 대상 구현과 실행 환경에서 별도로 확인해야 한다.

타이머 인터럽트 핸들러 안에서 바로 schedule()을 부르면 PIC에 EOI를 보내기 전에 문맥이 바뀔 수 있다. PintOS는 yield_on_return 플래그만 세워 두고, 핸들러가 정리된 뒤 안전한 지점에서 실제 yield를 실행한다.

인터럽트 끝에서 yield하는 이유 구조

타이머 인터럽트 handler 안에서 바로 schedule()을 호출하면 외부 인터럽트 처리 중에 context switch가 일어난다. 이는 PIC에 EOI를 보내기 전에 CPU가 다른 스레드로 가는 것이므로, 다음 타이머 인터럽트를 받을 수 없게 되고 실행 문맥이 꼬인다. PintOS는 yield_on_return bool 하나로 “인터럽트 끝나면 yield하라”는 예약만 남기고, 실제 yield는 handler가 완전히 끝난 뒤 수행한다.

상세 설명

인터럽트 문맥에서 미뤄야 하는 이유

외부 인터럽트(IRQ)는 CPU가 현재 실행 흐름을 강제로 중단하고 커널의 특수 진입로(IDT vector)로 뛰는 사건이다. 이때 하드웨어가 강제하는 규칙이 있다.

하드웨어가 강제하는 것의미
인터럽트 발생 시 EFLAGS.IF = 0handler 진입 시 추가 인터럽트 차단
PIC ISR bit 유지EOI 보내기 전까지 같은 우선순위 IRQ 재진입 차단
RSP 전환 (IST/TSS)커널 스택으로 전환

OS가 이 문맥에서 sleep/block/schedule 같은 일반 커널 흐름으로 들어가면:

  1. PIC에 EOI를 보내지 않아 다음 인터럽트가 영원히 차단될 수 있다
  2. in_external_intr == true인 채로 다른 스레드가 실행되어, 해당 스레드의 인터럽트 관련 ASSERT가 터질 수 있다
  3. 인터럽트가 꺼진 상태에서 context switch하면 새 스레드도 인터럽트가 꺼진 채 실행될 수 있다

실제 OS (Linux/Windows)

항목LinuxWindows
interrupt 안에서 하는 일hardirq: 장치 acknowledge, 짧은 상태 기록ISR: interrupt 원인 확인, acknowledge
뒤로 미루는 흐름softirq, threaded IRQ, workqueueDPC (Deferred Procedure Call)

공통 원칙: 급한 하드웨어 응답은 interrupt 문맥에서 짧게 처리하고, 스케줄링·깨우기·긴 후처리는 안전한 지점으로 미룬다. PintOS의 yield_on_return은 Linux의 TIF_NEED_RESCHED를 1비트로 축소한 교육용 모델이다.

PintOS 구현

PintOS의 전체 흐름을 코드 순서로 추적한다.

1단계: 타이머 인터럽트 진입

intr_handler()에서 vector 0x20..0x2F이면 external interrupt로 판단하고 문맥 표시를 설정한다.

2단계: time slice 만료 → 예약만 남긴다

thread_yield()를 직접 호출하지 않고 bool 표시만 남긴다.

3단계: handler 안에서 yield 직접 호출은 ASSERT로 금지

in_external_intr == true인 동안 thread_yield() 호출은 커널 panic이다.

4단계: EOI 후 안전한 지점에서 yield

순서가 중요하다: (1) 문맥 표시 해제 → (2) PIC EOI → (3) yield. 이 순서가 뒤바뀌면 thread_yield() 안의 ASSERT가 터지거나 PIC가 다음 인터럽트를 차단한다.

QEMU 에뮬레이션

QEMU는 yield_on_return 변수를 모른다. QEMU가 하는 일과 PintOS가 하는 일의 경계는 다음과 같다.

계층하는 일코드
QEMU i8254 PIT가상 timer 출력 변화 생성pit_irq_timer_update() → qemu_set_irq()
QEMU i8259 PICIRQ line → IRR bit → CPU INT line raisepic_set_irq() → pic_update_irq()
PintOS interrupt.cvector 0x20 handler 호출, EOI 전송intr_handler() → pic_end_of_interrupt()
PintOS thread.ctick 카운트, yield 예약, schedulethread_tick() → thread_yield() → schedule()

QEMU 관점에서는 “IRQ line이 올라갔고, guest가 port I/O로 EOI를 보냈다”까지만 보인다. “현재 PintOS thread를 ready list에 다시 넣을지”는 guest OS 정책이다.

순서도 / 개념도

타이머 인터럽트 → yield 전체 흐름

sequenceDiagram
    participant QEMU as QEMU PIT/PIC
    participant CPU as Guest CPU
    participant IH as intr_handler()
    participant TT as thread_tick()
    participant TY as thread_yield()

    QEMU->>CPU: PIT output → IRQ0 → INT line raise
    CPU->>IH: vector 0x20 진입<br/>in_external_intr = true
    IH->>TT: timer_interrupt() → thread_tick()

    alt thread_ticks >= TIME_SLICE
        TT->>IH: intr_yield_on_return()<br/>yield_on_return = true
    else thread_ticks < TIME_SLICE
        TT->>IH: (아무 것도 안 함)
    end

    IH->>IH: in_external_intr = false
    IH->>QEMU: pic_end_of_interrupt(0x20)<br/>outb(0x20, 0x20)

    alt yield_on_return == true
        IH->>TY: thread_yield()
        TY->>TY: do_schedule(THREAD_READY)<br/>→ schedule() → context switch
    end

”왜 handler 안에서 바로 못 하나” 판단 흐름

flowchart TD
    IRQ[타이머 IRQ 발생] --> HANDLER[timer_interrupt 진입<br/>in_external_intr = true]
    HANDLER --> CHECK{time slice<br/>만료?}
    CHECK -->|No| DONE1[handler 정상 종료]
    CHECK -->|Yes| DIRECT{바로 schedule<br/>호출하면?}
    DIRECT --> PROBLEM1[ASSERT 실패<br/>intr_context == true]
    DIRECT --> PROBLEM2[PIC EOI 미전송<br/>다음 IRQ 차단]
    DIRECT --> PROBLEM3[실행 문맥 꼬임]

    CHECK -->|Yes| RESERVE[yield_on_return = true<br/>예약만 남김]
    RESERVE --> EXIT[in_external_intr = false]
    EXIT --> EOI[pic_end_of_interrupt]
    EOI --> YIELD[thread_yield 호출<br/>안전한 지점에서 context switch]
