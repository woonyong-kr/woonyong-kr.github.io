pml4_set_page 실패 뒤 claim 롤백 Trace

pml4_set_page 실패 뒤 claim 롤백 Trace

한 줄 요약: vm_do_claim_page()에서 frame을 얻은 뒤 pml4_set_page()나 swap_in()이 실패하면 연결한 page->frame·frame->page 양방향 포인터, 설치한 PTE, 할당한 user frame을 모두 되돌려야 하며, 부분 상태는 “장부는 resident인데 PTE는 not-present”인 모순으로 무한 pf·stale pointer·frame leak을 만든다.

pml4_set_page 실패 뒤 claim 흐름

vm_do_claim_page()는 frame을 얻은 뒤 page와 frame을 서로 연결한다. 이어 PTE를 설치하고 page의 내용을 frame으로 가져온다. 이 과정에서 pml4_set_page() 또는 swap_in()이 실패하면 앞서 만든 상태를 역순으로 되돌려야 한다. page->frame과 frame->page의 연결, 설치된 PTE, 할당된 user frame 가운데 일부만 남으면 커널 metadata와 CPU page table이 서로 다른 상태를 나타내기 때문이다.

커널 장부에는 page가 resident로 기록되어 있는데 CPU page table에는 mapping이 없다면 CPU는 같은 VA에서 계속 pf를 발생시킬 수 있다. 반대로 PTE만 남고 frame의 내용이 준비되지 않았다면 유저가 초기화되지 않은 bytes에 접근할 수 있다. 따라서 claim의 성공 여부는 page metadata, frame metadata, PTE가 함께 일관된 상태에 도달했는지로 판단해야 한다.

CPU/MMU와 OS metadata가 어긋날 때

MMU가 참조하는 것은 page table이다. OS가 page->frame을 설정했더라도 PTE가 present가 아니면 CPU는 계속 pf를 발생시킨다.

CPU/MMU가 보는 것OS metadata가 말하는 것불일치 시 결과
PTE present = 0page->frame != NULL (resident)같은 VA에 무한 pf 반복
PTE present = 1page->frame == NULL유저가 초기화 안 된 frame bytes 접근 가능
PTE가 가리키는 PAframe->kva에서 파생된 PA불일치면 다른 frame의 데이터 노출

하드웨어는 rollback이 필요하다고 OS에 알려주지 않는다. PTE와 metadata의 일관성을 유지하고 실패했을 때 부분 상태를 정리하는 일은 OS의 책임이다.

Linux와 Windows의 세부 구조와 오류 처리는 다르지만, 아래 표에 제시된 범위에서는 fault 처리 중 실패가 발생했을 때 관련 page table과 장부를 함께 정리한다.

항목LinuxWindows
fault 중 frame 확보 실패alloc_pages() 실패 → OOM killer 또는 SIGKILLworking set trimming 또는 process termination
PTE 설치 실패set_pte_at() 전에 page table page alloc 실패 → cleanup label로 점프prototype PTE 설치 실패 → VAD entry 복원
swap_in 실패I/O error → page 해제, PTE clear, SIGBUS 전달pagefile read 실패 → STATUS_IN_PAGE_ERROR
장부 정리 대상page refcount, reverse mapping, LRU list, PTE, TLBPFN entry, working set list, PTE, prototype PTE

이 비교에서 공통으로 확인할 수 있는 원칙은 page metadata가 resident라고 나타낼 때 page table과 physical page 장부도 같은 상태를 나타내야 한다는 점이다. 실패 지점마다 cleanup 경로를 두는 이유도 부분 상태가 남지 않게 하기 위해서다.

PintOS의 claim과 rollback

현재 W09 코드의 vm_do_claim_page()는 frame을 확보한 뒤 양방향 포인터를 연결한다. 이어서 PTE를 설치하고 swap_in()을 호출한다. 두 단계 중 하나라도 실패하면 vm_destroy_page_frame()으로 rollback한다.

vm_destroy_page_frame()은 owner의 page table에서 PTE를 지우고 frame을 frame table에서 제거한다. 그다음 user page를 반환하고 양방향 포인터를 끊은 뒤 frame wrapper를 해제한다.

실패 시점에 따라 이미 만들어진 상태와 정리할 대상이 달라진다.

실패 지점이미 생긴 것vm_destroy_page_frame이 하는 일
vm_get_frame() 실패없음호출되지 않음 (NULL 검사에서 조기 반환)
pml4_set_page() 실패frame↔page 양방향 링크pml4_clear_page (no-op: PTE 미설치), frame table에서 제거, palloc_free, link 해제, frame free
swap_in() 실패frame↔page 링크 + PTE 설치됨pml4_clear_page (PTE 제거 + invlpg), frame table에서 제거, palloc_free, link 해제, frame free

vm_get_frame()이 실패하면 frame과 page를 아직 연결하지 않았으므로 되돌릴 상태가 없다. pml4_set_page()가 실패한 시점에는 양방향 링크가 이미 생겼지만 PTE는 설치되지 않았다. swap_in()이 실패한 시점에는 링크와 PTE가 모두 존재한다. 이때는 PTE까지 제거해야 유저가 준비되지 않은 frame에 접근하지 않는다.

pml4_set_page 실패 조건

pml4_set_page()는 내부에서 pml4e_walk(..., create = 1)을 호출한다. 중간 page table page(PDPT, PD, PT)가 없으면 palloc_get_page(PAL_ZERO)로 새로 할당한다. 이 할당이 실패하면 pte == NULL이 되고 함수는 false를 반환한다.

vm_do_claim_page()가 rollback할 때 page 자체는 free하지 않는다. 이 함수는 SPT에 있던 page를 frame에 올리려는 함수이며 SPT entry의 소유자가 아니기 때문이다. page 제거 여부는 process kill이나 SPT cleanup 같은 caller의 정책에서 결정한다.

QEMU에서 보이는 상태

QEMU는 page->frame이나 frame->page를 알지 못한다. QEMU가 관찰하는 것은 guest page table과 guest physical memory의 접근 결과뿐이다.

시나리오QEMU 관점
PTE 설치 실패 → rollback같은 VA 재접근 시 guest page table walk 실패 → 다시 pf
PTE 설치 후 swap_in 실패 → PTE 미정리present PTE를 통해 초기화 안 된 frame bytes에 접근 가능
정상 rollback (PTE clear + invlpg)같은 VA 재접근 시 pf → PintOS가 process kill

따라서 QEMU가 rollback 정책을 대신 수행하지는 않는다. guest OS가 PTE와 frame metadata를 일관되게 유지해야 한다.

다음 값에서는 frame->kva에서 KERN_BASE를 빼 frame의 physical address를 구할 수 있다.

frame의 physical address:

PTE 설치가 성공하면 이 physical address에 present, writable, user flag가 결합된다.

상태 일관성 점검

pml4_set_page()가 실패한 직후에는 page와 frame의 metadata가 서로 연결되어 있지만 CPU가 사용할 mapping은 없다.

rollback이 끝나면 양방향 연결과 frame이 제거된다. PTE도 없는 상태이므로 metadata와 CPU의 관점이 다시 일치한다.

swap_in() 실패 뒤 PTE를 정리하지 않으면 metadata와 mapping은 존재하지만 frame bytes가 초기화되지 않은 위험 상태가 남는다.

frame 메모리 크기

제시된 크기 계산에서는 claim 한 번에 frame wrapper와 4096-byte user page가 함께 필요하다.

rollback에서 frame을 반환하지 않으면 이 비용이 leak으로 남아 user pool 고갈을 앞당긴다.

PTE 설치 실패 직후에는 양방향 link만 남아 있다. cleanup은 이 link와 새 frame을 제거해 page metadata와 page table이 모두 frame 없음 상태를 나타내도록 만든다.

swap_in 실패 뒤 PTE clear가 필요한 이유

%% swap_in 실패 뒤 PTE clear가 필요한 이유
flowchart LR
  before_pte["PML4 walk<br/>PTE = 0x12340007<br/>present + writable + user"]
  before_user["유저 코드<br/>같은 VA 접근<br/>불확정 bytes 읽기"]
  before_frame["before_frame"]
  clear["pml4_clear_page()<br/>PTE present bit = 0"]
  tlb["invlpg<br/>TLB stale entry 제거"]
  next["다음 접근<br/>#PF"]
  kill["handler<br/>process kill"]
  cleanup["vm_destroy_page_frame()"]
  before_pte -->|PA mapping| before_frame
  before_frame -->|user accessible| before_user
  clear --> tlb
  tlb --> next
  next --> kill
  before_user --> cleanup
  cleanup --> clear

swap_in()이 실패했는데 present PTE를 남겨 두면 유저 접근이 준비되지 않은 frame으로 전달될 수 있다. pml4_clear_page()로 present bit를 해제하고 invlpg로 stale TLB entry를 제거해야 다음 접근이 다시 pf로 이어진다.
