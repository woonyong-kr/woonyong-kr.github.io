mmap 실패 조건은 어떤 순서로 검사해야 하나

한 줄 요약: mmap()은 file-backed page를 등록하기 전에 addr==NULL, page-align 안 된 addr/offset, length==0, fd 0·1·없는 fd, kernel VA·64비트 wrap range를 순서대로 탈락시켜야 하며, PintOS의 실패 반환값은 Linux와 달리 NULL이다.

그런데 다음 호출들은 왜 실패해야 할까

mmap()은 성공하면 파일을 유저 주소 공간에 붙인다.

그런데 다음 호출들은 왜 실패해야 할까?

질문은 이것이다.

mmap()은 file-backed page를 만들기 전에 어떤 인자들을 먼저 탈락시켜야 할까?

mmap 실패 조건 구분

mmap() 구현은 성공 경로보다 실패 경로가 먼저 안정되어야 한다.

성공 경로만 생각하면 이렇게 보인다.

하지만 잘못된 인자를 통과시키면 이후 단계가 더 위험해진다.

잘못된 인자늦게 발견하면 생기는 문제
addr == NULLnull page가 합법 영역처럼 보일 수 있음
misaligned addrSPT key를 page 단위로 잡기 어려움
misaligned offsetVA page와 file page 경계가 어긋남
length == 0mapping metadata는 없는데 성공처럼 보임
bad fd파일이 아닌 콘솔이나 없는 fd를 backing file처럼 다룸
kernel range유저 프로세스가 커널 주소를 자기 mapping처럼 요구함
overflow range[addr, addr + length)가 64비트에서 되감겨 검사 우회

이 말은 즉, mmap() 검증은 “친절한 예외 처리”가 아니라 주소 공간의 의미를 망가뜨리지 않기 위한 방어선이다.

mmap 실패 조건 상태

mmap 검증은 다음 순서로 나누어 생각하면 덜 헷갈린다.

이번 Lab은 1-4단계에 초점을 둔다. 5단계의 overlap 검사는 mmap은 왜 이미 쓰는 주소 범위를 덮으면 안 되나에서 따로 본다.

정상 입력은 이렇게 생겼다.

이 입력은 page 단위로 끊기 쉽다.

반대로 이 입력은 시작 주소가 page 중간이다.

SPT entry는 보통 0x10001000 같은 page base를 key로 삼는다. 그런데 호출자는 0x10001234부터 mapping을 만들겠다고 했다. 이 상태를 허용하면 “파일 첫 바이트가 page 중간부터 시작하는가?” 같은 추가 의미가 생긴다.

PintOS 과제는 이 복잡도를 다루지 않는다. 그래서 page-aligned 주소만 받게 한다.

실제 운영체제

Linux mmap()은 실패하면 MAP_FAILED를 반환하고 errno로 이유를 알려준다. 대표적으로 length == 0이나 page size에 맞지 않는 offset은 실패 조건이다.

일반적인 Linux mmap(addr, length, prot, flags, fd, offset)에서 addr는 hint일 수 있다. 커널이 다른 빈 주소를 고를 수도 있다. 하지만 MAP_FIXED 계열처럼 주소를 강하게 요구하면 충돌, 권한, 정렬 조건이 더 중요해진다.

Windows는 POSIX mmap() 대신 file mapping object와 view를 사용한다. CreateFileMapping으로 file mapping object를 만들고, MapViewOfFile 계열로 프로세스 주소 공간에 view를 붙인다. Windows도 handle, offset alignment, 접근 권한, view 범위를 검증한다.

현실 OS는 PintOS보다 훨씬 많은 조건을 본다.

  • 파일 권한과 mapping 권한의 충돌
  • shared/private mapping
  • copy-on-write
  • ASLR과 빈 주소 선택
  • VMA 병합과 분할
  • page cache, dirty write-back, file truncation

PintOS는 이런 일반 OS 설계를 addr, length, writable, fd, offset 다섯 인자로 줄여 학습한다.

PintOS

PintOS user wrapper는 이미 다섯 인자를 register에 넣는다.

  • RDI: addr
  • RSI: length
  • RDX: writable
  • R10: fd
  • R8: offset

이 저장소의 현재 커널은 아직 SYS_MMAP case와 do_mmap() 본문이 비어 있다. 따라서 구현자는 검증 위치를 정해야 한다.

보통은 이렇게 나눈다.

중요한 차이가 하나 있다.

PintOS user header에서는 MAP_FAILED가 NULL이다.

Linux의 (void *) -1을 그대로 가져오면 PintOS 테스트의 CHECK(... == MAP_FAILED)와 어긋난다.

QEMU

QEMU는 mmap() 인자가 잘못됐는지 모른다.

QEMU가 보는 것은 guest CPU가 실행하는 instruction과 guest page table이다.

따라서 fd == 1을 mapping하려는지, offset == 0x1234인지, addr == NULL인지는 PintOS 정책이다.

다만 잘못된 mapping을 PintOS가 허용한 뒤 유저 코드가 그 주소를 접근하면 QEMU는 x86 MMU처럼 page walk를 수행한다. QEMU target/i386/emulate/x86_mmu.c에는 PTE present bit와 user bit를 검사하는 흐름이 있고, 실패하면 page fault exception을 만든다.

이 말은 즉, QEMU는 최종 하드웨어 효과를 재현할 뿐이고, mmap 인자 검증 자체는 guest OS인 PintOS의 책임이다.

mmap 실패 조건 코드

1. 유저 wrapper는 mmap 인자를 register로

pintos/lib/user/syscall.c

syscall5의 네 번째와 다섯 번째 인자는 R10, R8로 들어간다. 그래서 mmap handler에서 fd를 f->R.rcx 같은 곳에서 읽으면 안 된다.

2. 실패값은 NULL이다

pintos/include/lib/user/syscall.h

실패한 mmap은 유저에게 0x0을 돌려야 한다.

3. page 크기와 kernel boundary는 PintOS

pintos/include/threads/vaddr.h

LOADER_KERN_BASE는 0x8004000000이다. 따라서 이 값 이상은 PintOS kernel virtual address 영역으로 본다.

4. fd는 현재 thread의 fd table에서 찾는다

pintos/userprog/process.c

fd 0과 1은 stdin/stdout 의미로 예약되어 있다. 파일 시스템의 regular file이 아니므로 mmap-bad-fd2, mmap-bad-fd3에서는 실패해야 한다.

5. VM file-backed 함수는 아직 검증을 채워야 한다

pintos/vm/file.c

현재 skeleton은 비어 있으므로, 성공 page 등록 전에 검증 행렬을 구현해야 한다.

6. QEMU는 page walk와 protection

target/i386/emulate/x86_mmu.c

또한 read/write emulation은 translation 실패를 page fault exception으로 바꾼다. 하지만 이 단계는 이미 guest가 메모리 접근을 시도한 뒤다. mmap() syscall 인자를 거절하는 시점은 PintOS 커널 안에 있어야 한다.

mmap-overlap은 이번 Lab의 끝에서 다음 단계로 넘긴다. 인자 자체가 정상이어도 주소 범위가 이미 다른 의미를 가지면 실패해야 한다.

mmap 실패 조건 값 추적

1. misaligned address

pg_ofs(addr) != 0이므로 실패한다.

2. misaligned file offset

반대로 mmap-off.c의 offset = 0x1000은 page-aligned다.

그래서 mmap-off는 성공해야 하고, file offset 0x1000부터 보이는 page를 만든다.

3. kernel boundary

PintOS의 kernel virtual base는 다음 값이다.

mmap-kernel.c의 첫 시도는 시작 주소가 정확히 kernel base다.

따라서 실패해야 한다.

4. wrap-around range

mmap-kernel.c의 세 번째 시도는 더 교묘하다.

64비트 unsigned 덧셈으로 보면 다음처럼 끝 주소가 되감긴다.

이런 range를 단순히 end < KERN_BASE 같은 식으로만 보면 검사를 우회할 수 있다. 그래서 end < addr이면 overflow로 보고 실패시키는 조건이 필요하다.

5. zero length

이 range에는 page가 하나도 없다. PintOS 테스트는 이 호출을 성공한 mapping으로 취급하지 않는다. mmap-zero-len은 MAP_FAILED를 기대하고, mmap-zero는 그 주소를 읽으면 죽어야 한다고 본다.

정리

  • mmap() 실패 조건은 file-backed page를 등록하기 전에 걸러야 한다.
  • PintOS의 실패 반환값은 Linux와 달리 NULL이다.
  • fd 0, fd 1, 없는 fd는 regular file mapping 대상이 아니다.
  • addr, offset은 page-aligned여야 하고, length == 0은 실패해야 한다.
  • kernel virtual address와 64비트 wrap-around range는 user range 검증에서 막아야 한다.
  • QEMU는 mmap 인자 정책을 모르고, 잘못된 주소 접근이 실제로 일어났을 때 page walk와 pf만 재현한다.
  • overlap 검사는 별도 단계이며 SPT에 이미 등록된 lazy page까지 봐야 한다.

mmap 실패 조건 관련 개념

  • mmap syscall 흐름
    • SYS_MMAP register 인자가 커널 handler로 들어오는 입구.
  • mmap overlap validation
    • 인자가 정상이어도 주소 범위가 이미 점유되어 있으면 실패하는 이유.
  • mmap file backed page
    • 검증을 통과한 뒤 file-backed lazy page가 되는 전체 모델.
  • file backed metadata
    • page별 file, offset, read/zero bytes를 저장하는 기준.
  • munmap 범위
    • 등록한 mapping range를 나중에 해제하는 흐름.
  • Page Fault Trace
    • 잘못된 주소 접근이 page fault와 process exit으로 이어지는 관문.
