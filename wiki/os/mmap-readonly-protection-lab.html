mmap read-only 쓰기 보호 Lab

mmap read-only 쓰기 보호 Lab

확인 범위: 이 문서는 PintOS의 lazy mmap에서 read-only 쓰기 보호가 SPT metadata와 PTE 권한에 걸쳐 작동해야 한다는 일반 원리와 구현 선택 기준을 설명한다. 제시된 코드 위치와 예상 fault 값은 구현과 디버깅에 사용할 검증 기준이다. 현재 저장소는 VM skeleton 상태이므로 특정 구현의 테스트 통과 여부, 실제 실행 기록, 버전별 동작이나 성능을 검증한 결과로 해석해서는 안 된다.

writable = 0인데 쓰기를 시도하면 왜 프로세스가 종료되어야 할까

PintOS VM 테스트 mmap-ro는 파일을 read-only로 매핑한 직후 해당 주소에 값을 쓴다.

여기서 writable = 0이면 쓰기를 허용하지 않았다는 뜻이다. 따라서 이 접근을 계속 진행시키지 않고 프로세스를 종료해야 한다.

이 동작을 구현하려면 한 가지를 더 따져야 한다.

이 write는 page table의 PTE_W만 보면 막을 수 있을까, 아니면 SPT의 page metadata도 필요할까?

read-only 쓰기 보호가 필요한 두 지점

mmap은 보통 lazy loading으로 구현한다. mmap()을 호출할 때는 “이 주소가 이 파일과 연결된다”는 정보만 SPT에 넣는다. 실제 frame과 PTE는 해당 주소에 처음 접근할 때 만든다.

따라서 read-only mapping의 쓰기는 서로 다른 두 지점에서 차단해야 한다.

층막아야 하는 상황
SPT metadata아직 PTE가 없는 lazy page에 첫 접근이 write로 들어온 경우
PTE PTE_W bit이미 page-in되어 present인 read-only page에 write하는 경우

따라서 writable은 pml4_set_page()를 호출할 때 한 번 사용하고 버리는 임시 인자가 아니다. page fault handler가 나중에 write fault를 처리할 수 있는지 판단하려면 mapping의 쓰기 권한이 page metadata에 남아 있어야 한다.

fault 처리 흐름에서 확인할 값

먼저 다음 네 값을 구분해 보면 전체 흐름을 이해하기 쉽다.

값의미어디서 확인하나
writable이 mapping이 유저 write를 허용하는가mmap() 인자, SPT/page metadata
PTE_WCPU가 이 present page의 write를 허용하는가pml4_set_page(..., rw) 결과
PF_Wfault를 낸 접근이 write였는가f->error_code
PF_Ppage가 없었는가, 권한 위반이었는가f->error_code

write fault가 발생하면 SPT에서 해당 page를 찾고, 그 page가 쓰기를 허용하는지 확인한다. read-only page라면 claim하지 않고 실패해야 한다. writable page라면 claim한 뒤, 저장해 둔 권한에 따라 PTE의 PTE_W를 켜거나 끈다.

먼저 read해서 page-in한 뒤 같은 page에 write하면 처리 경로가 달라진다.

순서도

read-only lazy page의 첫 write fault

flowchart TD
    A["user code: *map = 0"] --> B["CPU: PTE 없음 → #PF"]
    B --> C["page_fault() 진입"]
    C --> D["error_code 분해"]
    D --> E["not_present=true, write=true, user=true"]
    E --> F["vm_try_handle_fault(f, fault_addr, user, write, not_present)"]
    F --> G{"spt_find_page(spt, va)"}
    G -- 없음 --> H["return false → kill"]
    G -- 있음 --> I{"write && !page->writable?"}
    I -- Yes --> J["return false → kill"]
    I -- No --> K["vm_do_claim_page(page)"]
    K --> L["frame 할당 + swap_in + PTE 설치"]

먼저 읽고 나중에 쓸 때의 두 단계 fault

flowchart TD
    A["1st access: tmp = *map (read)"] --> B["#PF: not_present=1, write=0"]
    B --> C["SPT hit + writable=false → read는 허용"]
    C --> D["claim → PTE = frame|PTE_P|PTE_U (PTE_W 없음)"]
    D --> E["read 성공"]
    E --> F["2nd access: *map = 0 (write)"]
    F --> G["#PF: present=1 (PF_P=1), write=1"]
    G --> H["protection fault (rights violation)"]
    H --> I["vm_try_handle_fault: not_present=false"]
    I --> J["return false → kill"]

PTE_W bit를 결정하는 흐름

flowchart LR
    A["mmap(writable=0)"] --> B["SPT page.writable=false"]
    B --> C["vm_do_claim_page()"]
    C --> D["pml4_set_page(pml4, va, kva, page->writable)"]
    D --> E["PTE = vtop(kva) | PTE_P | PTE_U"]
    E --> F["PTE_W 비트 = 0"]

테스트 입력과 SPT의 약속

테스트 입력을 구체적인 값으로 놓고 흐름을 따라가 보자.

do_mmap()은 이 입력을 받아 다음 정보를 SPT에 남겨야 한다.

1. 첫 접근이 write인 경우

mmap-ro는 mapping을 먼저 읽지 않고 바로 쓴다.

아직 PTE가 없다면 CPU가 보고하는 fault는 다음과 같은 형태일 수 있다.

SPT에는 해당 page가 있지만 writable=false다. 그러므로 vm_try_handle_fault()는 이 fault를 lazy load로 처리해 실행을 계속시키면 안 된다.

2. 먼저 읽고 나중에 쓰는 경우

유저 코드가 먼저 읽었다면 read fault는 처리할 수 있다.

이때 claim한 PTE는 read-only로 설치해야 한다.

그 뒤 같은 주소에 write하면 page가 이미 present이므로 error code가 달라진다.

처리 경로는 다르지만 결과는 같다. read-only mapping에 write한 프로세스가 계속 실행되어서는 안 된다.

실제 운영체제와 비교

Linux에서 mmap()은 PROT_READ, PROT_WRITE 같은 protection을 VMA에 기록한다. PROT_READ만 있는 mapping에 쓰면 보통 SIGSEGV로 이어진다. 다만 실제 Linux는 demand paging, page cache, shared/private mapping, copy-on-write도 함께 판단한다.

Windows도 MapViewOfFile 계열에서 view의 접근 권한을 관리한다. read-only view에 쓰면 access violation으로 이어질 수 있다. 내부에는 section object, VAD, prototype PTE 같은 더 복잡한 구조가 연결된다.

현실의 운영체제와 PintOS가 판단해야 하는 질문은 같다.

현실의 운영체제는 mapping 범위의 metadata뿐 아니라 공유 page, COW, 파일 캐시, 보안 정책까지 함께 다룬다. PintOS에서는 이 문제를 struct page, SPT, PTE_W로 축소하여 직접 구현한다.

현재 저장소는 VM skeleton 상태다. 따라서 이 Lab은 이미 통과하는 동작을 설명하는 문서가 아니다. 구현해야 할 판단 기준을 테스트와 코드 위치에 연결해 보여 준다.

구현할 때는 다음 의미가 이어져야 한다.

writable을 struct file_page에만 둘지, 공통 struct page 필드로 둘지는 구현자가 선택할 수 있다. 다만 실행 파일의 read-only text page, anonymous page, file-backed mmap page가 모두 write permission 판단을 필요로 한다. 따라서 공통 helper를 통해 권한을 읽을 수 있도록 설계하는 편이 안전하다.

QEMU가 담당하는 범위

QEMU는 mmap, SPT, struct file_page, PintOS의 fd를 알지 못한다.

QEMU가 해석하는 대상은 x86 page table permission이다.

  • target/i386/cpu.h
    • PG_RW_MASK
    • PG_ERROR_P_MASK
    • PG_ERROR_W_MASK
    • PG_ERROR_U_MASK
  • target/i386/tcg/system/excp_helper.c
    • page table permission을 검사해 write가 허용되지 않으면 protection fault를 만든다.
    • store access이면 error code에 PG_ERROR_W_MASK를 붙인다.

QEMU에서는 다음과 같은 흐름으로 보인다.

반면 not-present write fault를 SPT metadata에 따라 거절하는 일은 QEMU가 아니라 PintOS의 VM 정책이 담당한다.

주소와 fault 값 추적

1. page base 계산

mmap-ro는 page 시작 주소부터 int 4바이트를 쓰려고 한다.

2. 첫 write가 lazy page에 들어온 경우

이 값만 보면 page가 없으므로 새로 준비하면 된다고 판단하기 쉽다. 그러나 SPT metadata에는 writable=false도 들어 있으므로 이 권한까지 함께 확인해야 한다.

3. read로 page-in한 뒤 write하는 경우

read fault가 먼저 처리되어 frame physical base가 0x12340000이라고 가정하자.

이 PTE는 present이며 user 접근은 허용하지만 write는 허용하지 않는다.

판단 기준

  • mmap-ro는 read-only file-backed mapping에 write했을 때 프로세스가 종료되는지 검사한다.
  • lazy 상태의 첫 write는 PF_P=0인 not-present write fault일 수 있다.
  • 이 fault를 권한에 따라 거절하려면 SPT에 writable=false metadata가 남아 있어야 한다.
  • 먼저 read하여 page-in한 뒤 write하면 PTE_W가 없으므로 PF_P=1인 protection fault가 발생한다.
  • PintOS에서는 vm_try_handle_fault()의 writable 검사와 pml4_set_page()의 rw 인자가 같은 쓰기 권한을 나타내야 한다.
  • QEMU는 mmap의 의미를 판단하지 않고 guest PTE permission과 pf error code를 재현한다.

관련 문서

  • mmap file backed page
    • file-backed mapping이 SPT와 page fault로 이어지는 전체 모델.
  • file backed metadata
    • writable을 포함한 file-backed page metadata 설계 기준.
  • vm try handle fault() decision
    • not-present fault라도 claim 전에 권한을 봐야 하는 이유.
  • Page Fault Error Code
    • PF_P/PF_W/PF_U를 숫자로 분해하는 법.
  • PTE bit
    • PTE_W가 PTE 값에서 어떤 bit인지 확인.
  • read buffer writable PTE
    • syscall read()에서도 writable page 검사가 필요한 이유.
