PML4 생성과 커널 영역 복사

PML4 생성과 커널 영역 복사

확인 범위: 이 문서는 x86-64 PML4와 커널 매핑 공유의 일반 원리를 설명하고, 제시된 PintOS·Linux·QEMU 코드 경로를 구현 사례로 구분해 다룬다. 구체적인 코드 위치·동작, 버전별 차이, 실행 결과와 비용·성능 판단은 해당 소스와 실제 실행·측정 기록으로 별도 검증해야 한다.

한 줄 요약: pml4_create()는 4 KB 페이지 하나로 새 주소 공간의 루트를 만들고, PML4 상위 절반(인덱스 256~511)의 커널 엔트리를 memcpy로 복사해 모든 프로세스가 같은 커널 매핑을 공유하게 한다.

PML4 생성과 커널 영역 복사 차이

새 프로세스를 만들 때 OS는 독립된 주소 공간을 부여해야 한다. x86-64에서 주소 공간의 실체는 PML4(Page Map Level 4) 테이블이다. pml4_create()는 4 KB 페이지 하나를 할당하고 base_pml4(커널 초기화 시 만들어진 원본 PML4)의 내용을 통째로 복사하여 커널 영역 매핑은 공유하되 유저 영역은 비어 있는 새 PML4를 만든다. 이것이 모든 프로세스가 커널 주소(0xFFFF_8000_0000_0000 이상)를 동일하게 접근할 수 있는 비밀이다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

x86-64의 4단계 페이지 테이블은 PML4 → PDPT → PD → PT → 물리 프레임 순으로 내려간다. PML4는 512개 엔트리를 갖고(각 8 bytes, 총 4 KB = 1 page), 각 엔트리가 512 GB 범위를 커버한다.

48비트 가상 주소에서 PML4 index는 bit 47:39 = 9비트 = 0~511이다. canonical 주소 규칙에 의해:

  • index 0~255 (bit 47 = 0) → 유저 공간 (0x0000_0000_0000_0000 ~ 0x0000_7FFF_FFFF_FFFF)
  • index 256~511 (bit 47 = 1) → 커널 공간 (0xFFFF_8000_0000_0000 ~ 0xFFFF_FFFF_FFFF_FFFF)

따라서 PML4를 memcpy로 복사하면 커널 엔트리(index 256511)가 자동으로 공유된다. 유저 엔트리(index 0255)는 base_pml4에서 비어 있으므로 새 PML4에도 비어 있다.

핵심: 커널 매핑은 PML4 수준에서 복사되지만, 하위 테이블(PDPT, PD, PT)은 같은 물리 프레임을 가리킨다. 따라서 커널 페이지 테이블 메모리는 모든 프로세스가 공유한다. 커널이 새 커널 매핑을 추가하면 base_pml4만 수정하면 되고, 이미 생성된 프로세스의 PML4에는 반영되지 않는다(PintOS에서 커널 주소 매핑은 부팅 시 고정이므로 문제없다).

실제 OS (Linux)

Linux의 pgd_alloc()도 동일한 패턴을 따른다:

  1. 페이지 할당: __get_free_pages()로 PGD(PML4에 해당) 페이지 할당
  2. 커널 매핑 복사: pgd_ctor()에서 init 프로세스의 PGD(= swapper_pg_dir)에서 커널 영역 엔트리를 복사
  3. KPTI 분리: Meltdown 완화가 활성화되면 유저 모드용 PGD와 커널 모드용 PGD를 2페이지 쌍으로 할당 (8 KB)

Linux는 PintOS와 달리 커널 매핑이 런타임에 변경될 수 있다. vmalloc 영역이 대표적인데, 새 vmalloc 매핑이 추가되면 page fault를 통해 다른 프로세스의 PGD에 lazy하게 전파된다.

PintOS 구현

pml4_create() — threads/mmu.c:101-107

단 5줄이지만, 이 함수가 하는 일의 의미를 분해하면:

  1. palloc_get_page(0): 플래그 0 = kernel pool에서 할당, PAL_ZERO 없음. 어차피 바로 memcpy로 덮어쓰므로 zero-fill 불필요.
  2. memcpy(pml4, base_pml4, PGSIZE): 512개 엔트리 전부 복사. PintOS에서 유저 영역 엔트리는 index 0 하나만 사용되고(가상 주소 0x400000 ~ USER_STACK은 모두 512 GB 범위 안), 나머지 index 1~255는 0이다. 커널 영역 엔트리는 index 256(= 0x100)부터 시작해 KERN_BASE 이상의 1:1 매핑을 가리킨다.

base_pml4 초기화 — threads/init.c:177-200 (paging_init())

이 함수가 하는 일:

  1. PAL_ASSERT | PAL_ZERO로 PML4 할당 (실패 시 PANIC)
  2. 물리 주소 [0, mem_end)를 커널 가상 주소 [KERN_BASE, KERN_BASE + mem_end)에 1:1 매핑
  3. 커널 코드 영역(.text)은 PTE_W를 빼서 쓰기 보호
  4. pml4e_walk(pml4, va, 1) — create=1이므로 PDPT/PD/PT를 필요할 때마다 palloc으로 새로 할당
  5. pml4_activate(0) — CR3에 base_pml4 물리 주소 로드

호출 경로

pml4_create()는 두 곳에서 호출된다:

  1. __do_fork() (process.c:366) — fork 시 자식 프로세스의 PML4 생성
  2. setup_process_address_space() (process.c:917) — exec 시 새 주소 공간 생성

pml4_destroy() — threads/mmu.c:199-210

PML4 해제 시에는 유저 영역만 재귀적으로 해제한다:

pml4[0]만 해제하는 이유: PintOS에서 유저 주소는 모두 PML4 index 0 범위(0 ~ 512 GB)에 들어간다. index 256 이상의 커널 엔트리가 가리키는 하위 테이블은 모든 프로세스가 공유하므로 해제하면 안 된다.

QEMU 에뮬레이션

QEMU TCG 모드에서 pml4_create()의 핵심 동작은 palloc_get_page() → memcpy()이다. 이 자체는 일반 메모리 연산이므로 특별한 QEMU 처리가 없다. 중요한 것은 이후 pml4_activate()(= lcr3())를 통해 CR3를 새 PML4의 물리 주소로 전환하는 순간이다. 이때 QEMU는 helper_write_crN()으로 env->cr[3]를 갱신하고 SoftTLB를 flush한다.

GDB에서 pml4_create() 결과 확인:

(gdb) b pml4_create
(gdb) c
(gdb) finish
(gdb) p/x $rax                    # 반환된 PML4 커널 VA
(gdb) x/8gx $rax                  # PML4 엔트리 0~7 (유저 영역 → 0)
(gdb) x/8gx ($rax + 256*8)        # PML4 엔트리 256~ (커널 영역 → base_pml4과 동일)
(gdb) x/8gx base_pml4 + 256*8     # base_pml4 커널 영역과 비교
