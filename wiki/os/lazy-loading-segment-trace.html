Lazy Loading Segment 흐름

Lazy Loading Segment 흐름

확인 범위: 이 문서는 demand paging과 lazy loading의 일반 원리 및 PintOS에서 예상되는 처리 흐름을 설명한다. 제시된 함수·코드 좌표·운영체제별 세부 동작과 비용·성능 판단은 특정 구현과 버전의 실제 코드, 실행 기록 및 측정 결과를 별도로 확인해야 한다.

한 줄 요약: load_segment()는 ELF 내용을 바로 RAM에 읽지 않고 “이 주소는 합법이고 나중에 파일 어디서 채운다”는 약속만 SPT에 적어 둔다. 실제 읽기는 그 주소를 처음 건드려 pf가 났을 때 lazy_load_segment()가 수행한다 — demand paging의 뼈대다.

Lazy Loading Segment 흐름에서 먼저 헷갈리는 지점

ELF 파일을 실행할 때 PintOS는 왜 load_segment()에서 곧바로 파일 내용을 전부 RAM에 읽지 않고, lazy_load_segment()를 나중에 호출하도록 남겨둘까?

답은 demand paging이다.

프로그램의 주소 공간에는 “나중에 필요하면 가져와도 되는 페이지”가 많다. 처음부터 모두 읽으면 실행 시작이 느려지고 RAM도 낭비된다. 그래서 커널은 처음에는 “이 주소는 합법이고, 나중에 어디서 어떻게 채워야 한다”는 약속만 SPT에 적어 둔다.

추상 개념 (CPU/MMU 하드웨어 규칙)

CPU와 MMU가 제공하는 하드웨어 규칙이 lazy loading을 가능하게 만든다.

1. 페이지 테이블의 Present 비트

CPU가 가상 주소를 물리 주소로 변환할 때 page table entry(PTE)의 Present 비트를 검사한다. Present = 0이면 CPU는 pf(Page Fault, 인터럽트 14번)를 발생시킨다. 이것이 lazy loading의 핵심 메커니즘이다. 커널은 의도적으로 PTE를 설치하지 않음으로써 “나중에 필요할 때 채우겠다”는 뜻을 표현한다.

2. CR2 레지스터

Page fault가 발생하면 CPU는 fault를 일으킨 가상 주소를 CR2 레지스터에 저장한다. 커널의 fault handler는 CR2를 읽어서 어떤 페이지가 필요한지 알아낸다.

3. 명령어 재실행 (Instruction Restart)

Page fault handler가 정상적으로 복귀하면 CPU는 fault를 일으킨 바로 그 명령어를 다시 실행한다. 이번에는 PTE가 설치되어 있으므로 정상적으로 메모리 접근이 성공한다. 유저 프로세스는 fault가 발생했다는 사실조차 모른다.

4. TLB 무효화

커널이 새로운 PTE를 설치한 뒤에는 TLB(Translation Lookaside Buffer)를 무효화해야 한다. 그렇지 않으면 CPU가 이전의 “not present” 캐시를 계속 사용할 수 있다. x86-64에서는 invlpg 명령어 또는 CR3 재로드로 TLB를 플러시한다.

이 네 가지 하드웨어 규칙이 없으면 demand paging은 불가능하다. 소프트웨어(커널)는 이 규칙 위에서 정책을 결정할 뿐이다.

실제 운영체제

Linux: execve → mmap → demand paging

Linux에서 execve()가 ELF 바이너리를 실행하면 커널은 load_elf_binary()를 호출한다. 이 함수는 ELF의 각 PT_LOAD 세그먼트에 대해 elf_map() → do_mmap()을 호출한다. 이때 파일의 해당 영역을 프로세스의 주소 공간에 file-backed memory mapping으로 등록한다. 실제 파일 데이터를 RAM에 읽지는 않는다.

유저 코드가 해당 주소에 처음 접근하면 page fault가 발생하고, 커널의 do_page_fault() → handle_mm_fault() → filemap_fault()가 호출된다. 이 경로에서 page cache를 확인하고, 캐시에 없으면 디스크에서 읽어온다.

Windows: Section Object + Demand

Windows에서 실행 파일(.exe)을 로드하면 커널은 PE(Portable Executable) 헤더를 파싱하고 Section Object를 만든다. 각 섹션(.text, .data, .rdata 등)은 NtMapViewOfSection()으로 프로세스의 가상 주소 공간에 매핑된다.

접근 시 page fault가 발생하면 Memory Manager가 페이지를 Modified Page List 또는 디스크(pagefile/원본 exe)에서 가져온다. Windows도 같은 DLL/EXE의 code section을 여러 프로세스가 공유하며, COW를 사용한다.

공통점: Linux, Windows, PintOS 모두 “ELF/PE 파싱 → 메타데이터만 등록 → 첫 접근 시 fault → 실제 로드”라는 동일한 demand paging 패턴을 따른다.

PintOS

PintOS VM 과제의 핵심은 이 실제 OS 흐름을 작게 구현하는 것이다.

load_segment()의 페이지 분할 로직

load_segment()는 세그먼트를 PGSIZE(4096) 단위로 쪼개어 페이지마다 다음 값을 계산한다.

그 다음 aux를 할당하고 file_reopen(file)으로 독립적인 파일 핸들을 만들어 aux에 저장한다.

그리고 SPT에 uninit page를 등록한다.

file_reopen()을 쓰는 이유

원본 file은 load() 안에서 열고 닫는 수명을 갖는다. lazy_load_segment()는 나중에(첫 page fault 시점에) 호출되므로, 그때까지 살아 있을 독립적인 파일 핸들이 필요하다. file_reopen()은 같은 inode를 참조하지만 독립적인 position과 수명을 갖는 새 struct file을 반환한다. 자세한 흐름은 file 수명 Trace에서 다룬다.

aux 구조체

aux 자체의 수명: load_segment()에서 malloc → 첫 page fault에서 lazy_load_segment()가 사용 후 free. Fault가 한 번도 나지 않은 page는 uninit_destroy()에서 정리되어야 한다.

uninit_initialize()의 이중 호출 구조

이 한 줄에 두 가지 초기화가 들어 있다:

  1. page_initializer = anon_initializer: page의 operations를 anon_ops로 바꿔서 타입을 VM_ANON으로 전환한다.
  2. init = lazy_load_segment: 실제 파일 데이터를 frame의 kva에 채운다.

QEMU

QEMU는 lazy_load_segment()라는 함수를 모른다.

QEMU가 관찰하는 것은 더 낮은 층이다.

  1. guest CPU가 어떤 VA를 읽는다.
  2. guest page table에 present PTE가 없으면 pf를 만든다.
  3. PintOS handler가 guest RAM 안의 PML4/PTE를 수정한다.
  4. handler가 iret으로 돌아오면 CPU는 같은 명령어를 다시 실행한다.

QEMU의 역할은 x86-64 CPU와 MMU의 동작을 에뮬레이션하는 것이다. Page fault를 만들고, CR2에 fault 주소를 넣고, PTE를 해석하는 것은 모두 QEMU가 수행하는 하드웨어 시뮬레이션이다. Lazy loading 정책은 PintOS 커널의 책임이고, QEMU는 그 정책이 실행될 수 있는 CPU/MMU/메모리 환경을 흉내 낸다.

QEMU의 소프트웨어 TLB도 관련이 있다. QEMU는 자체 TLB 캐시를 유지하며, guest가 PTE를 수정하면 해당 TLB 엔트리를 무효화해야 한다. 이 과정이 올바르게 동작하지 않으면 fault handler가 PTE를 설치해도 CPU가 여전히 old translation을 사용할 수 있다.

Lazy Loading Segment 흐름 값 추적

예제 1: 세그먼트가 2페이지에 걸치는 경우

ELF segment의 파라미터가 다음과 같다고 하자.

  • upage = 0x401000
  • ofs = 0x2000
  • read_bytes = 6000
  • zero_bytes = 2192
  • PGSIZE = 4096

검증: read_bytes + zero_bytes = 6000 + 2192 = 8192 = 2 * PGSIZE. 정상.

첫 번째 반복 (i=0):

page_read_bytes = min(6000, 4096) = 4096
page_zero_bytes = 4096 - 4096 = 0
aux = { file=reopened, ofs=0x2000, read_bytes=4096, zero_bytes=0 }
→ vm_alloc_page_with_initializer(VM_ANON, 0x401000, writable, lazy_load_segment, aux)

read_bytes -= 4096  → 1904 남음
zero_bytes -= 0     → 2192 남음
upage += 4096       → 0x402000
ofs += 4096         → 0x3000

두 번째 반복 (i=1):

page_read_bytes = min(1904, 4096) = 1904
page_zero_bytes = 4096 - 1904 = 2192
aux = { file=reopened, ofs=0x3000, read_bytes=1904, zero_bytes=2192 }
→ vm_alloc_page_with_initializer(VM_ANON, 0x402000, writable, lazy_load_segment, aux)

read_bytes -= 1904  → 0
zero_bytes -= 2192  → 0

예제 2: 순수 BSS 페이지 (read_bytes=0)

어떤 세그먼트의 마지막 부분에서:

read_bytes = 0
zero_bytes = 4096

이 경우:

page_read_bytes = min(0, 4096) = 0
page_zero_bytes = 4096 - 0 = 4096

lazy_load_segment()에서 file_read_at()은 0바이트를 읽고(사실상 no-op), memset(kva, 0, 4096)으로 전체 페이지를 0으로 채운다. 이것이 .bss 섹션의 전형적인 패턴이다.

예제 3: 메모리 비용 계산

10개의 PT_LOAD 페이지를 가진 프로그램이 시작된다고 하자.

즉시 로딩 (eager loading) 비용:

  • 물리 메모리: 10 * 4096 = 40,960 바이트
  • 디스크 I/O: 10번의 파일 읽기
  • 시작 시간: 모든 읽기가 끝나야 실행 시작

Lazy loading 비용 (프로그램이 3페이지만 실제 접근):

  • 물리 메모리: 3 * 4096 = 12,288 바이트 (70% 절약)
  • 디스크 I/O: 3번의 파일 읽기
  • SPT 오버헤드: 10 * sizeof(struct spt_entry) + 10 * sizeof(struct lazy_load_arg) (수백 바이트)
  • page fault 처리 비용: 3번의 fault handler 실행

Trade-off: page fault마다 수백~수천 사이클의 오버헤드가 추가되지만, 사용하지 않는 7페이지의 메모리와 I/O를 아끼는 이득이 훨씬 크다.
