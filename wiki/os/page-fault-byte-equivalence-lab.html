Page Fault 뒤 user VA와 frame offset 바이트 비교 Lab

Page Fault 바이트 대응 쟁점

page fault를 살린 뒤에는 이런 질문이 남는다.

x/16xb fault_addr와 x/16xb frame->kva + offset은 정말 같은 바이트를 보여 줄까?

정답은 “같아야 한다”다. 단, 두 주소가 같은 숫자라서가 아니라 서로 다른 가상 주소가 같은 physical frame의 같은 offset을 가리키도록 page table이 고쳐졌기 때문이다.

이 Lab의 목표는 lazy loading이나 stack growth가 성공한 직후, 유저 가상 주소와 커널 가상 주소가 같은 16바이트를 읽는지 GDB에서 자동으로 비교하는 것이다.

Page Fault 바이트 대응 혼동

VM 구현이 실패할 때는 보통 다음 중 하나가 어긋난다.

증상의심할 지점
SPT lookup은 성공했는데 다시 fault가 난다pml4_set_page()가 mapping을 설치하지 못했을 수 있다
frame은 붙었는데 유저 주소로 읽으면 실패한다user VA의 PTE와 frame->kva가 같은 frame을 보지 않을 수 있다
유저 주소와 kernel VA byte가 다르다offset 계산, lazy file read, zero fill, frame 재사용이 틀렸을 수 있다
x/16xb fault_addr가 GDB에서 실패한다아직 handler가 mapping을 설치하기 전이거나 현재 주소 공간이 다를 수 있다

이 말은 즉, struct page와 struct frame 포인터가 맞아 보이는 것만으로는 부족하다. CPU가 다시 같은 명령어를 실행했을 때 실제로 읽을 byte가 frame 안에 준비되어 있는지 확인해야 한다.

순서도

page fault → claim → byte 비교 전체 흐름

sequenceDiagram
    participant U as User Code
    participant CPU as CPU/MMU
    participant PF as page_fault()
    participant VM as vm_try_handle_fault()
    participant CL as vm_do_claim_page()
    participant SW as swap_in(page, kva)
    participant GDB as GDB Observer

    U->>CPU: mov rax, [0x401234]
    CPU->>CPU: page table walk → PTE not present
    CPU->>PF: #PF, CR2=0x401234
    PF->>VM: vm_try_handle_fault(f, 0x401234, ...)
    VM->>VM: spt_find_page(spt, 0x401000)
    VM->>CL: vm_do_claim_page(page)
    CL->>CL: frame = vm_get_frame()
    CL->>CL: frame->page = page, page->frame = frame
    CL->>CL: pml4_set_page(pml4, 0x401000, kva, writable)
    CL->>SW: swap_in(page, frame->kva)
    SW->>SW: file_read_at / disk_read / memset(0)
    SW-->>CL: true
    CL-->>VM: true
    VM-->>PF: true
    PF->>CPU: iretq → 같은 명령 재실행
    CPU->>CPU: page table walk → PTE present!
    CPU->>U: mov 성공, rax = byte at 0x401234

    Note over GDB: 이 시점에서 비교
    GDB->>GDB: x/16xb 0x401234 (user VA)
    GDB->>GDB: x/16xb frame->kva+0x234 (kernel VA)
    GDB->>GDB: 두 덤프가 같으면 매핑 정상

Page Fault 바이트 대응 차이

page fault를 살린 뒤 같은 byte는 세 이름으로 보인다.

이름예시누가 주로 보는가
user VA0x401234유저 프로그램과 CPU/MMU
page base + offset0x401000 + 0x234PintOS SPT와 page table 코드
kernel VA + offsetframe->kva + 0x234PintOS 커널과 GDB

핵심 관계는 다음이다.

따라서 byte 비교는 단순히 주소 숫자를 비교하는 실험이 아니다. page table mapping이 올바르게 설치되었고, frame 내용이 올바르게 채워졌는지 확인하는 실험이다.

Page Fault 바이트 대응 예시

유저 프로그램이 아직 lazy load되지 않은 주소를 읽다가 page fault가 났다고 하자.

계산은 이렇게 된다.

값계산결과
page basefault_addr & ~0xfff0x401000
offsetfault_addr & 0xfff0x234
kernel byte addressframe->kva + offset0xffff800012340234

비교해야 하는 두 덤프는 다음이다.

두 덤프의 16바이트가 같다면, 현재 주소 공간에서 user VA와 kernel direct-map VA가 같은 physical frame의 같은 offset으로 이어진 것이다.

실제 운영체제

Linux와 Windows에서도 같은 물리 page를 여러 virtual address로 볼 수 있다. 예를 들어 커널은 유저 페이지를 직접 매핑하거나 임시로 매핑해서 copy, page fault 처리, I/O를 수행한다.

하지만 실제 OS는 훨씬 많은 층을 거친다.

관점실제 OS
합법 주소 판단VMA, VAD, section object, permission metadata
물리 page 관리page cache, PFN database, NUMA, COW, refcount
디버깅kernel debugger, crash dump, process address space switch

그래도 디버깅 질문은 같다. “유저 주소가 가리키는 byte와 커널이 잡은 physical page 안의 byte가 같은가?”를 확인해야 한다.

확인한 코드 좌표는 다음이다.

파일위치이 Lab에서 쓰는 의미
userprog/exception.c161-182CR2를 fault_addr로 읽고 vm_try_handle_fault()로 넘긴다
vm/vm.c63-70spt_find_page()가 fault 주소의 page metadata를 찾아야 한다

vm/vm.cvm_do_claim_page() symbolframe/page를 연결하고 swap_in(page, frame->kva)를 호출한다. 줄 번호는 snapshot마다 달라질 수 있다.

W09의 VM 파일은 skeleton이므로, 이 Lab은 구현이 채워진 뒤 확인할 디버깅 절차다. 특히 pml4_set_page() 호출과 swap_in() 성공 이후에 비교해야 한다.

QEMU

QEMU는 PintOS의 struct page나 SPT를 모른다. 하지만 GDB가 요청한 guest register와 guest memory를 보여 준다.

확인한 QEMU 코드 좌표는 다음이다.

파일위치의미
target/i386/gdbstub.c204-207GDB가 guest CR2, CR3를 CPUX86State에서 읽는다
target/i386/tcg/system/excp_helper.c651-653page fault 전달 전 guest CR2가 갱신된다
gdbstub/gdbstub.c1308-1312GDB memory read packet을 debug memory read로 넘긴다
gdbstub/system.c452-468physical mode가 아니면 CPU debug memory read로 위임한다
system/physmem.c4030-4054guest virtual address를 debug translation한 뒤 physical address space byte를 읽는다

따라서 GDB의 x/16xb fault_addr는 host macOS/Linux 프로세스의 포인터를 직접 읽는 명령이 아니다. QEMU gdbstub이 guest 주소를 번역해 읽어 주는 관찰 경로다.

pml4_get_page()는 threads/mmu.c에서 PTE의 frame address에 pg_ofs(uaddr)를 더해 반환한다. 그래서 page base로 부르면 frame base가 나오고, page 중간 주소로 부르면 offset이 더해진 kernel VA가 나온다.

Page Fault 바이트 대응 GDB

1. page fault에서 fault 주소 저장하기

먼저 page_fault()에 멈춰 fault 주소와 offset을 GDB convenience variable로 저장한다.

확인할 것:

확인기대
$pf_addrCR2와 같은 faulting user VA
$pf_pageSPT lookup에 쓸 page-aligned VA
$pf_offframe 안에서 비교할 byte offset

2. claim 뒤 kernel VA 계산하기

vm_do_claim_page()에서 pml4_set_page()와 swap_in(page, frame->kva)가 성공한 뒤 멈춘다. 구현 위치가 다를 수 있으므로, 핵심은 “frame이 붙고 bytes가 채워진 뒤”다.

함수 입구에서 바로 비교하면 아직 frame이 없거나 byte가 채워지지 않았을 수 있다. 구현한 코드에서 frame/page 연결, pml4_set_page(), swap_in()이 지나간 뒤까지 next 또는 임시 breakpoint로 이동한다.

그 지점에서 다음 값을 만든다. finish로 vm_do_claim_page()가 성공 반환한 뒤에도 $kva_byte 같은 GDB convenience variable은 남는다.

5. page 끝 경계에서는 길이를 줄이기

fault_addr가 page 끝에 가까우면 16바이트 덤프가 다음 page로 넘어간다.

이 경우 뒤 8바이트는 다음 page에 속한다. 다음 page가 아직 mapping되지 않았다면 user VA 쪽 덤프가 실패할 수 있다.

안전하게 현재 page 안에서만 비교하려면 길이를 줄인다.

GDB Python에서는 n = min(16, 0x1000 - off)처럼 계산한다.

정리

  • fault_addr는 유저 프로그램이 접근하려다 실패한 user VA다.
  • frame->kva는 PintOS 커널이 같은 physical frame을 읽는 kernel VA다.
  • 둘은 같은 숫자가 아니어도, page table mapping이 맞으면 같은 frame의 같은 offset byte를 보여 준다.
  • 자동 비교는 pml4_get_page(pml4, fault_addr) == frame->kva + offset과 16바이트 dump equality를 함께 확인한다.
  • QEMU gdbstub은 guest memory를 읽는 관찰 경로이고, VM 정책의 정답은 PintOS 구현이 만든다.
