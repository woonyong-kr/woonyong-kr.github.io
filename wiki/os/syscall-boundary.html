syscall 경계

syscall 경계

한 줄 요약: syscall 경계는 유저가 커널 능력을 빌리는 유일한 합법 통로로, 고정된 진입점·원자적 권한 전환·인자 검증·반환값 통제라는 네 속성으로 보호를 구현한다.

syscall 경계

syscall 경계는 유저 프로그램이 커널 서비스를 요청할 수 있는 유일한 합법적 통로다. 유저 코드는 파일을 읽거나, 프로세스를 만들거나, 메모리를 확장하는 등의 일을 직접 할 수 없다. 이 모든 작업은 하드웨어 자원에 직접 접근해야 하는데, 그 접근 권한은 커널만 갖기 때문이다. syscall 경계는 유저가 “무엇을 해 달라”고 요청하면 커널이 “검증 후 대신 수행”하는 요청-검증-실행 패턴을 강제한다.

보호의 세 기둥(유저/커널 모드 분리, 특권 명령어 제한, syscall 경계) 중 syscall 경계는 유저가 커널의 능력을 사용하는 유일한 인터페이스를 정의한다. 나머지 두 기둥이 “못하게 막는” 역할이라면, syscall 경계는 “이것만은 할 수 있게 여는” 역할이다.

상세 설명

추상 개념 (설계 원칙)

syscall 경계가 보호 메커니즘인 이유는 다음 네 가지 속성 때문이다:

1. 진입점 고정: 유저 코드가 커널의 아무 주소나 호출할 수 없다. CPU는 syscall 명령어 실행 시 LSTAR MSR에 등록된 단 하나의 진입점으로만 점프한다. 커널이 진입점을 통제하므로 유저가 커널 내부의 임의 함수를 실행하는 것이 불가능하다.

2. 권한 전환 원자성: syscall 명령어는 CPL 변경(3→0), RIP 변경(유저→커널 진입점), RFLAGS 저장을 하드웨어 한 명령어로 수행한다. 중간에 인터럽트가 끼어들 수 없으므로, “유저 권한인데 커널 코드를 실행”하는 반쪽짜리 상태가 발생하지 않는다.

3. 인자 검증 의무: 커널은 유저가 전달한 모든 인자를 의심해야 한다. 포인터가 유저 주소 공간 내인지, 버퍼 크기가 유효한지, fd 번호가 열린 파일을 가리키는지 등을 검증한 뒤에야 실제 작업을 수행한다. 검증 없이 유저 포인터를 역참조하면 커널 메모리가 노출되거나 corruption이 발생한다.

4. 반환 값 통제: 커널은 작업 결과를 정해진 레지스터(RAX)에 담아 반환한다. 유저는 커널 내부 상태를 직접 볼 수 없고, 커널이 노출하기로 결정한 정보만 받는다.

  • 유저 공간 (CPL 3)
  • write(fd, buf, size)
  • RAX=SYS_WRITE, RDI=fd, RSI=buf, RDX=n
  • syscall 명령어
  • ══════════════════════════════════════════╡ ← syscall 경계
  • 커널 공간 (CPL 0)
    1. 진입점 고정 (LSTAR → syscall_entry)
    1. 인자 검증 (fd 유효? buf 유저 주소?)
    1. 작업 수행 (파일에 쓰기)
    1. 결과 반환 (RAX = 쓴 바이트 수)
  • sysretq 명령어
  • ══════════════════════════════════════════╡ ← 경계 복귀
  • 유저 코드 계속 실행

실제 OS (Linux)

Linux의 syscall 경계는 약 450개의 syscall 번호로 정의된다. 각 번호는 sys_call_table[] 배열의 인덱스이며, 커널이 노출하기로 결정한 서비스의 완전한 목록이다. 새로운 커널 기능이 추가되어도 syscall이 추가되지 않으면 유저는 접근할 수 없다. 이 “화이트리스트” 설계가 보안의 핵심이다.

Linux는 추가로 seccomp(Secure Computing)으로 프로세스별 syscall 필터링을 지원한다. 컨테이너 환경에서는 허용된 syscall 목록을 더 줄여 공격 표면을 최소화한다.

PintOS 구현

PintOS는 약 20개의 syscall만 구현한다.

경계의 하드웨어 측면:

syscall 명령어 실행 시 CPU가 LSTAR MSR에 등록된 syscall_entry로 점프한다 (userprog/syscall-entry.S). 이 어셈블리 코드가 유저 레지스터를 struct intr_frame에 저장한 뒤 C 함수 syscall_handler()를 호출한다.

경계의 소프트웨어 측면 — 검증:

  • syscall_handler(struct intr_frame *f)
  • f->R.rax로 syscall 번호 확인
  • 번호별 분기 (switch-case)
  • SYS_WRITE: fd, buffer, size 검증
  • SYS_READ: fd, buffer, size 검증
  • SYS_OPEN: filename 포인터 검증
  • …
  • 유저 포인터 검증
  • is_user_vaddr() — KERN_BASE 미만인지
  • pml4_get_page() — 매핑 존재하는지
  • 실제 작업 수행
  • f->R.rax = 반환값

PintOS에서 syscall 경계가 깨지는 대표적 버그:

  • 유저 포인터를 검증하지 않고 역참조 → 커널 패닉 또는 정보 유출
  • syscall 번호 범위를 체크하지 않음 → 잘못된 함수 포인터 호출
  • 문자열 인자의 NULL 종료를 확인하지 않음 → 커널 메모리까지 읽음

경계의 복귀:

syscall_handler()가 반환하면, 어셈블리 코드가 struct intr_frame에서 유저 레지스터를 복원하고 sysretq 명령어(또는 iretq)로 유저 모드에 복귀한다. CPL이 0→3으로 되돌아가면서 커널 접근 권한이 박탈된다.

QEMU 에뮬레이션

QEMU TCG는 guest의 syscall 명령어를 만나면 helper_syscall()(target/i386/seg_helper.c)을 호출하여 하드웨어 동작을 재현한다. 이 과정에서 QEMU가 하는 일과 하지 않는 일의 경계가 명확하다.

QEMU가 하는 일 (하드웨어 재현):

  1. env->regs[R_ECX] ← 유저 RIP (돌아갈 주소 보존)
  2. env->regs[11] ← RFLAGS (R11에 보존)
  3. RFLAGS를 MSR_SYSCALL_MASK로 마스킹 → IF 클리어 등
  4. env->eip ← LSTAR MSR 값 (커널 진입점)
  5. CS를 MSR_STAR[47:32]에서 로드, SS를 CS+8로 설정 — CPL 0

QEMU가 하지 않는 일 (OS 영역):

  • syscall 번호(RAX)를 해석하지 않음 — guest OS의 syscall_handler()가 처리
  • 인자(RDI/RSI/RDX) 검증 안 함 — guest OS 책임
  • 커널 스택(TSS.rsp0)으로의 전환 — syscall 명령어 자체는 스택을 바꾸지 않음. PintOS의 syscall-entry.S가 수동으로 커널 스택을 설정

GDB로 syscall 경계를 관찰:

(gdb) break *syscall_entry          # LSTAR가 가리키는 주소에 breakpoint
(gdb) info registers rax rdi rsi rdx  # syscall 번호와 인자 확인
(gdb) info registers rcx r11         # 보존된 유저 RIP와 RFLAGS
(gdb) x/i $rip                       # 현재 명령어 — syscall_entry 첫 줄

Linux의 fast/slow path 차이: sysretq는 RCX→RIP, R11→RFLAGS를 원자적으로 복원하므로 빠르다. 그러나 signal pending, ptrace 추적 중, 또는 iret이 필요한 특수한 경우 slow path(iretq)를 탄다. PintOS는 항상 do_iret()(iretq)를 사용한다.

syscall 진입 시 스택 상태 (PintOS)

syscall 명령어는 스택을 전환하지 않는다 — 이것이 int 0x80이나 IDT 기반 진입과의 핵심 차이다. syscall 실행 직후 RSP는 여전히 유저 스택을 가리킨다. PintOS의 syscall-entry.S가 수동으로 커널 스택을 설정한다:

syscall 명령어 실행 직후:
  RIP = LSTAR (syscall_entry)
  RCX = 유저 RIP (복귀 주소)
  R11 = 유저 RFLAGS
  RSP = ⚠ 아직 유저 스택!! (위험 구간)
  CS  = 커널 코드 세그먼트
  CPL = 0 (커널 모드)

syscall-entry.S 첫 동작:
  movabs $tss, %r12
  movq 4(%r12), %rsp     # TSS.rsp0 → 커널 스택으로 교체
  # 이 시점부터 안전 — IF는 이미 마스킹되어 인터럽트 차단 중

이 “유저 RSP인데 CPL=0” 구간이 바로 MSR_SYSCALL_MASK에서 IF를 클리어하는 이유다. IF=1이면 이 구간에서 인터럽트가 발생하여 유저 스택에 커널 데이터가 노출될 수 있다.
