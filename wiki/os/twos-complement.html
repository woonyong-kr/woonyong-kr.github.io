2의 보수

2의 보수

확인 범위: 이 문서는 2의 보수의 표현 원리와 선택 이유, 정수 범위 및 signed·unsigned 해석 기준을 설명하고 PintOS와 운영체제 관련 코드를 예시로 연결한다. 다만 특정 PintOS·Linux·Windows·x86-64 구현의 코드, 컴파일 옵션, 플래그 동작과 GDB 출력은 해당 버전의 실제 소스·빌드 설정·실행 기록을 검증한 결과가 아니므로, 구현별 판단에는 별도 확인이 필요하다.

한 줄 요약: 2의 보수(2’s complement)는 현대 CPU가 부호 있는 정수를 표현하는 표준 방식이다. 비트를 뒤집고 1을 더하면 음수가 되고, 덧셈 회로 하나로 양수와 음수를 동시에 처리할 수 있다.

2의 보수 구분

컴퓨터는 0과 1만 안다. 양수는 이진수로 자연스럽게 표현되지만, 음수는 별도 규칙이 필요하다. 규칙 없이 그냥 MSB를 부호 비트로 정하면(부호-절대값 방식) 0이 두 개 생기고, 덧셈 회로가 복잡해진다. OS 코드에서 이 규칙을 모르면 다음을 이해할 수 없다.

  • INT_MIN이 왜 (-INT_MAX - 1)로 정의되는가
  • exit(-1)이 메모리에서 0xFFFFFFFF로 보이는 이유
  • MLFQS의 nice 값이 -20 ~ 20 범위를 가지는 이유
  • PTE 비트 필드와 부호 있는 오프셋이 같은 레지스터에 섞이는 상황

2의 보수 흐름

비유: 시계 바늘로 이해하는 음수

12시간 시계를 생각한다. 현재 3시에서 5시간을 빼면 어디인가? 3 - 5 = -2가 아니라, 시계를 거꾸로 돌려 10시가 된다. 12시간 체계에서 -2와 10은 같은 위치다.

2의 보수도 같은 원리다. 8비트(256칸)에서 -1은 255(0xFF)와 같은 위치에 놓인다. 0에서 1을 빼면 시계처럼 한 바퀴 돌아 255에 도착한다.

세 가지 음수 표현 방식 비교

부호-절대값 (Sign-Magnitude)

가장 높은 비트(MSB)는 부호를 나타내고, 나머지 비트는 값의 크기를 나타낸다.

+5 = 0000 0101
-5 = 1000 0101
+0 = 0000 0000
-0 = 1000 0000  ← 0이 두 개

문제: +0과 -0이 존재한다. 덧셈 시 부호를 먼저 비교해야 해서 회로가 복잡해진다.

1의 보수 (1’s Complement)

음수를 만들려면 모든 비트를 뒤집는다.

+5 = 0000 0101
-5 = 1111 1010  (비트 반전)
+0 = 0000 0000
-0 = 1111 1111  ← 여전히 0이 두 개

덧셈이 부호-절대값보다 단순하지만, 여전히 -0이 존재한다. 1의 보수 덧셈에서 최상위 비트에서 올림(carry)이 발생하면 결과에 1을 더해야 한다(end-around carry).

2의 보수 (2’s Complement)

모든 비트를 뒤집고 1을 더한다.

+5 = 0000 0101
-5 = 1111 1011  (비트 반전 + 1)
+0 = 0000 0000
-0 = 0000 0000  ← 0이 하나뿐

0이 하나뿐이다. 덧셈기 하나로 양수·음수 모두 처리할 수 있다. 현대 CPU가 2의 보수를 선택한 이유다.

왜 “비트 반전 + 1”이 음수가 되는가

N비트 2의 보수에서 음수 -x의 정의는 2^N - x이다.

8비트에서 -5를 구하는 과정:

2^8 - 5 = 256 - 5 = 251 = 1111 1011

이것을 두 단계로 나누면:
  (2^8 - 1) - 5 + 1
= 1111 1111 - 0000 0101 + 1
= 1111 1010 + 1           ← 1111 1010은 비트 반전 결과
= 1111 1011               ← 비트 반전 + 1 = 2의 보수

2^N - 1에서 x를 빼는 것은 모든 비트를 뒤집는 것과 같다(1의 보수). 여기에 1을 더하면 2의 보수가 된다.

범위와 비대칭

N비트 2의 보수의 표현 범위:

최솟값: -2^(N-1)
최댓값: +2^(N-1) - 1

8비트: -128 ~ +127 (총 256개) 32비트: -2,147,483,648 ~ +2,147,483,647 (총 약 43억 개)

음수가 양수보다 하나 더 많다. 0이 양수 쪽을 차지하기 때문이다. 이 비대칭이 INT_MIN을 -INT_MAX - 1로 정의하는 이유다.

왜 INT_MIN을 직접 쓰지 않는가

틀린 정의: #define INT32_MIN -2147483648

C 컴파일러는 -2147483648을 “단항 마이너스 연산자 + 리터럴 2147483648”로 파싱한다. 그런데 2147483648은 32비트 signed int 범위를 넘는다. 컴파일러가 이를 unsigned 또는 long으로 해석할 수 있어서 예상과 다른 타입이 된다.

올바른 정의: #define INT32_MIN (-INT32_MAX - 1)
                              (-2147483647 - 1)

이렇게 쓰면 모든 중간 값이 signed int 범위 안에 머문다.

덧셈이 그냥 되는 이유

2의 보수의 가장 큰 장점은 덧셈기 하나로 양수 + 양수, 양수 + 음수, 음수 + 음수를 모두 처리할 수 있다는 것이다.

  5 + (-3) = 2

  0000 0101   (+5)
+ 1111 1101   (-3, 2의 보수)
-----------
1 0000 0010   → 8비트 범위에서 올림(carry)을 버리면 0000 0010 = +2

올림(carry out)을 무시하면 정답이 나온다. 별도의 뺄셈 회로가 필요 없다. CPU의 ALU(Arithmetic Logic Unit)가 단순해지는 핵심 이유다.

%% 2의 보수 ALU 덧셈 흐름
flowchart LR
  a["입력 A"]
  b["입력 B"]
  adder["ALU 덧셈기<br/>ADD 명령어<br/>signed/unsigned 공통 비트 연산"]
  result["결과 비트"]
  carry["carry out<br/>2의 보수에서는 무시"]
  overflow["overflow<br/>signed 오버플로우 검출"]
  a --> adder
  b --> adder
  adder --> result
  adder --> carry
  adder --> overflow

CPU는 ADD 명령어 하나로 signed/unsigned 모두 처리한다. 결과 비트는 같고, 해석만 다르다. signed 오버플로우(OF 플래그)와 unsigned 올림(CF 플래그)을 별도로 검출한다.

2의 보수 코드

PintOS: INT_MIN 정의

(-INT32_MAX - 1)은 2의 보수 비대칭을 안전하게 다루는 표준 패턴이다. PintOS의 limits.h도 같은 방식을 쓴다.

PintOS: exit(-1)의 메모리 표현

exit(-1)이 실패를 의미하는 관례에서, -1의 비트 패턴 0xFFFFFFFF는 “모든 비트가 1”이라는 점에서 특별하다. 어떤 양수와도 겹치지 않는다.

PintOS: MLFQS nice 값과 signed 연산

MLFQS 스케줄러의 nice 값은 -20 ~ 20 범위의 signed int이다. recent_cpu도 signed 고정소수점(17.14 형식)이다. MLFQS를 구현하면 이 두 값을 struct thread에 signed 필드로 추가한다. 이 값들의 덧셈, 뺄셈, 비교가 정확하게 동작하는 이유는 2의 보수 덧셈기가 signed 연산을 자연스럽게 처리하기 때문이다.

priority = PRI_MAX - (recent_cpu / 4) - (nice × 2)

nice = -20일 때: nice × 2 = -40
  비트: 0xFFFFFFD8 (32비트 2의 보수)
  priority가 올라간다 (빼기의 빼기 = 더하기)

nice = 20일 때: nice × 2 = 40
  비트: 0x00000028
  priority가 내려간다

Linux/Windows와의 차이

실제 OS와 PintOS 모두 2의 보수를 사용한다. 차이가 있다면:

  • Linux 커널은 C 표준의 signed overflow가 정의되지 않은 동작(UB)임을 인지하고, -fwrapv 플래그로 2의 보수 wraparound를 보장한다. PintOS는 이 옵션을 명시하지 않으므로, signed overflow에 의존하는 코드를 쓰면 안 된다.
  • Linux의 pid_t, uid_t, off_t 등은 signed 타입이다. -1은 “에러” 또는 “없음”을 의미하는 관례가 널리 쓰인다. PintOS도 tid_t가 int이고, 에러 시 TID_ERROR(-1)을 반환한다.
  • x86-64 CPU는 signed와 unsigned를 구별하지 않고 같은 ADD 명령어를 쓴다. OF(Overflow Flag)와 CF(Carry Flag)를 동시에 설정하고, 소프트웨어가 어느 플래그를 볼지 결정한다. JG(signed 비교)와 JA(unsigned 비교)가 다른 플래그를 확인한다.

정리

2의 보수는 “비트 반전 + 1”로 음수를 만드는 방식이다. 0이 하나뿐이고, 덧셈기 하나로 양수와 음수를 동시에 처리할 수 있어서 현대 CPU의 표준이 되었다. 1의 보수는 -0이 존재하고 end-around carry가 필요해서 사라졌다.

PintOS 코드를 읽을 때 기억할 것:

  • 0xFFFFFFFF는 unsigned 4,294,967,295이자 signed -1이다. 해석 방식이 의미를 결정한다.
  • INT_MIN은 (-INT_MAX - 1)로 정의된다. 2의 보수의 비대칭 때문이다.
  • CPU의 ADD 명령어는 signed/unsigned를 구분하지 않는다. 비트 연산은 같고, 플래그 해석만 다르다.
