IPC Message Passing — 커널을 경유하는 프로세스 간 통신

IPC Message Passing — 커널을 경유하는 프로세스 간 통신

한 줄 요약: 커널 버퍼를 경유해 write/send·read/recv로 데이터를 주고받는 IPC message passing.

IPC Message Passing 구조

Message passing에서는 프로세스가 커널 버퍼를 경유해서 데이터를 주고받는다. 보내는 프로세스가 write()/send()로 커널에 데이터를 넘기면, 받는 프로세스가 read()/recv()로 이를 꺼낸다.

shared memory보다 복사가 더 필요하지만, kernel object가 blocking과 기본 전달 순서를 제공한다. 그러나 여러 writer 사이의 application protocol, message framing, transaction 일관성까지 보장하지는 않는다. 이런 요구가 있다면 IPC별 atomicity 계약을 확인하고 별도 동기화를 설계해야 한다.

Pipe

Pipe는 단순한 IPC 방식이다. pipe() 시스템 콜을 호출하면 읽기용과 쓰기용 fd가 하나씩 반환된다.

Pipe 데이터는 커널 버퍼를 통과한다. 원문에 기록된 4KB~64KB는 특정 구현과 설정에서 관찰할 수 있는 범위이지, 모든 시스템에 적용되는 고정 계약은 아니다. 일반적인 blocking 동작에서는 버퍼가 가득 찬 동안 write()가 대기하고, 읽을 데이터가 없는 동안 read()가 대기한다. 이 대기는 생산자와 소비자의 진행을 조절하지만, application protocol이나 여러 writer 사이의 일관성까지 대신하지는 않는다.

제한: 하나의 pipe는 단방향이다. 보통 fork()로 fd를 상속한 부모-자식이 사용한다. 다만 fd를 상속·복제하거나 Unix domain socket의 SCM_RIGHTS로 전달받은 다른 프로세스도 사용할 수 있다. 양방향 통신에는 pipe 2개나 full-duplex socket이 필요하다.

셸의 |도 이 메커니즘을 사용한다. ls | grep .md에서는 ls의 stdout을 pipe의 쓰기 끝에 연결하고 grep의 stdin을 읽기 끝에 연결한다.

Named Pipe (FIFO)

FIFO는 파일 시스템에 이름이 있는 특수 파일로 존재한다. 이 이름을 통해 부모-자식 관계가 아닌 프로세스끼리도 통신할 수 있다.

내부 동작은 일반 pipe와 같다. 파일처럼 보이지만 데이터가 디스크에 저장되는 것은 아니며 커널 버퍼를 통과한다.

Message Queue

Pipe가 바이트 스트림을 전달하는 데 비해 message queue는 메시지 단위의 경계를 보존한다. 따라서 보낸 메시지 하나를 받는 쪽에서도 메시지 하나로 읽는다.

POSIX message queue

Pipe와 달리 메시지 경계를 보존하고 우선순위를 지원한다. 우선순위가 높은 메시지는 낮은 메시지보다 먼저 꺼내진다.

System V message queue

msg_type을 사용하면 특정 타입의 메시지만 선택해서 받을 수 있다.

Socket

Socket은 같은 머신뿐 아니라 네트워크로 연결된 다른 머신과도 통신할 수 있는 IPC다. 같은 머신에서는 AF_UNIX를, 다른 머신과의 통신에는 AF_INET을 사용할 수 있다.

두 가지 타입의 특성은 다음과 같다.

  • SOCK_STREAM (TCP): 연결 기반, 바이트 스트림, 순서 보장, 신뢰성 보장
  • SOCK_DGRAM (UDP): 비연결, 메시지 단위, 순서/신뢰성 미보장, 빠름

같은 머신에서 AF_UNIX (Unix domain socket)을 사용하면 네트워크 스택을 거치지 않는다. 이 특성 때문에 TCP보다 빠를 수 있으며 Docker, PostgreSQL, nginx 같은 서비스가 로컬 통신에 사용한다.

Signal

Signal의 주 용도는 이벤트를 알리는 것이다. 전통적인 kill()은 signal number를 전달한다. POSIX sigqueue()와 real-time signal은 sigval을 통해 작은 integer 또는 pointer 값도 함께 전달할 수 있다. 다만 pointer가 수신 프로세스에서 자동으로 유효한 공유 데이터가 되는 것은 아니므로 큰 payload를 전달하는 수단으로 사용하지 않는다.

주요 시그널에는 SIGTERM(종료 요청), SIGKILL(강제 종료, 핸들링 불가), SIGCHLD(자식 종료), SIGINT(Ctrl+C), SIGUSR1/2(사용자 정의)가 있다.

Signal은 payload와 delivery 제약이 크다. 따라서 “작업 완료 알림”이나 “설정 리로드 요청”처럼 단순한 신호를 전달하는 데 주로 사용한다.

상황추천

실제 시스템에서는 여러 방식을 조합할 수 있다. 예를 들어 shared memory로 대용량 데이터를 공유하고 pipe나 socket으로 “데이터 준비됐다”는 알림을 보내는 방식이다.

PintOS

PintOS는 IPC 메커니즘을 직접 구현하지 않는다. 프로세스 사이의 데이터 전달은 wait()/exit()의 종료 코드가 거의 전부다. 이 방식도 공유 메모리 기반 IPC가 아니다. 커널의 struct thread에 저장된 값을 부모가 읽는다(Process Record는 왜 thread와 따로 필요한가).

PintOS에서는 IPC 자체보다 그 기반이 되는 메커니즘을 다룬다. 가상 메모리 매핑(mmap file backed page는 어떻게 파일을 메모리처럼 보이게 하나), 페이지 테이블, 동기화 프리미티브(세마포어, 락, 조건 변수: 잠들고 깨우는 구조를 구분하기)는 실제 OS가 IPC를 구현할 때 사용하는 요소다.

IPC Message Passing 숫자 추적

Pipe 커널 버퍼 크기

OS버퍼 크기비고
Linux흔히 16 pages로 시작kernel 설정과 fcntl(F_SETPIPE_SZ)에 따라 변경 가능
macOS구현·버전 의존고정값으로 계약하지 않음
PintOS미구현—

원문에 기록된 Linux 5.x의 64 KB = 16 × 4 KB pages, F_SETPIPE_SZ 최대 1 MB, macOS 16 KB는 특정 시점과 설정에서 얻은 관찰값이다. 현재 시스템의 계약값으로 사용하려면 page size, /proc/sys/fs/pipe-max-size, F_GETPIPE_SZ 또는 해당 OS 문서를 다시 확인해야 한다.

POSIX atomicity 계약은 pipe capacity와 별개다. 한 번의 write()가 해당 pipe의 PIPE_BUF 이하이면 다른 writer의 데이터와 섞이지 않도록 보장된다. PIPE_BUF보다 큰 write는 일부만 기록되거나 다른 writer의 데이터와 interleave될 수 있으므로 런타임의 PIPE_BUF 값을 확인해야 한다.

데이터 복사 비용 비교

아래 수치는 원문에 기록된 비교값이다. 구현, 환경, payload와 측정 조건이 제시되지 않았으므로 일반적인 성능 보장이나 현재 시스템의 실행 결과로 해석해서는 안 된다.

IPC 방식복사 횟수1 MB 전송 시 복사량대략적 지연
Pipe / Socket2회 (user→kernel→user)2 MB~10 µs (로컬)
Shared Memory0회 (동일 물리 페이지 매핑)0 MB~100 ns (캐시 라인 전파)
Message Queue2회2 MB + 메시지 헤더~15 µs
Unix Domain Socket2회2 MB~5 µs (TCP 스택 생략)

여기서 복사 2회는 프로세스 A의 유저 버퍼에서 커널 버퍼로 이동하는 copy_from_user와, 커널 버퍼에서 프로세스 B의 유저 버퍼로 이동하는 copy_to_user를 뜻한다.

Pipe를 통한 부모→자식 데이터 전달

sequenceDiagram
    participant P as 부모 프로세스
    participant K as 커널 Pipe 버퍼 (64 KB)
    participant C as 자식 프로세스

    P->>P: pipe(pipefd) → fd[0]=읽기, fd[1]=쓰기
    P->>P: fork()
    Note over P: close(fd[0]) — 읽기 끝 닫기
    Note over C: close(fd[1]) — 쓰기 끝 닫기
    P->>K: write(fd[1], "hello", 5)
    Note over K: copy_from_user: 5 bytes 복사
    C->>K: read(fd[0], buf, 100)
    K-->>C: copy_to_user: "hello" 5 bytes
    Note over C: buf = "hello"

이 그림의 64 KB는 앞에서 설명한 특정 Linux 시점·설정의 관찰값이며, 모든 pipe의 고정 크기를 뜻하지 않는다.

코드 좌표

PintOS는 pipe/socket/message queue를 직접 구현하지 않는다. 다만 IPC의 기반이 되는 OS 메커니즘을 다음 위치에서 살펴볼 수 있다. 표의 역할 설명은 PintOS가 해당 IPC를 구현한다는 뜻이 아니라, 실제 OS의 IPC 동작과 연결해 이해하기 위한 대응 관계다.

파일함수/구조체역할 (IPC 관점)
userprog/syscall.csyscall_handler()write/read syscall 분기 — 실제 OS에서 pipe/socket fd 처리의 시작점
threads/synch.c:49sema_down()pipe read()가 비어있을 때 block — 실제 OS pipe 동기화 원형
threads/synch.c:109sema_up()pipe write()가 데이터를 넣은 뒤 reader를 깨움
threads/synch.c:195cond_wait()실제 OS의 poll/select 내부에서 사용되는 조건 변수 대기
threads/synch.c:213cond_signal()조건 충족 시 대기자 깨우기
vm/vm.cvm_alloc_page_with_initializer()shared memory 구현 시 공유 페이지 매핑 기반
threads/mmu.c:251pml4_set_page()shared memory 구현 시 동일 물리 페이지를 두 프로세스에 매핑

원문은 Linux의 pipe 구현 위치를 fs/pipe.c의 pipe_write()/pipe_read()로 기록한다. 또한 내부에서 pipe_buf_operations으로 커널 페이지를 관리하고 wait_event_interruptible()로 동기화한다고 설명한다. 이 좌표를 현재 kernel source에 적용하려면 사용 중인 버전에서 다시 확인해야 한다.
