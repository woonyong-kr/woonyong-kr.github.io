파일 디스크립터

파일 디스크립터

한 줄 요약: write(1, …)의 1이 무엇인지 — 파일 디스크립터가 왜 작은 정수인지 풀어가는 문서.

이 문서는 write(1, ...)의 1이 무엇을 가리키는지 이해하는 데서 시작한다. fd가 커널 내부 I/O 객체를 간접 참조하는 과정을 먼저 살펴본다. 이어서 Linux와 Windows의 모델을 비교하고, PintOS 구현과 GDB 관찰 지점을 따라간다.

fd 1의 의미

처음에는 1이 화면 장치의 주소처럼 보일 수 있다. 하지만 1은 주소가 아니다. 유저 프로그램이 커널에 “내가 가진 1번 I/O 대상에 5바이트를 써 달라”고 요청할 때 사용하는 작은 번호표다.

이 번호표를 file descriptor, 줄여서 fd라고 부른다.

커널 객체 대신 fd를 사용하는 이유

유저 프로그램이 파일, 터미널, 파이프, 소켓 같은 I/O 대상을 직접 다루려면 각 대상의 내부 구현을 알아야 한다.

  • 디스크 파일의 실제 위치, inode, 캐시 상태를 유저가 알 필요가 없다.
  • 터미널과 디스크 파일은 구현이 다르지만, 유저 코드는 둘 다 read/write로 다루고 싶다.
  • 이 문서가 설명하는 OS 설계에서는 커널 객체 주소를 직접 노출하지 않고, 보안과 안정성을 위해 간접 식별자를 사용한다.

그래서 OS는 유저에게 커널 포인터를 주지 않고 프로세스마다 작은 정수 번호를 준다. fd는 유저 공간에서 커널 내부 I/O 객체를 간접 참조하기 위한 index다.

fd에서 파일 객체까지

fd를 이해하는 최소 모델은 다음과 같다.

%% fd가 커널 내부 파일 객체로 내려가는 핵심 모델
flowchart LR
  user["유저 프로그램<br/>write(3, buf, 5)"]
  fd_table["프로세스 fd table<br/>fd_table[3]"]
  file["struct file<br/>inode"]
  inode["struct inode<br/>디스크 파일 실체"]
  user -->|"fd = 3"| fd_table
  fd_table -->|"fd_table[3]"| file
  file -->|"inode"| inode

유저 프로그램은 3만 본다. 커널은 현재 프로세스의 fd table에서 3번 칸을 찾아 실제 객체로 내려간다.

여기서는 두 가지 성질을 구분해야 한다.

  • 같은 숫자 3이라도 프로세스가 다르면 다른 대상을 가리킬 수 있다.
  • fd는 파일 내용이 아니라 “열린 상태”를 가리킨다. 열린 상태에는 현재 읽기 위치 같은 정보가 붙을 수 있다.

open()부터 close()까지

작은 정수인 fd가 실제 파일 객체와 연결되는 순서를 코드로 따라가 보자.

유저 프로그램에 보이는 값은 작은 정수 하나다.

커널 안에서는 대략 다음 흐름이 생긴다.

%% open 호출이 struct file 포인터를 fd table에 꽂고 fd를 반환하는 흐름
flowchart LR
  user["User<br/>open(&quot;sample.txt&quot;)"]
  kernel["Kernel syscall<br/>SYS_OPEN"]
  filesys["filesys_open()<br/>struct file *"]
  fd_table["fd table<br/>fd_table[next_fd] = file"]
  result["User<br/>fd = 2"]
  user -->|"open"| kernel
  kernel -->|"파일 이름 전달"| filesys
  filesys -->|"struct file *"| kernel
  kernel -->|"process_add_file()"| fd_table
  fd_table -->|"fd 반환"| result

그다음 write(fd, ...)는 파일 이름을 다시 찾지 않는다. fd table에서 열린 파일 객체를 바로 찾는다.

실제 운영체제의 모델

Linux에서 fd는 프로세스의 file descriptor table index다. 단순화하면 다음 구조로 내려간다.

stdin, stdout, stderr는 관례적으로 fd 0, 1, 2다.

이 구조 때문에 shell에서 redirection이 가능하다. stdout을 파일로 바꾸면 프로그램은 여전히 write(1, ...)를 호출한다. 다만 fd table의 1번 칸이 터미널 대신 파일을 가리킨다.

Windows는 같은 문제를 handle 모델로 푼다. Win32 API에서 CreateFile, ReadFile, WriteFile은 HANDLE을 사용한다. Linux fd처럼 작은 정수 index로 설명하기보다는 커널 object를 가리키는 불투명한 handle 값으로 이해하는 편이 좋다.

두 모델 모두 유저 프로그램에 커널 내부 객체 주소를 직접 주지 않는다. 대신 OS가 검증할 수 있는 간접 식별자를 제공한다.

PintOS의 fd table

이 저장소의 PintOS 구현은 fd table을 struct thread 안에 둔다.

  • PintOS 저장소 상대 경로 pintos/include/threads/thread.h
    • struct file **fd_table
    • int next_fd
  • PintOS 저장소 상대 경로 pintos/userprog/process.c
    • process_add_file
    • process_get_file
    • process_close_file
  • PintOS 저장소 상대 경로 pintos/userprog/syscall.c
    • open
    • read
    • write
    • close

초기 유저 프로세스가 시작될 때 fd table을 0으로 채운 페이지 하나로 만든다.

next_fd = 2인 이유는 0과 1을 표준 입력과 출력에 예약하기 때문이다. 이 코드베이스의 stdio.h에는 다음 값이 정의되어 있다.

PintOS의 open()은 파일 이름을 검사한 뒤 filesys_open(file)로 struct file *를 얻는다. 이어서 process_add_file(opened_file)로 fd table에 넣는다.

write(fd, buffer, size)는 fd == 1이면 화면 출력으로 처리한다. 그 외의 fd는 table에서 파일 객체를 찾는다.

close(fd)는 fd table의 칸을 비우고 file_close()로 열린 파일 객체를 닫는다.

PintOS와 QEMU의 역할

QEMU는 PintOS의 fd 의미를 처리하지 않는다.

SYS_OPEN, SYS_WRITE, SYS_CLOSE 같은 의미는 guest OS인 PintOS가 syscall_handler에서 해석한다. QEMU는 그 코드가 실행될 CPU, 메모리, 디스크 장치처럼 보이는 환경을 제공한다.

파일 I/O가 디스크까지 내려가면 역할은 다음과 같이 갈린다.

관련 코드는 다음 위치에서 볼 수 있다.

  • PintOS 디스크 경로
    • PintOS 저장소 상대 경로 pintos/filesys/inode.c
    • PintOS 저장소 상대 경로 pintos/devices/disk.c
  • QEMU 디스크 에뮬레이션 경로
    • hw/ide/core.c
    • block/block-backend.c

QEMU의 host fd와 PintOS guest fd는 구분해야 한다. PintOS fd는 guest OS 내부 번호다. QEMU가 backing file이나 socket을 다룰 때 쓰는 host fd는 QEMU 프로세스에 속한 별개의 번호다.

invalid fd를 다룰 때 주의할 점

이 저장소의 syscall 구현은 함수마다 invalid fd를 처리하는 방식이 조금 다르다.

  • write()는 process_get_file(fd)가 NULL이면 -1을 반환한다.
  • close()는 fd < 2, 범위 밖 fd, 비어 있는 칸을 조용히 무시한다.
  • filesize(), seek(), tell()은 fd가 잘못되었을 때 file_length, file_seek, file_tell로 바로 내려갈 수 있으므로 직접 테스트하며 정책을 확인해야 한다.

유저가 전달한 fd는 임의의 숫자일 수 있다. 따라서 커널은 먼저 그 값이 현재 프로세스 table의 유효한 index인지 확인해야 한다.
