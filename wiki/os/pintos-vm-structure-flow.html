PintOS VM 구조와 흐름

PintOS VM 구조와 흐름

한 줄 요약: PintOS VM은 MMU가 아는 것(VA→4단계 page-table walk→PA 또는 pf, PTE의 P/W/U/A/D 비트)과 모르는 것(이 page가 합법인가, backing이 파일/swap/zero인가)의 간격을 SPT·struct page·struct frame으로 메워, “아직 메모리에 없는 주소 접근”을 pf 시점에 lazy하게 살리는 골격을 구현한다.

주소 접근에서 page fault 처리까지

Virtual Memory는 물리 메모리보다 큰 주소 공간을 프로세스마다 독립적으로 제공하는 추상화다. 이전 단계까지는 프로그램 실행 전에 필요한 코드와 데이터를 모두 메모리에 올렸다. PintOS VM 단계에서는 아직 메모리에 없는 주소에 접근했을 때 필요한 page를 lazy하게 준비해야 한다.

유저 코드가 가상 주소(VA)에 접근하면 MMU는 페이지 테이블 4단계 walk을 수행해 물리 주소(PA)를 찾는다. PTE가 present 상태라면 변환된 주소로 접근을 계속한다. present가 아니라면 CPU는 CR2에 fault 주소를 기록하고 pf(Page Fault, vector 0x0E)를 발생시킨다.

MMU는 PTE의 P/W/U/A/D 비트와 page table만 해석한다. fault가 발생한 주소가 프로세스에 허용된 주소인지, 필요한 데이터가 파일·swap·zero 중 어디에서 와야 하는지는 알지 못한다.

하드웨어가 아는 것하드웨어가 모르는 것
VA → 4단계 walk → PA 또는 pf”이 page가 원래 합법한가”
PTE의 P/W/U/A/D 비트page의 backing source (파일, swap, zero)
CR2에 fault 주소 기록SPT, struct page, struct frame
error code에 원인 인코딩page type (anonymous, file-backed, uninit)

PintOS의 VM 서브시스템은 이 간격을 SPT, struct page, struct frame으로 메운다. SPT에서 fault 주소에 해당하는 page를 찾고, 실제 RAM의 frame을 확보한 뒤, page type에 맞는 데이터를 채우고 PTE를 설치한다. 처리가 끝나 iretq로 돌아가면 fault를 일으킨 명령어가 다시 실행된다.

%% PintOS VM 구조 흐름
flowchart TD
  user["User Code<br/>mov (%rsi), %al<br/>RSI = 0x8048123"]
  pml4["pml4 (Hardware Page Table)<br/>CPU/MMU가 4단계 walk으로 VA -&gt; PA 변환<br/>present 아니면 #PF"]
  spt["SPT (Supplemental Page Table)<br/>hash table<br/>key: page-aligned page-&gt;va<br/>value: struct page<br/>type / writable / backing"]
  frame["struct frame<br/>실제 RAM의 4KB 자리<br/>palloc(PAL_USER)로 확보<br/>부족하면 vm_evict_frame()으로 victim 교체"]

PintOS의 VM 객체

SPT는 page-aligned VA를 key로 사용하고 struct page를 value로 보관하는 hash table이다. struct page는 가상 주소, 쓰기 가능 여부, 현재 연결된 frame, page type별 메타데이터를 담는다. struct frame은 실제 RAM의 4KB 자리와 그 자리를 사용하는 page를 연결한다. page_operations는 page type에 따라 swap_in, swap_out, destroy 동작을 선택하는 vtable 역할을 한다.

struct page {
    const struct page_operations *operations;  // vtable
    void *va;                                  // 가상 주소 (page-aligned)
    struct frame *frame;                       // 현재 frame (NULL이면 미거주)
    bool writable;                             // 논리적 쓰기 가능 여부

    union {                                    // type별 메타데이터
        struct uninit_page uninit;  // VM_UNINIT: initializer + aux
        struct anon_page anon;      // VM_ANON:  swap_index
        struct file_page file;      // VM_FILE:  file*, ofs, read_bytes
    };
};

struct page_operations {          // "vtable"
    bool (*swap_in)(page, kva);   // frame bytes 준비
    bool (*swap_out)(page);       // frame bytes 저장
    void (*destroy)(page);        // 자원 해제
    enum vm_type type;            // VM_UNINIT/ANON/FILE
};

page는 등록 시점부터 모두 같은 상태로 존재하지 않는다. VM_UNINIT page는 첫 접근 전까지 initializer와 aux를 보관한다. 첫 접근이 발생하면 uninit_initialize가 실제 type으로 전환하고 lazy callback을 실행한다. VM_ANON page는 zero-fill 또는 swap disk를 사용하고, VM_FILE page는 file I/O를 사용한다.

타입등록 시점첫 접근 시swap-out 대상swap-in 방법
VM_UNINITvm_alloc_page_with_initializeruninit_initialize → 실제 type으로 전환전환 후 해당 type 규칙uninit_initialize (lazy callback)
VM_ANON스택 확장 또는 UNINIT에서 전환anon_initializer → zero-fillswap disk에 4KB 저장swap disk에서 4KB 읽기
VM_FILEmmap 또는 UNINIT에서 전환file_backed_initializer → file_readdirty면 file_write_atfile_read_at

page fault의 판단 순서

page fault가 발생하면 PintOS는 먼저 fault 주소가 유저 영역에 속하는지 확인한다. 유저 영역이 아니면 잘못된 접근으로 처리한다. not_present fault라면 SPT에서 page를 찾는다. page가 있으면 claim을 시도하고, 없다면 스택 확장 조건을 검사한다. present page에 대한 write fault라면 COW 후보로 보고 쓰기 보호 처리를 시도한다. 어떤 조건에도 해당하지 않으면 프로세스를 종료한다.

SPT에서 page를 찾은 뒤에는 vm_do_claim_page()가 실제 메모리에 올리는 작업을 맡는다. vm_get_frame()은 user pool에서 frame을 확보한다. 여유 frame이 없으면 victim을 골라 기존 page를 swap_out하고 PTE를 제거한 뒤 frame을 재활용한다.

확보한 frame과 page를 양방향으로 연결하고 PTE를 설치하면, page_operations.swap_in()이 page type에 맞춰 frame의 내용을 준비한다. VM_UNINIT은 uninit_initialize(), VM_ANON은 swap disk read, VM_FILE은 file_read_at()으로 이어진다. PTE 설치나 swap_in에 실패하면 설치한 상태와 연결을 rollback한다. 성공하면 iretq 이후 같은 명령어가 다시 실행된다.

QEMU와 PintOS의 경계

QEMU는 x86 CPU처럼 4단계 page walk을 수행한다. PTE가 present가 아니면 CR2를 설정하고 pf를 PintOS에 전달한다. PintOS가 PTE를 설치하고 iretq로 돌아오면 QEMU는 같은 명령어를 다시 실행한다. 새 PTE가 유효하면 이번에는 VA가 PA로 변환되어 접근이 끝난다.

QEMU가 해석하는 범위는 PTE 비트와 guest physical memory backing이다. SPT, struct page, VM_UNINIT, swap_in()이 어떤 의미인지는 알지 못한다. 주소 접근과 pf 발생은 QEMU가 에뮬레이션하지만, 해당 주소의 합법성과 backing source를 판단하고 page를 준비하는 일은 PintOS가 담당한다.

%% QEMU와 PintOS page fault 계층 흐름
flowchart TD
  qemu["QEMU<br/>VA -&gt; pml4 walk -&gt; PA -&gt; RAMBlock.host[offset]<br/>PTE not present -&gt; CR2 설정 -&gt; #PF inject"]
  pintos["PintOS<br/>page_fault() -&gt; vm_try_handle_fault()<br/>-&gt; spt_find_page() -&gt; vm_do_claim_page()<br/>-&gt; pml4_set_page() -&gt; swap_in()<br/>-&gt; iretq (QEMU가 명령 재실행)"]
  retry["재실행<br/>같은 명령어가 다시 실행되고"]
  qemu -->|#PF 전달| pintos
  pintos -->|iretq| retry
  retry -->|명령 재실행| qemu

Linux·Windows와 비교한 위치

Linux와 Windows도 하드웨어가 알지 못하는 page의 합법성, backing source, frame 상태를 OS 자료구조로 관리한다. Linux는 VMA를, Windows는 VAD를 사용해 주소의 합법성을 판단한다. PintOS의 SPT와 struct page는 이 역할을 학습할 수 있도록 핵심 골격만 남긴 교육용 구현이다.

frame 관리와 eviction도 같은 문제를 더 단순한 구성으로 다룬다. Linux의 buddy allocator와 zone, Windows의 PFN database와 working set에 대응하는 위치에 PintOS의 palloc user pool이 있다. Linux의 LRU approximation (MGLRU), Windows의 clock과 working set trimming에 비해 PintOS는 clock algorithm을 사용한다. 아래 표는 동일한 구현이라는 뜻이 아니라, 각 시스템에서 비슷한 질문을 담당하는 요소를 나란히 놓은 것이다.

항목LinuxWindowsPintOS
page 메타데이터VMA (vm_area_struct)VAD (Virtual Address Descriptor)SPT의 struct page
page 합법성 판단VMA tree 검색VAD tree 검색hash table lookup
frame 관리buddy allocator + zonePFN database + working setpalloc user pool
eviction 정책LRU approximation (MGLRU)clock + working set trimmingclock algorithm
page type 구분page cache / anon / swap / filesection object / pagefile / mapped fileVM_ANON / VM_FILE / VM_UNINIT
COWfork 시 PTE read-only + refcountsection object 기반PTE_W 해제 + frame ref_count

한 주소의 값 추적

유저 코드가 0x8048123을 읽다가 fault가 발생했다고 두면, PintOS는 fault 주소를 page base와 page offset으로 나눈다. page base인 0x8048000은 SPT 조회와 PTE 설치에 쓰이고, offset인 0x123은 frame이 준비된 뒤 최종 물리 주소를 계산할 때 유지된다.

fault_addr     = 0x8048123
page base      = fault_addr & ~0xFFF = 0x8048000
page offset    = fault_addr & 0xFFF  = 0x123

VA 비트 분해 (48비트 canonical):
  PML4 index   = (0x8048123 >> 39) & 0x1FF = 0x001
  PDPT index   = (0x8048123 >> 30) & 0x1FF = 0x000
  PD index     = (0x8048123 >> 21) & 0x1FF = 0x002
  PT index     = (0x8048123 >> 12) & 0x1FF = 0x048
  Offset       = 0x8048123 & 0xFFF          = 0x123

vm_get_frame() 결과:
  frame PA     = 0x12340000  (예시)
  frame KVA    = ptov(0x12340000) = 0x8004000000 + 0x12340000
               = 0x8016340000

pml4_set_page() 결과:
  PTE value    = vtop(frame->kva) | PTE_P | PTE_W | PTE_U
               = 0x12340000 | 0x001 | 0x002 | 0x004
               = 0x12340007

재실행 시 guest PA:
  0x12340000 + 0x123 = 0x12340123
  → QEMU: RAMBlock.host + 0x12340123

이 예시에서는 vm_get_frame()이 PA 0x12340000인 frame을 돌려준다. pml4_set_page()가 해당 frame과 PTE flags를 결합해 mapping을 만들면, 재실행된 명령어의 page offset 0x123이 유지되어 guest PA 0x12340123에 접근한다.

PintOS의 기본 메모리와 swap 크기를 page 단위로 환산하면 다음과 같다.

USER_POOL 기본 크기 = ~32 MB (실제 물리 메모리의 절반)
1 page             = 4 KB = 0x1000
최대 user frame 수 ≈ 32 MB / 4 KB = 8192 frames

swap disk          = 4 MB (기본)
swap slot 수       = 4 MB / 4 KB = 1024 slots
1 slot             = 8 sectors (8 × 512 = 4096 bytes)

코드 좌표

page fault의 판단에서 시작하려면 vm_try_handle_fault()를 먼저 보고, 실제 claim 과정은 vm_do_claim_page()와 vm_get_frame()으로 이어서 볼 수 있다. page type별 데이터 준비와 방출은 uninit.c, anon.c, file.c에 나뉘며, 하드웨어 page table을 바꾸는 동작은 threads/mmu.c에 있다.
