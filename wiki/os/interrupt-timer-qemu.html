QEMU 타이머 인터럽트

QEMU 타이머 인터럽트

끝나지 않는 코드가 CPU를 계속 점유하더라도 OS는 타이머 인터럽트를 통해 주기적으로 제어권을 되찾는다. QEMU는 이 과정을 가상 PIT, PIC, guest CPU interrupt state로 재현한다.

타이머 인터럽트와 선점

어떤 스레드가 다음 코드를 실행한다고 하자.

이 코드는 자발적으로 yield()를 호출하지 않는다. 그래도 운영체제는 CPU의 제어권을 되찾을 수 있어야 한다. 그렇지 않으면 다른 스레드의 실행뿐 아니라 키보드 입력, 디스크 완료, 타임아웃 처리도 멈춘다.

운영체제는 이런 상황에서 **타이머 인터럽트(timer interrupt)**를 이용한다. CPU는 현재 명령어를 계속 실행하므로, 실행 중인 코드가 스스로 멈추지 않으면 운영체제가 일반적인 함수 호출만으로 중간에 끼어들 수 없다. 그래서 OS는 CPU 바깥의 타이머 장치가 일정한 간격으로 interrupt를 발생시키도록 설정한다. interrupt가 발생하면 OS는 잠시 제어권을 얻어 시간을 계산하고 스케줄링 여부를 판단한다.

따라서 스케줄러가 스스로 CPU를 빼앗는 것은 아니다. 타이머 인터럽트가 스케줄러를 실행할 기회를 만들고, 실제로 어느 스레드를 실행할지는 운영체제의 스케줄링 정책이 결정한다.

QEMU·PintOS 타이머 인터럽트 흐름

QEMU에서 실행되는 PintOS의 타이머 선점은 네 층으로 나눠 볼 수 있다.

층하는 일이 문서의 대표 증거

Interrupt controller장치 신호를 CPU interrupt vector로 전달한다PintOS 8259A PIC remap, QEMU i8259.c
CPU interrupt entry현재 register를 저장하고 handler로 들어간다PintOS intr-stubs.S, intr_handler()
OS scheduler policytick을 세고 필요하면 양보한다PintOS thread_tick(), TIME_SLICE

이 흐름을 읽을 때는 QEMU와 PintOS의 역할을 구분해야 한다.

  • QEMU는 PintOS 스레드를 고르지 않는다.
  • PintOS는 실제 host 타이머를 직접 만지지 않는다.
  • timer interrupt는 둘 사이의 경계에서 “PintOS가 하드웨어라고 믿는 사건”으로 보인다.

타이머 주파수와 time slice

PintOS의 기본 타이머 주파수는 TIMER_FREQ = 100이다.

값의미
PIT 입력 주파수1,193,180 Hz
TIMER_FREQ100 Hz
count = 1193180 / 10011,932 (≈ 0x2E9C)
1 tick≈ 10 ms
TIME_SLICE4 ticks = ≈ 40 ms

A 스레드가 계속 계산하고 있고 B 스레드가 READY 상태라고 하자.

여기서 tick 103에 스케줄링한 주체는 QEMU가 아니라 PintOS다. QEMU는 장치 신호와 CPU interrupt 사건을 흉내 낸다. A를 계속 실행할지 B로 전환할지는 PintOS가 결정한다.

PintOS에서 interrupt가 처리되는 과정

8254 PIT를 100Hz로 설정한다

PintOS의 timer 초기화 코드는 8254 PIT(Programmable Interval Timer)를 설정한다.

  • PintOS 저장소 상대 경로 pintos/devices/timer.c
  • PintOS 저장소 상대 경로 pintos/include/devices/timer.h

설정의 기준은 TIMER_FREQ = 100이다.

timer_init()은 PIT 입력 주파수를 TIMER_FREQ로 나눈 count를 계산해 I/O port에 쓴다.

0x40과 0x43은 메모리 주소가 아니라 x86 I/O port다. PintOS가 outb를 실행하면 QEMU의 PIT I/O port 모델이 이 쓰기를 받는다.

IRQ0을 vector 0x20으로 전달한다

PC의 8259A PIC는 오래된 기본 설정에서 IRQ 번호를 CPU exception vector와 겹치게 전달할 수 있다. PintOS는 PIC를 다시 설정해 외부 IRQ를 0x20..0x2f 범위로 옮긴다.

  • PintOS 저장소 상대 경로 pintos/threads/interrupt.c

따라서 PIT의 IRQ0은 PintOS에서 interrupt vector 0x20으로 보인다. timer_init()이 intr_register_ext(0x20, timer_interrupt, ...)를 호출하는 이유도 여기에 있다.

interrupt entry에서 register를 저장한다

CPU가 interrupt를 받아 handler로 들어갈 때는 원래 실행하던 상태를 보존해야 한다. PintOS의 interrupt stub은 register를 stack에 저장한 뒤 intr_handler()를 호출한다.

  • PintOS 저장소 상대 경로 pintos/threads/intr-stubs.S

저장된 영역은 struct intr_frame으로 해석된다. CPU register 실행에서 본 것처럼 register는 실행 중인 코드의 현재 상태를 나타낸다.

timer_interrupt가 tick을 센다

  • PintOS 저장소 상대 경로 pintos/devices/timer.c

이 코드베이스에는 alarm-clock 과제 구현이 들어 있어 thread_awake(ticks)도 호출한다. 선점 흐름에서는 ticks++와 thread_tick()이 직접 관련된다.

thread_tick이 TIME_SLICE를 검사한다

  • PintOS 저장소 상대 경로 pintos/threads/thread.c

thread_tick()은 여기서 바로 schedule()을 호출하지 않는다. 외부 interrupt 처리 중에 sleep하거나 복잡한 스케줄링을 직접 실행하면 위험하므로, PintOS는 interrupt에서 나가기 직전에 yield하라는 표시만 남긴다. 그 이유는 intr yield on return() 이유에서 별도의 질문으로 다룬다.

QEMU에서 가상 하드웨어가 동작하는 과정

PC machine이 i8259와 i8254를 만든다

QEMU에서 PintOS가 보는 PC 하드웨어는 board 초기화 코드에서 만들어진다.

  • hw/i386/pc.c
  • hw/i386/isapc.c

PIC는 pc_i8259_create()로 만들어진다. 일반 TCG 경로에서는 i8259_init(..., x86_allocate_cpu_irq())를 통해 CPU 쪽 interrupt 입력에 연결된다.

PIT는 pc_basic_device_init() 안에서 만들어진다.

여기서 0x40은 PintOS가 outb(0x40, ...)로 접근한 PIT data port base다.

i8254가 guest의 port write를 받는다

  • hw/timer/i8254.c
  • include/hw/timer/i8254.h

QEMU의 PIT 모델은 PIT_FREQ를 사용한다.

PintOS가 port 0x43과 0x40에 값을 쓰면 QEMU의 pit_ioport_write()가 이를 받아 channel mode와 count를 갱신한다. count가 로드되면 QEMU는 다음 transition 시간을 다시 계산한다.

i8254가 IRQ line을 올리고 내린다

PIT output이 바뀌면 QEMU는 IRQ line level을 변경한다.

  • hw/timer/i8254.c

이 호출은 PintOS 스레드를 바꾸라는 뜻이 아니다. 가상 PIT의 출력선을 올리거나 내리는 하드웨어 동작을 QEMU 내부 callback으로 표현한 것이다.

i8259가 IRQ0 pending을 CPU에 전달한다

QEMU의 i8259 모델은 IRQ line 변화를 받으면 IRR(Interrupt Request Register)에 pending bit를 세운다. 이어서 필요하면 CPU 쪽 interrupt line을 올린다.

  • hw/intc/i8259.c

PC machine에 APIC/IOAPIC이 함께 있는 구성에서는 QEMU apic.c도 interrupt pending을 CPU에 알리는 경로에 포함될 수 있다.

  • hw/intc/apic.c

PintOS가 보는 타이머 인터럽트는 QEMU 내부에서 i8254, i8259/IOAPIC/APIC, guest CPU interrupt state가 차례로 이어진 결과다.

실제 운영체제와의 범위 차이

실제 OS도 타이머를 스케줄링과 시간 관리에 사용하지만, 이 문서에서 살펴본 PintOS보다 구조가 복잡하다.

Linux에서는 local APIC timer, high-resolution timer, scheduler tick, tickless idle, per-CPU run queue 같은 요소가 함께 작동한다. SMP 환경에서는 CPU마다 실행 큐와 타이머 상태가 있으므로 전역 ready list 하나만으로 설명할 수 없다.

Windows도 timer interrupt와 quantum(시간 할당량)을 스케줄링, timeout, wait 깨우기 등에 사용한다. 이 과정에는 handle, dispatcher object, DPC 같은 구조도 함께 등장한다.

타이머 장치APIC timer, HPET, TSC deadline 등 다양8254 PIT 하나
CPU 수SMP (per-CPU timer, per-CPU run queue)단일 CPU
스케줄링CFS (weighted fair), RT class, deadline classround-robin + priority
ticklessCONFIG_NO_HZ (idle 시 tick 생략)항상 100Hz tick
time slicevruntime 기반, 동적 (최소 0.75ms ~ 수십ms)고정 4 ticks (≈ 40ms)

값으로 흐름 확인하기

PIT count 계산

PintOS는 TIMER_FREQ = 100을 목표로 count를 계산한다.

QEMU의 PIT_FREQ는 1,193,182다. 두 값은 문서와 구현에서 흔히 보이는 PIT 기준값 차이에 가깝다. 이 문서에서 흐름을 이해할 때는 약 100Hz, 즉 약 10ms마다 IRQ0이 발생한다는 관계를 사용한다.

tick과 time slice 계산

따라서 timer_sleep(20)은 대략 20 ticks * 10 ms = 200 ms로 해석할 수 있다. 정확한 wall-clock 시간은 QEMU clock, host scheduling, interrupt 지연의 영향을 받는다. PintOS 과제의 논리에서는 스레드를 tick 단위로 깨우고 선점한다는 점이 중요하다.

interrupt frame의 바이트 의미

intr-stubs.S는 register를 stack에 차례로 저장한다.

QEMU 자체에 host debugger를 붙여 실행 경로를 따라갈 때는 guest GDB와 관찰 대상이 다르다.

  • guest GDB: PintOS가 보는 register, memory, timer_interrupt()를 본다.
  • host debugger: QEMU process 안의 pit_irq_timer_update(), pic_set_irq(), apic_update_irq()를 본다.

  • 왜 timer_interrupt() 안에서 바로 schedule()하지 않는가?

  • GDB에서 보는 RIP은 host QEMU process의 RIP인가, guest PintOS의 RIP인가?

다시 설명할 때의 연결 순서

타이머 인터럽트는 실행 중인 코드가 스스로 CPU를 내놓지 않아도 OS가 주기적으로 제어권을 얻도록 한다. PintOS는 8254 PIT를 100Hz로 설정하고 IRQ0을 vector 0x20의 timer_interrupt()로 받는다. thread_tick()은 TIME_SLICE=4를 세며, 만료되면 intr_yield_on_return()을 통해 interrupt에서 복귀하기 직전의 양보를 예약한다.

QEMU는 이 과정에 필요한 i8254, i8259, APIC 같은 가상 하드웨어와 guest CPU interrupt state를 제공한다. 그러나 PintOS의 스케줄링 정책을 해석하거나 실행할 스레드를 직접 선택하지는 않는다. 시간 관계는 100Hz -> 10ms/tick, 4 ticks -> 약 40ms time slice로 연결할 수 있다.
