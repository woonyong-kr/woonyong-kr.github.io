USER_STACK 경계와 스택 크기 제한

USER_STACK 경계와 스택 크기 제한

한 줄 요약: 유저 스택은 USER_STACK 상한에서 RSP가 줄며 아래로 자라지만 무한정 자라면 힙·세그먼트와 충돌하므로 OS가 최대 크기(Linux 기본 RLIMIT_STACK 8 MB)로 제한하고, 하한을 넘는 pf는 스택 확장 거부(SIGSEGV)로 처리한다.

USER_STACK 경계와 스택 크기 제한 차이

유저 스택은 가상 주소 공간의 특정 상한 주소(USER_STACK)에서 아래 방향으로 자란다. 무한정 자라면 힙이나 코드/데이터 세그먼트와 충돌하므로, OS는 스택 최대 크기를 제한한다. 이 문서는 USER_STACK 주소의 의미, 스택 하한 계산, 스택 확장 거부 조건을 다룬다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

CPU/MMU는 “스택 영역”을 특별히 인식하지 않는다. RSP 레지스터가 가리키는 주소에 매핑이 없으면 pf(page fault)가 발생할 뿐이다. 스택의 시작점, 방향(x86에서는 아래로), 최대 크기는 전적으로 OS가 관리한다.

x86-64에서 스택은 아래로 자란다:

  • push rax: RSP를 8 감소시킨 뒤 그 주소에 값을 쓴다
  • call func: RSP를 8 감소시킨 뒤 return address를 쓴다
  • sub rsp, N: RSP를 N만큼 감소시킨다 (지역 변수 공간 확보)

따라서 스택 확장 = RSP가 줄어드는 방향 = 낮은 주소로 이동.

실제 OS (Linux)

Linux에서 유저 스택의 시작점은 프로세스마다 다르다(ASLR 적용). 기본 시작점은 약 0x7FFFFFFFFFFF 근처이며, ASLR이 수 MB 범위에서 무작위 오프셋을 적용한다.

스택 최대 크기는 RLIMIT_STACK으로 제한된다:

$ ulimit -s
8192          # 기본 8 MB (= 8192 KB)

커널은 expand_stack()에서 fault 주소가 현재 VMA 시작보다 아래이지만 RLIMIT_STACK 범위 안이면 VMA를 확장한다. 범위를 넘으면 SIGSEGV를 보낸다.

항목값
기본 RLIMIT_STACK8 MB
hard limit보통 unlimited
ASLR 범위~8 MB 오프셋
스택 VMA 플래그VM_GROWSDOWN

스택 최대 크기는 관례적으로 1 MB로 제한한다. vm_try_handle_fault()에서 스택 확장 여부를 판단할 때 하한 주소를 검사한다:

USER_STACK 경계와 스택 크기 제한 값 추적

USER_STACK        = 0x47480000
PGSIZE            = 0x1000 (4 KB)
최대 스택 크기    = 1 MB = 0x100000 = 256 pages

초기 스택:
  stack_bottom    = USER_STACK - PGSIZE = 0x4747F000
  RSP 초기값      = USER_STACK = 0x47480000
  사용 가능 범위  = [0x4747F000, 0x47480000)  → 4 KB

최대 확장 후:
  스택 하한       = USER_STACK - 1MB = 0x47380000
  사용 가능 범위  = [0x47380000, 0x47480000)  → 1 MB = 256 pages

스택 페이지 계산:
  초기: 1 page (setup_stack에서 할당)
  최대: 256 pages (page fault마다 1 page씩 확장)
  확장 가능 횟수: 255회 (1 → 256)

주소 공간에서 스택의 위치:

0x0000000000       코드/데이터 시작
     ...           ELF 세그먼트, 힙
0x47380000         스택 하한 (최대 확장 시)
     ...           스택 (아래→위로 채워짐)
0x4747F000         초기 stack_bottom
0x47480000         USER_STACK (RSP 초기값)
     ...           (미사용 유저 공간)
0x8004000000       KERN_BASE (커널 영역 시작)

스택 확장 거부 예시

RSP = 0x47400000, fault addr = 0x473FFFFF (push)
  addr >= rsp - 8?          0x473FFFFF >= 0x473FFFF8  ✓
  addr < USER_STACK?        0x473FFFFF < 0x47480000   ✓
  addr >= USER_STACK - 1MB? 0x473FFFFF >= 0x47380000  ✓
  → 확장 허용

RSP = 0x47380010, fault addr = 0x47380008 (push)
  addr >= rsp - 8?          0x47380008 >= 0x47380008  ✓
  addr < USER_STACK?        0x47380008 < 0x47480000   ✓
  addr >= USER_STACK - 1MB? 0x47380008 >= 0x47380000  ✓
  → 확장 허용 (하한 경계)

RSP = 0x47380008, fault addr = 0x47380000 (push)
  → pg_round_down(0x47380000) = 0x47380000
  → 확장 허용 (마지막 페이지)

RSP = 0x47380000, fault addr = 0x4737FFF8 (push)
  addr >= USER_STACK - 1MB? 0x4737FFF8 >= 0x47380000  ✗
  → segfault! 스택 오버플로우

QEMU 에뮬레이션

QEMU는 스택 경계를 인식하지 않는다. guest CPU가 RSP 아래 주소에 접근하면:

  1. softmmu TLB에서 해당 GVA 검색 → miss
  2. PML4 walk → PTE에 present=0 발견
  3. #PF 예외 주입 (vector 14, error code = PF_U | PF_W)
  4. PintOS page_fault() → vm_try_handle_fault() → vm_should_grow_stack() 판단
  5. 확장 허용이면 vm_stack_growth() → vm_alloc_page() → vm_claim_page() → PTE 생성
  6. QEMU softmmu TLB에 새 GVA→HVA 엔트리 추가
  7. 같은 명령어 재실행 → TLB hit → 정상 접근

스택 오버플로우(1 MB 초과)인 경우:

  • vm_should_grow_stack() → false
  • page_fault() → exit(-1) → 프로세스 종료
  • QEMU 관점에서는 단지 guest OS가 예외를 처리한 것일 뿐

관찰 시나리오

시나리오 1: 재귀 함수로 점진적 스택 확장 관찰

깊은 재귀를 유발하는 테스트(예: pt-grow-stk-sc)를 실행하면서:

  1. break vm_stack_growth로 각 확장 이벤트 추적
  2. 첫 호출: stack_bottom이 0x4747F000 → 0x4747E000 (2페이지째)
  3. 재귀가 깊어질수록 stack_bottom이 0x1000씩 감소
  4. stack_usage $rsp로 현재 사용량 모니터링
  5. 256페이지(1 MB)에 도달하면 다음 접근에서 vm_should_grow_stack() → false
  6. 프로세스가 exit(-1)로 종료됨을 확인

시나리오 2: rsp - 32 조건의 의미 확인

PintOS는 fault_addr >= rsp - 32 조건을 사용한다 (Linux의 rsp - 128과 다름):

  1. push 명령어: RSP를 8 감소 → fault_addr = rsp - 8 ✓
  2. sub rsp, 24 + 접근: fault_addr는 rsp - 24까지 가능 ✓
  3. 의도적으로 rsp보다 40 아래에 접근하는 코드를 작성하면:
    • fault_addr < rsp - 32 → vm_should_grow_stack() false → segfault
  4. 이 32바이트 여유는 PUSHA 등 다중 push 명령어 패턴을 수용하기 위한 것
