시스템 콜 진입의 스택 전환과 intr_frame

시스템 콜 진입의 스택 전환과 intr_frame

확인 범위: 이 문서는 x86-64 시스템 콜 경계의 일반 원리를 바탕으로 PintOS의 스택 전환과 intr_frame 구성, QEMU의 CPU 상태 변경 역할을 설명한다. 파일 경로·구조체 크기·필드 오프셋·예시 주소·GDB 기대값은 제시된 PintOS 및 QEMU 코드 경로를 전제로 한 구현별 확인 항목이며, 특정 버전의 실제 실행 기록이나 성능 측정 결과를 뜻하지 않는다.

한 줄 요약: syscall 명령이 LSTAR MSR로 커널 진입점을 잡고 CPL을 0으로 올리면, TSS의 rsp0가 가리키는 커널 스택으로 갈아탄 뒤 유저 레지스터를 intr_frame에 저장한다.

syscall intr_frame 기준

write(1, "hi", 2)를 호출하면 유저 프로그램은 syscall 명령을 실행한다.

그런데 syscall_handler(struct intr_frame *f)는 C 함수다. C 함수라면 인자를 스택과 레지스터 규칙에 맞게 받아야 한다. 그렇다면 질문은 이렇게 바뀐다.

이 질문이 중요한 이유는 GDB에서 현재 $rdi를 보는 것과 f->R.rdi를 보는 것이 같은 뜻이 아니기 때문이다.

syscall 스택 전환 오해

커널은 유저 스택을 그대로 믿으면 안 된다.

유저 프로그램의 %rsp는 유저 주소 공간 안의 값이다. 그 주소가 매핑되어 있지 않을 수도 있고, 악의적으로 커널을 헷갈리게 만들 수도 있다. 커널 함수 호출, 지역 변수, lock 획득, 파일 시스템 접근을 유저 스택 위에서 하면 커널 자체가 깨진다.

그래서 시스템 콜 진입에는 두 일이 필요하다.

  1. 유저가 남긴 register 값을 잃지 않고 저장한다.
  2. 커널 코드는 현재 스레드의 커널 스택에서 실행한다.

이 말은 즉, 시스템 콜은 단순히 “함수 하나 호출”이 아니라 유저 register snapshot 만들기와 스택 전환을 포함하는 경계 통과다.

syscall 스택 전환 차이

PintOS의 x86-64 시스템 콜 진입은 다음 모델로 잡으면 된다.

중요한 점이 하나 있다.

x86-64의 syscall 명령은 interrupt gate처럼 자동으로 struct intr_frame을 만들어주지 않는다. RCX와 R11에 복귀 정보를 남기고, RIP를 커널 진입 주소로 바꾸는 정도의 빠른 경로다. PintOS가 직접 커널 스택으로 옮기고, 직접 intr_frame 모양을 만든다.

PintOS 유저 라이브러리는 syscall wrapper에서 register를 맞춘다.

이때 유저 %rsp는 유저 스택을 가리킨다. 예를 들어 다음처럼 생각할 수 있다.

syscall 명령이 실행되면 CPU 관점에서는 복귀할 주소와 flags가 저장된다.

하지만 아직 syscall_handler()가 받을 struct intr_frame *f는 없다. 그 구조체는 PintOS의 syscall_entry.S가 커널 스택에 직접 쌓아 만든다.

실제 운영체제

Linux와 Windows도 원칙은 같다. 유저 모드 요청이 들어오면 커널은 커널 스택에서 실행되어야 하며, 유저 register 상태를 안전한 형태로 저장한 뒤 syscall 번호와 인자를 해석한다.

다만 실제 OS의 진입 코드는 PintOS보다 훨씬 복잡하다.

실제 OS에서 더 복잡한 이유의미
CPU별 자료구조여러 CPU가 동시에 syscall을 처리한다.
보안 완화speculative execution 취약점, 권한 경계, user pointer 검증을 고려한다.
tracing/audit/seccompsyscall 진입과 반환 사이에 관찰, 필터링, 감사 로직이 붙을 수 있다.
ABI 안정성오래된 프로그램도 같은 syscall ABI로 계속 실행되어야 한다.

x86-64에서 특히 조심할 점은 syscall 명령과 interrupt/trap gate를 섞지 않는 것이다. interrupt gate는 권한 레벨이 바뀔 때 TSS의 커널 스택을 하드웨어가 사용할 수 있지만, syscall fast path는 OS entry code가 스택을 신중하게 다뤄야 한다.

PintOS는 이 복잡한 현실 중 “register를 어디에 저장하고, handler가 무엇을 읽는가”를 보이도록 단순화한 교육용 구현이다.

PintOS

PintOS에서 이 흐름을 잡는 파일은 네 개다.

위치역할
SW_AI-W11-pintos/pintos/lib/user/syscall.c유저 wrapper가 syscall 번호와 인자를 register에 넣는다.
SW_AI-W11-pintos/pintos/userprog/syscall.cMSR_LSTAR를 syscall_entry로 설정하고, syscall_handler()가 intr_frame을 읽는다.
SW_AI-W11-pintos/pintos/userprog/syscall-entry.S커널 스택으로 전환하고 struct intr_frame 모양으로 register를 push한다.
SW_AI-W11-pintos/pintos/userprog/tss.c현재 스레드의 커널 스택 꼭대기를 tss->rsp0에 저장한다.

tss->rsp0은 스케줄링 때마다 바뀐다.

PintOS의 struct thread는 4KB 페이지 안에 놓인다. 그래서 (uint64_t) next + PGSIZE는 그 스레드의 커널 스택 꼭대기를 뜻한다. x86 스택은 아래 주소로 자라므로, 이 꼭대기에서부터 push가 내려오며 intr_frame을 만든다.

여기서 한 가지 단순화도 보인다. syscall-entry.S는 %rbx, %r12를 잠시 저장하기 위해 전역 temp1, temp2를 쓴다. PintOS 과제 환경에서는 이 흐름을 이해하기 쉽지만, 여러 CPU가 동시에 syscall에 들어올 수 있는 실제 OS라면 이런 전역 scratch 공간은 그대로 쓰기 어렵고 CPU별 entry stack이나 per-CPU 자료구조 같은 장치가 필요하다.

QEMU

QEMU는 SYS_WRITE의 의미를 처리하지 않는다.

QEMU가 하는 일은 guest CPU가 syscall 명령을 실행했을 때의 CPU 의미를 재현하는 것이다. 확인한 QEMU TCG 경로에서는 다음 파일이 핵심이다.

위치확인할 것
target/i386/tcg/emit.c.incgen_SYSCALL()이 gen_helper_syscall()을 호출한다.
target/i386/tcg/system/seg_helper.chelper_syscall()이 RCX, R11, RIP, segment/flags 상태를 바꾼다.
target/i386/tcg/system/misc_helper.cguest가 wrmsr로 쓴 MSR_STAR, MSR_LSTAR, MSR_FMASK 값을 QEMU의 guest CPU state에 저장한다.

helper_syscall()에서 중요한 관찰은 이것이다.

즉 QEMU는 “유저가 어디로 돌아가야 하는가”와 “커널 진입 주소가 어디인가”를 CPU 의미대로 바꾼다. 하지만 PintOS의 syscall_handler()를 대신 실행하거나, RAX == SYS_WRITE를 해석해서 파일에 쓰지는 않는다.

여기서 RCX와 R11은 일반 인자 register처럼 보존되는 값이 아니다. x86-64 syscall 규칙에서 RCX는 복귀할 유저 RIP, R11은 유저 RFLAGS snapshot을 담는 특수 register가 된다. PintOS도 이 값을 f->R.rcx, f->R.r11이 아니라 f->rip, f->eflags 필드로 옮긴다.

syscall 스택 전환 코드

1. 유저 wrapper가 register를 맞춘다

파일:

  • SW_AI-W11-pintos/pintos/lib/user/syscall.c

핵심 줄:

이 코드는 write(fd, buffer, size) 같은 C 함수 호출이 결국 syscall ABI register 배치로 바뀐다는 증거다.

2. PintOS가 syscall 진입 주소를 MSR에 쓴다

파일:

  • SW_AI-W11-pintos/pintos/userprog/syscall.c

핵심 줄:

MSR_LSTAR 때문에 syscall 명령의 목적지가 PintOS의 syscall_entry가 된다.

3. PintOS가 현재 스레드의 커널 스택을 TSS에 기록한다

파일:

  • SW_AI-W11-pintos/pintos/userprog/tss.c
  • SW_AI-W11-pintos/pintos/userprog/process.c
  • SW_AI-W11-pintos/pintos/threads/thread.c

핵심 줄:

스케줄러가 다음 스레드를 고르면 process_activate(next)가 호출되고, 그 안에서 tss_update(next)가 실행된다. 그래서 syscall이 들어왔을 때 syscall_entry.S는 “현재 실행 중인 유저 스레드의 커널 스택”을 찾을 수 있다.

4. syscall_entry가 intr_frame을 직접 만든다

파일:

  • SW_AI-W11-pintos/pintos/userprog/syscall-entry.S

핵심 흐름:

movq 4(%r12), %rsp의 4는 임의의 숫자가 아니다. PintOS의 struct task_state는 앞에 4바이트 res1이 있고 바로 뒤에 8바이트 rsp0이 온다. 구조체가 packed이므로 rsp0의 offset이 4바이트가 되고, 그 위치에서 현재 스레드의 커널 스택 꼭대기를 읽는다.

여기서 RDI의 의미가 바뀐다.

시점현재 RDI저장된 f->R.rdi
유저 wrapper 직후첫 번째 syscall 인자아직 없음
syscall_entry가 push하는 동안아직 원래 인자커널 스택에 저장될 준비
movq %rsp, %rdi 이후struct intr_frame *첫 번째 syscall 인자가 snapshot에 보존됨
syscall_handler() 안C 함수 첫 번째 인자 fwrite()의 fd 같은 유저 인자

따라서 syscall handler 안에서 현재 $rdi는 fd가 아니라 f 포인터다. fd는 f->R.rdi에서 읽어야 한다.

5. handler가 snapshot을 읽고 반환값을 snapshot에 쓴다

파일:

  • SW_AI-W11-pintos/pintos/userprog/syscall.c

핵심 줄:

처음 f->R.rax는 syscall 번호다. handler가 끝날 때는 반환값이 된다. syscall_entry.S가 나중에 popq %rax를 하므로, 수정된 f->R.rax가 유저 모드의 반환값으로 돌아간다.

6. QEMU는 syscall CPU 의미만 재현한다

파일:

  • target/i386/tcg/emit.c.inc
  • target/i386/tcg/system/seg_helper.c
  • target/i386/tcg/system/misc_helper.c

핵심 흐름:

QEMU의 이 경로는 PintOS가 MSR_LSTAR에 쓴 값을 guest CPU state의 env->lstar로 보관하고, syscall 때 env->eip를 그 값으로 바꾸는 쪽에 가깝다.

시스템 콜 진입을 이해할 때 핵심은 세 층을 나누는 것이다.

층질문답
CPU/QEMUsyscall 명령은 무엇을 바꾸는가?RCX, R11, RIP, segment/flags 같은 CPU 상태
PintOS entry커널 C 코드가 쓸 안전한 스택은 어디인가?tss->rsp0이 가리키는 현재 스레드의 커널 스택
PintOS handlersyscall 번호와 인자는 어디서 읽는가?커널 스택에 만든 struct intr_frame

현재 register와 saved snapshot을 구분하면 syscall 디버깅에서 가장 흔한 혼동이 줄어든다.

syscall 스택 전환 관련 문서

  • syscall 전체 흐름
    • intr_frame 이후 syscall 번호가 실제 커널 기능으로 이어지는 전체 흐름
  • TSS와 커널 스택
    • tss->rsp0, GDT의 TSS descriptor, TR의 관계를 개념으로 먼저 잡기
  • 유저 포인터 검증
    • f->R.rsi 같은 유저 포인터를 커널이 검증해야 하는 이유
  • CPU 레지스터 실행 모델
    • register snapshot과 현재 register를 구분하는 기본 모델
  • QEMU GDB Stub
    • GDB가 보여주는 guest state와 PintOS snapshot의 차이
  • 스레드 스케줄러
    • 스케줄러가 다음 스레드를 고르고 tss->rsp0 갱신으로 이어지는 흐름
  • syscall 명령
    • syscall 명령의 CPU 의미 상세
  • LSTAR MSR
    • MSR_LSTAR에 진입 주소를 등록하는 메커니즘
  • CPL 권한 전환
    • CPL 0↔3 전환 상세
  • TSS rsp0
    • TSS rsp0가 스케줄링 때마다 갱신되는 흐름
  • intr frame 레이아웃
    • struct intr_frame의 필드별 offset 구조
  • register snapshot
    • register snapshot과 현재 register의 관계
  • do iret() 복원
    • iretq/sysretq 복원 경로
  • syscall handler() 분기
    • handler의 switch 분기 구조
  • x86 64 syscall ABI
    • x86-64 syscall ABI 레지스터 규약
