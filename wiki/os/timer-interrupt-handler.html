타이머 인터럽트 핸들러 timer_interrupt()

타이머 인터럽트 핸들러 timer_interrupt()

timer_interrupt()는 8254 PIT에서 들어온 IRQ0마다 시간 카운터를 올리고, 잠든 스레드와 선점 스케줄링을 한 번씩 확인한다.

타이머 인터럽트 핸들러 변화

timer_interrupt()는 하드웨어 타이머(8254 PIT)가 매 tick마다 발생시키는 IRQ0 인터럽트의 핸들러다. 이 함수는 OS 시간 관리와 선점형 스케줄링의 시작점이다. 매 tick마다 글로벌 tick 카운터를 증가시키고, thread_tick()을 호출해 time slice를 검사하며, alarm clock의 thread_awake()를 호출해 잠든 스레드를 깨운다.

이 함수는 외부 인터럽트 컨텍스트에서 실행되므로 sleep, yield, lock acquire 같은 블로킹 연산을 직접 수행할 수 없다.

상세 설명

하드웨어에서 핸들러까지

하드웨어 타이머는 주기적으로 CPU에 인터럽트를 건다. x86에서는 다음 순서로 timer_interrupt()에 도달한다.

  1. 8254 PIT가 카운터를 감소시키다가 0에 도달하면 IRQ0 펄스를 발생시킨다.
  2. 8259 PIC가 IRQ0를 받아 CPU에 INT 신호를 보낸다.
  3. CPU가 현재 명령어를 완료한 뒤 EFLAGS의 IF(Interrupt Flag)를 확인하고, IF=1이면 인터럽트를 수락한다.
  4. CPU가 IDT(Interrupt Descriptor Table)에서 벡터 0x20에 해당하는 게이트를 찾아 handler로 점프한다.

이 과정은 하드웨어가 자동으로 진행하며, OS는 handler를 등록한다. 8254 PIT 자체의 동작은 i8254 PIT, IRQ 전달은 i8259 PIC, QEMU에서의 흐름은 QEMU timer interrupt에서 다시 찾을 수 있다.

실제 OS (Linux/Windows)

Linux에서 타이머 인터럽트 핸들러는 tick_handle_periodic()이다. HZ 값(보통 250 또는 1000)에 따라 초당 발생 횟수가 달라진다. 최신 Linux는 NO_HZ(tickless) 모드를 지원해 idle 상태에서 불필요한 tick을 억제한다.

Windows는 KiTimerExpiration이 비슷한 역할을 한다. 기본 tick 간격은 약 15.625ms(64 Hz)이지만 고정밀 타이머를 요청하면 1ms까지 줄어든다.

PintOS 구현

PintOS의 타이머 인터럽트 처리 흐름은 초기화, 핸들러 실행, 선점 판단의 세 단계로 이어진다.

1단계: 타이머 초기화 (timer_init())

  • 8254 PIT의 입력 클럭은 1,193,180 Hz다.
  • TIMER_FREQ(기본 100)으로 나누면 카운터 초기값 11,932가 된다.
  • 카운터가 0에 도달할 때마다 IRQ0이 발생하므로, 초당 약 100번 인터럽트가 발생한다.
  • intr_register_ext(0x20, ...)로 벡터 0x20에 timer_interrupt를 등록한다.

2단계: 핸들러 본체 (timer_interrupt())

세 줄은 시간 기록, 선점 검사, 깨울 스레드 확인을 각각 담당한다.

줄동작의미
ticks++글로벌 tick 카운터 증가timer_ticks(), timer_elapsed()의 기준
thread_tick()time slice 검사TIME_SLICE(4) tick 소진 시 intr_yield_on_return()
thread_awake(ticks)sleep_list 확인wake_tick ≤ ticks인 스레드를 READY로 전환

sleep_list와 깨우는 시점의 관계는 sleep list와 wake tick과 alarm clock sleep list Lab에서 이어서 확인할 수 있다.

3단계: 선점 판단 (thread_tick())

  • thread_ticks는 현재 스레드가 실행된 tick 수다. schedule()에서 0으로 초기화된다.
  • TIME_SLICE는 4 tick이다. 4 tick이 지나면 intr_yield_on_return()을 호출한다.
  • intr_yield_on_return()은 인터럽트 핸들러 복귀 시 yield할 것을 예약한다. handler 안에서 바로 schedule()을 호출하지 않는 이유는 intr yield on return() 이유에서 다룬다.

TIME_SLICE 검사만 다시 살펴보려면 TIME SLICE 검사, 인터럽트 복귀 시점의 상태 배치는 intr frame 레이아웃을 참고할 수 있다.

QEMU 에뮬레이션

QEMU의 8254 PIT 에뮬레이션(hw/timer/i8254.c)은 호스트의 타이머(POSIX timer 또는 Windows timer)를 사용해 guest에게 주기적 IRQ0을 전달한다. QEMU TCG 모드에서는 호스트 타이머 해상도에 따라 tick 간격이 약간 불균일할 수 있지만, guest OS 관점에서는 정확한 주기로 인터럽트가 도착하는 것처럼 보인다.

타이머 인터럽트 핸들러 값 추적

PIT 카운터 계산

PIT 입력 클럭     = 1,193,180 Hz
TIMER_FREQ        = 100 Hz
카운터 초기값     = (1,193,180 + 50) / 100 = 11,932
실제 tick 주기    = 11,932 / 1,193,180 ≈ 0.010001 초 ≈ 10.001 ms

Time Slice 계산

TIME_SLICE        = 4 ticks
1 tick             ≈ 10 ms
time slice         ≈ 40 ms

1초 동안 가능한 선점 횟수 = 100 / 4 = 25회

I/O 포트 주소

포트역할
0x40PIT 카운터 0 데이터 (읽기/쓰기)
0x43PIT 제어 레지스터
0x34제어어: 카운터0, LSB+MSB, 모드2(rate generator), 2진수

인터럽트 벡터

PIC는 IRQ07을 벡터 0x200x27에, IRQ815를 0x280x2F에 매핑한다.

관찰 시나리오

시나리오 1: TIME_SLICE 만료 → 선점적 스케줄링

목표: 한 스레드가 4 tick(~40ms) 연속 실행된 뒤 timer_interrupt에 의해 yield되는 전체 과정을 관찰한다.

절차:

  1. 두 스레드(Thread A pri=31, Thread B pri=31)를 생성하는 테스트 실행
  2. GDB 스크립트 1, 2를 설정하고 tick별 thread_ticks 증가를 추적
  3. thread_ticks=4 도달 시 intr_yield_on_return() 호출을 확인
  4. 핸들러 복귀 후 schedule() → 다른 스레드로 전환 확인

예상 결과:

[timer] tick=100 thread=threadA (ticks_in_slice=1)
[timer] tick=101 thread=threadA (ticks_in_slice=2)
[timer] tick=102 thread=threadA (ticks_in_slice=3)
[timer] tick=103 thread=threadA (ticks_in_slice=4)
[timer] PREEMPT: thread=threadA ticks=4 → yield_on_return
   ... iretq 직전 schedule() → context switch
[timer] tick=104 thread=threadB (ticks_in_slice=1)

시나리오 2: timer_sleep → thread_awake

목표: timer_sleep(200) 호출 후 정확히 200 tick 뒤에 sleep_list에서 깨어나는 것을 확인한다.

절차:

  1. 한 스레드가 timer_sleep(200)을 호출하는 테스트 실행
  2. GDB로 thread_sleep 진입 시 wake_tick 값 확인 (현재 ticks + 200)
  3. GDB 스크립트 3으로 매 tick의 thread_awake 검사 관찰
  4. wake_tick에 도달하는 순간 thread_unblock 호출 확인

예상 결과:

[sleep] thread=sleeper wake_tick=350 (current ticks=150)
... (200 ticks 경과)
[timer] awake check: ticks=350, front=sleeper (wake_tick=350) → WAKE
[unblock] sleeper: BLOCKED → READY (pri=31)

타이머 인터럽트 핸들러 점검

timer_interrupt()를 설명할 때는 하드웨어 전달, PintOS handler 본체, 스케줄링 판단을 구분하면 흐름이 선명해진다.

  • 하드웨어 기준: 8254 PIT가 IRQ0을 만들고, 8259 PIC가 CPU의 IDT 벡터 0x20으로 전달한다.
  • PintOS 기준: handler 본체는 ticks++, thread_tick(), thread_awake(ticks) 세 일을 한다.
  • 스케줄링 기준: thread_tick()은 handler 안에서 바로 schedule()을 부르지 않고 intr_yield_on_return()으로 복귀 뒤 yield를 예약한다.

수치로는 TIMER_FREQ=100일 때 1 tick이 약 10ms이고, TIME_SLICE=4일 때 한 스레드의 기본 실행 조각이 약 40ms다. timer_sleep(200)은 약 2초 뒤 thread_awake() 경로에서 READY로 돌아오는 요청이다.

설명을 시작할 때는 다음 문장으로 전체 역할을 잡을 수 있다.

타이머 인터럽트는 시간 카운터를 올리는 함수가 아니라, 시간 관리와 선점 스케줄링을 매 tick마다 이어 주는 연결점이다.
