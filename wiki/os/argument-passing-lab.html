argv는 유저 스택에 어떤 바이트로 놓이는가

한 줄 요약: 유저 프로그램 시작 전 커널은 argv[0]="args-multiple" 같은 문자열 본문과 그 주소 배열, argc=5, argv[argc]=NULL을 정해진 순서로 유저 스택에 직접 쌓아 둬야 한다.

argv 스택 테스트

꼬리에 꼬리를 물면 질문은 이렇게 바뀐다.

  • argc = 5라는 숫자는 어디에 들어갈까?
  • argv[0] = "args-multiple" 문자열은 어느 주소에 놓일까?
  • argv 배열은 문자열 자체를 담을까, 문자열의 주소를 담을까?
  • 왜 argv[argc] = NULL을 꼭 넣어야 할까?
  • QEMU는 이 argv 의미를 알고 있을까, 아니면 그냥 메모리 바이트만 보여줄까?

이 Lab은 PintOS load()가 만든 초기 유저 스택을 주소와 바이트로 계산한다.

argv 스택 배치 혼동

C 프로그램의 main(int argc, char *argv[])는 마법처럼 인자를 받지 않는다.

프로그램이 처음 실행될 때 커널과 유저 런타임은 약속된 위치에 값을 준비한다. 그 값이 틀리면 프로그램은 시작하자마자 잘못된 문자열을 읽거나, argv[i]를 따라가다가 page fault를 낸다.

이 말은 즉, argument passing은 단순 문자열 파싱 과제가 아니다. 실행 파일을 로드한 뒤 첫 유저 코드가 믿고 읽을 초기 스택 ABI를 만드는 작업이다.

따라서 PintOS 로더는 main()이 실행되기 전에 이 결과가 나오도록 RDI, RSI, RSP, 유저 스택 메모리를 맞춰야 한다.

실제 운영체제

Linux에서는 커널의 execve()가 새 프로그램의 주소 공간을 만들고, 초기 유저 스택에 argc, argv, envp, auxiliary vector 같은 정보를 놓는다. 그 뒤 ELF interpreter와 C runtime이 _start에서 이 값을 받아 main(argc, argv, envp)로 넘긴다.

Windows는 Unix식 argv 스택 ABI가 중심이 아니다. 프로세스는 명령줄 문자열과 process parameters를 받으며, C runtime이 GetCommandLineW() 계열의 정보를 파싱해 argc/argv 형태로 만들어 줄 수 있다. Win32 프로그램 관점에서는 wWinMain처럼 다른 진입 형태도 흔하다.

PintOS는 이 현실을 크게 줄인다. 환경 변수, auxiliary vector, 동적 링커, 유니코드 명령줄 정책은 다루지 않고, 과제 테스트가 요구하는 argc와 argv만 만든다.

PintOS

PintOS의 핵심 흐름은 pintos/userprog/process.c의 load() 안에 있다.

  1. strtok_r(fn_copy, " ", &save_point)로 명령줄을 token으로 나눈다.
  2. filesys_open(argv[0])로 실행 파일 이름만 열어 ELF를 로드한다.
  3. setup_stack(if_)로 USER_STACK - PGSIZE부터 USER_STACK까지 한 페이지를 매핑한다.
  4. 각 문자열을 스택에 역순으로 복사한다.
  5. 스택 포인터를 8바이트 경계로 내린다.
  6. argv[argc] = NULL을 쌓는다.
  7. 문자열 주소들을 8바이트 포인터로 쌓는다.
  8. RDI = argc, RSI = argv 시작 주소, RSP = fake return address 위치로 맞춘다.

이 코드베이스에서는 USER_STACK이 다음 값이다.

그리고 setup_stack()은 Project 2, 즉 #ifndef VM 빌드에서 이 주소 바로 아래 한 페이지를 실제 유저 페이지로 매핑한다. 같은 파일의 #else 아래에는 Project 3 이후 VM용 setup_stack()이 따로 있으며, 현재 코드에는 lazy stack setup을 채울 TODO가 남아 있다.

현재 구현에서 보이는 교육용 제한도 같이 기억해야 한다.

  • argv[64] 배열을 사용하므로 token 개수는 최대 64개로 제한된다.
  • 스택은 처음에 한 페이지뿐이므로 문자열과 포인터가 4096B를 넘는 상황은 실제 OS처럼 정교하게 처리하지 않는다.
  • 환경 변수, auxiliary vector, shell quoting, Unicode command line 규칙은 다루지 않는다.

QEMU

QEMU는 argc나 argv의 의미를 처리하지 않는다.

QEMU 관점에서는 다음 일만 보인다.

  • guest CPU가 PintOS 커널 코드를 실행한다.
  • PintOS가 guest memory의 유저 스택 페이지에 바이트를 쓴다.
  • do_iret() 뒤 guest register의 RSP, RDI, RSI, RIP가 유저 코드 시작값으로 바뀐다.
  • QEMU gdbstub은 guest register와 guest memory를 GDB에 보여준다.

관련 QEMU 위치:

  • target/i386/gdbstub.c
    • x86_cpu_gdb_read_register
  • gdbstub/gdbstub.c
    • handle_read_mem
    • handle_write_mem

이 말은 즉, argv[2]가 "arguments"라는 해석은 PintOS와 유저 프로그램의 약속이다. QEMU는 0x4747ffed 주소에 어떤 바이트들이 있는지만 읽고 쓸 수 있게 해준다.

PintOS의 단순화에서 특히 조심할 점은 공백 처리다. args-dbl-space 테스트는 two spaces!처럼 공백이 두 번 있어도 빈 인자를 만들지 않는다. 현재 코드의 strtok_r() 사용은 연속 공백을 구분자로 소비하므로 기대 결과가 two, spaces! 두 인자로 나온다.

argv 스택 배치 코드

확인할 핵심 위치는 다음이다.

  • PintOS 저장소 상대 경로 pintos/userprog/process.c
    • load(): argv[64], strtok_r, filesys_open(argv[0])
    • setup_stack(): USER_STACK 아래 한 페이지 매핑
    • 문자열 역순 복사: memcpy(stack_p, argv[argi], size)
    • 포인터 배열 적재: *(uintptr_t *) stack_p = (uintptr_t) argv[n]
    • register 설정: if_->R.rdi = argc, if_->R.rsi = (uint64_t) stack_p
    • fake return address 적재: stack_p -= 8, memset(stack_p, 0, 8), if_->rsp = (uintptr_t) stack_p
  • PintOS 저장소 상대 경로 pintos/include/threads/vaddr.h
    • USER_STACK = 0x47480000
    • PGSIZE = 4096
  • PintOS 저장소 상대 경로 pintos/tests/userprog/args.c
    • argv가 8바이트 정렬인지 검사
    • argv[argc] == NULL까지 출력
  • PintOS 저장소 상대 경로 pintos/tests/userprog/args-multiple.ck
    • 기대 출력
  • target/i386/gdbstub.c
    • x86_cpu_gdb_read_register: guest CPU register 값을 GDB 형식으로 읽어 준다.
  • gdbstub/gdbstub.c
    • handle_read_mem: GDB의 memory read 요청을 guest memory read로 연결한다.

argv 스택 배치 GDB

PintOS GDB에서 아래 순서로 보면 가장 직접적이다.

  1. load에 breakpoint를 걸고 file_name과 argc를 확인한다.

  6. args-multiple 또는 args-dbl-space 테스트 출력과 비교한다.

정리

  • argc는 RDI에, argv 시작 주소는 RSI에 들어간다.
  • 문자열 바이트는 유저 스택 위쪽에 놓이고, argv 배열은 그 문자열들의 주소를 담는다.
  • argv[argc] = NULL은 인자 배열의 끝을 알려주는 sentinel이다.
  • 현재 PintOS 코드는 strtok_r()로 공백을 단순 분리하므로 연속 공백은 빈 인자를 만들지 않는다.
  • QEMU는 이 정책을 처리하지 않고, guest register와 guest memory를 보여주는 하드웨어 역할만 한다.
