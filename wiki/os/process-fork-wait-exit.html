fork/wait/exit 흐름

fork()가 부모-자식 관계를 만들고, exit()가 종료 상태를 남기며, wait()가 그 상태를 회수한다. 세 함수는 따로 외우기보다 같은 생명주기 안에서 봐야 한다.

부모와 자식 사이에 남는 상태

fork() 이후에는 부모와 자식이 독립적으로 실행되므로 종료와 대기의 순서가 고정되지 않는다. 부모가 먼저 wait()를 호출할 수도 있고, 자식이 먼저 exit()할 수도 있다. fork()는 현재 프로세스의 복제본을 만들고, exit()는 종료 코드를 남기며, wait()는 부모가 그 코드를 회수하게 한다.

따라서 세 함수의 관계는 호출 순서만으로 설명할 수 없다. 자식이 아직 실행 중이면 부모가 기다릴 장소가 필요하다. 자식이 먼저 종료되면 부모가 나중에 읽을 상태를 보관해야 한다. 부모가 기다리지 않고 종료하면 남은 상태를 다른 방식으로 정리해야 한다. 결국 이 흐름은 부모와 자식 사이에 남은 상태를 언제, 누가 회수하느냐의 문제다.

운영체제마다 상태를 남기는 방식

Linux와 Windows도 종료를 기다리고 종료 코드를 회수하지만, 프로세스 생성과 상태 보존 방식은 다르다.

Linux:

  • fork() → clone() → copy_process(): struct task_struct를 복제하고, copy_mm()으로 주소 공간을 복제한다(COW). copy_files()로 fd table을 복제한다.
  • 자식이 exit() → do_exit() → exit_notify(): 자식은 zombie 상태(EXIT_ZOMBIE)가 된다. struct task_struct는 남아 있고 exit code가 exit_code 필드에 저장된다.
  • 부모가 wait4()/waitpid() → wait_task_zombie(): zombie의 exit code를 읽고 release_task()로 task_struct를 완전 해제한다.
  • orphan 처리: 부모가 먼저 죽으면 forget_original_parent() → find_new_reaper()로 init(pid 1) 또는 subreaper가 입양한다.

Windows:

  • CreateProcess()는 fork와 다르게 새 프로그램을 즉시 로드한다 (fork+exec에 해당).
  • 종료는 ExitProcess() → NtTerminateProcess().
  • 부모는 WaitForSingleObject(hProcess, ...)로 자식 종료를 대기하고, GetExitCodeProcess()로 종료 코드를 읽는다.
  • Windows에는 orphan/zombie 개념이 약하다. 프로세스 핸들을 닫으면 커널 오브젝트가 해제된다.

PintOS에서는 child_status가 상태를 잇는다

PintOS에서는 struct thread와 별도로 둔 child_status가 fork, wait, exit 사이의 상태를 보존하고 두 세마포어가 실행 순서를 맞춘다.

핵심 자료구조:

자식이 exit하면 struct thread는 곧 palloc_free_page()로 해제된다. 이때 부모가 아직 wait()를 호출하지 않았다면 struct thread 안에 둔 exit status도 함께 사라진다. child_status는 malloc()으로 따로 할당되므로 thread 해제와 무관하게 살아남아 부모의 나중 호출까지 종료 상태를 보존할 수 있다.

child_status의 생명주기는 fork에서 시작해 wait 또는 orphan 정리에서 끝난다.

단계동작child_status 상태
forkmalloc(cs), sema_init(fork/wait, 0)tid=TID_ERROR, exited=false
thread_create 성공cs->tid = tidtid 확정
__do_fork 완료sema_up(&fork_sema)fork_success=true
child exitcs->exit_status=N, cs->exited=true, sema_up(&wait_sema)zombie 상태
parent waitsema_down(&wait_sema), 읽기, free(cs)해제
parent dies firstcs->orphaned=true, orphan_list로 이동orphan 상태
orphan child exitfinish_self_status() → free(cs)해제

이 생명주기를 실제 함수 호출 순서로 나누면 fork에서는 초기화 완료를 기다리고, wait에서는 종료 알림을 기다리며, exit에서는 상태를 남긴 뒤 소유권에 따라 레코드를 정리한다.

fork: 자식 초기화가 끝날 때까지 기다리기

wait: 종료 알림을 기다린 뒤 상태 회수하기

process_wait(child_tid)는 부모의 child_status_list에서 해당 자식을 찾는다. 레코드가 없으면 -1을 반환한다. 찾은 자식을 아직 wait하지 않았다면 기다린 사실을 표시하고 wait_sema를 내린다. 자식이 이미 종료했다면 즉시 통과하고, 아직 실행 중이면 종료 알림까지 BLOCKED 상태로 기다린다. 깨어난 부모는 exit status를 읽고 레코드를 해제한다.

exit: 상태를 남기고 소유권에 따라 정리하기

자식은 exit status를 기록하고 열린 파일과 주소 공간을 정리한다. finish_self_status()는 exited=true로 바꾸고 wait_sema를 올려 기다리는 부모를 깨운다. 부모가 먼저 종료하는 경우에는 이미 끝난 자식의 레코드를 해제하고, 실행 중인 자식의 레코드는 orphaned=true로 표시해 orphan_list로 옮긴다. orphan 자식은 나중에 종료할 때 자신의 레코드를 해제한다.

같은 구조에서 달라지는 세 가지 실행 순서

앞의 함수들이 맡는 역할은 같지만, 부모와 자식 가운데 누가 먼저 wait하거나 exit하는지에 따라 child_status가 머무는 시간과 해제 주체가 달라진다.

QEMU가 재현하는 범위

QEMU는 fork/wait/exit의 의미를 직접 해석하지 않는다. PintOS 커널이 메모리를 복사하고 스레드를 전환하며 레코드를 할당하거나 해제하는 동안, QEMU는 그 작업을 구성하는 guest 명령어와 CPU 효과를 재현한다.

PintOS 동작QEMU가 재현하는 것
fork의 pml4 복사guest memory read/write (페이지 복사는 guest 커널 코드)
sema_down으로 부모 BLOCKEDguest thread가 schedule()을 호출해 다른 thread로 전환 — QEMU는 그냥 다음 guest 명령어 실행
exit의 pml4 해제guest가 palloc_free_page 호출 — guest memory 관리 구조 변경일 뿐
syscall(SYS_FORK)CPU의 syscall 명령어 효과 재현 → RIP를 LSTAR로 전환
child_status malloc/freeguest의 palloc 또는 malloc — guest 메모리 풀 내부 조작

TCG 관점 상세:

  • process_fork()의 thread_create() 호출은 새 커널 스택 페이지를 palloc_get_page()로 할당한다. QEMU는 guest physical memory 내에서 페이지를 “사용 중”으로 표시하는 guest 코드를 실행할 뿐이다.
  • __do_fork()에서 PML4를 복사할 때 memcpy나 페이지별 복사가 일어난다. TCG는 이를 대량의 guest memory load/store로 번역하며, 이 과정에서 softmmu TLB miss가 빈번할 수 있다.
  • fork/wait의 세마포어 동기화(sema_down/sema_up)에서 intr_disable()이 cli 명령어를 실행한다. TCG는 guest EFLAGS.IF를 0으로 설정하고, 이 동안 가상 timer interrupt 전달을 보류한다.
  • KVM 모드에서는 cli/sti가 guest CPL 0에서 실행되므로 VM exit 없이 처리된다.

GDB로 흐름 관찰하기

다음 스크립트는 fork 초기화, wait/exit 동기화, child_status의 생애와 orphan·zombie 상태를 각각 관찰하기 위한 좌표다. 스크립트 자체는 관찰 방법을 제시하며, 실행 결과를 포함하지는 않는다.

1. fork 핸드셰이크 타이밍 — fork_sema 상태 추적

(gdb) b process_fork
(gdb) commands
  silent
  printf "=== FORK START: parent tid=%d(%s) ===\n", \
    thread_current()->tid, thread_current()->name
  continue
end
(gdb) # 부모가 sema_down하는 지점
(gdb) b process.c:210
(gdb) commands
  silent
  printf ">>> parent sema_down(fork_sema): waiting for child init\n"
  continue
end
(gdb) # 자식이 sema_up하는 지점
(gdb) b process.c:391
(gdb) commands
  silent
  printf "<<< child sema_up(fork_sema): init complete, tid=%d\n", \
    thread_current()->tid
  continue
end

2. wait/exit 세마포어 상태 관찰

(gdb) b process_wait
(gdb) commands
  silent
  printf "=== WAIT: parent tid=%d waiting for child_tid=%d ===\n", \
    thread_current()->tid, child_tid
  continue
end
(gdb) # sema_down(&wait_sema) 직전
(gdb) b process.c:500
(gdb) commands
  silent
  printf ">>> parent sema_down(wait_sema): cs->exited=%d\n", cs->exited
  continue
end
(gdb) # finish_self_status에서 sema_up
(gdb) b process.c:570
(gdb) commands
  silent
  printf "<<< child sema_up(wait_sema): exit_status=%d\n", cs->exit_status
  continue
end

3. child_status 레코드 생애 추적

(gdb) # 할당 시점
(gdb) b process_fork
(gdb) commands
  silent
  printf "CS ALLOC: fork child, parent=%d\n", thread_current()->tid
  continue
end
(gdb) # 해제 시점 — reparent_or_reap에서 free
(gdb) b reparent_or_reap_children
(gdb) commands
  silent
  printf "CS REAP CHECK: parent=%d scanning %d children\n", \
    thread_current()->tid, \
    list_size(&thread_current()->child_status_list)
  continue
end

4. orphan 발생 탐지 — 부모 exit 시 살아있는 자식

(gdb) b reparent_or_reap_children
(gdb) commands
  silent
  set $e = thread_current()->child_status_list.head.next
  while ($e != &thread_current()->child_status_list.tail)
    set $cs = (struct child_status *)((char *)$e - offsetof(struct child_status, elem))
    if !$cs->exited
      printf "  ORPHAN: child not yet exited, will be orphaned\n"
    end
    set $e = $e->next
  end
  continue
end

5. zombie 상태 탐지 — exit했지만 wait되지 않은

(gdb) # 특정 부모의 child_status_list에서 exited=true, waited=false인 항목
(gdb) set $parent = thread_current()
(gdb) set $e = $parent->child_status_list.head.next
(gdb) while ($e != &$parent->child_status_list.tail)
  set $cs = (struct child_status *)((char *)$e - offsetof(struct child_status, elem))
  if $cs->exited && !$cs->waited
    printf "ZOMBIE: child exit_status=%d, not yet waited\n", $cs->exit_status
  end
  set $e = $e->next
end

흐름에서 추적할 값

fork에서는 복제할 주소 공간과 fd table, SPT의 크기가 자원 사용량을 결정한다. 다음 계산은 구조와 예시 값을 보여 주며 실제 실행 측정값은 아니다.

fork 시 복사되는 자원 크기:

PML4 테이블 자체   = 4 KB (1 페이지)
유저 페이지 수     = 프로그램 크기에 비례
 예) 코드 4 페이지 + 데이터 2 페이지 + 스택 1 페이지 = 7 × 4 KB = 28 KB
fd table           = 배열 크기 × sizeof(struct file *)
 예) 128 슬롯 × 8 bytes = 1024 bytes
SPT (해시 테이블)  = 항목 수 × sizeof(struct page)

자식이 남기는 종료 상태는 다음 범위와 관례로 설명된다.

exit status 범위:

exit(status) → status는 int (32-bit)
관례:
  0   = 정상 종료
  -1  = 에러 종료 (PintOS 표준)
  >0  = 다양한 에러 코드 (Linux: signal 번호 등)

wait_sema는 자식이 먼저 끝난 경우와 부모가 먼저 기다린 경우를 같은 연산으로 처리한다.

wait 세마포어 동작:

fork 시: sema_init(&child->wait_sema, 0)
exit 시: sema_up(&child->wait_sema)     → value: 0→1
wait 시: sema_down(&child->wait_sema)   → value: 1→0 (즉시 통과)
         또는 value==0이면 BLOCKED       → exit의 sema_up을 기다림
