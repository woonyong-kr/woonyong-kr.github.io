자식 상태 구조체

자식 상태 구조체

확인 범위: 이 문서는 자식의 실행 객체보다 종료 상태 기록이 오래 유지되어야 한다는 일반 원리와 수명·동기화·해제 책임의 선택 기준을 설명하고, 제시된 PintOS 구현을 사례로 구조와 흐름을 해설한다. 코드 위치·필드 크기·Linux 비교 수치·동시성 안전성·QEMU 동작에 관한 내용은 특정 코드와 환경의 검증 결과가 아니라 입력에 제시된 설명이므로, 실제 적용 시 해당 버전의 소스·빌드 환경·실행 기록과 성능 측정으로 별도 확인해야 한다.

자식 스레드가 먼저 사라져도 부모의 wait()는 종료 코드를 받아야 한다. struct child_status는 자식의 실행이 끝난 시점과 부모가 결과를 회수하는 시점 사이에서 종료 정보를 보존한다.

실행 객체와 종료 기록의 수명

자식이 exit()를 호출하면 실행에 쓰이던 struct thread는 곧 정리될 수 있다. 그러나 부모가 아직 wait()를 호출하지 않았다면 종료 코드를 읽을 별도 장소가 필요하다. PintOS는 이 정보를 struct thread에 계속 남겨 두는 대신, 힙에 만든 struct child_status에 보관한다.

두 객체의 수명은 다음처럼 다르다.

%% child_status와 struct thread의 수명 차이
flowchart LR
  cs_alloc["child_status 할당<br/>fork() 시점"]
  cs_live["child_status 유지<br/>fork 성공/실패 통신<br/>exit status 보존<br/>wait 동기화"]
  cs_free["child_status 해제<br/>부모 wait() 완료<br/>또는 orphan 정리"]
  th_alloc["struct thread 할당<br/>thread_create()"]
  th_live["struct thread 유지<br/>실행 상태<br/>스택, pml4, SPT"]
  th_free["struct thread 해제<br/>process_exit()<br/>또는 schedule()"]
  cs_alloc --> cs_live
  cs_live --> cs_free
  th_alloc --> th_live
  th_live --> th_free

struct thread는 자식의 실행이 끝나면 해제할 수 있다. 반면 struct child_status는 부모가 wait()로 결과를 회수하거나, 부모와 자식의 종료 순서에 따라 다른 주체가 정리할 때까지 남아 있어야 한다. 따라서 이 레코드는 종료 코드만 저장하는 것이 아니라 fork 초기화 확인, wait 동기화, orphan 정리에 필요한 상태도 함께 가진다.

Linux zombie와의 차이

입력에 제시된 설명에 따르면 Linux는 별도 힙 레코드 대신 zombie 상태를 사용한다. 프로세스가 exit하면 task_struct가 EXIT_ZOMBIE 상태로 남는다. 메모리와 fd 같은 자원은 대부분 해제되지만, task_struct 자체는 부모가 waitpid()를 호출할 때까지 유지된다.

설계Linux (zombie)PintOS (child_status)
메모리 비용~6KB (task_struct 전체)48B (child_status만)
장점task_struct에 모든 정보 보존경량, thread 해제 즉시 가능
단점zombie 누적 시 메모리 낭비별도 할당/해제 관리 필요
수거 주체부모 waitpid() / init부모 process_wait() / orphan 정리

이 비교의 수치는 특정 환경에서 직접 검증한 결과가 아니라 입력에 제시된 값이다. 뒤에 나오는 구조체 정의에서는 padding을 포함한 크기를 약 80B로 설명하므로, 48B와 80B가 각각 어떤 구성과 계산 기준을 가리키는지는 실제 소스와 빌드 결과로 확인해야 한다.

PintOS 구현을 읽는 순서

PintOS 구현은 구조체의 필드, 부모와 자식이 그 구조체를 가리키는 방법, 수명 상태의 변화, 최종 해제 주체의 순서로 볼 수 있다. 먼저 각 필드가 어떤 사건을 기록하는지 확인하면, 뒤의 process_wait(), reparent_or_reap_children(), finish_self_status()가 같은 레코드를 어떻게 나누어 다루는지 연결해서 이해할 수 있다.

구조체와 필드

include/threads/thread.h:33 — 구조체 정의:

각 필드는 서로 다른 시점 사이에 정보를 전달한다. tid는 부모가 기다릴 자식을 찾게 하고, exit_status는 자식의 종료 결과를 보존한다. waited, exited, orphaned는 부모와 자식 중 누가 어떤 단계를 이미 수행했는지 나타낸다. 두 semaphore는 fork 초기화와 자식 종료라는 서로 다른 사건을 기다리는 데 쓰인다.

부모와 자식이 같은 레코드를 찾는 방법

부모는 child_status_list를 순회하여 특정 tid에 해당하는 레코드를 찾고 wait()를 처리한다. 자식은 self_status를 통해 자신의 레코드에 바로 접근하여 exit_status와 종료 상태를 기록하고 sema_up을 호출한다. 같은 struct child_status를 부모는 목록의 원소로, 자식은 직접 포인터로 참조하는 구조다.

생성부터 해제까지의 상태 변화

fork 시 레코드를 할당한 뒤 fork_sema로 자식 초기화 결과를 기다린다. fork가 성공하면 레코드는 자식이 실행되는 동안 유지된다. 이후 자식이 먼저 종료하면 부모의 wait()가 레코드를 회수하고, 부모가 먼저 종료하면 레코드에 orphan 상태를 남겨 자식이 나중에 정리하도록 한다.

stateDiagram-v2
    [*] --> Allocated: fork() — malloc + 초기화
    Allocated --> ForkWait: fork_sema로 동기화
    ForkWait --> Active: fork 성공 (fork_success=true)
    ForkWait --> Failed: fork 실패 (fork_success=false)
    Active --> ChildExited: 자식 exit (exited=true, sema_up)
    Active --> Orphaned: 부모 먼저 exit (orphaned=true)
    ChildExited --> Reaped: 부모 wait() (free)
    Orphaned --> SelfFree: 자식 exit 시 자기가 free
    Failed --> Reaped: 부모가 free
    Reaped --> [*]
    SelfFree --> [*]

해제 책임은 부모와 자식의 종료 순서 및 wait 여부에 따라 달라진다.

부모가 wait하는 경우

process_wait()는 부모 목록에서 tid가 일치하는 레코드를 찾는다. 이미 waited가 설정되어 있으면 중복 wait를 거부한다. 자식이 아직 종료하지 않았다면 wait_sema에서 기다리고, 종료 통지를 받은 뒤 exit_status를 읽어 목록에서 제거하고 해제한다.

process_wait() (userprog/process.c L485–508) — 규칙 1:

부모가 먼저 종료하는 경우

부모가 종료할 때는 자식별 상태에 따라 처리가 갈린다. 이미 종료했지만 wait하지 않은 자식의 레코드는 부모가 즉시 해제한다. 아직 실행 중인 자식의 레코드에는 orphaned = true를 기록하고 orphan_status_list로 옮긴다. 이 표시는 나중에 자식이 자신의 레코드를 해제해야 한다는 뜻이다.

reparent_or_reap_children() (userprog/process.c L534–558) — 규칙 2, 3 준비:

자식이 종료하는 경우

자식은 finish_self_status()에서 자신의 레코드를 종료 상태로 바꾸고 wait_sema를 올린다. 부모가 기다리고 있었다면 이 통지로 깨어난다. 부모가 이미 종료하여 orphaned가 설정되어 있고 wait 처리도 없었다면, 자식이 직접 목록에서 레코드를 제거하고 해제한다.

finish_self_status() (userprog/process.c L561–578) — 규칙 3 실행:

종료 순서별 동작

입력에 제시된 분석은 PintOS가 단일 CPU이고 process_exit()가 reparent_or_reap_children() 다음에 finish_self_status()를 호출한다는 전제에서 다음 동작을 설명한다. 이 표는 실제 실행으로 검증한 결과가 아니라 해당 전제와 코드 설명에서 도출한 분석이다.

시나리오처리 흐름
부모 wait 중 자식 exit자식이 sema_up(&wait_sema)로 부모를 깨운다. 부모가 free(cs)하고, 자식은 cs->orphaned가 false이므로 해제하지 않는다.
부모 exit 후 자식 exit부모가 orphaned=true를 설정하고 레코드를 orphan_status_list로 옮긴다. 자식은 종료 시 orphaned && !waited를 확인하고 직접 해제한다.
자식 exit 후 부모 waitcs->exited=true이므로 부모는 sema_down 없이 종료 코드를 회수하고 레코드를 해제한다.
자식 exit 후 부모 exit (wait 없이)부모의 reparent_or_reap_children()가 exited && !waited인 레코드를 즉시 해제한다.

이 설계에서 중요한 판단 대상은 단순히 자식이 종료했는지가 아니다. 부모가 wait했는지, 어느 쪽이 먼저 종료했는지, 현재 레코드의 해제 책임이 누구에게 있는지를 함께 보아야 한다.

QEMU와의 관계

입력의 설명에 따르면 QEMU는 child_status를 직접 관리하지 않는다. child_status는 PintOS 커널 내부의 소프트웨어 구조체다. QEMU TCG가 sema_down과 sema_up 등에 해당하는 명령을 번역하여 실행하더라도, 상태 기록과 동기화 절차 자체는 PintOS의 커널 로직에 속한다.

값과 메모리 비용을 읽을 때의 주의점

다음 값은 입력에 제시된 추정과 비교값이며, 특정 소스 버전과 빌드 환경에서 측정된 결과로 확인된 것은 아니다.

항목값
struct child_status 크기 (x86-64)~80B (alignment padding 포함)
semaphore 2개 비용48B (24B × 2)
list_elem 비용16B (prev + next)
프로세스당 child_status 수자식 수만큼 (부모 list에 N개)
Linux zombie task_struct~6,016B
PintOS cs vs Linux zombie 비율~1.3% (80B / 6016B)

입력의 계산에서는 부모가 자식 10개를 fork할 때 child_status 10개가 800B를 차지하고, Linux zombie 10개는 60KB를 차지한다고 설명한다. 구조체 크기와 비교 대상은 아키텍처와 구현에 따라 달라질 수 있으므로 실제 적용 전에는 해당 환경에서 다시 확인해야 한다.
