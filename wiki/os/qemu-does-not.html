QEMU가 하지 않는 일

QEMU가 하지 않는 일

확인 범위: 이 문서는 QEMU가 제공하는 하드웨어 메커니즘과 PintOS가 결정하는 정책을 구분해 문제 조사 위치를 정하는 개념 설명과 선택 기준을 다룬다. 제시된 코드 좌표·상수·GDB 출력·소스 검색 결과와 QEMU의 실제 동작 여부는 특정 버전이나 현재 실행 환경에서 재검증한 결과가 아니므로, 구현별 판단에는 해당 코드와 실행 기록의 별도 확인이 필요하다.

QEMU는 하드웨어처럼 동작하는 환경을 제공하지만, 그 위에서 실행되는 OS의 판단까지 대신하지 않는다. syscall 번호 해석, 프로세스 선택, 파일 시스템 정책은 PintOS 커널 코드의 몫이다.

디버깅할 코드를 어떻게 찾는가

PintOS에서 syscall, 프로세스, 파일 시스템 문제가 생겼을 때는 먼저 QEMU가 제공하는 하드웨어 메커니즘과 guest OS가 결정하는 정책을 구분해야 한다. QEMU는 명령어 실행, 인터럽트 신호 생성, sector I/O와 같은 메커니즘을 재현한다. syscall 번호의 의미, 다음에 실행할 프로세스, 파일과 디렉터리의 구조는 PintOS 커널 코드가 판단한다.

이 구분은 문제를 조사할 위치를 좁히는 기준이다. 다만 증상만으로 QEMU가 정확히 동작했다고 단정할 수는 없다. 먼저 메커니즘이 예상대로 작동했는지 확인한 뒤, 문제가 없다면 OS의 정책과 구현을 살펴봐야 한다.

메커니즘과 정책

여기서 메커니즘은 하드웨어가 동작하는 방식을, 정책은 OS가 자원을 해석하고 배분하는 규칙을 뜻한다.

구분메커니즘 (How)정책 (What/When)
정의하드웨어가 제공하는 동작 원리OS가 결정하는 자원 분배 규칙
주체CPU, MMU, 인터럽트 컨트롤러커널 코드 (스케줄러, syscall 핸들러, VFS)
예시SYSCALL 명령어로 CPL 0 진입syscall 번호 10이 open()인지 결정
예시CR3 교체로 주소 공간 전환어떤 프로세스의 CR3를 로드할지 결정
예시PIT가 IRQ0 신호 생성타이머 인터럽트마다 선점할지 결정

이 문서에서 다루는 QEMU의 역할은 표의 메커니즘 쪽이다. 정책은 guest OS인 PintOS가 실행하는 코드에서 나온다.

QEMU가 판단하지 않는 세 가지

Syscall 번호의 의미

guest에서 SYSCALL 명령어가 실행되면 QEMU가 재현하는 동작은 다음과 같다.

1. RIP를 LSTAR MSR 값으로 교체
2. CS/SS를 커널 세그먼트로 교체
3. RFLAGS에서 IF 등을 마스킹
4. 이전 RIP를 RCX에, RFLAGS를 R11에 저장

이 단계는 제어를 커널로 넘기는 메커니즘이다. RAX에 들어 있는 syscall 번호(예: SYS_WRITE = 10)가 무엇을 뜻하고 어떤 함수를 호출해야 하는지는 QEMU가 해석하지 않는다. QEMU의 관점에서 RAX = 10은 64비트 정수이며, 그 번호를 SYS_WRITE로 연결하는 일은 guest OS의 syscall_handler()가 맡는다.

QEMU: SYSCALL 명령어 → CPL 전환, RIP 점프 (메커니즘)
PintOS: syscall_handler() → RAX 값으로 switch/case 분기 (정책)

프로세스의 관계와 실행 순서

QEMU가 직접 다루는 상태는 다음과 같다.

  • CPUX86State: 레지스터 값 묶음 하나
  • RAMBlock: guest physical memory 한 덩어리
  • CR3: 현재 활성화된 페이지 테이블의 물리 주소

PintOS가 process_create_initd()로 새 프로세스를 만들 때도 QEMU에는 메모리와 CPU 상태의 변화로 보인다.

1. guest가 메모리를 할당한다 (palloc) → RAMBlock 안에서 일어나는 일
2. guest가 struct thread를 초기화한다 → 메모리 쓰기일 뿐
3. guest가 CR3를 교체한다 → QEMU가 TLB flush (메커니즘)
4. guest가 새 RIP로 점프한다 → QEMU가 그 주소의 명령어를 실행 (메커니즘)

프로세스의 수, 부모와 자식의 관계, 다음에 실행할 프로세스는 PintOS가 관리한다. struct thread 배열도 QEMU에는 guest 메모리에 저장된 바이트 배열이며, 그 구조와 필드의 의미는 PintOS 코드가 부여한다.

파일 시스템의 구조와 정책

QEMU의 IDE controller 모델은 sector 단위 I/O를 처리한다.

guest가 I/O 포트 0x1F0~0x1F7에 접근
→ IDE controller 모델이 sector 번호 × 512 byte offset 계산
→ 호스트 파일(pintos.dsk)에서 해당 offset의 512 byte를 읽기/쓰기

파일 시스템의 의미는 이 I/O 위에서 PintOS가 해석한다.

QEMU가 모르는 것누가 아는가
파일 이름PintOS filesys (inode → name)
디렉터리 구조PintOS filesys (dir_lookup)
파일 권한PintOS filesys (deny_write_cnt)
빈 블록 관리PintOS filesys (free_map)
읽기/쓰기 캐싱 정책PintOS buffer cache (해당 시)

QEMU에는 pintos.dsk가 flat byte 배열로 보인다. sector 42에 쓰라는 요청을 받으면 파일의 42 × 512 = 21504 바이트 오프셋에 쓰지만, 그 위치가 어떤 파일이나 디렉터리에 속하는지는 판단하지 않는다.

Linux + KVM에서 보이는 같은 경계

문서에 제시된 Linux + KVM 환경의 대응 관계도 메커니즘과 정책의 구분을 보여준다.

영역KVM(=QEMU 커널 모듈)guest Linux
syscallVM exit 발생시키지 않음 (guest 안에서 처리)syscall_handler에서 번호 해석
프로세스VMCS에 guest 상태 하나만 보관task_struct로 프로세스 관리
파일 시스템virtio-blk로 블록 I/O 전달ext4/btrfs가 정책 결정

PintOS에서 조사할 위치

다음 예시는 증상별로 먼저 살펴볼 경계를 보여준다. 각 결론은 QEMU의 메커니즘이 예상대로 동작하는지 확인했다는 전제에서 적용한다.

증상: "write syscall이 동작하지 않는다"
→ QEMU 문제인가? NO. QEMU는 SYSCALL 명령어를 정확히 실행했다.
→ OS 문제다. syscall_handler()의 분기, 인자 검증, 또는 파일 I/O 로직을 봐야 한다.

증상: "프로세스가 스케줄링되지 않는다"
→ QEMU 문제인가? NO. QEMU는 타이머 인터럽트를 정확히 발생시켰다.
→ OS 문제다. thread_tick(), ready_list, schedule()을 봐야 한다.

증상: "디스크에서 데이터가 깨져서 온다"
→ QEMU 문제인가? 드물지만 가능 (IDE 모델 버그).
→ 대부분 OS 문제. sector 번호 계산, inode 파싱을 봐야 한다.

따라서 write syscall 문제는 syscall_handler()의 분기와 인자 검증, 파일 I/O 로직으로 조사를 이어갈 수 있다. 스케줄링 문제는 thread_tick(), ready_list, schedule()을 살펴볼 대상이다. 디스크 데이터가 깨지는 경우에는 sector 번호 계산과 inode 파싱을 우선 확인하되, IDE 모델의 가능성을 완전히 제외하지 않는다.

QEMU 소스에서 확인할 경계

이 문서가 제시하는 소스 코드의 역할은 다음과 같다.

  • target/i386/tcg/sysemu/ — TCG 코드에 syscall 번호 dispatch table이 없다
  • hw/ide/core.c — 파일 이름이나 디렉터리 파싱 코드가 없다
  • QEMU 코드 전체에 struct thread나 schedule()이 없다 (guest OS의 것)

또한 이 문서는 QEMU 소스에서 SYS_WRITE, SYS_OPEN 같은 상수를 검색하면 0건이라고 설명한다. 이는 QEMU가 PintOS의 syscall 번호를 직접 해석하지 않는다는 점을 확인하기 위한 검색 기준이다. 이 수정본에서는 해당 검색을 다시 실행한 결과로 제시하지 않는다.

GDB에서 값의 의미 구분하기

다음 예제는 같은 값이 QEMU와 PintOS에서 어떻게 다르게 해석되는지 보여준다. 표시된 출력은 이 문서에 포함된 예시이며, 현재 실행 환경에서 검증한 결과는 아니다.

(gdb) info registers rax
rax  0xa  10              ← QEMU는 "10"이라는 숫자만 안다
                           PintOS는 "SYS_WRITE"로 해석한다

(gdb) p thread_current()->tid
$1 = 3                    ← QEMU는 tid라는 개념을 모른다
                           이건 guest 메모리의 struct 필드일 뿐

(gdb) x/4x 0x8004e000     ← QEMU는 이 주소의 바이트만 안다
0x8004e000: 0x03  0x00  0x00  0x00  ← PintOS는 이것이 tid=3임을 안다
