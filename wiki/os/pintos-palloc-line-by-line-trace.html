palloc.c 라인별 해석 Trace

palloc.c 라인별 해석 Trace

확인 범위: 이 문서는 제시된 가정과 vault source snapshot을 바탕으로 palloc.c의 메모리 분할·bitmap·할당 흐름을 설명하는 계산 예시이며, 특정 버전의 실제 구현이나 실행 결과를 검증한 기록은 아니다. 현재 코드의 동작, 행 번호의 대응, 실제 주소·메모리 크기·성능에 관한 판단은 해당 구현의 symbol과 설정, e820 entry, 실행 로그 및 측정 결과를 별도로 확인해야 한다.

한 줄 요약: palloc.c를 byte가 아닌 page 단위(예: 20 MiB usable = 5120 pages)로 읽어, resolve_area_info()→populate_pools()→init_pool()이 e820 메모리를 kernel/user pool로 가르고 bitmap의 false bit로 free page를 공개하기까지를 라인별 숫자 흐름으로 추적한다.

이 문서의 행 번호는 vault source snapshot 기준이다. 현재 구현을 확인할 때는 행 번호가 아니라 함수·구조체 symbol 검색을 정본으로 사용한다.

palloc.c 라인별 해석 쟁점

palloc.c를 보면 base_mem, ext_mem, user_pages, kern_pages, bitmap, pool->base 같은 값이 한꺼번에 나온다.

이 문서의 목표는 코드를 “무슨 뜻인지”가 아니라 “각 줄이 어떤 숫자를 만들고, 다음 줄에 어떤 재료로 넘어가는지”까지 읽는 것이다.

예시는 단순화를 위해 다음 가정을 쓴다.

실제 실행에서는 e820 entry, 커널 이미지 크기, bitmap 구현 크기, -ul 옵션에 따라 숫자가 달라질 수 있다. 여기서는 계산 감각을 잡는 것이 목적이다.

먼저 잡을 단위

palloc은 byte 단위가 아니라 page 단위 allocator다.

값의미예시
PGSIZE한 page 크기4096 bytes
20 MiBguest usable memory 예시20 * 1024 * 1024 = 20,971,520 bytes
total_pagesusable memory를 page로 나눈 개수20,971,520 / 4096 = 5120 pages
true bitmap bit사용 중 또는 사용 불가능allocator가 주면 안 됨
false bitmap bitfree pageallocator가 줄 수 있음

QEMU에서 보는 palloc

QEMU는 palloc의 존재를 모른다. QEMU가 하는 일은 guest physical memory를 호스트 프로세스의 mmap 영역(RAMBlock)으로 backing하는 것뿐이다.

palloc이 pool->base + PGSIZE * idx로 계산한 kernel VA를 반환할 때, 실제 메모리 접근 경로:

PAL_ZERO 플래그가 붙으면 memset(pages, 0, PGSIZE * page_cnt)가 실행된다. QEMU TCG는 이를 host memset으로 변환하여 RAMBlock의 해당 4 KB 영역을 0으로 채운다.

GDB에서 palloc 결과를 확인할 때:

이 x/4x 명령은 GDB stub이 QEMU에게 guest memory 읽기를 요청하고, QEMU가 RAMBlock에서 해당 offset의 bytes를 반환하는 과정이다.

    C --> D["populate_pools()"]

    D3 --> D4["bitmap 전부 true(사용불가)로 초기화"]
    D4 --> D5["e820 재순회:\nusable_bound 이후 page만\nbitmap false(free)로 열기"]

    E1 --> E2["pool->base + PGSIZE * idx\n= kernel VA 반환"]
    E2 --> F["palloc_free_page(page)"]
    F --> F1["page_idx 계산\nbitmap true → false로 복원"]
