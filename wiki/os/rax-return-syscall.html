RAX의 syscall 번호와 반환값

RAX의 syscall 번호와 반환값

확인 범위: 이 문서는 x86-64에서 RAX가 함수 반환값·syscall 번호·syscall 반환값으로 쓰이는 일반 원리와 Linux·PintOS·QEMU에서의 역할을 설명한다. 다만 제시된 코드 좌표, 번호·오프셋, 실행 흐름과 GDB 관찰값은 특정 구현·저장소·버전 및 실제 실행 기록을 대조해야 확정할 수 있으며, 본문만으로 검증된 결과를 뜻하지 않는다.

한 줄 요약: RAX는 함수 반환값, syscall 번호, syscall 반환값 세 역할을 시점에 따라 갈아입는 x86-64에서 가장 다의적인 레지스터다.

RAX의 syscall 번호와 반환값 차이

RAX는 x86-64에서 가장 다의적인 범용 레지스터다. 평상시에는 함수 반환값을 전달하는 ABI 규약의 레지스터이고, syscall 명령어 실행 시에는 호출할 시스템 콜 번호를 커널에 전달하는 채널이 된다. 커널이 시스템 콜 처리를 마치면 결과값을 다시 RAX에 써서 유저 공간으로 돌려보낸다. 즉 RAX는 syscall의 입구이자 출구다.

상세 설명

추상 개념 (x86-64 ABI)

System V AMD64 ABI는 RAX를 다음 세 역할에 사용한다:

왜 RAX인가? x86 역사에서 AX(Accumulator)는 산술/반환 전용 레지스터였다. 64비트 확장(RAX)에서도 이 전통을 이어받아 ABI 표준이 되었다.

128비트 반환: 구조체가 16바이트 이하이면 RAX:RDX 쌍으로 반환한다. 하지만 syscall에서는 RAX 단독으로 결과를 전달한다.

RAX가 intr_frame에 저장되는 위치:

syscall_handler()가 f->R.rax에 결과를 쓰면, do_iret()이 이 값을 CPU의 RAX 레지스터로 복원한다. 유저 프로그램은 syscall 명령어 직후 RAX에서 결과를 읽는다.

lib/user/syscall.c — 유저 측 래퍼:

유저 라이브러리의 syscall1() 같은 인라인 어셈블리가 RAX에 번호를 넣고 syscall을 실행한 뒤, 반환된 RAX를 C 반환값으로 사용한다.

QEMU 에뮬레이션

QEMU는 RAX가 “syscall 번호”인지 “함수 반환값”인지 알지 못한다. CPUX86State.regs[R_EAX]에 64비트 정수 하나를 보관할 뿐이다.

syscall 명령어 실행 시 QEMU TCG 경로:

  1. TCG가 guest syscall 명령어를 만나면 helper_syscall()을 호출한다.
  2. helper_syscall()은 하드웨어 규약을 재현한다: RCX ← RIP, R11 ← RFLAGS, RIP ← LSTAR MSR 값.
  3. RAX 자체는 건드리지 않는다 — 값이 보존되어 PintOS syscall_handler()에 전달된다.
  4. PintOS가 f->R.rax에 결과를 쓰면, do_iret()이 이를 movq 시퀀스로 CPU RAX에 복원한다.
  5. QEMU TCG는 이 movq를 그대로 번역 실행하여 regs[R_EAX]를 업데이트한다.
sequenceDiagram
    participant G as Guest Code (PintOS)
    participant T as QEMU TCG
    participant C as CPUX86State

    G->>C: RAX ← 10 (SYS_WRITE)
    G->>T: syscall 명령어
    T->>T: helper_syscall()
    T->>C: RCX ← RIP, R11 ← RFLAGS
    T->>C: RIP ← LSTAR (syscall_entry)
    Note over C: RAX = 10 (변경 없음)
    G->>G: syscall_handler() → f->R.rax = 42
    G->>T: do_iret() — iretq 실행
    T->>C: RAX ← 42 (반환값 복원)
    Note over C: RAX = 42 (유저에 전달)

GDB로 RAX 관찰하기:

QEMU GDB stub이 x86_cpu_gdb_read_register()로 CPUX86State.regs[R_EAX]를 읽어 GDB에 전달한다. GDB가 보여주는 $rax는 항상 guest의 RAX 값이다.

에러 반환 경로 — PintOS vs Linux:

flowchart TD
    CALL[syscall 호출] --> HANDLER[syscall_handler]
    HANDLER --> SUCCESS{성공?}
    SUCCESS -->|Yes| OK["f->R.rax = 결과값<br/>(쓴 바이트 수, fd 등)"]
    SUCCESS -->|No| ERR["f->R.rax = -1<br/>(PintOS 통합 에러)"]
    OK --> IRET[do_iret → 유저 복귀]
    ERR --> IRET

    HANDLER --> LINUX_SUCCESS{Linux: 성공?}
    LINUX_SUCCESS -->|Yes| LOK["RAX = 결과값"]
    LINUX_SUCCESS -->|No| LERR["RAX = -errno<br/>(-EFAULT, -EINVAL 등)"]
    LOK --> SYSRET[sysret → 유저 복귀]
    LERR --> SYSRET

PintOS는 에러를 -1 하나로 통합하지만, Linux는 RAX에 음수 errno를 넣어 에러 종류를 구분한다. libc의 syscall() 래퍼가 음수 RAX를 감지하면 errno에 절대값을 저장하고 -1을 반환한다.
