SSD와 HDD 저장 장치

SSD와 HDD 저장 장치

확인 범위: 이 문서는 HDD와 SSD의 동작 원리와 OS의 블록 디바이스 추상화, 버퍼 캐시가 필요한 이유를 개념적으로 설명하고 PintOS와 QEMU 코드는 그 흐름을 보여 주는 특정 구현 사례로 다룬다. 제시된 지연 시간·대역폭·배수와 코드 동작은 특정 장치, 버전, 실제 소스 및 실행·성능 측정으로 검증한 결과가 아니므로 구체적인 환경에 적용하려면 별도 확인이 필요하다.

한 줄 요약: HDD는 회전하는 자기 디스크 위를 헤드가 이동하며 읽고, SSD는 전기 신호로 NAND 플래시 셀에 접근한다. 이 물리적 차이가 순차/임의 접근 성능, 섹터 크기, 버퍼 캐시의 존재 이유를 결정한다.

SSD와 HDD 저장 장치가 비용을 줄이는 자리

파일 시스템, 버퍼 캐시, 페이지 교체 알고리즘은 모두 “디스크 I/O가 느리다”는 전제 위에 설계되었다. 그런데 왜 느린지, 얼마나 느린지를 모르면 이 설계의 이유를 납득할 수 없다.

이 문서를 읽으면 다음을 구분할 수 있다.

  • HDD에서 임의 접근이 왜 순차 접근보다 수백 배 느린지
  • SSD가 HDD보다 빠르지만 RAM보다는 여전히 수천 배 느린 이유
  • OS가 왜 512바이트(또는 4KB) 단위로 디스크를 다루는지
  • PintOS가 DISK_SECTOR_SIZE 512를 쓰는 이유

SSD와 HDD 저장 장치 차이

HDD (Hard Disk Drive) — 기계적 회전과 탐색

HDD는 자기 물질이 코팅된 원판(플래터, Platter)이 고속으로 회전하고, 읽기/쓰기 헤드(Head)가 팔(Arm) 끝에서 반지름 방향으로 이동하며 데이터를 읽는다.

%% HDD의 플래터, 트랙, 헤드 암 구조
flowchart TD
  case["HDD 내부 구조"]
  spindle["스핀들 모터<br/>7200 RPM 회전"]
  platter["플래터 (원판)"]
  track["트랙<br/>동심원"]
  sector["섹터<br/>전통적 512바이트"]
  arm["헤드/암"]
  seek["반지름 방향 이동<br/>Seek"]
  case -->|회전| spindle
  spindle --> platter
  platter -->|같은 반지름| track
  track -->|각도로 분할| sector
  arm --> seek
  seek -->|목표 트랙 접근| track

구성 요소:

  • 플래터 (Platter): 양면에 자기 물질. 여러 장 겹친다.
  • 트랙 (Track): 플래터 위의 동심원 하나.
  • 섹터 (Sector): 트랙을 일정 각도로 나눈 호(arc). 전통적으로 512바이트.
  • 실린더 (Cylinder): 같은 반지름의 트랙을 모든 플래터에서 모은 집합.
  • 헤드 (Head): 자기 신호를 읽고 쓰는 부품. 플래터 면마다 하나.

데이터를 읽으려면 세 단계 지연이 발생한다.

  1. 탐색 시간 (Seek Time): 헤드가 목표 트랙으로 이동. 평균 4~8ms.
  2. 회전 지연 (Rotational Latency): 목표 섹터가 헤드 아래로 올 때까지 대기. 7200RPM 기준 평균 4.17ms.
  3. 전송 시간 (Transfer Time): 섹터 데이터를 읽는 시간. 수십 μs.

임의 접근(random access) 한 번에 약 812ms가 걸린다. 1초에 약 100150회만 가능하다.

SSD (Solid State Drive) — 전기 신호로

SSD는 움직이는 부품이 없다. NAND 플래시 메모리 칩에 전기 신호로 데이터를 읽고 쓴다.

%% SSD 컨트롤러와 NAND 채널, 블록, 페이지 구조
flowchart TD
  controller["SSD 컨트롤러<br/>FTL"]
  lba["OS가 보낸 LBA"]
  nand0["NAND 채널 0"]
  nand1["NAND 채널 1"]
  nand2["NAND 채널 2"]
  block0["블록 0<br/>삭제 최소 단위"]
  block1["블록 0<br/>삭제 최소 단위"]
  block2["블록 0<br/>삭제 최소 단위"]
  page0["페이지<br/>읽기/쓰기 최소 단위"]
  page1["페이지<br/>읽기/쓰기 최소 단위"]
  page2["페이지<br/>읽기/쓰기 최소 단위"]
  lba -->|논리 주소| controller
  controller -->|매핑| nand0
  controller -->|병렬 접근| nand1
  controller -->|매핑| nand2
  nand0 --> block0
  nand1 --> block1
  nand2 --> block2
  block0 --> page0
  block1 --> page1
  block2 --> page2

구성 요소:

  • 셀 (Cell): 전자를 가두는 최소 단위. SLC(1비트), MLC(2비트), TLC(3비트), QLC(4비트).
  • 페이지 (Page): 읽기/쓰기의 최소 단위. 보통 4KB~16KB.
  • 블록 (Block): 삭제의 최소 단위. 보통 128256페이지. 수백 KB수 MB.
  • FTL (Flash Translation Layer): 논리 주소를 물리 페이지에 매핑하는 펌웨어. HDD의 LBA를 그대로 받아 내부적으로 변환한다.

SSD의 핵심 특성:

  • 읽기: 임의 접근도 수십 μs. HDD보다 100배 이상 빠르다.
  • 쓰기: 빈 페이지에 쓰기는 빠르지만, 이미 데이터가 있는 블록은 삭제 후 재기록이 필요하다 (erase-before-write).
  • 수명: 셀당 쓰기 횟수에 한계가 있다 (SLC ~10만회, TLC ~3000회). FTL이 웨어 레벨링(wear leveling)으로 균등 분배한다.

성능 비교 — 왜 버퍼 캐시가 필요한가

계층임의 접근 지연순차 대역폭
CPU 레지스터< 1ns—
L1 캐시~1ns—
DRAM~100ns~50 GB/s
SSD (NVMe)10100μs37 GB/s
SSD (SATA)50100μs~500 MB/s
HDD812ms100200 MB/s

DRAM과 SSD 사이에 약 1000배, DRAM과 HDD 사이에 약 100,000배 속도 차이가 있다. 이 차이 때문에 OS는 디스크에서 읽은 데이터를 RAM에 캐시(버퍼 캐시)해서 재사용한다.

OS 관점에서 HDD와 SSD의 공통점

OS는 HDD든 SSD든 동일한 블록 디바이스 인터페이스로 다룬다.

  • 섹터 번호(LBA)로 주소를 지정한다.
  • 섹터 단위(512바이트 또는 4KB)로 읽고 쓴다.
  • 내부가 기계식이든 플래시든 OS는 신경 쓰지 않는다.

SSD의 FTL이 이 추상화를 가능하게 한다. FTL은 OS가 보내는 LBA를 내부 NAND 물리 페이지 주소로 변환하므로, OS 입장에서 SSD는 “빠른 HDD”처럼 보인다.

SSD와 HDD 저장 장치 코드

PintOS: ATA 디스크 인터페이스

PintOS는 QEMU가 에뮬레이션하는 ATA(IDE) 디스크를 사용한다. 물리적으로는 NAND나 자기 디스크가 아니라 호스트의 파일이지만, guest OS인 PintOS 입장에서는 512바이트 섹터 단위로 읽고 쓰는 블록 디바이스다.

disk_read()의 내부 흐름:

이 코드가 하는 일: CPU가 ATA 컨트롤러의 I/O 포트에 섹터 번호를 쓰고, 읽기 명령을 보낸 뒤, 디스크가 완료 인터럽트를 보낼 때까지 세마포어로 잠든다. 완료 후 데이터 레지스터에서 512바이트를 PIO(Programmed I/O) 방식으로 가져온다.

PintOS 디스크 배치

%% PintOS에서 QEMU ATA 디스크가 채널과 디스크로 나뉘는 배치
flowchart LR
  pintos["PintOS<br/>ATA 디스크 인터페이스"]
  ch0["채널 0<br/>I/O base 0x1F0<br/>IRQ 14"]
  ch1["채널 1<br/>I/O base 0x170<br/>IRQ 15"]
  hd00["hd0:0<br/>부트 로더 + 커널"]
  hd01["hd0:1<br/>파일 시스템"]
  hd10["hd1:0<br/>scratch"]
  hd11["hd1:1<br/>swap"]
  pintos --> ch0
  pintos --> ch1
  ch0 --> hd00
  ch0 --> hd01
  ch1 --> hd10
  ch1 --> hd11

QEMU: IDE 컨트롤러 에뮬레이션

PintOS가 “디스크”라고 믿는 것은 실제로 QEMU가 호스트 파일을 IDE(ATA) 컨트롤러 뒤에 연결한 것이다. QEMU의 hw/ide/ 디렉터리가 이 에뮬레이션을 담당한다.

QEMU IDE 에뮬레이션의 핵심:

  • guest가 I/O 포트 0x1F0~0x1F7에 쓰면 QEMU가 트랩해서 가상 ATA 레지스터를 갱신한다.
  • CMD_READ_SECTOR_RETRY (0x20) 명령이 오면, QEMU는 호스트 파일에서 해당 오프셋의 512바이트를 읽어 가상 데이터 레지스터에 채운다.
  • 완료 후 가상 IRQ 14(또는 15)를 guest에 주입한다.

즉 PintOS의 disk_read() → ATA 포트 I/O → QEMU 트랩 → 호스트 pread() → 가상 인터럽트 → PintOS sema_up() 순서로 동작한다.

관련 QEMU 소스: hw/ide/ide-internal.h

실제 OS vs PintOS 차이

  • 실제 Linux: SATA/NVMe 드라이버가 DMA(Direct Memory Access)로 데이터를 전송한다. CPU가 바이트마다 포트를 읽지 않는다.
  • PintOS: PIO 모드만 사용한다. CPU가 insw 명령으로 512바이트를 직접 읽어온다. 교육 목적으로 단순화된 구현이다.
  • 실제 SSD: NCQ(Native Command Queuing)로 여러 요청을 동시에 처리한다. PintOS는 한 번에 하나의 섹터만 요청한다.

정리

HDD는 기계적 회전과 헤드 이동 때문에 임의 접근에 수 ms가 걸린다. SSD는 전기 신호로 접근하므로 수십 μs로 줄어들지만, 여전히 RAM(100ns)보다 1000배 느리다. 이 속도 차이가 OS에서 버퍼 캐시, 페이지 캐시, I/O 스케줄러가 존재하는 근본 이유다.

OS는 HDD와 SSD를 모두 “섹터 번호로 접근하는 블록 디바이스”로 추상화한다. PintOS의 disk_read()/disk_write()가 바로 이 추상화의 구현이며, QEMU가 호스트 파일을 ATA 디스크처럼 보이게 에뮬레이션한다.
