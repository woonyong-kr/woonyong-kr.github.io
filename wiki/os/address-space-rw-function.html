QEMU 메모리 접근 함수 address_space_rw()

QEMU 메모리 접근 함수 address_space_rw()

한 줄 요약: address_space_rw()는 GPA 기반 RAM·MMIO 접근 API지만, TCG의 일반 CPU load/store와 x86 port I/O가 모두 이 함수를 직접 거치는 것은 아니다.

QEMU 메모리 접근 함수 구조

address_space_rw()는 QEMU 내부에서 Guest Physical Address(GPA)로 RAM이나 MMIO MemoryRegion을 읽고 쓰는 API다. DMA 장치 모델, GDB stub·관리 기능처럼 버퍼 기반 물리 메모리 접근이 필요한 호출자가 이 함수 또는 방향별 래퍼를 사용할 수 있다. 반면 TCG가 생성한 일반 CPU load/store의 fast path는 SoftTLB와 내부 dispatch 경로를 사용하며 이 API를 매번 직접 호출하지 않는다. x86 in/out도 별도의 port-I/O 주소 공간과 handler를 사용한다.

상세 설명

추상 개념 (에뮬레이션 계층)

물리 머신에서 CPU가 메모리에 접근하면 메모리 버스를 통해 DRAM 칩에 도달한다. 하지만 에뮬레이터에서는 “물리 주소”가 가짜이므로 소프트웨어가 이 접근을 중재해야 한다.

편의 래퍼들

내부 동작 흐름

  1. AddressSpace에서 MemoryRegion 찾기: FlatView를 통해 GPA가 어느 MemoryRegion에 속하는지 탐색한다. FlatView는 중첩된 MemoryRegion 계층 구조를 선형 구간 배열로 평탄화한 것이다.

  2. RAM vs MMIO 분기:

    • RAM: memory_region_is_ram(mr) → RAMBlock의 host 포인터 + offset으로 HVA를 계산하고 memcpy()
    • MMIO: mr->ops->read() 또는 mr->ops->write() 콜백 호출

  3. 경계 횡단 처리: 접근이 MemoryRegion 경계를 넘으면 여러 번 분할하여 각 영역에 대해 별도 처리한다.

PintOS에서의 영향

PintOS 자체 코드에서 address_space_rw()를 직접 호출하지는 않는다. 이 함수는 QEMU 측 코드다. 하지만 PintOS를 디버깅할 때 간접적으로 이 함수를 사용하는 경우가 많다:

GDB x/Nx addr 명령: GDB stub이 게스트 메모리를 읽을 때 cpu_physical_memory_read()를 호출한다. 이것이 address_space_rw()의 래퍼다.

IDE PIO와 DMA의 경계: 이 저장소의 PintOS disk_write()는 outb()로 명령을 내리고 outsw()로 512B를 직접 전송하는 PIO 경로다. 이 경로를 IDE DMA의 address_space_read() 호출로 연결하면 안 된다. Bus-master DMA를 사용하는 별도 장치·모드라면 장치가 guest RAM에 접근할 때 AddressSpace DMA helper를 사용할 수 있다.

레거시 IDE의 0x1F0~0x1F7은 x86 I/O port 주소이며 AddressSpace의 MMIO MemoryRegion 범위가 아니다. CPU가 in/out 명령으로 이 port를 접근하는 제어 경로와, 장치가 guest RAM을 읽고 쓰는 DMA 경로를 구분해야 한다.
