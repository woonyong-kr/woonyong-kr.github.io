syscall 복귀 경로 — sysretq vs iretq

syscall 복귀 경로 — sysretq vs iretq

확인 범위: 이 문서는 x86-64의 sysretq와 iretq 복귀 원리와 선택 기준을 설명하고, 제시된 PintOS·Linux·QEMU 경로를 구현 사례로 다룬다. 코드 위치·버전별 동작·실행 관찰과 성능 수치는 해당 소스 및 환경에서 별도로 검증해야 하며, 본문만으로 특정 구현의 검증 결과로 간주하지 않는다.

한 줄 요약: 유저 모드 복귀 경로는 syscall과 짝인 빠른 sysretq와 인터럽트·예외용 범용 iretq 두 가지이며, PintOS는 syscall 복귀에 sysretq, context switch·exec에는 iretq를 쓴다.

syscall 복귀 경로 구조

x86-64에서 syscall 처리가 끝난 뒤 유저 모드로 돌아가는 경로는 두 가지다. sysretq는 syscall 명령어와 짝으로 설계된 빠른 복귀 명령어이고, iretq는 인터럽트/예외 복귀용 범용 명령어다. PintOS는 syscall_entry()에서 sysretq로 복귀하고, process_exec()나 context switch에서는 do_iret() → iretq로 복귀한다. 두 경로의 차이를 이해하면 왜 커널이 상황에 따라 다른 복귀 명령어를 쓰는지 알 수 있다.

상세 설명

추상 개념 (CPU 하드웨어 규칙)

sysretq가 하는 일 (Intel SDM Vol. 2B):

  1. RCX → RIP (복귀할 유저 코드 주소)
  2. R11 → RFLAGS (유저 모드 플래그 복원)
  3. CS ← STAR[63:48] + 16 (유저 코드 세그먼트, CPL 3)
  4. SS ← STAR[63:48] + 8 (유저 스택 세그먼트)
  5. CPL 0 → CPL 3 전환

sysretq는 스택을 건드리지 않는다. RCX와 R11에서 직접 복원하므로 pop이 없고, 그래서 iretq보다 마이크로아키텍처적으로 빠르다.

iretq가 하는 일:

  1. 스택에서 RIP, CS, RFLAGS, RSP, SS를 순서대로 pop
  2. CS의 RPL에 따라 CPL 전환
  3. SS:RSP로 스택 전환

iretq는 스택 5개 값을 읽어야 하고, 권한 검사가 더 엄격하다. 대신 어떤 상황에서든 유저 모드 복귀가 가능하다.

비교 항목sysretqiretq
복귀 주소 소스RCX 레지스터스택 pop
RFLAGS 소스R11 레지스터스택 pop
RSP 소스직접 설정 필요스택 pop
pop 횟수05
CPL 전환항상 CPL 0→3CS RPL에 따라
사용 조건syscall로 진입한 경우만범용
상대 성능~20 cycle 빠름기준선

실제 OS (Linux)

Linux는 syscall 복귀에 대부분 sysretq를 사용하지만, 아래 경우 iretq로 fallback한다:

  • ptrace로 RIP/RFLAGS가 변경된 경우 (RCX/R11에 담을 수 없는 값)
  • signal handler를 설정해야 하는 경우
  • 단일 스텝(TF 비트) 디버깅 중

entry_SYSCALL_64 → swapgs; sysretq 경로가 fast path이고, ret_from_fork → iretq 경로가 slow path다.

PintOS 구현

PintOS의 syscall-entry.S에서 복귀 경로 (line 48~68):

핵심 포인트:

  1. RAX는 pop으로 복원: syscall_handler()가 f->R.rax에 반환값을 기록하고, pop으로 RAX에 들어간다
  2. RCX는 if->rip에서: 진입 시 push %rcx로 저장한 유저 RIP를 다시 RCX에 넣는다
  3. R11은 if->eflags에서: 진입 시 push %r11로 저장한 유저 RFLAGS를 다시 R11에 넣는다
  4. RSP는 마지막 pop: popq %rsp로 유저 스택 포인터를 복원한 뒤 즉시 sysretq

진입 시 저장 ↔ 복귀 시 복원 대응표:

진입 (push)복귀 (pop)용도
push %rcx (line 18)popq %rcx (line 64)유저 RIP
push %r11 (line 16)popq %r11 (line 66)유저 RFLAGS
push %rbx (line 15)popq %rsp (line 67)유저 RSP
push %rax (line 22)popq %rax (line 62)syscall 번호 → 반환값

sysretq의 보안 취약점 — non-canonical RCX

sysretq에는 유명한 하드웨어 설계 결함이 있다. sysretq가 RCX를 RIP에 넣을 때, RCX가 non-canonical 주소(비트 47과 63이 다른 주소)이면 CPU가 gp(General Protection fault)를 발생시킨다. 문제는 이 gp가 아직 CPL 0 상태에서 발생한다는 점이다.

공격 시나리오:

  1. 유저가 ptrace나 signal로 RCX(→ 복귀할 RIP)를 non-canonical 주소로 조작
  2. 커널이 sysretq를 실행
  3. CPU가 gp를 발생시키지만, 이때 아직 CPL 0
  4. gp 핸들러가 유저 스택(이미 RSP가 유저 값으로 전환됨)에 접근하여 커널 권한으로 유저 메모리를 읽고 쓰는 상황 발생

Linux는 이 취약점을 방어하기 위해 sysretq 직전에 RCX가 canonical인지 검사하고, non-canonical이면 iretq 경로로 fallback한다. PintOS는 유저 프로그램이 RCX를 조작할 수 없으므로(ptrace 미구현) 이 검사가 없다.

canonical 주소 조건 (x86-64, 48-bit):
  비트 63:48 = 모두 0 (유저 공간)
  비트 63:48 = 모두 1 (커널 공간)

non-canonical 예시: 0x0000_8000_0000_0000
  비트 47 = 1, 비트 63 = 0 → non-canonical → #GP

PintOS에서 iretq를 쓰는 경우

do_iret()는 iretq를 사용한다. PintOS에서 이 경로를 타는 상황:

  1. process_exec(): 새 바이너리 로드 후 처음 유저 모드 진입 — syscall로 들어온 게 아니므로 RCX/R11에 올바른 값이 없음
  2. context switch (thread_launch): 스케줄러가 다른 스레드로 전환 — 이전 syscall 진입 맥락이 아닌 일반 스레드 전환
  3. fork 후 자식의 첫 실행: __do_fork에서 intr_frame을 복사해 do_iret으로 복귀

QEMU 에뮬레이션

QEMU TCG는 sysretq를 다음과 같이 에뮬레이션한다:

번역 단계 (translate.c): gen_SYSRET() → gen_helper_sysret(cpu_env, tcg_const_i32(dflag)) 를 TCG IR에 삽입한다. guest의 sysretq 명령어를 만나면 TCG helper 함수를 호출하도록 변환한다.

실행 단계 (seg_helper.c): helper_sysret(CPUX86State *env, int dflag) 가 실제 동작을 수행한다:

QEMU의 iretq 에뮬레이션(helper_iret_real/protected)은 이보다 복잡하다. 스택에서 5개 값(RIP, CS, RFLAGS, RSP, SS)을 pop하고, 세그먼트 권한 검사, nested task 처리, IOPL 비교 등을 수행한다. 이 복잡도 차이가 실제 하드웨어에서의 성능 차이를 반영한다.

GDB에서 sysretq 에뮬레이션 관찰:

(gdb) break userprog/syscall-entry.S:68    # sysretq 직전
(gdb) commands
  silent
  printf "sysretq: RCX(→RIP)=%p, R11(→RFLAGS)=%p, RSP=%p, RAX=%d\n", \
         $rcx, $r11, $rsp, $rax
  continue
  end

sysretq 직전에 RCX=유저코드 복귀 주소, R11=유저 RFLAGS, RSP=유저 스택, RAX=반환값이 확인되어야 한다.

(gdb) # iretq 경로와 비교하려면:
(gdb) break do_iret
(gdb) commands
  silent
  printf "iretq: intr_frame at %p\n", $rdi
  x/5gx $rdi+120    # RIP, CS, RFLAGS, RSP, SS (intr_frame 끝 5개)
  continue
  end

syscall 복귀 경로 값 추적

sysretq 복귀 경로에서 pop하는 레지스터 수와 스택 변화:

  • syscall_handler 반환 시점: RSP = intr_frame의 r15 위치
  • popq %r15 ~ %rax: 15개 레지스터 × 8 = 120 bytes
  • addq $32, %rsp: es(8) + ds(8) + vec_no(8) + error_code(8) = 32 bytes
  • popq %rcx: 8 bytes (rip)
  • addq $8, %rsp: cs skip = 8 bytes
  • popq %r11: 8 bytes (eflags)
  • popq %rsp: 8 bytes (rsp)
  • 총 소비: 120 + 32 + 8 + 8 + 8 + 8 = 184 bytes
  • = sizeof(struct intr_frame) - sizeof(ss) = 192 - 8 = 184
  • (ss는 sysretq가 STAR MSR에서 설정하므로 pop 불필요)

sysretq vs iretq 성능 비교

항목sysretqiretq
메모리 접근0회 (레지스터에서 복원)5회 pop (RSP→RIP/CS/RFLAGS/RSP/SS)
권한 검사CPL 0→3 고정 (단순)CS RPL 기반 (복잡한 세그먼트 검사)
마이크로 명령어 수 (Intel Skylake 기준)~4 μops~15 μops
대략 지연~20 cycles~40 cycles
PintOS에서의 추가 비용3 pop (RCX, R11, RSP)전체 intr_frame 구성 필요
QEMU TCG 에뮬레이션helper_sysret 1개helper_iret_protected + 다수 세그먼트 로드

PintOS에서 sysretq는 syscall 왕복 1회당 ~20 cycle 절감이지만, QEMU 에뮬레이션 환경에서는 helper 함수 호출 오버헤드가 지배적이므로 이 차이가 크게 드러나지 않는다.

fork/exec에서 iretq를 써야 하는 이유 (숫자로)

process_exec → do_iret 경로:
  새 바이너리 로드 → setup_stack → intr_frame 구성
  intr_frame.rip = ELF e_entry (예: 0x400000)
  intr_frame.cs  = SEL_UCSEG (유저 코드 세그먼트)
  intr_frame.rsp = USER_STACK (0x47480000)
  → 이 값들은 syscall 진입 시 RCX/R11에 저장된 적이 없음
  → sysretq 불가 → iretq 필수

__do_fork → do_iret 경로:
  부모 intr_frame 복사 → if.R.rax = 0 (자식의 fork 반환값)
  → RCX/R11은 부모 값이 아닌 복사본에서 와야 함
  → iretq가 스택에서 일관되게 복원하므로 더 안전

순서도

flowchart TD
    A[syscall_handler 반환] --> B[pop r15~rax<br/>15개 범용 레지스터 복원]
    B --> C[addq $32, %rsp<br/>es/ds/vec_no/error_code skip]
    C --> D[popq %rcx<br/>유저 RIP 복원]
    D --> E[addq $8, %rsp<br/>cs skip]
    E --> F[popq %r11<br/>유저 RFLAGS 복원]
    F --> G[popq %rsp<br/>유저 스택 복원]
    G --> H[sysretq<br/>CPL 0→3 전환]
    H --> I[유저 모드 코드 실행 재개<br/>RIP=RCX, RFLAGS=R11]
