Page Fault GDB에서 CR2와 SPT를 한 화면에 맞춰 보기

Page Fault GDB에서 CR2와 SPT를 한 화면에 맞춰 보기

확인 범위: 이 문서는 CR2, RIP, SPT, frame, PTE를 구분하고 연결해 관찰하는 일반 원리와 W09 PintOS skeleton 구현 중의 디버깅 기준을 설명하며, 제시된 값과 코드 좌표는 관계를 이해하기 위한 사례다. 특정 구현의 완성 여부나 실제 실행 결과·성능을 검증하려면 해당 코드 버전과 GDB 실행 기록 및 측정 결과를 별도로 확인해야 한다.

CR2와 SPT 디버깅

GDB에서 page_fault()에 멈췄을 때 초보자가 가장 자주 헷갈리는 질문은 이것이다.

info registers의 rip, cr2, f->rip, fault_addr, struct page *page는 서로 같은 값을 말하는 걸까?

같은 사건을 보고 있지만 같은 값은 아니다.

  • cr2와 fault_addr는 접근하려다 실패한 유저 가상 주소다.
  • rip 또는 f->rip는 fault를 일으킨 명령어 주소다.
  • pg_round_down(fault_addr)는 SPT lookup에 쓰는 page base다.
  • struct page *page는 PintOS가 “이 주소는 원래 합법이고, 나중에 어떻게 채울지” 기억하는 커널 metadata다.
  • frame->kva는 page를 실제 4096바이트 frame에 붙인 뒤 커널이 읽을 수 있는 커널 가상 주소다.

이 Lab의 목표는 GDB에서 이 값들을 한 줄씩 대응시키는 감각을 만드는 것이다.

Page Fault GDB에서 CR2와 구분

page fault 디버깅은 값 이름이 비슷해서 쉽게 섞인다.

예를 들어 lazy loading 버그를 고치는 중이라면, 다음 중 어느 것이 틀렸는지 구분해야 한다.

관찰 값이 값이 답하는 질문
cr2어떤 VA 접근이 실패했는가
f->error_codenot-present인가, write인가, user 접근인가
f->rip어떤 명령어가 재실행되어야 하는가
pg_round_down(fault_addr)SPT에서 찾을 page key는 무엇인가
page->vaSPT가 기억한 합법 page base가 맞는가
page_get_type(page)lazy, anon, file-backed 중 무엇으로 채울 page인가
page->frame / frame->kva실제 4096바이트 frame이 붙었는가
pml4_get_page(t->pml4, fault_addr)CPU가 다시 번역할 수 있는 PTE가 설치되었는가

이 값들을 한 화면에서 맞추지 못하면, page fault가 왜 죽었는지와 왜 살아났는지를 구분하기 어렵다.

Page Fault GDB에서 CR2와 차이

page fault 관찰은 네 층을 분리해서 읽는다.

층대표 값의미
CPU가 남긴 fault 정보CR2, error_code, RIP하드웨어가 실패 지점을 커널에 알려 준다
PintOS handler snapshotstruct intr_frame *f예외 진입 시점의 register를 커널 stack에 저장한 값
PintOS VM metadatastruct page, SPT, struct framefault를 살릴 정책과 backing store를 기억한다
QEMU debug viewCPUX86State, debug memory pathGDB가 보는 guest register와 guest memory를 제공한다

이 말은 즉, GDB 한 화면에 값이 여러 개 보이더라도 “한 구조체의 필드만 보는 것”이 아니다. CPU 예외 정보, PintOS가 저장한 snapshot, PintOS VM metadata, QEMU가 제공하는 debug 관찰 경로를 동시에 보는 것이다.

Page Fault GDB에서 CR2와 사례

유저 프로그램이 아직 lazy load되지 않은 주소를 읽는다고 하자.

여기서 바로 계산한다.

SPT lookup은 0x401234 그대로가 아니라 page base인 0x401000을 기준으로 해야 한다. 반면 RIP = 0x401050은 “어떤 명령어로 돌아갈 것인가”를 말한다. RIP와 CR2가 같아야 하는 것은 아니다.

실제 운영체제

Linux와 Windows도 page fault가 나면 CPU가 남긴 fault 주소와 fault 종류를 커널이 해석한다.

Linux는 VMA, page cache, swap, COW, signal 전달 같은 많은 정책을 거쳐 fault를 살리거나 SIGSEGV로 보낸다. Windows도 VAD, section object, page file, access violation 같은 더 복잡한 구조를 가진다.

현실 OS 디버깅에서도 핵심은 같다.

  • fault address와 instruction pointer를 구분한다.
  • page table에 지금 present한지와 OS metadata상 합법인지 구분한다.
  • debugger가 보여주는 값이 현재 register인지, trap frame인지, 커널 metadata인지 구분한다.

PintOS는 이 구조를 훨씬 작게 줄여서 page_fault()와 vm_try_handle_fault() 주변에서 관찰하게 만든다.

그 다음 VM이 켜져 있으면 fault를 살릴 기회를 준다.

W09의 vm.c는 아직 skeleton이다. 따라서 이 Lab은 “이미 구현되어 있는 동작”을 확인하는 문서가 아니라, 구현 중에 어떤 값을 연결해서 봐야 하는지 정리하는 디버깅 기준이다.

QEMU

QEMU는 PintOS의 VM 정책을 모른다. 하지만 GDB가 보는 guest register와 memory를 제공한다.

근거 파일:

  • target/i386/gdbstub.c
  • gdbstub/gdbstub.c
  • gdbstub/system.c
  • system/physmem.c
  • target/i386/tcg/system/excp_helper.c

이번 Lab에서 확인한 QEMU 쪽 좌표는 다음과 같다.

파일위치이 Lab에서 보는 값
target/i386/gdbstub.c204-207GDB가 guest CR2, CR3를 CPUX86State에서 읽음

gdbstub/gdbstub.c1308-1312GDB memory read packet을 debug memory read로 넘김
gdbstub/system.c452-468physical mode가 아니면 cpu_memory_rw_debug()로 위임
system/physmem.c4030-4054guest VA를 debug translation해 physical address space byte로 읽음

x86 gdbstub은 control register를 guest CPU state에서 읽는다.

#PF가 전달될 때도 QEMU 내부 guest CPU state의 CR2가 갱신된다.

GDB memory dump는 host pointer를 바로 읽는 것이 아니다. QEMU 공통 gdbstub의 memory read packet은 system mode에서 gdb_target_memory_rw_debug()로 내려가고, 보통 cpu_memory_rw_debug()를 거쳐 guest 주소를 debug translation한 뒤 address_space_rw()로 byte를 읽는다.

이 말은 즉, PintOS GDB에서 x/16xb 0x401234를 입력하면 macOS/Linux host process의 주소 0x401234를 읽는 것이 아니라, QEMU가 에뮬레이션하는 guest machine의 주소를 읽으려 한다.

CR2와 SPT 디버깅 값 추적

다음 값을 한 번에 계산해 보자.

page 단위 값:

이름계산결과
page base0x401234 & ~0xfff0x401000
offset0x401234 & 0xfff0x234
PTE frame base0x12345007 & ~0xfff0x12345000
guest physical byte0x12345000 + 0x2340x12345234
kernel VA byteKERN_BASE + 0x12345000 + 0x2340x8016345234

따라서 같은 byte를 여러 이름으로 볼 수 있다.

여기서 0x401050과 0x401234는 서로 다른 역할이다. 하나는 실행 위치이고, 다른 하나는 접근 대상이다.

Page Fault GDB에서 CR2와 GDB

0. 어떤 상황에서 멈출지 고르기

먼저 “page fault가 나기만 하면 된다”가 아니라, 어떤 VM 정책을 확인할지 정한다.

확인하려는 정책좋은 멈춤 지점기대하는 관찰
lazy executable page첫 instruction/data 접근 뒤 page_fault()SPT에 UNINIT page가 있고 claim 뒤 file bytes가 채워진다
stack growthrsp 근처의 낮은 주소 접근SPT miss지만 stack 조건을 만족해 새 page가 만들어진다
swapped anonymous pageeviction 뒤 같은 VA 재접근SPT page는 남아 있고 anon metadata가 slot을 가리킨다
file-backed mmapmmap range 첫 접근 또는 dirty write-backpage별 file offset과 writable metadata가 fault 처리에 쓰인다

현재 W09 VM 코드는 skeleton이므로, 처음에는 테스트 통과보다 breakpoint에서 값 관계를 채우는 데 초점을 둔다. 구현이 진행될수록 같은 관찰표를 pt-grow-*, mmap-*, swap-* 계열 테스트에 적용하면 된다.

1. breakpoints 잡기

VM 구현 중에는 아래 지점을 한 번에 잡아 둔다.

lazy loading까지 확인한다면 다음도 추가한다.

2. page_fault에서 CPU 힌트와 PintOS

확인할 것:

확인기대
fault_addr와 cr2같은 faulting VA
f->ripfault를 낸 명령어 주소
f->error_code & PF_Pnot-present와 protection fault 구분
f->error_code & PF_Wread fault와 write fault 구분
f->error_code & PF_Uuser 접근인지 kernel 접근인지 구분

주의할 점이 있다. info registers rip은 지금 GDB가 멈춘 현재 실행 위치를 보여줄 수 있다. handler 안에서 멈췄다면 현재 rip는 커널 handler 쪽일 수 있다. fault 당시 유저로 돌아갈 지점은 f->rip를 같이 봐야 한다.

3. SPT lookup 값 맞추기

spt_find_page()에 들어가면 page-aligned key를 직접 계산한다.

구현에 따라 지역 변수 이름은 달라질 수 있다. 핵심은 fault_addr 그대로와 page base를 구분하는 것이다.

4. claim 뒤 frame과 PTE 확인하기

vm_do_claim_page()에서 frame을 얻은 뒤에는 양방향 링크와 PTE 설치를 본다.

기대하는 관계:

단, pml4_get_page()는 page base에 대해 확인하는 것이 안전하다. fault 주소가 page 중간이면 pml4_get_page(t->pml4, fault_addr)는 같은 frame의 offset이 더해진 주소를 돌려준다.

5. byte가 실제로 채워졌는지 보기

lazy load가 성공했다면 frame의 앞부분과 fault offset 근처를 본다.

유저 VA로도 같은 byte가 보이는지 확인한다.

이때 x/16xb fault_addr는 QEMU GDB stub의 guest memory read 경로를 탄다. host process 주소를 직접 읽는 것이 아니다.

정리

  • CR2는 fault가 난 주소이고, RIP는 fault를 낸 명령어 주소다.
  • PintOS의 f->rip는 handler가 끝난 뒤 다시 실행할 guest instruction 위치를 이해하는 데 중요하다.
  • SPT는 fault_addr의 page base로 page metadata를 찾는다.
  • claim 뒤에는 struct page, struct frame, PTE가 같은 4096바이트 frame을 가리켜야 한다.
  • QEMU GDB stub은 guest register와 guest memory를 보여준다. host QEMU process의 C 포인터와 섞으면 안 된다.

Page Fault GDB에서 CR2와 관련 문서

  • Page Fault Trace

  • vm do claim page()
