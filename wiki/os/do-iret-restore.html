do_iret() 레지스터 복원

do_iret() 레지스터 복원

do_iret()는 intr_frame에 저장된 레지스터 스냅샷을 iretq로 원자적으로 복원해, 멈춰 있던 스레드의 실행을 다시 이어 준다.

왜 레지스터 스냅샷을 통째로 복원하나

컨텍스트 스위치나 유저 모드 복귀는 RIP 하나만 되돌린다고 끝나지 않는다. CPU가 다시 실행을 이어가려면 다음 명령어 주소, 권한 수준, 플래그, 스택 포인터가 서로 맞는 한 묶음으로 돌아와야 한다.

do_iret()는 struct intr_frame에 저장된 실행 스냅샷을 CPU에 다시 얹는 함수다. x86-64의 iretq는 항상 RIP, CS, RFLAGS를 하나의 architectural state transition으로 복원하고, 더 낮은 권한으로 돌아가는 CPL 전환(예: 0→3)이면 RSP와 SS도 함께 복원한다. thread_launch()가 현재 스레드의 상태를 저장하는 쪽이라면, do_iret()는 다음 스레드의 상태를 복원하는 짝이다.

iretq가 필요한 이유

일반 ret 명령어는 스택에서 RIP만 꺼낸다. 인터럽트나 예외에서 돌아갈 때는 최소한 RIP, CS, RFLAGS를 함께 복원해야 하고, 유저 모드처럼 바깥 privilege level로 돌아갈 때는 RSP와 SS도 같은 전이에 포함해야 한다. 이를 개별 mov로 나누면 권한과 실행 상태 사이에 관찰 가능한 불일치가 생길 수 있다.

iretq가 소비하는 스택 범위는 target CS가 가리키는 CPL에 따라 달라진다:

CPL 전환 규칙

iretq는 복원하는 CS의 RPL(하위 2-bit)을 보고 CPL을 결정한다:

  • CS=0x08 (RPL=0) → 커널 모드로 복원 (커널 스레드 간 전환)
  • CS=0x23 (RPL=3) → 유저 모드로 복원 (유저 프로세스로 복귀)

유저 모드로 전환될 때 CPU는 자동으로 SS:RSP도 스택에서 복원한다. 같은 CPL로 돌아가면 SS:RSP를 pop하지 않으며, live RSP는 RIP/CS/RFLAGS를 소비한 다음 위치를 가리킨다. 따라서 같은-CPL 전환 코드는 frame의 뒤쪽 배치가 곧 재개할 stack 위치가 되도록 구성해야 한다.

실제 OS (Linux/Windows)

Linux에서도 iretq는 인터럽트/예외 리턴의 표준 경로다. 다만 성능을 위해 두 가지 빠른 경로를 추가로 사용한다:

경로명령어조건복원 대상
Fast pathsysretqsyscall 리턴, 단순 조건 충족 시RCX→RIP, R11→RFLAGS
Slow pathiretq인터럽트 리턴, signal 처리 등스택에서 5개 레지스터
Very slowiretq + NMI workaroundNMI 중첩 시동일 + IST 스택 보호

sysretq는 iretq보다 수십 사이클 빠르지만, RFLAGS의 특정 비트(TF 등)를 제대로 복원하지 못하는 제약이 있어, 항상 사용할 수는 없다.

Windows도 유사하게 KiSystemServiceExit에서 fast path(sysretq)와 slow path(iretq)를 분기한다.

PintOS 구현

현재 로컬 PintOS는 경로를 나눈다. do_iret()을 통과하는 초기 유저 진입·인터럽트/예외·스레드 상태 복원은 iretq를 사용하지만, 정상 syscall 복귀는 userprog/syscall-entry.S 끝의 sysretq를 사용한다.

do_iret()의 핵심 동작을 단계별로 분해하면:

1단계: RSP를 intr_frame 시작 주소로 설정

이 시점부터 기존 커널 스택은 포기된다. 스택 변수, 지역 변수 모두 접근 불가.

2단계: 범용 레지스터 15개 복원 (offset 0~112)

15개 레지스터 × 8 bytes = 120 bytes. struct gp_registers 전체에 해당.

3단계: 세그먼트 레지스터 복원 + 건너뛰기

vec_no와 error_code는 CPU가 인터럽트 진입 시 사용하는 값이므로 복원하지 않는다.

4단계: iretq 실행

이 시점에서 RSP는 intr_frame의 rip 필드를 가리킨다. CPU는 RIP, CS, RFLAGS를 꺼내고, target CS가 바깥 CPL이면 이어서 RSP와 SS까지 꺼내 실행을 재개한다.

메모리 레이아웃과 오프셋 계산

offset필드크기do_iret()에서의 의미
0x00~0x70R.r15~R.rax120 B범용 레지스터 15개 복원
0x78es slot8 BES와 padding
0x80ds slot8 BDS와 padding
0x88vec_no8 B복원하지 않고 건너뜀
0x90error_code8 B복원하지 않고 건너뜀
0x98rip8 B항상 pop
0xA0cs8 B slot항상 pop, target CPL 결정
0xA8eflags8 B항상 pop
0xB0rsp8 B바깥 CPL로 전환할 때만 pop
0xB8ss8 B slot바깥 CPL로 전환할 때만 pop
0xC0frame 끝—packed intr_frame 전체 192 B

호출 경로 3가지

do_iret()는 PintOS에서 세 가지 경로에서 호출된다:

경로호출 위치CS 값효과
Context switchthread_launch()0x08 (커널)커널 스레드 간 전환, out_iret 레이블로 복귀
새 프로세스 시작process_exec() → do_iret(&_if)0x23 (유저)ELF의 e_entry로 유저 모드 진입
fork 자식 시작__do_fork() → do_iret(&if_)0x23 (유저)부모의 중단 지점으로 유저 모드 복귀 (RAX=0)

QEMU 에뮬레이션

QEMU TCG에서 iretq는 guest 코드의 iretq opcode(0x48 0xCF)를 만나면 Translation Block을 종료하고 helper_iret_protected() 헬퍼를 호출한다. 이 헬퍼가 하드웨어의 iretq 동작을 소프트웨어로 재현한다.

TCG iretq 처리 단계:

단계TCG 함수/동작CPUX86State 변경
1helper_iret_protected() 진입—
2guest 스택에서 RIP 읽기 (cpu_ldq_kernel)env->eip = new_rip
3guest 스택에서 CS 읽기 + GDT lookupenv->segs[R_CS] 갱신, env->hflags에 CPL 반영
4guest 스택에서 RFLAGS 읽기env->eflags = new_rflags (IF, IOPL 등 마스크 적용)
5CPL 변경 시 SS:RSP 읽기env->regs[R_ESP] = new_rsp, env->segs[R_SS] 갱신
6segment descriptor cache 전체 갱신DS, ES, FS, GS의 DPL 검사 → 위반 시 NULL로 리셋
7TB lookup/생성새 env->eip에서 다음 TB 시작

단계 6이 중요하다: 하드웨어 iretq는 CPL이 바뀌면 DS, ES 등의 DPL을 재검사하여, 현재 CPL보다 높은 권한의 세그먼트를 NULL selector로 리셋한다. TCG도 이를 재현한다.

RFLAGS 마스크 규칙: iretq가 복원하는 RFLAGS에서 VM, RF 비트는 조건부로 처리되고, CPL > 0이면 IOPL 필드는 변경하지 않는다. TCG의 helper_iret_protected()도 이 마스크를 정확히 적용한다.

iretq와 Translation Block 경계: iretq는 반드시 TB의 마지막 명령어다. iretq 후 새 RIP에서 새 TB가 시작되므로, 커널→유저 전환 시 TB chain이 끊기고 새로운 유저 코드 TB로 점프한다. 이것이 context switch 비용의 일부다.

GDB에서 do_iret 전체 흐름 관찰 (5단계):

(gdb) b *do_iret+4
(gdb) commands
  printf "=== do_iret 진입 ===\n"
  printf "tf address: %p\n", $rdi
  printf "tf->rip: 0x%lx\n", *(uint64_t *)($rdi + 152)
  printf "tf->cs:  0x%x\n", *(uint16_t *)($rdi + 160)
  printf "tf->rsp: 0x%lx\n", *(uint64_t *)($rdi + 176)
  continue
end

; iretq 직전 (addq $32 실행 후, RSP가 rip 필드를 가리키는 시점)
(gdb) b *do_iret+87
(gdb) commands
  printf "=== iretq 직전 ===\n"
  printf "stack top (RIP): 0x%lx\n", *(uint64_t *)$rsp
  printf "stack +8  (CS):  0x%lx\n", *(uint64_t *)($rsp+8)
  printf "stack +16 (RFLAGS): 0x%lx\n", *(uint64_t *)($rsp+16)
  printf "stack +24 (RSP): 0x%lx\n", *(uint64_t *)($rsp+24)
  printf "stack +32 (SS):  0x%lx\n", *(uint64_t *)($rsp+32)
  stepi
  printf "=== iretq 직후 ===\n"
  info registers rip cs rsp ss eflags
end

이 breakpoint로 iretq 전후의 5개 레지스터 변화를 한 눈에 볼 수 있다. CS가 0x08→0x23으로 바뀌면 유저 모드 전환, 0x08→0x08이면 커널 스레드 간 전환이다.

sysretq와의 성능 차이 (QEMU TCG):

실제 하드웨어에서 두 명령의 비용은 CPU model과 복귀 조건에 따라 달라지므로 고정 cycle 수로 일반화하지 않는다. QEMU TCG에서도 helper와 최적화 경로는 version에 따라 달라질 수 있다. 현재 PintOS syscall fast return이 sysretq라는 사실과 do_iret() 경로가 iretq라는 사실을 분리해 측정해야 한다.

Linux iretq/sysretq 선택 로직 상세

Linux 커널의 syscall 복귀 경로(entry_SYSCALL_64)에서 iretq와 sysretq를 선택하는 조건:

%% Linux iretq와 sysretq 선택 조건
flowchart TD
  done["syscall 핸들러 완료"]
  notify["TIF_NOTIFY_SIGNAL<br/>or TIF_SINGLESTEP?"]
  flags["RFLAGS에 TF/AC/RF<br/>특수 비트?"]
  segments["CS/SS가<br/>표준 유저 값?"]
  slow["slow path: iretq"]
  fast["fast path: sysretq"]
  sysret["RCX ← RIP<br/>R11 ← RFLAGS<br/>sysretq"]
  iret["스택에 5개 값 push<br/>iretq"]
  done --> notify
  notify -->|"Yes"| slow
  notify -->|"No"| flags
  flags -->|"Yes"| slow
  flags -->|"No"| segments
  segments -->|"No"| slow
  segments -->|"Yes"| fast
  fast --> sysret
  slow --> iret

sysretq의 제약: sysretq는 RCX에서 RIP를, R11에서 RFLAGS를 복원한다. RFLAGS의 RF(Resume Flag)를 복원하지 못하고, non-canonical RCX가 들어가면 gp가 ring 0에서 발생하는 보안 버그가 있었다 (CVE-2014-4699). 이 때문에 Linux는 ptrace로 RIP가 변경된 경우 반드시 iretq 경로를 사용한다.

현재 로컬 PintOS도 경로를 구분한다. 이 Linux 조건표와 세부 조건은 다르지만, 정상 syscall 복귀는 sysretq, 초기 유저 진입·인터럽트/예외·스레드 상태 복원은 do_iret()의 iretq를 사용한다.
