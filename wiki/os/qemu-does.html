QEMU가 하는 일

QEMU가 하는 일

한 줄 요약: QEMU가 하는 세 가지 — guest register 보관·주소 변환 재현·장치 I/O 처리.

QEMU가 하는 일 상태

QEMU는 세 가지 일을 한다. guest register 보관, 주소 변환 효과 재현, 장치 I/O 처리. 이 세 가지는 모두 “하드웨어가 하는 일을 소프트웨어로 흉내내기”다. QEMU는 syscall 번호를 해석하지 않고, 프로세스를 관리하지 않으며, 파일 시스템 정책을 세우지 않는다. OS가 하는 일과 QEMU가 하는 일의 경계를 정확히 아는 것이 PintOS 디버깅의 전제다.

상세 설명

추상 개념 (하드웨어 에뮬레이터의 역할)

물리 CPU는 레지스터에 값을 저장하고, 명령어를 fetch/decode/execute하며, MMU를 통해 가상→물리 주소 변환을 수행하고, I/O 포트나 MMIO를 통해 장치와 통신한다.

QEMU는 이 물리 CPU 없이 동일한 효과를 만들어낸다.

물리 하드웨어의 일QEMU의 재현 방식
레지스터에 값 저장CPUX86State.regs[], eip, eflags, cr[] 구조체 필드
명령어 실행TCG(Tiny Code Generator)로 guest 명령어를 host 명령어로 번역 실행
MMU 주소 변환softmmu: guest page table walk를 소프트웨어로 수행
장치 I/O장치 모델(PIT, PIC, IDE)이 I/O 포트 접근에 응답
인터럽트 전달가상 PIC/APIC 모델이 인터럽트 핀을 에뮬레이션

핵심: QEMU는 메커니즘(CPU가 어떻게 동작하는가)을 재현한다. 정책(어떤 프로그램에게 어떤 자원을 줄 것인가)은 guest OS의 몫이다.

실제 OS 관점에서의 QEMU

실제 OS 개발에서 QEMU는 두 가지 역할로 쓰인다.

  1. 개발/테스트 환경: 물리 하드웨어 없이 OS를 부팅하고 테스트할 수 있다. 커널 크래시가 나도 호스트 OS는 안전하다.
  2. 디버깅 도구: GDB stub을 통해 guest CPU 상태를 멈추고, 레지스터와 메모리를 검사할 수 있다. 물리 CPU에서는 JTAG 같은 비싼 장비가 필요한 일을 소프트웨어로 할 수 있다.

KVM 가속 모드에서는 guest 명령어가 물리 CPU에서 직접 실행된다. 이 경우 QEMU는 장치 모델 제공과 VM entry/exit 관리에 집중한다. PintOS는 KVM 없이 순수 TCG 에뮬레이션을 사용한다.

PintOS에서의 QEMU 역할

PintOS를 실행할 때 QEMU가 하는 구체적인 일:

1. Guest register 보관

PintOS가 RAX에 syscall 번호를 넣고 syscall 명령을 실행하면, QEMU는 CPUX86State.regs[R_EAX]에 그 값을 보관하고, syscall 명령의 하드웨어 의미(RCX←RIP, R11←RFLAGS, RIP←LSTAR MSR 값)를 재현한다.

%% syscall 명령에서 QEMU와 PintOS의 역할
flowchart LR
  user["PintOS 유저<br/>RAX = SYS_WRITE<br/>syscall 실행"]
  qemu["QEMU TCG<br/>regs[R_EAX] 업데이트<br/>RIP를 LSTAR로 바꿈"]
  kernel["PintOS syscall_handler()<br/>f-&gt;R.rax를 SYS_WRITE로 해석"]
  user -->|CPU 명령 효과| qemu
  qemu -->|커널 진입 상태 제공| kernel

QEMU는 SYS_WRITE가 무엇을 의미하는지 모른다. QEMU는 RAX 값을 보관하고 syscall 명령의 CPU 동작만 재현한다.

2. 주소 변환 효과 재현

PintOS가 pml4_set_page()로 PTE를 설치하면, 그 변경은 guest RAM 안의 page table 메모리에 쓰여진다. 이후 유저 코드가 해당 VA에 접근하면, QEMU softmmu가 guest page table을 walk하여 물리 프레임을 찾고, RAMBlock 호스트 메모리에서 실제 바이트를 읽어 결과를 돌려준다.

%% 유저 VA 접근과 QEMU softmmu 주소 변환
flowchart LR
  user["유저 코드<br/>mov eax, [0x400000]"]
  ram["QEMU RAMBlock<br/>host_mem[0x1234000]에서<br/>4바이트 읽기"]
  softmmu["QEMU softmmu<br/>guest PML4→PDPT→PD→PT<br/>PA 0x1234000 계산"]
  user -->|VA 0x400000 접근| softmmu
  softmmu -->|guest PA 계산| ram

3. 장치 I/O 처리

PintOS가 disk_write()로 IDE 컨트롤러에 섹터를 쓰면, QEMU IDE 장치 모델이 해당 I/O 포트 접근을 가로채고, BlockBackend을 통해 호스트 파일(pintos.dsk 등)에 데이터를 쓴다.

%% IDE 포트 쓰기와 호스트 파일 기록
flowchart LR
  pintos["PintOS<br/>outb(0x1F7, CMD_WRITE)"]
  ide["QEMU IDE model<br/>port 0x1F7 접근 감지<br/>write 명령 처리"]
  block["QEMU BlockBackend<br/>호스트 파일에<br/>512B 섹터 기록"]
  pintos -->|I/O port 접근| ide
  ide -->|sector write| block

PIT(timer)와 PIC(interrupt controller)도 같은 방식이다. PIT 모델이 주기적으로 IRQ0을 발생시키면, PIC 모델이 CPU 인터럽트 핀을 올리고, QEMU가 guest의 인터럽트 벡터를 통해 PintOS의 timer_interrupt()를 호출하게 만든다.

QEMU 에뮬레이션 (자기 자신)

QEMU의 세 가지 하위 시스템 사이의 상호작용:

%% QEMU 에뮬레이션 하위 시스템
flowchart TD
  tcg["TCG 번역기<br/>guest 명령어를<br/>host 명령어로 변환"]
  softmmu["SoftMMU<br/>TLB 조회·guest VA→PA 변환"]
  ram["RAMBlock<br/>guest PA→host memory backing"]
  device["장치 모델<br/>PIT · PIC · IDE"]
  block["BlockBackend"]
  host["호스트 파일"]
  tcg -->|메모리 접근| softmmu
  softmmu --> ram
  tcg -->|I/O 포트 접근| device
  device --> block
  block --> host

TCG Translation Block은 guest 명령어 몇 개를 묶어 host 코드로 번역하고 캐시한다. 같은 guest 코드를 반복 실행하면 번역 오버헤드가 사라진다.

TCG 번역 비용

항목대략 값
TB(Translation Block) 크기100500 host 명령어
TB 캐시 크기 (기본)32 MB
최초 번역 비용guest 명령어당 10100 ns
캐시 히트 시 오버헤드25x native (간접 호출 비용)
KVM 가속 시 오버헤드~1.05x native (VM entry/exit 비용)

PintOS는 KVM 없이 순수 TCG를 사용하므로 25x 오버헤드가 발생하지만, OS 학습에는 충분한 속도다.
