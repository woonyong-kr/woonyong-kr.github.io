워드 정렬 패딩 (Word Align Padding)

워드 정렬 패딩 (Word Align Padding)

한 줄 요약: 워드 정렬 패딩은 스택 포인터를 8바이트 경계로 내림 정렬해 비정렬 접근을 방지하는 작업이다.

스택 포인터를 정렬하는 이유

스택에 데이터를 배치할 때는 포인터와 정수 값이 적절한 주소 경계에 놓이도록 해야 한다. 여기서 다루는 워드 정렬 패딩은 스택 포인터를 8바이트(word) 경계로 내림 정렬하는 작업이다.

비정렬 메모리 접근은 성능을 떨어뜨릴 수 있다. 캐시 라인 경계를 걸치면 두 캐시 라인에서 데이터를 읽어야 할 수 있기 때문이다. movaps처럼 정렬된 피연산자를 요구하는 일부 SSE 명령어는 정렬 조건을 위반하면 gp(General Protection) 예외를 일으킨다. callee가 ABI에 맞춰 local 변수를 배치하거나 명령어를 선택할 수 있다는 점에서도 정렬 규칙은 중요하다.

이때 8바이트 워드 정렬과 함수 호출 시의 16바이트 스택 정렬은 구분해야 한다. x86-64 ABI(System V AMD64)는 함수 호출 시점의 RSP 정렬 규칙을 정의한다. call 명령어가 8바이트 return address를 push하므로 함수 본문에 진입한 시점의 RSP는 16n + 8 형태가 된다.

운영체제와 호출 규약의 정렬

Linux에서는 execve → create_elf_tables() 과정에서 argv와 envp 문자열을 스택에 복사한 뒤, 포인터 배열을 쌓기 전에 스택 포인터를 정렬한다. glibc의 _start 진입 시 RSP는 16바이트 정렬 상태다.

Windows의 x64 calling convention도 RSP의 16바이트 정렬을 요구한다. 호출자는 추가로 32바이트 shadow space를 확보한다.

PintOS 초기 스택의 워드 정렬

userprog/process.c의 setup_initial_stack() 함수는 유저 프로그램의 초기 스택을 구성한다. 먼저 문자열을 push하고 스택 포인터를 8바이트 경계에 맞춘다.

비트 연산 & -8은 주소의 하위 3비트를 0으로 만든다. -8의 이진 표현은 ...11111111111111111111111111111000이므로 AND 연산의 결과는 원래 주소보다 크지 않은 8의 배수가 된다.

문자열 다음에는 sentinel(0), argv 포인터 배열, fake return address를 push한다. 각 항목은 8바이트(uintptr_t)이므로 이 과정에서도 8바이트 정렬은 유지된다.

다만 8바이트 정렬이 유지된다는 사실만으로 _start 진입 시 RSP가 항상 16바이트 정렬된다고 결론 내릴 수는 없다. 최종 주소까지 계산해 별도로 확인해야 한다.

QEMU와 GDB에서 구분해 볼 정렬 문제

QEMU TCG는 게스트 명령어의 정렬 조건을 소프트웨어로 처리한다. movaps/movdqa 같은 SSE 명령어를 번역할 때 주소의 하위 비트를 검사하고, 비정렬 주소이면 raise_exception_ra(EXCP0D_GPF, ...) (#GP)를 발생시킨다. 일반 mov 명령어는 x86-64에서 비정렬 접근이 허용되므로 실행을 계속한다.

따라서 캐시 라인 분할에 따른 실제 하드웨어 성능 차이와 명령어의 정렬 조건 위반으로 발생하는 예외는 서로 다른 문제다.

GDB에서는 _start breakpoint에서 RSP를 검사해 해당 실행의 정렬 결과를 확인할 수 있다.

(gdb) b _start
(gdb) p/x $rsp & 0xf
$1 = 0x0              ← 16바이트 정렬 확인
(gdb) x/8gx $rsp      ← fake return + argv 포인터 배열 확인

이 출력은 관찰한 실행에서 16바이트 정렬이 확인되었다는 뜻이다. 모든 입력에 대한 보장을 직접 나타내지는 않는다.

& -8의 주소 계산

주소 예시로 비트 연산을 추적하면 다음과 같다.

표현64비트 이진
-8 (2의 보수)0xFFFFFFFFFFFFFFFF8 = ...1111111111111000
주소 예: 0x4747FFDD...0100_0111_0100_0111_1111_1111_1101_1101
AND 결과...0100_0111_0100_0111_1111_1111_1101_1000 = 0x4747FFD8

AND 연산 뒤에는 하위 3비트가 0이 되므로 결과 주소가 8의 배수가 된다. 이 예시에서 padding 크기는 원래 주소와 정렬된 주소의 차이인 0xFFDD - 0xFFD8 = 5 bytes다.

args-many 스택 주소 추적

args-many 테스트 예제: `./args-many a b

아래 값은 문자열 배치부터 최종 RSP까지 한 실행 사례를 추적한 결과다.

  • 주소(예시) 내용 설명
  • 0x4747FFE5 “args-many\0” 10 bytes
  • 0x4747FFE3 “a\0” 2 bytes
  • 0x4747FFE1 “b\0” 2 bytes
  • 0x4747FFDF “c\0” 2 bytes
  • 0x4747FFDD “d\0” 2 bytes
  • 총 18 bytes
  • word-align
  • 0x4747FFD8 (padding 5 bytes) & -8 → 0xFFD8
  • 0xFFDD & 0xFFF8 = 0xFFD8
  • sentinel
  • 0x4747FFD0 0x0000000000000000 argv[5] = NULL
  • argv 포인터
  • 0x4747FFC8 0x4747FFDD argv[4] → “d”
  • 0x4747FFC0 0x4747FFDF argv[3] → “c”
  • 0x4747FFB8 0x4747FFE1 argv[2] → “b”
  • 0x4747FFB0 0x4747FFE3 argv[1] → “a”
  • 0x4747FFA8 0x4747FFE5 argv[0] → “args-many”
  • fake return
  • 0x4747FFA0 0x0000000000000000 fake return address

이 사례에서 RSP는 0x4747FFA0이다. 0xFFA0 & 0xF = 0x0이므로 이 주소의 16바이트 정렬이 확인된다.

특정 실행 결과와 일반적인 정렬 보장

문자열을 정렬한 뒤 push하는 8바이트 원소는 1개의 sentinel, argc개의 포인터, 1개의 fake return address다. 원소 수는 argc + 2이고 최종 주소는 다음과 같이 계산한다.

RSP_final = aligned_after_strings - 8 × (argc + 2).

aligned_after_strings가 8의 배수라는 사실만으로는 RSP_final이 16의 배수라고 단정할 수 없다. 16바이트 정렬 여부를 판단하려면 aligned_after_strings의 나머지와 8 × (argc + 2)를 함께 계산해야 한다.

argc=5이면 push 원소는 7개이고 이동량은 56 bytes다. RSP는 계속 8바이트 경계에 놓이지만, 시작 주소에 따라 16바이트 경계에서는 벗어날 수 있다. 따라서 앞의 특정 주소에서 16바이트 정렬이 확인된 결과와 PintOS 구현이 모든 입력에서 이를 보장한다는 주장은 구분해야 한다.

제시된 구현에서는 문자열 영역의 길이와 padding에 따라 최종 정렬 상태가 달라질 수 있다. 실제 PintOS에서는 SSE를 사용하지 않으므로 이 제약이 문제로 드러나지 않는다.

초기 스택 구성 순서

flowchart TD
    A["USER_STACK = 0x47480000"] --> B["문자열 역순 push<br/>stack_p -= strlen+1, memcpy"]
    B --> C["stack_p & -8<br/>8바이트 내림 정렬<br/>padding 0~7 bytes"]
    C --> D["NULL sentinel push<br/>stack_p -= 8, memset 0"]
    D --> E["argv 포인터 역순 push<br/>argc회 반복, 각 8 bytes"]
    E --> F["RDI = argc, RSI = stack_p"]
    F --> G["fake return address push<br/>stack_p -= 8, memset 0"]
    G --> H["if_->rsp = stack_p<br/>do_iret으로 유저 진입"]
  • USER_STACK (0x47480000)
  • ↓ 문자열 역순 push
  • “args-many\0” | 가변 길이
  • “a\0” “b\0” …
  • ↓ RSP & -8 (8바이트 내림 정렬)
  • padding (0~7 bytes)
  • ↓ 포인터 배열 + sentinel + fake return
  • NULL sentinel (8B)
  • argv[n-1] ptr (8B)
  • …
  • argv[0] ptr (8B)
  • fake return (8B) | ← RSP (16바이트 정렬 여부 확인 지점)
