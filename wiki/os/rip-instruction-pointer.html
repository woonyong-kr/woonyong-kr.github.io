RIP — 다음 명령어 주소

RIP — 다음 명령어 주소

확인 범위: 이 문서는 RIP의 일반 원리와 Linux·PintOS·QEMU에서의 구현 및 관찰 지점을 개념적으로 설명한다. 제시된 코드 위치, 구조체 배치, 주소 범위, GDB 출력과 성능 관련 판단은 특정 소스 버전이나 실제 실행·측정으로 검증한 결과가 아니므로, 적용 대상의 코드와 실행 기록을 별도로 확인해야 한다.

한 줄 요약: 다음 실행할 명령어의 가상 주소를 담는 x86-64 RIP 레지스터 — fetch 단계가 참조.

RIP 상태

RIP(Register Instruction Pointer)는 x86-64 CPU가 다음에 실행할 명령어의 가상 주소를 담는 64비트 레지스터다. CPU는 fetch 단계에서 RIP를 참조해 명령어를 가져온다. 인터럽트 진입, 컨텍스트 스위치, 시스템 콜 복귀처럼 실행 위치가 바뀌는 OS의 제어 흐름도 결국 RIP를 저장하거나 새로운 값으로 바꾸고 다시 복원하는 과정으로 볼 수 있다.

상세 설명

추상 개념 (CPU 하드웨어 규칙)

x86-64에서 RIP는 소프트웨어가 MOV 등의 범용 명령어로 직접 쓸 수 없는 특수 레지스터다. 실행 위치는 순차 실행, 분기와 점프, 인터럽트와 예외, 복귀 명령에 따라 다음과 같이 바뀐다.

변경 원인하드웨어 동작예시
순차 실행현재 명령어 크기만큼 자동 증가add rax, 1 → RIP += 명령어 길이
분기/점프JMP, CALL, RET 등이 RIP를 즉시값/레지스터값으로 설정call 0x401000
인터럽트/예외CPU가 현재 RIP를 스택에 push 후, IDT 핸들러 주소로 설정pf → page_fault handler
IRET / SYSRET스택/MSR에서 복원커널→유저 복귀 시

x86-64 명령어의 길이는 1~15 bytes로 일정하지 않다. 따라서 순차 실행 때 RIP가 증가하는 크기도 명령어마다 다르며, CPU의 명령어 디코더가 길이를 결정한 뒤 RIP를 갱신한다.

RIP-relative Addressing

RIP는 다음 명령어를 찾는 데만 쓰이지 않는다. x86-64의 MOV, LEA 등 다수 명령어는 [RIP + disp32] 형태로 주소를 인코딩할 수 있다. 이때 disp32는 현재 명령어 다음 주소, 즉 갱신된 RIP를 기준으로 한 상대 오프셋이다. 이 RIP-relative addressing은 64비트 모드가 32비트 모드와 구별되는 특징 중 하나다.

이 주소 지정 방식에는 다음과 같은 특성이 있다.

항목설명
PIC (Position-Independent Code)코드가 어디에 로드되든 상대 오프셋만 맞으면 동작 → 공유 라이브러리·PIE 바이너리 필수
32비트 범위disp32로 ±2 GB 범위 접근 가능. x86-64 small code model에서 전역 데이터 접근에 충분
절대 64비트 주소 불필요절대 주소(8 bytes)보다 명령어 크기가 작아 icache 효율적

PintOS의 유저 프로그램도 GCC가 기본적으로 RIP-relative addressing을 사용해 컴파일한다. objdump -d 결과에서 (%rip) 표기가 보이면 이 모드다.

실제 OS (Linux)

하드웨어가 실행 위치를 RIP에 보관하더라도, OS가 중단된 실행을 나중에 이어 가려면 그 값을 메모리의 실행 문맥에 옮겨 두어야 한다. Linux 커널에서는 struct pt_regs의 ip 필드가 이 역할을 한다. 시그널 전달과 ptrace 디버깅, context switch처럼 실행 위치를 보존하거나 변경해야 하는 경로가 이 필드를 읽거나 쓴다.

새 실행 흐름을 시작할 때는 그 흐름이 처음 재개될 주소를 이 문맥에 넣는다. 예를 들어 do_fork() 후 자식의 pt_regs.ip는 ret_from_fork 주소로 설정된다. 이후 자식이 스케줄링되면 저장된 주소가 복원되어 fork 복귀 코드부터 실행된다. 프로그램 시작, 자식 생성, 시그널 전달, 디버거의 레지스터 변경도 같은 관점에서 비교할 수 있다.

경로RIP 설정 값시점
execve()ELF e_entry 또는 동적 링커 주소프로그램 시작
fork() → copy_thread()ret_from_fork자식 스케줄링 시
signal delivery시그널 핸들러 주소유저 복귀 직전
ptrace(PTRACE_SETREGS)디버거가 지정한 값디버깅 중

PintOS 구현

PintOS에서도 Linux의 pt_regs.ip와 마찬가지로, CPU가 중단한 위치를 메모리의 실행 문맥에 저장한다. 그 위치가 struct intr_frame의 rip 필드다.

이 필드는 새 실행 흐름을 시작하거나 기존 흐름을 복제하고 복원하는 다음 경로에서 사용된다.

  1. thread_create() — 커널 스레드 최초 RIP 설정: 새 스레드를 만들 때 t->tf.rip = (uintptr_t) kernel_thread로 설정한다. 이 스레드가 처음 스케줄되면 do_iret()가 이 rip를 복원하여 kernel_thread() 함수부터 실행을 시작한다. kernel_thread()는 intr_enable() → function(aux) → thread_exit() 순서로 진행한다.

  1. ELF 적재 후 유저 진입: load() → e_entry를 if_.rip에 설정 → do_iret()로 유저 모드 진입. 이때 RIP = ELF header의 e_entry (보통 0x400000 부근).

  2. fork — 자식의 RIP: __do_fork()에서 부모의 intr_frame을 memcpy(&if_, &args->if_, ...)로 통째로 복사한다. 따라서 자식의 rip는 부모가 syscall을 호출한 시점의 다음 명령어 주소와 동일하다. if_.R.rax = 0으로 반환값만 바꾸고, do_iret(&if_)로 유저 복귀하면 자식은 부모와 같은 코드 위치에서 rax=0(fork 반환값 0)으로 재개된다.

  3. 시스템 콜 진입: syscall 명령어가 실행되면 CPU가 현재 RIP를 RCX에 저장하고, LSTAR MSR에 등록된 커널 진입점 주소를 RIP에 로드한다.

  4. 컨텍스트 스위치: thread_launch()가 현재 스레드의 레지스터를 저장할 때 intr_frame의 rip에 복귀 주소가 담기며, do_iret()가 다음 스레드의 rip를 복원하여 그 스레드가 중단했던 지점부터 재개한다.

QEMU 에뮬레이션

실제 CPU 대신 QEMU TCG 모드에서 guest를 실행하면 RIP도 에뮬레이터의 상태로 표현된다. guest RIP는 CPUX86State.eip 필드에 저장된다. 이름은 32비트 호환 형태지만 64비트 모드에서는 64비트 폭으로 사용된다. QEMU는 코드를 Translation Block(TB) 단위로 번역하며, 각 TB의 시작 주소를 그 시점의 RIP로 삼는다.

TCG에서 RIP의 생명주기

1. TB 시작: QEMU가 guest RIP(CPUX86State.eip)를 읽어 TB의 pc 필드에 기록
2. TB 번역: guest 명령어를 TCG IR로 변환. 각 명령어 후 RIP를 갱신하는 IR 포함
3. TB 실행: 호스트 코드 실행. TB 끝에서 CPUX86State.eip에 최종 RIP를 write-back
4. TB 체인: 다음 TB를 lookup. cache hit이면 host JMP, miss면 다시 번역

인터럽트가 주입되면 QEMU는 하드웨어의 RIP 전환 규칙도 에뮬레이션한다. timer interrupt를 주입하는 경우 guest의 현재 RIP를 guest 커널 스택에 push하고, IDT 핸들러 주소를 RIP에 로드한다. 이 과정은 x86_cpu_exec_interrupt() → do_interrupt_all() 경로에서 수행된다.

GDB로 RIP 관찰

RIP 자체와 저장된 복귀 주소를 함께 보면 유저 코드, 커널 진입, fork 복귀, context switch 사이의 전환을 추적할 수 있다. 다음 명령은 관찰 지점을 보여 주지만, 출력값과 주소 범위는 실제 실행 결과로 별도 확인해야 한다.

RIP 관련 QEMU 내부 구조체

CPUX86State {
    target_ulong eip;       // guest RIP (64비트 모드에서 64비트)
    // ...
}

TranslationBlock {
    target_ulong pc;        // 이 TB가 시작하는 guest RIP
    target_ulong cs_base;   // segment base (64비트 long mode에서 0)
    uint16_t size;           // TB의 guest 바이트 수
    // ...
}

RIP 값 추적

PintOS에서 RIP 값을 해석할 때는 현재 주소가 유저 영역인지 커널 영역인지 먼저 구분할 수 있다. 다음 범위와 전형적인 값은 특정 실행에서 확인된 결과가 아니라 문서가 제시하는 추적 기준이므로, 대상 환경의 배치와 함께 확인해야 한다.

struct intr_frame 내 rip의 오프셋은 gp_registers(15 × 8 = 120 bytes) + es(2) + pad(6) + ds(2) + pad(6) + vec_no(8) + error_code(8)로 계산하면 152 bytes (0x98)다. 이 배치는 적용 대상의 실제 구조체 정의로 확인해야 한다.

순서도 / 개념도

flowchart TD

    I --> A

RIP와 디버깅: 자주 만나는 패턴

오류나 중단 지점에서 RIP가 가리키는 주소는 CPU가 실행 흐름을 어디에서 멈췄는지 보여 준다. 다만 중단 원인에 따라 현재 명령어를 가리키기도 하고 그 다음 주소를 가리키기도 하므로, 예외 종류와 함께 해석해야 한다.

상황RIP가 가리키는 곳의미
#PF (page fault)fault를 일으킨 명령어MMU가 변환 실패. CR2에 fault 주소, RIP에 명령어 주소
#GP (general protection)위반 명령어권한 부족 또는 잘못된 세그먼트 접근
kernel panic 메시지crash 시점의 커널 코드addr2line 또는 objdump -d로 함수 역추적 가능
breakpoint중단된 명령어 다음GDB가 INT3을 삽입하여 RIP를 trap 후 주소 + 1

#PF 발생 시 CPU는 RIP를 증가시키지 않는다. fault handler가 문제를 해결한 뒤 IRET으로 복귀하면 같은 명령어가 다시 실행된다. demand paging은 이 재실행 흐름을 이용한다.
