명시적 가용 리스트

명시적 가용 리스트

확인 범위: 이 문서는 명시적 가용 리스트의 구조, 탐색·삽입 정책과 설계 선택 기준을 설명하며, 제시된 코드는 특정 환경에서 검증된 구현이 아니라 개념적 예시다. 실제 mm.c의 자료구조·복잡도·처리량·메모리 이용률에 관한 판단은 해당 코드와 실행 환경, 버전, 실행 기록 및 성능 측정을 별도로 확인해야 한다.

한 줄 요약: Explicit free list는 빈 블록의 페이로드 영역에 prev/next 포인터를 넣어, 빈 블록끼리만 이중 연결 리스트로 연결하는 할당기 구조다.

명시적 가용 리스트 구분

Implicit free list의 가장 큰 약점은 빈 블록을 찾을 때 할당 블록까지 전부 순회한다는 것이다. 힙에 블록이 1000개 있고 그중 빈 블록이 10개뿐이라면, first fit 탐색은 평균적으로 할당 블록 수백 개를 헛되이 건너뛰어야 한다.

Explicit free list는 빈 블록끼리만 연결하여 이 문제를 해결한다. 빈 블록의 페이로드는 어차피 비어 있으므로, 그 공간에 prev/next 포인터를 저장해 이중 연결 리스트를 만든다. 할당 요청이 오면 이 리스트만 순회하면 되므로 탐색 시간이 빈 블록 수에만 비례한다.

이 구조를 모르면 glibc malloc의 bins, segregated list, 그리고 PintOS palloc과 비교할 때 설계 선택의 이유를 이해할 수 없다.

이 문서를 읽고 나면 다음을 구분할 수 있어야 한다.

  • 빈 블록 안에 포인터를 넣는 방법과 최소 블록 크기가 커지는 이유
  • LIFO 삽입과 주소 순서 삽입의 트레이드오프
  • implicit → explicit 전환에서 코드가 바뀌는 지점과 바뀌지 않는 지점

명시적 가용 리스트 흐름

빈 블록의 내부 구조

Implicit free list에서 빈 블록의 페이로드는 사용자에게 반환되지 않은 빈 공간이다. Explicit free list는 이 빈 공간에 두 개의 포인터를 저장한다.

%% 명시적 가용 리스트의 블록 내부 구조
flowchart LR
  allocated["할당 블록<br/>헤더 4B<br/>페이로드<br/>푸터 4B"]
  free["빈 블록<br/>헤더 4B<br/>prev 8B<br/>next 8B<br/>빈 공간<br/>푸터 4B"]
  bp["bp<br/>페이로드 시작"]
  previous["이전 빈 블록"]
  next["다음 빈 블록"]
  free_prev["free:prev"]
  free_next["free:next"]
  bp -->|가리키는 위치| free_prev
  free_prev -->|prev| previous
  free_next -->|next| next

할당 블록에는 포인터가 없다. 블록이 할당되면 prev/next 위치가 사용자 데이터로 덮어씌워진다. 포인터는 빈 상태일 때만 존재한다.

최소 블록 크기가 커진다

64비트 시스템에서 포인터는 8바이트다. 빈 블록에 prev(8B) + next(8B) = 16바이트가 필요하다.

최소 블록 크기 = 헤더(4) + prev(8) + next(8) + 푸터(4) = 24바이트

Implicit free list의 최소 블록 크기 16바이트보다 8바이트 커진다. 32비트 시스템이면 포인터가 4바이트이므로 최소 블록 크기는 같은 16바이트로 유지된다. 이것은 내부 단편화의 트레이드오프다. 빈 블록을 빠르게 찾는 대신 작은 블록의 오버헤드가 늘어난다.

탐색 — 빈 블록만 순회

할당 요청이 오면 free list의 head부터 next 포인터를 따라간다. 할당 블록은 리스트에 없으므로 건너뛸 필요가 없다.

%% 명시적 가용 리스트의 빈 블록 탐색
flowchart LR
  free_listp["free_listp"]
  free48["빈 48B<br/>prev = NULL"]
  free16["빈 16B"]
  free32["빈 32B"]
  null["NULL"]
  subgraph_cluster_heap_graph["힙 실제 배치"]
  h_alloc1["할당"]
  h_free48["빈 48B"]
  h_alloc2["할당"]
  h_alloc3["할당"]
  h_free16["빈 16B"]
  h_alloc4["할당"]
  h_free32["빈 32B"]
  h_epilogue["에필로그"]
  implicit["implicit: 7개 블록 모두 순회"]
  explicit["explicit: 빈 3개만 순회"]
  free_listp --> free48
  free48 -->|next| free16
  free16 -->|next| free32
  free32 -->|next| null
  free16 -->|prev| free48
  free32 -->|prev| free16
  h_alloc1 --> h_free48
  h_free48 --> h_alloc2
  h_alloc2 --> h_alloc3
  h_alloc3 --> h_free16
  h_free16 --> h_alloc4
  h_alloc4 --> h_free32
  h_free32 --> h_epilogue
  h_epilogue --> implicit
  implicit --> explicit

블록 수 N 중 빈 블록이 M개라면, implicit의 탐색은 O(N), explicit의 탐색은 O(M)이다. 할당률이 높을수록(M << N) 성능 차이가 크다.

왜 explicit가 더 빠른가?

블록 하나를 검사하는 시간을 c로 두고 평균 탐색 비용을 계산한다.

implicit 평균 탐색 비용 = c × N (전체 블록 순회) explicit 평균 탐색 비용 = c × M (빈 블록만 순회) 속도 향상 비율 = (c × N) / (c × M) = N / M

힙에 블록이 1000개, 그중 빈 블록이 10개라면 N / M = 1000 / 10 = 100이다. explicit free list는 이 경우 탐색량을 평균 100배 줄인다.

할당률이 높아 빈 블록 M이 전체 N에서 차지하는 비율이 작을수록 향상 폭이 커진다. “빈 블록만 연결한다”는 설계 선택의 이유가 이 비율에서 나온다.

삽입 정책 — LIFO vs 주소 순서

블록을 해제하면 free list에 삽입해야 한다. 두 가지 전략이 있다.

  • LIFO (Last In, First Out): 새로 해제된 블록을 리스트 맨 앞에 넣는다. O(1) 삽입. 단순하고 빠르지만, 리스트가 주소 순서와 무관해져서 인접 빈 블록을 바로 찾기 어렵다.
  • 주소 순서 (Address-ordered): 블록 주소 기준으로 정렬된 위치에 삽입한다. O(M) 삽입이 필요하지만, 인접 블록이 리스트에서도 인접하므로 병합이 자연스럽다. first fit + 주소 순서 조합은 best fit에 가까운 메모리 이용률을 보인다.

할당과 해제 — implicit에서 바뀌는 코드

Implicit free list에서 explicit로 바꿀 때 블록 구조(헤더/푸터)와 병합 로직(coalesce)은 그대로 유지된다. 바뀌는 부분은 세 곳이다.

  • find_fit(): 힙 전체 순회 → free list 순회
  • place(): 블록을 할당하면 free list에서 제거
  • free() / coalesce(): 빈 블록을 free list에 삽입, 병합 시 원래 블록을 리스트에서 제거 후 합친 블록을 삽입

병합 시 리스트 관리

병합은 implicit free list와 같은 네 가지 경우를 따르되, 추가로 리스트 포인터를 갱신해야 한다. Case 2(현재 + 다음 병합)를 예로 들면:

  1. 다음 블록을 free list에서 제거 (prev/next 포인터 재연결)
  2. 현재 블록의 헤더에 합산 크기 기록
  3. 합산된 블록의 푸터에 같은 크기 기록
  4. 합친 블록을 free list에 삽입

실제 할당기와의 비교

  • glibc malloc (ptmalloc2): 크기별로 여러 개의 explicit free list를 두는 bins 구조를 사용한다. small bin, large bin, unsorted bin, fastbin으로 나뉘며, 각 bin이 특정 크기 범위의 빈 블록을 관리한다. 이것이 segregated list의 기반이다.
  • PintOS: palloc은 비트맵 기반이라 free list를 쓰지 않는다. PintOS의 malloc은 arena/descriptor 방식이며, explicit free list와는 다른 설계다.
  • Malloc Lab: 학생 구현에서 implicit → explicit 전환은 대표적인 최적화 단계다. 보통 이 단계에서 처리량(throughput)이 크게 개선된다.

Explicit free list 매크로 (개념적 구현)

Malloc Lab mm.c의 블록 접근 매크로는 implicit free list와 동일하다. Explicit free list에서는 빈 블록의 prev/next 접근 매크로가 추가된다.

bp는 페이로드 시작 주소다. 빈 블록일 때 bp 위치에 prev, bp+8 위치에 next가 들어간다. 할당되면 이 공간은 사용자 데이터로 덮어씌워진다.

이 두 함수가 explicit free list의 핵심이다. place()에서 할당 시 remove_free_block을, coalesce()에서 병합 전 관련 블록에 remove_free_block을 호출하고 합친 블록에 insert_free_block을 호출한다.

실제 학생 코드와의 차이

이 볼트의 Malloc Lab 최종 구현(mm.c)은 explicit free list 대신 AVL 트리 기반 best fit을 사용한다. prev/next 대신 LEFT, RIGHT, SAME_NEXT 포인터와 balance factor를 둔다. 그러나 블록 경계를 관리하는 매크로(HDRP, FTRP, PACK, GET_SIZE, GET_ALLOC, NEXT_BLKP, PREV_BLKP)와 coalesce() 로직은 implicit free list와 동일하다. 이는 블록 구조(implicit)와 탐색 자료구조(explicit/tree/segregated)가 독립적으로 교체 가능한 설계임을 보여준다.

정리

Explicit free list는 빈 블록의 빈 페이로드에 prev/next 포인터를 저장해, 빈 블록만 O(M) 탐색할 수 있게 만든다. 블록 구조(헤더/푸터)와 병합 로직은 implicit free list에서 그대로 이어받고, 탐색과 삽입/제거만 리스트 연산으로 교체한다. LIFO 삽입은 O(1)으로 빠르지만 메모리 이용률이 낮고, 주소 순서 삽입은 이용률이 높지만 O(M) 비용이 든다. 여기서 더 발전하면 크기별로 여러 리스트를 두는 segregated list, 2의 거듭제곱으로 분할·병합하는 buddy system으로 이어진다.
