fsync 보장 — 데이터가 디스크에 도달하는 순간

fsync 보장 — 데이터가 디스크에 도달하는 순간

범위: 이 문서는 write·fsync·fdatasync의 일반적인 내구성 경계와 선택 기준을 설명하고 Linux·PintOS·QEMU 경로를 개념적으로 비교한다. 제시된 코드 좌표, 구현 세부, 버전별 동작과 성능 수치는 특정 소스·환경에서 검증된 결과가 아니므로 실제 적용 시 대상 코드와 버전, 캐시·장치 설정 및 실행 기록을 별도로 확인해야 한다.

한 줄 요약: 일반 write 성공과 달리 fsync는 파일 데이터와 필요한 메타데이터의 동기화 완료를 기다리지만, 최종 내구성은 파일시스템·driver·장치 cache가 flush 계약을 지킨다는 전제에 의존한다.

fsync 보장 구조

fsync(fd)는 해당 파일의 수정된 in-core 데이터와 파일을 복구하는 데 필요한 메타데이터를 storage stack으로 동기화하고 완료를 기다리는 시스템 콜이다. 일반 write() 성공만으로는 이 내구성 경계를 보장하지 않는다. 다만 fdatasync()도 데이터와 데이터 검색에 필요한 메타데이터를 동기화하는 POSIX 수단이며, 어느 호출도 장치 firmware가 cache flush/FUA 계약을 거짓으로 이행하는 상황까지 보장하지는 못한다.

상세 설명

추상 개념 (저장소 계층 규칙)

write()에서 디스크까지의 경로:

유저 버퍼
  ↓  write() syscall — 커널 공간으로 복사
커널 페이지 캐시 (page cache / buffer cache)
  ↓  OS가 나중에 flush (주기적 또는 메모리 압박 시)
디스크 컨트롤러 write buffer
  ↓  디스크 펌웨어가 실제 플래터/NAND에 기록
비휘발성 매체

각 계층의 보장:

시스템 콜보장 범위전원 차단 시
write() 성공 반환커널 버퍼까지데이터 유실 가능
fsync(fd) 성공 반환파일 데이터 + 필요한 파일 메타데이터의 동기화 완료를 storage stack이 보고장치와 driver가 flush 계약을 지킬 때 내구성 확보
fdatasync(fd) 성공 반환데이터 + 이후 데이터 검색에 필요한 메타데이터불필요한 metadata update는 남을 수 있음
sync()전체 filesystem의 dirty state 동기화정확한 반환 의미는 OS/POSIX version 확인 필요
O_SYNC / O_DSYNC각 write에 file-integrity/data-integrity completion 적용같은 hardware flush 전제에 의존

fsync가 보장하는 것과 하지 않는 것:

  • 보장: OS·filesystem·driver가 파일 데이터와 요구되는 메타데이터의 동기화 완료를 기다림
  • 보장 안 함: 디렉터리 엔트리 갱신 — 새 파일의 경우 fsync(dir_fd)도 필요
  • 전제: driver가 cache flush 또는 FUA를 적절히 사용하고 장치가 완료를 정직하게 보고해야 함. volatile write-back cache, firmware 결함, 전원 보호 부재는 별도 위험

실제 OS (Linux)

Linux의 fsync 구현 경로:

vfs_fsync()
  → file->f_op->fsync()      /* 파일시스템별 구현 */
    → ext4_sync_file()
      1. journal commit (저널링 사용 시)
      2. filemap_write_and_wait_range()  — dirty page cache 기록
      3. blkdev_issue_flush()            — 디스크 cache flush 명령

Linux page cache와 dirty writeback:

  • write()는 page cache의 페이지를 dirty로 표시
  • pdflush/writeback 커널 스레드가 주기적으로 dirty 페이지를 디스크에 기록 (기본 30초)
  • fsync()는 해당 파일의 dirty 페이지를 즉시 기록하고 완료를 기다림

fdatasync vs fsync:

  • fdatasync()는 파일 크기가 변하지 않았다면 inode 메타데이터 기록을 생략
  • 로그 파일처럼 append만 하는 경우 fdatasync는 추가 seek 없이 데이터만 기록 → 더 빠름

PintOS 구현

PintOS에는 fsync() 시스템 콜이 없다. 저장소 모델이 훨씬 단순하다:

1. 쓰기 경로 — 버퍼 캐시 없이 직접 기록

PintOS의 기본 파일시스템(inode_write_at)은 disk_write()를 직접 호출한다. 중간에 page cache나 buffer cache가 없으므로 write() 반환 시점에 데이터가 이미 디스크 I/O를 완료한 상태다.

2. disk_write() — PIO(Programmed I/O) 동기 기록

sema_down(&c->completion_wait)가 핵심이다. IDE 컨트롤러가 데이터를 받았다는 인터럽트를 보낼 때까지 호출 스레드가 블록된다. 따라서 disk_write() 반환 시점에 데이터가 (QEMU 가상) 디스크에 전달된 것이 보장된다.

3. filesys_done() — 종료 시 최종 flush

init.c:420의 power_off() 직전에 호출된다. FAT 파일시스템 사용 시 fat_close()가 메모리 상의 FAT 테이블 전체를 disk_write()로 디스크에 기록한다.

4. PintOS에서 fsync가 불필요한 이유

PintOS의 기본 구현은:

  • buffer cache 없음 → 모든 write()가 즉시 disk_write() 호출
  • disk_write()가 동기적(IRQ 완료 대기) → 반환 시 디스크 도달 보장
  • 따라서 모든 write() = 사실상 O_SYNC 모드

buffer cache 프로젝트를 구현하면 상황이 달라진다:

  • dirty 블록이 메모리에 남아 있을 수 있음
  • filesys_done() 시점에 한꺼번에 flush
  • 이 경우 PintOS에도 fsync 개념이 의미를 갖게 됨

QEMU 에뮬레이션

QEMU에서 PintOS의 disk_write()가 호스트 파일에 도달하는 경로:

PintOS disk_write()
  → PIO OUT 명령
  → QEMU IDE 컨트롤러 에뮬레이션 (hw/ide/core.c)
    → BlockBackend write (block/block-backend.c)
      → 호스트 파일 pwrite() (filesys.dsk)

QEMU는 기본적으로 호스트 OS의 page cache를 사용하므로, 실제로는 호스트 fsync()가 호출되기 전까지 데이터가 호스트 디스크에 도달하지 않을 수 있다. 하지만 PintOS 테스트에서는 QEMU 종료 시 호스트가 flush하므로 문제가 되지 않는다.

fsync 보장 값 추적

fsync 비용 비교 (실제 하드웨어 기준):

HDD 7200 RPM:
  랜덤 write 1회: ~8 ms (seek + rotation)
  fsync (1 dirty page): ~8 ms (1회 seek)
  fsync (100 dirty pages, 연속): ~15 ms (순차 기록)

SSD (NVMe):
  랜덤 write 1회: ~20 μs
  fsync (1 dirty page): ~50 μs (FUA 오버헤드)
  fsync (100 dirty pages): ~200 μs

PintOS disk_write() (QEMU IDE 에뮬레이션):
  1 섹터(512 B) PIO 기록: ~수 μs (가상 장치, 호스트 메모리 속도)
  IRQ 완료 대기 포함: ~수십 μs (QEMU 스케줄링 의존)

PintOS 파일 쓰기 시 disk_write 호출 횟수:

4 KB 파일 쓰기 = 4096 / 512 = 8 섹터
각 섹터마다 disk_write() 1회 → 총 8회 PIO 전송
inode 갱신 1회 → +1회
총 disk I/O = 9회

fsync 보장 점검

  • write() 성공과 fsync() 성공은 서로 다른 약속이다. 전자는 커널이 데이터를 받았다는 뜻이고, 후자는 해당 파일의 dirty 데이터와 필요한 메타데이터를 디스크 쪽으로 밀어냈다는 뜻이다.
  • 새 파일을 안전하게 교체하려면 파일 내용만 fsync()해서는 부족할 수 있다. rename()으로 바뀐 디렉터리 엔트리까지 보장하려면 디렉터리 fd도 별도로 동기화해야 한다.
  • PintOS 기본 파일시스템에서는 disk_write()가 동기적으로 끝나므로 fsync() 시스템 콜이 없다. 하지만 buffer cache를 붙이면 dirty 블록이 RAM에 남을 수 있어 fsync() 같은 명시적 flush 계약이 다시 필요해진다.
  • QEMU 위의 PintOS에서 disk_write()가 끝났다는 말은 guest 관점의 완료다. 호스트 파일과 실제 저장장치까지의 내구성은 QEMU block backend와 호스트 OS 캐시 정책을 따로 봐야 한다.
