SPT 해시 테이블

SPT 해시 테이블

범위: 이 문서는 해시 테이블과 SPT의 일반 원리·자료구조 선택 기준을 설명하고, 입력에 제시된 PintOS 코드와 Linux·Windows 비교를 바탕으로 구현 구조를 해설한다. 구체적인 버전별 동작과 실행 관찰값, 해시 분포·조회 지연 등 성능 판단은 해당 코드 버전 확인과 GDB·QEMU 실행 및 별도 측정이 필요한 검증 범위다.

한 줄 요약: PintOS SPT는 체이닝 해시 테이블로 구현돼 faulting address를 pg_round_down 후 h(key) & (bucket_cnt-1)로 평균 O(1) 조회해 page type(ANON/FILE/UNINIT)·swap 상태·file offset을 즉시 얻으며 원소 수 > bucket×2면 rehash한다 — Linux의 VMA red-black tree(O(log N), 영역 단위)와 달리 개별 4 KB page 단위다.

SPT 해시 테이블 상태

Supplemental Page Table(SPT)은 프로세스의 모든 가상 페이지 메타데이터를 관리하는 자료구조다. PintOS에서 SPT는 체이닝 기반 해시 테이블로 구현된다. page fault가 발생하면 faulting address로 SPT를 O(1) 조회하여 해당 페이지의 타입(ANON/FILE/UNINIT), swap 상태, 파일 오프셋 등을 즉시 알아낸다. SPT 조회 성능이 page fault 처리 전체 지연 시간을 좌우하므로, 해시 테이블 선택은 성능상 핵심이다.

상세 설명

추상 개념 (자료구조 규칙)

해시 테이블은 key → bucket index 매핑으로 평균 O(1) 탐색을 제공한다. 충돌 해결 방식에 따라 chaining(연결 리스트)과 open addressing(선형/이차 탐색)으로 나뉜다. PintOS는 chaining을 사용한다.

핵심 구성 요소는 세 가지다:

  • 해시 함수 h(key): key를 정수로 변환
  • 버킷 인덱스: h(key) & (bucket_cnt - 1) (bucket_cnt가 2의 거듭제곱이므로 비트마스크 사용)
  • 충돌 해결: 같은 bucket에 들어간 원소들을 연결 리스트로 체이닝

Linux가 개별 page가 아닌 VMA 단위로 관리하는 이유: 프로세스가 수천 개의 4 KB page를 갖지만, 이들은 보통 수십 개의 연속 영역(code, data, heap, stack, mmap 등)에 속한다. 영역 단위로 관리하면 메타데이터 양이 크게 줄고, 범위 검색(이 주소가 어느 VMA에 속하는가?)이 트리 탐색 한 번으로 끝난다.

PintOS 구현

1. 해시 테이블 초기화

초기 bucket_cnt = 4. 원소가 늘면 자동 rehash로 bucket을 2배씩 확장한다.

2. 해시 함수: page_hash()

hash_bytes()는 FNV-1a (Fowler–Noll–Vo) 64-bit 해시를 사용한다:

VA가 8바이트이므로 FNV 루프가 8번 돈다. 결과를 & (bucket_cnt - 1)로 마스킹하여 bucket index를 얻는다.

3. 비교 함수: page_less()

같은 bucket 내에서 원소를 찾을 때 less()로 동등성을 판단한다: !less(a,b) && !less(b,a)이면 같은 원소다.

4. 조회: spt_find_page()

스택에 임시 struct page를 만들어 VA만 채우고, 이것의 hash_elem으로 hash_find()를 호출한다. hash_find()는 내부에서:

  1. find_bucket(): page_hash(&temp.hash_elem) → & (bucket_cnt - 1) → bucket 결정
  2. find_elem(): 해당 bucket의 리스트를 순회하며 page_less()로 비교

5. Rehash 정책

모든 원소를 새 bucket 배열로 재배치한다. 확장 시 bucket 수가 2배가 되므로 마스크 비트가 1개 늘어나고, 각 원소는 기존 bucket 또는 기존+offset bucket으로 이동한다.

QEMU 에뮬레이션

QEMU는 SPT를 인식하지 않는다. guest OS가 일반 메모리(malloc/hash table)에서 관리하는 자료구조일 뿐, QEMU는 해당 메모리 접근을 일반 load/store로 처리한다. GDB에서 guest 메모리를 읽어 hash table 상태를 관찰할 수 있다.

VA 해싱 예제:

VA = 0x0000000000401000 (코드 영역 두 번째 페이지)

  1. pg_round_down → 0x0000000000401000 (이미 정렬됨)
  2. hash_bytes(&va, 8): FNV-1a로 8바이트 해시 → 예: 0x7a3b... (64-bit)
  3. bucket_idx = hash & (bucket_cnt - 1): bucket_cnt=128이면 hash & 0x7F

rehash 비용:

page 64→65개 삽입 시 bucket 64→128 확장. 기존 64개 원소를 모두 재해싱하고 새 bucket에 배치. O(N) 비용이지만 amortized O(1).

SPT 전체 순회 (디버깅용)

(gdb) define dump_spt
  set $spt = &thread_current()->spt
  set $i = 0
  while $i < $spt.hash_table.bucket_cnt
    set $bucket = &$spt.hash_table.buckets[$i]
    set $e = $bucket->head.next
    while $e != &$bucket->tail
      set $he = (struct hash_elem*)((char*)$e - 0)
      set $pg = (struct page*)((char*)$he - 0)
      printf "  bucket[%d]: page va=%p type=%d\n", $i, $pg->va, $pg->operations->type
      set $e = $e->next
    end
    set $i = $i + 1
  end
end

관찰 시나리오

시나리오: 프로그램 로드 시 SPT 성장 추적

args-many 테스트 실행 중 SPT가 어떻게 성장하는지 추적한다:

  1. supplemental_page_table_init에 bp → bucket_cnt=4 확인
  2. hash_insert에 bp → load_segment loop에서 page 등록마다 호출
  3. rehash에 bp → bucket 확장 시점: elem 5→bucket 8, elem 9→bucket 16, …
  4. load 완료 후 spt.hash_table.elem_cnt → 총 page 수
  5. page fault 시 spt_find_page → 해시 조회 1회로 page 메타데이터 획득
