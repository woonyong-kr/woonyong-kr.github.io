PintOS 부트 시퀀스

PintOS 부트 시퀀스

한 줄 요약: QEMU가 SeaBIOS를 실행하면, BIOS가 디스크 첫 섹터(loader.S)를 0x7c00에 올리고, loader가 커널을 메모리에 적재한 뒤 start.S가 CPU를 64비트 long mode로 전환하고 main()을 호출한다.

PintOS 부트 시퀀스 문제

PintOS 코드를 읽으면 thread_init(), palloc_init(), intr_init() 같은 초기화 함수가 main()에서 순서대로 호출되는 걸 볼 수 있다. 그런데 main()은 누가 호출하는가? CPU는 처음에 16비트 리얼 모드로 시작하는데, 어떻게 64비트 C 코드가 실행되는가?

부트 시퀀스를 모르면 다음 질문에 답할 수 없다.

  • 커널은 물리 메모리 어디에 놓이는가? → LOADER_PHYS_BASE(0x200000)에 적재된다.
  • 커널 가상 주소 LOADER_KERN_BASE(0x8004000000)는 언제 매핑되는가? → start.S에서 부트 페이지 테이블을 만들 때.
  • main()이 호출될 때 인터럽트는 켜져 있는가? → 꺼져 있다. thread_start()에서 처음 켠다.
  • 페이지 테이블은 언제 교체되는가? → main() 안의 paging_init()에서 부트 테이블을 커널 테이블로 바꾼다.

PintOS 부트 시퀀스 흐름

부트 시퀀스는 세 파일이 순서대로 실행권을 넘기는 릴레이다.

%% PintOS 부트 실행권 이동
flowchart LR
  bios["BIOS<br/>SeaBIOS<br/>디스크 첫 섹터 확인"]
  loader["loader.S<br/>16비트 리얼 모드<br/>0x7c00에서 시작"]
  start["start.S<br/>보호 모드 → 롱 모드<br/>0x200000로 진입"]
  main["main()<br/>init.c<br/>커널 초기화 시작"]
  bios -->|디스크 1섹터를 0x7c00에 적재| loader
  loader -->|커널 첫 바이트를 0x200000에 적재| start
  start -->|64비트 스택 설정 후 호출| main

1단계: BIOS → loader.S (16비트 리얼 모드)

QEMU는 SeaBIOS 펌웨어를 내장하고 있다. 전원이 켜지면 BIOS가 디스크 첫 섹터(512바이트)를 물리 주소 0x7c00에 복사하고 그 주소로 점프한다. 이것이 loader.S의 start 레이블이다.

이 시점에서 CPU는 16비트 리얼 모드이고, 인터럽트는 cli로 꺼져 있다. loader.S가 하는 일은 세 가지다.

  1. A20 라인 활성화 — 키보드 컨트롤러(포트 0x64/0x60)를 통해 주소선 20번을 켠다. 이것이 꺼져 있으면 1MB 이상의 메모리에 접근할 수 없다.
  2. 메모리 맵 획득 — BIOS 인터럽트 INT 15h, E820h를 호출해 물리 메모리 영역 정보를 수집한다. 이 정보는 나중에 palloc_init()이 사용 가능한 메모리 풀을 잡을 때 쓰인다.
  3. 보호 모드 진입 + 커널 적재 — 최소한의 GDT(null, 코드, 데이터 세그먼트)를 로드하고, CR0의 PE 비트를 켜서 32비트 보호 모드로 전환한다. 그 뒤 IDE 컨트롤러를 직접 폴링하여 디스크에서 커널 이미지를 LOADER_PHYS_BASE(0x200000, 2MB)에 적재한다.

적재가 끝나면 call *%eax로 커널 첫 바이트, 즉 start.S의 _start로 점프한다.

2단계: start.S (32비트 보호 모드 → 64비트 롱 모드)

start.S의 bootstrap 함수는 CPU를 64비트 롱 모드로 전환하는 다리 역할을 한다. 순서는 다음과 같다.

  1. CPUID 확인 — CPU가 롱 모드를 지원하는지 검사한다. 지원하지 않으면 무한 루프에 빠진다.
  2. PAE 활성화 — CR4의 PAE 비트를 켠다. 롱 모드는 PAE(Physical Address Extension)가 필수다.
  3. 부트 페이지 테이블 설정 — 4단계 페이지 테이블(PML4 → PDPT → PDE)을 2MB 대형 페이지로 구성한다. 두 가지 매핑을 동시에 만든다.
    • 항등 매핑(identity map): 물리 0 ~ 256MB → 가상 0 ~ 256MB (전환 직후 코드가 같은 주소에서 계속 실행되기 위해)
    • 커널 매핑: 물리 0 ~ 256MB → 가상 LOADER_KERN_BASE(0x8004000000) ~ (전환 후 커널 가상 주소로 점프하기 위해)
  4. EFER MSR 설정 — IA32_EFER(MSR 0xC0000080)의 LME(Long Mode Enable)와 SCE(System Call Enable) 비트를 켠다.
  5. 페이징 활성화 — CR0의 PG 비트를 켠다. PAE + LME + PG가 모두 켜지면 CPU가 롱 모드에 진입한다.
  6. 64비트 GDT 로드 + 원거리 점프 — 64비트용 GDT를 로드하고, lret으로 entry_64 레이블로 점프한다.

entry_64에서는 부트 스택을 LOADER_KERN_BASE + 0x1000에 설정하고 main()을 호출한다.

왜 페이지 테이블을 두 번 만드는가?

start.S에서 만드는 부트 페이지 테이블은 2MB 대형 페이지로 물리 메모리 첫 256MB만 거칠게 매핑한다. main() 안의 paging_init()은 palloc_init()이 알려준 실제 메모리 크기에 맞춰 4KB 페이지 단위로 정밀한 커널 페이지 테이블을 새로 만들고, CR3를 교체한다. 부트 테이블은 “커널이 페이지 할당기를 초기화하기 전까지 버티는 임시 매핑”이다.

3단계: main() — 서브시스템 초기화 순서

main()의 초기화 호출 순서는 의존 관계에 따라 정해져 있다. 순서를 바꾸면 커널이 멈춘다.

%% main() 서브시스템 초기화 순서
flowchart TD
  early["초기 준비<br/>bss_init()<br/>read_command_line()<br/>parse_options()"]
  thread_console["스레드와 콘솔<br/>thread_init()<br/>console_init()"]
  memory["메모리와 페이징<br/>palloc_init()<br/>malloc_init()<br/>paging_init() → CR3 교체"]
  descriptor["USERPROG 디스크립터<br/>tss_init()<br/>gdt_init()"]
  interrupt_devices["인터럽트와 장치<br/>intr_init()<br/>timer_init()<br/>kbd_init()<br/>input_init()"]
  user_entry["예외와 시스템 콜<br/>exception_init()<br/>syscall_init()"]
  scheduler["스케줄러 시작<br/>thread_start()<br/>serial_init_queue()<br/>timer_calibrate()"]
  storage_vm["저장장치와 VM<br/>disk_init()<br/>filesys_init()<br/>vm_init()"]
  actions["부팅 완료<br/>&quot;Boot complete.&quot;<br/>run_actions()"]
  early --> thread_console
  thread_console --> memory
  memory --> descriptor
  descriptor --> interrupt_devices
  interrupt_devices --> user_entry
  user_entry --> scheduler
  scheduler --> storage_vm
  storage_vm --> actions

초기화 단계 사이에는 다음과 같은 의존 관계가 있다.

  • thread_init() → palloc_init() 순서: 스레드 시스템은 메모리 할당 없이 현재 실행 흐름만 등록한다. palloc은 그 뒤에 초기화한다.
  • palloc_init() → paging_init() 순서: 페이지 테이블을 만들려면 물리 페이지를 할당할 수 있어야 한다.
  • intr_init() → thread_start() 순서: IDT를 먼저 설정해야 인터럽트를 켜도 안전하다.
  • thread_start()가 인터럽트를 켜는 시점: 이전의 모든 초기화는 인터럽트가 꺼진 상태에서 실행된다.
  • thread_start() → serial_init_queue() 순서: 시리얼 포트를 폴링 방식에서 인터럽트 구동 방식으로 바꾸려면 인터럽트가 이미 켜져 있어야 한다. 그래서 스케줄러를 시작한 뒤에 호출된다.

PintOS 부트 시퀀스 코드

loader.S — 리얼 모드에서 보호 모드로

BIOS가 0x7c00으로 점프하면 이 코드부터 실행된다. 리얼 모드 16비트이므로 .code16 지시자를 쓴다. cli로 인터럽트를 끄는 이유는, 보호 모드로 전환하는 동안 IDT가 설정되어 있지 않기 때문이다.

CR0의 PE 비트를 켜면 보호 모드에 진입한다. 하지만 CS 레지스터에 리얼 모드 값이 캐시되어 있으므로, ljmp로 코드 세그먼트를 GDT의 커널 코드 셀렉터(0x08)로 다시 로드해야 한다. 그 뒤 IDE 컨트롤러를 직접 구동해 커널을 물리 주소 0x200000에 적재하고, 그 주소로 call한다.

start.S — 보호 모드에서 롱 모드로

RELOC(x) 매크로는 x - LOADER_KERN_BASE로, 아직 커널 가상 주소 매핑이 활성화되기 전이므로 물리 주소로 변환한다. PAE → CR3 설정 → LME → PG 순서가 정확해야 한다. PG를 켜는 순간 CPU가 롱 모드에 진입하며, 바로 뒤의 lret이 64비트 코드 세그먼트로 전환한다.

64비트 모드에 들어온 뒤 부트 스택을 커널 가상 주소 영역에 잡고 main()을 호출한다. 이 시점에서 물리 0 ~ 256MB가 항등 매핑과 커널 가상 매핑 양쪽으로 접근 가능하다.

QEMU 관점

QEMU는 SeaBIOS를 내장 펌웨어로 사용한다. PintOS를 -hda 옵션으로 디스크 이미지를 지정하면, SeaBIOS가 디스크 첫 섹터에서 부트 시그니처(0xAA55)를 확인하고 0x7c00에 적재한다. loader.S가 IDE 포트(0x1F0~0x1F7)에 직접 I/O하는 것은, QEMU의 IDE 컨트롤러 에뮬레이션이 이 포트의 읽기/쓰기를 가로채 가상 디스크 이미지에서 데이터를 돌려주기 때문에 동작한다.

실제 x86 하드웨어에서는 BIOS가 실제 플래시 ROM에서 실행되고, IDE 포트가 물리 디스크 컨트롤러와 연결된다. QEMU에서는 이 모든 것이 소프트웨어로 에뮬레이션되지만, PintOS 코드 입장에서는 차이가 없다.

실제 OS와의 차이

  • Linux: GRUB 같은 부트로더가 커널 이미지를 메모리에 올리고, 커널 자체가 start_kernel()에서 초기화를 시작한다. 부트로더가 멀티스테이지(stage1 → stage1.5 → stage2)이고, 커널은 압축 해제 과정을 거친다.
  • PintOS: 512바이트 단일 스테이지 부트로더(loader.S)가 커널을 직접 IDE 폴링으로 적재한다. 파일 시스템을 이해하지 못하고 디스크 섹터를 순서대로 읽는다. 압축 없음, 멀티스테이지 없음.

정리

PintOS 부트 시퀀스는 세 단계를 거친다. BIOS가 loader.S를 0x7c00에 올리고, loader.S가 리얼 → 보호 모드 전환 후 커널을 0x200000에 적재한다. 이어서 start.S가 보호 → 롱 모드 전환 후 main()을 호출한다. main()에서는 BSS 초기화 → 스레드 → 메모리 → 페이징 → 인터럽트 → 스케줄러 순서로 서브시스템을 켠다. 인터럽트는 thread_start()에서 처음 활성화된다.
