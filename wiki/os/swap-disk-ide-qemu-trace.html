Swap Slot 쓰기는 어떻게 PintOS IDE와 QEMU BlockBackend까지 내려가는가

Swap Slot 쓰기 시작

Swap Lab (anonymous page가 디스크 슬롯으로 나갔다 돌아오는 법)에서는 anonymous page 한 장이 swap slot으로 나간다고 했다. 여기서 한 단계 더 내려가면 다음 질문이 생긴다.

PintOS가 disk_write(swap_disk, 24, buffer)를 호출하면, QEMU host 파일의 어느 바이트가 실제로 바뀔까?

이 Trace에서는 swap을 “VM 정책”으로만 설명하지 않는다. PintOS ATA PIO 코드에서 QEMU IDE와 block backend 코드로 이어지는 경로까지 따라간다.

Swap Slot 쓰기 문제

swap을 처음 배울 때 흔히 두 가지를 혼동한다.

  • “swap slot”이 CPU page table 어딘가에 있는 값이라고 생각한다.
  • QEMU가 “이건 swap이구나”라고 알고 처리한다고 생각한다.

둘 다 아니다. swap slot은 PintOS가 정하는 운영체제 정책상의 번호다. QEMU는 그 의미를 모르며, guest가 ATA 디스크의 몇 번째 sector를 읽거나 쓰는지만 본다.

따라서 swap out은 두 층으로 나누어 읽어야 한다.

이 구분을 이해하면 anon_swap_out()을 구현할 때도 page metadata에는 slot을 저장하고 disk layer에는 sector 번호를 넘겨야 한다고 판단할 수 있다.

Swap Slot 쓰기 차이

한 장의 anonymous page가 host 파일의 byte range에 도달하기까지 값은 다음과 같이 변환된다.

flowchart LR
    A["anon page 4096B\nslot = 3"] --> B["sector 24..31\n(slot × 8)"]
    B --> C["disk_write() × 8\nATA PIO CMD 0x30"]
    C --> D["QEMU cmd_write_pio\nWIN_WRITE = 0x30"]
    D --> E["ide_sector_write()\nsector_num << 9"]
    E --> F["blk_aio_pwritev()\noffset = 0x3000"]
    F --> G["host swap.dsk\nbyte 12288..16383"]

각 층이 기억하는 정보도 다르다.

실제 운영체제

Linux와 Windows도 anonymous page를 RAM에서 내보낼 때 block storage나 pagefile 같은 backing store를 사용할 수 있다. 다만 실제 OS에서는 다음 요소가 PintOS보다 훨씬 복잡하다.

  • 어떤 page를 reclaim할지 고르는 정책
  • swap slot 또는 pagefile 공간 할당
  • block I/O scheduler, cache, writeback
  • 압축, 암호화, NUMA, cgroup 또는 working set 정책

그래도 다루는 질문은 같다.

RAM에서 빠진 anonymous page의 bytes를 나중에 같은 VA fault에서 복원할 수 있도록 어디에 저장할 것인가?

PintOS는 이 질문을 교육용으로 단순화해 anonymous page의 4096B를 swap disk의 연속 sector 8개에 저장한다.

QEMU

QEMU는 swap slot을 모른다. QEMU IDE 모델은 PintOS가 보낸 ATA command를 해석한다. 이 저장소의 QEMU 코드에서 이어지는 경로는 다음과 같다.

  • hw/ide/core.c
    • WIN_READ -> cmd_read_pio
    • WIN_WRITE -> cmd_write_pio
    • cmd_read_pio()는 s->req_nb_sectors = 1 뒤 ide_sector_read() 호출
    • cmd_write_pio()는 s->req_nb_sectors = 1 뒤 512B transfer를 시작
    • ide_sector_read()는 ide_buffered_readv()
    • ide_sector_write()는 blk_aio_pwritev()
  • block/block-backend.c
    • blk_aio_preadv()
    • blk_aio_pwritev()
  • hw/ide/ide-internal.h
    • WIN_READ = 0x20
    • WIN_WRITE = 0x30
  • include/block/block-common.h
    • BDRV_SECTOR_BITS
    • BDRV_SECTOR_SIZE

로컬 QEMU 코드에서 확인한 좌표는 다음과 같다.

질문QEMU 사용자 포크 링크의미
ATA write command 값은 어디에 있는가hw/ide/ide-internal.h#L85WIN_WRITE = 0x30
command table은 어디서 handler를 고르는가hw/ide/core.c#L2093WIN_READ는 cmd_read_pio, WIN_WRITE는 cmd_write_pio로 간다
PIO write는 몇 sector씩 시작하는가hw/ide/core.c#L1555cmd_write_pio()가 req_nb_sectors = 1로 잡고 512B transfer를 시작한다
write sector는 block backend offset을 어떻게 계산하는가hw/ide/core.c#L1076ide_sector_write()가 sector_num << BDRV_SECTOR_BITS를 blk_aio_pwritev()에 넘긴다
sector shift 값은 무엇인가include/block/block-common.h#L263BDRV_SECTOR_BITS = 9, 즉 512B sector다
block backend는 offset을 무엇으로 받는가block/block-backend.c#L1716blk_aio_pwritev()의 두 번째 인자가 byte offset이다

숫자 변환은 다음 코드에서 드러난다.

BDRV_SECTOR_BITS는 block layer의 sector shift다. 이 QEMU 소스에서는 BDRV_SECTOR_BITS = 9이고 1 << 9 = 512다. 따라서 sector_num << BDRV_SECTOR_BITS는 sector_num * 512와 같은 뜻이다.

PintOS가 sector 24를 쓰면 QEMU block backend는 host swap disk image의 byte offset 24 * 512 = 12288부터 512B를 쓴다.

slot / sector / offset 판단표

swap 구현을 디버깅할 때는 같은 위치를 층마다 다른 이름과 단위로 표현한다. 이 이름을 섞으면 버그가 발생한 층을 잘못 판단할 수 있다.

이름어느 층의 값인가단위예시틀리면 생기는 증상
slotPintOS VM 정책4096B page 한 장slot = 3page metadata가 같은 swap 위치를 공유하거나 free bitmap을 잘못 갱신한다
sectorPintOS disk driver와 QEMU IDE512Bsector = slot * 8 = 24swap-in 때 page 안 512B 조각 순서가 어긋난다
frame offsetPintOS frame 안 byte 위치byte0, 512, 1024같은 page 안에서 잘못된 512B 조각을 읽거나 쓴다
block backend offsetQEMU block layerbyte24 << 9 = 0x3000host disk image의 다른 byte range를 덮어쓴다

anon_swap_out() 구현에서 slot만 저장하고 sector를 저장하지 않는 것은 자연스럽다. sector는 언제든 slot * (PGSIZE / DISK_SECTOR_SIZE)로 다시 계산할 수 있기 때문이다. 반대로 QEMU GDB에서 보이는 값은 보통 slot이 아니라 sector_num 또는 byte offset이다.

정리

  • swap slot은 PintOS VM이 정한 metadata이고 QEMU는 그 의미를 모른다.
  • PintOS page 4096B는 disk sector 512B 8개로 나뉜다.
  • disk_write() 한 번은 ATA PIO로 sector 하나를 쓰는 흐름이다.
  • QEMU IDE 모델은 guest sector 번호를 sector_num << BDRV_SECTOR_BITS로 host disk image byte offset으로 바꾼다.
  • slot 3은 sector 24..31이고, swap disk image 안에서는 offset 0x3000..0x3fff에 해당한다.
  • 같은 “disk write”라도 PintOS VM은 slot을 기억하고, PintOS disk driver는 sector를 보며, QEMU block backend는 byte offset만 본다.
