IPC 공유 메모리

IPC 공유 메모리

확인 범위: 이 문서는 IPC 공유 메모리의 일반 원리와 구현 방식, 다른 IPC와의 선택 기준을 개념적으로 설명한다. 제시된 코드·Linux 및 PintOS 동작, 복사 횟수와 성능 수치는 특정 버전이나 환경의 실제 코드·실행 기록·측정 결과로 검증된 결론이 아니므로, 구현별 판단에는 별도 확인이 필요하다.

한 줄 요약: 분리된 가상 메모리를 가진 프로세스들이 같은 물리 페이지를 매핑해 직접 데이터를 공유하는 IPC.

IPC 공유 메모리 흐름

프로세스끼리는 가상 주소 공간이 분리되어 있다. A와 B가 모두 0x5000을 사용하더라도 기본 private mapping에서는 서로 다른 PTE를 가지지만, OS가 의도적으로 같은 shared object/frame을 같은 VA나 서로 다른 VA에 매핑할 수도 있다. 주소 숫자만으로 공유 여부를 판단할 수 없다.

Shared memory는 같은 물리 페이지를 두 프로세스의 페이지 테이블에 각각 매핑하는 방식이다. A가 자기 주소에 값을 쓰면, B가 자기 주소를 읽을 때 그 값이 바로 보인다. 커널 버퍼를 경유하지 않고 직접 메모리에 접근하기 때문에 IPC 중 가장 빠르다.

%% IPC shared memory mapping
flowchart TD
  proc_a["프로세스 A<br/>VA 0x7f000000<br/>ptr = mmap(...)"]
  proc_b["프로세스 B<br/>VA 0x7f500000<br/>ptr = mmap(...)"]
  pte_a["A의 page table<br/>PTE: VA 0x7f000000 -&gt; PFN 0x1A000"]
  pte_b["B의 page table<br/>PTE: VA 0x7f500000 -&gt; PFN 0x1A000"]
  frame["같은 물리 페이지<br/>PA 0x1A000<br/>공유 데이터 저장"]
  proc_a -->|"가상 주소 접근"| pte_a
  proc_b -->|"가상 주소 접근"| pte_b
  pte_a -->|"PFN 0x1A000"| frame
  pte_b -->|"PFN 0x1A000"| frame

다른 IPC와의 차이

pipe, socket, message queue 같은 IPC는 커널 버퍼를 경유한다. 데이터가 유저→커널, 커널→유저로 복사가 2번 발생한다.

%% Pipe와 shared memory 비교
flowchart TD
  pipe_a["App A"]
  kernel_buffer["커널 버퍼<br/>copy 1"]
  pipe_b["App B<br/>copy 2"]
  shm_a["App A<br/>*ptr = data"]
  shared_page["같은 물리 페이지<br/>copy 0"]
  shm_b["App B<br/>reads *ptr"]
  pipe_a -->|"write()"| kernel_buffer
  kernel_buffer -->|"read()"| pipe_b
  shm_a -->|"store"| shared_page
  shared_page -->|"load"| shm_b

속도가 빠른 대신 두 프로세스가 동시에 쓸 수 있기 때문에 동기화를 직접 해줘야 한다. 보통 세마포어나 뮤텍스를 같이 쓴다.

구현 메커니즘

shared memory의 실체는 결국 페이지 테이블 매핑이다.

POSIX shared memory (Linux)

shm_open()은 /dev/shm/ 아래에 tmpfs 파일을 만든다. mmap()으로 그 파일을 MAP_SHARED로 매핑하면 두 프로세스가 같은 물리 페이지를 공유한다. 디스크 I/O 없이 메모리에만 존재한다.

System V shared memory (전통 방식)

shmget()으로 공유 메모리 세그먼트를 만들고, shmat()으로 자기 주소 공간에 붙인다. 커널 내부적으로는 역시 같은 물리 페이지를 두 프로세스의 페이지 테이블에 매핑하는 것이다.

익명 shared memory

파일 없이 MAP_SHARED | MAP_ANONYMOUS로 매핑하면, fork() 후 부모-자식이 같은 물리 페이지를 공유한다. 파일 backing 없이 순수 메모리만 공유하는 가장 단순한 형태다.

mmap과의 관계

shared memory는 mmap의 특수한 사용 사례다.

mmap 용도flagsbacking
파일 읽기 전용 매핑MAP_PRIVATE파일
파일 공유 매핑MAP_SHARED파일 (write-back)
익명 private 매핑MAP_PRIVATE | MAP_ANONYMOUSswap
IPC shared memoryMAP_SHARED | MAP_ANONYMOUS메모리만

MAP_PRIVATE는 쓰기 시 copy-on-write로 복사본을 만들어서 원본에 영향을 주지 않는다. MAP_SHARED는 쓰기가 다른 프로세스에게도 보이고, 파일 backed면 파일에도 반영된다.

PintOS의 mmap은 MAP_SHARED/MAP_PRIVATE 구분 없이 단순화된 형태다(→ mmap file backed page는 어떻게 파일을 메모리처럼 보이게 하나).

동기화 문제

shared memory 자체는 동기화를 제공하지 않는다. 두 프로세스가 동시에 같은 주소에 쓰면 race condition이 발생한다.

일반적인 해결 방법은 공유 메모리 영역 안에 동기화 객체를 함께 배치하는 것이다.

또는 세마포어(sem_open)를 별도로 두는 방식도 있다.

IPC 공유 메모리 값 추적

IPC 방식별 데이터 전송 비용

1 MB 데이터를 프로세스 A → B로 전달할 때:

방식복사 횟수복사 총량대략적 시간
pipe2회 (유저→커널, 커널→유저)2 MB~200 μs
Unix socket2회2 MB~250 μs
shared memory0회 (매핑만)0 MB~10 μs (동기화 비용만)
message queue2회2 MB~300 μs

4 KB 페이지 기준 1 MB 범위는 256 page에 해당한다. 다만 mmap() 호출 시 256개 물리 page와 PTE가 즉시 모두 만들어진다고 단정하면 안 된다. 보통 VMA를 먼저 만들고 실제 frame 할당과 PTE 설치는 page fault 시점에 지연될 수 있다.

공유 메모리 영역의 페이지 테이블

%% 공유 메모리 영역의 페이지 테이블
flowchart LR
  proc_a["프로세스 A VA<br/>0x7f000000<br/>0x7f001000<br/>0x7f002000<br/>0x7f003000"]
  frames["같은 물리 프레임<br/>PA 0x1A000<br/>PA 0x1A001<br/>PA 0x1A002<br/>PA 0x1A003"]
  proc_b["프로세스 B VA<br/>0x7f500000<br/>0x7f501000<br/>0x7f502000<br/>0x7f503000"]
  proc_a -->|"PTE -&gt; PFN"| frames
  proc_b -->|"PTE -&gt; PFN"| frames

가상 주소는 다르지만 PTE가 같은 물리 프레임 번호(PFN)를 가리킨다. 따라서 A가 자기 VA에 쓰면 B가 자기 VA를 읽을 때 동일한 데이터를 본다.

POSIX shm 객체 크기

/dev/shm/ 은 보통 tmpfs (메모리 기반 파일 시스템)
최대 크기 = tmpfs mount의 size 옵션과 host/container 구성에 의존
일부 Linux 환경의 50% 기본값을 보편 계약으로 가정하지 않음

shm_open("my-shm", ...) → /dev/shm/my-shm 파일 생성
ftruncate(fd, 4096) → shared object의 논리 크기를 4 KB로 설정
mmap(...) → 각 프로세스에 VMA 생성
첫 접근 → 구현에 따라 물리 frame 할당과 PTE 설치가 지연될 수 있음

공유 메모리 설정과 통신 흐름

%% 공유 메모리 설정과 통신 흐름
flowchart TD
  a_open["프로세스 A<br/>shm_open(&quot;/my-shm&quot;, O_CREAT)"]
  a_size["프로세스 A<br/>ftruncate(fd, 4096)"]
  kernel_size["커널<br/>shared object 논리 크기 4KB"]
  a_mmap["프로세스 A<br/>mmap(fd, MAP_SHARED)<br/>VA 0x7f000000"]
  b_open["프로세스 B<br/>shm_open(&quot;/my-shm&quot;, O_RDWR)"]
  b_mmap["프로세스 B<br/>mmap(fd, MAP_SHARED)<br/>VA 0x7f500000"]
  fault["각 프로세스의 첫 접근<br/>page fault 가능"]
  shared["fault 처리 뒤 같은 backing page<br/>A/B PTE가 같은 PFN 참조"]
  transfer["커널 개입 없는 통신<br/>A: *ptr = 42<br/>B: val = *ptr"]
  a_open -->|"fd 반환"| a_size
  a_size -->|"크기 확정"| kernel_size
  kernel_size -->|"VMA 생성"| a_mmap
  a_mmap -->|"객체 이름 공유"| b_open
  b_open -->|"fd 반환"| b_mmap
  b_mmap -->|"VMA 생성"| fault
  a_mmap -->|"첫 store"| fault
  fault -->|"frame/PTE 준비"| shared
  shared -->|"load/store"| transfer

PintOS는 프로세스 간 공유 메모리를 지원하지 않는다. mmap()은 파일을 현재 프로세스에만 매핑하고, MAP_SHARED 플래그가 없다. fork 시에도 COW로 복사본이 생기므로 진정한 공유는 아니다.

장단점 정리

장점: 복사 없이 직접 접근하므로 대용량 데이터 공유에 가장 빠르다. 데이터베이스 공유 버퍼, 멀티미디어 처리, 고성능 서버의 워커 간 통신에 쓰인다.

단점: 동기화를 직접 구현해야 하고, 잘못하면 race condition이나 corruption이 발생한다. 네트워크를 넘어서는 통신에는 사용할 수 없다(같은 머신의 프로세스끼리만 가능).
