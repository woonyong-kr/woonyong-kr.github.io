유저 스택 / 커널 스택 분리

한 줄 요약: 각 스레드는 유저 스택과 커널 스택을 따로 갖는다. CPL 3→0 전환 과정에서 커널 스택으로 교체하면, 유저가 조작한 RSP로 커널 메모리를 망가뜨리는 일을 막을 수 있다.

유저 스택 / 커널 스택 분리 상태

x86-64에서 스레드는 유저 모드에서 사용하는 유저 스택과 커널 모드에서 사용하는 커널 스택을 따로 둔다. 두 스택을 분리하면 커널은 유저가 지정한 RSP를 그대로 사용하지 않고 별도의 커널 스택에서 실행할 수 있다. 따라서 유저 프로그램이 커널 스택의 데이터를 읽거나, 조작한 RSP를 통해 커널 메모리에 쓰는 위험을 차단할 수 있다.

CPL 3에서 CPL 0으로 전환할 때 어떤 방식으로 커널 스택을 불러오는지는 진입 경로에 따라 달라진다. 인터럽트가 발생하면 CPU가 TSS의 rsp0을 읽어 스택을 자동으로 교체한다. syscall 명령어는 TSS를 이용한 자동 스택 전환을 지원하지 않는다. 따라서 PintOS에서는 뒤에서 살펴볼 syscall_entry.S가 커널 스택을 직접 불러온다.

상세 설명

추상 개념 — 왜 스택을 분리하는가

위험단일 스택일 때분리 스택일 때
유저가 커널 데이터 읽기스택 frame 탐색으로 커널 주소 노출유저 스택에 커널 데이터 없음
유저가 RSP 조작커널 진입 시 조작된 RSP 사용 → 임의 메모리 쓰기CPU가 rsp0로 강제 교체
스택 오버플로우 전파유저 overflow가 커널 데이터 덮어씀각 스택이 독립 영역

하드웨어 메커니즘 — TSS rsp0

인터럽트로 권한 레벨이 CPL 3에서 CPL 0으로 바뀌면 x86-64 CPU는 TSS의 rsp0을 읽고, 그 주소를 새 RSP로 사용한다. 이후 커널 진입에 필요한 상태를 새 커널 스택에 저장한다.

이 인터럽트 전환 과정은 하드웨어가 수행하므로 유저 코드가 개입할 수 없다. 이 설명은 syscall 명령어의 진입 과정에는 그대로 적용되지 않는다.

실제 OS (Linux)

Linux에서는 struct thread_info와 커널 스택이 같은 페이지 블록에 위치한다 (전통적으로 8 KB 또는 16 KB). 최근 커널(4.9+)은 CONFIG_VMAP_STACK으로 가상 매핑된 커널 스택을 사용하여 overflow를 guard page로 잡아낸다.

유저 스택은 프로세스의 가상 주소 공간 상단 근처에 위치하며, RLIMIT_STACK (기본 8 MB)까지 성장한다.

PintOS 구현

PintOS에서 두 스택의 위치와 크기:

커널 스택:

각 스레드는 1 페이지(4 KB)를 할당받아 하단에 struct thread, 상단에 커널 스택을 배치한다:

크기 제약: struct thread + magic이 페이지 하단을 차지하므로 커널 스택은 약 3 KB 미만이다.

유저 스택:

유저 프로그램 로드 시 setup_stack()이 유저 가상 주소 공간 최상위에 1 페이지를 할당한다:

VM 활성화 시 stack growth로 추가 페이지를 할당할 수 있다 (최대 256 페이지 = 1 MB).

TSS rsp0 설정 (userprog/tss.c:76):

context switch 시 process_activate() → tss_update()를 호출하여, 다음 스레드의 커널 스택 최상위 주소를 TSS에 기록한다.

syscall 진입 시 스택 전환 흐름

중요: syscall 명령어는 int 0x80과 달리 TSS 자동 스택 전환을 하지 않는다. 따라서 syscall_entry.S에서 수동으로 TSS의 rsp0을 읽어 RSP를 교체한다. 반면 인터럽트(int N)는 CPU가 TSS.rsp0을 자동으로 사용한다.

인터럽트 진입 시 스택 전환

유저 모드에서 인터럽트가 발생하면:

커널 모드(CPL 0)에서 인터럽트가 발생하면 스택 전환 없이 현재 커널 스택을 계속 사용한다.

QEMU 에뮬레이션

QEMU(TCG 모드)는 하드웨어 TSS 자동 스택 전환을 소프트웨어로 재현한다:

  1. CPL 전환 감지: guest의 syscall 또는 int N 명령어를 번역할 때, TCG frontend가 do_interrupt_64() (target/i386/seg_helper.c)를 호출한다.
  2. rsp0 읽기: do_interrupt_64()가 CPUX86State에서 TR 레지스터 → TSS 세그먼트 → rsp0 오프셋(+4)을 읽어 guest RSP를 교체한다.
  3. syscall 특수 경로: syscall은 하드웨어에서도 TSS 자동 전환을 하지 않으므로, QEMU도 rsp0 교체 없이 guest RSP를 그대로 둔다. PintOS의 syscall_entry.S가 수동으로 TSS.rsp0을 읽는 과정까지 TCG가 충실히 번역한다.

GDB에서 확인하는 법:

(gdb) break syscall_entry
(gdb) x/gx $gs_base+4       # TSS.rsp0 (PintOS는 gs_base가 TSS 시작)
(gdb) info registers rsp     # syscall 진입 전 유저 RSP
(gdb) si 4                   # movq 4(%r12), %rsp 실행 후
(gdb) info registers rsp     # 커널 RSP로 교체됨을 확인

유저 스택 / 커널 스택 분리 값 추적

항목값
PintOS 커널 스택 크기~3 KB (4 KB 페이지 - struct thread - magic)
PintOS 유저 스택 초기 크기1 페이지 = 4 KB
PintOS USER_STACK0x47480000
PintOS 유저 스택 최대 크기256 페이지 = 1 MB (VM 활성화 시)
Linux 커널 스택 크기16 KB (CONFIG_THREAD_SIZE)
Linux 유저 스택 최대 크기8 MB (RLIMIT_STACK 기본값)
TSS rsp0 계산(uint64_t)thread + PGSIZE = thread page 상단
syscall 시 TSS 자동 전환안 함 (수동 로드 필요)
interrupt 시 TSS 자동 전환함 (CPL 3→0일 때)
