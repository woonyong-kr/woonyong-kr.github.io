RSP 스택 포인터 (RSP Stack Pointer)

RSP 스택 포인터 (RSP Stack Pointer)

확인 범위: 이 문서는 RSP의 일반적인 동작 원리와 선택·판단 기준을 설명하고 Linux, PintOS, QEMU 사례를 통해 적용 방식을 예시한다. 특정 코드 좌표와 크기·주소 계산, 실행 출력, 성능이나 동작에 관한 판단은 해당 구현의 실제 코드·버전·실행 기록과 측정 결과를 대조해야 하며, 본문만으로 검증된 결과로 간주하지 않는다.

한 줄 요약: 현재 스택 최상단 주소를 가리키는 x86-64 RSP — 함수 호출·인터럽트·컨텍스트 스위치의 핵심.

RSP 스택 포인터 상태

RSP는 x86-64의 스택 포인터 레지스터로, 현재 스택의 최상단(top) 주소를 가리킨다. 함수 호출, 인터럽트 처리, 컨텍스트 스위치에서 RSP는 항상 “지금 어디에 데이터를 쌓고 빼는가”를 결정하는 핵심 레지스터다. x86 스택은 높은 주소에서 낮은 주소로 자란다.

상세 설명

추상 개념 (CPU 하드웨어 규칙)

RSP의 하드웨어 수준 동작:

명령어RSP 변화설명
push raxRSP -= 8, [RSP] = RAX스택에 값 넣기
pop raxRAX = [RSP], RSP += 8스택에서 값 빼기
call funcRSP -= 8, [RSP] = 복귀주소함수 호출
retRIP = [RSP], RSP += 8함수 복귀
sub rsp, NRSP -= N지역 변수 공간 확보
add rsp, NRSP += N지역 변수 공간 해제

x86-64 ABI 정렬 규칙: call 명령 직전에 RSP는 반드시 16바이트 정렬이어야 한다. call이 8바이트 복귀주소를 push하므로, 함수 진입 시 RSP는 16N+8 형태가 된다.

인터럽트/예외 발생 시 RSP 전환:

  • 같은 특권 레벨 내 → RSP 변경 없이 현재 스택에 인터럽트 프레임 push
  • CPL 3→0 전환 → TSS.rsp0에서 커널 스택 주소를 읽어 RSP를 교체한 뒤 인터럽트 프레임 push
%% RSP 스택 프레임 배치
flowchart TD
  high["높은 주소 (예: 0x8004_7000)"]
  stack["스택 바닥 (초기 RSP)<br/>... 함수 인자 ...<br/>복귀 주소<br/>saved RBP<br/>지역 변수 a<br/>지역 변수 b ← RSP (스택 최상단)<br/>(빈 공간)"]
  low["낮은 주소"]
  growth["스택이 자랄 방향<br/>↓"]
  high --> stack
  stack --> low
  stack -.-> growth

실제 OS (Linux)

Linux에서 RSP가 관여하는 주요 장면:

  1. 유저 → 커널 전환: syscall 명령이 실행되면, CPU는 유저 RSP를 swapgs와 함께 저장하고 TSS.rsp0의 커널 스택으로 전환한다.
  2. 스레드 생성: clone() 시 자식 스레드의 pt_regs.sp를 새로 할당한 스택의 꼭대기로 설정한다.
  3. 시그널 전달: 유저 RSP를 시그널 프레임 크기만큼 내리고 시그널 핸들러 컨텍스트를 push한다.
  4. stack guard page: 유저 스택 바닥에 guard page를 두어 스택 오버플로 시 SIGSEGV를 발생시킨다.

커널 스택 크기: 보통 16 KB (4페이지, THREAD_SIZE).

PintOS 구현

PintOS에서 RSP를 사용하는 핵심 장면:

1. running_thread() — RSP로 현재 스레드 찾기

PintOS의 각 스레드는 정확히 1 페이지(4 KB)를 점유한다. 페이지 바닥에 struct thread가 놓이고, 페이지 꼭대기가 스택 시작점이다. RSP를 4 KB 경계로 내림(round down)하면 struct thread*가 된다.

%% PintOS 스레드 페이지에서 RSP 위치
flowchart TD
  start["페이지 시작 (0x8004_7000) ← pg_round_down(RSP) = struct thread*"]
  page["struct thread<br/>name"]
  n_end["페이지 끝 (0x8004_7FFF)"]
  start --> page
  page --> n_end

2. 스레드 초기화 — 스택 꼭대기로 RSP 설정

새 스레드의 RSP를 페이지 끝에서 8바이트 아래로 설정한다. 이 8바이트는 thread_launch()가 사용할 가짜 복귀 주소 슬롯이다.

초기 RSP 값 계산 예:

  • t = 0x8004_7000
  • PGSIZE = 4096 = 0x1000
  • sizeof(void*) = 8
  • RSP = 0x8004_7000 + 0x1000 - 8 = 0x8004_7FF8

3. do_iret — RSP를 인터럽트 프레임에서 복원

iretq가 스택에서 RIP, CS, RFLAGS, RSP, SS를 차례로 pop하여 유저 RSP로 돌아간다.

4. stack growth — RSP로 스택 접근 판별

page fault 시, fault 주소가 현재 RSP - 8 이상이면 스택 확장으로 판단한다. push 명령은 RSP를 8 감소시킨 뒤 쓰므로 RSP - 8까지가 정상 접근이다.

QEMU 에뮬레이션

QEMU의 CPUX86State 구조체에서 RSP는 regs[R_ESP]로 관리된다. GDB stub의 gdb_get_reg로 읽을 수 있다:

(gdb) info registers rsp
rsp  0x47480ff8

RSP 스택 포인터 값 추적

항목값
RSP 레지스터 크기64비트 (8바이트)
push/pop 단위8바이트 (x86-64)
PintOS 커널 스택 크기4 KB (1 페이지) - struct thread ≈ 3.8 KB 사용 가능
Linux 커널 스택 크기16 KB (4 페이지)
x86-64 ABI 정렬16바이트 (call 직전)
iretq가 pop하는 크기40바이트 (RIP 8 + CS 8 + RFLAGS 8 + RSP 8 + SS 8)

PintOS 스레드 스택 여유 계산:

  • 1페이지 = 4,096 B
  • struct thread ≈ 200 B (아래에서 위로)
  • 초기 RSP = 페이지 끝 - 8 = 4,088 B offset
  • 실제 사용 가능 = 4,088 - 200 = 약 3,888 B
  • 깊은 재귀 시 struct thread를 덮어쓸 위험 (stack overflow → ASSERT 실패)
