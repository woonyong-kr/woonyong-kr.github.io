저널링

저널링

범위: 이 문서는 저널링의 일반 원리와 모드별 선택 기준을 설명하고, ext4·PintOS·QEMU를 구체적 사례와 설명용 산술로 구분해 다룬다. 코드 경로, 기본값, 쓰기 순서, 크래시 결과와 성능·내구성 판단은 해당 구현의 버전·설정·실제 코드 및 실행 기록을 별도로 확인해야 하며, 본문의 GDB 절차와 수치는 그 자체로 특정 환경의 검증 결과를 뜻하지 않는다.

한 줄 요약: 실제 쓰기 전에 무엇을 쓸지를 저널에 먼저 기록(write-ahead log)해 크래시 일관성을 보장하는 저널링.

저널링 변화

저널링은 파일 시스템의 크래시 일관성(crash consistency)을 보장하는 기법이다. 디스크에 실제 데이터를 쓰기 전에 “무엇을 쓸 것인지”를 별도의 저널 영역에 먼저 기록(write-ahead log)함으로써, 시스템이 중간에 꺼져도 재부팅 시 저널을 재생(replay)하여 파일 시스템을 일관된 상태로 복구할 수 있다.

상세 설명

추상 개념 (디스크 하드웨어 규칙)

섹터(전통적으로 512B)는 디스크의 주소 지정·전송 단위이지, 모든 장치와 장애 조건에서 보장되는 원자적 쓰기 경계가 아니다. 전원 상실, 컨트롤러·장치 캐시, 저장 매체와 설정에 따라 한 섹터 안에서도 torn write가 생길 수 있다. 하나의 파일 시스템 연산(예: 파일 생성)이 여러 블록을 갱신하다 중단되면 일부만 반영된 불일관 상태도 생긴다. 저널링은 커밋 기록과 순서·영속성 장벽을 함께 사용해 복구 가능한 경계를 만든다:

  1. Journal Write: 변경할 모든 블록의 내용을 저널 영역에 기록한다
  2. Journal Commit: 커밋 블록을 저널에 쓴다 (이 쓰기가 원자적 경계)
  3. Checkpoint: 저널의 내용을 실제 위치에 반영(checkpoint)한 뒤 저널을 해제한다
%% 저널 트랜잭션 시간선
flowchart LR
  start["TxBegin<br/>(TxID)"]
  blocks["블록들<br/>(D, M, B)"]
  commit["TxEnd<br/>(commit)"]
  checkpoint["Checkpoint<br/>실제 위치에 반영"]
  release["저널 해제"]
  crash_before["크래시<br/>커밋 블록 없음<br/>무시"]

  commit -. 커밋 이후 실패 .-> crash_after

크래시 복구 시:

  • 커밋 블록이 없는 트랜잭션 → 버린다 (아무 일도 없었던 것처럼)
  • 커밋 블록이 있는 트랜잭션 → 재생한다 (redo)

실제 OS (Linux ext4)

ext4의 jbd2 (Journaling Block Device 2) 구현:

  • 저널 크기: 파일 시스템 크기와 mkfs 설정에 따라 달라진다. 아래 계산에서는 설명용으로 128 MiB를 사용한다.
  • 저널 위치: 파일 시스템 내 inode 8번 (journal inode)
  • 커밋 간격: 기본 5초 (commit=5)
  • 트랜잭션 크기: 저널의 1/4까지
%% ext4 저널 영역 구조
flowchart TD
  superblock["ext4 슈퍼블록"]
  journal_inode["journal inode<br/>(inode #8)"]
  descriptor["Descriptor Block<br/>포함된 블록 목록"]
  data_blocks["Data / Metadata Blocks<br/>실제 변경 내용"]
  commit["Commit Block<br/>트랜잭션 완료 표시"]
  revoke["Revoke Block<br/>재생 제외 표시"]

  journal_inode --> descriptor
  descriptor --> data_blocks
  data_blocks --> commit
  commit -. 필요할 때 기록 .-> revoke

기본 모드는 ordered: 데이터를 먼저 쓰고 메타데이터를 저널에 기록한다. 이렇게 하면 메타데이터가 가리키는 블록에 항상 올바른 데이터가 있음을 보장한다.

PintOS 구현

PintOS는 저널링을 구현하지 않는다. PintOS의 파일 시스템은 교육 목적의 단순한 구현이다:

  • filesys/inode.c의 inode_write_at()은 디스크에 직접 쓴다
  • 중간에 크래시가 나면 파일 시스템이 불일관 상태가 될 수 있다
  • free_map_release()도 비트맵을 즉시 갱신하므로, 할당-해제 중간 크래시 시 블록 누수 가능

이것이 실제 OS와 PintOS의 핵심적인 차이점 중 하나다. PintOS에서는 QEMU 위에서 실행되므로 실제 전원 차단이 없어 문제가 드러나지 않는다.

fsync와 저널의 관계

저널링 파일 시스템에서 fsync(fd)가 보장하려는 일반 흐름:

  1. 해당 파일의 dirty 페이지를 디스크에 쓴다
  2. 해당 파일의 메타데이터가 진행 중인 저널 트랜잭션에 속한다면 필요한 저널 기록과 commit을 완료한다
  3. 파일 시스템·mount·cache 설정이 요구하는 flush/barrier까지 완료한 뒤 리턴한다

정확한 경로는 파일 시스템, journaling mode, dirty metadata와 현재 트랜잭션 상태에 따라 달라진다. 따라서 fsync()를 언제나 새 commit block 하나를 쓰는 호출로 정의하면 안 된다. 반환 뒤의 내구성 범위도 장치가 flush/FUA 계약을 올바르게 지킨다는 전제를 포함한다.

저널링 값 추적

ext4 저널 크기 산술 예시 (1 TiB 파일 시스템):

항목값
파일 시스템 크기2,147,483,648 섹터 (512B) = 1 TiB
저널 크기128 MB = 262,144 섹터
저널 비율0.012207%
블록 크기4,096 B
저널 블록 수32,768 블록
최대 트랜잭션~8,192 블록 (저널의 1/4)
커밋 간격5초
Descriptor Block 크기1 블록 (4 KB)
Commit Block 크기1 블록 (4 KB)

단일 4KiB 데이터 블록만 놓고 단순화한 full journal 예시는 저널 데이터 1블록과 home-location 데이터 1블록을 쓴다. descriptor·commit 블록은 트랜잭션 단위로 여러 변경이 공유하므로, 이를 매 데이터 블록마다 더해 고정 4x로 일반화하면 안 된다. ordered 모드 역시 데이터는 home location에 한 번 쓰고 메타데이터만 journal+checkpoint하지만 실제 write amplification은 변경된 메타데이터 수와 batching에 좌우된다.

QEMU 에뮬레이션

PintOS는 저널링을 구현하지 않으므로, QEMU 관점에서는 “저널이 없는 디스크 I/O”가 어떻게 처리되는지가 핵심이다.

디스크 쓰기 경로와 원자성

PintOS의 disk_write()는 PIO(Programmed I/O) 모드로 한 번에 512바이트(1 섹터)를 쓴다. 이때 QEMU 내부 경로는:

flowchart TD
  pintos["PintOS disk_write()"]
  command["outb(0x1F7, CMD_WRITE_SECTOR_RETRY)<br/>ATA command 발행"]
  pio["output_sector()<br/>outsw(0x1F0, buf, 256)<br/>256 × 2B = 512B PIO 전송"]
  trap["QEMU PIO trap<br/>ide_ioport_write()"]
  ide["ide_sector_write()"]
  block["QEMU block layer I/O<br/>예: blk_pwrite() 계열 API"]
  host_syscall["호스트 backend API<br/>aio/io_uring/preadv·pwritev 등<br/>(설정에 따라 다름)"]
  image["호스트 디스크 이미지<br/>.dsk 파일에 기록"]
  no_journal["guest PintOS<br/>저널 없음"]

  pintos --> command
  command --> pio
  pio --> trap
  trap --> ide
  ide --> block
  block --> host_syscall
  host_syscall --> image
  pintos -.-> no_journal
  host_syscall -.-> host_journal

QEMU의 block layer는 이미지 형식, cache mode, 호스트 파일·블록 장치와 I/O backend 설정에 따라 서로 다른 경로로 쓰기를 전달한다. 호스트가 Linux ext4 파일 위의 이미지라면 jbd2가 호스트 파일 시스템의 메타데이터 일관성을 돕지만, 이것이 guest PintOS의 여러 섹터 갱신을 하나의 트랜잭션으로 만들거나 guest가 기대한 시점의 영속성을 대신 보장하지는 않는다. guest 파일 시스템의 크래시 일관성과 host 파일 시스템의 보호 범위는 별도 계약이다.

크래시 시뮬레이션이 어려운 이유

시나리오실제 하드웨어QEMU
전원 차단디스크 내부 캐시에 있는 미완료 쓰기 손실QEMU 프로세스 kill → 호스트 파일 캐시 유실 가능
섹터 부분 쓰기장치의 원자 쓰기 단위·캐시·전원 보호에 따라 torn write 가능이미지 형식·cache mode·host backend·저장 장치에 따라 달라지므로 불가하다고 가정할 수 없음
2개 섹터 연속 쓰기 중간 크래시첫 섹터만 기록됨QEMU kill 타이밍 따라 재현 가능하나 비결정적

QEMU 위에서 PintOS를 돌릴 때, 파일 시스템 불일관성을 의도적으로 재현하려면 QEMU를 특정 disk_write() 직후에 kill하는 스크립트가 필요하다. 단순 kill로는 호스트 파일 시스템 캐시 때문에 데이터가 살아남을 수 있다.

GDB에서 저널 부재 확인

(gdb) break disk_write
(gdb) commands
  silent
  printf "WRITE sector %d\n", sec_no
  continue
end
(gdb) continue

inode_create() 시 다음 순서로 disk_write가 호출됨을 확인할 수 있다:

  1. free_map_allocate() → 비트맵 섹터 쓰기
  2. disk_inode 메타데이터 쓰기 (sector 인자)
  3. 데이터 블록 초기화 쓰기 (zeros)

이 세 쓰기 사이에 저널 기록이 없으므로, 2번과 3번 사이에 크래시가 나면 inode는 할당된 블록을 가리키지만 그 블록은 초기화되지 않은 상태가 된다.

저널링 점검

  • 저널링은 “데이터를 두 번 쓰는 기능”이라기보다, 여러 블록 변경을 하나의 복구 가능한 트랜잭션으로 묶는 장치다.
  • 커밋 블록이 없으면 재부팅 때 버리고, 커밋 블록이 있으면 redo한다. 그래서 커밋 블록이 크래시 복구의 경계가 된다.
  • fsync(fd)는 dirty 데이터만 내려보내는 호출이 아니다. 저널링 파일 시스템에서는 관련 데이터·메타데이터와 필요한 journal commit·flush가 내구성 경계를 넘도록 기다리지만, 실제 단계는 파일 시스템과 트랜잭션 상태에 따라 달라진다.
  • PintOS에는 저널이 없으므로 inode_create(), free_map_allocate(), disk_write() 사이의 순서가 크래시 일관성으로 보호되지 않는다. QEMU 위에서는 guest PintOS 파일시스템과 host 파일시스템 저널링을 분리해서 봐야 한다.
