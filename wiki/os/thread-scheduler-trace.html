스레드 스케줄러 (Thread Scheduler) Trace

스레드 스케줄러 (Thread Scheduler) Trace

thread_create()로 만든 스레드는 곧바로 CPU를 받지 않는다. PintOS 스케줄러가 ready_list에서 다음 CPU 주인을 선택한 뒤, context switch가 실제 실행 흐름을 전환한다.

생성된 스레드는 언제 CPU를 받는가

thread_create()로 스레드를 만들면 바로 실행되는 것처럼 보일 수 있다. 하지만 스레드가 생성되어 존재하는 상태와 현재 CPU에서 실행되는 상태는 다르다. 생성된 스레드나 BLOCKED 상태에서 깨어난 스레드는 먼저 READY 상태가 되어 실행 차례를 기다린다.

이 설명은 아래에 제시된 상태 전이와 스케줄러 코드 흐름을 바탕으로 한다. 스케줄러는 스레드를 직접 실행시키기보다 다음 CPU 주인을 선택한다. PintOS는 ready_list에 실행 가능한 스레드를 모아 두고, 그중 하나를 고른 다음 context switch로 실제 실행 흐름을 바꾼다.

이 흐름으로 진입하는 대표적인 경로는 세 가지다. timer tick으로 TIME_SLICE가 끝날 수 있고, 새 스레드나 깨어난 스레드가 생겨 선점 여부를 판단할 수 있으며, 동기화 사건을 기다리는 현재 스레드가 BLOCKED 상태로 바뀔 수도 있다.

상태와 스케줄링의 관계

CPU는 한 번에 하나의 코드만 실행하지만 스레드는 여러 개 존재할 수 있다. 따라서 OS는 다음 실행 기회를 어느 스레드에 줄지 계속 결정해야 한다. PintOS에서는 스레드 상태가 바뀔 때 ready_list과 어떤 관계를 맺는지 따라가며 이 결정을 추적할 수 있다.

상태의미ready_list에 있나?
RUNNING지금 CPU에서 실행 중아니오
READY실행할 준비를 마치고 대기 중예
BLOCKED사건을 기다리는 중(lock, sleep, I/O 등)아니오

스케줄러는 READY 상태인 스레드 중에서 다음 실행 대상을 고른다. 현재 RUNNING 스레드가 CPU를 양보하면 READY로 바뀌고, 어떤 사건을 기다려야 하면 BLOCKED로 바뀐다. 선택된 스레드는 RUNNING이 된 뒤 context switch를 통해 CPU를 이어받는다.

이 구조를 이해하면 timer interrupt가 선점 기회를 만드는 이유, lock을 잡은 스레드가 오래 실행될 때 시스템이 느려질 수 있는 이유, semaphore와 condition variable이 스레드를 BLOCKED 상태로 보내는 이유를 하나의 흐름으로 설명할 수 있다. READY 스레드 중 무엇을 먼저 선택할지는 스케줄링 정책의 문제이며, priority donation도 이 정책과 연결된다.

우선순위가 선택 순서를 결정하는 과정

여기서는 PintOS가 우선순위 스케줄링을 사용하며, priority 값이 높은 스레드를 먼저 선택한다고 전제한다.

전체 과정은 READY 진입, 대기열 정렬, CPU 양보 여부 판단, 다음 스레드 선택 순서로 살펴보면 된다. ready_list가 priority 내림차순으로 유지된다면 T3 -> T2 -> T1 순으로 스레드를 꺼낸다. 따라서 먼저 스레드가 언제 ready_list에 들어가는지 확인하고, 이어서 현재 스레드가 언제 CPU를 양보하는지 살펴본다.

BLOCKED에서 READY로 돌아올 때

BLOCKED 스레드가 기다리던 사건이 끝나면 thread_unblock()이 호출된다.

  • SW_AI-W11-pintos/pintos/threads/thread.c

이 함수는 스레드를 ready_list에 넣고 상태를 READY로 바꾸지만, 함수 안에서 곧바로 선점하지는 않는다. 따라서 스레드가 깨어나도 즉시 CPU를 받는다고 단정할 수 없다. 실제 선점 여부는 check_preemption() 같은 별도 지점에서 판단한다.

RUNNING 스레드가 양보할 때

현재 스레드가 CPU를 양보하면 READY 상태로 돌아가 ready_list에 다시 들어간다.

  • SW_AI-W11-pintos/pintos/threads/thread.c

따라서 thread_yield()는 현재 스레드도 다시 실행 후보에 포함한 뒤 다음 후보를 선택해 달라는 요청으로 이해할 수 있다.

다음 스레드를 고를 때

next_thread_to_run()은 먼저 ready_list가 비어 있는지 확인한다. 비어 있으면 idle을 반환하고, 후보가 있으면 목록의 맨 앞 원소를 꺼낸다.

  • SW_AI-W11-pintos/pintos/threads/thread.c

목록이 우선순위 내림차순으로 정렬되어 있으므로 list_pop_front는 가장 높은 우선순위의 스레드를 선택한다. 앞의 예에서는 T2가 선택된다.

더 높은 우선순위가 READY가 될 때

다음으로, 새 READY 스레드 때문에 현재 RUNNING 스레드가 CPU를 양보하는 경로를 살펴본다. 이 코드베이스의 check_preemption()은 ready_list의 맨 앞 원소와 현재 스레드의 priority를 비교한다.

timer tick이 선점으로 이어지는 과정

더 높은 우선순위의 스레드가 등장할 때만 스케줄링이 일어나는 것은 아니다. tick마다 thread_tick()이 호출되며, 현재 스레드가 TIME_SLICE를 모두 사용하면 CPU 양보가 예약된다.

  • SW_AI-W11-pintos/pintos/threads/thread.c

TIME_SLICE = 4이고 같은 스레드가 계속 RUNNING이라면 카운터는 다음과 같이 변한다.

다만 timer interrupt 처리 도중에 곧바로 양보를 실행하지는 않는다. intr_yield_on_return()이 요청을 남기면 인터럽트 핸들러가 끝나는 안전한 지점에서 실제 thread_yield()가 호출되고, 그때 스케줄링이 진행된다.

이 문서에서 사용하는 1 tick = 10 ms라는 전제에 따르면 TIME_SLICE = 4는 40 ms마다 선점 기회를 만든다. schedule()이 새 스레드를 RUNNING으로 바꿀 때 카운터는 thread_ticks = 0으로 초기화되므로, 새 스레드도 4 tick의 TIME_SLICE를 받는다. context switch까지 이어지는 세부 흐름은 컨텍스트 스위치 (Context Switch) Trace에서 추적한다.

QEMU와 PintOS가 맡는 범위

QEMU 자체가 스케줄러인 것은 아니다. ready_list를 관리하고 priority 정책에 따라 다음 스레드를 선택하는 주체는 PintOS다.

  • PintOS (정책)
  • ready_list, priority, thread_yield,
  • check_preemption, do_schedule, schedule
  • QEMU (메커니즘)
  • 8254 PIT 에뮬레이션 → IRQ0 전달
  • guest CPU 명령 실행 (TCG)
  • switch_threads의 스택 교체는 guest 코드

QEMU는 timer interrupt를 guest에 주입하는 과정에 관여한다. 그러나 어떤 스레드를 ready_list에 넣고 어떤 priority 정책을 적용할지는 알지 못한다. 즉, tick과 interrupt라는 사건은 QEMU가 흉내 내지만, 그 사건에 대응하는 스케줄링 정책은 PintOS가 수행한다.

흐름을 직접 확인하는 지점

먼저 thread_unblock과 thread_yield에 breakpoint를 두면 어떤 스레드가 ready_list에 들어가는지 추적할 수 있다. 이때 p thread_current()->name, p thread_current()->priority로 현재 스레드의 이름과 priority를 확인한다.

다음으로 next_thread_to_run에 breakpoint를 두고 p list_empty(&ready_list)를 확인한다. 함수가 반환하기 직전에는 next 후보의 name/priority를 살펴보면 목록의 후보와 실제 선택 결과를 연결할 수 있다.

선점 경로는 check_preemption과 thread_tick을 나누어 관찰한다. 전자는 더 높은 우선순위의 READY 스레드가 생긴 경우이고, 후자는 TIME_SLICE가 만료된 경우다. 이는 관찰 지점을 제시한 절차일 뿐이며, 실제 실행 결과를 기록한 것은 아니다.
