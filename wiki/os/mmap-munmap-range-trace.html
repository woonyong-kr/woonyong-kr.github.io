mmap munmap 범위 흐름 (Mmap Munmap Range Trace)

mmap munmap 범위 흐름 (Mmap Munmap Range Trace)

한 줄 요약: munmap은 주소만 받으므로, do_mmap 시점에 남긴 범위 metadata로 어떤 page를 dirty write-back하고 정리할지 추적해야 한다 — 범위 정리는 전적으로 OS metadata의 일이다.

mmap munmap 범위 흐름

PintOS munmap()은 시작 주소만 넘기고 길이를 넘기지 않는다. do_munmap(addr)이 어떤 page들을 write-back하고 정리해야 하는지 알려면, do_mmap() 시점에 남긴 mapping 범위 metadata가 필요하다. 이 Trace는 range 찾기→dirty write-back→PTE/SPT/frame/file 정리의 전체 순서를 추적한다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

CPU/MMU는 “이 주소부터 몇 page가 하나의 mapping이다”라는 정보를 가지고 있지 않다. MMU가 아는 것은 PTE가 present인지, dirty인지, writable인지뿐이다.

하드웨어가 아는 것하드웨어가 모르는 것
PTE present/dirty/writable 비트연속된 page가 같은 mapping에 속하는지
PTE를 not-present로 바꾸면 다음 접근 시 pf어떤 page를 write-back해야 하는지
dirty bit는 CPU가 store할 때 자동 setwrite-back 대상 바이트 수 (read_bytes)

따라서 “범위 정리”는 전적으로 OS metadata의 일이다.

do_munmap() 정리 순서:

중요 원칙: “의미를 먼저 저장하고, 마지막에 번역을 지운다.” PTE를 먼저 지우면 dirty bit를 읽을 수 없다.

never-faulted page 처리:

아직 첫 fault가 나지 않은 page는 page->uninit.aux에 file reference를 들고 있다. 이 page는 dirty가 아니므로 write-back이 불필요하지만, uninit_destroy()가 aux->file을 file_close()하고 free(aux)해야 한다.

process exit 경로:

mmap-exit 테스트: child가 munmap() 없이 종료해도 dirty mapping이 파일에 남아야 한다. spt_kill이 file-backed page의 dirty write-back을 수행해야 하는 이유다.

mmap-close 테스트: fd를 닫은 뒤에도 mapping이 살아 있어야 한다. file_reopen()으로 독립 file reference를 만들지 않으면, fd close 시점에 파일이 닫혀 write-back이 실패한다.

QEMU 에뮬레이션

QEMU는 mapping 범위를 모른다. QEMU가 보는 것:

  1. PintOS가 PTE를 not-present로 바꾸면 → 다음 guest 접근 시 EXCP0E_PAGE 발생
  2. PintOS가 dirty page를 file_write_at()으로 되돌리면 → 파일 시스템이 IDE sector write를 냄
  3. QEMU IDE 모델이 ide_sector_write()→blk_aio_pwritev(sector_num << 9) 호출

“이 주소부터 몇 page를 munmap해야 한다”는 의미는 QEMU가 아니라 PintOS 커널 metadata가 만든다.
