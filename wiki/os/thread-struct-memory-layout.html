스레드 구조체 메모리 배치 (Thread Struct Memory Layout)

스레드 구조체 메모리 배치 (Thread Struct Memory Layout)

PintOS는 스레드마다 4 KB 페이지 하나를 할당하고, 페이지 바닥에는 struct thread, 꼭대기에는 아래쪽으로 자라는 커널 스택을 함께 배치한다.

스레드 구조체 메모리 배치 상태

PintOS에서 각 스레드는 전용 4 KB(= 1 page) 페이지 하나를 할당받는다. 이 페이지에는 struct thread와 커널 스택이 함께 존재한다. 구조체는 페이지 바닥(offset 0)에 놓이고, 커널 스택은 페이지 꼭대기(offset 4096)에서 아래쪽으로 자란다. 둘 사이의 magic 필드는 스택이 구조체 영역을 침범했는지 감지하는 센티넬 역할을 한다.

상세 설명

추상 개념 (메모리 배치 규칙)

스레드별 커널 스택을 독립된 페이지에 배치하면 현재 스레드를 빠르게 식별하고 스택 침범을 감지할 수 있다.

  1. RSP → 스레드 식별: RSP를 page-align하면 곧바로 struct thread*를 얻는다. 별도의 per-CPU 변수나 테이블을 조회하지 않고 O(1)로 현재 스레드를 찾을 수 있다.
  2. 오버플로우 감지: 구조체 끝에 magic 값을 둔다. 스택이 구조체 영역까지 자라 이 값을 훼손하면 assertion failure를 통해 오버플로우를 감지할 수 있다.

실제 OS와의 비교 (Linux/Windows)

먼저 PintOS의 한 페이지 공존 구조를 기준으로 살펴본 뒤, Linux와 Windows가 구조체와 커널 스택을 어떻게 분리하는지 비교한다. 아래 내용은 PintOS 코드의 직접 설명이 아니라 운영체제별 구현을 요약한 비교이며, 세부 크기와 배치는 버전 및 구성에 따라 달라질 수 있다.

Linux는 초기의 구조체·스택 결합 방식에서 점차 둘을 분리하는 방향으로 바뀌었다. 4.9+부터 THREAD_SIZE(보통 16 KB)의 커널 스택은 vmalloc() 영역에서 할당하고, task_struct는 slab allocator에서 별도로 할당한다. thread_info만 스택 바닥에 두거나, CONFIG_THREAD_INFO_IN_TASK로 task_struct 안에 넣는다. RSP를 기반으로 현재 프로세스를 찾던 방식도 per-CPU 변수 current_task를 사용하는 방식으로 대체되었다.

Windows의 비교 요약에서는 KTHREAD/ETHREAD 구조체를 pool memory에서 할당하고, 12~24 KB의 커널 스택은 별도로 할당하는 것으로 정리한다. 현재 스레드는 KPCR(Kernel Processor Control Region) per-CPU 구조체를 통해 추적한다. 이 설명은 Windows의 전체 버전과 구성을 일반화한 보장이 아니라, PintOS와 메모리 배치 방식을 비교하기 위한 구현 개요다.

PintOS 구현

이제 앞에서 설명한 배치 규칙이 PintOS 코드에서 어떻게 구현되는지 순서대로 살펴본다.

4 KB 페이지 내부 배치:

+--4096 (0x1000)-----------------------------+
|                                             |
|            Kernel Stack                     |
|           (grows downward ↓)                |
|                                             |
|  ← RSP는 이 영역 어딘가를 가리킨다         |
|                                             |
+---------------------------------------------+
|  magic (unsigned, 4 bytes) = 0xcd6abf4b     |  ← 센티넬
+---------------------------------------------+
|  tf (struct intr_frame, 176 bytes)          |
+---------------------------------------------+
|  spt, user_rsp, stack_bottom (VM 전용)      |
+---------------------------------------------+
|  pml4, fd_table, child_status_list, ...     |
|  (USERPROG 전용 필드)                       |
+---------------------------------------------+
|  elem, waiting_lock, donation_list, ...     |
+---------------------------------------------+
|  name[16], wake_tick, base_priority         |
+---------------------------------------------+
|  priority, status, tid                      |
+--offset 0----------------------------------+

thread_create() 할당:

palloc_get_page()가 반환하는 주소는 page-aligned 상태로 하위 12비트가 0이다. 따라서 이 주소가 곧 struct thread*가 된다.

running_thread() — RSP 기반 스레드 식별:

먼저 rrsp()로 현재 RSP를 읽고, pg_round_down()으로 하위 12비트를 0으로 마스킹한다. 그 결과 페이지 시작 주소인 struct thread*를 얻는다.

is_thread() — magic 검증:

thread_current()는 값을 반환하기 전에 이 매크로로 ASSERT를 수행한다. magic이 깨졌다면 커널 스택이 구조체 영역을 침범한 것으로 판단한다.

QEMU 에뮬레이션

QEMU는 struct thread의 의미를 직접 알지 못한다. QEMU에서 4 KB 스레드 페이지는 guest physical memory(RAMBlock)를 구성하는 페이지 하나일 뿐이다. QEMU와 PintOS가 맞닿는 지점은 다음 세 가지다.

  1. RSP 레지스터: CPUX86State.regs[R_ESP]에 guest RSP가 보관된다. PintOS가 thread_launch()로 RSP를 새 스레드 페이지의 tf 위치에 설정하면, QEMU는 해당 guest VA를 page table walk로 번역한다.
  2. CR3 전환: pml4_activate()가 CR3을 바꾸면 QEMU의 softmmu TLB가 flush된다. 스레드 페이지는 커널 영역에 있어 모든 주소 공간에서 같은 매핑을 사용하지만, TLB flush 비용은 발생한다.
  3. GDB stub: GDB에서는 p *(struct thread *)0x8004e000처럼 guest memory를 struct thread로 캐스팅해 확인할 수 있다. 이를 통해 스레드 상태를 디버깅한다.

struct thread 필드별 정확한 오프셋

실제 struct thread 선언 순서에 x86-64 alignment를 적용한 오프셋 계산은 다음과 같다.

  • Offset Size Field Type
  • 0x000 4 tid int (tid_t)
  • 0x004 4 status enum (int)
  • 0x008 4 priority int
  • 0x00C 4 base_priority int
  • 0x010 8 wake_tick int64_t
  • 0x018 16 name[16] char[]
  • 0x028 16 donation_list struct list (head+tail)
  • 0x038 16 donation_elem struct list_elem (prev+next)
  • 0x048 8 waiting_lock struct lock *
  • 0x050 16 elem struct list_elem
  • USERPROG 추가
  • 0x060 8 pml4 uint64_t *
  • 0x068 8 fd_table struct file **
  • 0x070 4 next_fd int
  • 0x074 4 (padding)
  • 0x078 16 child_status_list struct list
  • 0x088 8 self_status struct child_status *
  • 0x090 8 running_file struct file *
  • VM 추가
  • 0x098 ?? spt struct supplemental_page_table
  • 0x??? 8 user_rsp uintptr_t
  • 0x??? 8 stack_bottom void *
  • 공통
  • 0x??? 176 tf struct intr_frame (packed)
  • 0x??? 4 magic unsigned int
  • 4 (padding to alignment)

주의: spt의 크기는 해시 테이블 구현에 따라 달라진다. 따라서 정확한 오프셋은 p &((struct thread *)0)->magic으로 GDB에서 직접 확인해야 한다.

주소 예시: palloc이 0x8004e000을 반환했다고 가정하면 다음과 같이 추적할 수 있다.

  • struct thread* = 0x8004e000
  • magic 위치 ≈ 0x8004e16c (offset 0x16c ≈ 364)
  • 커널 스택 top = 0x8004f000 (offset 4096)
  • RSP가 0x8004ef80이면 → pg_round_down(0x8004ef80) = 0x8004e000 → 현재 스레드

커널 코드가 복잡해져 함수 호출 깊이와 지역 변수 사용량이 늘어나면 약 3.7 KB의 스택은 부족할 수 있다. 이 비교에서는 Linux가 스택을 16 KB로 늘리고 vmalloc 영역에 guard page를 둔 배경을 이러한 위험과 연결해 설명한다. 반면 PintOS는 교육용이며 함수 호출 깊이가 제한적이므로 4 KB 페이지를 사용한다.
