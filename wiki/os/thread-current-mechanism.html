thread_current() — RSP로 현재 스레드 찾기

thread_current()는 현재 RSP가 들어 있는 4 KB 커널 스택 페이지를 찾아, 그 페이지 바닥에 놓인 struct thread를 현재 스레드로 읽어 낸다.

현재 스레드를 어떻게 찾는가

스케줄링, 동기화, syscall 처리 같은 커널 코드는 지금 CPU에서 실행 중인 스레드의 정보에 자주 접근한다. 이를 위해서는 현재 스레드를 빠르게 식별할 방법이 필요하다.

가능한 방법은 다음과 같다.

방법장점단점
전역 변수 current_thread단순멀티코어에서 per-CPU 관리 필요, context switch마다 갱신 필요
전용 CPU 레지스터/MSR빠름아키텍처 종속, 레지스터가 부족할 수 있음
스택 포인터로 계산추가 저장 불필요스레드와 스택을 같은 메모리에 배치해야 함

PintOS는 스택 포인터로 현재 스레드를 계산한다. 각 스레드의 struct thread와 커널 스택을 하나의 4 KB 페이지에 함께 배치한다. struct thread는 페이지 시작에 있고 커널 스택은 페이지 끝에서 아래로 자란다. 따라서 현재 RSP가 가리키는 주소를 페이지 경계로 내리면 struct thread의 시작 주소를 얻을 수 있다.

이 방식에서는 별도의 현재 스레드 저장소를 읽는 대신, 스택 포인터(RSP)를 페이지 경계로 내림(round down)하면 곧바로 struct thread의 시작 주소가 나온다. 계산에 필요한 것은 현재 RSP와 페이지 크기뿐이므로 thread_current()는 O(1)로 동작한다.

PintOS 구현

하나의 4 KB 페이지에서 RSP와 struct thread의 관계는 다음과 같다.

%% thread_current()의 4 KB 페이지 레이아웃
flowchart TD
  page["페이지 시작: 4 KB 정렬<br/>pg_round_down(RSP) = struct thread *<br/>struct thread<br/>name"]
  rsp["RSP<br/>rrsp()로 읽는 현재 스택 포인터"]
  base["struct thread *<br/>RSP &amp; ~0xFFF"]
  rsp --> base
  base --> page

running_thread()는 이 배치 규칙을 주소 계산으로 옮긴 매크로다.

rrsp()는 인라인 어셈블리로 현재 RSP 값을 읽는다. pg_round_down()은 주소를 4 KB(PGSIZE) 경계로 내린다. 계산식은 addr & ~(PGSIZE - 1)이며, PGSIZE가 4096일 때 addr & ~0xFFF와 같다.

계산한 주소가 실제 스레드를 가리키는지는 thread_current()가 추가로 검사한다.

이 구현이 성립하려면 다음 조건이 모두 유지되어야 한다.

  1. palloc_get_page()가 4 KB 정렬된 주소를 반환한다.
  2. struct thread가 페이지의 시작 주소에 배치된다.
  3. 커널 스택이 같은 페이지의 끝에서 아래로 자란다.
  4. 실행 중인 스레드의 RSP가 그 페이지 내부를 가리킨다.

이 조건 아래에서는 RSP를 round down한 결과가 struct thread의 시작 주소와 일치한다. thread_current()는 이어서 magic과 스레드 상태를 검사한 뒤 해당 포인터를 반환한다.

magic으로 잘못된 포인터 감지하기

struct thread의 끝부분에는 unsigned magic 필드가 있다. 스레드를 만들 때 이 필드는 THREAD_MAGIC 값(0xcd6abf4b)으로 설정된다. 커널 스택이 아래쪽으로 넘쳐 struct thread 영역을 침범하면 이 값이 바뀔 수 있다.

is_thread()는 포인터가 NULL이 아닌지 확인하고 magic이 THREAD_MAGIC과 같은지 검사한다. 따라서 thread_current()의 첫 번째 ASSERT가 실패했다면 계산한 주소가 유효한 스레드를 가리키지 않거나 스택 오버플로우가 magic을 침범했을 가능성을 살펴볼 수 있다. 이 검사만으로 원인을 하나로 확정할 수 있는 것은 아니다.

두 번째 ASSERT는 계산된 스레드의 상태가 THREAD_RUNNING인지 확인한다. 전체 실행 흐름은 다음과 같다.

%% thread_current() 실행 흐름
flowchart LR
  rsp["RSP 읽기<br/>rrsp()"]
  round["pg_round_down<br/>RSP &amp; ~0xFFF"]
  cast["캐스팅<br/>(struct thread *)"]
  check["is_thread(t)<br/>magic == THREAD_MAGIC?"]
  status["상태 검사<br/>t-&gt;status == THREAD_RUNNING?"]
  ret["return t<br/>현재 스레드 반환"]
  panic_magic["ASSERT 실패<br/>스택 오버플로우 가능"]
  panic_status["ASSERT 실패<br/>RUNNING 상태 아님"]
  rsp --> round
  round --> cast
  cast --> check
  check --> status
  status --> ret
  check --> panic_magic
  status --> panic_status

부팅 직후의 최초 스레드

thread_init()이 실행되는 시점에는 일반적인 스레드 생성 절차로 만든 현재 스레드가 아직 없다. 이때도 running_thread()를 사용할 수 있도록 loader.S가 초기 스택의 바닥을 페이지 경계에 맞춰 둔다.

thread_init()은 현재 RSP에서 계산한 주소를 initial_thread로 삼고, 그 위치를 main 스레드로 초기화한다. 이후 상태를 THREAD_RUNNING으로 바꾸고 tid를 할당한다.

다른 OS의 현재 스레드 접근 방식

PintOS의 스택 기반 계산은 현재 스레드를 찾는 여러 설계 가운데 하나다. 이 문서에서 비교 대상으로 제시한 Linux와 Windows는 CPU별 영역을 통해 현재 스레드에 접근한다.

Linux:

  • x86-64에서 per-CPU 변수 current_task를 GS 세그먼트 base를 통해 접근한다.
  • current 매크로는 this_cpu_read_stable(pcpu_hot.current_task)로 구현되어 있다.
  • GS base는 wrmsrl(MSR_GS_BASE, ...) 또는 swapgs 명령어로 설정한다.
  • context switch 시 __switch_to()에서 current_task를 갱신한다.
  • 과거 Linux(2.6 이전)는 PintOS와 같은 스택 기반 방식(current_thread_info())을 사용했다.

Windows:

  • KPCR(Kernel Processor Control Region)의 CurrentThread 필드를 GS 세그먼트를 통해 접근한다.
  • KeGetCurrentThread()가 이 값을 반환한다.

이 비교는 각 방식의 구조를 설명하기 위한 것이다. 본문에는 해당 Linux와 Windows 설명을 직접 검증한 실행 결과나 외부 근거가 포함되어 있지 않으므로, PintOS 구현을 입증하는 근거로 사용하지 않는다.

QEMU에서 보이는 동작

QEMU 관점에서 thread_current()는 guest 커널이 실행하는 일반 코드다. rrsp()는 guest CPU의 RSP 레지스터를 읽고, pg_round_down()은 그 값에 비트 연산을 적용한다.

QEMU TCG 관점에서 이 동작은 다음과 같이 설명할 수 있다.

  • rrsp()의 인라인 어셈블리 mov %%rsp, %0는 guest RSP를 읽는 move에 해당한다.
  • pg_round_down()의 AND 연산은 TCG IR and_i64에 대응한다.
  • thread_current() 자체에는 MMIO나 특권 명령어가 없다.
  • KVM 모드에서도 guest 커널의 일반 코드로 실행되는 구조다.

이 설명은 명령의 구조에서 예상되는 동작이다. 본문에는 TCG IR, fast path, VM exit 여부를 실제로 측정하거나 추적한 결과가 포함되어 있지 않다.

GDB로 주소 관계 확인하기

현재 RSP를 페이지 경계로 내린 주소를 struct thread *로 해석하면 thread_current()와 같은 계산을 재현할 수 있다.

(gdb) p *(struct thread *)($rsp & ~0xfff)

이 명령은 함수를 호출하지 않고 현재 스레드로 계산되는 구조체의 필드를 관찰하는 용도다. 아래 명령들은 실제 검증 결과가 아니라, 각 관계를 GDB에서 확인하기 위한 관찰 절차다.

RSP와 struct thread 주소 비교

(gdb) # 현재 RSP와 round-down 결과 비교
(gdb) p/x $rsp
(gdb) p/x ($rsp & ~0xfff)
(gdb) p *(struct thread *)($rsp & ~0xfff)
(gdb) # thread_current()의 반환값과 일치하는지 확인
(gdb) p thread_current()

첫 세 명령은 현재 RSP, round-down한 주소, 그 주소에서 해석한 구조체를 차례로 보여 준다. 마지막 명령은 이 주소가 thread_current()의 반환값과 일치하는지 비교할 때 사용한다.

magic 필드 확인

(gdb) # magic이 THREAD_MAGIC(0xcd6abf4b)인지 확인
(gdb) set $t = (struct thread *)($rsp & ~0xfff)
(gdb) p/x $t->magic
(gdb) # 0xcd6abf4b가 아니면 스택 오버플로우 발생
(gdb) p $t->magic == 0xcd6abf4b

이 절차는 계산한 스레드의 magic이 THREAD_MAGIC과 같은지 확인한다. 값이 다르면 무결성 검사가 실패한 상태이며, 스택 오버플로우 가능성을 포함해 주소 계산과 메모리 상태를 함께 살펴봐야 한다.

스택의 남은 공간 관찰

(gdb) set $page_base = ($rsp & ~0xfff)
(gdb) set $page_top = $page_base + 4096
(gdb) # 스택은 page_top에서 아래로 자라므로, 남은 공간 = RSP - (page_base + sizeof(struct thread))
(gdb) p/d $rsp - $page_base
(gdb) # 이 값이 sizeof(struct thread)에 가까워지면 magic 침범 위험

스택은 페이지 위쪽에서 아래로 자라고 struct thread는 페이지 아래쪽에 있다. 따라서 RSP가 struct thread의 끝에 가까워질수록 두 영역 사이의 여유가 줄어든다.

context switch 전후 비교

(gdb) # thread_launch의 do_iret 직전에 breakpoint
(gdb) b thread_launch
(gdb) commands
  silent
  printf "=== before switch: tid=%d name=%s RSP=0x%lx ===\n", \
    ((struct thread *)($rsp & ~0xfff))->tid, \
    ((struct thread *)($rsp & ~0xfff))->name, $rsp
  continue
end
(gdb) # do_iret 후 RSP가 바뀌면 thread_current()도 바뀐다

breakpoint에서 RSP와 round-down한 주소의 스레드 정보를 함께 출력하면 context switch 전후의 변화를 비교할 수 있다. 새 스레드의 스택으로 RSP가 바뀌면 thread_current()가 계산하는 페이지도 바뀐다.

전체 스레드 목록과 현재 스레드 비교

(gdb) # all_list의 모든 스레드 출력
(gdb) set $e = all_list.head.next
(gdb) while ($e != &all_list.tail)
  set $t = (struct thread *)((char *)$e - offsetof(struct thread, allelem))
  printf "tid=%d name=%-16s status=%d priority=%d magic=0x%x\n", \
    $t->tid, $t->name, $t->status, $t->priority, $t->magic
  set $e = $e->next
end

이 스크립트는 all_list를 순회하며 각 스레드의 tid, 이름, 상태, 우선순위, magic을 출력한다. 현재 RSP에서 구한 스레드를 목록의 THREAD_RUNNING 상태와 비교할 때 사용할 수 있다.

다른 스레드의 저장된 RSP 확인

(gdb) # blocked 스레드의 context에 저장된 rsp로 해당 thread 확인
(gdb) set $target_tid = 3
(gdb) # target의 thread 구조체를 all_list에서 찾은 뒤
(gdb) # 해당 thread의 tf.rsp를 round-down하면 자기 자신이 나와야 한다
(gdb) p/x $target_thread->tf.rsp
(gdb) p ($target_thread->tf.rsp & ~0xfff) == (uint64_t)$target_thread

대상 스레드의 저장된 tf.rsp가 그 스레드의 4 KB 페이지 안을 가리킨다면, round-down한 주소는 해당 struct thread의 주소와 같아야 한다. 이 명령은 그 관계를 비교한다.

주소 계산 따라가기

PGSIZE = 4096 = 0x1000
PGMASK = PGSIZE - 1 = 0xFFF

pg_round_down(addr) = addr & ~0xFFF

예시:
  RSP = 0x8004_2E50 (스택 중간 어딘가)
  pg_round_down(0x8004_2E50) = 0x8004_2E50 & 0xFFFF_FFFF_FFFF_F000
                              = 0x8004_2000  ← struct thread 시작

struct thread 크기: 약 200+ bytes (멤버에 따라 다름)
magic 필드 offset: struct thread 끝 부근 (~1800 bytes 범위 내)
사용 가능한 스택 공간: 4096 - sizeof(struct thread) ≈ 3800+ bytes

THREAD_MAGIC = 0xcd6abf4b

스택 오버플로우 위험 기준:
  지역 변수 > ~3 KB면 magic을 덮어쓸 수 있다
  재귀 호출 깊이가 깊어도 마찬가지

예시의 RSP에서 하위 12비트를 지우면 0x8004_2000이 된다. 4 KB 페이지 안의 주소가 같은 페이지 시작 주소로 모이는 이유다.

뒤이어 적힌 struct thread 크기, magic 위치, 사용 가능한 스택 공간, 지역 변수 크기는 대략적인 값이다. 실제 값은 struct thread의 멤버와 빌드 결과에 따라 달라질 수 있으므로 고정된 경계로 간주하지 않는다. 스택 사용량을 판단할 때는 해당 빌드의 sizeof(struct thread)와 실제 RSP를 확인해야 한다.
