Priority Inversion

Priority Inversion

확인 범위: 이 문서는 Priority Inversion과 priority donation의 일반 원리 및 적용 기준을 설명하고, PintOS·Linux·QEMU 관련 코드 좌표, 구현 값, 복잡도와 동작 특성은 특정 구현에 관한 서술로 구분한다. 후자의 정확성과 실제 재현 여부는 해당 코드·버전 및 GDB·실행 기록이나 성능 측정을 별도로 확인해야 하며, 본문만으로 검증 결과를 의미하지 않는다.

우선순위 스케줄러에서도 높은 우선순위 스레드가 항상 먼저 끝나는 것은 아니다. 낮은 우선순위 스레드가 lock을 들고 있고, 그 사이에 중간 우선순위 스레드가 CPU를 가져가면 높은 우선순위 스레드는 간접적으로 밀릴 수 있다.

Priority Inversion은 왜 발생하는가

우선순위 기반 스케줄러는 높은 우선순위 스레드를 먼저 실행한다. 그러나 높은 우선순위 스레드 H가 낮은 우선순위 스레드 L이 보유한 lock을 요청하면, H는 lock을 얻을 때까지 BLOCKED 상태가 된다. L이 lock을 풀어야 H가 다시 실행될 수 있다.

이때 중간 우선순위 스레드 M이 L을 선점하면 문제가 생긴다. M은 H보다 우선순위가 낮지만, H는 L이 lock을 해제할 때까지 기다려야 하므로 결과적으로 M보다 늦게 실행된다. lock 의존성이 스케줄러의 우선순위 순서를 뒤집는 이 상황을 Priority Inversion(우선순위 역전)이라고 한다.

실시간 시스템에서는 이 지연이 데드라인 위반으로 이어질 수 있다. 이를 막으려면 lock holder인 L이 H의 우선순위를 일시적으로 이어받아 M의 선점을 피해야 한다. 이 메커니즘이 priority donation이다.

세 스레드로 보는 역전 과정

H, M, L의 우선순위가 각각 31, 20, 10이고 L이 lock A를 보유한 상황을 보자.

Priority donation이 없을 때

%% donation 없는 priority inversion 타이밍
flowchart LR
  t0["t0<br/>L(10)<br/>lock A 획득<br/>임계 영역 실행"]
  t1["t1<br/>H(31)<br/>lock_acquire(A)<br/>L이 holder라 BLOCKED"]
  t2["t2<br/>M(20) READY<br/>M.pri &gt; L.pri<br/>L을 선점"]
  t3["t3<br/>M 실행 완료<br/>L 재개<br/>lock_release(A)"]
  hrun["H(31)<br/>lock A 획득<br/>M보다 늦게 실행"]
  wait["H 대기 연장<br/>L이 CPU를 못 받아<br/>lock A 해제가 지연됨"]
  problem["역전<br/>H(31) &gt; M(20)이지만<br/>M이 먼저 실행됨"]
  t0 -->|H 도착| t1
  t1 -->|H BLOCKED| t2
  t2 -->|M이 L 선점| wait
  wait --> problem
  problem -->|M 종료 후| t3
  t3 -->|L release -&gt; sema_up| hrun
단계상태결과
t0L이 lock A를 획득하고 임계 영역을 실행한다.정상적으로 실행된다.
t1H가 lock A를 요청하지만 L이 보유하고 있어 BLOCKED 상태가 된다.L이 빨리 끝나야 H도 곧 실행될 수 있다.
t2M이 도착하고 M.pri > L.pri이므로 L을 선점한다.L의 lock 해제가 늦어지고 H의 대기도 길어진다.
t3M이 끝난 뒤 L이 재개되어 lock A를 해제한다.H는 M의 실행 시간만큼 더 기다린 뒤 실행된다.

따라서 H(31)가 M(20)보다 우선순위가 높은데도 M이 먼저 실행된다. M과 같은 중간 우선순위 스레드가 여러 개라면 H의 대기 시간이 무한히 늘어날 수 있는데, 이를 Unbounded priority inversion이라고 한다.

1997년 7월 Mars Pathfinder에서는 VxWorks RTOS의 저우선순위 버스 관리 태스크가 Lock을 잡은 상태에서 중간 우선순위 통신 태스크에 선점됐다. 그 결과 고우선순위 watchdog이 시스템을 반복해서 리셋하는 장애가 발생했다.

Priority Donation으로 holder를 먼저 실행하기

H가 기다리기 시작하면 lock holder인 L에게 자신의 우선순위를 “기부”한다. L의 effective priority가 10에서 31로 올라가면 M(20)은 L을 선점하지 못한다.

%% priority donation 적용 후 타이밍
flowchart LR
  t0["t0<br/>L(10)<br/>lock A 획득<br/>임계 영역 실행"]
  t1["t1<br/>H(31)<br/>lock_acquire(A)<br/>BLOCKED"]
  donate["donate 31 to L<br/>L.effective = 31"]
  t2["t2<br/>M(20) READY<br/>L(31)보다 낮아<br/>선점 실패"]
  hrun["H(31)<br/>sema_up 후 READY<br/>즉시 실행"]
  mrun["M(20)<br/>H 뒤에 실행"]
  release["L(31)<br/>lock_release(A)"]
  t0 -->|H 도착| t1
  t1 -->|holder=L| donate
  donate -->|effective priority 상승| t2
  t2 -->|Scheduler가 L 유지| release
  release -->|lock A 해제| hrun
  hrun -->|H 작업 완료 후| mrun

L은 높아진 effective priority로 임계 영역을 마치고 lock A를 release한다. 이후 sema_up으로 H가 READY 상태가 되면 H가 바로 실행되고, M은 H의 작업이 끝난 뒤 실행된다.

Nested Donation이 필요한 경우

lock 대기가 연쇄적으로 이어질 수도 있다. H가 M이 보유한 Lock B를 기다리고, M도 L이 보유한 Lock A를 기다린다면 H의 donation은 M에서 멈추면 안 된다. L이 실행되어 Lock A를 풀어야 M과 H의 대기가 차례로 끝나기 때문이다.

%% nested donation chain
flowchart LR
  h["H(31)<br/>waiting_lock = B"]
  lock_b["Lock B<br/>holder = M"]
  lock_a["Lock A<br/>holder = L"]
  limit["PintOS 제한<br/>최대 전파 깊이 8단계"]
  m["m"]
  l["l"]
  h -->|waits| lock_b
  lock_b -->|held by| m
  m -->|waits| lock_a
  lock_a -->|held by| l
  h -. donate 31 .-> m
  m -. propagate 31 .-> l
  l -->|chain traversal| limit

이 경우 H의 우선순위 31이 M을 거쳐 L까지 전파되어야 한다. PintOS에서는 waiting_lock → holder 체인을 따라가며 donation을 전파하고, 최대 깊이를 8단계로 제한한다.

Linux의 Priority Inheritance와 Priority Ceiling

Linux는 PI와 PP라는 두 프로토콜을 제공한다.

프로토콜메커니즘용도
PI (Priority Inheritance)rt_mutex — CONFIG_RT_MUTEXESPREEMPT_RT 패치, 실시간 태스크
PP (Priority Ceiling)PTHREAD_PRIO_PROTECTPOSIX — Lock에 정적 ceiling 설정

rt_mutex는 task_struct.pi_waiters (Red-Black Tree)를 사용하여 O(log n) donation/restore를 구현한다. chain propagation depth는 기본 1024로 제한된다.

PintOS의 Priority Donation 구현

PintOS에서는 struct thread에 effective priority와 원래 우선순위, donation 관계, 대기 중인 lock을 나타내는 필드를 둔다.

lock_acquire에서 donation하기

lock_acquire의 threads/synch.c:210에서는 lock holder가 있을 때 현재 스레드를 holder의 donation_list에 넣고 waiting_lock을 기록한다. 현재 스레드의 우선순위가 holder보다 높으면 holder의 우선순위를 올린다. 이어서 waiting_lock 체인을 최대 8단계까지 따라가며 중첩 donation을 전파한다.

lock_release에서 donation 철회하기

lock_release의 threads/synch.c:284에서는 해제할 lock을 기다리던 스레드를 donation_list에서 제거한다. 그런 다음 refresh_priority(t)가 base_priority와 남은 donation 가운데 가장 높은 값을 비교해 effective priority를 다시 계산한다.

세마포어에 donation을 바로 적용할 수 없는 이유

세마포어에는 holder 개념이 없다. down한 스레드와 up하는 스레드가 다를 수 있으므로, 대기 중인 고우선순위 스레드가 누구에게 우선순위를 기부해야 하는지 결정할 수 없다. 반면 Lock은 holder를 추적하므로 donation의 대상을 정할 수 있다.

QEMU에서 보이는 Priority Inversion

QEMU는 priority inversion 자체를 인식하지 못한다. QEMU가 보는 것은 guest CPU의 명령어 흐름이다. donation으로 thread->priority가 바뀌어도 QEMU에는 guest 메모리의 정수 값을 변경하는 일반 store 연산으로 보인다.

다만 QEMU의 단일 vCPU 특성은 PintOS에서 priority inversion이 발생하고 재현되는 조건에 영향을 준다.

항목멀티코어 실제 하드웨어QEMU 단일 vCPU (PintOS)
M이 L을 선점하는 시점M이 다른 코어에서 이미 실행 중일 수 있음반드시 타이머 인터럽트에서 발생
선점 빈도코어별 독립TIME_SLICE(4 tick) 단위
inversion 지속 시간M의 실행 시간 전체M의 time slice 소진까지
디버깅 재현성타이밍 의존, 비결정적타이머 기반, 상대적으로 결정적

PintOS의 priority inversion은 단일 CPU에서 time-slicing으로 발생한다. 따라서 멀티코어 환경의 복잡한 경쟁 조건은 없으며 디버깅도 비교적 쉽다.

전체 처리 순서는 L의 lock 획득에서 시작한다. H가 같은 lock을 요청하면 donation이 발생하고, 높아진 우선순위의 L이 M보다 먼저 lock을 해제한다. refresh_priority()로 L의 우선순위를 복원한 뒤 sema_up()이 H를 깨우면 H가 lock을 획득해 실행한다.

donation이 없을 때 priority inversion 감지

(gdb) define check_inversion
  set $h = (struct thread *)$arg0
  set $l = ((struct lock *)$h->waiting_lock)->holder
  if $l->priority < $h->priority
    printf "⚠ INVERSION: %s(pri=%d) blocked by %s(effective=%d, base=%d)\n", \
      $h->name, $h->priority, $l->name, $l->priority, $l->base_priority
  end
end
