CPU 메모리 접근에서 Page Fault 복구까지의 Trace

한 줄 요약: CPU가 가상 주소에 접근할 때 매핑이 없으면 pf(인터럽트 14번)가 발생한다. 운영체제는 rcr2()에서 fault 주소를, error_code에서 fault 성격을 읽고, vm_try_handle_fault() → vm_do_claim_page() 경로를 거쳐 프레임을 연결한다. 이 과정을 Linux·PintOS·QEMU의 역할을 구분해 단계별로 추적한다.

Page Fault 복구 키워드

나중에 필요한 내용을 다시 찾을 때는 다음 기준과 용어를 사용한다.

  • CPU memory access
    • 기준 구분
      • Linux / Windows VM subsystem
      • PintOS pml4 / page_fault() / vm_try_handle_fault()
      • QEMU guest MMU emulation
    • 주소 변환 기준
      • thread_current()->pml4
      • pml4_activate()
      • lcr3(vtop(pml4))
    • x86-64 page walk
      • PML4(va)
      • PDPE(va)
      • PDX(va)
      • PTX(va)
      • pg_ofs(va)
    • fault 처리
      • rcr2()
      • f->error_code
      • vm_try_handle_fault()
      • vm_do_claim_page()

먼저 이해할 질문

왜 어떤 주소에 접근하면 프로그램이 곧바로 종료되는 반면, 어떤 주소에 접근하면 운영체제가 페이지를 준비한 뒤 아무 일도 없었던 것처럼 실행이 계속될까?

이 질문을 이해하려면 먼저 page fault가 항상 치명적인 오류는 아니라는 점을 알아야 한다. Page fault는 CPU가 운영체제에 다음 판단을 요청하는 예외에 가깝다.

“방금 이 가상 주소를 읽거나 쓰거나 실행하려 했지만 현재 상태로는 변환할 수 없다. 이 접근을 복구할 것인가, 아니면 프로세스를 종료할 것인가?”

Page Fault 복구가 헷갈리는 이유

운영체제가 메모리를 관리할 때 달성하려는 목적은 크게 두 가지다.

  1. 보호(protection): 프로세스가 다른 프로세스의 메모리처럼 허용되지 않은 영역에 접근하지 못하게 막는다.
  2. 지연 로딩(demand paging): 실제로 필요해진 페이지만 메모리에 올려 RAM 사용을 줄인다.

CPU만으로는 현재 접근이 복구 가능한 상황인지, 잘못된 접근인지 판단할 수 없다. 따라서 CPU는 문제를 예외(exception)로 보고하고, 운영체제가 정책에 따라 복구 또는 종료를 결정한다.

이후 흐름은 다음 순서로 읽으면 된다.

  1. CPU가 현재 주소 공간을 기준으로 가상 주소 변환을 시도한다.
  2. 변환이나 권한 검사에 실패하면 pf와 진단 정보를 남긴다.
  3. 운영체제가 해당 fault를 복구할 수 있는지 판단한다.
  4. 복구할 수 있다면 프레임과 PTE를 준비한다.
  5. 예외에서 복귀해 fault가 발생했던 명령어를 다시 실행한다.

기준을 먼저 분리하기

설명의 기준이 섞이지 않도록 각 주체의 역할을 먼저 구분한다.

기준이 문서에서의 역할여기서 말하는 것
CPU / MMU하드웨어 규칙명령 실행 중 생성된 가상 주소를 현재 CR3의 page table로 번역한다
Linux / Windows실제 OS 개념 기준demand paging, memory protection, file mapping, copy-on-write 같은 현실의 VM 정책을 설명한다
PintOS실제 코드 증거pml4, pml4e_walk(), page_fault(), vm_try_handle_fault() 같은 과제 코드와 변수 흐름을 보여 준다
QEMU하드웨어 에뮬레이터 기준PintOS가 실제 CPU·MMU·메모리로 인식하는 동작을 guest CPU state로 재현한다

먼저 자주 생기는 오해를 바로잡자.

CPU가 메모리를 먼저 읽은 뒤 그 결과를 MMU에 넘기는 구조가 아니다. 더 정확히는 CPU가 명령어를 실행하면서 가상 주소를 만들고, 그 주소가 load/store/fetch에 필요해지는 순간 CPU 내부의 주소 변환 장치인 MMU/TLB 경로가 현재 CR3을 기준으로 번역을 시도한다.

PintOS의 C 코드가 MMU 자체로 동작하는 것도 아니다. PintOS는 MMU가 사용할 구조를 준비하고, MMU가 보고한 예외를 처리한다.

  • MMU가 참조할 page table page를 만든다.
  • 현재 주소 공간의 PML4를 CR3에 올린다.
  • Page fault가 발생하면 CR2와 error code를 읽는다.
  • 복구가 허용된 fault라면 frame을 확보하고 PTE를 설치한다.

Page Fault 발생 시 남는 상태

Page fault(#PF)는 x86에서 메모리 접근을 주소 변환으로 이어갈 수 없거나 접근 권한이 맞지 않을 때 발생하는 CPU 예외다.

CPU는 page fault가 발생하면 운영체제가 원인을 판단할 수 있도록 두 가지 핵심 정보를 남긴다.

  • CR2: fault가 발생한 가상 주소, 즉 “어떤 VA 때문에 발생했는가?”를 알려 준다.
  • error code: not present, write, user 등 “어떤 성격의 fault인가?”를 알려 준다.

운영체제는 이 정보를 바탕으로 다음 중 하나를 선택한다.

  • 합법적인 접근이라면 페이지를 준비하고 매핑을 설치한 뒤 같은 명령어를 다시 실행한다.
  • 복구할 수 없는 접근이나 버그라면 프로세스를 종료한다.

같은 pf가 서로 다른 결말로 이어지는 예

A) 복구 가능: 스택이 아래로 성장해야 하는 순간

유저 프로그램이 함수를 깊게 호출해 스택을 더 사용하려 하면, 아직 매핑되지 않은 스택 페이지에 처음 접근할 수 있다.

  • Page fault가 발생한다.
  • OS가 해당 접근을 허용 가능한 스택 성장으로 판단한다.
  • 새 프레임을 할당하고 매핑을 설치한다.
  • 같은 명령어를 다시 실행하며 프로그램이 계속 진행된다.

B) 복구 불가: 잘못된 포인터 접근

예를 들어 char *p = (char *)0xdeadbeef; *p = 1; 같은 접근은 일반적으로 유저 프로그램에 허용되지 않은 주소를 대상으로 한다.

  • Page fault가 발생한다.
  • OS가 정상적인 매핑이나 성장 규칙에 해당하지 않는다고 판단한다.
  • 프로세스를 종료한다.

실제 운영체제의 판단

현실의 운영체제는 page fault를 다음과 같이 처리한다.

  • 복구할 수 있는 fault: demand paging, file mapping(mmap), copy-on-write 같은 정책을 적용한 뒤 실행을 재개한다.
  • 복구할 수 없는 fault: Linux는 일반적으로 SIGSEGV(segmentation fault)로, Windows는 Access Violation 계열로 종료하거나 예외 처리한다.

즉, 현실의 운영체제에는 어떤 fault를 복구할지 결정하는 다양한 정책이 있으며, 이 정책은 파일 시스템·캐시·보안·성능과 깊이 연결된다.

9. 예외에서 복귀하면 같은 명령어를 다시 실행한다

vm_try_handle_fault()가 true를 반환하면 page_fault()는 그대로 return한다. 이후 interrupt return 경로가 struct intr_frame에 저장된 실행 상태로 복귀한다.

QEMU가 담당하는 범위

PintOS의 page_fault()는 guest OS 코드이며, QEMU는 guest의 syscall이나 VM 정책을 대신 처리하지 않는다.

QEMU의 역할은 guest CPU가 메모리에 접근할 때 x86 MMU가 수행할 주소 변환·권한 검사·예외 발생을 재현하는 것이다.

대표적인 단서는 다음 코드 흐름에서 확인할 수 있다.

  • target/i386/tcg/system/excp_helper.c
    • x86_cpu_tlb_fill()이 주소 변환을 요청한다.
    • get_physical_address()가 현재 guest CR3와 access type을 준비한다.
    • mmu_translate()가 page walk와 permission check를 수행한다.
    • 실패하면 TranslateFault에 exception_index = EXCP0E_PAGE, error_code, cr2 = addr를 담는다.

QEMU의 4단계 page walk에도 PintOS의 PML4/PDPE/PDX/PTX와 같은 bit 위치가 나타난다.

변환에 성공하면 QEMU는 최종 guest physical address를 만든다.

변환에 실패하면 QEMU는 env->cr[2] = err.cr2로 guest CR2를 갱신한 뒤 pf를 발생시킨다.

따라서 PintOS가 rcr2()로 읽는 CR2 값은 QEMU 내부에서 guest CPU state인 env->cr[2]로 표현된다. 다만 이것이 QEMU가 PintOS의 VM 정책까지 처리한다는 뜻은 아니다. QEMU는 하드웨어의 효과를 재현하고, fault를 복구할지 프로세스를 종료할지는 PintOS가 결정한다.

Page Fault 복구를 추적하는 GDB 체크리스트

다음은 page fault가 발생했을 때 확인할 최소 항목이다. 주소 공간 선택 → fault 정보 → page walk → PTE 설치 순서로 추적한다.

1. 현재 주소 공간의 PML4가 CR3에 올라가는지 확인한다

확인할 질문:

  • process_activate(next)의 next->pml4가 pml4_activate()의 pml4로 전달되는가?
  • lcr3() 이후의 rcr3() 값이 vtop(pml4)와 일치하는가?

2. fault 주소와 fault 종류를 확인한다

확인할 질문:

  • rcr2() 값이 실제로 접근하려던 데이터 VA인가?
  • f->rip는 해당 접근 명령어의 주소인가?
  • PF_P/PF_W/PF_U 해석이 not_present/write/user와 일치하는가?

3. page walk helper에서 index를 확인한다

확인할 질문:

  • fault_addr와 같은 page base를 사용해 pml4e_walk()가 호출되는가?
  • create=0 조회 경로와 create=1 설치 경로를 구분할 수 있는가?

4. PTE가 설치되는 순간을 확인한다

확인할 질문:

  • upage는 pg_round_down(fault_addr)와 같은가?
  • kpage는 frame->kva와 같은가?
  • PTE_ADDR(*pte)는 vtop(kpage)와 같은가?
  • 하위 bit에 PTE_P, PTE_U, 필요한 경우 PTE_W가 들어갔는가?

정리

  • CPU가 메모리를 읽어 MMU에 넘기는 것이 아니다. CPU 명령 실행 중 생성된 VA를 MMU/TLB 경로가 현재 CR3을 기준으로 번역한다.
  • Linux와 Windows에서 page fault는 VM subsystem이 복구 또는 종료를 결정하는 정책 이벤트다.
  • PintOS에서 주소 공간의 기준은 thread_current()->pml4 -> pml4_activate() -> lcr3(vtop(pml4)) -> CR3 흐름으로 설정된다.
  • PintOS에서 page table 조회와 설치는 pml4e_walk(), pml4_get_page(), pml4_set_page()를 통해 관찰할 수 있다.
  • PintOS의 fault 처리는 page_fault()가 rcr2()와 f->error_code를 읽는 순간 시작된다.
  • PintOS VM이 구현해야 할 복구 목표는 vm_try_handle_fault() -> spt_find_page() -> vm_do_claim_page() -> pml4_set_page() -> swap_in() 흐름이다.
  • 현재 W11 VM 코드는 skeleton 상태이므로 SPT lookup, frame allocation, PTE 설치, lazy load 정책을 구현해야 한다.
  • QEMU는 PintOS의 정책을 알지 못하며, guest x86 MMU의 page walk와 pf 전달 효과만 재현한다.
