장치 모델 (PIT · PIC · IDE)

장치 모델 (PIT · PIC · IDE)

한 줄 요약: 물리 장치를 소프트웨어 객체로 재현한 QEMU device model — PIT·PIC·IDE 세 핵심 장치.

장치 모델 구조

QEMU의 장치 모델(device model)은 물리 PC의 하드웨어 장치를 소프트웨어 객체로 재현한 것이다. PintOS가 사용하는 핵심 장치는 세 가지다: i8254 PIT(주기적 타이머 인터럽트 생성), i8259 PIC(IRQ를 CPU 인터럽트 벡터로 변환), IDE controller(디스크 섹터 읽기/쓰기). 이 세 장치가 함께 동작해야 PintOS가 시간을 추적하고, 인터럽트를 받고, 디스크에 접근할 수 있다. QEMU는 각 장치를 C 구조체 + QEMU_CLOCK 타이머 + I/O 포트 핸들러로 구현한다.

상세 설명

추상 개념 (하드웨어 PC의 장치 구조)

x86 PC에서 CPU는 장치와 두 가지 방법으로 통신한다:

  1. I/O 포트: in/out 명령어로 특정 포트 번호에 바이트를 읽고 쓴다 (PIO)
  2. 인터럽트: 장치가 IRQ 라인을 올리면 PIC이 CPU에 전달한다

세 장치의 관계:

%% QEMU 장치 모델 관계
flowchart LR
  PIT["i8254 PIT<br/>주기적 타이머 인터럽트<br/>I/O port: 0x40~0x43"]
  IDE["IDE controller<br/>디스크 섹터 읽기/쓰기<br/>I/O port: 0x1F0~0x1F7"]
  PIC["i8259 PIC<br/>IRQ를 CPU 인터럽트 벡터로 변환<br/>I/O port: 0x20~0x21"]
  CPU["CPU<br/>in/out 명령어로 PIO 수행<br/>INTR 수신 후 handler로 점프"]
  PIT --> PIC
  IDE --> PIC
  PIC --> CPU
  CPU <--> PIT
  CPU <--> PIC
  CPU <--> IDE

장치는 능동적이고, CPU는 반응적이다. PIT는 일정 주기마다 IRQ0을 발생시키고, IDE는 I/O가 완료되면 IRQ14/15를 발생시킨다. CPU는 인터럽트가 오면 현재 실행을 멈추고 핸들러로 점프한다.

실제 OS (Linux)

Linux도 레거시 호환을 위해 i8254/i8259를 초기화하지만, 실제로는 더 현대적인 장치를 사용한다:

레거시 장치현대 대체 장치이유
i8254 PITHPET, Local APIC Timer코어별 독립 타이머, 고해상도
i8259 PICI/O APIC + Local APICMSI, 다중 코어 인터럽트 분배
IDE PIOAHCI / NVMeDMA, 높은 처리량, 대기열

PintOS는 교육용이므로 가장 단순한 레거시 장치만 사용한다. QEMU는 이 레거시 장치를 기본으로 제공하므로 PintOS와 궁합이 좋다.

QEMU 구현

QEMU는 각 장치를 QOM(QEMU Object Model) 객체로 구현한다. 핵심 패턴:

  1. 상태 구조체: 장치의 레지스터, 카운터, 모드 등을 C 구조체 필드로 보관
  2. I/O 포트 핸들러: guest in/out 명령어를 가로채 핸들러 함수를 호출
  3. QEMU 타이머: 주기적/일회성 이벤트를 호스트 시간 기반으로 스케줄링
  4. IRQ 연결: qemu_set_irq()로 PIC 입력 라인의 레벨을 변경

i8254 PIT 모델

항목값
QEMU 소스hw/timer/i8254.c, include/hw/timer/i8254.h
상태 구조체PITChannelState (counter, gate, mode, count 등)
I/O 포트0x40~0x43
타이머 종류QEMU_CLOCK_VIRTUAL (가상 시간, icount와 동기화 가능)
IRQ 출력channel 0 → qemu_set_irq() → PIC IRQ0
핵심 주파수PIT_FREQ = 1,193,182 Hz

동작: guest가 outb(0x43, 0x34); outb(0x40, lo); outb(0x40, hi)를 실행하면, QEMU I/O 핸들러가 count 값을 읽고 timer_new_ns(QEMU_CLOCK_VIRTUAL, pit_irq_timer, ...)으로 host 타이머를 설정한다. 타이머 만료 시 pit_irq_timer_update() → qemu_set_irq() → PIC 모델로 IRQ0이 전달된다.

i8259 PIC 모델

항목값
QEMU 소스hw/intc/i8259.c
상태 구조체PICCommonState (irr, imr, isr, priority 등)
I/O 포트Master: 0x200x21, Slave: 0xA00xA1
cascadeSlave → Master IRQ2
출력CPU INTR 핀 (TCG가 인터럽트 체크 시점에 확인)

동작: 장치가 qemu_set_irq(pic_irq_N, 1)을 호출하면, PIC 모델이 IRR(Interrupt Request Register) 비트를 설정하고, IMR(Interrupt Mask Register)과 우선순위를 검사한 뒤 CPU에 인터럽트를 주입한다. CPU가 인터럽트를 수락하면(INTA cycle) PIC이 IRR → ISR 전환 후 벡터 번호를 전달한다.

guest가 PIC를 리맵할 때: outb(0x20, 0x11) → ICW1으로 초기화 시퀀스 시작 → ICW2로 시작 벡터 설정(0x20) → 이후 PIC 모델 내부 irq_base 필드 갱신.

IDE Controller 모델

항목값
QEMU 소스hw/ide/piix.c, hw/ide/core.c
상태 구조체IDEState (sector, nsector, status, io_buffer 등)
I/O 포트Channel 0: 0x1F00x1F7, Channel 1: 0x1700x177
IRQChannel 0: IRQ14, Channel 1: IRQ15
백엔드BlockBackend → 호스트 파일 (-drive file=...)

동작: guest outb(0x1F7, 0x20) (READ SECTOR) → QEMU IDE 핸들러가 LBA 레지스터에서 섹터 번호를 계산 → BlockBackend를 통해 호스트 파일에서 512바이트 읽기 → io_buffer에 저장 → status 레지스터 DRQ 비트 설정 + IRQ14 발생 → guest insw(0x1F0, buf, 256) 16비트 워드 256번으로 데이터 수거.

PintOS에서 세 장치의 초기화 순서

PintOS main() 함수에서:

1. timer_init()      — PIT 100Hz 설정, IRQ 0x20 핸들러 등록
2. kbd_init()        — 키보드 IRQ 0x21 핸들러 등록
3. serial_init_queue() — 시리얼 IRQ 0x24 핸들러 등록
4. disk_init()       — IDE 채널 0/1 초기화, IRQ 0x2E/0x2F 핸들러 등록
5. intr_enable()     — CPU IF 플래그 설정, 인터럽트 수신 시작
6. timer_calibrate() — PIT tick을 이용해 loops_per_tick 측정

인터럽트가 꺼진 상태에서 장치를 초기화한 뒤, intr_enable()로 한꺼번에 인터럽트를 여는 패턴이다.

인터럽트 전달 타이밍 (QEMU)

PIT 100 Hz 기준:

  • PIT count = (1,193,182 + 50) / 100 ≈ 11,932
  • 1 tick ≈ 11,932 / 1,193,182 ≈ 10.0 ms
  • QEMU virtual clock 기준: 10,000,000 ns per tick

IDE PIO 1 섹터 읽기:

  • guest가 cmd 레지스터에 0x20 기록
  • QEMU가 동기적으로 호스트 파일에서 512 byte 읽기 (host I/O 시간)
  • IRQ14 발생 → PIC → CPU
  • guest가 insw 256회로 512 byte 수거
  • PintOS 코드에서 sema_down(&completion_wait)로 IRQ 대기

관찰 시나리오

시나리오 1: PIT → PIC → CPU 인터럽트 전달 체인

목표: PIT tick이 PIC을 거쳐 CPU interrupt handler까지 도달하는 전체 경로를 추적한다.

절차:

  1. b timer_interrupt로 timer handler 진입 확인
  2. b pic_end_of_interrupt로 EOI 전송 확인
  3. ticks 변수 관찰: 10ms마다 1씩 증가하는지 확인
  4. intr_yield_on_return() 호출 여부 확인 (thread_tick이 time_slice 소진 시)

예상 결과:

  • timer_interrupt 호출 간격: tick 단위로 정확히 1씩 증가
  • EOI가 timer_interrupt 내에서 전송됨 (PIC master에 outb(0x20, 0x20))
  • thread_ticks >= TIME_SLICE(4) 일 때 intr_yield_on_return() 호출 → 인터럽트 복귀 시 yield

시나리오 2: disk_read 완료까지의 장치 협력 관찰

목표: disk_read()가 select_sector → issue_command → sema_down(대기) → IDE IRQ → sema_up(깨움) → insw(데이터 수거)로 진행되는 전체 흐름을 관찰한다.

절차:

  1. b disk_read, b select_sector, b issue_command으로 명령 발행 추적
  2. b interrupt_handler 조건 $vec == 0x2E로 IDE IRQ 도착 확인
  3. sema_down/sema_up 시점에서 현재 thread 확인
  4. insw 루프에서 input_sector 호출 추적

예상 결과:

  • disk_read: lock_acquire → select_sector(LBA 설정) → issue_command(0x20) → sema_down(block)
  • QEMU가 호스트 파일에서 512B 읽은 후 IRQ14 발생
  • interrupt_handler: vector=0x2E → sema_up(&completion_wait) → 대기 중인 thread unblock
  • 깨어난 thread가 input_sector() → insw(port, buf, 256) 256회로 데이터 수거
  • lock_release로 완료
