UNINIT swap_in 실패 롤백 Trace

UNINIT swap_in 실패 롤백 Trace

UNINIT swap_in 실패 롤백에서 먼저 헷갈리는 지점

vm_do_claim_page()는 PTE를 설치한 뒤 swap_in(page, frame->kva)를 호출한다.

그런데 이 page가 아직 UNINIT이면 swap_in()은 disk swap에서 읽는 함수가 아니라 uninit_initialize()다.

그러면 uninit_initialize()가 page type을 ANON 또는 FILE로 바꾼 뒤, 마지막 lazy callback이 실패하면 무엇을 누가 되돌려야 할까?

이 질문은 pml4 set page 실패 뒤 claim 롤백 Trace의 안쪽 질문이다. 바깥쪽에서는 PTE, frame link, user frame을 되돌린다. 안쪽에서는 aux 소유권, page type 전환, partially initialized page metadata를 어떻게 남기지 않을지 정해야 한다.

UNINIT swap_in 실패 롤백 혼동

lazy loading 실패는 “파일을 못 읽었으니 false”로 끝나지 않는다.

실패 직전에는 이미 여러 상태가 바뀌었을 수 있다.

바뀐 상태실패 후 방치하면 생기는 문제
PTE 설치 완료유저가 아직 검증되지 않은 frame bytes를 읽을 수 있다
page->frame, frame->page 연결cleanup이나 eviction이 resident page라고 착각한다
page->operations가 uninit_ops에서 anon_ops/file_ops로 변경더 이상 page->uninit.aux로 cleanup할 수 없다
aux가 callback에 전달됨누가 file close/free를 해야 하는지 모호해진다

이 말은 즉, swap_in() 실패는 두 층으로 나누어야 한다.

  • 바깥층: vm_do_claim_page()가 PTE와 frame 연결을 되돌린다.
  • 안쪽층: uninit_initialize()와 lazy callback이 aux와 page type metadata를 일관되게 만든다.

UNINIT swap_in 실패 롤백 흐름

UNINIT page의 첫 fault는 다음 네 단계를 지난다.

실패 책임은 이렇게 나누어 생각한다.

책임담당 위치실패 시 해야 할 일
PTE와 frame 노출 제거vm_do_claim_page()pml4_clear_page(), link 해제, frame release
aux 수명lazy callback 또는 타입별 destroy 계약close/free가 정확히 한 번 일어나게 한다
page type metadataanon_initializer(), file_backed_initializer(), callback실패해도 destroy(page)가 처리 가능한 상태로 둔다
SPT entry 제거fault 실패 뒤 process cleanup 경로supplemental_page_table_kill()에서 현재 page ops 기준으로 정리

중요한 판단은 이것이다.

PintOS 과제에서는 보통 fault를 살리지 못하면 process를 종료한다. 따라서 “retry 가능한 lazy page로 되돌리기”보다 “노출하지 않고 정리 가능하게 실패하기”가 구현 난이도와 책임 경계가 더 명확하다.

UNINIT swap_in 실패 롤백 입력 차이

ELF segment의 두 번째 page가 첫 fault를 냈다고 하자.

성공 경로라면 lazy_load_segment(page, aux)가 다음을 수행한다.

하지만 file_read_at()이 1904바이트를 채우지 못해 callback이 false를 반환했다고 하자.

기대 상태는 다음이다.

실제 운영체제

Linux와 Windows도 demand paging 중간에 실패할 수 있다. 예를 들어 파일-backed page를 fault로 읽는 중 I/O 오류, 메모리 부족, 권한 불일치가 발생할 수 있다.

실제 OS는 PintOS보다 훨씬 많은 장부를 함께 관리한다.

실제 OS 장부PintOS에서 대응해서 생각할 것
VMA / VADSPT entry와 page metadata
page cache / section objectfile-backed page metadata와 reopened file
page descriptor / PFN databasestruct frame과 frame table
PTE와 TLBPML4 entry와 pml4_clear_page()
reference countaux, file object, frame ownership

공통 원칙은 같다. 유저 주소에 page를 노출하기 전에 bytes와 metadata가 모두 성공해야 한다. 실패했다면 user-visible mapping과 kernel metadata가 같은 결론을 말하게 되돌린다.

PintOS

현재 자동화 기준 PintOS 코드는 W09 저장소다.

  • SW_AI-W11-pintos/pintos/vm/vm.c

  • SW_AI-W11-pintos/pintos/vm/anon.c
  • SW_AI-W11-pintos/pintos/vm/file.c
  • SW_AI-W11-pintos/pintos/userprog/process.c

vm_do_claim_page()는 frame을 붙이고 swap_in()으로 page type별 초기화를 호출한다.

UNINIT page에서 이 swap_in()은 uninit_initialize()로 간다.

uninit_initialize()는 중요한 주석을 이미 갖고 있다. page_initializer()가 union 안의 값을 덮어쓸 수 있으므로 init과 aux를 먼저 지역 변수로 꺼낸다.

이 구조에서 실패 지점은 두 개다.

실패 지점page 상태필요한 처리
page_initializer() 실패아직 타입 전환이 완전하지 않을 수 있음partial metadata를 남기지 않거나 destroy 가능하게 만든다
init(page, aux) 실패이미 ANON/FILE로 바뀌었을 수 있음aux 소유권을 정리하고 false를 바깥으로 전파한다

W09 skeleton의 anon_initializer()와 file_backed_initializer()는 page->operations를 바꾸는 자리만 열어 둔다. 구현할 때는 성공/실패를 명확히 반환하고, 실패가 가능한 allocation을 한다면 rollback 가능한 순서로 작성해야 한다.

lazy_load_segment()도 TODO다. 이 함수가 aux를 해석해 file read와 zero fill을 수행한다.

실전 구현에서는 callback 계약을 문서화해 두는 편이 안전하다.

둘을 섞으면 double free나 leak이 생긴다.

QEMU

QEMU는 UNINIT, aux, struct page를 모른다.

QEMU가 보는 것은 더 단순하다.

따라서 lazy callback이 실패했는데 PintOS가 PTE를 지우지 않으면 QEMU는 성공한 mapping으로 간주하고 같은 명령어를 진행시킨다. frame bytes가 덜 채워졌는지, aux가 leak됐는지는 QEMU가 알 수 없다.

이 말은 즉, uninit_initialize() 안쪽 실패를 하드웨어가 대신 막아 주지 않는다. PintOS가 false를 전파하고, vm_do_claim_page()가 mapping을 지워야 한다.

UNINIT swap_in 실패 롤백 코드

1. swap_in()은 operation table

파일:

  • SW_AI-W11-pintos/pintos/include/vm/vm.h

따라서 swap_in()은 항상 swap disk read를 뜻하지 않는다. 현재 page->operations가 무엇인지에 따라 uninit_initialize(), anon_swap_in(), file_backed_swap_in() 중 하나가 실행된다.

2. uninit_initialize()는 union

파일:

  • SW_AI-W11-pintos/pintos/vm/uninit.c

주석의 핵심은 “page_initialize may overwrite the values”다. struct page는 union으로 uninit, anon, file을 공유하므로 타입 전환 후에는 예전 page->uninit.aux를 안정적으로 읽을 수 없다.

3. vm_do_claim_page()는 swap_in()

파일:

  • SW_AI-W11-pintos/pintos/vm/vm.c

W09 구현에서는 swap_in() 실패 시 vm_destroy_page_frame()이 rollback을 수행한다.

vm_destroy_page_frame()은 PTE clear, frame table 제거, palloc free, link 해제를 한번에 처리한다.

이 함수가 바깥층 rollback의 전부다. 안쪽층(aux 정리)은 lazy_load_segment() 같은 callback이 false를 반환하기 전에 이미 처리한다.

4. lazy callback은 성공/실패 모두 aux를 소비한다

파일:

  • SW_AI-W11-pintos/pintos/userprog/process.c

W09의 lazy_load_segment()는 done 레이블로 성공/실패 경로를 합친다.

load_segment()는 page별 file_reopen()과 aux를 만들고, 등록 실패 시 즉시 cleanup한다. 자세한 수명은 file 수명 Trace에서 본다.

UNINIT swap_in 실패 롤백 값 추적

PTE 설치 뒤 lazy callback 실패 직전의 값을 넣어 보자.

이때 lazy_load_segment()가 false를 반환하면 frame bytes는 믿을 수 없다.

그래서 rollback 뒤 기대값은 다음이다.

그리고 aux는 다음 둘 중 하나여야 한다.

UNINIT swap_in 실패 롤백 GDB

GDB에서는 uninit_initialize()와 lazy callback 사이를 나누어 본다.

uninit_initialize()에 들어가면 먼저 아직 UNINIT 상태인지 확인한다.

page_initializer()가 지나간 뒤에는 operation table이 바뀌는지 본다. 구현에 따라 정확한 next 횟수는 달라질 수 있다.

lazy callback 실패를 한 번 주입한다.

vm_do_claim_page()의 실패 처리 지점으로 돌아온 뒤 확인한다.

기대:

추가로 aux cleanup은 implementation별로 확인한다.

설계확인할 것
callback이 aux를 freecallback failure path에서 file_close(aux->file), free(aux)가 한 번 실행되는가
page metadata로 ownership 이동이후 destroy(page)가 같은 file reference를 한 번만 닫는가
process kill cleanup에 맡김rollback이 frame/PTE만 제거하고 SPT page destroy와 충돌하지 않는가

정리

  • UNINIT page의 swap_in()은 uninit_initialize()다.
  • uninit_initialize()는 page_initializer()가 union을 덮어쓰기 전에 init과 aux를 지역 변수로 꺼낸다.
  • page_initializer() 성공 뒤 lazy callback이 실패하면 page는 이미 ANON 또는 FILE로 전환됐을 수 있다.
  • aux는 callback이 free하거나 현재 page type의 destroy 경로로 넘겨야 한다. 둘 다 하거나 둘 다 안 하면 안 된다.
  • PTE, frame link, user frame release는 vm do claim page()의 rollback 책임이다.
  • QEMU는 이 정책을 모르고 guest PTE와 frame bytes만 본다.

UNINIT swap_in 실패 롤백 관련 문서

  • claim rollback
    • PTE/link/frame을 되돌리는 바깥쪽 claim 실패 경로.
  • lazy aux 수명
    • lazy page의 aux와 reopened file이 언제까지 살아야 하는지.
  • aux ownership 계약
    • executable lazy page와 mmap lazy page에 공통 적용할 aux 소유권 계약.
  • aux cleanup checklist
    • callback 실패와 never-faulted cleanup을 실제 helper/assert 분기표로 내리는 Trace.
  • mmap aux 전환
    • UNINIT(FILE)이 struct file_page metadata로 전환되는 ownership 질문.
  • mmap UNINIT cleanup
    • 한 번도 fault가 없던 UNINIT(FILE) page cleanup 흐름.
  • spt kill cleanup
    • 실패 뒤 process cleanup이 SPT page를 destroy하는 흐름.
  • PintOS VM 시각
    • VM 시각화에서 이 Trace의 위치.
