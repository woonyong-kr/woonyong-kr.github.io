하드 링크와 소프트 링크

하드 링크와 소프트 링크

한 줄 요약: 하드 링크는 같은 inode를 가리키는 디렉터리 엔트리를 하나 더 만드는 것이고, 소프트 링크(심볼릭 링크)는 경로 문자열을 담은 별도 파일을 만드는 것이다.

파일 이름을 지웠는데 데이터가 남는 이유

파일 시스템에서는 “파일 이름”과 “파일 실체(데이터)“가 분리되어 있다. 디렉터리는 이름을 inode 번호에 연결하고, inode는 실제 데이터의 위치를 가리킨다.

이 구조에서는 하나의 파일 실체에 여러 이름을 붙일 수 있다. 하드 링크와 소프트 링크는 모두 다른 이름으로 파일에 접근하게 해 주지만, 이름과 파일 실체를 연결하는 방식은 다르다. 이 차이를 알면 ln 명령어와 패키지 매니저의 심볼릭 링크, 공유 라이브러리 버전 관리, 파일을 삭제해도 inode가 남는 이유를 설명할 수 있다.

디렉터리 엔트리와 inode

파일 시스템에서 디렉터리는 특수한 파일이다. 그 내용은 (이름, inode 번호) 쌍의 배열이다.

%% 디렉터리 엔트리의 name에서 inode로 이어지는 매핑
flowchart LR
  directory["디렉터리 <local-home>/<br/>name &#124; inode 번호<br/>hello.txt &#124; 42<br/>world.txt &#124; 57<br/>data/ &#124; 63"]
  inode42["inode 42<br/>메타데이터<br/>데이터 블록 위치"]
  directory --> inode42

hello.txt를 읽을 때 OS는 먼저 디렉터리에서 이름 hello.txt에 대응하는 inode 42를 찾는다. 이어서 inode 42의 메타데이터를 읽고 데이터 블록의 위치를 알아낸다. 이름은 디렉터리가 관리하고, 데이터의 위치는 inode가 관리한다.

하드 링크는 같은 inode에 이름을 추가한다

하드 링크를 만들면 기존 파일의 inode 번호가 새 디렉터리 엔트리에 등록된다. 새 파일 실체를 만드는 것이 아니라, 기존 파일 실체에 접근할 이름을 하나 더 붙이는 셈이다.

%% 하드 링크 생성 뒤 hello.txt와 greeting.txt가 같은 inode 42를 가리키는 구조
flowchart LR
  directory["디렉터리 <local-home>/<br/>name &#124; inode 번호<br/>hello.txt &#124; inode 42<br/>greeting.txt &#124; inode 42<br/>world.txt &#124; inode 57"]
  inode42["inode 42<br/>nlink: 2<br/>데이터 블록 -&gt; ..."]
  directory --> inode42

hello.txt와 greeting.txt는 같은 inode 42를 가리킨다. 둘은 동등하므로 어느 쪽이 원본이고 어느 쪽이 링크인지 구분할 수 없다.

inode의 nlink는 해당 inode를 가리키는 하드 링크 수를 나타낸다. 하드 링크를 만들면 nlink++가 되고, rm으로 이름 하나를 지우면 해당 디렉터리 엔트리가 삭제되면서 nlink--가 된다. inode와 데이터 블록은 nlink가 0이 되어야 해제될 수 있다.

inode 번호는 파일 시스템 내부에서 사용하는 인덱스다. 따라서 하드 링크는 같은 파일 시스템 안에서만 만들 수 있고, 다른 파일 시스템의 inode를 직접 가리킬 수 없다.

디렉터리에 대한 하드 링크도 일반적으로 금지된다. 디렉터리 그래프에 순환이 생기면 find, du 같은 도구가 무한 루프에 빠질 수 있기 때문이다.

소프트 링크는 경로를 담은 별도 파일이다

소프트 링크는 “이 파일은 경로 X를 가리킨다”라는 문자열을 담은 독립된 파일이다. 심볼릭 링크라고도 하며, 대상 파일과 별도로 자체 inode를 갖는다.

%% 소프트 링크가 별도 inode에 path 문자열을 저장하고 대상 파일을 다시 해석하는 구조
flowchart LR
  directory["디렉터리 <local-home>/<br/>name &#124; inode 번호<br/>hello.txt &#124; inode 42<br/>shortcut &#124; inode 99"]
  inode42["inode 42<br/>타입: 일반 파일<br/>nlink: 1<br/>데이터 블록 -&gt; ..."]
  inode99["inode 99<br/>타입: 심볼릭 링크<br/>내용: path 문자열<br/>&quot;<local-home>/hello.txt&quot;"]
  directory --> inode42
  directory --> inode99
  inode99 --> inode42

소프트 링크의 inode는 경로 문자열을 저장한다. 대상 파일의 inode를 공유하지 않으므로 소프트 링크를 만들어도 원본 파일의 nlink는 변하지 않는다.

원본 파일을 삭제하면 소프트 링크에 저장된 경로가 더 이상 대상을 찾지 못한다. 이 상태를 **깨진 링크(dangling link)**라고 하며, 링크를 통해 접근하면 오류가 발생한다.

경로 문자열은 파일 시스템 경계를 넘어 해석할 수 있으므로 다른 파일 시스템의 대상도 가리킬 수 있다. 디렉터리에 대한 소프트 링크도 허용된다.

두 링크를 구분하는 기준

항목하드 링크소프트 링크
자체 inode없음 (원본과 공유)있음 (별도 inode)
inode nlink 변화증가변화 없음
원본 삭제 시데이터 유지 (nlink > 0)깨진 링크
파일 시스템 간불가가능
디렉터리 링크불가 (순환 방지)가능
저장 내용디렉터리 엔트리만 추가경로 문자열 파일
파일 크기추가 공간 거의 없음경로 문자열 길이만큼

두 링크의 차이는 무엇을 저장하고 따라가는지에서 나온다. 하드 링크는 같은 inode 번호를 디렉터리 엔트리에 한 번 더 저장한다. 소프트 링크는 별도 inode에 대상의 경로 문자열을 저장하고, 접근할 때 그 경로를 다시 해석한다.

하드 링크 삭제와 nlink

파일 삭제는 먼저 디렉터리 엔트리를 제거하는 작업이다. 같은 inode를 가리키는 하드 링크가 여러 개라면 이름 하나를 지워도 다른 이름으로 데이터에 접근할 수 있어야 한다. nlink는 inode를 계속 유지할지 판단하는 기준이 된다.

파일 삭제는 다음 순서로 진행된다.

  1. unlink("hello.txt") 호출
  2. 디렉터리에서 hello.txt 엔트리를 제거한다
  3. inode의 nlink--
  4. nlink가 0이고 열려 있는 프로세스도 없으면 → inode와 데이터 블록 해제
  5. nlink가 0이지만 열려 있는 프로세스가 있으면 → 프로세스가 닫을 때까지 유지

이 설계에서는 실행 중인 프로그램의 바이너리를 업데이트할 수 있다. 기존 파일을 unlink하고 새 파일을 같은 이름으로 만들면, 기존 프로세스는 이전 inode를 계속 사용하고 새 프로세스는 새 inode를 연다.

PintOS에서 보는 링크의 기반

디렉터리 엔트리

PintOS의 디렉터리 엔트리도 name → inode_sector 매핑을 표현한다. 이 구조에서 하드 링크를 만든다면 서로 다른 name이 같은 inode_sector를 가리키는 엔트리 두 개가 필요하다.

PintOS가 하드 링크를 지원하지 않는 이유

PintOS의 dir_remove()는 디렉터리 엔트리를 지울 때 바로 inode_remove()를 호출한다.

이 동작은 PintOS에 nlink 카운터가 없기 때문에 가능하다. PintOS의 struct inode에는 열린 횟수를 나타내는 open_cnt와 삭제 예약을 나타내는 removed 플래그만 있고, 하드 링크 수를 추적하는 nlink 필드는 없다.

dir_remove()가 호출되면 inode_remove()가 삭제를 예약한다. 실제 해제는 마지막으로 inode를 연 주체가 inode_close()를 호출할 때 이루어진다.

PintOS에 하드 링크를 추가하려면

하드 링크를 구현하려면 inode를 가리키는 이름의 수를 저장하고, 그 수에 따라 삭제 여부를 판단해야 한다.

  1. inode_disk에 nlink 필드를 추가한다.
  2. dir_add()에서 기존 inode 섹터를 새 이름에 연결할 때 nlink++.
  3. dir_remove()에서 inode_remove() 대신 nlink--하고, nlink == 0일 때만 삭제를 예약한다.

Linux ext4와 PintOS의 삭제 흐름

Linux ext4에서 unlink() 시스템 콜이 실행되면 다음 순서로 처리된다.

  1. 디렉터리 엔트리를 제거한다.
  2. inode의 i_nlink--.
  3. i_nlink가 0이면 inode를 “orphan list”에 등록한다.
  4. 열려 있는 struct file이 모두 닫히면 evict_inode()에서 데이터 블록과 inode를 해제한다.

이 흐름은 PintOS의 open_cnt와 removed 조합과 비슷하다. 다만 Linux는 nlink를 사용해 같은 inode를 가리키는 여러 이름의 참조까지 추적한다.

항목Linux (ext4)PintOS
inode에 nlink있음 (i_nlink)없음
하드 링크지원 (link() 시스템 콜)미지원
심볼릭 링크지원 (symlink() 시스템 콜)미지원
파일 삭제 기준nlink == 0 && 열린 fd 없음removed == true && open_cnt == 0
디렉터리 . / ..하드 링크 (nlink에 반영)미구현

하드 링크는 같은 inode에 접근할 이름을 추가하고, nlink로 그 이름의 수를 관리한다. 소프트 링크는 경로 문자열을 담은 별도 파일이므로 대상의 inode와 독립적이지만, 경로의 대상이 사라지면 깨진다.

PintOS에는 nlink 필드가 없다. 그래서 dir_remove()가 inode 삭제를 바로 예약하며 하드 링크를 지원하지 않는다. 하드 링크를 구현하려면 inode_disk에 nlink를 추가하고, 디렉터리 엔트리 제거와 inode 해제를 참조 카운트에 따라 분리해야 한다.
