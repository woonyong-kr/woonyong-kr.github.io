fork 때 SPT는 왜 같이 복사해야 하나

한 줄 요약: fork()는 present PTE만이 아니라 SPT에 남은 lazy·swapped·file-backed page의 “앞으로 fault가 나면 그 주소를 어떻게 살릴지에 대한 약속”까지 복제해야 하며, supplemental_page_table_copy()가 page type별로 분기해 자식의 주소 공간을 다시 만든다.

fork SPT 복사 쟁점

fork()는 부모 프로세스를 복제한다.

그런데 부모의 주소 공간에는 두 종류의 정보가 섞여 있다.

  • page table에 이미 올라간 resident page
  • page table에는 아직 없지만 SPT에는 남아 있는 lazy page, swapped page, file-backed page

처음에는 이렇게 묻게 된다.

부모의 page table만 복사하면 자식의 주소 공간도 복사된 것 아닐까?

VM 과제에서는 아니다. page table은 “지금 번역 가능한 page”만 설명한다. fork()가 복사해야 하는 것은 지금의 PTE만이 아니라, 앞으로 page fault가 났을 때 그 주소를 어떻게 살릴지에 대한 약속이다.

fork SPT 복사 필요성

Project 2의 단순 주소 공간에서는 부모가 가진 present PTE를 순회해 frame 내용을 memcpy하면 어느 정도 설명이 된다.

하지만 VM을 켜면 합법적인 주소가 항상 present PTE를 가진다는 보장이 사라진다.

예를 들어 부모가 ELF segment를 lazy load로 등록해 두었다면, 아직 접근하지 않은 .text page는 page table에 없을 수 있다. 그래도 그 주소는 불법이 아니다. SPT에 “첫 접근 때 파일 offset에서 읽어 올 page”라는 의미가 남아 있기 때문이다.

이때 fork()가 present PTE만 복사하면 자식은 이런 page를 잃어버린다.

이 말은 즉, VM 이후의 fork()는 주소 공간의 현재 RAM 내용과 주소 공간의 미래 page fault 의미를 함께 복제해야 한다.

실제 운영체제

Linux의 fork()는 주소 공간을 논리적으로 복제한다. 실제 물리 page를 모두 즉시 복사하면 너무 비싸기 때문에, 일반적으로 private page는 copy-on-write로 처리한다.

처음에는 부모와 자식 PTE가 같은 물리 page를 가리키되 write permission을 막아 둔다. 한쪽이 write하려고 하면 protection fault가 나고, 커널이 그때 새 page를 할당해 4 KB를 복사한 뒤 write를 허용한다.

Windows는 Unix식 fork()를 일반 프로세스 생성 모델로 제공하지 않는다. CreateProcess는 새 process object와 address space를 만들고, 실행 image section을 매핑한다. handle 상속이나 section object, copy-on-write image/page 개념은 있지만, “부모 주소 공간 전체를 fork로 복제한다”라고 설명하면 틀린다.

그래도 실제 OS들이 공통으로 다루는 문제는 같다.

  • 어떤 주소 범위가 합법인가?
  • 어떤 protection을 가지는가?
  • backing store는 파일, zero-fill, swap, shared object 중 무엇인가?
  • 언제 실제 물리 page를 붙일 것인가?

PintOS의 SPT는 이 큰 문제를 학습용 크기로 줄인 것이다.

PintOS

PintOS에서 fork()는 먼저 syscall handler를 거쳐 process_fork()로 내려간다.

자식 스레드의 시작점은 __do_fork()다.

여기서 중요한 분기점은 #ifdef VM이다.

!VM 경로의 duplicate_pte()는 부모 page table에서 present PTE를 순회한다. 부모 frame의 4 KB를 새 frame으로 복사하고, 자식 page table에 같은 VA로 매핑한다.

VM 경로에서는 이 방식만으로 부족하다. 그래서 supplemental_page_table_copy()가 별도 hook으로 들어간다.

이 함수가 해야 할 일은 구현 선택에 따라 달라질 수 있지만, 최소 질문은 다음과 같다.

page 상태자식에게 필요한 것
uninit lazy pageinitializer, 독립 aux, file offset, read/zero bytes, writable 의미
present anonymous pagefork 순간의 4 KB 내용 또는 COW 공유 상태
swapped anonymous pageswap slot 내용을 자식도 복원할 수 있는 별도 의미
file-backed pagefile handle/reference, offset, read/zero bytes, writable, dirty 정책
stack page자식의 stack으로 독립 동작할 page 의미와 내용

주의할 점은 struct page 포인터를 그대로 두 SPT에 꽂는 설계다. 그러면 부모와 자식이 같은 page metadata를 소유하게 되어 한쪽 supplemental_page_table_kill()이나 eviction이 다른 쪽 주소 공간을 깨뜨릴 수 있다.

같은 이유로 UNINIT page의 page->uninit.aux 포인터도 그대로 공유하면 위험하다. aux는 첫 fault 또는 destroy에서 소비되고 해제될 수 있으므로, 부모와 자식이 각자 aux와 file reference를 소유해야 한다. 이 질문은 fork에서 lazy UNINIT page의 aux는 어떻게 복사해야 하나에서 별도로 본다.

exec() 경계도 같이 봐야 한다. process_exec()는 새 ELF를 로드하기 전에 process_cleanup()을 호출한다. VM이면 supplemental_page_table_kill(&curr->spt)가 먼저 실행되고, 그 뒤 기존 pml4를 파괴한다. 그래서 fork() 직후 자식이 exec()하면 fork로 받은 옛 주소 공간은 새 프로그램 주소 공간으로 교체된다.

supplemental_page_table_copy 분기표

supplemental_page_table_copy(dst, src)를 구현할 때는 “부모 SPT를 순회한다”에서 멈추면 안 된다.

부모 SPT의 entry 하나마다 먼저 물어야 할 질문은 이것이다.

처음 구현에서는 다음처럼 판단 기준을 고정해 두면 실수를 줄일 수 있다.

부모 page 상태판별할 값자식에게 만들 것공유하면 위험한 것이어서 볼 문서
lazy UNINIT executable pageoperations->type == VM_UNINIT, page_get_type(page) == VM_ANON 또는 구현한 target type새 struct page, 새 aux, 새 reopened file, 같은 va/read_bytes/zero_bytes/writablepage->uninit.aux, aux->filefork에서 lazy UNINIT page의 aux는 어떻게 복사해야 하나
resident anonymous pagepage_get_type(page) == VM_ANON, page->frame != NULL새 page와 child 전용 frame에 4KB 복사, 또는 COW metadataparent frame의 writable ownership, frame->page linkCOW write protect fault는 언제 page copy로 살아나나
swapped-out anonymous pagepage_get_type(page) == VM_ANON, page->frame == NULL, anon metadata에 slot 있음child 전용 slot 복사, parent swap-in 후 child frame 복사, 또는 refcount 있는 shared slotslot 번호만 얕게 복사한 ownershipfork에서 swapped out anonymous page는 어떻게 복사해야 하나, swapped anonymous page fork snapshot 흐름
lazy UNINIT(FILE) mmap pageoperations->type == VM_UNINIT, target type이 VM_FILE새 aux, 새 file reference, 같은 offset/range/writable 의미mmap aux와 file referencemmap file page의 aux는 언제 struct file page로 옮겨야 하나
resident file-backed pagepage_get_type(page) == VM_FILE, page->frame != NULL구현 정책에 따라 frame snapshot, file metadata 복제, dirty/write-back 기준dirty bit 의미, shared struct file_pagemmap dirty write back은 어떻게 디스크 쓰기로 내려가나
stack page구현한 stack marker 또는 va가 stack 범위child stack page 의미와 fork 순간 bytes부모 stack frame, parent page 객체스택 성장 페이지 폴트는 언제 살려야 하나

이 표의 핵심은 “값은 같게, 소유권은 분리”다.

예를 들어 lazy page에서는 ofs=0x2000, read_bytes=4096 같은 값은 부모와 자식이 같아야 한다. 하지만 그 값을 담은 aux 포인터와 그 안의 struct file * 소유권은 분리되어야 한다. swapped page도 마찬가지다. slot 번호라는 값 하나를 그대로 복사하는 것이 아니라, 그 slot의 4096바이트 snapshot을 자식이 언제까지 읽을 수 있는지까지 결정해야 한다.

추천 구현 흐름

구현 전략은 프로젝트 코드 구조마다 달라질 수 있지만, 흐름은 다음 질문 순서로 잡는다.

이 말은 즉, supplemental_page_table_copy()는 단순 memcpy(struct page) 함수가 아니다.

struct page 안에는 union이 들어 있고, 현재 어떤 union 멤버가 의미 있는지는 operations->type과 page_get_type(page)로 나뉜다. W09 스켈레톤의 page_get_type()도 VM_UNINIT이면 page->uninit.type을 돌려주도록 되어 있다. 그래서 “지금은 UNINIT이지만 나중에 어떤 type으로 초기화될 page인가”를 따로 읽어야 한다.

실패 rollback 기준

SPT copy는 fork() 중간에 실행된다. 따라서 실패하면 자식은 아직 유저 모드로 나가면 안 되고, 이미 만든 child-side 자원은 정리되어야 한다.

실패 지점이미 생겼을 수 있는 것되돌릴 것
child page allocation 실패없음바로 false
child aux deep copy 실패child pagechild page free
file_reopen() 실패child page, child aux 일부reopened file 없으면 aux/page free
child SPT insert 실패child page, child aux/filechild page destroy 경로로 aux/file 정리
child frame allocation 실패child SPT page, aux/fileSPT에서 제거하고 page destroy
child PTE 설치 실패child frame, child page linkPTE clear, frame free, link 제거
child slot copy 실패child slot 일부, child pageslot bitmap/metadata 되돌림

여기서 중요한 기준은 supplemental_page_table_copy()가 false를 반환할 때 자식 SPT가 “반쯤 복사된 주소 공간”으로 남지 않아야 한다는 점이다. __do_fork()는 copy 실패를 보면 goto error로 빠지고 thread_exit()을 호출한다. 하지만 그 전에 child SPT에 들어간 page들이 destroy 경로로 한 번씩만 정리될 수 있어야 leak과 double free를 피할 수 있다.

작은 숫자 예시

부모가 세 page를 갖고 있다고 하자.

자식에게 필요한 결과는 다음처럼 서로 다른 기준을 쓴다.

swap slot 3이 실제 디스크에서 차지하는 범위는 512B sector 8개다.

QEMU는 sector 24..31을 읽고 쓸 수 있게 해 줄 뿐이다. 그 sector 범위가 parent snapshot인지 child snapshot인지는 PintOS의 swap slot metadata가 기억해야 한다.

GDB에서 분기표 확인하기

구현 뒤에는 copy 함수 안에서 page마다 다음 값을 한 줄로 찍을 수 있게 만든다.

lazy page를 만났다면 parent/child 포인터가 이렇게 갈라져야 한다.

resident anonymous page를 eager copy했다면 다음을 비교한다.

swapped anonymous page는 slot 번호만 보지 말고 ownership 정책까지 같이 본다.

struct anon_page가 아직 비어 있는 W09 스켈레톤에서는 위 명령이 바로 답을 주지 않는다. 구현자가 slot 번호, in-swap flag, refcount 또는 child 전용 slot 정보를 어디에 넣었는지에 맞춰 관찰식을 바꿔야 한다.

QEMU

QEMU는 supplemental_page_table_copy()의 의미를 모른다.

QEMU가 보는 것은 guest CPU state와 guest page table이다.

자식이 잘못 복사된 주소에 접근하면 QEMU는 x86 MMU처럼 page table walk를 시도한다. PTE가 없거나 권한이 맞지 않으면 pf를 guest에게 전달한다. 그 뒤 vm_try_handle_fault()가 SPT를 보고 살릴지 결정하는 것은 PintOS의 일이다.

관련 QEMU 코드 단서는 다음과 같다.

  • target/i386/tcg/system/excp_helper.c
    • get_physical_address()
    • x86_cpu_tlb_fill()
    • err.cr2
    • EXCP0E_PAGE
  • target/i386/gdbstub.c
    • guest CR2, CR3를 GDB register로 노출
  • target/i386/arch_memory_mapping.c
    • env->cr[3]에서 guest page table root를 읽고 PML4를 walk

즉 QEMU는 SPT를 “커널 자료구조”로 해석하지 않고, PintOS가 guest memory 안에서 읽고 쓰는 바이트로만 본다.

  • SW_AI-W11-pintos/pintos/userprog/process.c

흐름:

process_fork()는 args->if_ = *if_로 부모의 syscall 진입 시점 register snapshot을 복사한다. 그래서 자식은 부모와 거의 같은 실행 지점으로 돌아갈 수 있다. 단, 자식의 RAX는 나중에 0으로 바뀐다.

2. VM 경로는 SPT copy로 갈라진다

파일:

  • SW_AI-W11-pintos/pintos/userprog/process.c

핵심 분기:

이 분기는 “VM을 켠 뒤에는 page table 순회만으로 주소 공간을 설명할 수 없다”는 코드상의 증거다.

3. VM이 아닐 때는 present PTE만 복사한다

파일:

  • SW_AI-W11-pintos/pintos/userprog/process.c
  • SW_AI-W11-pintos/pintos/threads/mmu.c

duplicate_pte()는 pml4_for_each() 콜백이다. pml4_for_each()는 present PTE를 찾아 콜백을 호출하고, duplicate_pte()는 그 frame 내용을 새 page로 복사한다.

이 방식은 not-present lazy page를 보지 못한다. VM 과제에서 SPT copy가 필요한 이유가 여기서 드러난다.

5. exec는 fork로 받은 옛 주소 공간을 버린다

파일:

  • SW_AI-W11-pintos/pintos/userprog/process.c

process_exec()는 새 ELF를 로드하기 전에 process_cleanup()을 호출한다.

process_cleanup()은 VM에서 SPT를 kill하고, 그 다음 기존 PML4를 비운다.

그래서 tests/vm/mmap-inherit.c처럼 fork 후 exec하는 테스트에서는 부모의 mmap 영역이 새 프로그램에 그대로 남으면 안 된다.

fork SPT 복사 값 추적

4 KB page 복사 비용

부모가 present user page 100개를 가지고 있고, eager copy로 fork()한다고 하자.

부모가 lazy page 100개를 추가로 SPT에만 가지고 있다면, page table 복사만으로는 이 100개가 보이지 않는다.

PTE bit 예시

부모의 anonymous page가 frame 0x12345000에 resident라고 하자.

COW를 구현한다면 fork 직후에는 writable page도 임시로 read-only처럼 보이게 만들 수 있다. 그러면 write 시점에 PF_P=1, PF_W=1, PF_U=1인 protection fault가 들어오고, 커널은 “진짜 불법 write”인지 “COW로 살릴 write”인지 metadata로 구분해야 한다.

lazy page 예시

부모가 아직 읽지 않은 file-backed page는 PTE가 없을 수 있다.

자식에게 필요한 것은 frame 주소가 아니라 이 metadata다. 그래야 자식이 0x401123을 처음 읽을 때 다음 계산을 할 수 있다.

fork SPT 복사 GDB

PintOS GDB에서 다음 breakpoint를 잡으면 흐름을 볼 수 있다.

fork() 직후 부모와 자식의 page table root가 분리되는지 확인한다.

SPT 구현 후에는 copy 함수 안에서 각 page의 주소와 타입을 출력해 본다.

실행 후보 테스트:

COW write protect fault까지 구현했다면 다음 테스트도 연결된다.

관찰 목표는 다음이다.

QEMU 쪽에서는 GDB가 보여주는 CR3와 CR2가 guest CPU state라는 점만 확인한다.

CR3는 현재 guest page table root이고, CR2는 최근 page fault 주소다. SPT entry 자체는 QEMU register가 아니라 PintOS 커널 메모리 안의 자료구조다.

정리

VM을 켠 뒤의 fork()는 page table 복사만으로 끝나지 않는다.

page table은 현재 resident mapping을 보여 주고, SPT는 “이 주소가 원래 어떤 page였는가”를 기억한다. lazy load, swap, mmap, COW 같은 정책은 page table에 없는 의미를 SPT에 의존한다.

PintOS 코드에서 이 차이는 __do_fork()의 #ifdef VM 분기로 드러난다. !VM은 present PTE를 순회하지만, VM은 supplemental_page_table_copy()를 호출한다.

QEMU는 이 정책을 처리하지 않는다. QEMU는 guest CR3/PTE를 따라 주소 변환을 에뮬레이션하고, 실패하면 pf를 PintOS에 전달한다. 그 fault를 살릴지 죽일지는 PintOS의 SPT copy와 fault handler 구현에 달려 있다.
