주소 공간 교체

주소 공간 교체

범위: 이 문서는 주소 공간 교체의 일반 원리와 Linux·PintOS 구현을 비교해 설명하며, 함수 흐름·코드 좌표·상수·모드별 차이는 본문이 전제한 특정 구현에 한정된다. GDB 출력, QEMU 동작과 성능 영향은 실제 버전의 소스 코드·실행 기록·측정 결과로 검증된 결과가 아니라 관찰 예시와 판단 기준으로 구분해 읽어야 한다.

process_exec()는 같은 커널 스레드에서 유저 프로그램만 새 실행 파일로 갈아 끼운다. fork()가 주소 공간을 복사한다면, exec()는 기존 주소 공간을 버리고 새 ELF로 다시 시작한다.

복사가 아니라 교체다

process_exec()를 볼 때는 새 프로세스를 만든다고 생각하면 헷갈린다. 이 함수는 현재 스레드의 주소 공간을 완전히 파괴한 뒤 새 ELF 바이너리를 적재해 유저 모드로 들어간다. tid와 커널 스택은 그대로 남지만, 유저 영역의 코드·데이터·스택은 새 프로그램의 것으로 바뀐다. Unix/Linux의 execve() 시스템 콜에 해당한다.

교체 과정

exec 계열 시스템 콜이 하는 일

exec 계열 시스템 콜은 다음을 수행한다:

  1. 기존 주소 공간 파괴 — 유저 영역의 모든 페이지 매핑, 스택, 힙, mmap 영역을 해제한다. 커널 영역 매핑은 모든 프로세스가 공유하므로 유지된다.
  2. 새 ELF 적재 — 새 실행 파일의 ELF 헤더를 파싱하고, PT_LOAD 세그먼트를 가상 주소에 매핑한다.
  3. 새 스택 설정 — 유저 스택을 새로 할당하고 argv/argc를 배치한다.
  4. 유저 모드 진입 — 새 ELF의 e_entry를 RIP에 넣고 iret으로 유저 모드에 진입한다.

핵심 속성:

  • PID 불변: exec 전후로 PID(PintOS에서는 tid)가 바뀌지 않는다.
  • fd 테이블 유지: 열린 파일 디스크립터는 (FD_CLOEXEC이 없으면) exec 이후에도 유지된다. PintOS에서는 fd_table을 건드리지 않는다.
  • 돌아오지 않음: exec이 성공하면 호출 지점으로 돌아오지 않는다. do_iret()으로 새 유저 코드로 점프하기 때문이다.
  • 실패 시 반환: 파일이 없거나 ELF가 잘못되면 -1을 반환하고, 기존 프로세스는 이미 파괴된 상태이므로 thread_exit()으로 종료한다.

실제 OS (Linux)

Linux의 do_execveat_common() → exec_binprm() → load_elf_binary() 흐름:

  1. begin_new_exec(): 기존 mm_struct를 교체할 새 mm을 준비한다
  2. exec_mmap(): 기존 주소 공간(old_mm)을 mmput()으로 해제하고 새 mm을 활성화한다
  3. setup_new_exec(): 프로세스 이름, 시그널 핸들러를 리셋한다
  4. ELF PT_LOAD 세그먼트마다 elf_map()으로 mmap 매핑을 설정한다
  5. setup_arg_pages(): 스택 VMA를 설정하고 argv/envp를 복사한다
  6. start_thread(): pt_regs에 새 RIP(e_entry), RSP를 넣어 유저 모드 복귀를 준비한다

Linux에서는 exec 실패 시 old_mm으로 롤백이 가능하지만, PintOS는 이 보호가 없다.

VM 모드 vs non-VM 모드의 순서 차이

단계VM 모드 (#ifdef VM)non-VM 모드
1process_cleanup() 먼저close_running_file() 먼저
2close_running_file()process_cleanup()
3supplemental_page_table_init()—

VM 모드에서 process_cleanup()이 먼저 오는 이유: supplemental_page_table_kill()이 process_cleanup() 안에서 호출되며, SPT 엔트리들이 file 참조를 가질 수 있다. SPT를 먼저 정리해야 file-backed page의 file 참조가 올바르게 정리된다.

load() 내부 흐름

load()는 process_exec()의 핵심이다:

  1. setup_process_address_space() — pml4_create()로 새 PML4를 생성하고, process_activate()로 CR3를 전환한다. 이 시점부터 새 페이지 테이블이 활성화된다.
  2. copy_command_line() — 명령줄을 palloc 페이지에 복사한다.
  3. parse_command_line() — 공백으로 분리하여 argv 배열을 만든다.
  4. open_executable() — ELF 파일을 열고 file_deny_write()를 호출한다.
  5. read_elf_header() — ELF64 매직 넘버를 확인한다.
  6. load_program_headers() — 각 PT_LOAD 세그먼트를 load_loadable_segment() → load_segment()로 처리한다.
  7. setup_initial_stack() — 유저 스택 페이지를 만들고 argv를 배치한다.
  8. _if.rip = ehdr.e_entry — 엔트리 포인트를 RIP에 설정한다.

QEMU 에뮬레이션

QEMU TCG 관점에서 exec은 CR3 전환이 핵심이다. process_activate() → pml4_activate() → lcr3()가 실행되면, QEMU는 guest의 CR3 레지스터를 갱신하고 TLB를 전면 flush한다.

%% QEMU TCG에서 보이는 exec 핵심 이벤트
flowchart TD
  cleanup["process_cleanup()<br/>pml4_destroy()<br/>기존 PML4 해제"]
  qemu_old["QEMU<br/>기존 guest 물리 페이지 해제<br/>관련 SoftMMU TLB 무효화"]
  create["pml4_create()<br/>새 PML4 할당"]
  qemu_ram["QEMU<br/>RAMBlock 안에 새 PML4 테이블 생성"]
  activate["pml4_activate()<br/>lcr3(new_pml4)"]
  load_segment["load_segment()<br/>VM: UNINIT 등록<br/>non-VM: PTE 설정"]
  iret["do_iret()<br/>iretq"]
  qemu_cr3["helper_write_crN(env, 3, new_value)<br/>env-&gt;cr[3] 갱신<br/>tlb_flush(cpu)<br/>새 PML4 사용"]
  qemu_iret["helper_iret_protected()<br/>RPL 0→3, CS/SS 재설정<br/>RIP = e_entry<br/>첫 TB 번역"]
  cleanup --> qemu_old
  qemu_old --> create
  create --> qemu_ram
  qemu_ram --> activate
  activate --> qemu_cr3
  qemu_cr3 --> load_segment
  load_segment --> iret
  iret --> qemu_iret

GDB 관찰 스크립트:

관찰 시나리오

시나리오 1: exec 전후 주소 공간 교체 추적

프로그램 A가 exec(“B”)를 호출할 때, PML4가 실제로 교체되는 과정을 단계별로 관찰한다.

# 1. exec 직전 — 프로그램 A의 상태
(gdb) p thread_current()->tid
$1 = 3
(gdb) p/x thread_current()->pml4
$2 = 0x800523c000              ← A의 PML4 (kernel VA)
(gdb) p/x $cr3
$3 = 0x123c000                 ← A의 PML4 (guest PA)

# 2. process_cleanup() 실행 후
(gdb) exec_spt_status
[SPT] tid=3, pages=0, buckets=0    ← SPT 비어있음
(gdb) p/x thread_current()->pml4
$4 = 0x0                       ← PML4 파괴됨

# 3. setup_process_address_space() 후
(gdb) p/x thread_current()->pml4
$5 = 0x8005240000              ← B의 새 PML4
(gdb) p/x $cr3
$6 = 0x1240000                 ← CR3 전환 완료, TLB flush됨

# 4. load 완료 후
(gdb) exec_spt_status
[SPT] tid=3, pages=7, buckets=16   ← B의 페이지들
(gdb) p/x if_->rip
$7 = 0x400c10                  ← B의 e_entry
(gdb) p/x if_->rsp
$8 = 0x47480000                ← USER_STACK (고정)

# tid=3은 변하지 않았다 — 같은 커널 스레드에서 유저 프로그램만 교체

시나리오 2: exec 실패 후 프로세스 종료 관찰

존재하지 않는 파일을 exec하면 process_cleanup()이 이미 기존 주소 공간을 파괴한 상태에서 load()가 실패하고, 돌아갈 곳이 없어 thread_exit()가 호출되는 과정을 관찰한다.

# exec("no-such-file") 실행
[exec] file=no-such-file, tid=3
[cleanup] destroying addr space for tid=3    ← 기존 주소 공간 파괴
load: no-such-file: open failed              ← 파일 없음
[exec-fail] load failed for tid=3
# → process_exec()이 -1 반환 → syscall_handler에서 thread_exit() 호출
# → 프로세스가 exit status -1로 종료
# → 부모의 wait()가 -1을 수거

# 핵심: Linux와 달리 PintOS는 point_of_no_return이 없다.
# process_cleanup()이 호출된 순간 이미 복귀 불가능.
