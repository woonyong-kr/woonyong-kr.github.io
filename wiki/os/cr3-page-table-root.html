CR3 — 페이지 테이블 루트

한 줄 요약: CR3는 현재 활성 페이지 테이블(PML4)의 물리 주소를 담아 MMU의 주소 변환이 시작되는 뿌리이며, 이 값을 바꾸면 프로세스의 주소 공간 전체가 통째로 교체된다.

CR3 상태

CR3(Control Register 3)는 x86/x86-64 CPU에서 현재 활성화된 페이지 테이블의 물리 주소를 가리키는 레지스터다. MMU가 가상 주소를 물리 주소로 변환할 때 CR3에서 시작해 4단계(PML4→PDPT→PD→PT) page table walk을 수행한다. 프로세스(주소 공간)를 전환할 때 OS는 CR3에 새 프로세스의 PML4 물리 주소를 기록하고, 이 순간 TLB가 flush되어 이전 매핑이 무효화된다.

상세 설명

추상 개념 (CPU 하드웨어 규칙)

CR3의 구조 (x86-64, 4-level paging, PCID 미사용)는 CPU가 보고한 물리 주소 폭 MAXPHYADDR에 따라 달라진다:

%% CR3 비트 구조
flowchart LR
  cr3["CR3<br/>bit MAXPHYADDR-1:12 = PML4 물리 주소<br/>bit 4 = PCD, bit 3 = PWT<br/>나머지 low bits와 MAXPHYADDR 이상은 reserved<br/>(PCID 비활성 기준)"]

핵심: CR3에는 물리 주소가 들어간다. 가상 주소가 아니다. MMU가 아직 변환을 시작하기 전에 페이지 테이블 자체를 찾아야 하므로, 페이지 테이블의 위치는 물리 주소로 지정해야 한다.

주소 필드를 고정된 51:12로 가정하면 안 된다. 유효한 상위 bit는 CPUID.80000008H:EAX[7:0]의 MAXPHYADDR로 결정되고, 그 이상 bit는 예약 영역이다. PCID를 활성화하면 low 12 bit는 PCID가 되고 bit 63에는 no-flush 의미가 추가되므로 이 그림과 별도 규칙을 적용한다.

PCID를 사용하지 않고 CR3를 쓰면 현재 address space의 비전역(non-global) TLB entry가 무효화된다. CR4.PGE=1인 경우 global mapping은 유지될 수 있으므로 “항상 TLB 전체 flush”라고 단정하면 안 된다. PCID를 사용하면 TLB entry를 address-space tag로 구분하고 no-flush 조건을 적용할 수 있지만, PintOS는 PCID를 사용하지 않는다.

실제 OS (Linux)

Linux는 컨텍스트 스위치 시 switch_mm_irqs_off()에서 CR3를 교체한다. PCID를 지원하는 CPU에서는 NOFLUSH 비트(bit 63)를 설정해 TLB flush를 건너뛰고, PCID 태그로 주소 공간을 구분한다.

Meltdown 취약점 완화(KPTI: Kernel Page Table Isolation)가 활성화되면, 유저 모드와 커널 모드에서 서로 다른 PML4를 사용한다. syscall/인터럽트 진입 시 CR3를 커널용 PML4로 교체하고, 복귀 시 다시 유저용 PML4로 교체한다. 이 때문에 CR3 변경이 syscall 경로에서도 발생한다.

PintOS에서 CR3 관련 코드는 세 곳에 집중되어 있다:

1. CR3 읽기/쓰기 인라인 함수 (include/intrinsic.h):

lcr3은 Load CR3, rcr3은 Read CR3의 약자다.

2. pml4_activate() (threads/mmu.c:221):

핵심: vtop()으로 PML4의 커널 가상 주소를 물리 주소로 변환한 뒤 CR3에 기록한다. CR3에는 물리 주소가 들어가야 하기 때문이다. pml4가 NULL이면 커널 기본 페이지 테이블(base_pml4)을 사용한다.

3. 호출 경로 — 스레드 전환 시:

프로세스 종료 시에도 CR3를 변경한다:

PML4를 destroy하기 전에 CR3를 다른 PML4로 전환해야 한다. 현재 활성 PML4를 해제하면 CPU가 유효하지 않은 페이지 테이블을 참조하게 되어 즉시 fault가 발생한다.

QEMU 에뮬레이션

QEMU TCG 모드에서 mov cr3, rax 명령은 helper_write_crN()을 호출한다. 이 헬퍼는 CPUX86State.cr[3]에 값을 저장하고, SoftTLB를 전부 flush한다. KVM 모드에서는 실제 CPU의 CR3가 VMCS(Virtual Machine Control Structure)를 통해 관리된다.

TCG에서 CR3 변경의 내부 동작:

  1. lcr3(val) → guest 명령어 movq val, %cr3
  2. QEMU TCG가 helper_write_crN(env, 3, val) 호출
  3. env->cr[3] = val 저장
  4. tlb_flush(cs) → SoftTLB 전체 엔트리 무효화
  5. 이후 VA 접근 시 SoftTLB miss → 새 PML4 기준으로 page table walk 재수행

SoftTLB flush는 실제 하드웨어의 TLB flush를 소프트웨어로 정확히 재현한다. 다만, 실제 CPU의 TLB flush는 수백 cycle이지만 QEMU SoftTLB flush는 해시 테이블 초기화이므로 비용 특성이 다르다.

GDB에서 CR3 전환 관찰법:

# 1. pml4_activate에 breakpoint
(gdb) b pml4_activate
(gdb) c

# 2. 현재 CR3 값 확인
(gdb) p/x $cr3            # QEMU GDB stub이 제공하는 CR3 레지스터

# 3. 인자로 들어온 새 PML4 확인
(gdb) p/x pml4            # 커널 VA
(gdb) p/x vtop(pml4)      # 물리 주소 — 이것이 CR3에 기록될 값

# 4. lcr3 실행 후 CR3 변경 확인
(gdb) n                    # lcr3(vtop(pml4)) 실행
(gdb) p/x $cr3            # 새 PML4의 물리 주소로 변경됨

# 5. 컨텍스트 스위치 시 연속 관찰
(gdb) b schedule
(gdb) c
(gdb) p next->pml4        # 다음 프로세스의 PML4
(gdb) c                    # pml4_activate까지 진행
(gdb) p/x $cr3            # 전환 확인

# 6. process_cleanup에서 base_pml4 복원 관찰
(gdb) b process_cleanup
(gdb) c
# pml4_activate(NULL) 호출 후
(gdb) p/x $cr3            # base_pml4의 물리 주소

CR3 값 추적

항목값
CR3 레지스터 번호3 (Control Register)
PML4 물리 주소 정렬4 KB (0x1000) 단위
CR3에서 주소 비트bit MAXPHYADDR-1:12; 폭은 CPUID가 보고한 물리 주소 폭에 따름
TLB 무효화 범위PCID 미사용 CR3 write는 비전역 entry 무효화; CR4.PGE=1이면 global entry 유지 가능
PCID 범위0~4095 (12비트), PintOS 미사용

예시: PML4가 커널 VA 0xFFFF_8000_0012_3000에 있을 때:

vtop(0xFFFF_8000_0012_3000) = 0x0012_3000  (KERN_BASE 빼기)
CR3 ← 0x0000_0000_0012_3000
     = bit 20:12 = 0x123, 나머지 = 0
