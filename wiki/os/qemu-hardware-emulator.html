QEMU 하드웨어 에뮬레이터

QEMU 하드웨어 에뮬레이터

확인 범위: 이 문서는 QEMU가 guest에 CPU·메모리·장치 I/O를 제공하는 일반 원리와 PintOS에서의 역할을 설명한다. 다만 제시된 내부 구조·코드 좌표·실행 옵션·수치·성능 평가는 특정 QEMU 및 PintOS 구현과 실행 환경에 따라 달라질 수 있는 항목으로, 실제 코드·버전·실행 기록·측정을 확인한 검증 결과로 보아서는 안 된다.

QEMU는 host 프로세스 안에서 CPU, 메모리, 장치 I/O를 흉내 내어 guest OS가 실제 PC 위에서 실행되는 것처럼 보이게 한다. PintOS 입장에서는 QEMU가 하드웨어다.

QEMU 하드웨어 에뮬레이터 구조

QEMU(Quick EMUlator)는 하드웨어 전체를 소프트웨어로 재현하는 에뮬레이터다. CPU 명령어 실행, 메모리 접근, 장치 I/O를 호스트 프로세스 안에서 시뮬레이션하여, OS가 실제 하드웨어 위에서 동작한다고 착각하게 만든다. PintOS 개발에서 QEMU는 x86-64 PC 환경 전체를 제공하는 역할을 한다.

상세 설명

추상 개념 (에뮬레이터의 위치)

에뮬레이터는 ISA(Instruction Set Architecture)의 계약을 소프트웨어로 이행한다. OS는 CPU가 mov, int, syscall 같은 명령어를 실행하고, 물리 메모리가 특정 주소에 존재하며, PIC·PIT·IDE 같은 장치가 I/O 포트에 응답한다고 가정한다. 에뮬레이터가 이 모든 가정을 만족시키면 OS 입장에서는 구별할 수 없다.

핵심 구분: QEMU는 OS가 아니다. 프로세스를 생성하지 않고, syscall 번호를 해석하지 않으며, 파일 시스템 정책을 관리하지 않는다. QEMU가 하는 일은 오직 하드웨어 동작의 재현이다.

QEMU가 하는 일

1. CPU 명령어 실행 (TCG)

  • TCG(Tiny Code Generator)가 guest x86-64 명령어를 호스트 네이티브 코드로 번역
  • Translation Block 단위로 캐싱하여 같은 코드의 재번역을 방지
  • guest의 모든 레지스터 상태를 CPUX86State 구조체에 보관

2. 메모리 에뮬레이션

  • RAMBlock으로 guest physical memory를 호스트 프로세스의 mmap 영역에 backing
  • guest physical address → host virtual address 변환을 내부적으로 수행
  • E820 memory map을 BIOS 인터페이스를 통해 guest에 제공

3. 장치 모델

  • i8254 PIT: 프로그래밍 가능한 타이머, IRQ0 생성 (PintOS의 timer_interrupt() 트리거)
  • i8259 PIC: 인터럽트 컨트롤러, IRQ → CPU 인터럽트 벡터 변환
  • IDE controller: 디스크 섹터 R/W를 호스트 파일 I/O로 변환
  • Serial port: 콘솔 입출력

4. GDB Stub

  • GDB 프로토콜로 guest CPU 상태(레지스터, 메모리)를 외부에 노출
  • info registers = guest CPU 레지스터, x/Nx addr = guest memory

실제 OS (Linux)에서 하드웨어와의 차이

Linux가 실제 x86-64 하드웨어에서 동작할 때와 QEMU 위에서 동작할 때의 차이:

페이지 테이블 walkMMU 하드웨어가 CR3부터 자동 탐색softmmu가 소프트웨어로 4단계 walk 수행

Linux KVM 모드에서는 VT-x/AMD-V 하드웨어 가상화를 사용하여 guest 명령어를 CPU가 직접 실행하므로 성능 차이가 거의 없다. PintOS는 TCG 모드로만 실행되므로 이 성능 차이가 존재하지만, 교육 목적에는 영향이 없다.

PintOS에서의 QEMU 사용

PintOS는 pintos 스크립트를 통해 QEMU를 다음과 같이 실행한다:

qemu-system-x86_64 -m 4 -hda os.dsk -hdb swap.dsk \
    -serial stdio -gdb tcp::1234 -S
  • -m 4: guest에 4 MB RAM 제공
  • -hda os.dsk: 첫 번째 IDE 디스크 = OS 디스크
  • -hdb swap.dsk: 두 번째 IDE 디스크 = swap 디스크
  • -serial stdio: 시리얼 포트를 호스트 터미널에 연결
  • -gdb tcp::1234: GDB stub 활성화
  • -S: 시작 시 정지 (GDB attach 대기)

TCG 번역 과정 상세

TCG(Tiny Code Generator)는 2단계 번역을 수행한다:

Translation Block(TB) 단위로 캐싱하며, TB의 경계는 분기 명령어(jmp, call, ret, syscall 등)에서 나뉜다.

flowchart LR
    A["guest code\n0x8004001000:\nmov eax, 1\nadd ebx, eax\njmp 0x8004001020"] --> B["TCG Frontend\n(target/i386)"]
    B --> C["TCG IR\nmovi_i64 tmp0, 1\nadd_i64 rbx, rbx, tmp0\n..."]
    C --> D["TCG Backend\n(host arch)"]
    D --> E["Host native code\n(cached in TB)"]
    E --> F["실행"]

TB 캐시 히트 시 재번역 없이 바로 실행되므로, 같은 코드를 반복 실행하는 루프(예: PintOS의 schedule() → thread_launch())는 거의 네이티브 속도에 근접한다.
