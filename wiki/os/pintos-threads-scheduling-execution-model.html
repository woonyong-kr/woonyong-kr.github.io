PintOS Threads와 Scheduling

PintOS Threads와 Scheduling

확인 범위: 이 문서는 선점 스케줄링의 일반 원리와 PintOS Threads에서의 구현 구조·선택 기준을 설명하는 개념 자료다. 제시된 코드 좌표, 상수, 실행 흐름과 GDB 출력은 특정 코드 버전의 실제 실행이나 성능을 검증한 결과가 아니므로, 구현별 판단에는 해당 소스와 버전, 테스트 실행 기록 및 성능 측정이 별도로 필요하다.

PintOS의 스레드는 하나의 CPU를 아주 짧은 시간 단위로 나눠 쓴다. 타이머 인터럽트가 실행을 끊고, 스케줄러가 다음 스레드를 고르기 때문에 여러 프로그램이 동시에 도는 것처럼 보인다.

PintOS Threads와 차이

CPU가 한 번에 하나의 명령어만 실행한다면, 왜 여러 프로그램이 동시에 도는 것처럼 보일까? 답은 타이머 인터럽트와 프리엠프티브 스케줄링이다. 하드웨어 타이머(PIT)가 주기적으로 CPU를 멈추게 만들고, 커널이 다음에 실행할 스레드를 고른다. PintOS의 Threads 프로젝트는 이 메커니즘을 alarm clock, priority scheduling, priority donation, MLFQS 네 단계로 구현한다.

상세 설명

추상 개념 (하드웨어가 제공하는 것)

선점 스케줄링이 가능하려면 하드웨어가 두 가지를 제공해야 한다:

하드웨어역할x86-64 구현
타이머일정 간격으로 인터럽트 발생PIT(8254) → IRQ0 → IDT 0x20
문맥 저장/복원실행 상태를 저장하고 다른 상태로 교체레지스터 push/pop + iretq

소프트웨어(OS)가 결정하는 것은 “누구를 다음에 실행할 것인가”(정책)다.

실제 OS (Linux)에서의 스케줄링

Linux의 CFS(Completely Fair Scheduler)는 vruntime(가상 실행 시간)으로 공정성을 유지한다. 레드-블랙 트리에서 vruntime이 가장 작은 태스크를 다음에 실행한다.

Timer Sleep (Alarm Clock)

busy-wait 대 sleep list 비교:

방식CPU 사용코드
busy-wait (원본)잠자는 동안 100% 점유while (timer_elapsed(start) < ticks) thread_yield()
sleep list (구현)잠자는 동안 0%thread_sleep(start + ticks) → BLOCKED

올바른 구현 흐름:

%% timer_sleep()와 timer_interrupt() 흐름
flowchart LR
  sleep1["wake_tick = timer_ticks() + ticks<br/>절대 시각 계산"]
  sleep2["인터럽트 OFF"]
  sleep4["sleep_list 삽입<br/>wake_tick 오름차순"]
  sleep6["인터럽트 복원"]
  sleep3["current->wake_tick = wake_tick"]
  sleep5["thread_block()<br/>RUNNING → BLOCKED"]
  irq1["ticks++"]
  irq2["thread_tick()<br/>TIME_SLICE 검사"]
  irq3["thread_awake(ticks)<br/>sleep_list 순회"]
  irq4["wake_tick &lt;= ticks<br/>thread_unblock()"]
  sleep1 --> sleep2
  sleep2 --> sleep3
  sleep3 --> sleep4
  sleep4 --> sleep5
  sleep5 --> sleep6
  irq1 --> irq2
  irq2 --> irq3
  irq3 --> irq4

숫자 예: timer_sleep(50) 호출 시점이 tick 1000이면 wake_tick = 1050. 이후 50번의 타이머 인터럽트(500 ms) 후에 깨어난다.

Priority Scheduling

우선순위 범위: PRI_MIN = 0 ~ PRI_MAX = 63. 기본값 PRI_DEFAULT = 31.

우선순위가 반영되어야 하는 곳 4곳:

위치자료구조정렬 기준
ready_liststruct listpriority 내림차순
sema->waitersstruct listpriority 내림차순
cond->waitersstruct list (of semaphore_elem)waiter의 priority 내림차순
donation_liststruct listpriority 내림차순

선점이 발생하는 두 지점:

  1. thread_create(): 새 스레드 priority > 현재 스레드 → thread_yield()
  2. thread_unblock(): 깨어난 스레드 priority > 현재 스레드 → intr_yield_on_return()

Priority Donation

우선순위 역전 시나리오:

%% Priority Donation 타임라인
flowchart LR
  h_wait["H(63)<br/>lock_acquire() 대기"]
  m_run["M(62)<br/>CPU 독점 가능"]
  l_hold["L(61)<br/>lock 보유"]
  inversion["우선순위 역전<br/>H가 L을 기다리지만<br/>M이 L보다 먼저 실행"]
  donate["H(63)의 우선순위를<br/>L에게 기부"]
  h_run["H(63)<br/>lock 획득 후 실행"]
  l_run["L(61→63)<br/>기부받아 실행"]
  release["lock_release()<br/>L: 63→61"]
  h_wait --> inversion
  m_run --> inversion
  l_hold --> inversion
  inversion --> donate
  donate --> l_run
  l_run --> release
  release --> h_run

문제: H가 L의 lock을 기다리지만, M이 L보다 높아 L이 실행되지 못한다. H는 무한히 대기한다 (unbounded priority inversion).

해결: H(63)의 우선순위를 L에게 기부한다. L은 61에서 63으로 올라가 실행 기회를 얻고, lock_release() 뒤에는 61로 돌아간다. 그다음 H가 lock을 획득해 실행된다.

중첩 기부 전파: A(63)→B(50)→C(40) 체인에서 A가 B의 lock을 기다리고 B가 C의 lock을 기다리면, C는 63을 받아야 한다. waiting_lock 포인터를 따라 체인을 순회하며 전파한다.

필드용도
priority현재 유효 우선순위 (기부 반영)
base_priority기부 전 원래 우선순위
donation_list나에게 기부한 스레드 목록
donation_elem다른 스레드의 donation_list에 들어가는 원소
waiting_lock현재 기다리는 lock (전파 체인용)

MLFQS (Multi-Level Feedback Queue Scheduler)

고정 우선순위 대신 실행 이력에서 우선순위를 계산한다:

priority = PRI_MAX - (recent_cpu / 4) - (nice × 2)
recent_cpu = (2 × load_avg) / (2 × load_avg + 1) × recent_cpu + nice
load_avg = (59/60) × load_avg + (1/60) × ready_threads

%% MLFQS 계산 모델
flowchart LR
  ready["ready_threads"]
  load["load_avg<br/>(59/60) * load_avg<br/>+ (1/60) * ready_threads"]
  nice["nice"]
  recent["recent_cpu<br/>(2 * load_avg) / (2 * load_avg + 1)<br/>* recent_cpu + nice"]
  priority["priority<br/>PRI_MAX - recent_cpu / 4 - nice * 2"]
  fixed["17.14 고정소수점<br/>f = 1 &lt;&lt; 14 = 16384"]
  ready -->|매초| load
  load -->|매초 전체 재계산| recent
  nice --> recent
  recent -->|매 4 tick| priority
  nice --> priority
  fixed -. 계산 단위 .-> load
  fixed -. 계산 단위 .-> recent

갱신 주기:

값갱신 시점주기
recent_cpu (실행 스레드)매 tick10 ms
recent_cpu (전체 재계산)매 초 (100 tick)1 s
load_avg매 초 (100 tick)1 s
priority (전체)매 4 tick40 ms

17.14 고정소수점: 정수부 17비트 + 소수부 14비트. f = 1 << 14 = 16384. 곱셈 시 x * y / f, 나눗셈 시 x * f / y.

QEMU 에뮬레이션

QEMU는 PIT(8254)를 소프트웨어로 모델링한다:

%% QEMU PIT에서 PintOS timer_interrupt()까지
flowchart LR
  pit["hw/timer/i8254.c<br/>pit_irq_timer_update()"]
  irq0["100 Hz마다<br/>가상 IRQ0 생성"]
  pic["i8259 PIC 모델"]
  idt["IDT 0x20 디스패치"]
  interrupt["timer_interrupt() 진입"]
  ticks["ticks++"]
  thread_tick["thread_tick()"]
  awake["thread_awake()"]
  pit --> irq0
  irq0 --> pic
  pic --> idt
  idt -->|guest 인터럽트 전달| interrupt
  interrupt --> ticks
  ticks --> thread_tick
  thread_tick --> awake

QEMU가 하는 일은 “10 ms마다 IRQ0 신호를 만드는 것”뿐이다. 그 인터럽트를 받아서 스케줄링 결정을 하는 것은 PintOS의 일이다.

GDB로 확인:

(gdb) b timer_interrupt
(gdb) c
→ 매 tick마다 멈춤. info registers로 RSP가 커널 주소인지 확인.
(gdb) p ticks
$1 = 1042          ← 현재 tick
(gdb) p thread_ticks
$2 = 2             ← 현재 스레드가 이번 time slice에서 실행한 tick 수
                      4에 도달하면 선점 (TIME_SLICE = 4 → 40 ms)

선점 타이밍 계산: 스레드 A가 tick 1000에 실행 시작 → thread_ticks = 0. tick 1003에서 thread_ticks = 3. tick 1004에서 ++thread_ticks = 4 >= TIME_SLICE → intr_yield_on_return() → A는 READY로 전이.

디버깅 기준

스케줄링 버그는 대개 값 하나보다 순서에서 나온다:

  • 인터럽트를 끈 구간이 너무 길거나 복원을 빠뜨렸는가?
  • sleeping list에서 깨우는 조건이 off-by-one인가? (<= vs <)
  • ready_list가 항상 우선순위 내림차순을 유지하는가?
  • 락/세마포어 대기 큐에서도 우선순위가 반영되는가?
  • donation이 중첩될 때 원래 우선순위(base_priority) 복원이 맞는가?
  • lock_release() 후 donation_list에서 제거하고 유효 우선순위를 재계산했는가?

테스트 하나를 고르고 printf("tick=%lld, cur=%s(%d), ready=...", ticks, ...) 로 tick, current thread, ready list를 출력하면 훨씬 잘 보인다.
