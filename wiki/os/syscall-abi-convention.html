시스템콜 ABI Convention (Syscall ABI Convention)

시스템콜 ABI Convention (Syscall ABI Convention)

유저 프로그램과 커널은 서로 다른 권한에서 실행되지만, 요청 값은 같은 CPU 레지스터를 통해 주고받는다. x86-64 syscall ABI는 syscall 번호와 인자를 어느 레지스터에 담을지 정한 약속이다.

시스템콜 인자는 어디에서 찾는가

유저 프로그램이 write(fd, buf, size)를 호출하면 커널은 fd, buf, size의 값을 찾아야 한다. 그러나 syscall 명령어는 커널 진입점으로 실행 흐름을 옮길 뿐, 각 값의 위치까지 알려 주지는 않는다. 이 위치를 정하는 규칙이 syscall ABI다.

유저 코드는 RAX에 syscall 번호를 넣고 RDI부터 R9까지 정해진 레지스터에 인자를 배치한다. 커널은 진입 시 이 값을 struct intr_frame에 저장한 뒤, RAX를 기준으로 syscall을 선택하고 각 인자를 꺼낸다. 처리 결과는 다시 RAX에 담아 유저 코드에 돌려준다.

CPU 명령어와 소프트웨어 규약의 경계

syscall 명령어가 바꾸는 값

syscall 명령어 자체는 syscall 번호나 인자의 전달 위치를 강제하지 않는다. 하드웨어가 수행하는 기본 동작은 다음과 같다.

  1. RCX ← RIP (복귀 주소 저장)
  2. R11 ← RFLAGS (플래그 저장)
  3. RIP ← LSTAR MSR 값 (커널 진입점으로 점프)

어떤 레지스터를 syscall 번호와 인자에 사용할지는 OS와 libc가 합의한 소프트웨어 규약이다. Linux와 PintOS는 모두 System V AMD64 ABI를 바탕으로 하지만, 일반 함수 호출 ABI와 달리 네 번째 인자를 RCX가 아닌 R10에 넣는다. syscall 명령어가 RCX를 복귀 주소로 덮어쓰기 때문이다.

syscall ABI 레지스터 매핑

Linux와 PintOS의 구현

Linux

Linux도 같은 레지스터 규약을 사용한다. glibc의 syscall() wrapper는 유저 함수에서 RCX로 받은 네 번째 인자를 R10으로 옮긴 뒤 syscall 명령어를 실행한다. 커널은 entry_SYSCALL_64에서 레지스터를 pt_regs 구조체에 저장하고, sys_call_table[rax]를 통해 핸들러를 호출한다. 오류가 발생하면 음수 errno를 RAX에 넣어 반환한다.

PintOS 유저 코드

PintOS의 lib/user/syscall.c에 있는 syscall wrapper는 인라인 어셈블리로 각 값을 해당 레지스터에 직접 배치한다.

호출부에서는 편의 매크로를 사용해 인자 수에 맞는 wrapper를 선택한다.

예를 들어 write(fd, buf, size)는 syscall3(SYS_WRITE, fd, buf, size)로 바뀐다. 이때 RAX=SYS_WRITE(10), RDI=fd, RSI=buf, RDX=size로 배치된다.

PintOS 커널 코드

커널의 userprog/syscall.c에 있는 핸들러는 struct intr_frame에서 syscall 번호와 인자를 읽는다.

핸들러가 반환값을 f->R.rax에 쓰면 do_iret()이 RAX를 복원해 유저 프로그램에 전달한다. 따라서 RAX는 진입할 때 syscall 번호를 담고, 복귀할 때 처리 결과를 담는다.

호출별 레지스터 값 추적

syscall 예시RAXRDIRSIRDXR10
exit(0)1 (SYS_EXIT)0———
write(1, buf, 13)10 (SYS_WRITE)1buf 주소13—

PintOS의 syscall 번호는 include/lib/syscall-nr.h에 정의되어 있다.

  • SYS_HALT=0, SYS_EXIT=1, SYS_FORK=2, SYS_EXEC=3, …
  • SYS_READ=8, SYS_WRITE=10, SYS_MMAP=13, SYS_MUNMAP=14

write(1, buf, 13)이 호출되어 반환될 때까지의 값 이동은 다음 순서로 볼 수 있다.

QEMU가 재현하는 범위

QEMU도 syscall ABI 자체를 강제하지 않는다. QEMU가 담당하는 것은 CPU 명령어 수준의 동작이다.

  1. syscall 명령어 에뮬레이션: TCG가 syscall opcode를 만나면 helper_syscall()을 호출한다. 이 함수는 다음 하드웨어 동작을 재현한다.
    • env->regs[R_ECX] = env->eip (RCX ← RIP)
    • env->regs[11] = env->eflags (R11 ← RFLAGS)
    • env->eip = env->lstar (RIP ← LSTAR)
    • env->eflags &= ~env->fmask (FMASK로 플래그 마스킹)
  2. 레지스터 값 전달: RAX, RDI, RSI, RDX, R10 등의 값은 QEMU의 CPUX86State.regs[] 배열에 그대로 보존된다. GuestOS가 이 값을 어떻게 해석하는지는 QEMU의 역할이 아니다.
  3. sysretq 에뮬레이션: helper_sysret()이 RCX→RIP, R11→RFLAGS 복원을 수행한다. RAX의 반환값도 그대로 유지된다.

따라서 QEMU는 RAX가 syscall 번호라는 사실을 해석하지 않는다. CPU 명령어에 따른 레지스터 변화를 에뮬레이션하고, ABI에 따른 의미 부여는 GuestOS에 맡긴다.

관찰 시나리오

write(1, "Hello", 5)의 레지스터 왕복

args-single 테스트에서 유저 프로세스가 write(1, buf, 5)를 호출한다고 두고, RAX=10, RDI=1, RSI=buf주소, RDX=5가 intr_frame에 전달되는지 확인한다. 반환 단계에서는 쓴 바이트 수 5가 RAX에 담기는지를 관찰한다.

이 시나리오의 기대 결과는 진입 시 레지스터가 ABI 규약대로 배치되고, 복귀 시 RAX에 실제로 쓴 바이트 수 5가 담기는 것이다.

fork("child")의 부모·자식 반환값

fork-once 테스트에서는 RAX=2(SYS_FORK), RDI=“child” 주소로 진입하는지 확인한다. 같은 fork syscall에서 부모의 RAX에는 자식 pid가, 자식의 RAX에는 0이 반환되어야 한다.

이 시나리오에서는 __do_fork가 자식의 intr_frame.R.rax를 0으로 설정하는지 살펴보면 부모와 자식의 반환 경로를 구분할 수 있다.

두 구현은 번호, 인자, 반환값에 사용하는 기본 레지스터가 같다. 차이는 오류 전달 방식, syscall의 범위, 커널 분기 구조, vDSO 최적화처럼 각 OS가 ABI 위에서 선택한 구현에 있다.
