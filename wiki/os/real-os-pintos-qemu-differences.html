실제 OS, PintOS, QEMU의 차이

실제 OS, PintOS, QEMU의 차이

확인 범위: 이 문서는 실제 OS·PintOS·QEMU가 syscall, page fault, interrupt, disk I/O에서 맡는 역할과 이를 구분하는 일반 기준을 설명한다. 제시된 함수·파일 경로와 값 흐름은 특정 PintOS·QEMU 구현을 전제로 한 코드 좌표와 확인 방법이며, 실제 동작 여부나 버전별 차이·성능은 해당 소스와 실행 기록을 별도로 검증해야 한다.

한 줄 요약: 같은 write(1,“hi”,2) 한 줄도 실제 OS·PintOS·QEMU에서 거치는 경로가 다르며, 이 문서는 어디까지가 유저 코드·커널·에뮬레이터의 몫인지 그 경계를 갈라 설명한다.

실제 OS, PintOS, QEMU의 차이 시작

PintOS에서 유저 프로그램이 다음 코드를 실행한다고 하자.

초보자가 가장 많이 헷갈리는 질문은 이것이다.

이 write를 Linux가 처리할까, PintOS가 처리할까, QEMU가 처리할까?

정답은 실행 환경에 따라 다르다.

  • Linux 위에서 일반 프로그램으로 실행하면 Linux 커널이 처리한다.
  • Windows 위에서 Win32 API를 호출하면 Windows 커널 계층이 처리한다.
  • PintOS 유저 프로그램으로 실행하면 **PintOS 커널의 syscall_handler()**가 처리한다.
  • QEMU는 write의 뜻을 처리하지 않는다. QEMU는 PintOS가 실행될 CPU, 메모리, 인터럽트, 디스크처럼 보이는 환경을 제공한다.

이 문서의 목표는 세 층을 분리해서 보는 기준을 만드는 것이다.

실제 OS, PintOS, QEMU의 차이 필요성

OS 공부에서 가장 위험한 오류는 역할을 섞는 것이다.

예를 들어 “QEMU가 syscall을 처리한다”고 생각하면, syscall_handler()를 고쳐야 할 문제를 QEMU 소스에서 찾게 된다. 반대로 “PintOS가 디스크 하드웨어를 직접 가진다”고 생각하면, disk_write() 뒤에 왜 QEMU IDE 모델과 block backend가 나오는지 이해하기 어렵다.

역할을 분리하면 디버깅 방향도 분명해진다.

현상먼저 볼 층이유
SYS_WRITE가 잘못 처리됨PintOS syscall 코드syscall 번호와 fd 정책은 guest OS가 해석
page fault가 죽어야 하는지 살아야 하는지 애매함PintOS VM 코드SPT, stack growth, permission 정책은 guest OS 판단
GDB info registers가 기대와 다름QEMU GDB stub + PintOS snapshot현재 guest register와 저장된 struct intr_frame을 구분해야 함
disk sector write 위치가 궁금함PintOS disk 코드 + QEMU IDE/block 코드sector 의미는 PintOS에서 나오고 host 파일 offset 변환은 QEMU가 수행

실제 운영체제

Linux와 Windows는 실제 운영체제다.

Linux에서는 유저 프로그램이 libc wrapper나 직접 syscall ABI를 통해 커널에 들어가고, Linux 커널이 fd table, VFS, page table, scheduler, driver를 연결한다. write(1, buf, 5)에서 fd 1이 어떤 열린 파일 객체를 가리키는지 판단하는 주체는 Linux 커널이다.

Windows는 POSIX fd보다 handle과 Win32 API가 더 앞에 보인다. 예를 들어 파일이나 콘솔은 handle로 다루고, 내부적으로 object manager, I/O manager, memory manager 같은 더 큰 구조가 관여한다.

실제 OS가 PintOS보다 복잡한 이유는 단순히 코드가 많아서가 아니다.

  • 여러 CPU와 동시 실행을 다룬다.
  • 권한, 보안, 격리, 감사 정책을 다룬다.
  • 다양한 장치와 드라이버를 지원한다.
  • page cache, copy-on-write, NUMA, huge page, lazy allocation 같은 최적화를 다룬다.
  • 수십 년 동안 쌓인 ABI와 호환성을 유지한다.

PintOS는 이런 현실 OS를 그대로 복제하지 않는다. 대신 학습에 필요한 핵심 질문을 작게 만든다.

PintOS

PintOS는 guest OS다. QEMU 위에서 실행되지만, PintOS 입장에서는 자신이 하드웨어 위에서 직접 실행된다고 믿는다.

PintOS가 직접 결정하는 대표 정책은 다음과 같다.

질문PintOS가 보는 코드
syscall 번호를 어떻게 처리할까?pintos/userprog/syscall.c의 syscall_handler()
syscall 진입 때 user register를 어디에 저장할까?pintos/userprog/syscall-entry.S의 struct intr_frame 구성
page fault를 살릴까 죽일까?pintos/userprog/exception.c의 page_fault()와 vm_try_handle_fault()
timer interrupt 뒤 어떤 thread를 실행할까?pintos/devices/timer.c, pintos/threads/thread.c
user VA와 frame을 어떻게 연결할까?pintos/threads/mmu.c의 pml4_set_page()

중요한 점은 PintOS가 교육용으로 단순화되어 있다는 것이다.

  • 실제 Linux/Windows scheduler처럼 CPU별 run queue와 복잡한 fairness 정책을 모두 구현하지 않는다.
  • 실제 VM처럼 모든 mmap flag, COW, page cache 정책을 다루지 않는다.
  • 실제 파일 시스템처럼 journaling, 권한, crash recovery를 모두 다루지 않는다.

그래도 PintOS는 “OS가 무엇을 결정해야 하는가”를 보기 좋게 보여준다. syscall, page fault, scheduling, file descriptor 같은 핵심 판단이 작은 함수 안에 드러나기 때문이다.

QEMU

QEMU는 host OS 위에서 실행되는 process이고, 그 안에서 PintOS guest machine을 돌린다. 하지만 PintOS 안에서는 QEMU가 보이지 않는다. PintOS는 CPU, RAM, interrupt controller, timer, disk가 있다고 믿고 실행된다.

QEMU가 하는 일은 다음에 가깝다.

QEMU가 제공하는 것PintOS가 믿는 것
CPUX86State 같은 guest CPU state실제 x86 CPU register
QEMU process 안의 RAMBlock/memory region물리 메모리
PIT/PIC/APIC 같은 device model타이머와 interrupt controller
IDE/block backend디스크
GDB stub하드웨어 디버깅 포트처럼 보이는 remote debug 대상

QEMU가 하지 않는 일도 분명히 잡아야 한다.

  • SYS_WRITE가 stdout인지 판단하지 않는다.
  • fd table을 관리하지 않는다.
  • PintOS thread priority를 해석하지 않는다.
  • supplemental page table이 합법인지 판단하지 않는다.
  • PintOS 테스트의 성공/실패 의미를 모른다.

QEMU는 guest instruction과 guest device interaction을 재현한다. 그 위에서 어떤 OS 정책을 구현할지는 PintOS 코드의 일이다.

실제 OS, PintOS, QEMU의 차이 코드

1. PintOS는 syscall 진입 주소를 CPU MSR에 등록한다

근거 파일:

  • SW_AI-W11-pintos/pintos/userprog/syscall.c
  • SW_AI-W11-pintos/pintos/userprog/syscall-entry.S

핵심 흐름:

여기서 PintOS는 MSR_LSTAR에 syscall_entry 주소를 써 둔다. QEMU가 x86 syscall instruction을 재현하면 guest RIP는 이 주소로 이동하고, 그 다음부터는 PintOS 코드가 실행된다.

2. PintOS syscall_handler가 syscall 번호를 해석한다

근거 파일:

  • SW_AI-W11-pintos/pintos/userprog/syscall.c
  • SW_AI-W11-pintos/pintos/include/lib/syscall-nr.h

핵심 코드 모양:

f->R.rax는 handler 진입 직후에는 syscall 번호이고, handler 반환 직전에는 user program에 돌려줄 반환값이 된다. 이 의미 전환은 PintOS 정책이다. QEMU는 이 값을 SYS_WRITE라고 해석하지 않는다.

3. QEMU는 syscall instruction의 CPU 효과를 재현한다

근거 파일:

  • target/i386/tcg/emit.c.inc
  • target/i386/tcg/system/seg_helper.c

핵심 흐름:

이것이 QEMU의 역할이다. RIP = LSTAR가 된 뒤 LSTAR에 들어 있던 주소가 PintOS syscall_entry라면, 그 다음 의미 해석은 PintOS가 한다.

4. Page fault는 PintOS가 fault address와 error code를 읽어 판단한다

근거 파일:

  • SW_AI-W11-pintos/pintos/userprog/exception.c

핵심 흐름:

QEMU는 CPU 예외가 발생하는 조건과 guest state 변화를 재현할 수 있다. 하지만 “이 fault를 stack growth로 살릴지, invalid access로 죽일지”는 PintOS VM 정책이다.

5. Timer interrupt는 QEMU 장치 모델과 PintOS handler가 만나는 지점이다

근거 파일:

  • SW_AI-W11-pintos/pintos/devices/timer.c
  • hw/timer/i8254.c

핵심 흐름:

QEMU가 virtual timer output을 만든다. PintOS는 그 interrupt를 받아 OS 정책으로 바꾼다.

6. Disk sector write는 PintOS 의미에서 QEMU byte offset으로 내려간다

근거 파일:

  • hw/ide/core.c
  • block/block-backend.c
  • include/block/block-common.h

핵심 흐름:

PintOS 입장에서는 sector 번호를 쓰지만, QEMU block backend로 내려가면 sector_num << 9가 byte offset이 된다. BDRV_SECTOR_BITS = 9이면 한 sector는 2^9 = 512 bytes다.

예제 2. 0x8048123 주소 분해

PintOS VM은 보통 page base 단위로 page table/SPT를 본다. QEMU는 이 guest virtual access가 실제로 실행될 때 guest CPU의 주소 변환과 guest memory access를 재현한다.

예제 3. disk sector 24

PintOS가 “sector 24에 쓴다”고 말하면, QEMU block backend 쪽에서는 host 파일 또는 block backend의 byte offset 0x3000 근처로 내려간다. 단, PintOS가 host filesystem을 직접 호출하는 것은 아니다.

실제 OS, PintOS, QEMU의 차이 GDB

1. syscall 층 확인

PintOS GDB에서 syscall_handler에 멈춘다.

확인할 것:

  • f->R.rax가 SYS_WRITE 같은 syscall 번호인지
  • f->R.rdi/rsi/rdx가 유저 wrapper가 넣은 인자인지
  • info registers의 현재 register와 f->R.* snapshot을 섞고 있지 않은지

2. page fault 층 확인

확인할 것:

  • fault address는 CR2에서 온다.
  • fault를 살릴지 죽일지는 PintOS vm_try_handle_fault() 판단이다.
  • QEMU가 “이 주소는 stack growth다”라고 판단하는 것이 아니다.

3. QEMU GDB stub 층 확인

확인할 것:

  • 이 register는 host CPU register가 아니라 guest CPU state다.
  • x/16xb는 PintOS symbol/debug info와 QEMU guest memory read가 합쳐져 보이는 결과다.
  • host QEMU process 자체를 보려면 별도의 host debugger로 QEMU process에 붙어야 한다.

정리

  • Linux / Windows는 실제 운영체제다. syscall, VM, scheduler, driver를 실제 사용자와 장치 요구에 맞게 처리한다.
  • PintOS는 교육용 guest OS다. 실제 OS의 핵심 질문을 작은 코드와 자료구조로 보여준다.
  • QEMU는 OS가 아니다. PintOS가 하드웨어라고 믿는 CPU, 메모리, interrupt, disk, GDB stub을 제공한다.
  • syscall 번호, fd table, page fault 정책, scheduler 선택은 PintOS가 해석한다.
  • guest register, guest memory, virtual timer, IDE sector write 같은 하드웨어 효과는 QEMU가 재현한다.
