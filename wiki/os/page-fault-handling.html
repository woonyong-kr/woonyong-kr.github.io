페이지 폴트

페이지 폴트

한 줄 요약: Page fault(#PF, 벡터 14)는 MMU가 가상 주소를 변환하지 못할 때 나는 예외지만, 오류가 아니라 demand paging·lazy loading·stack growth·COW가 의도적으로 일으켜 OS가 처리하는 정상 경로다.

페이지 폴트 상태

Page fault는 CPU가 메모리에 접근했을 때 MMU가 해당 가상 주소를 물리 주소로 변환하지 못하면 발생하는 예외(#PF, 벡터 14)다. “오류”라는 이름과 달리, 현대 OS에서 page fault는 정상적인 동작 경로다. demand paging, lazy loading, stack growth, copy-on-write 모두 의도적으로 page fault를 발생시킨 뒤 OS가 처리하는 방식으로 구현된다.

page fault가 없으면 프로그램 실행 전에 모든 메모리를 미리 물리 프레임에 매핑해야 하므로, 메모리 낭비가 심하고 프로그램 시작 시간이 길어진다. page fault 덕분에 OS는 “실제로 접근하는 페이지만, 접근하는 시점에” 물리 메모리를 할당할 수 있다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

CPU가 가상 주소 VA에 접근하면 MMU가 page table walk를 수행한다(x86 64 페이지 테이블 워크). 이 과정에서 다음 중 하나라도 해당하면 pf 예외가 발생한다.

  1. Present bit = 0: 해당 PTE가 물리 프레임을 가리키지 않음
  2. 권한 위반: user mode에서 supervisor page 접근, 또는 read-only page에 write 시도
  3. Reserved bit 위반: PTE의 reserved bit가 설정된 경우

pf 발생 시 CPU는 다음을 수행한다.

1. fault를 일으킨 명령어의 실행을 중단 (RIP는 해당 명령어를 계속 가리킴)
2. error code를 스택에 push
3. CR2 ← fault 발생 가상 주소
4. IDT[14]로 점프 → OS의 page_fault handler

error code 3비트의 의미(페이지 폴트 error code에서 상세 설명):

비트이름0일 때1일 때
bit 0PF_Pnot-present faultprotection violation
bit 1PF_Wread 접근write 접근
bit 2PF_Ukernel modeuser mode

핵심: CPU는 RIP를 fault 명령어에 놓아둔다. 따라서 OS가 page를 준비한 후 handler에서 복귀하면, CPU는 같은 명령어를 처음부터 다시 실행한다(페이지 폴트 후 왜 같은 명령어를 다시 실행하나). 이번에는 MMU가 유효한 매핑을 찾으므로 정상 진행된다.

실제 OS (Linux/Windows)

Linux의 page fault 처리 흐름:

do_page_fault()
  → find_vma(mm, address)      // 해당 주소가 속한 VMA 검색
  → VMA 없음 → SIGSEGV (segfault)
  → VMA 있음 → handle_mm_fault()
    → 권한 검사 (read/write/exec)
    → __do_fault() 또는 do_anonymous_page()
    → 물리 프레임 할당 + PTE 설정
    → handler 복귀 → 같은 명령어 재실행

Linux의 VMA(Virtual Memory Area)는 PintOS의 SPT(Supplemental Page Table)와 유사한 역할을 한다. 둘 다 “이 가상 주소 범위는 합법적이며, 어떤 종류의 페이지인가”를 기록한다.

Windows의 page fault 처리:

KiPageFault()
  → MmAccessFault()
    → VAD(Virtual Address Descriptor) 검색
    → 없으면 → STATUS_ACCESS_VIOLATION
    → 있으면 → MiResolveProtoPteFault() 등
    → 물리 프레임 할당 + PTE 설정
개념LinuxWindowsPintOS
주소 범위 기록VMA (vm_area_struct)VAD (MMVAD)SPT (struct page)
fault handler 진입점do_page_fault()KiPageFault()page_fault()
합법성 판단find_vma()VAD 검색spt_find_page()

PintOS 구현

PintOS의 page fault 처리는 두 단계로 나뉜다.

1단계: page_fault() — CPU 예외 핸들러 (파일: userprog/exception.c)

IDT[14]에 등록된 핸들러. intr_frame에서 error code를 해석하고, fault 주소를 CR2에서 읽는다.

Project 3(VM) 이전에는 모든 page fault가 프로세스 종료로 이어진다. VM 구현 후에는 vm_try_handle_fault()에게 복구 기회를 준다.

2단계: vm_try_handle_fault() — VM 서브시스템 판단 (파일: vm/vm.c)

이 함수가 page fault 처리의 핵심 분기점이다(vm try handle fault 판단 흐름 Trace에서 분기별 상세 trace).

page fault가 정상 처리되는 경우의 구체적 예:

lazy-loaded code page에 처음 접근할 때:

  1. load_segment()가 vm_alloc_page_with_initializer()로 UNINIT page를 SPT에 등록
  2. 프로그램이 해당 코드 주소를 실행하려고 할 때 pf 발생
  3. vm_try_handle_fault() → vm_do_claim_page() → uninit_initialize() → 디스크에서 실제 바이트 읽기
  4. PTE 설정 후 복귀 → CPU가 같은 RIP에서 다시 fetch → 이번에는 성공

QEMU 에뮬레이션

QEMU는 guest CPU의 page fault를 두 가지 방식으로 처리한다.

TCG 모드: QEMU의 softmmu가 guest 가상 주소 → guest 물리 주소 변환을 수행한다. guest PTE의 present bit가 0이면, QEMU는 guest CPU state에 pf를 주입한다.

guest memory access
  → QEMU softmmu: guest page table walk
  → present bit = 0
  → env->error_code 설정
  → env->cr[2] = fault_addr
  → env->eip = guest IDT[14] handler 주소
  → guest OS의 page_fault() 실행

KVM 모드: guest가 EPT/NPT violation을 일으키면 VM exit가 발생하고, KVM이 host에서 처리하거나 guest에 pf를 inject한다.

QEMU의 핵심 관여 지점:

QEMU 행위실제 CPU 대응
softmmu guest PTE walkMMU 하드웨어
env->cr[2] 설정CR2 레지스터
guest IDT 참조CPU IDT lookup
QEMU TLB (CPUTLBEntry)하드웨어 TLB

QEMU는 자체 소프트웨어 TLB(CPUTLBEntry)를 유지한다. guest OS가 PTE를 바꾸면 QEMU TLB도 flush해야 한다. CR3 교체 시 QEMU는 tlb_flush()를 호출한다(TLB와 CR3 주소 공간 전환).

페이지 폴트 값 추적

page fault 한 건에서 CPU가 저장하는 데이터:

error code:     8 bytes (스택에 push)
CR2 (fault VA): 8 bytes (레지스터에 기록)
RIP:            8 bytes (IDT handler 주소로 교체, 원본은 스택)
RSP:            8 bytes (커널 스택으로 전환, 원본은 스택)
RFLAGS:         8 bytes (스택에 push)
CS/SS:          각 8 bytes (스택에 push)
-----------------
합계:           ~56 bytes가 커널 스택에 push됨

PintOS에서 page fault 관련 상수:

PGSIZE          = 4096 bytes (0x1000)
USER_STACK      = 0x47480000 (스택 최하단 한계)
KERN_BASE       = 0x8004000000
PF_P            = 0x1  (present bit)
PF_W            = 0x2  (write bit)
PF_U            = 0x4  (user bit)

fault 주소에서 page 번호 계산 예시:

fault_addr = 0x00000000004004a8
pg_round_down(fault_addr) = 0x0000000000400000
page_offset = fault_addr & 0xFFF = 0x4a8
SPT lookup key = 0x0000000000400000

페이지 폴트 점검

  • page fault는 항상 버그가 아니다. demand paging, lazy loading, stack growth처럼 일부 fault는 OS가 페이지를 준비한 뒤 같은 명령어를 다시 실행시키는 정상 경로다.
  • CPU/MMU 기준에서는 CR2, error_code, RIP가 핵심 증거다. Linux/Windows 기준에서는 VMA/VAD 같은 주소 범위 메타데이터가 합법성을 판단한다.
  • PintOS 기준에서는 page_fault()가 하드웨어가 남긴 정보를 읽고, vm_try_handle_fault()가 SPT 검색, stack growth, 종료 여부를 결정한다.
  • 설명할 때는 “주소 변환 실패”와 “OS가 복구 가능한 실패인지 판단하는 정책”을 분리해야 한다.
