PintOS VM 구현 준비

PintOS VM 구현 준비

확인 범위: 이 문서는 PintOS Project 3 VM 구현을 준비하기 위한 개념 설명과 설계·검증 질문, 권장 구현 순서를 정리한 체크리스트다. 제시된 코드 좌표, 분기 흐름, 수치 예시와 GDB 확인 항목은 특정 구현에서 실제로 검증된 결과를 보장하지 않으므로, 적용 중인 코드와 버전 및 실행·성능 측정 기록을 별도로 확인해야 한다.

한 줄 요약: PintOS Project 3 VM을 구현하기 전에 주소 변환·SPT·lazy loading·eviction·mmap/fork 영역별로 먼저 답해야 할 질문과 관련 문서를 묶은 체크리스트다. 코드를 짜기 전에 개념 구멍을 메우는 준비 문서.

PintOS VM 구현 쟁점

PintOS VM을 구현하기 전에 가장 먼저 생기는 질문은 보통 이것이다.

“page fault가 나면 도대체 어디서 무엇을 찾아서, 어떤 메모리에 무엇을 채우고, 어떤 비트를 세팅해야 다시 실행될까?”

목표는 VM 코드를 쓰기 전에 다음을 머릿속에 연결하는 것이다.

  • [주소 참조 과정](/wiki/hubs/pintos-vm-visual#주소 참조와 page fault): CPU가 주소를 읽다가 왜 커널로 들어오는가
  • [코드 로딩 과정](/wiki/hubs/pintos-vm-visual#lazy code loading): load_segment()는 왜 실제 바이트를 바로 읽지 않는가
  • [VM 데이터 구조](/wiki/hubs/pintos-vm-visual#page type 구조): UNINIT, ANON, FILE은 언제 바뀌는가
  • [ SPT API](/wiki/hubs/pintos-vm-visual#Frame과 SPT API): frame, page, SPT, PML4는 서로 무엇을 기억하는가
  • 바이트와 캐스팅: 같은 메모리도 어떤 타입으로 읽느냐에 따라 의미가 달라지는가

VM을 한 문장으로 말하면

VM은 “프로그램이 보는 주소”와 “실제 RAM의 바이트” 사이에 커널이 정책을 끼워 넣는 장치다.

이 말은 즉, 유저 프로그램이 0x401000을 읽는다고 해서 바로 RAM의 0x401000을 읽는 것이 아니다.

중간에 다음 질문들이 들어간다.

  • 이 주소는 이 프로세스에게 합법적인가?
  • 지금 RAM에 올라와 있는가?
  • 없으면 파일에서 읽어야 하는가, swap에서 읽어야 하는가, 0으로 채워야 하는가?
  • 읽기만 가능한가, 쓰기도 가능한가?
  • 접근 후에는 accessed/dirty bit를 어떻게 해석해야 하는가?

관련 문서:

  • 주소 변환과 메모리
  • x86 64 페이지 테이블 워크
  • 페이지 테이블 엔트리 비트 — CPU가 주소 변환 중에 읽고 쓰는 플래그들
  • 페이지 폴트 error code

구현 전 전체 그림

먼저 [VM 전체 그림](/wiki/hubs/pintos-vm-visual#원본 시각 자료)을 본다.

핵심 흐름은 이렇게 읽으면 된다.

flowchart TD
    A["유저 명령어: mov [0x401234], rax"] --> B["CPU/MMU: PML4 walk"]
    B -->|PTE present| C["정상 접근 — RAM 바이트 읽기/쓰기"]
    B -->|PTE absent| D["#PF exception → page_fault()"]
    D --> E["CR2=0x401234, error_code 해석"]
    E --> F{"vm_try_handle_fault()"}
    F -->|"SPT hit"| G["vm_do_claim_page(page)"]
    F -->|"SPT miss + stack growth 조건"| H["vm_stack_growth() → ANON page 생성"]
    H --> G
    F -->|"SPT miss + 조건 불충족"| I["kill(f) — Segfault"]
    G --> J["vm_get_frame() → palloc or eviction"]
    J --> K["frame↔page 양방향 연결"]
    K --> L["pml4_set_page(pml4, upage, kva, writable)"]
    L --> M["swap_in(page, kva) — type별 바이트 채움"]
    M --> N["handler return → 같은 명령어 재실행"]

여기서 중요한 문장은 “page fault는 항상 실패가 아니다”다.

PintOS VM에서 page fault는 lazy loading, stack growth, swap-in을 실행하는 정상 경로일 수 있다.

반드시 구분해야 하는 네 개의 표

VM 구현 중 가장 많이 헷갈리는 부분은 모든 것이 “페이지 테이블”처럼 보인다는 점이다.

이름누가 보는가무엇을 저장하는가없으면 어떤 일이 생기는가
PML4/page tableCPU/MMUVA page -> physical frame, PTE flagsCPU가 주소 번역을 못 해서 pf
SPTPintOS 커널합법적인 유저 page의 의미와 backing store커널이 fault를 살릴 근거를 잃음
frame tablePintOS 커널어떤 physical frame을 누가 쓰는가eviction victim을 고를 수 없음
swap tablePintOS 커널swap disk slot 사용 여부와 page 연결swap-out page를 복구할 수 없음

이 말은 즉, PML4에 없는 주소라도 SPT에 있으면 “아직 안 올라왔지만 합법적인 주소”일 수 있다.

관련 문서:

  • PintOS VM 객체 모델 — struct page, frame, operations가 나누는 책임
  • Supplemental Page Table은 왜 필요한가
  • Guest Physical Memory

구현 순서

권장 구현 순서는 다음이다.

  1. SPT를 만든다.
  2. lazy loading 등록을 만든다.
  3. page fault에서 SPT lookup과 claim을 연결한다.
  4. frame allocation과 pml4_set_page()를 안정화한다.
  5. stack growth를 넣는다.
  6. eviction과 swap을 넣는다.
  7. mmap/file-backed page를 넣는다.
  8. fork에서 SPT 복사를 완성한다.

각 단계는 이전 단계가 관찰 가능해야 다음으로 넘어간다.

flowchart LR
    S1["1. SPT 생성"] --> S2["2. Lazy Loading 등록"]
    S2 --> S3["3. Page Fault → SPT lookup + claim"]
    S3 --> S4["4. Frame alloc + pml4_set_page 안정화"]
    S4 --> S5["5. Stack Growth"]
    S5 --> S6["6. Eviction + Swap"]
    S6 --> S7["7. mmap / file-backed"]
    S7 --> S8["8. fork SPT 복사"]

예를 들어 vm_do_claim_page()가 제대로 동작하지 않으면 stack growth, swap, mmap은 모두 같은 방식으로 무너진다. 그래서 claim은 VM 구현의 허리다(위 다이어그램에서 3~4단계가 강조된 이유).

1단계 SPT는 무엇을 기억해야 하는가

SPT는 “PML4에 아직 없을 수도 있는 합법 page 목록”이다.

최소 질문:

  • va를 어떤 단위로 저장해야 하는가?
  • 같은 page가 두 번 들어오면 어떻게 막는가?
  • page를 찾을 때 0x401234로 찾는가, 0x401000으로 찾는가?
  • process exit 때 SPT 안의 모든 page는 누가 해제하는가?

핵심 답:

  • key는 page-aligned VA로 둔다.
  • pg_round_down(va)를 기준으로 찾는다.
  • 같은 upage가 이미 있으면 vm_alloc_page_with_initializer()는 실패해야 한다.
  • supplemental_page_table_kill()은 SPT의 모든 page를 destroy해야 한다.

관련 링크:

  • Supplemental Page Table은 왜 필요한가
  • [PintOS VM 객체 모델](/wiki/os/pintos-vm-object-model-knowledge#PintOS VM 객체 모델 흐름)
  • fork 때 SPT는 왜 같이 복사해야 하나

2단계 lazy loading은 무엇을 미루는가

lazy loading은 page 객체 생성을 미루는 것이 아니다.

미루는 것은 “실제 frame 확보와 file read”다.

load_segment() 시점:

  • page마다 upage, read_bytes, zero_bytes, writable, file offset을 계산한다.
  • 이 정보를 aux에 담는다.
  • SPT에 UNINIT page를 등록한다.
  • 아직 frame->kva에 ELF 바이트를 읽지 않는다.

첫 접근 시점:

  • pf 발생
  • vm_try_handle_fault()가 SPT에서 page를 찾음
  • vm_do_claim_page()가 frame을 확보
  • swap_in() -> uninit_initialize() -> lazy_load_segment() 실행
  • file bytes + zero bytes가 frame에 채워짐

관련 링크:

  • Lazy Loading Segment 흐름
  • file 수명 Trace
  • fork에서 lazy UNINIT page의 aux는 어떻게 복사해야 하나
  • [코드 로딩 과정 이미지](/wiki/hubs/pintos-vm-visual#lazy code loading)
  • ELF 로더는 파일을 어떻게 실행 중인 메모리로 바꾸는가

3단계 page fault는 어떤 질문에 답해야 하는가

page_fault()는 CPU가 던진 예외다. 하지만 OS는 그 예외를 정책 질문으로 바꿔야 한다.

CPU가 주는 정보:

정보PintOS에서 얻는 곳의미
fault addressCR2, rcr2()접근하려다 실패한 VA
present biterror code PF_Pnot-present fault인지 protection fault인지
write biterror code PF_Wwrite 접근이었는지
user biterror code PF_U유저 모드 접근이었는지
rsp/ripstruct intr_framestack growth 판단과 재시작 위치

vm_try_handle_fault()가 답해야 할 질문:

  • not-present fault인가?
  • user address인가?
  • write인데 read-only page인가?
  • SPT에 page가 있는가?
  • SPT에 없지만 stack growth로 인정할 수 있는가?
  • 인정한다면 어떤 page type으로 만들 것인가?

관련 링크:

  • CPU 메모리 접근에서 Page Fault 복구까지의 Trace
  • 페이지 폴트 error code
  • vm try handle fault 판단 흐름 Trace
  • [주소 참조 과정 이미지](/wiki/hubs/pintos-vm-visual#주소 참조와 page fault)

claim은 “page가 실제 frame을 얻고, CPU가 번역할 수 있는 PTE를 얻는 과정”이다.

5단계 stack growth는 어디까지 허용하는가

stack growth는 SPT에 없는 모든 주소를 살려 주는 기능이 아니다.

살릴 수 있는 주소는 “현재 유저 스택이 실제로 자라다가 닿은 근처”여야 한다.

판단 질문:

  • fault address가 user address인가?
  • USER_STACK보다 아래인가?
  • 최대 stack 크기 제한 안에 있는가?
  • rsp 근처 접근인가?
  • write 또는 push 계열 접근으로 볼 수 있는가?

정책을 너무 넓게 잡으면 잘못된 포인터가 조용히 새 stack page가 된다. 너무 좁게 잡으면 정상적인 push, 함수 호출, argument 저장이 죽는다.

관련 링크:

  • 스택 성장 페이지 폴트는 언제 살려야 하나
  • 스택 성장 경계 Lab
  • [stack growth 분기](/wiki/os/vm-try-handle-fault-decision-trace#3. stack growth 한계 계산)

6단계 frame eviction은 언제 필요한가

palloc_get_page(PAL_USER)가 실패하면 user pool에 빈 frame이 없다는 뜻이다.

이때 VM은 둘 중 하나를 해야 한다.

  • victim frame을 골라서 내보낸다.
  • 더 이상 메모리를 줄 수 없으므로 실패한다.

eviction에서 묻는 질문:

  • 어떤 frame을 victim으로 고를 것인가?
  • victim page가 dirty인가?
  • anonymous page면 swap slot에 써야 하는가?
  • file-backed page면 파일에 write-back해야 하는가?
  • PML4의 present mapping은 어떻게 제거할 것인가?

관련 링크:

  • 프레임 교체 (Frame Eviction) Trace
  • Clock hand로 victim frame 고르기 Lab
  • dirty bit로 victim 판단

8단계 mmap은 파일을 어떻게 메모리처럼 보이게 하는가

mmap()은 파일 바이트를 유저 VA 범위에 붙인다.

하지만 처음부터 파일 전체를 RAM에 읽는 것이 아니다. lazy loading과 비슷하게 “이 VA는 이 파일 offset에서 온다”는 metadata를 SPT에 넣고, page fault 때 필요한 page만 읽을 수 있다.

구현 전 질문:

  • addr는 page-aligned인가?
  • length가 0이면 실패해야 하는가?
  • file offset은 page-aligned인가?
  • mapping range가 기존 SPT page와 겹치는가?
  • read-only mapping에 write fault가 오면 어떻게 막는가?
  • munmap 때 dirty page만 write-back하는가?

관련 링크:

  • mmap file backed page는 어떻게 파일을 메모리처럼 보이게 하나
  • file backed page metadata에는 무엇을 저장해야 하나
  • lazy page aux ownership 계약
  • mmap file page의 aux는 언제 struct file page로 옮겨야 하나
  • fault가 한 번도 나지 않은 mmap page는 누가 정리하나
  • mmap region metadata는 누가 소유해야 하나
  • mmap 시스템콜 핸들러 흐름 (Mmap Syscall Handler Trace)
  • mmap 실패 조건은 어떤 순서로 검사해야 하나
  • mmap은 왜 이미 쓰는 주소 범위를 덮으면 안 되나
  • mmap read only 쓰기 보호 Lab
  • mmap 다중 region 격리는 무엇을 확인해야 하나
  • mmap dirty write back은 어떻게 디스크 쓰기로 내려가나

9단계 fork는 주소 공간의 무엇을 복사하는가

VM 이후 fork()는 단순히 register만 복사해서는 안 된다.

부모 주소 공간의 의미도 복사해야 한다.

복사해야 할 질문:

  • 아직 load되지 않은 lazy page는 자식에서도 lazy 상태로 남길 것인가?
  • lazy UNINIT page의 aux와 file reference는 부모/자식이 각각 소유하게 만들 것인가?
  • 이미 RAM에 있는 anonymous page는 새 frame으로 복사할 것인가?
  • swapped-out page는 swap slot을 어떻게 다룰 것인가?
  • swapped-out anonymous page의 slot 번호는 자식에게 그대로 복사해도 되는가?
  • file-backed page는 파일 metadata를 어떻게 복제할 것인가?
  • writable bit와 dirty/accessed bit는 어떻게 초기화할 것인가?

관련 링크:

  • fork 때 SPT는 왜 같이 복사해야 하나
  • fork에서 lazy UNINIT page의 aux는 어떻게 복사해야 하나
  • fork에서 swapped out anonymous page는 어떻게 복사해야 하나
  • swapped anonymous page fork snapshot 흐름
  • COW write protect fault는 언제 page copy로 살아나나
  • fork하면 fd table은 어떻게 복제되는가
  • [process fork 시각화](/wiki/hubs/pintos-process-visual#fork 생성과 초기화 동기화)

10단계 process cleanup은 무엇을 회수해야 하는가

VM을 구현한 뒤에는 process_exit()과 process_exec()가 단순히 page table만 버리면 안 된다.

정리해야 할 질문:

  • SPT 안의 모든 struct page를 순회하는가?
  • resident page의 frame과 PTE는 어떻게 정리하는가?
  • swapped-out anonymous page의 slot은 누가 free하는가?
  • dirty file-backed page는 exit 경로에서도 write-back되는가?
  • 아직 첫 접근이 없던 UNINIT lazy page의 aux와 file reference는 해제되는가?

관련 링크:

  • process cleanup은 SPT page들을 어떤 순서로 해제하나

swap_in type별 분기

vm_do_claim_page() 이후 swap_in(page, kva)가 호출되면, page의 현재 type에 따라 전혀 다른 경로를 탄다.

flowchart TD
    A["swap_in(page, kva)"] --> B{"page->operations"}
    B -->|"UNINIT"| C["uninit_initialize()"]
    C --> D{"page->init callback"}
    D -->|"anon_initializer"| E["memset(kva, 0, PGSIZE)\npage type → VM_ANON"]
    D -->|"file_backed_initializer"| F["file_read_at()\npage type → VM_FILE"]
    C --> G["lazy_load_segment(page, aux)\nfile bytes + zero padding"]
    B -->|"VM_ANON"| H["anon_swap_in()\nswap slot → frame memcpy"]
    B -->|"VM_FILE"| I["file_backed_swap_in()\nfile_read_at(file, kva, ...)"]
