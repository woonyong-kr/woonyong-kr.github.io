read() 버퍼는 왜 PTE_W까지 확인해야 하나?

확인 범위: 이 문서는 read()가 쓰기 대상 유저 버퍼의 매핑 여부뿐 아니라 쓰기 권한과 전체 범위를 검증해야 한다는 일반 원리와 PintOS에서의 설계 판단 기준을 설명한다. 제시된 코드와 PTE 값, GDB·QEMU 절차는 검증 방법 또는 예시이며, 특정 버전에서 실제로 실행해 얻은 결과나 성능 측정 결과를 보고하는 것은 아니다.

한 줄 요약: read(fd, buffer, size)의 buffer는 present 여부만 확인해서는 부족하다. 커널이 유저를 대신해 데이터를 쓰는 시스템 콜이므로 PTE_W까지 검사해 writable page인지 검증해야 한다.

read() 버퍼 PTE_W 쟁점

read(fd, buffer, size)에서 buffer 주소가 현재 프로세스의 page table에 매핑되어 있기만 하면 충분할까?

아니다. read()는 파일이나 키보드에서 읽은 바이트를 유저 버퍼에 써 주는 시스템 콜이다.

여기서 확인된 사실은 커널이 유저 버퍼를 쓰기 대상으로 사용한다는 점이다. 따라서 검증 단계에서는 buffer가 단순히 present인 page인지뿐 아니라, 쓰기가 허용된 writable page인지도 확인해야 한다.

read() 버퍼 PTE_W 문제

유저 포인터 검증은 다음 두 질문으로 나누어야 한다.

질문필요한 이유
이 주소가 mapped인가?없는 page에 접근하면 pf가 난다
이 방향으로 접근해도 되는가?read-only page에 쓰면 보호 규칙을 어긴다

write(fd, buffer, size)는 유저 버퍼에서 커널이나 파일 쪽으로 데이터를 가져간다. 따라서 유저 버퍼를 읽을 수 있어야 한다.

반대로 read(fd, buffer, size)는 커널이나 파일 쪽 데이터를 유저 버퍼로 내보낸다. 따라서 유저 버퍼에 쓸 수 있어야 한다.

즉, read() 검증은 pml4_get_page() != NULL 확인에서 끝나면 안 된다. PTE의 writable bit까지 살펴야 “이 page에 써도 되는가”라는 두 번째 질문에 답할 수 있다.

read() 버퍼 PTE_W 상태

PTE에는 주소와 권한이 함께 담긴다.

pml4_get_page()는 present mapping의 존재 여부를 확인하기에 적합하다. 다만 반환값은 frame을 가리키는 kernel virtual address다.

이 과정에서는 PTE_W 같은 flag의 판단 결과가 호출자에게 직접 드러나지 않는다. writable 여부를 판단하려면 PTE pointer 자체를 얻어 flag bit를 검사해야 한다.

VM 테스트에는 이 질문을 정확히 찌르는 케이스가 있다

VM 테스트에는 mapped 여부와 writable 여부의 차이를 직접 확인하는 케이스가 있다.

  • SW_AI-W11-pintos/pintos/tests/vm/pt-write-code2.c

실제 운영체제

PintOS에서 확인한 쟁점을 실제 운영체제의 처리 흐름과 연결하면, 공통점은 커널이 user buffer를 일반 pointer처럼 곧바로 신뢰하지 않는다는 데 있다.

Linux에서 read(fd, user_buf, len)은 커널이 user buffer로 데이터를 복사하는 흐름이다. 이때 user pointer는 쓰기 가능한 유저 메모리인지 확인하는 안전한 복사 경로를 거친다.

Windows도 같은 문제를 다룬다. ReadFile은 애플리케이션 관점의 이름이지만, 커널이나 드라이버 관점에서는 output buffer에 데이터를 써야 한다. 따라서 그 버퍼가 유저 주소인지, 쓰기 가능한지, 요청 방식에 맞게 probe되었는지를 처리해야 한다.

다만 실제 OS의 메모리 처리 정책은 PintOS보다 복잡하므로, present와 writable만으로 모든 경우를 설명할 수는 없다.

  • 현재 page가 없더라도 demand paging으로 복구할 수 있다.
  • copy-on-write page에서는 쓰기 fault가 “불법 접근”이 아니라 “복사 후 허용”을 뜻할 수 있다.
  • mmap, shared page, file-backed page는 backing metadata와 permission을 함께 살펴야 한다.
  • 실패 결과도 단순 종료가 아니라 -EFAULT, signal, exception 등으로 정책화된다.

QEMU

QEMU는 PintOS의 syscall 정책을 알지 못한다. QEMU의 역할은 x86 CPU가 page table permission을 해석하는 규칙을 재현하는 것이다.

여기서 특히 주의할 점이 있다.

read() 안에서 file_read()나 buf[i] = input_getc()가 실행될 때 실제 메모리 store는 유저 모드가 아니라 커널 모드에서 일어난다.

QEMU의 x86 page walk 경로는 write permission을 결정할 때 kernel/user context와 CR0.WP를 함께 고려한다.

  • target/i386/tcg/system/excp_helper.c

핵심 모델은 다음과 같다.

PintOS의 부팅 코드에서도 이 차이와 관련된 설정을 확인할 수 있다.

  • SW_AI-W11-pintos/pintos/threads/loader.S
    • 주석: WP가 꺼져 있으면 ring 0 code가 page table의 write-protect bit를 무시할 수 있음
  • SW_AI-W11-pintos/pintos/threads/start.S
    • 현재 long mode 진입에서 CR0_PE | CR0_PG를 켜는 흐름이 보임

따라서 read()가 read-only user page에 쓰는 문제를 “하드웨어 pf가 알아서 막아 줄 것”이라고 가정하면 위험하다. QEMU가 재현하는 하드웨어 동작과 PintOS가 시행해야 할 syscall 정책은 서로 다른 층의 책임이다. PintOS syscall 검증 코드가 PTE_W를 직접 확인해야 테스트 의도와 보안 경계가 일치한다.

3. QEMU fault에만 의존하면 안 되는 이유 확인

QEMU 쪽에서 살펴볼 위치:

확인할 질문:

이 실험의 목적은 syscall 정책을 검증하는 것이 아니라, 하드웨어 재현 층과 OS 정책 층을 구분하는 것이다. read() 버퍼를 거절할지는 QEMU가 아니라 PintOS syscall 코드가 결정해야 한다.

정리

  • read()는 user buffer를 읽는 syscall이 아니라 user buffer에 쓰는 syscall이다.
  • present mapping 확인은 “주소가 있다”에는 답하지만 “써도 된다”에는 답하지 못한다.
  • pml4_get_page() 반환값만으로는 PTE_W를 알 수 없다.
  • PintOS에서는 pml4e_walk()로 PTE pointer를 얻고 PTE_P/PTE_U/PTE_W를 함께 확인하는 helper가 필요하다.
  • QEMU는 x86 permission 규칙을 재현하지만 syscall의 유저 버퍼 정책을 대신 결정하지 않는다.
  • 특히 kernel context write와 CR0.WP 때문에 read-only user page 쓰기를 hardware fault에만 맡기면 학습용 테스트의 의도와 어긋날 수 있다.

  • write buffer boundary
