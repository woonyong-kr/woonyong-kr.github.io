보호 (Protection)

보호 (Protection)

한 줄 요약: 보호는 유저 프로그램이 커널 메모리·페이지 테이블·CPU를 함부로 다루지 못하도록 하드웨어가 강제하는 운영체제의 둘째 책임이다.

보호 상태

운영체제가 제공하는 추상화는 권한 장벽이 있어야 유지된다. 유저 프로그램이 커널 메모리를 직접 읽거나 페이지 테이블을 바꾸고, hlt 명령으로 CPU를 멈출 수 있다면 추상화만으로 시스템을 지킬 수 없다. 보호는 유저 코드가 할 수 있는 일과 커널 코드만 할 수 있는 일을 CPU 하드웨어의 규칙으로 분리한다.

이 장벽은 유저/커널 모드 분리, 특권 명령어 제한, syscall 경계로 이루어진다. 실행 중인 코드의 권한은 모드로 구분하고, 시스템 전체에 영향을 주는 명령은 커널에만 허용한다. 유저 프로그램이 커널 기능을 사용해야 할 때는 syscall 경계를 거쳐 요청한다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

x86-64 CPU는 CPL (Current Privilege Level) 이라는 2비트 값으로 현재 실행 권한을 나타낸다. 이 값은 CS 레지스터의 하위 2비트에 들어 있다.

CPL이름할 수 있는 일
0커널 모드 (Ring 0)모든 명령어 실행, 모든 메모리 접근, CR3/MSR 등 제어 레지스터 조작
3유저 모드 (Ring 3)일반 연산만 가능, 특권 명령어 실행 시 gp 예외 발생

Ring 1과 Ring 2도 x86 아키텍처에 정의되어 있지만 현대 OS에서는 거의 사용하지 않는다. 여기서는 실질적으로 사용하는 Ring 0과 Ring 3의 두 권한 수준을 다룬다.

유저 모드에서 커널 모드로 제어가 넘어가는 경로는 syscall, 인터럽트, 예외로 구분할 수 있다. 세 경로 모두 CPL 3에서 CPL 0으로 전환될 수 있지만, 커널 스택을 전환하는 방식까지 같지는 않다. 특히 x86-64 SYSCALL은 TSS의 rsp0를 사용해 RSP를 자동으로 바꾸지 않는다.

특권 명령어

CPU는 시스템 전체의 상태를 바꿀 수 있는 명령을 특권 명령어로 제한한다. 이런 명령은 CPL=0에서만 실행할 수 있으며, 유저 모드에서 실행하면 CPU가 gp(General Protection) 예외를 발생시킨다.

명령어역할유저 모드 시도 결과
mov cr3, rax페이지 테이블 루트 변경gp → 프로세스 종료
wrmsrMSR 레지스터 쓰기 (LSTAR 등)gp
hltCPU 정지gp
lgdt / lidtGDT/IDT 테이블 교체gp
in / outI/O 포트 직접 접근gp (IOPL 검사)
cli / sti인터럽트 비활성/활성gp

따라서 유저 프로그램이 hlt를 실행해도 CPU 전체가 바로 멈추지는 않는다. CPU가 gp 예외를 발생시키면 OS의 예외 핸들러가 해당 프로세스를 종료한다. 명령의 실행 자체를 하드웨어가 막는다는 점이 이 보호의 바탕이다.

PTE 보호 비트

실행할 수 있는 명령뿐 아니라 접근할 수 있는 메모리도 제한해야 한다. 페이지 테이블 항목(PTE)의 보호 비트는 페이지별로 접근 가능 여부와 허용할 연산을 정한다.

비트이름역할
bit 0Present (P)0이면 접근 시 pf
bit 1Read/Write (R/W)0이면 쓰기 시 pf (유저 모드)
bit 2User/Supervisor (U/S)0이면 유저 모드 접근 시 pf
bit 63Execute Disable (NX)1이면 해당 페이지에서 명령어 fetch 시 pf

커널 페이지의 U/S 비트는 0이다. 유저 프로그램이 커널 주소(예: 0x8004000000 이상)를 읽으려 하면 MMU가 pf를 발생시키고, OS는 이 예외를 처리해 접근을 차단한다.

syscall 경계

유저 프로그램은 파일 읽기나 프로세스 생성 같은 커널 기능을 직접 수행할 수 없다. 이런 기능이 필요하면 반드시 syscall 명령어로 커널에 요청해야 한다. syscall은 유저 영역과 커널 영역 사이에 허용된 통로다.

SYSCALL을 실행하면 CPU는 다음 RIP를 RCX에, RFLAGS를 R11에 저장한다. 이어서 LSTAR에서 커널 진입 RIP를 읽고, STAR에 설정된 selector를 바탕으로 CPL 0의 CS/SS를 선택하며, SFMASK에 지정된 flag를 지운다.

그러나 x86-64 SYSCALL은 TSS의 rsp0를 읽어 RSP를 바꾸지 않는다. 커널 진입 어셈블리가 유저 RSP를 보존한 뒤 현재 스레드의 커널 스택으로 전환해야 한다. CPU가 수행하는 권한·상태 전환과 커널 소프트웨어가 담당하는 스택·레지스터 저장은 서로 다른 단계다.

실제 OS (Linux/Windows)

Linux와 Windows도 CPU의 보호 규칙 위에 각자의 syscall 진입점과 추가 보호 기능을 구성한다.

Linux:

  • syscall 진입점은 entry_SYSCALL_64(arch/x86/entry/entry_64.S)
  • 커널 스택은 프로세스별 thread_info + 커널 스택 페이지에 위치
  • KPTI (Kernel Page Table Isolation)로 Meltdown 방어: 유저 모드일 때 커널 페이지 테이블 대부분을 unmap
  • SMEP/SMAP: 커널 모드에서 유저 메모리의 코드 실행/데이터 접근을 하드웨어적으로 차단

Windows:

  • syscall 진입점은 KiSystemCall64
  • SSDT (System Service Descriptor Table)로 syscall 번호 → 커널 함수 매핑
  • Kernel Patch Protection (PatchGuard)으로 커널 코드 무결성 검증

PintOS 구현

PintOS에서는 syscall 진입점을 등록하고, 진입 방식에 맞게 커널 스택을 선택한 뒤, 유저가 전달한 포인터를 검증하는 경로에서 보호가 드러난다.

1. syscall 진입점 등록 (부팅 시):

MSR_LSTAR에는 syscall_entry(어셈블리 진입점)의 주소를 쓴다. 이후 유저 프로그램이 syscall 명령어를 실행하면 CPU가 RIP를 이 주소로 바꾼다.

2. 커널 스택 전환 경로 구분:

유저 모드에서 커널로 들어온 뒤에도 유저 스택을 계속 신뢰해서는 안 된다. 다만 스택을 전환하는 주체는 진입 방식에 따라 달라진다.

  • IDT를 통한 인터럽트·예외가 CPL 3에서 CPL 0으로 전환되면 CPU가 TSS의 rsp0를 사용한다.
  • x86-64 SYSCALL은 RSP를 자동 전환하지 않는다. PintOS의 syscall_entry가 유저 RSP를 저장하고 현재 스레드의 커널 스택 포인터를 로드한다.

3. 유저 포인터 검증:

시스템 콜 경계를 통과했다고 해서 유저가 넘긴 값을 곧바로 신뢰할 수 있는 것은 아니다. 커널은 유저가 커널 주소를 넘겨 커널 메모리를 읽게 하는 공격을 막기 위해 포인터를 검증해야 한다.

QEMU 에뮬레이션

QEMU는 CPL 전환, 특권 명령어 검사, PTE 검사처럼 CPU와 MMU가 담당하는 보호 동작을 재현한다. 반면 syscall 번호의 의미나 주소를 어떻게 처리할지는 OS의 정책이므로 QEMU가 판단하지 않는다.

보호 요소QEMU가 재현하는 것QEMU가 모르는 것
CPL 전환syscall 시 CS 변경, CPL 0으로 전환syscall 번호의 의미
특권 명령어CPL=3에서 mov cr3시 gp 발생어떤 프로세스가 위반했는지
PTE 보호U/S=0인 페이지의 유저 접근 시 pf 발생해당 주소가 stack growth인지 invalid인지
TSS/RSP0IDT 인터럽트·예외의 privilege 전환 시 rsp0를 사용SYSCALL 진입 어셈블리의 소프트웨어 스택 전환과 OS의 소유권 정책

보호 값 추적

CPL은 CS 레지스터의 하위 2비트로 확인할 수 있다.

CS register 값 = 0x001B
하위 2비트    = 0x1B & 0x3 = 3  → 유저 모드

syscall 후:
CS register 값 = 0x0008
하위 2비트    = 0x08 & 0x3 = 0  → 커널 모드

PintOS의 세그먼트 셀렉터에도 커널과 유저의 권한 수준이 반영되어 있다.

SEL_KCSEG = 0x08  (커널 코드, CPL=0)
SEL_KDSEG = 0x10  (커널 데이터, CPL=0)
SEL_UCSEG = 0x1B  (유저 코드, CPL=3)  — 0x18 | 3
SEL_UDSEG = 0x23  (유저 데이터, CPL=3)  — 0x20 | 3

PintOS의 커널 스택은 struct thread가 놓인 페이지의 나머지 공간을 사용한다.

PGSIZE         = 4096 bytes (4 KB)
커널 스택      = struct thread가 차지하는 페이지의 나머지 공간
struct thread  ≈ 페이지 하단에 위치
스택 꼭대기    = 페이지 최상단 (thread page + PGSIZE)

순서도 / 개념도

다음 흐름은 syscall 명령 이후 CPU가 수행하는 전환과 커널 진입 코드가 수행하는 저장·분기를 구분해 보여 준다.

sequenceDiagram
    participant U as User Program (CPL=3)
    participant CPU as CPU/MMU
    participant K as Kernel (CPL=0)

    U->>CPU: syscall 명령어
    Note over CPU: RCX←next RIP<br/>R11←RFLAGS<br/>RIP←LSTAR<br/>CS←kernel CS (CPL=0)
    CPU->>K: syscall_entry 실행
    K->>K: syscall_entry가 유저 RSP 저장<br/>현재 thread의 kernel stack pointer 로드
    K->>K: register를 intr_frame에 push
    K->>K: syscall_handler() 분기
    K->>K: 결과를 f→R.rax에 저장
    K->>CPU: sysret / iretq
    Note over CPU: RIP←RCX<br/>RFLAGS←R11<br/>CS←user CS (CPL=3)
    CPU->>U: 유저 모드 복귀
