공유 파일 오프셋

공유 파일 오프셋

한 줄 요약: fork 후 부모·자식이 같은 struct file을 공유하느냐에 따라 파일 offset 공유 여부가 갈리는 문제 — Linux는 refcount로 공유.

fork 뒤 파일 offset은 어떻게 달라지는가

부모 프로세스와 자식 프로세스가 같은 파일을 가리키더라도 offset까지 반드시 공유하는 것은 아니다. fork 뒤 두 프로세스가 같은 struct file 객체를 참조하면 한쪽의 read()나 write()가 offset을 바꾸고, 다른 쪽도 바뀐 값을 보게 된다. 각 프로세스가 별도의 struct file 객체를 가지면 inode가 같아도 offset은 독립적으로 움직인다.

이 차이는 Linux와 PintOS의 구현에서 드러난다. Linux는 참조 카운트(refcount)를 늘려 같은 struct file을 공유한다. PintOS는 file_duplicate()로 struct file의 독립 사본을 만들고 복제 시점의 offset만 복사한다.

File Descriptor와 Open File Description

POSIX의 동작을 이해하려면 프로세스가 가진 fd와 커널의 File Description을 구분해야 한다.

fork가 일어나면 자식은 부모의 fd 테이블을 복사하지만, 각 fd는 부모와 같은 File Description을 가리킨다. 이때 참조 카운트가 1 증가한다. 부모가 read()하여 File Description의 offset을 전진시키면 자식도 그 offset을 본다.

이 문서에서는 이러한 공유가 파이프, 리다이렉션, 셸 스크립트의 동작과 연결된다고 설명한다. 다만 아래 셸 예시는 offset 공유의 필요성을 설명하기 위한 예시이며, 해당 동작을 직접 검증한 실행 결과는 제시하지 않는다.

Linux: 같은 struct file 공유

Linux에서는 부모와 자식의 fd가 같은 struct file을 참조한다. struct file의 f_pos가 공유 offset이고, f_count가 참조 수를 나타낸다.

%% Linux의 공유 struct file 구조
flowchart TD
  parent["프로세스 A<br/>fd_table<br/>[3] -&gt; struct file"]
  child["프로세스 B<br/>fork된 자식<br/>[3] -&gt; struct file"]
  file["struct file<br/>refcount = 2<br/>f_pos = 100<br/>f_inode -&gt; struct inode"]
  inode["struct inode<br/>파일의 실제 메타데이터"]
  parent -->|fd 3| file
  child -->|fd 3| file
  file -->|f_inode| inode
연산Linux struct file 동작
fork()f_count++ (같은 객체 참조)
dup()/dup2()f_count++ (같은 프로세스 내 공유)
open() (같은 파일)새 struct file 생성 (독립 offset)
close()f_count— (0이면 해제)
read()/write()f_pos 갱신 → 모든 공유자에게 영향

셸에서 리다이렉션된 파일을 여러 자식이 이어서 쓴다고 생각하면 공유 offset이 하는 역할을 볼 수 있다.

PintOS: struct file을 복사해 offset 분리

PintOS의 file_duplicate()는 같은 inode를 다시 열어 새 struct file을 만들고, 기존 pos를 새 객체에 복사한다. 복제 직후 두 객체의 offset 값은 같지만 이후에는 각각 갱신된다.

filesys/file.c:45 — file_duplicate():

fork 과정의 duplicate_fd_table()은 부모의 fd를 순회하면서 각 파일에 file_duplicate()를 호출한다.

userprog/process.c:274 — duplicate_fd_table():

따라서 부모와 자식의 struct file은 서로 다르지만 두 객체가 가리키는 inode는 같다.

%% PintOS의 복사된 struct file 구조
flowchart TD
  parent["부모<br/>fd_table<br/>[3] -&gt; struct file"]
  child["자식<br/>fd_table<br/>[3] -&gt; struct file"]
  parent_file["struct file<br/>pos = 100<br/>inode -&gt; 같은 inode"]
  child_file["struct file<br/>pos = 100<br/>복사 뒤 독립 pos"]
  inode["struct inode<br/>inode_reopen()<br/>open_cnt++"]

  child -->|fd 3| child_file
  parent_file -->|inode| inode
  child_file -->|inode| inode

항목Linux (POSIX)PintOS

offset 공유공유됨독립
inode 공유공유 (i_count++)공유 (open_cnt++)

메모리 비용/fd참조 카운트 1 증가struct file 1개 새 할당 (~24B)
POSIX 호환완전 호환비호환 (offset 독립)

PintOS의 선택은 문서에 제시된 구현 구조로 설명할 수 있다. PintOS의 struct file에는 refcount 필드가 없으므로 객체를 공유하려면 구조체와 close()의 참조 관리 로직을 확장해야 한다. 현재 구현은 fd 번호와 같은 inode 접근을 유지하면서 struct file을 복사해 offset을 분리한다. 또한 파일 시스템 접근은 filesys_lock 하나로 직렬화된다. 이 문서에서는 이를 동기화 복잡성을 줄인 교육용 구현으로 해석하지만, 그 설계 의도를 별도 자료로 확인한 것은 아니다.

fork 후 read()에서 보이는 차이

Linux에서는 부모와 자식이 같은 struct file의 f_pos를 사용한다. 부모의 read()가 f_pos를 바꾸면 자식의 다음 read()는 바뀐 위치에서 시작한다. PintOS에서는 복제 시점의 pos만 같고 이후 객체가 분리되므로, 부모의 read()가 자식의 pos를 바꾸지 않는다.

PintOS 복제 비용을 따라가기

문서에 제시된 구조와 크기 가정을 적용하면 다음과 같이 계산된다. struct file 크기와 연산 비용은 근삿값이며, 실제 측정 결과로 제시된 값은 아니다.

항목값
struct file 크기8B (inode*) + 4B (pos) + 4B (deny_write+padding) ≈ 16~24B
FD_MAXPGSIZE / sizeof(struct file*) = 4096 / 8 = 512
fork 시 fd_table 페이지1 page = 4096B (palloc_get_page)
inode refcount (open_cnt)fork마다 +1 (inode_reopen)
file_duplicate 비용calloc(1, sizeof file) + inode_reopen = ~수십 사이클

fd 3개가 열린 상태를 가정하면 자식은 fd_table용 페이지 하나와 각 fd의 새 struct file을 할당한다.

이 계산은 표에 적힌 크기를 사용한 추정이며, 실행 환경에서 측정한 메모리 사용량이나 사이클 수는 아니다.
