프로세스별 fd_table 배열

read(3, ...)의 3은 파일 이름이나 포인터가 아니라 현재 프로세스의 fd_table에서 파일을 찾는 번호라서, 다른 프로세스의 fd 3은 전혀 다른 struct file *를 가리킬 수 있다.

먼저 open()이 돌려준 2를 따라가 보자

파일을 열고 받은 2는 “두 번째 파일”이라는 이름이 아니라, 커널에게 파일을 다시 찾아 달라고 건네는 번호다.

사용자 프로그램은 fd == 2만 들고 있지만, 커널은 그 번호를 현재 프로세스의 테이블에서 찾아 실제 파일 객체를 꺼낸다.

이제 write(fd, ...)가 파일에 쓸 수 있는 이유와, 다른 프로세스의 fd 2가 같은 파일을 뜻하지 않는 이유를 이 연결에서 설명할 수 있다.

같은 fd라도 프로세스가 다르면 다른 파일일 수 있다

사용자 프로그램이 open()으로 파일을 열면 커널은 struct file *를 만든 뒤 비어 있는 fd_table 슬롯에 넣고, 그 자리 번호를 돌려준다. 따라서 read(3, ...)이나 close(3)의 3은 파일의 이름이나 주소가 아니라 “현재 프로세스의 세 번째 슬롯을 보라”는 뜻이다.

프로세스마다 테이블이 따로 있으므로 부모와 자식이 모두 fd 3을 갖고 있어도 같은 파일 객체를 가리킨다는 보장은 없고, 다른 프로세스의 열린 파일을 숫자만으로 건드릴 수도 없다.

프로세스 A와 B가 모두 fd 3을 쓰면, 커널은 어떤 파일을 읽어야 하는지 어떻게 구분하는가?

flowchart LR
  p1["프로세스 A<br/>fd_table[3]"] --> file_a["struct file A<br/>alpha.txt"]
  p2["프로세스 B<br/>fd_table[3]"] --> file_b["struct file B<br/>beta.txt"]

커널은 3이라는 숫자만 보지 않고, 그 숫자가 들어 있는 프로세스의 테이블까지 함께 본다.

PintOS는 이 연결을 한 페이지에 저장한다

PintOS는 각 thread 안에 파일 포인터 배열과 next_fd를 보관한다.

fd_table은 palloc_get_page(PAL_ZERO)로 받은 한 페이지이므로 처음에는 모든 슬롯이 NULL이고, next_fd는 표준 입출력 번호를 건너뛰어 2에서 시작한다.

현재 x86-64 빌드에서는 4 KiB 페이지에 8 bytes 포인터가 들어가므로 FD_MAX가 512가 되지만, 기준은 512라는 숫자가 아니라 PGSIZE / sizeof(struct file *)라는 식이라서 포인터가 4 bytes인 환경에서는 같은 한 페이지에 1024개 슬롯이 들어간다.

fd 0과 fd 1은 표준 입력과 표준 출력으로 따로 처리하므로, 이 배열에 넣는 일반 파일은 fd 2부터 시작한다.

파일을 열고 닫을 때 슬롯은 이렇게 바뀐다

open()은 첫 빈 슬롯에 파일 포인터를 넣고 그 번호를 돌려주며, read()와 write()는 같은 번호로 다시 그 슬롯을 찾고, close()는 파일을 닫은 뒤 그 자리를 비운다.

여기에서 이름과 실제 동작이 조금 다르다. process_add_file()은 next_fd에서 시작하지 않고 매번 fd 2부터 훑으므로, 어떤 파일이 실제로 열려 있는지는 next_fd가 아니라 fd_table[fd] != NULL로 판단해야 한다.

파일을 찾는 일은 배열 인덱스 하나면 끝나 O(1)이지만, 빈 자리를 찾는 일은 앞에서부터 훑어야 하므로 최악에는 O(n)이 된다. close()가 next_fd를 더 작은 번호로 낮춰도 open()은 다시 처음부터 훑기 때문에, next_fd를 열린 파일 목록처럼 읽으면 안 된다.

PintOS는 open()에서 받은 파일을 fd로 어떻게 다시 찾는가?

flowchart LR
  open["open('note.txt')"] --> add["process_add_file(file)"]
  add --> slot["fd_table[2] = file"]
  slot --> fd["return 2"]
  fd --> read["read(2, buf, size)"]
  read --> get["process_get_file(2)"]
  get --> file["struct file *"]

fork 뒤에도 같은 fd를 쓸 수 있을까

fork()는 자식에게 새 fd_table 페이지를 만든 뒤 부모 슬롯에 파일이 있으면 file_duplicate()로 새 struct file을 만들어 같은 번호에 넣는다. 그래서 복제된 슬롯에서는 부모와 자식이 같은 fd 번호를 써도 파일 객체의 주소와 이후 offset은 따로 움직이고, inode만 같은 파일을 가리킨다.

문제는 이 loop가 parent->next_fd보다 작은 슬롯만 본다는 점이다. open()으로 2, 3, 4를 받은 뒤 close(3)을 호출하면 fd_table[4]는 살아 있어도 next_fd가 3으로 내려갈 수 있고, 그 상태의 fork()는 fd 4를 자식에게 넘기지 못한다.

결국 열린 파일의 기준은 next_fd가 아니라 각 슬롯이 NULL인지 여부이고, 안전하게 복제하려면 fd 2부터 FD_MAX - 1까지 훑어 비어 있지 않은 슬롯을 모두 옮겨야 한다. 중간 fd를 닫은 뒤 큰 fd가 복제되는가는 이 상황을 GDB와 회귀 테스트로 확인하는 문서다.

프로세스가 끝나면 슬롯도 비워야 한다

프로세스가 끝날 때는 fd 2부터 열린 슬롯을 하나씩 닫고 마지막에 테이블 한 페이지를 해제한다. fd_table만 해제하면 파일 객체와 inode 참조가 남을 수 있으므로 file_close()와 페이지 해제는 둘 다 필요하다.

여기서 Linux와 비교하면 보이는 차이

Linux도 프로세스마다 파일 디스크립터 테이블을 두지만, 많은 파일과 다양한 fork·exec 동작을 처리해야 해서 크기를 늘릴 수 있는 fdtable과 비트맵을 사용한다. PintOS는 한 페이지 배열로 구조를 단순하게 보여 주는 대신, 복제 범위와 파일 offset 같은 정책을 코드에서 직접 확인해야 한다.

항목Linux현재 PintOS 구현
테이블 크기필요에 따라 확장포인터 한 페이지, 현재 x86-64에서 512 슬롯
빈 슬롯 찾기비트맵으로 관리fd 2부터 배열 순회
fork 뒤 파일 객체같은 open file description을 공유할 수 있음file_duplicate()로 새 struct file 생성
fork 뒤 offset공유될 수 있음복제된 슬롯에서는 독립
중간 fd가 비어 있을 때열린 entry를 기준으로 상속next_fd 범위를 쓰므로 큰 fd가 누락될 수 있음
종료참조 수가 0이 되면 해제슬롯별 file_close() 뒤 테이블 페이지 해제

디버깅을 더 내려가면 QEMU가 보인다

fd_table은 PintOS 커널 메모리에 있는 포인터 배열일 뿐이라 QEMU는 “fd 3”의 의미를 알지 못한다. QEMU는 process_get_file()이 파일을 찾은 뒤 디스크 I/O가 일어나거나, fd 0과 fd 1이 키보드·화면·시리얼 장치로 이어질 때만 하드웨어 쪽 동작을 맡는다.

fd lookup이 NULL을 반환하면 file_read()나 디스크 장치까지 갈 일이 없으므로, “fd를 찾지 못했다”는 문제는 PintOS의 테이블 정책에서 찾고 QEMU에서는 그 결과로 달라지는 guest 메모리와 I/O 경로만 보면 된다.

직접 멈춰서 보면 확인할 값

줄 번호는 구현이 바뀌면 금방 어긋나므로, 함수 이름으로 멈춘 뒤 부모와 자식의 같은 슬롯을 비교하는 편이 낫다.

open 2, 3, 4 -> close 3 -> fork 순서에서는 부모의 fd_table[4]가 NULL이 아닌데 자식의 같은 슬롯이 NULL로 남는지만 보면 된다. 이 비교 하나로 next_fd와 실제 열린 슬롯을 왜 나눠 봐야 하는지 확인할 수 있다.

fd를 보면 “이 숫자를 어느 프로세스의 fd_table에서 찾는가?”부터 확인하고, fork()를 보면 “열린 슬롯을 모두 복제하는가, 아니면 보조 변수 범위만 보는가?”를 보면 된다. 이 두 가지만 분리해도 fd 번호, struct file, 파일 offset, 프로세스 종료 정리가 한 흐름으로 보인다.
