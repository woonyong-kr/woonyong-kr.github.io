thread_init() — 스레딩 시스템 초기화

thread_init()은 부팅 직후 아직 이름 없는 커널 실행 흐름을 main 스레드로 등록한다. 이후 동기화와 스케줄러 코드는 이 등록 정보를 바탕으로 현재 스레드를 찾는다.

thread_init() 구조

PintOS가 부팅 직후 실행하는 코드 흐름에는 아직 스레드 이름과 상태가 없다. thread_init()은 이 흐름을 “main” 커널 스레드로 등록해 스레드 시스템 안으로 편입한다. 호출 전에는 thread_current()를 사용할 수 없으며, 호출 후에는 스레드를 전제로 하는 lock, semaphore, scheduler 인프라를 사용할 수 있다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

CPU가 직접 다루는 것은 “스레드”라는 운영체제 개념이 아니라 RSP(스택 포인터), RIP(명령 포인터), CR3(페이지 테이블), 각종 레지스터다. PintOS는 struct thread 같은 메타데이터를 스택 페이지에 배치하고 RSP에서 그 위치를 역산하는 소프트웨어 규약으로 현재 스레드를 찾는다.

부팅 직후 CPU는 부트 로더가 설정한 스택과 GDT를 사용해 커널 코드를 실행한다. 이 시점에는 다음 조건이 남아 있다.

  • 스택 페이지에 struct thread가 없다
  • ready_list, tid_lock 등 스케줄링 인프라가 미초기화 상태다
  • thread_current()의 반환값을 현재 스레드로 사용할 수 없다

thread_init()은 현재 실행 흐름에 struct thread를 연결하고 관련 자료구조를 초기화해 이 간극을 메운다.

실제 OS (Linux)

PintOS의 초기화 과정을 이해하기 위한 비교 대상으로, 이 문서는 Linux의 start_kernel() → sched_init() → init_idle() 순서를 대응 관계로 제시한다. Linux의 최초 프로세스(PID 0, swapper)는 정적으로 선언된 init_task 구조체로 표현된다. 이 비교에서는 커널 진입 시점의 실행 흐름을 struct task_struct에 연결한다는 점을 PintOS의 initial_thread와 공통점으로 본다.

현재 태스크를 찾는 구체적인 규약은 다르다. 이 문서가 제시한 비교에 따르면 Linux는 per-CPU 변수(current_task)로 현재 태스크를 추적하고, PintOS는 RSP를 페이지 경계로 내려 struct thread를 찾는다. 이 절은 두 구현의 대응 관계를 설명하기 위한 범위이며, 제시된 코드로 Linux 동작 전체를 검증한 결과는 아니다.

PintOS 구현

thread_init() 전체 흐름

함수는 인터럽트가 꺼져 있는지 확인한 뒤 임시 GDT, 전역 자료구조, 최초 스레드 순서로 초기화한다.

단계별 분석

1단계: 임시 GDT 재로드

부트 로더(loader.S)가 설정한 GDT는 실모드에서 보호모드로 전환하기 위한 최소 GDT다. thread_init()은 커널 코드와 데이터 세그먼트를 포함한 임시 GDT를 설치한다. 유저 세그먼트는 이후 gdt_init()에서 추가된다.

2단계: 전역 자료구조 초기화

자료구조용도
tid_lockTID 할당 시 경쟁 방지용 lock
ready_list실행 대기 중인 스레드 목록
sleep_listtimer_sleep()으로 잠든 스레드 목록
destruction_req종료된 스레드의 자원 회수 대기 목록

3단계: initial_thread 등록

running_thread()는 현재 RSP를 페이지 경계(4 KB)로 내려 struct thread 포인터를 얻는다. 이 계산이 성립하려면 부트 로더가 스택의 바닥을 페이지 경계에 맞춰 두어야 한다.

init_thread()는 struct thread의 필드를 초기화한다.

init_thread()이 임시로 설정한 THREAD_BLOCKED 상태는 곧바로 initial_thread->status = THREAD_RUNNING으로 바뀐다. 이 스레드가 시스템 최초의 RUNNING 상태 스레드가 된다.

thread_init() 후의 세계

thread_init()이 반환되면 다음 조건이 성립한다.

  • thread_current()가 “main” 스레드를 반환한다
  • lock_acquire(), sema_down() 등 동기화 함수를 사용할 수 있다
  • console_init()에서 콘솔 출력용 lock을 잡을 수 있다
  • 인터럽트는 아직 OFF 상태이며 스케줄링은 시작되지 않았다

스케줄링은 이후 thread_start()가 idle 스레드를 생성하고 intr_enable()을 호출한 뒤 시작된다.

thread_init() 값 추적

다음 개념도는 initial_thread의 스택 페이지와 tf.rsp, THREAD_MAGIC의 관계를 나타낸다.

%% initial_thread의 스택 레이아웃
flowchart TD
  page["offset 0<br/>struct thread<br/>.name = &quot;main&quot;<br/>.status = RUNNING<br/>.tid = 1<br/>.priority = 31 (PRI_DEFAULT)<br/>.magic = 0xcd6abf4b<br/>사용 가능 공간<br/>struct thread와 커널 스택 사이의 여유 영역<br/>커널 스택"]
  calc["tf.rsp 초기값<br/>tf.rsp = (uint64_t)t + PGSIZE - sizeof(void *)<br/>= t + 4096 - 8<br/>= t + 4088"]
  magic["검사 기준<br/>THREAD_MAGIC = 0xcd6abf4b<br/>스택 오버플로우 감지용 매직 넘버"]
  page -->|"init_thread()가 tf.rsp 설정"| calc
  page -->|"struct thread 끝부분 검사"| magic

부팅 순서에서 thread_init()은 명령행 옵션을 처리한 다음, 콘솔과 메모리 관련 초기화를 시작하기 전에 호출된다.

main() 호출 순서:
  bss_init()          ← BSS 영역 0으로 초기화
  read_command_line() ← 커널 인자 파싱
  parse_options()     ← 옵션 해석
  thread_init()       ← ★ 여기서 스레드 시스템 탄생
  console_init()      ← 콘솔 lock 초기화 (thread_init 필요)
  palloc_init()       ← 페이지 할당기 초기화
  malloc_init()       ← malloc 초기화
  paging_init()       ← 페이지 테이블 설정
  ...
  thread_start()      ← idle 스레드 생성 + 스케줄링 시작

순서도 / 개념도

아래 흐름은 thread_init()이 임시 GDT와 전역 자료구조를 초기화하고, 현재 실행 흐름을 RUNNING 상태 스레드로 등록한 뒤 후속 부팅 단계로 넘기는 과정을 보여 준다.

%% thread_init() 부팅 흐름
flowchart TD
  thread_init["thread_init()"]
  gdt["임시 GDT 재로드<br/>lgdt()"]
  globals["전역 자료구조 초기화<br/>ready_list, sleep_list<br/>tid_lock, destruction_req"]
  init["init_thread()<br/>memset, name = &quot;main&quot;<br/>priority = PRI_DEFAULT"]
  running_status["status = THREAD_RUNNING<br/>tid = 1"]
  return["thread_init() 반환"]
  current["thread_current()<br/>사용 가능"]
  next_init["console_init()<br/>palloc_init()<br/>..."]
  start["thread_start()<br/>idle 스레드 + intr_enable()"]
  boot["boot"]
  running["running"]
  boot --> thread_init
  thread_init --> gdt
  gdt --> globals
  globals --> running
  running --> init
  init --> running_status
  running_status --> return

  current --> next_init
