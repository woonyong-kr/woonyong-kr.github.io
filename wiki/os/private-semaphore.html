Private Semaphore 대기

Private Semaphore 대기

범위: 이 문서는 대기자별 private semaphore가 신호 대상을 분리하고 신호를 보존하는 일반 원리와 선택 기준을 설명하며, PintOS와 Linux/POSIX 구현 서술은 패턴을 이해하기 위한 예시다. 코드 위치, 자료구조 크기, 스택 안전성, 정렬 복잡도와 실제 동작에 관한 판단은 특정 코드와 버전, 실행 기록 또는 성능 측정을 별도로 확인해야 한다.

PintOS condition variable은 대기 스레드마다 초기값 0짜리 전용 세마포어를 두어, 공유 세마포어 한 개에서 생길 수 있는 신호 도난과 유실을 막는다.

Private Semaphore 대기 구조

Private semaphore는 PintOS의 condition variable 구현에서 사용하는 패턴으로, 각 대기 스레드가 자기만의 초기값 0 세마포어를 갖는 것이다. cond_wait() 호출 시 스택에 struct semaphore_elem을 생성하고, 그 안의 semaphore로 sema_down() → BLOCKED 한다. cond_signal()은 대기자 리스트에서 최고 우선순위의 semaphore_elem을 골라 sema_up() 한다. 이 패턴 덕분에 “정확히 의도한 스레드 하나만 깨우기”와 “signal 유실 방지”가 모두 해결된다.

상세 설명

추상 개념 — 왜 private인가

Condition variable의 가장 단순한 구현은 공유 세마포어 하나(초기값 0)를 대기자들이 공유하는 것이다. 하지만 이 방식에는 치명적인 문제가 있다:

공유 세마포어의 문제 — Spurious Wakeup + Stolen Wakeup:

%% 공유 세마포어에서 stolen wakeup이 생기는 흐름
flowchart TD
  t0["시각 0<br/>Thread A cond_wait<br/>sema_down(S)<br/>A BLOCKED"]
  t1["시각 1<br/>Thread B cond_wait<br/>sema_down(S)<br/>B BLOCKED"]
  t2["시각 2<br/>Signaler cond_signal<br/>sema_up(S)<br/>S.value = 1"]
  t3["시각 3<br/>A는 lock_acquire 대기<br/>아직 lock을 잡지 못함"]
  t4["시각 4<br/>Thread C cond_wait<br/>sema_down(S)"]
  t0 --> t1
  t1 --> t2
  t2 --> t3
  t3 --> t4

C는 signal을 기다린 적이 없는데, 남아있던 value를 소비해버렸다. A는 영원히 BLOCKED 상태에 빠진다.

Private semaphore의 해결:

각 대기자가 자기만의 세마포어를 가지므로, signal은 정확히 특정 세마포어의 value를 올린다. 다른 스레드가 가로챌 수 없다.

%% Private semaphore가 signal 대상을 분리하는 흐름
flowchart TD
  a["시각 0<br/>A cond_wait<br/>sema_A 초기값 0<br/>A BLOCKED"]
  b["시각 1<br/>B cond_wait<br/>sema_B 초기값 0<br/>B BLOCKED"]
  signal["시각 2<br/>cond_signal<br/>sema_A.value++<br/>A만 깨어남"]
  c["시각 3<br/>C cond_wait<br/>sema_C 초기값 0<br/>sema_A 접근 불가"]
  a --> b
  b --> signal
  signal --> c

Signal 유실 방지 메커니즘

cond_wait()에서 lock_release() → sema_down() 사이에 시간 간격이 존재한다 (원자적이지 않음). 이 간격에 다른 스레드가 cond_signal()을 호출하면?

%% sema_down 전에 signal이 와도 value가 기억되는 흐름
flowchart LR
  a1["Thread A<br/>sema_init(&amp;waiter.semaphore, 0)"]
  switch["컨텍스트 전환<br/>A가 sema_down 전에 멈춤"]
  b1["Thread B<br/>lock_acquire(&amp;lock)<br/>조건 변경<br/>cond_signal<br/>sema_up(&amp;waiter.semaphore)<br/>waiter.semaphore.value = 1<br/>lock_release(&amp;lock)"]
  a2["Thread A 재개<br/>sema_down(&amp;waiter.semaphore)<br/>value == 1<br/>즉시 통과"]
  a1 --> switch
  switch --> b1
  b1 --> a2

세마포어의 value가 signal을 기억하므로, 대기자가 sema_down()에 도달하기 전에 signal이 와도 유실되지 않는다. 이것이 세마포어가 단순한 sleep/wakeup보다 우수한 이유다.

실제 OS (Linux / POSIX)

POSIX pthread_cond_wait():

Linux의 pthread_cond_wait() 내부도 유사한 원리를 사용하지만, futex 기반으로 구현된다:

  1. 현재 세마포어 시퀀스 번호(seq)를 기록
  2. mutex_unlock()
  3. futex(FUTEX_WAIT, &seq, expected_seq) — seq가 변하면 깨어남
  4. mutex_lock()

시퀀스 번호가 private semaphore의 value 역할을 한다. signal이 seq를 변경하면 futex가 즉시 통과한다.

Linux 커널 wait_event():

커널은 per-thread wait_queue_entry를 할당하고 wait queue에 넣는다. wake_up()이 이 entry를 찾아 깨운다. private semaphore와 동일한 “per-waiter token” 패턴이다.

PintOS 구현

자료구조

이 구조체는 cond_wait() 스택 프레임에 할당된다. 스레드가 BLOCKED → READY → cond_wait() 반환할 때까지 스택이 유효하므로, 동적 할당(malloc) 없이 안전하다.

메모리 레이아웃:

%% cond_wait() 스택 프레임 안의 semaphore_elem 배치
flowchart TD
  stack["Thread A의 커널 스택 (4 KiB)<br/>스택 상단<br/>...<br/>cond_wait() 스택 프레임<br/>waiter.elem (16 B) - condition.waiters에 연결<br/>waiter.semaphore<br/>value (4 B) = 0 - sema_down에서 검사<br/>waiters (16 B) - Thread A 자신이 들어감<br/>...<br/>스택 바닥: thread 구조체"]

cond_wait() 내부의 private semaphore

핵심: ③에서 list_push_back으로 삽입 순서를 FIFO로 유지하되, cond_signal()에서 list_sort()로 우선순위 재정렬한다. 삽입 시점의 우선순위가 아닌 signal 시점의 동적 우선순위를 기준으로 깨울 대상을 선택하기 위함이다 (priority donation으로 우선순위가 변할 수 있으므로).

cond_signal() 내부의 private semaphore

cmp_sema_priority()는 각 semaphore_elem의 semaphore.waiters에서 가장 높은 우선순위 스레드를 찾아 비교한다. 이중 간접 참조가 필요한 이유: private semaphore의 waiters에 있는 스레드가 곧 깨어날 대상이기 때문이다.

%% cmp_sema_priority가 private semaphore의 waiters를 기준으로 깨울 대상을 고르는 흐름
flowchart LR
  before["정렬 전 condition.waiters<br/>sema_elem_A - sema_A.waiters: Thread A(50)<br/>sema_elem_B - sema_B.waiters: Thread B(30)<br/>sema_elem_C - sema_C.waiters: Thread C(40)"]
  after["cmp_sema_priority 정렬 후<br/>sema_elem_A(50)<br/>sema_elem_C(40)<br/>sema_elem_B(30)"]
  wake["깨울 대상<br/>list_pop_front<br/>sema_elem_A<br/>sema_up(&amp;sema_A)<br/>Thread A 깨어남"]
  before --> after
  after --> wake

Private Semaphore 대기 값 추적

항목값
struct semaphore_elem 크기list_elem(16) + semaphore(value 4 + waiters 16 + padding) = ~40 bytes
private semaphore 초기값0 (signal 전까지 BLOCKED 보장)
스택 할당 위치cond_wait()의 로컬 변수, 커널 스택 4 KiB 내
malloc 호출 수0 (힙 할당 없음)
cond_signal() list_sort 복잡도O(n log n), n = 대기자 수
cmp_sema_priority 내부 list_sort각 sema의 waiters도 재정렬 (donation 반영)
