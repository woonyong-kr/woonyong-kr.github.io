thread_create() 후 yield와 우선순위 선점

thread_create() 후 yield와 우선순위 선점

thread_create()는 새 스레드를 READY 상태로 만든 직후 현재 스레드와 우선순위를 비교한다. 새 스레드의 우선순위가 더 높으면 현재 스레드는 즉시 thread_yield()를 호출해 CPU를 양보해야 한다.

thread_create() 후 yield의 역할과 차이

thread_create()는 새 스레드를 만든 뒤, 그 스레드의 우선순위가 현재 실행 중인 스레드보다 높으면 즉시 thread_yield()를 호출해 CPU를 양보한다. thread_unblock() 뒤의 yield가 기존 스레드가 깨어나는 시점의 선점 지점이라면, 새 스레드 생성 직후의 yield는 새로 생성된 스레드를 위한 선점 지점이다. 이 검사가 없으면 우선순위가 높은 스레드가 ready_list에 들어간 뒤에도 다음 timer interrupt까지 기다려야 할 수 있다.

상세 설명

새 스레드의 우선순위가 더 높을 때

하드웨어는 스레드의 우선순위를 직접 판단하지 않는다. CPU는 현재 RIP가 가리키는 명령어를 실행할 뿐이다. Priority preemption은 OS가 “더 높은 우선순위의 스레드가 READY 상태가 되면 현재 스레드를 선점한다”라는 규칙을 적용하는 소프트웨어 정책이다. timer interrupt는 선점 여부를 주기적으로 판단할 기회를 제공한다. preemptive priority scheduling은 여기에 더해 새 스레드가 생성되거나 기존 스레드가 unblock되는 시점에도 즉시 yield가 필요한지 판단한다.

실제 OS (Linux/Windows)

Linux CFS에서는 vruntime을 기준으로 우선순위가 반영된다. wake_up_process() 등에서 깨어난 태스크의 vruntime이 현재 실행 중인 태스크보다 충분히 작으면 resched_curr()를 통해 TIF_NEED_RESCHED 플래그를 설정하고, 다음 preemption point인 syscall 리턴이나 interrupt 리턴 시점에 context switch가 일어난다. Linux RT 스케줄러(SCHED_FIFO/RR)는 PintOS와 마찬가지로 우선순위 비교를 바탕으로 preemption을 트리거한다.

Windows의 경우에는 KiReadyThread()에서 새 스레드의 priority가 현재 실행 중인 스레드보다 높을 때 DPC를 큐에 넣어 context switch를 요청한다고 설명할 수 있다. 다만 이는 해당 구현 흐름을 요약한 설명이며, 이 문서에는 이를 독립적으로 검증할 원문 근거가 제시되어 있지 않다.

PintOS 구현

thread_create()의 핵심 흐름은 다음과 같다.

단계별 분석:

  1. palloc_get_page(PAL_ZERO): 커널 풀에서 1 page(4 KiB)를 할당한다. 할당된 한 페이지는 struct thread와 커널 스택이 함께 사용한다.

  2. init_thread(t, name, priority): struct thread의 status를 THREAD_BLOCKED로 초기화하고 priority와 magic 값을 설정한다.

  3. thread_unblock(t): 새 스레드를 ready_list에 삽입하고 status를 THREAD_READY로 변경한다. 이때 인터럽트를 끈 뒤 list_insert_ordered()를 사용해 우선순위 순서에 맞게 삽입한다.

  4. Priority 비교 → yield: thread_unblock() 직후 새 스레드의 priority가 현재 스레드의 priority보다 높으면 thread_yield()를 호출해 CPU를 즉시 양보한다. thread_yield()는 현재 스레드를 ready_list에 넣은 뒤 schedule()을 호출한다.

thread_yield()의 동작:

schedule()에서 이어지는 next_thread_to_run()은 ready_list의 front, 즉 priority가 가장 높은 스레드를 꺼낸다. 따라서 방금 unblock된 새 스레드의 priority가 가장 높다면 그 스레드가 즉시 실행된다.

두 지점의 역할 분담:

지점함수의미
thread_create() 후thread_create()우선순위가 높은 새 스레드가 생성됨
thread_unblock() 후sema_up(), lock_release() 등기존 스레드가 BLOCKED 상태에서 깨어남

두 지점은 모두 “새로 READY 상태가 된 스레드의 우선순위가 현재 스레드보다 높은가?”를 검사한다. thread_create()는 내부에서 thread_unblock()을 호출하므로, thread_unblock() 안에서 yield하면 thread_create()의 yield가 중복되는 것처럼 보일 수 있다. 그러나 PintOS 기본 구현의 thread_unblock()에는 yield가 내장되어 있지 않으므로, thread_create()가 직접 우선순위를 검사해야 한다.

thread_create() 후 yield의 값 추적

시나리오: 3개 스레드의 우선순위 경합

시점 0: Thread A (priority 31) 실행 중
시점 1: Thread A가 thread_create("B", 40, ...) 호출
        → thread_unblock(B): B(40)가 ready_list에 삽입
        → 40 > 31이므로 thread_yield() 호출
        → schedule(): A(31) → ready_list, B(40) → RUNNING
시점 2: Thread B 실행 중
시점 3: Thread B가 thread_create("C", 35, ...) 호출
        → thread_unblock(C): C(35)가 ready_list에 삽입
        → 35 < 40이므로 yield 안 함
        → ready_list: [C(35), A(31)]

yield가 일어나지 않는 경우를 살펴보자. B(40)가 C(35)를 생성해도 B의 우선순위가 더 높으므로 B가 계속 실행된다.

timer_interrupt와의 차이:

  • timer interrupt: 4 ticks(TIME_SLICE)마다 선점 기회를 제공한다.
  • thread_create yield: 새 스레드를 생성한 직후 tick 지연 없이 선점 여부를 판단한다.

priority 63인 스레드가 생성되었는데 timer 방식만 사용한다면 최대 TIME_SLICE 하나만큼 실행이 지연될 수 있다. PintOS 기본값을 기준으로 계산하면 4 ticks × 약 10ms이므로 약 40ms에 해당한다.
