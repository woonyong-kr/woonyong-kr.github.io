부모가 먼저 종료되면 자식 상태는 누가 수거하는가

부모가 wait() 없이 먼저 종료되어도, 살아 있는 자식의 child_status는 바로 지우면 안 된다. 종료 상태를 쓸 자식이 아직 남아 있기 때문이다.

고아 프로세스 쟁점

처음에는 “부모가 죽었으니 부모의 child_status_list도 같이 사라지면 되지 않을까?”라고 생각하기 쉽다. 하지만 자식이 아직 살아 있다면 그 레코드는 바로 지우면 안 된다.

꼬리에 꼬리를 물면 질문은 이렇게 바뀐다.

  • 부모가 먼저 종료되어도 자식은 계속 실행될 수 있는가?
  • 살아 있는 자식의 child_status는 어느 리스트에 남아야 하는가?
  • 이미 종료한 자식 record와 아직 살아 있는 자식 record는 왜 다르게 처리해야 하는가?
  • root가 reparent된 자식을 wait()하면 어떤 값이 돌아오는가?
  • QEMU는 orphan, zombie, reparent 정책을 알고 있을까?

여기서는 exit 정상 수거 흐름에서 빠진 한 가지 경우, 즉 부모가 먼저 죽는 흐름만 떼어 본다.

부모가 먼저 종료되면 자식 상태 혼동

wait()는 부모가 자식 종료 상태를 수거하는 약속이다. 그런데 프로그램은 항상 착하게 wait()를 호출하고 종료하지 않는다.

예를 들어 shell이 다음 프로그램을 실행했다고 하자.

부모 역할을 하던 중간 프로세스는 자식 pid만 남기고 먼저 끝난다. 그 순간 커널에는 두 가지 선택지가 있다.

선택문제
부모의 child_status_list를 통째로 free아직 살아 있는 자식이 나중에 자기 종료 상태를 쓸 곳이 사라짐
모든 record를 영원히 남김기다리는 주체가 없어도 record가 계속 쌓임
살아 있는 자식 record만 전역 orphan 리스트로 넘김구현은 더 필요하지만 수명 문제가 풀림

이 말은 즉, 부모 종료 처리는 단순 cleanup이 아니라 남은 자식 상태 record의 소유권을 다시 정하는 지점이다.

부모가 먼저 종료되면 자식 상태 흐름

PintOS의 이 구현은 전역 static 리스트 orphan_status_list를 임시 보관소로 쓴다.

핵심은 record 상태에 따라 처리법이 다르다는 점이다.

record 상태부모 종료 시 처리
자식이 이미 종료했고 아직 wait되지 않음부모가 더 기다릴 수 없으므로 free
자식이 아직 살아 있음orphaned = true로 표시하고 orphan_status_list로 이동
root 자신이 종료 중reparent하지 않음

orphaned는 “원래 부모가 사라졌으니 일반적인 부모 wait 경로가 아니다”라는 표시다.

Orphan Reparent 시퀀스

sequenceDiagram
    participant P as Parent Thread
    participant K as Kernel (process.c)
    participant OL as orphan_status_list (전역 static)
    participant C as Child Thread

    Note over P: Parent가 exit() 호출
    P->>K: process_exit()
    K->>K: reparent_or_reap_children(curr)

    alt cs->exited && !cs->waited
        K->>K: list_remove(&cs->elem)
        K->>K: free(cs)
        Note over K: 이미 종료+미수거 → 즉시 해제
    else 자식이 아직 살아 있음
        K->>K: cs->orphaned = true
        K->>OL: list_push_back(&orphan_status_list, &cs->elem)
        Note over OL: orphan record 보관
    end

    K->>K: finish_self_status(curr)
    K->>K: cs->exited = true, sema_up(&cs->wait_sema)
    Note over P: Parent thread 종료 완료

    Note over C: Child가 나중에 exit() 호출
    C->>K: process_exit()
    K->>K: reparent_or_reap_children(curr) (자식의 자식 처리)
    K->>K: finish_self_status(curr)

    alt cs->orphaned && !cs->waited
        K->>K: free(cs)
        K->>K: self_status = NULL
        Note over K: 아무도 안 기다리므로 자가 정리
    else root가 wait(child_tid) 호출한 경우
        Note over K: waited=true이므로 process_wait()에서 수거
    end

reparent_or_reap_children 결정 흐름

flowchart TD
    A[reparent_or_reap_children 시작] --> B[curr->child_status_list 순회]
    B --> C{cs->exited == true?}

    C -->|Yes| D{cs->waited == true?}
    D -->|No| E[list_remove + free\n이미 종료 + 미수거 → 해제]
    D -->|Yes| F[이 경우는 발생하지 않음\nwait 완료 시 이미 free됨]

    C -->|No| G[자식이 아직 살아 있음]
    G --> H[cs->orphaned = true]
    H --> I[list_remove from curr->child_status_list]
    I --> J[list_push_back to orphan_status_list]

    E --> K{다음 elem?}
    J --> K
    F --> K
    K -->|Yes| C
    K -->|No| L[종료]

실제 운영체제

Linux와 Unix 계열에서는 부모가 먼저 종료된 자식은 보통 init 또는 subreaper 역할을 하는 프로세스 쪽으로 재부모화된다. 자식이 나중에 종료하면 새 보호자가 종료 상태를 수거할 수 있다. 실제 Linux는 process group, signal, namespace, subreaper, thread group 같은 조건이 붙기 때문에 PintOS보다 훨씬 복잡하다.

Windows는 Unix식 fork()와 waitpid() 중심 모델이 아니다. 프로세스는 커널 오브젝트이고, 누가 process handle을 들고 있는지가 수명과 관찰 가능성을 좌우한다. 부모가 먼저 종료되어도 다른 프로세스가 handle을 갖고 있으면 그 handle로 종료를 기다리거나 exit code를 읽을 수 있다.

공통점은 있다. 실제 OS도 “실행 주체의 수명”과 “종료 상태를 관찰할 수 있는 record의 수명”을 분리한다.

PintOS

이 구현에서 orphan record는 전역 static 리스트 orphan_status_list에 보관된다.

파일:

  • SW_AI-W11-pintos/pintos/userprog/process.c
  • SW_AI-W11-pintos/pintos/threads/thread.c
  • SW_AI-W11-pintos/pintos/include/threads/thread.h

initd()는 최초 유저 프로세스가 시작될 때 root를 저장한다.

thread.c에는 root thread 포인터를 읽고 쓰는 함수가 있다.

orphan_status_list는 process.c 44번째 줄에 static global로 선언되어 있고, ensure_orphan_status_list() (535줄)가 최초 사용 시 list_init()으로 초기화한다.

부모가 종료되면 thread_exit()이 process_exit()을 부르고, process_exit()은 세 일을 한다.

여기서 이번 Trace의 핵심은 reparent_or_reap_children()이다.

자식이 나중에 종료하면 finish_self_status()가 자기 record를 마무리한다.

이 말은 즉, 아무도 기다리지 않는 orphan record는 자식이 종료하는 순간 스스로 정리된다. 반대로 root가 이미 wait(orphan_pid)를 시작했다면 waited = true가 되어 process_wait() 쪽에서 상태를 읽고 free한다.

QEMU

QEMU는 이 정책을 모른다.

QEMU가 제공하는 것은 다음 층이다.

  • guest CPU register state
  • guest physical memory
  • syscall 명령 실행과 예외/인터럽트 전달
  • GDB stub을 통한 register와 memory 관찰

근거 위치:

  • gdbstub/gdbstub.c
    • gdb_read_register()
    • gdb_write_register()
    • gdb_create_default_process()
  • target/i386/gdbstub.c
    • x86_cpu_gdb_read_register()
  • target/i386/cpu.h
    • CPUX86State

QEMU 코드에도 “orphan CPU”라는 표현이 나오지만, 이것은 QEMU GDB stub이 CPU cluster에 속하지 않은 vCPU를 GDB process로 묶는 말이다. PintOS의 child_status reparent와는 다른 층의 용어다.

PintOS의 orphan reparent는 실제 OS의 init 재부모화를 그대로 구현한 것이 아니다. “부모가 먼저 사라져도 살아 있는 자식 record는 즉시 free하면 안 된다”는 수명 문제를 과제 코드로 줄인 모델이다.

부모가 먼저 종료되면 자식 상태 코드

struct child_status에는 orphan 여부를 표시하는 필드가 있다.

struct thread는 자식 record 목록과 자기 record 포인터를 둘 다 가진다.

process.c에는 orphan record를 보관하는 전역 리스트가 있다.

process_fork()는 record를 부모 리스트에 넣고, 자식의 __do_fork()는 같은 record를 self_status로 잡는다.

부모 종료 시점의 핵심 함수는 reparent_or_reap_children()이다.

자식 종료 시점의 핵심 함수는 finish_self_status()다.

이 두 함수가 함께 있어야 부모 먼저 종료와 자식 먼저 종료를 둘 다 처리할 수 있다.

정리

  • 부모가 먼저 종료되어도 살아 있는 자식의 child_status를 즉시 free하면 안 된다.
  • 이 PintOS 구현은 살아 있는 자식 record를 orphan_status_list (전역 static 리스트)로 옮기고 orphaned = true를 표시한다.
  • 이미 종료했고 wait되지 않은 자식 record는 부모 종료 시점에 더 이상 수거자가 없으므로 free한다.
  • 자식이 나중에 종료하면 finish_self_status()가 exited를 세우고, 아무도 기다리지 않는 orphan record는 스스로 free한다.
  • orphan_status_list는 ensure_orphan_status_list()에 의해 lazy 초기화된다.
  • QEMU는 orphan/reparent 정책을 모르고, guest register와 memory를 관찰할 수 있는 하드웨어 환경만 제공한다.
