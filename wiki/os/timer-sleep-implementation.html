timer_sleep 구현

timer_sleep 구현

확인 범위: 이 문서는 sleep/wakeup의 일반 원리와 구현 선택 기준을 PintOS의 timer_sleep 및 Linux·QEMU와의 비교를 통해 설명한다. 제시된 코드 좌표, 버전별 내부 구조, 실행·GDB 관찰 결과, 재현성 및 성능·복잡도 판단은 실제 대상 코드와 환경의 실행 기록이나 측정으로 별도 검증해야 한다.

한 줄 요약: timer_sleep은 busy-wait로 CPU를 태우는 대신 스레드를 BLOCKED로 재워 sleep_list에 넣고 타이머 인터럽트가 시각을 검사해 깨우며, 재우는 구간은 인터럽트를 끈 채 처리해야 깨우기 신호를 놓치지 않는다.

timer_sleep 구현 구조

timer_sleep(ticks)는 호출한 스레드를 지정된 틱 수만큼 재운 뒤 깨우는 함수다. PintOS의 기본 구현은 busy-wait(틱이 지날 때까지 CPU를 소모하며 반복)이지만, Project 1에서 sleep_list 기반의 block/unblock 방식으로 개선한다. 이 개선은 CPU 낭비를 없애고, alarm clock의 기본 동작을 올바르게 구현하는 첫 번째 과제다.

상세 설명

추상 개념 — Sleep/Wakeup 메커니즘

OS에서 “일정 시간 후 깨어나기”는 두 단계로 나뉜다.

  1. Sleep: 현재 스레드를 실행 가능 목록에서 빼고 (BLOCKED 상태), 깨울 조건(시각)을 기록한다.
  2. Wakeup: 타이머 인터럽트마다 조건을 검사하여, 조건이 만족된 스레드를 READY 상태로 복원한다.

핵심 제약: Sleep 과정에서 인터럽트 비활성화가 필수다. thread_block() 호출과 sleep_list 삽입 사이에 타이머 인터럽트가 끼어들면 스레드가 영원히 깨지 못할 수 있기 때문이다.

실제 OS (Linux)

Linux에서는 schedule_timeout()이 같은 역할을 한다. 내부적으로 hrtimer(고해상도 타이머)를 등록하고, 타이머 만료 시 wake_up_process()를 콜백으로 호출한다. PintOS의 sleep_list + tick 비교는 Linux의 timer wheel을 극도로 단순화한 것이다.

QEMU 에뮬레이션

timer_sleep은 순수 소프트웨어 로직이므로 QEMU가 특별히 개입하는 부분은 없다. 다만 sleep/wakeup의 타이밍 근원인 timer interrupt는 QEMU의 i8254 PIT 에뮬레이션에 의존한다.

단계QEMU 구성요소동작
1i8254 PIT (hw/timer/i8254.c)host timer 만료 → IRQ0 raise
2i8259 PIC (hw/intc/i8259.c)IRQ0 → CPU interrupt 전달
3TCG (target/i386/tcg/cc_helper.c)guest timer_interrupt() 실행
4guest OSthread_awake(ticks) → sleep_list 순회

QEMU의 -icount 옵션을 사용하면 가상 clock을 결정적으로 진행시킬 수 있어, timer_sleep 테스트의 재현성이 높아진다. 기본(real-time) 모드에서는 host 부하에 따라 tick 간격이 불규칙해질 수 있다.

GDB에서 sleep/wakeup 관찰:

(gdb) b thread_sleep
(gdb) commands
  p/d thread_current()->wake_tick
  p/d timer_ticks()
  continue
end
(gdb) b thread_awake
(gdb) commands
  p/d global_ticks
  info threads
  continue
end

이렇게 하면 sleep 진입 시 wake_tick과 현재 ticks를, wakeup 시 global_ticks와 깨어날 스레드를 자동으로 출력한다.

Linux hrtimer 상세 비교

PintOS의 timer_sleep은 Linux schedule_timeout() / msleep()의 교육용 단순화다. 주요 차이:

항목PintOS timer_sleepLinux schedule_timeoutLinux hrtimer_nanosleep
해상도1 tick (≈ 10 ms, TIMER_FREQ=100)1 jiffy (1~10 ms, HZ 의존)나노초 (ns)
자료구조정렬된 sleep_list (linked list)timer wheel (계층적 해시)red-black tree
삽입 비용O(n) — list_insert_orderedO(1) — bucket 직접 삽입O(log n) — RB tree
깨우기 비용O(k) — front에서 k개 popO(1) amortized — wheel cascadeO(log n) — tree 제거
인터럽트 원자성intr_disable() 전역spin_lock_irqsave() per-CPUhrtimer_lock
멀티코어단일 CPU, 전역 sleep_listper-CPU timer wheelper-CPU hrtimer base
오버슬립 보정없음 (다음 tick에 깨움)없음 (jiffy 정밀도)재프로그래밍 (HRTIMER_MODE_ABS)

timer wheel 구조 (Linux):

Level 0: 64 buckets — 각 1 jiffy 간격     (0~63 jiffies)
Level 1: 64 buckets — 각 8 jiffy 간격      (64~575 jiffies)
Level 2: 64 buckets — 각 64 jiffy 간격     (576~4671 jiffies)
Level 3: 64 buckets — 각 512 jiffy 간격    (4672~37439 jiffies)
Level 4: 64 buckets — 각 4096 jiffy 간격   (37440~299135 jiffies)

만료 시 하위 level로 “cascade”하여 정밀한 bucket에 재배치한다. PintOS의 단일 정렬 리스트 대비 삽입이 O(1)인 대신 cascade 비용이 간헐적으로 발생한다.

timer_sleep 구현 숫자 추적

구체적 타이밍 시나리오:

현재 ticks = 1000, timer_sleep(50) 호출
→ wake_tick = 1000 + 50 = 1050

sleep_list 상태 (정렬된 순서):
  [thread A, wake_tick=1020]
  [thread B, wake_tick=1035]
  [thread C, wake_tick=1050]  ← 새로 삽입
  [thread D, wake_tick=1100]

tick 1020: thread_awake(1020)
  → A의 wake_tick(1020) <= 1020 → unblock
tick 1035: thread_awake(1035)
  → B의 wake_tick(1035) <= 1035 → unblock
tick 1050: thread_awake(1050)
  → C의 wake_tick(1050) <= 1050 → unblock
  → D의 wake_tick(1100) > 1050 → break (이후 검사 불필요)

정렬 삽입 비용: O(n) — sleep_list에 n개 스레드가 있을 때. 깨우기 비용: O(1) amortized — front에서만 꺼내고, wake_tick이 아직 미래이면 즉시 break.

    TI->>TI: ticks++ → 1050
    TI->>TA: thread_awake(1050)
    TA->>SL: list_front() → wake_tick 검사
    TA->>User: thread_unblock() → READY

경쟁 조건 방지

인터럽트 비활성화가 필수인 이유:

  • 위험한 시나리오 (intr_disable 없이):
    1. cur->wake_tick = 1050 // 설정 완료
    1. 타이머 인터럽트 발생
  • → thread_awake(1050) 호출
  • → sleep_list에 cur가 아직 없으므로 무시
    1. list_insert_ordered(sleep_list, …) // 이제 삽입
    1. thread_block() // BLOCKED
  • → 이미 깨울 시각이 지났는데 sleep_list에 남아 영원히 BLOCKED

intr_disable()로 ②③④를 원자적으로 묶으면 이 문제가 발생하지 않는다.
