프로세스와 스레드 추상화

프로세스와 스레드 추상화

범위: 이 문서는 프로세스와 스레드 추상화의 일반 원리와 Linux·Windows·PintOS·QEMU에서의 구현 차이를 개념적으로 설명한다. 구조체 필드와 크기, 코드 경로, GDB 출력, 수용 가능한 스레드 수 같은 구현·버전 의존 판단은 해당 코드와 실제 실행 기록 및 측정으로 별도 검증해야 한다.

CPU는 지금 실행할 명령어 흐름 하나만 직접 본다. OS는 주소 공간을 프로세스로, 실행 흐름을 스레드로 나누어 여러 프로그램이 동시에 움직이는 것처럼 만든다.

프로세스와 스레드 추상화 차이

CPU는 하나의 명령어 스트림만 실행할 수 있다. “프로그램 여러 개가 동시에 돈다”는 환상은 OS가 CPU 위에 프로세스와 스레드라는 추상화를 놓아 만든다. 프로세스는 독립된 주소 공간 + 자원 소유 단위이고, 스레드는 그 안에서 실제로 명령어를 실행하는 흐름 단위다. 이 둘을 분리함으로써 하나의 프로세스 안에서 여러 스레드가 같은 메모리를 공유하면서 병렬로 실행될 수 있다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

CPU 자체는 “프로세스”나 “스레드”라는 개념을 모른다. CPU가 아는 것은:

CPU가 관리하는 것레지스터의미
다음 명령어 위치RIPProgram Counter
스택 위치RSPStack Pointer
주소 공간CR3Page Table Root
권한 수준CS의 CPLRing 0/3

OS는 이 레지스터 세트를 저장하고 복원하는 것으로 스레드 전환을 구현한다. CR3를 바꾸면 주소 공간이 바뀌므로 프로세스 전환이 된다.

하드웨어가 제공하는 메커니즘:

  • CR3 레지스터: 로드하면 MMU가 참조하는 page table이 바뀐다 → 주소 공간 격리
  • TSS (Task State Segment): interrupt/exception은 CPU가 rsp0를 사용하고, PintOS syscall 경로는 syscall-entry.S가 rsp0를 읽어 kernel stack으로 명시적으로 전환
  • Timer interrupt: OS가 주기적으로 CPU를 빼앗아 다른 스레드에 넘길 기회 제공

실제 OS (Linux/Windows)

Linux에서 프로세스와 스레드는 모두 task_struct로 표현된다. 차이는 자원 공유 수준이다:

자원프로세스 (fork)스레드 (clone + CLONE_VM)
주소 공간 (mm_struct)복사 (COW)공유
파일 디스크립터 테이블복사공유
PID새 PID새 TID, 같은 TGID
시그널 핸들러복사공유
커널 스택별도별도

Windows는 프로세스(EPROCESS)와 스레드(ETHREAD)를 명시적으로 분리된 구조체로 관리한다. 프로세스가 주소 공간과 핸들 테이블을 소유하고, 스레드가 스케줄링 단위가 된다.

핵심 차이: Linux는 task_struct 하나로 통합, Windows는 2단 구조체로 분리.

PintOS 구현

PintOS는 단일 주소 공간 모델에서 시작해 점진적으로 확장한다:

Project 1 (Threads): 커널 스레드만 존재한다. 모든 스레드가 같은 커널 주소 공간을 공유한다. struct thread가 스케줄링 단위다.

%% 4KB page에 배치된 struct thread와 kernel stack
flowchart TD
  page["4 KB page 하나<br/>kernel stack<br/>↓<br/>grows downward<br/>magic<br/>스택 오버플로우 감지<br/>intr_frame tf<br/>문맥 전환용 레지스터 저장<br/>struct thread"]
  top["4 KB page top"]
  bottom["0, page bottom = struct thread 시작"]
  top --> page
  page --> bottom

struct thread의 핵심 필드:

필드크기역할
tid4B스레드 고유 식별자
status4BRUNNING / READY / BLOCKED / DYING
priority4B스케줄링 우선순위 (0~63)
name[16]16B디버깅용 이름
elem16Bready_list 또는 waiters의 원소
tf (intr_frame)192Bpacked 레지스터 snapshot
magic4B스택 오버플로우 감지 (0xcd6abf4b)

Project 2 (User Programs): struct thread에 프로세스 속성이 추가된다.

추가 필드역할
pml4유저 주소 공간의 page table root
fd_table파일 디스크립터 테이블
child_status_list자식 프로세스 상태 추적
running_file실행 파일 쓰기 보호

PintOS에서 프로세스 = 스레드 1개 + 유저 주소 공간이다. 멀티스레드 프로세스는 지원하지 않는다. 따라서 struct thread가 사실상 Linux의 task_struct와 프로세스 구조체를 겸한다.

Project 3 (Virtual Memory): supplemental_page_table spt 필드가 추가되어 demand paging을 지원한다.

QEMU 에뮬레이션

QEMU는 “프로세스”와 “스레드”를 전혀 인식하지 못한다. QEMU가 보는 것은:

QEMU가 보는 것OS가 부여한 의미
CPUX86State.regs[R_EAX]어떤 thread의 RAX 값
CPUX86State.cr[3]어떤 process의 주소 공간
CPUX86State.eip어떤 thread의 다음 명령어
RAMBlock 특정 영역의 4KB어떤 thread의 struct thread + kernel stack

CR3가 바뀌면 QEMU는 softmmu TLB를 flush할 뿐, “프로세스가 전환되었다”는 사실을 모른다. RSP가 다른 커널 스택을 가리켜도 QEMU는 “스레드가 바뀌었다”고 인식하지 않는다.

GDB로 thread 관찰하기:

이 관찰에서 중요한 점: GDB가 struct thread의 필드를 보여주지만, 이는 QEMU가 아닌 GDB의 DWARF 디버그 정보 해석 결과다. QEMU 자체는 thread_current()가 무엇인지 모르고, 단지 guest 메모리의 바이트를 제공할 뿐이다.

프로세스와 스레드 추상화 값 추적

struct thread는 4 KB page 하나에 들어가야 한다:

구성 요소대략적 크기
struct thread 자체200400 bytes
magic4 bytes
kernel stack나머지 (~3.6 KB)
합계4096 bytes

커널 스택이 ~3.6 KB밖에 안 되므로 커널 함수에서 큰 지역 변수를 잡으면 안 된다. char buf[4096] 같은 선언은 stack overflow → magic 필드 덮어씀 → thread_current() assertion failure.

tid 범위: tid_t는 int (4바이트). allocate_tid()가 순차 발급하므로 이론상 2^31 - 1개까지 가능하나, 실제로는 메모리 제약이 먼저 온다. thread 1개 = 4 KB이므로 64 MB RAM에서 최대 ~16,000개.
