주소 변환 효과 재현 — QEMU의 MMU 에뮬레이션

주소 변환 효과 재현 — QEMU의 MMU 에뮬레이션

확인 범위: 이 문서는 실제 x86-64 MMU와 QEMU TCG의 SoftMMU·SoftTLB가 주소 변환 효과를 재현하는 일반 원리와 확인 기준을 설명한다. 구체적인 함수·구조체·크기·호출 경로와 PintOS 변환 예시, 실행 비용은 QEMU 버전·target·build configuration 및 실제 코드와 실행·측정 결과로 별도 검증해야 한다.

한 줄 요약: QEMU는 하드웨어 MMU가 없어 SoftMMU와 SoftTLB로 게스트 페이지 테이블을 소프트웨어 워크해 VA→PA 변환 효과를 재현하며, 게스트에는 실제 MMU와 동일하게 보인다.

주소 변환 효과 재현 차이

실제 CPU에는 MMU(Memory Management Unit)가 있어서 가상 주소(VA)를 물리 주소(PA)로 변환한다. QEMU는 하드웨어 MMU가 없으므로 이 변환 효과를 소프트웨어로 재현해야 한다. 게스트 OS(PintOS)가 CR3에 PML4 주소를 설정하고 가상 주소로 메모리에 접근하면, QEMU의 TCG가 게스트 페이지 테이블을 소프트웨어 워크하여 GPA를 알아낸 뒤, RAMBlock을 거쳐 호스트 메모리에 실제 접근한다. 이 모든 과정이 게스트 입장에서는 하드웨어 MMU와 동일하게 보인다.

상세 설명

추상 개념 (실제 CPU의 MMU)

실제 x86-64 CPU에서 페이징이 활성화되면(CR0.PG=1), TLB miss 시 page table walk로 주소를 변환한다. 4KiB page는 보통 PML4→PDPT→PD→PT를 거치지만, TLB hit이면 walk가 없고 huge page는 상위 단계의 large-page entry에서 일찍 끝난다.

VA → PML4[bits 47:39] → PDPT[bits 38:30] → PD[bits 29:21] → PT[bits 20:12] → PA + offset[bits 11:0]

이 워크를 하드웨어(page table walker)가 자동으로 수행하고, TLB에 캐시한다. 페이지 테이블에 valid 엔트리가 없으면 pf(page fault)를 발생시킨다.

QEMU의 소프트웨어 MMU

QEMU TCG 모드에서는 하드웨어 MMU 대신 SoftMMU가 주소 변환을 담당한다. 핵심 구조:

1. SoftTLB (CPUTLBEntry)

QEMU는 게스트의 TLB를 소프트웨어로 모사한다. CPUTLBEntry 배열이 최근 변환 결과를 캐시한다:

Guest VA → SoftTLB lookup
  → hit:  HVA를 바로 사용 (fast path)
  → miss: page table walk (slow path, huge page면 상위 단계에서 종료)

fast path는 TCG가 생성한 호스트 코드에 인라인되어 있어 매우 빠르다. 메모리 접근 명령어마다 TLB 룩업 코드가 삽입된다.

2. Slow Path — 소프트웨어 페이지 테이블 워크

SoftTLB miss 시 QEMU가 게스트의 페이지 테이블을 직접 워크한다:

1. CPUState에서 CR3 값 읽기 (게스트 PML4 base GPA)
2. GPA → HVA 변환 (RAMBlock)으로 PML4 테이블 접근
3. PML4E에서 PDPT base GPA 추출
4. PDPT → PD → PT 순서로 반복
5. 최종 GPA 획득
6. GPA → HVA 변환 (RAMBlock)
7. 결과를 SoftTLB에 캐시

3. 페이지 폴트 주입

워크 도중 present 비트가 0인 엔트리를 만나면, QEMU는 게스트에 pf를 **주입(inject)**한다:

  • CR2 ← fault address (GVA)
  • error code ← 접근 유형에 따라 설정
  • 게스트 IDT의 pf 핸들러로 제어 이전

게스트 OS(PintOS의 page_fault())는 이것이 소프트웨어 주입인지 하드웨어 예외인지 구분할 수 없다.

PintOS + QEMU에서의 동작

PintOS가 pml4_set_page()로 페이지 테이블 엔트리를 설정하면:

  1. PintOS는 GPA 공간의 메모리에 PTE를 기록
  2. QEMU의 SoftMMU가 다음 메모리 접근 시 이 PTE를 읽음
  3. PintOS가 CR3를 다시 로드(pml4_activate())하면 QEMU가 SoftTLB 전체를 flush

CR3 전환 시 QEMU의 동작:

QEMU 에뮬레이션 (TCG 코드 생성)

TCG가 mov rax, [rbx] 같은 메모리 접근 명령어를 번역할 때:

Guest: mov rax, [rbx]

TCG가 생성하는 호스트 코드 (의사코드):
1. gva = env->regs[RBX]
2. tlb_idx = (gva >> 12) & (TLB_SIZE - 1)
3. if (tlb[tlb_idx].addr_read == (gva & PAGE_MASK)):
       // fast path: TLB hit
       host_addr = tlb[tlb_idx].addend + gva
       result = *(uint64_t *)host_addr
   else:
       // slow path: page walk; large-page entry면 상위 단계에서 종료 가능
       result = tlb_fill(...);  // 실제 helper 이름과 호출 경로는 QEMU 버전별 확인
4. env->regs[RAX] = result

fast path는 비교 1회 + 메모리 로드 1회로 완료된다. 대부분의 메모리 접근이 이 경로를 탄다.

PintOS에서 실제 변환 예시:

Guest VA: 0x00000000'004005a0 (유저 코드 영역)
CR3: 0x0000000004A00000 (PML4 base GPA)

1. PML4 index = (0x4005a0 >> 39) & 0x1FF = 0
   PML4E at GPA 0x04A00000 + 0×8 = 0x04A00000
   PML4E 값 → PDPT base GPA = 0x04A01000

2. PDPT index = (0x4005a0 >> 30) & 0x1FF = 0
   PDPTE at GPA 0x04A01000 + 0×8 = 0x04A01000
   PDPTE 값 → PD base GPA = 0x04A02000

3. PD index = (0x4005a0 >> 21) & 0x1FF = 2
   PDE at GPA 0x04A02000 + 2×8 = 0x04A02010
   PDE 값 → PT base GPA = 0x04A03000

4. PT index = (0x4005a0 >> 12) & 0x1FF = 0
   PTE at GPA 0x04A03000 + 0×8 = 0x04A03000
   PTE 값 → frame GPA = 0x04B00000

5. page offset = 0x4005a0 & 0xFFF = 0x5a0
   최종 GPA = 0x04B005a0

6. QEMU RAMBlock: GPA 0x04B005a0 → HVA (mmap_base + 0x04B005a0)
