QEMU는 파일 시스템 정책을 세우지 않는다

QEMU는 파일 시스템 정책을 세우지 않는다

확인 범위: 이 문서는 블록 장치 에뮬레이션과 guest OS 파일 시스템 사이의 일반적인 책임 경계와 PintOS·QEMU를 기준으로 한 선택 기준을 설명한다. 제시된 함수·파일·포트·디스크 배치와 수치는 특정 구현의 예시이며, 실제 적용 여부는 대상 코드와 버전, 실행 기록을 별도로 확인해야 하고 성능 특성까지 검증한 결과는 아니다.

한 줄 요약: QEMU IDE 모델은 sector 단위 I/O만 처리하고 이름·디렉터리·권한·캐싱 정책은 guest OS(PintOS)가 정한다는 책임 경계.

QEMU 파일 시스템 경계 구조

QEMU의 IDE controller 모델은 sector 단위 I/O만 처리한다. 파일 이름, 디렉터리 구조, 접근 권한, 빈 블록 관리, 캐싱 정책은 모두 guest OS(PintOS)의 파일 시스템 계층이 결정하는 정책이다. QEMU에게 pintos.dsk는 flat byte 배열이고, “sector N을 읽어라/써라”가 QEMU가 이해하는 전부다.

상세 설명

추상 개념 (블록 장치 vs 파일 시스템)

저장소 스택은 두 계층으로 나뉜다:

계층추상화 단위역할주체
블록 장치sector (512 bytes)“sector N을 읽기/쓰기”하드웨어 (디스크 컨트롤러)
파일 시스템file, directory, inode”이름으로 데이터 찾기/저장”OS 소프트웨어

실제 하드 디스크도 “파일”을 모른다. 디스크 컨트롤러는 LBA(Logical Block Address)로 sector를 읽고 쓸 뿐이다. “이 sector가 어떤 파일의 몇 번째 바이트인가”는 OS의 파일 시스템 드라이버가 결정한다.

QEMU의 IDE 모델은 이 하드웨어 컨트롤러를 에뮬레이션한다. 따라서 QEMU도 파일을 모른다.

QEMU가 하는 일 vs 하지 않는 일

QEMU가 하는 일 (블록 장치 에뮬레이션)

guest가 IDE I/O 포트(0x1F0~0x1F7)에 접근하면:

1. guest가 sector 번호를 I/O 포트에 기록
   → 0x1F3 (LBA low), 0x1F4 (LBA mid), 0x1F5 (LBA high)
2. guest가 0x1F7에 READ(0x20) 또는 WRITE(0x30) 커맨드 기록
3. QEMU IDE 모델이 호스트 파일에서 해당 offset 읽기/쓰기
   → offset = sector_number × 512
4. guest가 0x1F0에서 데이터 읽기 (PIO 16비트 단위)

QEMU가 하지 않는 일 (파일 시스템 정책)

QEMU가 모르는 것PintOS에서 담당하는 코드
파일 이름 → sector 매핑inode.c: inode의 start + offset으로 sector 계산
디렉터리 탐색directory.c: dir_lookup() — 이름으로 inode 검색
빈 블록 관리free-map.c: bitmap으로 빈 sector 추적
파일 접근 권한inode.c: deny_write_cnt로 실행 중 파일 보호
파일 크기 관리inode.c: inode_disk.length
캐싱 정책buffer cache (구현 시)

PintOS 구현 — sector 요청이 만들어지는 과정

PintOS에서 filesys_open("hello.txt")가 호출될 때 OS가 하는 일을 QEMU가 보는 것과 비교한다:

PintOS (정책):
  1. filesys_open("hello.txt")
  2. dir_lookup(root_dir, "hello.txt", &inode)
     → root directory의 inode에서 엔트리를 순회
     → 이름이 일치하는 엔트리의 inode sector 번호 획득
  3. inode_open(inode_sector)
     → 해당 sector를 읽어서 struct inode_disk 획득
  4. inode_read_at(inode, buffer, size, offset)
     → offset에 해당하는 sector 번호 계산:
        sector_idx = byte_to_sector(inode, offset)
        = inode->data.start + offset / DISK_SECTOR_SIZE

QEMU (메커니즘):
  위 과정에서 disk_read()가 호출될 때마다:
  → I/O 포트 0x1F3~0x1F5에 sector 번호 기록 감지
  → 호스트 파일 pintos.dsk에서 sector × 512 offset의 512바이트 읽기
  → 0x1F0 포트를 통해 guest에 데이터 전달

QEMU는 “hello.txt”라는 문자열을 본 적이 없다. 최종적으로 I/O 포트에 도착하는 sector 번호만 처리한다.

구체 예제: sector 42 읽기

PintOS가 결정:
  "hello.txt"의 inode는 sector 5에 있다
  inode_disk.start = 40
  offset 1024에 해당하는 sector = 40 + 1024/512 = 42

QEMU가 실행:
  I/O 포트에 sector=42 도착
  호스트 파일 offset = 42 × 512 = 21,504
  pintos.dsk의 21,504 ~ 22,015 바이트를 읽어서 guest에 전달

QEMU가 모르는 것:
  - 이 512바이트가 "hello.txt"의 일부라는 사실
  - 이 데이터가 텍스트인지 바이너리인지
  - 이 파일의 소유자가 누구인지
  - 이 읽기가 허가된 것인지

실제 OS (Linux)에서의 비교

영역물리 디스크 / QEMU virtio-blkguest Linux
인터페이스sector 번호로 읽기/쓰기VFS → ext4 → block layer
파일 이름모름dentry cache + inode
저널링모름ext4 journal (jbd2)
권한모름inode.i_mode (rwxrwxrwx)

Linux에서 open("<local-home>/file.txt")를 실행할 때도 최종적으로 디스크에 도달하는 것은 sector 번호뿐이다. “file.txt”라는 이름은 VFS → ext4가 inode → block number로 변환한 결과다.

QEMU 에뮬레이션

QEMU IDE 코드에서 파일 시스템 관련 코드가 없다는 증거:

  • hw/ide/core.c의 ide_sector_read()는 sector 번호 → byte offset 변환만 한다
  • block/file-posix.c의 raw_pread()는 호스트 파일의 특정 offset에서 읽을 뿐이다
  • QEMU 소스 전체에서 inode, directory, filename, permission 같은 파일 시스템 개념이 IDE/block 코드에 없다

QEMU에게 pintos.dsk와 swap.dsk의 차이는 파일 이름뿐이다. 두 파일 모두 flat byte 배열로, sector 단위로 접근한다. 하나가 파일 시스템이고 다른 하나가 swap 영역이라는 사실은 PintOS만 안다.

QEMU 파일 시스템 경계 값 추적

PintOS 기본 파일 시스템의 디스크 레이아웃:

pintos.dsk 크기: 기본 2 MB = 2,097,152 bytes
sector 크기: 512 bytes
총 sector 수: 2,097,152 / 512 = 4,096 sectors

QEMU가 아는 것:
  - sector 0 ~ 4,095까지 읽기/쓰기 가능
  - 각 sector = 512 bytes

PintOS가 아는 것:
  - sector 0: free_map inode (FREE_MAP_SECTOR)
  - sector 1: root directory inode (ROOT_DIR_SECTOR)
  - sector 2~: free_map 데이터, root dir 데이터, 파일 inode, 파일 데이터
  - free_map bitmap: 4,096 bits = 512 bytes = 1 sector

swap.dsk 크기: 기본 4 MB
QEMU가 아는 것: sector 읽기/쓰기
PintOS가 아는 것: 각 swap slot = 8 sectors = 4 KB = 1 page
