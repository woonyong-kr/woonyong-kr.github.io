RAMBlock — host process 메모리로 backing

RAMBlock — host process 메모리로 backing

확인 범위: 이 문서는 RAMBlock의 역할과 주소 변환 구조, 관련 구성 요소의 관계를 개념적으로 설명한다. 제시된 QEMU·PintOS 코드 경로와 수치, 생성 순서, TCG·KVM 동작 및 성능 관련 판단은 특정 버전의 소스 확인이나 실제 실행·GDB 관찰·측정으로 검증한 결과가 아니다. 확인 대상과 기대 결과를 보여 주는 예시다.

한 줄 요약: 게스트 물리 메모리(GPA)를 host 프로세스 가상 메모리로 backing하는 단위 RAMBlock.

RAMBlock의 역할

RAMBlock은 QEMU가 게스트의 물리 메모리, 즉 GPA 공간을 호스트 프로세스의 가상 메모리로 backing하는 단위다. 예를 들어 게스트가 물리 주소 0x00000000~0x07FFFFFF (128 MB)에 접근하면, QEMU는 이 주소를 자신의 프로세스 주소 공간에 mmap된 영역의 해당 offset으로 변환한다. RAMBlock 구조체는 이 변환에 필요한 정보를 관리한다.

주소가 변환되는 과정

에뮬레이터의 메모리 접근을 이해하려면 게스트와 호스트 사이에서 주소가 어떻게 바뀌는지 먼저 살펴봐야 한다. 게스트의 가상 주소는 게스트 OS가 설정한 page table을 거쳐 게스트 물리 주소가 된다. QEMU는 이 물리 주소를 RAMBlock이 가리키는 호스트 가상 주소로 연결하고, 마지막으로 호스트 OS와 MMU가 호스트 물리 주소를 찾는다.

Guest Virtual Address (GVA)
    ↓ [guest page table walk — guest OS가 설정]
Guest Physical Address (GPA)
    ↓ [RAMBlock offset 변환 — QEMU가 관리]
Host Virtual Address (HVA)
    ↓ [host page table walk — host OS/MMU가 처리]
Host Physical Address (HPA)

이 가운데 RAMBlock이 관여하는 부분은 GPA → HVA 변환이다.

QEMU 구현 구조

RAMBlock 구조체

RAMBlock은 mmap된 호스트 메모리의 시작 주소와 사용 크기, 전역 RAM 공간에서의 offset 등을 보관한다.

생성 과정

QEMU 머신을 초기화할 때, 예를 들어 -m 128M 옵션을 사용하면 다음 흐름으로 RAMBlock이 만들어진다.

  1. pc_init()이 memory_region_init_ram()을 호출한다.
  2. 내부에서 qemu_ram_alloc()과 ram_block_add()가 차례로 실행된다.
  3. mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0)로 호스트 메모리를 할당한다.
  4. 새 RAMBlock을 전역 리스트 ram_list.blocks에 등록한다.

GPA → HVA 변환

변환의 기본 형태는 RAMBlock의 호스트 시작 주소에 block 내부 offset을 더하는 것이다.

게스트가 GPA에 접근하면 QEMU의 AddressSpace가 먼저 그 GPA를 포함하는 MemoryRegion을 찾는다. 이어서 MemoryRegion이 참조하는 RAMBlock을 찾고, block->host + (gpa - region->addr)로 HVA를 계산한다.

PintOS + QEMU 예시

PintOS를 -m 128 (128 MB)로 실행하는 경우 다음과 같은 RAMBlock 구성을 예상할 수 있다. 이 표의 이름과 범위는 실제 실행으로 확인한 값이 아니라 관찰 대상으로 제시된 예시다.

RAMBlockGPA 범위크기용도
pc.ram0x00000000 ~ 0x07FFFFFF128 MB메인 RAM
pc.bios0xFFFE0000 ~ 0xFFFFFFFF128 KBSeaBIOS ROM
vga.vram0xA0000 ~ 0xBFFFF128 KBVGA 프레임버퍼

PintOS의 E820 맵이 보고하는 사용 가능 영역의 예인 0x00100000 ~ 0x07FDFFFF도 pc.ram RAMBlock 내부의 offset으로 매핑되는 것으로 설명할 수 있다.

PintOS에서 보이는 메모리

PintOS는 RAMBlock의 존재를 직접 알지 못한다. PintOS에는 BIOS가 E820으로 알려 준 물리 메모리가 실제 RAM으로 보인다. palloc_get_page()로 할당한 물리 프레임 주소는 GPA이며, 이 주소에 대한 읽기와 쓰기는 QEMU를 거쳐 호스트 메모리에 전달된다.

PintOS palloc → frame PA = 0x00345000 (GPA)
QEMU: pc.ram->host + 0x00345000 = HVA 0x7f1234345000
Host MMU: HVA → HPA (투명)

KVM과 EPT를 사용하는 경로

QEMU가 KVM을 사용하면 GPA → HPA 변환은 하드웨어의 Intel EPT 또는 AMD NPT를 통해 처리된다. RAMBlock의 host 주소를 KVM에 등록하고(KVM_SET_USER_MEMORY_REGION), CPU가 guest page table walk와 EPT walk를 하드웨어에서 수행한다. 이 경로는 QEMU softmmu를 거치지 않으므로 오버헤드가 줄어드는 것으로 설명된다.

이 문서에서는 PintOS가 보통 TCG로 실행되어 KVM 경로를 사용하지 않는 경우를 기준으로 다룬다. 실제 실행 모드는 별도로 확인해야 한다.

다음 값은 PintOS에 128 MB 메모리를 설정했을 때 확인할 항목과 예상 계산을 정리한 것이다.

RAMBlock과 MemoryRegion의 관계

RAMBlock은 호스트의 mmap 영역이라는 물리적 backing을 나타낸다. MemoryRegion은 GPA 공간에서 어느 주소 범위를 어떻게 배치할지 나타내는 논리적 매핑이다. 두 구성 요소의 관계를 예시 값으로 나타내면 다음과 같다.

  • MemoryRegion “pc.ram” RAMBlock “pc.ram”
  • addr: 0x00000000 | → | host: 0x7f1234000
  • size: 0x08000000 | | offset: 0
  • ram_block | used_length: 128MB
  • readonly: false | | max_length: 128MB
  • flags: 0

AddressSpace의 dispatch 트리는 MemoryRegion을 기준으로 GPA가 속한 범위를 찾는다. 그런 다음 MemoryRegion에서 RAMBlock 포인터를 따라가 HVA를 얻는다.

Linux가 실제 하드웨어를 관리하는 방식, QEMU가 RAMBlock을 관리하는 방식, 게스트인 PintOS에 보이는 방식을 나란히 놓으면 각 계층의 역할을 구분하기 쉽다.

TCG softmmu TLB와 RAMBlock

TCG 모드에서는 번역된 load/store가 먼저 softmmu TLB를 조회한다.

flowchart TD
    A[TCG 번역된 load/store] --> B{softmmu TLB hit?}
    B -->|hit| C[TLB 캐시된 HVA로 직접 접근]
    B -->|miss| D[x86_cpu_tlb_fill]
    D --> E[guest page table walk<br/>GVA → GPA]
    E --> F[AddressSpace dispatch<br/>GPA → MemoryRegion]
    F --> G[RAMBlock 조회<br/>block->host + offset = HVA]
    G --> H[TLB 엔트리 갱신]
    H --> C

softmmu TLB는 QEMU 프로세스 안에서 {GVA, size, prot} → HVA 매핑을 캐시하는 소프트웨어 TLB다. TLB hit이면 캐시된 HVA에 바로 접근하므로 RAMBlock 조회를 건너뛴다. TLB miss이면 guest page table walk와 AddressSpace dispatch, RAMBlock 조회를 거쳐 새 엔트리를 만든다. cr3 교체(context switch) 시에는 tlb_flush()로 전체 엔트리를 무효화하는 흐름을 예상할 수 있으며, 실제 동작은 대상 버전에서 확인해야 한다.

관찰 시나리오

시나리오 1: PintOS 부팅 시 RAMBlock 생성 순서

이 시나리오에서는 QEMU가 PintOS를 위해 어떤 RAMBlock을 어떤 순서로 만드는지 확인한다. QEMU 프로세스를 gdb -p $(pgrep qemu) 또는 gdb --args qemu-system-x86_64 ...로 디버깅한다.

관찰할 결과는 pc.ram (128 MB), pc.bios (128 KB), vga.vram (128 KB)가 차례로 생성되는지와 각 host 포인터가 서로 다른 mmap 영역을 가리키는지다. 이 순서와 값은 기대 결과이며 실제 관찰 결과가 아니다.

시나리오 2: guest page fault에서 RAMBlock까지

이 시나리오에서는 PintOS에서 demand paging page fault가 발생했을 때 QEMU가 RAMBlock의 HVA를 찾는 경로를 추적한다.

확인할 경로는 x86_cpu_tlb_fill → guest page table walk → GPA 획득 → AddressSpace dispatch → pc.ram RAMBlock → block->host + offset = HVA → softmmu TLB 엔트리 갱신이다. 이 흐름 역시 실제 실행에서 검증해야 할 기대 결과다.
