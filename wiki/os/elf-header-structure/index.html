ELF Header 구조 상태

ELF(Executable and Linkable Format) header는 실행 파일의 처음 64 바이트(ELF64 기준)에 위치하며, OS 로더가 이 파일을 메모리에 적재하기 위해 알아야 할 모든 메타 정보를 담고 있다. 로더는 ELF header에서 매직 넘버로 유효성을 검증하고, program header table의 위치와 개수를 읽어 각 세그먼트를 어떤 가상 주소에 어떤 권한으로 매핑할지 결정한다.

상세 설명

추상 개념 (ELF 파일 구조)

ELF 파일은 크게 세 부분으로 나뉜다:

+------------------+  offset 0
| ELF Header       |  64 bytes (ELF64)
+------------------+  e_phoff
| Program Headers  |  e_phnum × e_phentsize
+------------------+
| Sections / Data  |  실제 코드와 데이터
+------------------+
| Section Headers  |  (링커용, 실행 시 불필요)
+------------------+

OS 로더는 ELF Header + Program Headers만 읽는다. Section Headers는 링커와 디버거를 위한 것이다.

ELF64 Header 필드

오프셋 크기 필드 설명
0x00 16B e_ident 매직: \x7fELF, 클래스(2=64bit), 엔디안(1=LE), 버전
0x10 2B e_type 2 = ET_EXEC (실행 파일)
0x12 2B e_machine 0x3E = EM_X86_64
0x14 4B e_version 1 = EV_CURRENT
0x18 8B e_entry 진입점 가상 주소 → RIP에 설정
0x20 8B e_phoff program header table의 파일 내 오프셋
0x28 8B e_shoff section header table의 파일 내 오프셋
0x30 4B e_flags 프로세서별 플래그 (x86-64는 0)
0x34 2B e_ehsize ELF header 크기 (64)
0x36 2B e_phentsize program header 엔트리 크기 (56)
0x38 2B e_phnum program header 개수
0x3A 2B e_shentsize section header 엔트리 크기
0x3C 2B e_shnum section header 개수
0x3E 2B e_shstrndx 섹션 이름 문자열 테이블 인덱스

ELF64 Program Header 필드

각 program header는 하나의 세그먼트를 기술한다:

오프셋 크기 필드 설명
0x00 4B p_type 1 = PT_LOAD (메모리에 적재)
0x04 4B p_flags PF_R(4), PF_W(2), PF_X(1) 조합
0x08 8B p_offset 세그먼트의 파일 내 오프셋
0x10 8B p_vaddr 적재할 가상 주소
0x18 8B p_paddr 물리 주소 (대부분 무시)
0x20 8B p_filesz 파일에서 읽을 바이트 수
0x28 8B p_memsz 메모리에서 차지할 바이트 수
0x30 8B p_align 정렬 (보통 0x1000 = 4 KiB)

p_memsz > p_filesz인 경우, 차이만큼 0으로 채운다 (BSS 영역).

실제 OS (Linux)

Linux의 fs/binfmt_elf.c에서 load_elf_binary()가 동일한 절차를 수행한다.

PintOS 구현

PintOS의 load() 함수(userprog/process.c:1106)는 도우미 함수들로 분해되어 있다:

  1. setup_process_address_space() (줄 916): pml4_create() + process_activate() — 빈 PML4 생성 후 활성화
  2. read_elf_header() (줄 967): 파일 첫 64 바이트를 읽고 6가지 검증 수행
/* read_elf_header() — 매직 + 구조 검증 (process.c:967) */
return read_success &&
    memcmp(ehdr->e_ident, "\177ELF\2\1\1", 7) == 0 &&  // 매직 7B
    ehdr->e_type == 2 &&          // ET_EXEC
    ehdr->e_machine == 0x3E &&    // EM_X86_64
    ehdr->e_version == 1 &&       // EV_CURRENT
    ehdr->e_phentsize == sizeof(struct Phdr) &&  // 56B
    ehdr->e_phnum <= 1024;        // 비정상적 phdr 수 방지
  1. load_program_headers() (줄 1032): e_phoff부터 e_phnum개의 phdr을 순회하며 type별 분기
/* load_program_headers() — PT_LOAD만 처리 (process.c:1032) */
switch (phdr.p_type) {
    case PT_NULL: case PT_NOTE: case PT_PHDR: case PT_STACK:
        break;          // 무시
    case PT_DYNAMIC: case PT_INTERP: case PT_SHLIB:
        return false;   // PintOS는 동적 링킹 미지원 → 거부
    case PT_LOAD:
        load_loadable_segment(file, &phdr);  // ★ 세그먼트 적재
}
  1. load_loadable_segment() (줄 1003) → validate_segment() (줄 882) → load_segment()

validate_segment()의 5가지 검증:

  • p_offset과 p_vaddr의 페이지 내 오프셋이 동일한가 (정렬)
  • p_offset이 파일 크기 이내인가
  • p_memsz >= p_filesz인가
  • p_vaddr과 p_vaddr + p_memsz가 유저 영역인가
  • p_vaddr >= PGSIZE인가 (0번 페이지 매핑 방지 — NULL 포인터 접근 탐지)
  1. load_segment(): VM 모드에서는 vm_alloc_page_with_initializer()로 UNINIT 페이지 등록, non-VM에서는 palloc_get_page() + file_read() + memcpy()로 즉시 적재
  2. 진입점 설정: ehdr.e_entry를 intr_frame.rip에 설정 (줄 1178)

read_bytes / zero_bytes 계산 예:

phdr: p_offset=0x3000, p_vaddr=0x403000, p_filesz=0x48, p_memsz=0x50

page_offset = p_vaddr & PGMASK = 0x403000 & 0xFFF = 0
read_bytes  = p_filesz - 0 = 0x48 = 72 bytes
zero_bytes  = PGSIZE - read_bytes = 4096 - 72 = 4024 bytes

QEMU 에뮬레이션

QEMU는 ELF를 해석하지 않는다 — ELF 해석은 순전히 guest OS(PintOS)의 소프트웨어 작업이다. QEMU가 관여하는 지점:

  • file_read() → disk I/O → QEMU IDE 에뮬레이션으로 ELF 바이트를 읽음
  • pml4_set_page() → PTE 설정 → QEMU softmmu TLB에 반영
  • page fault 시 lazy_load_segment() → disk에서 코드 읽기 → QEMU block backend

관찰 시나리오

시나리오 1: 정상 바이너리 PT_LOAD 매핑 관찰

args-single을 로드하면서 PT_LOAD 두 세그먼트가 어떻게 lazy page로 등록되는지 추적한다:

  1. break load으로 정지
  2. dump_elf_raw &ehdr로 header 64B 검증 — 매직 7f 45 4c 46, Type=2, Machine=0x3E
  3. continue하면 load_loadable_segment가 2번 호출됨
  4. 1차: vaddr=0x400000, flags=0x5(R+X), filesz=0x2a58, memsz=0x2a58 → zero=0
  5. 2차: vaddr=0x403000, flags=0x6(R+W), filesz=0x48, memsz=0x50 → BSS 0x08 bytes
  6. break vm_alloc_page_with_initializer에서 type, upage, writable, initializer 인자를 확인하고, 반환 뒤 spt_find_page(&thread_current()->spt, upage)로 UNINIT page 등록을 확인한다. info proc mappings는 SPT 내부 상태를 보여 주지 않는다.

시나리오 2: 잘못된 ELF 파일 거부 과정 추적

의도적으로 매직이 깨진 파일(예: 첫 4바이트를 0으로 패치)을 exec()하면:

  1. read_elf_header()에서 memcmp 실패 → false 반환
  2. load() → false → process_exec() → exit(-1) 경로 확인
  3. 이 과정에서 pml4_create()는 호출되었으나 바로 pml4_destroy()됨을 추적
