syscall 명령어

syscall 명령어

확인 범위: 이 문서는 x86-64 syscall의 일반적인 권한 전환 원리와 Linux·PintOS·QEMU 구현의 선택 차이를 설명한다. 구체적인 코드 좌표, 레지스터 값, 실행 흐름과 성능 비교는 제시된 구현 및 예시·관찰 시나리오의 범위에 한정된다. 실제 버전의 소스, 실행 기록 또는 성능 측정으로 검증된 결과를 뜻하지 않는다.

한 줄 요약: syscall은 x86-64가 제공하는 유저 모드(CPL3)→커널 모드(CPL0) 전환 전용 명령어다. int 0x80보다 빠르며, RIP를 RCX에, RFLAGS를 R11에 백업한 뒤 MSR_LSTAR가 가리키는 커널 진입점으로 이동한다.

syscall 명령어 흐름

유저 프로그램이 파일 I/O나 프로세스 생성 같은 OS 서비스를 요청하려면 유저 모드에서 커널 모드로 넘어가야 한다. x86-64 CPU는 이 전환을 위해 syscall 명령어를 제공한다. syscall을 실행하면 현재 권한 수준이 CPL 3에서 CPL 0으로 바뀌며, 인터럽트 게이트(int 0x80)를 이용하는 방식보다 빠르다.

이때 CPU가 커널 진입에 필요한 상태를 모두 준비하는 것은 아니다. CPU는 복귀 주소와 플래그를 보관하고 지정된 커널 진입점으로 이동하지만, RSP는 계속 유저 스택을 가리킨다. 따라서 커널 스택으로 전환하고 시스템 콜을 처리할 실행 문맥을 만드는 일은 OS가 맡는다.

CPU가 수행하는 권한 전환

syscall이 실행되면 CPU는 다음 순서로 상태를 바꾼다.

  1. RCX <- RIP: 다음에 실행할 유저 코드의 주소를 RCX에 저장한다.
  2. R11 <- RFLAGS: 현재 플래그 레지스터를 R11에 저장한다.
  3. RIP <- LSTAR MSR: MSR 0xC0000082에 저장된 커널 진입점 주소로 이동한다.
  4. CS <- STAR MSR[47:32]: CS를 커널 코드 세그먼트 셀렉터로 교체해 CPL 0으로 전환한다.
  5. SS <- STAR MSR[47:32] + 8: SS를 커널 데이터 세그먼트 셀렉터로 교체한다.
  6. RFLAGS &= ~SFMASK MSR: SFMASK에 지정된 RFLAGS 비트를 지운다. PintOS에서는 이 과정에 인터럽트 비활성화가 포함된다.

이 과정에서 스택은 바뀌지 않는다. syscall 직후에도 RSP는 유저 스택을 가리키므로, 커널 스택 전환은 OS의 진입 코드가 수행해야 한다.

반대 방향의 sysret은 저장해 둔 상태를 이용해 유저 모드로 돌아간다.

  • RIP <- RCX (유저 코드로 복귀)
  • RFLAGS <- R11 (플래그 복원)
  • CS/SS를 유저 세그먼트로 교체 (CPL 3)

MSR 레지스터 구성

CPU가 어느 진입점과 세그먼트를 사용할지는 다음 MSR에 설정된다.

MSR 이름주소역할PintOS 값
STAR0xC0000081CS 셀렉터 (커널/유저)(SEL_UCSEG-0x10)<<48 | SEL_KCSEG<<32
LSTAR0xC0000082커널 진입점 주소&syscall_entry
SFMASK0xC0000084마스킹할 RFLAGS 비트FLAG_IF | FLAG_TF | ...

STAR의 bit 47:32에는 SEL_KCSEG (0x08)이 들어가고, bit 63:48에는 SEL_UCSEG - 0x10 (0x13)이 들어간다. sysret을 실행할 때 CPU는 후자의 값에 0x10을 더해 SEL_UCSEG (0x23)를 만든다.

CPL 전환이 바꾸는 권한

유저 모드 (CPL 3)                    커널 모드 (CPL 0)
+-------------------+               +-------------------+
| 일반 명령어만 실행 |  -- syscall -> | 모든 명령어 실행   |
| I/O 포트 접근 불가 |               | I/O 포트 접근 가능 |
| CR3 변경 불가     |  <- sysret --  | CR3 변경 가능     |
+-------------------+               +-------------------+

각 세그먼트의 권한은 GDT에 있는 세그먼트 디스크립터의 DPL(Descriptor Privilege Level)로 정의된다.

셀렉터값DPL용도
SEL_KCSEG0x080커널 코드
SEL_KDSEG0x100커널 데이터
SEL_UDSEG0x1B3유저 데이터
SEL_UCSEG0x233유저 코드

Linux와 PintOS가 진입을 준비하는 방법

Linux와 PintOS 모두 syscall/sysret 메커니즘을 사용하지만, 진입 이후 필요한 기능과 구현 범위는 다르다. Linux의 진입점은 entry_SYSCALL_64이며, MSR은 syscall_init()에서 설정한다. Linux는 swapgs로 per-CPU 데이터 접근 기반을 전환하지만 PintOS에는 이 과정이 없다. syscall 번호도 달라서 write는 Linux에서 1, PintOS에서 9다. Linux는 gettimeofday 같은 일부 syscall을 vDSO를 통해 유저 공간에서 처리하기도 한다.

PintOS의 진입 과정

PintOS에서는 MSR 초기화, 어셈블리 진입, C 핸들러 실행이 차례로 이어진다.

먼저 userprog/syscall.c: syscall_init()에서 CPU가 사용할 세그먼트, 진입점, 플래그 마스크를 설정한다.

SFMASK에 FLAG_IF를 포함했으므로 syscall을 실행하면 인터럽트가 자동으로 비활성화된다. 이때 RSP는 아직 유저 스택을 가리킨다. 커널 스택으로 전환하기 전에 인터럽트가 발생하면 유저 스택에서 커널 코드가 실행되어 보안 취약점이 생길 수 있으므로, 스택 전환이 끝날 때까지 인터럽트를 막는다.

이후 userprog/syscall-entry.S: syscall_entry가 유저 RSP를 보관하고 TSS.rsp0에서 커널 스택 주소를 가져온다. 커널 스택으로 옮긴 뒤에는 복귀 상태와 범용 레지스터로 intr_frame을 구성하고 syscall_handler를 호출한다.

syscall_entry:
    movq %rbx, temp1(%rip)       # callee-saved 레지스터 임시 저장
    movq %r12, temp2(%rip)
    movq %rsp, %rbx              # 유저 RSP 보관
    movabs $tss, %r12
    movq (%r12), %r12
    movq 4(%r12), %rsp           # TSS.rsp0 → 커널 스택으로 전환
    # --- 이제 커널 스택 ---
    push $(SEL_UDSEG)            # if->ss
    push %rbx                    # if->rsp (유저)
    push %r11                    # if->eflags
    push $(SEL_UCSEG)            # if->cs
    push %rcx                    # if->rip (유저 복귀 주소)
    ...모든 범용 레지스터 push...
    movq %rsp, %rdi              # &intr_frame을 첫 번째 인자로
    call *syscall_handler
    ...모든 레지스터 pop...
    popq %rcx                    # if->rip 복원
    popq %r11                    # if->eflags 복원
    popq %rsp                    # 유저 스택 복원
    sysretq                      # 유저 모드 복귀

마지막으로 userprog/syscall.c: syscall_handler()는 f->R.rax의 syscall 번호를 기준으로 switch 분기한다. syscall 인자는 f->R.rdi, f->R.rsi, f->R.rdx에서 가져온다.

write 호출에서 레지스터 값 추적

유저 프로그램에서 write(1, "hello", 5)를 호출하는 예시에서는 syscall 번호와 인자가 다음과 같이 배치된다.

레지스터값의미
RAX9 (SYS_WRITE)syscall 번호
RDI1fd (stdout)
RSI0x0040_1000 (예시)buffer 주소
RDX5size

syscall을 실행한 직후에는 CPU가 다음 상태를 만든다.

  • RCX = 유저의 다음 RIP (syscall 다음 명령어 주소)
  • R11 = 유저의 RFLAGS
  • RIP = LSTAR에 저장된 syscall_entry 주소 (커널 영역, 예: 0x8004_XXXX)
  • CS = 0x08 (SEL_KCSEG, CPL 0)

전체 왕복 흐름은 다음 순서도처럼 이어진다.

sequenceDiagram
    participant User as 유저 프로그램 (CPL 3)
    participant CPU as x86-64 CPU
    participant Entry as syscall_entry.S
    participant Handler as syscall_handler()

    User->>CPU: syscall 명령어 실행
    Note over CPU: RCX ← RIP, R11 ← RFLAGS
    Note over CPU: RIP ← LSTAR, CS ← KCSEG
    Note over CPU: RFLAGS &= ~SFMASK (IF=0)
    CPU->>Entry: 커널 진입점으로 점프
    Note over Entry: RSP 아직 유저 스택!
    Entry->>Entry: TSS.rsp0 → RSP (커널 스택 전환)
    Entry->>Entry: 모든 레지스터 → intr_frame push
    Entry->>Handler: call syscall_handler(&if)
    Handler->>Handler: RAX로 분기, 서비스 실행
    Handler->>Entry: return
    Entry->>Entry: 레지스터 pop, RSP 복원
    Entry->>CPU: sysretq
    Note over CPU: RIP ← RCX, RFLAGS ← R11
    Note over CPU: CS ← UCSEG (CPL 3)
    CPU->>User: 유저 모드 복귀

QEMU가 syscall을 처리하는 방법

QEMU TCG는 syscall 명령어를 만나면 helper 함수로 동작을 에뮬레이션한다. 실제 CPU가 하드웨어에서 처리하는 MSR 읽기, CS/SS 교체, RFLAGS 마스킹을 소프트웨어로 재현하는 방식이다.

  1. gen_helper_syscall() — TCG 프론트엔드가 syscall opcode를 인식하면 helper 호출을 삽입
  2. helper_syscall() (target/i386/seg_helper.c) — 실제 에뮬레이션:
    • env->eip = env->star >> 32 (LSTAR MSR 읽기)
    • env->eflags &= ~env->fmask (SFMASK 마스킹)
    • cpu_x86_load_seg_cache(env, R_CS, ...) — 커널 CS 설정
    • cpu_x86_load_seg_cache(env, R_SS, ...) — 커널 SS 설정
  3. 이후 TCG가 syscall_entry의 guest 명령어들을 번역하여 실행

KVM 모드에서는 syscall이 하드웨어에서 직접 실행되므로 VM exit 없이 MSR 값이 반영된다. PintOS QEMU는 보통 TCG 모드다.

단계실제 CPUQEMU TCG
MSR 읽기하드웨어 MSR 레지스터env->lstar, env->star, env->fmask 변수
CS 교체마이크로코드cpu_x86_load_seg_cache() 호출
RFLAGS 마스킹하드웨어 ANDenv->eflags &= ~env->fmask
TB 경계해당 없음syscall 후 새 TB에서 syscall_entry 번역 시작

GDB로 관찰할 지점

다음 스크립트는 syscall 번호와 인자, 커널 스택 전환, MSR 초기화, sysretq 복귀 및 SFMASK의 효과를 관찰하도록 구성되어 있다. 이 문서에 제시된 스크립트와 출력은 관찰 시나리오이며, 실제 실행으로 검증된 결과를 뜻하지 않는다.

write(1, "hello", 5) 왕복 관찰

이 시나리오는 유저 프로그램이 write() 시스템 콜을 호출한 뒤 다시 유저 코드로 돌아올 때까지 레지스터가 어떻게 변하는지 추적한다.

# 1. 유저 측 syscall 래퍼 (lib/user/syscall.c)
#    RAX=9(SYS_WRITE), RDI=1(stdout), RSI=0x401000(buf), RDX=5(size)

# 2. syscall 명령어 실행 직후 — CPU 하드웨어 동작
[SYSCALL] rax=9 rdi=0x401000 rsi=0x401000 rdx=0x5
  user_rip=0x400c34 (saved in rcx), user_rflags=0x206 (saved in r11)
# → RIP는 LSTAR(syscall_entry 주소)로 점프, CS=0x08, IF=0

# 3. 커널 스택 전환
[STACK-SWITCH] rsp after switch: 0x8004004000 (was user: 0x47480000)
# → TSS.rsp0에서 커널 스택 주소를 가져와 RSP 교체

# 4. intr_frame 구성 후 syscall_handler 호출
[SYS] write(fd=1, buf=0x401000, size=5) [#1]

# 5. sysretq로 복귀
[SYSRET] returning to user: rip=0x400c34 rsp=0x47480000 rflags=0x206
# → 유저 코드의 syscall 다음 명령어에서 재개, IF=1 복원

SFMASK에 의한 인터럽트 비활성화 관찰

이 시나리오는 syscall 실행 전후의 RFLAGS에서 IF 비트가 어떻게 달라지는지 비교한다. 제시된 흐름에서는 커널 스택으로 전환하기 전에 인터럽트를 차단하는 역할을 확인하려는 것이다.

# syscall 실행 전 (유저 모드)
(gdb) check_sfmask
RFLAGS=0x206, IF=1 (인터럽트 ON)

# syscall_entry 진입 직후 (커널 모드, RSP 아직 유저 스택)
(gdb) check_sfmask
RFLAGS=0x006, IF=0 (인터럽트 OFF — SFMASK가 FLAG_IF를 마스킹)

# → 이 시점에서 RSP가 유저 스택을 가리키므로, 인터럽트가 발생하면
#   유저 스택에 커널 데이터가 쌓이는 보안 취약점이 생긴다.
#   SFMASK가 IF를 끄는 것이 이 위험을 방지한다.

# TSS.rsp0로 커널 스택 전환 완료 후 → 이후 sti로 인터럽트 재활성화 가능
