Lazy Loading과 Demand Paging — 필요할 때만 물리 메모리 할당

Lazy Loading과 Demand Paging — 필요할 때만 물리 메모리 할당

한 줄 요약: 프로그램의 모든 페이지를 미리 올리지 않고 실제 접근(page fault) 시점에 프레임을 할당·적재하는 기법으로, 메모리를 절약하고 시작 시간을 줄이며 over-commit을 지원한다.

Lazy Loading과 Demand Paging의 차이

프로그램을 실행할 때 모든 페이지가 즉시 필요한 것은 아니다. Demand paging은 프로그램의 모든 페이지를 미리 메모리에 올리지 않고, 실제 접근이 일어나 page fault가 발생할 때 물리 프레임을 할당하고 내용을 채우는 기법이다.

Lazy loading은 이 demand paging을 구현하는 방식 중 하나다. 프로그램을 적재할 때는 SPT에 나중에 불러올 내용을 등록하고, 실제 물리 메모리 할당은 해당 페이지에 접근할 때까지 미룬다.

이렇게 적재 시점과 실제 할당 시점을 나누면 다음과 같은 효과를 얻는다.

  1. 메모리 절약: 프로그램의 코드와 데이터 가운데 실제 실행 중 접근하는 부분만 메모리에 올릴 수 있다. 모든 내용을 미리 올릴 때 생기는 RAM 낭비를 줄인다.
  2. 빠른 시작: 실행 전에 ELF 전체를 디스크에서 읽지 않으므로 프로그램을 더 빨리 시작할 수 있다.
  3. over-commit: 당장 필요한 페이지만 물리 메모리에 배치하므로 물리 메모리보다 큰 가상 주소 공간을 사용할 수 있다.

동작 원리

Demand Paging의 추상적인 흐름

전통적인 eager loading은 프로그램을 시작하기 전에 ELF의 모든 segment를 RAM에 복사하고 PTE를 유효한 상태로 만든다. Demand paging은 우선 각 가상 주소에 어떤 파일 내용이 들어가야 하는지만 기록한다. 이후 프로그램이 그 주소에 접근하면 page fault를 처리하면서 필요한 페이지를 적재한다.

[Eager Loading — 전통 방식]
exec("program")
  → ELF의 모든 segment를 RAM에 복사
  → 모든 PTE를 유효하게 설정
  → 프로그램 시작
  → 시작까지 오래 걸림, RAM 많이 사용

[Demand Paging — lazy 방식]
exec("program")
  → ELF header만 읽고, "어떤 VA에 어떤 파일 내용이 와야 하는지" 기록
  → PTE는 invalid로 설정 (present bit = 0)
  → 프로그램 시작 (빠름)
  → 코드 실행 시 page fault 발생
  → OS가 해당 page만 디스크에서 읽어 RAM에 채움
  → PTE를 valid로 설정
  → 같은 명령어 재실행 → 정상 진행

이 흐름이 동작하려면 다음 세 요소가 필요하다.

  1. 메타데이터 저장소: 특정 VA의 내용을 파일의 어느 위치에서 가져와야 하는지 기억하는 구조다. PintOS에서는 SPT가 이 역할을 맡는다.
  2. page fault handler: present bit가 0인 PTE에 접근했을 때 원인을 확인하고 해당 페이지를 준비한다.
  3. 명령어 재실행: OS가 fault를 처리해 페이지를 준비하면 CPU가 같은 명령어를 다시 시도한다(페이지 폴트 후 왜 같은 명령어를 다시 실행하나).

Linux와 Windows에서의 Demand Paging

Linux에서 mmap() 또는 execve()로 파일을 매핑하면 VMA(Virtual Memory Area)는 생성되지만 물리 페이지는 바로 할당되지 않는다.

execve("program")
  → load_elf_binary()
  → elf_map() → do_mmap()
  → VMA 생성, PTE는 empty
  → 접근 시 #PF → do_page_fault() → filemap_fault()
  → page cache에서 page 찾거나 디스크에서 read
  → PTE 설정 → 재실행

Linux는 page cache로 파일 I/O를 캐싱한다. 여러 프로세스가 같은 파일의 같은 offset을 매핑하면 read-only 페이지의 물리 프레임을 공유할 수 있다. write가 발생하면 COW(Copy-on-Write)가 동작한다.

Linux의 page fault는 데이터를 가져오는 위치에 따라 두 종류로 나뉜다.

  • minor fault: page cache에 페이지가 이미 있어 디스크 I/O가 필요하지 않다(~1μs).
  • major fault: 디스크에서 페이지를 읽어야 한다(~ms 단위).

Windows도 같은 원리로 CreateFileMapping()과 MapViewOfFile()을 이용해 lazy mapping을 수행한다. VAD에 매핑 정보를 기록해 두고, 접근 시 발생하는 page fault를 통해 물리 페이지를 할당한다.

개념LinuxWindowsPintOS
매핑 기록VMAVADSPT (UNINIT page)
파일 캐시page cachecache manager없음
fault 종류 구분minor/majorsoft/hard없음 (항상 디스크 읽기)

PintOS 구현

PintOS의 lazy loading은 VM 프로젝트(Project 3)에서 구현한다. 처리 과정은 ELF를 읽을 때 필요한 정보를 등록하는 단계와 page fault가 발생했을 때 실제 페이지를 적재하는 단계로 나뉜다.

등록 단계: load_segment() — ELF 적재 시

기존의 eager load_segment()는 파일 내용을 즉시 읽어 RAM에 복사한다. lazy 버전은 각 페이지를 나중에 초기화할 수 있도록 파일 위치와 읽을 크기를 기록한 뒤 SPT에 UNINIT page만 등록한다.

이 시점에는 PTE가 설정되지 않는다. 따라서 프로그램이 해당 VA에 처음 접근하면 page fault가 발생한다.

실행 단계: page fault → lazy_load_segment() 호출

page fault handler는 fault가 발생한 주소를 기준으로 SPT에서 UNINIT page를 찾는다. 그런 다음 물리 프레임을 할당하고, 등록 단계에서 저장한 aux를 이용해 파일 내용을 읽는다. 초기화와 PTE 설정이 끝나면 handler가 복귀하고 같은 명령어가 다시 실행된다.

유저 코드가 upage 접근
  → #PF (PTE present = 0)
  → page_fault() → vm_try_handle_fault()
  → spt_find_page(spt, pg_round_down(fault_addr))
  → UNINIT page 발견
  → vm_do_claim_page(page)
    → palloc_get_page(PAL_USER)     // 물리 프레임 할당
    → swap_in(page, frame->kva)
    → uninit_initialize(page, kva)
      → lazy_load_segment(page, aux)  // 실제 파일 읽기
        → file_read_at(aux->file, kva, aux->read_bytes, aux->ofs)
        → memset(kva + aux->read_bytes, 0, aux->zero_bytes)
      → anon_initializer(page, type, kva)  // page type 전환: UNINIT → ANON
    → pml4_set_page(pml4, va, pa, writable)  // PTE 설정
  → handler 복귀 → 같은 명령어 재실행

UNINIT page의 생명 주기

UNINIT page는 실제 페이지를 만들기 전까지 초기화 callback과 aux를 보관한다. page fault가 발생해 uninit_initialize()가 실행되면 page type이 VM_ANON 또는 VM_FILE로 바뀐다.

vm_alloc_page_with_initializer()
  → uninit_new(page)
  → page->type = VM_UNINIT
  → page->uninit.init = lazy_load_segment
  → page->uninit.aux = aux (파일 위치 정보)
  → spt_insert_page()

[page fault 시]
  → uninit_initialize()
  → page->type이 VM_ANON 또는 VM_FILE로 전환
  → aux 메모리 해제 ([lazy page aux ownership 계약](/wiki/os/lazy-page-aux-ownership-contract-knowledge))

aux 소유권

aux는 malloc()으로 할당하므로 사용이 끝난 뒤 반드시 해제해야 한다. page fault가 발생했다면 lazy_load_segment()에서 사용한 뒤 해제한다. 페이지에 한 번도 접근하지 않은 채 프로세스가 종료되면 uninit_destroy()에서 해제해야 한다. 두 경로 가운데 어느 쪽에서도 소유권을 처리하지 않으면 메모리 누수가 발생한다(lazy page aux cleanup 구현 체크리스트 Trace).

QEMU에서 보이는 흐름

QEMU는 guest의 PTE present bit를 보고 pf를 주입한다. 이때 발생한 page fault가 lazy loading을 위한 것인지 실제 segfault인지는 QEMU가 판단하지 않는다. guest OS인 PintOS가 fault의 원인을 확인하고 처리한다.

guest instruction: mov (%rax), %rbx  (rax = lazy page VA)
  → QEMU softmmu: guest PTE walk
  → present bit = 0
  → QEMU: guest에 #PF inject (CR2, error code 설정)
  → PintOS page_fault() 실행
  → ... lazy_load_segment() → file_read_at() ...
  → PintOS: pml4_set_page() — guest PTE present = 1 설정
  → handler 복귀
  → QEMU: 같은 instruction 다시 번역/실행
  → 이번에는 softmmu가 유효한 PTE 발견 → 정상 진행

QEMU의 소프트웨어 TLB(CPUTLBEntry)도 이 과정의 영향을 받는다. pml4_set_page()로 해당 VA의 PTE를 설정한 뒤 QEMU TLB 항목이 갱신되면, 다음 접근부터는 page table walk 없이 진행할 수 있다.

Lazy Loading 값 추적

PintOS에서 args-none 프로그램의 ELF segment를 lazy loading한다고 가정하면, 각 페이지에 등록되는 값은 다음과 같다.

ELF file: args-none
code segment: file offset 0x0, VA 0x400000, size 0x1a78
data segment: file offset 0x2000, VA 0x402000, size 0x10

code segment를 lazy loading할 때:
  page 1: VA=0x400000, read_bytes=4096, zero_bytes=0,   ofs=0x0
  page 2: VA=0x401000, read_bytes=2680, zero_bytes=1416, ofs=0x1000
  → 2개 UNINIT page가 SPT에 등록

data segment:
  page 3: VA=0x402000, read_bytes=16,   zero_bytes=4080, ofs=0x2000
  → 1개 UNINIT page 등록

총 3개 UNINIT page, 0개 물리 프레임 할당
→ 프로그램 시작 시 메모리 사용: 0 user pages
→ 첫 명령어 실행 시 page 1에서 #PF → 1 user page 할당

이 예시에서는 프로그램을 시작할 때 세 개의 UNINIT page만 SPT에 등록되고 물리 프레임은 할당되지 않는다. 첫 명령어가 page 1에 접근한 뒤에야 page fault 처리 과정에서 첫 번째 user page가 할당된다.

일반적인 프로그램 크기와 working set을 기준으로 제시된 메모리 절약 범위는 다음과 같다.

전체 프로그램 크기:    수 MB ~ 수십 MB
실제 접근 working set: 전체의 10~30% (locality of reference)
절약:                 70~90%의 물리 메모리

PintOS에서:
  user pool 크기 ≈ 약 367 pages (e820 크기에 따라)
  demand paging 없이 큰 프로그램 → 즉시 메모리 부족
  demand paging 있으면 → working set만큼만 사용

이 수치는 일반적인 범위를 설명하기 위한 값이며, 실제 절약량은 프로그램이 접근하는 working set과 e820에 따른 PintOS user pool 크기에 달려 있다.
