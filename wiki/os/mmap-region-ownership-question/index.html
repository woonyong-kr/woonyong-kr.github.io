mmap region metadata는 누가 소유해야 하나

한 줄 요약: mmap 범위와 reopened file reference는 mmap_region이, page별 offset·read_bytes·zero_bytes·writable은 struct file_page가, 첫 fault 전 임시 작업지시서는 aux가 소유한다. 이렇게 나누면 범위 단위로 움직이는 munmap, page 단위로 처리되는 page fault, 첫 fault 전후로 metadata가 이동하는 lazy loading의 책임을 분리해 double close를 막을 수 있다.

범위와 page의 metadata가 모두 필요한 이유

mmap munmap 범위 흐름 (Mmap Munmap Range Trace)에서 설명하듯 munmap(addr)은 시작 주소 하나만 받고 여러 page를 정리해야 한다. 여기서 한 단계 더 나아가면 다음 질문이 생긴다.

mmap()으로 생긴 범위, reopened file reference, page별 offset/read_bytes는 mmap_region, struct file_page, aux 중 누가 소유해야 할까?

이 문서에서 사용하는 소유권 계약은 다음과 같다.

mmap_region:
  mapping 범위와 reopened file reference의 주인

struct file_page:
  한 page의 file offset, read_bytes, zero_bytes, writable, region pointer의 주인

aux:
  첫 fault 전 UNINIT page가 쓰는 임시 작업지시서
  첫 fault 성공 또는 never-faulted cleanup 뒤에는 남지 않아야 함

munmap()은 범위 단위로 움직이고 page fault는 page 단위로 처리된다. lazy loading 과정에서는 첫 fault를 경계로 metadata가 머무는 위치도 달라진다. 따라서 범위 전체의 상태와 각 page의 상태를 한 객체에 몰아넣기보다 역할에 따라 나눠야 한다.

mmap() 한 번으로 여러 page가 만들어지는 경우를 보자.

void *map = mmap ((void *) 0x10000000, 6000, 1, fd, 0);

page size가 4096이면 이 호출은 두 page를 만든다.

page VA file offset file에서 읽을 byte zero-fill byte
0 0x10000000 0 4096 0
1 0x10001000 4096 1904 2192

해제할 때는 시작 주소만 전달한다.

munmap (map);

munmap()은 length를 다시 받지 않는다. 커널은 mmap()이 성공했을 때 이 base에서 시작하는 mapping에 몇 개의 page가 속하는지 따로 기억해야 한다.

반면 page fault는 page 하나를 대상으로 발생한다.

fault addr = 0x10001388
page base  = 0x10001000

이 fault를 처리하려면 두 번째 page의 file offset과 read_bytes가 필요하다. 즉, 해제 범위를 찾기 위한 region metadata와 fault를 처리하기 위한 page별 metadata가 모두 있어야 한다.

file reference의 수명도 별도로 정해야 한다. mmap-close와 mmap-remove에서는 mapping 뒤에 원래 fd를 닫거나 파일 이름을 지워도 mapping을 통해 데이터를 읽을 수 있어야 한다. mapping이 fd table의 원래 struct file *에 의존해서는 안 되는 이유다. mapping은 별도로 reopen한 file reference를 소유해야 한다.

이제 다음 질문을 순서대로 살펴볼 수 있다.

  1. page별 metadata만으로 munmap(addr)의 범위를 안정적으로 알아내기 어려운 이유는 무엇인가?
  2. aux가 reopened file을 계속 소유하면 왜 문제가 되는가?
  3. mmap_region과 struct file_page의 소유 범위는 어떻게 나눠야 하는가?
  4. 첫 fault가 발생한 page와 한 번도 fault 나지 않은 page를 같은 cleanup 흐름에서 어떻게 처리할 수 있는가?
  5. 실제 OS는 이 문제를 어떤 범위 객체로 해결하는가?
  6. QEMU는 이 ownership을 알고 있는가?
  7. GDB에서는 close, free, write-back이 한 번씩만 일어나는지 어디에서 확인할 수 있는가?

region, file_page, aux의 역할

초보 구현에서는 region을 봉투, file_page를 봉투 안의 낱장, aux를 첫 fault 전까지만 쓰는 임시 메모로 생각할 수 있다.

struct mmap_region
  base              0x10000000
  page_cnt          2
  file              reopened file reference
  mappings elem     current thread의 mmap list에 연결

struct file_page for VA 0x10000000
  region            -> mmap_region
  ofs               0
  read_bytes        4096
  zero_bytes        0
  writable          true

struct file_page for VA 0x10001000
  region            -> mmap_region
  ofs               4096
  read_bytes        1904
  zero_bytes        2192
  writable          true

aux before first fault
  region            -> mmap_region
  ofs/read/zero/writable for this page

각 자원의 owner는 다음과 같이 나눌 수 있다.

자원/의미 추천 owner 이유
mapping base mmap_region munmap(addr)가 region을 찾는 key
page count 또는 byte length mmap_region 시작 주소만으로 순회 범위를 알기 위해 필요
reopened file reference mmap_region fd close/remove 뒤에도 mapping 전체가 같은 file object를 써야 함
page file offset struct file_page 또는 page별 aux fault/write-back은 page 단위로 계산함
read_bytes/zero_bytes struct file_page 또는 page별 aux 마지막 page write-back 크기와 zero-fill 판단에 필요
writable SPT page metadata와 struct file_page protection fault와 PTE permission 판단에 필요
first-fault callback input aux UNINIT 상태에서만 필요한 임시 작업지시서

이 구분에서 지켜야 할 규칙은 한 자원을 닫는 owner를 하나만 두는 것이다.

좋은 계약:
  region이 reopened file을 한 번 close한다.
  aux는 region pointer를 빌려 쓰고 free만 한다.
  file_page는 region pointer를 통해 file을 사용하지만 close하지 않는다.

위험한 계약:
  region도 file_close(file)을 하고,
  aux 실패 경로도 file_close(file)을 하고,
  file_page destroy도 file_close(file)을 한다.

여러 객체가 같은 file을 닫으려 하면 double close나 dangling pointer로 이어지기 쉽다.

두 page mapping의 수명

sample.txt 6000바이트를 두 page로 mapping한다고 하자.

base   = 0x10000000
length = 6000
file   = sample.txt reopened reference

do_mmap()이 성공한 시점에는 실제 file bytes를 아직 읽지 않아도 된다. 대신 region과 두 개의 UNINIT(FILE) page가 만들어진다.

thread_current()->mmap_list
  region A
    base     = 0x10000000
    page_cnt = 2
    file     = file_reopen(fd file)

SPT
  0x10000000 -> UNINIT(FILE), aux(page 0)
  0x10001000 -> UNINIT(FILE), aux(page 1)

첫 번째 page에 접근하면 page fault가 발생한다.

vm_do_claim_page()
  -> uninit_initialize()
       aux(page 0)을 꺼냄
       file_backed_initializer()
       page->file.region = region A
       page->file.ofs = 0
       page->file.read_bytes = 4096
       page->file.zero_bytes = 0
       file_read_at(region->file, frame->kva, 4096, 0)
       free(aux)

두 번째 page에는 한 번도 fault가 발생하지 않은 상태에서 munmap(base)가 호출될 수도 있다.

do_munmap(0x10000000)
  -> region A를 찾음
  -> page 0은 FILE 상태: dirty이면 write-back, PTE clear, SPT remove
  -> page 1은 UNINIT(FILE) 상태: write-back 없이 aux free, SPT remove
  -> region A의 reopened file close
  -> region A free

따라서 do_munmap()은 resident page와 never-faulted page를 모두 처리할 수 있어야 한다.

실제 운영체제와 비교

Linux는 vm_area_struct 같은 VMA 범위 객체에 mapping의 시작, 끝, permission, file, offset을 기록한다. munmap(addr, length)가 호출되면 VMA tree에서 범위를 찾고, 필요하면 VMA를 나누거나 합친다. page fault가 발생하면 VMA를 근거로 해당 주소가 합법인지 판단하고 file-backed page를 page cache와 연결한다.

Windows도 mapped view, section object, VAD 같은 범위 metadata를 둔다. 사용자는 MapViewOfFile()로 view를 얻고 UnmapViewOfFile(base)로 해제한다. 커널은 그 base가 어떤 view와 section/file object에 연결되는지 별도로 알고 있다.

현실의 OS는 PintOS보다 훨씬 복잡한 조건을 다룬다.

  • 같은 file page를 여러 process가 공유할 수 있다.
  • private mapping과 shared mapping, copy-on-write, page cache, write-back error를 처리한다.
  • multi-threaded process에서 mapping 변경과 page fault가 동시에 발생할 때 lock으로 제어한다.

그 차이를 감안해도 학습용 구현에서 남는 구분은 다음과 같다.

page table은 번역표이고, mapping object는 의미표다.
범위와 원본 file 의미는 page table entry만으로 복구할 수 없다.
질문 Linux / Windows PintOS QEMU
범위는 누가 기억하는가 VMA, VAD, mapped view 구현자가 만든 mmap_region 또는 동등한 metadata 모름
file reference는 누가 붙잡는가 kernel file/section/page-cache object file_reopen()으로 만든 mapping 전용 reference host block backend만 봄
page별 offset은 어디에 있는가 VMA offset + page index, page cache metadata struct file_page 또는 page별 aux 모름

PintOS에서 정해야 하는 소유권 계약

W09 PintOS skeleton은 ownership을 강제하지 않고 구현자에게 빈칸으로 남긴다.

확인한 위치와 관찰 내용은 다음과 같다.

위치 관찰
lib/user/syscall.c:148-155 mmap()은 5개 인자를 넘기지만 munmap()은 addr 하나만 넘김

이 구조에서는 다음 설계가 소유권을 비교적 분명하게 드러낸다.

struct mmap_region {
    void *base;
    size_t page_cnt;
    struct file *file;
    struct list_elem elem;
};

struct file_page {
    struct mmap_region *region;
    off_t ofs;
    size_t read_bytes;
    size_t zero_bytes;
    bool writable;
};

struct mmap_aux {
    struct mmap_region *region;
    off_t ofs;
    size_t read_bytes;
    size_t zero_bytes;
    bool writable;
};

mmap_region은 struct thread의 list에 들어간다. struct file_page는 한 page의 계산 정보를 보관하고 region의 file을 빌려 쓴다. aux는 첫 fault 전까지 UNINIT page가 붙잡는 임시 복사본이다.

이 설계만 가능한 것은 아니다. page마다 file_reopen()을 호출하고 struct file_page가 각 file을 소유하게 만들 수도 있다. 그 경우에는 각 page가 자기 file을 닫는다는 계약을 끝까지 지켜야 한다. region이 닫을 file과 page가 닫을 file을 섞어서는 안 된다.

munmap()에 length가 없는 영향

W09 PintOS의 user wrapper는 다음 형태다.

lib/user/syscall.c:148-155
  mmap(addr, length, writable, fd, offset) -> syscall5(...)
  munmap(addr) -> syscall1(...)

munmap()이 length를 전달하지 않으므로 do_mmap()이 성공할 때 region length나 page count를 저장해야 한다.

skeleton이 남겨 둔 결정

include/vm/file.h:9-16의 struct file_page는 비어 있고, vm/file.c:49-57의 do_mmap()과 do_munmap()도 비어 있다. 과제 구현자는 다음 사항을 직접 정해야 한다.

  • mapping 목록을 struct thread에 둘지
  • SPT entry만으로 range를 찾을지
  • reopened file을 region 단위로 닫을지 page 단위로 닫을지
  • never-faulted UNINIT(FILE) page의 aux를 어디서 free할지

struct page union과 aux의 수명

include/vm/vm.h:51-60에서 uninit, anon, file은 같은 union 멤버다. page가 VM_UNINIT에서 VM_FILE로 바뀌면 union의 내용도 전환된다. 따라서 전환 뒤에도 page->uninit.aux를 읽는 방식보다 필요한 metadata를 page->file로 옮기는 방식이 안전하다.

fd와 mapping의 file reference

filesys/file.c:35-38의 file_reopen()은 같은 inode를 가리키는 새 file object를 만든다. filesys/file.c:55-63의 file_close()는 그 file object를 닫고 free한다.

mmap-close.c:18-26은 mapping 뒤 fd를 닫아도 mapping을 읽을 수 있어야 한다. mmap-remove.c:19-42는 파일 이름을 제거한 뒤에도 mapping data가 살아 있어야 한다. 따라서 mapping은 fd table의 원본 file pointer가 아니라 mapping 전용 reopened file reference를 가져야 한다.

process exit의 cleanup 경로

userprog/process.c:541-552는 process exit에서 열린 fd를 닫은 뒤 process_cleanup()으로 들어간다. process_cleanup()은 VM이 켜져 있으면 supplemental_page_table_kill(&curr->spt)를 호출한다.

이 시점에는 fd table의 file이 이미 닫혔을 수 있다. mapping cleanup은 별도 file reference와 SPT/page metadata를 기준으로 진행해야 한다.

dirty write-back에 필요한 page metadata

threads/mmu.c:285-293의 pml4_is_dirty()는 PTE dirty bit만 알려 준다. 마지막 page에서 파일에 몇 byte를 써야 하는지는 알려 주지 않는다. 마지막 page의 read_bytes는 struct file_page 또는 동등한 metadata가 보관해야 한다.

QEMU가 보는 범위

QEMU는 mmap_region이나 struct file_page를 알지 못한다. QEMU가 보는 것은 더 낮은 층의 동작이다.

  • guest CPU가 not-present PTE를 만나면 page fault를 만든다.
  • guest가 writable PTE에 store하면 dirty bit가 set될 수 있다.
  • PintOS가 dirty file-backed page를 file_write_at()으로 쓰면 파일 시스템과 IDE 장치 모델을 거쳐 block backend write가 발생한다.

QEMU 코드에서는 x86 page walk 중 store access가 dirty bit 후보를 세우는 흐름을 볼 수 있다.

target/i386/tcg/system/excp_helper.c:417-422
  store access이면 PG_DIRTY_MASK를 set 후보에 넣음

IDE sector write는 sector 번호를 byte offset으로 바꾼다.

hw/ide/core.c:1076-1102
  blk_aio_pwritev(..., sector_num << BDRV_SECTOR_BITS, ...)

따라서 어떤 page가 어느 mmap region에 속하는지는 QEMU가 아니라 PintOS 커널의 VM metadata가 부여하는 의미다.

값으로 따라가는 metadata

mapping 범위 계산

입력은 다음과 같다.

base   = 0x10000000
length = 6000 = 0x1770
PGSIZE = 4096 = 0x1000

page count는 다음과 같이 계산된다.

page_cnt = DIV_ROUND_UP(6000, 4096)
         = 2

region은 두 page를 순회한다.

i = 0 -> va = 0x10000000
i = 1 -> va = 0x10001000

이 순회를 안정적으로 수행하려면 mmap_region에 page_cnt나 rounded length가 있어야 한다.

두 번째 page의 file offset

주소 0x10001388에 쓰기가 들어왔다고 하자.

access VA       = 0x10001388
page base       = 0x10001000
offset in page  = 0x388 = 904
page file ofs   = 4096
file byte ofs   = 4096 + 904 = 5000

이 page가 dirty이면 page 전체가 아니라 read_bytes=1904만 write-back해야 한다.

file_write_at(region->file, frame->kva, 1904, 4096)

zero_bytes=2192까지 파일에 쓰는 방식은 원래 6000바이트인 파일 뒤에 padding까지 기록하게 된다.

owner별 free와 close 횟수

추천 계약에 따라 length=6000 mapping을 한 번 만들고 한 번 해제할 때 기대하는 횟수는 다음과 같다.

file_reopen: 1회
file_close(region->file): 1회
free(region): 1회
free(aux): page마다 1회, 총 2회
destroy(page): page마다 1회, 총 2회

page 0에 첫 fault가 발생하고 page 1은 never-faulted 상태로 남아 있어도 file_close(region->file)은 한 번만 호출되어야 한다.

소유권을 나누는 기준

mmap_region은 mapping 범위와 reopened file reference를 소유한다. struct file_page는 page별 offset, read_bytes, zero_bytes, writable, region pointer를 보관하며 file-backed page의 지속 metadata가 된다.

aux는 첫 fault 전까지만 필요한 임시 작업지시서다. 첫 fault 성공, callback 실패, never-faulted cleanup 중 해당하는 경로에서 한 번만 free되어야 한다. reopened file을 닫는 책임까지 region, page, aux가 함께 가지면 double close나 dangling pointer가 생길 수 있다.

QEMU는 이 ownership을 알지 못한다. page fault, dirty bit, block write처럼 guest에서 드러나는 하드웨어 효과만 에뮬레이션한다.

관련 문서

  • munmap 범위
    • munmap(addr)가 region 범위 전체를 순회하는 흐름.
  • mmap file page aux 전환
    • 첫 fault 뒤 aux 내용을 struct file_page로 옮기는 이유.
  • mmap UNINIT cleanup
    • never-faulted UNINIT(FILE) page를 write-back 없이 정리하는 흐름.
  • dirty write back QEMU Trace
    • dirty file-backed page가 파일과 QEMU block write로 내려가는 흐름.
  • mmap multi region isolation
    • 같은 파일 다중 mapping과 큰 mapping에서 region/page metadata가 섞이지 않는지 확인.
  • file backed metadata
    • page별 file offset/read_bytes/zero_bytes 판단 기준.
  • File Descriptor
    • fd close와 file object lifetime을 분리하는 이유.
