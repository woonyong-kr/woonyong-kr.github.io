메모리 단편화

메모리 단편화

한 줄 요약: 내부 단편화는 할당 블록 안에서 쓰지 않는 공간이고, 외부 단편화는 빈 공간이 흩어져 큰 요청을 못 채우는 상태다.

메모리 단편화 문제

메모리 할당기는 요청한 크기를 실제로 관리할 수 있는 할당 단위에 맞춘다. 요청보다 큰 단위를 내주면 이미 할당된 블록 안에 쓰지 않는 공간이 남는다. 반대로 빈 공간의 총량이 충분해도 여러 곳에 흩어져 있으면 연속된 공간을 요구하는 요청을 처리하지 못할 수 있다. 앞의 낭비가 내부 단편화이고, 뒤의 상태가 외부 단편화다.

이 구분은 PintOS의 두 할당기를 이해할 때 드러난다. malloc은 요청을 정해진 블록 크기에 맞추면서 블록 내부의 공간을 일부 포기한다. palloc은 여러 페이지를 한꺼번에 요청할 때 연속된 빈 페이지를 찾아야 하므로, 빈 페이지가 흩어져 있으면 할당에 실패할 수 있다. 따라서 페이지 크기나 2의 거듭제곱 블록을 사용하는 이유를 단편화 하나만으로 설명할 수는 없지만, 각 할당 방식이 어떤 공간을 낭비하는지 판단하는 데 이 구분을 사용할 수 있다.

내부 단편화 (Internal Fragmentation)

할당기가 요청보다 큰 블록을 내줄 때, 블록 안에서 실제로 사용되지 않는 바이트가 내부 단편화다. 규격화된 택배 상자에 작은 물건을 넣으면 물건이 차지하지 않는 공간이 상자 안에 남는 것과 같다.

PintOS malloc은 요청 크기를 수용할 수 있는 2의 거듭제곱 크기 블록을 선택한다. PintOS palloc처럼 페이지 단위로 할당하면 필요한 데이터가 마지막 페이지를 전부 채우지 못할 수 있다. 정렬(alignment)을 위해 추가한 패딩도 할당 영역 안에 사용하지 않는 공간을 만들 수 있다.

2의 거듭제곱 블록과 내부 단편화

요청 크기마다 별도의 할당 방식을 두면 관리할 대상이 많아진다. PintOS malloc은 제한된 수의 descriptor를 두고 블록 크기를 2의 거듭제곱으로 구성한다. 입력에 제시된 구현에서는 descs[10] 배열 가운데 16~1024바이트에 해당하는 7개 descriptor를 실제로 채운다. 이 구성은 블록 주소 계산을 비트 연산으로 처리할 수 있게 하지만, 요청 크기와 선택된 블록 크기의 차이는 사용되지 않는 공간으로 남는다.

내부 단편화 최악 = 블록 크기 - 1바이트

예를 들어 17바이트 요청이 32바이트 블록에 배정되면 블록 안의 15바이트, 즉 47%가 사용되지 않는다. 이 수치는 아래 PintOS 크기 구간에서 17바이트 요청을 처리하는 경우를 보여준다.

외부 단편화 (External Fragmentation)

외부 단편화는 빈 메모리의 총합은 요청보다 크거나 같지만, 요청을 담을 만큼 연속된 빈 공간이 없어서 할당하지 못하는 상태다. 빈자리가 10개인 주차장에서도 자리가 흩어져 있으면 연속 3자리가 필요한 대형 트럭을 세울 수 없는 것과 같다.

크기가 다른 블록을 반복해서 할당하고 해제하면 사용 중인 공간 사이에 서로 떨어진 빈 공간이 생길 수 있다. 다만 시간이 지났다는 사실만으로 항상 악화된다고 단정할 수는 없으며, 실제 상태는 할당과 해제의 크기 및 순서에 따라 달라진다.

페이징이 다루는 외부 단편화

가상 메모리의 페이징은 물리 메모리를 고정 크기 프레임(4KB)으로 나눈다. 가상 주소 공간에서 연속으로 보이는 페이지를 서로 떨어진 물리 프레임에 매핑할 수 있으므로, 프로세스가 “연속된 10페이지”를 사용하더라도 물리 메모리에서 연속된 프레임 10개를 확보할 필요는 없다. 이런 불연속 프레임 매핑을 사용하는 페이지 단위 할당에서는 연속된 물리 공간 부족으로 생기는 외부 단편화를 피할 수 있다.

그 대신 마지막 페이지가 모두 사용되지 않으면 내부 단편화가 남는다. 4097바이트에 2페이지(8192바이트)를 할당하는 경우에는 3095바이트가 사용되지 않는다.

이 설명은 불연속 물리 프레임을 매핑할 수 있는 가상 메모리의 페이지 할당에 관한 것이다. 아래 PintOS palloc_get_multiple은 비트맵에서 연속된 물리 페이지를 직접 찾으므로 같은 범위의 결론을 적용할 수 없다. 여러 연속 페이지를 요구하는 이 인터페이스에서는 외부 단편화가 발생할 수 있다.

실제 OS와 PintOS의 할당 방식

Linux는 slab allocator와 buddy system을 사용해 단편화를 줄인다. slab은 같은 크기의 객체를 모아 캐시하고, buddy는 2의 거듭제곱 페이지 묶음을 분할하고 병합한다.

PintOS에서는 palloc과 malloc이 서로 다른 단편화 양상을 보여준다. palloc은 비트맵 기반 페이지 할당기이므로 여러 연속 페이지를 찾을 때 외부 단편화의 영향을 받을 수 있다. malloc은 고정 크기 descriptor를 사용하므로 요청보다 큰 블록을 선택할 때 내부 단편화를 감수한다. 입력에 제시된 비교 범위에서 PintOS 구현은 이 차이를 단순하게 관찰할 수 있는 교육용 구현이며, production 용도의 단편화 완화 기능을 모두 갖춘 것으로 설명되지는 않는다.

메모리 단편화 코드

PintOS malloc — 내부 단편화가 발생하는 지점

block_size는 16부터 2배씩 증가한다. 루프 조건이 block_size < PGSIZE / 2(= 2048)이므로 입력에 제시된 값에서는 1024가 마지막 블록 크기이고, 2048 크기의 descriptor는 만들어지지 않는다. 17바이트를 요청하면 block_size >= size를 처음 만족하는 32바이트 descriptor가 선택되므로 15바이트가 블록 안에 남는다.

이 선택 과정은 요청을 담을 수 있는 가장 작은 descriptor를 찾는다. 해당 블록 크기가 요청보다 크면 두 크기의 차이만큼 내부 단편화가 생긴다.

PintOS palloc — 외부 단편화가 발생하는 지점

bitmap_scan_and_flip은 비트맵에서 page_cnt개의 연속된 빈 비트를 찾는다. 1페이지 단위의 할당과 해제로 빈 비트가 여러 곳에 흩어지면, 빈 페이지의 총수는 충분해도 여러 연속 페이지를 요청하는 호출은 실패할 수 있다. 이것이 palloc 수준에서 나타나는 외부 단편화다.

palloc_get_page처럼 항상 1페이지만 요청하면 연속된 여러 페이지를 확보할 필요가 없으므로 이 형태의 외부 단편화는 발생하지 않는다. 입력 문서의 설명 범위에서는 PintOS 가상 메모리 시스템이 대부분 1페이지 단위로 할당하며, palloc_get_multiple로 연속 페이지를 요청하는 경우에 외부 단편화가 문제가 될 수 있다. 큰 malloc 블록이 그 예로 제시된다.

단편화 비교 다이어그램

단편화를 구분하는 기준

할당된 블록의 크기가 요청보다 커서 공간이 남았다면 내부 단편화다. 빈 공간의 총량은 충분하지만 연속된 공간을 확보하지 못했다면 외부 단편화다. 페이징도 어떤 계층의 할당을 말하는지에 따라 판단이 달라진다. 불연속 물리 프레임을 매핑하는 페이지 할당은 외부 단편화를 피하지만, PintOS palloc_get_multiple처럼 연속된 물리 페이지를 직접 요구하는 할당은 외부 단편화의 영향을 받을 수 있다.

PintOS malloc은 descriptor의 고정 블록 크기 때문에 내부 단편화를 남긴다. PintOS palloc은 한 페이지 요청에서는 연속성 문제가 없지만, 여러 연속 페이지 요청에서는 흩어진 빈 페이지를 모두 활용하지 못할 수 있다. Linux의 slab allocator와 buddy system은 입력에 제시된 범위에서 각각 같은 크기 객체의 캐시와 페이지 묶음의 분할·병합을 통해 이러한 낭비를 줄이는 방식으로 설명할 수 있다.
