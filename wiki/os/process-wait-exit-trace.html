부모는 자식의 exit status를 어떻게 받는가

부모는 자식의 exit status를 어떻게 받는가

부모의 wait(pid)는 단순한 대기가 아니다. 자식이 남긴 exit_status를 커널의 child_status 레코드에서 읽고, 그 레코드를 한 번만 수거하는 약속이다.

wait/exit 동기화 쟁점

부모가 자식을 만든 뒤에는 두 사건의 순서가 달라질 수 있다. 부모가 먼저 wait(pid)를 호출할 수도 있고, 자식이 먼저 exit(42)로 끝날 수도 있다. 어느 쪽이 먼저 일어나더라도 부모는 같은 종료 상태를 받아야 하며, 한 번 수거한 상태를 다시 읽어서는 안 된다.

이 장면을 따라가려면 다음 질문을 순서대로 확인해야 한다.

  • 자식이 exit(42)로 끝나면 숫자 42는 어디에 저장될까?
  • 부모가 먼저 wait(pid)를 호출하면 어떤 자료구조에서 잠들까?
  • 자식이 먼저 죽으면 부모는 나중에 어디서 종료 코드를 읽을까?
  • 왜 struct thread 자체가 아니라 별도 child_status 레코드가 필요할까?
  • QEMU는 이 wait와 exit 의미를 알고 있을까?

여기서는 SYS_WAIT과 SYS_EXIT에서 시작해 PintOS의 child_status, wait_sema, exit_status까지 내려간다. 먼저 부모가 기다리고 자식이 종료되는 경로를 본 뒤, 자식이 먼저 종료된 경로와 중복 wait 방지를 살펴본다. 마지막에는 같은 사건이 실제 운영체제와 QEMU에서 각각 어느 층의 책임인지 구분한다.

시각 자료로 먼저 흐름을 보고 싶다면 PintOS 프로세스 시각화에서 fork, wait, exit, orphan reparent 그림을 먼저 본다. 부모가 wait()하지 않고 먼저 종료되는 경우는 orphan reparent에서 따로 본다.

부모가 먼저 wait하면 process_wait(tid)는 자식의 상태 레코드를 찾고, 자식이 아직 끝나지 않았을 때 sema_down(&cs->wait_sema)에서 잠든다. 자식은 종료 코드를 기록한 뒤 sema_up(&cs->wait_sema)을 호출해 부모를 깨운다.

sequenceDiagram
    participant PU as Parent (User)
    participant PK as Parent (Kernel)
    participant CS as child_status
    participant CK as Child (Kernel)
    participant CU as Child (User)

    PU->>PK: syscall wait(child_tid)
    PK->>CS: child_status_list에서 tid 검색
    PK->>CS: cs->waited = true
    Note over PK: cs->exited == false
    PK->>PK: sema_down(&cs->wait_sema) → BLOCKED

    CU->>CK: syscall exit(42)
    CK->>CS: cs->exit_status = 42
    CK->>CK: process_exit() → finish_self_status()
    CK->>CS: cs->exited = true
    CK->>PK: sema_up(&cs->wait_sema) → Parent UNBLOCK

    PK->>CS: status = cs->exit_status (= 42)
    PK->>CS: list_remove, free(cs)
    PK->>PU: return 42

자식이 먼저 죽어도 종료 상태는 사라지지 않는다. cs->exit_status와 cs->exited가 남고 semaphore 값도 올라가 있으므로, 나중에 들어온 부모는 기다리지 않고 상태를 읽어 레코드를 수거한다.

sequenceDiagram
    participant CK as Child (Kernel)
    participant CS as child_status
    participant PK as Parent (Kernel)

    CK->>CS: cs->exit_status = 42
    CK->>CS: cs->exited = true
    CK->>CS: sema_up(&cs->wait_sema)
    Note over CS: sema value = 1

    Note over PK: 나중에 wait(child_tid) 호출
    PK->>CS: cs->waited = true
    Note over PK: cs->exited == true → sema_down 건너뜀
    PK->>CS: status = 42
    PK->>CS: list_remove, free(cs)
    PK-->>PK: return 42

wait()가 수거하는 것

부모가 자식을 만들었다면 자식이 정상적으로 끝났는지, 끝났다면 어떤 종료 코드(exit status)를 남겼는지 알아야 한다. 이 정보가 없으면 shell은 명령의 성공과 실패를 알 수 없고, 테스트 러너는 자식 테스트가 통과했는지 판단할 수 없다. 종료한 자식의 상태 기록을 언제 정리할지도 결정하기 어렵다.

따라서 wait()는 시간을 기다리는 데 그치지 않는다. 자식의 종료 상태를 수거하고 커널의 프로세스 생명주기를 정리한다.

PintOS에서는 이 역할을 다음 필드와 자료구조가 나누어 맡는다.

질문PintOS에서 보는 위치
누가 내 자식인가?부모의 child_status_list
종료 코드는 어디에 남는가?struct child_status.exit_status
부모는 어떻게 잠들고 깨어나는가?wait_sema의 sema_down() / sema_up()
이미 wait했는지는 어떻게 막는가?struct child_status.waited
자식이 이미 죽었는지는 어떻게 기억하는가?struct child_status.exited

exit(42)의 42는 자식의 유저 스택에서 부모의 유저 스택으로 직접 전달되지 않는다. 자식과 부모가 함께 참조하는 커널 메모리의 child_status 레코드에 저장되고, 부모가 wait()에서 그 값을 읽는다.

작은 예제로 보는 상태 전달

PintOS 테스트 wait-simple은 이 흐름을 작게 보여준다.

파일:

  • SW_AI-W11-pintos/pintos/tests/userprog/wait-simple.c
  • SW_AI-W11-pintos/pintos/tests/userprog/child-simple.c

부모는 자식을 만든 뒤 기다린다.

자식 child-simple은 main()에서 return 81;로 끝난다. 유저 런타임 관점에서는 종료 상태 81을 남기는 흐름이다.

자식이 남긴 81이 부모의 wait(pid) 반환값으로 돌아와야 이 기대 출력과 일치한다.

PintOS에서 상태가 이동하는 경로

1. 부모와 자식이 함께 볼 상태 레코드를 만든다

파일:

  • SW_AI-W11-pintos/pintos/include/threads/thread.h
  • SW_AI-W11-pintos/pintos/userprog/process.c

struct child_status는 부모가 자식 하나를 추적하기 위한 상태표다.

struct thread에는 이 상태표를 연결하는 필드가 있다.

부모에게 child_status_list는 자식들의 상태표 목록이다. 자식에게 self_status는 부모가 자신을 기다릴 때 읽을 상태표다. 부모가 자식의 struct thread 자체를 붙잡는 대신 별도 레코드를 쓰기 때문에, 자식의 실행이 끝난 뒤에도 부모가 수거할 정보는 남길 수 있다.

process_create_initd()와 process_fork()는 새 child_status를 만들 때 다음 기본값을 넣는다.

기본 종료 코드가 -1이면 자식이 정상적인 exit(status) 경로에서 값을 쓰지 못하고 예외로 죽었을 때, 부모가 wait()에서 -1을 받는 흐름이 된다.

2. wait(tid)가 커널로 들어온다

파일:

  • SW_AI-W11-pintos/pintos/userprog/syscall.c

유저 프로그램이 wait(tid)를 호출하면 x86-64 syscall ABI에 따라 syscall 번호와 인자가 레지스터에 담긴다.

PintOS의 syscall handler는 이 값을 읽어 process_wait()로 넘긴다.

반환값은 다시 f->R.rax에 들어간다. process_wait()가 42를 반환하면 유저 프로그램의 wait(tid)도 42를 반환한다.

3. process_wait()가 자식 상태를 찾고 필요하면 잠든다

파일:

  • SW_AI-W11-pintos/pintos/userprog/process.c

process_wait(child_tid)는 부모의 목록에서 대상 레코드를 찾는다. 레코드가 없거나 이미 기다린 자식이면 -1을 반환한다. 처음 기다리는 자식이라면 waited를 기록하고, 종료되지 않은 경우에만 semaphore에서 잠든다.

flowchart TD
    A[process_wait 진입] --> B{child_status_list에서<br/>tid 찾음?}
    B -- No --> R1[return -1]
    B -- Yes --> C{cs->waited?}
    C -- true --> R2[return -1]
    C -- false --> D[cs->waited = true]
    D --> E{cs->exited?}
    E -- false --> F[sema_down → BLOCKED]
    F --> G[깨어남]
    E -- true --> G
    G --> H[status = cs->exit_status]
    H --> I[list_remove, free]
    I --> R3[return status]

자식이 아직 살아 있음sema_down(&cs->wait_sema)에서 부모가 block
자식이 이미 죽었음cs->exited == true이므로 잠들지 않고 exit_status 읽기
이미 wait한 자식cs->waited == true이면 -1

이 분기에서 exited는 기다릴 필요가 있는지를 판단하고, waited는 같은 종료 상태를 두 번 수거하지 못하게 한다.

4. exit(status)가 공유 레코드에 값을 쓴다

파일:

  • SW_AI-W11-pintos/pintos/userprog/syscall.c

SYS_EXIT은 첫 번째 인자 RDI를 종료 코드로 사용한다.

exit(status)는 현재 스레드의 self_status에 종료 코드를 기록하고 thread_exit()로 간다.

따라서 exit(42)의 숫자 42가 저장되는 위치는 curr->self_status->exit_status다.

5. 종료 사실을 기록하고 부모를 깨운다

파일:

  • SW_AI-W11-pintos/pintos/threads/thread.c
  • SW_AI-W11-pintos/pintos/userprog/process.c

thread_exit()은 userprog 빌드에서 process_exit()을 먼저 호출한다.

process_exit()은 열린 파일을 닫고, 자식 상태를 정리하거나 root로 넘긴 뒤, 자기 자신의 상태표를 마무리한다.

finish_self_status()는 자식이 부모에게 종료 사실을 알리는 지점이다.

부모가 이미 wait()에서 잠들어 있었다면 sema_up()이 부모를 깨운다. 부모가 아직 wait()를 호출하지 않았다면 exited = true와 종료 상태가 남으므로, 나중에 부모가 잠들지 않고 exit_status를 읽는다.

실제 운영체제와 PintOS의 범위

Linux와 Unix 계열에서는 wait(), waitpid() 같은 API가 자식의 종료 상태를 가져온다. 자식이 먼저 종료되면 커널은 종료 상태를 보존하고, 부모가 wait할 때 그 상태를 넘기며 자식을 수거한다. 여기서 zombie는 아직 실행 중인 프로세스라기보다 부모가 종료 상태를 수거하지 않아 남은 커널 기록에 가깝다.

Windows는 Unix식 부모-자식 수거 모델과 다르다. 프로세스는 커널 오브젝트이며, 유저 프로그램은 프로세스 handle을 통해 WaitForSingleObject()로 종료를 기다리고 GetExitCodeProcess()로 종료 코드를 확인할 수 있다. 부모 관계보다 handle과 object reference가 중심이다.

PintOS는 부모-자식 관계, 한 번만 가능한 wait, 종료 상태 전달, 기다리는 동안 block되는 동작을 child_status와 semaphore로 보여준다. 실제 OS의 signal, thread group, process group, handle reference count, job control 같은 정책까지 설명하는 모델은 아니다.

QEMU가 담당하지 않는 것

QEMU는 wait()나 exit()의 의미를 처리하지 않는다.

  • guest CPU가 syscall 명령을 실행한다.
  • PintOS 커널 코드가 guest memory 안의 struct thread, struct child_status, semaphore 필드를 읽고 쓴다.
  • sema_down() 때문에 PintOS scheduler가 현재 guest thread를 THREAD_BLOCKED로 바꾸고 다른 guest thread를 고른다.
  • GDB로 보면 QEMU gdbstub은 guest register와 guest memory를 읽어 보여줄 뿐, wait 정책을 해석하지 않는다.

관련 QEMU 위치:

    • x86_cpu_gdb_read_register
    • x86_cpu_gdb_write_register
  • gdbstub/gdbstub.c
    • gdb_read_register
    • gdb_write_register
    • handle_read_mem
    • handle_write_mem

부모를 언제 깨울지는 PintOS의 정책이다. QEMU는 그 정책을 실행할 CPU와 메모리 환경을 제공한다.

값과 메모리 위치 추적

exit(42)가 일어났다고 가정하자.

이 코드베이스의 struct child_status는 tid_t tid 다음에 int exit_status가 온다. x86-64 GCC의 보통 배치에서는 개념적으로 다음처럼 보인다.

정확한 오프셋은 컴파일러와 구조체 padding에 따라 GDB에서 확인해야 한다.

42는 유저 스택에 남아 부모가 직접 읽는 값이 아니다. exit(42)의 인자는 syscall 진입 순간 RDI = 42지만, 이후 부모가 읽을 값은 커널 메모리의 child_status.exit_status에 저장된다. 부모가 그 값을 읽어 process_wait()의 반환값으로 만들면 syscall handler가 f->R.rax에 넣는다.

GDB에서 흐름 확인하기

GDB에서는 syscall 진입, 부모의 대기, 자식의 상태 기록, 부모의 반환 순서로 보면 된다.

  1. syscall_handler에 breakpoint를 걸고 SYS_WAIT, SYS_EXIT 케이스를 본다.
  2. process_wait에서 p child_tid, p curr->child_status_list를 확인한다.
  3. 자식이 아직 살아 있으면 sema_down(&cs->wait_sema)로 들어가는지 본다.
  4. exit에서 p status, p curr->self_status를 확인한다.
  5. finish_self_status에서 p cs->exit_status, p cs->exited를 확인한다.
  6. sema_up(&cs->wait_sema) 뒤 부모가 깨어나 status를 반환하는지 본다.

  • 자식이 먼저 끝나면 exited = true와 exit_status가 남아 부모가 나중에 바로 읽는다.
  • wait()는 자식 스레드 자체가 아니라 부모가 가진 child_status 레코드를 기준으로 동작한다.
  • exit(status)의 status는 curr->self_status->exit_status에 저장된다.
  • 예외로 죽은 자식이 정상 exit(status) 경로에서 값을 쓰지 못하면 기본 exit_status = -1 흐름으로 관찰된다.
  • QEMU는 이 정책을 처리하지 않으며 PintOS guest 코드가 실행될 CPU와 메모리 환경을 제공한다.
