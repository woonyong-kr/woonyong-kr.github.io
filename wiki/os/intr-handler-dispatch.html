intr_handler() — 인터럽트 디스패치

intr_handler() — 인터럽트 디스패치

intr_handler() 변화

intr_handler()는 PintOS에서 모든 인터럽트, fault, exception이 거쳐가는 단일 진입점이다. IDT의 모든 벡터가 intr-stubs.S의 어셈블리 스텁을 통해 이 함수로 도달한다. 이 함수는 벡터 번호로 외부/내부 인터럽트를 구분하고, 등록된 핸들러를 호출하며, 외부 인터럽트의 경우 PIC EOI와 yield_on_return을 처리한다.

상세 설명

추상 개념 (CPU/하드웨어 규칙)

CPU는 인터럽트 발생 시 IDT에서 벡터 번호에 해당하는 게이트 디스크립터를 찾아 해당 핸들러 주소로 점프한다. CPU가 하는 일은 여기까지다.

이 문서는 현재 로컬 KAIST PintOS의 x86-64 구현을 기준으로 한다. 따라서 RSP, TSS.rsp0, iretq, 8-byte 함수 포인터를 사용한다. 32-bit i386 PintOS의 ESP, TSS.esp0, iret, 4-byte 포인터 규칙과 섞지 않는다.

단계CPU가 하는 일OS가 하는 일
1벡터 번호로 IDT 인덱싱 → ISR 주소 획득IDT를 미리 채워둠 (intr_init)
2RFLAGS/CS/RIP push; CPL 3→0이면 TSS.rsp0로 RSP 전환 후 old SS/RSP도 push—
3ISR 주소로 점프intr-stubs.S → intr_handler()
4—벡터 번호로 외부/내부 판단, 핸들러 호출
5—외부면 PIC EOI + yield 검사
6iretq로 복귀do_iret() 또는 intr-stubs.S 복귀

핵심 구분: 벡터 0x00~0x1F는 CPU 예외(#PF, gp, de 등), 벡터 0x20~0x2F는 PIC를 통한 외부 하드웨어 인터럽트(timer=0x20, keyboard=0x21, IDE=0x2E 등).

Linux는 APIC 기반으로 PIC를 대체했고, 각 인터럽트 소스마다 irq_desc 구조체에 핸들러 체인을 등록한다. PintOS는 PIC + 단일 디스패치 함수로 단순화되어 있다.

PintOS 구현

핸들러 등록 (부팅 시):

등록된 핸들러는 intr_handlers[256] 배열에 저장된다. 벡터 번호가 인덱스.

디스패치 본체:

10단계 동작 해설:

#동작이유
①벡터 범위로 external 판단외부 인터럽트만 PIC EOI와 yield가 필요
②in_external_intr = trueintr_context() 반환값 제어 — 재진입 방지
③yield_on_return = false핸들러가 명시적으로 set하지 않으면 yield 안 함
④intr_handlers[vec_no] 호출벡터별 등록된 C 함수 실행
⑤0x27/0x2F 무시PIC spurious IRQ — master IRQ7, slave IRQ15
⑥PANIC미등록 벡터는 버그
⑦~⑧external 후처리 진입핸들러 실행 완료 후 정리
⑨pic_end_of_interrupt()PIC에 EOI 전송 — 안 하면 이후 IRQ 영구 차단
⑩thread_yield()timer가 TIME_SLICE 만료를 감지했으면 여기서 선점

외부 vs 내부 인터럽트의 흐름 차이:

외부 (timer, IDE, keyboard):
  CPU push → intr-stubs.S → intr_handler
  → in_external_intr=true → handler() → EOI → yield? → return

내부 (page fault, syscall, #GP):
  CPU push → intr-stubs.S → intr_handler
  → handler() → return   (EOI 없음, yield 없음)

QEMU 에뮬레이션

QEMU에서 인터럽트 디스패치 경로:

  1. 외부 인터럽트 주입: QEMU i8259 모델이 IRQ를 올리면 CPUX86State.interrupt_request 플래그가 설정됨
  2. TB 종료 시점 검사: Translation Block 실행 후 인터럽트 pending 검사 → cpu_exec에서 do_interrupt_x86_hardirq 호출
  3. IDT 워크: do_interrupt_all()에서 guest IDT를 읽어 벡터별 게이트 → RSP 전환 → ISR 주소로 점프
  4. EOI: guest가 outb(0x20, 0x20) 실행 시 QEMU PIC 모델의 ISR 비트 클리어

QEMU는 intr_handler() 함수를 인식하지 않는다. guest 코드의 일반 함수 호출로 처리한다. QEMU가 관여하는 것은 하드웨어 인터럽트 주입(IDT walk)과 PIC I/O 포트 에뮬레이션뿐이다.

intr_handler() 값 추적

벡터 번호 할당표:

범위용도예시
0x00~0x13CPU 예외0x00=#DE(div), 0x06=#UD(invalid opcode), 0x0D=#GP, 0x0E=#PF
0x14~0x1FIntel 예약사용하지 않음
0x20~0x27Master PIC IRQ 0~70x20=timer, 0x21=keyboard
0x28~0x2FSlave PIC IRQ 8~150x2E=primary IDE, 0x2F=secondary IDE
0x30syscallint $0x30 (PintOS), 아닌 syscall 명령 사용 시 MSR 경유

PIC EOI 포트:

Master PIC: outb(0x20, 0x20)  — command port, OCW2 EOI 명령
Slave PIC:  outb(0xA0, 0x20)  — slave도 EOI 필요 (IRQ 8~15)

Spurious IRQ 조건:

  • Master IRQ 7 (vec 0x27): master PIC의 ISR에 해당 비트가 없는데 INT 발생
  • Slave IRQ 15 (vec 0x2F): slave PIC의 race condition

현재 x86-64 빌드의 intr_handlers 배열 크기: 256 × 8 bytes (함수 포인터) = 2048 bytes. i386 빌드에 일반화하지 않는다.
