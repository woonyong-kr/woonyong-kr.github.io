FAT·FFS·EXT

FAT·FFS·EXT

확인 범위: 이 문서는 FAT·FFS·EXT의 파일 위치 지정과 빈 공간 관리에 관한 일반 원리와 선택 기준을 설명하고, PintOS FAT 부분은 입력에 제시된 코드 구조를 바탕으로 구현 관점을 덧붙인다. 특정 PintOS 버전의 실제 코드 일치 여부, QEMU 디스크 이미지의 실행 기록, 성능과 용량 관련 판단은 별도의 버전 확인·실행·측정 없이는 검증 결과로 간주하지 않는다.

한 줄 요약: FAT는 연결 리스트 테이블로 클러스터를 체인 연결하고, FFS/EXT는 inode + 블록 포인터로 파일 위치를 관리하며, 세 방식은 “빈 공간 추적”과 “파일 데이터 위치 지정” 전략이 근본적으로 다르다.

FAT·FFS·EXT 혼동

디스크에 파일을 저장하려면 두 가지 문제를 풀어야 한다.

  1. 파일 데이터가 어디에 있는가? — 파일 내용이 디스크 어느 섹터/클러스터에 흩어져 있는지 추적해야 한다.
  2. 빈 공간은 어디인가? — 새 파일을 쓸 때 사용 가능한 영역을 빠르게 찾아야 한다.

이 두 문제를 푸는 방식에 따라 파일 시스템의 성격이 완전히 달라진다. FAT, FFS(Berkeley Fast File System), EXT(Extended File System)는 각각 다른 전략을 선택했다. 이 세 가지를 비교하면 파일 시스템 설계의 핵심 트레이드오프를 이해할 수 있다.

PintOS Project 4에서 FAT 모드를 직접 구현하므로, FAT의 내부 구조를 코드 수준으로 이해하는 것이 필수다.

FAT·FFS·EXT 흐름

FAT — 테이블 하나로 모든 파일을 추적한다

FAT(File Allocation Table)는 MS-DOS 시절부터 쓰인 가장 단순한 파일 시스템이다. 핵심 아이디어는 디스크 전체에 대한 “클러스터 연결 테이블”을 하나 두는 것이다.

비유: 보물찾기 게임이다. 첫 번째 쪽지에 “다음 쪽지는 5번 상자에 있다”고 적혀 있고, 5번 상자의 쪽지에는 “다음은 12번 상자”라고 적혀 있다. 마지막 쪽지에는 “끝”이라고 적힌다. FAT 테이블이 바로 이 쪽지 모음이다.

동작 원리:

  1. 디스크의 데이터 영역을 동일한 크기의 클러스터로 나눈다.
  2. FAT 테이블은 클러스터 수만큼의 엔트리를 가진 배열이다.
  3. FAT[i]의 값은 클러스터 i 다음에 오는 클러스터 번호이다.
  4. 체인의 마지막 클러스터는 EOChain(End Of Chain) 값을 갖는다.
  5. 빈 클러스터는 FAT 엔트리 값이 0이다.

  fat_table["클러스터 번호 &#124; 0 &#124; 1 &#124; 2 &#124; 3 &#124; 4 &#124; 5 &#124; 6 &#124; 7<br/>다음 클러스터 &#124; --- &#124; EOF &#124; 5 &#124; 0 &#124; 6 &#124; EOF &#124; EOF &#124; 0"]
  summary["해석<br/>파일 A: 클러스터 2 -&gt; 5 -&gt; EOF<br/>파일 B: 클러스터 4 -&gt; 6 -&gt; EOF<br/>빈 공간: 클러스터 3"]

FAT의 장점은 단순함이다. 빈 공간을 찾으려면 테이블을 순회하며 값이 0인 엔트리를 찾으면 된다. 단점은 랜덤 접근이 느리다는 것이다. 파일의 N번째 클러스터를 찾으려면 체인을 처음부터 N번 따라가야 한다.

FFS — 디스크 구조를 이해하는 파일 시스템

Berkeley FFS(Fast File System, 1984)는 초기 UNIX 파일 시스템의 성능 문제를 해결하기 위해 만들어졌다. 핵심 혁신은 디스크의 물리적 구조를 파일 시스템 설계에 반영한 것이다.

초기 UNIX FS는 inode를 디스크 맨 앞에 몰아놓고 데이터 블록을 뒤에 배치했다. 파일을 읽으려면 inode(앞)와 데이터(뒤) 사이를 디스크 헤드가 왕복해야 했다. FFS는 이 문제를 **실린더 그룹(Cylinder Group)**으로 해결한다.

FFS의 핵심 설계:

  1. 디스크를 여러 실린더 그룹으로 나눈다.
  2. 각 그룹에 슈퍼블록 복사본, inode 테이블, 데이터 블록을 함께 배치한다.
  3. 같은 디렉터리의 파일은 같은 실린더 그룹에 할당한다.
  4. inode와 데이터가 가까이 있어 디스크 탐색 시간이 줄어든다.

  disk["디스크 전체<br/>실린더 그룹 0 &#124; 실린더 그룹 1 &#124; 실린더 그룹 2<br/>슈퍼블록 복사<br/>inode 비트맵<br/>블록 비트맵<br/>inode 테이블<br/>데이터 블록 &#124; 슈퍼블록 복사<br/>inode 비트맵<br/>블록 비트맵<br/>inode 테이블"]
  note["배치 의도<br/>같은 디렉터리의 inode와 데이터 블록을 가까운 그룹에 배치<br/>디스크 헤드 이동을 줄여 읽기 비용 완화"]

FFS는 또한 inode 안에 직접 블록 포인터(12개)와 간접 블록 포인터(single/double/triple indirect)를 두어, 파일 데이터가 디스크에 흩어져 있어도 빠르게 찾을 수 있게 했다. FAT의 연결 리스트 방식과 달리, N번째 블록을 찾는 데 체인을 따라갈 필요가 없다.

EXT — Linux의 표준 파일 시스템

EXT(Extended File System) 계열은 FFS의 설계를 Linux에 맞게 발전시킨 것이다. ext2 → ext3 → ext4로 진화했다.

  • ext2 (1993): FFS의 실린더 그룹을 블록 그룹으로 변환. 실린더라는 물리 개념 대신 논리적 블록 그룹으로 같은 효과를 낸다.
  • ext3 (2001): ext2에 저널링을 추가. 갑자기 전원이 꺼져도 파일 시스템 일관성을 복구할 수 있다.
  • ext4 (2008): extent 기반 할당 도입. 연속된 블록을 하나의 (시작 블록, 길이) 쌍으로 표현해서, 직접/간접 블록 포인터의 오버헤드를 줄인다.

QEMU 에뮬레이션 관점

PintOS가 FAT 테이블이나 데이터 클러스터를 읽고 쓸 때, 실제로는 QEMU가 에뮬레이션하는 IDE 컨트롤러를 통해 호스트의 디스크 이미지 파일에 접근한다. FAT 테이블은 섹터 1부터 시작하므로 호스트 이미지 파일에서 바이트 512(0x200) 지점부터 FAT 엔트리가 배열된다.

%% PintOS FAT 섹터와 QEMU 디스크 이미지 오프셋
flowchart TD
  mapping["PintOS FAT 구조 &#124; 호스트 디스크 이미지 pintos.dsk<br/>섹터 0: fat_boot &#124; 바이트 0x000 ~ 0x1FF<br/>섹터 1: FAT[0..127] &#124; 바이트 0x200 ~ 0x3FF<br/>섹터 2: FAT[128..255] &#124; 바이트 0x400 ~ 0x5FF<br/>... &#124; ...<br/>섹터 N+1: 데이터 시작 &#124; 바이트 (N+1)*512 ~<br/>QEMU는 섹터 번호를 512바이트 단위 오프셋으로 해석"]

디버깅 시 hexdump -C -s 0x200 -n 512 pintos.dsk로 FAT 테이블의 첫 섹터를 확인할 수 있다. 각 4바이트가 하나의 cluster_t 엔트리이며, 리틀 엔디안으로 저장된다. 0xFFFFFF0F가 보이면 EOChain(0x0FFFFFFF)이다.

QEMU는 이 과정에서 파일 시스템의 의미를 전혀 모른다. 단지 IDE PIO 명령에 따라 섹터 번호를 바이트 오프셋으로 변환하여 호스트 파일을 읽고 쓸 뿐이다. 자세한 구조는 IDE 컨트롤러 모델과 QEMU BlockBackend를 참고한다.

FAT·FFS·EXT 코드

PintOS의 FAT 테이블 구조

fat 필드가 핵심이다. fat[i]의 값이 클러스터 i의 다음 클러스터 번호다. EOChain(0x0FFFFFFF)이면 체인의 끝이고, 0이면 빈 클러스터다.

PintOS FAT 디스크 레이아웃

%% PintOS FAT 디스크 레이아웃
flowchart TD
  layout["부트 섹터 &#124; FAT 테이블 &#124; 데이터 영역<br/>(fat_boot) &#124; fat_start ~ N &#124; 클러스터 1"]

fat_boot_create()에서 FAT 테이블이 차지할 섹터 수를 계산한다.

한 섹터(512B)에 cluster_t(4B) 엔트리가 128개 들어간다. SECTORS_PER_CLUSTER가 1이므로 FAT 엔트리 128개당 데이터 섹터 128개 + FAT 섹터 1개가 필요하다. 이 비율로 전체 디스크를 나누면 FAT 영역 크기가 결정된다.

PintOS의 체인 생성 (fat_create_chain)

fat_create_chain()은 클러스터 체인에 새 클러스터를 추가하는 함수다. 이 함수가 파일 확장의 핵심이다.

PintOS Original FS vs FAT 모드

PintOS에는 두 가지 파일 시스템 모드가 존재한다. EFILESYS 매크로로 전환한다.

Original FS는 free_map(비트맵)으로 빈 섹터를 추적하고, inode의 start 필드로 연속 할당한다. FAT 모드는 FAT 테이블로 빈 클러스터를 추적하고, 체인으로 비연속 할당을 지원한다.

정리

FAT는 하나의 테이블(배열)로 클러스터 체인을 관리하는 가장 단순한 방식이다. 구현이 쉽고 호환성이 높지만 랜덤 접근이 느리다. FFS는 실린더 그룹으로 inode와 데이터를 가까이 배치해 디스크 탐색을 줄였고, EXT4는 여기에 저널링과 extent를 추가해 Linux 표준이 되었다. PintOS Project 4에서는 FAT 모드를 구현하며 fat_create_chain(), fat_remove_chain(), fat_get(), fat_put() 네 함수가 핵심이다.
