Guest Register Hosting — QEMU가 게스트 레지스터를 보관하는 방법

Guest Register Hosting — QEMU가 게스트 레지스터를 보관하는 방법

확인 범위: 이 문서는 QEMU의 TCG·KVM 모드에서 게스트 레지스터를 보관하고 GDB 및 PintOS와 연동하는 방식을 개념적으로 설명한다. 구조체 배치·offset·동기화 경로·명령어 수·성능·중단 시 일관성에 관한 구체적 주장은 특정 QEMU 코드와 빌드 옵션, 버전 및 실제 실행 기록을 확인해야 하는 구현 수준의 내용이다.

한 줄 요약: 게스트 CPU의 모든 레지스터를 host 메모리의 CPUX86State 구조체 필드로 보관하는 QEMU 방식.

Guest Register Hosting 상태

QEMU는 게스트 CPU의 모든 아키텍처 레지스터(RAXR15, RIP, RFLAGS, CR0CR4, 세그먼트 셀렉터 등)를 호스트 메모리의 C 구조체 CPUX86State 필드로 보관한다. 실제 하드웨어에서는 레지스터 파일이라는 전용 SRAM에 저장되지만, 에뮬레이터에서는 그냥 uint64_t 배열이다. TCG가 번역한 호스트 코드는 이 구조체의 필드를 직접 load/store하여 게스트 명령어를 실행하고, GDB stub은 이 필드를 읽어 디버거에 전달한다.

상세 설명

추상 개념 (레지스터 파일)

실제 x86-64 CPU의 레지스터는 CPU 다이 내부의 register file에 물리적으로 존재한다. 프로그래머가 mov rax, [rbx]를 실행하면 하드웨어가 register file에서 RBX 값을 읽어 주소로 사용하고, 메모리에서 가져온 값을 RAX 위치에 쓴다. 이 과정은 나노초 단위로 일어나며 소프트웨어가 개입할 여지가 없다.

에뮬레이터가 이를 소프트웨어로 재현하려면, register file을 호스트 메모리의 구조체로 모델링해야 한다.

QEMU 구현

CPUX86State 내부의 레지스터 배치

인덱싱 규칙

범용 레지스터 배열 regs[]의 인덱스는 x86 인코딩 순서를 따른다:

인덱스레지스터인덱스레지스터
0RAX8R8
1RCX9R9
2RDX10R10
3RBX11R11
4RSP12R12
5RBP13R13
6RSI14R14
7RDI15R15

이 순서는 ModR/M 바이트의 reg 필드 인코딩과 일치한다. GDB 프로토콜도 이 순서로 레지스터를 요청한다.

TCG가 레지스터를 읽고 쓰는 방식

TCG(Tiny Code Generator)는 게스트 명령어를 호스트 명령어로 번역할 때, 게스트 레지스터 접근을 CPUX86State 구조체의 필드 offset으로 변환한다:

게스트: mov rax, rbx
  ↓ TCG 번역
호스트: load tmp, [env + offsetof(CPUX86State, regs[3])]   // RBX 읽기
        store tmp, [env + offsetof(CPUX86State, regs[0])]   // RAX 쓰기

여기서 env는 현재 vCPU의 CPUX86State* 포인터이며, TCG가 번역한 모든 코드 블록에서 고정 레지스터(호스트 측)에 유지된다. offsetof는 컴파일 타임에 결정되어 단순 load/store 명령어로 치환된다.

GDB Stub이 레지스터를 읽는 경로

GDB: "g" 패킷 (모든 레지스터 읽기)
  → gdb_stub → cpu_gdb_read_register()
    → env->regs[0]  (RAX)
    → env->regs[1]  (RCX)
    → ...
    → env->eip      (RIP)
    → env->eflags   (RFLAGS)
    → env->segs[R_CS].selector  (CS)
    → ...

KVM 모드와의 비교 — 레지스터가 실제 하드웨어에 있는 경우

QEMU가 KVM 가속을 사용하면 게스트 레지스터는 실제 CPU 하드웨어에 존재한다. 이때 CPUX86State는 “마스터 복사본”이 아니라 “캐시된 스냅샷”으로 역할이 바뀐다:

항목TCG 모드 (PintOS 기본)KVM 모드
레지스터 실체CPUX86State 구조체 (호스트 메모리)실행 중에는 host CPU register file, VM exit 뒤에는 kernel KVM vCPU 상태
게스트 실행 중TCG 코드가 구조체 load/storeCPU가 직접 하드웨어 레지스터 사용
QEMU 제어권 복귀 시실행 경계에서 CPUX86State와 일관된 상태필요 시 KVM_GET_REGS ioctl로 vCPU GPR→QEMU 상태 동기화
GDB 읽기구조체 직접 읽기먼저 KVM_GET_REGS 호출 필요
성능느림 (소프트웨어 해석)빠름 (하드웨어 직접 실행)

KVM에서 VMCS(Virtual Machine Control Structure)는 Intel VT-x의 guest 제어 상태와 RIP/RSP/RFLAGS 같은 일부 guest 상태를 담지만, 일반 목적 레지스터 전체의 저장소는 아니다. Guest GPR은 실행 중 host CPU 레지스터에 있고 VM exit 뒤 kernel KVM vCPU 상태로 보존된다. QEMU는 필요할 때 KVM_GET_REGS로 그 vCPU 상태를 조회해 자신의 CPU 상태와 동기화한다.

PintOS는 TCG 모드로 실행되므로 이 구분이 직접 영향을 미치지 않지만, CPUX86State가 왜 존재하는지 이해하려면 “TCG에서는 유일한 진실, KVM에서는 동기화된 캐시”라는 이중 역할을 알아야 한다.

레지스터 Dirty Tracking과 Translation Block 최적화

TCG는 CPUX86State의 모든 필드를 매 명령어마다 읽고 쓰지 않는다. Translation Block(TB) 단위로 최적화한다:

  1. TB 시작: 게스트 레지스터를 CPUX86State에서 호스트 임시 레지스터(TCG temp)로 로드
  2. TB 내부: 호스트 레지스터 간 연산 — CPUX86State 접근 없이 진행
  3. TB 종료: 변경된 게스트 레지스터만 CPUX86State에 store back

이 “지연된 store-back” 덕분에, TB 내부에서 RAX를 10번 수정해도 CPUX86State에는 마지막 값 1회만 기록된다. 단, TB 경계에서는 반드시 모든 dirty 레지스터를 flush해야 다음 TB가 올바른 값을 읽는다.

TCG 임시 변수의 수명:

TB 시작: load rax_temp ← env->regs[0]
         load rbx_temp ← env->regs[3]
게스트 insn 1: add rax_temp, rbx_temp   (env 접근 없음)
게스트 insn 2: mov rcx_temp, rax_temp    (env 접근 없음)
...
TB 종료: store env->regs[0] ← rax_temp  (dirty → flush)
         store env->regs[1] ← rcx_temp  (dirty → flush)
         (rbx는 수정되지 않았으므로 store 안 함)

PintOS 디버깅에서의 의미

PintOS를 QEMU + GDB로 디버깅할 때 info registers가 보여주는 모든 값은 CPUX86State 필드에서 온다. 예를 들어:

  • rax = 0x1 → env->regs[0] == 0x1 (syscall 번호 SYS_HALT)
  • rip = 0x80048e0 → env->eip == 0x80048e0 (현재 실행 중인 유저 코드 주소)
  • cr3 = 0x3ff000 → env->cr[3] == 0x3ff000 (현재 프로세스의 PML4 물리 주소)

context switch가 발생하면 PintOS가 struct intr_frame에 레지스터를 저장/복원하는데, 이때 QEMU 관점에서는 게스트 코드가 메모리에 write하는 것일 뿐 — CPUX86State의 값이 게스트 소프트웨어에 의해 갱신되는 것이다.

GDB breakpoint와 레지스터 일관성:

GDB에서 breakpoint를 설정하면 QEMU는 현재 TB 실행을 중단하고 모든 dirty 레지스터를 CPUX86State에 flush한 뒤 GDB stub에 제어를 넘긴다. 따라서 info registers로 보는 값은 항상 breakpoint 시점의 정확한 스냅샷이다. 단, breakpoint 없이 Ctrl+C로 멈추면 TB 중간에서 중단될 수 있어, 일부 레지스터가 아직 flush되지 않았을 가능성이 이론적으로 존재한다 (실제로는 QEMU가 중단 시 flush를 보장).

PintOS Context Switch와 CPUX86State의 관계

PintOS의 thread_launch()가 레지스터를 push/pop할 때, QEMU 관점에서 일어나는 일:

PintOS: push rax     → 게스트 RSP -= 8, mem[RSP] = env->regs[0]
QEMU:   1. env->regs[4] -= 8                (RSP 갱신)
        2. address_space_write(env->regs[4], env->regs[0], 8)  (메모리에 기록)

PintOS: pop rax      → rax = mem[RSP], RSP += 8
QEMU:   1. address_space_read(env->regs[4], &val, 8)   (메모리에서 읽기)
        2. env->regs[0] = val               (RAX 갱신)
        3. env->regs[4] += 8                (RSP 갱신)

즉, PintOS의 “레지스터 저장”은 QEMU에서 “구조체 필드 → guest memory”로의 데이터 이동이고, “레지스터 복원”은 “guest memory → 구조체 필드”로의 이동이다. 실제 하드웨어에서 register file ↔ cache/DRAM 간 이동이 일어나는 것과 개념적으로 동일하다.

Guest Register Hosting 값 추적

항목값
CPUX86State 전체 크기약 10~20 KB (빌드 옵션에 따라 변동)
범용 레지스터 영역16 × 8 = 128 bytes (regs[0]~regs[15])
regs[0] offset0 (구조체 첫 필드)
regs[4] (RSP) offset32 bytes
eip offset128 bytes (regs[] 직후)
cr[3] (CR3) offset구조체 중반부 (~수백 bytes)
TCG load/store 오버헤드호스트 1~2 명령어 (base+offset 주소 계산 + 메모리 접근)

레지스터 접근 빈도 예시: guest mov rax, [rbx+8]

1. 호스트 load: env->regs[3]  → RBX 값 획득 (1 host insn)
2. 호스트 add:  RBX + 8       → 게스트 주소 계산 (1 host insn)
3. 호스트 load: softmmu lookup → 게스트 메모리 접근 (여러 host insn)
4. 호스트 store: env->regs[0] → RAX에 결과 저장 (1 host insn)
