thread_yield() 자발적 CPU 양보

확인 범위: 이 문서는 CPU 양보와 스케줄링의 일반 원리를 설명하되, 상태 전이·인터럽트 제어·실행 순서와 다른 운영체제와의 비교는 제시된 PintOS 구현을 기준으로 다룬다. 코드 좌표와 GDB·QEMU 시나리오는 관찰 방법과 예상 흐름이며, 버전별 구현 세부사항과 오버헤드·시간·큐 길이 같은 값은 해당 코드와 실제 실행·성능 측정으로 별도 검증해야 한다.

thread_yield()는 현재 스레드를 RUNNING에서 READY로 되돌리고 스케줄러에 CPU를 자발적으로 넘긴다. 스레드가 잠드는 것은 아니므로 우선순위에 따라 곧바로 다시 선택될 수도 있다.

thread_yield()가 바꾸는 것

thread_yield()를 호출한 스레드는 RUNNING에서 READY로 전이되고 ready_list에 다시 들어간다. 스케줄러는 그다음 실행할 스레드를 고른다. thread_block()을 호출했을 때처럼 BLOCKED 상태가 되는 것이 아니므로, CPU를 양보한 스레드도 ready_list에서 다른 스레드와 다시 경쟁한다.

CPU 양보와 인터럽트 제어

CPU 자체에는 “yield” 명령어가 없다. CPU는 명령어를 순서대로 실행하며, yield는 OS가 구현하는 소프트웨어 규약이다.

다만 yield 과정에서 race condition을 막으려면 하드웨어의 인터럽트 제어가 필요하다. 이 문서의 PintOS 구현은 x86-64의 cli 명령으로 RFLAGS.IF를 0으로 만든다. 외부 인터럽트를 차단한 동안 ready_list 조작, 상태 전이, context switch를 이어서 수행한다. 인터럽트를 끄지 않으면 timer interrupt가 끼어들어 ready_list를 동시에 건드릴 수 있다.

관점yield와의 관계
CPUyield 개념 없음, cli/sti로 IF 비트만 제어
MMUyield 자체와 무관, CR3 전환은 schedule() 단계에서 발생
PICIF=0이면 IRQ 전달 보류, yield 중 timer가 끼어들지 못함

Linux의 yield()는 CFS의 vruntime을 최대로 올려 해당 태스크를 뒤로 밀어낸다. PintOS의 thread_yield()가 스레드를 ready queue의 뒤쪽으로 보내는 것과 개념적으로 비슷하다. 다만 Linux의 SMP 환경에서는 per-CPU runqueue와 스핀락을 사용하며, PintOS는 단일 CPU에서 cli/sti로 인터럽트를 제어한다.

PintOS 구현과 실행 순서

호출부터 복귀까지는 다음 순서로 진행된다.

  1. ASSERT(!intr_context()) — 인터럽트 핸들러 안에서 thread_yield()를 직접 호출하지 못하게 한다. 핸들러에서는 즉시 호출하는 대신 yield를 예약하며, 그 이유는 인터럽트 끝에서 yield하는 이유에서 다룬다.
  2. intr_disable() — RFLAGS.IF를 0으로 만들어 timer interrupt를 차단한다. ready_list를 조작하는 동안 race condition이 생기지 않도록 하기 위한 단계다.
  3. list_insert_ordered() — 현재 스레드를 priority 내림차순에 맞춰 ready_list에 삽입한다. idle_thread는 ready_list가 비었을 때만 실행되므로 삽입하지 않는다.
  4. do_schedule(THREAD_READY) — 현재 스레드의 상태를 READY로 바꾸고 schedule() → next_thread_to_run() → thread_launch()를 호출한다. 이 과정에서 실제 context switch가 일어난다.
  5. intr_set_level(old_level) — context switch 직후에 실행되는 코드가 아니다. 양보한 스레드가 나중에 다시 스케줄되면 이 줄부터 실행을 재개하고, 저장해 둔 인터럽트 수준을 복원한다.

QEMU에서 보이는 동작

QEMU는 thread_yield() 자체를 별도의 동작으로 인식하지 않는다. guest OS가 실행하는 개별 명령과 메모리 접근을 다음과 같이 처리한다.

  1. cli 명령 → QEMU TCG가 CPUX86State.eflags IF 비트를 0으로 설정
  2. ready_list 메모리 조작 → 일반 메모리 접근으로 에뮬레이션
  3. thread_launch() → RSP 전환을 통한 스택 교체, QEMU는 일반 mov 명령으로 처리
  4. iretq 또는 sti → IF 비트 복원, 보류된 IRQ가 있으면 이 시점에 전달

비용과 스케줄링 값

  • yield 오버헤드: intr_disable() → list_insert_ordered(O(n), n=ready_list 길이) → schedule() → thread_launch(). 최소 수백 cycle.
  • ready_list 최대 길이: PintOS에서 스레드 수에 비례. 테스트 환경에서 보통 10개 미만.
  • TIME_SLICE와의 관계: TIME_SLICE = 4 ticks = 40ms. thread_yield()는 TIME_SLICE가 끝나기 전에도 호출할 수 있다.
  • thread_ticks 리셋: schedule()에서 thread_ticks = 0으로 초기화한다. yield한 스레드가 다시 선택되면 새 time slice가 시작된다.

실행 흐름

sequenceDiagram
    participant C as Current Thread
    participant K as Kernel (thread.c)
    participant S as Scheduler
    participant N as Next Thread

    C->>K: thread_yield()
    K->>K: ASSERT(!intr_context())
    K->>K: intr_disable() — IF=0
    K->>K: list_insert_ordered(ready_list, curr)
    K->>S: do_schedule(THREAD_READY)
    S->>S: curr->status = THREAD_READY
    S->>S: next = next_thread_to_run()
    S->>N: thread_launch(next)
    Note over C: 여기서 멈춤 — RSP가 next로 전환됨
    Note over N: next의 thread_launch 복귀 지점부터 실행
    Note over C: (나중에 다시 스케줄되면)
    C->>K: intr_set_level(old_level) — IF 복원

thread_yield()로 이어지는 경로는 다음과 같다.

  • thread_yield() 호출자
  • thread_create() — 새 스레드가 더 높은 우선순위일 때
  • check_preemption() — thread_set_priority(), sema_up() 등에서
  • intr_handler() — yield_on_return 플래그가 set된 경우
  • (timer tick에서 TIME_SLICE 만료 시)
