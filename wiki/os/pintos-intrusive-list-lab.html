PintOS intrusive list 실험: list_elem 주소에서 struct thread 복원하기

한 줄 요약: list_elem 주소를 이용해 바깥쪽 struct thread를 복원하는 PintOS intrusive list 실험이다.

PintOS intrusive list의 구조

PintOS의 리스트(ready_list, sleep_list, waiters, donation_list 등)는 모두 intrusive list 방식으로 구현된다. 별도로 할당한 리스트 노드를 사용하는 대신, 노드(struct list_elem)를 바깥 구조체 안에 필드로 직접 포함한다. 따라서 리스트에 저장되는 값은 “바깥 구조체의 포인터”가 아니라 **“바깥 구조체 안에 있는 list_elem 필드의 주소”**다. 이 주소에 list_entry() 매크로를 적용하면 원래 구조체를 복원할 수 있다.

Intrusive list가 OS 커널에서 선호되는 이유는 커널에서 malloc 실패가 치명적일 수 있고, 노드를 별도로 할당하는 오버헤드도 피해야 하기 때문이다. 또한 하나의 구조체가 여러 리스트에 동시에 속하는 패턴이 자주 나타난다. 예를 들어 thread가 ready_list와 donation_list에 함께 연결될 수 있다. 이때는 리스트마다 서로 다른 노드 필드를 사용해야 한다.

실제 OS 사례 — Linux

Linux 커널은 struct list_head를 사용한다. 이는 PintOS의 list_elem과 거의 같은 구조다.

Linux의 container_of와 PintOS의 list_entry는 같은 원리로 동작한다. list_elem 주소에서 필드 오프셋만큼 빼 바깥 구조체의 시작 주소를 구한다.

PintOS 구현

struct list_elem과 struct list

head와 tail은 **센티널(sentinel)**이다. 실제 데이터를 담지 않고 순회의 시작과 끝을 나타내는 표식으로만 사용된다.

list_entry() 매크로

주의할 점은 PintOS의 list_entry가 &(LIST_ELEM)->next에서 offsetof(STRUCT, MEMBER.next)를 빼는 방식이라는 것이다. Linux의 container_of가 ptr에서 offsetof(type, member)를 빼는 방식과 표현은 조금 다르지만, 얻는 결과는 같다.

struct thread 안의 list_elem 필드

핵심 규칙: elem과 donation_elem은 서로 다른 리스트에 사용해야 한다.

list_elem 필드사용되는 리스트용도
elemready_list, semaphore waiters, sleep_list스케줄링·동기화·sleep
donation_elem다른 thread의 donation_list우선순위 기부 추적

같은 list_elem을 두 리스트에 동시에 넣으면 prev/next 포인터가 덮어써져 두 리스트가 모두 손상된다. 이는 intrusive list에서 가장 흔히 발생하는 버그 중 하나다.
