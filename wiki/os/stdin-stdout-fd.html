표준 입출력 fd

한 줄 요약: fd 0·1은 stdin·stdout에 쓰이는 관례적 번호지만, Linux와 이 문서의 PintOS 구현은 두 번호를 서로 다르게 처리한다.

같은 fd 번호가 다른 구조를 가리키는 이유

프로그램은 보통 fd 0에서 입력을 읽고 fd 1로 결과를 쓴다. UNIX 전통에서 fd 0, 1, 2는 각각 stdin, stdout, stderr에 대응한다. 이 번호 자체에 특별한 기능이 내장된 것은 아니다. 운영체제와 프로그램이 같은 번호를 같은 용도로 사용하기로 한 관례다.

이 관례를 구현하는 방법은 운영체제마다 다르다. Linux에서는 fd 0과 fd 1도 일반 파일 디스크립터와 마찬가지로 실제 struct file 객체를 가리킨다. 반면 여기서 다루는 PintOS 구현은 fd_table[0]과 fd_table[1]을 비워 두고, read()와 write()가 fd 번호를 검사해 입력과 출력을 직접 처리한다. 따라서 “표준 입출력 fd는 일반 파일 fd와 다르다”는 설명은 UNIX나 Linux 전체가 아니라 이 PintOS 구현에 한정된다.

UNIX 관례와 Linux의 표준 입출력

POSIX 환경에서는 프로세스가 시작할 때 fd 0, 1, 2를 각각 stdin, stdout, stderr로 사용하는 것을 전제로 한다. 세 fd는 터미널뿐 아니라 파이프, 소켓 등 여러 I/O 대상에 연결될 수 있다. 셸 리다이렉션(>, <, 2>)도 같은 fd 번호를 다른 파일에 다시 연결하는 방식이다.

Linux에서 열려 있는 fd 0, 1, 2는 task_struct→files→fdt→fd[] 배열의 인덱스 0, 1, 2에 대응한다. 각 항목은 실제 struct file 객체를 가리키며 일반 파일과 같은 VFS 경로를 사용한다. 터미널에서 실행한 프로세스라면 /dev/pts/N 같은 tty 장치 파일에 연결될 수 있지만, 리다이렉션 여부에 따라 대상은 달라진다. dup2(), close(), pipe()로 연결을 바꿀 수도 있다.

Linux에서 fd 0/1이 거치는 경로를 tty 연결 상황으로 나타내면 다음과 같다.

PintOS의 fd 0과 fd 1 처리

이 문서의 PintOS 구현은 표준 입출력을 파일 객체로 표현하지 않는다. thread_init_struct()에서 t->next_fd = 2로 설정해 fd 0과 fd 1을 일반 파일 할당 대상에서 제외한다. fd_table[0]과 fd_table[1]에는 struct file 포인터를 저장하지 않아 두 항목은 NULL 상태로 남는다.

이 구조에서는 syscall이 fd 번호를 직접 확인해야 한다. read()는 fd 0이면 input_getc()로 키보드 입력을 한 바이트씩 읽는다.

이 경로는 VFS나 struct file을 거치지 않는다. 반대로 write()는 fd 1이면 putbuf()로 콘솔에 출력한다.

방향이 맞지 않는 요청은 오류로 처리한다. write(fd=0, ...)는 즉시 -1을 반환하고, read(fd=1, ...)도 즉시 -1을 반환한다. fd 2 이상은 일반 파일 경로로 보내 file_read() 또는 file_write()를 호출한다.

fd 번호용도read() 동작write() 동작
0stdininput_getc() 호출-1 반환
1stdout-1 반환putbuf() 호출
2 이상일반 파일file_read()file_write()

매크로 정의 (include/lib/stdio.h):

  • STDIN_FILENO = 0
  • STDOUT_FILENO = 1

fork, close, stderr의 차이

__do_fork()의 fd 복제 루프는 fd = 2부터 시작한다. fd 0과 fd 1은 파일 객체가 아니므로 복제 대상에서 빠진다. 자식도 next_fd = 2로 초기화되어 같은 관례를 따른다.

close(0)이나 close(1)을 호출하면 process_get_file(fd)가 NULL을 반환한다. 이 PintOS 구현에서는 두 호출이 아무 일도 하지 않은 채 실패한다. Linux에서는 상황이 다르다. close(0) 뒤에 실행한 다음 open()이 비어 있는 fd 0을 재사용할 수 있으므로, 원래 stdin이던 번호가 파일을 가리킬 수 있다.

POSIX 관례에서 fd 2는 stderr지만 이 PintOS 구현은 stderr를 별도로 처리하지 않는다. next_fd = 2에서 일반 파일 번호 할당을 시작하므로 fd 2도 일반 파일에 배정될 수 있다. PintOS의 에러 메시지는 printf()로 출력되어 fd 1인 stdout 경로를 사용한다.

QEMU가 관여하는 지점

QEMU는 PintOS syscall 내부의 fd 번호 분기나 input_getc(), putbuf() 호출을 결정하지 않는다. 이 로직은 guest CPU에서 실행되며, QEMU는 TCG로 번역하거나 KVM으로 직접 실행할 뿐이다. QEMU가 연결에 관여하는 시점은 PintOS가 I/O 장치에 접근할 때다.

stdout에서는 write(1, ...)이 PintOS의 putbuf()와 직렬 포트 출력을 거친 뒤 QEMU의 CharDevice를 통해 호스트 터미널에 도달한다.

QEMU의 CharDevice(Character Device)는 guest 직렬 포트와 호스트 I/O를 잇는 추상 계층이다. backend에 따라 stdio, pty, 네트워크 소켓, 파일 또는 null에 연결할 수 있다.

PintOS를 QEMU에서 실행할 때 기본 옵션 -serial stdio는 guest serial port를 호스트의 stdin/stdout에 매핑한다. 이 설정은 장치 사이의 연결만 제공한다. fd 0을 stdin으로 해석하는 일은 PintOS의 관례와 syscall 구현에 속한다.

Linux TTY와 PintOS 콘솔 비교

Linux에서 fd 0과 fd 1이 tty에 연결된 경우에는 VFS와 TTY 서브시스템을 거친다. 이 PintOS 구현은 그 계층을 두지 않고 putbuf()와 input_getc()를 직접 호출한다.

line disciplineN_TTY: echo, line editing, canonical/raw 모드없음 (raw 입출력만)

시그널 생성Ctrl+C → SIGINT, Ctrl+Z → SIGTSTP미지원 (시그널 없음)
리다이렉션dup2(fd, 0) → fd 0을 새 파일로 교체미지원
