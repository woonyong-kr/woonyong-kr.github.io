EFLAGS (RFLAGS) 레지스터

EFLAGS (RFLAGS) 레지스터

RFLAGS는 산술 결과, 인터럽트 허용 여부, I/O 권한처럼 CPU가 다음 명령을 어떻게 해석해야 하는지 알려 주는 비트 묶음이다.

EFLAGS 레지스터 상태

EFLAGS(64비트에서는 RFLAGS)는 CPU의 상태 플래그, 제어 플래그, 시스템 플래그를 모두 담는 64비트 레지스터다. 산술 연산 결과(CF, ZF, SF), 인터럽트 허용 여부(IF), 현재 I/O 특권 레벨(IOPL) 등을 비트 단위로 기록한다. 인터럽트나 context switch가 일어나면 이 레지스터를 저장해야 CPU가 복귀했을 때 이전 상태를 정확히 재현할 수 있다.

상세 설명

추상 개념 (CPU 하드웨어 규칙)

RFLAGS 레지스터는 64비트이지만 상위 32비트는 예약 영역이다. 하위 32비트가 원래 IA-32의 EFLAGS와 동일하다.

비트이름설명
0CF (Carry Flag)부호 없는 덧셈/뺄셈에서 올림/빌림 발생
1MBS항상 1 (Must Be Set)
2PF (Parity Flag)결과 하위 8비트의 1-bit 개수가 짝수면 1
6ZF (Zero Flag)결과가 0이면 1
7SF (Sign Flag)결과의 최상위 비트 (음수면 1)
8TF (Trap Flag)1이면 single-step 디버깅 모드
9IF (Interrupt Flag)1이면 외부 하드웨어 인터럽트 허용
10DF (Direction Flag)문자열 명령(rep movs 등) 방향 결정
11OF (Overflow Flag)부호 있는 연산에서 overflow 발생
12-13IOPLI/O Privilege Level (0~3)
14NT (Nested Task)TSS 기반 태스크 중첩
18AC (Alignment Check)정렬 검사 활성화 (ring 3에서만 유효)

하드웨어 동작 규칙:

  • syscall 명령은 RFLAGS를 R11에 저장하고, sysret은 R11에서 복원한다.
  • int N / 하드웨어 인터럽트는 RFLAGS를 스택에 push한다. interrupt gate는 IF를 0으로 만들지만 trap gate는 IF를 유지한다.
  • iretq는 스택에서 RFLAGS를 pop하여 복원한다.
  • cli/sti는 IF 비트만 조작하며, 보호 모드에서는 CPL <= IOPL일 때 허용된다. 일반적인 OS 설정은 유저 CPL=3, IOPL=0이므로 결과적으로 커널만 실행할 수 있다.

실제 OS (Linux)

Linux 커널은 pt_regs 구조체에 RFLAGS를 flags 필드로 저장한다. 유저 프로세스로 복귀할 때 iretq가 스택에서 RFLAGS를 복원하므로, 유저 프로세스는 자신이 중단된 시점의 CF/ZF/SF 등을 그대로 되찾는다. 커널은 유저의 IOPL을 0으로 유지하여 I/O 포트 접근을 차단하고, IF는 1로 설정하여 인터럽트를 받을 수 있게 한다.

PintOS 구현

PintOS는 include/threads/flags.h에 주요 EFLAGS 비트 매크로를 정의한다:

현재 packed struct intr_frame의 eflags 필드는 offset 0xA8(168)에 있다. CPU는 인터럽트·예외 진입 때 RIP, CS, RFLAGS를 저장하고, CPL 또는 stack이 전환될 때만 이전 SS:RSP도 저장한다. stub은 software가 쓰는 frame 모양을 일정하게 만들기 위해 나머지 slot을 보완할 수 있다.

유저 프로세스를 처음 시작할 때(process_exec → do_iret) EFLAGS를 FLAG_IF | FLAG_MBS(= 0x202)로 설정한다. 이는 인터럽트 허용 + MBS 고정 비트를 의미한다.

intr_get_level()은 read_eflags()로 현재 RFLAGS를 읽어 IF 비트를 확인한다. intr_enable()은 sti, intr_disable()은 cli로 IF를 조작한다.

QEMU 에뮬레이션

QEMU TCG는 CPUX86State.eflags 필드에 guest RFLAGS를 보관한다. 산술 명령어 실행 시 lazy evaluation으로 CF/ZF/SF 등을 계산한다 — 실제 플래그 값은 cc_src, cc_dst, cc_op 세 필드에서 필요할 때 계산하여 성능을 최적화한다. GDB stub의 info registers 명령은 이 lazy 상태를 force-compute하여 완전한 RFLAGS 값을 보여준다.

cli/sti 명령어를 TCG가 번역할 때, QEMU는 env->eflags의 IF 비트를 직접 조작한다. QEMU의 가상 인터럽트 컨트롤러(i8259)는 이 IF 비트를 확인하여 guest에 인터럽트를 주입할지 결정한다.

syscall 진입 시 RFLAGS 마스킹

syscall 명령어는 MSR_SYSCALL_MASK (0xC0000084)에 설정된 비트를 RFLAGS에서 클리어한다. PintOS는 syscall_init()에서 이 마스크를 설정한다:

마스크 값 = 0x200 | 0x100 | 0x400 | 0x3000 | 0x40000 | 0x4000 = 0x47700.

비트마스크 이유
IF (bit 9)커널 스택 전환 전 인터럽트 차단 — 유저 RSP가 아직 커널 스택으로 교체되지 않은 상태에서 인터럽트가 들어오면 유저 스택에 커널 데이터가 저장되어 보안 위협
TF (bit 8)single-step trap 방지 — syscall 진입 직후 db 발생하면 핸들러가 불완전한 상태에서 실행됨
DF (bit 10)문자열 명령어 방향 정규화 — 커널 코드는 DF=0(forward) 가정
IOPL (bits 12-13)I/O 특권 레벨 0으로 리셋
AC (bit 18)alignment check 비활성화
NT (bit 14)nested task 플래그 클리어 — iretq가 TSS chain을 따라가는 것 방지

Linux도 동일한 마스크 정책을 사용하지만, 추가로 X86_EFLAGS_FIXED 비트를 설정하고 SMAP(Supervisor Mode Access Prevention)이 활성화된 경우 AC 비트 처리가 달라진다.

TF (Trap Flag)와 디버깅

TF=1이면 CPU는 매 명령어 실행 후 db(Debug Exception, vector 1)를 발생시킨다. GDB의 stepi 명령이 이 메커니즘을 사용한다.

디버깅 시 주의: QEMU의 GDB stub은 guest의 TF가 아니라 자체 single-step 메커니즘을 사용한다. stepi로 PintOS를 디버깅할 때 guest RFLAGS의 TF는 변하지 않는다 — QEMU가 TCG 레벨에서 한 Translation Block만 실행하고 멈추는 방식이다.

IOPL (I/O Privilege Level) 심화

IOPL(bits 12-13)은 IN/OUT/INS/OUTS 명령어와 cli/sti 실행 가능 여부를 결정한다. CPL ≤ IOPL이면 실행 가능하다.

CPLIOPL=0IOPL=3
0 (커널)IN/OUT 허용, cli/sti 허용IN/OUT 허용, cli/sti 허용
3 (유저)IN/OUT 금지 (#GP), cli/sti 금지 (#GP)IN/OUT 허용, cli/sti 허용

PintOS는 유저 프로세스의 IOPL을 0으로 설정(FLAG_IF | FLAG_MBS = 0x202에 IOPL 비트 없음)하여, 유저가 cli/sti/IN/OUT을 실행하면 gp(General Protection Fault)가 발생한다. Linux도 동일하게 유저의 IOPL을 0으로 유지하지만, iopl() syscall로 특권 프로세스가 IOPL을 올릴 수 있다.

EFLAGS 레지스터 값 추적

유저 프로세스 초기 EFLAGS 값:

비트:  18  14  13 12  10  9   8   1
       AC  NT  IOPL   DF  IF  TF  MBS
값:    0   0   0  0   0   1   0   1    = 0x0000000000000202

FLAG_IF = 0x200 = 512, FLAG_MBS = 0x02 = 2 → 합계 0x202 = 514.

interrupt gate로 진입하면 CPU가 IF를 클리어하므로 이 예시의 EFLAGS는 0x02(MBS만)가 된다. trap gate는 IF를 유지하며, syscall 경로는 MSR_SYSCALL_MASK가 지정한 bit를 별도로 지운다. IF가 0인 경로에서 sti를 실행하면 다시 0x202가 된다.

산술 플래그 (CF/ZF/SF/OF) 실제 사용 예

조건 분기 명령어가 RFLAGS를 읽어 분기를 결정한다. 이것이 RFLAGS가 context switch 시 반드시 저장/복원되어야 하는 이유다.

QEMU TCG의 lazy evaluation이 중요한 이유: 매 산술 명령마다 6개 플래그를 모두 계산하면 성능이 나쁘다. 대신 cc_src(피연산자), cc_dst(결과), cc_op(연산 종류)만 기록하고, je 같은 조건 분기에서 필요한 플래그만 cc_op에 따라 계산한다.

%% QEMU TCG 산술 플래그 지연 계산
flowchart LR
  cmp["cmp rdi, rsi<br/>cc_op = CC_OP_SUBB"]
  lazy["cc_dst = rdi - rsi<br/>cc_src = rsi"]
  branch["je<br/>ZF 필요"]
  compute["compute_c_eflags()<br/>ZF = (cc_dst == 0)"]
  jump["점프 실행"]
  next["다음 명령어"]

  lazy --> branch
  branch --> compute

  compute -->|ZF=0| next

핵심 차이: syscall은 RFLAGS를 R11 레지스터에 보존하고, 인터럽트는 스택에 보존한다. 현재 로컬 PintOS의 정상 syscall 복귀는 sysretq가 R11에서 복원한다. do_iret()을 통과하는 초기 유저 진입·인터럽트/예외·스레드 상태 복원은 iretq가 frame의 RFLAGS를 복원한다.
