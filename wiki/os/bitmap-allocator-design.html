Bitmap Allocator

Bitmap Allocator

범위: 이 문서는 bitmap allocator의 일반 원리와 선택 기준을 설명하고, 제시된 PintOS의 palloc·swap 코드 구조를 구현 사례로 다룬다. 자료형 크기와 코드 위치, 메모리·swap 용량별 계산, 원자성, 검색·명령 비용 및 성능 평가는 해당 코드·빌드 환경·버전과 실제 실행·측정 기록을 확인해야 하는 구현 종속 판단이다.

한 줄 요약: 각 비트가 물리 페이지나 swap slot의 사용 여부를 나타내는 palloc·swap 공통 비트맵 할당자.

Bitmap Allocator 상태

PintOS의 lib/kernel/bitmap.c는 고정 크기 비트 배열을 관리하는 범용 자료구조다. 각 비트가 하나의 자원(물리 페이지 또는 swap slot)의 사용 여부를 표현한다. palloc(물리 페이지 할당)과 swap(디스크 슬롯 할당) 양쪽에서 동일한 bitmap API를 사용하여 free/used 상태를 추적한다. 비트 단위 조작에 x86 lock 접두사를 사용하여 단일 프로세서에서의 원자적 수정을 보장한다.

상세 설명

추상 개념 (Bitmap Allocator 설계)

Bitmap allocator는 가장 단순한 자원 할당기 중 하나다. N개의 자원에 대해 N비트 배열을 유지하고, 비트 0 = free, 비트 1 = used로 관리한다. 할당은 첫 번째 0 비트를 찾아 1로 설정하고, 해제는 해당 비트를 0으로 리셋한다.

장점:

  • O(1) 공간 효율: 자원당 1비트만 사용
  • 단순한 구현: 비트 연산만으로 동작
  • 연속 할당 가능: 연속된 N개의 0 비트를 스캔할 수 있음

단점:

  • O(N) 검색: 최악의 경우 전체 배열을 순회
  • 단편화 비가시: 외부 단편화를 직접 보여주지 않음

실제 OS (Linux)

Linux는 물리 페이지 관리에 bitmap 대신 buddy allocator를 사용한다:

  • buddy는 2^k 크기 블록을 관리하며, 분할/병합으로 외부 단편화를 줄인다
  • 각 order(0~10)별 free list를 유지하여 검색이 O(1)에 가까움
  • swap은 swap_map[] 배열(바이트 단위)로 각 slot의 참조 카운트를 관리

PintOS가 buddy 대신 bitmap을 쓰는 이유: 교육용 OS이므로 복잡한 buddy 분할/병합보다 비트 배열의 단순성을 택함. 연속 다중 페이지 할당(palloc_get_multiple)도 지원하지만, 실제로는 대부분 1페이지 단위로 할당한다.

PintOS 구현

struct bitmap 내부 구조

비트 N개를 저장하려면 DIV_ROUND_UP(N, 64)개의 unsigned long 원소가 필요하다.

비트 인덱싱

예: bit 137을 찾으려면:

  • elem_idx(137) = 137 / 64 = 2 → bits[2]
  • bit_mask(137) = 1 << (137 % 64) = 1 << 9 → bits[2]의 bit 9

원자적 비트 조작

PintOS는 x86 lock 접두사로 비트 조작의 원자성을 보장한다:

lock 접두사는 해당 메모리 위치에 대한 read-modify-write를 원자적으로 수행한다. 인터럽트 핸들러가 같은 비트맵을 접근할 수 있으므로, 단일 프로세서에서도 이 원자성이 필요하다.

핵심 API: bitmap_scan_and_flip

bitmap_scan(): start 위치부터 연속 cnt개의 비트가 모두 value인 구간을 찾는다. bitmap_set_multiple(): 찾은 구간의 비트를 반전시킨다.

이 함수가 palloc과 swap의 할당 핵심이다:

  • palloc: bitmap_scan_and_flip(pool->used_map, 0, page_cnt, false) → 연속 free 페이지 찾기
  • swap: bitmap_scan_and_flip(disk_bitmap, 0, 1, false) → 1개 free slot 찾기

두 가지 생성 방식

palloc이 bitmap_create_in_buf()를 사용하는 이유: palloc은 시스템 부팅 초기에 초기화되며, 이 시점에서는 malloc()이 아직 사용 불가하다 (malloc 자체가 palloc 위에 구현됨). 따라서 palloc은 물리 메모리의 일부를 직접 bitmap 저장 공간으로 지정한다.

Bitmap Allocator 값 추적

palloc bitmap 크기 계산

PintOS가 64 MB 물리 메모리로 부팅할 때:

항목계산결과
총 물리 페이지64 MB / 4 KB16,384 pages
kernel pool~8,192 pages8,192 bits
user pool~8,192 pages8,192 bits
kernel bitmap 원소8,192 / 64128 unsigned long
kernel bitmap 크기128 × 8 bytes1,024 bytes (= 0.25 page)
user bitmap 크기동일1,024 bytes
두 bitmap 합계2,048 bytes

bitmap 하나가 1 KB — 8,192개 페이지(32 MB)를 1 KB로 관리한다. 자원당 1비트의 공간 효율.

swap bitmap 크기 계산

PintOS swap 디스크가 4 MB일 때:

항목계산결과
swap 디스크 섹터 수4 MB / 512 B8,192 sectors
swap slot 수8,192 / 8 (SWAP_SLOT)1,024 slots
bitmap 원소 수1,024 / 6416 unsigned long
bitmap 크기16 × 8 bytes128 bytes
ref_count 배열1,024 × 8 bytes8,192 bytes

swap bitmap은 128 bytes로 1,024개 슬롯을 관리한다.

검색 성능

bitmap_scan()은 bit 단위로 순회한다 (bitmap_contains 내부):

시나리오검색 범위비교 횟수
palloc 1 page, pool 여유첫 0 비트까지1~수십
palloc 1 page, pool 거의 가득전체 스캔~8,192
swap 1 slot, disk 여유첫 0 비트까지1~수십
palloc 연속 4 pages연속 4개 0 비트~8,192 × 4 (최악)

최악의 경우 O(N)이지만, PintOS 규모(수천~만 개)에서는 실용적으로 빠르다. Linux의 buddy allocator가 O(1)에 가까운 것과 대비된다.

원자적 비트 조작의 비용

명령어사이클 (x86-64, 대략)
orq (non-locked)~1 cycle
lock orq2030 cycles (bus lock)
lock andq2030 cycles

lock 접두사는 약 20배 느리지만, 비트맵 조작은 할당/해제 시에만 발생하므로 전체 성능에 큰 영향이 없다.

last_mask: 마지막 원소의 유효 비트

예: bit_cnt = 100일 때:

  • 원소 수: DIV_ROUND_UP(100, 64) = 2
  • bits[0]: 64비트 모두 유효
  • bits[1]: 하위 36비트만 유효 (100 - 64 = 36)
  • last_mask = (1 << 36) - 1 = 0x0000000FFFFFFFFF
bits[1]:
  bit 64 ... 99  100 ... 127
  [유효 36비트]  [무시 28비트]
                 ← last_mask로 마스킹

bitmap_set_all(b, false) 같은 함수에서 마지막 원소의 무효 비트를 건드리지 않도록 last_mask를 사용한다.
