디렉터리와 작업 디렉터리

디렉터리와 작업 디렉터리

한 줄 요약: 디렉터리는 (이름, inode 섹터 번호) 쌍을 저장하는 특수한 파일이며, 작업 디렉터리(cwd)는 프로세스가 상대 경로를 해석할 때 기준이 되는 디렉터리다. PintOS 기본 구현은 루트 디렉터리 하나만 존재하는 플랫 구조이고, Project 4에서 하위 디렉터리를 구현한다.

디렉터리와 작업 디렉터리 구분

inode는 파일의 크기와 데이터 위치를 관리하지만, 이름은 모른다. 사용자가 open("hello.txt")를 호출하면 “hello.txt”라는 이름을 inode 섹터 번호로 변환하는 장치가 필요하다. 이 장치가 디렉터리다.

디렉터리가 없으면 파일을 섹터 번호로만 접근해야 한다. 디렉터리가 하나뿐이면 모든 파일이 같은 이름 공간에 있어서 이름 충돌이 생긴다. 하위 디렉터리가 있어야 <local-home>/docs/report.txt처럼 계층적으로 파일을 조직할 수 있다.

작업 디렉터리(current working directory)는 상대 경로의 기준이다. open("data.csv")가 <local-home>/data.csv인지 /tmp/data.csv인지를 결정하는 것이 cwd다.

디렉터리와 작업 디렉터리 차이

비유: 전화번호부

디렉터리는 전화번호부와 같다. 전화번호부에는 (이름, 전화번호) 쌍이 나열되어 있다. “김철수”를 찾으면 “010-1234-5678”이 나오듯, 디렉터리에서 “hello.txt”를 찾으면 inode 섹터 번호 42가 나온다. 전화번호부 자체도 전화번호를 가질 수 있듯이, 디렉터리 자체도 inode를 갖는 파일이다.

디렉터리의 본질: 특수한 파일

디렉터리는 일반 파일과 같은 방식으로 저장된다. inode가 있고, 데이터 섹터가 있다. 차이는 데이터의 내용이다. 일반 파일의 데이터는 임의의 바이트이고, 디렉터리의 데이터는 dir_entry 배열이다.

%% 디렉터리 inode 데이터 영역의 dir_entry 배열
flowchart TD
  entries["in_use &#124; name &#124; sector &#124; slot<br/>T &#124; &quot;a.txt&quot; &#124; 5 &#124; entry 0<br/>T &#124; &quot;b.txt&quot; &#124; 8 &#124; entry 1<br/>F &#124; &quot;&quot; &#124; 0 &#124; entry 2"]

각 dir_entry는 고정 크기이며, in_use 플래그로 사용 중/비어 있음을 구분한다. 파일을 삭제하면 해당 엔트리의 in_use를 false로 바꿀 뿐, 엔트리 자체를 지우지는 않는다. 새 파일을 추가할 때 in_use == false인 빈 슬롯을 재활용한다.

struct dir과 struct dir_entry

PintOS에서 디렉터리는 두 구조체로 표현된다.

  • struct dir: 열린 디렉터리 핸들. struct file과 비슷하게 inode 포인터와 현재 위치(pos)를 갖는다.
  • struct dir_entry: 디렉터리 안의 항목 하나. 파일 이름, inode 섹터 번호, 사용 여부를 담는다.

이름 검색 (lookup)

dir_lookup("hello.txt")은 디렉터리의 데이터 영역을 처음부터 끝까지 순차 탐색한다. dir_entry를 하나씩 읽어서 in_use == true이고 name이 일치하는 항목을 찾는다.

dir_lookup("b.txt")
-> entry 0: in_use=T, name="a.txt"  -> 불일치
-> entry 1: in_use=T, name="b.txt"  -> 일치! inode_sector=8 반환

검색 비용은 O(N)이다. 실제 OS(ext4)는 해시 트리(htree)로 O(1)에 가깝게 검색한다.

파일 생성과 삭제

생성 (dir_add):

  1. 이름이 유효한지 확인 (빈 문자열 금지, NAME_MAX=14 초과 금지).
  2. 같은 이름이 이미 있는지 lookup()으로 확인.
  3. in_use == false인 빈 슬롯을 찾는다. 없으면 디렉터리 끝에 새 엔트리를 추가한다.
  4. 엔트리에 이름과 inode 섹터 번호를 기록하고 in_use = true로 설정한다.

삭제 (dir_remove):

  1. lookup()으로 엔트리를 찾는다.
  2. 해당 엔트리의 in_use를 false로 기록한다.
  3. inode_remove()로 inode에 삭제 표시를 남긴다. 실제 디스크 블록 해제는 마지막 오프너가 inode_close()를 호출할 때 일어난다.

루트 디렉터리와 플랫 구조

PintOS 기본 구현에서 디렉터리는 루트 하나뿐이다. filesys_open("hello.txt")는 항상 루트 디렉터리에서 이름을 찾는다.

하위 디렉터리가 없으므로 경로 구분자(/)가 의미 없고, 모든 파일이 같은 이름 공간에 존재한다.

하위 디렉터리와 작업 디렉터리 (Project 4)

하위 디렉터리를 구현하려면 다음을 추가해야 한다.

1. 디렉터리와 파일의 구분: inode에 “이것은 디렉터리인가, 일반 파일인가”를 표시하는 플래그가 필요하다.

2. .과 .. 엔트리: 모든 디렉터리는 자기 자신(.)과 부모(..)를 가리키는 특수 엔트리를 포함해야 한다.

3. 경로 파싱: "/a/b/c.txt"를 ["a", "b", "c.txt"]로 분리하고, 루트 → a → b 순서로 디렉터리를 탐색해 최종 파일의 inode를 찾는다.

4. 작업 디렉터리 (cwd): 각 프로세스(또는 스레드)가 현재 디렉터리를 가리키는 포인터를 갖는다. 절대 경로(/로 시작)는 루트에서, 상대 경로는 cwd에서 탐색을 시작한다.

프로세스 A: cwd = /work/example
  open("data.csv") -> /work/example 에서 "data.csv" 검색

프로세스 B: cwd = /tmp
  open("data.csv") -> /tmp 에서 "data.csv" 검색

chdir() 시스템 콜이 cwd를 변경한다.

디렉터리와 작업 디렉터리 코드

struct dir과 struct dir_entry

dir_entry 하나의 크기는 4 + 15 + 1 = 20바이트다. 한 섹터(512B)에는 512 / 20 = 25개의 엔트리가 들어간다. dir_create(sector, 16)은 16개 엔트리를 담을 공간(320B, 1섹터)을 만든다.

lookup() — 선형 탐색

디렉터리 inode의 데이터를 dir_entry 크기씩 읽으면서 이름을 비교한다. inode_read_at()이 sizeof e보다 적게 반환하면 데이터 끝에 도달한 것이다.

dir_add() — 빈 슬롯 재활용

빈 슬롯이 없으면 ofs가 디렉터리 데이터의 끝을 가리키게 된다. 이 경우 확장 가능 파일이 구현되어 있어야 디렉터리에 새 엔트리를 추가할 수 있다. 기본 PintOS에서는 dir_create() 시 지정한 엔트리 수를 넘기면 추가가 실패한다.

dir_remove() — in_use 플래그 끄기

엔트리를 물리적으로 지우지 않고 in_use = false로 바꾼다. inode의 실제 삭제는 inode_close()에서 open_cnt가 0이 되고 removed == true일 때 수행된다. 이 설계 덕분에 다른 프로세스가 파일을 열고 있는 동안에도 이름을 지울 수 있다(UNIX unlink 의미론).

dir_readdir() — 디렉터리 순회

dir_readdir()은 struct dir의 pos를 이용해 디렉터리를 순회한다. in_use == false인 삭제된 엔트리는 건너뛰고, 사용 중인 다음 항목의 이름을 반환한다. ls 같은 명령이 이 함수를 반복 호출하여 디렉터리 내용을 열거한다. 반환 순서는 엔트리가 디스크에 저장된 물리적 순서이며, 이름 순서가 아니다.

정리

디렉터리는 (이름, inode 섹터 번호) 쌍을 저장하는 특수한 파일이다. PintOS에서 dir_entry 배열을 선형 탐색하여 이름을 inode로 변환한다. 기본 구현은 루트 디렉터리 하나만 있는 플랫 구조이지만, Project 4에서는 하위 디렉터리, ./.. 엔트리, 경로 파싱, 작업 디렉터리(cwd)를 추가하여 계층적 파일 시스템으로 확장한다. 디렉터리 확장에는 확장 가능 파일 구현이 선행되어야 한다.
