비트맵 스왑 테이블 (Bitmap Swap Table)

비트맵 스왑 테이블 (Bitmap Swap Table)

확인 범위: 이 문서는 비트맵 기반 swap slot 할당·참조 관리의 일반 원리와 Linux·Windows·PintOS의 선택 기준을 설명하고, 제시된 PintOS 코드 구조를 구체적 구현 사례로 다룬다. 코드 좌표, 자료형·버전 의존 수치, QEMU·GDB 실행 경로와 성능 복잡도 비교는 실제 소스 및 실행·측정 기록으로 별도 검증해야 한다.

한 줄 요약: swap disk slot(1 slot = 4 KB = 8 sectors)을 bitmap으로 관리해 각 bit가 1이면 사용·0이면 빈 slot이고 첫 0-bit를 flip해 alloc하며, PintOS는 COW fork를 위해 swap_ref_count[]까지 둬 같은 slot을 여러 프로세스가 ref/unref(0이면 bit clear)로 공유한다 — Linux swap_map[]의 per-cluster O(1) 검색과 달리 전역 swap_lock+선형 bitmap_scan O(n)이다.

비트맵 스왑 테이블 구조

Swap disk의 slot 할당/해제를 O(1)~O(n) bitmap으로 관리한다. 각 bit가 하나의 swap slot(= 4 KB = 8 sectors)을 대표하며, 1이면 사용 중, 0이면 빈 slot이다. PintOS에서는 COW fork를 위한 reference counting까지 추가하여, 같은 swap slot을 여러 프로세스가 공유할 수 있게 한다.

상세 설명

추상 개념 (OS 수준 설계)

Page eviction 시 anonymous page의 내용을 보존하려면 별도 저장소가 필요하다. Swap disk를 고정 크기 slot으로 분할하고, 어떤 slot이 비어 있는지를 bitmap으로 추적한다. Bitmap은 가장 단순한 공간 할당 자료구조로, 각 bit의 인덱스가 곧 slot 번호다.

핵심 연산 세 가지:

  • alloc: bitmap에서 첫 번째 0-bit를 찾아 1로 flip → slot 번호 반환
  • ref: reference count 증가 (COW fork 등)
  • unref: reference count 감소 → 0이 되면 bit를 0으로 clear

실제 OS (Linux/Windows)

Linux는 swap area를 swap_info_struct로 관리하며, 내부적으로 swap_map[] 배열에 reference count를 저장한다. 빈 slot 검색은 cluster 단위 캐시를 사용해 O(1) 수준으로 최적화한다. Windows는 pagefile.sys를 유사한 bitmap + allocation table로 관리한다.

PintOS 구현

PintOS는 vm/anon.c에서 bitmap과 reference count 배열을 별도로 둔다.

초기화 — vm_anon_init():

할당 — swap_slot_alloc():

bitmap_scan_and_flip(bm, start, cnt, value)는 연속 cnt개의 value bit를 찾아 반전시킨다. 여기서는 false(0)인 bit 1개를 찾아 true(1)로 바꾼다.

참조 증가 — swap_slot_ref():

COW fork 시 자식이 부모의 swapped page를 공유할 때 호출된다.

참조 감소 — swap_slot_unref():

reference count가 0이 되어야 비로소 bitmap bit를 clear한다.

비트맵 스왑 테이블 값 추적

항목값
swap slot 크기4,096 bytes (= 1 page)
slot당 sector 수8 (= 4096 / 512)
QEMU 기본 swap disk4 MB = 8,192 sectors
총 swap slot 수8,192 / 8 = 1,024 slots
bitmap 크기1,024 bits = 128 bytes
ref_count 배열1,024 × sizeof(size_t) = 8,192 bytes (x86-64)

swap slot 번호 idx에 대응하는 disk sector 범위: [idx × 8, idx × 8 + 7]

예: slot 5의 내용을 읽을 때 → disk_read(swap_disk, 40, buf) ~ disk_read(swap_disk, 47, buf + 3584)

QEMU 에뮬레이션

QEMU는 swap bitmap 자체를 인식하지 않는다 — swap 관리는 순수 guest 소프트웨어다. QEMU가 관여하는 유일한 지점은 disk_read()/disk_write() 호출이 IDE controller model을 거쳐 host 파일 I/O로 변환되는 경로다.

swap I/O 경로: anon_swap_out() → disk_write(swap_disk, sector, buf) → PintOS ide_write() → QEMU ide_transfer_start() → blk_pwrite() → host pwrite() on .swap 파일.

bitmap 연산(bitmap_scan_and_flip, bitmap_set 등)은 guest memory 내 비트 조작이므로, QEMU 입장에서는 일반 메모리 접근과 구분이 안 된다. GDB로 guest memory를 덤프해서 bitmap 상태를 직접 관찰하는 것이 디버깅의 핵심이다.

bitmap 내부 구조 상세

struct bitmap은 elem_type (= unsigned long, 8 bytes on x86-64) 배열로 비트를 저장한다:

flowchart TD

  calc["1024 slots<br/>DIV_ROUND_UP(1024, 64) = 16 elements<br/>16 * 8 = 128 bytes"]
  bits0["bits[0]<br/>slot 0~63<br/>bit 0 = slot 0"]
  bits1["bits[1]<br/>slot 64~127"]
  dots["..."]
  bits15["bits[15]<br/>slot 960~1023"]
  access["slot N 접근<br/>elem_idx = N / 64<br/>bit_mask = 1UL &lt;&lt; (N % 64)<br/>bits[elem_idx] &amp; bit_mask<br/>사용 중이면 nonzero"]
  elem --> calc
  calc --> bits0
  bits0 --> bits1
  bits1 --> dots
  dots --> bits15
  bits15 --> access

bitmap_scan()은 start부터 순차 탐색하므로 최악 O(n)이다. PintOS swap slot 수(1024)에서는 무시할 수 있지만, slot이 수만 개면 성능 이슈가 된다. Linux가 cluster 캐시를 쓰는 이유다.
