유저 포인터 검증 (User Pointer Validation) Trace

유저 포인터 검증 (User Pointer Validation) Trace

한 줄 요약: syscall로 받은 유저 포인터는 역참조 전에 무조건 검증해야 하며(NULL·overflow·KERN_BASE 이상 거부), PintOS는 Linux의 exception table 방식 대신 validate_user_buffer()로 page 단위 선검증해 통과 못 하면 exit(-1)한다 — 안 하면 커널 크래시나 커널 메모리를 유저에게 노출하는 구멍이 된다.

유저 포인터 검증 구조

유저 프로그램이 syscall로 커널에 포인터를 넘기면, 커널은 그 포인터를 무조건 검증한 뒤에만 역참조해야 한다. 검증 없이 접근하면 커널 자체가 크래시하거나, 유저가 커널 메모리를 읽는 보안 구멍이 된다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

x86-64 CPU에서 메모리 접근은 항상 현재 CR3이 가리키는 페이지 테이블을 통한 가상 주소 변환을 거친다. 변환 실패 시 CPU는 **#PF(Page Fault, exception 14)**를 발생시키고, fault 주소를 CR2에 기록한다.

커널 모드(CPL 0)에서도 페이지 테이블을 거치는 것은 동일하다. 다만 PTE의 User/Supervisor 비트가 0인 페이지는 커널만 접근 가능하다. 핵심 위험은: 유저가 넘긴 주소가 커널 영역(≥ KERN_BASE)이면, 커널 코드가 그 주소를 역참조할 때 커널 자신의 데이터를 유저에게 노출하게 된다는 것이다.

실제 OS (Linux/Windows)

Linux 커널은 유저 메모리를 직접 역참조하지 않는다. 대신 copy_from_user() / copy_to_user() 함수를 사용한다. 이 함수들은 내부적으로 접근을 시도하되, fault가 발생하면 exception table을 통해 안전하게 -EFAULT를 반환한다. 커널이 죽지 않는다.

Windows 커널도 유사하게 ProbeForRead() / ProbeForWrite()로 유저 버퍼를 사전 검증하고, SEH(Structured Exception Handling)로 fault를 잡는다.

두 OS 모두 **“커널이 유저 포인터를 직접 믿지 않는다”**는 원칙은 동일하다.

PintOS 구현

PintOS는 Linux의 exception table 방식 대신, 선검증(pre-validation) 방식을 사용한다. syscall handler가 유저 포인터를 사용하기 전에 명시적으로 검증 함수를 호출한다.

검증 단계별 코드 좌표

1단계: syscall 인자 추출

syscall handler가 struct intr_frame에서 레지스터 값을 꺼낸다. 예를 들어 write(fd, buffer, size)에서:

  • f->R.rdi = fd
  • f->R.rsi = buffer (유저 가상 주소)
  • f->R.rdx = size

이 시점에서 buffer는 유저가 임의로 설정한 값이다. 어떤 값이든 들어올 수 있다.

2단계: validate_user_buffer() — 구간 전체 검증

버퍼가 페이지 경계를 넘으면 여러 페이지를 검증해야 한다. 예를 들어 buffer=0x8048ff0, size=0x30이면 페이지 0x8048000과 0x8049000 두 개를 검증한다.

3단계: try_claim_user_addr() — 단일 주소 검증

4단계: user_page_accessible() — PTE 레벨 확인

이 함수는 pml4e_walk()로 4단계 페이지 테이블 워크를 수행해 PTE를 찾고, Present 비트와 Writable 비트를 확인한다.

QEMU 에뮬레이션

QEMU는 유저 포인터 검증 정책을 제공하지 않는다. 그건 guest OS(PintOS)의 책임이다.

하지만 검증을 빼먹고 커널에서 잘못된 주소를 접근하면, QEMU가 pf를 에뮬레이션한다:

즉 PintOS가 검증을 빼먹으면 → 커널에서 유저 주소 역참조 → QEMU MMU 변환 실패 → guest에 pf 전달 → PintOS page_fault() handler가 커널 모드 fault로 판단 → PANIC("Kernel bug")으로 전체 정지.

순서도 / 개념도

검증 없이 접근했을 때의 위험 시나리오

  • 유저 프로그램:
  • write(1, (void *)0x8004000000, 100);
  • ↑ 커널 주소!
  • 만약 검증 없이 커널이 이 주소를 읽으면:
  • 커널 코드 (CPL 0)
  • memcpy(kbuf, 0x8004000000, 100)
  • ↓
  • 커널 자신의 메모리를 읽어서
  • 유저에게 출력 → 정보 유출!
  • PintOS 검증이 이를 차단:
  • is_user_vaddr(0x8004000000) → false → exit(-1)
