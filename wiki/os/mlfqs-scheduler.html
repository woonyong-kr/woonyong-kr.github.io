MLFQS 스케줄러

MLFQS 스케줄러

확인 범위: 이 문서는 MLFQS의 일반 원리와 선택 기준을 PintOS의 공식·갱신 주기·고정소수점 구현 예시를 중심으로 설명하고 Linux와 Windows의 접근을 개념적으로 비교한다. 제시된 코드와 계산은 구현 지침 및 예시이며, 특정 PintOS 버전의 실제 코드 동작이나 실행 기록·성능 측정을 통해 검증한 결과는 아니다.

한 줄 요약: 고정 우선순위 스케줄러의 문제를 푸는 다단계 피드백 큐 스케줄러 MLFQS.

MLFQS 스케줄러 필요성

고정 우선순위 스케줄러에는 두 가지 문제가 있다.

  1. 기아(starvation): 우선순위가 낮은 스레드가 영원히 실행되지 못할 수 있다.
  2. 사용자 개입: 프로그래머가 스레드마다 직접 우선순위를 정해야 하므로, 시스템 전체의 공정성을 보장하기 어렵다.

MLFQS(Multi-Level Feedback Queue Scheduler)는 스레드의 최근 행동을 관찰하여 우선순위를 자동으로 조절한다. CPU를 많이 쓴 스레드는 우선순위가 내려가고, I/O를 기다리며 CPU를 양보한 스레드는 우선순위가 올라간다. 프로그래머가 우선순위를 직접 지정하지 않아도 시스템이 알아서 공정하게 배분한다.

MLFQS 스케줄러 구조

PintOS의 MLFQS는 4.4BSD 스케줄러 알고리즘을 따른다. 세 가지 값이 핵심이다.

1. nice 값

스레드가 다른 스레드에게 CPU를 얼마나 양보할 의향이 있는지를 나타낸다.

  • 범위: -20 ~ +20
  • nice = 0: 기본값, 양보하지도 뺏지도 않음
  • nice > 0: 양보 — 우선순위가 낮아짐
  • nice < 0: 공격적 — 우선순위가 높아짐

2. recent_cpu

스레드가 최근에 CPU를 얼마나 사용했는지를 추적하는 값이다.

  • 매 타이머 인터럽트(tick)마다, 현재 실행 중인 스레드의 recent_cpu가 1 증가한다.
  • 매 1초(100 ticks)마다, 모든 스레드의 recent_cpu가 감쇄(decay)된다.

감쇄 공식:

recent_cpu = (2 * load_avg) / (2 * load_avg + 1) * recent_cpu + nice

이 공식의 핵심은 (2 * load_avg) / (2 * load_avg + 1) 부분이다. 이 값은 항상 1보다 작으므로, 시간이 지나면 과거의 CPU 사용량이 점점 줄어든다. 시스템 부하가 높을수록(load_avg가 클수록) 감쇄가 느려져서 과거 사용량이 더 오래 반영된다.

3. load_avg

시스템 전체의 부하를 나타내는 값이다. 지수 가중 이동 평균(exponentially weighted moving average)으로 계산한다.

load_avg = (59/60) * load_avg + (1/60) * ready_threads

ready_threads는 실행 중이거나 ready 상태인 스레드 수다(idle 스레드 제외). 매 1초마다 갱신된다.

우선순위 재계산

priority = PRI_MAX - (recent_cpu / 4) - (nice * 2)
  • PRI_MAX는 63이다.
  • CPU를 많이 쓸수록(recent_cpu 증가) 우선순위가 내려간다.
  • nice가 클수록 우선순위가 내려간다.
  • 결과는 PRI_MIN(0) ~ PRI_MAX(63) 범위로 잘린다.
  • 매 4 ticks마다 모든 스레드의 우선순위를 재계산한다.

고정소수점 연산

커널에는 부동소수점 하드웨어를 쓸 수 없다(FPU 컨텍스트 저장 비용이 크고, 인터럽트 핸들러에서 사용하면 안 된다). 따라서 recent_cpu와 load_avg는 17.14 고정소수점 형식으로 구현한다.

정수 부분: 상위 17비트 (부호 포함)
소수 부분: 하위 14비트
변환 계수 f = 2^14 = 16384

주요 연산:

연산구현
정수 n → 고정소수점n * f
고정소수점 → 정수 (버림)x / f
고정소수점 → 정수 (반올림)(x + f/2) / f (양수), (x - f/2) / f (음수)
고정소수점 + 고정소수점x + y
고정소수점 * 고정소수점((int64_t) x) * y / f
고정소수점 / 고정소수점((int64_t) x) * f / y
고정소수점 + 정수x + n * f
고정소수점 * 정수x * n

int64_t로 중간값을 확장하는 이유는 32비트 곱셈에서 오버플로우를 방지하기 위해서다.

실제 운영체제

Linux의 CFS(Completely Fair Scheduler)는 MLFQS와 목표가 비슷하지만 구현이 다르다. CFS는 각 프로세스의 vruntime(가상 실행 시간)을 추적하고, 레드-블랙 트리에서 vruntime이 가장 작은 프로세스를 다음에 실행한다. nice 값(-20~19)은 vruntime 증가 속도의 가중치로 작용한다. CFS에는 고정된 타임 슬라이스가 없고 대신 스케줄링 주기(period)를 프로세스 수에 따라 동적으로 나눈다.

Windows는 우선순위 기반 선점형 스케줄러를 사용한다. 0~31 범위의 우선순위 레벨이 있고, 커널이 스레드의 행동에 따라 동적으로 우선순위를 조절한다(예: I/O 완료 후 일시적으로 boost). MLFQS와 비슷한 피드백 원리를 적용하지만, BSD 공식 대신 휴리스틱 규칙으로 동작한다.

PintOS

PintOS에서 MLFQS는 커널 명령줄 옵션 -o mlfqs로 활성화되며, 전역 변수 thread_mlfqs가 true가 된다.

MLFQS와 Priority Donation의 관계

MLFQS 모드에서는 thread_set_priority()와 priority donation이 비활성화된다. 우선순위는 오직 공식으로만 결정된다. 이 때문에 thread_mlfqs 플래그를 확인하여 두 스케줄링 모드를 분기해야 한다.

연산 예시

상황 설정

  • f = 16384 (2
  • 스레드 A: nice = 0, recent_cpu = 0
  • 초기 load_avg = 0, ready_threads = 1 (A만 실행 중)

tick 0 ~ 99 (첫 1초)

A가 100 ticks 동안 실행한다. 매 tick마다 recent_cpu가 1씩 증가한다.

recent_cpu(A) = 100 * f = 100 * 16384 = 1,638,400 (고정소수점)

매 4 ticks마다 우선순위 재계산:

tick 4:  priority = 63 - (4 * f / 4 / f) - (0 * 2) = 63 - 1 = 62
tick 96: priority = 63 - (96 * f / 4 / f) - 0 = 63 - 24 = 39

tick 100 (1초 경과)

load_avg 갱신:

load_avg = (59/60) * 0 + (1/60) * 1
         = 0 + 16384 / 60
         = 273  (고정소수점, ≈ 0.0167)

recent_cpu 감쇄:

decay = (2 * 273) / (2 * 273 + 16384)
      = 546 / 16930
      ≈ 0.0322  (고정소수점 연산으로 수행)

recent_cpu(A) = decay * 1,638,400 + nice * f
              ≈ 52,828  (고정소수점, ≈ 3.22)

A의 recent_cpu가 100에서 약 3.22로 급격히 줄어든다. 이는 load_avg가 아직 작기 때문에 감쇄 계수가 0에 가깝기 때문이다. 시스템이 더 바빠지면(load_avg 증가) 감쇄가 느려져서 과거 사용량이 더 오래 남는다.
