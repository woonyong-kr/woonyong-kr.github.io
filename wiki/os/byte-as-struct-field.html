바이트를 Struct Field로 해석하기

확인 범위: 이 문서는 연속 바이트를 구조체의 필드 경계·정렬·오프셋과 활성 union 멤버에 따라 해석하는 일반 원리와 확인 기준을 설명한다. PintOS·Linux·QEMU의 구체적인 레이아웃, 값, 크기와 GDB 출력은 고정된 보편 사실이 아니라 해당 선언·compiler·target ABI·packing·build 설정·branch·version 및 실제 실행 기록을 기준으로 다시 검증해야 하는 구현별 예시다.

한 줄 요약: 연속 바이트를 구조체 필드 경계·정렬에 맞춰 분할 해석하는 방식 — GDB x/20bx로 확인.

Struct field 해석

메모리의 연속된 바이트를 구조체의 필드 경계에 맞춰 분할 해석하는 것이 struct field 해석이다. C 컴파일러가 struct를 메모리에 배치할 때 각 필드의 크기와 정렬 규칙에 따라 오프셋이 결정된다. GDB에서 x/20bx addr로 보이는 20바이트의 의미 없는 숫자들이, p *(struct thread *)addr로 캐스팅하는 순간 tid, status, name, priority 등 의미 있는 필드로 분리된다. 이것이 바이트 해석의 최고 수준이다.

상세 설명

추상 개념 (구조체 메모리 레이아웃 규칙)

C 구조체의 비트 필드가 아닌 멤버는 선언 순서를 보존하지만, 필드 사이와 끝에는 구현·ABI가 정한 padding이 들어갈 수 있다. 정확한 offset과 전체 크기는 현재 compiler, target ABI, packing attribute를 기준으로 확인한다.

규칙설명
순서 보존필드는 선언 순서대로 메모리에 놓인다
정렬각 타입의 _Alignof(T)와 target ABI를 따른다. 크기 N과 정렬 N은 같은 개념이 아니다
패딩 삽입구현이 각 멤버의 정렬 조건을 맞추기 위해 빈 바이트를 넣을 수 있다
구조체 크기배열 원소가 연속 배치되도록 tail padding이 포함될 수 있으며 sizeof로 확인한다

예시: 일반적인 x86-64 System V ABI에서는 4바이트 int 뒤의 8바이트 포인터 앞에 4바이트 padding이 생긴다. 이는 C 전체의 보편 상수가 아니라 해당 ABI 예시다.

struct thread 레이아웃 해부

PintOS struct thread의 앞부분을 바이트 단위로 분해:

오프셋  크기  필드             타입            예시 값
------  ----  ---------------  -------------- ----------------
0x00    4     tid              tid_t (int)     0x00000005 (tid=5)
0x04    4     status           enum (int)      0x00000001 (READY)
0x08    16    name             char[16]        "main\0\0\0..."
0x18    4     priority         int             0x0000001F (31)
0x1C    4     (padding)        -               0x00000000
0x20    8     elem.prev        list_elem *     0x8004XXXX
0x28    8     elem.next        list_elem *     0x8004XXXX
...

GDB에서 같은 바이트를 두 가지로 보기:

# 원시 바이트 (첫 24바이트)
(gdb) x/24bx 0x8004e000
0x8004e000: 0x05 0x00 0x00 0x00 0x01 0x00 0x00 0x00
0x8004e008: 0x6d 0x61 0x69 0x6e 0x00 0x00 0x00 0x00
0x8004e010: 0x00 0x00 0x00 0x00 0x00 0x00 0x00 0x00

# 구조체로 해석
(gdb) p *(struct thread *)0x8004e000
$1 = {tid = 5, status = THREAD_READY, name = "main",
      priority = 31, elem = {prev = 0x8004..., next = 0x8004...}, ...}

0x05 0x00 0x00 0x00이 단독으로는 “정수 5”이지만, struct thread 오프셋 0에 있으므로 “tid = 5”라는 의미를 갖는다. 바로 뒤의 0x01 0x00 0x00 0x00은 “정수 1”이 아니라 “status = THREAD_READY(1)“다.

오프셋 계산의 중요성

struct field 해석의 핵심은 오프셋이다. 같은 4바이트 0x0000001F도 오프셋에 따라 전혀 다른 의미를 갖는다.

오프셋 0x00에 있으면: tid = 31
오프셋 0x04에 있으면: status = 31 (잘못된 enum 값 → 버그!)
오프셋 0x18에 있으면: priority = 31 (정상)

GDB에서 오프셋 확인:

(gdb) p &((struct thread *)0)->tid        → 0x0  (오프셋 0)
(gdb) p &((struct thread *)0)->status     → 0x4  (오프셋 4)
(gdb) p &((struct thread *)0)->name       → 0x8  (오프셋 8)
(gdb) p &((struct thread *)0)->priority   → 0x18 (오프셋 24)

list_entry 매크로: 역방향 struct field 해석

PintOS에서 가장 빈번한 struct field 해석 패턴은 list_entry() 매크로다. 리스트 elem의 주소에서 포함 구조체의 주소를 역산한다.

예: elem 주소가 0x8004e020이고 struct thread의 elem 오프셋이 0x20이면:

thread 주소 = 0x8004e020 - 0x20 = 0x8004e000

이것은 “0x8004e020이라는 주소에 있는 바이트를 struct thread의 elem 필드로 해석하고, 거기서 구조체 시작점을 역산”하는 과정이다.

struct page의 union 해석

struct page는 union을 사용하여 같은 바이트를 페이지 타입에 따라 다른 구조체로 해석한다:

union 영역의 같은 바이트가:

  • VM_UNINIT이면: init, type, aux, page_initializer 필드
  • VM_ANON이면: swap_index 필드
  • VM_FILE이면: file, ofs, read_bytes 필드

GDB에서 확인:

# 잘못된 해석 (타입 무시하고 anon으로 읽음)
(gdb) p page->anon.swap_index
$1 = 140737488355328    ← 의미 없는 큰 숫자 (실제로는 file page)

# 올바른 해석 (타입 확인 후 file로 읽음)
(gdb) p page->file
$2 = {file = 0x8004a200, ofs = 0, read_bytes = 4096}

struct intr_frame 해석

인터럽트 프레임은 CPU가 하드웨어적으로 푸시한 값과 소프트웨어가 푸시한 값이 혼재한다:

오프셋  크기  필드     누가 저장       값 예시
------  ----  -------  -------------- ----------------
0x00    8     R15      소프트웨어      0x0000000000000000
0x08    8     R14      소프트웨어      0x0000000000000000
...
0x70    8     RAX      소프트웨어      syscall 반환값
0x78    8     ES+pad   소프트웨어      segment selector slot
0x80    8     DS+pad   소프트웨어      segment selector slot
0x88    8     vec_no   stub             interrupt vector
0x90    8     error_code CPU/stub       exception error code
0x98    8     RIP      CPU 하드웨어    0x000000004001a0
0xA0    8     CS+pad   CPU 하드웨어    0x002b (유저 CS)
0xA8    8     RFLAGS   CPU 하드웨어    0x0000000000000206
0xB0    8     RSP      CPU 하드웨어    0x000047480000
0xB8    8     SS+pad   CPU 하드웨어    0x0023 (유저 SS)

이 표는 현재 저장소의 packed struct gp_registers 15개와 struct intr_frame 선언을 기준으로 계산한 것이다. CPU와 stub이 저장한 값이 섞이므로 선언과 intr-stubs.S를 함께 확인해야 한다.

실제 OS (Linux)

Linux task_struct는 약 6KB 크기에 수백 개의 필드가 있다. 필드 오프셋은 커널 빌드 옵션과 config에 따라 달라지므로, pahole 도구로 레이아웃을 확인한다:

PintOS의 struct thread가 ~200바이트인 데 비해 Linux의 task_struct는 ~6000바이트이므로, 오프셋 오류의 영향이 훨씬 크다.

QEMU 에뮬레이션

QEMU의 CPUX86State도 큰 내부 구조체다. 그러나 필드 순서·offset은 QEMU version과 build target에 따라 바뀔 수 있는 내부 구현이며 안정 API가 아니다:

GDB stub은 target별 register read callback으로 guest CPU state를 GDB remote protocol 순서에 맞춰 직렬화한다. 디버깅할 때는 현재 checkout의 callback과 offsetof/debug info를 확인하고, 위 축약 선언을 고정 offset 표처럼 사용하지 않는다.

Struct field 해석 값 추적

struct thread 필드 오프셋과 크기 (x86-64):

sizeof(tid_t) = 4,    alignof = 4,   offset = 0
sizeof(enum)  = 4,    alignof = 4,   offset = 4
sizeof(char[16]) = 16, alignof = 1,  offset = 8
sizeof(int)   = 4,    alignof = 4,   offset = 24 (0x18)
sizeof(struct list_elem) = 16, alignof = 8, offset = 32 (0x20)

struct page union 크기:
sizeof(struct uninit_page) = 32   (init + type + aux + page_initializer)
sizeof(struct anon_page) = 4      (swap_index만)
sizeof(struct file_page) = 24     (file + ofs + read_bytes)
→ union 크기 = max(32, 4, 24) = 32바이트

현재 packed `struct intr_frame` 크기:
gp_registers 15개 × 8바이트 = 120바이트
+ ES slot 8 + DS slot 8 + vec_no 8 + error_code 8
+ RIP 8 + CS slot 8 + RFLAGS 8 + RSP 8 + SS slot 8
= 192바이트 (`0xC0`)

다른 branch·compiler에서는 `p sizeof(struct intr_frame)`과 `p &((struct intr_frame *)0)->field`로 다시 확인한다.
