저장소 내구성 계약

저장소 내구성 계약

범위: 이 문서는 write()와 fsync()를 중심으로 저장소 내구성의 일반 원리와 Linux·Windows·PintOS·QEMU의 동작 차이를 개념적으로 설명한다. 제시된 코드 경로, 설정값, 실행 예시와 성능 수치는 특정 버전이나 환경에서 검증된 결과로 간주하지 말고, 실제 판단에는 대상 코드·버전·캐시 설정·실행 기록과 측정 결과를 별도로 확인해야 한다.

한 줄 요약: OS 세 책임 중 저장소 — write() 호출이 디스크 도달까지 무엇을 약속하고 무엇은 약속하지 않는지의 계약.

저장소 내구성 계약 변화

OS의 세 가지 핵심 책임 중 세 번째가 저장소다(나머지 둘: 추상화, 보호). 저장소 책임의 핵심은 “프로그램이 write()를 호출했을 때, 그 데이터가 언제, 어디에, 어떤 순서로 디스크에 도달하는가”라는 질문에 답하는 것이다.

이 계약이 중요한 이유는 단순하다. 전원이 나가도 데이터가 살아남으려면, RAM이 아니라 비휘발성 저장 장치에 도달해야 한다. write() 시스템 콜이 성공 반환했다고 해서 데이터가 디스크에 있다는 보장은 없다. OS는 성능을 위해 여러 층의 버퍼를 두기 때문이다. 이 간극을 명시적으로 좁히는 것이 fsync()의 역할이다.

상세 설명

추상 개념 (저장소 계층 규칙)

데이터가 프로그램에서 디스크까지 내려가는 경로에는 여러 버퍼 층이 있다.

%% 저장소 계층 규칙
flowchart TD
  user_buffer["프로그램 메모리<br/>(user buffer)"]
  page_cache["커널 페이지 캐시 /<br/>파일 시스템 버퍼"]
  disk_cache["디스크 컨트롤러<br/>write-back 캐시"]
  durable_media["비휘발성 매체<br/>(platters / NAND cells)"]
  user_buffer --> page_cache
  page_cache --> disk_cache
  disk_cache --> durable_media

각 층의 의미:

층위치전원 꺼지면
user buffer프로세스 가상 메모리소멸
페이지 캐시커널 RAM소멸
디스크 컨트롤러 캐시디스크 하드웨어 RAM소멸 (배터리 없으면)
비휘발성 매체자기 디스크 / NAND생존

write()는 user buffer → 커널 페이지 캐시로 데이터를 복사하고 즉시 반환한다. 이 시점에서 데이터는 아직 RAM에만 있다.

fsync(fd)는 해당 파일의 페이지 캐시 내용을 디스크까지 내려보내고, 디스크가 완료를 보고할 때까지 기다린다. 이것이 “내구성(durability) 계약”이다.

O_DIRECT와 O_SYNC: O_DIRECT는 페이지 캐시를 우회하여 user buffer에서 직접 디스크로 I/O를 수행한다. O_SYNC는 write() 반환 전에 데이터가 디스크에 도달하도록 보장한다. 둘 다 성능 비용이 크므로 데이터베이스 같은 특수 용도에서 사용한다.

실제 OS (Linux/Windows)

Linux의 저장소 경로:

%% Linux write()와 fsync(fd)의 저장소 경로
flowchart TD
  write_call["write(fd, buf, n)"]
  dirty_page["page를 dirty로 표시"]
  write_return["반환<br/>데이터는 아직 RAM"]
  fsync_call["fsync(fd)"]
  flush_cache["blkdev_issue_flush()<br/>디스크 캐시 flush"]
  fsync_return["반환<br/>비휘발성 매체에 도달"]
  copy_user["copy_user"]
  write_wait["write_wait"]
  write_call --> copy_user
  copy_user --> dirty_page
  dirty_page --> write_return
  fsync_call --> write_wait
  write_wait --> flush_cache
  flush_cache --> fsync_return

Linux의 dirty page writeback은 두 가지 경로로 자동 실행된다:

  • 주기적 writeback: dirty_writeback_centisecs (기본 5초)마다 kworker가 dirty page를 flush
  • 메모리 압박: free memory가 부족하면 dirty page를 flush하여 회수

Linux의 핵심 파일 시스템 호출:

호출보장
write()데이터가 페이지 캐시에 도달
fdatasync()파일 데이터가 디스크에 도달 (메타데이터 제외)
fsync()파일 데이터 + 메타데이터가 디스크에 도달
sync()모든 dirty 데이터가 디스크에 도달 (반환은 기다리지 않을 수 있음)

Windows:

Windows에서는 FlushFileBuffers(hFile)이 Linux의 fsync()에 해당한다. WriteFile()은 기본적으로 OS 캐시를 거친다. FILE_FLAG_NO_BUFFERING과 FILE_FLAG_WRITE_THROUGH로 캐시를 제어할 수 있다.

PintOS 구현

PintOS의 파일 시스템은 단순한 구조로, 페이지 캐시가 없다. 모든 write()는 곧바로 디스크 섹터에 기록된다.

%% PintOS write()에서 디스크 기록까지
flowchart TD
  write_call["write(fd, buf, n)"]
  file_write["file_write()"]
  inode_write["inode_write_at()"]
  block_write["block_write(fs_device,<br/>sector_idx, buffer)"]
  disk_record["즉시 디스크에 기록"]
  write_call --> file_write
  file_write --> inode_write
  inode_write --> block_write
  block_write --> disk_record

따라서 PintOS에서는 fsync()가 필요 없다. 하지만 이것은 실제 OS와 정반대 설계다.

측면PintOSLinux/Windows
페이지 캐시없음있음 (수백 MB~수 GB)
write() 의미즉시 디스크 기록페이지 캐시까지만
fsync()불필요 (구현 없음)내구성 보장의 핵심
성능매 write마다 디스크 I/O캐시 덕에 빠름, flush는 나중에

PintOS에서 디스크에 쓰는 경로의 코드:

block_write()는 즉시 IDE 컨트롤러에 명령을 보내고 완료를 기다린다.

VM과의 연결: mmap dirty writeback

VM 프로젝트에서 file-backed page가 dirty일 때 eviction이나 munmap 시 파일에 write-back하는 것도 이 저장소 경로를 탄다. 자세한 trace는 mmap dirty writeback에서 본다.

%% mmap dirty page write-back 경로
flowchart TD
  dirty_page["dirty file-backed page eviction"]
  file_write["file_write_at(file,<br/>page_kva, read_bytes, ofs)"]
  inode_write["inode_write_at()"]
  block_write["block_write()"]
  disk_sector["디스크 섹터에 기록"]
  dirty_page --> file_write
  file_write --> inode_write
  inode_write --> block_write
  block_write --> disk_sector

QEMU 에뮬레이션

PintOS의 block_write()는 IDE 컨트롤러 포트에 쓰는 것이다. QEMU는 이 I/O 포트 접근을 가로채서 QEMU BlockBackend로 전달한다.

%% PintOS block_write()에서 QEMU block backend까지
flowchart TD
  pintos_write["PintOS:<br/>block_write(dev, sector, buffer)"]
  ide_ports["outb/outw to IDE I/O ports<br/>(0x1F0~0x1F7)"]
  qemu_ide["QEMU IDE model이<br/>I/O 가로챔"]
  qemu_block["QEMU block backend:<br/>host file의 sector x 512 offset에 write"]
  host_write["host OS의 write() 호출"]
  pintos_write --> ide_ports
  ide_ports --> qemu_ide
  qemu_ide --> qemu_block
  qemu_block --> host_write

QEMU의 block backend 캐시 모드에 따라 실제 내구성이 달라진다:

QEMU 캐시 모드동작
writethrough매 write마다 host fsync (느리지만 안전)
writebackhost 페이지 캐시까지만 (빠르지만 host 크래시 시 손실 가능)
noneO_DIRECT, host 캐시 우회
unsafe모든 flush 무시 (테스트용, 가장 빠름)

PintOS 개발에서는 보통 writeback이나 기본값을 사용한다. QEMU가 비정상 종료하면 disk image가 손상될 수 있는 이유가 여기에 있다.

저장소 내구성 계약 값 추적

PintOS 파일 시스템의 디스크 I/O 단위:

BLOCK_SECTOR_SIZE = 512 bytes
PintOS page       = 4096 bytes = 8 sectors

1 page를 디스크에 쓸 때: 8번의 block_write() 호출
                          = 8 × 512 = 4096 bytes

swap 1 slot       = 1 page = 8 consecutive sectors
swap slot N의 시작 sector = N × 8

Linux 페이지 캐시의 dirty writeback 타이밍:

dirty_writeback_centisecs = 500  → 5초마다 writeback 스레드 실행
dirty_expire_centisecs    = 3000 → dirty page가 30초 이상이면 flush 대상
dirty_ratio               = 20  → 전체 메모리의 20% 이상 dirty면 동기 flush
dirty_background_ratio    = 10  → 10% 이상이면 비동기 flush 시작

fsync 비용 비교 (대략적 수치):

write() to page cache:  ~1μs (메모리 복사)
fsync() to SSD:         ~100μs~1ms
fsync() to HDD:         ~5~10ms (seek + rotation)
PintOS block_write():   매번 디스크 I/O → 매번 ~ms 단위 대기

저장소 내구성 계약 점검

  • write() 성공은 “커널이 데이터를 받았다”는 신호이고, 실제 OS에서는 그 데이터가 아직 page cache나 디스크 캐시에 남아 있을 수 있다.
  • fsync()는 dirty 데이터와 필요한 메타데이터를 디스크 쪽으로 밀어 내고, 저장장치가 완료를 보고할 때까지 기다려 이 간극을 좁힌다.
  • 버퍼 캐시를 쓰면 성능은 좋아지지만 크래시 시점의 중간 상태가 생기므로, 저널링이 커밋 순서를 남겨 복구 기준을 만든다.
  • PintOS 기본 파일시스템은 page cache와 저널링이 없어서 write()가 곧바로 block_write()로 내려간다. 그래서 학습할 때는 “PintOS에서 단순화된 계약”과 “실제 OS의 내구성 계약”을 분리해서 읽어야 한다.
