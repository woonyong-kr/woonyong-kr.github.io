파일 시스템 추상화

한 줄 요약: 물리 섹터 번호를 직접 다루는 위험을 없애고 이름·오프셋으로 데이터를 다루게 하는 파일 시스템 추상화 계층.

파일 시스템 추상화 구조

프로그램이 디스크의 물리 섹터 번호(sector 0, 1, 2…)를 직접 다루면 한 프로그램이 다른 프로그램의 데이터를 덮어쓸 수 있다. 섹터 배치가 바뀔 때마다 모든 프로그램을 수정해야 하는 문제도 생긴다. 파일 시스템은 디스크 섹터를 이름(name), 오프셋(offset), 읽기/쓰기 연산 뒤에 감춘다.

프로그램은 “report.txt의 100번째 바이트부터 50바이트 읽어줘”라고 요청하면 된다. 이 요청을 어느 디스크의 몇 번째 섹터에 대한 명령으로 바꿀지는 OS가 처리한다.

하드웨어에서 파일까지

디스크는 고정 크기 블록의 일차원 배열이며, 전통적인 섹터 크기는 512바이트다. 디스크 컨트롤러는 “섹터 N 읽기/쓰기”라는 명령만 이해한다. 파일 시스템은 이 인터페이스 위에 이름, 파일 내 위치, 파일 크기라는 추상화를 제공한다.

계층하드웨어가 보는 것프로그램이 보는 것
이름섹터 번호파일 경로 (docs/report.txt)
위치바이트 오프셋 없음 (섹터 단위)파일 내 바이트 오프셋 (pos)
크기섹터 개수파일 길이 (바이트 단위)

읽기와 쓰기 요청은 파일 오프셋 → inode의 블록 매핑 → 디스크 섹터 번호 순서로 변환된다.

Linux의 VFS

Linux VFS(Virtual File System)는 서로 다른 파일 시스템을 공통 인터페이스 뒤에 둔다. ext4, XFS, NFS, procfs가 같은 인터페이스를 구현하므로 프로그램은 구체적인 디스크 레이아웃과 관계없이 open() → read() → write() → close()를 호출할 수 있다.

Application
    ↓ open("/etc/passwd", O_RDONLY)
VFS Layer  ← struct file_operations { .read, .write, .llseek, ... }
    ↓
ext4 / XFS / NFS  ← 구체적인 디스크 레이아웃 처리
    ↓
Block I/O Layer
    ↓
Disk Controller  ← sector read/write

이 경로에서는 다음 구조체가 서로 다른 역할을 맡는다.

  • struct inode: 파일의 메타데이터 (크기, 권한, 블록 매핑)
  • struct file: 열린 파일 인스턴스 (현재 오프셋 pos, 접근 모드)
  • struct dentry: 디렉터리 엔트리 (이름 → inode 연결)

PintOS의 구현

PintOS의 파일 시스템은 교육용으로 단순화되어 있지만, 프로그램의 요청을 섹터 단위 I/O로 변환하는 계층은 동일하다.

프로그램 (syscall: open, read, write, close)
    ↓
struct file  ← inode 포인터 + pos + deny_write
    ↓
struct inode ← sector 번호 + 길이 + on-disk 데이터
    ↓
disk_read() / disk_write()  ← 섹터 단위 I/O

struct file은 열린 파일의 inode와 현재 위치, 쓰기 금지 상태를 보관한다.

프로그램이 file_read(file, buffer, size)를 호출하면 다음 변환이 일어난다.

  1. file->pos에서 현재 오프셋을 가져온다.
  2. inode_read_at(file->inode, buffer, size, file->pos)로 inode에 위임한다.
  3. inode가 오프셋을 섹터 번호로 변환하여 disk_read()를 호출한다.
  4. file->pos += bytes_read로 위치를 전진시킨다.

Linux와 비교하면 PintOS는 블록 배치, 디렉터리, 캐시, 동시 접근, 파일 확장 방식을 단순하게 구성한다.

기능LinuxPintOS
블록 매핑extent tree, indirect block연속 할당 (inode_disk.start + length)
디렉터리트리 구조 (중첩 가능)단일 루트 디렉터리
캐시page cache + buffer cache없음 (매번 디스크 접근)
동시 접근파일별 lock + RCU전역 filesys_lock
파일 확장동적 블록 할당생성 시 크기 고정

QEMU에서 보이는 디스크 I/O

QEMU에서 PintOS의 디스크 I/O는 다음 경로를 지난다.

PintOS: disk_read(filesys_disk, sector, buffer)
    ↓ outb(0x1F7, CMD_READ_SECTOR_RETRY)  ← Port I/O
IDE controller model (hw/ide/core.c)  ← 가상 IDE 레지스터
    ↓ ide_sector_read() → blk_aio_preadv()
BlockBackend (block/block-backend.c)  ← QEMU 블록 계층
    ↓ raw_co_preadv() → pread(fd, buf, 512, sector×512)
호스트 파일 I/O  ← os.img / swap.dsk 파일

PintOS가 disk_read(filesys_disk, sector_no, buf)를 호출하면 QEMU의 IDE 컨트롤러 모델은 이를 호스트 파일(os.img)의 sector_no × 512 오프셋에서 512바이트를 읽는 작업으로 변환한다.

PintOS의 이름, 오프셋, inode 같은 파일 시스템 추상화는 QEMU에 보이지 않는다. file_read(f, buf, 100)과 file_write(f, buf, 50)은 파일 시스템 수준에서는 다른 요청이지만, QEMU는 둘을 outb(0x1F7, 0x20) 같은 IDE 포트 I/O 명령으로 처리한다. 파일 시스템보다 아래 계층에서는 다시 “섹터 N 읽기/쓰기”만 남는 셈이다.

GDB에서는 다음 지점을 확인해 파일 오프셋이 섹터와 섹터 내부 위치로 바뀌는 과정을 추적할 수 있다.

PintOS에서 값이 변환되는 과정

PintOS 파일 시스템에서 사용되는 구체적인 값은 다음과 같다.

항목값

다음 요청은 파일 오프셋 1500에서 100바이트를 읽는다. 파일 데이터가 섹터 10에서 시작하므로 첫 번째 대상은 섹터 12다. 섹터 12의 476번째 바이트부터 36바이트를 읽은 뒤, 남은 64바이트를 섹터 13에서 읽는다.

file_read_at(file, buf, 100, 1500)
→ inode->data.start = 10  (섹터 10부터 파일 데이터 시작)
→ byte_to_sector(inode, 1500)
  = start + pos / DISK_SECTOR_SIZE
  = 10 + 1500 / 512 = 10 + 2 = 12
→ sector_ofs = 1500 % 512 = 476
→ sector_left = 512 - 476 = 36
→ chunk_size = min(size=100, inode_left, sector_left=36) = 36
→ disk_read(filesys_disk, 12, bounce)  // 512B 전체 읽기
→ memcpy(buf, bounce + 476, 36)        // 36B만 복사
→ 두 번째 루프: offset=1536, sector 13, sector_ofs=0
  chunk_size = min(64, inode_left, 512) = 64
  → disk_read(filesys_disk, 13, bounce)
  → memcpy(buf+36, bounce + 0, 64)
→ 총 2번 disk_read로 100B 완료

sector_ofs == 0이고 chunk_size == 512이면 bounce buffer를 거치지 않고 사용자 버퍼에 직접 읽는다. 4096바이트 연속 읽기에서는 8번의 disk_read 중 6번이 direct이고, 최초와 최후만 bounce를 사용한다.

층별로 구분하기

파일 시스템 추상화는 프로그램이 이름과 바이트 오프셋으로 요청하게 하고, OS가 그 요청을 inode의 블록 매핑과 디스크 섹터 번호로 바꾸는 층이다. 이 과정을 따라갈 때는 이름, 열린 핸들, inode 메타데이터, 섹터 I/O를 구분해야 한다.

fd는 프로세스가 보관하는 정수 핸들이다. 열린 파일 객체는 pos와 접근 상태를 가진 실행 중 상태이고, inode는 파일의 크기와 디스크 위치를 설명하는 메타데이터다. PintOS에서는 filesys_open()이 이름을 struct file로 바꾸고, file_read()와 file_write()가 현재 pos를 기준으로 inode_read_at() 또는 inode_write_at()에 위임한다.

그 아래의 QEMU는 파일 이름, fd, struct file, inode를 알지 못한다. QEMU가 처리하는 것은 결국 sector_no × 512 위치의 호스트 파일 I/O다. 흐름이 헷갈리면 지금 보고 있는 대상이 이름, 열린 핸들, inode 메타데이터, 섹터 I/O 중 어느 층에 속하는지부터 확인할 수 있다.
