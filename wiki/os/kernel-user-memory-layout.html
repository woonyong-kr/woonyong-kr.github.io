커널 영역과 유저 영역 — 가상 주소 공간은 어떻게 나뉘는가

확인 범위: 이 문서는 가상 주소 공간의 커널·유저 영역 구분이라는 일반 개념을 PintOS의 매핑·할당 구조와 Linux 비교를 통해 설명한다. 주소값, 코드 좌표, QEMU 동작, GDB 출력과 성능 관련 판단은 특정 코드·버전에서 실제 실행하거나 측정해 검증한 결과가 아니라, 제시된 구현 설명과 관찰 절차의 예시로 구분해 읽어야 한다.

한 줄 요약: 한 프로세스의 가상 주소 공간이 커널 영역과 유저 영역으로 나뉘는 구조.

가상 주소 공간의 전체 구조

하나의 프로세스가 실행 중일 때, CPU가 보는 가상 주소 공간은 크게 두 영역으로 나뉜다.

유저 모드에서 KERN_BASE 위의 주소에 접근하면 page fault가 발생한다. 이게 커널이 모드를 나눠서 보호하는 핵심 메커니즘이다.

커널 영역 — 1:1 매핑의 의미

”1:1 매핑”이란

PintOS에서 커널 영역의 가상 주소는 물리 메모리 전체를 그대로 올려놓은 구조다.

이 매핑은 부팅 시점에 전부 미리 설정된다. 이후에 커널이 메모리를 쓸 때 페이지 테이블을 건드릴 필요가 없다. ptov()와 vtop() 매크로가 단순한 덧셈/뺄셈으로 변환하는 이유도 이것이다.

palloc은 매핑을 만드는 게 아니다

여기서 가장 헷갈리는 부분이 palloc_get_page()의 역할이다.

1:1 매핑이 이미 전체 물리 메모리를 커버하고 있으므로, palloc_get_page()는 새로운 매핑을 만드는 게 아니다. 비트맵에서 “아직 안 쓰는 물리 페이지”를 찾아서 “사용 중”으로 표시한 뒤, 그 물리 페이지에 이미 대응하는 가상 주소를 반환하는 것뿐이다.

“가상 주소 어딘가를 새로 매핑해야 한다”는 전제 자체가 필요 없다. 1:1 매핑 덕분에 물리 메모리의 모든 바이트가 이미 가상 주소를 갖고 있고, palloc은 그중 빈 것을 골라주는 할당자일 뿐이다.

커널 스택이 충돌하지 않는 이유

모든 스레드가 같은 커널 페이지 테이블을 공유하니까, 원칙적으로는 다른 스레드의 커널 스택 영역에 접근할 수 있다. 하지만 각 스레드는 palloc_get_page()로 서로 다른 물리 페이지를 받고, 그 페이지의 맨 위를 자기 rsp로 설정하니까 실제로는 각자 다른 4KB 영역에서만 스택을 쓰게 된다.

커널이 schedule()에서 다른 스레드의 구조체에 접근하거나, thread_foreach()로 모든 스레드를 순회할 수 있는 것도 같은 이유다. 다 같은 커널 주소 공간에 있으니까.

커널 힙

커널 주소 공간 자체가 하나이므로 그 안의 모든 영역이 자연스럽게 공유된다. malloc()이나 palloc_get_page()로 할당하는 커널 메모리는 1:1 매핑 위에 있고, 어떤 스레드에서 할당하든 다른 스레드에서도 접근 가능하다.

유저 영역 — 프로세스마다 다른 매핑

유저 영역은 커널과 완전히 다르다. 미리 매핑돼 있지 않고, 페이지를 할당받은 뒤 pml4_set_page()로 유저 가상 주소 → 물리 주소 매핑을 새로 만들어야 한다.

각 프로세스는 자기만의 pml4를 갖고, 코드/데이터/BSS/힙/스택이 따로 매핑돼 있다. 프로세스 A의 코드가 올라간 가상 주소와 프로세스 B의 코드가 올라간 가상 주소가 같더라도, pml4가 다르기 때문에 서로 다른 물리 페이지를 가리킨다.

유저 풀과 커널 풀

PintOS는 물리 메모리를 커널 풀과 유저 풀로 나눈다.

유저 프로세스의 코드/데이터를 로드할 때는 유저 풀에서 물리 페이지를 받고, pml4_set_page()로 유저 가상 주소에 매핑한다. 커널 스택이나 struct thread를 만들 때는 커널 풀에서 받고, 1:1 매핑이 이미 있으니까 추가 매핑 없이 바로 쓴다.

공유 라이브러리 — 같은 물리 페이지, 다른 가상 주소

PintOS에는 없다

PintOS는 정적 링크만 지원한다. 모든 라이브러리 코드가 ELF 바이너리에 포함돼서 코드/데이터 세그먼트에 같이 로드된다.

리눅스에서는

공유 라이브러리(.so)는 유저 영역에 매핑된다. mmap으로 스택과 힙 사이 공간에 올리고, 물리 페이지는 여러 프로세스가 공유하되 각 프로세스의 유저 가상 주소에 따로 매핑하는 구조다.

libc.so 같은 걸 프로세스마다 물리 메모리에 중복 로드하면 낭비니까, 물리 페이지 하나를 여러 프로세스의 페이지 테이블이 동시에 가리키게 하는 것이다. 이건 shared memory(IPC 공유 메모리)와 동일한 메커니즘이다.

보안상 고정 주소를 쓰면 공격에 취약하니까, 리눅스는 ASLR(Address Space Layout Randomization)로 매핑 주소를 매번 랜덤하게 배치한다.

커널에는 공유 라이브러리 개념이 따로 없다. 커널 코드 자체가 전부 커널 영역에 상주하고, 모든 스레드가 이미 공유하고 있기 때문이다.

QEMU 에뮬레이션

QEMU는 게스트의 가상 주소 공간 레이아웃을 직접 관여하지 않는다. 커널/유저 분할은 순전히 게스트 OS가 PML4를 어떻게 설정하느냐에 달려 있다. QEMU가 관여하는 지점:

  • softmmu TLB: 게스트 가상 주소 → 게스트 물리 주소 변환을 캐시한다. KERN_BASE 위의 접근과 아래의 접근이 같은 TLB에서 관리되며, 캐시 항목의 user/supervisor 비트로 권한을 검사한다.
  • RAMBlock: 게스트 물리 메모리 전체(128 MB)를 하나의 RAMBlock으로 backing한다. 커널 풀이든 유저 풀이든 같은 RAMBlock 안의 다른 오프셋일 뿐이다.
  • CR3 전환: pml4_activate()가 lcr3()를 실행하면 QEMU는 softmmu TLB를 전면 flush한다. 이후 모든 메모리 접근이 새 PML4 기준으로 변환된다.
  • PTE user bit 검증: 유저 모드(CPL 3)에서 PTE의 user bit이 0인 페이지에 접근하면 QEMU가 page fault를 발생시킨다. 이것이 커널 영역 보호의 핵심이다.

GDB 관찰 스크립트

관찰 시나리오

시나리오 1: 유저/커널 영역 경계 실험 — 같은 물리 주소, 두 가지 접근 경로

커널이 palloc_get_page(PAL_USER)로 할당한 유저 frame의 KVA와 유저 VA가 같은 물리 주소를 가리키는 것을 확인한다:

# 1. palloc_get_page(PAL_USER) 호출
(gdb) p/x palloc_get_page(PAL_USER)
$1 = 0x8004800000          ← KVA (커널 가상 주소)

# 2. 이 KVA의 물리 주소 계산
(gdb) check_ptov 0x800000
PA=0x800000 → ptov → KVA=0x8004800000
# → 물리 주소 0x800000

# 3. pml4_set_page로 유저 VA 0x400000에 매핑
(gdb) p pml4_set_page(thread_current()->pml4, 0x400000, 0x8004800000, 1)

# 4. 유저 VA에서 같은 물리 페이지 접근
(gdb) classify_va 0x400000
0x400000 → USER (needs pml4 lookup)
  mapped to frame KVA=0x8004800000

# → 커널은 KVA(0x8004800000)로, 유저는 VA(0x400000)로 같은 물리 주소 접근
# → 1:1 매핑의 핵심: 커널이 유저 frame을 채울 때 KVA로 바로 memcpy 가능

시나리오 2: 프로세스 전환 시 커널 영역 공유 / 유저 영역 독립 확인

두 프로세스의 PML4를 비교하여 커널 영역 PTE는 동일하고 유저 영역 PTE는 다른 것을 확인한다:

# 1. 프로세스 A (tid=3) 상태
(gdb) show_layout
KERN_BASE = 0x8004000000
CR3 (current PML4 PA) = 0x123c000
tid=3, pml4=0x800523c000

# 2. PML4 상위 엔트리 (커널 영역) 덤프
(gdb) x/4gx 0x800523c000 + 256*8
# → 커널 PML4 엔트리들

# 3. 프로세스 B (tid=4)로 전환 후 같은 위치 비교
(gdb) x/4gx 0x8005240000 + 256*8
# → 동일한 값! (pml4_create에서 커널 영역을 복사하기 때문)

# 4. 유저 영역 엔트리는 다름
(gdb) x/4gx 0x800523c000    ← A의 PML4[0]
(gdb) x/4gx 0x8005240000    ← B의 PML4[0]
# → 다른 값 (각 프로세스가 독립적인 유저 매핑을 가짐)

정리

핵심을 한 문장으로 요약하면, 커널 영역은 1:1 매핑이 이미 돼 있어서 palloc은 빈 페이지를 골라주기만 하고, 유저 영역은 매핑이 없어서 페이지 할당 후 pml4에 등록해야 쓸 수 있다.

모든 스레드의 커널 스택은 같은 주소 공간에 있지만 서로 다른 물리 페이지를 받아서 rsp가 다른 곳을 가리키므로 충돌하지 않는다. 공유 라이브러리는 유저 영역에만 있고, 커널은 이미 전부 공유 상태라 별도 메커니즘이 필요 없다.
