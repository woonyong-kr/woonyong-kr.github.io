fork 세마포어 동기화

fork 세마포어 동기화

확인 범위: 이 문서는 PintOS의 fork 세마포어 handshake가 필요한 일반 원리와 구현 시 지켜야 할 선택 기준을 설명한다. 제시된 코드 좌표, 구조체 크기, QEMU·GDB 동작 및 타이밍 비교는 특정 코드 버전이나 실제 실행·성능 측정으로 검증한 결과가 아니라 입력 본문의 예시이므로, 적용 전에 대상 구현과 실행 기록을 별도로 확인해야 한다.

fork()는 자식을 만들었다고 바로 성공한 것이 아니다. 부모는 자식이 주소 공간과 파일 디스크립터 복제를 끝냈는지 확인한 뒤에야 fork 결과를 돌려줄 수 있다.

부모가 먼저 달려가면 안 되는 이유

PintOS에서 thread_create()가 반환했다는 말은 자식 스레드가 READY 큐에 들어갔다는 뜻이지, 자식의 __do_fork()가 성공했다는 뜻은 아니다. 자식이 CPU를 받아 주소 공간 복제, fd 테이블 복제, 반환값 설정을 마칠 때까지 부모가 먼저 진행하면 실패를 성공처럼 돌려줄 수 있다. 그래서 부모는 fork_sema에서 잠들고, 자식은 초기화 결과를 fork_success에 기록한 뒤 sema_up()으로 부모를 깨운다.

handshake가 필요한 지점

fork 동기화 문제

fork()의 핵심 난제는 비동기 복제다. 부모가 thread_create()를 호출하면 자식 스레드가 생성되지만, 자식의 실제 초기화(__do_fork)는 자식이 CPU를 받은 뒤에야 실행된다. 부모가 fork의 반환값(자식 tid)을 받는 시점에 자식이 아직 주소 공간을 복제하지 못했다면, 부모는 “성공한 줄 알고” 진행하다가 자식이 실패해도 알 방법이 없다.

따라서 부모는 자식의 초기화 결과(성공/실패)를 확인한 뒤에야 fork를 반환해야 한다.

실제 OS (Linux)

Linux fork()는 copy_process() 안에서 주소 공간 복제(COW 설정)를 동기적으로 수행한다. 부모 컨텍스트에서 직접 페이지 테이블을 복사하므로, copy_process()가 반환하면 복제는 이미 완료된 상태다. 세마포어 handshake가 따로 필요 없다.

PintOS는 자식 스레드의 __do_fork()에서 비동기적으로 복제하기 때문에, 세마포어 기반 handshake가 필수적이다.

PintOS 구현

데이터 구조

child_status 안에 fork_sema와 fork_success 필드가 있다.

부모 측 (process_fork)

자식 측 (__do_fork)

핵심 불변식

  1. 부모는 반드시 한 번만 sema_down한다. process_fork()에서 thread_create 성공 후 정확히 한 번.
  2. 자식은 반드시 한 번만 sema_up한다. 성공 경로든 실패 경로든, 정확히 한 번 sema_up을 호출해야 부모가 영원히 블록되지 않는다.
  3. fork_success는 sema_up 직전에 설정한다. 부모가 깨어났을 때 이미 올바른 값을 읽을 수 있도록 보장한다 (happens-before 관계).

QEMU 에뮬레이션

QEMU-TCG 관점에서 sema_down()/sema_up()은 특별한 것이 아니다. 모두 일반 메모리 읽기/쓰기와 인터럽트 비활성화(intr_disable())의 조합일 뿐이다. 그러나 fork handshake를 디버깅할 때 QEMU의 GDB stub을 활용하면 동기화 흐름을 정확히 추적할 수 있다.

GDB에서 fork handshake 관찰

# 부모의 sema_down 진입 관찰
(gdb) break process.c:210    # sema_down(&cs->fork_sema)
(gdb) commands
  silent
  printf "PARENT tid=%d blocking on fork_sema at %p, value=%d\n", \
         $lx_current().tid, &cs->fork_sema, cs->fork_sema.value
  continue
end

# 자식의 sema_up 관찰
(gdb) break process.c:391    # sema_up (성공 경로)
(gdb) break process.c:403    # sema_up (실패 경로)
(gdb) commands 2-3
  silent
  printf "CHILD tid=%d signaling fork_sema, fork_success=%d\n", \
         $lx_current().tid, cs->fork_success
  continue
end

TCG에서의 타이밍 비결정성

실제 하드웨어에서는 부모가 sema_down()에서 블록되고, timer interrupt가 오면 자식이 스케줄된다. QEMU에서는 TCG 실행 루프가 일정 수의 명령어를 실행한 후 timer 인터럽트를 주입하는데, 이 “일정 수”가 비결정적이다. 따라서:

항목실제 하드웨어QEMU TCG
timer interrupt 주기정확히 PIT 프로그래밍 값TCG icount에 의존, 약간의 지터
부모→자식 전환 타이밍timer tick에 동기화TB 실행 경계에서 인터럽트 확인
디버깅 재현성결정적 (같은 하드웨어)비결정적 (호스트 부하에 따라 변동)

sema_down() 호출 시 자식이 아직 READY 큐에 없을 수는 없다 — thread_create()가 이미 반환했으므로 자식은 READY 상태다. 그러나 자식이 CPU를 언제 얻느냐는 QEMU timer 주입 타이밍에 달려 있다.
