COW write-protect fault는 언제 page copy로 살아나나

확인 범위: 이 문서는 COW write-protect fault를 page copy 또는 writable remap으로 처리하는 일반 원리와 판단 기준을 설명하고, 제시된 로컬 PintOS 구현의 함수·metadata·테스트 흐름을 구체적 사례로 다룬다. 코드 경로와 bit·주소 계산은 본문에 제시된 구현을 기준으로 하며, 실제 동작 여부와 실행 결과·성능은 해당 저장소 버전에서 테스트와 GDB로 별도 검증해야 한다.

COW write fault 시작

fork()는 부모 프로세스의 주소 공간을 자식에게 물려준다.

그러면 처음 배우는 사람은 보통 이렇게 묻는다.

부모가 가진 모든 4KB page를 자식에게 바로 복사해야 할까?

실제 OS는 보통 그렇게 하지 않는다. 대부분의 page는 fork 직후에 읽기만 하고, 실제로 쓰는 page는 일부일 수 있기 때문이다.

copy-on-write, 줄여서 COW는 이 낭비를 줄이는 방법이다. 이름 그대로 처음에는 복사하지 않고 공유하다가, 누군가 write하려는 순간에만 복사한다.

PintOS VM 테스트에는 이 생각을 직접 묻는 파일이 있다.

tests/vm/cow/cow-simple.c

child가 large[0] = '@'를 실행할 때, 왜 page fault가 실패가 아니라 “이제 복사할 시간”이라는 신호가 될 수 있을까?

COW write fault 문제

fork() 때 모든 page를 즉시 복사하면 이해하기는 쉽다.

parent page 100개
  -> child page 100개 새로 할당
  -> 100 * 4096B memcpy

하지만 많은 프로그램은 fork() 직후 곧바로 exec()을 하거나, 부모와 자식이 대부분의 page를 읽기만 한다.

이때 즉시 복사는 낭비가 된다.

fork 직후 exec:
  복사한 100개 page 대부분을 곧 버림

fork 뒤 읽기만 함:
  부모와 자식이 같은 bytes를 따로 들고 있음

COW는 이 문제를 page table permission으로 푼다.

fork 직후:
  parent VA -> frame A, read-only처럼 보임, COW metadata 있음
  child  VA -> frame A, read-only처럼 보임, COW metadata 있음

child write:
  CPU가 write-protect page fault를 냄
  커널이 COW metadata를 확인
  frame B를 할당하고 frame A의 4KB를 복사
  child VA -> frame B, writable
  fault를 낸 store 명령 재실행

이 말은 즉, COW에서 page fault는 단순한 사고가 아니다. 커널이 일부러 걸어 둔 read-only 장치가 첫 write를 알려 주는 신호다.

COW write fault 흐름

COW는 “공유 read-only page”와 “진짜 read-only page”를 구분해야 한다.

상태 PTE 관점 커널 metadata 관점 write가 오면
code read-only page PTE_W=0 원래 writable 아님 죽여야 함
read-only mmap page PTE_W=0 또는 lazy not-present mapping writable 아님 죽여야 함
COW shared page PTE_W=0 원래 writable, 지금은 공유 중 복사 후 살릴 수 있음
normal writable page PTE_W=1 writable fault 없이 write

핵심은 PTE_W=0만 보고 판단하면 안 된다는 점이다.

PTE_W=0
  -> 진짜 read-only인가?
  -> 아니면 COW 때문에 임시로 write를 막은 것인가?

이 질문에 답하려면 page table 밖의 정보가 필요하다.

PintOS에서는 보통 SPT의 struct page, frame table, 또는 별도 COW metadata에 다음 의미를 저장한다.

이 page는 원래 writable이었는가?
현재 COW 공유 상태인가?
공유 frame의 참조 수는 몇 개인가?
write fault가 오면 새 frame으로 복사해야 하는가?

COW write fault 입력 차이

tests/vm/cow/cow-simple.c의 핵심 흐름은 짧다.

pa_parent = get_phys_addr((void*)large);

child = fork ("child");
if (child == 0) {
  pa_child = get_phys_addr((void*)large);
  CHECK (pa_parent == pa_child, "two phys addrs should be the same.");

  large[0] = '@';

  pa_child = get_phys_addr((void*)large);
  CHECK (pa_parent != pa_child, "two phys addrs should not be the same.");
  return;
}
wait (child);
CHECK (pa_parent == get_phys_addr((void*)large), "two phys addrs should be the same.");

테스트가 기대하는 상태 변화는 다음이다.

fork 전 parent:
  large VA -> frame A
  내용: "Lorem ipsum..."

fork 직후 child:
  parent large VA -> frame A
  child  large VA -> frame A
  둘의 frame identity가 같아야 함

child가 large[0] = '@':
  child write-protect fault
  child large VA -> frame B
  frame B[0] = '@'

parent wait 뒤:
  parent large VA -> frame A
  parent 내용은 여전히 "Lorem ipsum..."

여기서 get_phys_addr()라는 이름은 테스트 관점의 표현이다. PintOS의 검사 인터럽트는 pml4_get_page()로 해당 VA가 가리키는 frame identity를 얻고, page offset을 버려 비교한다. 이 테스트에서 중요한 것은 “정확한 출력 이름”보다 부모와 자식이 같은 4KB frame을 보다가 write 뒤 서로 다른 frame을 보는가다.

실제 운영체제

Linux의 fork()는 COW를 적극적으로 사용한다.

부모와 자식의 page table entry가 같은 물리 page를 가리키게 하되, private writable page는 잠시 read-only처럼 만든다. 둘 중 하나가 write하면 CPU가 protection fault를 내고, Linux 커널은 VMA와 page metadata를 보고 COW 후보인지 판단한다. 맞으면 새 page를 할당하고 내용을 복사한 뒤 write를 허용한다.

Windows는 Unix식 fork()를 일반 프로세스 생성 API로 제공하지 않는다. 보통은 CreateProcess가 새 process와 address space를 만든다. 그래도 Windows에도 image section, mapped section, private page에서 copy-on-write 개념은 존재한다.

현실 OS는 PintOS보다 훨씬 복잡하다.

  • 같은 physical page를 여러 process가 참조할 수 있다.
  • page cache, shared mapping, private mapping, file mapping을 함께 다룬다.
  • 멀티코어에서 동시에 write fault가 들어올 수 있다.
  • page reference count, reverse mapping, TLB shootdown, locking이 필요하다.

PintOS에서는 이 큰 문제를 fork(), PTE writable bit, SPT metadata, vm_handle_wp()로 줄여서 학습한다.

PintOS

현재 로컬 PintOS 저장소에는 COW가 구현되어 있다. 읽을 지점은 네 군데다.

첫째, 테스트가 COW의 기대 동작을 고정한다.

    pml4_set_page (owner->pml4, src_page->va, frame->kva, false);
}

vm_frame_add_owner (frame, dst_page, curr);

셋째, page fault 경로가 present write fault를 COW 후보로 넘긴다.

  • PintOS 저장소 상대 경로 pintos/userprog/exception.c
    • PF_P/PF_W/PF_U를 not_present/write/user로 분해한다.
  • PintOS 저장소 상대 경로 pintos/vm/vm.c
    • vm_try_handle_fault()
    • vm_handle_write_protect_fault()
    • vm_handle_wp()

vm_handle_wp()는 SPT metadata의 page->writable을 보고 COW로 살릴 수 있는 page와 진짜 read-only page를 구분한다.

RETURN_VALUE_IF (!page->writable, false);
RETURN_VALUE_IF (page->frame == NULL || page->frame->kva == NULL, false);

return vm_handle_cow (page);

넷째, vm_handle_cow()가 공유 수에 따라 copy와 remap을 나눈다.

RETURN_VALUE_IF (old_frame->ref_count > 1,
                 vm_copy_cow_page (page, old_frame));

return vm_remap_page (page, old_frame, true);

ref_count > 1이면 쓰기를 시도한 process만 새 frame을 받는다. ref_count == 1이면 더 이상 공유자가 없으므로 복사하지 않고 PTE writable만 복원한다.

  • PintOS 저장소 상대 경로 pintos/threads/mmu.c
    • pml4_set_page(pml4, upage, kpage, rw)
  • PintOS 저장소 상대 경로 pintos/include/threads/pte.h
    • PTE_P
    • PTE_W
    • PTE_U

pml4_set_page()는 rw가 true일 때만 PTE_W를 세운다.

*pte = vtop (kpage) | PTE_P | (rw ? PTE_W : 0) | PTE_U;

현재 구현의 큰 흐름은 다음과 같다.

supplemental_page_table_copy(parent -> child)
  -> anon_copy()
       -> writable resident page를 바로 memcpy하지 않음
       -> parent/child가 같은 frame을 보게 함
       -> 둘의 PTE_W를 끔
       -> vm_frame_add_owner()로 frame ref_count 증가

child write fault
  -> page_fault()
  -> not_present=false, write=true, user=true
  -> vm_try_handle_fault()
  -> vm_handle_write_protect_fault()
       -> SPT에서 page 찾기
       -> vm_handle_wp(page)
       -> page->writable 확인
       -> vm_handle_cow(page)
            -> ref_count > 1: 새 frame 할당 + 4KB copy + child PTE 교체
            -> ref_count == 1: 복사 없이 writable 복원
  -> true 반환
  -> 같은 store 명령 재실행

반대로 page->writable이 false이면 vm_handle_wp()는 false를 반환해야 한다. 그래야 pt-write-code나 read-only mmap write를 잘못 살리지 않는다.

not_present == true
  lazy load, swap in, stack growth 후보인지 검사

not_present == false && write == true
  present page write-protect fault
  -> vm_handle_write_protect_fault()
  -> page->writable이 true이면 COW 후보
  -> 진짜 read-only page이면 false

그 외
  false

이 구분이 흐려지면 0x7 COW fault와 pt-write-code, read-only mmap write를 같은 실패로 처리하거나, 반대로 모두 살려 버리는 오류가 생긴다.

QEMU

QEMU는 COW를 모른다.

QEMU가 하는 일은 x86 CPU처럼 page table permission을 검사하는 것이다.

  • target/i386/cpu.h
    • PG_RW_MASK
    • PG_ERROR_P_MASK
    • PG_ERROR_W_MASK
    • PG_ERROR_U_MASK
  • target/i386/tcg/system/excp_helper.c
    • PTE permission으로 PAGE_WRITE 가능 여부를 계산한다.
    • write가 허용되지 않으면 protection fault error code를 만든다.

QEMU의 page walk 흐름은 단순화하면 이렇다.

guest PTE에 writable bit가 없음
guest user code가 store 시도
  -> PAGE_WRITE 권한 없음
  -> do_fault_protect
  -> error_code = PG_ERROR_P_MASK | PG_ERROR_W_MASK | PG_ERROR_U_MASK
  -> guest #PF로 PintOS에 전달

그 다음은 PintOS의 일이다.

PintOS가 COW metadata를 보면:
  frame copy 후 true 반환

PintOS가 COW metadata를 못 찾으면:
  false 반환 후 kill

QEMU는 “이 read-only page가 COW 후보인지, 진짜 read-only code인지”를 판단하지 않는다. QEMU는 write permission fault를 만들어 줄 뿐이고, 의미 해석은 guest OS인 PintOS가 한다.

COW write fault 코드

1. cow-simple의 판정 기준

PintOS 저장소 상대 경로 pintos/tests/vm/cow/cow-simple.c의 전체 핵심 코드는 앞의 에 한 번만 둔다. 판정은 세 시점을 함께 본다: fork 직후 frame identity가 같은지, child의 첫 write 뒤 서로 달라지는지, wait(child) 뒤 parent가 원래 frame identity와 내용을 유지하는지 확인한다.

2. page fault handler는 write-protect

파일:

  • PintOS 저장소 상대 경로 pintos/userprog/exception.c

핵심 흐름:

not_present = (f->error_code & PF_P) == 0;
write = (f->error_code & PF_W) != 0;
user = (f->error_code & PF_U) != 0;

if (vm_try_handle_fault (f, fault_addr, user, write, not_present))
  return;

COW write는 보통 not_present == false, write == true, user == true인 경로로 들어온다.

3. vm_handle_wp()는 COW와 진짜

파일:

  • PintOS 저장소 상대 경로 pintos/vm/vm.c

핵심 위치:

RETURN_VALUE_IF (!page->writable, false);
RETURN_VALUE_IF (page->frame == NULL || page->frame->kva == NULL, false);

return vm_handle_cow (page);

현재 저장소 기준으로 이 함수는 비어 있지 않다. page->writable이 false이면 진짜 read-only write로 보고 실패시키고, true이면 vm_handle_cow()로 넘긴다.

vm_handle_cow()는 공유 수를 기준으로 두 갈래로 나뉜다.

RETURN_VALUE_IF (old_frame->ref_count > 1,
                 vm_copy_cow_page (page, old_frame));

return vm_remap_page (page, old_frame, true);

즉 COW fault를 살리는 기준은 “PTE_W가 없었다” 하나가 아니라 page->writable과 frame->ref_count까지 함께 보는 것이다.

4. PTE writable bit는 rw 인자로 정해진다

파일:

  • PintOS 저장소 상대 경로 pintos/threads/mmu.c

핵심 흐름:

*pte = vtop (kpage) | PTE_P | (rw ? PTE_W : 0) | PTE_U;

COW fork 직후에는 원래 writable page라도 rw=false처럼 page table에 넣어 첫 write를 fault로 바꾸는 전략을 쓴다.

COW write fault 값 추적

PTE bit 계산

PintOS의 pte.h 기준 주요 bit는 다음이다.

PTE_P = 0x1
PTE_W = 0x2
PTE_U = 0x4

frame base가 0x12345000이라고 하자.

일반 writable user page는 다음처럼 보인다.

PTE = 0x12345000 | PTE_P | PTE_W | PTE_U
    = 0x12345000 | 0x1 | 0x2 | 0x4
    = 0x12345007

COW fork 직후에는 같은 frame을 보되 writable bit를 끈다.

parent PTE = 0x12345000 | PTE_P | PTE_U
           = 0x12345005

child  PTE = 0x12345000 | PTE_P | PTE_U
           = 0x12345005

child가 write하면 CPU 관점의 error code는 이렇게 읽힌다.

error_code = 0x7 = 0b111

PF_P = 1 -> page는 present였음
PF_W = 1 -> write 접근 중 fault
PF_U = 1 -> user context

이 값은 demand paging의 not-present fault가 아니다. 이미 page는 있었다. 다만 write permission이 막혀 있었다.

COW 복사 뒤 계산

vm_handle_wp()가 child에게 새 frame 0x23456000을 할당했다고 하자.

old frame A = 0x12345000
new frame B = 0x23456000

memcpy(frame B, frame A, 4096)

child PTE = 0x23456000 | PTE_P | PTE_W | PTE_U
          = 0x23456007

그 뒤 같은 명령어 large[0] = '@'가 재실행된다.

before retry:
  frame B[0] = 'L'

after retry:
  frame B[0] = '@'
  frame A[0] = 'L'

그래서 child의 memcmp(buf, large, strlen(buf))는 달라지고, parent의 memcmp는 그대로 유지된다.

COW write fault GDB

현재 저장소의 VM 코드에는 COW 경로가 있으므로, 아래 breakpoint로 fork 공유와 첫 write 분리를 직접 따라갈 수 있다.

break __do_fork
break supplemental_page_table_copy
break anon_copy
break page_fault
break vm_try_handle_fault
break vm_handle_write_protect_fault
break vm_handle_wp
break vm_handle_cow
break vm_copy_cow_page
break pml4_set_page

child의 write fault에서 먼저 error code를 본다.

p/x f->error_code
p not_present
p write
p user
p/x fault_addr

기대하는 분류는 다음이다.

not_present = false
write       = true
user        = true

그 다음 COW metadata를 확인한다. 현재 구현에서 바로 볼 수 있는 핵심 필드는 page->writable, page->frame, page->frame->ref_count다.

p/x page->va
p page->frame
p page->writable
p page->frame->ref_count

테스트 명령은 다음이다.

make -C build check TESTS=tests/vm/cow/cow-simple

관찰 목표는 세 가지다.

1. fork 직후 parent/child의 large frame identity가 같다.
2. child write fault가 kill이 아니라 vm_handle_wp()로 살아난다.
3. child write 뒤 parent/child의 large frame identity가 달라지고 parent data는 유지된다.

QEMU 쪽에서 확인할 값은 guest CPU state다.

p/x $cr2

$cr2는 write fault를 낸 guest virtual address다. COW metadata와 frame reference count는 QEMU register가 아니라 PintOS 커널 메모리 안의 자료구조다.

정리

  • COW는 fork() 비용을 줄이기 위해 page를 즉시 복사하지 않고 공유한다.
  • 공유 중인 writable page는 page table에서 임시 read-only처럼 보여야 첫 write를 fault로 잡을 수 있다.
  • COW write fault는 보통 PF_P=1, PF_W=1, PF_U=1인 protection fault다.
  • 같은 protection fault라도 code page나 read-only mmap write는 죽어야 하고, COW page만 vm_handle_wp()로 살아야 한다.
  • 현재 로컬 PintOS 구현은 page->writable로 COW 후보를 가르고, frame->ref_count로 새 frame 복사와 writable remap을 나눈다.
  • QEMU는 COW를 모른다. QEMU는 PTE permission을 보고 #PF를 만들어 주고, 그 의미를 해석하는 것은 PintOS다.

COW write fault 관련 개념

  • SPT fork copy
    • fork()가 SPT page 의미를 자식에게 물려주는 흐름.
  • vm try handle fault() decision
    • PF_P/PF_W/PF_U가 fault 처리 분기로 바뀌는 지점.
  • Page Fault Error Code
    • 0x7 error code를 present write user fault로 읽는 법.
  • PTE bit
    • PTE_W가 write permission과 fault를 어떻게 만드는지.
  • TLB와 CR3
    • 부모와 자식의 address space 기준이 CR3로 분리되는 이유.
  • mmap read only Lab
    • COW와 달리 read-only file-backed mapping의 write를 죽여야 하는 기준.
