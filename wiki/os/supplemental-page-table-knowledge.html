Supplemental Page Table은 왜 필요한가

한 줄 요약: page table은 MMU가 “지금 이 VA를 어떤 PA로 번역할까”를 보는 하드웨어용 표이고, supplemental page table은 page fault handler가 “이 VA가 원래 합법인지, anon/file/uninit 중 무엇으로 frame을 준비할지”를 판단하는 커널용 의미 장부다.

SPT 필요성

CPU는 이미 page table을 보면서 가상 주소를 물리 주소로 바꾼다.

그런데 PintOS VM 과제는 왜 또 supplemental_page_table이라는 테이블을 만들라고 할까?

처음 헷갈리는 지점은 여기다.

page table은 “지금 당장 번역 가능한가?”를 위한 하드웨어용 표이고, supplemental page table은 “이 주소가 원래 어떤 의미였는가?”를 기억하는 커널용 표다.

SPT 구분

page table만 있으면 resident page, 즉 지금 물리 프레임에 올라와 있는 페이지만 잘 설명할 수 있다.

하지만 VM은 “아직 프레임은 없지만 합법적인 주소”를 많이 만든다.

  • 실행 파일의 .text/.data 페이지는 처음부터 전부 RAM에 올리지 않을 수 있다.
  • mmap으로 파일을 주소 공간에 붙여도, 실제 파일 내용은 첫 접근 때 읽어 올 수 있다.
  • 스택은 아래로 자라며, 아직 없는 페이지를 첫 write 순간에 만들어 줄 수 있다.
  • evict된 페이지는 page table에서는 빠졌지만 swap/file에는 원본이 남아 있을 수 있다.

이 상태를 page table만으로는 충분히 설명하지 못한다.

이 말은 즉, supplemental page table은 page fault handler가 “이 fault를 살릴 수 있는지” 판단하기 위한 근거 장부다.

SPT 흐름

머릿속에는 두 표를 분리해서 넣으면 된다.

표누가 주로 보는가답하는 질문
page tableCPU/MMU이 VA를 지금 어떤 PA로 번역할까?
supplemental page table커널 page fault handler이 VA는 원래 합법이고, 필요하면 어떻게 준비할까?

정상 접근 경로에서는 MMU가 page table만 보고 끝난다.

page fault가 난 뒤에야 커널이 supplemental page table을 본다.

프로세스를 시작할 때 커널은 아직 물리 프레임을 붙이지 않는다.

대신 supplemental page table에 이런 뜻의 정보를 넣는다.

프로그램이 0x8048123을 처음 읽으면 page fault가 난다.

PintOS는 fault address를 page base 0x8048000으로 내리고 supplemental page table에서 이 기록을 찾는다.

기록이 있으면 “죽일 fault”가 아니라 “살릴 fault”다.

실제 운영체제

Linux에는 vm_area_struct와 page table이 역할을 나눠 가진다.

  • vm_area_struct: 주소 범위의 의미, 권한, backing object를 설명한다.
  • page table/PTE: 현재 VA가 어떤 물리 프레임으로 번역되는지 설명한다.

Windows도 이름과 구조는 다르지만, 같은 문제를 다룬다. 프로세스 주소 공간의 영역, protection, section/file mapping, demand paging 상태를 커널 메모리 관리자에서 관리하고, 하드웨어 page table은 현재 번역 가능한 resident mapping을 담는다.

현실 OS는 PintOS보다 훨씬 복잡하다. copy-on-write, shared mapping, NUMA, huge page, page cache, working set, memory compression 같은 정책까지 들어간다.

그래도 핵심 질문은 같다.

page fault가 났을 때, 이 주소는 “원래 합법인데 아직 준비되지 않은 주소”인가, 아니면 “진짜 잘못된 주소”인가?

PintOS

PintOS에서 supplemental page table은 각 스레드, 더 정확히는 유저 프로세스의 주소 공간에 붙어 있다.

QEMU

QEMU는 supplemental page table의 의미를 모른다.

QEMU가 보는 것은 guest CPU가 접근하는 메모리와 guest page table이 만드는 하드웨어적 효과다.

파일:

  • target/i386/emulate/x86_mmu.c

대표 흐름은 이렇다.

즉 supplemental page table은 PintOS 커널의 guest memory 안에 있는 소프트웨어 자료구조다. QEMU는 그 구조체를 “SPT”라고 이해하지 않고, 그냥 guest가 읽고 쓰는 바이트로만 본다.

SPT 값 추적

page base 계산

SPT 조회 키는 보통 fault address 그대로가 아니라 page base다.

0x8048123과 0x8048fff는 같은 페이지 안의 다른 바이트다. 따라서 SPT는 둘을 같은 key 0x8048000으로 찾아야 한다.

PTE flag와 SPT metadata의 경계

여기서 가장 중요한 오해가 하나 있다.

PTE의 flag가 있으니, swap/file/lazy 상태도 PTE flag에 넣으면 되는 것 아닌가?

답은 아니다.

PTE의 낮은 12비트 flag는 CPU/MMU가 메모리 접근 순간에 빠르게 판단해야 하는 최소 상태만 담는다. PintOS 기준으로 자주 보는 flag는 다음이다.

bitPintOS 이름의미왜 필요한가
0PTE_Ppresent지금 frame에 붙어 있으면 바로 번역하고, 없으면 page fault를 낸다
1PTE_Wwritabletext/read-only/mmap/COW page에 대한 쓰기 보호를 한다
2PTE_Uuser유저 모드가 커널 전용 page에 접근하지 못하게 막는다
5PTE_Aaccessedeviction에서 최근 접근된 page인지 판단하는 힌트로 쓴다
6PTE_Ddirtyfile-backed write-back 또는 swap 저장 필요성을 판단하는 힌트로 쓴다

예를 들어 PTE가 다음 값이라고 하자.

4KB frame base는 항상 아래 12비트가 0이므로, PTE의 낮은 12비트는 flag로 쓴다.

2진수로 보면 더 분명하다.

반면 다음 정보는 PTE flag에 넣을 수 없거나, 넣더라도 커널 정책을 설명하기에 부족하다.

이 정보가 SPT의 책임이다.

SPT는 무엇을 저장하나

SPT는 page table처럼 전체 주소 공간을 [512][512][512][512]로 미리 만드는 표가 아니다. 실제로 의미 있는 page만 저장하는 sparse map이다.

기본 관계는 다음이다.

예를 들어 executable lazy page 하나는 SPT 안에서 이런 의미로 저장된다.

한 페이지 크기는 4096B이므로, 이 예시는 파일에서 1000바이트를 읽고 나머지 3096바이트를 0으로 채우는 page다.

page table의 PTE는 resident 상태가 된 뒤에야 다음 정도만 담는다.

따라서 file offset, read bytes, zero bytes 같은 복구 정보는 PTE가 아니라 SPT entry에 남아야 한다.

공통으로 필요한 필드는 보통 다음이다.

각 필드는 이런 뜻이다.

필드의미
va이 struct page가 대표하는 user virtual page의 시작 주소. SPT hash key
frame현재 RAM에 올라와 있으면 연결된 struct frame, lazy/swap/file 상태면 NULL일 수 있음
writablepage table에 mapping을 설치할 때 PTE_W를 켤지 판단하는 권한
operations현재 page가 VM_UNINIT, VM_ANON, VM_FILE 중 무엇인지와 swap_in/out/destroy 동작
hash_elemPintOS hash table에 이 page를 넣기 위한 연결자
unionpage type별 metadata를 같은 공간에 담기 위한 영역

frame이 있다는 것은 page table에도 present mapping이 있을 가능성이 높다는 뜻이다. 하지만 frame이 붙은 뒤에도 SPT entry는 보통 계속 남아 있어야 한다. eviction, fork, munmap, exit, swap-in 같은 작업에서 이 page의 원래 의미를 다시 알아야 하기 때문이다.

union은 왜 필요한가

struct page는 모든 page의 공통 껍데기다. 하지만 page 종류마다 추가로 기억해야 할 정보가 다르다.

한 page는 동시에 세 종류가 아니다.

그래서 PintOS는 union을 제공한다.

union은 멤버 중 가장 큰 구조체가 들어갈 만큼의 공간만 확보하고, 그 공간을 현재 page type에 맞게 해석한다.

현재 어떤 멤버를 써야 하는지는 operations와 page_get_type(page)가 알려준다.

전체 mmap() 요청 길이 자체를 모든 SPT entry에 저장할 필요는 없다. SPT entry 하나는 4KB page 하나를 설명한다. 전체 mapping 범위가 필요하면 별도의 mmap_region list를 둘 수 있고, 단순 구현에서는 page별 SPT entry를 순회하거나 시작 주소부터 page 단위로 검사할 수 있다.

hash로 구현할 때

PintOS에서는 SPT를 hash table로 구현하는 것이 가장 현실적이다.

이유는 SPT의 가장 흔한 연산이 단일 page lookup이기 때문이다.

구현 모양:

lookup은 임시 struct page를 만들어 같은 key로 찾는다.

여기서 pg_round_down()이 중요하다.

page 크기를 벗어난 주소는 다른 page base가 되므로 자연스럽게 다른 hash key로 간다.

tree로 구현할 때

SPT를 tree로 만들 수도 있다. 예를 들어 red-black tree나 B+ tree를 쓰면 주소 순서와 range query가 좋아진다.

정리

supplemental page table은 하드웨어 page table의 대체물이 아니다.

page table은 빠른 주소 번역을 위한 표이고, supplemental page table은 page fault를 해석하기 위한 커널의 의미 장부다.

PintOS에서는 이 장부를 직접 설계해야 한다. 핵심은 page-rounded VA로 struct page를 찾고, 그 페이지가 anon/file/uninit 중 무엇인지에 따라 frame을 준비한 뒤 page table mapping을 설치하는 것이다.
