스택 성장 페이지 폴트는 언제 살려야 하나

한 줄 요약: PintOS는 USER_STACK 아래 한 페이지만 처음 매핑하므로 깊은 호출이나 큰 지역 배열은 아직 매핑되지 않은 낮은 주소를 건드려 page fault를 낸다. 이 fault가 정상 스택 접근으로 보이면 새 페이지를 붙여 살리고, 아니면 죽이는 판단 기준을 정리한다.

스택 성장 이유

예를 들어 PintOS VM 테스트에는 이런 코드가 있다.

이 배열은 유저 스택에 놓인다. Project 2까지의 PintOS가 처음부터 매핑하는 스택 영역은 USER_STACK 바로 아래의 한 페이지뿐이다. 따라서 함수 호출이 깊어지거나 큰 지역 변수를 사용하면 프로그램이 그보다 낮은 주소까지 스택으로 쓰려고 할 수 있다. 아직 매핑되지 않은 주소라면 이 접근에서 page fault가 발생한다.

그렇다고 이 fault가 반드시 프로그램을 종료해야 하는 버그인 것은 아니다. 운영체제가 정상적인 스택 접근이라고 판단하면 새 페이지를 붙인 뒤 프로그램을 계속 실행할 수 있다.

스택 성장 폴트 필요성

스택은 위에서 아래로 자란다.

스택 top이 0x47480000이면 첫 페이지는 보통 다음 범위에 놓인다.

프로그램이 더 많은 스택을 사용하면 그 아래 페이지도 필요해진다.

하지만 모든 주소의 fault를 스택 성장으로 처리해서는 안 된다. 0x1000 같은 엉뚱한 포인터 접근까지 새 스택으로 받아들이면 메모리 보호가 무너진다.

따라서 stack growth에서는 다음 질문에 답해야 한다.

이 fault 주소는 “스택이 조금 더 필요해진 정상 접근”인가, 아니면 “잘못된 포인터 접근”인가?

스택 성장 폴트 흐름

스택 성장 page fault는 세 가지 정보를 함께 보고 판단한다.

정보어디서 오는가묻는 질문
fault_addrCPU의 CR2어떤 가상 주소 때문에 fault가 났나?
rspstruct intr_frame 또는 thread에 저장한 유저 rsp유저 스택 포인터 근처에서 난 fault인가?
USER_STACK과 한계 크기PintOS 상수와 과제 정책스택으로 허용된 주소 범위 안인가?

판단 흐름은 다음과 같다.

flowchart TD
    PF["#PF 발생<br/>fault_addr = CR2"] --> NP{"not_present?"}
    NP -->|"No (protection)"| KILL["프로세스 종료"]
    NP -->|"Yes"| SPT{"SPT에서<br/>page 검색?"}
    SPT -->|"있음"| CLAIM["vm_do_claim_page()<br/>lazy/anon/file claim"]
    SPT -->|"없음"| STK{"스택 성장<br/>조건 충족?"}
    STK -->|"fault_addr ≥ rsp - 8<br/>USER_STACK - 1MB ≤ addr"| GROW["vm_stack_growth()<br/>새 anon page 할당"]
    STK -->|"조건 불충족"| KILL

not_present/write/user가 PF_P/PF_W/PF_U에서 어떻게 나오는지는 페이지 폴트 error code에서 따로 분해한다.

fault_addr와 rsp는 서로 다른 역할을 한다.

  • fault_addr: 실제로 접근하다 실패한 주소
  • rsp: 그 순간 유저 코드가 “내 스택의 현재 경계”라고 생각하던 주소

스택 성장은 두 주소의 거리가 너무 멀지 않을 때만 허용한다.

스택 성장 폴트 예시

USER_STACK = 0x47480000이고 현재 rsp = 0x4747f010이라고 하자.

살릴 수 있는 접근

fault_addr는 rsp - 8이다. x86-64의 push 계열 동작은 스택 포인터를 8바이트 낮춘 위치에 값을 저장할 수 있으므로, 이런 접근은 스택 접근으로 볼 수 있다.

죽여야 하는 접근

이 주소는 현재 rsp보다 한 페이지 아래에 있다. PintOS 테스트 pt-grow-bad.c도 movq -4096(%rsp), %rax처럼 4096바이트 아래를 읽는 접근은 종료되어야 한다고 확인한다.

실제 운영체제

현실 OS도 필요할 때 스택을 확장하지만, 판단 기준은 PintOS보다 훨씬 복잡하다.

Linux는 프로세스 주소 공간의 VMA, guard page, RLIMIT_STACK, signal delivery, thread별 stack 같은 정보를 함께 본다. 많은 GNU/Linux 환경에서는 기본 stack limit이 8MB로 잡히지만, 배포판과 설정에 따라 달라질 수 있다.

Windows도 thread stack에 reserved 영역과 committed 영역을 두고, guard page를 밟으면 다음 페이지를 commit하는 방식으로 스택 성장을 처리한다.

두 OS 모두 스택의 자동 성장을 허용하되, 무한히 확장하거나 아무 주소나 스택으로 받아들이지는 않는다.

PintOS

PintOS KAIST Project 3 문서는 Project 2에서는 USER_STACK부터 시작하는 한 페이지 스택만 있었고, Project 3에서는 스택이 현재 크기를 넘어가면 필요한 페이지를 추가해야 한다고 설명한다.

일반적으로 판단 조건은 다음과 같이 잡는다.

KAIST 문서도 vm_try_handle_fault()에서 stack growth 여부를 식별하고, 가능하면 vm_stack_growth()를 호출하라고 안내한다. vm_stack_growth()는 addr을 PGSIZE 단위로 내린 뒤 그 주소에서 더 이상 fault가 발생하지 않도록 anonymous page를 할당해야 한다.

유저 rsp를 어디서 가져오는지는 fault가 발생한 시점에 따라 달라진다. 유저 코드 실행 중 page fault가 발생해 곧바로 커널로 들어왔다면 page_fault()가 받은 struct intr_frame의 rsp가 유저 스택 포인터다. 반면 커널이 syscall을 처리하며 유저 포인터를 읽다가 page fault를 냈다면 CPU는 이미 커널 모드에 있었다. 이때는 f->rsp를 유저 스택 포인터로 볼 수 없다. 이런 경우까지 처리하려면 syscall 진입 시점의 유저 rsp를 struct thread 같은 곳에 따로 저장하고, kernel-mode fault에서는 그 값을 기준으로 stack growth 후보를 판단해야 한다.

QEMU

QEMU는 “이 주소가 스택인지” 판단하지 않는다.

QEMU는 x86 하드웨어처럼 guest virtual address를 guest physical address로 번역한다. 번역에 실패하면 page fault 예외를 guest인 PintOS에 전달한다.

QEMU 코드에서는 이런 흐름을 볼 수 있다.

  • target/i386/emulate/x86_mmu.c
    • mmu_gva_to_gpa()
    • x86_write_mem_ex()
    • x86_read_mem_ex()
  • target/i386/machine.c
    • page fault payload를 env->cr[2]로 옮기는 로직

쓰기 접근에서 변환이 실패하면 QEMU는 fault 주소를 exception payload로 저장하고 EXCP0E_PAGE를 raise한다. 읽기 접근 경로에서는 env->cr[2] = gva로 fault 주소를 guest CR2에 둔다.

따라서 PintOS의 page_fault()가 보는 CR2 값은 QEMU가 흉내 낸 guest CPU 상태의 일부다. 다만 해당 fault를 스택 성장으로 살릴지는 QEMU가 아니라 PintOS가 결정한다.

스택 성장 폴트 값 추적

1. 1MB 한계는 몇 페이지인가

USER_STACK = 0x47480000이면 PintOS Project 3의 허용 스택 하한은 다음처럼 계산할 수 있다.

따라서 스택 후보 주소는 대략 다음 범위 안에 있어야 한다.

2. fault_addr를 page base로 내리기

vm_stack_growth()는 0x4747eff8이라는 한 바이트만 처리하는 것이 아니라 0x4747e000부터 시작하는 4096바이트 페이지를 준비해야 한다.

3. PUSH 때문에 rsp - 8을 허용하는 이유

현재 rsp = 0x4747f000이라고 하자.

x86-64 PUSH는 스택 포인터를 조정하는 과정에서 현재 rsp보다 8바이트 낮은 주소에 접근할 수 있다. 따라서 fault_addr >= rsp - 8과 같은 여유가 필요하다.

반대로 rsp - 4096은 한 페이지 아래에 있다. PintOS의 pt-grow-bad는 이 접근을 스택 성장으로 살려서는 안 된다고 확인한다.

정리

스택 성장 page fault는 가능한 한 많은 page fault를 살리는 기능이 아니다. CR2의 fault_addr, 유저 rsp, USER_STACK, 1MB 한계와 page base 계산을 함께 살펴 스택 접근으로 볼 수 있는 not-present fault만 처리해야 한다.

PintOS에서는 vm_try_handle_fault()가 이 조건을 판단하고, vm_stack_growth()와 vm_claim_page()가 실제 페이지 준비로 이어진다. QEMU는 이 정책에 관여하지 않고 guest CPU의 page fault 이벤트만 PintOS에 전달한다.

스택 성장 폴트 점검

  • 살릴 수 있는 fault는 “스택 근처의 not-present fault”다. fault_addr, 유저 rsp, USER_STACK, 1MB 한계를 함께 봐야 한다.
  • SPT에 이미 등록된 lazy/anon/file page는 stack growth가 아니라 claim 경로로 처리한다.
  • rsp - 8 근처 접근은 push 같은 x86-64 스택 동작 때문에 허용할 수 있지만, rsp - 4096처럼 한 페이지 아래 접근은 보통 잘못된 포인터로 본다.
  • QEMU는 page fault 이벤트와 레지스터 효과를 재현할 뿐, 이 주소를 스택으로 살릴지 결정하지 않는다. 그 정책은 PintOS의 vm_try_handle_fault()가 가진다.
