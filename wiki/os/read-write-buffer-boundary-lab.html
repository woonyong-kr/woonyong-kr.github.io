read/write 버퍼 경계 검증 Lab

확인 범위: 이 문서는 read/write 버퍼 검증의 일반 원리와 선택 기준을 설명하고, 입력에 제시된 PintOS·QEMU 코드 구조를 바탕으로 검증 범위와 권한 차이를 분석한다. 다만 실제 테스트 통과 여부, 특정 버전의 동작, GDB·QEMU 실행 기록과 성능은 검증 결과로 확정하지 않으며 별도의 실행과 측정이 필요하다.

그렇다면 커널의 검증도 똑같이 해도 될까

read(fd, buffer, size)와 write(fd, buffer, size)는 인자 모양이 비슷하다. 둘 다 buffer와 size를 받는다.

그렇다면 커널의 검증도 똑같이 해도 될까?

핵심 차이는 방향이다.

이 말은 즉, write()의 버퍼는 “읽을 수 있는 유저 구간”이어야 하고, read()의 버퍼는 “쓸 수 있는 유저 구간”이어야 한다.

꼬리 질문

이번 Lab은 다음 질문을 따라간다.

  • 왜 read()는 유저 포인터를 읽는 syscall이 아니라 유저 메모리에 쓰는 syscall일까?
  • page 경계를 넘는 버퍼는 왜 시작 주소 하나만 검사하면 부족할까?
  • read-boundary와 write-boundary 테스트는 무엇을 확인할까?
  • 현재 PintOS 코드에서 write()와 read()의 검증 범위는 어디가 다를까?
  • read-only code page에 read()로 쓰려 하면 왜 단순 present 검사만으로 부족할까?
  • QEMU는 page 경계를 넘는 접근을 어떤 단위로 나누어 pf를 재현할까?
  • GDB에서는 어떤 주소와 PTE bit를 보면 확인할 수 있을까?

read/write 버퍼 경계 검증 오해

시스템 콜에서 유저 버퍼를 다루는 순간 커널은 유저 프로세스 주소 공간을 대신 만진다. 여기서 실수하면 두 종류의 문제가 생긴다.

위험예시잘못된 결과
range 검증 부족시작 page만 mapped, 다음 page는 unmapped뒤쪽 바이트에서 kernel context page fault
방향 검증 부족read()가 read-only code page에 쓰기present는 맞지만 write 권한 위반
커널 주소 허용유저가 kernel address를 buffer로 전달유저가 커널 메모리 접근을 커널에게 시킴

초보자가 헷갈리기 쉬운 지점은 이것이다.

read()라는 이름만 보면 커널이 유저 버퍼를 읽는 것 같지만, 실제로는 파일에서 읽은 데이터를 유저 버퍼에 써 준다. 그래서 read()의 buffer 검증은 copy_to_user 성격을 가진다.

read/write 버퍼 경계 검증 상태

유저 버퍼 검증은 세 질문으로 나누어 생각하면 된다.

write()는 대체로 “유저 메모리에서 커널로 복사”다. 그래서 유저 버퍼가 읽기 가능해야 한다.

read()는 대체로 “커널에서 유저 메모리로 복사”다. 그래서 유저 버퍼가 쓰기 가능해야 한다.

read/write 버퍼 경계 검증 입력 차이

PintOS userprog 테스트에는 page 경계를 일부러 건드리는 도우미가 있다.

  • SW_AI-W11-pintos/pintos/tests/userprog/boundary.c
    • get_boundary_area()
    • copy_string_across_boundary()

핵심 아이디어는 8192바이트짜리 정적 배열 안에서 page boundary를 찾는 것이다.

그 다음 read-boundary는 boundary 앞에서 시작하는 buffer에 파일 내용을 읽어 온다.

write-boundary는 boundary를 가로지르는 문자열을 파일에 쓴다.

두 테스트의 목표는 “page 경계를 넘는 정상 버퍼는 성공해야 한다”다. 경계를 넘는다는 이유만으로 죽이면 안 되고, 경계를 넘는 모든 page가 유효한지 확인해야 한다.

실제 운영체제

Linux 커널 관점에서 write(fd, user_buf, len)은 user buffer에서 kernel/file 쪽으로 데이터를 가져오는 흐름이다. 그래서 copy_from_user()식 안전 복사가 핵심이다.

반대로 read(fd, user_buf, len)은 kernel/file 쪽 데이터를 user buffer로 내보내는 흐름이다. 그래서 copy_to_user()식 안전 복사가 핵심이다.

Windows도 같은 문제를 갖는다. Win32 API의 ReadFile/WriteFile 이름은 애플리케이션 관점이고, 커널/드라이버는 요청 버퍼가 유저 주소인지, 접근 권한이 맞는지, I/O manager가 어떤 방식으로 버퍼를 전달했는지에 맞춰 검증한다.

현실 OS는 PintOS보다 더 복잡하다.

  • page가 현재 없더라도 demand paging으로 살릴 수 있다.
  • read-only mapping, copy-on-write, shared mmap을 구분해야 한다.
  • 실패를 -EFAULT, signal, structured exception, 프로세스 종료 등으로 정책화해야 한다.
  • 다중 CPU와 비동기 I/O 중에도 버퍼 lifetime을 다뤄야 한다.

PintOS

현재 PintOS 저장소의 write()는 버퍼 전체 page range를 확인한다.

파일:

  • SW_AI-W11-pintos/pintos/userprog/syscall.c

흐름:

check_user_buffer()는 size == 0이면 바로 통과하고, 아니면 시작 주소와 마지막 주소를 확인한 뒤 page base를 하나씩 검사한다.

반면 현재 read()는 시작 주소만 확인한다.

이 차이는 학습 포인트다. read-boundary처럼 양쪽 page가 모두 정상 mapped인 테스트는 통과할 수 있다. 하지만 시작 page만 유효하고 뒤쪽 page가 unmapped인 버퍼라면, file_read() 아래의 inode_read_at()이 memcpy(buffer + bytes_read, ...)로 뒤쪽 page에 쓰는 순간 pf가 날 수 있다.

또 하나의 포인트는 권한이다. check_address()는 pml4_get_page()가 null인지로 present mapping만 본다. read-only code page처럼 present는 맞지만 쓰기 권한이 없는 page에 read()가 쓰려 하면, 단순 present 검사는 충분하지 않다.

QEMU

QEMU는 PintOS의 syscall 정책을 모른다. QEMU가 하는 일은 guest CPU와 guest MMU가 해야 할 일을 재현하는 것이다.

QEMU의 x86 memory helper는 page 경계를 넘는 접근을 한 번에 처리하지 않고 page 안에서 복사 가능한 크기만큼 잘라서 변환한다.

파일:

  • target/i386/emulate/x86_mmu.c

핵심 모델:

따라서 첫 page는 성공하고 둘째 page에서 실패하는 상황이 자연스럽게 생긴다. PintOS가 syscall 앞에서 range 전체를 검사하지 않으면, QEMU는 하드웨어처럼 두 번째 page 접근에서 page fault를 보여준다.

쓰기 접근 실패에서는 pf error code의 write bit가 켜진다. 중요한 점은 kernel이 유저 버퍼에 쓰다가 fault가 나면 CPU 관점에서는 kernel context fault로 보일 수 있다는 것이다. 그래서 syscall 진입부에서 미리 “이 유저 버퍼 전체에 써도 되는가”를 확인하는 습관이 필요하다.

관찰 결과

이번 Lab에서 코드만 읽어도 얻을 수 있는 결론은 다음과 같다.

관찰결론
write()는 check_user_buffer(buffer, size)를 호출한다page boundary를 넘는 구간 전체를 의식한다
read()는 check_address(buffer)만 호출한다시작 주소와 전체 range 검증이 다르다는 점을 보여준다
inode_read_at()은 memcpy(buffer + bytes_read, ...)를 호출한다read()의 user buffer는 커널이 쓰는 대상이다
pml4_get_page()는 present mapping이면 kernel VA를 돌려준다writable 권한 검사는 별도로 생각해야 한다
QEMU x86_mmu.c는 page 안에서 복사 가능한 크기만큼 나눈다첫 page 성공, 다음 page pf가 자연스럽다

이 관찰은 “테스트가 통과했다”와 “검증 모델이 충분하다”가 다르다는 점도 알려준다. read-boundary는 정상 경계 버퍼를 통과시키는 테스트이고, 시작 page만 mapped된 비정상 경계 버퍼까지 모두 막는지는 별도의 실험/구현 점검이 필요하다.

정리

read()와 write()는 이름보다 데이터 방향으로 이해해야 한다.

PintOS에서는 이 복잡한 현실을 check_address(), check_user_buffer(), pml4_get_page(), PTE bit 확인 같은 작은 코드로 배운다. QEMU는 이 정책을 대신 결정하지 않고, guest page table과 permission 위반을 CPU 예외처럼 보여준다.

read/write 버퍼 경계 검증 관련 개념

  • 유저 포인터 안전 복사
    • 유저 포인터를 커널 포인터처럼 믿으면 안 되는 이유
  • read buffer writable PTE
    • read() destination buffer가 present일 뿐 아니라 writable인지 판단하는 기준
  • 유저 포인터 검증
    • syscall 인자에서 page table 검사까지 내려가는 흐름
  • syscall 전체 흐름
    • RDI/RSI/RDX에 syscall 인자가 들어오는 과정
  • PTE bit
    • PTE의 present/write/user/accessed/dirty bit 의미
  • Page Fault Error Code
    • pf error code에서 read/write/user context를 해석하는 법
  • User Programs 실행 경계
    • User Programs 전체
