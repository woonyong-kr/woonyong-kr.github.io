실행 파일 쓰기 금지

실행 파일 쓰기 금지

한 줄 요약: 실행 중 프로세스의 ELF 원본이 다른 fd로 덮어써지면 안 되는 이유와 file_deny_write() 흐름을 확인하는 실험.

실행 파일 쓰기 금지 흐름

실행 중인 프로세스의 ELF 파일은 코드의 원본이다. 다른 fd가 같은 inode를 덮어쓸 수 있으면 아직 로드하지 않은 code page가 오염될 수 있다. PintOS는 file_deny_write() → inode->deny_write_cnt로 이 보호를 구현하며, 실행 파일 handle을 process lifetime 동안 보관하여 deny를 유지해야 한다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

CPU/MMU는 “이 page의 원본이 디스크 파일인가”를 모른다. 하드웨어가 아는 것은 PTE의 present/writable/user 비트뿐이다. “실행 중인 파일에 쓰면 안 된다”는 정책은 순수하게 OS의 파일 시스템 계층에서 강제한다.

단, VM 이후에는 하드웨어와의 관계가 깊어진다. 실행 파일 page를 lazy loading하는 경우, page fault 시점에 file_read_at()으로 원본 파일을 읽는다. 이때 원본 파일이 중간에 변경되었다면 로드되는 code bytes가 달라진다.

Linux에서 실행 중인 파일에 대해 쓰기 open하면 ETXTBSY가 반환된다. 하지만 unlink 후 같은 이름으로 새 파일을 만들 수 있다 — 기존 프로세스는 원래 inode를 계속 참조한다. PintOS는 deny_write_cnt 정수 하나로 이 복잡성을 축소한다.

PintOS 구현

PintOS의 deny write 메커니즘은 세 층으로 나뉜다:

  file["Layer 2: File<br/>filesys/file.c<br/>file_deny_write(): file-&gt;deny_write = true<br/>file_deny_write(): inode_deny_write(inode)<br/>file_allow_write(): file-&gt;deny_write = false<br/>file_allow_write(): inode_allow_write(inode)"]
  inode["Layer 3: Inode<br/>filesys/inode.c<br/>inode-&gt;deny_write_cnt++ / --<br/>inode_write_at(): cnt &gt; 0 -&gt; return 0"]
  process --> file
  file --> inode

QEMU 에뮬레이션

QEMU는 “이 inode가 실행 파일인가”를 모른다. 쓰기 금지 정책은 PintOS의 파일 시스템 계층에서 완결된다.

%% deny write 여부와 QEMU write 도달
flowchart TD
  start["write(fd, buf, 16)"]
  inode_write["PintOS<br/>inode_write_at()"]
  denied["deny_write_cnt &gt; 0<br/>return 0"]
  no_disk["disk_write() 호출 없음<br/>QEMU IDE write 없음"]
  allowed["deny_write_cnt == 0<br/>sector 계산 진행"]
  disk["disk_write(filesys_disk, sector, bounce)"]
  guest_ide["guest IDE port access"]
  qemu["qemu"]
  start --> inode_write
  inode_write --> denied
  denied --> no_disk
  inode_write --> allowed
  allowed --> disk
  disk --> guest_ide
  guest_ide --> qemu

따라서 QEMU IDE write breakpoint가 잡힌다면 PintOS가 위쪽에서 쓰기를 막지 못한 것이다.

실행 파일 쓰기 금지 값 추적

rox-simple의 16바이트 write

buffer size    = 16 bytes
expected write = 0 bytes (deny_write_cnt > 0)

deny_write가 없다고 가정한 sector 계산:
  DISK_SECTOR_SIZE = 512 bytes
  write offset     = 0 (파일 시작부터)
  sector_ofs       = 0 % 512 = 0
  chunk_size       = min(16, 512) = 16

  실제 I/O (bounce buffer 경로):
    disk_read(sector_idx, bounce)     // 512 bytes 읽기
    memcpy(bounce + 0, buffer, 16)    // 16 bytes 덮어쓰기
    disk_write(sector_idx, bounce)    // 512 bytes 쓰기

  deny_write_cnt > 0이면:
    inode_write_at() 첫 줄에서 return 0
    위 I/O 전혀 발생하지 않음

recursive child의 counter 변화

child-rox 5 시작  → deny_write_cnt = 1
child-rox 4 시작  → deny_write_cnt = 2
child-rox 3 시작  → deny_write_cnt = 3
child-rox 2 시작  → deny_write_cnt = 4
child-rox 1 시작  → deny_write_cnt = 5

child-rox 1 exit  → deny_write_cnt = 4  (write → 0)
child-rox 2 exit  → deny_write_cnt = 3  (write → 0)
child-rox 3 exit  → deny_write_cnt = 2  (write → 0)
child-rox 4 exit  → deny_write_cnt = 1  (write → 0)
child-rox 5 exit  → deny_write_cnt = 0  (이후 write 가능)

file object와 inode의 관계

%% file object와 inode 관계
flowchart LR
  loader["loader handle (L)<br/>struct file L<br/>L.deny_write = true"]
  user_fd["유저 open handle (U)<br/>struct file U<br/>U.deny_write = false"]
  inode["inode I<br/>open_cnt = 2 (L + U)<br/>deny_write_cnt = 1 (L만)"]
  write["U로 write 시도<br/>file_write(U, buf, size)"]
  loader --> inode
  user_fd --> inode
  user_fd --> write
  inode --> write

유저 handle U는 deny_write = false여도 loader handle L과 같은 inode를 가리킨다. 따라서 쓰기 허용 여부는 handle별 플래그가 아니라 inode의 카운터로 결정된다.
