fork하면 fd table은 어떻게 복제되는가

한 줄 요약: fork 시 부모가 열어 둔 fd를 자식이 어떻게 공유·복제하는지 정리.

fd table fork 복제 쟁점 

int fd = open ("sample.txt");
pid_t pid = fork ();

if (pid == 0) {
  read (fd, child_buf, 10);
  close (fd);
} else {
  wait (pid);
  read (fd, parent_buf, 10);
}

이 코드를 보면 두 가지 질문이 생긴다.

  • 자식이 close(fd)하면 부모의 fd도 닫힐까?
  • 자식이 read(fd, ...)로 파일 위치를 움직이면 부모의 파일 위치도 같이 움직일까?

두 질문에 답하려면 먼저 fd의 의미를 구분해야 한다. fd는 “파일 그 자체”가 아니라 현재 프로세스의 fd table index다. 따라서 자식이 close(fd)해도 부모의 fd table entry가 직접 지워지지는 않는다. 반면 파일 위치가 함께 움직이는지는 부모와 자식의 fd entry가 어떤 열린 파일 상태를 가리키는지에 따라 달라진다.

fork가 fd table을 복제하는 이유

fork()는 실행 흐름을 하나 더 만드는 시스템 콜이다. 하지만 실행 흐름만 복제해서는 기존 프로그램의 I/O 상태를 이어갈 수 없다.

프로그램은 이미 열린 파일, 표준 입출력, 현재 작업 중인 파일 위치를 가진 채 실행되고 있을 수 있다. 자식 프로세스가 부모의 열린 파일을 전혀 보지 못하면 fork() 뒤 exec()로 CGI 프로그램을 실행하거나 표준 출력 리다이렉션을 물려주는 패턴이 깨진다.

그렇다고 모든 커널 객체를 구분 없이 공유할 수도 없다. 파일 위치와 닫기, 쓰기 금지 같은 상태가 부모와 자식에게 어떻게 보이고 언제까지 유지되는지 정해야 한다. 따라서 fork()의 fd 복제는 값을 단순히 복사하는 작업이 아니라, 프로세스별 fd table과 열린 파일 상태의 공유 범위 및 수명을 정하는 경계다.

fd를 따라가는 세 경계

fd는 fd number → process별 fd_table slot → 열린 파일 상태 → inode 순서로 읽어야 한다. Linux의 일반적인 fork 모델에서는 부모와 자식의 entry가 같은 open file description을 참조하므로 offset과 file status flag를 공유한다.

현재 local PintOS의 동작은 다르다. file_duplicate()가 같은 inode를 다시 열고 pos 값을 복사한 별도의 struct file을 만든다. 부모와 자식은 같은 fd number와 fork 순간의 offset을 갖지만, 그 뒤의 offset은 독립적으로 움직인다. 두 구조는 아래 에서 비교한다.

파일 위치가 달라지는 장면

sample.txt의 처음 20바이트를 부모가 읽은 뒤 fork()한다고 하자.

int fd = open ("sample.txt");
read (fd, buf, 20);      // parent의 pos = 20
pid_t pid = fork ();
시점 parent struct file A child struct file B 공유되는 것
fork 직후 pos=20 pos=20 fd number와 sample.txt inode
child가 10 B read 후 pos=20 pos=30 inode와 파일 내용

이 PintOS 구현에서 child의 read는 별도 객체 B의 offset만 전진시킨다. parent의 객체 A는 20을 유지한다. 이 흐름은 PintOS 테스트 fork-read가 기대하는 동작과 맞는다.

실제 운영체제와의 차이

Linux에서 fork()는 자식에게 부모 fd table의 복사본을 준다. 그러나 각 fd entry는 보통 같은 open file description을 가리킨다.

부모와 자식이 같은 open file description A(offset 20)를 참조한다면 child가 10 B를 읽었을 때 A의 offset은 30이 된다. 이후 parent도 30부터 읽는다. 이 공유 규칙은 shell redirection, pipe, CGI 서버, dup2() 같은 패턴의 기반이 된다.

execve()는 주소 공간과 프로그램 이미지를 바꾸지만 fd는 기본적으로 유지한다. 단, close-on-exec 플래그가 켜진 fd는 execve() 경계에서 닫힌다.

Windows는 Unix식 fork()를 기본 모델로 사용하지 않는다. CreateProcess를 호출할 때 어떤 handle을 상속할지 정하거나 DuplicateHandle로 handle을 명시적으로 복제한다. 따라서 Windows의 동작을 Linux처럼 “fork가 자동으로 fd table을 복제한다”라고 설명하면 맞지 않는다.

두 운영체제에는 공통점도 있다. 부모와 자식 사이에 I/O 대상을 넘길 때 유저 프로그램은 커널 객체 주소를 직접 받지 않는다. 대신 OS가 관리하는 간접 식별자인 fd 또는 handle을 받는다.

PintOS의 복제 과정

이 저장소의 PintOS에서 fork syscall은 syscall_handler() → process_fork() → __do_fork() → duplicate_fd_table() 순서로 내려간다. parent는 child tid를 반환받고 child는 0을 반환받는다. 상세 호출과 fd별 loop는 아래 Mermaid에서 확인할 수 있다.

duplicate_fd_table()의 구현은 다음과 같은 선택을 한다.

for fd = 2; fd < parent->next_fd && fd < FD_MAX; fd++:
  if parent->fd_table[fd] == NULL:
    continue
  curr->fd_table[fd] = file_duplicate(parent->fd_table[fd])

curr->next_fd = parent->next_fd

file_duplicate()는 부모의 struct file *를 자식의 table에 그대로 넣지 않는다.

file_duplicate(file)
  -> inode_reopen(file->inode)
  -> file_open(...)
  -> nfile->pos = file->pos
  -> deny_write 상태도 필요하면 복사

따라서 부모와 자식의 fd 번호가 같더라도 struct file 객체는 서로 다르다. 두 객체는 같은 inode를 보지만, 파일 위치 pos는 fork 순간의 값을 복사한 뒤 각각 움직인다.

process_exec()의 동작도 함께 볼 필요가 있다. 이 함수는 process_cleanup()으로 기존 주소 공간을 정리하고 새 ELF를 로드하지만 fd table은 닫지 않는다. 따라서 fork()로 만들어진 자식이 곧바로 exec()를 호출해도 fd table은 유지된다.

PintOS 테스트 multi-child-fd와 child-close는 이 흐름을 확인한다.

  • PintOS 저장소 상대 경로 pintos/tests/userprog/multi-child-fd.c
  • PintOS 저장소 상대 경로 pintos/tests/userprog/child-close.c

현재 구현에는 별도로 살펴볼 경계도 있다. 중간 fd를 닫아 next_fd가 낮아진 상태에서 더 큰 fd가 아직 열려 있다면 duplicate_fd_table()은 그 fd를 보지 못한다. 예를 들어 fd 2, 3, 4를 연 뒤 fd 3만 닫고 바로 fork()하면, 현재 코드에서는 fd 4가 자식에게 복제되지 않는다.

QEMU가 담당하는 범위

QEMU는 fd_table[4]가 무엇을 뜻하는지 해석하지 않는다.

PintOS 커널이 guest memory 안의 struct thread와 fd_table 포인터 배열을 읽고 쓴다. QEMU는 그 메모리 접근과 CPU 명령 실행을 에뮬레이션한다.

두 fd는 다음처럼 구분된다.

PintOS guest fd
  - guest OS 내부 fd table index
  - syscall_handler와 process.c가 의미를 해석

QEMU host fd
  - QEMU 프로세스가 host 파일, 디스크 이미지, socket 등을 열 때 쓰는 fd
  - guest fd와 같은 번호 체계가 아님

파일 내용이 디스크까지 내려갈 때 QEMU의 장치 모델이 등장한다.

PintOS file_read/file_write
  -> inode_read_at/inode_write_at
  -> disk_read/disk_write
  -> QEMU IDE device model
  -> QEMU BlockBackend
  -> host backing file

따라서 fork()의 fd table 복제 정책은 QEMU가 아니라 PintOS가 정한다.

fork() 뒤 fd가 보이는가 Linux는 보통 보인다. Windows는 명시적 handle 상속/복제 모델 duplicate_fd_table()로 보이게 만든다 guest fd 의미를 모름
열린 파일 상태 공유 Linux는 같은 open file description을 공유 새 struct file을 만들고 pos를 복사 해당 없음
자식 close(fd)의 효과 자식 fd table slot만 제거, 공유 객체 refcount 감소 자식의 별도 struct file을 닫음 guest memory 변화만 저장
파일 위치 pos Linux는 공유될 수 있음 fork 시점 값만 복사, 이후 독립 해당 없음
exec() 뒤 fd 기본 유지, close-on-exec이면 닫힘 process_exec()에서 fd table을 닫지 않으므로 유지 해당 없음
교육용 단순화 refcount, fd flags, CLOEXEC, VFS, pipe/socket 등 복잡 파일 중심, fd_table 한 페이지, file_duplicate() 중심 OS 정책 없음

특히 pos의 차이를 주의해야 한다. PintOS 테스트를 근거로 “fork 후 fd는 항상 독립적인 파일 위치를 가진다”고 일반화할 수는 없다. 파일 위치가 독립적인 것은 이 PintOS 구현의 선택이며, Linux의 일반적인 fork fd 공유 모델과 다르다.

코드에서 복제 흐름 따라가기

1) syscall 번호가 fork 흐름으로 들어간다

파일:

  • PintOS 저장소 상대 경로 pintos/userprog/syscall.c

핵심 흐름:

case SYS_FORK:
  f->R.rax = fork ((const char *) f->R.rdi, f);
  break;

RDI에는 자식 이름 문자열 포인터가 들어간다. syscall 진입 시점의 struct intr_frame *f도 process_fork()까지 전달된다.

2) 자식은 __do_fork()에서 fd table을 복제한다

파일:

  • PintOS 저장소 상대 경로 pintos/userprog/process.c

핵심 순서:

__do_fork()
  -> 부모 intr_frame 복사
  -> 부모 주소 공간 복사
  -> duplicate_fd_table(curr, parent)
  -> if_.R.rax = 0
  -> do_iret(&if_)

자식에서 fork() 반환값이 0인 이유도 이 순서에서 드러난다. 부모는 process_fork()의 반환값으로 child tid를 받는다. 자식은 복사한 intr_frame의 RAX를 0으로 바꾼 뒤 유저 모드로 돌아간다.

3) file_duplicate()는 같은 포인터를 공유하지 않는다

파일:

  • PintOS 저장소 상대 경로 pintos/filesys/file.c

핵심 의미:

nfile = file_open(inode_reopen(file->inode))
nfile->pos = file->pos

두 줄은 각각 다음을 뜻한다.

  • inode_reopen: 같은 파일 내용을 가리키는 inode 참조를 다시 얻는다.
  • nfile->pos = file->pos: fork 순간의 파일 위치 값을 복사한다.

하지만 nfile은 새 struct file이다. 이후 file_read()가 nfile->pos를 바꿔도 부모의 file->pos는 함께 바뀌지 않는다.

4) next_fd가 복제 범위를 제한한다

현재 duplicate_fd_table()은 fd < parent->next_fd 범위만 순회한다.

for fd = 2; fd < parent->next_fd && fd < FD_MAX; fd++:
  ...

그런데 process_close_file()은 닫은 fd가 next_fd보다 작으면 next_fd를 그 fd로 내린다.

close(3)
  -> fd_table[3] = NULL
  -> next_fd = 3

두 동작을 함께 보면 다음 질문이 생긴다.

fd 4가 아직 열려 있는데 next_fd가 3으로 내려가면, fork()는 fd 4를 복제할까?

현재 코드만 보면 답은 “복제하지 않는다”다. duplicate_fd_table()의 loop 조건 때문에 fd 4가 복제 범위 밖에 놓이기 때문이다. 이 지점은 fd allocation hint와 fd table 복제 범위를 같은 변수로 관리할 때 생기는 위험을 보여 준다.

값으로 fd table 추적하기

1) fd table 한 페이지의 크기

PintOS 구현은 fd table을 4KB 페이지 하나로 잡는다.

PGSIZE = 4096
sizeof(struct file *) = 8

FD_MAX = PGSIZE / sizeof(struct file *)
       = 4096 / 8 = 512  // 현재 local x86-64 build

fd table base가 0x80045000이라고 가정하면 각 칸의 주소는 다음과 같다.

fd_table[2] 주소 = 0x80045000 + 2 * 8 = 0x80045010
fd_table[3] 주소 = 0x80045000 + 3 * 8 = 0x80045018
fd_table[4] 주소 = 0x80045000 + 4 * 8 = 0x80045020

2) fork 후 file 객체와 pos

fork 직전의 상태는 다음과 같다.

parent fd_table[2] = 0x80041230
*(struct file *)0x80041230
  inode = 0x80039000
  pos   = 20

fork 직후에는 부모와 자식의 fd entry가 서로 다른 struct file을 가리킨다.

parent fd_table[2] = 0x80041230
child  fd_table[2] = 0x80051000

parent file.pos = 20
child  file.pos = 20
parent file.inode == child file.inode 또는 같은 inode 참조

그 뒤 자식이 30바이트를 읽으면 자식의 위치만 바뀐다.

child  file.pos = 50
parent file.pos = 20

이것이 PintOS의 file_duplicate() 방식이다.

3) next_fd 복제 범위 쟁점

다음 순서로 fd를 열고 닫는 상황을 보자.

int a = open ("sample.txt");  // fd 2, next_fd = 3
int b = open ("sample.txt");  // fd 3, next_fd = 4
int c = open ("sample.txt");  // fd 4, next_fd = 5
close (b);                    // fd 3 비움, next_fd = 3
fork ();

fork 직전 부모의 상태는 다음과 같다.

parent->next_fd    = 3
parent->fd_table[2] = file A
parent->fd_table[3] = NULL
parent->fd_table[4] = file C

현재 duplicate_fd_table()의 loop는 다음 조건으로 돈다.

for fd = 2; fd < parent->next_fd; fd++

따라서 실제로 순회하는 범위는 다음과 같다.

fd = 2만 순회
fd = 3은 fd < 3 조건에서 중단
fd = 4는 보지도 않음

이 구현에서는 fd 4가 자식에게 복제되지 않는다. 이 결론은 process_close_file()의 next_fd 갱신과 duplicate_fd_table()의 loop 조건을 함께 읽어서 얻은 결과다.

GDB로 확인할 지점

1) fork-read 테스트로 pos 독립 여부 보기

테스트 파일:

  • PintOS 저장소 상대 경로 pintos/tests/userprog/fork-read.c

테스트에서 살펴볼 흐름은 다음과 같다.

부모가 먼저 20바이트 읽음
자식이 fork 후 나머지를 읽음
부모가 wait 후 다시 나머지를 읽음
부모도 성공해야 함

Linux처럼 같은 open file description의 offset을 공유한다면 자식이 나머지를 읽은 뒤 부모가 같은 위치에서 다시 나머지를 읽기 어렵다. 따라서 이 테스트는 PintOS의 file_duplicate() 방식과 연결해서 읽어야 한다.

2) GDB로 fd table 복제 보기

breakpoint:

b duplicate_fd_table
b file_duplicate
b process_close_file

확인할 값:

p parent->next_fd
p/x parent->fd_table
p/x parent->fd_table[2]
p/x parent->fd_table[3]
p/x parent->fd_table[4]

file_duplicate() 안에서는 부모 file과 새 file의 주소를 비교한다.

p/x file
n
p/x nfile
p file->pos
p nfile->pos

주소가 다르고 pos가 같다면 “같은 file 객체 공유”가 아니라 “상태를 복사한 새 file 객체”라는 뜻이다.

3) next_fd 복제 범위 확인

다음 테스트 상황을 만들고 duplicate_fd_table()에서 멈춘다.

int a = open ("sample.txt");
int b = open ("sample.txt");
int c = open ("sample.txt");
close (b);
fork ();

확인할 질문은 세 가지다.

  • parent->next_fd가 3으로 내려갔는가?
  • parent->fd_table[4]는 아직 NULL이 아닌가?
  • 자식의 fd_table[4]가 NULL로 남는가?

현재 코드에서 예상되는 상태는 parent->fd_table[4] != NULL인데도 child->fd_table[4] == NULL인 경우다. 자식이 유저 변수 c == 4로 read(c, ...)를 호출하면 process_get_file(4)가 NULL을 반환하므로 read는 실패한다.

이 질문은 reuse Lab (닫힌 fd 번호가 다시 쓰이는 순간)에서 남긴 “닫힌 fd 번호 재사용” 실험의 다음 단계다.

4) fork + exec fd 유지 보기

테스트 파일:

  • PintOS 저장소 상대 경로 pintos/tests/userprog/multi-child-fd.c
  • PintOS 저장소 상대 경로 pintos/tests/userprog/child-close.c

다음 흐름을 따라가면 된다.

parent open("sample.txt") -> handle
child fork()
child exec("child-close <handle>")
exec된 child가 같은 handle 번호로 파일 내용을 읽음

이 흐름은 process_exec()이 fd table을 닫지 않는다는 사실과 연결된다.

기억해야 할 경계

  • fd는 파일 자체가 아니라 프로세스별 fd table index다.
  • fork()는 자식에게 fd table의 의미를 물려줘야 표준 입출력, 리다이렉션, 열린 파일 상속을 이어갈 수 있다.
  • Linux에서는 보통 부모와 자식의 fd가 같은 open file description을 가리키므로 file offset이 공유될 수 있다.
  • 이 PintOS 구현은 file_duplicate()로 새 struct file을 만들고 pos를 복사하므로 fork 이후 file offset이 독립적으로 움직인다.
  • 자식의 close(fd)는 자식 fd table entry를 닫는다. 부모 fd table entry를 직접 지우지는 않는다.
  • QEMU는 guest fd의 의미를 해석하지 않는다. PintOS가 변경한 guest memory와 disk I/O를 에뮬레이션한다.
  • 현재 코드에서는 next_fd를 fd allocation hint와 fork 복제 범위로 함께 쓴다. 이 때문에 open 2, 3, 4 -> close 3 -> fork 흐름에서 fd 4가 자식 복제에서 빠진다.
  • 이 경계는 별도 regression test 후보다. 가능한 설계는 FD_MAX 전체에서 NULL이 아닌 slot을 복제하거나 next_fd를 항상 가장 큰 열린 fd보다 큰 값으로 유지하는 것이다.
