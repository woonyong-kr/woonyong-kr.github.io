fd close/reuse Lab (닫힌 fd 번호가 다시 쓰이는 순간)

한 줄 요약: 닫힌 fd 번호가 다음 open에서 다시 쓰이는 순간을 코드로 확인하는 실험.

다음 코드에서 c는 몇 번 fd가 될까

처음 보면 “한 번 쓴 fd 번호를 다시 써도 될까?”라는 의문이 생긴다. fd는 파일에 영구히 붙는 ID가 아니라 현재 프로세스의 fd table에서 사용 중인 칸 번호다. 따라서 close(a)가 해당 칸을 비우면 다음 open()이 그 번호를 다시 사용할 수 있다.

이 장면에서 살펴볼 질문은 두 가지다.

  • close(fd)로 비운 번호를 다음 open()이 왜 다시 사용할 수 있을까?
  • remove(name)으로 파일 이름을 지운 뒤에도 이미 열린 fd로 왜 계속 읽고 쓸 수 있을까?

fd close/reuse 오해

fd를 “파일 그 자체”라고 생각하면 다음 세 상황을 혼동하기 쉽다.

  • close(2) 뒤에 fd 2를 다시 받아도 되는가?
  • 이미 닫은 fd를 한 번 더 close(2)하면 무슨 일이 일어나는가?
  • remove("a.txt")는 열린 fd까지 닫는가?

세 질문은 fd와 파일 이름이 서로 다른 자료구조에 속한다는 사실로 설명할 수 있다.

fd는 파일 이름도, 디스크 주소도, 커널 포인터도 아니다. fd는 현재 프로세스의 fd table index다.

close(fd)는 fd table에서 해당 index의 칸을 비운다. 반면 remove(name)은 디렉터리에서 이름을 지운다. 두 작업은 서로 다른 자료구조를 변경한다.

fd close/reuse 흐름

먼저 fd table을 포인터 배열로 생각해 보자.

close(2)를 호출하면 다음과 같이 2번 칸이 비워진다.

그다음 open()은 빈 칸에 새 struct file *를 넣고 그 칸의 번호를 사용자에게 반환한다.

fd 재사용은 특별한 예외가 아니라 비워진 배열 index를 다시 사용하는 과정이다.

이번 Lab에서 분리해 볼 세 가지 상황

1) 같은 파일을 두 번 열기

두 호출은 같은 파일 이름에서 출발하지만 서로 다른 fd를 반환해야 한다.

두 struct file이 같은 inode를 가리키더라도 현재 위치 pos와 같은 열린 상태는 따로 움직일 수 있다.

2) 닫은 fd 번호 재사용

close(a) 뒤에도 C 변수 a에는 값 2가 남아 있다. 그러나 커널의 fd_table[2]는 이미 비워진 상태다.

따라서 close(a) 뒤에 write(a, ...)를 호출한다고 해서 예전 파일 A에 쓰는 것은 아니다. 그때도 fd_table[2]가 비어 있으면 호출은 실패한다. 그 사이에 새 파일 C가 2번 칸에 들어왔다면 같은 숫자가 C를 가리킬 수 있다.

3) 이름을 지운 뒤 열린 fd로 계속 쓰기

remove("deleteme")는 fd table을 비우지 않는다. 디렉터리 entry에서 이름을 지우고 inode를 “삭제 예정” 상태로 표시한다.

열린 fd가 모두 닫히면 inode 자원이 실제로 해제된다.

실제 운영체제

Linux에서도 fd는 프로세스별 fd table의 index다. open()은 보통 사용할 수 있는 가장 낮은 fd 번호를 반환한다. 따라서 close(3) 뒤의 open()이 다시 3을 반환하는 것은 자연스럽다.

Linux의 unlink()도 이름과 열린 fd를 분리해서 이해해야 한다. unlink("a.txt")는 directory entry를 제거한다. 이미 열린 fd가 있다면 파일 내용은 마지막 참조가 사라질 때까지 남을 수 있다.

Windows에서는 같은 문제를 HANDLE과 object lifetime으로 다룬다. Win32 HANDLE은 Linux fd와 같은 “작은 정수 배열 index”라기보다 불투명한 handle 값으로 보는 편이 낫다. 삭제에는 share mode, delete disposition, handle 참조 수 같은 정책이 얽혀 있으므로 Unix의 unlink 규칙을 그대로 적용하면 안 된다.

유저에게 보이는 작은 식별자와 실제 커널 객체의 생명주기는 분리되어 있다.

PintOS

이 저장소의 PintOS는 fd table을 struct thread에 둔다.

  • PintOS 저장소 상대 경로 pintos/include/threads/thread.h
    • struct file **fd_table
    • int next_fd
  • PintOS 저장소 상대 경로 pintos/userprog/process.c
    • process_add_file
    • process_get_file
    • process_close_file
    • duplicate_fd_table
  • PintOS 저장소 상대 경로 pintos/userprog/syscall.c
    • open
    • close
    • remove

초기 유저 프로세스는 0으로 채운 fd_table 한 페이지를 받고 next_fd를 2로 시작한다.

현재 process_add_file()은 next_fd부터 검색하지 않는다. 매번 fd 2부터 FD_MAX까지 빈 칸을 훑는다.

이 구현에서 fd 재사용이 일어나는 이유는 next_fd만이 아니다. 할당 루프가 2번 칸부터 빈 칸을 다시 찾기 때문에 닫힌 낮은 fd가 먼저 재사용된다.

process_close_file()은 파일을 닫은 뒤 해당 칸을 비우고 next_fd를 조정한다.

현재 구현에서 next_fd는 “다음 할당 시작점”이라기보다 복제 범위와 힌트에 가깝다. duplicate_fd_table()은 fd < parent->next_fd인 범위만 복제한다. 중간 fd를 닫은 뒤 더 큰 fd가 살아 있다면 GDB에서 next_fd와 살아 있는 fd 범위를 함께 확인해야 한다.

fd 2, 3, 4가 열린 상태에서 close(3)만 하면 next_fd가 3으로 내려간다. 그 직후 fork()가 fd 4까지 복제할까?

이 Lab에서는 답을 미리 단정하지 않고 현재 코드에서 직접 확인할 방법을 살펴본다.

QEMU

QEMU는 PintOS의 guest fd가 뜻하는 바를 알지 못한다.

fd_table[2] = NULL과 같은 변화는 PintOS 커널이 guest memory에 기록한 포인터 값의 변화다. QEMU는 그 바이트를 저장하고 실행할 뿐, “2번 fd가 닫혔다”는 의미를 해석하지 않는다.

파일 내용이 디스크로 내려갈 때는 QEMU의 장치 모델을 거친다.

관련 코드는 다음 위치에서 볼 수 있다.

  • hw/ide/core.c
    • ide_sector_read
    • ide_sector_write
  • block/block-backend.c
    • blk_co_preadv
    • blk_co_pwritev_part

QEMU의 host fd와 PintOS의 guest fd는 서로 다른 층에 속한 번호다. PintOS fd 2는 guest kernel 자료구조의 index다. QEMU 내부의 host fd는 디스크 이미지 파일이나 socket을 다루는 host process의 자원이다.

따라서 syn-remove 테스트는 remove() 뒤에도 write, seek, read가 가능한지 확인한다.

4) fork 복제 범위 질문 만들기

현재 구현의 복제 범위를 확인하려면 다음 상황을 만들 수 있다.

duplicate_fd_table()이 fd < parent->next_fd까지만 돈다면, fd 4는 복제 대상에 들어갈까?

이 질문은 fd table의 빈 칸 재사용과 next_fd 관리가 함께 설계되어야 하는 이유를 보여 준다. 자세한 답은 fork하면 fd table은 어떻게 복제되는가에서 file_duplicate()와 next_fd 복제 범위를 함께 보며 이어간다.

정리

  • fd는 파일의 영구 ID가 아니라 현재 프로세스 fd table의 index다.
  • close(fd)는 file_close()를 호출하고 fd table slot을 NULL로 비운다.
  • 다음 open()은 비워진 slot을 다시 사용할 수 있다.
  • remove(name)은 파일 이름과 inode의 삭제 표시를 다루며 이미 열린 fd table slot을 직접 비우지 않는다.
  • QEMU는 guest fd의 의미를 해석하지 않고 guest memory와 disk I/O 장치 동작을 제공한다.
  • 현재 PintOS 구현에서는 process_add_file()이 fd 2부터 빈 칸을 검색하므로 next_fd가 실제 할당 시작점인지 코드를 통해 확인해야 한다.
