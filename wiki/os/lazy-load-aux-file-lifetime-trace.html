Lazy Load aux/file 수명 Trace

Lazy Load aux/file 수명 Trace

한 줄 요약: load_segment()는 page별 aux에 file·offset·read_bytes를 저장하고 소유권을 UNINIT page로 넘긴다. 첫 pf에서 lazy_load_segment()가 소비·해제하며, 끝까지 fault가 없을 때만 uninit_destroy()가 미소비 자원을 해제한다.

Lazy Load aux/file 수명 구조

load_segment()는 파일을 바로 읽지 않고 page별 aux 구조체에 “어떤 파일의 어느 offset에서 얼마나 읽어야 하는지”를 기록해 둔다. 이 aux는 첫 page fault까지 살아 있어야 하고, fault 처리 후에는 반드시 해제되어야 한다. aux의 수명 관리가 lazy loading의 핵심 계약이다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

CPU/MMU는 aux를 모른다. CPU가 아는 것:

CPU/MMU가 아는 것CPU/MMU가 모르는 것
PTE가 not-present이면 pf 발생그 page가 어떤 파일의 어떤 offset과 관련되는지
fault address를 CR2에 넣음aux 포인터의 존재
error code에 P/W/U 비트 넣음file_read_at()이 필요하다는 것
fault 처리 후 같은 명령어를 재실행aux가 해제되었는지

aux는 순전히 OS가 “미래의 page fault handler에게 보내는 작업 지시서”다.

PintOS 구현

struct lazy_load_arg (include/vm/vm.h:44):

수명 4단계:

1단계: 생성 — load_segment() (process.c)

핵심: 각 page가 독립된 aux를 가진다. 모든 page가 같은 aux를 공유하면, 반복문이 다음 page로 넘어가며 offset을 바꾼 뒤 먼저 fault가 온 page가 잘못된 offset을 읽는다.

file_reopen(file)으로 독립 file 객체를 만드는 이유: 원본 file은 load() 함수가 끝나면서 닫히거나, exec()/exit() 경로에서 닫힐 수 있다. reopen된 file은 같은 inode를 가리키지만 position과 수명이 독립이다.

2단계: 보관 — uninit_new() (uninit.c:28)

aux는 SPT의 UNINIT page 안에서 fault가 올 때까지 대기한다. 이 시점에서 frame은 없고, 파일 읽기도 없다.

3단계: 소비 — lazy_load_segment() (process.c:1309)

file_read_at()은 file position을 바꾸지 않고 특정 offset에서 읽는다. lazy page들은 fault 순서가 파일 offset 순서와 같다는 보장이 없으므로, position 의존적인 file_read()보다 안전하다.

4단계: 미소비 정리 — uninit_destroy() (uninit.c:65)

프로세스가 exit하거나 exec할 때, 한 번도 fault가 나지 않은 UNINIT page가 남아 있을 수 있다. supplemental_page_table_kill()이 uninit_destroy()를 호출해 미소비된 aux의 file reference와 heap memory를 회수한다.

QEMU 에뮬레이션

QEMU는 aux, file_reopen(), SPT를 모른다. QEMU가 보는 사건:

  1. guest CPU가 present PTE가 없는 VA를 접근 → EXCP0E_PAGE + error code + env->cr[2] = addr
  2. PintOS page fault handler가 SPT와 aux를 보고 frame을 채우고 PTE를 설치
  3. 예외 처리 후 같은 명령어가 재실행 → 이번에는 PTE가 present이므로 정상 접근

“이 파일 offset을 읽어야 한다”는 판단은 PintOS 정책이고, QEMU는 CPU/MMU 예외만 재현한다.

두 번째 page fault 시 frame 채우기

설명용 frame 주소를 frame->kva = 0xffff800012340000으로 놓으면, aux->ofs = 0x3000에서 읽은 1,904바이트는 0xffff800012340000부터 0xffff80001234076f까지 채우고, 나머지 2,192바이트는 0xffff800012340770부터 page 끝 0xffff800012340fff까지 0으로 채운다. 이 KVA는 byte layout을 추적하기 위한 예시값이며 실제 PintOS 실행 주소라고 가정하지 않는다.

이 흐름에서 해제 주체는 배타적이다. 등록 실패는 load_segment(), fault 소비 성공은 lazy_load_segment(), fault 없는 teardown은 uninit_destroy()가 맡으며 같은 aux를 둘이 정리해서는 안 된다.
