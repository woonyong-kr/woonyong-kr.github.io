CPL 3→0 권한 전환

CPL 3→0 권한 전환

확인 범위: 이 문서는 x86-64의 CPL 3→0 전환에 관한 일반 원리와 Linux·PintOS·QEMU의 구현 구조 및 관찰 방법을 설명한다. 제시된 코드 좌표, 설정값, 예상 결과와 성능 수치는 특정 소스·빌드·CPU에서 실제 코드와 버전, 실행 기록, 측정을 통해 별도로 검증해야 한다.

CPL은 지금 실행 중인 코드가 유저 권한인지 커널 권한인지 CPU가 구분하는 값이다. syscall은 이 값을 Ring 3에서 Ring 0으로 바꾸는 정해진 진입로다.

CPL 3→0 권한 전환 구조

CPL(Current Privilege Level)은 x86-64 CPU가 현재 실행 중인 코드의 권한 수준을 나타내는 2-bit 값이다. Ring 3(유저)에서 Ring 0(커널)로의 전환은 syscall 명령어 실행 시 하드웨어가 자동으로 수행한다. 이 전환은 소프트웨어가 임의로 할 수 없으며, CPU가 미리 등록된 MSR(Model-Specific Register) 값에 따라 안전하게 수행한다.

상세 설명

추상 개념 (x86-64 하드웨어 규칙)

CPL은 CS(Code Segment) 레지스터의 하위 2 bit에 저장된다:

  • CS = 0x08 → RPL=0 (커널), CS = 0x23 → RPL=3 (유저)

syscall 명령어가 하는 일 (하드웨어 동작)

syscall 실행 시 CPU는 다음 상태 전이를 하나의 architecturally atomic instruction effect로 수행한다. 이는 중간 상태를 관찰할 수 없다는 뜻이지, 실제 실행 시간이 1 CPU cycle이라는 뜻은 아니다.

  1. RCX ← RIP (다음 명령어 주소 저장 — 돌아올 곳)
  2. R11 ← RFLAGS (현재 플래그 저장)
  3. RFLAGS &= ~MSR_SYSCALL_MASK (인터럽트 비활성화 등)
  4. CS ← MSR_STAR[47:32] (커널 CS 세그먼트 → CPL 0)
  5. SS ← MSR_STAR[47:32] + 8 (커널 SS 세그먼트)
  6. RIP ← MSR_LSTAR (커널 진입점으로 점프)

주의: syscall은 스택을 전환하지 않는다! RSP는 여전히 유저 스택을 가리킨다. 커널 스택 전환은 소프트웨어(syscall_entry)가 TSS.rsp0에서 읽어서 수행한다.

sysret 명령어 (커널→유저 복귀)

  1. RIP ← RCX (저장해둔 유저 RIP 복원)
  2. RFLAGS ← R11 (저장해둔 플래그 복원)
  3. CS ← MSR_STAR[63:48] + 16 (유저 CS → CPL 3)
  4. SS ← MSR_STAR[63:48] + 8 (유저 SS)

실제 OS (Linux)

Linux의 entry_SYSCALL_64 (arch/x86/entry/entry_64.S)는 PintOS와 거의 동일한 구조다:

  1. swapgs — per-CPU 데이터 접근을 위해 GS base 전환
  2. RSP를 per-CPU 영역의 커널 스택 주소로 교체
  3. 유저 레지스터를 pt_regs 구조체로 push
  4. syscall_handler 호출

PintOS는 swapgs 대신 전역 tss 변수에서 직접 rsp0를 읽는다 (단일 CPU).

PintOS 구현

MSR 초기화 (userprog/syscall.c:87)

MSR_STAR 비트 분해:

MSR_STAR = 0x001B_0008_0000_0000
             ↑         ↑
        [63:48]=0x13  [47:32]=0x08

sysret 시: CS = 0x13 + 16 = 0x23 (SEL_UCSEG, RPL=3)
            SS = 0x13 + 8  = 0x1B (SEL_UDSEG, RPL=3)
syscall 시: CS = 0x08 (SEL_KCSEG, RPL=0)
            SS = 0x10 (SEL_KDSEG, RPL=0)

MSR_SYSCALL_MASK: syscall 실행 시 RFLAGS에서 마스킹할 비트. FLAG_IF를 마스킹하여 커널 스택 전환 전까지 인터럽트를 차단한다.

syscall_entry

핵심: 하드웨어(syscall)가 CPL을 0으로 전환하지만, 소프트웨어(syscall_entry)가 TSS.rsp0에서 커널 스택 주소를 읽어 RSP를 교체한다.

세그먼트 셀렉터 값

이름값RPL용도
SEL_KCSEG0x080커널 코드 세그먼트
SEL_KDSEG0x100커널 데이터 세그먼트
SEL_UDSEG0x1B3유저 데이터 세그먼트

RPL(Requested Privilege Level) = 셀렉터의 하위 2 bit. 0x1B = 0001_1011 → RPL = 3.

QEMU 에뮬레이션

QEMU TCG 모드에서 syscall 명령어는 helper_syscall() (target/i386/tcg/seg_helper.c)로 처리된다. 세부 단계:

  1. TCG 프론트엔드가 syscall opcode(0x0F 0x05)를 디코딩 → gen_helper_syscall() 호출 생성
  2. helper_syscall() 실행:
    • env->regs[R_ECX] = env->eip (RCX ← 다음 명령어 주소)
    • env->regs[11] = env->eflags (R11 ← RFLAGS)
    • env->eflags &= ~env->fmask (MSR_SYSCALL_MASK 적용)
    • cpu_x86_load_seg_cache(env, R_CS, selector, ...) → CS 교체, CPL=0
    • env->eip = env->lstar (MSR_LSTAR → RIP)
  3. Translation Block은 syscall에서 종료(TB end) → 다음 TB는 syscall_entry 주소에서 시작
  4. sysret도 동일하게 helper_sysret() → CS를 유저 셀렉터로, CPL=3으로 복원

중요: QEMU의 helper 구현과 실제 하드웨어의 내부 cycle 수는 다르다. 그러나 guest가 관찰하는 syscall 전후의 architectural state transition은 동일해야 한다.

관찰 시나리오

시나리오 1: write syscall 전체 CPL 왕복 추적

목표: write(1, "hello", 5) 호출 시 CPL 3→0→3 전환의 모든 단계를 관찰한다.

절차:

  1. trace_cpl_roundtrip define 로드
  2. args-single onearg 같은 간단한 유저 프로그램 실행 (내부에서 write syscall 발생)
  3. 관찰: syscall_entry에서 CS=0x08, RAX=syscall 번호(SYS_WRITE=10), RCX=유저 RIP
  4. sysretq 직전 RCX=유저 복귀 RIP, R11=복원할 RFLAGS, RAX=반환값(5=written bytes)

예상 결과:

  • syscall_entry: CS=0x08(CPL=0), RSP가 아직 유저 스택 → 커널 스택 전환 후 intr_frame push
  • sysretq: RCX/R11에서 RIP/RFLAGS를 복원하고 STAR가 정한 유저 CS/SS로 CPL 3에 복귀
  • 왕복에서 RAX가 syscall 번호(10)에서 반환값(5)으로 변경되는 것 확인

시나리오 2: 인터럽트 vs syscall CPL 전환 비교

목표: 외부 인터럽트(timer IRQ)와 syscall의 CPL 전환 메커니즘 차이를 관찰한다.

절차:

  1. b *syscall_entry에서 CS, RSP 기록 (syscall 경로)
  2. b intr_entry에서 CS, RSP 기록 (인터럽트 경로)
  3. timer interrupt가 유저 모드에서 발생할 때와 커널 모드에서 발생할 때 비교

예상 결과:

  • syscall: 하드웨어가 RSP를 전환하지 않음 → 소프트웨어가 TSS.rsp0으로 전환
  • 인터럽트: 하드웨어(CPU)가 자동으로 TSS.rsp0에서 커널 RSP를 로드하고 SS/RSP/RFLAGS/CS/RIP를 push
  • 커널 모드에서 인터럽트 발생 시: 스택 전환 없음 (이미 Ring 0이므로)
  • 두 경로 모두 최종적으로 intr_frame 구조체에 동일 형태로 상태 저장
