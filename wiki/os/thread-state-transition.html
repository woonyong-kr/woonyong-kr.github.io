Thread 상태 전이 — READY / RUNNING / BLOCKED / DYING

Thread 상태 전이 — READY / RUNNING / BLOCKED / DYING

스레드가 왜 실행되지 않는지 보려면 먼저 READY, RUNNING, BLOCKED, DYING 중 어디에 머무는지와 그 상태를 바꾼 이벤트를 따라가야 한다.

스레드가 멈춘 이유를 상태로 읽기

스레드가 실행되지 않는다면 먼저 CPU를 기다리는지, 특정 사건을 기다리는지 구분해야 한다. READY인 스레드는 실행할 수 있지만 CPU를 아직 할당받지 못했다. BLOCKED인 스레드는 세마포어·락·타이머 같은 조건이 충족되기를 기다린다. 스케줄러는 READY인 스레드만 선택하므로, 현재 상태와 전이를 일으킨 주체를 함께 보면 어떤 코드가 스레드를 다시 움직일지 좁힐 수 있다.

상태 전이의 기본 규칙

PintOS를 설명하는 네 가지 상태

이 문서에서는 PintOS의 스레드 상태를 READY, RUNNING, BLOCKED, DYING으로 나누어 설명한다. READY, RUNNING, BLOCKED는 실행 가능 여부와 대기 이유를 나타내고, DYING은 종료된 스레드의 자원을 다음 스케줄링 과정에서 회수하기 위한 상태다. 전이를 추적할 때는 상태 이름만 보는 대신 어떤 주체와 이벤트가 상태를 바꾸는지 함께 본다.

  • READY → RUNNING: 스케줄러가 READY인 스레드를 선택해 CPU를 할당한다. 스레드가 스스로 이 전이를 일으킬 수는 없다.
  • RUNNING → READY: 선점(preemption)되거나 스레드가 자발적으로 CPU를 양보(yield)할 때 일어난다. timer interrupt는 이 문서에서 다루는 대표적인 선점 원인이다.
  • RUNNING → BLOCKED: 실행 중인 스레드가 조건이 충족될 때까지 기다리기로 할 때 일어난다. lock 획득 실패, sema_down(), timer_sleep()이 여기에 해당한다.
  • BLOCKED → READY: 다른 스레드나 인터럽트 핸들러가 대기 조건을 충족할 때 일어난다. sema_up(), lock_release(), wake 시간에 도달한 timer tick이 이 전이를 일으킬 수 있다.
  • RUNNING → DYING: thread_exit()가 호출되면 일어난다. 자원은 다음 schedule()에서 회수된다.

이 상태 모델에서는 BLOCKED에서 RUNNING으로 바로 전이하지 않고 READY를 거친다. CPU를 할당할 스레드는 스케줄러가 READY 상태에서 선택하기 때문이다.

실제 OS (Linux/Windows)

Linux의 task_struct 상태:

상태매크로의미
RUNNINGTASK_RUNNINGREADY와 RUNNING을 하나로 합침
INTERRUPTIBLETASK_INTERRUPTIBLEsignal로 깨울 수 있는 BLOCKED
UNINTERRUPTIBLETASK_UNINTERRUPTIBLEsignal 무시, I/O 완료만 대기
STOPPEDTASK_STOPPEDSIGSTOP, ptrace에 의한 정지
ZOMBIEEXIT_ZOMBIE종료했지만 parent가 wait() 안 함

Linux는 READY와 RUNNING을 TASK_RUNNING으로 합친다. run queue에서 CPU 할당을 기다리는 경우와 실제 CPU에서 실행 중인 경우를 커널 코드에서는 같은 상태값으로 나타낸다. SMP에서는 여러 CPU가 각각 TASK_RUNNING 스레드를 실행할 수 있다.

Linux의 BLOCKED에 대응하는 상태는 둘로 나뉜다. TASK_INTERRUPTIBLE은 signal을 받으면 READY에 해당하는 상태로 돌아가며, 시스템 콜은 EINTR을 반환한다. TASK_UNINTERRUPTIBLE은 I/O가 끝날 때까지 기다리는 상태로, ps에서는 D state로 볼 수 있다.

Windows의 스레드 상태:

상태의미
Ready실행 가능, dispatcher queue에 대기
RunningCPU에서 실행 중
WaitingWaitForSingleObject 등으로 대기
Standby특정 CPU에 배정되었지만 아직 미실행
Terminated종료 완료

Windows는 Ready와 Running 사이에 Standby 상태를 둔다. dispatcher가 스레드를 특정 CPU에 할당하면 Standby가 되고, 해당 CPU가 실제로 context switch하면 Running으로 바뀐다.

PintOS 구현

PintOS는 threads/thread.h에서 상태를 다음과 같이 정의한다.

각 전이를 일으키는 함수는 다음과 같다.

전이함수파일
READY → RUNNINGschedule() → next_thread_to_run()threads/thread.c
RUNNING → READYthread_yield()threads/thread.c
RUNNING → BLOCKEDthread_block()threads/thread.c
BLOCKED → READYthread_unblock()threads/thread.c
RUNNING → DYINGthread_exit()threads/thread.c

thread_yield() — RUNNING → READY:

thread_yield()는 intr_disable()로 인터럽트를 끈 뒤 현재 스레드를 ready_list에 삽입한다. 인터럽트를 끄지 않으면 list를 조작하는 도중 timer interrupt가 발생해 같은 list를 건드릴 수 있다.

thread_block() — RUNNING → BLOCKED:

thread_block()은 현재 스레드를 대기 큐에 직접 넣지 않는다. sema_down()과 같은 호출자가 먼저 스레드를 대기 큐에 넣은 뒤 thread_block()을 호출한다. 따라서 thread_block()은 현재 스레드를 멈추는 역할만 맡고, 어떤 조건과 대기 큐에서 깨울지는 호출자가 결정한다.

thread_unblock() — BLOCKED → READY:

sema_up(), lock_release(), timer interrupt의 wake 로직 등은 thread_unblock()을 호출해 BLOCKED인 스레드를 READY로 바꾼다.

선점(preemption) 경로:

intr_yield_on_return()은 즉시 yield하지 않고 플래그만 세운다. 인터럽트 핸들러 안에서 schedule()을 호출하지 않고, interrupt return 직전에 스케줄링하기 위해서다(QEMU 타이머 인터럽트).

QEMU 에뮬레이션

QEMU는 guest의 스레드 상태를 알지 못한다. QEMU에서 스레드 전환은 guest가 메모리의 다른 위치에 있는 명령어를 실행하기 시작한 것으로 보일 뿐이다.

GDB에서는 다음과 같이 PintOS 스레드 상태를 확인할 수 있다.

QEMU는 timer interrupt 전달에 관여한다. QEMU의 i8254 PIT 모델이 100Hz로 IRQ0을 발생시키면 guest CPU에 인터럽트가 주입된다. 이어 PintOS의 timer_interrupt()가 실행되면서 상태 전이가 시작된다.

Thread 상태 전이 값 추적

PintOS 상태 전이와 관련된 상수는 다음과 같다.

TIME_SLICE        = 4 ticks
PIT frequency     = 100 Hz
1 tick            = 10 ms
최대 연속 실행    = 4 × 10ms = 40ms

thread_status enum:
  THREAD_RUNNING  = 0
  THREAD_READY    = 1
  THREAD_BLOCKED  = 2
  THREAD_DYING    = 3

timer_sleep(100)을 호출하면 상태는 다음 순서로 바뀐다.

tick 0:   RUNNING → BLOCKED (sleep_list에 삽입, wake_tick = current + 100)
tick 1~99: BLOCKED 유지 (timer_interrupt가 매 tick 확인)
tick 100:  BLOCKED → READY (thread_unblock)
tick ???:  READY → RUNNING (scheduler가 선택할 때)

스레드는 100 ticks 동안 BLOCKED에 머문 뒤 READY가 된다. 그다음 실제로 다시 실행되기까지 READY에서 더 기다릴 수 있으므로, READY → RUNNING이 즉시 일어난다고 보장할 수는 없다.
