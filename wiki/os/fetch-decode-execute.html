fetch → decode → execute

fetch → decode → execute

확인 범위: 이 문서는 x86-64의 fetch·decode·execute 사이클과 OS 개입 지점, PintOS 및 QEMU TCG의 동작을 설명하는 학습용 개념 문서다. 실제 코드 경로와 세부 동작, 버전별 수치 및 성능 판단은 해당 구현의 소스·버전·실행 기록과 측정 결과를 별도로 확인해야 한다.

CPU는 RIP가 가리키는 바이트를 읽고, 그 바이트를 명령어로 해석한 뒤, 레지스터나 메모리를 바꾸는 일을 계속 반복한다. 이 반복이 fetch, decode, execute다.

fetch → decode → execute 상태

CPU의 동작은 끊임없는 세 단계 반복이다. fetch: RIP가 가리키는 메모리 주소에서 명령어 바이트를 읽어온다. decode: 읽어온 바이트를 opcode + operand로 분해하여 어떤 연산인지 파악한다. execute: 해당 연산을 수행하고 결과를 레지스터나 메모리에 기록한다. 이 사이클은 CPU가 전원이 켜진 순간부터 꺼질 때까지 멈추지 않으며, OS를 포함한 모든 소프트웨어는 이 사이클 위에서 실행된다.

상세 설명

추상 개념 (CPU 하드웨어 규칙)

x86-64 기준으로 각 단계에서 일어나는 일:

Fetch

  1. CPU는 RIP(instruction pointer) 레지스터가 가리키는 가상 주소에서 바이트를 읽는다.
  2. 이 가상 주소는 MMU를 통해 물리 주소로 변환된다 (PML4 → PDPT → PD → PT → 물리 프레임).
  3. L1 instruction cache에서 먼저 찾고, miss이면 L2 → L3 → 메인 메모리 순서로 접근한다.
  4. x86-64는 가변 길이 명령어(1~15 bytes)이므로, CPU는 충분한 바이트를 프리페치한다.

Decode

  1. 첫 바이트(또는 prefix + 첫 바이트)에서 opcode를 식별한다.
  2. opcode에 따라 뒤따르는 바이트에서 ModR/M, SIB, displacement, immediate 필드를 파싱한다.
  3. 마이크로아키텍처 수준에서는 복잡한 명령어를 **μop(마이크로 연산)**으로 분해한다.
  4. 명령어의 총 길이가 결정되면 RIP += 명령어_길이 (다음 fetch 준비).

Execute

  1. ALU, FPU, 또는 메모리 유닛에서 연산을 수행한다.
  2. 결과를 destination 레지스터나 메모리에 기록한다.
  3. EFLAGS 레지스터의 상태 플래그(ZF, CF, SF, OF)가 갱신된다.
  4. 분기 명령이면 RIP가 대상 주소로 변경된다 (다음 fetch가 분기 대상에서 시작).

예외 상황: fetch나 execute 도중 page fault, protection fault 등이 발생하면 사이클이 중단되고 exception handler로 제어가 이동한다.

실제 OS (Linux/Windows)

OS 관점에서 fetch-decode-execute 사이클은 “CPU가 알아서 하는 것”이다. OS가 개입하는 지점은:

  • context switch: schedule()이 RIP, RSP 등을 다른 스레드의 값으로 교체하면, 다음 fetch는 그 스레드의 코드에서 시작된다.
  • interrupt: timer interrupt가 발생하면 현재 사이클이 완료된 후 IDT를 통해 interrupt handler로 fetch가 이동한다.
  • page fault: fetch 중 present=0인 PTE를 만나면 pf가 발생한다. OS가 페이지를 적재하고 fault 명령어를 재시도한다.
  • syscall: 사용자 코드에서 syscall 명령어를 execute하면, LSTAR MSR이 가리키는 커널 진입점으로 RIP가 변경된다.

PintOS 구현

PintOS에서 fetch-decode-execute 사이클이 직접 보이는 곳:

최초 실행: thread_create() → kernel_thread() → do_iret()

do_iret()이 struct intr_frame의 RIP를 CPU에 복원하는 순간, CPU는 해당 주소에서 fetch를 시작한다.

User program 진입: ELF loader가 e_entry를 intr_frame.rip에 설정하고, do_iret()이 이를 복원하면 CPU는 사용자 프로그램의 첫 명령어에서 fetch를 시작한다.

Context switch: thread_launch()가 현재 스레드의 레지스터를 intr_frame에 저장하고, 다음 스레드의 intr_frame에서 복원한다. 복원된 RIP에서 fetch가 재개된다.

QEMU 에뮬레이션

QEMU는 guest CPU의 fetch-decode-execute를 소프트웨어로 재현한다.

TCG (Tiny Code Generator) 모드:

  1. guest 명령어를 **TCG IR (중간 표현)**으로 변환 (fetch + decode에 해당)
  2. TCG IR을 호스트 native 코드로 번역
  3. 번역된 호스트 코드를 실행 (execute에 해당)
  4. 번역 결과를 Translation Block (TB) cache에 저장하여 같은 guest 코드를 다시 만나면 재번역 없이 실행

QEMU는 guest의 RIP를 CPUX86State.eip에 보관한다. GDB stub은 이 값을 읽어 info registers에서 보여준다.

TB cache와 무효화 기준

세부 수치는 QEMU version과 target에 따라 달라질 수 있으므로, 위 값은 이 학습 문서의 관찰 기준이며 보편 상수로 취급하지 않는다. 실행 흐름의 정본은 아래 QEMU TCG 번역 흐름이다.

GDB로 QEMU의 fetch-decode-execute 관찰:

(gdb) si                        # guest 명령어 1개 실행 (step instruction)
(gdb) x/i $rip                  # 현재 RIP의 guest 명령어 (decode 결과)
(gdb) x/10bx $rip               # 같은 주소의 원시 바이트 (fetch 대상)
(gdb) info registers rax rflags # execute 결과 확인

CPU 상태와 fetch-decode-execute의 관계

기본 cycle의 정본은 위 Mermaid다. RIP는 fetch 주소를, decode 결과는 instruction 길이와 operand를 결정한다. execute는 범용 register·memory·RFLAGS를 바꿀 수 있으며, 순차 실행이면 instruction 길이만큼 이동하고 branch·exception·interrupt·syscall이면 target RIP로 전환한다. instruction fetch가 fault 나면 CR2에는 fault address가 남는다.

OS 개입 지점과 사이클 중단

flowchart LR
    FDE["fetch→decode→execute\n반복 중"] --> INT{"인터럽트\n발생?"}
    INT -->|No| FDE
    INT -->|Yes| SAVE["복귀 상태 저장\nIDT 또는 syscall 진입점으로 전환"]
    SAVE --> HANDLER["interrupt / exception / syscall 처리"]
    HANDLER --> SCHED{"스케줄링\n필요?"}
    SCHED -->|No| IRET["경로별 return instruction\n원래 RIP에서 fetch 재개"]
    SCHED -->|Yes| CTX["context_switch()\nnext thread의 RIP 복원"]
    CTX --> FDE2["다른 스레드의\nfetch→decode→execute"]

OS 개입 흐름의 정본은 위 Mermaid다. 비동기 interrupt, fault, 명시적 syscall은 서로 다른 entry/return 규칙을 사용하므로 하나의 고정된 저장 frame이나 iretq로 일반화하지 않는다. 스케줄링이 발생하면 다음 thread의 저장된 architectural state에서 fetch를 재개한다.
