fork는 왜 자식 초기화가 끝날 때까지 부모를 재우는가

fork는 왜 자식 초기화가 끝날 때까지 부모를 재우는가

fork 초기화 handshake 쟁점

fork()는 부모에게 자식 pid를 반환하고 자식에게는 0을 반환한다.

그렇다면 부모가 pid를 받는 순간, 자식의 주소 공간과 fd table 복제가 이미 성공했다고 확신할 수 있을까?

처음에는 다음과 같이 생각하기 쉽다.

thread_create()가 성공해 자식 스레드가 만들어졌다면 바로 pid를 반환해도 되지 않을까?

하지만 PintOS에서는 그것만으로 충분하지 않다. thread_create()는 커널 스레드의 틀만 만든다. fork()가 보장하는 유저 프로세스 복제는 자식 스레드가 __do_fork() 안에서 page table, SPT, fd table, register 반환값까지 준비해야 비로소 끝난다.

이 Trace에서는 [fork 생성 흐름](/wiki/hubs/pintos-process-visual#fork 생성 흐름)의 sema_down(&fork_sema)와 fork_success 박스를 실제 코드 수준까지 내려가며 살펴본다.

fork 초기화 handshake 오해

fork()의 반환값은 단순한 스레드 id가 아니다.

부모에게 양수 pid가 돌아왔다는 것은 커널이 적어도 다음 조건을 보장했다는 뜻이다.

약속깨지면 생기는 일
자식의 register snapshot이 준비됐다자식이 부모와 같은 지점으로 돌아가지 못한다
자식의 주소 공간 복제가 성공했다child가 첫 유저 명령어에서 바로 죽을 수 있다
자식의 fd table 복제가 성공했다fork-read, fork-close 같은 fd 상속 테스트가 불안정해진다
자식의 fork() 반환값이 0으로 설정됐다부모와 자식이 같은 분기로 진입할 수 있다
실패했다면 부모의 fork()는 -1을 받아야 한다부모가 존재하지 않는 자식을 wait하거나 생성을 성공으로 오해한다

따라서 thread_create()의 성공과 fork()의 성공은 서로 다르다. fork_sema는 두 성공 시점 사이의 간격을 메우는 동기화 지점이다.

꼬리 질문

앞의 쟁점을 코드에서 확인하려면 다음 질문을 순서대로 살펴보면 된다.

  1. 부모는 왜 thread_create() 직후에 바로 반환하면 안 될까?
  2. 자식은 __do_fork()에서 무엇을 준비해야 “fork 성공”이라고 말할 수 있을까?
  3. fork_sema와 fork_success는 각각 어떤 역할을 맡을까?
  4. 실패 경로에서 부모는 어떻게 TID_ERROR를 받는가?
  5. 자식의 RAX = 0은 어느 memory snapshot에 기록되는가?
  6. 실제 OS는 이 동기화를 어떻게 더 복잡하게 처리할까?
  7. QEMU는 이 parent-child handshake를 알고 있을까?
  8. GDB에서는 fork_sema.value, fork_success, if_.R.rax를 어디서 관찰할 수 있을까?

fork 초기화 handshake 흐름

fork()는 부모와 자식이 한 번 악수한 뒤에야 부모가 유저 모드로 돌아가는 흐름으로 이해하면 쉽다.

핵심은 각 장치의 역할을 분리해서 보는 것이다.

장치담당
fork_sema”자식 초기화가 끝났는가”를 부모에게 알림
fork_success초기화 결과가 성공인지 실패인지 저장
wait_sema나중에 “자식이 종료했는가”를 기다리는 별도 통로

fork_sema는 생성 완료를 동기화하고, wait_sema는 종료 완료를 동기화한다. 둘을 섞으면 fork()의 반환 시점과 wait()의 수거 시점이 서로 꼬인다.

실제 운영체제

Linux에서 fork()는 호출자에게 두 번 반환되는 것처럼 보인다.

실행 흐름반환값
부모child pid
자식0
실패부모에게 -1, errno 설정

실제 Linux 내부는 PintOS보다 훨씬 복잡하다. task_struct, mm_struct, file table, signal state, cgroup, namespace, copy-on-write page table 같은 구조가 함께 복제되거나 공유된다. 그래도 사용자가 보는 핵심 약속은 같다. 부모에게 성공 pid가 반환되면 커널은 자식 task가 실행 가능한 상태로 준비됐음을 보장한다.

Windows는 Unix식 fork()를 일반 API로 제공하지 않는다. CreateProcess는 새로운 process object와 address space를 만들고 실행 image를 로드한다. 부모 주소 공간 전체를 복제한 뒤 같은 지점으로 두 번 돌아오는 모델이 아니므로, PintOS의 fork_sema를 Windows API에 그대로 대응시켜서는 안 된다.

그럼에도 두 운영체제에는 공통 질문이 있다. “새 실행 주체가 성공적으로 초기화되었는가, 실패했다면 호출자에게 어떤 오류를 돌려줄 것인가”는 실제 OS에서도 중요한 경계다.

PintOS

PintOS의 fork() syscall은 syscall handler에서 register snapshot을 받아 process_fork()로 전달한다.

부모 쪽 process_fork()는 먼저 child_status를 만든다.

그다음 자식을 만들고, 자식이 결과를 기록할 때까지 잠든다.

자식 쪽 __do_fork()는 초기화 성공을 알리기 전에 여러 작업을 마쳐야 한다.

초기화에 실패하면 반대 값을 기록한다.

이 실패 경로가 중요한 이유는 부모가 sema_down()에서 반드시 깨어나야 하기 때문이다. 자식이 실패했는데 sema_up()을 하지 않으면 부모는 영원히 blocked 상태로 남는다.

QEMU

QEMU는 fork_sema의 의미를 알지 못한다.

QEMU 관점에서 보이는 것은 다음과 같다.

  • guest CPU가 syscall 명령을 실행한다.
  • PintOS가 guest memory 안의 struct child_status와 struct semaphore 필드를 읽고 쓴다.
  • sema_down()이 thread_block()으로 이어지면 PintOS scheduler가 현재 guest thread를 THREAD_BLOCKED로 만든다.
  • sema_up()이 thread_unblock()으로 이어지면 blocked guest thread가 ready list로 이동한다.
  • GDB stub은 guest register와 guest memory를 보여줄 뿐, 이를 “fork 초기화 완료 알림”이라는 의미로 해석하지 않는다.

근거가 되는 QEMU 위치는 다음과 같다.

  • target/i386/tcg/system/seg_helper.c
    • helper_syscall()
  • target/i386/tcg/emit.c.inc
    • gen_SYSCALL()
  • target/i386/gdbstub.c
    • x86_cpu_gdb_read_register()
  • gdbstub/gdbstub.c
    • handle_read_mem()

즉, QEMU가 fork()를 구현하는 것은 아니다. QEMU는 syscall instruction의 실행과 guest memory/register 관찰 환경을 제공하고, fork()의 정책은 PintOS가 구현한다.

PintOS의 단순화는 의도적이다. 실제 OS의 process 생성 경로 전체를 재현하는 대신, “부모가 성공 pid를 받기 전에 자식 복제 결과를 확인해야 한다”는 핵심 경계만 작게 보여준다.

process_fork()의 성공 경로는 thread_create() 뒤에 곧바로 반환하지 않는다.

__do_fork()는 자식의 반환 register까지 준비한 뒤 부모를 깨운다.

실패 경로에서도 부모를 깨운다.

이 세 줄이 없으면 부모는 fork() 실패를 전달받지 못하거나 fork_sema에서 깨어나지 못한다.

fork 초기화 handshake 값 추적

semaphore 값 변화

fork_sema는 0으로 시작한다.

부모가 sema_down(&fork_sema)를 호출하면 값이 0이므로 waiters에 들어가 blocked 상태가 된다.

자식은 초기화에 성공하면 결과를 먼저 기록한 뒤 semaphore를 올린다.

sema_up()은 부모를 ready 상태로 만들고 value를 증가시킨다. 부모가 다시 실행되면 sema_down() 루프에서 빠져나오면서 그 값을 소비한다.

register 반환값 예시

부모가 fork("child") syscall에 진입했다고 하자.

자식은 부모의 struct intr_frame을 복사받지만, 유저 모드로 돌아가기 전에 RAX만 변경된다.

부모에게는 process_fork()의 반환값이 syscall return register에 들어간다.

즉, 같은 fork() 호출 뒤에 if (pid == 0) 분기가 부모와 자식에서 다르게 갈리는 이유는 커널이 자식의 register snapshot을 의도적으로 수정했기 때문이다.

Fork Handshake 전체 흐름

sequenceDiagram
    participant P as Parent (process_fork)
    participant K as Kernel (thread_create)
    participant C as Child (__do_fork)

    P->>P: child_status 생성<br/>fork_success = false<br/>fork_sema.value = 0
    P->>K: thread_create(__do_fork, args)
    K-->>P: tid (커널 스레드 생성 완료)
    P->>P: cs->tid = tid
    P->>P: sema_down(&fork_sema)<br/>→ BLOCKED

    Note over C: 스케줄러에 의해 child 실행 시작
    C->>C: intr_frame 복사 (parent → child)
    C->>C: pml4_create() + process_activate()
    C->>C: SPT 복제 또는 pml4_for_each(duplicate_pte)
    C->>C: duplicate_fd_table()
    C->>C: if_.R.rax = 0

    alt 성공
        C->>C: fork_success = true
        C->>P: sema_up(&fork_sema)
        Note over P: BLOCKED → READY
        C->>C: do_iret(&if_) → user mode (RAX=0)
        P->>P: fork_success == true<br/>return tid
    else 실패
        C->>C: fork_success = false
        C->>C: cs->exited = true
        C->>P: sema_up(&fork_sema)
        Note over P: BLOCKED → READY
        C->>C: thread_exit()
        P->>P: fork_success == false<br/>return TID_ERROR
    end

정리

  • thread_create()의 성공은 fork()의 성공과 같지 않다.
  • 부모는 fork_sema에서 자식의 __do_fork() 결과를 기다린다.
  • 자식은 주소 공간, fd table, register 반환값을 준비한 뒤 fork_success = true와 sema_up()으로 부모를 깨운다.
  • 실패 경로에서도 반드시 fork_success = false와 sema_up()으로 부모를 깨워야 한다.
  • 자식의 fork() 반환값이 0인 이유는 __do_fork()가 복사된 intr_frame의 RAX를 0으로 바꾸기 때문이다.
  • QEMU는 이 정책을 처리하지 않으며, guest syscall/register/memory의 실행 환경만 제공한다.
