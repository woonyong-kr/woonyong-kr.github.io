mmap dirty write-back 시작

mmap()으로 파일을 메모리에 붙인 뒤 포인터로 값을 바꿨다고 하자.

char *p = mmap((void *) 0x10000000, 4096, 1, fd, 0);
memcpy(p, "hello", 5);
munmap(p);

유저 코드는 write(fd, ...)를 호출하지 않았다. 그런데 munmap() 뒤 파일을 다시 읽으면 "hello"가 파일에 남아야 한다.

mmap dirty write-back 구분

mmap은 파일을 메모리처럼 보이게 만든다. 그래서 유저 코드는 파일 쓰기를 포인터 대입으로 표현할 수 있다.

%% write syscall과 mmap store의 저장 시점
flowchart LR
  write_call["write(fd, buf, 5)"]
  syscall_copy["syscall 순간에<br/>파일로 5바이트 복사"]
  store["p[0] = 'h'"]
  memory_store["지금은 메모리 store"]
  later["나중에 munmap / eviction / exit 때<br/>파일로 되돌릴 수 있음"]
  write_call --> syscall_copy
  store --> memory_store
  memory_store --> later

이 차이 때문에 운영체제는 “이 page가 원본 파일과 달라졌는가?”를 기억해야 한다. 그 신호가 dirty bit다.

dirty bit는 보통 CPU page table entry에 있는 하드웨어 상태다. 유저 코드가 해당 page에 store를 하면 CPU가 PTE의 dirty bit를 세운다. OS는 그 bit를 보고 “이 file-backed page는 backing file에 써야 한다”고 판단한다.

반대로 clean page를 무조건 write-back하면 문제가 생긴다. 예를 들어 mapping을 만든 뒤 다른 경로의 write()가 파일을 바꿨는데, mapping 쪽 page는 한 번도 수정하지 않았다면 munmap()이 예전 frame 내용을 파일에 덮어쓰면 안 된다. 그래서 dirty bit는 “저장해야 하는가”뿐 아니라 “덮어쓰지 말아야 하는가”를 판단하는 기준이 된다.

Trace 판단표

dirty write-back에서 헷갈리기 쉬운 판단은 다음 네 가지다.

질문 판단 기준 잘못 처리하면 생기는 문제
page가 resident인가? page->frame과 PTE 존재 여부 아직 fault가 없던 page를 빈 frame처럼 write-back할 수 있음
page가 dirty인가? pml4_is_dirty(pml4, page->va) clean page가 파일의 최신 내용을 덮어쓸 수 있음
어디에 쓸 것인가? page metadata의 file offset 모든 page가 offset 0으로 쓰이거나 mapping별 offset이 섞임
몇 바이트를 쓸 것인가? page metadata의 read bytes 마지막 page의 zero padding까지 파일 크기 뒤에 써 버림

이 말은 즉, dirty bit 하나만으로는 부족하다. dirty bit는 “써야 하는가”를 알려 주지만, “어느 파일의 어느 offset에 몇 바이트를 쓸 것인가”는 file backed page metadata가 알려 줘야 한다.

파일 길이가 6000바이트이고, 다음처럼 매핑한다고 하자

파일 길이가 6000바이트이고, 다음처럼 매핑한다고 하자.

char *p = mmap((void *) 0x10000000, 6000, 1, fd, 0);
p[5000] = 'X';
munmap(p);

page size가 4096 = 0x1000이면 두 번째 page가 문제의 page다.

flowchart LR

  page0["page 0<br/>VA 0x10000000-0x10000fff<br/>file offset 0-4095<br/>write-back 4096B"]
  page1["page 1<br/>VA 0x10001000-0x10001fff<br/>file offset 4096-5999<br/>write-back 1904B"]
  store["p[5000] = 'X'<br/>5000 - 4096 = 904<br/>page 1 내부 offset 904"]
  dirty["PTE_D = 1<br/>munmap 때 dirty page로 판단"]
  writeback["file_write_at(file, frame, 1904, 4096)<br/>zero padding은 파일에 쓰지 않음"]

  map --> page0
  map --> page1
  page1 --> store
  store --> dirty
  dirty --> writeback

유저가 이 주소에 store하면 page table의 dirty bit가 켜진다. munmap()은 두 번째 page를 보며 dirty == true를 확인하고, frame 앞 1904바이트만 파일 offset 4096으로 되돌려야 한다.

실제 운영체제

Linux의 mmap()은 프로세스 주소 공간에 VMA를 만들고, file-backed page는 page cache와 연결된다. 유저가 mapping을 통해 쓰면 해당 page는 dirty file page가 된다. 커널은 msync(), munmap(), memory pressure, background writeback 같은 여러 계기로 dirty page를 파일 시스템에 기록할 수 있다.

Windows도 file mapping object와 mapped view를 통해 비슷한 문제를 다룬다. 수정된 mapped page는 modified 상태가 되고, flush, unmap, memory manager 정책에 따라 backing file로 기록된다.

현실 OS는 PintOS보다 훨씬 복잡하다. 공유 mapping, private mapping, copy-on-write, page cache 일관성, writeback error, 파일 크기 변경, 권한, 다중 CPU 동기화를 함께 다룬다.

구현 체크포인트

PintOS 구현에서 dirty write-back을 넣을 때는 다음 순서를 고정한다.

  1. file_backed_swap_in() 또는 lazy callback 성공 시점에 struct file_page에 file reference, offset, read bytes, writable 정보를 남긴다.
  2. file_backed_swap_out()은 resident frame이 있는 page만 대상으로 삼고, dirty이면 file_write_at(file, frame->kva, read_bytes, file_offset)을 호출한다.
  3. do_munmap()은 mapping 범위를 page 단위로 순회하면서 같은 write-back helper를 재사용한다.
  4. write-back 뒤에는 PTE dirty bit를 내리거나 PTE를 제거해 같은 dirty 상태를 다음 cleanup 경로에서 중복 처리하지 않게 한다.
  5. fault가 없었던 UNINIT(FILE) page는 frame byte가 없으므로 write-back 대상이 아니다. 이 경우는 fault가 한 번도 나지 않은 mmap page는 누가 정리하나에서 aux/file reference만 정리한다.

이 체크포인트는 QEMU 기준이 아니라 PintOS VM 정책이다. QEMU는 아래에서 볼 sector write 효과만 재현한다.

QEMU

QEMU는 mmap, struct page, struct file_page, dirty write-back 정책을 모른다.

QEMU가 보는 것은 두 종류의 하드웨어 효과다.

첫째, guest CPU가 user store를 실행할 때 x86 page walk의 dirty bit 효과를 흉내 낸다.

  • target/i386/cpu.h
    • PG_DIRTY_BIT = 6
    • PG_DIRTY_MASK
  • target/i386/tcg/system/excp_helper.c
    • access_type == MMU_DATA_STORE이면 PG_DIRTY_MASK를 set할 bit에 포함한다.

둘째, PintOS 파일 시스템이 IDE sector write를 요청하면 가상 IDE 장치와 block backend write를 수행한다.

  • hw/ide/ide-internal.h
    • WIN_WRITE = 0x30
  • hw/ide/core.c
    • cmd_write_pio()
    • ide_sector_write()
    • blk_aio_pwritev(s->blk, sector_num << BDRV_SECTOR_BITS, ...)
  • include/block/block-common.h
    • BDRV_SECTOR_BITS = 9
    • BDRV_SECTOR_SIZE = 512

이 말은 즉, QEMU는 “dirty mmap page를 저장한다”가 아니라 “guest가 sector N에 512바이트 write command를 냈다”만 처리한다.

2. 마지막 page write-back 범위

파일 길이 6000바이트의 두 번째 page는 실제 파일 바이트가 1904바이트뿐이다.

%% 마지막 page write-back 범위
flowchart TD
  input["PGSIZE = 4096<br/>file length = 6000<br/>page 1 file offset = 4096"]
  calc["read_bytes = 6000 - 4096 = 1904<br/>zero_bytes = 4096 - 1904 = 2192"]
  ok["정상<br/>file_write_at(file, frame-&gt;kva, 1904, 4096)<br/>파일에 대응되는 1904B만 write-back"]

뒤쪽 2192바이트는 파일 내용이 아니라 page padding이다.

3. file offset이 sector로 바뀌는 계산

PintOS 파일 시스템에서 sector 크기는 512바이트다.

만약 inode의 첫 data sector가 200이라면, 두 번째 mmap page의 첫 파일 바이트는 disk sector 208부터 시작한다.

QEMU block backend offset은 다시 바이트 offset으로 계산된다.

%% file offset이 disk sector와 QEMU block backend offset으로 바뀌는 계산
flowchart TD
  file["DISK_SECTOR_SIZE = 512 = 0x200<br/>file offset = 4096 = 0x1000"]
  sector["sector offset from file start = 4096 / 512 = 8<br/>offset inside sector = 4096 % 512 = 0"]
  disk["inode data start sector = 200<br/>file offset sector = 8<br/>disk sector = 208"]
  qemu["QEMU block backend byte offset<br/>208 &lt;&lt; 9 = 106496 = 0x1A000"]
  file --> sector
  sector --> disk
  disk --> qemu

이 숫자는 “guest 파일 안 offset”이 아니라 “가상 disk image 안 block backend byte offset”이다.

관찰 목표:

  • mmap-write: mapping으로 쓴 데이터가 munmap() 뒤 파일에 남아야 한다.
  • mmap-clean: mapping으로 수정하지 않은 clean page가 원본 파일 변경을 덮어쓰면 안 된다.
  • mmap-exit: 명시적 munmap() 없이 process exit에서 write-back되어야 한다.
  • swap-file: file-backed page가 eviction 뒤에도 파일 내용을 잃지 않아야 한다.

정리

  • mmap write-back은 유저가 write() syscall을 호출하지 않아도 발생할 수 있다.
  • CPU의 store는 PTE dirty bit를 켜고, OS는 그 bit를 보고 file-backed page를 저장할지 판단한다.
  • PintOS에서는 file_backed_swap_out()과 do_munmap()이 dirty check와 file_write_at()을 연결해야 한다.
  • 마지막 page는 전체 4096B가 아니라 파일에 대응되는 read_bytes만 write-back해야 한다.
  • PintOS 파일 시스템은 byte offset write를 inode sector write로 바꾸고, QEMU는 그 결과인 IDE sector write만 처리한다.
  • QEMU는 mmap 정책을 모르며, guest PTE dirty bit 효과와 block backend I/O를 하드웨어처럼 보이게 한다.
