pml4_get_page() — PML4 walk으로 매핑 확인

확인 범위: 이 문서는 pml4_get_page()의 page table walk과 유저 포인터 매핑 확인 원리를 설명하고, 제시된 PintOS 코드와 Linux·Windows·QEMU 비교를 바탕으로 선택 기준과 한계를 정리한다. 코드 좌표, GDB 관찰 시나리오, 반환값 계산 및 동작·성능 관련 판단은 특정 소스 버전과 실제 실행 기록 또는 측정으로 별도 검증해야 한다.

한 줄 요약: pml4_get_page()는 유저 VA를 따라 4단계 page table walk을 수행한다. 매핑이 있으면 해당 프레임의 KVA를, 없으면 NULL을 반환한다. MMU의 자동 walk과 달리 pf를 일으키지 않으므로, syscall에서 유저 포인터가 실제로 매핑되어 있는지 확인하는 두 번째 단계로 사용할 수 있다.

유저 주소의 매핑을 확인하는 과정

syscall이 받은 유저 포인터를 커널에서 사용하려면 먼저 주소 범위와 실제 매핑을 구분해 확인해야 한다. is_user_vaddr()는 주소가 유저 영역, 즉 KERN_BASE 아래에 있는지 검사한다. 이 검사를 통과하더라도 해당 주소에 물리 프레임이 매핑되어 있다는 보장은 없다. pml4_get_page()는 이 두 번째 조건을 확인한다.

pml4_get_page()는 유저 가상 주소(uaddr)를 받아 4단계 page table walk을 수행한다. 매핑된 물리 프레임을 찾으면 커널이 접근할 수 있는 가상 주소(KVA)를 반환하고, 매핑이 없으면 NULL을 반환한다.

MMU의 walk과 다른 점

MMU와 pml4_get_page()는 같은 4단계 page table을 참조하지만, walk을 시작하는 조건과 매핑이 없을 때의 동작이 다르다.

  • MMU의 walk: 명령어를 실행하는 동안 자동으로 수행한다. TLB 캐시를 사용하며, present 엔트리를 찾지 못하면 pf가 발생한다.
  • pml4_get_page()의 walk: 소프트웨어가 명시적으로 호출한다. TLB을 거치지 않고 page table을 메모리에서 직접 읽으며, present 엔트리를 찾지 못하면 NULL을 반환한다.

커널 코드가 유저 포인터를 바로 dereference하면 매핑이 없을 때 pf가 발생할 수 있다. 그 전에 pml4_get_page()를 호출하면 예외를 발생시키지 않고 현재 매핑의 존재 여부를 확인할 수 있다. 다만 이 검사는 호출 시점에 present인 매핑만 찾으므로, 아직 적재되지 않은 lazy page까지 유효한 페이지로 판단하지는 못한다.

실제 OS와의 비교

Linux에서는 follow_page() 또는 __get_user_pages()가 비슷한 목적으로 page table을 소프트웨어적으로 walk한다. 이 과정은 pgd_offset() → p4d_offset() → pud_offset() → pmd_offset() → pte_offset_map() 체인으로 이어진다.

반면 Linux의 copy_from_user()와 copy_to_user()는 page table을 먼저 직접 walk하지 않는다. 유저 주소에 접근한 뒤 pf가 발생하면 fixup table을 통해 에러를 처리한다. 이는 page-fault-based validation을 실제 OS에서 사용하는 방식이다.

Windows의 MmProbeAndLockPages()는 유저 버퍼의 매핑을 확인하고 해당 물리 페이지를 잠근다.

PintOS 구현

호출은 다음 순서로 진행된다.

  1. **ASSERT(is_user_vaddr(uaddr))**는 커널 주소가 이 함수에 전달되지 않았는지 확인한다. 조건을 어기면 디버그 빌드에서 assertion failure가 발생한다.

  2. **pml4e_walk(pml4, va, 0)**은 create=0으로 4단계 walk을 수행한다.

    • 호출은 pml4e_walk() → pdpe_walk() → pgdir_walk() 순서로 이어진다.
    • 어느 단계에서든 엔트리가 not-present이면 새 테이블을 할당하지 않고 즉시 NULL을 반환한다.
    • 모든 중간 엔트리가 존재하면 최종 PT 엔트리의 주소를 반환한다.

  3. ***pte & PTE_P**는 최종 PT 엔트리의 present 비트를 검사한다. present가 아닌 PTE는 swap out되었거나, lazy page라서 아직 물리 프레임이 없는 상태일 수 있다.

  4. **ptov(PTE_ADDR(*pte)) + pg_ofs(uaddr)**는 물리 프레임 주소를 KVA로 바꾸고 원래 주소의 page offset을 더한다.

    • PTE_ADDR(*pte)는 PTE의 하위 12비트 플래그를 제거해 물리 프레임 주소를 얻는다.
    • ptov()는 물리 주소에 KERN_BASE를 더해 커널 가상 주소로 바꾼다.
    • pg_ofs(uaddr)는 원래 유저 주소의 12비트 page offset을 보존한다.

따라서 반환값은 커널이 해당 유저 데이터에 접근할 때 사용할 수 있는 KVA다.

syscall에서의 사용

첫 번째 조건은 주소가 유저 영역에 있는지 확인한다. 두 번째 조건은 그 주소에 현재 present인 물리 프레임이 실제로 연결되어 있는지 확인한다.

lazy page를 다룰 때의 한계

pml4_get_page()가 반환하는 값은 호출 시점의 매핑 상태다. lazy loading이나 swap-in이 필요한 페이지에는 아직 present인 매핑이 없으므로 NULL을 반환한다. VM 프로젝트에서 이 함수만으로 포인터를 검증하면 유효한 lazy page도 잘못 거부할 수 있다. 이런 페이지를 허용해야 하는 문맥에서는 page-fault-based validation이 더 적절하다.

pml4_set_page()와의 관계

pml4_set_page()는 create=1로 walk한다. 중간 테이블이 없으면 새로 할당한 뒤 매핑을 설정한다. pml4_get_page()는 create=0으로 호출하므로 기존 테이블을 읽을 뿐 새 매핑을 만들지 않는다.

QEMU에서의 실행

QEMU에서 pml4_get_page() 자체는 순수 소프트웨어 코드이므로 일반 명령어로 번역되어 실행된다. 다만 하드웨어 MMU의 page table walk을 소프트웨어로 따라간다는 점에서 QEMU의 SoftMMU와 다음처럼 비교할 수 있다.

반환값 계산 예시

pml4_get_page(pml4, 0x0804_8123)을 호출한다고 하자. VA 0x0804_8123이 물리 프레임 0x1234_5000에 매핑되어 있다고 가정한다.

walk 결과:
  PML4[0] → PDPT
  PDPT[0] → PD
  PD[66]  → PT   (0x0804_8000 >> 21 = 66)
  PT[72]  → PTE  (PTE 값: 0x1234_5067 = 0x1234_5000 | PTE_P | PTE_W | PTE_U | ...)

PTE_ADDR(0x1234_5067) = 0x1234_5067 & ~0xFFF = 0x1234_5000  (물리 프레임 주소)
ptov(0x1234_5000) = 0x1234_5000 + KERN_BASE = 0x1234_5000 + 0x80_0400_0000
                  = 0x80_1634_5000  (KVA)
pg_ofs(0x0804_8123) = 0x0804_8123 & 0xFFF = 0x123

반환값 = 0x80_1634_5000 + 0x123 = 0x80_1634_5123

커널은 계산된 KVA(0x80_1634_5123)를 통해 해당 유저 데이터에 접근할 수 있다.

매핑 상태에 따른 반환값은 다음과 같다.

상황walk 결과pml4_get_page 반환
매핑 완료PT[idx] presentKVA
UNINIT lazy pageSPT에만 존재, PML4에 없음NULL
Swap out된 pagePTE present=0, swap slot 정보NULL
완전 무효 주소어떤 테이블에도 없음NULL
