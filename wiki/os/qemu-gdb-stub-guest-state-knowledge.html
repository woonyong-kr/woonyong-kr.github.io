QEMU GDB Stub은 어떤 상태를 보여주는가

QEMU GDB Stub은 어떤 상태를 보여주는가

한 줄 요약: PintOS를 디버깅 모드로 실행했을 때 QEMU GDB stub이 보여주는 것은 host가 아니라 guest CPU와 memory의 상태다.

먼저 익힐 핵심 용어

QEMU GDB Stub을 이해하려면 다음 개념을 연결해서 익혀야 한다.

  • guest CPU state: CPUX86State, env->regs[], env->eip, env->eflags, env->cr[2], env->cr[3]
  • GDB register read: handle_get_reg(), handle_read_all_regs(), gdb_read_register(), x86_cpu_gdb_read_register()
  • GDB memory read: handle_read_mem(), gdb_target_memory_rw_debug(), cpu_memory_rw_debug(), guest virtual address
  • PintOS snapshot: struct intr_frame, f->R.rax, f->rip, f->error_code
  • VM 디버깅 연결
    • Page Fault GDB 관찰: CR2, RIP, SPT entry를 한 화면에서 대조하는 실습
    • PintOS byte 비교: user VA dump와 frame->kva + offset byte를 비교하는 실습

GDB가 보여주는 register는 누구의 것인가

PintOS를 --gdb로 실행한 뒤 GDB에서 다음 명령을 입력한다고 하자.

이때 보이는 RAX, RIP, memory byte가 어느 층의 상태인지 먼저 구분해야 한다.

  • Mac/Linux host CPU의 실제 register인가?
  • QEMU process 내부의 C 변수인가?
  • PintOS가 실제 하드웨어로 인식하는 guest CPU와 guest memory인가?

정답은 세 번째다. QEMU GDB stub에 연결한 GDB는 기본적으로 guest 관점의 CPU register와 memory를 보여준다.

여기서 이어지는 핵심 질문은 다음과 같다.

  • PintOS의 --gdb 옵션은 QEMU에 어떤 실행 인자를 전달하는가?
  • info registers는 QEMU가 보관한 guest CPU state의 어느 값을 읽는가?
  • x/16xb address는 host pointer와 guest address 중 무엇을 읽는가?
  • struct intr_frame snapshot과 현재 info registers 값은 왜 달라질 수 있는가?
  • GDB symbol과 QEMU memory read는 어떻게 결합되어 PintOS 구조체처럼 보이는가?

host와 guest를 구분해야 하는 이유

OS 디버깅에서 특히 주의할 오해는 GDB에 보이는 모든 값이 같은 층에 속한다고 생각하는 것이다. PintOS를 QEMU 위에서 실행하면 관찰 대상은 다음과 같이 나뉜다.

이 층을 섞으면 판단도 달라진다.

질문흔한 오해올바른 기준
info registers의 RAX는 무엇인가?host CPU의 RAXQEMU가 보관한 guest CPU의 RAX
x/16xb 0x8048123은 어디를 읽는가?host process 주소QEMU의 debug memory 경로를 통해 guest 주소를 읽는다
breakpoint는 누가 처리하는가?PintOS가 GDB server를 구현한다QEMU GDB stub이 guest 실행을 멈춘다
syscall의 의미는 누가 해석하는가?QEMU GDB stub이 해석한다PintOS syscall_handler()가 해석한다

따라서 GDB는 PintOS 내부에서 실행되는 프로그램이 아니다. QEMU가 제공하는 remote debugging 창을 통해 guest 상태를 관찰하는 외부 도구다.

관찰 흐름

처음에는 다음 모델을 기억하면 충분하다.

QEMU는 PintOS의 thread, fd, page, syscall가 운영체제 수준에서 무엇을 뜻하는지 알지 못한다.

QEMU가 아는 것QEMU가 모르는 것
guest register 값PintOS syscall 번호의 정책

breakpoint와 single-stepPintOS scheduler의 의도
guest CPU의 halt와 continuePintOS 테스트의 실패 원인

그런데도 GDB에서 struct thread를 볼 수 있는 이유는 QEMU가 struct thread를 이해하기 때문이 아니다. GDB가 kernel.o의 debug symbol을 알고 있고, QEMU가 해당 guest memory byte를 읽어 줄 수 있기 때문이다.

syscall_handler에서 두 register 상태 비교하기

PintOS에서 write(1, "hello", 5)를 실행하던 중 syscall_handler()에서 멈췄다고 하자.

이 장면에서는 서로 다른 두 register 관찰 결과가 함께 나타난다.

관찰의미
f->R.raxsyscall 진입 시 PintOS가 저장한 user register snapshot
info registers현재 멈춰 있는 guest CPU state

두 상태는 같을 수도 있고 다를 수도 있다. 예를 들어 syscall_handler()에 진입한 뒤 C 함수 호출이 진행되면 현재 guest register는 kernel C 코드를 실행하기 위해 바뀔 수 있다. 반면 f->R.rax는 syscall entry 시점의 snapshot이므로 사용자가 어떤 syscall을 요청했는지 판단하는 기준이 된다.

이 차이는 CPU 레지스터와 명령어 실행에서 설명하는 struct intr_frame과 직접 연결된다.

page fault에서 CR2와 RIP가 갈라지는 이유

Page fault를 관찰할 때도 현재 CPU state와 PintOS가 저장한 snapshot을 구분해야 한다. page_fault()에 breakpoint를 걸면 다음 값들이 한 화면에 함께 보일 수 있다.

관찰 값값이 속한 층답할 수 있는 질문
info registers cr2QEMU가 노출한 guest CPU state어떤 guest VA 접근이 실패했는가?
info registers rip현재 멈춘 guest CPU stateCPU가 지금 어느 명령을 실행하는가?
f->ripPintOS가 예외 진입 시 저장한 snapshotfault 처리 후 어느 user instruction으로 돌아가는가?
f->error_codePintOS struct intr_frame에 저장된 pf error codenot-present, write, user fault 중 무엇인가?
struct page *pagePintOS SPT metadatafaulting page를 복구할 근거가 있는가?

따라서 CR2와 RIP는 GDB에서 모두 register처럼 보이더라도 역할이 다르다.

QEMU 관점에서는 page walk 실패가 guest env->cr[2]를 갱신하고 pf를 발생시킨다. PintOS 관점에서는 page_fault()가 rcr2()로 그 값을 읽은 뒤 f->rip와 f->error_code를 확인하고 vm_try_handle_fault()로 전달한다. 이 값들을 직접 대조하는 절차는 Page Fault GDB에서 CR2와 SPT를 한 화면에 맞춰 보기에서 다룬다.

실제 운영체제 디버깅과 비교

실제 Linux의 일반 process를 GDB로 디버깅하면 GDB는 보통 ptrace 같은 kernel API를 통해 OS가 관리하는 process register와 address space를 읽는다. Windows debugger도 Windows debugging API와 kernel 지원을 통해 thread context, breakpoint, memory에 접근한다. Kernel debugging에는 별도의 transport와 권한 모델이 적용된다.

PintOS를 QEMU에서 실행하면 중간에 가상화 층이 하나 더 생긴다. Host OS에서 QEMU는 하나의 user process지만, QEMU GDB stub에 연결한 GDB는 QEMU의 C stack이 아니라 QEMU가 에뮬레이션하는 guest machine을 디버깅한다.

QEMU process 자체를 조사하려면 별도의 host GDB 또는 LLDB로 qemu-system-x86_64 process에 연결해야 한다. 이때 보이는 register와 stack은 QEMU 구현을 실행하는 host thread의 상태다.

PintOS가 QEMU GDB stub을 여는 과정

PintOS가 직접 GDB server를 구현하는 것은 아니다. PintOS 실행 스크립트는 --gdb 옵션을 받으면 QEMU 실행 인자에 -s와 -S를 추가한다.

  • -s: QEMU GDB server를 TCP 1234 port에 연다.
  • -S: guest CPU를 시작 직후 멈춘다.

QEMU 내부의 register와 memory read

QEMU에서는 GDB remote packet을 처리하는 공통 gdbstub 코드와 x86 register를 읽고 쓰는 target별 코드가 분리되어 있다.

Memory read도 비슷한 경로를 따른다.

QEMU system mode의 GDB memory 경로에는 physical memory mode도 있다. 다만 일반적인 GDB 주소는 guest CPU의 현재 주소 변환 맥락을 따르는 guest address로 이해할 수 있다. QEMU의 cpu_memory_rw_debug() 설명에서도 addr를 guest virtual address로 두고, 현재 CPU 설정에 따라 주소를 변환한 뒤 byte를 읽는 함수로 정의한다.

코드에서 근거 확인하기

1. PintOS 스크립트가 QEMU에 전달하는 옵션

PintOS 스크립트의 근거 파일은 -s -S이며, 실제 파일 좌표는 SW_AI-W11-pintos/pintos/utils/pintos에서 확인할 수 있다.

  • --gdb 옵션을 제공한다.
  • self.gdb가 true이면 QEMU command에 -s와 -S를 추가한다.
  • QEMU option의 의미는 qemu-options.hx에서 확인할 수 있다.
  • -S는 시작 시 guest CPU를 멈춘다.
  • -s는 -gdb tcp::1234의 축약형이다.

2. PintOS 문서에 나온 remote 연결 절차

근거 파일은 SW_AI-W11-pintos/docs/pintos/08-implementation-guide.md이다.

이때 연결하는 대상은 PintOS 내부 server가 아니라 QEMU GDB stub이다.

3. 공통 gdbstub에서 CPU callback으로 이어지는 흐름

근거 파일은 gdbstub/gdbstub.c와 include/hw/core/cpu.h이다.

  • handle_get_reg()는 gdb_read_register(gdbserver_state.g_cpu, ...)를 호출한다.
  • handle_read_all_regs()도 gdbserver_state.g_cpu->gdb_num_g_regs 범위를 순회하며 register를 읽는다.
  • CPUClass에는 gdb_read_register, gdb_write_register, memory_rw_debug callback이 있다.
  • x86 CPU class 초기화는 cc->gdb_read_register = x86_cpu_gdb_read_register를 통해 target별 구현을 연결한다.

4. x86 guest register를 읽는 위치

x86 gdbstub은 CPUX86State에서 값을 읽으며, 근거 파일은 target/i386/gdbstub.c과 target/i386/cpu.h이다.

  • 일반 register는 env->regs[...]에서 읽는다.
  • Instruction pointer는 env->eip에서 읽는다.
  • Flags는 env->eflags에서 읽는다.
  • Control register는 env->cr[0], env->cr[2], env->cr[3], env->cr[4]에서 읽는다.

이 guest CPU state는 cpu.h의 CPUArchState에 구조체 필드로 보관된다.

5. guest address를 읽는 memory debug 경로

근거 파일은 gdbstub/system.c와 system/physmem.c이다.

  • handle_read_mem()은 gdb_target_memory_rw_debug()로 이어진다.
  • System mode의 gdb_target_memory_rw_debug()는 physical mode가 아니면 cpu_memory_rw_debug()로 내려간다.
  • cpu_memory_rw_debug()는 page 단위로 debug translation을 수행하고 address_space_rw()로 byte를 읽거나 쓴다.
  • include/hw/core/cpu.h의 cpu_memory_rw_debug() 설명은 입력 주소를 guest virtual address로 정의한다.

따라서 GDB의 memory dump는 host pointer를 직접 읽는 것이 아니라 QEMU의 guest memory 경로를 통과한다.

실제 값이 해석되는 과정

1. register packet은 byte로 전송된다

설명을 위해 guest register가 다음 상태라고 하자.

x86-64 GDB register 전송에서는 값을 target byte order로 담는다. x86-64는 little-endian이므로 RIP = 0x80042123은 낮은 byte부터 전송된다.

GDB는 이를 다시 숫자로 해석해 rip 0x80042123처럼 표시한다. 즉, 화면에 보이는 숫자 표현과 QEMU protocol에서 오가는 byte를 구분해야 한다.

2. memory 명령의 주소는 guest address다

다음 명령을 생각해 보자.

PintOS page table이 이 user VA를 다음 guest PA에 mapping했다고 가정한다.

QEMU debug memory 경로는 현재 guest CPU의 주소 변환 기준으로 guest 주소를 읽는다. 그 위치에 "hello"가 있다면 GDB는 다음과 같이 표시할 수 있다.

이 byte는 host process 주소 0x8048123에서 가져온 것이 아니라 guest memory에서 읽은 결과다.

3. guest virtual address와 physical address 구분하기

QEMU system gdbstub에는 physical memory mode도 있으므로 현재 읽는 주소가 guest virtual address인지 guest physical address인지 확인해야 한다.

PintOS 과제에서 x/.. f->R.rsi처럼 user pointer를 확인할 때는 주로 guest virtual address 관점에서 본다. 반면 page table entry의 frame 주소를 따라갈 때는 guest physical memory 관점을 별도로 구분해야 한다.

1. QEMU가 1234 port에서 기다리는지 확인

다른 terminal에서는 다음을 실행한다.

GDB에서는 다음과 같이 연결한다.

이 연결은 QEMU의 -s 옵션이 연 GDB server로 향한다.

2. guest register와 snapshot 대조하기

intr_frame을 확인하려면 다음 관찰을 함께 수행한다.

  • info registers의 현재 rip는 kernel handler 내부를 가리키는가?
  • f->rip는 syscall 처리 후 돌아갈 user instruction 주소인가?
  • f->R.rax는 SYS_WRITE 같은 syscall 번호인가?
  • f->R.rsi가 user buffer 주소라면 x/5xb f->R.rsi로 byte를 확인할 수 있는가?

3. host QEMU process와 guest를 각각 관찰하기

동일한 QEMU 실행도 서로 다른 두 관찰자로 볼 수 있다.

관찰자연결 대상기대하는 값
PintOS용 GDBtarget remote localhost:1234guest register와 guest memory
host GDB/LLDBqemu-system-x86_64 processQEMU C 코드의 실행 상태

PintOS 과제를 디버깅할 때는 대개 첫 번째가 필요하며, QEMU 자체를 조사할 때 두 번째를 사용한다.

4. page fault에서 현재 register와 snapshot 맞추기

VM을 구현할 때는 page_fault()에서 guest register와 PintOS snapshot을 함께 본다.

확인 대상판단 기준
cr2 == fault_addrQEMU가 노출한 guest CR2와 PintOS가 rcr2()로 읽은 fault VA가 같은가?
f->rip와 info registers ripfault 당시 user instruction과 현재 handler 위치를 구분했는가?
f->error_code & PF_Pnot-present fault와 protection fault를 구분했는가?
x/16xb fault_addrQEMU GDB stub의 guest memory read 경로로 user VA byte를 읽는다는 점을 고려했는가?

이 확인 절차는 Page Fault GDB에서 CR2와 SPT를 한 화면에 맞춰 보기과 Page Fault 뒤 user VA와 frame offset 바이트 비교 Lab로 이어진다.

정리

  • PintOS --gdb는 QEMU에 -s -S를 전달해 QEMU GDB stub을 활성화한다.
  • GDB의 target remote localhost:1234는 PintOS 내부 server가 아니라 QEMU GDB stub에 연결된다.
  • info registers는 host CPU register가 아니라 QEMU가 보관한 guest CPU state를 보여준다.
  • x/.. address는 host process pointer를 직접 읽지 않고 QEMU debug memory 경로를 통해 guest memory를 읽는다.
  • PintOS 수준의 의미는 GDB symbol과 PintOS 자료구조를 통해 해석하며, hardware 상태를 관찰하는 창은 QEMU가 제공한다.
