세마포어, 락, 조건 변수: 잠들고 깨우는 구조를 구분하기

한 줄 요약: sema_down()·lock_acquire()·cond_wait()는 모두 스레드를 재우지만 답하는 질문이 다르다 — semaphore는 남은 토큰 수, lock은 임계 구역의 소유자, condition variable은 거짓 조건에서 잠들 곳과 깨워 줄 주체를 정한다.

왜 동기화 도구가 세 개나 필요할까

sema_down(), lock_acquire(), cond_wait()는 모두 스레드를 기다리게 만들 수 있다. 처음에는 모두 “잠깐 멈추는 함수”처럼 보이지만, 실제로는 서로 다른 질문에 답한다.

도구답하는 질문
semaphore지금 사용할 수 있는 토큰이 몇 개인가?
lock이 임계 구역의 주인이 누구인가?
condition variable조건이 아직 거짓이면 어디에서 잠들었다가 누가 깨워 주는가?

이 차이를 모르면 thread.elem이 어떤 waiters list에 들어갔는지, 왜 lock이 내부적으로 semaphore를 쓰는지, 왜 cond_wait()가 lock을 풀었다가 다시 잡는지 헷갈린다.

동기화는 공유 상태를 안전하게 바꾸는 순서를 만드는 일이다. 큐를 공유하는 생산자와 소비자를 보면 세 도구가 맡는 역할을 함께 볼 수 있다.

여기서는 세 가지 문제가 한꺼번에 생긴다.

  • 큐의 내부 포인터를 동시에 바꾸면 안 된다.
  • 큐가 비었으면 소비자는 CPU를 낭비하지 말고 자야 한다.
  • 생산자가 새 item을 넣으면 잠든 소비자 중 하나를 깨워야 한다.

lock은 큐의 공유 상태를 보호한다. condition variable은 큐가 비어 있는 동안 소비자가 잠들 장소와, 상태가 바뀌었을 때 깨우는 통로를 제공한다. semaphore는 더 낮은 레벨에서 “토큰이 없으면 잠들고, 토큰이 생기면 깨어난다”는 동작을 구현한다.

세 도구가 잠들고 깨우는 흐름

세마포어는 카운터와 대기열로 구성된다.

락은 “토큰이 1개뿐인 semaphore + holder 기록”이다.

조건 변수는 조건 자체를 저장하지 않는다. 실제 조건은 lock으로 보호받는 공유 상태에 있고, 조건 변수는 그 조건이 바뀌기를 기다리는 스레드가 잠드는 장소를 제공한다.

sequenceDiagram
    participant T as Consumer Thread
    participant L as Lock
    participant C as Condition Variable
    participant PS as Private Semaphore

    T->>L: lock_release(lock)
    T->>C: cond->waiters에 semaphore_elem 추가
    T->>PS: sema_down(&waiter.semaphore) → BLOCKED
    Note over T: 조건이 참이 될 때까지 잠듦

    Note right of C: ... Producer가 cond_signal() ...
    C->>PS: sema_up(&waiter.semaphore)
    PS->>T: UNBLOCK
    T->>L: lock_acquire(lock) → 다시 잡기
    T->>T: while(조건) 재검사

condition variable은 조건 검사를 대신하지 않는다. 깨어난 스레드는 lock을 다시 획득한 뒤 공유 상태의 조건을 재검사해야 하므로 보통 if가 아니라 while을 사용한다.

이 기본 흐름을 이해하면 구현을 살펴볼 때의 질문도 순서대로 정리된다.

  • 공유 상태를 보호하면서 조건이 맞을 때까지 CPU를 낭비하지 않고 기다리려면 어떤 도구가 필요한가?
  • 실제 OS는 mutex, semaphore, condition variable, wait queue, futex, dispatcher object 같은 대기·깨우기 구조를 어떻게 나누는가?
  • PintOS는 이 구조를 struct semaphore, struct lock, struct condition과 intrusive list로 어떻게 단순화하는가?
  • QEMU는 동기화 의미가 아니라 guest CPU 실행과 guest memory read/write 중 어느 부분을 흉내 내는가?
  • sema->value, thread.elem, semaphore_elem.elem 주소는 어떤 리스트 연결을 보여 주는가?
  • GDB에서는 sema_down(), sema_up(), cond_wait(), cond_signal()의 waiters list와 thread status를 어디서 확인하는가?

세마포어 값과 대기 순서

세마포어 값이 0인 상태에서 세 스레드가 기다린다고 하자.

PintOS의 이 코드베이스는 sema_down()에서 waiter를 priority 내림차순으로 넣고, sema_up()에서 list_sort()로 다시 정렬한다.

priority-sema 테스트는 이 순서를 확인한다.

조건 변수는 semaphore를 한 단계 더 감싼다.

  • cond->waiters (semaphore_elem list):
  • semaphore_elem A | | semaphore_elem B
  • .semaphore | | .semaphore
  • .value = 0 | | .value = 0
  • .waiters: | | .waiters:
  • [Thread A] | | [Thread B]

cond_signal()은 cond.waiters 안의 private semaphore들을 비교해서, 그 semaphore 안에서 기다리는 스레드 priority가 가장 높은 쪽을 고른다.

실제 운영체제에서는 무엇이 달라지는가

앞의 구조는 “공유 상태 보호”, “대기”, “깨우기”라는 역할을 구분하기 위한 모델이다. 실제 운영체제에서도 이 역할은 필요하지만, 실행 문맥과 지원 정책이 더 다양하므로 하나의 단순한 대기열 구조로 일반화할 수 없다.

Linux 사용자 공간에는 POSIX mutex, condition variable, semaphore가 있으며, 내부적으로 futex 같은 커널 대기 원시 연산과 연결될 수 있다. 커널 내부에는 wait queue, spinlock, mutex, rwsem, completion 같은 더 많은 도구가 있다.

이름이 비슷해도 구현과 보장 범위는 다르다. 어떤 lock은 sleep할 수 있고, 어떤 lock은 interrupt context에서 써서는 안 되며, 어떤 lock은 priority inheritance를 지원한다. 따라서 도구를 구분할 때는 이름만 보지 말고, 스레드가 잠들 수 있는지와 어떤 실행 문맥에서 사용할 수 있는지, 어떤 스케줄링 정책이 결합되는지를 함께 봐야 한다.

Windows도 mutex, semaphore, condition variable, event, SRWLOCK 같은 여러 동기화 도구를 제공한다. Windows 커널은 dispatcher object와 wait 상태를 통해 스레드를 재운다. 이 구조를 PintOS처럼 struct thread.elem 하나를 직접 waiters list에 넣는 형태로 일반화하면 안 된다.

현실 OS에서 구조가 더 복잡해지는 이유는 다음과 같다.

  • 여러 CPU가 동시에 같은 자료구조에 접근한다.
  • interrupt context, user thread context, kernel worker context가 나뉜다.
  • timeout, cancellation, alertable wait, priority boost, realtime scheduling 같은 정책이 붙는다.
  • 메모리 배리어와 원자 연산이 필요하다.

이 차이를 기준으로 보면 PintOS는 동기화 의미를 학습할 수 있도록 자료구조와 실행 경로를 작게 드러낸 구현이고, QEMU는 그 PintOS 코드가 실행되는 더 낮은 층을 제공한다.

PintOS가 세 도구를 구현하는 방식

PintOS의 동기화 도구는 threads/synch.c와 include/threads/synch.h에 모여 있다.

세마포어는 남은 토큰 수인 value와 토큰을 기다리는 스레드 list인 waiters를 가진다. waiter list의 원소는 struct thread.elem이다.

락은 현재 owner인 holder와 초기값 1인 semaphore를 가진다. priority donation은 lock holder를 알 수 있을 때만 의미가 있다.

조건 변수의 waiters는 struct semaphore_elem list다. 각 semaphore_elem 안에는 private semaphore가 하나 있으며, 실제로 잠드는 스레드는 이 private semaphore의 waiters에 들어간다.

연산실제 동작
sema_down()value>0이면 value—, 아니면 thread.elem을 waiters에 넣고 block
sema_up()waiters 정렬 후 하나 unblock, value++
lock_acquire()donation 설정 → sema_down(&lock->semaphore) → holder 설정
lock_release()donation 해제 → holder=NULL → sema_up(&lock->semaphore)
cond_wait()private sema 생성 → cond->waiters에 추가 → lock 해제 → sema_down → lock 재획득
cond_signal()cond->waiters 정렬 → 최고 priority의 private sema를 sema_up

여기서는 thread.elem의 재사용 제약이 중요하다. struct thread의 elem은 ready_list와 semaphore waiters에서 함께 쓰이지만, 한 스레드가 두 상태에 동시에 있지 않기 때문에 가능하다.

상태thread.elem이 들어갈 수 있는 곳
READYready_list
BLOCKED on semaphoresema->waiters
BLOCKED on sleepsleep_list

반대로 우선순위 기부: lock을 기다리는 스레드가 holder를 밀어 올리는 이유의 donation_elem은 별도 필드다. lock을 기다리는 스레드는 semaphore waiters에 elem으로 들어가는 동시에 holder의 donation list에는 donation_elem으로 들어갈 수 있기 때문이다.

QEMU가 담당하는 경계

QEMU는 semaphore, lock, condition variable의 의미를 해석하지 않는다.

  • guest CPU가 sema_down() 같은 PintOS 커널 함수를 실행한다.
  • guest memory 안의 struct semaphore, struct lock, struct condition, struct list_elem 바이트가 바뀐다.
  • GDB stub을 통해 guest register와 guest memory를 읽을 수 있다.
  • timer interrupt 같은 하드웨어 사건은 QEMU 장치 모델과 interrupt controller를 통해 guest에 전달될 수 있다.

sema->waiters에 어떤 스레드가 들어갔다는 의미는 PintOS가 만든다. QEMU는 그 주소의 바이트를 보관하고 접근을 에뮬레이션할 뿐이다.

구분semaphorelockcondition variable
실제 OS커널/라이브러리별로 timeout, cancellation, PI 등 정책이 붙을 수 있음mutex, spinlock, rwlock 등으로 세분화wait queue와 mutex 재획득 규칙이 복잡

PintOS 코드에서 확인하는 구현

semaphore는 value와 waiters다

PintOS: SW_AI-W11-pintos/pintos/include/threads/synch.h

sema_down()은 value가 0이면 현재 스레드의 elem을 waiters에 넣고 block한다.

PintOS: SW_AI-W11-pintos/pintos/threads/synch.c

sema_up()은 waiters를 priority 순서로 정렬한 뒤 하나를 ready 상태로 돌린다.

이 흐름은 스레드 스케줄러 (Thread Scheduler) Trace의 thread_block()과 thread_unblock()으로 이어진다.

lock은 binary semaphore에 owner를 더한다

PintOS: SW_AI-W11-pintos/pintos/include/threads/synch.h

초기화할 때 semaphore value를 1로 둔다.

획득은 semaphore down 뒤 holder를 현재 스레드로 바꾼다.

해제는 holder를 비우고 semaphore up으로 waiter를 깨운다.

이 holder 필드 때문에 priority donation도 가능해진다. semaphore 자체에는 owner가 없으므로 누구에게 priority를 빌려줄지 알 수 없다.

condition variable은 private semaphore를 사용한다

PintOS: SW_AI-W11-pintos/pintos/threads/synch.c

cond_wait()은 stack 위에 semaphore_elem waiter를 만들고 cond->waiters에 넣는다.

여기에는 두 단계 list가 있다.

  • cond->waiters는 semaphore_elem.elem을 담는다.
  • 각 private semaphore의 waiters는 thread.elem을 담는다.

cond_signal()은 condition waiters를 동적 priority 기준으로 정렬한 뒤 private semaphore를 up한다.

비교 함수는 각 private semaphore의 waiters에서 가장 앞 스레드를 꺼내 priority를 비교한다.

이 구현은 signal 시점에 private semaphore waiters에서 실제 blocked thread를 읽어 priority를 판단한다. 따라서 cond_signal()을 디버깅할 때는 cond->waiters만 보지 말고 각 private semaphore의 waiters까지 내려가야 한다.

테스트가 확인하는 기대 순서

PintOS 테스트에는 다음 파일이 있다.

  • SW_AI-W11-pintos/pintos/tests/threads/priority-sema.c
  • SW_AI-W11-pintos/pintos/tests/threads/priority-condvar.c
  • SW_AI-W11-pintos/pintos/tests/threads/priority-donate-sema.c

priority-sema.c는 semaphore에서 가장 높은 priority thread가 먼저 깨어나는지 본다. priority-condvar.c는 cond_signal()이 cond_wait() 중인 스레드 가운데 가장 높은 priority를 깨우는지 본다.

priority-donate-sema.c는 lock donation과 semaphore blocking이 함께 섞인 순서를 만든다. 낮은 priority L이 lock을 들고 semaphore에서 자고, 높은 priority H가 그 lock을 기다려 L에게 donation한다. main이 semaphore를 올리면 L이 먼저 깨어나 lock을 풀고 H가 이어서 진행한다.

semaphore waiters에 들어가는 주소

가정: thread T가 주소 0x8004_7000에 있고, elem 필드의 offset이 0x18이라면, sema_down()에서 waiters list에 들어가는 주소는 T 자체가 아니라 T->elem 주소다.

waiters의 원소를 thread로 되돌릴 때는 다음처럼 해석한다.

condition variable의 두 단계 주소

cond->waiters를 struct thread로 바로 캐스팅하면 틀린다. 먼저 struct semaphore_elem으로 되돌린 뒤 그 안의 semaphore waiters를 봐야 한다.

semaphore value 변화

초기값 0 semaphore에서 한 스레드가 기다리고 나중에 up이 호출되면 다음 순서로 값이 바뀐다.

  • 시점 | sema->value | waiters | 동작
  • 초기 | 0 | []
  • T1 down | 0 (유지) | [T1] | value==0 → T1 block
  • T2 up | 1 | [] (T1 꺼냄) | T1 unblock, value++
  • T1 재개 | 0 | [] | value— (while 루프 탈출)

기다리는 스레드가 없으면 sema_up()은 waiters에서 원소를 꺼내지 않고 value만 증가시킨다.

관찰 시나리오

priority-sema에서 sema_up이 고르는 스레드

  1. watch-sema-up 정의 후 priority-sema 테스트 실행
  2. 여러 스레드가 sema_down에서 block된 후, main이 sema_up 할 때마다 “waking=xxx(pri=NN)” 출력
  3. priority 내림차순으로 깨워지는지 확인 (63→62→61…)
  4. 중간에 dump-sema-waiters &sema 실행하여 waiters list가 priority 순 정렬인지 확인

lock contention과 priority donation

  1. watch-lock-contention과 watch-lock-release 정의 후 priority-donate-one 실행
  2. H가 lock을 요청할 때 “CONTENTION: thread=H(pri=31) wants lock held by L(pri=21)” 출력
  3. L이 lock_release 할 때 “priority before release: 31” → “priority after release: 21”로 priority 복원 확인

이 시나리오는 관찰 절차와 기대 상태를 제시한다. 문서 안에는 실제 실행 결과가 포함되어 있지 않으므로, 출력 순서와 priority 변화는 GDB에서 직접 확인해야 한다.

다시 구분하는 기준

semaphore는 value와 waiters로 토큰이 없을 때 잠들고 토큰이 생겼을 때 깨우는 흐름을 만든다. lock은 value 1인 semaphore에 holder를 붙여 owner가 있는 임계 구역을 만든다. condition variable은 조건 자체가 아니라 조건이 바뀔 때까지 잠드는 장소이며, PintOS의 cond_wait()은 private semaphore를 만들고 cond_signal()은 그 semaphore를 sema_up()한다.

이 의미와 구현을 관찰하는 층도 구분해야 한다. PintOS는 waiters list와 스레드 상태를 관리하고, QEMU는 그 의미를 해석하지 않은 채 guest CPU 실행과 guest memory의 바이트를 에뮬레이션한다.
