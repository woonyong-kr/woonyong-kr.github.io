list_elem 구조

list_elem 구조

한 줄 요약: KAIST x86-64 PintOS의 여러 리스트가 공유하는 16바이트 intrusive 노드 struct list_elem 구조. 32-bit PintOS에서는 같은 구조가 8바이트다.

list_elem 구조 상태

KAIST x86-64 PintOS의 ready_list, sleep_list, waiters, donation_list 등은 struct list_elem 노드로 원소를 연결한다. 이 노드는 8바이트 포인터 두 개로 이루어져 전체 크기가 16바이트다. 32-bit Stanford PintOS에서는 포인터가 4바이트이므로 struct list_elem은 8바이트이고, 이를 두 개 포함하는 struct list는 16바이트다.

리스트가 struct thread*를 직접 보관하는 것은 아니다. thread 구조체 안에 침투(intrusive) 방식으로 내장된 list_elem을 연결하고, list_entry() 매크로를 사용해 list_elem의 주소에서 바깥 구조체의 주소를 역산한다.

상세 설명

추상 개념 (Intrusive vs Non-intrusive)

리스트 구현 방식은 노드와 데이터를 분리하는 Non-intrusive 방식과, 데이터 구조체 안에 링크 필드를 넣는 Intrusive 방식으로 나눌 수 있다.

전략노드 구조장점단점
Non-intrusive별도 노드가 데이터 포인터를 보관한 원소가 여러 리스트에 자유롭게 참여malloc 필요, 캐시 분산
Intrusive데이터 구조체 안에 링크 필드 내장malloc 불필요, 캐시 지역성 우수한 elem 필드는 한 리스트에만 참여 가능

커널 환경에서는 malloc 비용이 크고 인터럽트 컨텍스트에서 호출할 수 없기 때문에 Linux 커널의 struct list_head와 PintOS는 모두 Intrusive 방식을 사용한다.

실제 OS (Linux)

Linux 커널의 struct list_head는 PintOS의 list_elem과 거의 같은 형태다.

바깥 구조체의 주소를 역산하는 매크로도 이름만 다르다.

Linux의 task_struct에는 tasks, run_list, wait_dequeue_entry 등 여러 list_head가 있다. 각 필드는 서로 독립적이므로 하나의 task_struct가 여러 리스트에 동시에 참여할 수 있다.

PintOS 구현

struct list_elem (include/lib/kernel/list.h):

struct list — sentinel 기반 이중 연결 리스트:

리스트를 초기화하면 head.next → tail, tail.prev → head로 연결된다. 빈 리스트에도 두 sentinel이 존재하므로 순회할 때 NULL을 검사할 필요가 없다.

thread 안의 list_elem (include/threads/thread.h):

하나의 elem 필드는 한 번에 하나의 리스트에만 들어갈 수 있다. READY 상태의 thread는 보통 ready_list에 있고, RUNNING 상태에서는 스케줄링 리스트에 속하지 않는다. BLOCKED 상태에서는 sema->waiters 같은 동기화 대기열이나 구현에 따라 sleep_list에 들어간다. 같은 elem을 두 리스트에 동시에 넣으면 두 리스트가 공유하는 prev/next 링크가 깨진다.

donation_elem은 elem과 별개의 필드다. 따라서 thread는 elem으로 한 리스트에 참여하면서도 donation_elem으로 다른 thread의 donation_list에 참여할 수 있다.

list_entry 매크로:

list_entry()는 LIST_ELEM의 next 필드 주소에서 해당 멤버가 바깥 구조체 안에서 차지하는 오프셋을 뺀다. 이 계산으로 바깥 구조체의 시작 주소를 얻는다.

순회 패턴

PintOS에서는 다음과 같은 순회 패턴을 반복해서 사용한다.

list_begin()은 head.next를 반환하고, list_end()는 &tail을 반환한다. 빈 리스트에서는 head.next가 곧 &tail이므로 순회 조건이 처음부터 거짓이 된다.

list_elem 구조 값 추적

다음은 struct thread 안에서 elem의 오프셋을 계산하는 예시다. 실제 값은 구조체 배치에 따라 달라진다.

struct thread 시작 주소: 0x8004_2000
elem 오프셋 (offsetof):  예를 들어 136 (0x88)
elem 주소:               0x8004_2088
elem.prev:               0x8004_2088 + 0 = 0x8004_2088
elem.next:               0x8004_2088 + 8 = 0x8004_2090

list_entry(e, struct thread, elem) 계산:
  &e->next = 0x8004_2090
  offsetof(struct thread, elem.next) = 136 + 8 = 144
  result = 0x8004_2090 - 144 = 0x8004_2000  ← thread 시작 주소 복원!

이 예시에서 &e->next는 0x8004_2090이고, offsetof(struct thread, elem.next)는 144다. 두 값을 빼면 struct thread의 시작 주소인 0x8004_2000을 복원할 수 있다.

메모리 크기는 다음과 같다.

  • KAIST x86-64: struct list_elem 16 bytes, struct list 32 bytes
  • 32-bit PintOS: struct list_elem 8 bytes, struct list 16 bytes
  • sentinel 두 개가 구조체 자체에 포함되므로 빈 리스트도 각각 32 bytes(x86-64), 16 bytes(32-bit)를 차지한다
  • 정확한 크기와 elem.next 오프셋은 대상 ABI에서 sizeof·offsetof로 확인한다
