guest physical ≠ host physical ≠ host virtual

guest physical ≠ host physical ≠ host virtual

한 줄 요약: QEMU에서 동시에 존재하는 세 주소 — GPA·HVA·HPA의 구분.

guest physical ≠ host 상태

QEMU 에뮬레이션 환경에서 메모리 주소는 세 종류가 동시에 존재하며, 각각 완전히 다른 주소 공간에 속한다. Guest Physical Address(GPA)는 게스트 OS가 보는 물리 주소, Host Virtual Address(HVA)는 QEMU 프로세스의 가상 주소, Host Physical Address(HPA)는 호스트 CPU의 실제 물리 주소다. 이 셋을 혼동하면 GDB 디버깅, 메모리 덤프, PintOS palloc 분석에서 잘못된 해석을 하게 된다.

상세 설명

추상 개념 — 네 단계 주소 변환

에뮬레이터 위에서 OS를 실행할 때 주소 변환은 네 단계를 거친다:

각 단계의 주체와 규칙이 다르다:

각 주소의 구체적 의미

GPA (Guest Physical Address)

게스트 OS가 “물리 메모리”라고 믿는 주소다. PintOS에서 palloc_get_page(PAL_USER)가 반환하는 커널 VA에서 KERN_BASE를 빼면 GPA가 된다. E820 맵으로 BIOS가 게스트에 알려준 범위 내에서만 유효하다.

  • PintOS 기본 설정: 0x00000000 ~ 0x07FFFFFF (128 MB)
  • 0x00000000 ~ 0x000FFFFF: BIOS/legacy 영역
  • 0x00100000 (1 MB) ~: 커널 로드 시작점
  • CR3 레지스터에 저장되는 PML4 base도 GPA다

HVA (Host Virtual Address)

QEMU 프로세스가 mmap()으로 할당한 영역의 주소다. QEMU는 게스트 메모리 전체를 하나의 큰 mmap 블록으로 잡고, GPA를 이 블록의 offset으로 변환한다.

HVA = RAMBlock.host + (GPA - RAMBlock.offset)

예를 들어 RAMBlock.host가 0x7f0000000000이고 GPA가 0x00100000이면:

HVA = 0x7f0000000000 + 0x00100000 = 0x7f0000100000

QEMU의 address_space_rw(), address_space_map() 등이 이 변환을 수행한다.

HPA (Host Physical Address)

호스트 하드웨어의 실제 DRAM 주소다. QEMU 소프트웨어 에뮬레이션(TCG)에서는 HPA를 직접 다룰 일이 없다. 호스트 OS의 MMU가 HVA → HPA를 투명하게 처리한다. KVM 하드웨어 가상화에서는 EPT(Extended Page Table) 또는 NPT(Nested Page Table)가 GPA → HPA 직접 변환을 수행한다.

GDB에서 보는 주소는 어느 것인가?

QEMU의 GDB stub을 통해 디버깅할 때:

GDB 명령해석하는 주소근거
info registers → RIPGVA게스트 CPU의 instruction pointer
info registers → CR3GPAPML4 물리 base
x/Nx addrGVAGDB가 guest MMU walk를 수행
monitor xp/Nx addr (QEMU monitor)GPAQEMU가 RAMBlock으로 직접 접근

따라서 x/x $cr3은 CR3 값을 GVA로 해석하려 시도하므로 의미 없다. CR3에 담긴 GPA를 읽으려면 QEMU monitor의 xp 명령을 써야 한다.

TCG vs KVM: 주소 변환 경로의 차이

PintOS는 QEMU TCG(소프트웨어 에뮬레이션)로 실행된다. KVM(하드웨어 가상화)과 주소 변환 경로가 근본적으로 다르다:

항목TCG (PintOS 사용)KVM
GVA → GPAQEMU가 소프트웨어로 PML4 walk 수행guest CPU가 HW로 walk
GPA → HPARAMBlock mmap (HVA 경유)EPT/NPT가 HW로 직접 변환
TLBQEMU 내부 softmmu TLB (소프트웨어)CPU HW TLB + EPT TLB
pf 처리QEMU가 감지 → guest에 예외 주입CPU가 직접 guest pf 발생
성능느림 (매 메모리 접근에 소프트웨어 개입)빠름 (HW 이중 page walk)

TCG에서 cpu_ldl_data() 같은 함수가 guest 메모리를 접근할 때마다 softmmu TLB를 확인하고, miss면 address_space_rw()로 GPA → HVA 변환을 수행한다. SoftMMU TLB의 구조와 fast/slow path 상세는 주소 변환 효과 재현 — QEMU의 MMU 에뮬레이션에서 다룬다.

SoftMMU TLB가 주소 계층을 연결하는 방식

SoftMMU TLB는 GVA → HVA를 한 번에 매핑한다. 이것이 핵심이다. GVA → GPA → HVA를 매번 2단계로 수행하면 느리므로, TLB hit 시에는 addend 필드로 GVA에서 HVA를 직접 계산한다:

addend = HVA_of_page_start - GVA_of_page_start
HVA = GVA + addend

이 addend는 GPA → HVA 변환(RAMBlock offset)과 GVA → GPA 변환(page table walk 결과)을 합친 값이다. TLB miss 시에만 두 단계를 분리해서 수행한 뒤, 합산된 addend를 TLB에 캐시한다.

PintOS에서의 구체적 예: 전체 변환 Walk-through

유저 프로그램이 전역 변수 int x(GVA=0x400040)를 읽는 상황:

1. Guest CPU (에뮬레이션): GVA 0x400040
   PML4[0] → PDPT[0] → PD[2] → PT[0] → PTE.frame = 0x200 (GPA page)
   GPA = 0x200000 + 0x040 = 0x200040

2. QEMU softmmu: GPA 0x200040
   RAMBlock.host = 0x7f0000000000 (mmap base)
   HVA = 0x7f0000000000 + 0x200040 = 0x7f0000200040

3. Host OS (macOS): HVA 0x7f0000200040
   macOS page table → HPA (투명, QEMU가 관여 안 함)

PintOS vtop() 매크로는 GVA → GPA를 계산한다:
