TLB와 CR3 주소 공간 전환

TLB와 CR3 주소 공간 전환

한 줄 요약: 두 프로세스가 같은 가상 주소를 써도 충돌하지 않는 까닭은 CR3가 현재 주소 공간의 페이지 테이블 루트를 가리키기 때문이다. 컨텍스트 스위치에서 CR3를 바꾸면 주소 공간이 통째로 전환되며, 이때 이전 매핑이 남은 TLB를 어떻게 비우는지를 본다.

같은 가상 주소는 어떻게 서로 다른 메모리를 가리키는가

프로세스 A와 프로세스 B가 모두 0x8048123이라는 가상 주소를 사용한다고 하자. CPU가 이 주소를 어느 프로세스의 메모리로 해석할지는 현재 선택된 주소 공간에 따라 달라진다.

이 문제는 주소 변환과 컨텍스트 스위치가 만나는 지점에서 드러난다. 주소 변환만 보면 VA를 page table을 거쳐 PA로 바꾸는 과정으로 끝난다. 컨텍스트 스위치만 보면 레지스터와 스택을 교체하는 과정으로 보인다. 그러나 실행할 유저 프로세스가 바뀌면 주소를 해석할 때 기준으로 삼는 page table도 함께 바뀌어야 한다.

가상 주소는 프로세스마다 독립적으로 사용할 수 있는 번호다.

따라서 숫자가 같아도 어느 프로세스의 주소 공간에서 해석하느냐에 따라 연결되는 물리 프레임은 달라질 수 있다. CPU에는 현재 주소 변환에 사용할 page table root를 가리키는 레지스터가 필요하며, x86-64에서는 대표적으로 CR3가 이 역할을 한다.

page table을 메모리에 접근할 때마다 처음부터 끝까지 걷는 데에는 비용이 든다. x86-64 4단계 page table에서는 최악의 경우 PML4, PDP, PD, PT를 거쳐 실제 데이터에 접근하기까지 메모리를 여러 번 읽어야 한다. CPU는 이 비용을 줄이려고 최근 주소 변환 결과를 TLB(Translation Lookaside Buffer)에 캐시한다.

주소 공간을 전환할 때에는 다음 두 작업을 함께 고려해야 한다.

해야 할 일이유
CR3를 새 page table root로 바꾼다같은 VA를 새 프로세스 기준으로 해석해야 한다
낡은 TLB entry를 버리거나 구분한다이전 프로세스의 VA -> PA 번역을 재사용하면 격리가 깨진다

TLB miss는 필요한 번역이 캐시에 없다는 뜻이다. 이때 page table walk를 거쳐 번역을 정상적으로 얻을 수도 있다. page fault는 page table walk를 완료할 수 없거나 접근 권한이 맞지 않아 예외가 발생한 상태다.

실제 운영체제가 추가로 다루는 문제

Linux와 Windows도 프로세스별 주소 공간을 관리하며, context switch 때 현재 주소 변환의 기준을 바꾼다. 다만 실제 OS에서는 여러 CPU와 성능 및 보안 문제까지 함께 고려해야 하므로 PintOS보다 처리 과정이 복잡하다.

실제 OS의 추가 고려왜 필요한가
TLB shootdown여러 CPU가 같은 주소 공간의 낡은 TLB entry를 들고 있을 수 있다
PCID/ASID 계열 최적화주소 공간이 바뀌어도 TLB 전체를 매번 버리지 않기 위해
global page커널 공통 mapping처럼 자주 쓰는 entry를 유지하기 위해
KPTI 같은 보안 설계유저/커널 page table 분리로 side-channel 위험을 줄이기 위해
huge page큰 범위를 적은 TLB entry로 덮어 성능을 높이기 위해

실제 OS는 CR3가 바뀔 때마다 TLB 전체를 단순히 flush하는 방식에만 의존하지 않는다. CPU 기능과 SMP 환경을 고려해 필요한 번역을 구분하거나 무효화하면서 전환 비용을 줄인다.

Windows는 Linux와 내부 이름 및 자료구조가 다르다. 그러나 프로세스 주소 공간을 하드웨어 page table root와 연결하고, 다른 프로세스의 스레드로 전환할 때 주소 변환 기준을 맞춰야 한다는 문제는 같다.

PintOS에서 주소 공간이 전환되는 과정

PintOS에서는 이 과정을 비교적 단순한 흐름으로 볼 수 있다.

next->pml4는 다음에 실행할 유저 프로세스의 page table root다. PintOS의 구현에는 다음과 같은 단순화가 있다.

항목PintOS의 단순화
단일 CPU 중심 학습실제 SMP TLB shootdown을 구현하지 않는다
단순 주소 공간 전환process_activate()가 곧바로 pml4_activate()를 호출한다
공통 커널 mappingpml4_create()가 base_pml4를 복사해서 커널 주소는 어느 프로세스 page table에서도 계속 보이게 한다

PintOS의 schedule()은 현재 커널 코드가 실행 중인 상태에서 다음 스레드의 pml4를 활성화한다. 전환 뒤에도 커널 코드와 커널 스택에 계속 접근할 수 있는 이유는 각 프로세스의 PML4에 커널 영역 mapping이 공통으로 들어 있기 때문이다.

PintOS는 특정 page의 PTE를 변경한 뒤 그 page가 현재 활성 주소 공간에 속하면 invlpg로 해당 TLB entry만 무효화한다.

이 경로는 page table을 바꾼 뒤 TLB에 남아 있을 수 있는 낡은 번역도 함께 처리해야 한다는 점을 보여준다.

QEMU가 재현하는 CR3와 TLB

QEMU는 PintOS의 스케줄러나 VM 정책을 이해해 처리하는 것이 아니라, x86 CPU처럼 보이는 실행 환경을 제공한다.

PintOS가 movq ..., %cr3 명령을 실행하면 QEMU TCG 경로에서는 control register write helper가 호출되고, CR3 값이 QEMU의 guest CPU state에 저장된다.

여기서 QEMU의 tlb_flush()는 host CPU의 실제 TLB를 직접 비운다는 뜻이 아니다. QEMU가 guest 주소 변환을 빠르게 재현하려고 내부에 유지하는 translation cache를 버린다는 뜻이다.

주소 변환을 수행할 때에도 QEMU는 현재 guest CR3를 기준으로 page walk를 시작한다.

따라서 PintOS에서는 CPU에 CR3를 쓰는 동작으로 보이고, QEMU 내부에서는 guest CPU state의 env->cr[3]를 변경한 뒤 낡은 guest translation cache를 비우는 동작으로 나타난다.

구현 계층 비교

구분CR3를 어떻게 보는가TLB를 어떻게 다루는가
Linux / Windows실제 CPU의 현재 page table rootPCID, global page, shootdown 등으로 비용 최적화
PintOSnext->pml4의 물리 주소를 mov %cr3로 로드전체 정책은 단순하지만 invlpg로 현재 page의 낡은 번역을 지움
QEMUguest CPU state의 env->cr[3]QEMU 내부 guest translation cache를 flush

이 세 계층에서 같은 이름이 가리키는 대상을 혼동하지 않아야 한다.

  • PintOS의 pml4는 guest OS가 만든 page table이다.
  • QEMU의 env->cr[3]는 guest CPU가 가진 것처럼 보이는 CR3 상태다.
  • host macOS/Linux의 실제 CR3와 host CPU TLB는 여기서 직접 보는 대상이 아니다.

GDB로 확인할 지점

PintOS를 QEMU+GDB로 실행한다면 다음 순서로 주소 공간 전환을 확인할 수 있다. 아래 항목은 확인할 지점과 질문이며, 실제 실행 결과를 뜻하지 않는다.

1. context switch에서 CR3가 바뀌는지 보기

확인할 질문:

  • next가 바뀔 때 next->pml4도 바뀌는가?
  • pml4_activate() 직전과 직후의 cr3 값이 달라지는가?
  • 커널 스레드나 종료 경로에서 base_pml4로 돌아가는 순간이 있는가?

2. 같은 VA가 다른 frame으로 가는지 보기

프로세스별로 같은 upage가 다른 kpage로 연결되는 순간을 찾으면 가상 주소 숫자가 같더라도 주소 공간에 따라 의미가 달라지는 과정을 확인할 수 있다.

3. PTE를 지운 뒤 invlpg가 호출되는지 보기

확인할 질문:

  • rcr3() == vtop(pml4) 조건이 참인가?
  • 참이면 invlpg(vpage) 경로로 들어가는가?
  • 현재 활성 주소 공간이 아니면 왜 지금 당장 invlpg가 필요하지 않은가?

4. QEMU 쪽에서 보고 싶다면

QEMU를 디버그 빌드로 따라갈 수 있다면 다음 지점을 살펴본다.

이 계층에서는 PintOS 함수 이름이 보이지 않는다. guest instruction의 효과가 env->cr[3] 변경과 tlb_flush() 호출로 나타난다.

다시 설명할 때 확인할 관계

  • CR3는 현재 주소 공간의 page table root를 가리킨다.
  • TLB는 최근 VA page → PA frame 번역 결과를 저장하는 캐시다.
  • TLB miss는 캐시 실패이고, page fault는 page table walk 또는 권한 검사 실패다.
  • context switch로 유저 프로세스가 바뀌면 레지스터와 스택뿐 아니라 주소 변환 기준도 바뀌어야 한다.
  • PintOS는 schedule()에서 process_activate(next)를 호출하고, pml4_activate()가 movq ..., %cr3로 내려간다.
  • QEMU는 guest CR3를 env->cr[3]에 저장하고, paging 중이면 내부 TLB cache를 flush한다.
  • 실제 Linux와 Windows는 PCID, global page, TLB shootdown 같은 최적화와 SMP 문제까지 다룬다.
