인터럽트 프레임 레지스터 스냅샷 (Intr Frame Register Snapshot)

인터럽트 프레임 레지스터 스냅샷 (Intr Frame Register Snapshot)

확인 범위: 이 문서는 인터럽트 프레임이 실행 상태를 저장·복원·복제·조립하는 일반 원리와 PintOS·Linux·QEMU에서의 대응 관계를 설명한다. 제시된 파일·함수·크기·레지스터 배치와 GDB 출력 예시는 특정 코드와 실행 환경에 의존하므로, 실제 적용 여부와 값은 해당 소스·버전 및 직접 실행 기록으로 별도 검증해야 한다.

한 줄 요약: struct intr_frame은 CPU 실행 상태(하드웨어가 push한 SS/RSP/RFLAGS/CS/RIP + 소프트웨어가 push한 RAX~R15/DS/ES)를 통째로 얼린 스냅샷으로, interrupt·syscall·context switch·fork(rax=0만 변경)·최초 user 진입(do_iret) 다섯 장면이 모두 같은 구조체를 저장·복원·복제·조립 단위로 재사용한다.

인터럽트 프레임 레지스터 스냅샷 상태

struct intr_frame은 CPU의 전체 실행 상태를 메모리에 얼려두는 스냅샷이다. 레이아웃 자체는 struct intr frame 레이아웃에서 다루므로, 이 문서에서는 “왜 스냅샷이 필요한가”, “어디서 찍히고 어디서 복원되는가”, “한 장의 스냅샷이 OS 전체에서 어떻게 재사용되는가”에 집중한다.

핵심 아이디어: CPU는 레지스터 집합으로 구동되며, 실행 상태를 전환하려면 레지스터를 통째로 바꿔야 한다. intr_frame은 이 “바꿔치기”의 단위 — 하나의 실행 흐름(thread, process, interrupt handler)이 중단될 때 레지스터 값을 저장하는 틀이자, 재개될 때 복원할 값의 원본이다.

상세 설명

추상 개념 (CPU 하드웨어 규칙)

x86-64 CPU에서 인터럽트나 예외가 발생하면 하드웨어가 RFLAGS, CS, RIP를 스택에 push하고, privilege level이 바뀔 때만 old SS와 old RSP를 추가한다. 일부 예외는 error code도 push한다. 이것이 하드웨어 스냅샷의 최소 단위다.

소프트웨어(OS)는 이 위에 범용 레지스터(RAX~R15), 세그먼트 레지스터(DS, ES)를 추가로 push하여 완전한 스냅샷을 만든다. 이 전체가 struct intr_frame이다.

저장 주체저장되는 레지스터크기
CPU 하드웨어RFLAGS, CS, RIP; 권한 전환 시 old SS/RSP; 일부 예외는 error_code24~48 bytes
소프트웨어 (intr_entry)RAX~R15, DS, ES, vec_no나머지

스냅샷의 5가지 사용 장면

intr_frame이 “단순 저장 구조체”가 아닌 이유는, OS의 핵심 메커니즘 5가지가 모두 같은 구조체를 재사용하기 때문이다.

%% intr_frame의 5가지 사용 장면
flowchart LR
  frame["&quot;struct intr_frame<br/>CPU 실행 상태 스냅샷&quot;<br/>shape=box<br/>penwidth=1.4"]
  interrupt["① Interrupt handling<br/>timer IRQ 등 외부 인터럽트<br/>복귀"]
  syscall["② Syscall 처리<br/>user에서 kernel 진입<br/>user 복귀"]
  context_switch["③ Context switch<br/>thread A frame 저장<br/>thread B frame 복원"]
  fork_scene["④ fork<br/>부모 frame 복사<br/>rax = 0만 변경"]
  first_entry["⑤ 최초 user mode 진입<br/>load()가 frame 조립<br/>do_iret()"]
  frame --> interrupt
  frame --> syscall
  frame --> context_switch
  frame --> fork_scene
  frame --> first_entry

①~② 은 “같은 흐름의 중단/재개” — 한 thread가 커널에 들어갔다 나올 때 자기 frame을 복원한다.

③ 은 “다른 흐름으로 전환” — schedule()이 다음 thread의 frame을 do_iret()에 넘긴다. CPU는 frame에 적힌 RIP로 점프하므로, frame을 바꾸면 실행 흐름이 바뀐다.

④ 는 “복제” — fork는 부모의 frame을 memcpy한 뒤 rax = 0만 바꾼다. 자식이 do_iret()로 복원하면 부모와 같은 PC에서 시작하되, fork()의 반환값만 다르다.

⑤ 는 “조립” — 아직 실행된 적 없는 프로그램을 위해 frame을 수동으로 채운다. e_entry → RIP, USER_STACK → RSP, SEL_UCSEG → CS 등.

실제 OS (Linux)

Linux에서 동등한 구조체는 struct pt_regs (arch/x86/include/asm/ptrace.h). 역할과 구조가 거의 동일하다. Linux도 fork 시 부모의 pt_regs를 자식에게 복사하고 regs->ax = 0으로 설정한다 (copy_thread_tls).

QEMU 에뮬레이션

QEMU TCG에서 인터럽트가 발생하면 do_interrupt_all() (target/i386/excp_helper.c)이 guest CPU 상태에서 RFLAGS, CS, RIP를 guest 스택에 push하는 동작을 에뮬레이션한다. CPL 3→0 전환에서는 old SS와 old RSP도 추가한다. 이 결과가 guest OS가 보는 intr_frame의 하드웨어 부분이다.

QEMU 내부 경로 (long mode, CPL 3→0 전환):

%% QEMU long mode 인터럽트 진입 흐름
flowchart TD
  start["do_interrupt_all()"]
  interrupt64["do_interrupt64()<br/>target/i386/excp_helper.c"]
  idt["1. IDT에서<br/>게이트 디스크립터 읽기"]
  push["3. guest 스택에 push<br/>SS(old), RSP(old), RFLAGS,<br/>CS(old), RIP, [error_code]"]
  tss["2. CPL 3→0이면 TSS의 rsp0 읽기<br/>new_stack = env-&gt;tr.base + rsp0_offset"]
  jump["4. env-&gt;eip = gate.offset<br/>handler 주소로 점프"]
  start --> interrupt64
  interrupt64 --> idt
  idt --> tss
  tss --> push
  push --> jump

핵심: QEMU는 CPUX86State 구조체의 regs[R_ESP], eflags, segs[].selector 등을 읽어 guest 메모리(x86_stq_phys)에 기록한다. 이 push된 값들이 guest OS(PintOS)의 intr_entry가 범용 레지스터를 추가로 push해서 완성하는 intr_frame의 하드웨어 부분이다.

소프트웨어 push 부분 (intr_entry)은 QEMU 입장에서 일반 명령어 실행이다 — pushq %rax, pushq %rbx 등이 순차적으로 Translation Block(TB)으로 번역되어 실행될 뿐, 특별한 에뮬레이션이 필요 없다.
