Timer Calibration: loops_per_tick은 왜 부팅 때 재는가

Timer Calibration 시작

이 문서에서는 PintOS가 부팅 중 loops_per_tick을 측정하는 이유를 살펴보고, 긴 sleep과 sub-tick busy-wait를 구분하는 기준을 코드 흐름 및 QEMU의 역할과 연결해 설명한다.

PintOS는 부팅할 때 다음과 같은 메시지를 출력한다.

여기서 한 가지 의문이 생긴다.

이미 8254 PIT가 1초에 100번 timer interrupt를 만들어 주는데, 왜 커널은 다시 loops_per_tick을 측정할까?

핵심은 timer interrupt와 busy-wait가 서로 다른 시간 범위를 담당한다는 데 있다.

  • timer interrupt는 tick 단위의 시간 기준을 만든다.
  • timer_sleep()은 1 tick 이상 기다릴 때 현재 스레드를 BLOCKED 상태로 전환한다.
  • timer_usleep()처럼 1 tick보다 짧은 시간은 스레드를 재우기 애매하므로 busy_wait()로 근사한다.
  • timer_calibrate()는 이 busy-wait에 필요한 기준값을 부팅할 때 한 번 측정한다.

Timer Calibration이 필요한 이유

PintOS의 기본 timer interrupt 주파수는 TIMER_FREQ = 100이다.

따라서 PintOS가 timer interrupt만으로 구분하기 쉬운 시간 단위는 대략 다음과 같다.

timer_sleep(10) 같은 요청은 자연스럽게 처리할 수 있다. 현재 tick이 100이라면 wake_tick = 110에 깨우면 된다.

하지만 timer_usleep(500)은 다르다. 500 us는 0.5 ms이고, 1 tick은 10 ms다. 즉 500 us는 한 tick보다 훨씬 짧다. 이 요청을 sleep_list에 넣어 기다리게 하면 다음 timer interrupt가 올 때까지 최대 10 ms 가까이 지연될 수 있다.

그래서 PintOS는 대기 방식을 다음과 같이 나눈다.

요청 시간PintOS 방식이유
1 tick 이상timer_sleep()CPU를 양보하고 BLOCKED 상태가 되는 편이 낫다
1 tick 미만busy_wait()다음 tick을 기다리기에는 시간 단위가 너무 거칠다

여기서 busy_wait()는 빈 루프를 반복할 뿐이다.

따라서 커널은 다음 질문에 답할 수 있어야 한다.

현재 QEMU guest 환경에서 “한 tick 동안” 빈 루프를 대략 몇 번 실행할 수 있을까?

그 답이 loops_per_tick이다.

Timer Calibration 구조

처음에는 다음 흐름으로 기억하면 된다.

  • timer_calibrate() 실행
  • interrupt가 켜진 상태에서 측정
  • 빈 루프를 실행하면서 ticks의 변화를 관찰
  • 결과: loops_per_tick = “한 tick 안에 실행되는 빈 루프 수”

loops_per_tick은 CPU의 절대 성능을 나타내는 값이 아니다.

더 정확히는 현재 실행 환경에서 PintOS의 빈 루프가 timer tick 하나가 지나는 동안 대략 몇 번 실행되는지를 나타내는 값이다.

timer_usleep(500)을 호출하는 경우

timer_usleep(500)을 호출하는 상황을 살펴보자.

PintOS의 real_time_sleep()은 먼저 요청 시간을 tick 수로 환산한다.

정수 나눗셈 결과가 0이므로 이 요청은 1 tick보다 짧다고 판단한다.

따라서 PintOS는 스레드를 BLOCKED 상태로 보내지 않고 busy_wait()를 사용한다. 500 us는 10,000 us, 즉 1 tick의 0.05배이므로 loops_per_tick의 0.05배만큼 빈 루프를 실행한다.

반대로 timer_msleep(25)라면 계산 결과가 달라진다.

1 tick 이상이므로 timer_sleep(2)로 내려간다. 이때 실제 벽시계 시간은 호출 시점이 tick 경계의 어디에 있었는지에 따라 달라질 수 있다. 중요한 점은 25 ms를 정확히 맞춘다는 뜻이 아니라 정수 tick 두 개를 기준으로 재운다는 것이다.

실제 운영체제

실제 OS도 긴 기다림과 매우 짧은 지연을 구분한다.

Linux 커널에는 timer, hrtimer, scheduler sleep, delay loop처럼 시간을 처리하는 여러 경로가 있다. 일반적인 thread sleep은 CPU를 양보하는 방식으로 처리하지만, 장치 초기화나 매우 짧은 hardware timing에는 busy-wait 계열의 지연이 사용될 수 있다.

Windows도 thread wait, waitable timer, high-resolution counter와 커널 내부의 짧은 spin/delay 경로를 구분한다.

실제 OS가 PintOS보다 복잡한 이유는 다음과 같다.

  • CPU frequency scaling
  • multicore와 per-CPU timer
  • high-resolution timer
  • tickless idle
  • 전력 관리
  • 실시간성 요구

그래도 핵심 판단 기준은 같다.

flowchart TD
    A[sleep 요청] --> B{요청 시간 ≥ 1 tick?}
    B -- Yes --> C[스레드를 BLOCKED로<br/>CPU 양보]
    B -- No --> D[busy-wait로<br/>짧게 루프]

PintOS는 이 판단을 ticks > 0인지 아닌지로 단순화한다.

PintOS

PintOS의 부팅 과정에서 timer 관련 초기화는 세 단계로 나뉜다.

sequenceDiagram
    participant Init as init.c main()
    participant Timer as timer.c
    participant Thread as thread.c
    participant PIT as 8254 PIT

    Timer->>PIT: count = 11932 → I/O port 0x40
    Timer->>Timer: intr_register_ext(0x20, timer_interrupt)
    Init->>Thread: thread_start()
    Thread->>Thread: intr_enable() → interrupt ON
    Init->>Timer: timer_calibrate()
    Timer->>Timer: loops_per_tick = 1024
    loop 대략 측정 (2배씩)
        Timer->>Timer: too_many_loops(loops_per_tick << 1)
    end
    loop 정밀 측정 (비트 시험)
        Timer->>Timer: too_many_loops(high_bit | test_bit)
    end
    Timer->>Init: printf("loops/s")

timer_calibrate()는 interrupt가 켜진 상태에서만 동작한다.

그 이유는 too_many_loops()가 ticks의 변화, 즉 timer interrupt가 발생한 결과를 기준으로 판단하기 때문이다.

핵심 흐름은 다음과 같다.

flowchart TD
    A[too_many_loops 진입] --> B[tick 경계 대기: while ticks == start]
    B --> C[start = ticks 갱신]
    C --> D[busy_wait loops 회]
    D --> E{start != ticks?}
    E -- Yes --> F[return true: 한 tick보다 길다]
    E -- No --> G[return false: 한 tick 안에 끝남]

true은 “이만큼의 loop는 한 tick 안에 끝내기에는 너무 많다”는 뜻이다.

QEMU

QEMU는 loops_per_tick을 알지 못한다.

QEMU의 역할은 PintOS가 사용하는 8254 PIT와 interrupt line을 에뮬레이션하는 것이다.

근거 파일은 다음과 같다.

  • include/hw/timer/i8254.h
    • PIT_FREQ
    • i8254_pit_init()
  • hw/isa/piix.c
    • i8254_pit_init(isa_bus, 0x40, 0, NULL)
  • hw/timer/i8254.c
    • timer_new_ns(QEMU_CLOCK_VIRTUAL, pit_irq_timer, s)
    • pit_irq_timer_update()
    • qemu_set_irq()

각 층의 역할을 나누면 다음과 같다.

  • PintOS (Guest OS)
  • timer_calibrate() → loops_per_tick
  • timer_sleep() → BLOCKED
  • busy_wait() → 빈 루프
  • QEMU (Emulator)
  • i8254 PIT 에뮬레이션
  • pit_irq_timer → IRQ0 → vector 0x20
  • guest CPU 명령 실행 (TCG)

따라서 QEMU가 “PintOS의 busy-wait를 보정한다”고 이해하면 안 된다.

QEMU는 timer tick이 들어올 수 있는 하드웨어 환경을 제공하고, 보정은 guest OS인 PintOS가 자신의 코드로 수행한다.

여기서 ticks == 0이면 요청 시간이 1 tick 미만이다.

PintOS는 이 경우 scheduler에 맡기지 않고 현재 CPU에서 짧게 루프를 실행한다.

Timer Calibration 값 추적

1. PIT count 계산

PintOS는 TIMER_FREQ=100을 목표로 PIT count를 계산한다.

따라서 channel 0은 대략 11,932 input cycles마다 출력을 바꾸어 100 Hz tick에 가까운 interrupt를 만든다.

QEMU의 PIT_FREQ는 1,193,182로 정의되어 있다. 두 값은 8254 PIT의 표준 입력 주파수를 각 코드에서 근사한 값이다. 이 문서의 핵심인 1 tick ~= 10ms 판단에서는 같은 모델로 이해해도 된다.

2. loops/s 메시지는 어떻게 나오는가

timer_calibrate()의 출력은 다음 계산에서 나온다.

출력이 49,152,000 loops/s라고 가정하면 내부 값은 대략 다음과 같다.

이 값이 “CPU clock이 50 MHz다”라는 뜻은 아니다.

현재 환경에서 빈 루프와 barrier()가 초당 그 정도 반복된다는 의미에 가깝다.

3. 500 us busy-wait 계산

timer_usleep(500)은 0.05 tick에 해당한다.

loops_per_tick = 500,000이라고 가정하면 필요한 loop 수는 대략 다음과 같다.

실제 PintOS 코드는 overflow 가능성을 줄이기 위해 식을 나누어 계산한다.

4. ticks와 loops_per_tick은 서로 다른 역할을 한다

항목ticksloops_per_tick

timer_ticks()가 interrupt를 잠시 끄고 ticks를 읽는 이유도 이 차이에서 나온다.

64비트 ticks를 읽는 도중 timer interrupt가 끼어들어 값이 바뀌는 상황을 피하기 위한 것이다.

  • too_many_loops()는 busy_wait() 전후에 ticks가 바뀌었는지 확인한다.

2. real_time_sleep() 분기 보기

timer_usleep(500) 같은 호출에서는 다음 값을 확인한다.

ticks == 0이면 busy_wait()로 내려간다.

timer_msleep(25) 같은 호출에서는 다음 값을 확인한다.

ticks > 0이면 timer_sleep()로 내려간다.

3. QEMU host GDB와 PintOS GDB stub 구분하기

PintOS GDB stub에서 b timer_interrupt를 설정하면 guest kernel 함수에서 멈춘다.

반면 QEMU 자체를 host GDB로 실행해 b pit_irq_timer_update를 설정하면 QEMU host process의 함수에서 멈춘다.

두 디버거는 같은 사건을 서로 다른 층에서 관찰한다.

  • PintOS GDB stub (guest 관점)
  • b timer_interrupt → guest kernel 함수
  • p ticks → guest 전역변수
  • p loops_per_tick → guest 전역변수
  • Host GDB (QEMU process 관점)
  • b pit_irq_timer_update → QEMU host 함수
  • p s->channels[0].count → QEMU PIT 내부 상태

이 구분은 QEMU GDB Stub은 어떤 상태를 보여주는가와 함께 살펴보면 더 분명해진다.

정리

  • TIMER_FREQ=100이면 PintOS의 기본 timer tick은 약 10 ms다.
  • timer_sleep()은 1 tick 이상 기다릴 때 스레드를 BLOCKED 상태로 보내 CPU를 양보한다.
  • 1 tick보다 짧은 지연은 timer interrupt 단위로 표현하기 어려우므로 busy_wait()를 사용한다.
  • timer_calibrate()는 부팅 중 ticks의 변화를 관찰해 한 tick 안에 실행되는 loop 수를 loops_per_tick으로 저장한다.
  • QEMU는 loops_per_tick을 알지 못한다. QEMU는 PIT와 IRQ의 하드웨어 효과를 에뮬레이션하고, PintOS는 그 tick을 이용해 자체 보정값을 만든다.
