PintOS User Programs 실행 경계와 System Call

PintOS User Programs 실행 경계와 System Call

범위: 이 문서는 x86-64의 유저·커널 실행 경계와 시스템 콜, PintOS의 프로그램 적재·인자 전달·포인터 검증 및 QEMU의 하드웨어 효과 재현을 설명하고 구현 선택 기준과 관찰 절차를 제시한다. 구체적인 코드 경로·구조체 offset·상수·Linux/Windows 비교와 GDB 시나리오의 동작 여부 및 성능 판단은 특정 소스 버전과 실제 빌드·실행·측정 기록을 대조해야 하는 검증 대상이며, 본문만으로 검증 결과를 뜻하지 않는다.

한 줄 요약: ELF를 적재하고 유저 모드로 전환해 main을 실행하는 과정과, 커널-유저 경계에서의 system call.

User-Kernel 경계 차이

사용자 프로그램은 커널 안의 함수가 아니다. 디스크에 있는 ELF 실행 파일을 읽어 메모리에 올리고, 유저 모드로 전환해서 main(argc, argv)를 실행해야 한다. 이 전환의 핵심은 커널 모드와 유저 모드 사이의 경계다. 유저 프로그램이 커널 기능을 쓸 때는 반드시 시스템 콜이라는 좁은 문을 통과해야 하며, 커널은 유저가 넘긴 포인터를 신뢰해서는 안 된다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

x86-64 CPU는 Current Privilege Level(CPL)로 현재 실행 중인 코드의 권한을 구분한다. CPL 0은 커널 모드, CPL 3은 유저 모드다. 유저 모드에서는 I/O 포트 접근, 페이지 테이블 변경, 인터럽트 플래그 조작 같은 특권 명령을 실행할 수 없다.

유저가 커널 기능을 요청하는 유일한 경로는 syscall 명령이다. 이 명령이 실행되면 CPU는 자동으로 다음을 수행한다:

  1. RCX ← 유저 RIP (돌아갈 주소 보존)
  2. R11 ← RFLAGS (유저 플래그 보존)
  3. RIP ← MSR_LSTAR 값 (커널 진입점)
  4. CPL 0으로 전환

돌아갈 때는 sysretq 또는 iretq가 CPL 3으로 복원한다.

실제 OS (Linux/Windows)

Linux에서 유저 프로그램 실행 경계는 PintOS보다 훨씬 복잡하다:

PintOS 구현

PintOS는 이 복잡한 세계를 네 가지 핵심 과제로 축소한다:

과제 1: ELF 적재와 주소 공간 구성

process_exec() → load() → load_segment() → setup_stack()

ELF 헤더에서 PT_LOAD 세그먼트를 읽고, 코드/데이터를 유저 주소 공간에 배치한다. 스택은 USER_STACK (0x47480000) 아래로 자란다.

과제 2: Argument Passing

명령줄 "echo hello pintos"가 주어지면 커널은 유저 스택에 다음을 배치해야 한다:

주소            내용                 설명
0x4747ffed      "echo\0"            argv[0] 문자열
0x4747fff2      "hello\0"           argv[1] 문자열
0x4747fff8      "pintos\0"          argv[2] 문자열 (끝에 \0 포함하면 fff8~fffe)
              ... padding ...       8바이트 정렬
0x4747ffd0      0x0                 argv[3] = NULL sentinel
0x4747ffd8      0x4747fff8          argv[2] 주소
0x4747ffe0      0x4747fff2          argv[1] 주소
0x4747ffe8      0x4747ffed          argv[0] 주소
              ... fake return ...
RSP →         argc=3, argv 포인터    RDI=3, RSI=argv 주소

이 배치가 틀리면 유저의 main(argc, argv)는 시작 직후부터 엉뚱한 값을 읽는다.

과제 3: System Call 연결

유저 프로그램은 파일 열기, 화면 출력, 프로세스 대기를 직접 할 수 없다. 모든 커널 기능은 시스템 콜을 통해 요청한다:

유저: write(1, "hello", 5)
  → RAX = SYS_WRITE (10)
  → RDI = 1  (fd)
  → RSI = 문자열 주소
  → RDX = 5  (크기)
  → syscall 명령
  → 커널: syscall_handler(f)
  → f->R.rax에서 번호 읽기
  → f->R.rdi/rsi/rdx에서 인자 읽기
  → 결과를 f->R.rax에 저장
  → iretq로 유저 복귀

과제 4: 유저 포인터 검증

유저가 넘긴 주소가 유효한 유저 영역인지 반드시 확인해야 한다. 확인 없이 커널이 유저 포인터를 역참조하면, 악의적 프로그램이 커널 메모리를 읽거나 덮어쓸 수 있다.

검증 방법은 두 가지다:

방법구현장단점
사전 검증is_user_vaddr() + pml4_get_page()안전하지만 느림
page fault 기반접근 후 fault 시 프로세스 종료빠르지만 구현 복잡

QEMU 에뮬레이션

QEMU는 유저-커널 경계의 의미를 모른다. QEMU가 재현하는 것은 하드웨어가 하는 일뿐이다.

SYS_WRITE가 무엇인지, fd 1이 stdout인지는 QEMU가 아닌 PintOS 커널이 해석한다.

QEMU가 syscall 명령을 만나면 helper_syscall()이 실행된다. 이 함수는 x86-64 ISA 매뉴얼대로 다음을 수행한다:

QEMU TCG에서 이 과정이 일어나는 코드 경로:

QEMU 파일함수역할
target/i386/tcg/emit.c.incgen_SYSCALL()TCG IR 생성: helper_syscall 호출 코드 방출
target/i386/tcg/system/seg_helper.chelper_syscall()실제 레지스터 전환 로직: RCX/R11 저장, MSR_LSTAR→RIP
target/i386/cpu.hCPUX86State.msr_lstarguest MSR_LSTAR 값 보관

sysretq도 마찬가지다. PintOS syscall-entry.S의 마지막 sysretq를 QEMU가 만나면 helper_sysret()이 CPL 3으로 되돌리고, RCX→RIP, R11→RFLAGS를 복원한다.

QEMU 관점에서 syscall 전후의 guest state 변화:

QEMU가 syscall의 하드웨어 효과만 재현하고 의미를 해석하지 않는다는 증거는, QEMU가 RAX 값을 절대 변경하지 않는다는 점이다. RAX를 SYS_WRITE에서 반환값으로 바꾸는 것은 PintOS의 syscall_handler()다.

유저 모드에서 특권 명령(CR3 쓰기, hlt, I/O 포트 접근 등)을 실행하면 QEMU는 raise_exception()으로 gp(0) fault를 guest에 전달한다. PintOS는 이를 받아 해당 프로세스를 종료한다.

Linux vs PintOS syscall 경로 심화 비교

syscall 진입에서 복귀까지의 경로를 단계별로 비교하면 PintOS가 어디를 단순화했는지 드러난다.

단계Linux (x86-64)PintOS
MSR_LSTAR 설정syscall_init() → entry_SYSCALL_64syscall_init() → syscall_entry
스택 전환per-CPU cpu_current_top_of_stack (GS base)TSS의 rsp0에서 읽기
레지스터 저장push로 pt_regs 구성 (168B)push로 intr_frame 구성 (184B)
번호 검증cmp __NR_syscall_max, 범위 초과 시 -ENOSYS번호별 switch-case, default는 thread_exit()
syscall tablesys_call_table[nr] 함수 포인터 배열switch(f->R.rax) 분기문
유저 포인터 접근copy_from_user() (fault handler + extable)is_user_vaddr() + pml4_get_page() 또는 page fault 기반
복귀sysretq (빠른 경로) 또는 iretq (signal 처리 등)sysretq (정상) 또는 do_iret() (fork 자식 첫 실행 등)
signal 처리exit_to_user_mode() → signal delivery없음

PintOS에서 sysretq 대신 do_iret()을 쓰는 경우는 다음과 같다: fork된 자식의 첫 실행, process_exec()로 새 프로그램을 시작할 때. 이 경우 유저 RIP/RSP/RFLAGS를 직접 지정해야 하므로 iretq가 필요하다.

RCX와 R11이 0으로 push되는 이유: CPU가 syscall 시 RCX에 유저 RIP를, R11에 RFLAGS를 덮어쓰기 때문에 원래의 유저 RCX/R11은 이미 파괴되었다. 대신 유저 RIP는 rip 필드에, RFLAGS는 eflags 필드에 따로 저장된다.

복귀 경로(sysretq 직전)에서는 역순으로 pop한 뒤, RCX에 유저 RIP를, R11에 RFLAGS를 복원하고, RSP를 유저 스택으로 되돌린 뒤 sysretq를 실행한다.

관찰 시나리오

시나리오 1: syscall 진입부터 복귀까지 전체 레지스터 흐름

args-single one 테스트에서 write syscall 하나를 전체 추적:

  1. syscall-frame-dump 정의 후 실행
  2. RAX=10(SYS_WRITE), RDI=1(stdout), RSI=buf, RDX=size 확인
  3. tss-rsp0-watch 병행하여 커널 스택 상단 주소 확인
  4. return-path-watch로 sysretq 경로에서 RCX에 유저 RIP가 복원되는지 확인
  5. 복귀 후 유저 코드가 RAX에 반환값(쓴 바이트 수)을 받는지 확인

이 시나리오로 user wrapper → syscall 명령어 → syscall_entry.S → syscall_handler → sysretq → user 전체 왕복을 register 수준에서 검증한다.

시나리오 2: 잘못된 포인터가 exit(-1)로 이어지는 경로

bad-read 테스트에서 유저가 커널 주소를 역참조:

  1. user-ptr-fail-watch 정의 후 실행
  2. page fault 발생: addr=0x(커널 주소), user=1 확인
  3. validate 실패 → exit(-1) 호출 추적
  4. exit(-1) 결과가 부모의 wait()으로 전달되는지 확인

시나리오 3: fork 후 자식의 syscall이 부모와 다른 커널 스택을 사용하는지 확인

  1. tss-rsp0-watch 정의 후 fork-once 실행
  2. process_activate에서 부모와 자식의 rsp0가 다른 주소를 가리키는지 확인 (각 thread의 page 상단)
  3. 자식이 syscall 진입 시 RSP가 자식의 커널 스택 범위 내에 있는지 syscall-frame-dump로 확인
