File-backed Page 복사 (fork SPT copy)

File-backed Page 복사 (fork SPT copy)

한 줄 요약: fork()가 SPT를 복사할 때 file-backed page는 프레임 전체를 복사하는 대신 같은 파일의 같은 offset을 가리키는 새 page 메타데이터를 만든다. 이 글에서는 부모와 자식이 파일 영역을 참조하면서도 쓰기 독립성(MAP_PRIVATE의 COW 시맨틱)을 지키는 방식을 살펴본다.

File-backed Page 복사 구조

fork()가 부모의 SPT를 자식에게 복사할 때는 file-backed page와 anonymous page에 서로 다른 전략을 적용해야 한다. file-backed page에는 원본 파일이라는 backing store가 있으므로 frame 내용을 그대로 복제하는 것보다 같은 파일의 같은 offset을 가리키는 새 page 메타데이터를 만드는 것이 핵심이다. 부모와 자식은 같은 파일 영역을 참조하지만, 쓰기 결과는 서로 독립적이어야 한다.

상세 설명

추상 개념(OS 일반 규칙)

POSIX fork() 시맨틱에서는 mmap 영역도 자식 프로세스에 이어진다. 먼저 일반적인 속성 관계를 정리하면 다음과 같다.

속성부모자식
가상 주소동일 VA동일 VA
backing file같은 파일, 같은 offset같은 파일, 같은 offset
dirty 상태부모의 현재 상태fork 시점의 snapshot
frame 공유MAP_PRIVATE → COWMAP_PRIVATE → COW

Linux의 MAP_PRIVATE mmap은 fork 시 COW로 처리된다. 처음에는 부모와 자식이 같은 physical frame을 공유하되 writable 비트를 끈다. 이후 어느 한쪽이 쓰기를 시도하면 page fault가 발생하고 해당 frame이 분리된다.

반면 MAP_SHARED mmap은 fork 후에도 부모와 자식이 같은 physical frame을 계속 공유하므로, 한쪽에서 쓴 결과가 다른 쪽에도 보인다.

PintOS 구현

이 문서에서 확인한 PintOS 구현은 MAP_SHARED를 지원하지 않고 모든 mmap을 private 시맨틱으로 처리한다. 따라서 fork 시 자식에는 독립된 복사본이 필요하다.

아래 세 가지 상태 구분은 OS 일반 규칙이 아니라, 이 문서가 확인 대상으로 삼은 supplemental_page_table_copy()의 분기와 관련 구현을 바탕으로 정리한 것이다.

Case 1: UNINIT(FILE) — 아직 fault가 발생하지 않은 상태

부모가 mmap()으로 등록했지만 아직 접근하지 않은 page다. 이 상태에서는 page->operations->type == VM_UNINIT이고 page->uninit.type에 VM_FILE 비트가 있다.

복사할 때는 vm_alloc_page_with_initializer()로 자식 SPT에 같은 타입의 UNINIT page를 등록한다. 이 과정에서는 aux 구조체를 deep copy해야 한다. aux에 struct file *, off_t offset, size_t read_bytes, size_t zero_bytes가 들어 있기 때문이다.

다음은 이 설명의 근거로 확인한 실제 구현 uninit_copy()(vm/uninit.c L74–99)이다.

구현의 처리 순서는 다음과 같다. 먼저 malloc으로 aux를 shallow copy한 뒤 file_reopen()으로 file을 분리하고, 마지막으로 vm_alloc_page_with_initializer()를 사용해 자식 SPT에 등록한다. 이때 uninit.init은 lazy_load_file 함수 포인터를 그대로 복사한다.

%% UNINIT FILE page의 aux deep copy와 file_reopen
flowchart LR
  parent_page["부모 SPT page<br/>VA: 0x400000<br/>type: UNINIT<br/>aux: file_a"]
  parent_aux["struct lazy_load_arg<br/>file: file_a<br/>ofs: 0<br/>read: 4096"]
  child_page["자식 SPT page<br/>VA: 0x400000<br/>type: UNINIT<br/>aux: file_b"]
  child_aux["struct lazy_load_arg<br/>file: file_b<br/>ofs: 0<br/>read: 4096"]
  inode["같은 inode<br/>file_a != file_b<br/>file_reopen()으로 file 객체 분리"]
  parent_page --> parent_aux
  child_page --> child_aux
  parent_aux -.-> child_aux
  parent_aux --> inode
  child_aux --> inode

중요: aux->file은 file_reopen()으로 복제해야 한다. 부모와 자식이 같은 struct file을 공유하면 file_close() 시 use-after-free가 발생할 수 있다. file_reopen()은 같은 inode를 공유하면서도 file position과 deny_write 카운트는 각각 독립적으로 유지한다.

Case 2: Resident FILE page — frame에 올라온 상태

부모가 이미 page에 접근해 내용이 frame에 적재된 상태다. 이때는 VM_TYPE(page->operations->type) == VM_FILE이고 page->frame != NULL이다.

다음은 이 경로의 근거로 확인한 실제 구현 file_copy()(vm/file.c L197–210)이다.

확인한 구현에서 드러나는 한계: file_copy()는 자식 page의 file_page metadata(file 포인터, offset 등)를 명시적으로 복사하지 않는다. vm_alloc_page()은 file_backed_initializer()만 호출하고 page->operations = &file_ops만 설정하므로, 자식의 page->file.file은 초기화되지 않은 상태로 남을 수 있다. 또한 file_reopen()도 호출하지 않으므로 부모와 자식이 같은 struct file을 공유할 가능성이 있다. 이는 코드에서 관찰되는 동작과 그로부터 추론한 위험을 구분해 해석해야 하는 부분이다.

Case 3: Swapped-out FILE page

file-backed page가 evict되면 file_backed_swap_out()(vm/file.c L54–92)이 실행된다. 확인한 구현은 page가 dirty 상태일 때 파일에 writeback하고, 모든 owner를 page->file.swapped = true로 설정한 뒤 frame을 해제한다. anonymous page와 달리 swap disk를 사용하지 않으며 원본 파일이 backing store 역할을 한다.

file_copy()는 src_page->file.swapped 플래그로 이 상태를 감지한다. 이후 file_read_at()을 사용해 원본 파일에서 직접 읽은 내용으로 자식 frame을 채운다. swap slot을 복사하는 anonymous page 경로와 다른 점이다.

여기서는 struct file_page의 swapped 필드(include/vm/file.h L14)가 핵심이다. 확인한 구현에서 이 필드는 file_backed_swap_out() 시 true로, file_backed_swap_in() 시 false로 바뀐다.

struct file_page 필드

문서의 초기 의사 코드에 나온 zero_bytes는 실제 구현의 struct file_page에 저장되지 않는다. 이 값은 PGSIZE - page_read_bytes로 계산할 수 있으므로 별도 필드가 필요하지 않다. 다만 lazy_load_file()의 aux인 struct lazy_load_arg에는 page_zero_bytes 필드가 있다.

QEMU 에뮬레이션

QEMU는 file-backed page 복사 정책에 직접 관여하지 않는다. memcpy()와 file_read_at()은 모두 guest 메모리 내부에서 일어나며, QEMU TCG는 관련 명령어를 번역해 실행한다. 다만 fork 과정에서 file_read_at()이 호출되면 IDE controller model을 통한 disk I/O가 발생한다. 따라서 swapped file page를 복사하는 경로는 resident frame을 직접 memcpy()하는 경로보다 상당히 느리다.

File-backed Page 복사 값 추적

8192바이트 파일을 mmap으로 매핑한 경우를 예로 들면 각 page의 값은 다음과 같다.

pageVAfile offsetread_byteszero_bytes
00x10000000040960
10x10001000409640960

fork 시 자식도 두 개의 page entry를 만들어야 한다. 각 page에서 file_reopen()을 한 번 호출하고 aux를 한 번 deep copy하므로, 전체 file_reopen() 호출 횟수는 mmap page 수와 같다.

관찰 시나리오

시나리오 1: mmap 후 fork — UNINIT FILE

목적: 부모가 mmap()으로 파일을 매핑한 뒤 fork했을 때 자식 SPT에 UNINIT(FILE) page가 정확히 복사되는지 확인한다.

준비: mmap-read 또는 이와 유사하게 mmap 후 fork를 호출하는 테스트를 사용한다.

기대 결과: 부모의 각 UNINIT(FILE) page마다 uninit_copy()이 호출된다. file_reopen()은 새 struct file*을 반환하며, 자식 aux의 file 포인터는 부모와 다른 주소를 가리켜야 한다. 이는 실행으로 확인해야 할 기대값이며, 이 문서 자체가 실행 결과를 보장하지는 않는다.

시나리오 2: resident FILE page의 frame 내용

목적: 부모가 mmap 영역에 접근해 page를 frame에 올린 뒤 fork했을 때 file_copy()가 memcpy로 자식 frame에 같은 바이트를 복사하는지 확인한다.

기대 결과: memcpy(dst_page->frame->kva, src_page->frame->kva, PGSIZE) 후 두 frame의 4096 bytes가 서로 같아야 한다. 이 역시 관찰 스크립트로 검증할 기대값이다.
