vm_do_claim_page는 fault를 실제 frame mapping으로 바꾼다

확인 범위: 이 문서는 page fault를 실제 frame mapping으로 전환하는 일반 원리와 구현 선택 기준을 설명한다. PintOS·Linux·Windows·QEMU의 코드 경로와 수치 추적은 특정 구현을 해석하기 위한 예시다. 실제 코드의 정확성, 버전별 함수·동작, 실행 결과와 성능은 본문만으로 검증되지 않았으므로 해당 소스와 실행 기록, 측정을 별도로 확인해야 한다.

fault가 실제 메모리 접근으로 바뀌는 과정

vm_do_claim_page()가 호출되는 시점에는 SPT에서 접근이 허용된 page를 이미 찾은 상태다. 그러나 이 page가 존재한다는 사실만으로 CPU가 해당 주소를 읽거나 쓸 수 있는 것은 아니다. page에 물리 frame을 연결하고, 하드웨어 page table에 PTE를 설치하고, page type에 맞는 bytes를 frame에 채워야 한다.

여기서 “claim”은 page가 실제 frame 하나를 차지하도록 만든다는 뜻이다. 이 작업이 끝나면 fault를 낸 명령어를 다시 실행했을 때 주소 변환과 메모리 접근이 성공할 수 있다.

CPU가 같은 명령어를 다시 실행하려면

CPU가 pf를 발생시킨 뒤 OS가 준비해야 하는 것은 세 가지다.

준비없으면 생기는 일
물리 frame담을 실제 4KB RAM 자리가 없다
PTE present mappingCPU가 같은 VA를 다시 번역할 수 없다
frame contents번역은 되지만 읽는 bytes가 의미 없는 값이다

pf는 fault(trap 아님)이므로 RIP는 fault를 낸 명령어를 가리킨다. OS가 PTE를 설치하고 iretq로 돌아가면 CPU는 그 명령어를 다시 실행한다.

다른 OS 구현과의 대응 관계

Linux의 page fault handler는 VMA를 찾은 뒤 handle_mm_fault() → __handle_mm_fault() → handle_pte_fault()를 거쳐 type별 물리 page를 준비한다. do_anonymous_page(), do_fault() (file-backed), do_swap_page() 등은 PintOS의 swap_in() type 분기와 대응한다. Windows에서는 VAD를 조회한 뒤 working set manager가 page를 resident 상태로 만든다.

항목LinuxWindowsPintOS
fault 판단VMA tree + PTE 상태VAD tree + prototype PTESPT hash lookup
frame 확보alloc_pages(GFP_HIGHUSER)MiAllocateVad/PFN DBvm_get_frame() → palloc(PAL_USER)
PTE 설치set_pte_at()MiMakePdeExistAndMakeValidpml4_set_page()

실패 처리OOM killer / SIGSEGVSTATUS_COMMITMENT_LIMIT / AVfalse → process kill

PintOS의 claim 순서

제시된 vm_do_claim_page() 구현은 frame 확보, 양방향 연결, PTE 설치, frame 내용 준비의 순서로 진행된다.

각 단계가 끝날 때 page, frame, PTE, frame bytes의 상태는 다음과 같이 달라진다.

단계page→frameframe→pagePTEframe bytes
claim 전NULL—not present—
vm_get_frame() 후NULLNULLnot present미초기화
양방향 연결 후frame Fpage Pnot present미초기화
pml4_set_page() 후frame Fpage Ppresent + flags미초기화
swap_in() 후frame Fpage Ppresent + flags유효한 데이터

vm_get_frame()은 새 frame을 할당하거나 기존 frame을 eviction하는 두 경로를 가진다.

frame을 확보한 뒤에는 swap_in()이 page type에 맞는 함수를 호출해 bytes를 준비한다.

VM_FILEfile_backed_swap_in()file_read_at(file, kva, read_bytes, ofs) + memset(zero_bytes)

QEMU에서 보이는 두 번의 page walk

QEMU는 vm_do_claim_page() 자체를 알지 못한다. QEMU의 관점에서는 PTE가 없는 첫 번째 page walk가 pf로 끝나고, PintOS가 PTE를 설치한 뒤 재실행된 두 번째 page walk가 실제 guest PA를 찾는 과정으로 보인다.

%% QEMU page walk와 vm_do_claim_page() 이후 재실행 흐름
flowchart TD
  first["1차 fault<br/>QEMU mmu_translate(VA)"]
  miss["PTE not present<br/>#PF inject"]
  record["CR2 = fault_addr<br/>error_code = P/W/U 비트"]
  pintos["PintOS 처리<br/>vm_do_claim_page()"]
  pte["PTE 설치"]
  retry["2차 재실행<br/>QEMU mmu_translate(VA)"]
  hit["PTE present<br/>guest PA"]
  host["RAMBlock.host + offset<br/>실제 host memory 접근"]
  first --> miss
  miss --> record
  record --> pintos
  pintos --> pte
  pte --> retry
  retry --> hit
  hit --> host

QEMU의 x86_cpu_tlb_fill() → mmu_translate() → get_physical_address()는 PTE를 읽고, present가 아니면 EXCP0E_PAGE를 raise한다. PintOS가 PTE를 설치하고 iretq로 돌아가면 QEMU는 softmmu TLB를 갱신하며, 다음 접근에서는 설치된 mapping을 사용할 수 있다.

주소와 값으로 따라가기

다음 추적은 유저 코드가 0x8048123을 읽다가 fault를 일으킨 경우를 보여 준다.

fault_addr = 0x8048123
page base  = 0x8048000   (fault_addr & ~0xFFF)
offset     = 0x123       (fault_addr & 0xFFF)

SPT lookup key = 0x8048000
SPT hit: struct page P
  P.type       = VM_UNINIT (lazy loaded ELF segment)
  P.writable   = false (code segment)
  P.frame      = NULL

vm_get_frame() 결과:
  KERN_BASE    = 0x8004000000
  frame PA     = 0x12340000   (palloc이 반환한 KVA의 vtop)
  frame KVA    = 0x8016340000 (= KERN_BASE + 0x12340000)

pml4_set_page() 계산:
  *pte = vtop(frame->kva) | PTE_P | PTE_U
       = 0x12340000 | 0x001 | 0x004    (writable=false이므로 PTE_W 없음)
       = 0x12340005

swap_in() = uninit_initialize():
  lazy callback이 file_read_at(file, kva, read_bytes, ofs) 실행
  frame 0x8016340000에 ELF segment bytes 복사

재실행 시:
  VA 0x8048123 → page walk → PA 0x12340123
  → QEMU: RAMBlock.host + 0x12340123 → 실제 bytes 읽기 성공

커널이 같은 bytes를 직접 볼 때:
  frame->kva + 0x123 = 0x8016340000 + 0x123 = 0x8016340123

이 예시에서 사용하는 frame과 page table의 크기는 다음과 같다.

1 frame        = 4 KB = 4096 bytes = 0x1000
PTE 하나       = 8 bytes (64-bit)
PT 하나        = 512 entries × 8 = 4096 bytes = 1 page
pml4_set_page  = 최대 4 page 할당 (PML4→PDPT→PD→PT, 경로가 없으면)

claim 전후 상태와 실패 복구

claim 전에는 SPT의 page가 존재해도 frame과 PTE가 없다. claim이 끝나면 page와 frame이 서로 연결되고, PTE는 frame의 물리 주소와 접근 flag를 담으며, page type도 초기화 결과에 따라 바뀔 수 있다.

%% vm_do_claim_page() 전후 page, frame, PTE 상태
flowchart LR
  page_before["struct page P<br/>va=0x8048000<br/>frame=NULL<br/>type=UNINIT"]
  pte_before["PTE[0x8048000]<br/>present=0<br/>(not mapped)"]
  page_after["struct page P<br/>va=0x8048000<br/>frame=F<br/>type=FILE"]
  frame_after["struct frame F<br/>kva=0x8016..<br/>page=P<br/>owner=curr<br/>ref_count=1"]
  pte_after["PTE[0x8048000]<br/>0x12340005<br/>PA=0x12340000<br/>P=1 W=0 U=1"]
  page_before --> pte_before
  page_after -->|"page-&gt;frame"| frame_after
  frame_after -->|"frame-&gt;page"| page_after
  frame_after --> pte_after
  pte_before -->|"pml4_set_page()"| pte_after

frame을 얻지 못하면 즉시 실패한다. frame 연결 뒤 pml4_set_page()나 swap_in()이 실패하면 PTE와 owner, 양방향 link를 정리하고 새 frame을 반환하는 rollback이 필요하다.

%% vm_do_claim_page() 실패 경로와 rollback
flowchart TD
  claim["vm_do_claim_page(page)"]
  get_frame["vm_get_frame()"]
  frame_null["frame == NULL?"]
  pml4["pml4_set_page()"]
  pml4_fail["실패?"]
  swap_in["swap_in(page, kva)"]
  swap_fail["실패?"]
  ok["return true"]
  fail["return false"]
  link["page-&gt;frame / frame owner 연결"]
  rollback["rollback<br/>PTE clear, owner·양방향 link 해제<br/>새 frame 반환"]
  claim --> get_frame
  get_frame --> frame_null
  frame_null -->|"Yes"| fail
  frame_null -->|"No"| link
  link --> pml4
  pml4 --> pml4_fail
  pml4_fail -->|"Yes"| rollback
  pml4_fail -->|"No"| swap_in
  swap_in --> swap_fail
  swap_fail -->|"Yes"| rollback
  swap_fail -->|"No"| ok
  rollback --> fail
