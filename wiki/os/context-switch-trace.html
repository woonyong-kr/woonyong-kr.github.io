컨텍스트 스위치 (Context Switch) Trace

컨텍스트 스위치 (Context Switch) Trace

스레드 전환은 함수 호출처럼 다른 코드로 점프하는 일이 아니다. CPU 레지스터와 스택을 저장하고 복원해야 다음 스레드가 실행을 이어 갈 수 있다. USERPROG가 켜진 PintOS에서 주소 공간이 다른 유저 프로세스로 전환할 때는 페이지 테이블 기준도 함께 바뀐다.

컨텍스트 스위치를 따라가며 확인할 질문

스케줄러를 처음 보면 스레드 전환을 함수 호출처럼 이해하기 쉽다. 그러나 이 문서에서 다루는 PintOS의 전환 과정은 CPU 레지스터와 스택을 저장하고 복원하는 작업이다. USERPROG가 켜져 있고 주소 공간이 달라진다면 페이지 테이블 기준도 전환 대상에 포함된다.

이 흐름을 따라가며 다음 질문에 답한다.

  • 왜 타이머 interrupt 안에서 바로 thread_yield()하지 않고 끝까지 미루는가?
  • schedule()은 “다음 스레드를 고르는 코드”인가, “레지스터를 바꾸는 코드”인가?
  • thread_launch()는 현재 스레드의 어느 값을 어디에 저장하는가?
  • do_iret() 뒤에는 왜 함수 호출처럼 원래 위치로 돌아오지 않는가?
  • GDB에서 보는 RIP/RSP는 PintOS 스레드의 필드인가, QEMU의 guest CPU state인가?

함수 호출과 다른 점

컨텍스트 스위치를 모르면 스케줄러를 “함수 포인터를 바꿔 호출하는 코드”처럼 오해하기 쉽다.

CPU에는 현재 RIP, RSP, 범용 레지스터, flags, segment와 주소 변환 기준이 들어 있다. 스레드 A를 멈추고 B를 실행하려면 A가 나중에 돌아올 수 있도록 이 실행 상태를 저장해야 한다. 그런 다음 B가 마지막으로 멈춘 지점의 상태를 CPU에 복원해야 한다.

따라서 컨텍스트 스위치는 스레드 이름만 바꾸는 일이 아니다. 다음에 실행할 instruction pointer와 stack pointer를 포함한 CPU 실행 상태를 바꾸는 일이다.

저장, 선택, 복원

이 문서에서 살펴보는 컨텍스트 스위치는 세 단계로 나눌 수 있다.

단계초보자용 해석실제로 바뀌는 것
저장지금 어디까지 실행했는지 잃지 않게 적어 둔다현재 스레드의 register snapshot
선택다음 CPU 주인을 고른다ready_list에서 next 선택
복원다음 스레드가 멈춘 지점으로 돌아간다다음 스레드의 RIP/RSP/registers

CPU 위에서 실행되는 순간에는 하나의 레지스터 집합과 하나의 현재 스택만 사용된다. 여러 스레드가 존재한다는 말은 이 문맥에서 스레드마다 다시 실행하는 데 필요한 상태가 따로 저장되어 있다는 뜻이다.

PintOS의 timer 선점 흐름에 이 세 단계를 연결하면 다음과 같다.

A에서 B로 전환하는 장면

스레드 A가 실행 중이고 타이머가 4번째 tick을 발생시켰다고 하자.

PintOS는 A가 나중에 실행을 이어 갈 수 있도록 현재 상태를 보존한 뒤 B로 넘어가야 한다.

이 전환에서는 A의 CPU 상태를 저장한 다음 B의 저장된 상태를 복원한다.

PintOS와 실제 운영체제의 범위

이 문서에 적힌 범위에서 현실 OS의 컨텍스트 스위치는 PintOS보다 더 많은 요소와 연결된다.

  • Linux는 per-CPU run queue, scheduler class, preemption model, tickless, CPU migration, TLB shootdown 같은 요소를 함께 다룬다.
  • Windows는 dispatcher, thread/process object, priority, quantum, wait reason, APC 같은 요소가 scheduler와 연결된다.
  • 두 OS 모두 FPU/SIMD register, debug register, 보안 기능, SMP 동기화까지 고려해야 한다.

이 차이가 있어도 이 문서에서 비교하는 기본 흐름은 같다.

PintOS는 이 흐름을 학습 가능한 크기로 보여 준다. PintOS를 실제 OS와 같은 규모의 구현으로 볼 수는 없지만, 레지스터와 스택을 저장하고 복원하는 전환 원리는 여기서 확인할 수 있다.

PintOS에서 문맥이 이동하는 과정

1. 스레드의 문맥은 어디에 저장되는가?

PintOS에서 먼저 볼 단서는 struct thread 안의 struct intr_frame tf다.

  • PintOS 저장소 상대 경로 pintos/include/threads/thread.h
    • 각 struct thread는 전용 4KB 페이지의 아래쪽에 놓인다.
    • 같은 페이지의 위쪽은 그 스레드의 커널 스택으로 쓰인다.
    • struct thread 필드에 struct intr_frame tf;가 들어 있다.

이 구조에서는 스레드별 문맥이 각 스레드가 소유한 메모리에 저장되고, 커널 스택도 스레드별로 존재한다. 스택이 너무 커지면 같은 4KB 페이지 안의 struct thread를 덮을 수 있다.

현재 스레드를 찾는 방법도 이 구조를 이용한다.

  • PintOS 저장소 상대 경로 pintos/threads/thread.c
    • running_thread()는 현재 rsp를 읽고 페이지 시작 주소로 내림한다.
    • 그 페이지 시작 주소를 struct thread *로 해석한다.

따라서 PintOS의 “현재 스레드”는 현재 CPU stack pointer가 속한 4KB 페이지에서 역산된다.

2. timer interrupt가 왜 스케줄링으로 이어지는가?

timer interrupt는 OS가 실행 흐름을 다시 판단하는 주기적인 기회다.

  • PintOS 저장소 상대 경로 pintos/threads/thread.c
    • thread_tick()이 tick마다 호출된다.
    • TIME_SLICE를 다 쓰면 intr_yield_on_return()을 호출한다.
  • PintOS 저장소 상대 경로 pintos/threads/interrupt.c
    • intr_yield_on_return()은 yield_on_return = true를 설정한다.
    • intr_handler()는 외부 interrupt 마무리 지점에서 그 값을 보고 thread_yield()를 호출한다.

thread_tick()은 그 자리에서 schedule()을 호출하지 않는다. 대신 인터럽트 핸들러가 끝나는 지점에서 thread_yield()가 실행되도록 예약한다. 이 이유는 인터럽트 끝에서 yield하는 이유에서 따로 살펴본다.

3. schedule()은 무엇을 바꾸는가?

PintOS의 스케줄러는 다음 CPU 주인을 정한다. 여기서는 ready_list에서 다음 스레드를 고르지만, schedule() 자체가 모든 레지스터를 직접 저장하고 복원하지는 않는다.

  • PintOS 저장소 상대 경로 pintos/threads/thread.c
    • next_thread_to_run()이 ready_list에서 다음 스레드를 고른다.
    • schedule()이 next->status = THREAD_RUNNING, thread_ticks = 0 등을 처리한다.
    • USERPROG일 때 process_activate(next)로 주소 공간을 전환한다.
    • 마지막에 thread_launch(next)로 실제 문맥 교체로 내려간다.

각 함수의 역할은 다음과 같이 나뉜다.

단계함수하는 일
선택next_thread_to_run()ready_list에서 다음 후보를 뽑는다
상태 전환schedule()next->status, thread_ticks, 주소 공간을 갱신한다
레지스터 교체thread_launch(next)현재 tf에 저장하고 다음 tf를 복원한다
실제 복귀do_iret(tf)iretq로 tf->rip/tf->rsp 기준 실행을 재개한다

4. 주소 공간과 커널 스택 기준도 바뀐다

USERPROG가 켜진 PintOS에서 주소 공간이 다른 실행 흐름으로 전환할 때는 레지스터 외의 기준도 바뀐다.

  • PintOS 저장소 상대 경로 pintos/userprog/process.c
    • process_activate(next)가 pml4_activate(next->pml4)와 tss_update(next)를 호출한다.
  • PintOS 저장소 상대 경로 pintos/threads/mmu.c
    • pml4_activate()가 lcr3(...)로 page table root를 바꾼다.
  • PintOS 저장소 상대 경로 pintos/userprog/tss.c
    • tss_update(next)가 tss->rsp0 = (uint64_t) next + PGSIZE로 다음 스레드의 커널 스택 꼭대기를 기록한다.

따라서 유저 프로세스 A에서 B로 넘어갈 때는 TLB 기준과 다음 syscall 또는 interrupt에서 사용할 kernel stack도 함께 바뀐다.

5. thread_launch()와 do_iret()

PintOS KAIST 코드에서 실제 문맥 교체는 thread_launch()에서 확인할 수 있다.

  • PintOS 저장소 상대 경로 pintos/threads/thread.c
    • tf_cur = &running_thread()->tf는 현재 스레드의 문맥 저장 위치다.
    • tf = &next->tf는 다음 스레드의 문맥 복원 소스다.
    • 인라인 어셈블리가 현재 레지스터들을 tf_cur에 써넣는다.
    • 마지막에 do_iret(tf)를 호출한다.

A가 나중에 다시 선택되면 do_iret(&A->tf)는 A를 out_iret 지점으로 돌려보낸다. A의 관점에서는 이전에 호출한 thread_launch()가 그때 반환한 것처럼 실행이 이어진다. 이 구조에서 컨텍스트 스위치는 일반적인 함수 호출보다 저장된 continuation으로 복귀하는 과정에 가깝다.

QEMU가 담당하는 범위

이 Trace에서 QEMU는 스케줄러가 아니다.

  • PintOS의 schedule()/thread_launch()/do_iret()는 guest OS 내부 코드다.
  • QEMU는 그 코드가 실행되는 동안, x86-64 CPU의 iretq 같은 명령이 실제 CPU에서 실행된 것 같은 효과를 내도록 에뮬레이션한다.

문서에서 근거로 삼는 QEMU 위치는 다음과 같다.

  • target/i386/tcg/emit.c.inc
    • gen_IRET()가 iret 계열 instruction을 helper 호출로 번역한다.
  • target/i386/tcg/seg_helper.c
    • helper_iret_protected()가 protected/long mode의 interrupt return을 처리한다.
  • target/i386/cpu.h
    • CPUX86State에 guest 범용 레지스터 배열과 eip 같은 guest CPU state가 있다.
  • target/i386/gdbstub.c
    • x86_cpu_gdb_read_register()가 GDB 요청에 대해 env->regs[...], env->eip, env->eflags 등을 읽어 돌려준다.

따라서 이 환경에서 GDB의 info registers로 보는 값은 host macOS/Linux의 실제 레지스터가 아니라 QEMU가 관리하는 guest CPU register state다.

코드에서 따라갈 경로

1. interrupt 진입은 struct intr_frame

  • PintOS 저장소 상대 경로 pintos/threads/intr-stubs.S
    • intr_entry가 범용 레지스터를 stack에 저장하고 intr_handler()를 호출한다.
    • 반환 경로에서 같은 순서로 레지스터를 복원한 뒤 iretq를 실행한다.
  • PintOS 저장소 상대 경로 pintos/include/threads/interrupt.h
    • struct intr_frame은 R.r15부터 R.rax, rip, eflags, rsp, ss까지 담는다.

2. timer tick은 yield를 예약한다

  • PintOS 저장소 상대 경로 pintos/threads/thread.c
    • thread_tick()은 ++thread_ticks >= TIME_SLICE일 때 intr_yield_on_return()을 호출한다.
  • PintOS 저장소 상대 경로 pintos/threads/interrupt.c
    • intr_handler()는 외부 interrupt 마무리에서 yield_on_return을 확인하고 thread_yield()를 호출한다.

3. thread_yield()는 현재 스레드를 READY로 바꾼다

  • PintOS 저장소 상대 경로 pintos/threads/thread.c
    • thread_yield()는 ASSERT(!intr_context())로 interrupt context 직접 호출을 막는다.
    • idle thread가 아니면 현재 스레드를 ready_list에 다시 넣고 do_schedule(THREAD_READY)로 내려간다.

4. thread_launch()와 do_iret()가 실제로 전환한다

  • PintOS 저장소 상대 경로 pintos/threads/thread.c
    • thread_launch(next)가 현재 register들을 running_thread()->tf에 저장한다.
    • do_iret(&next->tf)가 다음 register들을 복원한다.
    • iretq 이후의 RIP/RSP는 다음 스레드의 tf가 정한다.

2. struct intr_frame의 주요 오프셋

do_iret()와 thread_launch()의 어셈블리에서는 struct intr_frame을 메모리에 놓인 레지스터 배열처럼 사용한다.

3. out_iret이 저장되는 이유

현재 A에서 B로 넘어가는 장면에서는 두 frame을 다음과 같이 가리킨다.

thread_launch(B)는 A의 tf.rip에 out_iret label 주소를 저장한다.

그 뒤 do_iret(&B->tf)가 실행되면 CPU 상태는 B의 tf.rip/tf.rsp를 기준으로 바뀌고 A는 멈춘다.

나중에 B 또는 다른 스레드가 A를 다시 고르면 다음 흐름으로 A가 재개된다.

A는 이전에 멈췄던 thread_launch()의 끝부분에서 실행을 이어 간다.

GDB에서 확인할 지점

다음 항목은 PintOS(QEMU+GDB)에서 관찰할 대상과 명령을 정리한 것이다. 이 문서에는 명령을 실제로 실행한 결과가 포함되어 있지 않다.

1. 타이머 틱에서 양보가 예약되는지

확인할 것:

  • thread_ticks가 TIME_SLICE에 도달하는 순간
  • intr_context()가 true인 상태에서만 intr_yield_on_return()이 호출되는지
  • 이 시점에는 아직 thread_launch()로 내려가지 않았는지

2. interrupt 끝에서 실제 yield가 일어나는지

확인할 것:

  • yield_on_return이 true로 바뀌는지
  • in_external_intr가 false로 내려간 뒤 thread_yield()가 호출되는지
  • thread_yield()의 ASSERT(!intr_context())가 왜 필요한지

3. schedule()이 next를 고르는지

확인할 것:

next_thread_to_run()에서 ready_list가 비어 있지 않다면 반환값은 list_pop_front(&ready_list)에서 나온다.

4. thread_launch()의 저장 위치와 복원 소스

breakpoint에 걸리면:

관찰 포인트:

  • $cur는 현재 $rsp가 속한 4KB 페이지 시작 주소를 struct thread *로 해석한 값이다.
  • &$cur->tf는 현재 스레드 A의 저장 위치다.
  • &th->tf는 다음 스레드 B의 복원 소스다.
  • x/24gx로 보면 tf + 152 근처에 rip/cs/eflags/rsp/ss가 이어진다.

5. do_iret() 직전의 frame

확인할 것:

do_iret() 안에서는 movq %0, %rsp 때문에 현재 stack pointer가 tf 주소로 바뀐다. 그 뒤 iretq가 실행되면 RIP/RSP는 tf->rip/tf->rsp를 기준으로 바뀐다.

흐름을 다시 연결하기

  • 컨텍스트 스위치는 다음 스레드 함수를 호출하는 일이 아니라 레지스터와 스택 포인터를 저장하고 복원하는 일이다.
  • PintOS는 현재 스레드의 문맥을 struct thread 안의 struct intr_frame tf에 저장한다.
  • schedule()은 다음 스레드를 고르고 상태와 주소 공간 기준을 갱신한 뒤 실제 레지스터 교체를 thread_launch()에 맡긴다.
  • thread_launch()는 현재 스레드가 나중에 돌아올 주소로 out_iret을 저장한다.
  • do_iret()와 iretq는 다음 스레드의 tf->rip/tf->rsp로 실행을 재개한다.
  • QEMU는 PintOS의 스케줄링 정책을 결정하지 않는다. guest CPU state와 iretq의 효과를 에뮬레이션하고 GDB가 그 상태를 읽도록 한다.
