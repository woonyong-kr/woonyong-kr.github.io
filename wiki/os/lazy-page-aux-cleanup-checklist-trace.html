lazy aux cleanup 쟁점

lazy page aux ownership 계약에서는 aux를 누가 닫고 해제할지 원칙을 세웠다.

하지만 실제 구현을 시작하면 질문이 더 구체적으로 바뀐다.

lazy_load_segment()와 load_mmap_page()는 성공, 실패, never-faulted cleanup에서 file_close()와 free()를 어떤 순서로 호출해야 할까?

짧은 답은 이것이다.

lazy aux cleanup 문제

aux cleanup 버그가 항상 page fault 실패로 바로 드러나는 것은 아니다.

이 문서에서 다루는 구현에서는 file-backed lazy page의 frame bytes를 올바르게 채웠더라도 file reference ownership을 잘못 관리하면 이후 munmap(), exit(), fork() 경로에서 문제가 드러날 수 있다.

빠진 기준나중에 보이는 증상
등록 실패 때 aux 정리load_segment() 또는 do_mmap() 실패마다 file reference leak
executable lazy 성공 뒤 aux 해제이미 RAM에 올라온 code/data page에도 불필요한 file object가 남음
mmap lazy 성공 뒤 metadata 이동dirty write-back 때 file/offset/read size를 찾지 못함
callback 실패 때 owner 결정aux leak 또는 file_backed_destroy()와 callback의 double close
never-faulted UNINIT destroy접근하지 않은 lazy page마다 heap/file leak

따라서 이 구현에서 aux는 단순한 인자가 아니다. 등록, 첫 fault, destroy로 상태가 바뀔 때마다 소유 주체와 정리 책임도 함께 바뀌는 자원이다.

lazy aux cleanup 사례

ELF segment와 mmap() region이 모두 마지막 page 일부만 파일에서 읽는다고 하자.

frame에 채워야 할 바이트는 둘 다 같다.

하지만 성공 뒤 metadata 수명은 다르다.

page 종류성공 뒤 aux성공 뒤 file metadata
executable lazy page더 필요 없으므로 callback이 close/freeframe bytes만 남아도 됨
mmap lazy pagewrapper는 free 가능dirty write-back을 위해 page->file 또는 region에 남아야 함

따라서 같은 helper로 frame bytes를 채울 수는 있어도, 성공 뒤 ownership 이동은 page 종류별로 나누어야 한다.

실제 운영체제

Linux와 Windows도 demand paging 중간의 file reference와 metadata 수명을 관리한다.

차이는 구현 단위다.

Linux는 VMA, file object, page cache, address_space 같은 구조를 통해 “이 주소는 어떤 file offset에서 온다”를 기억한다. Windows도 section object, mapped view, VAD 같은 구조로 같은 종류의 정보를 보존한다.

현실 OS에서는 PintOS의 aux 같은 작은 학생 구현 구조체가 그대로 핵심 객체가 되지는 않는다. 그래도 원칙은 같다.

PintOS에서는 그 규칙을 구현자가 직접 코드로 만들어야 한다.

PintOS

W09 PintOS skeleton은 필요한 자리를 의도적으로 비워 둔다.

process.c의 Project 3 경로에서 lazy_load_segment()는 TODO이고, load_segment()는 아직 aux = NULL을 넘긴다.

uninit_new()는 그 aux를 page->uninit.aux에 저장한다.

첫 fault에서는 uninit_initialize()가 union이 덮이기 전에 aux를 지역 변수로 꺼낸다.

따라서 구현은 다음 순서로 안전해진다.

1. 공통 aux 구조체와 destroy

W09에서는 struct lazy_load_arg가 ANON과 FILE lazy page 모두에 공통으로 쓰인다.

uninit_destroy()가 공통 cleanup을 담당한다.

이 함수가 never-faulted page의 모든 cleanup을 책임진다. mmap 성공 경로에서 file ownership을 page->file로 옮긴 뒤에는 aux->file = NULL을 먼저 해야 double close를 피할 수 있다.

2. 등록 실패는 등록자가 정리한다

W09 load_segment()는 aux를 만든 뒤 SPT 등록에 실패하면 즉시 정리한다.

file_reopen() 실패와 SPT 등록 실패 모두 즉시 cleanup한다. 이 경로를 빼먹으면 SPT에도 없어서 나중에 uninit_destroy()가 대신 정리할 기회가 없다.

3. executable lazy callback은 성공/실패

W09의 lazy_load_segment()는 성공/실패 모두 aux를 소비한다.

done 레이블 뒤의 cleanup이 성공/실패 경로 모두를 감싼다. filesys_lock으로 file 접근을 보호하고, aux와 aux->file의 NULL 체크를 거친다.

4. mmap lazy callback은 metadata를 옮긴

mmap() page는 dirty write-back을 위해 첫 fault 뒤에도 file, offset, read size가 필요하다.

5. never-faulted page는

첫 fault가 없으면 callback이 호출되지 않는다. W09의 uninit_destroy()가 이 경로를 책임진다.

W09에서는 ANON과 FILE lazy page 모두 struct lazy_load_arg를 공통으로 쓰기 때문에 future type 분기가 필요 없다. 만약 aux 타입이 page 종류별로 다르다면, page_get_type(page)으로 분기하거나 aux 안에 kind 필드를 두어야 한다.

QEMU

QEMU는 이 cleanup helper를 모른다.

QEMU가 볼 수 있는 것은 CPU와 MMU 수준의 결과다.

  • present PTE가 없으면 x86 translation code가 EXCP0E_PAGE를 만들고 fault address를 CR2에 넣는다.
  • write access이면 page fault error code에 write bit가 들어간다.
  • PintOS가 PTE를 설치한 뒤 handler에서 돌아오면 같은 guest instruction이 다시 실행된다.

따라서 aux를 double close하거나 leak해도 QEMU가 직접 알려 주지 않는다. QEMU는 하드웨어 효과를 재현하고, aux 수명은 PintOS 커널의 내부 장부다.

lazy aux cleanup 코드

PintOS W09에서 확인할 위치:

  • pintos/include/vm/vm.h:44-60: struct page가 uninit, anon, file을 union으로 묶는다.
  • pintos/include/vm/vm.h:80-83: swap_in()과 destroy()가 현재 operation table로 dispatch된다.
  • pintos/include/vm/uninit.h:12-18: struct uninit_page가 callback, future type, aux, initializer를 가진다.
  • pintos/vm/uninit.c:27-42: uninit_new()가 page->uninit.aux = aux 상태를 만든다.
  • pintos/vm/uninit.c:47-56: uninit_initialize()가 init과 aux를 지역 변수로 보존한 뒤 page initializer와 callback을 호출한다.
  • pintos/vm/uninit.c:59-68: 첫 fault가 없던 UNINIT page가 process exit에 남을 수 있으므로 destroy가 필요하다고 말한다.
  • pintos/userprog/process.c:1246-1257: lazy_load_segment()가 첫 fault 때 호출될 TODO 함수로 남아 있다.
  • pintos/userprog/process.c:1287-1295: page별 read_bytes, zero_bytes를 계산하고 vm_alloc_page_with_initializer()를 호출한다.
  • pintos/vm/file.c:23-29: file_backed_initializer()가 page->operations = &file_ops로 전환하는 자리다.
  • pintos/include/vm/file.h:9-10: struct file_page는 비어 있으므로 file/offset/read size metadata를 구현자가 설계해야 한다.
  • pintos/filesys/file.c:35-37: file_reopen()은 mapping 수명을 원래 fd close와 분리할 수 있는 새 file object를 만든다.
  • pintos/filesys/file.c:88-90: file_read_at()은 file position에 의존하지 않고 특정 offset에서 읽는다.
  • pintos/tests/vm/mmap-close.c:18-26: fd를 닫아도 mapping으로 file 내용을 읽을 수 있어야 한다.
  • pintos/tests/vm/mmap-remove.c:18-42: mapping 뒤 파일을 닫고 삭제해도 mapped data가 유지되어야 한다.

QEMU에서 확인할 위치:

  • target/i386/tcg/system/excp_helper.c:500-520: access type에 따라 page fault error code를 만들고 EXCP0E_PAGE, cr2 = addr를 설정한다.
  • target/i386/tcg/system/excp_helper.c:613-653: address translation 실패를 guest exception으로 올리고 guest CR2를 갱신한다.
  • target/i386/cpu.h:345-352: page fault error code bit가 정의된다.

lazy aux cleanup GDB

GDB에서는 같은 aux가 어느 시점에 사라지는지 본다.

확인할 기준:

  • vm_alloc_page_with_initializer() 실패 경로에서 aux가 즉시 정리되는가?
  • lazy_load_segment() 성공 뒤 같은 aux가 다시 destroy 경로에서 닫히지 않는가?
  • load_mmap_page() 성공 뒤 aux->file = NULL 같은 ownership 이동 표시가 있는가?
  • file_backed_destroy()는 page->file.file만 닫고, 이미 free된 aux를 보지 않는가?
  • never-faulted UNINIT page는 uninit_destroy()에서 aux를 정리하는가?
  • callback 실패 뒤 pml4_get_page(thread_current()->pml4, page->va)가 0으로 돌아가는가?

정리

  • aux cleanup은 lazy_load_segment() 하나만의 문제가 아니라 등록, fault, destroy를 잇는 상태 전이 문제다.
  • SPT 등록 전에 실패하면 등록자가 aux를 정리해야 한다.
  • SPT 등록 뒤 첫 fault 전에는 page->uninit.aux가 owner이므로 uninit_destroy()가 cleanup 경로를 가져야 한다.
  • executable lazy page는 성공 뒤 aux와 reopened file을 소비하고 버린다.
  • mmap lazy page는 성공 뒤 file ownership과 offset metadata를 page->file 또는 region object로 옮긴다.
  • callback 실패 때는 aux를 callback이 정리할지, 현재 type destroy가 정리할지 하나만 선택해야 한다.
  • QEMU는 이 ownership을 모르고 page fault, error code, CR2 같은 하드웨어 결과만 재현한다.
