원자적 연산

확인 범위: 이 문서는 원자적 연산과 경쟁 조건의 일반 원리, 실행 환경에 따른 원자성 보장 방식의 선택 기준을 설명하고 PintOS와 Linux 스타일 코드를 사례로 제시한다. 다만 제시된 코드의 특정 버전과 실제 구현 일치 여부, 실행 기록 및 성능은 검증한 결과가 아니므로 별도의 코드·환경 확인과 측정이 필요하다.

원자적 연산(Atomic Operation)은 실행이 시작된 뒤 끝나기 전까지 다른 스레드나 인터럽트가 중간 상태를 볼 수 없는 연산이다.

원자적 연산이 필요한 이유

두 스레드가 같은 변수를 동시에 읽고 쓰면 경쟁 조건(race condition)이 발생할 수 있다. count++처럼 단순해 보이는 연산도 실제로는 읽기 → 더하기 → 쓰기의 세 단계로 나뉜다. 한 스레드가 이 단계를 마치기 전에 다른 스레드가 끼어들면 두 연산이 서로의 결과를 덮어쓸 수 있다.

C 코드 count++는 다음과 같은 기계어 단계로 실행된다.

mov eax, [count]    ← 1. 메모리에서 값 읽기
add eax, 1          ← 2. 레지스터에서 1 더하기
mov [count], eax    ← 3. 결과를 메모리에 쓰기

두 스레드가 동시에 count++를 실행하면 다음과 같은 흐름이 가능하다.

%% count++ 경쟁 조건 타임라인
flowchart TD
  timeline["순서 &#124; 스레드 A &#124; 스레드 B &#124; count<br/>1 &#124; mov eax"]

두 스레드가 각각 값을 한 번씩 증가시켜도 결과가 1만 증가할 수 있다. 두 스레드가 같은 값을 읽은 뒤 각자 계산한 결과를 차례로 쓰기 때문이다. 이것이 경쟁 조건이다.

이 문제를 막으려면 읽기부터 쓰기까지의 전체 과정을 다른 실행 흐름이 나누어 관찰하거나 방해할 수 없는 하나의 연산처럼 다뤄야 한다. **원자적(Atomic)**이라는 말은 “더 이상 쪼갤 수 없는”이라는 뜻이다. 원자적 연산은 시작되면 완료될 때까지 중간 상태가 다른 관찰자에게 보이지 않는다. 연산은 성공하거나 실패하며, 반쯤 실행된 상태는 드러나지 않는다.

화장실을 사용하는 상황에 비유하면, “문 확인 → 들어가기 → 잠그기” 사이에 다른 사람이 끼어들지 못해야 한다. 이 과정이 하나로 보호되지 않으면 두 사람이 동시에 들어갈 수 있다. 공유 상태를 다루는 코드도 같은 이유로 확인과 변경 사이를 보호해야 한다.

이 관점은 다음 동기화 동작을 이해하는 데 필요하다.

  • 세마포어, 락, 조건 변수가 왜 인터럽트를 끄는지
  • sema_down()에서 while (sema->value == 0) 검사와 sema->value--가 왜 하나의 묶음이어야 하는지
  • 멀티코어 시스템에서 인터럽트 끄기만으로 왜 부족한지

원자성을 보장하는 방법

원자성을 확보하는 방법은 실행 환경에 따라 달라진다. 단일 코어에서는 현재 코어의 실행 흐름이 바뀌지 않도록 막을 수 있다. 멀티코어에서는 다른 코어가 동시에 같은 메모리에 접근하는 상황까지 제어해야 한다.

인터럽트 비활성화

싱글코어 시스템에서 경쟁 조건이 발생하는 원인은 인터럽트에 의한 컨텍스트 스위치다. 인터럽트를 끄면 현재 스레드가 CPU를 독점하므로 다른 스레드가 원자 구간에 끼어들 수 없다. PintOS는 싱글코어 환경이므로 이 방법을 사용한다.

하드웨어 원자적 명령어

멀티코어에서는 한 코어의 인터럽트를 꺼도 다른 코어가 계속 실행된다. x86 CPU는 이런 동시 접근을 제어하기 위해 lock 접두사를 지원한다. lock add [count], 1은 다른 코어가 같은 주소에 접근하지 못하도록 메모리 버스를 잠근 상태에서 증가 연산을 수행한다. lock cmpxchg(Compare-And-Swap, CAS)는 “읽기 → 비교 → 조건부 쓰기”를 하나의 명령어로 수행한다.

소프트웨어 동기화 프리미티브

세마포어, 뮤텍스, 스핀락 같은 상위 수준 도구는 내부적으로 인터럽트 비활성화나 하드웨어 원자적 명령어를 사용해 자신의 상태를 원자적으로 변경한다. 프로그래머는 이러한 도구로 임계 영역(critical section)을 보호한다.

PintOS에서 원자 구간 만들기

PintOS는 싱글코어 에뮬레이션 환경이다. 동기화 프리미티브는 인터럽트를 꺼서 공유 상태를 변경하는 동안 컨텍스트 스위치가 일어나지 않게 한다.

cli 명령어는 CPU의 인터럽트 플래그(IF)를 끈다. IF가 꺼져 있으면 타이머 인터럽트가 발생해도 CPU가 무시하므로 컨텍스트 스위치가 일어나지 않는다. 그동안 현재 코드가 CPU를 독점한다.

세마포어의 원자적 down 연산

sema_down()은 “값 확인 → 대기 또는 감소”를 하나의 원자적인 흐름으로 수행해야 한다. 확인과 감소 사이에 다른 스레드가 끼어들면 세마포어 불변량이 깨질 수 있다.

intr_disable()과 intr_set_level() 사이에서는 인터럽트가 꺼져 있으므로 스케줄러가 중간에 끼어들 수 없다. 따라서 while 루프의 값 확인부터 value--까지가 하나의 원자적 연산처럼 동작한다.

멀티코어에서 필요한 하드웨어 지원

Linux 커널은 멀티코어 환경이므로 인터럽트를 끄는 것만으로는 부족하다. 현재 코어의 인터럽트를 막아도 다른 코어는 같은 메모리에 동시에 접근할 수 있기 때문이다. Linux는 lock 접두사가 붙은 x86 명령어를 사용한다.

lock incl은 “메모리 버스를 잠그고 → 값을 읽고 → 1 더하고 → 결과를 쓰고 → 버스 잠금을 푸는” 과정을 CPU가 한 번에 수행한다. 다른 코어는 이 과정이 끝날 때까지 같은 캐시 라인에 접근할 수 없다.

PintOS와 Linux의 차이는 경쟁이 발생하는 범위에서 드러난다.

항목PintOSLinux
코어 수1 (QEMU TCG)다수
원자성 보장cli/sti (인터럽트 끄기)lock 접두사 + 스핀락
경쟁 원인인터럽트 → 컨텍스트 스위치인터럽트 + 다른 코어 동시 접근
sema_down 보호intr_disable()raw_spin_lock_irqsave()

PintOS에서는 코어가 하나이므로 intr_disable()로 인터럽트를 끄면 현재 코드 외의 실행 흐름이 CPU를 사용할 수 없다. 반면 멀티코어에서는 다른 코어가 독립적으로 실행되므로 한 코어의 인터럽트를 끄는 것만으로 경쟁을 막을 수 없다.

원자적 연산을 이해하면 PintOS의 동기화 프리미티브가 공유 상태를 바꾸기 전에 인터럽트를 끄는 이유를 설명할 수 있다. sema_down, sema_up, lock_acquire, lock_release는 intr_disable()로 원자 구간을 만들고 그 안에서 공유 상태를 변경한다. 멀티코어 환경에서는 같은 목적을 위해 lock 접두사나 CAS 같은 하드웨어 원자적 명령어가 필요하다.
