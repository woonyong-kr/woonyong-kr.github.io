Frame Eviction과 Swap

Frame Eviction과 Swap

확인 범위: 이 문서는 frame eviction과 swap의 일반 원리와 선택 기준을 설명하고 Linux와 PintOS의 구조를 비교하되, 함수명·코드 좌표·COW 처리·QEMU I/O 등 구체적 내용은 본문에 전제된 특정 구현을 대상으로 한다. 제시된 수치와 GDB 절차는 계산 및 관찰 방법이며, 실제 코드·버전·실행 기록이나 성능 측정으로 검증된 결과를 뜻하지 않는다.

한 줄 요약: RAM이 부족하면 OS가 쓰지 않는 프레임을 빼앗아(evict) 재할당하고, 빼앗긴 페이지는 dirty bit에 따라 swap disk나 원본 파일에 보존했다가 이후 page fault로 복원한다.

Frame Eviction과 Swap 차이

물리 메모리(RAM)는 유한하다. 모든 프로세스가 요청하는 페이지를 동시에 물리 프레임에 올릴 수 없으므로, OS는 사용하지 않는 프레임을 빼앗아(evict) 새 페이지에 재할당해야 한다. 빼앗긴 페이지의 내용은 종류에 따라 swap disk나 원본 파일에 보존되어, 나중에 다시 필요하면 page fault를 통해 복원된다. 이 메커니즘 덕분에 프로세스는 물리 메모리보다 큰 가상 주소 공간을 사용할 수 있다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

MMU는 eviction 자체를 수행하지 않는다. 하드웨어가 제공하는 것은 PTE의 accessed bit와 dirty bit뿐이다.

  • Accessed bit (A): MMU가 해당 PTE로 주소 변환을 수행할 때마다 1로 설정한다. OS가 주기적으로 0으로 초기화하여 “최근 참조 여부”를 추적한다.
  • Dirty bit (D): 해당 프레임에 쓰기가 발생하면 1로 설정된다. eviction 시 dirty page는 반드시 저장소에 write-back해야 한다.

eviction 정책(어떤 프레임을 빼앗을지)은 전적으로 OS 소프트웨어의 책임이다.

실제 OS (Linux)

Linux는 kswapd 데몬과 direct reclaim 경로를 통해 프레임을 회수한다.

  • Active/Inactive LRU 계열: 페이지의 최근 참조 상태를 바탕으로 활성·비활성 목록 사이를 이동시키고, 회수 후보를 고르는 전통적인 접근이다.
  • Multi-Gen LRU: 최근 참조 시점이 비슷한 페이지를 세대별로 묶는 대안 구현이다. 사용 여부와 세부 정책은 kernel 버전·build·runtime 설정에 따라 달라지므로 Linux kernel Multi-Gen LRU 문서와 실행 중인 설정을 함께 확인한다.
  • Anonymous page → swap partition/file: swapfile이나 swap partition에 4 KB 단위로 기록. swap 영역의 slot은 bitmap으로 관리한다.
  • File-backed page → write-back or discard: dirty이면 원본 파일에 write-back, clean이면 바로 버린다(원본에서 다시 읽으면 되므로).

PintOS 구현

PintOS의 eviction/swap 구조는 세 계층으로 나뉜다.

1계층: 프레임 할당과 eviction 진입

vm_get_frame()이 palloc_get_page(PAL_USER)를 호출한다. 물리 메모리가 부족하면 NULL을 반환하고, 이때 vm_evict_frame()을 호출하여 victim 프레임을 확보한다.

flowchart TD

  palloc["palloc_get_page(PAL_USER)"]
  success["성공<br/>frame 반환"]
  fail["실패<br/>vm_evict_frame()"]
  victim["vm_get_victim()<br/>정책으로 victim 선택"]
  swap_out["swap_out(victim-&gt;page)<br/>victim 페이지를 저장소로 내보냄"]
  return_victim["victim 프레임 반환<br/>이제 비어있는 프레임"]

  palloc --> success
  palloc --> fail
  fail --> victim
  victim --> swap_out
  swap_out --> return_victim

2계층: Victim 선택 — Clock Algorithm

vm_get_victim()은 전역 frame 리스트를 순환하며 accessed bit = 0인 첫 프레임을 victim으로 선택한다. accessed bit = 1인 프레임은 0으로 초기화하고 다음으로 넘어간다(second chance).

%% Clock Algorithm victim 선택 흐름
flowchart LR
  hand["clock hand"]
  f0["F0<br/>A=1<br/>clear A=0"]
  f1["F1<br/>A=0<br/>victim"]
  f2["F2<br/>A=1<br/>다음 순회에서 clear A=0"]
  more["..."]
  hand --> f0
  f0 --> f1
  f1 -.-> f2
  f2 --> more

PintOS에서 accessed bit 확인은 pml4_is_accessed(), 초기화는 pml4_set_accessed()로 수행한다.

3계층: swap_out / swap_in — 페이지 타입별 분기

struct page_operations의 vtable 패턴으로 타입별 동작이 분기된다.

페이지 타입swap_out 동작swap_in 동작
VM_ANONswap disk에 8 sector 기록, slot 번호를 anon_page에 저장slot에서 8 sector 읽기, bitmap 해제
VM_FILEdirty이면 원본 파일에 write-back, clean이면 아무것도 안 함원본 파일에서 다시 읽기

공통적으로 swap_out 후에는 PTE의 present bit을 0으로 만들어, 다음 접근 시 page fault가 발생하도록 한다.

COW 다중 소유자 처리 (anon_swap_out 상세):

실제 PintOS 구현에서 anon_swap_out()은 하나의 프레임을 여러 프로세스가 COW로 공유하는 경우를 처리한다. frame->ref_count가 1보다 크면 swap slot을 공유 소유자 수만큼 참조 카운트를 올린다:

이 설계 덕분에 COW로 공유하던 3개 프로세스의 동일 페이지가 evict되면, swap disk에는 한 번만 기록되고 swap slot 하나를 참조 카운트 3으로 관리한다.

swap_lock — sector 단위 락:

disk_read()/disk_write() 호출마다 swap_lock을 acquire/release한다. 8번의 sector I/O에서 매번 lock을 잡고 놓는 이유는 다른 프로세스의 swap I/O와 interleaving을 허용하기 위함이다. 전체 page를 한 번에 잠그면 swap I/O 병렬성이 떨어진다.

QEMU 에뮬레이션

QEMU의 역할은 swap disk를 에뮬레이션하는 것이다.

  • PintOS에서 disk_read()/disk_write()를 호출하면 QEMU의 IDE controller model이 이를 받아 호스트 파일(swap.dsk)에 대한 실제 I/O로 변환한다.
  • sector 번호 × 512 byte = 호스트 파일 내 byte offset. 4 KB page = 8 × 512 byte sector.
  • QEMU는 어떤 sector가 swap인지, 데이터인지 구분하지 않는다. 바이트 블록을 전달할 뿐이다.

관찰 시나리오

시나리오 1: 메모리 고갈 시 eviction cascade 추적

다수의 page를 할당하는 테스트(예: swap-file)를 실행하며, eviction이 처음 발생하는 시점과 그 후의 연쇄 eviction 패턴을 관찰한다.

  1. vm_evict_frame에 bp → palloc 실패 시점 확인
  2. vm_get_victim에서 clock hand가 리스트를 몇 바퀴 도는지 counting
  3. anon_swap_out에서 swap slot 번호 순서 → 0, 1, 2, … 순차 할당 확인
  4. disk_write에서 sector 번호 → slot 0은 sector 0-7, slot 1은 8-15, … 확인
  5. eviction 직후 vm_do_claim_page에서 새 page가 같은 frame을 받는지 확인

시나리오 2: COW frame eviction과 swap

fork 후 COW 공유 frame이 eviction되는 경우:

  1. fork 실행 → frame->ref_count=2 확인
  2. 메모리 압박 → anon_swap_out 진입 → ref_count=2에서 swap_slot_ref 호출 확인
  3. swap_ref_count[slot]=2 → 두 프로세스가 같은 slot 공유
  4. 한쪽 프로세스가 swap_in → swap_slot_unref → swap_ref_count=1
  5. 나머지 프로세스도 swap_in → swap_ref_count=0 → bitmap reset → slot 해제

Frame Eviction과 Swap 점검

  • eviction은 MMU가 직접 수행하는 일이 아니라, OS가 accessed/dirty bit을 참고해 선택하는 정책이다.
  • anonymous page 1개는 4 KB이고 swap slot 하나는 512 B sector 8개다.
  • COW 공유 frame을 evict할 때 anon_swap_out()은 frame 내용을 한 번만 쓰고 swap_ref_count를 owner 수에 맞춘다.
  • 각 owner page는 anon.swapped=true, 같은 swap_idx, frame=NULL 상태가 되고 PTE는 pml4_clear_page()로 제거된다.
  • 이후 각 owner가 page fault로 swap-in하면 swap_slot_unref()가 호출되고, 마지막 참조가 빠질 때 bitmap slot이 해제된다.
