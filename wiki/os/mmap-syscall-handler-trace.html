mmap 시스템콜 핸들러 흐름 (Mmap Syscall Handler Trace)

한 줄 요약: 유저의 mmap() 호출이 커널 do_mmap()에 닿으려면 syscall handler의 SYS_MMAP case를 거쳐야 하며, 이 trace는 유저 레지스터의 다섯 인자가 검증되어 do_mmap()으로 연결되는 전체 경로를 따라간다.

확인 범위: PintOS 구현 경로는 woonyong-kr/pintos 5594d46의 lib/user/syscall.c, userprog/syscall.c, vm/file.c를 기준으로 확인했다. Linux·Windows 비교 표는 개념적 경로 비교이며, 특정 버전의 runtime 검증 결과가 아니다.

mmap 시스템콜 핸들러 흐름

userprog/syscall.c의 SYS_MMAP case는 다섯 register 인자를 mmap()으로 넘기고, 같은 파일의 mmap()은 검증을 마친 뒤 vm/file.c의 do_mmap()을 호출한다. 아래 흐름은 이 두 source file의 5594d46 snapshot에서 직접 확인한 경로만 설명하며, 다른 commit의 동작은 범위에 포함하지 않는다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

CPU는 mmap의 의미를 모른다. CPU가 아는 것은 syscall 명령어가 실행되면 MSR_LSTAR에 저장된 커널 진입점 주소로 RIP를 바꾸고, CPL을 3→0으로 전환하며, 유저 RIP를 RCX에 백업한다는 것뿐이다.

하드웨어 동작무엇을 함무엇을 모름
syscall 명령어CPL 3→0, RIP←LSTAR, RCX←유저RIP, R11←RFLAGSRAX=14가 mmap이라는 것
register 전달RAX/RDI/RSI/RDX/R10/R8에 값을 넣음각 값이 주소, 길이, fd 등이라는 것
반환sysretq로 CPL 0→3, RIP←RCXRAX에 든 값이 성공 주소인지 MAP_FAILED인지

PintOS 구현

저장소 확인: woonyong-kr/pintos 5594d46에서 유저 wrapper, syscall dispatch, 인자 검증, do_mmap()·do_munmap() 구현을 확인했다. 아래 설명은 이 commit을 기준으로 한다.

유저 wrapper (lib/user/syscall.c):

syscall 번호 (include/lib/syscall-nr.h):

  • SYS_MMAP = 14 (0xe)
  • SYS_MUNMAP = 15 (0xf)

실패값 (include/lib/user/syscall.h):

커널 handler (userprog/syscall.c): SYS_MMAP과 SYS_MUNMAP case가 각각 mmap(), munmap()으로 dispatch된다. mmap()은 주소·길이·정렬·fd·파일 길이를 검증한 뒤 do_mmap()을 호출한다.

VM 입구 (vm/file.c): do_mmap()은 범위 충돌을 먼저 확인하고 페이지마다 file-backed lazy metadata를 등록한다. 실패하면 생성한 mapping을 do_munmap()으로 되돌린다. do_munmap()은 같은 map_start에 속한 페이지를 순서대로 SPT에서 제거한다.

SYS_MMAP case의 핵심 구조:

QEMU 에뮬레이션

QEMU는 SYS_MMAP = 14라는 번호를 해석하지 않는다. QEMU가 하는 일:

  1. gen_SYSCALL() (emit.c.inc): TCG 코드로 helper_syscall 호출 생성
  2. helper_syscall() (seg_helper.c): guest MSR(STAR, LSTAR, FMASK) 값을 이용해 guest RIP/CS/SS/RFLAGS를 변경
  3. MSR 저장 (misc_helper.c): syscall_init()에서 쓴 MSR_LSTAR→syscall_entry 주소를 보관

PintOS가 syscall_init()에서 MSR_LSTAR에 syscall_entry 주소를 써 두었으므로, QEMU CPU 에뮬레이션은 syscall 명령 후 guest RIP를 그 주소로 이동시킨다. 그 뒤 RAX = 14를 보고 do_mmap()을 호출할지는 PintOS 코드의 일이다.

R10 주의점

3인자 이하 syscall(write, read 등)은 RDI/RSI/RDX만 쓴다. mmap은 5인자이므로 4번째가 R10, 5번째가 R8에 들어간다. R10을 놓치면 fd 해석이 깨진다.

    H->>F: process_get_file(3)
    F-->>H: struct file * (또는 NULL)
    alt file == NULL 또는 검증 실패
        H->>H: f->R.rax = NULL (MAP_FAILED)

    H->>E: return
    E->>C: sysretq (CPL 0→3)
    C->>U: RAX = 결과값

관련 문서

  • mmap file backed page
    • handler를 지난 뒤 file-backed lazy page가 되는 전체 모델.
  • mmap invalid argument
    • SYS_MMAP case에서 뽑은 인자를 어떤 실패 조건으로 걸러야 하는지.
  • munmap 범위
    • SYS_MUNMAP이 do_munmap()으로 들어오는 입구와 범위 정리.
  • file backed metadata
    • do_mmap()이 page별로 저장해야 하는 file, offset, read/zero bytes.
  • mmap dirty write back
    • writable mapping이 dirty page write-back으로 이어지는 흐름.
  • syscall stack switch
    • syscall_entry.S가 register snapshot을 만드는 과정.
  • syscall 전체 흐름
    • write(1, buf, size) 전체 흐름 Trace와 비교.
  • syscall handler() 분기
    • syscall 번호별 분기 상세.
  • syscall ABI
    • RAX/RDI/RSI/RDX 인자 전달 규약.
  • RDX 인자
    • 3인자까지의 register 배치.
  • File Descriptor
    • fd 숫자가 열린 file object로 해석되는 방식.
  • fd 번호
    • fd 0=stdin, 1=stdout 특수 처리.
  • Page Fault Trace
    • handler에서 등록한 lazy page가 첫 접근 때 살아나는 관문.
  • LSTAR MSR
    • LSTAR MSR 진입점 등록 상세.
  • CPL 권한 전환
    • CPL 3→0 권한 전환 상세.
