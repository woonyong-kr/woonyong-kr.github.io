GDB Stub Protocol — guest register를 전달하는 법

GDB Stub Protocol — guest register를 전달하는 법

확인 범위: 이 문서는 GDB Remote Serial Protocol과 QEMU GDB stub의 일반적인 동작 원리 및 구현을 해석할 때의 선택 기준을 설명하며, 제시된 패킷 흐름·코드 경로·QEMU master 구현 설명은 특정 구현을 이해하기 위한 예시다. 실제 코드 위치와 동작, 레지스터 매핑, 실행 기록, 지연·처리량 등 버전과 환경에 따라 달라지는 판단은 해당 소스 버전과 실행 환경에서 별도로 검증해야 한다.

한 줄 요약: QEMU GDB stub이 Remote Serial Protocol로 host GDB와 TCP 통신하는 구조 — target remote 순간 일어나는 일.

GDB Stub Protocol 상태

QEMU의 GDB stub은 GDB Remote Serial Protocol을 구현하여 호스트의 GDB와 TCP 소켓으로 통신한다. PintOS 디버깅에서 target remote localhost:1234를 치는 순간, GDB와 QEMU 사이에 텍스트 기반 패킷 프로토콜이 열린다. 이 프로토콜은 레지스터 읽기/쓰기, 메모리 읽기/쓰기, breakpoint 설정, single-step 등 모든 디버깅 동작을 guest 관점에서 수행한다. GDB는 자신이 “x86-64 CPU에 직접 연결되었다”고 생각하지만, 실제로는 QEMU가 CPUX86State 구조체를 중계하는 것이다.

상세 설명

패킷 프레이밍

GDB Remote Protocol의 일반 command/response 패킷은 다음 프레임을 사용한다:

$<payload>#<2-digit hex checksum>

체크섬은 payload의 모든 바이트를 합한 값의 하위 8비트를 hex로 인코딩한 것이다. ACK mode에서 수신 측은 체크섬을 검증한 뒤 +(ACK)를 보내고, 불일치 시 -(NACK)를 보내 재전송을 요청한다. +, -, interrupt character 같은 제어 바이트는 이 $...#.. 프레임 밖에서 전달될 수 있으므로 “모든 전송 바이트”가 이 형식이라고 일반화하지 않는다.

예시: $g#67
  payload = "g" (ASCII 0x67)
  checksum = 0x67 = "67"

PintOS 디버깅에서 실제로 사용되는 주요 명령어:

연결 수립

1. QEMU 시작: qemu-system-x86_64 -s -S ...
   -s: localhost:1234에서 GDB 연결 대기
   -S: 시작 시 CPU 정지 (freeze)

2. GDB 연결:
   (gdb) target remote localhost:1234

3. 초기 핸드셰이크:
   GDB → QEMU: $qSupported:...#xx     (기능 협상)
   QEMU → GDB: $PacketSize=...;...#xx
   GDB → QEMU: $?#3f                   (stop reason)
   QEMU → GDB: $S05#b8                 (SIGTRAP = 정지 상태)

메모리 접근 경로

GDB가 x/4x 0x8004000000을 실행하면:

GDB → QEMU:  $m8004000000,10#xx    (16바이트 읽기)

QEMU 내부:
  gdb_handle_packet()
    → gdb_read_memory()
      → cpu_memory_rw_debug()
        → address_space_rw()          guest 물리 주소로 변환
          → RAMBlock에서 바이트 읽기   호스트 메모리에서 실제 데이터

QEMU → GDB:  $<32 hex chars>#xx

여기서 0x8004000000은 guest 가상 주소다. QEMU는 내부적으로 guest의 현재 CR3(PML4)을 사용하여 가상 → 물리 주소 변환을 수행한 뒤 RAMBlock에서 데이터를 읽는다.

Breakpoint 메커니즘

Z0는 GDB가 요청하는 software breakpoint 유형이다. 다만 QEMU system emulation의 구현을 “guest RAM을 항상 0xCC로 덮고 나중에 원본 바이트를 복원한다”라고 단정하면 안 된다. QEMU GDB stub은 target별 breakpoint 삽입 경로를 호출하고, TCG에서는 CPU breakpoint 상태와 번역 경계를 이용해 해당 guest PC에서 실행을 멈출 수 있다. 실제 guest 바이트 변경 여부는 target과 실행 모드의 구현으로 확인한다.

현재 QEMU master의 TCG 경로에서는 gdbstub/system.c가 accelerator의 insert_gdbstub_breakpoint에 위임하고, accel/tcg/tcg-accel-ops.c가 cpu_breakpoint_insert()로 CPU breakpoint 목록에 등록한다. 이후 accel/tcg/cpu-exec.c의 check_for_breakpoints()가 TB lookup 전에 정확한 PC와 같은 page의 breakpoint를 검사한다. 같은 page에서는 CF_NO_GOTO_TB | CF_BP_PAGE와 1-instruction 실행 경계를 사용한다. 따라서 “설정 즉시 해당 주소의 기존 TB를 반드시 무효화하고 재번역한다”는 source 설명은 현재 구현과 맞지 않으며 보존하지 않는다.

Stop Reply

QEMU가 실행을 멈췄을 때 GDB에 보내는 응답:

패킷의미발생 상황
S05SIGTRAPbreakpoint, stepi 완료
S0BSIGSEGVdebug target가 SIGSEGV로 정지했다고 보고한 경우; guest pf와 자동으로 같지 않음
S02SIGINTCtrl+C (사용자 중단)
T05thread:01;SIGTRAP + 스레드 정보멀티스레드 모드

PintOS 디버깅 실전 흐름

(gdb) target remote :1234        → 연결 + 기능 협상 + stop reason
(gdb) break thread_start         → Z0,<addr>,1 → breakpoint 등록
(gdb) continue                   → c → QEMU TB 실행 재개
  ... PintOS가 thread_start()에 도달 ...
  QEMU: breakpoint 주소 도달 → $S05 전송
(gdb) info registers             → g → 레지스터 덤프
(gdb) x/10x $rsp                 → m<rsp값>,50 → 스택 메모리 읽기
(gdb) stepi                      → s → 1명령어 실행
  QEMU: target별 single-step 완료 → $S05
(gdb) print $cr2                 → p<cr2 reg#> → page fault 주소

GDB Stub Protocol 값 추적

패킷 오버헤드 계산:

동작패킷 수 (왕복)전형적 지연
stepi2 (s + g)~1ms (localhost TCP)
info registers1 (g)~0.5ms
x/16x addr1 (m)~0.5ms
break *addr1 (Z0)~0.5ms

체크섬 계산 예시:

패킷: $m8004000000,10#??
payload: "m8004000000,10"
  'm'=0x6D, '8'=0x38, 주소의 '0' 8개=8×0x30, '4'=0x34,
  ','=0x2C, '1'=0x31, 길이의 '0'=0x30
  합계: 0x6D + 0x38 + (8×0x30) + 0x34 + 0x2C + 0x31 + 0x30
      = 0x02E6 → 하위 8비트: 0xE6
패킷: $m8004000000,10#e6

QEMU 에뮬레이션 관점

GDB stub은 QEMU 메인 루프와 긴밀하게 연동된다. GDB가 연결되면 QEMU의 vCPU 실행 모드가 바뀐다.

GDB 연결 시 QEMU 내부 상태 변화

정상 실행 모드:
  cpu_exec() → TB 체이닝 → 수백~수천 guest 명령어 연속 실행

GDB 연결 + breakpoint 설정 후:
  cpu_exec() → TB 실행 → 등록 breakpoint 주소 감지
    → gdb_set_stop_cpu() → vm_stop(RUN_STATE_DEBUG)
    → gdb_handlesig() → stop reply 전송 → 대기

GDB single-step 모드 (stepi):
  cpu_exec() → target별 single-step 상태 설정 → 1명령어 실행
    → gdb_handlesig() → stop reply 전송 → 대기

GDB stub이 vCPU에 미치는 성능 영향

모드TB 체이닝명령어/초비고
GDB 미연결활성 (direct jump)~100M+최대 성능
GDB 연결, breakpoint 없음활성~100M+거의 동일
GDB 연결, breakpoint N개breakpoint 주소 검사·번역 경계 영향구현·개수 의존target별 삽입 경로 사용
GDB single-step명령어 단위 실행 제어구현 의존target별 single-step 경로 사용
