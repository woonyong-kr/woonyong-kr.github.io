thread_start() — idle 스레드 생성과 선점형 스케줄링 시작

thread_start() — idle 스레드 생성과 선점형 스케줄링 시작

확인 범위: 이 문서는 idle 스레드와 선점형 스케줄링의 일반 원리 및 PintOS·Linux·QEMU 구현을 바탕으로 한 동작 설명과 비교를 다룬다. 제시된 코드 좌표, 버전별 실제 구현 여부, GDB 실행 결과와 성능·전력 관련 판단은 별도의 소스 및 실행·측정 기록으로 검증해야 한다.

thread_start()는 idle 스레드를 준비한 뒤 인터럽트를 켜서, PintOS가 timer interrupt로 스레드를 선점할 수 있는 상태로 들어가게 한다.

thread_start() 변화

thread_start()는 PintOS 부팅에서 thread_init() 이후 호출되는 함수로, 두 가지 결정적 일을 한다: (1) idle 스레드를 생성하고, (2) intr_enable()로 인터럽트를 활성화해 선점형 스케줄링을 시작한다. 이 함수가 반환된 뒤에야 비로소 timer interrupt가 발생하고, 스레드 간 선점이 가능해진다.

idle 스레드는 “아무 스레드도 실행할 것이 없을 때” CPU가 안전하게 머무르는 장소다. ready_list가 비면 next_thread_to_run()이 idle 스레드를 반환한다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

CPU는 항상 무언가를 실행해야 한다. 멈출 수 없다(HLT 명령 전까지). 만약 실행할 스레드가 없는데 스케줄러가 NULL을 반환하면 커널은 크래시한다. idle 스레드는 이 문제를 해결하기 위한 소프트웨어 관례로, CPU를 hlt 명령어로 저전력 대기시키면서도 인터럽트가 오면 즉시 깨어나게 한다.

x86-64에서 hlt은 특권 명령(ring 0)이며, 다음 인터럽트까지 CPU 파이프라인을 멈춘다. 인터럽트가 발생하면 CPU는 hlt 다음 명령부터 재개한다.

실제 OS (Linux)

Linux에서 idle 스레드는 PID 0 (swapper)이며, 부팅 시 start_kernel() → rest_init() → cpu_startup_entry() 경로로 진입한다. per-CPU로 하나씩 존재하며, 아키텍처별 arch_cpu_idle() 구현이 hlt 또는 mwait 등을 호출한다.

Linux의 idle 스레드는 태스크 배열에 직접 들어가지 않으며, __schedule()에서 runqueue가 비었을 때 fallback으로 선택된다. PintOS의 next_thread_to_run()이 list_empty(&ready_list) 시 idle_thread를 반환하는 것과 동일한 패턴이다.

PintOS 구현

thread_start()의 전체 흐름:

단계별 분석:

  1. sema_init(&idle_started, 0): 동기화용 세마포어 초기화. 값 0 → sema_down 시 즉시 block.

  2. thread_create("idle", PRI_MIN, idle, &idle_started): idle 스레드를 우선순위 최저(0)로 생성. thread_func는 idle(), aux로 세마포어 포인터 전달. 이 시점에서 idle은 ready_list에 들어간다.

  3. intr_enable(): EFLAGS의 IF 비트를 설정. 이후 timer interrupt(IRQ0)가 발생 가능. 즉, 여기서부터 선점이 시작된다.

  4. sema_down(&idle_started): main 스레드가 block되어 idle에게 CPU를 양보. idle이 한 번 스케줄되면 idle_thread = thread_current() 후 sema_up(&idle_started)로 main을 깨운다.

idle() 함수의 동작:

핵심 트릭: sti; hlt을 한 쌍으로 실행한다. sti만 하면 hlt 전에 인터럽트가 끼어들 수 있고, hlt만 하면 인터럽트가 꺼진 상태라 영원히 멈춘다. x86은 sti 직후 한 명령어는 인터럽트를 지연시키므로, sti; hlt은 원자적으로 “인터럽트 켜고 멈춤”이 된다.

idle이 ready_list에 다시 들어가지 않는 이유:

thread_yield()에 조건이 있다:

idle 스레드는 yield 시 ready_list에 넣지 않는다. 대신 next_thread_to_run()에서 list_empty(&ready_list) 시 특수 케이스로 idle_thread를 반환한다.

QEMU 에뮬레이션

hlt 명령어 에뮬레이션:

Guest가 hlt을 실행하면 QEMU TCG에서:

translate.c: gen_helper_hlt()  → TCG op 생성
  → helper_hlt()               // target/i386/misc_helper.c
      env->hflags &= ~HF_INHIBIT_IRQ_MASK;
      env->halted = 1;
      cs->exception_index = EXCP_HLT;
      cpu_loop_exit(cs);        // vCPU 루프 탈출

cpu_loop_exit() 후 QEMU의 메인 루프(cpu_exec())는 cs->halted를 보고 vCPU를 sleep 상태로 전환한다. 이후 가상 인터럽트(timer IRQ)가 주입되면 cs->halted = 0으로 설정되고 실행이 재개된다.

sti shadow 에뮬레이션:

x86은 sti 직후 1 명령어는 인터럽트를 지연시킨다 (interrupt shadow). QEMU는 이를 HF_INHIBIT_IRQ_MASK 플래그로 구현한다:

helper_sti()  // target/i386/misc_helper.c
  env->eflags |= IF_MASK;               // IF=1 설정
  env->hflags |= HF_INHIBIT_IRQ_MASK;   // 1명령어 동안 IRQ 억제

HF_INHIBIT_IRQ_MASK는 다음 명령어(hlt) 실행 후 자동으로 클리어된다. 이 메커니즘이 PintOS idle()의 sti; hlt 원자성을 보장한다 — sti와 hlt 사이에 인터럽트가 끼어들지 못한다.

GDB로 idle 스레드 관찰

① idle 스레드 진입 확인:
   (gdb) b idle
   → hit 시 idle 스레드가 최초 스케줄된 것

② sti;hlt 루프 관찰:
   (gdb) b *idle+오프셋    # asm volatile 위치
   (gdb) info registers eflags
   → IF 비트 상태 확인

③ idle에서 깨어나는 시점:
   (gdb) b intr_handler
   (gdb) commands
     > p intr_name(f->vec_no)
     > bt
     > continue
     > end
   → timer IRQ로 idle이 깨어나는 것 확인

④ next_thread_to_run 관찰:
   (gdb) b next_thread_to_run
   (gdb) commands
     > p list_empty(&ready_list)
     > continue
     > end
   → ready_list가 비면 idle_thread 반환 확인

⑤ idle_ticks 증가 추적:
   (gdb) watch idle_ticks
   → idle 상태에서 timer tick마다 증가
