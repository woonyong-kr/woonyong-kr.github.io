Process Record는 왜 thread와 따로 필요한가

자식 스레드가 먼저 사라져도 부모는 나중에 wait(pid)로 종료 코드를 읽어야 한다. 그래서 종료 상태는 struct thread가 아니라 조금 더 오래 남을 수 있는 process record에 놓인다.

그럼 부모는 어디에서 exit(81)의 81을 읽어야 할까

wait(pid)는 이미 끝난 자식의 종료 코드도 읽을 수 있어야 한다.

그런데 자식이 끝났다면 자식의 struct thread도 곧 사라질 수 있다.

그럼 부모는 어디에서 exit(81)의 81을 읽어야 할까?

이 질문이 Process Record, 이 코드베이스에서는 struct child_status가 필요한 이유다.

Process Record 문제

부모와 자식은 동시에 끝나지 않는다.

가능한 순서는 최소 세 가지다.

순서필요한 정보
부모가 먼저 wait() 호출자식이 끝날 때까지 부모를 재울 장소
자식이 먼저 exit() 호출부모가 나중에 읽을 종료 코드
부모가 먼저 종료아직 살아 있는 자식 상태 레코드를 넘기거나 정리할 기준

struct thread 하나에 모든 것을 넣으면 수명 문제가 생긴다.

자식이 종료하면서 자기 struct thread가 THREAD_DYING으로 넘어가도, 부모가 아직 wait(pid)를 호출하지 않았을 수 있다. 반대로 부모가 먼저 죽으면 자식은 아직 자기 종료 상태를 기록해야 할 수 있다.

이 말은 즉, wait/exit에는 스레드 자체보다 조금 더 오래 남을 수 있는 작은 커널 기록이 필요하다.

Process Record 차이

child_status는 부모와 자식 사이에 놓인 작은 상태표다.

부모는 child_status_list로 “내가 기다릴 수 있는 자식인가”를 판단한다.

자식은 self_status로 “내 종료 코드를 어디에 써야 하는가”를 찾는다.

wait-twice 테스트를 보자

wait-twice 테스트를 보자.

기대 결과는 다음 흐름이다.

첫 번째 wait()가 성공하면 부모는 child_status를 리스트에서 제거하고 해제한다.

두 번째 wait()는 더 이상 같은 child_status를 찾지 못한다. 그래서 -1이 된다.

waited 필드는 “동시에 두 번 기다리는 상황”을 막고, list_remove()와 free()는 “한 번 수거한 자식 상태를 다시 수거하지 않는다”는 규칙을 완성한다.

실제 운영체제

Linux와 Unix 계열에서는 자식이 종료한 뒤에도 부모가 아직 wait()하지 않았다면 종료 상태가 커널에 남는다. 흔히 zombie라고 부르는 상태는 계속 CPU를 쓰는 실행 주체가 아니라, 부모가 수거해야 할 종료 기록에 가깝다.

Windows는 모델이 다르다. 프로세스는 커널 오브젝트이고, 사용자는 process handle을 통해 종료를 기다리거나 종료 코드를 조회한다. 부모-자식 관계보다 handle과 object reference count가 더 중심이다.

두 실제 OS 모두 PintOS보다 훨씬 복잡하다. signal, process group, handle 상속, job object, 권한, reference count, multi-thread process 같은 현실 조건이 붙기 때문이다.

PintOS

이 코드베이스의 핵심 구조체는 SW_AI-W11-pintos/pintos/include/threads/thread.h에 있다.

struct thread에는 연결점 두 개가 있다.

각 필드는 질문 하나에 답한다.

필드답하는 질문
tid부모가 기다리는 pid가 이 자식인가
exit_status자식이 남긴 종료 코드는 무엇인가
waited부모가 이미 wait를 시작했거나 끝냈는가
exited자식이 이미 종료했는가
orphaned원래 부모가 먼저 종료되어 root 쪽으로 넘어갔는가
fork_success자식이 주소 공간과 fd table 복제를 끝냈는가
fork_sema부모가 fork() 반환 전에 자식 초기화를 기다리는 통로
wait_sema부모가 wait()에서 자식 종료를 기다리는 통로
elem부모 또는 root의 child_status_list에 들어가기 위한 list node

중요한 구분은 fork_sema와 wait_sema다.

fork_sema는 “자식이 만들어졌는가”를 기다린다. wait_sema는 “자식이 끝났는가”를 기다린다.

QEMU

QEMU는 child_status의 의미를 알지 못한다.

QEMU 관점에서는 다음 정도만 보인다.

  • guest CPU가 syscall 명령을 실행한다.
  • PintOS 커널이 guest memory 안의 struct child_status 바이트를 읽고 쓴다.
  • sema_down() 때문에 PintOS scheduler가 guest thread 상태를 바꾼다.
  • GDB stub은 guest register와 guest memory를 읽고 써 준다.

근거가 되는 QEMU 위치는 다음이다.

  • target/i386/gdbstub.c
    • x86_cpu_gdb_read_register()
    • x86_cpu_gdb_write_register()
  • gdbstub/gdbstub.c
    • handle_read_mem()
    • handle_write_mem()

이 말은 즉, “누가 부모이고 누가 자식인가”는 PintOS 커널의 정책이다. QEMU는 그 정책이 실행될 하드웨어 효과를 재현할 뿐이다.

PintOS의 child_status는 실제 OS의 프로세스 관리 전체를 흉내 내는 구조가 아니다. 학습자가 fork, wait, exit의 최소 수명 문제를 코드로 다루게 하는 축소 모델이다.

Process Record 코드

process_fork()는 부모 쪽에서 child_status를 만들고 부모 리스트에 넣는다.

파일: SW_AI-W11-pintos/pintos/userprog/process.c

__do_fork()는 자식 쪽에서 같은 레코드를 자기 self_status로 붙잡는다.

process_wait()는 부모 리스트에서 tid가 맞는 레코드를 찾고, 필요하면 wait_sema에서 잔다.

exit(status)는 종료 코드를 자식의 self_status에 쓴다.

파일: SW_AI-W11-pintos/pintos/userprog/syscall.c

process_exit()은 자식 레코드와 자기 레코드를 마무리한다.

finish_self_status()는 부모가 기다릴 수 있도록 exited = true를 남기고 wait_sema를 올린다.

Process Record 값 추적

예를 들어 자식 tid = 7이 exit(81)로 끝난다고 하자.

exit(81) syscall 진입 순간에는 register가 이렇게 보인다.

PintOS exit()이 실행되면 커널 메모리의 레코드가 바뀐다.

정확한 offset은 구조체 padding 때문에 GDB에서 확인한다.

부모가 wait(7)로 돌아올 때는 반대 방향이다.

이 말은 즉, 종료 코드는 유저 스택에서 부모 스택으로 직접 복사되는 값이 아니다. 부모와 자식이 공유하던 커널 상태표를 거쳐 전달된다.

    participant C as 자식 thread

    P->>P: list_push_back(child_status_list, cs)
    P->>C: thread_create(__do_fork)
    P->>CS: sema_down(fork_sema) — 자식 초기화 대기

    C->>CS: self_status = cs
    C->>C: 주소 공간 복제, fd 복제
    C->>CS: fork_success = true
    C->>CS: sema_up(fork_sema)

    Note over P: fork() 반환, tid 획득

    Note over C: 유저 코드 실행...
    C->>CS: exit_status = 81
    C->>CS: exited = true
    C->>CS: sema_up(wait_sema)
    Note over C: thread 소멸

    P->>CS: process_wait(tid)<br/>waited = true
    P->>CS: sema_down(wait_sema) — 이미 exited면 즉시 통과
    P->>P: status = cs->exit_status (81)
    P->>CS: list_remove + free
    Note over CS: 소멸

부모가 먼저 종료하는 경우 (orphan):

flowchart TD
    A["부모 process_exit()"] --> B["reparent_or_reap_children()"]
    B --> C{"자식 cs->exited<br/>AND !cs->waited?"}
    C -->|Yes| D["list_remove + free<br/>(이미 끝났고 아무도 안 기다림)"]
    C -->|No| E["cs->orphaned = true<br/>orphan_status_list로 이동"]
    E --> F["자식이 나중에 exit()"]
    F --> G["finish_self_status()"]
    G --> H{"cs->orphaned<br/>AND !cs->waited?"}
    H -->|Yes| I["list_remove + free<br/>(자기가 스스로 정리)"]
    H -->|No| J["sema_up(wait_sema)<br/>(누군가 기다리고 있음)"]

정리

  • child_status는 부모와 자식 사이에 놓인 작은 Process Record다.
  • 부모는 child_status_list로 자식 여부와 wait 가능 여부를 판단한다.
  • 자식은 self_status로 자기 종료 코드를 기록할 위치를 찾는다.
  • fork_sema는 fork 생성 완료 동기화, wait_sema는 exit 완료 동기화다.
  • 자식의 struct thread가 사라져도 부모가 읽을 종료 기록은 별도 레코드에 남아야 한다.
  • QEMU는 이 레코드의 의미를 모르고, guest CPU/register/memory 관찰 환경만 제공한다.
