TCG 코드 번역

TCG 코드 번역

확인 범위: 이 문서는 TCG의 번역 구조와 OS·QEMU 책임 경계, TCG와 KVM의 선택 기준을 개념적으로 설명한다. 제시된 코드 좌표, 버전별 동작, 실행 출력 예시와 캐시 크기·처리 비용·성능 비율 등의 수치는 실제 QEMU·PintOS 소스와 사용 환경의 실행 기록 및 측정으로 별도 검증해야 한다.

한 줄 요약: guest CPU 명령어를 host 명령어로 바꿔 실행하는 동적 바이너리 번역 엔진 TCG.

TCG 코드 번역 구조

TCG(Tiny Code Generator)는 QEMU가 guest CPU 명령어를 host CPU 명령어로 변환하여 실행하는 동적 바이너리 번역(Dynamic Binary Translation) 엔진이다. OS 책임 경계 관점에서 TCG의 의미는 명확하다: OS는 “CPU가 명령어를 실행한다”고 가정하는데, TCG가 이 가정을 소프트웨어로 이행한다. OS는 TCG의 존재를 전혀 알지 못하며, 알 필요도 없다.

상세 설명

왜 TCG가 필요한가

QEMU의 핵심 책임은 “guest 하드웨어를 재현”하는 것이다. 이 중 가장 비용이 큰 것이 CPU 명령어 실행이다. 단순 인터프리터 방식(한 명령어씩 읽고 → 해석하고 → 시뮬레이션)은 실제 CPU 대비 100~1000배 느리다. TCG는 guest 명령어를 host 네이티브 코드로 사전 번역하여 이 격차를 10배 이내로 줄인다.

번역 파이프라인 개요

TCG의 번역은 3단계로 이루어진다:

  1. Frontend — guest ISA(x86-64)의 명령어를 디코드하여 ISA 독립적인 중간 표현(TCG IR)으로 변환
  2. Optimizer — 불필요한 연산 제거, 상수 전파
  3. Backend — TCG IR을 host ISA(ARM64 등)의 네이티브 코드로 변환

번역 단위는 **Translation Block(TB)**이라 하며, 분기 없이 순차 실행되는 기본 블록(basic block) 하나에 해당한다. TB의 상세 구조, 캐싱, 체이닝, 무효화는 QEMU TCG 번역 블록에서 다룬다.

Apple Silicon Mac에서 PintOS를 돌릴 때 TCG가 사용된다. 이때 x86-64 guest 코드가 ARM64 host 코드로 번역되어 실행된다.

OS가 모르는 것

TCG는 OS 책임 경계 바깥에 있다. OS(PintOS)가 mov rax, [rbx]를 실행하면:

  • 실제 하드웨어: CPU 파이프라인이 fetch → decode → execute
  • QEMU TCG: TB 캐시 조회 → (miss면 번역) → host 코드 실행 → 결과를 CPUX86State에 기록

두 경우 모두 OS가 관찰하는 결과는 동일하다. RAX에 값이 들어가고, page fault가 나면 pf exception이 발생한다. TCG는 하드웨어 계약의 소프트웨어 이행이며, OS-QEMU 책임 분리의 핵심 사례다.

PintOS 개발자에게 미치는 영향

TCG는 OS에 투명하지만, 개발자에게는 두 가지 가시적 영향이 있다:

  1. 성능 차이 — timer_calibrate()가 측정하는 loops_per_tick이 실제 하드웨어와 크게 다르다. TCG 번역 오버헤드 때문에 busy-wait 루프가 느리게 돌기 때문이다.

  2. 디버깅 동작 — GDB breakpoint 설정 시 해당 주소의 TB가 무효화되고 재번역된다. single-step 모드에서는 TB 크기가 1 명령어로 제한되어 눈에 띄게 느려진다.

PintOS에서 timer_calibrate()가 측정하는 loops_per_tick 값이 실제 하드웨어와 크게 다른 이유가 여기 있다. busy-wait 루프의 각 반복이 TB 실행을 거치기 때문이다.

TCG IR 연산 수

TCG IR에는 약 150개의 opcode가 정의되어 있다. 대표적인 것:

TCG IR op의미x86-64 대응
tcg_gen_mov_i6464비트 레지스터 복사mov rax, rbx
tcg_gen_add_i6464비트 덧셈add rax, rbx
tcg_gen_ld_i64메모리 로드mov rax, [addr]
tcg_gen_st_i64메모리 스토어mov [addr], rax
tcg_gen_brcond_i64조건 분기cmp + jcc

x86-64의 복잡한 CISC 명령어 하나가 TCG IR 여러 개로 분해된다. 예를 들어 push rbp는 RSP 감소 + 메모리 스토어 2개의 IR로 변환된다.

PintOS 구체 사례: syscall 명령어의 번역

PintOS에서 유저 프로그램이 syscall 명령어를 실행할 때, TCG가 이를 어떻게 처리하는지 추적하면 TCG의 동작을 구체적으로 이해할 수 있다.

x86-64 syscall 명령어

syscall은 TB를 종료시키는 명령어다. 이유:

  1. CPL이 3→0으로 바뀐다 (권한 전환)
  2. RIP가 LSTAR MSR 값으로 점프한다
  3. RFLAGS가 수정된다 (FMASK MSR 적용)

TCG는 이 모든 부수 효과를 에뮬레이션해야 하므로, syscall을 만나면 현재 TB를 끝내고 helper 함수(helper_syscall)를 호출하는 TCG IR을 생성한다.

번역 결과 (개념적)

; TB #1: syscall 직전까지의 유저 코드
tcg_gen_mov_i64(rax, SYS_WRITE)    ; mov rax, 1
tcg_gen_mov_i64(rdi, fd_val)        ; mov rdi, 1
tcg_gen_mov_i64(rsi, buf_addr)      ; mov rsi, 0x4747a0
tcg_gen_mov_i64(rdx, size_val)      ; mov rdx, 13
gen_helper_syscall()                 ; syscall 에뮬레이션
tcg_gen_exit_tb()                    ; TB 종료

; helper_syscall() 내부에서:
; 1. CPUX86State.eip = CPUX86State.lstar (0x8004000200 등)
; 2. CPUX86State.hflags의 CPL 비트를 0으로 설정
; 3. CPUX86State.eflags &= ~FMASK
; → 다음 TB는 커널의 syscall_entry에서 시작

이후 QEMU는 CPUX86State.eip(= LSTAR 값 = PintOS의 syscall_entry)를 PC로 새 TB를 조회/번역한다. 커널 코드의 TB 체인이 시작되며, syscall_handler() → iret → 유저 복귀까지가 별도 TB들로 번역된다.

GDB에서 TCG 디버깅

TB 통계 확인

QEMU monitor(-monitor stdio 또는 Ctrl-A c)에서:

(qemu) info jit
# 출력 예시:
# Translation buffer state:
# gen code size       7654321/33554432
# TB count            12345
# TB avg host size    620 bytes
# TB avg guest size   35 bytes
# cross page TB count 234

gen code size가 32 MB(33,554,432)에 가까워지면 전체 flush가 임박했음을 의미한다.

특정 guest 주소의 TB 디스어셈블

(qemu) info tb 0x000000004747a0
# 해당 guest PC에서 시작하는 TB의 host 코드 디스어셈블리 출력

PintOS 디버깅 중 특정 함수가 의도대로 실행되는지 확인할 때, TB 경계가 어디서 끊기는지 보면 분기/인터럽트 동작을 이해하는 데 도움이 된다.
