TSS rsp0 커널 스택

TSS rsp0 커널 스택

확인 범위: 이 문서는 x86-64의 권한 전환과 TSS rsp0의 일반 원리를 설명하고, Linux·PintOS·QEMU의 동작과 코드 좌표는 입력 본문에 제시된 구현을 기준으로 정리한다. 구체적인 코드 경로와 값의 일치 여부, 버전별 차이, 실제 실행 결과 및 성능은 해당 소스 버전과 GDB·QEMU 실행 기록을 별도로 확인해야 한다.

유저 모드에서 커널로 들어올 때는 유저 스택을 그대로 믿을 수 없다. TSS rsp0는 이 순간 CPU와 진입 코드가 사용할 커널 스택 꼭대기를 알려 주는 주소다.

TSS rsp0 커널 스택 상태

x86-64에서 유저 모드(ring 3) 코드가 실행되는 도중 인터럽트나 syscall이 발생하면, CPU는 커널 모드(ring 0)로 전환하면서 스택도 교체해야 한다. 이때 CPU가 “커널 스택이 어디인지”를 찾는 유일한 방법이 **TSS(Task-State Segment)**의 rsp0 필드를 읽는 것이다. OS는 컨텍스트 스위치 때마다 이 필드를 현재 스레드의 커널 스택 꼭대기 주소로 갱신해야 한다.

상세 설명

추상 개념 (CPU 하드웨어 규칙)

x86-64 CPU는 권한 수준(ring) 전환이 수반되는 인터럽트/예외 발생 시 다음 순서로 동작한다:

  1. GDT의 Task Register(TR)가 가리키는 TSS 세그먼트를 찾는다
  2. TSS에서 목적 ring에 해당하는 RSP를 읽는다 (ring 0이면 rsp0)
  3. 새 RSP로 스택을 전환한 뒤 이전 SS, RSP, RFLAGS, CS, RIP를 push한다
  4. 핸들러 코드로 점프한다

syscall 명령어는 약간 다르다. CPU가 자동으로 TSS에서 rsp0를 읽지 않고 RSP를 그대로 둔다. 대신 진입점 코드(소프트웨어)가 TSS에서 rsp0를 직접 읽어 스택을 전환한다. 결과적으로 어느 경로든 TSS rsp0가 올바른 커널 스택을 가리켜야 한다.

TSS 구조체의 x86-64 레이아웃(간략):

실제 OS (Linux)

Linux는 per-CPU TSS를 cpu_tss_rw 배열에 두고, 컨텍스트 스위치 시 __switch_to()에서 cpu_tss_rw[cpu].x86_tss.sp0을 새 태스크의 커널 스택 꼭대기로 설정한다. Linux는 IST(Interrupt Stack Table)도 활용해 NMI, double fault, MCE 등 치명적 예외는 별도 스택에서 처리한다.

PintOS 구현

PintOS에서 TSS는 전역 변수 하나(struct task_state *tss)로 관리된다. 핵심 함수 세 개:

tss_init() — 부팅 시 1회 호출 (userprog/tss.c:51):

한 페이지(4 KB)를 할당해 0으로 초기화하고, 현재 스레드의 커널 스택으로 rsp0를 설정한다.

tss_update() — 스레드 전환 시마다 호출 (userprog/tss.c:76):

next + PGSIZE가 커널 스택 꼭대기인 이유: PintOS에서 struct thread는 4 KB 페이지 하단에 위치하고, 같은 페이지의 상단이 커널 스택이다.

QEMU 에뮬레이션

QEMU TCG에서 인터럽트/예외에 의한 ring 전환 시 TSS rsp0 읽기는 do_interrupt64() (target/i386/tcg/seg_helper.c)에서 수행된다. 이 함수는 CPUX86State::tr (Task Register)를 참조하여 TSS 세그먼트 베이스 주소를 얻고, rsp0 필드를 guest 메모리에서 직접 읽는다.

단계TCG 함수/동작효과
1do_interrupt64()env->tr.base에서 TSS 베이스 주소 획득
2cpu_ldq_kernel(env, tss_base + 4)TSS offset 4에서 rsp0 읽기 (8 bytes)
3env->regs[R_ESP] = rsp0guest RSP를 커널 스택으로 전환
4old SS/RSP/RFLAGS/CS/RIP push커널 스택에 interrupt frame 구성

syscall 경로는 다르다. TCG의 helper_syscall() (target/i386/tcg/seg_helper.c)은 하드웨어처럼 RSP를 건드리지 않는다. LSTAR가 가리키는 syscall_entry 코드가 소프트웨어적으로 TSS에서 rsp0를 읽는데, 이 메모리 접근은 TCG에서 일반 ldq 연산으로 번역된다.

TR(Task Register)와 TSS의 관계: PintOS 부트 시 gdt_init()이 GDT에 TSS 디스크립터를 등록하고 ltr 명령어로 TR에 로드한다. 이후 QEMU의 CPUX86State::tr.base가 TSS의 guest 물리 주소를 보존하므로, do_interrupt64()가 매번 GDT를 재참조하지 않고 캐시된 베이스를 사용한다.

GDB에서 TSS rsp0 관찰 (3단계):

  1. b tss_update — breakpoint 설정 후 p/x (uint64_t)next + 4096으로 갱신될 rsp0 값 확인
  2. b syscall_entry — syscall 진입 시 x/gx &tss로 tss 포인터, x/gx *(uint64_t *)&tss + 4로 실제 rsp0 값 확인
  3. si 3번(movabs, movq, movq) 후 info registers rsp — RSP가 rsp0 값으로 전환되었는지 확인
