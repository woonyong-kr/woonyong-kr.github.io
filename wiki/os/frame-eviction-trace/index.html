프레임 교체 (Frame Eviction) Trace

확인 범위: 이 문서는 프레임 교체의 일반 원리와 선택·보존 기준을 설명하면서, 입력에 제시된 현재 PintOS VM 구현의 코드 경로와 QEMU의 역할을 구분해 해설한다. 구체적인 함수·줄 번호·상태 전이와 테스트·GDB 관찰값은 해당 코드 및 실행 환경에서 별도로 확인해야 하며, 본문 자체는 특정 버전의 실행 기록이나 성능 측정 결과를 제시하지 않는다.

프레임이 부족하면 어떤 일이 일어나는가

메모리가 부족하면 프로그램을 그대로 실패시켜도 된다고 생각하기 쉽다. 그러나 가상 메모리(VM)를 사용하는 운영체제는 먼저 다른 가능성을 살핀다.

지금 RAM에 올라온 페이지 중 하나를 잠시 내보내고, 그 자리에 새 페이지를 올릴 수 있나?

프레임은 한정된 실제 메모리 공간이고, 페이지는 그 공간을 빌려 쓰는 가상 메모리 단위다. 새 페이지에 내줄 빈 프레임이 없다면 운영체제는 기존 페이지가 차지한 프레임을 회수해야 한다. 이 과정이 frame eviction이다.

가상 메모리는 프로세스가 실제 DRAM보다 넉넉한 메모리를 가진 것처럼 보이게 한다. 이를 유지하려면 운영체제가 다음 세 가지 일을 해야 한다.

  1. 비어 있는 프레임을 관리한다.
  2. 빈 프레임이 없으면 victim frame을 고른다.
  3. victim의 내용을 보존해야 한다면 swap 영역이나 파일에 기록한 뒤, 회수한 프레임을 새 페이지에 넘긴다.

따라서 frame eviction은 CPU 메모리 접근에서 Page Fault 복구까지의 Trace의 뒷부분에 해당한다. vm_try_handle_fault()가 복구할 수 있는 fault라고 판단했더라도 실제 프레임을 확보하지 못하면 프로그램은 실행을 계속할 수 없다.

페이지와 프레임을 구분해서 보기

프레임 교체 흐름을 따라가려면 각 구조가 어떤 질문에 답하는지 구분해야 한다.

개념 질문
struct page 이 유저 VA는 어떤 의미의 페이지인가?
struct frame 지금 어느 실제 프레임이 이 페이지 내용을 담고 있는가?
page table PTE CPU가 이 VA를 지금 어떤 프레임으로 번역할 수 있는가?
swap/file backing 프레임에서 쫓겨난 내용을 어디에 보관할 것인가?

전체 실행 순서는 아래 Mermaid를 정본으로 삼는다. vm_get_frame()은 빈 user page를 얻지 못하면 내부에서 vm_evict_frame()을 호출한다. vm_evict_frame()은 vm_get_victim()으로 내보낼 프레임을 고르고 swap_out()을 수행한 뒤, 재사용할 frame을 반환한다.

여기서 SPT는 supplemental page table이다. page table이 현재 CPU가 해당 VA를 번역할 수 있는지를 나타낸다면, SPT는 그 VA가 원래 합법적인 페이지인지와 backing이 어디에 있는지를 기억한다.

프레임 세 개로 보는 교체 과정

페이지 크기가 4096B이고 유저 풀에서 쓸 수 있는 프레임이 3개뿐이라고 해보자.

frame F0 -> page A (VA 0x8048000)
frame F1 -> page B (VA 0x8049000)
frame F2 -> page C (VA 0x804a000)

새로 필요한 page D (VA 0x804b000)

빈 프레임이 없으므로 운영체제는 A, B, C 중 하나를 victim으로 골라야 한다. B를 고른다면 다음 순서로 프레임을 넘길 수 있다.

1. B가 수정되었는지 확인
2. 필요하면 B 내용을 swap/file에 기록
3. B의 PTE present bit를 끔
4. F1.page를 D로 바꿈
5. D 내용을 F1.kva로 읽어 옴
6. D의 PTE를 F1에 매핑

유저 프로그램에는 D에 대한 접근이 잠시 느려진 것으로 보이지만, 내부에서는 4KB 크기의 프레임을 다른 페이지에 넘기는 작업이 일어난다.

현실의 운영체제와 PintOS

Linux와 Windows는 PintOS보다 훨씬 복잡한 물리 메모리 관리자와 페이지 교체 정책을 사용한다.

  • Linux는 LRU 계열 reclaim, anonymous/file-backed page, page cache, writeback, cgroup, NUMA 같은 요소를 함께 다룬다.
  • Windows는 working set, standby/modified page list, section object, pagefile 같은 구조로 resident page와 backing store를 관리한다.

그래도 운영체제가 답해야 하는 기본 질문은 PintOS와 같다.

이 페이지를 RAM에서 내보내도 되는가? 내보낸다면 내용을 어디에 보관해야 하는가?

현실의 운영체제는 여기에 SMP, 장치 I/O, 파일 캐시, 보안, 성능 정책까지 고려하므로 PintOS보다 훨씬 많은 상태를 살핀다.

현재 기준 PintOS VM 구현에서 frame eviction의 뼈대는 다음 파일에 있다.

  • PintOS 저장소 상대 경로 pintos/vm/vm.c
    • vm_get_frame()
    • vm_evict_frame()
    • vm_get_victim()
    • vm_do_claim_page()
  • PintOS 저장소 상대 경로 pintos/include/vm/vm.h
    • struct page
    • struct frame
    • struct page_operations
  • PintOS 저장소 상대 경로 pintos/vm/anon.c
    • anon_swap_in()
    • anon_swap_out()
  • PintOS 저장소 상대 경로 pintos/vm/file.c
    • file_backed_swap_in()
    • file_backed_swap_out()

현재 기준 저장소에서 eviction은 clock 기반 victim 선택에서 page type별 swap out 호출로 이어진다. 일부 함수에는 이전 과제 주석이 남아 있지만, 그 아래에 실제 구현 코드가 들어 있다.

vm_get_frame()의 흐름은 다음과 같다.

palloc()으로 frame을 얻는다.
유저 풀 메모리가 꽉 차면 frame을 evict해서 사용 가능한 공간을 얻는다.

따라서 코드를 읽을 때는 어디를 새로 채워야 하는지가 아니라, 빈 프레임 확보 실패를 어떤 구현 경로로 복구하는지를 따라가야 한다.

QEMU가 담당하는 층

QEMU는 PintOS의 frame eviction 정책을 알지 못한다.

QEMU에서 PintOS의 유저 프레임은 guest physical memory 안의 4KB 영역이다. 이 guest physical memory는 QEMU process의 MemoryRegion/RAMBlock 같은 구조로 backing된다.

대표 코드 위치:

  • include/system/memory.h
    • struct MemoryRegion
    • address_space_rw()
  • include/system/ramblock.h
    • struct RAMBlock
    • host
    • ramblock_ptr()
  • system/physmem.c
    • address_space_rw()
    • cpu_physical_memory_read()
    • cpu_physical_memory_write()
  • excp_helper.c
    • x86 page walk 중 present/accessed/dirty bit를 확인하고 갱신하는 경로

PintOS의 swap out과 host OS의 swap out은 이름은 비슷하지만 서로 다른 층에서 일어난다.

  • PintOS swap out: guest OS가 자신의 페이지를 디스크나 파일 backing으로 내보내기로 결정한다.
  • Host OS swap out: macOS/Linux가 QEMU process의 host memory를 swap할 수 있다.

PintOS가 anon_swap_out()을 구현해도 QEMU가 그 의미를 해석하는 것은 아니다. QEMU는 guest가 디스크 장치와 메모리를 읽고 쓰는 하드웨어 효과를 제공할 뿐이다.

항목 Linux / Windows PintOS QEMU
victim 선택 복잡한 reclaim/working set 정책 vm_get_victim()의 clock algorithm 정책 없음
프레임 관리 전역/NUMA/per-process 상태가 얽힘 struct frame과 별도 frame table을 직접 설계 guest RAM backing을 제공
dirty 판단 PTE dirty, writeback 상태, file cache 등 pml4_is_dirty()와 page type별 swap_out() 활용 가능 guest PTE bit 효과를 에뮬레이션
내보낼 위치 swap/pagefile/file backing anon은 swap, file-backed는 파일 writeback OS 정책을 모름
실패 처리 OOM killer, working set 조정, 프로세스 예외 등 구현 실패 시 테스트 실패 또는 panic 가능 guest가 한 메모리 접근의 하드웨어 결과만 제공

프레임을 넘길 때 지켜야 할 계약

eviction의 목표는 단순히 프레임 하나를 얻는 것이 아니다. old page와 이어진 모든 연결을 안전하게 끊고, 같은 프레임을 new page에 넘겨야 한다.

현재 구현에서 확인할 계약은 네 단계로 나눌 수 있다.

단계 구현 질문 코드 자리
1. 빈 frame 시도 palloc_get_page(PAL_USER)가 성공했는가 vm_get_frame()
2. victim 선택 빈 frame이 없으면 어떤 struct frame을 고를 것인가 vm_get_victim()의 clock hand
3. old page 보존 victim page의 bytes를 swap 또는 file에 저장했는가 swap_out(victim->page)
4. stale mapping 제거 old page의 PTE와 page->frame 연결을 끊었는가 anon_swap_out(), file_backed_swap_out()의 owner 순회

swap_out()만 호출하고 작업을 끝내면 위험하다. swap_out()이 bytes를 보존하더라도 old PTE가 present로 남아 있으면 CPU는 이미 다른 page가 사용하기 시작한 frame을 old VA로 계속 접근할 수 있다.

victim frame을 재사용하기 위한 최소 후처리는 다음과 같은 흐름이다.

victim = vm_get_victim()
old = victim->page

swap_out(old) 성공
old page table entry를 not-present로 변경
old->frame = NULL
victim->page = NULL

return victim

이후 vm_do_claim_page(new_page)가 같은 frame을 받아 새 연결을 만든다.

victim->page = new_page
new_page->frame = victim
pml4_set_page(new_page->va, victim->kva, writable)
swap_in(new_page, victim->kva)

이 과정에서 빠진 단계에 따라 서로 다른 문제가 생긴다.

빠진 단계 생기는 문제 증상
swap_out(old) 실패를 무시 old page의 dirty bytes가 사라짐 swap 테스트에서 이전 값이 깨짐
old PTE clear 누락 old VA와 new VA가 같은 frame을 공유 서로 다른 주소의 값이 같이 변함
old->frame = NULL 누락 SPT metadata가 resident라고 오해 다음 fault/cleanup에서 같은 frame을 두 번 만짐
victim->page = NULL 누락 새 claim 전에 frame owner가 섞임 frame table 순회와 destroy에서 잘못된 page를 봄

swap_out()이 내용을 보존할 위치는 page type에 따라 달라진다.

page type 내보낼 위치 판단 기준 이어서 볼 문서
VM_ANON swap disk slot 원본 파일이 없으므로 4096B snapshot 필요 Anonymous Page와 Swap Slot, Swap Slot 쓰기는 어떻게 PintOS IDE와 QEMU BlockBackend까지 내려가는가
VM_FILE dirty 원래 file offset mmap으로 수정된 bytes를 파일에 write-back mmap dirty write back은 어떻게 디스크 쓰기로 내려가나
VM_FILE clean 다시 파일에서 읽을 수 있음 dirty bit가 꺼져 있으면 write-back 생략 가능 file backed page metadata에는 무엇을 저장해야 하나
VM_UNINIT 보통 frame이 아직 없음 아직 claim되지 않은 lazy page는 eviction 대상이 아님 Lazy Loading Segment 흐름

vm_get_victim()도 아무 frame이나 고를 수 없다. 현재 구현은 frame table을 순환하면서 clock hand로 accessed bit를 확인한다. 최근에 접근된 frame에는 vm_frame_set_accessed(frame, false)를 적용해 한 번 더 기회를 준다.

PTE에 새 mapping 설치하기

파일:

  • PintOS 저장소 상대 경로 pintos/threads/mmu.c

*pte = vtop(kpage) | PTE_P | (rw ? PTE_W : 0) | PTE_U;

old PTE의 present bit 제거하기

같은 파일의 pml4_clear_page()는 present bit를 끈다.

*pte &= ~PTE_P;

victim page가 쫓겨났는데도 PTE가 present로 남으면 CPU가 예전 프레임에 계속 접근할 수 있다. 그러면 new page와 old page가 같은 프레임을 동시에 소유한 것처럼 되어 메모리 내용이 깨진다.

accessed/dirty bit로 선택과 보존 결정하기

PintOS는 다음 helper를 제공한다.

  • pml4_is_accessed()
  • pml4_set_accessed()
  • pml4_is_dirty()
  • pml4_set_dirty()

PTE_A = 0x20, PTE_D = 0x40이다. clock 알고리즘은 accessed bit를 보고 최근에 사용한 페이지에 한 번 더 기회를 줄 수 있다. dirty bit는 수정된 페이지를 swap이나 파일에 기록해야 하는지 판단하는 데 사용할 수 있다.

QEMU의 x86 TCG 경로도 같은 하드웨어 의미를 흉내 낸다. excp_helper.c에는 page walk 중 PG_ACCESSED_MASK를 세우고, store 접근이면 PG_DIRTY_MASK까지 세우는 흐름이 있다.

주소와 상태 값 추적하기

한 프레임 안에서 바이트 찾기 

PGSIZE = 4096 = 0x1000

frame->kva = 0x800012340000
page->va   = 0x0000008048000

pml4_set_page(pml4, page->va, frame->kva, writable)가 성공하면:

VA 0x8048123
  page base = 0x8048000
  offset    = 0x123

frame base = frame->kva
byte addr  = frame->kva + 0x123

유저가 0x8048123을 읽으면 현재 mapping에 따라 frame->kva + 0x123에 있는 바이트를 읽는다.

PTE에서 주소와 flag 분리하기

어떤 PTE가 다음 값이라고 해보자.

PTE = 0x0000000012345067

낮은 12비트는 flag이고 위쪽 비트는 frame base 주소다.

PTE_ADDR(PTE) = 0x0000000012345000
flags         = 0x067

0x001 PTE_P present
0x002 PTE_W writable
0x004 PTE_U user
0x020 PTE_A accessed
0x040 PTE_D dirty

이 PTE는 유저가 읽고 쓸 수 있으며 최근에 접근되었고 수정된 적도 있는 페이지를 나타낸다. 이 페이지를 victim으로 고른다면 dirty data를 먼저 보존해야 한다.

eviction 전후의 소유 관계 

eviction 전:
  F1.kva bytes = page B 내용
  B.frame      = F1
  F1.page      = B
  B의 PTE      = present

eviction 후:
  B.frame      = NULL 또는 non-resident 표시
  B의 PTE      = not-present
  F1.page      = D
  D.frame      = F1
  F1.kva bytes = page D 내용
  D의 PTE      = present

이 상태 전이가 완전하지 않으면 대표적으로 두 가지 버그가 생긴다.

  • stale mapping: 쫓겨난 page B가 여전히 F1을 가리킨다.
  • lost dirty data: 수정된 B를 저장하지 않고 F1을 D로 덮어쓴다.

점검할 불변식

  • 빈 user frame을 얻지 못하면 vm_get_frame()은 vm_evict_frame()으로 넘어간다.
  • victim 선택은 frame table을 clock hand로 돌며 accessed bit가 꺼진 frame을 찾는 일이다.
  • swap_out(victim->page)는 bytes를 보존하고 old owner들의 PTE와 page->frame 연결을 끊어야 한다.
  • anonymous page와 file-backed page는 서로 다른 기준으로 내용을 보존한다. anonymous page는 swap slot과 swap_ref_count를 사용하고, file-backed page는 file offset과 dirty bit를 사용한다.
  • QEMU는 이 정책을 해석하지 않고 guest 메모리 접근과 디스크 I/O라는 하드웨어 효과만 제공한다.

프레임 교체를 설명하는 관점

frame eviction은 메모리가 부족할 때 페이지를 포기하는 작업이 아니다. 한정된 프레임을 다른 페이지가 안전하게 재사용할 수 있도록 기존 내용을 보존하고 소유 관계와 주소 변환을 바꾸는 작업이다.

PintOS에서는 vm_get_frame()이 빈 프레임을 얻지 못하면 vm_evict_frame()으로 이어진다. 이때 victim의 struct page, PTE present bit, dirty/accessed bit, swap/file backing을 함께 처리해야 페이지 내용과 주소 변환을 보존할 수 있다.

QEMU는 이러한 교체 정책을 알지 못한다. QEMU가 제공하는 것은 guest physical memory와 x86 page-table의 하드웨어 효과다. 따라서 PintOS가 수행하는 swap out과 host OS가 QEMU process를 swap out하는 현상은 구분해서 보아야 한다.
