바이트를 Pointer로 해석하기

확인 범위: 이 문서는 x86-64에서 같은 바이트를 정수와 포인터로 구분해 해석하는 일반 원리와 PintOS·GDB·QEMU에서의 적용 기준을 설명한다. 제시된 주소, 필드 오프셋, 구조체 배치, 명령 출력과 포인터 유효성 판단은 특정 빌드의 코드·설정·실행 기록을 검증한 결과가 아니므로 실제 환경의 선언, ABI, 버전과 디버깅 결과로 별도 확인해야 한다.

한 줄 요약: 8바이트를 주소로 해석하면 포인터가 되는 방식 — 같은 바이트가 정수와 포인터로 다르게 읽힘.

Pointer 해석

메모리의 8바이트(x86-64 기준)를 주소로 해석하면 포인터가 된다. 같은 바이트 0x00 0x40 0x00 0x80 0x00 0x00 0x00 0x00이 정수로 읽으면 0x0000000080004000이지만, 포인터로 해석하면 “주소 0x80004000을 가리키는 참조”가 된다. OS 디버깅에서는 struct thread의 pml4, fd_table 같은 포인터 필드와 magic 같은 정수 무결성 필드를 선언에 따라 구분해야 한다.

상세 설명

추상 개념 (포인터 인코딩 규칙)

x86-64에서 포인터는 8바이트 정수와 물리적으로 동일한 비트 패턴이다. 차이는 순전히 의미론적이다.

속성규칙
크기8바이트 (64비트)
바이트 순서Little-endian (LSB가 낮은 주소)
정렬8바이트 정렬 권장
유효 비트PintOS의 4-level paging 전제에서는 48비트 canonical form
canonical 규칙CR4.LA57=0이면 bit[63:48]은 bit[47]의 부호 확장. LA57이면 57비트 규칙을 사용

Canonical form의 결과:

유저 공간:   0x0000000000000000 ~ 0x00007FFFFFFFFFFF  (bit47=0, 상위 0)
커널 공간:   0xFFFF800000000000 ~ 0xFFFFFFFFFFFFFFFF  (bit47=1, 상위 1)
비정규 구간: 0x0000800000000000 ~ 0xFFFF7FFFFFFFFFFF  (사용 불가)

PintOS에서는 커널 주소가 KERN_BASE = 0x8004000000부터 시작하므로 실제 Linux/Windows의 canonical 분할과는 다르다. 하지만 “8바이트가 주소인가 정수인가”라는 해석 문제는 동일하다.

포인터 vs 정수: 같은 바이트, 다른 의미

주소 0x800400e010의 내용: 00 d0 00 04 80 00 00 00

정수로 해석:
(gdb) x/1gx 0x800400e010  → 0x000000800400d000
  → 정수로만 보면 의미 없는 큰 숫자

포인터로 해석:
(gdb) x/1a 0x800400e010   → 0x800400d000
  → 이 값이 struct thread* 라면, 0x800400d000에 다른 스레드가 있다
  → (gdb) p *(struct thread *)0x800400d000  → 해당 스레드 구조체 전체 출력

GDB의 x/a 포맷이 핵심이다. x/x는 정수로 보여주고, x/a는 주소(address)로 보여준다. 출력 형태는 비슷하지만, x/a는 심볼 테이블을 참조하여 가장 가까운 심볼 이름을 덧붙여준다.

PintOS에서 포인터로 해석하는 핵심 필드

구조체필드타입가리키는 대상오프셋
struct threadpml4uint64_t *PML4 테이블의 커널 VA+104 근처
struct threadfd_tablestruct file **fd 테이블 페이지+136 근처
struct threadparentstruct thread *부모 스레드가변
struct pageframestruct frame *물리 프레임 구조체가변
struct framekvavoid *프레임의 커널 가상 주소+0
struct framepagestruct page *역방향 참조+8
intr_frameripuint64_t다음 실행할 명령어 주소+136
intr_framerspuint64_t스택 포인터+152

intr_frame의 rip, rsp는 타입이 uint64_t(정수)이지만 의미는 포인터다. 이것이 “같은 바이트, 다른 해석”의 전형적 사례다.

NULL 포인터와 잘못된 포인터

포인터 디버깅에서 가장 자주 만나는 패턴:

NULL 포인터 (8바이트 전부 0):
(gdb) x/1a 0x800400e010   → 0x0
  → fd_table[3]이 NULL이면 해당 fd가 닫혀 있다

의심스러운 포인터 (수명 종료·손상 여부를 추가 확인):
(gdb) x/1a 0x800400e010   → 0x800400f000
(gdb) p *(struct thread *)0x800400f000
  → 현재 빌드의 THREAD_MAGIC과 불일치하면 구조체 불변식 위반이다. 이것만으로 해제 여부를 확정하지 말고 할당 수명과 overwrite를 함께 추적한다.

정렬 의심 (대상 타입의 정렬 조건과 비교):
(gdb) x/1a 0x800400e010   → 0x800400d003
  → `_Alignof(struct thread)`가 8인 현재 빌드라면 의심 신호다. ABI·packing에 따라 요구 정렬이 달라지고 x86-64는 일부 비정렬 접근도 허용하므로 하위 3비트만으로 무효를 확정하지 않는다.

GDB 실전 디버깅 패턴

패턴 1: 포인터 체인 추적 (thread → fd_table → file → inode)

# 1. 현재 스레드 찾기
(gdb) p thread_current()
$1 = (struct thread *) 0x800400e000

# 2. fd_table 포인터 읽기
(gdb) p/x ((struct thread *)0x800400e000)->fd_table
$2 = 0x800400f000

# 3. fd=3 슬롯의 file* 읽기 (오프셋 = 3 × 8 = 24)
(gdb) x/1a 0x800400f000+24
0x800400f018: 0x800400a200

# 4. 해당 file 구조체 보기
(gdb) p *(struct file *)0x800400a200

패턴 2: PML4 → 페이지 테이블 엔트리 추적

# PML4 base 읽기
(gdb) p/x thread_current()->pml4
$1 = 0x8004501000

# PML4[0] 읽기 (첫 번째 8바이트)
(gdb) x/1gx 0x8004501000
0x8004501000: 0x0000000000502067

# 하위 12비트 = 플래그 (0x067 = Present|RW|User)
# 상위 비트 = 다음 테이블의 PA (0x502000)
# 이 PA를 포인터로 따라가면 PDPT에 도달

패턴 3: 연결 리스트 포인터 따라가기

# ready_list의 첫 번째 elem
(gdb) p ready_list.head.next
$1 = (struct list_elem *) 0x800400e0b8

# list_entry로 thread* 역산 (elem 오프셋 확인 필요)
(gdb) p (struct thread *)((char *)0x800400e0b8 - 오프셋)

실제 OS (Linux/Windows)

Linux에서도 포인터 해석은 동일하지만 KASLR(Kernel Address Space Layout Randomization)이 적용되어 커널 포인터의 기준 주소가 부팅마다 달라진다. /proc/kallsyms로 현재 심볼 주소를 확인해야 한다.

Linux의 task_struct에서 포인터 필드 예:

필드타입대응하는 PintOS 개념
mmstruct mm_struct *pml4 (주소 공간)
filesstruct files_struct *fd_table
parentstruct task_struct *parent
stackvoid *커널 스택 시작 주소

QEMU 에뮬레이션

QEMU의 CPUX86State 내부에서 포인터와 정수의 구분이 모호한 대표 사례:

QEMU는 guest의 포인터를 host 포인터로 직접 사용하지 않는다. 반드시 address_space_rw() 등으로 GPA → HVA 변환을 거친다.

Pointer 해석 값 추적

포인터 크기와 배열 인덱싱:

x86-64 포인터 크기: 8바이트

fd_table 배열 크기 = PGSIZE / sizeof(struct file *)
                   = 4096 / 8
                   = 512 슬롯

fd=3의 주소 = fd_table_base + 3 × 8 = fd_table_base + 24 (0x18)
fd=100의 주소 = fd_table_base + 100 × 8 = fd_table_base + 800 (0x320)

struct page 포인터 배열에서:
pages[5]의 주소 = pages_base + 5 × 8 = pages_base + 40 (0x28)
