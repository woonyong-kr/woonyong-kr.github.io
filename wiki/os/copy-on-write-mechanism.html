Copy-on-Write — 쓰기 전까지 복사를 미루는 메모리 최적화

확인 범위: 이 문서는 Copy-on-Write의 일반 원리와 구현 선택 기준을 설명한다. Linux·Windows·PintOS·QEMU의 코드 경로와 동작은 입력 본문에 제시된 특정 구현에 한정한다. 코드 좌표, 버전별 세부 동작, 실행 기록과 메모리·시간·성능 수치는 실제 소스와 해당 실행 환경에서 별도로 검증해야 한다.

복사가 실제로 필요할 때까지 기다리는 이유

fork()는 부모 프로세스의 전체 주소 공간을 자식에게 복제해야 한다. 그러나 fork 직후 exec()을 호출해 새 프로그램을 적재하면, 복제한 페이지 대부분은 사용되기 전에 버려진다. 이때 모든 페이지를 미리 복사하면 곧 폐기할 데이터를 위해 메모리와 복사 비용을 지불하게 된다.

**Copy-on-Write(COW)**는 부모와 자식이 처음에는 같은 물리 프레임을 공유하게 한다. 두 프로세스의 페이지는 읽기 전용으로 매핑된다. 어느 한쪽이 페이지에 쓰려고 할 때 page fault가 발생하며, OS는 그 시점에 쓰기를 시도한 프로세스만을 위한 복사본을 만든다.

MMU와 OS가 역할을 나누는 방식

COW는 PTE의 writable bit를 이용하는 소프트웨어 기법이다. fork부터 쓰기 허용까지의 흐름은 다음과 같다.

  1. fork 시 부모와 자식의 PTE가 같은 물리 프레임을 가리키게 한다.
  2. 양쪽 PTE의 writable bit을 0으로 바꾸어 읽기 전용으로 만든다.
  3. 읽기 접근은 같은 프레임에서 데이터를 읽으므로 정상적으로 처리된다.
  4. 어느 한쪽이 쓰기 접근을 시도하면, MMU는 쓰기가 금지된 페이지에 대한 write protection fault (#PF, error code bit 1 = PF_W)를 발생시킨다.
  5. OS의 fault handler는 해당 페이지가 COW page인지 실제 read-only page인지 판별한다.
  6. COW page라면 새 프레임을 할당하고 원본 데이터를 복사한 뒤, 쓰기를 시도한 쪽의 PTE가 새 프레임을 writable 상태로 가리키게 한다.
  7. 공유가 풀려 원래 프레임을 참조하는 프로세스가 하나만 남으면, 원본 PTE도 writable 상태로 복원할 수 있다.

하드웨어가 제공하는 기능은 writable=0인 페이지에 쓰기가 발생했을 때 fault를 일으키는 것뿐이다. 해당 페이지가 COW page인지 실제 read-only page인지는 OS가 관리하는 메타데이터로 구분한다. PintOS의 예에서는 PTE writable=0이면서 SPT의 page->writable 필드가 true이면 COW page로 판단한다.

Linux에서의 처리

입력에 제시된 Linux 구현은 fork 시 COW를 기본으로 사용한다.

  • do_wp_page() (mm/memory.c)는 write fault의 진입점이다. page_count() == 1이면 PTE만 writable 상태로 복원해 기존 페이지를 재사용하고, > 1이면 wp_page_copy()를 호출한다.
  • wp_page_copy()는 새 page를 할당하고 copy_user_highpage()로 데이터를 복사한다. 이어 새 PTE를 설정하고 기존 page에 put_page()를 호출해 refcount를 줄인다.
  • **KSM (Kernel Same-page Merging)**은 내용이 같은 anonymous page를 주기적으로 찾아 하나의 프레임으로 병합하는 COW의 확장이다. 입력에서는 가상화 환경의 메모리를 절약하는 최적화로 설명한다.
  • fork 뒤 exec()이 호출되면 exec_mmap()은 기존 주소 공간 전체를 exit_mmap()으로 해제한다. 이에 따라 COW로 공유하던 page들의 refcount가 감소하고 대부분 부모만 남는다.

PintOS에서 COW가 동작하는 경로

입력에 제시된 PintOS 구현에서는 anonymous page의 anon_copy()가 fork 시 frame을 공유한다. 이후 쓰기 접근으로 fault가 발생하면 vm_handle_wp() → vm_handle_cow() → vm_copy_cow_page() 경로가 이를 처리한다.

공유 상태를 기록하는 자료구조

struct frame {
    void *kva;                  // 커널 가상 주소
    struct page *page;          // 주 소유 page
    struct list_elem elem;      // frame table 연결
    struct thread *owner_thread;// 주 소유 thread
    size_t ref_count;           // ★ COW 참조 카운터
    struct list owners;         // ★ frame_owner 리스트 (공유 추적)
};

ref_count는 frame을 공유하는 소유자의 수를 나타내고, owners list는 그 소유자를 추적한다. vm_frame_add_owner()가 호출되면 ref_count++가 수행되고, vm_frame_remove_owner()가 호출되면 ref_count--가 수행된다.

fork 시 공유 상태 설정

anon_copy() (vm/anon.c:190)는 자식 SPT에 같은 VA의 page를 만든다. page가 swap 상태이면 swap slot의 참조 수만 늘린다. 메모리에 올라온 page라면 부모와 자식의 PTE를 읽기 전용으로 설정하고 같은 frame을 공유하게 한다.

이 단계가 끝나면 SPT에서는 page->writable = true이지만 PTE에서는 false인 상태가 된다. PintOS는 이 차이를 이용해 COW page와 실제 read-only page를 구분한다.

write fault 처리

쓰기가 금지된 COW page에 접근하면 다음 함수 체인이 실행된다.

vm_try_handle_fault()
  → present이지만 write → vm_handle_write_protect_fault() (vm/vm.c:528)
    → spt_find_page(addr) → vm_handle_wp(page) (vm/vm.c:386)
      → page->writable 확인 (진짜 read-only이면 false 반환 = kill)
      → vm_handle_cow(page) (vm/vm.c:397)
        → ref_count > 1: vm_copy_cow_page() — 새 frame에 복사
        → ref_count == 1: vm_remap_page() — PTE writable 복원만

vm_handle_wp()는 page->writable을 먼저 확인한다. 값이 false이면 COW가 아니라 실제 read-only page에 대한 접근이므로 실패를 반환한다. frame과 커널 가상 주소가 유효하면 vm_handle_cow(page)로 처리를 넘긴다.

공유 중인 frame의 ref_count가 1보다 크면 쓰기를 시도한 page에 새 frame이 필요하다. vm_copy_cow_page()는 새 frame을 할당하고 기존 데이터를 복사한 뒤, 새 frame을 writable 상태로 매핑한다.

vm_remap_page()는 page가 가리키는 frame이 바뀌면 새 frame에 owner를 추가한다. 이어 기존 PTE를 제거하고 새 PTE를 설정한다. 기존 frame에서 owner를 제거해 refcount를 줄이는 정리는 별도로 이루어진다.

frame과 swap slot의 수명 관리

page가 frame의 owner에서 빠질 때 vm_destroy_page_frame()은 먼저 참조 수를 줄인다. 다른 프로세스가 계속 공유하고 있으면 frame을 남겨 두고, 참조 수가 0이 된 뒤에만 물리 메모리를 해제한다.

anonymous page가 swap된 상태에서 fork되면 anon_copy()는 swap slot의 swap_ref_count를 증가시킨다. 부모와 자식은 swap-in할 때 같은 디스크 데이터를 읽지만, swap-in 이후에는 각자 독립된 frame을 갖는다. 입력에 제시된 구현에서 swap은 frame을 COW로 공유하지 않고 eager copy하는 방식이다.

QEMU에서 관찰되는 경계

COW 정책은 guest OS가 구현한다. 입력에 제시된 QEMU TCG 경로에서는 PTE walk를 소프트웨어로 수행하고, writable=0인 페이지에 쓰기가 발생하면 pf를 guest에 전달한다. QEMU가 COW page 여부를 직접 판단하거나 복사하는 것은 아니다.

QEMU 내부 경로는 guest MOV [addr], val → TCG 번역 → store_helper() → x86_cpu_tlb_fill() → pte & PTE_W == 0 → raise_exception(EXCP0E_PAGE) → guest page_fault() → vm_handle_write_protect_fault() 순서로 제시되어 있다.

다음 GDB 스크립트는 fork 전후의 frame 참조 수, COW fault, 실제 복사와 부모·자식 PTE를 관찰하도록 구성되어 있다. 실행 결과는 입력에 포함되어 있지 않으므로 해당 환경에서 별도로 확인해야 한다.

복사 비용과 참조 수의 변화

입력에 제시된 비교에서는 부모가 가진 page 중 자식이 실제로 수정하는 page만 복사할 때의 차이를 다음과 같이 계산한다.

시나리오Eager CopyCOW
부모 100 page, fork 후 exec100 page 복사 → 100 page 해제0 page 복사 (PTE 설정만)
부모 100 page, 자식이 10 page 수정100 page 복사 = 400 KiB10 page 복사 = 40 KiB
부모 1000 page, fork 후 즉시 exit1000 page 복사 → 1000 page 해제0 page 복사

입력에는 Eager copy 1 page의 비용을 palloc_get_page와 memcpy(4096 bytes)를 합해 수 μs, COW setup 1 page의 비용을 PTE writable 해제와 vm_frame_add_owner()를 합해 수십 ns로 제시한다. 이를 바탕으로 fork+exec 패턴에서 COW가 수백~수천 배 빠르다고 설명한다. 이 시간과 배수는 실제 실행 환경의 측정 결과가 입력에 포함되어 있지 않은 추정치이므로, 성능 판단에 사용하려면 별도로 측정해야 한다.

PintOS struct frame의 메타데이터 비용도 입력의 구조체 크기 가정에 따라 계산되어 있다.

  • ref_count (size_t, 8 bytes)와 owners (struct list, 16 bytes)를 합하면 frame당 24 bytes다.
  • user pool이 64 MB이고 page 크기가 4096 bytes라면 frame 수는 64 × 1024 × 1024 / 4096 = 16,384다.
  • 이 가정에서 COW 메타데이터 총량은 16,384 × 24 = 384 KiB다.
  • frame_owner 구조체는 COW 공유 시에만 malloc되며, 입력에서 제시한 크기는 list_elem(16) + page ptr(8) + thread ptr(8) = 32 bytes다.

이 계산에서 구조체 크기와 메모리 구성은 환경에 따라 달라질 수 있으므로, 384 KiB가 무시할 수준인지에 대한 판단도 실제 환경을 기준으로 해야 한다.

하나의 frame을 부모와 자식이 공유한 뒤 차례로 쓰는 경우, 참조 수와 PTE는 다음과 같이 바뀐다.

초기: frame F5, ref_count=1, owners=[Parent/VA 0x403000]

fork:  anon_copy() → vm_frame_add_owner(F5, child_page, child_thread)
       F5.ref_count = 2, owners=[Parent/0x403000, Child/0x403000]
       Parent PTE: W=0, Child PTE: W=0  (둘 다 read-only)

자식 쓰기: vm_copy_cow_page(child_page, F5)
       새 frame F9 할당, memcpy(F9.kva, F5.kva, 4096)
       vm_frame_remove_owner(F5, child_page)  → F5.ref_count = 1
       vm_frame_add_owner(F9, child_page, child)  → F9.ref_count = 1
       Child PTE: → F9, W=1

부모 쓰기: vm_handle_cow() → ref_count == 1
       vm_remap_page(parent_page, F5, true)
       Parent PTE: F5, W=1 (복사 없이 writable 복원)

자식이 먼저 쓰면 새 frame F9를 할당받고, 기존 frame F5의 참조 수는 1로 줄어든다. 이후 부모가 쓰려고 할 때는 F5를 공유하는 다른 프로세스가 없으므로 데이터를 다시 복사하지 않고 PTE의 writable 상태만 복원한다.

COW vs Eager Copy 메모리 사용 비교

시나리오: 부모 10 page (40 KiB), fork 후 자식이 3 page만 수정

Eager Copy:
  fork 직후: 부모 10 page + 자식 10 page = 20 frames (80 KiB)
  시간: palloc × 10 + memcpy × 10 = ~10 μs

COW:
  fork 직후: 공유 10 frames (40 KiB), ref_count=2
  자식 write 3회 후: 공유 7 frames + 독립 3 frames = 13 frames (52 KiB)
  시간: fork ~1 μs + fault 3회 × ~2 μs = ~7 μs

절약: 메모리 28 KiB (35%), 특히 fork+exec이면 메모리/시간 모두 ~100% 절약

이 비교는 COW가 수정된 page만 추가로 할당하는 모습을 보여 주는 계산 예시다. 여기에 적힌 시간과 절약 비율은 입력에 제시된 값이며, 실제 성능이나 사용량으로 간주하려면 해당 환경에서 검증해야 한다.

구현을 점검할 때 볼 지점

  • 부모와 자식의 PTE가 같은 frame을 가리키면서 PTE_W=0으로 바뀌는 지점에서 COW 공유가 시작된다.
  • PTE만으로는 실제 read-only page와 COW page를 구분할 수 없다. 입력에 제시된 PintOS 구현에서는 SPT의 page->writable과 frame의 ref_count를 함께 확인한다.
  • frame->ref_count > 1이면 쓰기를 시도한 쪽만 새 frame을 받는다. ref_count == 1이면 복사하지 않고 writable 상태만 복원한다.
  • swapped anonymous page는 frame을 공유하지 않는다. 대신 swap_ref_count를 늘려 같은 swap slot의 원본을 보존한다.
  • QEMU는 COW 정책을 판단하지 않는다. writable 보호 위반을 pf로 전달하며, COW로 처리할지 접근 위반으로 처리할지는 PintOS의 fault handler가 결정한다.
