BlockBackend에서 호스트 파일 I/O까지

BlockBackend에서 호스트 파일 I/O까지

확인 범위: 이 문서는 PintOS의 디스크 I/O가 QEMU의 IDE 및 BlockBackend 계층을 거쳐 호스트 파일 I/O로 이어지는 일반 구조와 raw 이미지의 오프셋 계산·관찰 방법을 설명한다. 제시된 함수명, 파일 경로, 포트·IRQ, 호출 형태와 성능 비교는 특정 PintOS·QEMU 버전의 실제 코드나 실행 기록·측정으로 검증한 결과가 아니므로, 적용 대상 버전의 소스와 실행 환경에서 별도로 확인해야 한다.

한 줄 요약: PintOS disk_write 섹터가 IDE 에뮬레이션을 거쳐 호스트 .dsk 파일의 pwrite로 내려가는 경로.

BlockBackend에서 호스트 파일 구조

PintOS 커널이 disk_write()로 섹터를 기록하면, guest CPU의 I/O 포트 명령이 QEMU의 IDE 컨트롤러 에뮬레이션을 거쳐 최종적으로 호스트 파일 시스템의 .dsk 파일에 대한 pwrite()/pread() 호출로 변환된다. QEMU의 BlockBackend 계층은 이 변환을 담당하며, 게스트가 보는 “디스크”가 실제로는 호스트의 일반 파일이라는 사실을 숨긴다.

상세 설명

추상 개념 — 에뮬레이터의 디스크 모델

실제 하드웨어에서 IDE 컨트롤러는 물리 디스크의 플래터에 직접 읽기/쓰기를 수행한다. 에뮬레이터에서는 물리 디스크가 없으므로, QEMU가 호스트의 파일을 “가상 디스크”로 사용한다.

QEMU의 블록 I/O 스택

QEMU의 블록 I/O는 여러 계층으로 나뉜다:

BlockDevOps (IDE controller model)
    ↓
BlockBackend (blk)
    ↓
BlockDriverState (BDS) — format driver (raw, qcow2, ...)
    ↓
BlockDriverState (BDS) — protocol driver (file, nbd, ...)
    ↓
호스트 시스템 콜 (pread/pwrite/aio)
계층역할PintOS 시나리오
BlockDevOps장치 모델이 블록 요청 발행IDE controller가 sector read/write 요청
BlockBackend권한 검사, 통계, 큐잉read-only 여부 확인
BDS (format)디스크 이미지 형식 해석raw format → offset 직접 매핑
BDS (protocol)호스트 파일 접근file-posix.c의 pread/pwrite

PintOS는 -drive file=os.dsk,format=raw 형태로 QEMU에 디스크를 전달하므로, format driver는 raw이다. raw format은 변환 없이 sector_number × 512 = file_offset으로 직접 매핑한다.

PintOS 디스크 구성

PintOS는 QEMU에 최대 4개 IDE 디스크를 연결한다:

IDE 위치index용도파일명
primary master0OS 커널os.dsk
primary slave1파일 시스템fs.dsk
secondary master2scratch(임시 파일)
secondary slave3swapswap.dsk

PintOS 실행 스크립트(pintos 유틸리티)가 각 .dsk 파일을 QEMU 인자로 전달한다:

-drive file=os.dsk,format=raw,index=0,media=disk
-drive file=fs.dsk,format=raw,index=1,media=disk

PintOS 측 I/O 경로 (Guest)

PintOS의 devices/disk.c에서 disk_write()가 호출되면:

output_sector()는 x86 outsw 명령으로 I/O 포트 0x1F0(primary) 또는 0x170(secondary)에 데이터를 보낸다:

QEMU 측 처리 (Host)

  1. I/O 포트 가로채기: 게스트의 outb/outsw가 실제 하드웨어에 가지 않고, QEMU의 I/O 포트 에뮬레이션 계층에 도달한다.

  2. IDE 모델 처리: hw/ide/core.c의 IDE 에뮬레이션 코드가 명령(0x30 = WRITE SECTOR)을 해석하고, 전송된 512B 데이터를 내부 버퍼에 저장한다.

  3. BlockBackend 호출: IDE 모델이 blk_pwrite(blk, sector * 512, buf, 512, 0) 형태로 BlockBackend에 쓰기를 요청한다.

  4. raw format 통과: raw driver는 offset 변환 없이 그대로 protocol driver에 전달한다.

  5. 호스트 파일 쓰기: block/file-posix.c가 호스트의 pwrite(host_fd, buf, 512, sector * 512) 시스템 콜을 실행한다.

  6. IRQ 발생: 쓰기 완료 후 QEMU가 가상 IRQ14를 주입하고, PintOS의 completion_wait 세마포어가 up된다.

BlockBackend에서 호스트 파일 값 추적

swap에 page 하나(4096 bytes)를 쓰는 경우:

항목값계산
page 크기4096 bytes-
섹터 크기512 bytes-
섹터 수8개4096 / 512
시작 섹터slot × 8slot 0 → sector 0, slot 1 → sector 8
파일 내 offsetslot × 8 × 512 = slot × 4096slot 0 → 0, slot 1 → 4096
I/O 포트 주소0x170 (secondary channel의 data-port base)swap = IDE index 3, secondary slave
outsw 호출 횟수8회섹터당 1회 × 8섹터
전체 outsw words256 × 8 = 2048섹터당 256 words

Linux 비교 — 블록 I/O 스택

계층QEMU (PintOS 시나리오)Linux 실제 블록 I/O
장치 모델IDE controller (hw/ide/core.c)NVMe/SCSI/AHCI 드라이버
블록 계층BlockBackend → BDSBlock Layer (bio/request)
스케줄러없음 (즉시 처리)mq-deadline, none, bfq
포맷 드라이버raw (offset 직접 매핑)파일 시스템 (ext4, xfs) 위 raw 또는 LVM
프로토콜file-posix (pread/pwrite)nvme_submit_cmd / scsi_dispatch_cmd
비동기 I/Oaio (선택적)io_uring / libaio
캐시 계층호스트 OS page cachepage cache + 장치 write cache
DMA없음 (PIO 에뮬레이션)DMA scatter-gather list

Linux의 실제 블록 I/O는 QEMU보다 훨씬 복잡하다. bio(block I/O) 구조체가 생성되어 I/O 스케줄러를 거치고, DMA를 통해 장치에 직접 전달된다. PintOS의 PIO(Programmed I/O) 방식은 CPU가 매 바이트를 직접 옮기므로 DMA에 비해 매우 비효율적이다.

QEMU의 raw format 최적화

raw format은 변환 비용이 0이라는 장점이 있다:

format장점단점offset 변환
raw변환 없음, 호스트에서 직접 dd 가능동적 크기 불가, snapshot 불가sector × 512
qcow2동적 크기, snapshot, 압축L1/L2 테이블 lookup 오버헤드L1[idx] → L2[idx] → cluster offset
vmdkVMware 호환복잡한 메타데이터grain table lookup

PintOS가 raw를 사용하기 때문에 xxd 등으로 호스트에서 직접 섹터 내용을 확인할 수 있다. 이는 디버깅에 큰 이점이다.
