OS 커널 아키텍처 — Monolithic, Microkernel, Exokernel

OS 커널 아키텍처 — Monolithic, Microkernel, Exokernel

확인 범위: 이 문서는 Monolithic·Microkernel·Exokernel의 책임 배치와 일반적인 장단점·선택 기준을 설명하며, 성능과 격리 효과는 구체적인 구현·구성·권한 모델과 동일 환경의 측정에 따라 달라진다. PintOS의 호출 경로와 장애 시나리오, Linux·seL4·MINIX 3 등의 코드 크기·이미지 크기·버전 관련 내용은 제시된 코드와 실제 실행 기록을 대조해야 하는 검증 대상이지, 이 문서만으로 확인된 구현 결과는 아니다.

한 줄 요약: 커널이 직접 하는 일의 범위로 갈리는 OS 설계 — Monolithic·Microkernel·Exokernel 비교.

핵심 질문

OS를 설계할 때는 파일 시스템, 디바이스 드라이버, 네트워크 스택, 프로세스 관리 가운데 어디까지 커널이 직접 맡을지 정해야 한다. 이 기능을 모두 커널 안에 둘 수도 있고, 커널에는 최소 기능만 남긴 채 나머지를 유저 프로세스로 분리할 수도 있다. 이 책임 범위와 배치 방식에 따라 성능, 안정성, 보안, 확장성의 특성이 달라진다.

Monolithic Kernel

Monolithic Kernel은 OS의 거의 모든 기능을 하나의 커널에 둔다.

%% 모놀리식 커널 — 파일시스템·드라이버·네트워크·IPC가 모두 커널 안에 있고 유저는 syscall로만 진입
flowchart TD
  app["User applications"]
  boundary["syscall 경계"]
  kernel["하나의 kernel address space"]
  fs["파일시스템"]
  sched["스케줄러"]
  mem["메모리 관리"]
  disk["디스크 드라이버"]
  net["네트워크 스택"]
  ipc["IPC"]
  hw["Hardware"]
  app --> boundary --> kernel
  kernel --> fs
  kernel --> sched
  kernel --> mem
  kernel --> net
  kernel --> ipc
  fs --> disk --> hw
  sched --> hw
  mem --> hw
  net --> hw

파일 시스템과 디스크 드라이버가 같은 커널 주소 공간에 있으면, 파일 시스템은 디스크 드라이버를 함수로 호출하고 포인터를 직접 전달할 수 있다. 이 내부 호출 경로에는 서버 사이의 IPC에서 발생할 수 있는 컨텍스트 스위칭이나 메시지 복사가 필요하지 않다. 따라서 같은 조건의 IPC 경로와 비교하면 호출 비용을 줄일 수 있지만, 실제 성능은 호출 경로와 cache 상태를 측정해야 판단할 수 있다.

같은 주소 공간을 공유하는 구조는 장애의 영향 범위도 넓힌다. 드라이버가 널 포인터를 역참조하는 등 오류를 일으키면 커널 전체가 패닉할 수 있다. 모든 코드가 ring 0에서 실행되므로 드라이버 문제를 커널과 분리된 장애로 격리하기 어렵다.

대표: Linux, PintOS, Unix (전통), FreeBSD, Windows NT (하이브리드지만 사실상 monolithic에 가까움)

Linux에서 GPU 드라이버 버그가 커널 패닉으로 이어져 시스템 전체가 멈추는 상황은 이 구조의 장애 범위를 보여준다. 드라이버가 커널 안에 있으므로 드라이버의 문제가 커널의 문제로 이어질 수 있다.

모듈 (Loadable Kernel Module)

Linux는 순수 monolithic 구조의 단점을 완화하기 위해 커널 모듈을 지원한다. 드라이버를 .ko 파일로 만들어 런타임에 커널에 로드하거나 언로드할 수 있다. 그러나 로드된 모듈은 커널 주소 공간에서 ring 0으로 실행된다. 모듈은 빌드와 구성에 유연성을 주지만, 보호 경계를 기준으로 보면 런타임 격리를 제공하지 않는다.

Microkernel

Microkernel은 커널에 IPC, 기본 스케줄링, 메모리 관리(주소 공간 생성/삭제) 같은 최소 기능만 남긴다. 파일 시스템과 디바이스 드라이버 같은 나머지 기능은 유저 공간의 별도 프로세스인 서버로 옮긴다.

%% 마이크로커널 — FS 서버와 드라이버가 유저 공간으로 빠지고, 커널엔 IPC·스케줄링·주소 공간만 남는다
flowchart TD
  app["User application"]
  fss["FS 서버"]
  drv["디스크 드라이버"]
  kernel["Microkernel"]
  ipc["IPC"]
  sched["기본 스케줄링"]
  addr["주소 공간 관리"]
  hw["Hardware"]
  app -->|IPC send| kernel
  kernel --> ipc
  kernel --> sched
  kernel --> addr
  ipc -->|message delivery| fss
  fss -->|disk request IPC| kernel
  ipc --> drv
  drv -->|권한이 부여된 I/O 또는 kernel 중개| hw
  sched --> hw
  addr --> hw

앱이 파일을 읽을 때는 커널 내부의 파일 시스템 함수를 바로 호출하는 대신, 커널이 중개하는 IPC를 통해 파일 서버에 요청한다. 파일 서버가 디스크 작업을 요청하면 다시 IPC를 거쳐 디스크 드라이버 서버에 전달할 수 있다.

이 경로에서는 추가적인 유저↔커널 전환, scheduling, 데이터 전달 비용이 생길 수 있다. 실제 비용은 커널 설계, fast path, shared memory·capability 전달 방식에 따라 달라진다. 모든 IPC가 payload 복사를 요구하는 것은 아니다.

서버를 커널과 분리하면 장애를 더 좁은 범위에 가둘 수 있다. 파일 서버가 죽어도 커널이 살아 있다면 파일 서버만 재시작할 수 있고, 유저 공간의 드라이버 버그도 커널 장애와 분리할 수 있다. 이 구조가 제공하는 안정성과 보안의 정도는 실제 서버 구성과 권한 모델에 따라 달라진다.

대표: MINIX 3, seL4, QNX, L4 계열, GNU Hurd

QNX는 자동차, 의료기기, 원자력 시설처럼 안정성이 생명인 시스템에서 쓰인다. 이런 환경에서는 드라이버 하나의 장애가 시스템 전체의 장애로 이어지지 않도록 하는 것이 중요하다.

세대별 발전

Mach 계열은 IPC와 server 구조의 비용이 비판받았고, L4 계열은 작은 IPC fast path를 핵심 목표로 삼았다. seL4는 명시된 모델·가정·구성에 대해 기능 정확성, capability enforcement 등 여러 정형 증명 결과를 제공한다. 다만 이 결과가 모든 응용·드라이버·하드웨어를 포함한 시스템 전체의 보안을 무조건 보장한다는 뜻은 아니다.

Exokernel

Exokernel은 커널이 하드웨어 자원 보호(격리)만 담당하고, 자원 관리 정책은 애플리케이션에 맡기는 구조다. OS가 하나의 정책을 강제하는 대신 앱이 자기 상황에 맞는 정책을 선택하게 한다.

%% 엑소커널 — 커널은 자원 보호만, FS·네트워크·메모리 정책은 각 앱의 LibOS가 직접 담당
flowchart TD
  a["App1 + LibOS-A<br/>자체 FS · 자체 네트워크"]
  b["App2 + LibOS-B<br/>자체 메모리 · 자체 디스크"]
  ex["자원 보호(격리)만 담당"]
  hw["Hardware"]
  a -->|자원 요청| ex
  b -->|자원 요청| ex
  ex -->|권한을 검증한 자원 binding| hw

전통 OS에서는 파일 시스템의 동작 방식을 커널이 정한다. 데이터베이스가 자체 방식으로 디스크를 관리하려 해도 OS의 파일 시스템과 버퍼 캐시를 거쳐야 한다. Exokernel은 이런 제약을 줄이고 자원 관리 정책을 앱 쪽으로 옮긴다.

각 앱은 LibOS(라이브러리 OS)를 링크해 자체 파일 시스템, 메모리 관리, 네트워크 스택을 구현한다. 커널은 특정 물리 페이지가 앱A에 할당됐다는 보호 관계만 관리하고, 앱A가 그 페이지를 어떻게 사용하는지는 관여하지 않는다.

장점: 앱이 하드웨어 자원을 직접 제어하므로 특수 목적에 맞춘 최적화가 가능하다. 웹 서버에 맞춘 네트워크 스택이나 DB에 맞춘 디스크 관리가 그 예다.

단점: 앱마다 필요한 OS 기능을 직접 구현해야 하므로 개발 난이도가 높고 범용 OS로 사용하기 어렵다.

대표: MIT Exokernel (연구용), Unikernel (현대적 변형)

현대에는 Exokernel의 아이디어가 Unikernel로 이어졌다. 하나의 앱과 필요한 OS 기능만 합쳐 가상머신 위에 올리는 방식으로, 클라우드 환경에서 쓰인다.

IPC 오버헤드 비교

Monolithic과 microkernel의 성능 차이를 살필 때는 커널 내부 함수 호출과 IPC 경로의 비용을 비교해야 한다.

항목Monolithic (함수 호출)Microkernel (IPC)
privilege 전환kernel 내부 함수 호출에는 추가 전환 없음IPC API·fast path·reply 방식에 따라 달라짐
데이터 전달같은 주소 공간이면 포인터 전달 가능copy, shared memory, grant/capability 등 구현에 따라 달라짐
scheduling직접 함수 호출에는 server switch 없음receiver 상태와 kernel 정책에 따라 switch가 생길 수 있음
비용 판단호출 경로와 cache 상태를 측정payload, 전환·switch 수와 IPC 구현을 같은 환경에서 측정

예를 들어 앱→파일 서버→디스크 드라이버→파일 서버→앱으로 동기 요청·응답을 설계하면 여러 IPC leg가 생긴다. 그러나 실제 횟수와 비용은 forwarding, asynchronous I/O, shared memory와 driver 권한 모델에 따라 달라진다. 따라서 고정 4회 × 5,000 ns 계산을 일반적인 사실로 사용해서는 안 된다.

GDB 관찰 스크립트

Monolithic 특성 확인: syscall → 커널 함수 직접

(gdb) b syscall_handler
(gdb) commands
  printf "syscall #%d from thread=%s\n", (int)f->R.rax, thread_current()->name
  c
end

함수 호출 체인 확인 (ring 전환 없이 직접 호출)

(gdb) b file_read
(gdb) commands
  bt 5
  c
end

→ syscall_handler → read → file_read → inode_read_at → disk_read 전부 같은 ring 0 스택에서 실행됨을 확인

Context switch 없는 커널 내부 경로 확인

(gdb) b disk_read
(gdb) commands
  printf "disk_read: sector=%d, caller=%s, same_thread=%d\n", \
    (int)sec_no, thread_current()->name, 1
  c
end

→ Microkernel이었다면 disk_read 시점의 thread가 디스크 드라이버 서버 프로세스여야 하지만, PintOS에서는 원래 syscall을 호출한 스레드 그대로임

관찰 시나리오

시나리오 1: Monolithic 함수 호출 체인 증명

PintOS에서 파일을 filesys_open()으로 열어 얻은 일반 파일 descriptor에 write(fd, "hello", 5)를 호출하고 디스크까지 도달하는 경로를 추적한다. 이 관찰은 커널 내부 호출이 같은 ring 0 실행 흐름에 있는지 확인하기 위한 것이다. fd=1은 stdout 경로일 수 있으므로 이 실험에 쓰지 않는다.

  1. syscall_handler에 bp → f->R.rax = SYS_WRITE 확인
  2. file_write_at에 bp → bt → 스택이 syscall_handler → write → file_write_at
  3. inode_write_at에 bp → bt → ... → inode_write_at (여전히 같은 thread)
  4. disk_write에 bp → bt → ... → disk_write (ring 0, 같은 RSP 범위)
  5. 전체 경로에서 thread_current()->name이 변하지 않음 → context switch 없이 직접 호출 증명

Microkernel 구조라면 step 2~4 사이에서 IPC send/receive와 context switch가 발생해 thread가 바뀌는 경로를 예상할 수 있다.

시나리오 2: 커널 내 버그가 전체 시스템 crash를 유발하는지

  1. vm/vm.c에서 의도적으로 NULL 역참조 코드 삽입 (예: *(int*)0 = 42;)
  2. 실행 → PANIC: Kernel bug at ... → 시스템 전체 정지
  3. Microkernel이었다면 해당 서버만 crash되고 커널은 살아있어 재시작 가능

이 시나리오는 Monolithic 구조에서 커널 주소 공간을 공유할 때 fault isolation이 부족해질 수 있음을 관찰하려는 절차다.

코드 좌표

파일 (PintOS)함수/구조체Monolithic 특성

Microkernel 구조라면 filesys_read(), disk_read()는 별도 유저 프로세스에 있고 커널은 이들 사이의 IPC만 중개한다. PintOS에서는 syscall_handler() → file_read() → inode_read_at() → disk_read()가 모두 같은 ring 0 안에서 이어지는 함수 호출 체인이다.

QEMU 에뮬레이션 관점

QEMU는 커널 아키텍처 자체를 인식하지 않는다. QEMU가 보는 것은 guest CPU의 명령어, 메모리 접근, I/O 포트 접근이다. 따라서 Monolithic과 microkernel 모두에 같은 하드웨어 에뮬레이션을 제공한다.

관점Monolithic (PintOS)Microkernel (가상)
syscall 처리KAIST x86-64 구성에서는 QEMU가 SYSCALL 상태 전환을 재현하고 guest LSTAR 진입점으로 이동같은 ISA·진입 방식을 쓴다면 하드웨어 동작은 동일하며 OS 정책은 다름
FS 접근커널 내 함수 호출 → QEMU는 일반 guest 명령어로 봄IPC → context switch → QEMU는 CR3 전환 + 추가 명령어로 봄
디스크 I/O커널 내 outb(0x1F7,...) → QEMU IDE 에뮬레이션user driver에 I/O 권한을 부여하거나 kernel이 중개한 뒤 같은 장치 모델에 도달
실행 차이kernel 함수 호출 중심IPC와 scheduling 때문에 추가 guest instruction·address-space switch가 생길 수 있음

PintOS의 syscall_handler() → file_read() → disk_read()는 같은 kernel address space의 함수 호출로 이어질 수 있다. Microkernel 설계는 IPC와 scheduling을 추가하고 경우에 따라 CR3 전환도 일으킨다. 다만 이것이 매번 QEMU의 번역 블록 캐시 전체를 무효화한다는 뜻은 아니다. 성능 차이는 실제 instruction 수, address-space switch, TLB 동작과 IPC 구현을 측정해야 판단할 수 있다.

PintOS의 위치

PintOS는 전형적인 monolithic kernel이다. 파일 시스템, 디바이스 드라이버, 메모리 관리, 프로세스 관리가 모두 커널 주소 공간에 있고 함수 호출로 연결된다. syscall_handler()에서 file_read()를 호출하면 같은 ring 0 안에서 함수 호출이 이어진다.

PintOS에서 다루는 커널 영역과 유저 영역 — 가상 주소 공간은 어떻게 나뉘는가도 monolithic kernel의 전형적인 패턴을 보여준다. 커널 1:1 매핑, 커널 풀/유저 풀 분리, syscall을 통한 유저↔커널 전환은 이 문서에서 설명한 monolithic 설계와 연결된다.

OS 커널 아키텍처 관련 문서

  • User 메모리
    • monolithic kernel의 메모리 구조.
  • User 보호
    • ring 0/3 보호 메커니즘.
  • IPC Message Passing
    • microkernel의 핵심 통신 메커니즘.
  • IPC Shared Memory
    • 프로세스 간 메모리 공유.
  • PintOS 디렉터리 구조
    • PintOS 디렉터리 구조가 monolithic 설계를 반영하는 방식.
  • QEMU
    • 실제 OS와 PintOS/QEMU의 차이 전체 비교.
  • Kernel Mode
    • ring 0/3 모드 전환이 monolithic에서 syscall에만 발생하는 이유.
  • syscall handler() 분기
    • monolithic 구조에서 syscall이 커널 함수로 직접 분기되는 흐름.
  • syscall 전체 흐름
    • write(1, buf, size) 전체 흐름이 ring 0에서 함수 호출 체인으로 이어지는 예.
  • Windows 실제 OS
    • Linux/Windows 실제 OS 비교.
  • IDT
    • IDT도 커널 안에서 관리되는 구조.
