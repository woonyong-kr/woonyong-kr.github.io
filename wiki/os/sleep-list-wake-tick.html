sleep_list와 wake_tick — Alarm Clock 구현의 핵심 자료구조

한 줄 요약: sleep_list는 잠든 스레드를 wake_tick(깨울 절대 tick) 순으로 정렬 보관하고, timer interrupt가 매 tick마다 맨 앞만 비교해 busy-wait 없이 깨운다.

sleep_list와 wake_tick의 역할

스레드를 일정 시간 재우려면 언제 다시 실행할지를 기록하고, 그 시간이 되었는지 주기적으로 확인해야 한다. wake_tick은 각 스레드가 깨어나야 할 절대 시각을 담는다. sleep_list는 잠든 스레드를 wake_tick이 이른 순서로 보관하는 전역 리스트다.

두 값을 함께 사용하면 timer interrupt handler는 매 tick마다 리스트의 맨 앞만 보고 깨울 스레드가 있는지 판단할 수 있다. 잠든 스레드는 반복해서 yield()할 필요가 없으므로 busy-wait(while (elapsed < ticks) yield())에서 발생하는 CPU 낭비도 피할 수 있다.

타이머 기반 Sleep의 흐름

OS가 “일정 시간 후 깨워라”라는 요청을 처리하는 방식은 다음 두 가지로 나눌 수 있다.

방식장점단점
Busy-wait (spin)구현 단순CPU 100% 소비, 다른 스레드 실행 방해
Sleep queue + wakeup tickCPU 양보, 효율적정렬 삽입 비용 O(n), 인터럽트 동기화 필요

Sleep queue를 사용하는 경우 실행 중인 스레드를 BLOCKED 상태로 바꾼다. 이후 타이머 인터럽트가 매 tick마다 가장 이른 deadline을 확인한다. deadline에 도달한 스레드는 READY 상태로 돌아가 다시 스케줄링될 수 있다.

Linux의 schedule_timeout() / msleep()도 커널의 timer wheel (hrtimer) 인프라를 사용한다. 각 sleep 요청은 timer_list 구조체로 등록되어 해시 기반 타이머 휠에 삽입된다. PintOS의 단순 정렬 리스트와 자료구조는 다르지만, deadline 기록 → 인터럽트에서 만료 확인 → wakeup이라는 흐름은 같다.

PintOS 구현

자료구조

sleep_list는 thread_init()에서 list_init(&sleep_list)로 초기화된다.

Sleep 경로: timer_sleep() →

timer_sleep(ticks)
  start = timer_ticks()          // 현재 절대 tick 읽기
  thread_sleep(start + ticks)    // 절대 deadline 전달
    cur->wake_tick = wake_ticks  // 스레드에 deadline 기록
    list_insert_ordered(&sleep_list, &cur->elem, cmp_thread_ticks, NULL)
    thread_block()               // RUNNING → BLOCKED, schedule() 호출

timer_sleep()은 현재 tick에 대기 시간을 더해 절대 deadline을 만든다. thread_sleep()은 이 값을 현재 스레드의 wake_tick에 저장하고, 스레드를 sleep_list에 넣은 뒤 BLOCKED 상태로 전환한다.

정렬 기준 함수 cmp_thread_ticks()는 wake_tick이 작은 스레드를 리스트 앞에 배치한다.

Wakeup 경로: timer_interrupt() →

thread_awake()는 먼저 sleep_list의 맨 앞 스레드를 확인한다. 그 스레드의 wake_tick이 아직 현재 tick보다 크다면, 뒤에 있는 스레드들의 시간도 오지 않은 상태이므로 바로 탐색을 끝낸다. 반대로 wake_tick <= global_ticks이면 해당 스레드를 꺼내 READY 상태로 전환한다. 같은 tick에 깨어날 스레드가 여러 개라면 조건을 만족하는 스레드를 모두 처리한다.

thread_awake()는 timer_interrupt() 안에서 호출되므로 실행 시점에는 이미 인터럽트가 비활성화되어 있다.

인터럽트 동기화

thread_sleep()에서는 intr_disable() → 삽입 → thread_block() → intr_set_level(old_level) 순서를 지켜야 한다. 리스트 삽입과 상태 전환 사이에 timer interrupt가 끼어들면 sleep 요청을 놓치거나, 아직 RUNNING 상태인 스레드를 깨우려는 race가 생길 수 있기 때문이다.

인터럽트를 비활성화하지 않았을 때 가능한 흐름은 다음과 같다.

Race 1: 삽입 전 인터럽트
  thread_sleep():
    cur->wake_tick = 510          ← 여기서 timer_interrupt 발생
    --- timer_interrupt(tick=510) ---
      thread_awake(510):
        sleep_list 탐색 → 아직 삽입 안 됨 → 아무도 안 깨움
    --- 복귀 ---
    list_insert_ordered(...)      ← wake_tick=510인데 이미 지남
    thread_block()                ← 영원히 깨어나지 못함!

Race 2: 삽입 후, block 전 인터럽트
  thread_sleep():
    cur->wake_tick = 510
    list_insert_ordered(...)      ← 여기서 timer_interrupt 발생
    --- timer_interrupt(tick=510) ---
      thread_awake(510):
        pop & thread_unblock(cur) ← RUNNING 스레드를 unblock → assertion fail!

Race 1에서는 timer interrupt가 리스트 삽입 전에 발생한다. 인터럽트는 깨울 스레드를 찾지 못하고 지나가며, 뒤늦게 BLOCKED 상태가 된 스레드는 해당 tick에 깨어날 기회를 놓친다. Race 2에서는 리스트 삽입 직후 인터럽트가 발생해 아직 RUNNING 상태인 스레드에 thread_unblock()을 호출하게 된다.

intr_disable()은 wakeup 시각 설정부터 리스트 삽입과 block까지의 구간에 timer interrupt가 끼어들지 못하게 한다. thread_block() 내부에서 schedule()이 호출된 뒤 새로 실행되는 스레드가 intr_set_level(old_level)로 인터럽트 상태를 복원한다.

QEMU에서 보이는 범위

QEMU는 sleep_list의 의미나 정렬 규칙을 알지 못한다. QEMU가 담당하는 부분은 timer interrupt를 발생시키고 guest 코드를 실행하는 일이다.

  1. QEMU의 i8254 PIT 모델이 매 10ms마다 IRQ0을 에뮬레이션한다.
  2. i8259 PIC 모델이 IRQ0을 CPU 인터럽트로 변환한다.
  3. TCG가 timer_interrupt() 핸들러 주소로 점프하는 guest CPU 동작을 에뮬레이션한다.
  4. thread_awake()는 guest 소프트웨어로 실행되며, QEMU는 해당 명령어를 번역해 실행한다.

GDB에서 sleep_list를 관찰할 때 표시되는 주소는 모두 guest virtual address다. QEMU GDB stub은 guest의 현재 PML4를 사용해 이 주소를 guest physical → host virtual로 변환한다.

sequenceDiagram

Linux의 schedule_timeout()은 내부적으로 timer_list를 타이머 휠에 등록하고 schedule()로 실행을 양보한다. 콜백은 wake_up_process()를 호출해 스레드를 깨운다. PintOS의 sleep_list와 thread_awake()는 이 패턴을 단순화한 구조다.

GDB 관찰 스크립트

다음 스크립트로 sleep 진입, wakeup, 정렬 상태와 잔여 tick을 관찰할 수 있다.

관찰 시나리오

시나리오 1: alarm-multiple 테스트 — 다수 스레드

alarm-multiple 테스트에서는 5개 스레드가 서로 다른 sleep 기간으로 timer_sleep()을 호출한다. 이 과정에서 sleep_list의 정렬 삽입과 순차적인 wakeup을 관찰할 수 있다.

관찰 절차:
1. trace_sleep_entry → 5개 스레드의 wake_tick 기록
2. dump_sleep_list → wake_tick 오름차순 정렬 확인
3. verify_sleep_order → 자동 정렬 검증
4. trace_awake_unblock → 가장 작은 wake_tick부터 순서대로 깨움 확인
5. 각 깨움 후 dump_sleep_list → 리스트가 줄어드는 것 확인

기대 결과:
- 삽입 순서와 무관하게 wake_tick 오름차순 정렬
- thread_awake()는 front만 비교 후 break (O(1) 탈출)
- 동일 tick에 여러 스레드 깨어남 가능 (같은 wake_tick)

이 절차의 관찰 대상은 호출 순서와 관계없는 오름차순 정렬, 맨 앞 원소를 기준으로 한 탐색 종료, 같은 wake_tick을 가진 여러 스레드의 wakeup이다. 기대 결과는 실제 실행 결과가 아니라 관찰 시 확인할 조건을 나타낸다.

시나리오 2: Race Condition 부재 확인 —

두 번째 시나리오에서는 thread_sleep()의 intr_disable() → 삽입 → thread_block() 구간 사이에 timer interrupt가 끼어들지 않는지 살펴본다.

관찰 절차:
1. break thread_sleep 후 stepi로 intr_disable() 전후 EFLAGS IF 비트 관찰
   (gdb) p/x $eflags → IF=0x200 확인 후 intr_disable → IF=0x000
2. list_insert_ordered 직후 sleep_list 상태 확인 — 스레드가 들어갔지만 아직 RUNNING
3. thread_block() 호출 → status가 THREAD_BLOCKED로 변경 확인
4. schedule() 후 새 스레드가 intr_set_level(old_level)로 IF 복원 확인
5. timer_interrupt에 break → thread_awake()가 정렬된 front만 확인하는지 추적

기대 결과:
- intr_disable~thread_block 구간에서 timer_interrupt 끼어들지 않음
- 삽입과 block이 원자적으로 완료된 후에야 timer_interrupt가 sleep_list를 스캔
- Race 1(삽입 전 인터럽트)과 Race 2(삽입 후 block 전 인터럽트) 모두 방지됨

여기서도 기대 결과는 검증을 마쳤다는 뜻이 아니다. GDB로 인터럽트 플래그, 스레드 상태, sleep_list의 변화를 차례로 확인할 때 사용할 판단 기준이다.
