TLB 캐시 메커니즘

TLB 캐시 메커니즘

확인 범위: 이 문서는 TLB의 주소 변환 캐싱과 무효화에 관한 일반 원리와 선택 기준을 설명하고, Linux·Windows·PintOS·QEMU 사례는 입력에 제시된 동작과 코드 흐름을 바탕으로 구분해 서술한다. 특정 CPU 구성, 명령 비용, hit rate에 따른 계산, flush 횟수와 성능 판단은 해당 버전의 실제 코드·실행 기록·측정으로 검증된 결과가 아니라 예시이므로 적용 대상 환경에서 별도 확인이 필요하다.

한 줄 요약: TLB는 최근 VA→PA 변환 결과를 CPU 안에 캐싱해 최대 5번 메모리 접근이 필요한 page table walk을 1 cycle로 줄이며, page table을 바꾸면 OS가 직접 무효화해 일관성을 지킨다.

TLB 캐시 메커니즘 흐름

TLB(Translation Lookaside Buffer)는 CPU 내부에 있는 소규모 고속 캐시로, 최근에 수행한 가상 주소 -> 물리 주소 변환 결과를 저장한다. x86-64의 4단계 page table walk은 최악의 경우 PML4, PDPT, PD, PT, 데이터까지 5번의 메모리 접근이 필요하지만, TLB에 캐시된 항목은 1 cycle만에 변환이 완료된다. TLB는 주소 변환 성능의 핵심이며, OS는 TLB의 일관성을 유지하기 위해 page table 변경 시 적절한 무효화(invalidation) 작업을 수행해야 한다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

TLB는 VA page -> PA frame 매핑의 캐시다. 논리적으로 각 TLB 엔트리는 다음 정보를 담는다:

TLB 종류엔트리 수연관도대상 페이지 크기

TLB hit vs TLB miss

flowchart TD
  va["VA 접근"]
  search["TLB 검색<br/>(tag = VPN, 현재 주소 공간)"]

중요: TLB miss와 page fault는 다른 사건이다.

사건의미CPU가 pf를 발생시키는가?
TLB hit캐시에서 변환 결과를 찾음아니오
TLB miss캐시에 없어서 page table walk 필요아니오 (walk이 성공하면)
Page faultwalk 결과 present=0이거나 권한 위반예

x86에서 TLB miss 처리는 하드웨어가 자동으로 수행한다(hardware-managed TLB). 소프트웨어가 TLB refill을 직접 처리하는 MIPS 등과 다르다.

TLB 무효화

OS가 page table을 변경하면 TLB에 남은 오래된 엔트리가 현실과 불일치할 수 있다. 이를 해결하는 방법:

무효화 방법x86-64 명령어범위사용 시점
전체 flushmov CR3, <value>전체 TLB (global 제외)주소 공간 전환
단일 페이지invlpg <addr>특정 VA 하나PTE 변경 후
PCID + 선택적mov CR3 + NOFLUSH bitPCID별 선택최적화된 전환

mov CR3 명령으로 CR3에 값을 쓰면 (PCID 미사용 시) global bit가 아닌 모든 TLB 엔트리가 자동으로 flush된다. 이것이 context switch 때 TLB가 비워지는 메커니즘이다.

실제 OS (Linux/Windows)

Linux

Linux는 TLB 성능 최적화를 위해 여러 기법을 사용한다:

  • PCID(Process Context ID): CR3에 12-bit PCID를 함께 기록해, 주소 공간 전환 시 TLB 전체를 flush하지 않고 PCID가 다른 엔트리만 무시한다. 최대 4096개 PCID를 사용할 수 있다.
  • Global page: 커널 매핑처럼 모든 프로세스가 공유하는 페이지는 PTE의 global bit를 설정해 CR3 전환 시에도 TLB에 남긴다.
  • TLB shootdown: SMP 환경에서 한 CPU가 page table을 변경하면, 같은 주소 공간을 사용 중인 다른 CPU의 TLB도 무효화해야 한다. Linux는 IPI(Inter-Processor Interrupt)를 보내 다른 CPU에서 invlpg 또는 TLB flush를 실행한다.
  • Lazy TLB: 커널 스레드로 전환할 때는 유저 주소 공간 접근이 없으므로 TLB flush를 생략한다.
  • KPTI(Kernel Page Table Isolation): Meltdown 취약점 대응으로, 유저 모드와 커널 모드에서 별도의 page table을 사용한다. 모드 전환마다 CR3를 바꾸므로 TLB flush가 추가로 발생하며, PCID로 비용을 줄인다.

Windows

Windows도 유사한 최적화를 적용한다. ASN(Address Space Number)은 Linux의 PCID에 해당하며, KeFlushCurrentTb()가 TLB flush를 수행한다.

PintOS 구현

PintOS는 단일 CPU 환경이므로 TLB 관리가 단순하다.

CR3 전환으로 전체 flush

schedule() -> process_activate() -> pml4_activate()로 이어지는 경로에서 CR3를 새 프로세스의 PML4 물리 주소로 설정한다. PCID를 사용하지 않으므로, 이 mov CR3 명령으로 non-global TLB 엔트리가 모두 flush된다.

PTE 변경 후 invlpg

핵심 패턴: PTE를 변경한 뒤, 현재 활성 주소 공간(rcr3() == vtop(pml4))인 경우에만 invlpg로 해당 페이지의 TLB 엔트리를 무효화한다. 비활성 주소 공간의 PTE를 변경한 경우, 다음에 그 주소 공간이 활성화될 때 CR3 전환으로 TLB가 자동 flush되므로 invlpg가 불필요하다.

PintOS가 생략하는 것

기능PintOS이유
PCID미사용단일 CPU, 프로세스 수 적음
Global page미사용커널 매핑이 모든 PML4에 복사되어 있음
TLB shootdown불필요단일 CPU
Huge page TLB미사용4KB 페이지만 사용
KPTI미적용교육용 OS

QEMU 에뮬레이션

QEMU TCG 모드에서는 실제 하드웨어 TLB 대신 소프트웨어 TLB를 유지한다. QEMU의 “softmmu”가 이 역할을 한다.

%% QEMU CR3 변경과 내부 TLB flush
flowchart TD
  guest["Guest가 mov CR3 실행"]
  helper["QEMU helper_write_crN()"]
  update["cpu_x86_update_cr3(env, new_cr3)"]
  flush["paging 중이면 tlb_flush(env_cpu(env))"]
  setcr3["setcr3"]
  guest --> helper
  helper --> update
  update --> setcr3
  setcr3 --> flush

QEMU의 tlb_flush()는 host CPU의 TLB가 아니라 QEMU 내부의 guest 주소 변환 캐시를 비운다. 이 캐시는 CPUTLBEntry 구조체 배열로 구현되어 있으며, guest VA -> host VA 매핑을 저장한다.

Guest가 invlpg 명령을 실행하면:

%% QEMU invlpg와 단일 페이지 flush
flowchart TD
  guest["Guest invlpg &lt;addr&gt;"]
  helper["QEMU helper_invlpg()"]
  flush["tlb_flush_page(env_cpu(env), addr)"]
  guest --> helper
  helper --> flush

이는 해당 page에 대한 QEMU 내부 캐시 엔트리만 제거한다.

TLB 캐시 메커니즘 값 추적

TLB hit vs miss 비용

TLB hit:        ~1 cycle
TLB miss (4KB): PML4 접근 + PDPT 접근 + PD 접근 + PT 접근 + 데이터 접근
                = 4 * ~4 cycles (L1 cache hit) + 1 = ~17 cycles (최선)
                = 4 * ~100 cycles (DRAM) + 1 = ~401 cycles (최악)

TLB hit rate이 99%이면 평균 변환 비용:
  0.99 * 1 + 0.01 * 401 = 0.99 + 4.01 = 5.0 cycles

TLB hit rate이 95%이면:
  0.95 * 1 + 0.05 * 401 = 0.95 + 20.05 = 21.0 cycles

TLB가 커버하는 주소 범위

4KB 페이지 기준:
  L1 DTLB 64 엔트리 * 4KB = 256KB
  L2 STLB 1536 엔트리 * 4KB = 6MB

2MB 페이지 기준:
  L2 STLB에 2MB 엔트리가 있으면:
  32 엔트리 * 2MB = 64MB

PintOS에서 TLB flush 횟수

TIMER_FREQ = 100 Hz -> 초당 100 tick
TIME_SLICE = 4 tick -> 최대 초당 25회 context switch
각 context switch마다 CR3 전환 -> TLB flush

최악의 경우 초당 25회 TLB 전체 flush

invlpg vs 전체 flush 비용 비교

invlpg:                    ~100 cycles (단일 페이지)
mov CR3 (전체 flush):      ~200 cycles (하드웨어 비용)
                           + TLB miss 연쇄 (수천 cycles)

단일 PTE 변경 -> invlpg가 유리
주소 공간 전환 -> 전체 flush 불가피
