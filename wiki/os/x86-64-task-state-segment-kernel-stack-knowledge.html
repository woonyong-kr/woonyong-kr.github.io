x86-64 TSS 커널 스택 전환

x86-64 TSS 커널 스택 전환

유저 프로그램이 커널에 진입할 때는 유저 스택을 그대로 믿을 수 없어서, x86-64는 TSS의 rsp0을 통해 현재 스레드의 커널 스택 꼭대기를 찾는다.

x86-64 TSS 커널 스택 전환

유저 프로그램이 실행 중일 때 CPU의 RSP는 유저 스택을 가리킨다. 이 상태에서 interrupt, page fault, syscall로 커널에 진입해야 할 때, 유저 스택을 그대로 쓰면 안 된다 — 유저 스택은 조작되었거나 매핑이 깨져 있을 수 있다. TSS(Task-State Segment)는 이 문제에 대한 x86-64 CPU의 답이다. TSS의 rsp0 필드에 현재 스레드의 커널 스택 꼭대기 주소를 넣어 두면, 권한 전환 시 CPU(또는 OS entry code)가 안전한 커널 스택으로 갈아탈 수 있다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

커널 진입에는 두 가지가 동시에 필요하다.

필요한 것이유담당 구조
권한 전환ring 3 → ring 0CS selector, GDT descriptor
스택 전환유저 스택 → 커널 스택TSS의 rsp0 (또는 OS entry code)

Page table과 TSS/GDT는 역할이 다르다.

질문답하는 구조
이 VA가 어느 frame으로 번역되는가?page table
이 VA는 유저 모드에서 접근 가능한가?page table의 PTE_U bit
지금 실행 중인 코드는 유저 권한인가 커널 권한인가?CS selector, CPL
유저→커널 진입 시 새 RSP는 어디인가?TSS의 rsp0 (또는 entry code가 직접 읽음)

네 가지 이름만 분리하면 전체 구조가 잡힌다.

이름의미
GDTselector 숫자를 descriptor 의미로 바꾸는 CPU용 표
TSS descriptorGDT 안에서 “TSS 구조체는 메모리 여기 있다”라고 가리키는 항목
TR (Task Register)CPU가 현재 사용할 TSS descriptor를 기억하는 레지스터
TSS.rsp0ring 0 진입 때 사용할 커널 스택 꼭대기 주소

실제 OS (Linux/Windows)

현대 x86-64 OS도 TSS를 “하드웨어 스레드 스케줄러”로 쓰지 않는다. 오래된 x86의 hardware task switching은 거의 쓰이지 않으며, TSS는 세 가지 용도로만 남는다.

용도의미
ring 0 stack pointer유저→커널 진입 시 사용할 스택
IST (Interrupt Stack Table)double fault, NMI용 별도 안전 스택
CPU 요구 구조x86-64 권한 전환에 유효한 TSS/TR이 필수
항목LinuxWindowsPintOS
TSS 개수per-CPU 1개per-CPU 1개전역 1개 (단일 CPU)
커널 스택 크기16KB (4 pages, THREAD_SIZE)24KB (일반), 12KB (ISR)4KB 내 상단
IST 사용IST1=double fault, IST2=NMI 등예외별 IST미사용
KPTI유저/커널 PML4 분리KVA Shadow미적용
syscall stackMSR_KERNEL_GS_BASE → per-CPU 영역에서 스택 전환KVASCODE 진입점에서 전환syscall_entry.S가 tss→rsp0 직접 읽음

PintOS 구현

PintOS에서 TSS 사용 흐름:

%% PintOS TSS 갱신 순서
flowchart TD
  boot["init (부팅)"]
  tss_init["tss_init()<br/>tss = palloc_get_page(PAL_ZERO)"]
  tss_update_boot["tss_update(thread_current())<br/>tss-&gt;rsp0 = next + PGSIZE"]
  gdt_init["gdt_init()<br/>GDT[SEL_TSS &gt;&gt; 3] = TSS descriptor"]
  tr_load["lgdt()"]
  schedule["schedule()<br/>다음 thread 선택"]
  activate["process_activate(next)<br/>tss_update(next) + pml4_activate(next-&gt;pml4)"]
  tss_update_next["tss_update(next)<br/>tss-&gt;rsp0 = next + PGSIZE"]
  boot -->|부팅 중| tss_init
  tss_init --> tss_update_boot
  tss_update_boot --> gdt_init
  gdt_init --> tr_load
  tr_load -->|이후 context switch| schedule
  schedule --> activate
  activate --> tss_update_next

커널 진입 경로별 TSS 사용 방식이 다르다.

경로TSS 사용 방식
interrupt/trap gate (ring 3→0)CPU가 TSS rsp0을 자동 사용 가능
x86-64 syscall fast pathPintOS syscall_entry.S가 tss->rsp0을 직접 읽어 RSP에 넣음

syscall entry의 핵심 어셈블리:

즉 syscall 명령은 CPU가 자동으로 intr_frame을 만들어 주는 것이 아니다. LSTAR MSR이 가리키는 진입점(syscall_entry)에서 PintOS entry code가 TSS의 rsp0을 읽고, 커널 스택 위에 struct intr_frame을 직접 구성한다.

QEMU 에뮬레이션

QEMU는 PintOS의 thread, process, syscall_handler() 의미를 모른다. QEMU가 재현하는 것은 guest x86 CPU의 TSS/GDT/TR 하드웨어 규칙이다.

QEMU 코드역할
helper_ltr() (seg_helper.c)guest ltr 명령 처리, GDT에서 TSS descriptor를 읽어 env->tr에 저장
do_interrupt64() (seg_helper.c)ring 3→0 진입 시 get_rsp_from_tss()로 새 RSP 획득
helper_syscall() (seg_helper.c)syscall instruction의 CPU 상태 변화(RCX, R11, RIP=LSTAR) 재현. TSS stack switch는 하지 않음 — PintOS entry code가 직접 수행

x86-64 TSS 커널 스택 전환 값 추적

SEL_TSS = 0x28은 GDT index 5

x86-64 TSS descriptor는 16바이트(일반 descriptor 2칸)를 차지한다.

rsp0 offset = 4 bytes

그래서 syscall_entry.S가 movq 4(%r12), %rsp로 rsp0을 읽는다.

rsp0 = thread + PGSIZE 계산 예제
