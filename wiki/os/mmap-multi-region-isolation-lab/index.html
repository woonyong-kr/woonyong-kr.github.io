mmap 다중 region 격리는 무엇을 확인해야 하나

한 줄 요약: mmap-twice·mmap-shuffle·mmap-inherit·swap-file 네 테스트를 한 묶음으로, 같은 파일을 두 VA에 매핑하거나 큰 mapping을 page별로 쓰거나 fork/exec 경계를 지나도 각 mapping의 file·offset·dirty metadata가 region/page 단위로 분리돼 섞이지 않는지 확인하는 격리 기준을 정리한다.

mmap 다중 region 격리 쟁점

mmap-read 하나만 통과하면 file-backed page 구현이 끝난 것처럼 보일 수 있다. 그러나 한 page를 올바르게 읽는 것만으로는 여러 mapping 사이의 격리를 확인할 수 없다. 다음 질문까지 살펴봐야 한다.

같은 파일을 두 번 매핑하거나, 큰 파일을 여러 page로 매핑하거나, fork/exec 경계를 지나면 각 mapping의 file metadata가 서로 섞이지 않는가?

이 Lab은 mmap-twice, mmap-shuffle, mmap-inherit, swap-file을 한 묶음으로 보고, 구현자가 확인해야 할 격리 기준을 정리한다.

mmap 다중 region 격리 필요성

mmap() 구현은 한 page가 잘 읽히는지만 보면 틀린 설계도 통과해 보일 수 있다.

예를 들어 다음 구현은 겉으로는 단순하다.

struct file_page {
  struct file *file;
  off_t ofs;
};

하지만 여러 mapping이 생기면 질문이 늘어난다.

mapping A: sample.txt -> 0x10000000
mapping B: sample.txt -> 0x20000000

두 mapping은 같은 파일 내용을 읽을 수 있어야 한다. 그렇다고 같은 struct page, 같은 SPT entry, 같은 cleanup ownership을 공유해도 된다는 뜻은 아니다. mmap 구현에서 격리해야 하는 대상은 파일 내용 자체가 아니라 주소 공간 안에서 각 mapping이 갖는 의미다.

mmap 다중 region 격리 구조

처음에는 mmap_region을 mapping 단위 봉투로 보고, struct file_page를 page 단위 영수증으로 보면 된다.

region A
  base     = 0x10000000
  page_cnt = 1
  file ref = sample.txt reopened #A
  page A0
    va  = 0x10000000
    ofs = 0

region B
  base     = 0x20000000
  page_cnt = 1
  file ref = sample.txt reopened #B
  page B0
    va  = 0x20000000
    ofs = 0

중요한 불변식은 네 가지다.

불변식 깨지면 생기는 증상
SPT key는 file offset이 아니라 page-aligned VA다 같은 파일 offset을 두 번 매핑할 수 없다
region metadata는 mapping별로 분리된다 munmap(A)가 B까지 닫거나 지운다
page metadata는 page별 file offset/read bytes를 가진다 큰 mapping에서 모든 page가 offset 0을 읽거나 쓴다
cleanup ownership은 한 곳에서만 file을 닫는다 leak, double close, use-after-free가 난다

mmap 다중 region 격리 예시

mmap-twice는 같은 파일을 두 번 열어 서로 다른 주소에 매핑한다.

char *actual[2] = {(char *) 0x10000000, (char *) 0x20000000};

mmap (actual[0], 4096, 0, handle[0], 0);
mmap (actual[1], 4096, 0, handle[1], 0);

둘 다 같은 sample.txt의 offset 0을 읽는다. 하지만 SPT에서는 서로 다른 VA page다.

SPT[0x10000000] -> page A, file offset 0
SPT[0x20000000] -> page B, file offset 0

mmap-shuffle은 더 큰 압박을 준다.

#define SIZE (128 * 1024)
char *buf = (char *) 0x10000000;
mmap (buf, SIZE, 1, handle, 0);

128KB는 4KB page 32개다.

page 0  -> offset 0
page 1  -> offset 4096
...
page 31 -> offset 126976

반복 shuffle()은 여러 page에 write를 만든다. 이때 모든 dirty page가 자기 file offset으로 되돌아가야 한다.

mmap-inherit는 부모가 0x54321000에 file mapping을 만든 뒤 child를 exec("child-inherit")로 바꾼다. child program은 같은 주소에 memset()을 시도하고 죽어야 한다.

부모: 0x54321000 mapping 있음
child exec 이후: 0x54321000 mapping 없어야 함

이 테스트는 부모의 mapping metadata가 child의 새 주소 공간에 새어 들어가면 안 된다는 경계를 보여준다.

실제 운영체제

Linux는 process address space 안에 VMA를 둔다. 같은 파일을 여러 번 매핑하면 VMA가 여러 개 생길 수 있고, 각 VMA는 자기 주소 범위와 file offset을 가진다. 실제 file page는 page cache를 통해 공유될 수 있지만, mapping 범위와 권한은 VMA별 metadata로 분리된다.

Windows도 section object와 mapped view, VAD 같은 구조로 mapping 범위와 protection을 관리한다. 같은 파일 mapping object를 여러 view로 붙일 수 있지만, 각 view의 base address와 범위는 별도로 추적된다.

현실 OS는 PintOS보다 더 복잡하다.

  • page cache 공유와 process별 VMA metadata를 함께 다룬다.
  • copy-on-write, shared/private mapping, partial unmap, truncate를 고려한다.
  • 여러 thread가 동시에 mapping을 건드릴 수 있어 lock ordering도 중요하다.

PintOS에서는 이 복잡도를 줄여서 한 process의 SPT와 구현자가 만든 region/page metadata가 섞이지 않는지를 확인한다.

PintOS

W09 PintOS skeleton에서 user wrapper는 이미 준비되어 있다.

  • lib/user/syscall.c:148-155
    • mmap()은 5개 인자를 넘긴다.
    • munmap()은 시작 주소 하나만 넘긴다.
  • include/lib/syscall-nr.h:68-78
    • SYS_MMAP, SYS_MUNMAP 번호가 있다.

하지만 VM 쪽은 구현자가 채워야 한다.

  • include/vm/file.h:9-16
    • struct file_page는 비어 있다.
    • do_mmap(), do_munmap()이 선언되어 있다.
  • vm/file.c:23-58
    • file-backed initializer, swap in/out, destroy, mmap, munmap skeleton이 있다.
  • include/vm/vm.h:85-89
    • struct supplemental_page_table 설계는 구현자 선택이다.

따라서 격리 Lab에서 확인할 구현 포인트는 다음이다.

위치 확인할 것
do_mmap() mapping마다 region metadata를 만들거나, 같은 효과의 범위 metadata를 남기는가
vm_alloc_page_with_initializer() SPT 중복 검사가 page-aligned VA 기준인가
struct file_page page별 ofs, read_bytes, zero_bytes, writable이 독립인가
do_munmap() base로 찾은 region 범위만 정리하는가
supplemental_page_table_kill() exit/exec cleanup에서 모든 mapping page를 type별로 정리하는가
supplemental_page_table_copy() fork/exec 경계에서 부모 mapping metadata가 child 새 주소 공간으로 새지 않는가

여기서 process_exit() 순서도 중요하다.

process_exit()
  -> close_open_files(curr)
  -> process_cleanup()
       -> supplemental_page_table_kill(&curr->spt)

fd table이 먼저 닫히므로 mapping은 원래 fd table file pointer에 기대면 안 된다. file_reopen() 결과를 page나 region이 책임지는 설계가 필요하다.

QEMU

QEMU는 mmap_region도, struct file_page도, SPT도 모른다. QEMU가 볼 수 있는 것은 하드웨어 효과다.

  • guest CPU가 mapped VA를 읽다가 PTE가 없으면 page fault가 난다.
  • guest CPU가 writable PTE에 store하면 dirty bit가 켜진다.
  • PintOS가 file_write_at()으로 파일 시스템 write를 만들면 IDE/block write가 발생한다.

QEMU의 x86 page walk 코드에는 store 접근에서 dirty bit를 세우는 흐름이 있다.

access_type == MMU_DATA_STORE
  -> set |= PG_DIRTY_MASK

하지만 dirty page가 region A의 offset 4096에 속하는지, region B의 offset 4096에 속하는지는 PintOS metadata만 안다.

mmap 다중 region 격리 값 추적

같은 파일 두 번 매핑 

mapping A base = 0x10000000
mapping B base = 0x20000000
file offset    = 0
page size      = 0x1000

SPT key는 반드시 VA page여야 한다.

key A = 0x10000000
key B = 0x20000000

file offset만 key처럼 쓰면 둘 다 offset 0이라 한쪽이 다른 한쪽을 덮는다.

128KB mapping 

SIZE     = 128 * 1024 = 131072 = 0x20000
PGSIZE   = 4096       = 0x1000
page_cnt = 0x20000 / 0x1000 = 32

page 17의 VA와 file offset은 다음처럼 맞아야 한다.

base        = 0x10000000
i           = 17
page va     = base + i * 0x1000 = 0x10011000
file offset = i * 0x1000        = 0x11000

이 page가 dirty이면 write-back도 offset 0x11000으로 가야 한다.

dirty bit

x86 PTE dirty bit는 bit 6이다.

PTE_D = 0x40

예를 들어 PTE low bits가 0x067이면 다음처럼 해석한다.

0x067 & 0x040 = 0x040
dirty = true

하지만 dirty 여부만으로 file offset은 알 수 없다. offset은 struct file_page 또는 region metadata에서 가져와야 한다.

구현 중 체크포인트

이 Lab의 목적은 테스트 이름을 외우는 것이 아니라, 구현 중 metadata가 섞이는 순간을 잡는 것이다. 따라서 GDB에서는 값의 존재 여부에 그치지 않고 어떤 값은 같아야 하며 어떤 값은 달라야 하는지를 비교한다.

1. mmap-twice: 같은 file offset, 다른 mapping

mmap-twice.c:13-27은 같은 sample.txt를 두 주소에 붙인다.

mapping A base = 0x10000000
mapping B base = 0x20000000
file offset    = 0

관찰할 값은 다음처럼 나뉜다.

값 기대
region A->base, region B->base 서로 다름
page A, page B 서로 다른 struct page *
page A->va, page B->va 0x10000000, 0x20000000
page A->file.ofs, page B->file.ofs 둘 다 0이어도 됨
region A->file, region B->file 보통 서로 다른 reopened file reference

같은 파일 내용과 같은 offset을 읽더라도 SPT entry와 cleanup owner는 mapping별로 분리되어야 한다. ofs가 같다는 이유로 page를 공유하면 munmap(A)가 B의 의미까지 망가뜨린다.

GDB에서는 do_mmap()이 각 page 등록을 끝낸 직후를 잡는 것이 좋다.

b do_mmap
b vm_alloc_page_with_initializer
b spt_insert_page

확인식은 구현한 구조체 이름에 맞춰 조정한다.

p/x region->base
p region->file
p/x upage
p/x aux->ofs
p page
p/x page->va
p page->file.region
p/x page->file.ofs

2. mmap-shuffle: page index와 file offset

mmap-shuffle.c:12-37은 128KB를 한 번에 mapping하고 여러 번 섞는다.

SIZE     = 128 * 1024 = 0x20000
PGSIZE   = 0x1000
page_cnt = 32

page i의 기준은 항상 다음 식이다.

page_va  = region->base + i * PGSIZE
file_ofs = region->file_offset + i * PGSIZE

예를 들어 i = 17이면 다음 값이 나와야 한다.

page_va  = 0x10011000
file_ofs = 0x11000

dirty write-back을 디버깅할 때는 PTE_D만 보지 말고, 그 dirty page가 어느 file offset으로 쓰이는지까지 같이 본다.

b file_backed_swap_out
b do_munmap
p/x page->va
p/x page->file.ofs
p page->file.read_bytes
p pml4_is_dirty(thread_current()->pml4, page->va)

기대 불변식은 다음이다.

page->file.ofs == region->file_offset + (page->va - region->base)

이 식이 깨지면 모든 page가 offset 0을 읽거나, dirty page가 엉뚱한 위치에 write-back될 수 있다.

3. mmap-inherit: fork 뒤 exec

mmap-inherit.c:13-35는 부모가 0x54321000에 mapping을 만든 뒤 child를 fork하고, child가 exec("child-inherit")를 호출하게 한다. child-inherit.c:10-14는 같은 주소에 memset()을 시도한다.

여기서 검증하는 것은 fork 직후 복사 여부만이 아니다. child가 exec()로 새 프로그램 주소 공간을 만들 때 이전 SPT와 mmap metadata가 정리되는지도 함께 본다.

b process_exec
b supplemental_page_table_kill
b page_fault

child의 exec() 이후에는 다음이 기대값이다.

spt_find_page(&child->spt, 0x54321000) == NULL
page fault at 0x54321000 -> invalid access -> exit -1
parent mapping at 0x54321000 remains valid

따라서 supplemental_page_table_kill()이 child의 old SPT를 지울 때 parent의 region/file reference를 같이 닫거나 free하면 안 된다. 부모와 자식이 같은 region pointer를 얕게 공유했다면 여기서 부모 mapping이 함께 망가질 수 있다.

4. page 등록 실패 rollback

do_mmap()은 여러 page를 등록하다가 중간에 실패할 수 있다. 예를 들어 page 0, 1은 등록했는데 page 2에서 SPT 중복이나 allocation 실패가 날 수 있다. 이 상태에서 성공한 것처럼 반환하면 일부 page만 남은 mapping이 이후 버그의 원인이 된다.

do_mmap()
  -> region 생성
  -> page 0 등록 성공
  -> page 1 등록 성공
  -> page 2 등록 실패
  -> page 0, 1 SPT entry 제거
  -> page 0, 1 aux/free 정리
  -> region list에서 제거
  -> reopened file close
  -> MAP_FAILED 반환

rollback에서 확인할 값은 다음이다.

자원 실패 후 기대
SPT entry 등록했던 VA들이 모두 사라짐
aux 등록 실패한 page의 aux까지 누수 없이 free
region thread의 mmap list에 남지 않음
reopened file 정확히 한 번 close
PTE/frame 아직 claim 전이면 없어야 하고, claim 뒤 실패라면 pml4 set page 실패 뒤 claim 롤백 Trace 기준으로 정리

이 rollback은 mmap은 왜 이미 쓰는 주소 범위를 덮으면 안 되나과도 연결된다. overlap을 늦게 발견하면 일부 page만 남는 반쪽 mapping이 생길 수 있으므로, 가능하면 등록 전에 전체 range를 먼저 검사한다.

5. mmap_list lock 범위

W09 skeleton은 mmap_region 구조체나 lock을 강제하지 않는다. 구현자가 struct thread에 mmap_list를 둔다면 최소한 다음 코드들이 같은 ownership 규칙을 따라야 한다.

코드 경로 mmap metadata 접근
do_mmap() region 추가, page 등록
do_munmap() base로 region 찾기, region 제거
supplemental_page_table_kill() exit/exec cleanup 중 region/page 정리
page fault lazy callback page별 metadata를 aux에서 struct file_page로 이전

lock을 추가한다면 critical section은 list 삽입, 제거, 탐색처럼 짧은 metadata 조작에 맞춘다. file read/write나 frame eviction처럼 오래 걸리거나 다시 page fault/파일시스템 lock과 만날 수 있는 작업을 같은 lock 안에 크게 넣으면 lock ordering 문제가 생기기 쉽다.

초보 구현에서 먼저 지킬 기준은 이것이다.

metadata list를 바꾸는 동안에는 같은 list를 동시에 순회하지 않게 한다.
file I/O와 page/frame 정리는 owner를 확정한 뒤 list lock 밖에서 수행한다.

정리

  • mmap-twice는 같은 file offset을 두 VA에 붙일 수 있어야 하므로 SPT key와 region metadata가 VA 기준으로 분리되어야 한다.
  • mmap-shuffle은 큰 mapping의 page별 offset과 dirty write-back 위치가 섞이지 않는지 확인한다.
  • mmap-inherit는 부모 mapping metadata가 child의 새 program 주소 공간에 남지 않아야 한다는 cleanup 경계를 보여준다.
  • swap-file은 file-backed page가 eviction 압력 뒤에도 file offset과 EOF 뒤 zero-fill 의미를 잃지 않아야 함을 묻는다.
  • QEMU는 mapping 격리를 모르고, PintOS가 만든 PTE dirty bit와 block device write 효과만 재현한다.
  • do_mmap()의 중간 실패는 성공한 page, aux, region, reopened file을 모두 되돌려야 한다.
  • mmap_list를 추가한다면 list 조작과 file I/O를 같은 큰 lock 범위에 묶지 않는다.
