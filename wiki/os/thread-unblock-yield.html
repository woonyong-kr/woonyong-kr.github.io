thread_unblock() 후 yield — Priority Preemption의 첫 번째 지점

thread_unblock() 후 yield — Priority Preemption의 첫 번째 지점

범위: 이 문서는 unblock 이후 선점 판단을 분리하는 일반 원리와 선택 기준을 설명하고, 제시된 PintOS·Linux·Windows 경로와 코드는 특정 구현의 사례로 다룬다. 코드 좌표·버전별 동작·GDB 실행 기록·선점 지연과 성능 수치는 해당 소스와 실제 실행·측정으로 별도 검증해야 한다.

thread_unblock()은 스레드를 READY로 올리지만 바로 선점하지 않는다. 깨운 쪽이 우선순위를 비교하고, 필요할 때 thread_yield()로 CPU를 내놓는다.

왜 깨운 직후에 비교해야 하나

thread_unblock()은 BLOCKED 상태의 스레드를 READY로 전환하고 ready_list에 넣는다. 여기까지는 “이제 실행될 수 있다”는 표시일 뿐이고, 지금 CPU를 쓰는 스레드를 밀어내지는 않는다. 그래서 스레드를 깨운 호출자가 곧바로 우선순위를 비교해야 한다.

PintOS에서는 sema_up() 끝에서 check_preemption()을 호출한다. 방금 깨어난 스레드가 현재 스레드보다 우선순위가 높으면 thread_yield()로 CPU를 넘긴다. Priority preemption에서 첫 번째로 눈여겨볼 지점이 바로 이 경로이고, 두 번째 지점은 새 스레드를 만든 직후의 thread_create() 경로다.

상세 설명

CPU가 모르는 스레드 상태

하드웨어는 “스레드를 깨운다”는 개념을 모른다. CPU가 아는 것은 현재 RIP에 있는 명령어를 실행하는 것뿐이다. 스레드 상태 전이(BLOCKED→READY)와 선점(preemption)은 전부 OS 소프트웨어가 구현한 정책이다.

Preemptive priority scheduling에서 “unblock 즉시 선점”이 필요한 이유는, timer interrupt만으로는 최악의 경우 한 tick(PintOS 기준 10 ms) 동안 낮은 우선순위 스레드가 CPU를 독점하기 때문이다. 높은 우선순위 스레드가 READY가 되는 순간 즉시 CPU를 넘겨야 priority scheduling의 의미가 살아난다.

실제 OS (Linux/Windows)

Linux CFS(Completely Fair Scheduler)에서는 try_to_wake_up() → check_preempt_curr()가 이 역할을 한다. 깨어난 태스크의 vruntime이 현재 태스크보다 충분히 작으면 TIF_NEED_RESCHED 플래그를 세우고, 다음 커널→유저 복귀 지점 또는 preempt_enable() 지점에서 context switch가 일어난다.

Windows에서는 KiUnwaitThread() 후 dispatcher가 우선순위를 비교하고, 깨어난 스레드가 현재 스레드보다 높으면 즉시 preemption을 스케줄한다.

공통적으로 unblock 함수 자체는 선점하지 않고, 호출자 또는 반환 경로에서 선점 여부를 판단한다. unblock이 인터럽트 핸들러나 임계 구간 안에서 호출될 수 있어, 즉시 context switch하면 안 되는 경우가 있기 때문이다.

PintOS 구현

PintOS에서 thread_unblock()은 인터럽트를 끈 상태에서 호출되며, 자체적으로는 선점하지 않는다:

주석에도 명시되어 있다: “이 함수는 현재 실행 중인 스레드를 선점하지 않는다.” 그 이유는 호출자가 인터럽트를 꺼둔 채로 다른 데이터를 원자적으로 갱신할 수 있어야 하기 때문이다.

선점은 thread_unblock()을 호출하는 sema_up()에서 발생한다:

check_preemption()은 ready_list 맨 앞 스레드의 우선순위와 현재 스레드를 비교한다:

intr_context() 체크가 중요하다. timer interrupt 핸들러 안에서 sema_up()이 호출되면(예: alarm clock의 wake-up) check_preemption()이 아무 일도 하지 않고, 대신 intr_yield_on_return()으로 yield가 예약되어 핸들러 복귀 시점에 context switch가 일어난다.

QEMU 에뮬레이션

QEMU 관점에서 thread_unblock()과 check_preemption()은 순수 guest 코드다. 유일하게 QEMU가 관여하는 경로는 timer interrupt에 의한 alarm wakeup이다: i8254 PIT가 IRQ0을 발생시키면 → timer_interrupt() → timer_check_sleep_list() → thread_unblock()이 호출된다. 이 경우 intr_context()가 true이므로 check_preemption()은 skip되고, 대신 intr_yield_on_return()이 예약된다.

GDB로 unblock 시점의 선점 판단을 관찰하는 방법:

Linux와 Windows의 공통점은 “즉시 switch하지 않고 플래그/인터럽트로 예약”하는 것이다. 이는 현재 코드가 spinlock을 잡고 있거나 critical section에 있을 수 있기 때문이다. PintOS는 단일 CPU에서 인터럽트 비활성화로 보호하므로, check_preemption()에서 인터럽트가 켜진 상태라면 안전하게 즉시 yield할 수 있다.

thread_unblock() 후 yield 숫자 추적

Priority preemption 없이 timer interrupt만으로 선점하는 경우의 최악 지연:

항목값
PintOS timer frequency100 Hz
TIME_SLICE4 ticks
1 tick10 ms
최악 선점 지연 (timer만)40 ms (TIME_SLICE 만큼)
unblock 즉시 선점 지연~0 ms (몇 명령어)

Priority 31 스레드가 BLOCKED 상태에서 깨어날 때, 현재 실행 중인 priority 0 스레드가 timer interrupt를 기다려야 한다면 최대 40 ms가 낭비된다. check_preemption()으로 즉시 yield하면 이 지연이 사실상 0이 된다.
