버디 시스템

버디 시스템

한 줄 요약: Buddy system은 메모리를 2의 거듭제곱 크기 블록으로 관리하며, 할당 시 큰 블록을 반으로 쪼개고 해제 시 같은 크기의 인접 블록(버디)과 합치는 구조다.

버디 시스템 혼동

Segregated free list는 크기 클래스별로 빈 블록을 관리해 빠른 할당을 달성한다. 그런데 해제 후 인접 빈 블록을 합치는 병합(coalescing) 문제가 남는다. Simple segregated storage(PintOS malloc())는 아예 병합을 하지 않아 외부 단편화가 누적된다. Segregated fits(glibc malloc)는 병합하지만 임의 크기 블록의 인접 관계를 추적하는 것이 복잡하다.

Buddy system은 이 문제에 대한 우아한 해법이다. 블록 크기를 2의 거듭제곱으로 제한하면, 어떤 블록의 “버디”(같은 크기의 짝 블록) 주소를 비트 연산 하나로 계산할 수 있다. 해제 시 버디가 빈 상태인지 확인하고, 빈 상태라면 합쳐서 두 배 크기 블록으로 만든다. 이 병합이 재귀적으로 올라가므로 큰 연속 영역을 빠르게 복원할 수 있다.

Linux 커널의 물리 페이지 할당기(page allocator)가 buddy system을 사용한다. OS 커널이 물리 메모리를 어떻게 관리하는지 이해하려면 이 구조를 알아야 한다.

이 문서를 읽고 나면 다음을 구분할 수 있어야 한다.

  • 버디 주소를 XOR로 계산하는 원리
  • 분할(split)과 병합(merge)의 재귀적 동작
  • 내부 단편화와 외부 단편화의 트레이드오프
  • Linux kernel buddy allocator와 PintOS palloc의 차이

버디 시스템 흐름

버디란 무엇인가

같은 부모 블록에서 반으로 쪼개진 두 블록을 서로의 버디(buddy)라 한다. 예를 들어 256바이트 블록을 반으로 나누면 128바이트 블록 두 개가 생기고, 이 두 블록이 서로의 버디다.

핵심 성질은 버디끼리만 합칠 수 있다는 것이다. 같은 크기여도 다른 부모에서 나온 블록은 합칠 수 없다. 이 제약 덕분에 병합이 단순해진다.

버디 주소 계산 — XOR 한 번

블록 크기가 2의 거듭제곱이면 버디 주소를 비트 연산으로 구할 수 있다.

XOR 연산의 성질상 같은 계산을 두 번 하면 원래 주소로 돌아온다. 블록이 주소의 “왼쪽 절반”이면 버디는 “오른쪽 절반”이고, 반대도 마찬가지다.

왜 XOR로 버디를 찾을 수 있는가?

블록 크기가 2^k이면 주소의 k번째 비트가 왼쪽/오른쪽을 구분한다. XOR 2^k는 이 비트만 뒤집으므로 정확히 짝 블록의 주소가 된다.

이 성질은 블록 크기가 2의 거듭제곱이고 주소가 크기에 정렬(aligned)되어 있을 때만 성립한다. 임의 크기 블록에서는 이런 계산이 불가능하다. 이것이 buddy system이 2의 거듭제곱을 고집하는 이유다.

분할 (Split) — 큰 블록을 반으로 나누기

요청 크기에 맞는 블록이 없으면 더 큰 블록을 반으로 쪼갠다.

256바이트 요청 시, 1024바이트 블록만 남아 있는 경우:

%% Buddy system split flow
flowchart TD
  request["요청<br/>256B"]
  block1024["남은 블록<br/>1024B<br/>order 10"]
  split512["분할 결과<br/>512B + 512B<br/>order 9"]
  save512["오른쪽 512B<br/>free_list[9]"]
  split256["왼쪽 512B를 다시 분할<br/>256B + 256B<br/>order 8"]
  save256["오른쪽 256B<br/>free_list[8]"]
  return256["왼쪽 256B 반환<br/>요청 충족"]
  request --> block1024
  block1024 --> split512
  split512 --> save512
  split512 --> split256
  split256 --> save256
  split256 --> return256

1024B → 512B 두 개 → 왼쪽 512B를 다시 256B 두 개로 분할. 오른쪽 512B와 오른쪽 256B는 각각의 free list에 넣는다. 분할은 요청 크기에 도달할 때까지 반복한다.

병합 (Merge) — 버디끼리 합치기

블록을 해제하면 버디가 빈 상태인지 확인한다. 빈 상태면 합쳐서 두 배 크기 블록으로 만들고, 합친 블록의 버디도 확인한다. 이것이 최대 크기에 도달할 때까지 반복된다.

256B 블록 해제 흐름:

%% Buddy system merge flow
flowchart TD
  free256["256B 블록 해제<br/>주소 0x1000"]
  buddy256["버디 확인<br/>0x1000 XOR 0x100 = 0x1100"]
  merge512["0x1100이 빈 상태<br/>512B 블록으로 병합<br/>시작 주소 0x1000"]
  buddy512["다음 버디 확인<br/>0x1000 XOR 0x200 = 0x1200"]
  stop["0x1200이 사용 중<br/>병합 중단"]
  enqueue["512B 블록 등록<br/>free_list[9]"]
  free256 --> buddy256
  buddy256 --> merge512
  merge512 --> buddy512
  buddy512 --> stop
  stop --> enqueue

병합은 O(log N)이다. 최대 order까지 올라가며 확인하므로, 전체 메모리 크기에 대한 로그 횟수만 필요하다.

내부 단편화 — 2의 거듭제곱 강제의 대가

요청 크기를 2의 거듭제곱으로 올림하므로 내부 단편화가 발생한다.

최악의 경우: 2^k + 1 바이트 요청 → 2^(k+1) 바이트 할당 낭비율 = (2^(k+1) - 2^k - 1) / 2^(k+1) ≈ 50%

평균적으로는 약 25%의 내부 단편화가 발생한다. 이것이 buddy system의 가장 큰 단점이다. Linux 커널은 이 문제를 slab allocator로 완화한다. Buddy system 위에 slab을 올려 작은 객체를 효율적으로 관리한다.

외부 단편화 — buddy system이 강한 이유

반면 외부 단편화에는 강하다. 인접한 빈 블록을 빠르게 병합해 큰 연속 영역을 복원하기 때문이다. Implicit free list에서는 병합을 하더라도 비인접 빈 블록은 합칠 수 없다. Buddy system은 “같은 부모에서 나온 블록”이라는 제약이 있지만, 이 제약 덕분에 병합 대상을 O(1)에 찾을 수 있어 병합이 적극적으로 이루어진다.

실제 OS와의 비교

  • Linux 커널 buddy allocator: 물리 페이지를 order 0(4KB) ~ order 10(4MB) 범위로 관리한다. 각 order마다 free list를 두어 segregated free list와 결합한 형태다. /proc/buddyinfo에서 각 order의 빈 블록 수를 확인할 수 있다.
  • PintOS palloc: buddy system을 사용하지 않는다. 비트맵 기반 할당기로, 연속된 빈 페이지를 비트맵에서 탐색한다. 구현은 단순하지만 큰 연속 영역을 빠르게 찾기 어렵다.
  • PintOS malloc(): 페이지 내부에서 고정 크기 블록을 관리하는 simple segregated storage다. 페이지 자체의 할당은 palloc이 담당한다.

Linux 커널 buddy allocator의 구조

Linux 커널의 buddy allocator는 mm/page_alloc.c에 구현되어 있다. 핵심 구조는 zone별로 order 0~10까지의 free area를 유지하는 것이다.

Linux는 단순한 buddy system 위에 migration type(Unmovable, Movable, Reclaimable)을 추가해 메모리 compaction을 지원한다. 이것은 buddy system의 외부 단편화 문제를 더욱 완화하는 확장이다.

PintOS는 어떻게 다른가 — 실제 palloc 코드

PintOS의 물리 페이지 할당기는 buddy system이 아니라 비트맵 기반이다. 위 개념 코드와 비교해 보면 분할·병합 대신 비트맵 스캔 한 번으로 연속 페이지를 찾는다.

bitmap_scan_and_flip이 핵심이다. 빈 페이지(false) page_cnt개가 연속으로 늘어선 구간을 비트맵에서 선형 탐색하고, 찾으면 한 번에 사용 중(true)으로 표시한다. order 분할도, 버디 병합도 없다. 대신 큰 연속 영역을 요청하면 비트맵 전체를 훑어야 할 수 있고, 인접하지 않은 빈 페이지를 합치는 적극적 병합이 없어 외부 단편화에 buddy보다 약하다. 구현이 단순한 대신 buddy의 O(1) 병합 이점을 포기한 설계다.

malloc()은 또 다르다. threads/malloc.c의 descs[]는 16바이트부터 PGSIZE/2까지 2의 거듭제곱 크기 클래스마다 free_list를 두는 simple segregated storage다. 페이지 하나(arena)를 같은 크기 블록으로 잘게 나눠 쓰다가, arena의 모든 블록이 비면 그 arena를 통째로 palloc에 돌려준다. 블록 단위 병합은 하지 않는다.

정리

Buddy system은 메모리를 2의 거듭제곱 크기 블록으로 관리한다. 할당 시 큰 블록을 반으로 분할하고, 해제 시 버디(같은 부모에서 나온 짝 블록)와 합친다. 버디 주소를 XOR 한 번으로 계산할 수 있어 병합이 O(1)이고, 재귀적 병합으로 큰 연속 영역을 빠르게 복원한다. 내부 단편화(평균 25%)가 대가이며, Linux 커널은 slab allocator를 위에 올려 작은 객체의 단편화를 줄인다. PintOS는 buddy system 대신 비트맵 기반 palloc을 사용하며, 이는 구현은 단순하지만 큰 연속 할당에서 buddy보다 불리하다.

  • 연결 문서: 메모리 단편화, 비트맵 할당기 설계
  • 관련: 운영체제
