loops_per_tick 보정

확인 범위: 이 문서는 loops_per_tick 보정의 일반 원리와 알고리즘, PintOS와 Linux·QEMU의 역할 차이를 개념적으로 설명한다. 제시된 코드 경로, 반복 횟수, 보정값, 소요 시간과 지연 정확도는 특정 구현·설정·실행 환경에 따른 예시이므로 실제 코드와 버전, 부팅 출력 및 측정 기록을 확인해야 한다.

한 줄 요약: 빈 루프가 timer tick 1개(약 10ms) 안에 몇 번 도는지 부팅 시 1회 측정하는 sub-tick 지연 보정 상수.

loops_per_tick 보정 구조

loops_per_tick은 현재 실행 환경에서 빈 루프가 timer tick 1개(약 10 ms) 안에 몇 번 도는지를 나타내는 상수다. 부팅할 때 한 번 측정하며, sub-tick 지연(timer_usleep, timer_nsleep)이 필요하면 이 값을 지연 시간의 비율에 맞춰 환산해 busy-wait 루프 횟수를 정한다.

CPU와 가상화 환경에 따라 빈 루프의 실행 속도가 달라지므로 이 값은 컴파일할 때 고정하기 어렵다. PintOS는 먼저 어떤 루프 횟수가 한 tick 안에 실행되는지 판별하고, 그 경계를 두 단계로 좁힌다. 거친(coarse) 단계에서는 후보를 2의 거듭제곱 단위로 두 배씩 늘린다. 한 tick을 넘는 구간을 찾으면 미세(fine) 단계로 넘어가 하위 8비트를 한 비트씩 확정한다. 이 과정이 이 문서에서 말하는 이진 탐색(binary search)이다.

상세 설명

추상 개념 (하드웨어 / 알고리즘)

측정에 필요한 질문은 하나다. busy_wait(N)을 실행하는 동안 timer interrupt가 발생했는가? 인터럽트가 발생하지 않았다면 N회는 한 tick 안에 실행된 것이고, 발생했다면 한 tick을 넘긴 것이다. too_many_loops()가 이 판별을 담당하고, 보정 알고리즘은 그 결과를 이용해 적절한 N의 경계를 찾는다.

이진 탐색 알고리즘

탐색은 넓은 범위를 빠르게 찾는 Phase 1과 그 범위 안에서 값을 다듬는 Phase 2로 이어진다.

Phase 1 — Coarse (거친 탐색)
  loops_per_tick = 1024
  while too_many_loops(loops_per_tick × 2) == false:
      loops_per_tick ×= 2
  ⇒ loops_per_tick은 "한 tick 안에 드는 최대 2^k" 값

Phase 2 — Fine (미세 탐색)
  high_bit = loops_per_tick          // 2^k
  for test_bit = 2^(k-1) down to 2^(k-9):
      if too_many_loops(high_bit | test_bit) == false:
          loops_per_tick |= test_bit
  ⇒ 상위 1비트 아래 8비트를 한 비트씩 확정

Phase 1이 한 tick을 넘지 않는 가장 큰 2의 거듭제곱을 찾으면, Phase 2가 그 값 아래의 비트를 시험한다. 각 비트는 추가해도 한 tick 안에 들어올 때만 결과에 남는다. 이 과정을 마치면 약 9비트 정밀도(0.2% 이내)의 근사값을 얻는다.

too_many_loops(N) 판별

1. tick 경계 동기화: ticks가 바뀔 때까지 spin
2. 현재 ticks 기록
3. busy_wait(N) 실행
4. ticks가 바뀌었으면 true (N은 한 tick보다 크다)

측정은 새 tick이 시작된 직후에 진행해야 한다. tick 중간에서 시작하면 남은 시간이 0~10 ms 사이 어디인지 알 수 없어 루프 처리량을 실제보다 작게 측정할 수 있다. 따라서 먼저 ticks가 바뀌기를 기다린 뒤 busy_wait(N)을 실행해 거의 full tick(~10 ms)을 측정 구간으로 확보한다.

실제 OS (Linux)

Linux의 대응물은 loops_per_jiffy(또는 lpj)다. calibrate_delay() 함수에서 부팅 시 측정하며, 알고리즘은 PintOS와 거의 동일한 이진 탐색이다.

측정 함수timer_calibrate()calibrate_delay()

용도busy_wait() sub-tick 지연__delay(), udelay(), ndelay()

출력 메시지Calibrating timer... N loops/s.Calibrating delay loop... N BogoMIPS

Linux의 BogoMIPS는 loops_per_jiffy × HZ / 500000으로 계산한다. “Bogus MIPS”라는 이름 그대로, 실제 CPU 성능 지표가 아니라 지연 루프 보정용 근사값이다.

PintOS 구현

PintOS 구현에서도 앞에서 본 순서가 그대로 드러난다. 먼저 결과를 저장할 변수를 선언하고, Phase 1에서 탐색 범위를 잡은 뒤 Phase 2에서 하위 비트를 확정한다. 이후 지연 함수가 확정된 값을 사용한다.

변수 선언

Phase 1: Coarse 탐색

loops_per_tick이 약 500,000인 경우에는 1024 → 2048 → … → 524288 순서로 후보를 늘리며 약 9회 반복한다. 다음 두 배 값이 한 tick을 넘는다고 판별되면 Phase 1을 끝낸다.

Phase 2: Fine 탐색

high_bit >> 10에 도달하기 전까지 비트를 하나씩 낮추므로 정확히 8회 반복한다. 각 반복에서는 too_many_loops()를 한 번 호출하며, 이 호출 안에서 tick 경계를 기다린 다음 busy_wait를 한 번 실행한다.

총 측정 시간

각 too_many_loops() 호출에는 최소 1 tick(10 ms)과 busy_wait 시간이 필요하다. Phase 1을 약 9회, Phase 2를 8회 수행하는 예시에서는 총 ~17회 × ~10 ms이므로 측정에 약 170 ms가 걸린다.

사용처: busy_wait 계산

보정이 끝나면 real_time_sleep()은 요청한 시간이 한 tick보다 짧을 때 loops_per_tick을 비율로 환산해 busy-wait 횟수를 구한다.

예시: timer_usleep(500) → num=500, denom=1,000,000

loops_per_tick × 500 / 1000 × 100 / (1000000/1000)
= loops_per_tick × 500 / 1000 × 100 / 1000
= loops_per_tick × 0.05

loops_per_tick = 491,520이면 약 24,576회 루프가 필요하며, 이 예시에서는 약 500 µs에 해당한다.

QEMU 에뮬레이션

QEMU는 loops_per_tick을 직접 알거나 결정하지 않는다. QEMU와 guest OS의 역할은 다음과 같이 나뉜다.

  1. QEMU가 i8254 PIT 카운터를 QEMU_CLOCK_VIRTUAL 기반으로 에뮬레이션한다.
  2. 카운터가 만료되면 qemu_set_irq()로 IRQ0를 발생시킨다.
  3. guest CPU가 busy_wait() 루프를 TCG 번역 블록으로 실행한다.
  4. PintOS가 그 실행 중 tick 변경 여부를 관찰해 loops_per_tick을 보정한다.

QEMU 호스트 스케줄링, TCG 번역 오버헤드, icount 모드 여부에 따라 같은 guest OS라도 loops_per_tick 값이 실행마다 달라질 수 있다. 따라서 guest OS는 고정값을 가정하지 않고 런타임에 측정한다.

loops_per_tick 보정 값 추적

다음 표는 두 탐색 단계가 어떻게 이어지는지 보여 주는 특정 실행 환경의 예시다. 먼저 Coarse 단계가 경계가 포함된 범위를 찾고, 이어지는 Fine 단계가 그 범위에서 비트를 시험한다.

출력 메시지 역산

보정 결과가 초당 루프 수로 출력되었다면 tick 빈도를 이용해 loops_per_tick을 역산할 수 있다.

49,152,000 loops/s  →  loops_per_tick = 49,152,000 / 100 = 491,520

이 값은 BogoMIPS가 아니다. PintOS는 BogoMIPS 용어를 쓰지 않으며, 단순히 loops/s로 표시한다.

순서도

flowchart TD
    A["timer_calibrate() 시작"] --> B["loops_per_tick = 1024"]
    B --> C{"too_many_loops(lpt × 2)?"}
    C -- false --> D["loops_per_tick <<= 1"]
    D --> C
    C -- true --> E["Phase 1 완료: 2^k 확보"]
    E --> F["test_bit = 2^(k-1)"]
    F --> G{"test_bit > 2^(k-9)?"}
    G -- true --> H{"too_many_loops(high | test_bit)?"}
    H -- false --> I["loops_per_tick |= test_bit"]
    I --> J["test_bit >>= 1"]
    H -- true --> J
    J --> G
    G -- false --> K["Phase 2 완료: 9비트 정밀도 확보"]
    K --> L["printf loops/s 출력"]
