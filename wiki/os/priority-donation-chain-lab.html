Priority Donation Chain 실험: 높은 우선순위가 lock 줄을 타고 전파되는지 보기

한 줄 요약: nested priority donation은 waiting_lock 포인터를 따라 holder의 holder까지 우선순위를 전파하는 문제로, priority-donate-chain 테스트는 main priority가 0→3→6→…→21로 올라가 가장 아래 holder가 먼저 실행되고 lock 0이 풀리기를 기대한다.

그런데 holder도 다른 lock을 기다리고 있다면 어떻게 될까

높은 우선순위 스레드가 lock 하나를 기다리면 holder에게 우선순위를 기부한다.

그런데 holder도 다른 lock을 기다리고 있다면 어떻게 될까?

이 상황에서는 thread 7의 높은 우선순위가 thread 6에서 멈추면 안 된다. thread 6이 기다리는 thread 5, 다시 thread 4, 결국 main까지 전파되어야 lock 0이 빨리 풀린다.

이 실험의 질문은 이것이다.

Priority Donation Chain 필요성

priority inversion은 lock 하나에서만 생기지 않는다. 실제 커널 코드에서는 lock을 잡은 스레드가 또 다른 lock이나 이벤트를 기다리는 일이 생긴다.

이때 donation이 한 단계에서 끊기면 높은 우선순위 작업은 여전히 낮은 우선순위 chain 뒤에 막힌다.

H가 T6에게만 기부하고 끝나면, main은 여전히 priority 0이다. main이 실행되지 않으면 lock 0은 풀리지 않고, 전체 chain은 앞으로 가지 못한다.

이 말은 즉, nested donation은 “가장 급한 스레드가 실제로 막혀 있는 가장 아래 holder를 빨리 실행시키는 장치”다.

Priority Donation Chain 흐름

Priority donation chain은 waiting_lock 포인터를 따라간다.

PintOS 구조체로 번역하면 이렇게 된다.

필드질문의미

Priority Donation Chain 사례

PintOS 테스트 priority-donate-chain.c는 숫자를 작게 만들어 chain을 보여준다.

각 thread는 자기 lock을 먼저 잡고, 그 다음 바로 앞 thread가 들고 있는 lock을 얻으려 한다.

정상이라면 thread 7이 만들어진 뒤 main의 effective priority는 21까지 올라간다.

테스트가 기대하는 핵심 관찰은 다음이다.

꼬리 질문

  • 왜 필요한가?
    • 높은 우선순위 thread가 lock chain의 맨 아래 holder 때문에 막힐 수 있기 때문이다.
  • 실제 OS는 어떻게 하나?
    • priority inheritance가 필요한 동기화 객체에서 wait chain, scheduler class, realtime 정책을 함께 다룬다.
  • PintOS는 어디서 단순화했나?
    • struct thread에 waiting_lock과 donation_list를 직접 넣고, 과제 테스트 깊이에 맞춘 작은 chain을 본다.
  • QEMU는 무엇을 흉내 내나?
    • donation 의미가 아니라 guest CPU 실행, guest memory, interrupt, GDB 관찰 경로를 흉내 낸다.
  • 숫자를 넣으면 무엇이 계산되나?
    • 0 -> 3 -> 6 -> ... -> 21처럼 holder의 effective priority가 올라간다.
  • GDB로 어디를 보면 확인되나?
    • lock_acquire(), refresh_priority(), lock_release()에서 priority, waiting_lock, donation_elem 주소를 본다.

실제 운영체제

실제 OS에도 priority inversion 문제는 있다. 다만 모든 lock을 PintOS처럼 단순한 donation_list로 처리한다고 보면 안 된다.

Linux는 realtime mutex나 priority inheritance futex 같은 경로에서 priority inheritance를 다룬다. 일반 mutex, spinlock, scheduler class, CPU별 run queue, preemption model이 모두 얽히므로 “항상 PintOS식 donation이 일어난다”라고 단정하면 안 된다.

Windows도 thread priority, wait object, dispatcher, priority boost 같은 정책이 함께 작동한다. handle/object 모델과 scheduler 정책이 분리되어 있고, SMP 환경에서 여러 CPU가 동시에 실행된다.

현실 OS의 핵심은 이것이다.

PintOS는 이 큰 문제를 lock, semaphore, list, priority 숫자만으로 관찰 가능하게 줄인다.

lock_acquire()에서 holder가 있으면 현재 스레드는 holder의 donation_list에 들어간다. 그 다음 현재 스레드가 기다리는 lock을 waiting_lock에 기록한다.

chain 전파는 holder가 또 다른 lock을 기다리는지 보는 방식이다.

이 코드베이스는 while (idx < 7)로 최대 7단계까지 따라간다. 이것은 범용 OS 설계라기보다 PintOS priority-donate-chain 테스트가 만드는 깊이에 맞춘 교육용 구현으로 읽어야 한다.

QEMU

QEMU는 priority donation을 이해하지 않는다.

QEMU 입장에서는 다음만 보인다.

  • guest CPU가 PintOS 커널 코드를 실행한다.
  • guest memory 안의 struct thread 필드 바이트가 바뀐다.
  • thread_yield()나 schedule()이 실행되면 guest register와 guest stack 흐름이 바뀐다.
  • GDB stub이 guest register와 guest memory를 GDB에 보여준다.

확인할 QEMU 경계:

  • target/i386/gdbstub.c
    • x86_cpu_gdb_read_register()가 env->regs[...], env->eip, env->eflags 같은 guest CPU state를 읽는다.
  • hw/intc/apic.c
    • cpu_interrupt(..., CPU_INTERRUPT_HARD)가 guest CPU에 interrupt pending 상태를 전달하는 경로에 나온다.

따라서 GDB에서 thread_current()->priority를 볼 수 있는 이유는 QEMU가 PintOS scheduler를 해석해서가 아니다. QEMU가 guest memory를 읽을 수 있게 해 주기 때문이다.

  • SW_AI-W11-pintos/pintos/include/threads/thread.h

4. lock release 후 priority 회복

PintOS:

  • SW_AI-W11-pintos/pintos/threads/synch.c
  • SW_AI-W11-pintos/pintos/threads/thread.c

lock_release()는 현재 lock 때문에 들어온 donor만 제거한다.

그 뒤 refresh_priority()는 현재 thread의 effective priority를 다시 계산한다.

이 말은 즉, lock 하나를 풀었다고 모든 donation을 지우면 안 된다. 다른 lock 때문에 아직 남아 있는 donor가 있으면 그 priority는 유지되어야 한다.

Priority Donation Chain 값 추적

1. priority 숫자 변화

priority-donate-chain의 main thread는 처음에 priority 0으로 낮아진다.

thread가 하나씩 만들어지며 chain이 길어지면 main의 effective priority는 이렇게 바뀐다.

중간에 interloper 6의 priority가 17이어도 main이 18 또는 21로 올라가 있으면 interloper가 먼저 실행될 수 없다.

2. struct thread 안의 주소 계산

이 저장소의 struct thread 앞부분은 64비트 환경에서 다음 크기 감각으로 볼 수 있다.

struct thread 앞부분 offset은 다음처럼 계산된다.

필드offset
tid0x00
status0x04
priority0x08
base_priority0x0c
wake_tick0x10
name0x18
donation_list0x28
donation_elem0x48
waiting_lock0x58
elem0x60

예를 들어 thread 7의 struct thread *가 0x80005000이라고 하자.

holder의 donation_list에 들어가는 것은 0x80005000이 아니라 0x80005048이다. semaphore waiters나 ready list에 들어가는 것은 0x80005060이다.

이 차이가 보이면 GDB에서 list를 볼 때 “이 원소가 donor list의 원소인가, ready/waiter list의 원소인가”를 구분할 수 있다.

3. list_entry()가 되돌리는 주소

list_entry(e, struct thread, donation_elem)는 e에서 thread 시작 주소를 복원한다.

같은 thread라도 elem 기준으로 복원할 때는 offset이 다르다.

Priority Donation Chain GDB

1. 테스트 출력으로 확인

Threads 빌드 디렉터리에서 donation chain 테스트를 실행하면 된다.

확인할 줄은 main의 priority가 단계적으로 올라가는 부분이다.

현재 자동화에서는 PintOS 코드 디렉터리에 빌드 산출물을 쓰지 않기 위해 이 테스트를 직접 실행하지 않았다. 대신 테스트 소스와 기대 출력 파일을 근거로 삼았다.

2. GDB에서 donation이 들어가는 순간 보기

lock_acquire()에서 holder가 있는 경우를 잡는다.

멈춘 순간에는 curr->waiting_lock이 아직 설정되기 전일 수 있다. 한두 줄 진행한 뒤 다시 본다.

3. chain을 따라가기

holder가 다시 다른 lock을 기다리는지 본다.

이 값이 이어져 있으면 donation은 한 단계가 아니라 wait chain을 따라 전파되어야 한다.

4. offset을 직접 확인하기

GDB에서 실제 offset이 문서 계산과 맞는지 확인한다.

기대 감각:

5. release 뒤 priority가 내려가는지 보기

lock_release()에서 donation 제거와 refresh_priority() 이후 값을 비교한다.

좀 더 세밀하게 보려면 refresh_priority()에 멈춘다.

확인해야 할 결론은 “release한 lock 때문에 들어온 donation만 제거되고, 남은 donation이 있으면 effective priority가 그만큼 유지된다”는 것이다.

순서도: Donation Chain 전파 흐름

sequenceDiagram
    participant T7 as thread 7 (pri=21)
    participant T6 as thread 6 (pri=18)
    participant T5 as thread 5 (pri=15)
    participant M as main (pri=0)
    participant RL as ready_list

    Note over M: main holds lock[0], base_priority=0
    Note over T5: holds lock[5], waits lock[4]...
    Note over T6: holds lock[6], waits lock[5]

    T7->>T6: lock_acquire(lock[6]) → holder=T6
    T7->>T6: donation_list에 T7 삽입
    T7->>T7: waiting_lock = lock[6]
    Note over T7,T6: T6.priority = max(18, 21) = 21

    T7->>T5: chain: T6.waiting_lock→lock[5]→holder=T5
    Note over T5: T5.priority = max(15, 21) = 21

    T7->>M: chain 끝: ...→lock[0]→holder=main
    Note over M: main.priority = max(0, 21) = 21

    T7->>T7: sema_down(lock[6].semaphore) → BLOCKED

    Note over M: main이 effective priority 21로 실행
    M->>M: lock_release(lock[0])
    M->>M: donation_list에서 lock[0] donor 제거
    M->>M: refresh_priority() → priority = base(0)
    M->>RL: check_preemption() → yield

flowchart TD
    A[lock_acquire 진입] --> B{lock->holder 존재?}
    B -- No --> C[sema_down으로 바로 획득]
    B -- Yes --> D[holder->donation_list에 curr 삽입]
    D --> E[curr->waiting_lock = lock]
    E --> F[holder = lock->holder]
    F --> G{holder->waiting_lock != NULL?}
    G -- Yes --> H[holder = waiting_lock->holder]
    H --> I[holder->priority = max existing, donor priority]
    I --> J{depth < 7?}
    J -- Yes --> G
    J -- No --> K[chain 전파 종료]
    G -- No --> K
    K --> L[sema_down → BLOCKED]

정리

  • nested priority donation은 waiting_lock을 따라 holder의 holder에게 priority를 전파하는 문제다.
  • priority-donate-chain 테스트는 main priority가 0 -> 3 -> 6 -> ... -> 21로 올라가야 함을 기대한다.
  • PintOS에서는 priority, base_priority, waiting_lock, donation_list, donation_elem이 핵심 필드다.
  • donation_elem과 elem은 주소가 다르다. GDB에서 list를 볼 때 어떤 list node인지 구분해야 한다.
  • QEMU는 donation을 처리하지 않는다. QEMU는 PintOS guest memory와 guest CPU state를 관찰 가능하게 해 주는 에뮬레이터다.
