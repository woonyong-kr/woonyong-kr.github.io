파일과 확장 가능 파일

파일과 확장 가능 파일

한 줄 요약: 파일은 이름 없는 바이트 스트림이며, struct file은 inode 위에 현재 위치(pos)와 쓰기 보호 상태를 얹은 핸들이다. PintOS 기본 구현은 파일 크기를 생성 시 고정하지만, Project 4에서는 쓰기가 파일 끝을 넘으면 자동으로 디스크 블록을 할당하는 확장 가능 파일(extensible file)로 바꿔야 한다.

파일과 확장 가능 파일의 관계

운영체제에서 “파일”은 디스크에 저장된 바이트 열이다. 사용자 프로그램은 open() → read()/write() → close() 순서로 파일에 접근한다. 이 인터페이스 뒤에서 커널이 파일의 현재 상태를 관리하는 구조체가 struct file이다.

struct file을 이해하면 파일 디스크립터가 무엇을 가리키는지, seek()이 왜 필요한지, 같은 파일을 두 프로세스가 열어도 읽기 위치가 왜 서로 독립적인지 설명할 수 있다.

기본 PintOS에서는 filesys_create("a.txt", 1024)처럼 파일을 만들 때 크기를 확정한다. 반면 실제 OS에서는 write()가 파일 끝을 넘어갈 때 필요한 블록을 추가할 수 있다. Project 4의 과제 중 하나는 기본 PintOS의 고정 크기 파일을 이와 같은 확장 가능 파일로 바꾸는 것이다.

파일과 확장 가능 파일의 차이

비유: 책갈피가 꽂힌 노트

파일은 빈 줄이 없는 노트와 비슷하다. inode가 “이 노트는 몇 페이지이고 어느 서랍에 있다”는 물리적 정보를 담는다면, struct file은 노트를 펼쳐 책갈피(pos)를 꽂아 둔 상태를 나타낸다. 같은 노트를 두 사람이 각자 열면 책갈피 위치는 다르지만, 두 사람이 보는 노트 자체(inode)는 하나다.

struct file의 구조

%% struct file과 inode 관계
flowchart LR
  file_handle["struct file<br/>파일 핸들<br/>inode: struct inode *<br/>pos: 0<br/>deny_write: false"]
  inode_memory["struct inode<br/>메모리 inode<br/>open_cnt: 2<br/>sector: 5<br/>removed: false"]
  inode_disk["inode_disk<br/>디스크 inode<br/>start: 10<br/>length: 2048<br/>data sectors"]
  file_handle --> inode_memory
  inode_memory <--> inode_disk

struct file은 세 필드로 구성된다.

  • inode: 파일의 실체를 가리키는 포인터. 크기와 데이터 위치 같은 물리적 정보가 여기에 있다.
  • pos: 다음 read()/write()가 시작될 바이트 오프셋. file_seek()으로 직접 변경할 수 있다.
  • deny_write: 실행 중인 바이너리의 변조를 막기 위해 쓰기를 금지하는 플래그.

파일 열기 → 읽기 → 닫기 흐름

  1. filesys_open("hello.txt") → 루트 디렉터리에서 이름을 찾아 inode 섹터 번호를 얻는다.
  2. inode_open(sector) → inode를 메모리에 올린다(이미 열려 있으면 open_cnt++).
  3. file_open(inode) → struct file을 calloc으로 할당하고 pos = 0으로 초기화한다.
  4. file_read(file, buf, size) → inode_read_at()으로 pos 위치부터 데이터를 읽고, 읽은 만큼 pos를 전진시킨다.
  5. file_close(file) → 쓰기 보호 해제 → inode_close() → struct file 해제.

고정 크기 파일의 한계

기본 PintOS에서 파일을 만드는 filesys_create()는 initial_size 바이트만큼 연속된 섹터를 미리 할당한다. 파일 크기는 생성 시점에 확정되며, file_write()가 파일 끝에 도달하면 그 뒤에는 더 쓸 수 없다.

filesys_create("a.txt", 1024)
→ inode_create(sector, 1024)
→ free_map_allocate(2섹터, &start)    // 1024B = 2섹터
→ 디스크에 2섹터 0으로 채움
→ 이후 write는 1024B 범위 안에서만 가능

확장 가능 파일 (Extensible File)

실제 OS에서는 write()가 현재 파일 크기를 넘으면 새 블록을 자동으로 할당한다. Project 4에서 이를 구현하려면 두 부분을 바꿔야 한다.

1. inode_write_at()에서 파일 확장

기본 inode_write_at()은 offset + size > inode_length이면 기록을 멈춘다. 확장 가능 파일에서는 부족한 공간만큼 새 섹터(또는 클러스터)를 할당하고 inode_disk.length를 갱신해야 한다.

2. 연속 할당 → 인덱스 할당으로 전환

기본 inode_disk.start는 연속 할당을 전제로 한다. 파일이 커질 때 바로 다음 섹터가 비어 있지 않으면 확장할 수 없다. 이를 해결하는 방법은 두 가지다.

  • FAT 체인: fat_create_chain()으로 클러스터를 하나씩 연결한다. byte_to_sector()가 FAT 체인을 따라가도록 수정한다.
  • 인덱스 블록: inode 안에 직접/간접 블록 포인터 배열을 두어 비연속 섹터를 가리킨다 (ext2/ext4 방식).
[고정 크기 — 연속 할당]
inode_disk.start = 10
데이터: 섹터 10, 11  (끝)

[확장 가능 — FAT 체인]
클러스터 3 → 클러스터 7 → 클러스터 12 → EOChain
파일이 커지면 fat_create_chain()으로 클러스터 추가

file_deny_write / file_allow_write

실행 중인 프로그램의 바이너리 파일이 변조되면 위험하다. load() 과정에서 file_deny_write()를 호출하면 inode->deny_write_cnt++가 되고, 이후 inode_write_at()은 0을 반환한다. 프로세스가 종료되면 file_allow_write()로 카운터를 내린다.

같은 inode를 두 프로세스가 실행 중이면 카운터가 2가 된다. 따라서 두 프로세스가 모두 종료되어야 다시 쓰기가 허용된다.

파일과 확장 가능 파일 코드

struct file 정의

struct file은 헤더가 아니라 file.c 안에 정의되어 있다. 외부에서는 file_read(), file_seek() 같은 함수로만 접근한다. 이는 구조체 내부를 캡슐화하려는 의도다.

file_open()과 file_close()

calloc으로 할당하므로 모든 필드가 0으로 초기화된다. inode의 소유권은 file_open()이 넘겨받는다. 따라서 할당에 실패하면 inode_close()를 호출해 자원을 정리한다.

file_read() — pos 자동 전진

file_read()는 pos에서 시작해 size바이트를 읽고, 실제로 읽은 바이트만큼 pos를 전진시킨다. file_read_at()은 pos를 바꾸지 않는 변형이다.

file_duplicate() — fork가 파일 핸들을 복제하는 과정

fork()가 호출되면 자식 프로세스는 부모의 fd table을 복제한다. 이때 각 struct file을 file_duplicate()로 복사하면 같은 inode를 공유하면서도 pos와 deny_write 상태가 독립적인 새 핸들이 생긴다. inode_reopen()은 같은 inode의 open_cnt를 1 증가시켜 여러 참조가 함께 존재할 수 있게 한다.

file_write() — 고정 크기의 한계

inode_write_at() 내부에서는 offset >= inode_length이면 기록을 중단한다. 확장 가능 파일을 구현하려면 이 지점에서 새 섹터를 할당하고 inode_disk.length를 갱신해야 한다.

정리

struct file은 inode에 읽기·쓰기 위치(pos)와 쓰기 보호 플래그를 더한 파일 핸들이다. 같은 파일을 여러 번 열면 여러 struct file이 하나의 inode를 공유하며, 각 핸들의 pos는 서로 독립적이다. 기본 PintOS는 생성 시점에 파일 크기를 고정한다. 이 제한을 없애려면 inode_write_at()이 파일 끝을 넘는 쓰기를 처리할 때 새 블록을 동적으로 할당해야 한다. 파일이 비연속 블록까지 사용하며 확장되려면 FAT 체인이나 인덱스 블록도 필요하다.
