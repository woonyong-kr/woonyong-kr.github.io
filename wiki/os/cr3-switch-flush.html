CR3 전환과 TLB Flush

CR3 전환과 TLB Flush

확인 범위: 이 문서는 CR3 전환과 TLB 무효화의 일반 원리 및 선택 기준을 설명하고 PintOS·Linux·QEMU의 동작을 예시로 다룬다. 다만 제시된 코드 좌표, 버전별 지원 여부, 실행 흐름과 성능 수치는 실제 소스 버전·실행 기록·측정을 통해 검증된 결과가 아니다. 구현별 설명과 예시로 읽고 별도로 확인해야 한다.

한 줄 요약: 주소 공간을 바꿀 때 CR3에 새 PML4 물리 주소를 쓰면 TLB의 non-global 엔트리가 무효화된다. 한 페이지만 무효화할 때는 INVLPG를 사용하며, PCID가 활성화된 환경에서는 CR3 설정에 따라 flush를 피할 수 있다.

주소 공간 전환에서 CR3와 TLB가 맡는 역할

프로세스가 바뀌면 CPU가 참조해야 할 주소 공간도 바뀐다. OS는 새 주소 공간의 PML4 물리 주소를 CR3 레지스터에 기록해 페이지 테이블의 시작점을 교체한다.

이때 이전 주소 공간에서 만든 VA→PA 변환 캐시가 그대로 사용되면, 새 프로세스의 주소가 이전 프로세스의 물리 메모리로 변환될 수 있다. 따라서 일반적인 CR3 기록은 TLB의 non-global 엔트리를 무효화한다. 다만 이 동작을 곧바로 “TLB 전체 flush”라고 부르면 global 엔트리와 PCID 예외가 가려진다. 이 문서에서 전체 flush는 별도 설명이 없는 한 non-global 엔트리의 무효화를 뜻한다.

CR3 전환은 페이지 테이블의 시작점을 바꾸는 동작이고, TLB flush는 캐시된 주소 변환을 무효화하는 효과다. 주소 공간 전체를 전환할 때는 MOV CR3, <val>을 사용한다. 현재 주소 공간에서 한 VA의 매핑만 바뀌었다면 INVLPG <addr>로 그 엔트리만 무효화할 수 있다.

CPU/MMU 수준의 동작 구분

동작TLB 효과명령어
MOV CR3, <val>전체 flush (non-global 엔트리)lcr3()
INVLPG <addr>해당 VA 1개만 무효화invlpg()
PCID 활성 + CR3 bit 63 = 0전체 flush—
PCID 활성 + CR3 bit 63 = 1flush 안 함 (PCID 전환만)—

PCID를 사용하지 않는 조건에서는 CR3에 같은 값을 다시 써도 flush가 발생한다. Global bit(PTE bit 8)이 설정된 엔트리는 CR3 기록으로 flush되지 않는다. 커널 매핑처럼 여러 주소 공간이 공유하는 엔트리를 유지하기 위한 구분이다. PCID(Process Context ID)를 사용하면 TLB 엔트리에 주소 공간 태그를 붙여 flush 없이 전환할 수 있지만, 이 문서가 설명하는 PintOS 구현은 PCID를 사용하지 않는다.

TLB flush 비용은 다음과 같이 제시되어 있다. 이 값은 L1 cache hit과 특정 working set을 가정한 예시이며, 이 문서에서 실제로 측정한 결과는 아니다.

TLB miss 1회: ~7 ns (4단계 walk, L1 cache hit 가정)
TLB 전체 flush 후 재채움: 수백~수천 ns (working set 크기에 비례)
컨텍스트 스위치 직후 첫 수십 개 VA 접근이 모두 TLB miss → "cold TLB" 패널티

운영체제에 따른 처리 방식

Linux

Linux는 TLB flush 비용을 줄이기 위해 여러 최적화를 사용한다고 설명할 수 있다. 아래 버전과 구현 세부 사항은 이 문서에서 실제 소스나 실행 기록으로 검증하지 않았으므로, 해당 구현을 조사할 때 확인할 후보로 사용해야 한다.

최적화 기법LinuxWindowsPintOS
PCID4.14+에서 코어당 6개 PCID 할당, flush 없이 전환지원 (CR4.PCIDE, Windows 10+)미사용 (매번 전체 flush)
Lazy TLB커널 스레드 전환 시 CR3 유지유사 (system thread)미사용 (항상 pml4_activate)

  • PCID 활용: switch_mm_irqs_off()에서 NOFLUSH_BIT(CR3 bit 63)을 설정해 flush 없이 PCID만 전환하고, 새로운 PCID 할당이 필요할 때만 flush가 발생한다고 설명한다.
  • KPTI (Kernel Page-Table Isolation): Meltdown(CVE-2017-5754)에 대응해 유저 모드에서는 커널 매핑이 최소화된 PML4를 사용하고, syscall/interrupt 진입 시 커널 전용 PML4로 교체한다고 설명한다. CR3 교체 횟수는 늘지만 PCID로 비용을 줄인다.
  • Lazy TLB: 커널 스레드로 전환할 때 CR3를 바꾸지 않는 방식이다. 커널 스레드가 유저 주소를 사용하지 않는다는 전제에서는 이전 프로세스의 유저 TLB가 남아 있어도 해당 주소를 참조하지 않는다.

PintOS

이 문서의 PintOS 설명은 PCID를 사용하지 않는 단순한 모델을 전제로 한다. CR3 전환 경로와 개별 페이지 무효화 경로를 나누어 보면 각 동작의 목적이 드러난다.

컨텍스트 스위치 — process_activate()

제시된 흐름에서는 schedule() → thread_launch() 직전에 이 함수가 호출된다. 새 스레드의 PML4 물리 주소를 CR3에 기록하면 이전 스레드의 non-global 유저 매핑이 무효화되고, 이후 주소 변환은 새 PML4를 기준으로 이루어진다. 이 호출 위치는 실제 PintOS 소스 버전에서 별도로 확인해야 한다.

프로세스 종료 — process_cleanup()

종료 경로에서는 pml4_destroy()보다 먼저 커널 기본 PML4로 전환한다. 현재 CPU가 참조하는 페이지 테이블을 먼저 해제하지 않기 위한 순서다. 이 순서를 지키지 않을 때 triple fault가 발생한다는 설명은 가능한 결과로 제시된 것이며, 이 문서에서 실행으로 재현한 결과는 아니다.

pml4_activate() 구현

pml4가 NULL이면 base_pml4를 사용한다. vtop()은 커널 VA를 물리 주소로 변환하고, lcr3()는 인라인 어셈블리 movq %0, %%cr3로 그 주소를 CR3에 기록한다.

개별 페이지 무효화 — invlpg 사용 패턴

PintOS의 pml4_clear_page(), pml4_set_dirty(), pml4_set_accessed()는 PTE를 수정한 뒤 현재 활성 PML4를 수정한 경우에만 invlpg를 호출한다고 제시되어 있다.

현재 활성 PML4의 매핑을 바꾸면 CPU가 그 VA의 이전 변환을 계속 보유할 수 있으므로 즉시 무효화해야 한다. 다른 프로세스의 PML4를 수정했다면 현재 CPU의 활성 주소 공간이 아니므로 여기서 invlpg를 호출하지 않는다. 이 문서의 모델에서는 해당 프로세스가 다음에 스케줄될 때 CR3 전환으로 TLB가 갱신된다.

QEMU 에뮬레이션

QEMU TCG(Tiny Code Generator) 모드에서는 게스트의 TLB 동작을 소프트웨어로 구현한다고 설명한다. 아래 파일 좌표와 호출 관계는 실제 QEMU 버전에서 검증된 결과가 아니라 확인이 필요한 구현 설명이다.

  • QEMU는 CPUTLBEntry 배열로 게스트 TLB를 시뮬레이션한다. 구조체는 include/exec/cpu-defs.h에 정의되어 있다고 제시되어 있다.
  • MOV CR3 명령이 번역되면 helper_write_crN() (target/i386/tcg/sysemu/misc_helper.c) → tlb_flush() (accel/tcg/cputlb.c)가 호출되어 모든 CPUTLBEntry를 무효화한다고 설명한다.
  • INVLPG 명령은 helper_invlpg() → tlb_flush_page() (accel/tcg/cputlb.c)로 해당 VA 하나를 무효화한다고 설명한다.
  • QEMU의 TLB 크기는 기본 256 엔트리(CPU_TLB_SIZE)이며 실제 CPU보다 작아 flush 비용이 상대적으로 더 크다고 제시되어 있다. 이 수치와 비교는 버전 및 환경별 확인이 필요하다.
  • TCG 번역 캐시(TranslationBlock)도 CR3 변경 시 무효화 대상이 될 수 있다고 설명한다. 주소 공간이 바뀌면 이전 코드 번역의 유효성도 달라질 수 있기 때문이다.
Guest: MOV CR3, RAX
  → TCG IR: call helper_write_crN(env, 3, val)
    → helper_write_crN():
        env->cr[3] = val
        tlb_flush(cs)  // ★ 모든 CPUTLBEntry 무효화
    → 이후 guest 메모리 접근 시 softmmu slow path → x86_cpu_tlb_fill() → PTE walk

Guest: INVLPG [addr]
  → TCG IR: call helper_invlpg(env, addr)
    → tlb_flush_page(cs, addr)  // 해당 VA 1개만 무효화

다음 GDB 스크립트는 CR3 전환과 페이지 단위 무효화를 관찰하기 위한 예시다. 이 문서에는 실행 결과가 포함되어 있지 않다.

CR3 값이 바뀌는 과정

다음 값은 PintOS 컨텍스트 스위치의 동작을 설명하기 위한 예시이며, 실제 실행에서 수집한 값은 아니다.

프로세스 A: pml4 VA = 0x8004200000
            vtop()  = 0x4200000      (KERN_BASE 0x8004000000 차감)
            CR3     = 0x4200000

프로세스 B: pml4 VA = 0x8004201000
            vtop()  = 0x4201000
            CR3     = 0x4201000

schedule() → process_activate(B)
  lcr3(0x4201000)
  → CPU: CR3 ← 0x4201000
  → TLB: 모든 non-global 엔트리 무효화
  → 이후 VA 접근 시 B의 PML4에서 새로 walk

이 예시에서 주소 공간은 A에서 B로 바뀐다. process_activate(B)가 B의 PML4 물리 주소를 CR3에 기록하면 A의 non-global 변환이 무효화된다. 이후 B의 VA에 처음 접근할 때는 B의 PML4를 기준으로 page-table walk가 필요하다.

아래 cold start 계산도 측정 결과가 아니라 주어진 가정을 곱한 예시다.

유저 프로그램 working set = 100 페이지
TLB miss 비용 = ~7 ns/miss (L1 cache hit 가정)
cold TLB 패널티 ≈ 100 × 7 ns = 700 ns

sequenceDiagram
    participant Sched as schedule()
    participant PA as process_activate()
    participant CPU as CPU/MMU
    participant TLB as TLB

    Sched->>PA: process_activate(next)
    PA->>PA: pml4_activate(next->pml4)
    PA->>PA: vtop(next->pml4) → PA

    CPU->>TLB: flush all non-global entries
    TLB-->>TLB: 모든 캐시 엔트리 무효화

    PA->>PA: tss_update(next)
