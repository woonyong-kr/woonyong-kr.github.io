유저 포인터 안전 복사는 왜 별도 규칙이 필요한가

유저 포인터 안전 복사는 왜 별도 규칙이 필요한가

한 줄 요약: 커널은 유저가 넘긴 포인터를 그대로 믿으면 안 된다. NULL·커널 주소·unmapped 주소·page 경계 침범을 걸러내야 유저가 커널 권한을 악용하는 일을 막을 수 있다.

syscall에서 유저 포인터가 위험한 이유

커널이 syscall을 처리할 때는 유저 프로그램이 넘긴 포인터를 그대로 사용해서는 안 된다. 이 포인터는 NULL이거나 커널 영역을 가리킬 수 있다. 주소가 매핑되지 않았거나, 요청한 범위 중 일부만 매핑되어 있을 수도 있다.

커널은 유저 프로그램보다 높은 권한으로 메모리에 접근한다. 따라서 유저 주소를 검증하지 않고 읽거나 쓰면 커널 메모리가 노출되거나 커널이 crash할 수 있다. 유저 포인터 검증은 단순한 입력 검사가 아니라, 유저가 커널 권한을 악용하지 못하도록 막는 경계 검사다.

유저 포인터를 검증하는 두 모델

CPU와 MMU의 규칙 위에서 유저 포인터를 다루는 방법은 크게 두 가지다.

모델방식장점단점
선검증 (Verify-then-use)접근 전에 주소 범위 + PTE 확인구현 단순, fault 없이 실패 반환TOCTOU 취약, page 경계 누락 위험
후처리 (Use-with-fault-handling)접근 시도 후 fault를 잡아 처리race 없음, demand paging과 자연스럽게 통합커널 fault handler 복잡

x86-64 MMU는 PTE의 U/S 비트로 user/kernel 접근을 구분한다. 그러나 커널 모드(CPL=0)에서는 user page도 읽을 수 있다. 커널이 유저 주소에 잘못 접근하더라도 MMU가 항상 자동으로 막아주는 것은 아니다. SMAP/SMEP이 있는 최신 CPU에서는 커널의 유저 접근을 추가로 제한할 수 있다.

Linux와 Windows의 처리 방식

항목LinuxWindows
주요 모델후처리 (copy_from_user/copy_to_user)IRP method (Buffered I/O, Direct I/O, Neither I/O)
메커니즘_ASM_EXTABLE로 fault 복구 주소 등록 → fault 시 오류 반환ProbeForRead/ProbeForWrite + SEH
page 경계fault가 나면 그 시점에 처리, 사전 전체 검사 불필요probe 후 lock/MDL로 page 고정
실패 결과-EFAULT 반환 (프로세스는 계속)STATUS_ACCESS_VIOLATION

Linux는 먼저 주소를 완벽하게 검사해 이후의 fault를 없애는 방식에 의존하지 않는다. 대신 유저 주소에 접근하는 구간을 특별한 위험 구간으로 취급하고, 그 구간에서 발생한 fault를 커널이 통제할 수 있는 결과로 바꾼다.

PintOS의 선검증 흐름

PintOS는 교육용으로 선검증 모델을 기본으로 사용한다. syscall이 버퍼를 받으면 먼저 범위와 각 page를 검사한다. 모든 검사가 끝난 뒤에야 실제 I/O 함수가 버퍼를 사용한다.

sequenceDiagram
    participant U as 유저 프로그램
    participant SC as syscall_handler()
    participant VA as validate_user_buffer()
    participant TC as try_claim_user_addr()
    participant MM as pml4_get_page() / spt_find_page()
    participant IO as file_write() / putbuf()

    U->>SC: write(fd, buffer=0x8048ff0, size=0x30)
    SC->>VA: validate_user_buffer(buffer, size, false, f)
    VA->>VA: buffer != NULL, size > 0, no overflow
    loop 각 page base
        VA->>TC: validate_user_addr(addr, write, f)
        TC->>TC: addr != NULL, is_user_vaddr(addr)
        TC->>MM: user_page_accessible(curr, addr, write)
        alt PTE present + 권한 OK
            MM-->>TC: true
        else PTE 없음 → SPT 조회 / stack growth
            TC->>MM: vm_claim_page() 또는 vm_try_handle_fault()
            MM-->>TC: true/false
        end
        TC-->>VA: true/false (false면 exit(-1))
    end
    VA-->>SC: 모든 page 검증 완료
    SC->>IO: file_write(file, buffer, size)

try_claim_user_addr()는 주소 하나를 세 단계로 검사한다.

첫 단계에서는 NULL과 커널 영역 주소를 거부한다. 두 번째 단계에서는 PML4를 따라가 PTE가 존재하는지 확인하고, 쓰기 접근이라면 PTE_W 권한도 검사한다. VM이 활성화된 경우에는 세 번째 단계에서 SPT를 조회한다. 대상 page를 찾으면 claim하고, 필요한 경우 stack growth를 시도한다.

주소 하나만 검사해서는 버퍼 전체가 안전하다고 판단할 수 없다. 버퍼의 시작 주소가 유효해도 범위가 다음 page로 넘어갈 수 있기 때문이다. validate_user_buffer()는 버퍼가 걸치는 모든 page base를 순회하며 각각을 검사한다.

page 경계를 계산하는 방법

위 버퍼는 시작 page의 마지막 16 bytes와 다음 page의 첫 32 bytes를 사용한다. 따라서 두 page가 모두 유효해야 전체 48 bytes에 안전하게 접근할 수 있다.

커널 주소를 차단하는 방법

is_user_vaddr()는 주소가 KERN_BASE보다 작은지 확인한다. 경계와 같거나 그보다 큰 주소는 유저 주소로 인정하지 않는다.

세 가지 실패 유형

PintOS가 막아야 하는 입력은 다음 세 유형으로 볼 수 있다.

  • write(1, NULL, 5)처럼 NULL 또는 unmapped 주소가 들어오면 try_claim_user_addr()의 addr == NULL 검사나 매핑 검사에서 실패한다.
  • read(fd, 0xffff800000000000, 8)처럼 커널 주소가 들어오면 !is_user_vaddr(addr) 검사에서 실패한다.
  • write(1, 0x8048ff0, 0x30)처럼 버퍼 일부만 매핑되어 있으면 첫 page가 유효하더라도 다음 page 검사에서 실패한다.

세 경우 모두 validate_user_addr()가 실패를 확인하면 exit(-1)로 이어진다.

검증을 빠뜨렸을 때 QEMU에서 보이는 일

QEMU는 check_address()나 validate_user_buffer()의 존재를 알지 못한다. QEMU가 재현하는 것은 guest CPU가 실행하는 명령어와 page table의 효과다.

PintOS의 선검증이 성공하면 guest 코드는 정상적으로 계속 실행된다. 반대로 검증하지 않은 커널 코드가 잘못된 유저 주소를 실제로 읽으면 QEMU MMU가 PML4 walk를 수행한다. PTE가 없거나 권한을 위반하면 page fault가 발생하고 guest의 page_fault()로 진입한다.

이때 error code를 보면 fault가 커널 모드의 읽기 또는 쓰기에서 발생했는지 구분할 수 있다.

GDB로 검증 흐름 관찰하기

다음 스크립트는 각 검증 지점에 breakpoint를 두고 전달된 주소와 판단 경로를 관찰하는 데 사용한다. 아래에 적힌 출력은 스크립트가 확인하려는 대상이며, 실제 실행 결과를 뜻하지는 않는다.

1) validate_user_buffer 호출 추적

write(1, 0x8048ff0, 0x30) 호출에서 buffer, size, page 수를 확인한다.

2) try_claim_user_addr 단계별 판단 추적

이 breakpoint에서는 주소가 NULL인지, KERN_BASE 이상인지, PTE 확인으로 진행하는지를 구분한다.

3) page 경계 순회 확인

계산된 시작 page부터 버퍼의 끝까지 어떤 page base를 순회하는지 확인한다.

4) 검증 실패 시 exit(-1) 추적

validate_user_addr()에 들어온 주소와 이후의 thread_exit를 함께 관찰한다. thread_exit 출력만으로 원인을 확정하지 않고, 앞선 검증 흐름과 연결해 판단해야 한다.

5) 커널 주소 주입 공격 시뮬레이션 관찰

read(fd, 커널주소, 8)와 같은 호출에서 is_user_vaddr에 전달된 주소가 경계를 넘는지 관찰한다.

6) VM 모드에서 lazy page claim 관찰

PTE가 없는 주소가 SPT 조회와 vm_claim_page 경로로 이어지는지 관찰한다.

Linux와 PintOS의 차이

두 운영체제는 유저 주소를 위험한 입력으로 다루지만, fault를 통제하는 시점과 실패 결과가 다르다.

항목LinuxPintOS
검증 모델후처리 (fault 기반)선검증 (접근 전 확인)
핵심 함수copy_from_user() / copy_to_user()validate_user_buffer() / try_claim_user_addr()
fault 처리_ASM_EXTABLE → 복구 주소로 점프 → -EFAULT 반환page fault handler에서 kernel mode fault → PANIC (검증 빼먹으면)
TOCTOUrace 면역 (fault 시점에 판단)선검증은 TOCTOU 가능하나 PintOS는 단일 CPU + 인터럽트 비활성화로 회피
page 경계fault 나면 그 page만 처리사전에 모든 page base를 순회
SMAP/SMEPCR4 비트로 커널의 유저 접근 차단, stac/clac로 일시 허용미적용 (x86-64 SMAP 미사용)
VM 연동fault → handle_mm_fault() → page table 설치try_claim → spt_find_page → vm_claim_page
실패 결과-EFAULT (프로세스 계속)exit(-1) (프로세스 종료)
SMP 고려다른 CPU에서 munmap 가능 → 후처리 필수단일 CPU, race 없음

Linux는 실제 접근 시점의 fault를 복구 가능한 오류로 바꾼다. PintOS는 접근 전에 모든 page를 검사하고, 검증 실패 시 해당 프로세스를 종료한다. 따라서 PintOS에서 선검증을 빠뜨린 채 커널이 잘못된 주소에 접근하면 kernel mode page fault로 이어질 수 있다.
