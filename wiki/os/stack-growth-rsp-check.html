Stack Growth RSP 근처 Fault 판단

Stack Growth RSP 근처 Fault 판단

확인 범위: 이 문서는 page fault 기반 스택 확장의 일반 원리와 판단 기준을 설명하고, Linux·Windows·PintOS 및 QEMU 동작은 입력 본문에 제시된 구현과 코드 좌표를 바탕으로 구분해 다룬다. 구체적인 상수·함수 위치·실행 흐름·성능이나 실제 동작 여부는 해당 코드 버전과 GDB·QEMU 실행 기록을 별도로 확인해야 하며, 본문 자체를 특정 환경의 검증 결과로 간주하지 않는다.

한 줄 요약: 유저 스택은 고정 크기가 아니라 page fault로 동적 확장되며, fault 주소가 RSP-8 이상이면서 USER_STACK 아래 허용 범위 안인지로 정당한 스택 확장과 잘못된 접근을 가른다.

Stack Growth RSP 근처 상태

유저 스택은 고정 크기가 아니라 page fault를 통해 동적으로 확장된다. 모든 page fault가 스택 확장은 아니므로, fault 주소가 현재 RSP 근처인지 판단하는 기준이 필요하다. x86-64에서 push, call, PUSHA 등의 명령이 RSP 아래 최대 8바이트까지 접근할 수 있고, sub rsp, N + 접근 패턴에서는 RSP보다 한참 아래를 건드릴 수 있으므로, 일반적으로 fault 주소가 RSP - 8 이상이면서 USER_STACK 아래의 허용 범위 안에 있으면 스택 확장으로 판단한다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

x86-64 CPU는 스택 확장을 하드웨어 수준에서 자동으로 하지 않는다. MMU는 단지 매핑이 없는 주소에 접근하면 pf(Page Fault)를 발생시킬 뿐이다. OS가 fault handler에서 다음을 결정한다:

  1. fault 주소가 스택 영역인가?
  2. 유효한 스택 접근 패턴인가 (RSP 근처인가)?
  3. 스택 최대 크기를 초과하지 않는가?

하드웨어가 제공하는 정보는 CR2(fault 주소)와 intr_frame::rsp(fault 시점의 스택 포인터)뿐이다.

실제 OS (Linux)

Linux는 vm_area_struct의 VM_GROWSDOWN 플래그로 스택 VMA를 표시한다. Page fault 시 expand_stack()이 호출되어 fault 주소가 현재 VMA 시작 주소 아래이지만 RSP - 65536(또는 아키텍처별 값) 이상이면 스택을 확장한다. RLIMIT_STACK(기본 8 MB)으로 최대 크기를 제한한다.

핵심 판단 기준:

조건이유
fault_addr >= rsp - 32push는 RSP-8, sub rsp, N + 접근은 더 아래를 건드릴 수 있음. 32바이트 여유는 PUSHA 등 다중 push 패턴과 테스트 호환성을 위한 마진
fault_addr < USER_STACK스택은 USER_STACK(0x47480000)에서 아래로 자란다
fault_addr >= USER_STACK - STACK_MAXSTACK_MAX = 1 MB = 0x100000, 스택 최대 크기 제한

커널 fault에서 user_rsp를 쓰는 이유: syscall 진입 시 f->rsp는 커널 스택의 RSP다. 유저 RSP는 syscall-entry.S(line 9)에서 %rbx에 저장한 뒤, syscall_handler에서 thread_current()->user_rsp(thread.h:153)에 보관한다. 커널 코드가 유저 포인터를 역참조하다 fault가 나면, 유저 스택 기준으로 판단해야 하므로 user_rsp를 사용한다.

vm_stack_growth()(vm/vm.c:366)는 현재 stack_bottom에서 pg_round_down(addr)까지 여러 페이지를 한 번에 할당할 수 있다:

stack_bottom(thread.h:154)은 현재 스택이 매핑된 가장 낮은 주소를 추적한다. 초기값은 USER_STACK - PGSIZE(setup_stack에서 첫 페이지 할당 후).

Stack Growth RSP 근처 값 추적

USER_STACK = 0x47480000 (약 1.18 GB)
최대 스택 = 1 MB = 0x100000
스택 하한 = USER_STACK - 1MB = 0x47480000 - 0x100000 = 0x47380000

예시 1: push (RSP = 0x47477FF0)
  push rax → addr = RSP - 8 = 0x47477FE8
  0x47477FE8 >= 0x47477FF0 - 32 = 0x47477FD0  ✓
  0x47477FE8 < 0x47480000                       ✓
  0x47477FE8 >= 0x47380000                      ✓
  → 스택 확장 허용

예시 2: sub rsp, 128 + 접근 (RSP = 0x47477FF0)
  sub rsp, 128 → RSP = 0x47477F70 (RSP 자체는 fault 안 남)
  mov [rsp], rax → addr = 0x47477F70
  0x47477F70 >= 0x47477FF0 - 32 = 0x47477FD0?  ✗
  → segfault (rsp - 32 범위를 초과)
  ※ 단, 이 경우 sub rsp 후 RSP가 이미 갱신되었으므로
    실제 판단은: 0x47477F70 >= 0x47477F70 - 32 = 0x47477F50 ✓
    → 스택 확장 허용 (RSP가 sub 이후 값이 기준)

예시 3: 임의 주소 0x40000000 접근 (RSP = 0x47477FF0)
  0x40000000 >= 0x47477FF0 - 32 = 0x47477FD0?  ✗
  → segfault (스택이 아닌 잘못된 접근)

페이지 단위: 스택은 한 번에 4 KB 단위로 확장된다. pg_round_down(0x47477FE8) = 0x47477000. vm_stack_growth()는 현재 stack_bottom에서 타겟 페이지까지 여러 페이지를 한 번에 할당할 수 있다.

QEMU 에뮬레이션

QEMU TCG에서 pf(Page Fault) 예외는 do_interrupt_x86_hardirq() → do_interrupt_all() → do_interrupt64()를 통해 처리된다. fault 주소는 CPUX86State::cr[2](CR2 레지스터)에 저장되며, PintOS의 page_fault() handler가 이 값을 f->rsp와 함께 읽어 스택 확장 여부를 판단한다.

단계TCG 동작효과
1guest 코드가 매핑 없는 주소 접근cpu_x86_tlb_fill() 실패 → raise_exception_err_ra()
2do_interrupt64()IDT 0xE(#PF) 벡터 참조, IST/RSP0로 스택 전환
3CPU가 error code pushenv->error_code에 W/U/P 비트 기록
4env->cr[2] = fault_addrCR2에 fault 주소 저장
5RIP → PintOS page_fault()handler가 CR2, RSP 읽어 스택 확장 판단

GDB에서 스택 확장 fault 관찰 (4단계):

  1. b vm_should_grow_stack — 스택 확장 판단 함수에 breakpoint
  2. p/x fault_addr — fault 주소 확인 (CR2에서 전달된 값)
  3. p/x rsp — 현재 유저 RSP 확인 (user fault면 f->rsp, kernel fault면 user_rsp)
  4. fault_addr >= rsp - 32 인지 직접 계산하여 스택 확장 허용 여부 확인

추가 관찰: p/x $cr2로 QEMU GDB stub을 통해 CR2 값을 직접 확인할 수 있다. info registers에서 CR2는 마지막 page fault의 fault 주소를 항상 보존한다.
