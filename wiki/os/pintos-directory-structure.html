PintOS 디렉터리 구조

PintOS 디렉터리 구조

한 줄 요약: threads·userprog·vm·filesys·devices 등 서브시스템별로 나뉜 PintOS 소스 트리 구조.

PintOS 소스 트리를 읽는 법

PintOS 소스 트리는 OS의 핵심 서브시스템에 따라 디렉터리를 나눈다. 주요 디렉터리는 커널 코어를 담은 threads/, 유저 프로그램을 지원하는 userprog/, 가상 메모리를 구현하는 vm/, 파일 시스템을 다루는 filesys/, 하드웨어 드라이버가 모인 devices/, 공용 라이브러리를 제공하는 lib/, 헤더를 분리한 include/다.

이 구분은 PintOS 프로젝트 1~4의 진행 순서와 직접 대응한다. 프로젝트가 진행되면 주요 수정 범위도 threads/에서 userprog/, vm/, filesys/ 순으로 확장된다.

전체 트리 구조

%% PintOS 전체 트리 구조
flowchart TD
  root["pintos/"]
  root --> threads["threads/<br/>부트·스레드·동기화·MMU"]
  root --> userprog["userprog/<br/>process·syscall·exception·TSS"]
  root --> vm["vm/<br/>SPT·frame·swap·mmap"]
  root --> filesys["filesys/<br/>inode·directory·FAT"]
  root --> devices["devices/<br/>timer·disk·keyboard·serial"]
  root --> lib["lib/<br/>kernel/user 공용 자료구조"]
  root --> include["include/<br/>소스 트리와 대칭인 계약"]

이 밖의 최상위 디렉터리에는 테스트 코드를 담은 tests/, PintOS 실행 스크립트 등을 포함한 호스트 유틸리티가 있는 utils/, 빌드 도구를 모은 tools/가 있다.

threads/ — 커널의 기반

threads/는 OS 부트, 스레드 관리, 동기화, 페이지 할당, 인터럽트 처리를 담당한다. 다른 서브시스템이 의존하는 기반 코드도 이 디렉터리에 모여 있다.

파일줄 수(약)역할프로젝트
init.c300main() — 커널 진입점, 서브시스템 초기화 순서 결정-
thread.c800struct thread, thread_create(), schedule(), do_schedule()P1
synch.c450semaphore, lock, condition variableP1
palloc.c250페이지 할당자 — kernel pool / user pool 비트맵P3
malloc.c300힙 할당자 — arena + descriptor-
mmu.c200PML4 page table 생성/조작 (pml4_set_page, pml4_get_page)P3
interrupt.c400IDT 설정, intr_register_ext(), intr_handler()-
start.S5064비트 모드 전환, BSS 초기화, main() 점프-
loader.S100디스크에서 커널 적재 (BIOS → protected mode → long mode)-
kernel.lds.S50링커 스크립트 — 섹션 배치 (text, data, bss)-
intr-stubs.S200인터럽트 엔트리 스텁 256개 (어셈블리 매크로)-

init.c의 초기화 흐름은 다음과 같다.

%% init.c 초기화 순서
flowchart TD
  main["init.c::main()"] --> thread_init["thread_init()"]
  thread_init --> memory["palloc_init() → malloc_init() → paging_init()"]
  memory --> cpu["tss_init() → gdt_init() → intr_init()"]
  cpu --> devices_init["timer_init() → disk_init()"]
  devices_init --> filesys_init["filesys_init()"]
  filesys_init --> thread_start["thread_start()"]
  thread_start --> actions["run_actions()"]

main()은 thread_init() → console_init() → palloc_init() → malloc_init() → paging_init() → tss_init() → gdt_init() → intr_init() → timer_init() → disk_init() → filesys_init() → thread_start() → run_actions() 순으로 초기화를 진행한다. 마지막 단계인 run_actions()에서 테스트 또는 유저 프로그램을 실행한다.

userprog/ — 유저 영역과 커널의 경계

userprog/는 프로세스의 생명주기인 fork/exec/wait/exit를 관리한다. 시스템 콜과 exception을 처리하고, 유저 영역과 커널 사이의 전환 메커니즘도 담당한다.

파일줄 수(약)역할프로젝트
process.c600process_fork(), process_exec(), process_wait(), process_exit(), load()P2, P3
syscall.c400syscall_handler() — syscall 번호별 분기, fd 연산P2
syscall-entry.S30syscall 명령어 진입점 — MSR LSTAR에 등록P2
exception.c100page_fault() — pf → vm_try_handle_fault() 전달P2, P3
tss.c50tss_update() — rsp0 갱신 (커널 스택 전환)P2
gdt.c50GDT 설정 — 커널/유저 코드/데이터 세그먼트-

유저 프로그램의 시스템 콜은 다음 경로를 따른다.

%% 유저 프로그램 syscall 호출 체인
flowchart TD
  user["lib/user syscall wrapper<br/>RAX=SYS_*, 인자 register"]
  entry["syscall-entry.S<br/>LSTAR 진입·커널 stack"]
  handler["syscall_handler()<br/>f-&gt;R.rax 분기"]
  process["process_fork/exec/wait"]
  file["fd lookup → file_read/write"]
  user -->|syscall| entry --> handler
  handler --> process
  handler --> file

syscall-entry.S는 MSR LSTAR가 가리키는 syscall 진입점이다. 이 진입점을 거치면 syscall_handler()가 시스템 콜 번호에 따라 처리 경로를 나눈다. 예를 들어 SYS_FORK는 process_fork(), SYS_EXEC는 process_exec(), SYS_WAIT는 process_wait()로 이어진다. SYS_WRITE는 파일 디스크립터 테이블을 조회한 뒤 file_write()를 호출한다.

vm/ — 가상 메모리 엔진

vm/는 Supplemental Page Table(SPT)과 demand paging을 관리한다. anonymous page와 swap, file-backed page와 mmap, stack growth, frame eviction도 이 영역에 속한다.

파일줄 수(약)역할프로젝트
vm.c500SPT 관리, vm_try_handle_fault(), vm_do_claim_page(), vm_evict_frame()P3
anon.c200anonymous page — anon_swap_in(), anon_swap_out(), swap slot 관리P3
file.c200file-backed page — file_backed_swap_in(), file_backed_swap_out(), mmap/munmapP3
uninit.c100UNINIT page — uninit_initialize(), lazy loading 첫 fault 처리P3
inspect.c50디버깅용 — 가상 주소의 물리 프레임 검사P3

page type은 함수 포인터 테이블을 통해 다음과 같은 계층을 이룬다.

%% struct page와 page_operations 관계
flowchart TD
  page["struct page<br/>union {<br/>struct uninit_page uninit;<br/>struct anon_page anon;<br/>struct file_page file;<br/>}<br/>struct page_operations *operations;"]
  operations["struct page_operations<br/>swap_in()<br/>swap_out()<br/>destroy()"]

filesys/ — 파일 시스템

filesys/는 FAT 기반 파일 시스템을 구현한다. inode와 디렉터리를 관리하며 파일 읽기와 쓰기를 처리한다.

파일줄 수(약)역할프로젝트
filesys.c150filesys_open(), filesys_create(), filesys_remove()P2, P4
inode.c400inode_read_at(), inode_write_at() — FAT 체인 따라 읽기/쓰기P4
fat.c300FAT 테이블 — fat_get(), fat_put(), fat_create_chain()P4
directory.c250디렉터리 엔트리 검색, 생성, 삭제P4
file.c150struct file — file_read(), file_write(), deny_write 관리P2
free-map.c100초기 디스크 블록 할당 (FAT 도입 전 레거시)-
page_cache.c50버퍼 캐시 스켈레톤 (P4 선택 구현)P4

devices/ — 하드웨어 추상화의 최소 구성

devices/에는 PintOS가 다루는 하드웨어의 드라이버가 모여 있다. 각 드라이버는 QEMU가 에뮬레이트하는 장치에 대응한다.

파일QEMU 장치I/O 포트역할
timer.ci8254 PIT0x40~0x43100 Hz tick, timer_interrupt()
disk.cIDE controller0x1F0~0x1F7섹터 단위 read/write, disk_read(), disk_write()
kbd.ci8042 keyboard0x60, 0x64키보드 입력
vga.cVGA text mode0xB8000 (메모리 매핑)80x25 텍스트 출력
serial.c16550 UART0x3F8시리얼 포트 (GDB 연결용)
intq.c--interrupt queue (kbd/serial 공용 버퍼)
input.c--키보드 입력 통합

lib/ — 커널과 유저가 공유하는 라이브러리

lib/에는 커널과 유저 영역에서 공통으로 사용하는 유틸리티가 있다.

경로주요 파일역할
lib/string.c, stdio.c, stdlib.cmemcpy, snprintf, atoi 등
lib/arithmetic.c, random.c64비트 나눗셈, 의사 난수
lib/kernel/console.c, bitmap.c, hash.c, list.c커널 전용: 콘솔, 비트맵, 해시 테이블, 이중 연결 리스트
lib/user/syscall.c, console.c유저 전용: syscall wrapper (fork(), write() 등)

lib/kernel/list.c는 PintOS 전역에서 사용하는 침투적 리스트(Intrusive List)를 구현한다. list_elem을 구조체 내부에 임베드하고 list_entry() 매크로로 컨테이너를 역참조하므로 malloc 없이 리스트를 조작할 수 있다.

include/ — 소스 구조와 대칭인 헤더 트리

include/는 소스 디렉터리와 같은 구조로 헤더를 분리한다.

경로주요 헤더역할
include/threads/thread.hstruct thread스레드 구조체 정의
include/threads/synch.hstruct lock, semaphore, condition동기화 프리미티브
include/threads/vaddr.hKERN_BASE, PHYS_BASE가상 주소 상수
include/threads/pte.hPTE 비트 마스크page table entry 비트 연산
include/userprog/process.hprocess_fork/exec/wait/exit프로세스 API
include/vm/vm.hstruct page, page_operationsVM 핵심 타입
include/lib/syscall-nr.hSYS_HALT, SYS_FORK 등syscall 번호 열거

실제 OS인 Linux와 비교하기

%% Linux 6.x 소스 트리와 PintOS 디렉터리 비교
flowchart TD
  linux["Linux"] --> kernel["kernel/ + arch/x86/<br/>scheduler·syscall·interrupt"]
  linux --> mm["mm/<br/>VMA·page fault·reclaim"]
  linux --> fs["fs/<br/>VFS와 여러 filesystem"]
  linux --> drivers["drivers/<br/>다양한 hardware"]
  pintos["PintOS"] --> pthreads["threads/ + userprog/"]
  pintos --> pvm["vm/"]
  pintos --> pfs["filesys/"]
  pintos --> pdevices["devices/"]
  kernel -. 대응 .-> pthreads
  mm -. 대응 .-> pvm
  fs -. 대응 .-> pfs
  drivers -. 대응 .-> pdevices

PintOS와 Linux의 큰 구조적 차이는 threads/의 범위에서 드러난다. Linux는 스케줄링을 kernel/sched/에, 메모리를 mm/에 두어 두 영역을 완전히 분리한다. PintOS에서는 Linux의 kernel/과 mm/ 일부에 해당하는 코드가 threads/에 함께 있으며, thread.c와 palloc.c도 같은 디렉터리에 놓인다.

source snapshot을 거칠게 비교하면 Linux mm/는 PintOS 메모리 코드보다 약 10배 이상 복잡하고, fs/는 30개 이상의 파일 시스템 구현을 담는다. drivers/는 약 2,000배 규모로 표현되며 전체 source의 약 60%를 차지한다고 설명한다. 다만 이 값은 Linux version과 집계 방식에 따라 달라지므로 고정 통계가 아니라 교육용 규모 비교로만 사용해야 한다.

상위 디렉터리 수준에서 보면 Linux kernel/은 PintOS threads/와 userprog/에 대응한다. mm/은 vm/과 palloc에, fs/는 filesys/에, drivers/는 devices/에 대응한다. arch/x86/은 start.S와 loader.S 같은 아키텍처 의존 코드에 해당하며, include/와 lib/는 각각 같은 이름의 PintOS 디렉터리와 대응한다. Linux에서 네트워크 스택을 담는 net/에 해당하는 디렉터리는 PintOS에 없다.
