info registers = guest CPU 상태

범위: 이 문서는 GDB의 info registers가 QEMU가 유지하는 guest CPU 상태를 표시한다는 개념과 일반적인 판독 기준을 설명한다. 코드 좌표, 패킷 크기·레지스터 순서, 주소·레지스터 예시와 세부 동작은 특정 QEMU·PintOS 구현 및 실행 환경에서 검증된 결과가 아니므로, 실제 적용 시 해당 코드·버전·실행 기록과 측정을 통해 별도로 확인해야 한다.

한 줄 요약: GDB info registers가 호스트가 아니라 QEMU가 소프트웨어로 유지하는 guest CPU 상태(CPUX86State)를 보여준다는 점.

info registers = guest 상태

PintOS 디버깅에서 GDB의 info registers(줄여서 i r) 명령어는 호스트 CPU가 아니라 QEMU가 소프트웨어로 유지하는 guest CPU 상태를 보여준다. 이 값들은 CPUX86State 구조체의 필드에서 읽어오며, 물리 CPU 레지스터와는 무관하다. 이 사실을 모르면 “레지스터 값이 이상하다”를 하드웨어 문제로 착각할 수 있다.

상세 설명

추상 개념 (레지스터 읽기의 두 경로)

물리 하드웨어에서 디버거가 레지스터를 읽는 경로와 QEMU에서의 경로는 근본적으로 다르다:

환경레지스터 읽기 방법소스
물리 CPU + JTAG디버그 포트로 CPU halt → 레지스터 버스 읽기실제 하드웨어 레지스터
KVM VMVM exit → VMCS에서 guest 레지스터 추출하드웨어 VMCS 영역
QEMU TCG (PintOS)GDB stub → CPUX86State.regs[] 필드 읽기C 구조체 메모리

PintOS는 세 번째 경로다. info registers를 치면 QEMU 프로세스 내부의 C 구조체를 읽는 것이다.

GDB Remote Protocol 흐름

사용자: (gdb) info registers
   ↓
GDB: $g#67 패킷 전송 (TCP localhost:1234)
   ↓
QEMU gdbstub.c: cpu_gdb_read_register() 호출
   ↓
QEMU: CPUX86State에서 레지스터 값을 hex 문자열로 인코딩
   ↓
QEMU → GDB: $<hex values>#<checksum>
   ↓
GDB: 값을 파싱하여 표 형태로 출력

g 패킷이 반환하는 레지스터 순서는 GDB의 x86-64 target description에 의해 고정된다:

실제 OS (Linux)에서의 비교

Linux + KVM 환경에서 virsh나 crash utility로 VM의 레지스터를 볼 때도 원리는 같다:

  • KVM: guest 레지스터가 VMCS(Virtual Machine Control Structure)에 저장되어 있고, VM exit 시 호스트가 읽을 수 있다
  • QEMU/KVM: kvm_get_regs() 시스템 콜로 VMCS에서 값을 가져온다
  • 순수 QEMU(PintOS): VMCS 없이 CPUX86State C 구조체에서 직접 읽는다

두 경우 모두 GDB에게 보여주는 인터페이스는 동일한 Remote Serial Protocol이다.

QEMU 에뮬레이션

GDB가 breakpoint에서 멈출 때 일어나는 일:

1. QEMU TCG 실행 루프가 breakpoint 주소 감지
2. cpu_handle_guest_debug() → vCPU 실행 중단
3. gdb_handlesig() → GDB에게 SIGTRAP 보고
4. GDB가 info registers 요청 → gdb_read_register() 호출
5. CPUX86State.regs[0..15], eip, eflags를 hex로 인코딩하여 전송

QEMU는 breakpoint를 guest 코드에 int3 (0xCC)를 삽입하는 소프트웨어 방식으로 구현한다. 하드웨어 breakpoint(DR0~DR3)도 에뮬레이션하지만 PintOS 디버깅에서는 소프트웨어 방식이 기본이다.

struct intr_frame과의 관계

PintOS에서 인터럽트/syscall 진입 시 레지스터를 struct intr_frame에 스냅샷한다. 이 스냅샷과 info registers의 차이:

시점info registersstruct intr_frame
인터럽트 진입 직후현재 CPU 상태 (커널)인터럽트 직전 상태 (유저)
schedule() 직후새 스레드의 상태이전 스레드가 저장한 상태
용도실시간 디버깅문맥 복원용

info registers는 “지금 이 순간”이고, struct intr_frame은 “저장된 과거”다.

info registers = guest 값 추적

GDB Remote Protocol g 패킷의 실제 바이트 예:

GDB 전송:  $g#67     (3 byte + TCP 오버헤드)
QEMU 응답: $<328 hex chars>#<2 hex checksum>  (약 333 byte)

RAX = 0x000000000000000a 일 때 hex 인코딩:
→ 리틀엔디안으로 "0a00000000000000" (16 hex chars = 8 bytes)

전체 범용 레지스터 16개: 16 × 16 = 256 hex chars
RIP: 16 hex chars
EFLAGS: 8 hex chars
세그먼트 6개: 6 × 8 = 48 hex chars
총: 328 hex chars = 164 raw bytes

특정 레지스터만 읽기:

(gdb) info register rax      ← RAX만
(gdb) info register rip rsp  ← RIP과 RSP만
(gdb) p/x $rax               ← RAX를 hex로
(gdb) p $eflags              ← EFLAGS를 symbolic으로 (IF ZF PF 등)
