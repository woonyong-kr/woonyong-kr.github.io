thread_launch() — register 저장과 스레드 전환

thread_launch() — register 저장과 스레드 전환

확인 범위: 이 문서는 컨텍스트 전환과 레지스터 저장·복원의 일반 원리를 바탕으로 PintOS thread_launch()의 구현 흐름을 설명한다. 구체적인 오프셋과 Linux·QEMU 비교, 실행 상태 및 성능에 관한 판단은 해당 코드·버전과 실제 실행 기록 또는 측정을 확인해야 하는 구현별 검증 사항이다.

thread_launch()는 스케줄러가 고른 다음 스레드로 넘어가기 위해, 현재 레지스터를 intr_frame에 저장하고 다음 스레드의 intr_frame을 do_iret()로 복원한다.

thread_launch() 상태

PintOS의 스케줄러가 다음 스레드를 고르면 thread_launch()가 실제 실행 흐름을 넘긴다. 이 함수는 현재 스레드의 레지스터 상태를 자신의 struct intr_frame(tf)에 저장한 뒤, 다음 스레드의 tf를 do_iret()로 복원한다. 현재 실행 상태를 스스로 저장하려면 레지스터를 사용하는 도중에도 원래 값을 보존해야 하므로, 함수 전체가 인라인 어셈블리로 구현되어 있다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

Context switch가 일어나면 CPU가 사용하던 레지스터 세트도 현재 스레드의 것에서 다음 스레드의 것으로 바뀌어야 한다. CPU에는 실행에 사용할 레지스터 세트가 하나뿐이므로, 먼저 현재 값을 이전 스레드의 메모리 저장 영역에 쓰고 다음 스레드의 저장 영역에서 값을 읽어 CPU에 로드한다.

  1. 현재 레지스터 값을 메모리(이전 스레드의 저장 영역)에 쓴다.
  2. 다음 스레드의 저장 영역에서 레지스터 값을 읽어 CPU에 로드한다.

이 과정에는 “현재 레지스터를 저장하려면 레지스터를 사용해야 한다”는 부트스트랩 문제가 있다. thread_launch()는 일부 레지스터를 스택에 먼저 보관한 뒤 저장용 포인터로 재사용하고, 나중에 원래 값을 꺼내 저장한다. 이런 저장 순서는 어셈블리에서 세밀하게 제어한다.

x86-64에서는 iretq 명령어가 스택에서 RIP, CS, EFLAGS, RSP, SS를 한 번에 복원한다. PintOS는 이 복원 형식에 맞춰 레지스터 상태를 struct intr_frame 레이아웃에 저장한다.

실제 OS (Linux/Windows)

PintOS의 방식을 실제 OS와 비교하면, 왜 thread_launch()가 모든 레지스터를 struct intr_frame에 담는지 더 분명해진다. 아래 비교에서 Linux의 context switch는 __switch_to() (arch/x86/kernel/process_64.c)를 기준으로 한다. Linux는 callee-saved 레지스터(rbx, rbp, r12-r15)만 저장한다. 나머지는 커널 진입 시 이미 pt_regs에 저장되어 있으므로 전환 과정에서 추가로 다룰 상태가 줄어든다.

반면 PintOS는 모든 레지스터를 struct intr_frame 형태로 저장하는 단순한 방식을 쓴다. 교육용 구조를 따라가기 쉽지만, 이 문서의 비교 기준에서는 Linux보다 저장하고 복원하는 상태가 많다.

Linux가 callee-saved만 추가로 저장할 수 있는 것은 context switch가 커널 코드 안에서 일어나기 때문이다. 커널 진입(syscall/interrupt) 시 caller-saved 레지스터는 이미 pt_regs에 저장되어 있고, 이후에는 C ABI가 보장하는 callee-saved 레지스터를 보존하면 된다.

PintOS 구현

thread_launch()는 threads/thread.c에 있으며, 전체가 하나의 인라인 어셈블리 블록이다.

함수 시그니처와 호출 위치

schedule() 함수의 마지막에서 thread_launch(next)로 호출된다. 이 시점에:

  • 인터럽트는 OFF 상태
  • thread_current()->status는 이미 READY 또는 BLOCKED 또는 DYING으로 변경됨
  • next->status는 THREAD_RUNNING으로 설정됨
  • thread_ticks는 0으로 리셋됨

어셈블리 분석

코드의 핵심 흐름을 단계별로 분석한다.

준비 단계:

1단계: scratch 레지스터 확보

rax를 포인터로, rcx를 다음 tf 주소로 사용하기 위해 먼저 push해 원래 값을 보존한다.

2단계: 범용 레지스터 저장 (tf_cur→R에)

r15부터 rdx까지 12개 레지스터를 tf_cur의 gp_registers 영역에 직접 저장한다.

3단계: push했던 rcx, rbx, rax 복구 후 저장

스택에 push한 순서(rax→rbx→rcx)의 역순(rcx→rbx→rax)으로 pop해 원래 값을 tf에 저장한다.

4단계: 세그먼트 레지스터 저장

5단계: 복귀 주소(RIP) 저장

call __next; pop %%rbx 트릭은 현재 RIP를 얻는 관용적 x86 패턴이다. 여기에 out_iret - __next 오프셋을 더해 out_iret 레이블의 주소를 계산한다. 이렇게 하면 나중에 이 스레드로 돌아왔을 때 out_iret: 에서 실행이 재개된다.

6단계: CS, EFLAGS, RSP, SS 저장

7단계: 다음 스레드로 전환

do_iret()는 다음 스레드의 tf에서 모든 레지스터를 복원하고 iretq로 점프한다. 이 call은 “return하지 않는 call”이다. 현재 스레드 관점에서는 do_iret 호출 이후 시간이 멈추고, 나중에 다른 스레드가 이 스레드를 다시 thread_launch()로 전환해주면 out_iret: 레이블에서 실행이 재개된다.

전체 흐름 요약

QEMU 에뮬레이션

QEMU는 thread_launch()의 인라인 어셈블리를 어떻게 실행하는가?

TCG 번역 관점:

  • thread_launch()의 어셈블리 전체가 하나의 basic block이 아니다. call __next와 call do_iret에서 Translation Block 경계가 생긴다.
  • push, movq, pop 같은 일반 명령어는 TCG IR로 번역되어 호스트에서 빠르게 실행된다.
  • 핵심 전환은 iretq (do_iret 내부). TCG의 gen_helper_iret_protected가 guest ring 전환, 스택 교체, RFLAGS 복원을 모두 에뮬레이션한다.

call __next; pop %%rbx 패턴의 TCG 처리:

  • call __next는 TCG에서 return address를 guest 스택에 push하고 __next로 jump하는 코드로 번역된다.
  • pop %%rbx는 방금 push된 return address를 꺼내 guest rbx에 넣는다.
  • 이 패턴은 position-independent code에서 현재 RIP를 얻기 위해 사용하며, TCG에서 정확히 재현된다.

TB 무효화와 context switch:

  • thread_launch()에서 tf에 레지스터를 저장하는 것은 일반 메모리 쓰기다. TB cache에 영향 없다.
  • do_iret()의 iretq가 CS/RIP를 바꾸면 다음 TB를 새로 찾거나 번역해야 한다.
  • process_activate() → pml4_activate() → CR3 전환은 전체 TB cache flush를 유발한다. 이것이 context switch에서 가장 비용이 큰 QEMU 작업이다.

addq 오프셋 검증

gp_registers 끝 = +120
+120: es (2B + 6B pad = 8B)
+128: ds (2B + 6B pad = 8B)
rax += 120 → es 위치
rax += 32  → +152 = rip 위치 (vec_no 8B + error_code 8B + rip 시작 = 120+8+8+16 = 152)

addq $32는 es(8B) + ds(8B) + vec_no(8B) + error_code(8B) = 32B를 건너뛴다.
