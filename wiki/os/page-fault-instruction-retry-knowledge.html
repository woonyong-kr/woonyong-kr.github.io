페이지 폴트 후 왜 같은 명령어를 다시 실행하나

한 줄 요약: page fault는 fault 명령어의 RIP를 저장하는 fault형 예외라 핸들러가 페이지를 준비하고 iretq하면 같은 명령어를 처음부터 재실행하며, 이 재시도가 demand paging·stack growth·COW의 전제다.

페이지 폴트 재실행 상태

CPU가 메모리 접근 명령어를 실행하다 page table에 유효한 매핑이 없으면 pf(page fault)를 일으킨다. 이때 CPU는 fault를 일으킨 명령어의 주소를 interrupt frame에 저장하고, OS의 fault handler로 제어를 넘긴다. handler가 page를 준비하고 return하면, iretq가 저장된 RIP로 복귀하여 같은 명령어를 처음부터 다시 실행한다. 이 메커니즘이 없으면 demand paging, stack growth, lazy loading, copy-on-write 같은 VM 정책이 성립하지 않는다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

x86-64 CPU는 명령어 실행 중 메모리 접근이 실패하면 fault 유형 예외(exception)를 발생시킨다. fault와 trap의 결정적 차이는 복귀 지점이다.

예외 유형복귀 RIP대표 예
Faultfault를 일으킨 명령어 자체pf (14), gp (13)
Trapfault를 일으킨 명령어의 다음int 0x80, breakpoint (3)

page fault는 fault 유형이므로, handler가 return하면 CPU는 fault 명령어를 재실행한다. CPU는 두 값을 남긴다.

handler는 명령어를 대신 실행하는 것이 아니라, 그 명령어가 다음번에 성공할 수 있도록 메모리 조건을 준비하는 코드다.

PintOS 구현

PintOS에서 page fault → 같은 명령어 재실행의 전체 흐름은 다음과 같다.

sequenceDiagram
    participant CPU as CPU (QEMU)
    participant IF as intr_entry
    participant PF as page_fault()
    participant VM as vm_try_handle_fault()
    participant MMU as pml4_set_page()
    participant RET as iretq

    CPU->>CPU: movb $0x41, (%rax) 실행
    Note over CPU: VA 0x4747eff8 → PTE not present
    CPU->>IF: #PF 발생, RIP·CS·RFLAGS 저장<br/>privilege/stack 전환 시에만 이전 RSP·SS도 저장
    IF->>IF: 범용 레지스터 저장 → struct intr_frame
    IF->>PF: call intr_handler → page_fault(f)
    PF->>PF: fault_addr = rcr2() → 0x4747eff8
    PF->>PF: error_code 분해 → not_present/write/user
    PF->>VM: vm_try_handle_fault(f, fault_addr, ...)
    VM->>VM: SPT 조회 또는 stack growth 판단
    VM->>MMU: frame 할당 + pml4_set_page()
    MMU->>MMU: *pte = vtop(kpage) | PTE_P | PTE_W | PTE_U
    VM-->>PF: return true
    PF-->>IF: return
    IF->>RET: 레지스터 복원 → iretq
    RET->>CPU: RIP = f->rip (같은 명령어)
    CPU->>CPU: movb $0x41, (%rax) 재실행 → 성공

핵심은 f->rip를 handler가 바꾸지 않는다는 점이다. iretq가 저장된 RIP로 복귀하면 CPU는 자동으로 같은 명령어를 재실행한다.

QEMU 에뮬레이션

QEMU는 PintOS의 VM 정책을 모른다. QEMU가 하는 일은 guest CPU가 x86 MMU 규칙으로 주소 변환을 시도하고, 실패하면 guest에게 pf를 전달하는 것이다.

PintOS가 rcr2()로 읽는 값은 QEMU가 흉내 낸 CPUX86State.cr[2]이고, f->rip는 env->eip에서 온다.

예제: VA 0x4747eff8에 대한 page fault 및 재실행

이 바이트 쓰기는 handler가 대신 한 것이 아니다. handler가 PTE를 설치했고, CPU가 원래 명령어를 재실행하면서 쓴 것이다.
