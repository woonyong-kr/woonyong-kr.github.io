thread_block — 현재 스레드를 BLOCKED 상태로 전환

thread_block()은 현재 스레드를 THREAD_BLOCKED로 바꾸고 schedule()로 CPU를 넘긴다. BLOCKED 스레드는 ready_list에 없어서, 누군가 깨워 주기 전까지 다시 선택되지 않는다.

기다리는 스레드는 어떻게 CPU를 넘기는가

세마포어 값이 0이거나, 락을 얻을 수 없거나, sleep의 종료 시점을 기다려야 하는 스레드는 당장 실행을 계속할 수 없다. PintOS에서는 이런 스레드가 thread_block()을 호출한다. 이 함수는 현재 실행 중인 스레드의 상태를 THREAD_BLOCKED로 바꾸고 schedule()을 호출해 다른 스레드에 CPU를 넘긴다.

BLOCKED 스레드는 ready_list에 들어가지 않는다. 따라서 누군가 thread_unblock()을 호출해 READY 상태로 되돌리기 전까지 스케줄러의 선택 대상이 되지 않는다. 세마포어, 락, 조건 변수, sleep은 이 전이를 이용해 기다리는 동안 CPU를 사용하지 않는 대기를 만든다.

CPU를 포기한다는 점에서는 thread_yield()와 비슷하지만, 다음 실행 조건이 다르다.

함수전이다시 실행되는 조건
thread_yield()RUNNING → READY스케줄러가 ready_list에서 선택
thread_block()RUNNING → BLOCKED누군가 thread_unblock() 호출

thread_yield()는 실행 가능한 상태를 유지한 채 잠시 양보한다. 반면 thread_block()은 기다리는 조건이 충족될 때까지 실행 대상에서 빠진다.

속성thread_block()thread_yield()
전이RUNNING → BLOCKEDRUNNING → READY
ready_list들어가지 않음들어감
재실행 조건thread_unblock() 필요스케줄러 자동 선택
인터럽트반드시 OFF 상태내부에서 OFF로 바꿈
대표 용도세마포어 대기, sleep시간 할당 소진, 선점

PintOS에서 일어나는 상태 전이

구현은 상태 변경과 스케줄러 호출로 이루어진다.

두 ASSERT는 호출 문맥을 제한한다. 첫 번째 조건에 따라 thread_block()은 인터럽트 컨텍스트에서 호출할 수 없다. 이 문서가 제시한 이유는 ISR 안에서 block하면 인터럽트 처리가 중단되어 시스템이 멈출 수 있다는 것이다. 두 번째 조건은 인터럽트가 꺼져 있어야 한다는 뜻이다. 문서의 설명에 따르면 상태를 BLOCKED로 바꾸는 작업과 schedule() 호출 사이에 타이머 인터럽트가 끼어들어 현재 상태를 RUNNING으로 잘못 판단하는 상황을 막기 위한 조건이다. 이 이유들은 코드의 ASSERT 자체가 증명하는 실행 결과가 아니라, 해당 전제 조건을 해석한 설명이다.

schedule() 내부에서는 do_schedule()을 거쳐 thread_launch()로 이어지고, 다른 스레드의 컨텍스트로 전환된다. BLOCKED 스레드는 이 전환 이후 실행을 멈춘다. 나중에 thread_unblock()이 스레드를 READY 상태로 바꾸고 ready_list에 넣으면, 스케줄러가 그 스레드를 선택했을 때 중단 지점부터 실행이 이어진다.

호출자는 block 전에 자신을 대기 구조에 등록해야 한다. waiters나 sleep_list 등에 등록하지 않으면 다른 실행 주체가 해당 스레드를 찾아 thread_unblock()할 수 없다. 이 등록과 상태 전환 사이를 보호하기 위해 다음 호출 지점들은 thread_block() 전에 intr_disable()로 인터럽트를 끈다.

위치용도
sema_down() (synch.c:72)세마포어 값이 0이면 대기
idle() (thread.c:489)idle 스레드가 할 일 없을 때 대기
thread_sleep() (thread.c:768)timer_sleep에서 tick까지 대기

전체 흐름은 다음과 같다.

flowchart TD
    A[호출자: intr_disable] --> B[자신을 waiters/sleep_list에 등록]
    B --> C[thread_block 호출]
    C --> D["ASSERT: !intr_context()"]
    D --> E["ASSERT: intr_level == OFF"]
    E --> F["current→status = THREAD_BLOCKED"]
    F --> G["schedule() → context switch"]
    G --> H["⏸ 여기서 멈춤"]

    I[다른 스레드가 thread_unblock 호출] --> J["status = THREAD_READY"]
    J --> K[ready_list에 삽입]
    K --> L[스케줄러가 선택하면 여기서 재개]
    L --> M[intr_set_level 복원]

Linux와 Windows의 대기 구조와 비교하기

PintOS의 상태 전이를 실제 OS의 대기 구조와 나란히 보면 각 단계의 역할을 구분하기 쉽다. 다만 아래 내용은 이 문서에 제시된 대응 관계이며, 각 OS의 모든 대기 경로가 PintOS와 동일하다는 뜻은 아니다.

Linux에서는 __schedule()을 호출하기 전에 set_current_state(TASK_INTERRUPTIBLE) 또는 TASK_UNINTERRUPTIBLE로 상태를 설정한다. 이 문서의 비교에 따르면 TASK_INTERRUPTIBLE은 시그널로도 깨어날 수 있고, TASK_UNINTERRUPTIBLE은 wake_up() 경로로 깨어난다. 시그널 깨우기를 지원하지 않는 PintOS의 THREAD_BLOCKED는 이 가운데 TASK_UNINTERRUPTIBLE에 가깝다.

항목LinuxPintOS
대기 구조wait_queue_head_t + wait_queue_entrystruct list waiters (세마포어 내부)
상태 설정set_current_state() → schedule() 분리thread_block() 안에서 한 번에 처리
깨우기wake_up() → try_to_wake_up()thread_unblock()
시그널 깨우기TASK_INTERRUPTIBLE이면 가능지원 안 함 (BLOCKED만 존재)
SMP 고려per-CPU runqueue, migration단일 CPU, 단일 ready_list

Windows에서는 KeWaitForSingleObject()로 dispatcher object(mutex, event, semaphore)를 기다린다. 스레드는 Waiting 상태로 전환되고, dispatcher가 signaled 상태가 되면 KiUnwaitThread()를 거쳐 Ready 상태로 돌아온다. 이 문서에서는 이 흐름을 PintOS의 block/unblock에 대응시킨다.

세부 항목을 함께 비교하면 다음과 같다.

QEMU와 GDB에서 보이는 것

QEMU는 thread_block()이라는 운영체제 수준의 의미를 직접 알지 못한다. guest CPU가 실행하는 명령어 흐름만 번역하고 실행한다. 이 문서가 제시한 명령어 수준의 대응은 다음과 같다.

  1. 상태 변경: mov DWORD PTR [rax+0x18], 2 — current->status = THREAD_BLOCKED (2 = BLOCKED). QEMU의 softmmu가 guest virtual → guest physical 변환을 수행하고, RAMBlock 내 해당 offset에 값을 쓴다.
  2. schedule() 호출: call schedule — TCG Translation Block 경계에서 새 블록으로 점프.
  3. thread_launch의 레지스터 저장/복원: push rbx; push rbp; ... mov rsp, [rdi+0x...] — 다른 스레드의 스택으로 전환. QEMU는 CPUX86State.regs[R_ESP]를 갱신한다.
  4. iretq (유저 복귀 시): QEMU TCG가 iretq를 에뮬레이션하여 CPUX86State.eip, cs, rflags를 intr_frame에서 복원한다.

GDB stub에서는 스택 포인터의 변화를 관찰할 수 있다.

이 예시에서 RSP가 바뀌는 지점은 다른 스레드의 스택으로 전환되는 context switch 지점에 해당한다. QEMU에서는 그 변화가 mov rsp, ... 명령어의 실행으로 나타난다. 제시된 주소는 관찰 예시이지 모든 실행에서 재현되는 고정 주소가 아니다.

연산과 값의 추적 범위

thread_block() 본문만 보면 상태 변경 한 줄과 schedule() 호출 한 줄이다. 그러나 호출 뒤에는 schedule() → do_schedule() → thread_launch()로 이어지는 컨텍스트 스위치가 따른다.

원문은 비용을 다음과 같이 추정한다.

  • thread_block(): 상태 변경 + schedule = 수십 사이클
  • thread_unblock(): status = THREAD_READY + list_insert_ordered = O(n) (ready_list 크기)
  • 실제 비용은 context switch의 thread_launch (약 수백 사이클)가 지배적

이 수치는 본문에 측정 환경이나 실행 결과가 제시되지 않은 추정치다. 따라서 특정 빌드나 실행에서 검증된 성능값으로 사용해서는 안 된다.

다음 메모리 주소도 4 MB RAM에서 스레드 A가 block되고 스레드 B로 전환되는 과정을 설명하기 위한 예시다.

코드 크기에 대해서도 원문은 다음 값을 제시한다.

  • ASSERT 2개 (디버그 빌드): 각각 조건 분기 + PANIC 호출부
  • mov DWORD PTR [...], 2: 7 bytes (x86-64)
  • call schedule: 5 bytes
  • 합계: 약 12 bytes (release), 수십 bytes (debug ASSERT 포함)

이 값 역시 실제 binary나 disassembly를 첨부해 검증한 결과가 아니라, 제시된 명령어를 바탕으로 한 설명 범위의 값이다.

sema_down()에서 block된 뒤 깨어나는 흐름

세마포어 값이 0일 때 스레드 A가 sema_down()을 호출하면 자신을 대기 구조에 등록하고 block한다. 이후 스레드 B가 sema_up()을 호출해 A를 깨우면 A가 ready_list로 돌아간다.

# 1. 스레드 A (tid=3)가 sema_down 호출 — value=0이므로 block
[SEMA-BLOCK] sema=0x8004003100 value=0, tid=3 about to block
[BLOCK] tid=3 name='main' status=0
  #0 thread_block() at thread.c:287
  #1 sema_down() at synch.c:72
  #2 lock_acquire() at synch.c:107
[SCHEDULE] from tid=3 status=2 → next=tid=4 name='child-1'

# 2. 스레드 B (tid=4)가 작업 후 sema_up 호출
[UNBLOCK] tid=3 name='main' by tid=4
# → 스레드 A가 ready_list에 복귀
# → 스케줄러가 priority 비교 후 A를 선택하면 재개

idle 스레드의 block/unblock 순환

ready_list가 비면 idle() 스레드가 block된다. 문서의 시나리오에서는 이후 타이머 인터럽트가 sleep이 끝난 스레드를 thread_unblock()하고, 해당 스레드가 ready_list에 들어가 실행 후보가 된다.

# ready_list 비어있을 때
[IDLE] idle thread blocking, ready_list empty
[BLOCK] tid=1 name='idle' status=0
[SCHEDULE] from tid=1 status=2 →
# ... (CPU는 hlt 상태, 타이머 인터럽트 대기)

# timer_sleep 만료로 sleep_list의 스레드가 깨어남
[UNBLOCK] tid=3 name='main' by tid=0 (interrupt context)
# → idle 스레드가 아닌 main이 ready_list에 들어감
# → schedule이 main을 선택
# → idle은 여전히 BLOCKED (할 일 생기면 schedule이 건너뜀)
