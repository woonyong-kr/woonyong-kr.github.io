Pintos COW 발표 정리와 트러블슈팅

Pintos COW 발표 정리와 트러블슈팅

한 줄 요약: fork 시점에는 page를 즉시 복사하지 않고 frame·swap slot을 공유하며, write 또는 접근이 발생하면 필요한 process만 분리하는 Copy-on-Write 구현과 트러블슈팅을 정리한다.

한 문장 요약

Copy-on-Write는 fork() 시점에 page 내용을 즉시 복사하지 않는다. 부모와 자식이 실제 page 저장 위치인 frame 또는 swap slot을 공유하고, write 또는 접근이 발생하면 필요한 process만 독립 frame으로 분리한다.

발표 흐름

  1. COW는 fork 시점에 수행하던 복사를 write 시점까지 미룬다.
  2. PML4는 실제 매핑을 담당하고, SPT는 page 상태를 메타데이터로 관리한다.
  3. 초기 구현에서는 swap된 page가 fork 도중 즉시 복사되는 문제가 있었다.
  4. 이를 해결하기 위해 SPT는 별도로 만들되 실제 page 저장 위치는 공유한다.
  5. page에 접근하면 필요한 process만 새 frame으로 분리한다.
  6. 메모리가 부족하면 공유 frame도 하나의 swap slot으로 옮긴다.

1페이지 - COW 개념

대본

Copy-on-Write는 fork 시점에 모든 메모리를 복사하지 않고, 실제 쓰기가 발생할 때까지 복사를 미루는 방식입니다.

fork 직후에는 부모와 자식이 같은 물리 page를 읽기 전용으로 공유합니다.

한쪽 process가 쓰기를 시도하면 page fault가 발생합니다. 이때 ref_count를 확인해 frame이 공유 중인지 판단합니다. 공유 중이라면 새 frame을 만들고 기존 내용을 복사합니다.

ref_count가 1보다 크면 여러 process가 frame을 공유하고 있다는 뜻입니다. 1이면 더 이상 공유 중인 frame이 아니라고 판단합니다.

이 방식은 실제로 사용하지 않을 page까지 미리 복사하지 않으므로 fork 시점의 메모리 복사 비용을 줄일 수 있습니다.

코드 설명

  • pintos/vm/vm.c:385 vm_handle_wp() page가 원래 writable인지 확인한 뒤 write-protect fault를 COW 처리로 넘긴다.
  • pintos/vm/vm.c:397 vm_handle_cow() old_frame->ref_count > 1이면 공유 중인 frame으로 판단하고 vm_copy_cow_page()를 호출한다.
  • pintos/vm/vm.c:410 vm_copy_cow_page() 새 frame을 가져와 memcpy()로 기존 frame의 내용을 복사한 뒤, 현재 process만 새 frame으로 remap한다.

fork 직후와 write 뒤 frame 관계

flowchart LR
  subgraph before["fork 직후"]
    a0["A VA"] --> f20["Frame 2<br/>ref_count=2"]
    b0["B VA"] --> f20
  end
  subgraph after["B write fault 처리 후"]
    a1["A VA"] --> f21["Frame 2<br/>A만 유지"]
    b1["B VA"] --> f4["Frame 4<br/>복사 후 B만 remap"]
  end
  before --> fault["B write-protect fault<br/>Frame 2를 Frame 4로 복사"] --> after

remap은 현재 process의 가상주소가 가리키는 물리 frame을 바꾸는 작업이다. 구현에서는 현재 process의 PML4 매핑을 새 frame으로 바꾸고, SPT의 page->frame도 같은 frame을 가리키도록 갱신한다.

2페이지 - PML4와 SPT

대본

Copy-on-Write의 동작을 이해하려면 먼저 PML4와 SPT의 역할을 구분해야 합니다.

PML4는 CPU와 MMU가 직접 참조하는 실제 page table입니다. SPT는 OS가 page 상태를 관리하는 보조 page table입니다.

두 테이블은 각각 쓰기 가능 여부에 관한 상태를 가집니다. fork할 때 SPT의 쓰기 권한은 유지하고 PML4의 쓰기 플래그만 read-only로 바꾸면, fork된 메모리에 쓰기를 시도할 때 page fault를 유도할 수 있습니다.

page에는 UNINIT, ANON, FILE 세 가지 타입이 있습니다. 이 구현에서는 그중 ANON 타입에 Copy-on-Write를 적용했습니다.

코드 설명

  • pintos/include/vm/vm.h:44 struct page SPT에 저장되는 page 메타데이터다.
  • pintos/include/vm/vm.h:46 va 이 page가 담당하는 유저 가상주소다.
  • pintos/include/vm/vm.h:47 frame page가 실제 메모리에 올라와 있을 때 연결되는 frame이다.
  • pintos/include/vm/vm.h:50 writable OS 관점에서 이 page가 논리적으로 writable인지 나타낸다.
  • pintos/include/vm/vm.h:54 union page 타입에 따라 uninit, anon, file 중 하나의 메타데이터를 가진다.

쓰기 권한을 구분해야 하는 이유

COW는 두 상태의 차이를 이용한다. SPT에서는 writable이지만 PTE에서는 read-only라면, 발생한 fault는 단순한 권한 위반이 아니라 COW를 위해 의도적으로 쓰기를 막아 둔 결과일 수 있다.

3페이지 - 문제: swap된 page를 fork 중 즉시 복사하는 비용

대본

메모리에 올라온 frame의 복사를 구현한 뒤에는 swap된 메모리를 어떻게 처리할지가 문제로 남았습니다. swap된 page에도 복사를 미루는 방식을 적용하려면 별도의 처리가 필요했습니다.

메모리에 있는 ANON page는 부모와 자식이 같은 frame을 공유할 수 있습니다. 반면 swap된 page는 이미 디스크로 내려간 상태이므로 공유할 물리 frame이 없습니다.

초기 구현에서는 fork 도중 swap slot을 읽어 자식 process의 새 frame으로 복사했습니다. 그러나 Copy-on-Write의 목적은 fork 시점의 복사를 피하고 write 또는 접근 시점까지 미루는 것입니다. 초기 방식으로는 swap된 slot의 복사 시점을 미룰 수 없었습니다.

설명 포인트

이 부분에서는 코드보다 문제의 조건을 먼저 설명한다. 메모리에 있는 ANON page는 frame을 공유할 수 있지만, swap된 ANON page에는 부모와 자식이 함께 참조할 frame이 없었다.

4페이지 - 해결: swap slot도 공유 대상으로 만든다

대본

이 문제를 해결하기 위해 page가 frame뿐 아니라 swap slot도 공유할 수 있도록 수정했습니다.

fork할 때 부모의 SPT page 자체를 공유하지는 않습니다. 자식에게는 별도의 SPT page를 만듭니다.

부모의 SPT page가 swap된 상태라면 disk_read를 수행하지 않습니다. 대신 slot과 상태 값을 자식 page에 복사하고, swap_slot_ref를 호출해 해당 swap slot의 참조 수만 늘립니다.

이렇게 하면 fork 도중 자식 frame을 만들지 않아도 됩니다. 부모와 자식은 실제 접근이 발생할 때까지 같은 swap slot을 공유합니다.

코드 설명

  • pintos/vm/anon.c:190 anon_copy() fork 도중 ANON page를 자식 SPT에 복사하는 함수다.
  • pintos/vm/anon.c:198 부모 page에 frame이 없거나 swapped 상태라면 resident frame 공유 경로로 들어가지 않는다.
  • pintos/vm/anon.c:202 자식 page의 operations를 anon_ops로 설정한다.
  • pintos/vm/anon.c:203 dst_page->anon = src_page->anon;으로 anon 메타데이터의 값을 복사한다.
  • pintos/vm/anon.c:204 부모와 자식이 같은 swap slot을 참조하므로 swap_slot_ref()로 참조 수를 늘린다.

anon 대입에서 공유되는 것

dst_page->anon = src_page->anon;은 anon 객체의 포인터를 공유하는 코드가 아니다.

struct page에는 다음과 같이 union 값이 들어 있다.

따라서 anon은 포인터가 아니라 값 필드다. 이 대입은 swapped, swap_idx 같은 값을 복사한다.

5페이지 - 접근 이후: 필요한 process만 새 page를 생성

대본

실제 접근이 발생하면 resident ANON page와 swapped ANON page는 서로 다른 경로로 분리됩니다.

먼저 메모리에 있던 ANON page를 보겠습니다. B가 write를 시도하면 COW fault가 발생합니다. 분리 전에는 A와 B가 같은 Frame 2를 참조하므로 ref_count가 1보다 큽니다.

이 경우 새 Frame 4를 만들고 기존 Frame 2의 내용을 memcpy합니다. 그다음 B만 새 Frame 4로 remap합니다. A는 기존 Frame 2를 계속 참조합니다.

swap에 있던 ANON page도 접근한 process만 분리됩니다. B가 접근하면 slot 5의 내용을 읽어 Frame 6을 만들고, B의 page는 swap-in된 상태가 됩니다. 이후 slot 5는 A만 참조하므로 swap_ref_count가 1로 줄어듭니다.

코드 설명

  • pintos/vm/vm.c:410 vm_copy_cow_page() resident frame을 COW 방식으로 분리하는 함수다.
  • pintos/vm/vm.c:414 새 frame을 하나 할당한다.
  • pintos/vm/vm.c:417 기존 공유 frame의 내용을 새 frame으로 복사한다.
  • pintos/vm/vm.c:419 현재 process의 page만 새 frame으로 remap한다.
  • pintos/vm/anon.c:115 anon_swap_in() swap에 있던 ANON page를 접근 시점에 frame으로 읽어오는 경로다.

6페이지 - 메모리 부족 시 공유 frame의 swap-out

대본

메모리가 부족하면 여러 process가 공유하는 frame도 swap-out 대상이 될 수 있습니다.

Frame 2를 A와 B가 함께 참조한다고 가정하겠습니다. 이 frame이 victim으로 선택되었을 때 한 process의 상태만 바꾸면, 나머지 process가 가진 page 상태와 실제 frame 상태가 어긋납니다.

먼저 Frame 2의 내용을 새 swap slot 6에 기록합니다. 이어서 owner 수에 맞게 swap_ref_count를 설정합니다.

그다음 frame을 참조하던 모든 process를 순회합니다. 각 page에 swap-out 상태와 slot 정보를 기록하고, 각 page table의 mapping을 제거합니다.

이 처리가 끝나면 공유 frame은 메모리에서 내려가고, 두 SPT는 같은 swap slot을 공유합니다. 나중에 둘 중 하나가 접근하면 그 process에만 frame을 할당해 lazy하게 처리합니다.

코드 설명

  • pintos/vm/anon.c:134 anon_swap_out() ANON frame을 swap disk로 내리는 함수다.
  • pintos/vm/anon.c:141 현재 frame을 참조하는 owner 수를 저장한다.
  • pintos/vm/anon.c:142 새 swap slot을 하나 할당한다.
  • pintos/vm/anon.c:145 frame의 내용을 swap slot에 disk_write()한다.
  • pintos/vm/anon.c:151 owner 수에 맞게 swap slot reference count를 늘린다.
  • pintos/vm/anon.c:154 frame owner 리스트를 순회한다.
  • pintos/vm/anon.c:159 각 owner page를 swapped=true로 바꾼다.
  • pintos/vm/anon.c:160 각 owner page에 같은 swap_idx를 저장한다.
  • pintos/vm/anon.c:161 frame이 더 이상 메모리에 없으므로 frame=NULL로 바꾼다.
  • pintos/vm/anon.c:163 각 process의 PML4 mapping을 제거한다.

pop_front로 owner를 제거하는 이유

list_pop_front(&frame->owners)는 owner를 리스트에서 실제로 제거한다.

이 코드는 frame을 swap out해 메모리에서 내보내는 시점에 실행된다. 따라서 해당 frame을 가리키는 owner가 frame owner 리스트에 남아 있어서는 안 된다.

대신 각 owner가 가리키던 struct page에 다음 상태를 저장한다.

owner 관계는 frame list에서 사라진다. 이후에는 각 process의 SPT가 swap_idx를 통해 page의 위치를 기억한다.

발표 중 자주 헷갈린 표현

remap

현재 process의 가상주소가 가리키는 물리 frame을 바꾸는 작업이다.

구현에서는 현재 process의 PML4 mapping을 새 frame으로 바꾸고, SPT의 page->frame도 새 frame을 가리키도록 갱신한다.

SPT writable과 PTE_W

COW는 두 상태의 차이를 이용해 write fault를 유도한다.

anon 값 복사

dst_page->anon = src_page->anon;은 포인터 공유가 아니라 값 복사다. 부모와 자식의 struct page는 서로 다르다. 다만 복사된 swap_idx 값이 같으므로 두 page가 같은 swap slot을 가리킨다.

swap_ref_count

여러 SPT page가 하나의 swap slot을 함께 가리킬 수 있으므로 slot에도 reference count가 필요하다.

FILE page

이 COW 설명은 ANON page를 중심으로 한다. FILE 또는 mmap page는 file-backed 정책을 따르므로 여기서는 ANON COW와 구분한다.
