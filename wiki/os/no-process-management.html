QEMU는 프로세스 관리를 하지 않는다

PintOS가 tid=2를 멈추고 tid=3을 실행할 때 QEMU는 “프로세스가 바뀌었다”고 세지 않는다. QEMU는 달라진 레지스터와 메모리를 실행하고, 그 값에 프로세스라는 의미를 붙이는 일은 PintOS가 맡는다.

먼저 schedule()이 바꾸는 장면을 보자

ready_list에 tid=2, tid=3이 기다리고 tid=1이 실행 중이라고 해 보자. PintOS의 schedule()은 다음에 실행할 struct thread를 고르고, 그 스레드의 주소 공간과 커널 스택으로 CPU 상태를 바꾼다. 이 장면을 보면 같은 CPU 한 개가 여러 프로세스를 번갈아 실행하는 이유를 설명할 수 있다.

한 번의 schedule()에서 PintOS와 QEMU가 각각 무엇을 바꾸는가?

tid, ready_list, “다음에 누가 실행되는가”는 PintOS가 읽고 쓰는 약속이다. 반면 QEMU는 CR3가 바뀌면 새 페이지 테이블로 주소를 변환하고 RIP, RSP가 가리키는 다음 명령어를 실행할 뿐, 그 변화가 tid=1에서 tid=2로 넘어간 결과인지는 알지 못한다.

프로세스라는 이름은 struct thread에서 나온다

PintOS는 실행 단위를 struct thread로 저장하고, 그 안의 필드들을 연결해 프로세스의 상태와 관계를 만든다. 실제 구조체에는 더 많은 필드가 있지만, 여기서는 이 경계를 만드는 값만 보면 충분하다.

tid는 실행 단위를 구별하고, status와 ready_list는 실행할 차례를 정하며, child_status_list는 부모와 자식 및 종료 상태를 연결한다. 이 값들은 모두 guest memory 안에 놓이지만, QEMU에게는 메모리의 어느 위치에 어떤 바이트가 쓰였는지만 보일 뿐 THREAD_READY나 “자식 프로세스”라는 뜻은 전달되지 않는다.

PintOS가 해석하는 상태QEMU가 실제로 처리하는 변화
tid, status 갱신guest memory의 바이트 쓰기
ready_list에 삽입포인터 값이 연결되는 메모리 쓰기
child_status_list 생성구조체가 놓일 메모리 확보와 초기화
pml4를 활성화CR3가 가리키는 페이지 테이블로 주소 변환

표의 마지막 행만 CPU 주소 변환과 직접 이어지지만, 그마저도 QEMU는 “이 CR3가 어느 프로세스의 것인가”가 아니라 “이 물리 주소의 페이지 테이블을 사용할 것인가”만 처리한다.

CR3가 바뀌어도 QEMU가 프로세스를 세지는 않는다

컨텍스트 스위치에서 PintOS는 다음 struct thread를 고른 뒤 process_activate()를 통해 그 스레드의 pml4를 CR3에 로드한다. CPU와 QEMU는 그 순간부터 새 페이지 테이블을 따라 가상 주소를 변환하지만, 프로세스 수를 늘리거나 ready_list에서 항목을 꺼내는 일은 하지 않는다.

그래서 디버깅할 때 CR3 값이 바뀐 사실은 “주소 공간이 바뀌었다”는 하드웨어 관찰이고, “어떤 프로세스를 왜 선택했는가”는 PintOS 스케줄러의 질문이다. 둘을 같은 층에서 찾으면 QEMU 설정을 고치려다 PintOS의 리스트나 상태 전이 버그를 놓치기 쉽다.

fork()도 QEMU에게는 메모리 상태의 변화다

process_fork()가 새 struct thread와 페이지 테이블을 만들고 부모의 파일·메모리 상태를 복사하면, PintOS는 이를 자식 프로세스 생성으로 해석한다. QEMU는 그 과정에서 guest memory가 할당·복사되고 나중에 CR3가 바뀌는 것을 실행할 뿐, QEMU 내부에 자식 프로세스 객체를 만들거나 부모-자식 관계를 저장하지 않는다.

이 차이는 exit()에서도 같다. PintOS는 child_status에 종료 코드를 남기고 wait()가 회수할 수 있게 하지만, QEMU가 보는 것은 메모리 값의 변경과 이후 실행 흐름뿐이다.

문제가 생겼을 때 어느 쪽을 먼저 볼까

자식의 종료 코드, wait()의 반환, 우선순위, ready_list 순서가 이상하면 PintOS의 struct thread, 리스트, 동기화 코드를 먼저 본다. 반대로 페이지 폴트가 나거나 기대한 주소가 다른 물리 페이지로 번역되면 현재 CR3, pml4 내용, 그리고 QEMU가 실행하는 메모리·장치 경로를 함께 확인한다.

현재 PintOS 상태와 CPU 레지스터를 같은 중단점에서 어떻게 비교하는가?

이 명령은 프로세스 이름표를 읽는 PintOS 상태와, 실제로 CPU가 사용할 주소 변환 상태를 나란히 보여 준다. 두 값이 모두 바뀌었다고 해서 QEMU가 tid를 해석한 것은 아니며, PintOS가 레지스터에 필요한 값을 올려놓았기 때문에 같은 순간을 관찰할 수 있는 것이다.
