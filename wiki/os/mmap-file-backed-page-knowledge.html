mmap file-backed page는 어떻게 파일을 메모리처럼 보이게 하나

한 줄 요약: mmap은 파일 내용을 지금 복사하라는 명령이 아니라 “이 가상 주소 범위를 이 파일의 이 offset에 연결해 두라”는 약속이다. 실제 읽기는 page fault가 났을 때 file-backed page가 처리하므로 read() 호출 없이 p[123]만으로 파일 바이트가 보인다.

mmap file-backed page 질문

보통 read(fd, buf, 4096)을 호출하면 파일 바이트가 유저 버퍼로 복사된다. 그렇다면 mmap(addr, 4096, writable, fd, 0)을 호출했을 때는 왜 addr[0]을 읽는 것만으로 파일의 첫 바이트가 보일까?

이 코드는 read()를 직접 호출하지 않는다. 그래도 운영체제는 파일 offset 123의 바이트를 p[123]에서 읽을 수 있게 만들어야 한다.

따라서 mmap은 “파일 내용을 지금 복사해라”가 아니라 이 가상 주소 범위를 이 파일의 이 offset과 연결해 두라는 약속이다.

mmap file-backed page 혼동

파일 I/O는 두 가지 관점에서 볼 수 있다.

방식유저 코드가 보는 것커널이 하는 일
read / write파일과 버퍼 사이의 복사syscall마다 파일 offset에서 바이트를 복사
mmap파일이 메모리 배열처럼 보임주소 범위를 파일 backing 정보와 연결하고 page fault 때 채움

mmap은 파일을 메모리처럼 다루는 인터페이스를 만든다. 큰 파일의 일부를 랜덤 접근할 때 매번 lseek + read를 호출하지 않고 포인터 연산으로 접근할 수 있다. 실제 OS에서는 실행 파일, 공유 라이브러리, 데이터베이스, IPC, 큰 힙 할당까지 mmap 계열 메커니즘을 넓게 쓴다.

두 방식의 차이는 파일 바이트를 읽는 시점에서 드러난다. mmap()은 먼저 주소 범위와 파일 offset의 관계를 기록한다. 실제 frame은 아래 흐름처럼 첫 접근에서 page fault가 발생할 때 채운다.

mmap file-backed page 흐름

머릿속에는 “주소 범위와 파일 구간을 잇는 표”를 그리면 된다.

page table은 “지금 VA가 어느 frame으로 번역되는가”를 담는다.

supplemental page table은 “아직 frame은 없어도 이 VA가 어떤 파일에서 와야 하는가”를 담는다.

따라서 mmap은 보통 page table을 바로 채우는 작업이 아니다. SPT에 file-backed page 약속을 등록하는 작업으로 이해하면 된다.

    participant K as Kernel (syscall)
    participant SPT as Supplemental PT
    participant PF as Page Fault Handler
    participant FS as File System
    participant PT as Page Table

    K->>SPT: UNINIT(FILE) page 등록<br/>(VA range ↔ file offset)
    K-->>U: 매핑된 VA 반환

    U->>U: p[5000] 읽기 시도

    PF->>SPT: spt_find_page(0x10001000)

    PF->>FS: file_read_at(file, frame, 1904, 4096)
    PF->>PT: pml4_set_page(VA → frame)
    PF-->>U: 명령어 재실행 → 데이터 획득

mmap file-backed page 입력 차이

파일 길이가 6000바이트이고 사용자가 다음처럼 매핑한다고 하자.

page size가 4096 = 0x1000이면 두 개의 page 약속이 생긴다.

VA page파일 offset파일에서 읽을 바이트0으로 채울 바이트
0x10000000040960
0x10001000409619042192

이후 p[5000]을 읽는다고 하자.

처음 접근할 때 page table에 mapping이 없으면 page fault가 발생한다. OS는 SPT에서 0x10001000의 backing 정보를 찾는다. 이어서 파일 offset 4096부터 1904바이트를 읽어 frame 앞부분에 넣고, 나머지 2192바이트를 0으로 채운다.

실제 운영체제

Linux에서 mmap()은 프로세스 주소 공간에 VMA를 만든다. VMA는 “이 주소 범위의 의미”를 들고 있다.

  • 어떤 파일과 연결되는가
  • 어느 offset부터 연결되는가
  • 읽기/쓰기/실행 권한은 무엇인가
  • MAP_SHARED인가, MAP_PRIVATE인가
  • page fault가 나면 어떤 fault handler가 채울 것인가

파일 내용은 보통 page cache와 연결된다. read()와 mmap()은 유저 인터페이스는 다르지만 실제 파일 page를 캐시하고 dirty page를 write-back하는 문제를 공유한다.

Windows도 파일 mapping object와 view를 통해 비슷한 문제를 푼다. Win32 API 이름은 CreateFileMapping, MapViewOfFile이고, NT 커널 내부에서는 section object와 view, page fault 처리가 연결된다.

현실 OS는 PintOS보다 훨씬 복잡하다. 공유 매핑, 사적 매핑, copy-on-write, file truncation, page cache 일관성, NUMA, huge page, 보안 권한까지 다룬다.

PintOS

PintOS는 Project 3 VM에서 mmap을 교육용으로 축소한다.

사용자 레벨 wrapper는 이미 있다.

  • pintos/lib/user/syscall.c
    • mmap()은 syscall5(SYS_MMAP, addr, length, writable, fd, offset)을 호출한다.
    • munmap()은 syscall1(SYS_MUNMAP, addr)을 호출한다.
  • pintos/include/lib/syscall-nr.h
    • SYS_MMAP
    • SYS_MUNMAP

하지만 현재 저장소 상태에서 커널 쪽은 아직 완성되지 않은 스켈레톤이다.

  • pintos/userprog/syscall.c
    • syscall_handler()의 switch에는 아직 SYS_MMAP, SYS_MUNMAP case가 없다.
  • pintos/vm/file.c
    • file_backed_swap_in()
    • file_backed_swap_out()
    • do_mmap()
    • do_munmap()
    • 모두 채워야 할 자리다.
  • pintos/include/vm/file.h
    • struct file_page가 비어 있어 file, offset, read bytes 같은 metadata를 추가해야 한다.

PintOS에서 구현할 흐름은 다음처럼 잡으면 된다.

flowchart LR
    MUNMAP["munmap(addr)"] --> ITER["mapping 범위<br/>page 순회"]
    ITER --> DIRTY{"dirty bit<br/>set?"}
    DIRTY -->|"Yes"| WB["file_write_at()<br/>write-back"]
    DIRTY -->|"No"| SKIP["skip"]
    WB --> CLR["pml4_clear_page()<br/>+ SPT 제거"]
    SKIP --> CLR
    CLR --> CLOSE["file_reopen된<br/>파일 close"]

여기에는 중요한 단순화가 있다.

PintOS의 mmap syscall은 Linux처럼 prot, flags를 받지 않는다. user wrapper의 인자는 addr, length, writable, fd, offset이다. 따라서 MAP_SHARED와 MAP_PRIVATE의 모든 조합을 일반화해서 다루는 모델은 아니다.

테스트가 확인하는 동작은 파일 backed page를 lazy load하고, writable mapping의 dirty page를 적절히 파일에 되돌리는지에 집중된다.

QEMU

QEMU는 guest OS인 PintOS의 mmap 의미를 모른다.

QEMU가 보는 것은 다음뿐이다.

  • guest CPU가 syscall instruction을 실행한다.
  • PintOS 커널 코드가 guest memory 안의 struct page, struct file_page, SPT를 읽고 쓴다.
  • page fault가 나면 x86 예외처럼 PintOS에 전달한다.
  • PintOS가 page table을 고친 뒤 같은 명령어를 다시 실행하면, QEMU는 guest physical memory read/write를 수행한다.
  • PintOS 파일 시스템이 디스크 sector를 읽거나 쓰면, QEMU IDE 장치 모델이 block backend I/O로 바꾼다.

QEMU 메모리와 디스크 경로에서 볼 수 있는 단서는 다음이다.

  • system/physmem.c
    • guest physical address를 MemoryRegion 안 offset으로 바꾸고 guest RAM 바이트를 읽고 쓴다.
  • hw/ide/core.c
    • ide_sector_read()
    • ide_sector_write()
  • block/block-backend.c
    • blk_aio_preadv()
    • blk_aio_pwritev()
  • include/block/block-common.h
    • BDRV_SECTOR_BITS = 9
    • BDRV_SECTOR_SIZE = 512

PintOS mmap의 file offset, dirty page, file_write_at() 같은 의미는 QEMU의 정책이 아니다. QEMU는 그 결과로 바뀐 guest RAM 바이트와 disk sector I/O를 하드웨어처럼 보이게 할 뿐이다.

mmap file-backed page 코드

1. 유저 프로그램은 SYS_MMAP 번호로 커널에 들어간다

파일:

  • pintos/lib/user/syscall.c
  • pintos/include/lib/syscall-nr.h

SYS_MMAP, SYS_MUNMAP 번호도 enum에 있다.

2. 현재 커널 syscall_handler에는 mmap 처리가 없다

파일:

  • pintos/userprog/syscall.c

현재 switch (f->R.rax)는 SYS_HALT부터 SYS_TELL 계열까지만 처리하고 default로 빠진다.

따라서 현재 코드 상태에서는 mmap()을 호출해도 커널이 do_mmap()으로 연결하지 않는다. VM 과제 구현에서는 SYS_MMAP과 SYS_MUNMAP case를 추가해야 한다.

3. file-backed page 연산 테이블은 준비되어 있다

파일:

  • pintos/vm/file.c

이 테이블은 “이 page가 file-backed일 때 page fault로 들어오면 어떤 함수를 부를지”를 정한다.

4. lazy page는 첫 fault 때 구체 타입으로 바뀐다

파일:

  • pintos/vm/uninit.c

처음에는 VM_UNINIT으로 SPT에 들어가 있다. 첫 접근이 일어나면 file_backed_initializer()가 page operations를 file-backed로 바꾸고, 이어서 초기화 callback이 파일 내용을 frame에 채운다.

5. 실제 파일 바이트는 file_read_at에서 읽는다

파일:

  • pintos/filesys/file.c

mmap page-in은 현재 file position을 움직이면 안 되므로 file_read()보다 file_read_at()이 맞다. write-back도 같은 이유로 file_write_at()을 써야 한다.

6. 테스트가 요구하는 동작

파일:

  • pintos/tests/vm/mmap-read.c
  • pintos/tests/vm/mmap-write.c
  • pintos/tests/vm/mmap-clean.c
  • pintos/tests/vm/mmap-off.c
  • pintos/tests/vm/mmap-bad-off.c

테스트에서 읽을 수 있는 요구사항은 다음과 같다.

  • 파일을 매핑한 뒤 memcmp(actual, sample, ...)로 메모리 접근이 파일 내용과 같아야 한다.
  • 파일 끝 뒤 같은 page의 나머지 바이트는 0이어야 한다.
  • writable mapping에서 메모리로 쓴 뒤 munmap()하면 파일에 반영되어야 한다.
  • clean page는 munmap() 때 덮어쓰면 안 된다.
  • page-aligned nonzero offset은 파일 중간을 mapping하는 정상 사례로 동작해야 한다.
  • offset이 page-aligned가 아니면 실패해야 한다.

dirty write-back을 할 때는 같은 page 안에서도 파일에 대응되는 구간을 구분해야 한다.

정리

  • mmap은 파일을 즉시 복사하는 호출이 아니라 VA 범위와 파일 offset의 관계를 등록하는 호출이다.
  • 실제 OS는 VMA/section/page cache 같은 큰 VM 구조로 이 관계를 관리한다.
  • PintOS는 SPT, struct page, struct file_page, file_backed_swap_in/out으로 이 동작의 주요 부분을 구현하게 만든다.
  • anonymous page는 swap slot이 backing이고, file-backed page는 원본 파일 offset과 dirty write-back이 backing이다.
  • read-only mmap은 읽기를 lazy load로 처리할 수 있지만, 첫 접근이 write이면 SPT의 writable=false metadata로 막아야 한다.
  • QEMU는 PintOS의 mmap 의미를 모르고 guest CPU, guest RAM, IDE disk I/O만 에뮬레이션한다.
  • 값을 추적할 때는 page base, page offset, file offset, read bytes, zero bytes가 서로 맞는지 계속 확인해야 한다.

mmap file-backed page 점검

  • mmap() 호출 시점에는 파일 전체를 RAM으로 복사하지 않는다. VA 범위, file offset, read_bytes, zero_bytes를 SPT에 약속으로 남긴다.
  • 실제 바이트 읽기는 첫 page fault에서 file_backed_swap_in()이 수행한다.
  • file-backed page는 anonymous page와 다르게 swap slot이 아니라 원본 파일 offset을 backing으로 삼는다.
  • munmap() 또는 eviction 때는 dirty 여부와 writable 여부를 보고 파일에 다시 쓸지 판단해야 한다.
  • 마지막 page에서는 read_bytes와 zero_bytes를 분리해야 한다. zero-fill tail을 파일 내용처럼 write-back하면 파일 길이와 의미가 깨진다.
