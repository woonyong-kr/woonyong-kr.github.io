페이지 타입 Transition (Page Type Transition)

페이지 타입 Transition (Page Type Transition)

한 줄 요약: PintOS의 모든 가상 페이지는 VM_UNINIT로 태어나, 첫 page fault에서 uninit_initialize()가 page->operations 테이블을 교체해 VM_ANON 또는 VM_FILE로 전환된다. 등록과 실제 초기화를 나누는 two-phase initialization을 C의 다형성 패턴으로 구현한 것이다.

페이지 타입 Transition 흐름

PintOS의 모든 가상 페이지는 VM_UNINIT 상태로 태어난다. 첫 page fault가 발생하면 uninit_initialize()가 호출되어 페이지를 실제 타입(VM_ANON 또는 VM_FILE)으로 전환(transmute)한다. 이 전환은 page->operations 함수 포인터 테이블을 교체하는 것으로 이루어지며, C 언어에서 다형성(polymorphism)을 구현한 패턴이다.

상세 설명

추상 개념 (타입 전환 설계)

Lazy loading 설계에서 페이지 등록 시점과 실제 물리 메모리 할당 시점을 분리해야 한다. 등록 시점에는 “나중에 어떤 타입이 될 것인지”와 “그때 어떤 초기화를 할 것인지”만 기록해두고, 실제 fault가 발생할 때 비로소:

  1. 물리 frame 할당
  2. 타입별 initializer 호출 (operations 교체)
  3. 사용자 정의 init 콜백으로 내용 채우기

이 두 단계 초기화(two-phase initialization)가 타입 전환의 핵심이다.

실제 OS (Linux/Windows)

Linux의 vm_area_struct는 생성 시점부터 타입이 결정된다 (MAP_ANONYMOUS, MAP_PRIVATE 등). Fault handler (handle_pte_fault)에서 do_anonymous_page() 또는 filemap_fault()를 직접 분기한다. PintOS처럼 UNINIT 중간 상태가 별도로 존재하지는 않지만, PTE가 없는 상태(not present)가 사실상 같은 역할을 한다.

PintOS 구현

1단계: 등록 — vm_alloc_page_with_initializer()

이 시점에서 page->operations = &uninit_ops로 설정된다.

struct uninit_page에 저장되는 것:

  • init: 사용자 정의 콜백 (예: lazy_load_segment)
  • type: 최종 타입 (VM_ANON 또는 VM_FILE)
  • aux: 초기화에 필요한 데이터 (예: struct lazy_load_arg)
  • page_initializer: 타입별 초기화 함수

2단계: 전환 — uninit_initialize() (= uninit_ops.swap_in)

호출 순서:

  1. page_initializer(page, type, kva) — 타입 전환: page->operations를 &anon_ops 또는 &file_ops로 교체
  2. init(page, aux) — 내용 채우기: 파일에서 읽기, 0 채우기 등

타입별 initializer가 하는 일:

anon_initializer():

file_backed_initializer():

union이 핵심:

union이므로 전환 후 uninit 필드의 메모리를 anon 또는 file이 덮어쓴다. uninit_initialize()가 init과 aux를 먼저 지역 변수에 복사한 뒤 page_initializer를 호출하는 이유가 여기에 있다 — initializer가 union을 덮어쓰면 uninit.init에 접근할 수 없기 때문이다.

페이지 타입 Transition 값

union 멤버크기 (bytes)
struct uninit_pageinit(8) + type(4) + aux(8) + page_initializer(8) = 28 (+ padding → 32)
struct anon_pageswap_idx(8) + swapped(1) = 9 (+ padding → 16)
struct file_pagefile(8) + ofs(8) + page_read_bytes(8) + swap_idx(8) + swapped(1) = 33 (+ padding → 40)
union 전체max(32, 16, 40) = 40 bytes

QEMU 에뮬레이션

QEMU는 page type transition을 전혀 모른다. QEMU가 보는 것은:

  1. #PF 발생: Guest가 PTE가 없는 주소에 접근 → QEMU TCG의 x86_cpu_tlb_fill()이 softmmu TLB miss 처리 → x86 pf 주입
  2. frame 할당: PintOS의 palloc_get_page()가 free pool에서 PA를 가져가는 것은 QEMU 입장에서 일반 메모리 write
  3. PTE 설치: pml4_set_page()가 PTE에 PA|flags를 기록하면, 다음 softmmu TLB lookup에서 hit하여 guest가 정상 접근 가능
  4. operations 포인터 교체: page->operations = &anon_ops는 QEMU에게 일반적인 8바이트 메모리 store

핵심: union 덮어쓰기, operations 교체, init 콜백 호출 — 이 모든 것이 QEMU에게는 단순 메모리 read/write의 연속이다. 타입 전환의 의미론은 GuestOS만 이해한다.

관찰 시나리오

시나리오 1: load_segment lazy 등록 → 첫 접근

설정: args-single onearg 실행, 코드 세그먼트의 첫 페이지에 대한 page fault

관찰 목표: vm_alloc_page_with_initializer로 VM_ANON|VM_MARKER_0 타입 등록 후, 첫 명령어 fetch 시 pf → uninit_initialize → anon_initializer → lazy_load_segment 순서 확인

GDB 실행:

기대 결과: uninit_initialize() 내부에서 (1) anon_initializer가 operations를 &anon_ops로 교체, (2) lazy_load_segment가 파일에서 데이터를 읽어 kva에 memcpy. 두 단계 모두 성공하면 return true.

시나리오 2: mmap 후 첫 접근 시 FILE 전환

설정: mmap-read 테스트, mmap된 파일 페이지에 대한 page fault

관찰 목표: do_mmap → vm_alloc_page_with_initializer(VM_FILE) → 첫 read 시 pf → uninit_initialize → file_backed_initializer → lazy_load_segment 순서

GDB 실행:

기대 결과: file_backed_initializer가 page->file.file = la->file, page->file.ofs = la->ofs 등을 설정. union이 uninit→file로 재해석됨.
