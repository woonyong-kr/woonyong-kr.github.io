fd 숫자의 의미

fd 숫자의 의미

확인 범위: 이 문서는 fd 숫자의 일반 개념과 할당·재사용 원리를 설명하고, Linux와 제시된 PintOS 구현을 사례로 구분해 다룬다. 구체적인 코드 위치, 테이블 크기, 실행 상태, QEMU·GDB 관찰 결과와 성능 특성은 해당 소스·아키텍처·실행 환경에서 별도로 검증해야 한다.

한 줄 요약: fd는 파일 이름이 아니라 프로세스별 fd 테이블의 인덱스라는 점 — 커널이 부여하는 음이 아닌 정수.

fd 숫자의 의미 변화

파일 디스크립터(fd)는 프로세스가 열린 파일(또는 파이프, 소켓 등 I/O 자원)을 식별하기 위해 커널이 부여하는 음이 아닌 정수다. fd 자체는 “파일의 이름”이 아니라 프로세스별 fd 테이블의 인덱스(배열 첨자)이며, 그 인덱스 위치에 실제 파일 객체의 포인터가 저장된다.

상세 설명

추상 개념 (POSIX 규약)

POSIX에서 fd는 다음 규칙을 따른다.

  • fd 0, 1, 2는 관례적으로 stdin, stdout, stderr에 할당된다.
  • POSIX open()과 dup() 계열은 API별 조건에 따라 사용 가능한 가장 낮은 음이 아닌 정수를 선택한다. 따라서 fd 0이 닫혀 있다면 open()이 0을 반환할 수 있다. 현재 PintOS의 process_add_file()은 stdin/stdout을 예약해 명시적으로 fd 2부터 찾는다.
  • fd는 프로세스별 자원이다. 같은 숫자 3이라도 프로세스 A와 B에서 전혀 다른 파일을 가리킬 수 있다.
  • close(fd) 후 해당 번호는 다시 할당 가능해진다.
  • pipe()가 반환하는 fd도 같은 프로세스별 fd table의 음이 아닌 index라는 점에서는 동일하다.

fd 번호가 의미 없는 “이름표”가 아니라 배열 인덱스라는 점이 핵심이다. 커널은 프로세스마다 고정 크기(또는 동적 확장) 배열을 유지하고, fd 번호로 O(1) 접근한다.

실제 OS (Linux)

Linux 커널에서 각 task_struct는 files_struct를 가리키고, 그 안의 fdtable이 struct file * 포인터 배열을 관리한다.

기본 배열 크기는 NR_OPEN_DEFAULT (보통 64)이며, 필요하면 동적으로 확장한다. RLIMIT_NOFILE (기본 1024)이 프로세스당 상한, /proc/sys/fs/nr_open (기본 1,048,576)이 시스템 절대 상한이다.

PintOS 구현

PintOS는 fd 테이블을 단순 배열로 구현한다.

fd 테이블 초기화(process.c:154-155):

  • fd 0, 1은 stdin/stdout 용으로 예약(실제 struct file *를 넣지 않고 syscall에서 특별 처리).
  • process_add_file()(process.c:637)은 fd 2부터 FD_MAX까지 빈 슬롯을 순회하며 가장 작은 빈 번호를 반환한다.
  • process_get_file(fd)(process.c:662)는 범위 검사 후 fd_table[fd]를 직접 반환한다 — O(1).
  • process_close_file(fd)(process.c:673)는 filesys_lock을 잡고 file_close() 후 슬롯을 NULL로 비우고 next_fd를 갱신한다.

POSIX lowest-available 근사 구현:

PintOS의 process_add_file()은 항상 fd=2부터 순회하므로 POSIX의 lowest-available 규칙을 만족한다. 그러나 next_fd는 순수한 “다음 할당 힌트”로, close 시 더 작은 fd로 당겨진다(process.c:693):

단, process_add_file()의 for 루프는 fd=2부터 시작하므로 next_fd 힌트와 무관하게 항상 lowest-available을 보장한다.

QEMU 에뮬레이션

QEMU는 fd와 무관하다 — fd_table은 guest OS 커널 메모리의 순수 소프트웨어 구조체다. 그러나 파일 I/O의 끝단에서 QEMU가 관여한다:
