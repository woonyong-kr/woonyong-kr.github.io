버퍼 캐시

버퍼 캐시

확인 범위: 이 문서는 버퍼 캐시의 일반 원리와 쓰기·교체 정책의 선택 기준을 설명한다. Linux와 PintOS·QEMU의 구조 및 관찰 방법은 이해를 돕는 예시로 다룬다. 코드 좌표와 버전별 동작, 호출 횟수·지연·성능 수치는 특정 구현과 실행 환경의 실제 코드 및 실행 기록으로 별도 검증해야 한다. 본문은 그러한 검증 결과를 보고하지 않는다.

버퍼 캐시가 필요한 이유

버퍼 캐시(buffer cache)는 디스크 섹터의 내용을 RAM에 임시로 보관하는 커널 내부 계층이다. 파일을 읽거나 쓸 때 이 계층을 거치면, 이미 캐시에 들어 있는 섹터는 물리 디스크 I/O 없이 RAM에서 처리할 수 있다. 버퍼 캐시가 없는 구조에서는 inode_read_at()이 호출될 때마다 512 B 단위 PIO가 발생할 수 있다. 이 경우 본문에서 가정한 수십 ms 수준의 디스크 지연이 그대로 드러난다.

디스크는 섹터(512 B) 단위로 접근한다. CPU가 파일에서 일부 바이트만 필요하더라도, 먼저 그 바이트가 포함된 섹터 전체를 RAM으로 읽어야 한다. 본문에서 가정한 디스크와 RAM의 접근 시간 차이는 10^4~10^5배다. 따라서 한 번 읽은 섹터를 RAM에 유지해 다시 사용하는 것이 버퍼 캐시의 기본 목적이다.

읽기·쓰기·교체 흐름

읽기를 요청한 섹터가 캐시에 있으면 cache hit가 발생한다. 이때는 RAM에 있는 데이터를 바로 반환한다. 섹터가 없다면 cache miss이므로 disk_read()로 데이터를 가져온 뒤 캐시 슬롯에 저장하고 반환한다.

쓰기에서는 먼저 캐시 안의 섹터를 수정하고 dirty 상태로 표시한다. Write-back 정책을 사용한다면 이 시점에 disk_write()를 호출하지 않는다. dirty 데이터는 이후 flush가 실행될 때 디스크에 모아서 기록한다.

캐시가 가득 차면 LRU나 clock 같은 교체 정책으로 비울 victim 슬롯을 고른다. 선택한 슬롯이 dirty 상태라면 데이터를 먼저 write-back한 뒤 그 슬롯을 재사용한다.

flowchart TD
  filesys["파일 시스템<br/>inode_read_at()<br/>inode_write_at()"]
  cache["버퍼 캐시<br/>sector -&gt; RAM buffer 매핑<br/>cache hit: RAM에서 반환<br/>dirty slot: 나중에 flush"]
  disk["디스크 I/O<br/>disk_read() / disk_write()<br/>ATA PIO<br/>물리 디스크"]
  filesys --> cache
  cache --> disk

쓰기 정책: Write-through와 Write-back

Write-through와 Write-back은 데이터를 디스크에 기록하는 시점이 다르다. 이 차이는 쓰기 성능과 전원 손실 시의 데이터 유실 위험에 영향을 준다.

항목Write-throughWrite-back (Lazy Write)
동작write 즉시 캐시 + 디스크에 모두 기록캐시만 수정, 나중에 디스크로 flush
장점전원 손실 시 데이터 안전I/O 횟수 대폭 감소, 같은 섹터 반복 쓰기 흡수
단점매 write마다 디스크 I/O 발생dirty 데이터 유실 위험 (전원 손실 시)
사용처임베디드, 안전 최우선 시스템Linux, Windows, 대부분 범용 OS

PintOS Project 4는 write-back을 의도한다. page_cache_writeback()이 dirty 슬롯을 나중에 flush하고, page_cache_kworkerd()가 주기적으로 슬롯을 순회하는 구조다.

교체 정책

캐시가 가득 차면 어떤 슬롯을 내보낼지 결정해야 한다. 각 알고리즘은 최근 접근 시점이나 접근 빈도를 서로 다른 방식으로 사용한다.

알고리즘동작장점단점
LRU가장 오래 접근 안 된 슬롯 교체직관적, hit rate 높음O(n) 탐색 또는 복잡한 자료구조 필요
Clock (Second-chance)circular queue + accessed bit 순회O(1) amortized, 구현 간단LRU 근사, 최적은 아님
LFU접근 빈도 가장 낮은 슬롯 교체자주 쓰는 hot data 보호오래 전 hot data가 evict 안 되는 문제

PintOS VM의 frame eviction은 clock algorithm을 사용한다. 버퍼 캐시에도 같은 알고리즘을 적용할 수 있다. 이때 accessed bit는 frame eviction에서 사용하는 PTE의 A bit가 아니라 캐시 슬롯의 소프트웨어 플래그로 관리한다.

Linux의 버퍼 캐시

Linux에서는 버퍼 캐시가 페이지 캐시(page cache)와 통합되어 있다. struct buffer_head는 블록 디바이스의 섹터 단위 캐싱을 담당하고, 그 위의 struct page 기반 페이지 캐시는 파일 단위 캐싱을 수행한다. 본문에서 설명하는 2.4 커널 이후의 구조에서는 두 계층을 통합해 같은 데이터가 두 곳에 중복으로 캐시되는 문제를 해소했다.

본문이 제시하는 Linux 버퍼 캐시의 주요 설정값은 다음과 같다. 실제 값과 동작은 대상 버전과 실행 환경에서 별도로 확인해야 한다.

  • 기본 블록 크기: 4096 B (파일 시스템 의존)
  • dirty writeback 주기: dirty_writeback_centisecs = 500 (5초)
  • dirty 비율 임계: dirty_ratio = 20% (전체 메모리 대비)
  • dirty_background_ratio: 10% (백그라운드 writeback 시작 임계)

fsync()가 호출되면 해당 inode에 연결된 모든 dirty 버퍼를 즉시 write-back한다.

Linux는 순차 읽기 패턴을 감지하면 아직 요청되지 않은 다음 페이지를 미리 디스크에서 불러오는 Readahead(선행 읽기)를 수행한다. 본문이 제시하는 기본 readahead 창은 128 KB(32 pages)이며, blockdev --setra로 조정할 수 있다. 이 메커니즘은 순차 파일 읽기 성능이 디스크의 순차 대역폭에 가까워지도록 돕는다. PintOS의 page_cache_readahead()라는 함수 이름도 이 개념에서 따왔다.

PintOS 구현 단계

PintOS의 버퍼 캐시 구조는 Project 단계에 따라 달라진다.

Project 1~3에는 버퍼 캐시가 없다. inode_read_at()과 inode_write_at()은 bounce buffer를 거쳐 매번 disk_read() 또는 disk_write()를 직접 호출한다. 섹터보다 작은 범위를 접근할 때는 512 B bounce 버퍼로 섹터 전체를 읽은 뒤 필요한 부분만 복사한다.

이 구조에서는 접근할 때마다 물리 I/O가 발생하므로, 같은 섹터를 반복해서 읽어도 이전 데이터를 재사용하지 못한다.

Project 4에서는 page_cache.c에 버퍼 캐시 스텁이 제공된다. VM 시스템의 struct page 프레임워크 위에 VM_PAGE_CACHE 타입으로 구현하도록 설계된 구조다.

의도된 구현에서는 각 캐시 슬롯이 하나의 struct page와 물리 frame에 대응한다. page_cache_readahead는 디스크에서 데이터를 읽고, page_cache_writeback은 dirty 슬롯을 디스크에 쓴다. page_cache_kworkerd 스레드는 dirty 슬롯을 주기적으로 flush한다.

QEMU에서 보이는 경계

버퍼 캐시는 guest OS 내부의 소프트웨어이므로 QEMU가 직접 에뮬레이션하는 대상은 아니다. guest가 disk_read()를 통해 IN/OUT 명령을 보내면 QEMU의 IDE controller model은 호스트 파일의 해당 오프셋을 읽어 데이터 레지스터에 넣는다. guest의 버퍼 캐시가 같은 섹터에 대한 요청을 흡수하면 QEMU까지 도달하는 I/O 횟수도 줄어든다.

QEMU 호스트 측에도 별도의 캐시 계층이 있다. -drive cache=writeback(기본값)을 사용하면 호스트 OS의 page cache가 디스크 이미지 I/O를 흡수한다. cache=none은 O_DIRECT를 사용해 호스트 page cache를 우회한다. 따라서 PintOS 버퍼 캐시와 호스트 page cache가 동시에 데이터를 캐싱할 수 있다. 벤치마크 결과를 해석할 때는 이 이중 캐싱을 고려해야 한다.

GDB로 관찰할 지점

다음 스크립트는 버퍼 캐시와 디스크 I/O 경로를 관찰하기 위한 방법이다. 실제 호출 횟수와 breakpoint 도달 여부는 대상 코드와 실행 환경에서 확인해야 한다.

1. bounce buffer 사용 확인 — disk_read 호출 횟수 세기:

(gdb) set $disk_read_count = 0
(gdb) break disk_read
(gdb) commands
  silent
  set $disk_read_count = $disk_read_count + 1
  continue
  end
(gdb) # 테스트 실행 후
(gdb) print $disk_read_count

2. inode_read_at에서 bounce vs direct 경로 확인:

(gdb) break filesys/inode.c:197
(gdb) commands
  silent
  printf "sector=%d sector_ofs=%d chunk=%d\n", sector_idx, sector_ofs, chunk_size
  continue
  end

sector_ofs가 0이고 chunk_size가 512이면 direct path를 사용하고, 그렇지 않으면 bounce buffer를 거친다.

3. inode_write_at의 deny_write_cnt 확인:

(gdb) break filesys/inode.c:240
(gdb) commands
  printf "inode=%p deny_write_cnt=%d\n", inode, inode->deny_write_cnt
  continue
  end

4. page_cache.c 스텁 호출 감지 (Project 4):

(gdb) break page_cache_readahead
(gdb) break page_cache_writeback
(gdb) break page_cache_kworkerd

이 breakpoint가 hit되면 VM_PAGE_CACHE 경로가 활성화된 상태다.

5. disk I/O 패턴 분석 — 연속 섹터 접근 감지:

(gdb) set $prev_sector = -1
(gdb) break disk_read
(gdb) commands
  silent
  if sec_ == $prev_sector + 1
    printf "sequential: sector %d\n", sec_
  else
    printf "random: sector %d (gap=%d)\n", sec_, sec_ - $prev_sector
  end
  set $prev_sector = sec_
  continue
  end

이 스크립트로 readahead가 효과를 낼 수 있는 순차 접근 패턴인지 확인할 수 있다.

값과 계산의 의미

항목값
섹터 크기512 B (DISK_SECTOR_SIZE)
bounce buffer 크기512 B (malloc, 재사용)
PintOS 캐시 슬롯 상한 (Project 4 명세)64개
64슬롯 × 512 B32 KB 총 캐시
4 KB page 단위 캐시라면64 × 4096 = 256 KB
Linux dirty writeback5초 간격

본문의 계산에 따르면 4 KB 파일은 512 B 섹터 8개로 구성된다. 버퍼 캐시가 없는 구조에서는 이를 읽을 때 8 섹터 × disk_read() = 8회 PIO가 필요하다. 같은 데이터가 캐시에 남아 있다면 첫 읽기 이후의 반복 읽기는 추가 디스크 I/O 없이 처리할 수 있다.

동일 섹터를 10회 읽는 상황을 가정한 비교는 다음과 같다. 호출 횟수와 예상 지연은 실제 실행 결과가 아니라 본문에 제시된 시나리오다.

방식disk_read() 호출예상 지연 (QEMU IDE 기준)
bounce (캐시 없음)10회~10 × 수백 μs = 수 ms
buffer cache (1회 miss)1회~수백 μs + 9 × RAM 접근 ≈ 수백 μs

이해 점검

  • inode는 파일의 어느 바이트가 어느 디스크 섹터에 있는지 계산하고, 버퍼 캐시는 그 섹터의 내용을 RAM에 잠시 보관한다.
  • cache hit이면 disk_read()를 호출하지 않고 RAM의 데이터를 복사한다. cache miss이면 디스크에서 섹터를 읽어 캐시 슬롯을 채운다.
  • dirty 캐시 슬롯은 수정된 데이터가 아직 RAM에만 있는 상태다. 이 데이터는 fsync()나 주기적 flush가 실행될 때 디스크에 기록되어야 한다.
