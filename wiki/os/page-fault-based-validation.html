Page Fault 기반 유저 포인터 검증

Page Fault 기반 유저 포인터 검증

한 줄 요약: 유저 포인터 검증은 접근 전에 PML4를 걷는 verify-then-dereference와 일단 접근 후 fault로 처리하는 fault-based 두 방식이 있고, PintOS는 전자를 기본으로 lazy loading·stack growth에 후자를 병행한다.

Page Fault 기반 유저 포인터 검증 구조

유저 포인터를 검증하는 방식은 크게 두 가지다. 하나는 접근 전에 미리 PML4를 walk하여 매핑을 확인하는 “verify-then-dereference” 방식이고, 다른 하나는 일단 접근하고 page fault가 나면 처리하는 “fault-based” 방식이다. PintOS는 주로 전자를 쓰되, VM 프로젝트에서 lazy loading과 stack growth를 처리할 때 page fault handler가 합법적 접근을 구제하는 후자 방식도 병행한다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

x86-64 CPU가 메모리 접근 명령을 실행하면, MMU가 4단계 page table을 walk한다. 매핑이 없거나 권한이 맞지 않으면 CPU는 #PF (Interrupt 14) 예외를 발생시킨다. 이때 CPU는 자동으로:

  1. CR2 레지스터에 fault 주소를 저장
  2. error code를 스택에 push한다. PintOS는 P, W/R, U/S 비트를 주로 쓰지만 x86-64에는 RSVD, instruction fetch, protection key 등 추가 비트도 정의된다.
  3. IDT 14번 핸들러로 점프
error code 비트의미
PF_P (bit 0)0 = not present, 1 = 권한 위반
PF_W (bit 1)0 = 읽기 접근, 1 = 쓰기 접근
PF_U (bit 2)0 = 커널 모드, 1 = 유저 모드

핵심은 fault 후에도 같은 명령어가 재시도된다는 점이다. 핸들러가 매핑을 설치하고 iret하면, CPU는 fault를 일으킨 정확히 그 명령어를 다시 실행한다(RIP가 fault 명령어를 가리키고 있으므로).

실제 OS (Linux/Windows)

Linux: copy_from_user() / copy_to_user() 앞의 access_ok()는 일반적으로 user range를 검사하며 page table을 완전히 미리 walk해 모든 byte를 보장하는 절차가 아니다. 실제 user-memory 접근 중 fault는 architecture별 exception table·fixup 경로가 처리해 kernel panic 대신 미복사 byte 수나 -EFAULT로 변환한다.

/* 개념적 흐름 */
.text:   movl (%rdi), %eax      # 유저 주소 접근 시도
.fixup:  movl $-EFAULT, %eax    # fault 시 이리로 점프
.ex_table: .text 주소, .fixup 주소

Windows: __try / __except 구조적 예외 처리(SEH)로 유저 메모리 접근 fault를 포착한다.

PintOS 구현

PintOS는 두 방식을 계층적으로 결합한다.

방식 1: Verify-then-dereference (기본)

pml4e_walk()로 PTE를 찾고, present 비트와 writable 비트를 직접 확인한다.

방식 2: Page fault handler (VM 프로젝트)

vm_try_handle_fault()가 SPT에서 페이지를 찾아 물리 프레임을 할당하고 PTE를 설치하면, page_fault()가 정상 return → iret → CPU가 같은 명령어를 재시도한다.

두 방식이 만나는 지점:

%% try_claim_user_addr에서 두 검증 방식이 만나는 흐름
flowchart TD
  entry["try_claim_user_addr()"]
  range["is_user_vaddr()<br/>유저 주소 범위 검사"]
  pml4["user_page_accessible()<br/>PML4 walk"]
  spt["[VM] spt_find_page()<br/>vm_claim_page()"]
  fault["[VM] vm_try_handle_fault()<br/>stack growth 등"]
  entry --> range
  range --> pml4
  pml4 --> spt
  spt --> fault

syscall 진입 시 try_claim_user_addr()에서 가능한 한 사전 검증하되, lazy page나 stack growth처럼 fault를 통해서만 알 수 있는 경우에는 vm_try_handle_fault()를 호출한다.

두 방식의 비교

항목Verify-then-dereferenceFault-based
검사 시점접근 전접근 시 (fault 발생 후)
구현 복잡도낮음높음 (exception table / handler 필요)
성능매번 PML4 walk 비용fault 없으면 비용 0, fault 시 비용 큼
TOCTOU 안전성취약 (검사~접근 사이 변경 가능)안전 (하드웨어가 원자적으로 판단)
lazy loading 지원SPT 별도 조회 필요자연스럽게 통합

TOCTOU (Time-of-check to time-of-use) 문제: 멀티스레드 환경에서 스레드 A가 verify 통과 후 접근하기 전에 스레드 B가 매핑을 해제하면, 커널이 invalid 주소를 접근하게 된다. fault-based 방식은 CPU가 접근과 검사를 하드웨어적으로 동시에 수행하므로 이 문제가 없다. PintOS는 단일 CPU에서 동작하고, 커널 내부에서 preemption이 제한적이어서 TOCTOU가 심각한 문제는 아니지만, 실제 OS에서는 중요한 차이다.

항목값

CR2 레지스터fault 주소 저장 (64비트)
error code 저장 폭legacy 32-bit PintOS 설명에서는 32-bit 값으로 다루며 하위 P/W/U를 사용한다. KAIST x86-64 intr_frame에서는 64-bit slot으로 보존하고 같은 하위 비트를 해석한다.

fault → handler 진입 latency~100-300 cycles (x86-64)
