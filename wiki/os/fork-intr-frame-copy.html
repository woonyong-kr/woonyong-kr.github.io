fork — intr_frame 복사와 rax=0

fork — intr_frame 복사와 rax=0

범위: 이 문서는 fork가 실행 상태를 복제하고 자식의 반환값을 구분하는 일반 원리와, 제시된 Linux·PintOS 코드에서 intr_frame 복사 및 rax=0 설정이 이루어지는 방식을 설명한다. 구조체 크기·복사 횟수·offset·코드 위치·QEMU 동작·경합 여부는 특정 구현과 현재 코드 상태에 의존하므로, 실제 버전의 소스와 빌드·GDB 실행 기록을 확인해야 검증 결과로 판단할 수 있다.

한 줄 요약: fork가 부모와 같은 지점에서 시작하는 자식을 만드는 비결은 부모의 intr_frame(전체 레지스터 스냅샷)을 통째로 복사하되 자식의 rax만 0으로 바꿔 부모(자식 tid)와 자식(0)을 반환값으로 구분하는 것이다.

fork 상태

fork()가 “부모와 같은 지점에서 실행을 시작하는 자식”을 만들 수 있는 이유는, 부모의 struct intr_frame을 자식에게 통째로 복사하기 때문이다. 현재 packed intr_frame은 CPU 실행 상태(RIP, RSP, 범용 레지스터, RFLAGS 등)를 담은 192-byte 스냅샷이므로, 이것을 복사하면 자식은 부모가 중단된 바로 그 명령어에서 재개할 수 있다.

단, 딱 한 가지 — rax만 0으로 바꾼다. x86-64 ABI에서 함수 반환값은 RAX에 담기므로, 부모는 fork()에서 자식 tid를 받고 자식은 0을 받아 서로를 구분한다.

상세 설명

추상 개념 (fork의 핵심 원리)

fork의 의미는 “현재 실행 상태를 복제한다”이다. 실행 상태란 곧 CPU 레지스터 집합이며, OS에서 이것을 담는 구조체가 intr_frame이다.

부모 fork() 호출 시점의 레지스터:
  RIP = fork() 반환 직후 명령어 주소
  RSP = 유저 스택 꼭대기
  RAX = (아직 반환값 미정)
  RDI, RSI, ... = fork() 호출 시점의 값

자식이 받는 복사본:
  RIP = 동일  ← 같은 명령어에서 시작
  RSP = 동일  ← 같은 스택 위치
  RAX = 0     ← 유일한 차이: fork() 반환값 = 0
  RDI, RSI, ... = 동일

이 원리는 POSIX 표준이며, Linux, macOS, PintOS 모두 동일하다.

실제 OS (Linux)

Linux의 copy_thread_tls() (arch/x86/kernel/process.c):

Linux는 추가로 childregs->sp를 자식 커널 스택으로 조정하고, ret_from_fork를 통해 유저 모드로 복귀한다.

PintOS 구현

PintOS의 fork frame 전달은 3단계로 이루어진다:

1단계: 부모가 frame을 args에 값 복사

부모가 syscall_handler(struct intr_frame *f)를 통해 받은 if_ 포인터가 가리키는 frame은 부모의 커널 스택 위에 있다. 이것을 heap에 할당된 fork_args로 값 복사한다. 부모 스레드가 다른 인터럽트를 받아도 args->if_는 안전하다.

2단계: 자식이 args에서 로컬 변수로 복사

자식 thread는 __do_fork()에서 로컬 struct intr_frame if_를 선언하고, args에서 memcpy한 뒤 args를 해제한다. 이제 frame은 자식의 커널 스택에 있다.

3단계: rax=0 설정 후 do_iret()

do_iret()은 if_의 모든 레지스터를 CPU에 복원하고 iretq로 유저 모드에 진입한다. 자식은 부모가 fork()를 호출한 바로 다음 명령어에서 실행을 시작하며, RAX=0이므로 fork() == 0 분기를 탄다.

주의: sema_up 이후 부모는 즉시 실행 재개할 수 있다. 하지만 자식은 아직 do_iret를 호출하지 않은 상태(커널 모드)이므로 경합은 없다 — 자식의 유저 주소 공간은 이미 완전히 복제 완료된 상태다.

왜 포인터가 아니라 값 복사인가

부모의 frame은 부모 커널 스택에 있다. 자식이 이 포인터를 직접 쓰면:

  • 부모가 syscall에서 복귀하면 스택이 해제되어 dangling pointer
  • 부모에게 다음 인터럽트가 오면 frame이 덮어씌워짐

따라서 heap(fork_args)을 거치는 2회 값 복사가 필수적이다.

QEMU 에뮬레이션

QEMU 관점에서 fork frame 복사 과정은 대부분 순수 소프트웨어 동작이다. 구조체 값 복사는 guest memory 안의 현재 packed intr_frame 192 bytes를 옮길 뿐이며, QEMU의 특별한 개입은 없다.

QEMU가 개입하는 유일한 순간: iretq

do_iret()의 iretq 명령어에서 QEMU TCG는 gen_helper_iret_protected()를 호출한다:

  1. 스택에서 RIP, CS, RFLAGS를 pop하고, CPL 0→3 전환이므로 RSP와 SS도 pop
  2. CS의 RPL 비트(하위 2비트)를 확인 → 현재 SEL_UCSEG=0x23 → RPL=3
  3. CPL을 3으로 전환 (kernel → user mode)
  4. env->eip을 새 RIP로 설정 → 기존 TranslationBlock 무효화 → 새 TB 생성

GDB에서 fork frame 복사 관찰법

(gdb) b __do_fork
(gdb) c
[자식 thread가 __do_fork에 진입]

# 1. memcpy 직후 자식의 로컬 if_ 확인
(gdb) n  # memcpy 실행
(gdb) p/x if_.R.rax        # 아직 부모의 반환값(부모 tid)
(gdb) p/x if_.rip          # 부모가 fork() 호출한 다음 명령어

# 2. rax=0 설정 관찰
(gdb) n  # if_.R.rax = 0 실행
(gdb) p/x if_.R.rax        # 0x0 확인

# 3. do_iret 직전 frame 전체 덤프
(gdb) p if_                 # 현재 packed layout 192 bytes 확인
(gdb) p/x if_.cs            # 0x23 (SEL_UCSEG, user code selector)

# 4. do_iret 이후 유저 모드 확인
(gdb) b *if_.rip            # 자식이 도착할 유저 주소에 BP
(gdb) c
(gdb) p $rax                # 0x0 — fork() 반환값
(gdb) p $cs                 # RPL=3 확인

fork 값

intr_frame 크기:       192 bytes
fork 당 복사 횟수:     2회 (부모→heap, heap→자식)
총 복사량:             192 × 2 = 384 bytes

rax 변경 offset:
  gp_registers 내 rax 위치 = 마지막 필드
  struct gp_registers 시작부터 rax field까지: 14 × 8 = 112 bytes
  intr_frame 시작부터 R.rax field까지: 112 bytes
  gp_registers 전체 크기: 15 × 8 = 120 bytes
