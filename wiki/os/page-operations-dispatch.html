page_operations 분기

page_operations 분기

한 줄 요약: struct page의 UNINIT·ANON·FILE 타입은 프레임을 채우고, 내보내고, 정리하는 방식이 서로 다르다. PintOS는 이러한 다형성을 OOP의 vtable에 해당하는 struct page_operations 함수 포인터 테이블로 구현한다. 따라서 page->operations->swap_in()을 한 번 호출하면 page 타입에 맞는 함수로 분기된다.

page_operations 분기 흐름

PintOS VM의 struct page는 UNINIT, ANON, FILE 가운데 한 타입을 가진다. 타입마다 프레임에 내용을 채우는 방법, 프레임의 내용을 내보내는 방법, 자원을 정리하는 방법이 다르다.

PintOS는 이러한 차이를 struct page_operations라는 함수 포인터 테이블로 표현한다. 이 구조체는 OOP 언어의 vtable과 같은 역할을 한다. 호출하는 쪽에서 page->operations->swap_in(page, kva)를 실행하면 현재 page 타입에 연결된 함수가 선택된다. UNINIT page라면 uninit_initialize, ANON page라면 anon_swap_in, FILE page라면 file_backed_swap_in이 실행된다.

이 구조를 이해하려면 세 타입의 메서드가 맡는 책임뿐 아니라, 각 메서드가 언제 호출되고 UNINIT page가 언제 ANON 또는 FILE page로 전환되는지도 함께 살펴봐야 한다.

상세 설명

추상 개념 — 함수 포인터 테이블로 만드는 다형성

하드웨어나 CPU는 page_operations를 알지 못한다. page_operations는 PintOS 커널이 page 타입별 동작을 구분하기 위해 사용하는 소프트웨어 설계다.

각 page에는 그 page를 다루는 함수들의 주소가 담긴 테이블을 가리키는 포인터가 있다. page 타입이 바뀌면 이 포인터가 가리키는 테이블도 교체된다.

덕분에 호출하는 코드는 page 타입을 직접 확인하지 않아도 된다.

타입을 구분하는 if-else나 switch 대신 함수 포인터를 따라가면 현재 타입에 맞는 구현이 실행된다.

실제 OS (Linux/Windows)

Linux도 같은 패턴을 쓴다.

  • struct address_space_operations: readpage(), writepage(), releasepage() 등 backing store별 함수 포인터
  • struct vm_operations_struct: fault(), map_pages(), page_mkwrite() 등 VMA별 fault 처리

Windows도 prototype PTE, section object, pagefile handler 등 backing 유형별로 page fault 처리를 분기한다.

PintOS의 page_operations는 이 구조를 교육용으로 단순화한 것이다. 실제 OS에서는 메서드가 수십 개에 이를 수 있지만, PintOS는 swap_in, swap_out, destroy 세 동작으로 범위를 좁힌다.

메서드별 상세

1. swap_in — “프레임에 내용을 채운다”

호출 시점: vm_do_claim_page() → swap_in(page, frame->kva)

UNINIT의 swap_in = uninit_initialize()

이 함수는 프레임의 내용만 채우는 것이 아니라 page 자체를 다른 타입으로 전환한다는 점에서 특별하다.

함수가 실행되고 나면 page->operations는 uninit_ops에서 anon_ops 또는 file_ops로 바뀐다. 이후 같은 page에서 swap_in이 다시 필요해지면 uninit_initialize가 아니라 anon_swap_in이나 file_backed_swap_in이 실행된다.

%% uninit_initialize()에서 union을 덮기 전 값을 보존하고 단락 평가로 반환하는 순서
sequenceDiagram
  participant Claim as vm_do_claim_page()
  participant Uninit as uninit_initialize()
  participant Page as struct page
  participant Initializer as page_initializer()
  participant Lazy as init(page, aux)
  Claim->>Uninit: swap_in(page, kva)
  Uninit->>Page: init과 aux를 local에 저장
  Uninit->>Initializer: initializer(page, type, kva)
  alt VM_ANON
    Initializer->>Page: page->operations = &anon_ops
  else VM_FILE
    Initializer->>Page: page->operations = &file_ops
  end
  alt initializer 실패
    Initializer-->>Uninit: false
    Uninit-->>Claim: false, init은 호출하지 않음
  else initializer 성공
    Initializer-->>Uninit: true
    Uninit->>Lazy: saved init(page, saved aux)
    Lazy-->>Uninit: true 또는 false
    Uninit-->>Claim: lazy 결과 반환
  end

여기서 uninit->init과 uninit->aux는 page_initializer 호출 전에 꺼내야 한다. page_initializer가 union을 anon_page나 file_page로 덮어쓰면 기존 uninit 멤버를 더 이상 그대로 읽을 수 없기 때문이다.

ANON의 swap_in = anon_swap_in()

eviction으로 swap disk에 옮겨졌던 anonymous page를 프레임으로 복원한다.

FILE의 swap_in = file_backed_swap_in()

eviction으로 프레임을 잃은 file-backed page를 파일에서 다시 읽는다.

2. swap_out — “프레임 내용을 backing store로 내보낸다”

호출 시점: vm_evict_frame() → victim page를 골라 swap_out(page)

UNINIT의 swap_out = NULL

UNINIT page는 아직 frame을 가진 적이 없으므로 eviction 대상이 될 수 없다. 따라서 swap_out은 NULL이다. swap_out 매크로는 NULL 여부를 확인하지 않고 함수를 호출하므로, UNINIT page가 eviction victim으로 잘못 선택되면 크래시한다. 이는 frame이 없는 UNINIT page는 victim이 될 수 없다는 전제에 따른 설계다.

ANON의 swap_out = anon_swap_out()

FILE의 swap_out = file_backed_swap_out()

anon page는 항상 swap disk에 내용을 써야 한다. 반면 file-backed page는 dirty일 때만 원본 파일에 write-back한다. clean file-backed page의 내용은 원본 파일에서 다시 읽을 수 있으므로 별도로 쓰지 않아도 된다.

3. destroy — “page 자원을 정리한다”

호출 시점: vm_dealloc_page() → destroy(page) → free(page)

UNINIT의 destroy = uninit_destroy()

프로세스가 종료될 때 한 번도 fault되지 않은 page가 남아 있을 수 있다. aux가 동적으로 할당되었다면 이 단계에서 해제해야 한다.

ANON의 destroy = anon_destroy()

FILE의 destroy = file_backed_destroy()

QEMU 에뮬레이션

QEMU는 page_operations 추상화를 알지 못한다. QEMU가 관찰하고 에뮬레이션하는 동작은 다음과 같다.

  • guest CPU가 메모리에 접근하면 guest page table을 walk한다
  • PTE가 present가 아니면 pf를 guest에 전달한다
  • PintOS 커널이 swap disk sector를 읽으면 QEMU IDE controller가 block I/O를 수행한다
  • PintOS가 page table을 고치면 QEMU는 다음 접근에서 새 PTE를 읽는다

swap_in, swap_out, destroy는 모두 PintOS 커널이 결정하는 소프트웨어 정책이다. QEMU는 이 정책의 결과로 일어나는 page table 변경, disk I/O, 메모리 접근과 같은 하드웨어 효과만 에뮬레이션한다.

union 메모리 레이아웃

uninit_page, anon_page, file_page는 union 멤버이므로 같은 메모리 공간을 공유한다.

x86-64에서 설명을 위해 각 field의 크기를 더하면 uninit_page는 function pointer 8B + enum 4B + aux pointer 8B + initializer pointer 8B로 28B다. file_page는 file pointer 8B + off_t 4B + read_bytes 8B + zero_bytes 8B로 역시 28B다. alignment padding을 포함한 대표적인 sizeof는 둘 다 32B가 될 수 있다. 다만 실제 크기는 구현의 field와 ABI에 따라 달라지므로 대상 build에서 확인해야 한다.

%% struct page와 union 메모리 레이아웃
flowchart LR
  page["struct page<br/>operations pointer · va · frame · writable"]
  uninit["uninit_page<br/>init 8B · type 4B · aux 8B · initializer 8B<br/>field 합 약 28B + padding"]
  anon["anon_page<br/>swap_slot 등<br/>구현에 따라 다름"]
  file["file_page<br/>file 8B · off_t 4B · read_bytes 8B · zero_bytes 8B<br/>field 합 28B, 대표 sizeof 32B"]
  page -->|"union 멤버"| uninit
  page -->|"같은 공간"| anon
  page -->|"같은 공간"| file

이 메모리 공유 방식 때문에 uninit_initialize는 aux를 미리 꺼내야 한다. anon_initializer가 page->operations = &anon_ops를 쓰고 page->anon을 활성 union 멤버로 사용하기 시작한 뒤 page->uninit.init을 읽으면, 같은 공간에 놓인 page->anon의 바이트를 다른 타입으로 잘못 해석하게 된다.
