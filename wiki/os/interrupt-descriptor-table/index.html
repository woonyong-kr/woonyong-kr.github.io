인터럽트 디스크립터 테이블 (Interrupt Descriptor Table)

인터럽트 디스크립터 테이블 상태

IDT는 x86-64 CPU가 인터럽트·예외·소프트웨어 트랩을 받았을 때 “어떤 코드를 실행할지” 알려주는 벡터 테이블이다. 256개 엔트리를 가지며, 각 엔트리(Gate Descriptor)에 핸들러 함수 주소와 권한 정보(DPL)가 담긴다. CPU는 인터럽트 벡터 번호를 인덱스로 IDT를 조회해 핸들러로 점프한다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

x86-64 CPU는 IDTR 레지스터에 IDT의 선형 base 주소와 크기(limit)를 보관한다. 주소 변환이 활성화된 환경에서 이 base를 물리 주소라고 부르면 안 된다. 인터럽트가 발생하면 CPU가 자동으로 수행하는 단계:

  1. 벡터 번호로 IDT[vector] 참조
  2. Gate Descriptor에서 target CS:RIP, IST, DPL 추출
  3. 소프트웨어 INT n이면 CPL과 gate DPL을 검사하고, 권한이 부족하면 #GP 발생. 하드웨어 IRQ와 CPU 예외에는 이 검사를 같은 방식으로 적용하지 않음
  4. 유저 모드(CPL=3) → 커널 모드(CPL=0) 전환 시 TSS.rsp0에서 커널 스택 로드
  5. 기존 SS, RSP, RFLAGS, CS, RIP를 커널 스택에 push (= intr_frame의 뼈대)
  6. Interrupt Gate이면 RFLAGS.IF=0 (인터럽트 비활성화), Trap Gate이면 IF 유지
  7. Gate의 target RIP로 점프

IDT 엔트리는 16바이트 Gate Descriptor:

Bit 범위        | 필드
0-15           | offset_15_0 (핸들러 주소 하위 16비트)
16-31          | segment selector (CS, 보통 커널 코드 세그먼트)
32-34          | IST (Interrupt Stack Table 인덱스, 0이면 미사용)
35-39          | reserved
40-43          | type (0xE=Interrupt Gate, 0xF=Trap Gate)
44             | 0 (system segment)
45-46          | DPL (0=커널만 호출, 3=유저도 호출 가능)
47             | P (present)
48-63          | offset_31_16
64-95          | offset_63_32 (x86-64 확장)
96-127         | reserved

핵심 구분:

Gate Type IF 변경 용도
Interrupt Gate (0xE) IF=0 (끔) 하드웨어 인터럽트, 대부분의 예외
Trap Gate (0xF) IF 유지 소프트웨어 트랩 (syscall, breakpoint)

벡터 번호 할당 관례:

범위 용도
0-19 CPU 예외 (#DE, #DB, #BP, #OF, #PF 등)
20-31 Intel 예약
32-47 IRQ 0-15 (PIC 리매핑 후)
48-255 소프트웨어 인터럽트, 자유 사용

실제 OS (Linux/Windows)

Linux에서 IDT 설정은 arch/x86/kernel/idt.c에서 이루어진다. 부팅 초기 idt_setup_early_traps()로 최소한의 예외 핸들러를 등록하고, 이후 idt_setup_apic_and_irqs()로 전체 인터럽트를 등록한다. Linux는 x86-64에서 syscall 명령어를 사용하므로 시스템 콜은 IDT를 거치지 않고 LSTAR MSR 경로를 탄다. 현대 Linux는 PIC 대신 APIC/IO-APIC를 사용해 벡터 할당이 더 유연하다.

Windows NT는 IDT를 KiInitializeIdt()에서 설정하며, 각 예외/인터럽트에 대응하는 KiTrap* 핸들러를 등록한다.

PintOS 구현

PintOS는 interrupt.c에서 256개 엔트리의 IDT를 관리한다.

IDT 배열과 Gate 구조체:

/* threads/interrupt.c */
#define INTR_CNT 256
static struct gate idt[INTR_CNT];        /* IDT 본체 */
static intr_handler_func *intr_handlers[INTR_CNT];  /* C 핸들러 테이블 */
static const char *intr_names[INTR_CNT]; /* 디버그용 이름 */

struct gate는 16바이트로 x86-64 Gate Descriptor를 그대로 C 비트필드로 표현한다.

초기화 흐름 (intr_init):

  1. pic_init() — 8259A PIC를 초기화, IRQ 0-15를 벡터 0x20-0x2f로 리매핑
  2. 256개 엔트리 모두 intr_stubs[i] (어셈블리 스텁) 주소로 Interrupt Gate 등록
  3. lidt(&idt_desc) — IDTR 레지스터에 IDT 주소/크기 적재

핸들러 등록 API:

void intr_register_ext(uint8_t vec_no,
                       intr_handler_func *handler,
                       const char *name);
/* 외부(하드웨어) 인터럽트 전용 — 벡터 0x20~0x2f, DPL=0, INTR_OFF */

void intr_register_int(uint8_t vec_no, int dpl,
                       enum intr_level level,
                       intr_handler_func *handler,
                       const char *name);
/* 내부 예외/트랩 — DPL과 INTR_ON/OFF 선택 가능 */

dpl=3으로 등록하면 유저 모드에서도 int N 명령으로 호출 가능하다. PintOS에서 syscall 명령어를 사용하므로 시스템 콜은 IDT가 아닌 LSTAR MSR 경로를 탄다.

디스패치 흐름:

하드웨어 인터럽트 / CPU 예외 발생
  → CPU가 IDT[vector]의 어셈블리 스텁으로 점프
    → intr_stubs.S: 레지스터를 스택에 push → intr_frame 구성
      → intr_handler(struct intr_frame *f) 호출
        → intr_handlersvec_no — C 핸들러 실행
        → 외부 인터럽트면 pic_end_of_interrupt(irq) — EOI
        → yield_on_return 플래그 설정 시 thread_yield()

QEMU 에뮬레이션

QEMU TCG는 guest CPU가 인터럽트를 받는 동작을 소프트웨어로 재현한다. cpu_exec() 루프에서 cpu->interrupt_request 플래그를 확인하고, pending interrupt가 있으면 x86 interrupt 경로에서 guest IDT gate를 읽고 type·DPL·CPL·present·offset 등을 해석한다. 그 결과에 따라 guest stack과 RIP/RSP를 갱신한다. QEMU가 PintOS의 C handler 의미를 아는 것은 아니지만 IDT gate 자체는 CPU 규칙대로 해석한다.

QEMU의 IDT 처리 단계 (target/i386/seg_helper.c):

  1. cpu_x86_load_seg_cache()로 IDTR에서 IDT base+limit 획득
  2. vector * 16으로 Gate Descriptor 오프셋 계산, limit 범위 검사
  3. x86_ldq_phys()로 guest 물리 메모리에서 16바이트 Gate Descriptor 로드
  4. Gate의 type 필드 확인 — 0xE(Interrupt Gate)이면 env->eflags의 IF 비트 클리어
  5. CPL 검사: 소프트웨어 인터럽트(int N)면 CPL ≤ DPL 확인, 위반 시 #GP 주입
  6. CPL 3→0 전환 시: TSS에서 RSP0을 읽어 guest 커널 스택으로 교체
  7. SS/RSP/RFLAGS/CS/RIP를 guest 커널 스택에 push (error code가 있으면 추가 push)
  8. Gate의 target CS:RIP를 env->eip/env->segs[R_CS]에 설정

GDB로 QEMU의 IDT 처리를 관찰하려면:

(gdb) info registers idtr    # IDTR base와 limit 확인
(gdb) set $idt_base = 0x...   # 위 출력의 base 값을 명시적으로 대입
(gdb) x/2gx $idt_base + 14*16 # #PF(벡터 14) Gate Descriptor 원시 바이트
(gdb) x/5gx $rsp              # 인터럽트 진입 후 커널 스택에 push된 값 확인

IST (Interrupt Stack Table) 심화

IST는 x86-64에서 도입된 메커니즘으로, 특정 인터럽트에 대해 무조건 미리 지정된 스택으로 전환한다. TSS 안에 7개의 IST 포인터(IST1~IST7)가 있고, Gate Descriptor의 IST 필드(3비트)가 0이 아니면 해당 IST 스택을 사용한다.

IST가 필요한 이유: 일반적인 인터럽트는 현재 CPL이 0이면 스택 전환 없이 현재 커널 스택을 그대로 사용한다. 그런데 커널 스택 자체가 손상된 상태(#DF, Double Fault)이거나 NMI처럼 언제든 발생할 수 있는 경우, 손상된 스택 위에서 핸들러를 실행하면 복구 불가능하다. IST는 이런 치명적 예외에 대해 독립된 스택을 보장한다.

Linux의 IST 할당:

IST 슬롯 벡터 용도 이유
IST 1 #DF (8) Double Fault 스택 손상 상태에서도 동작해야 함
IST 2 NMI (2) Non-Maskable Interrupt IF=0이어도 발생, 기존 스택 상태 불확실
IST 3 #MC (18) Machine Check 하드웨어 오류, 즉시 처리 필수
IST 4 #DB (1) Debug Exception 커널 디버깅 중첩 방지

PintOS가 IST를 쓰지 않는 이유: PintOS는 make_gate() 매크로에서 .ist = 0으로 고정한다(interrupt.c:85). 교육용 OS이므로 Double Fault 복구 같은 고급 기능이 불필요하고, 커널 스택 overflow 시 단순히 패닉하면 충분하다. 실제 OS에서는 IST 없이 #DF를 처리하면 triple fault → 즉시 리부트가 발생한다.

인터럽트 디스크립터 테이블 값 추적

  • IDT 엔트리 크기: 16바이트 x 256 = 4096바이트 (정확히 1 page)
  • PintOS IDTR limit: 256 x 16 - 1 = 4095 (0xFFF)
  • PIC 리매핑: IRQ 0 → 벡터 0x20 (32), IRQ 7 → 벡터 0x27
  • Timer IRQ = IRQ 0 = 벡터 0x20 (32)
  • Keyboard IRQ = IRQ 1 = 벡터 0x21 (33)
  • IDE primary = IRQ 14 = 벡터 0x2e (46)
  • Page Fault = 벡터 0x0e (14)

PintOS IDT에서 등록되는 핸들러 목록

PintOS 소스에서 실제로 intr_register_ext()와 intr_register_int()로 등록하는 핸들러:

벡터 등록 함수 핸들러 Gate 타입 DPL 등록 위치
0x0E (14) intr_register_int page_fault() Interrupt (IF 끔) 0 userprog/exception.c
0x20 (32) intr_register_ext timer_interrupt() Interrupt (IF 끔) 0 devices/timer.c
0x21 (33) intr_register_ext keyboard_interrupt() Interrupt (IF 끔) 0 devices/input.c
0x2E (46) intr_register_ext IDE channel 0 Interrupt (IF 끔) 0 devices/ide.c
0x2F (47) intr_register_ext IDE channel 1 Interrupt (IF 끔) 0 devices/ide.c

모든 외부 인터럽트(intr_register_ext)는 DPL=0, INTR_OFF(Interrupt Gate)로 고정된다. 내부 예외(intr_register_int)에서 INTR_ON을 지정하면 Trap Gate가 된다.

IDT Gate 타입 확인 (Interrupt vs Trap) 

(gdb) # 벡터 N의 Gate type 필드 추출 (offset 5의 bits 0-3)
(gdb) define show_gate_type
  set $base = (uint8_t *)$arg0
  set $vec = $arg1
  set $type_byte = *($base + $vec * 16 + 5)
  set $type = $type_byte & 0xF
  set $dpl = ($type_byte >> 5) & 0x3
  printf "IDT[%d]: type=0x%x (%s), DPL=%d\n", $vec, $type, \
    $type == 0xE ? "Interrupt" : "Trap", $dpl
end
(gdb) show_gate_type idt 0x20
(gdb) show_gate_type idt 0x0E

IST 미사용 확인 (PintOS에서 모든 Gate의 IST=0) 

(gdb) define check_all_ist
  set $i = 0
  set $non_zero = 0
  while $i < 256
    set $ist_byte = *((uint8_t *)idt + $i * 16 + 4)
    set $ist = $ist_byte & 0x7
    if $ist != 0
      printf "IDT[%d] has IST=%d (unexpected!)\n", $i, $ist
      set $non_zero = $non_zero + 1
    end
    set $i = $i + 1
  end
  printf "Total non-zero IST entries: %d (expected 0 for PintOS)\n", $non_zero
end
(gdb) check_all_ist

관찰 시나리오 1: 유저→커널 전환 전체 추적

  1. b intr_handler if (f->cs & 3) == 3 — 유저 모드에서 온 인터럽트만 포착
  2. hit 시 p/x f->rsp — 유저 스택 주소 (보통 0x47480000 부근)
  3. p/x $rsp — 현재 커널 스택 주소 (보통 0x8004xxxx 부근)
  4. p/x thread_current()->tf.rsp — TSS.rsp0으로 전환된 커널 스택 확인
  5. 이 차이가 TSS + IDT의 자동 스택 전환 결과

# pic_end_of_interrupt 직전에 BP를 걸고, skip하면 이후 같은 IRQ가 오지 않는 것을 확인

set $normal = 0

commands

  set $normal = $normal + 1

    printf "10th timer: now skipping EOI to observe blocking\n"

  end
