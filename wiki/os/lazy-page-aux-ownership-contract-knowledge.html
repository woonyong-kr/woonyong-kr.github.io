lazy page aux ownership 계약

lazy page aux ownership 계약

lazy aux 소유권 쟁점

file 수명 Trace에서는 executable lazy page가 aux에 file offset과 read size를 담아 첫 page fault까지 들고 가는 흐름을 봤다.

mmap file page의 aux는 언제 struct file page로 옮겨야 하나에서는 mmap() page도 첫 fault 전에는 UNINIT(FILE)과 aux로 시작할 수 있다고 봤다.

그러면 질문은 이것이다.

executable lazy page와 mmap lazy page는 같은 aux cleanup 규칙을 써도 될까?

짧은 답은 “같은 ownership 원칙을 쓰되, 성공 뒤 metadata가 남아야 하는지는 다르다”다.

lazy aux 소유권 혼동

aux는 작은 포인터처럼 보이지만, 실제로는 미래 page fault handler에게 넘기는 작업지시서다.

작업지시서 안에는 단순 숫자만 있는 것이 아니다. file_reopen()으로 얻은 file reference, heap에 할당한 구조체, page별 offset과 byte count가 같이 들어갈 수 있다.

그래서 다음 세 버그가 자주 생긴다.

잘못된 규칙결과
성공 뒤 callback도 free(aux)하고 destroy도 다시 free(aux)double free 또는 double close
실패 뒤 callback이 false만 반환하고 aux를 방치file reference와 heap memory leak
fork()가 부모 aux 포인터를 자식과 공유한쪽 exit이 다른 쪽 lazy page의 작업지시서를 깨뜨림

이 말은 즉, aux는 “어디서 쓰는가”보다 “누가 소유하는가”를 먼저 정해야 한다.

lazy aux 소유권 흐름

UNINIT page의 ownership은 상태별로 나누면 명확하다.

상태page operationsownercleanup 책임
등록 직후uninit_opspage->uninit.auxfault 전 destroy면 uninit_destroy()

가장 중요한 문장은 이것이다.

destroy(page)는 현재 page->operations를 따라간다. 따라서 page_initializer()가 page->operations = &file_ops로 바꾼 뒤 callback이 실패하면, 나중 cleanup은 file_backed_destroy() 쪽으로 들어갈 수 있다.

첫 fault 전 상태는 executable segment든 mmap page든 비슷하다.

성공 뒤 executable lazy page는 보통 aux가 더 필요 없다.

반대로 mmap page는 성공 뒤에도 file offset과 read size가 필요하다. 나중에 dirty page를 write-back해야 하기 때문이다.

이 경우 file reference의 owner는 aux에서 page->file로 넘어갔다. 따라서 free(aux)는 wrapper만 해제하고, file_close(page->file.file)은 file_backed_destroy() 또는 do_munmap()의 책임으로 남긴다.

실제 운영체제

Linux는 mmap() 범위를 VMA로 기억하고, file reference와 page cache를 통해 fault 이후에도 backing file 의미를 보존한다. executable demand paging도 VMA와 file mapping 정보를 바탕으로 필요한 page를 읽는다.

Windows도 section object, mapped view, VAD 같은 구조로 file mapping의 수명과 권한을 관리한다.

현실 OS에는 PintOS의 aux처럼 학생이 직접 만든 작은 구조체가 그대로 있지는 않다. 하지만 원칙은 같다.

PintOS

W09 PintOS skeleton에서 aux ownership을 결정해야 하는 근거는 이미 코드에 있다.

struct page는 type별 metadata를 union으로 둔다.

이 말은 page->uninit.aux와 page->file이 같은 저장 공간을 다른 타입으로 해석한다는 뜻이다.

uninit_new()는 page를 아직 frame 없는 작업지시서 상태로 만든다.

첫 fault에서는 uninit_initialize()가 aux를 지역 변수로 꺼낸 뒤 page type을 바꿀 수 있는 initializer를 호출한다.

여기서 aux를 먼저 지역 변수에 잡는 이유가 중요하다. page_initializer()가 union을 덮어쓰면 page->uninit.aux 자리는 더 이상 안전한 저장소가 아니기 때문이다.

따라서 구현 계약은 이렇게 잡을 수 있다.

QEMU

QEMU는 이 ownership 계약을 모른다.

QEMU가 보는 것은 CPU와 장치 수준의 결과뿐이다.

  • present PTE가 없으면 EXCP0E_PAGE를 만들고 fault address를 guest CR2에 넣는다.
  • user store가 성공하면 x86 page walk 과정에서 dirty bit를 세울 수 있다.
  • PintOS file system이 sector write를 요청하면 IDE/block backend write로 내려간다.

즉, aux leak이나 double close는 QEMU가 직접 감지해 주지 않는다. QEMU는 page fault와 dirty bit 같은 하드웨어 효과를 재현하고, aux lifetime은 PintOS 커널 내부 정책이다.

lazy aux 소유권 코드

PintOS W09에서 확인할 위치:

  • pintos/include/vm/vm.h:44-60: struct page가 uninit, anon, file을 union으로 묶는다.
  • pintos/include/vm/uninit.h:12-18: struct uninit_page가 init, future type, aux, page_initializer를 저장한다.
  • pintos/vm/uninit.c:27-42: uninit_new()가 page->uninit.aux = aux 상태를 만든다.
  • pintos/vm/uninit.c:47-56: uninit_initialize()가 aux를 지역 변수에 보존한 뒤 initializer와 callback을 호출한다.
  • pintos/vm/uninit.c:59-68: 한 번도 참조되지 않은 UNINIT page가 process exit에 남을 수 있으므로 destroy가 필요하다고 말한다.
  • pintos/vm/file.c:23-29: file_backed_initializer()가 page->operations = &file_ops로 전환하는 자리다.
  • pintos/filesys/file.c:35-37: file_reopen()은 mapping 생명주기를 fd close와 분리할 수 있는 새 file object를 만든다.

QEMU에서 확인할 위치:

  • target/i386/tcg/system/excp_helper.c:516-520: page fault exception과 cr2 = addr를 만든다.
  • target/i386/tcg/system/excp_helper.c:651-653: fault address를 guest CR2에 반영한다.
  • target/i386/cpu.h:323-336: dirty bit 위치와 mask가 정의된다.
  • target/i386/tcg/system/excp_helper.c:417-428: store 접근에서 accessed/dirty bit를 세울 수 있다.
  • hw/ide/core.c:1076-1102: PintOS가 IDE sector write를 요청하면 QEMU block backend write로 내려간다.
  • include/block/block-common.h:263-264: QEMU block sector는 1 << 9 = 512바이트다.

lazy aux 소유권 GDB

GDB에서는 aux 포인터와 page->operations가 언제 바뀌는지 같이 보면 된다.

확인할 기준:

  • 첫 fault 전 process exit이면 uninit_destroy()가 aux를 정리해야 한다.
  • page_initializer() 뒤에는 page->uninit.aux를 다시 읽지 않는다.
  • executable lazy 성공 뒤에는 aux와 reopened file이 남지 않는다.
  • mmap lazy 성공 뒤에는 page->file 또는 region metadata가 write-back에 필요한 file reference를 가진다.
  • 실패 경로에서는 false 반환 전에 aux owner가 하나로 결정되어 있어야 한다.

정리

  • aux는 첫 fault 전 UNINIT page가 가진 임시 작업지시서다.
  • UNINIT이 ANON 또는 FILE로 바뀌면 page->uninit.aux 저장소에 계속 의존하면 안 된다.
  • executable lazy page는 성공 뒤 aux를 보통 소비하고 해제한다.
  • mmap lazy page는 성공 뒤 필요한 metadata를 page->file이나 region object로 옮긴다.
  • never-faulted page는 uninit_destroy()가, fault 후 page는 현재 type의 destroy가 정리한다.
  • 실패 경로는 “재시도 가능한 UNINIT 복구”보다 “유저에게 노출하지 않고 destroy 가능한 상태”를 목표로 잡는 편이 안전하다.
