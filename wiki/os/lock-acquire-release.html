락 획득과 해제

락 획득과 해제

lock_acquire()와 lock_release()는 binary semaphore의 down/up에 소유자 추적과 priority donation 처리를 얹어 임계 구역을 보호한다.

락 획득과 해제 차이

lock_acquire()와 lock_release()는 Lock의 두 연산으로, 내부적으로 binary semaphore의 sema_down()/sema_up()을 감싼다. 여기에 소유자 등록, priority donation 전파, donation 철회가 붙으면서 단순한 0/1 세마포어가 “누가 잡았는지”를 아는 Lock이 된다. acquire는 holder가 있으면 donation chain을 따라 우선순위를 전파한 뒤 sema_down()으로 대기하고, release는 이 Lock을 기다리던 기부자들을 제거한 뒤 effective priority를 재계산하고 sema_up()으로 대기자를 깨운다.

상세 설명

추상 개념 (Lock Acquire/Release 의미론)

Lock acquire/release의 정확성 조건은 세 가지다:

조건의미위반 시
상호 배제동시에 두 스레드가 Lock을 잡을 수 없다데이터 경쟁
소유자 일치release는 acquire한 스레드만 가능ASSERT 실패 (PintOS), undefined behavior (Linux)
비재귀같은 Lock을 두 번 acquire 금지데드락 (PintOS는 ASSERT로 사전 차단)

실제 OS (Linux)

Linux mutex_lock() (kernel/locking/mutex.c)는 3단계 경로를 밟는다:

  1. Fast path: atomic_cmpxchg()로 owner를 설정. 성공하면 즉시 반환 — syscall 없이 단일 CAS 명령어.
  2. Midpath (optimistic spinning): owner가 다른 CPU에서 실행 중이면 짧게 spin. context switch 비용(~수 us)보다 Lock 보유 시간이 짧을 때 유리.
  3. Slowpath: wait queue에 TASK_UNINTERRUPTIBLE로 등록, schedule() 호출.

mutex_unlock()은 owner를 NULL로 하고 wait queue에서 다음 태스크를 깨운다. Linux는 priority donation 대신 priority inheritance (PI) mutex (rt_mutex)를 별도 제공한다.

POSIX pthread_mutex_lock()은 유저 공간에서 futex 기반으로 구현된다. uncontended 경로는 커널 진입 없이 원자 연산 하나로 끝난다.

PintOS 구현

lock_acquire() 전체 흐름

Phase 1 상세 — donation 전파 경로:

%% lock_acquire() 중첩 donation 전파 경로
flowchart TD
  a["Thread A<br/>priority 60<br/>lock_acquire(L1)"]
  l1["획득 시도<br/>Lock L1<br/>holder = Thread B"]
  b["직접 donation<br/>Thread B<br/>priority 30<br/>waiting_lock = L2"]
  l2["중첩 대기<br/>Lock L2<br/>holder = Thread C"]
  c["중첩 donation<br/>Thread C<br/>priority 20<br/>waiting_lock = NULL"]
  result["전파 결과<br/>B.priority = 60<br/>C.priority = 60<br/>총 2단계"]
  a --> l1
  l1 --> b
  b --> l2
  l2 --> c
  c --> result

결과: B.priority = 60, C.priority = 60. 깊이는 A -> B (idx=0), B -> C (idx=1)로 총 2단계다.

최대 8단계(idx < 7 + 초기 1단계)인 이유: 현실적인 Lock 중첩 깊이를 넘지 않으면서 무한 루프를 방지하기 위함이다. 데드락이 있으면 이 루프가 순환할 수 있으나, idx < 7 가드가 이를 차단한다.

lock_release() 전체 흐름

Phase 1 상세 — 왜 waiting_lock == lock으로 필터링하는가:

스레드 T가 Lock A, Lock B를 동시에 보유할 수 있다. Lock A를 release할 때, Lock B를 기다리는 기부자까지 제거하면 안 된다. d_t->waiting_lock이 정확히 이 Lock인 경우만 제거한다.

%% lock_release() donation 필터링 기준
flowchart TD
  t["Thread T<br/>Lock A, Lock B 보유<br/>donation_list = X, Y, Z"]
  x["Thread X<br/>waiting_lock = Lock A<br/>필터 결과: 제거"]
  y["Thread Y<br/>waiting_lock = Lock A<br/>필터 결과: 제거"]
  z["Thread Z<br/>waiting_lock = Lock B<br/>필터 결과: 유지"]
  remove["Lock A release<br/>X, Y donation_elem 제거"]
  keep["Lock B 대기 donation 유지<br/>Z는 donation_list에 남음"]
  refresh["refresh_priority(T)<br/>base_priority와 Z.priority 중 max"]
  t --> x
  t --> y
  t --> z
  x --> remove
  y --> remove
  z --> keep
  remove --> refresh
  keep --> refresh

Lock A를 release할 때는 X.waiting_lock == Lock A, Y.waiting_lock == Lock A인 donation만 제거한다. Z.waiting_lock == Lock B인 donation은 남기고, refresh_priority(T)는 base_priority와 Z.priority 중 더 큰 값을 고른다.

lock_try_acquire() — 비차단 획득

donation 없이 sema_try_down()만 호출한다. 실패하면 BLOCKED가 아니라 false를 반환하므로 donation이 불필요하다.

lock_held_by_current_thread() — 소유자

lock_acquire()의 재귀 방지 ASSERT와 lock_release()의 소유자 확인에 사용된다.

락 획득과 해제 값 추적

항목값
lock_acquire ASSERT 수3개 (NULL, intr_context, held_by_current)
lock_release ASSERT 수2개 (NULL, held_by_current)
중첩 donation 최대 깊이8단계 (초기 1 + while idx < 7)
sema_down 인터럽트 비활성 구간while loop + thread_block()
sema_up check_preemption()value++ 직후 호출 — 깨운 스레드가 더 높으면 즉시 yield
lock_try_acquire donation 여부없음 (비차단이므로 불필요)

타이밍 예제:

시각 0: Thread A (pri 60) lock_acquire(L)
  L.holder == NULL → Phase 1 건너뜀
  sema_down: value 1→0, 즉시 통과
  L.holder = A

시각 1: Thread B (pri 40) lock_acquire(L)
  L.holder == A → Phase 1 진입
  donation_list에 B 삽입, but A.priority(60) > B.priority(40) → 기부 안 함
  sema_down: value==0 → BLOCKED

시각 2: Thread C (pri 50) lock_acquire(L)
  L.holder == A → Phase 1 진입
  donation_list에 C 삽입 (C(50) > B(40) 이므로 앞에)
  A.priority(60) > C.priority(50) → 기부 안 함
  sema_down: BLOCKED

시각 3: A lock_release(L)
  Phase 1: B, C 모두 waiting_lock==L → 모두 제거
  refresh_priority: base_priority로 복원
  sema_up: waiters 정렬 → C(50) 먼저 unblock
