fork에서 lazy UNINIT page의 aux는 어떻게 복사해야 하나

fork에서 lazy UNINIT page의 aux는 어떻게 복사해야 하나

fork lazy UNINIT 쟁점

fork 때 SPT는 왜 같이 복사해야 하나는 VM 이후의 fork()가 부모의 SPT 의미를 자식에게 복사해야 한다고 설명한다.

그런데 부모 SPT 안에 아직 한 번도 접근하지 않은 UNINIT lazy page가 있으면 바로 다음 질문이 생긴다.

부모 page->uninit.aux 포인터를 자식 page->uninit.aux에 그대로 넣어도 될까?

짧은 답은 이렇다.

fork에서 lazy UNINIT page의 혼동

lazy loading에서 aux는 “나중에 이 page fault가 나면 어떤 파일의 어느 offset을 읽을지”를 담는 작업지시서다.

load_segment()가 끝난 뒤에도 아직 frame은 없다. UNINIT page만 SPT에 들어 있고, page->uninit.aux가 나중의 lazy_load_segment(page, aux) 호출을 기다린다.

문제는 fork()다.

부모와 자식이 같은 aux 포인터를 공유하면 다음 순서가 가능하다.

이 말은 즉, SPT copy에서 “같은 lazy page 의미를 복제한다”는 말은 같은 포인터를 공유한다는 뜻이 아니다. 부모와 자식이 각자 cleanup, first fault, exec, exit를 독립적으로 겪을 수 있으므로 metadata ownership도 분리해야 한다.

fork에서 lazy UNINIT page의 흐름

UNINIT lazy page의 fork copy는 세 가지를 분리해서 봐야 한다.

대상복사해야 하는 의미공유하면 생기는 문제
struct page자식 SPT에 들어갈 별도 page 객체부모 exit/evict/destroy가 자식 page metadata를 망가뜨림
aux 구조체file, offset, read bytes, zero bytes 작업지시서한쪽 첫 fault나 destroy가 free(aux)하면 다른 쪽이 dangling pointer를 봄
struct file *나중에 read_at할 파일 객체 참조한쪽 close가 다른 쪽 lazy read를 불가능하게 만들 수 있음

초기 PintOS 구현에서 가장 단순한 안전 모델은 이것이다.

더 복잡한 모델도 가능하다. 예를 들어 aux와 file reference에 refcount를 붙이면 공유할 수 있다. 하지만 PintOS 스켈레톤은 refcount 정책을 제공하지 않는다. refcount를 직접 설계하지 않았다면, 얕은 포인터 복사는 안전한 기본값이 아니다.

fork에서 lazy UNINIT page의 예시

부모가 ELF text segment의 첫 page를 아직 읽지 않았다고 하자.

부모 SPT의 의미는 이렇다.

자식에게 필요한 것은 “같은 작업 내용”이지 “같은 작업지시서 주소”가 아니다.

두 file 객체는 같은 inode를 가리키도록 file_reopen() 또는 필요한 속성까지 복제하는 helper로 만들 수 있다. 중요한 점은 부모와 자식이 각자의 file_close() 시점을 가져도 서로의 lazy page를 깨뜨리지 않아야 한다는 것이다.

실제 운영체제

Linux의 fork()는 보통 주소 공간을 copy-on-write로 복제한다. 아직 page cache에서 읽지 않은 executable-backed page도 VMA, file reference, page cache, page table entry metadata를 통해 “나중에 fault가 나면 어느 파일 offset에서 가져올지”를 유지한다.

핵심은 fd 숫자가 아니라 커널 내부 객체 참조다. 사용자가 fd를 닫아도 이미 만들어진 mapping은 별도 file/VMA reference로 살아 있을 수 있다. fork() 뒤 부모와 자식은 논리적으로 같은 mapping을 보지만, 그 수명은 refcount와 VM metadata로 관리된다.

Windows는 Unix식 fork()를 일반 API로 제공하지 않는다. CreateProcess가 새 process와 address space를 만들고 image section, VAD, section object 같은 구조로 executable/file mapping을 관리한다. 따라서 “fork에서 aux를 복사한다”는 표현은 PintOS 학습용 구현에 맞춘 설명이다.

공통 판단 기준은 같다.

PintOS

W09 PintOS 스켈레톤에서 UNINIT page는 uninit_new()가 만든다.

첫 fault 때는 vm_do_claim_page()가 swap_in(page, frame->kva)를 호출하고, UNINIT page의 swap_in은 uninit_initialize()다.

따라서 supplemental_page_table_copy()가 부모의 UNINIT page를 만났을 때 선택지는 대략 셋이다.

선택지의미판단
얕은 복사child page가 parent aux를 그대로 가리킴refcount 없으면 위험
deep copychild 전용 aux를 할당하고 file을 reopen/duplicate초기 구현의 안전한 기본값
eager claimfork 시점에 부모 lazy page를 실제 frame으로 읽고 child frame을 채움단순하지만 lazy loading 장점이 줄고 fork 비용이 커짐

초기 구현에서는 deep copy가 가장 설명하기 쉽다.

이 코드는 실제 프로젝트 코드에 그대로 붙이라는 뜻이 아니라 판단 기준을 보여 주는 예시다. aux 구조체 이름과 필드는 구현자가 정한다. 중요한 불변식은 child가 parent의 aux와 file 객체를 소유하지 않는다는 점이다.

QEMU

QEMU는 aux, struct page, SPT copy를 모른다.

QEMU가 보는 흐름은 더 낮은 수준이다.

따라서 parent와 child가 같은 aux 포인터를 공유해서 dangling pointer가 생겨도, QEMU가 “이건 잘못된 SPT 복사다”라고 알려 주지는 않는다. QEMU는 guest memory 바이트와 CPU exception을 재현할 뿐이고, 그 바이트를 struct lazy_load_arg로 해석하는 책임은 PintOS 커널에 있다.

fork에서 lazy UNINIT page의 코드

PintOS W09에서 확인한 지점:

  • pintos/userprog/process.c:342-345: VM 빌드의 __do_fork()가 supplemental_page_table_init(&curr->spt) 뒤 supplemental_page_table_copy(&curr->spt, &parent->spt)를 호출한다.
  • pintos/vm/vm.c:181-183: supplemental_page_table_copy()는 스켈레톤 함수이므로 UNINIT 복제 정책을 구현해야 한다.
  • pintos/include/vm/uninit.h:12-18: struct uninit_page가 init, type, aux, page_initializer를 저장한다.
  • pintos/vm/uninit.c:27-42: uninit_new()가 page->uninit.aux = aux로 작업지시서를 보관한다.
  • pintos/vm/uninit.c:47-56: uninit_initialize()가 저장된 aux를 init(page, aux)로 넘긴다.
  • pintos/vm/uninit.c:59-68: 한 번도 참조되지 않은 UNINIT page가 exit 때 남을 수 있으므로 destroy에서 resource 정리가 필요하다고 주석이 말한다.
  • pintos/userprog/process.c:1275-1295: load_segment()가 page별 page_read_bytes와 page_zero_bytes를 계산하고 vm_alloc_page_with_initializer(..., lazy_load_segment, aux)를 호출하는 자리다.
  • pintos/filesys/file.c:35-37: file_reopen()은 같은 inode를 가리키는 새 file 객체를 만든다.
  • pintos/filesys/file.c:88-90: file_read_at()은 file position을 바꾸지 않고 특정 offset에서 읽는다.

QEMU에서 확인한 지점:

  • target/i386/tcg/system/excp_helper.c:516-520: 주소 변환 실패를 EXCP0E_PAGE, error code, cr2 = addr로 만든다.
  • target/i386/tcg/system/excp_helper.c:651-653: fault address를 guest CR2에 넣고 exception을 올린다.
  • target/i386/cpu.h:347-352: page fault error code bit가 PG_ERROR_P/W/U/RSVD/I_D/PK로 정의된다.

fork lazy UNINIT 값 추적

부모와 자식이 같은 aux를 얕게 공유한다고 하자.

부모가 먼저 fault를 처리한 뒤 free(aux)를 호출하면 child는 아직 같은 숫자를 들고 있다.

운이 나쁘면 같은 heap 주소가 다른 용도로 재사용된다.

deep copy가 되면 숫자는 이렇게 갈라져야 한다.

같아야 하는 것은 offset/read size 같은 값이고, 달라야 하는 것은 소유권을 가진 포인터다.

GDB에서는 fork() 직후와 첫 fault 직전에 부모/자식의 aux 주소가 분리되는지 본다.

실패 신호:

  • parent와 child의 page->uninit.aux가 같은 주소다.
  • parent가 먼저 fault를 처리한 뒤 child fault에서 aux 값이 깨진다.
  • child uninit_destroy()가 parent가 이미 free한 aux를 다시 free한다.
  • file_read_at()에 들어가는 file 포인터가 이미 닫힌 file 객체다.

정리

fork()에서 lazy UNINIT page를 복사한다는 말은 “나중에 같은 파일 offset을 읽을 수 있는 권리와 작업지시서를 자식에게도 준다”는 뜻이다.

그 작업지시서가 aux다. aux는 첫 fault 또는 destroy에서 소비되고 해제될 수 있으므로, 부모와 자식이 같은 포인터를 공유하면 수명 충돌이 생긴다.

PintOS의 안전한 초기 구현 기준은 다음이다.

QEMU는 이 정책을 모른다. QEMU는 child의 PTE가 없을 때 pf와 CR2를 만들어 줄 뿐이고, 그 fault를 살릴 수 있는 aux 수명은 PintOS 구현자가 보장해야 한다.

fork에서 lazy UNINIT page의 관련 문서

  • SPT fork copy
    • fork()가 SPT 의미를 복제해야 하는 전체 흐름.
  • lazy aux 수명
    • aux와 reopened file이 첫 fault 또는 destroy까지 살아야 하는 이유.
  • swapped anon fork 질문
    • swapped-out anonymous page의 slot snapshot과 ownership 질문.
  • file backed metadata
    • file-backed page가 file, offset, read/zero bytes를 기억해야 하는 이유.
  • vm try handle fault() decision
    • SPT hit가 fault 처리로 이어지는 분기.
  • PintOS VM 시각화
    • VM 시각화에서 lazy loading과 fork 질문 위치 잡기.
