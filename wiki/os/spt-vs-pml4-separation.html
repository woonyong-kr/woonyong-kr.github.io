SPT와 PML4를 둘 다 두는 이유

SPT와 PML4를 둘 다 두는 이유

확인 범위: 이 문서는 PML4와 SPT의 역할 분리 및 선택 기준을 개념적으로 설명하고, 제시된 PintOS·Linux·QEMU 코드 좌표와 처리 흐름을 구현 관점의 예시로 다룬다. 실제 코드의 일치 여부, 버전별 구조·함수 위치, GDB 실행 결과와 크기·성능 수치는 별도의 소스 확인과 실행·측정 없이는 검증 결과로 간주하지 않는다.

한 줄 요약: MMU가 직접 walk하는 PML4는 VA→PA 매핑만 담을 수 있어, 커널은 lazy·swap·file-backed 같은 미매핑 페이지의 출처와 메타데이터를 따로 추적하는 SPT를 함께 둔다.

SPT와 PML4를 둘 다 두는 이유 차이

PintOS(및 대부분의 OS)는 가상 메모리를 관리하기 위해 두 가지 테이블을 유지한다: 하드웨어가 직접 사용하는 PML4 페이지 테이블과, 커널이 소프트웨어적으로 관리하는 Supplemental Page Table(SPT). PML4는 “현재 물리 프레임이 매핑된 페이지”만 알고, SPT는 “매핑 여부와 관계없이 이 프로세스가 소유한 모든 가상 페이지의 메타데이터”를 알고 있다.

상세 설명

추상 개념 — 하드웨어 vs 소프트웨어의 역할 분리

PML4 (하드웨어 페이지 테이블):

  • MMU가 주소 변환 시 직접 walk하는 구조
  • VA → PA 매핑만 저장 (present bit = 1인 엔트리만 유효)
  • 구조가 고정되어 있음 (4단계, 512-entry, 각 8바이트)
  • 메타데이터 저장 공간이 극히 제한적 (PTE의 여분 비트 몇 개뿐)

SPT (소프트웨어 보조 테이블):

  • page fault 시 커널이 참조하는 구조
  • 매핑되지 않은 페이지(lazy, swapped-out, file-backed)도 추적
  • 페이지 타입, 원본 파일, offset, swap slot 등 풍부한 메타데이터 저장
  • 자료구조 선택 자유 (해시 테이블, 트리 등)

왜 PML4만으로 부족한가

상황PML4만으로 해결 가능?SPT가 필요한 이유

실제 OS (Linux)

Linux에서 SPT에 해당하는 것은 struct vm_area_struct (VMA) 리스트/트리다. 각 VMA는 연속된 가상 주소 범위를 하나의 정책(파일 매핑, 익명, 스택 등)으로 관리한다. page fault 발생 시 커널은 VMA를 찾아 해당 페이지를 어떻게 채울지 결정한다.

Linux의 PML4(pgd)는 하드웨어 walk용이고, VMA가 “이 주소가 valid한가, 어디서 데이터를 가져오는가”를 결정한다.

PintOS 구현

Page fault 처리 흐름에서의 역할 분담:

  1. MMU가 PML4 walk → present=0 발견 → pf exception
  2. 커널의 vm_try_handle_fault() 진입
  3. spt_find_page(spt, fault_addr) — SPT에서 해당 VA의 struct page 검색
  4. page가 없으면 → invalid access (kill)
  5. page가 있으면 → vm_do_claim_page(): frame 할당, swap_in(), PML4에 매핑 설치

핵심 통찰: PML4의 present=0은 “매핑 없음”만 의미하고, SPT가 “왜 없는지, 어떻게 복구하는지”를 결정한다.

QEMU 에뮬레이션

QEMU는 PML4 walk를 소프트웨어로 재현한다 — get_phys_addr() (target/i386/excp_helper.c)가 guest CR3에서 시작하여 4단계를 순회한다. present=0을 발견하면 QEMU가 guest CPU에 pf exception을 주입하고, PintOS의 page_fault() handler가 호출된다.

QEMU는 SPT의 존재를 전혀 모른다 — SPT는 순수 소프트웨어 구조체이므로 guest memory의 malloc된 영역에 있을 뿐이다. QEMU가 하는 일은 “PML4 walk 실패 → pf exception 생성”까지이고, 그 이후 “SPT 조회 → frame 할당 → PML4 매핑 설치”는 전부 PintOS 커널 코드(guest instruction)가 수행한다.

GDB로 이 이원 구조를 확인하는 법:

(gdb) # PML4 관점: 매핑 없음 확인
(gdb) p/x thread_current()->pml4
(gdb) x/gx (CR3) + 8*(VA>>39 & 0x1FF)     # PML4 엔트리 → present=0

(gdb) # SPT 관점: 메타데이터는 있음
(gdb) call spt_find_page(&thread_current()->spt, 0x40001000)
(gdb) p ((struct page*)$)->operations->type   # VM_UNINIT
(gdb) p ((struct page*)$)->uninit.aux         # lazy_load_arg 주소

두 테이블의 일관성

시점PML4SPT
vm_alloc_page (lazy)엔트리 없음page 생성, UNINIT 타입
page fault → claimpresent=1, frame PA 기록frame 포인터 연결
eviction (swap out)present=0으로 클리어swap slot 기록, frame=NULL
munmap / exit엔트리 삭제page 제거, destroy() 호출

SPT와 PML4를 둘 다 두는 이유 값 추적

  • PML4 엔트리 크기: 8 bytes (64-bit)
  • PML4 한 테이블: 512 entries × 8B = 4 KB (한 페이지)
  • PTE에서 OS가 쓸 수 있는 비트: bit 9–11 (3비트, avail) — swap slot 번호(최대 수천 개) 저장 불가
  • SPT struct page 크기: ~80–120 bytes (union 포함) — 풍부한 메타데이터 저장 가능
  • 해시 테이블 lookup: O(1) 평균, VA의 page-aligned 주소를 키로 사용

Page Fault에서 PML4·SPT 역할 분담

flowchart TD
    PF[Page Fault 발생<br>VA = 0x4000_1000]
    PML4{PML4 walk 결과}
    PML4 -->|present=0| SPT_LOOKUP[SPT에서 VA 검색<br>spt_find_page]
    PML4 -->|present=1, write fault| CHECK_W[writable 확인<br>COW 처리]

    SPT_LOOKUP -->|page 발견| TYPE{page 타입?}
    SPT_LOOKUP -->|page 없음| STACK{stack growth?}
    STACK -->|Yes| GROW[vm_stack_growth<br>SPT+PML4 동시 등록]
    STACK -->|No| KILL[프로세스 종료]

    TYPE -->|UNINIT| LAZY[swap_in: 파일/zero로 frame 채움]
    TYPE -->|ANON| SWAP[swap_in: swap disk에서 읽기]
    TYPE -->|FILE| FILE_READ[swap_in: 파일에서 읽기]

    LAZY --> INSTALL[PML4에 VA→PA 매핑 설치<br>pml4_set_page]
    SWAP --> INSTALL
    FILE_READ --> INSTALL
    INSTALL --> RETRY[같은 명령어 재실행]

페이지 생명주기에서 PML4·SPT 상태 변화

sequenceDiagram
    participant APP as 유저 프로그램
    participant SPT as SPT (소프트웨어)
    participant PML4 as PML4 (하드웨어)
    participant FRAME as Physical Frame

    Note over SPT,PML4: 1. vm_alloc_page (lazy 등록)
    APP->>SPT: UNINIT page 생성 (VA=0x4000_1000)
    Note over PML4: 엔트리 없음 (present=0)

    Note over SPT,PML4: 2. 첫 접근 → page fault → claim
    APP->>PML4: load [0x4000_1000] → #PF
    PML4->>SPT: page_fault → spt_find_page
    SPT->>FRAME: palloc_get_page → frame 할당
    SPT->>PML4: pml4_set_page(VA, PA, writable)
    Note over PML4: present=1, PA 기록

    Note over SPT,PML4: 3. Eviction (swap out)
    SPT->>FRAME: swap_out → swap disk 기록
    SPT->>PML4: pml4_clear_page(VA)
    Note over PML4: present=0
    Note over SPT: swap_slot 기록, frame=NULL

    Note over SPT,PML4: 4. 재접근 → page fault → swap in
    APP->>PML4: load [0x4000_1000] → #PF
    PML4->>SPT: spt_find_page → ANON, swap_slot
    SPT->>FRAME: swap_in → 새 frame에 복원
    SPT->>PML4: pml4_set_page(VA, new_PA, writable)

    Note over SPT,PML4: 5. exit → cleanup
    SPT->>PML4: pml4_clear_page or pml4_destroy
    SPT->>SPT: spt_kill → destroy(page) → frame 해제
