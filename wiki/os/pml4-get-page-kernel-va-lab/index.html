pml4_get_page는 왜 커널 가상 주소를 돌려주나

한 줄 요약: pml4_get_page(pml4, uaddr)는 유저 가상 주소를 그대로 반환하지 않는다. 대신 같은 물리 프레임에서 동일한 위치를 가리키며, 커널이 직접 접근할 수 있는 커널 가상 주소(kaddr)를 반환한다.

pml4_get_page 쟁점

유저 프로그램이 write(1, 0x8048123, 5)를 호출했다고 하자.

0x8048123은 유저 프로세스의 주소 공간에서 해석되는 가상 주소다. 반면 syscall_handler()는 커널 코드다. 그렇다면 커널이 이 주소부터 5바이트를 검사하거나 복사하려면 어떤 주소를 사용해야 할까?

PintOS에서는 다음과 같은 코드를 자주 볼 수 있다.

void *kaddr = pml4_get_page (thread_current ()->pml4, uaddr);

여기서 kaddr는 uaddr와 같은 숫자가 아니다. pml4_get_page()는 유저 가상 주소를 그대로 반환하는 대신, 같은 물리 프레임의 같은 위치를 커널이 볼 수 있도록 커널 가상 주소로 변환해 반환한다.

순서도

전체 흐름은 두 단계로 나누어 보면 쉽다. 먼저 함수 내부에서 유저 가상 주소가 어떤 프레임과 offset을 가리키는지 찾고, 그다음 같은 위치를 유저·물리·커널·호스트 주소 층에서 어떻게 바라보는지 구분한다.

pml4_get_page() 내부 흐름 

flowchart TD
    INPUT["입력: pml4, uaddr"] --> ASSERT["ASSERT(is_user_vaddr(uaddr))"]
    ASSERT --> WALK["pte = pml4e_walk(pml4, uaddr, 0)<br/>create=0: 조회 전용"]
    WALK --> CHECK{pte != NULL<br/>AND *pte & PTE_P?}
    CHECK -->|no| NULL["return NULL<br/>매핑 없음"]
    CHECK -->|yes| EXTRACT["frame_base = PTE_ADDR(*pte)<br/>= *pte & ~0xFFF"]
    EXTRACT --> PTOV["kva_base = ptov(frame_base)<br/>= KERN_BASE + frame_base"]
    PTOV --> OFFSET["offset = pg_ofs(uaddr)<br/>= uaddr & 0xFFF"]
    OFFSET --> RETURN["return kva_base + offset"]

첫 순서도는 PintOS 함수가 반환값을 계산하는 과정을 보여 준다. 두 번째 그림은 그 결과가 QEMU의 host pointer와는 다른 주소 층에 속한다는 점을 보여 준다.

질문 사슬

아래 질문을 순서대로 따라가면 유저 포인터의 위험성부터 GDB 검증까지 연결할 수 있다.

  • 왜 커널은 유저 포인터의 숫자를 그대로 믿고 역참조하면 안 될까?
  • 실제 Linux와 Windows는 유저 버퍼를 어떻게 안전하게 읽을까?
  • PintOS의 pml4_get_page()는 page table에서 무엇을 찾을까?
  • 반환값은 왜 user virtual address가 아니라 kernel virtual address일까?
  • QEMU 관점에서 이 주소는 host pointer일까, 아니면 guest 내부의 주소일까?
  • 구체적인 숫자를 넣으면 uaddr, PTE, guest physical address, kernel virtual address는 어떻게 계산될까?
  • GDB에서는 어떤 값을 비교해야 두 주소가 같은 frame을 가리킨다고 확인할 수 있을까?

pml4_get_page 필요성

유저 포인터는 커널 관점에서 신뢰할 수 없는 숫자다.

write(1, buffer, size);

여기서 buffer는 유저 프로그램이 넘긴 주소다. 커널이 이 주소를 검증하지 않고 읽으면 다음 문제가 생길 수 있다.

문제 왜 위험한가
매핑되지 않은 주소 커널 안에서 page fault가 발생할 수 있다
커널 주소 유저가 커널 메모리를 읽거나 쓰게 만들 수 있다
다른 프로세스 기준 주소 같은 숫자라도 현재 page table이 다르면 다른 바이트를 뜻한다
page boundary 시작 주소는 유효해도 뒤쪽 바이트가 다음 unmapped page로 넘어갈 수 있다

따라서 커널은 먼저 “이 유저 주소가 현재 프로세스의 page table에서 실제 frame으로 이어지는가?”를 확인해야 한다. 매핑이 존재한다면 이어서 “그 frame의 같은 위치를 커널이 어떤 주소로 접근해야 하는가?”를 계산해야 한다.

pml4_get_page 흐름

먼저 다음 세 문장을 기준으로 삼으면 된다.

  1. 유저 가상 주소는 프로세스마다 별도로 해석되는 이름이다.
  2. PTE에는 그 이름이 가리키는 guest physical frame base가 들어 있다.
  3. PintOS 커널은 KERN_BASE 위쪽에 물리 메모리를 다시 매핑해 두므로, 같은 frame을 ptov(physical)로 변환해 커널 주소처럼 볼 수 있다.

이 세 단계를 함수의 흐름으로 연결하면 다음과 같다.

user virtual address
  -> 현재 process pml4로 page table walk
  -> PTE에서 guest physical frame base 추출
  -> frame base + page offset
  -> ptov(frame base) + offset
  -> PintOS kernel virtual address

즉, pml4_get_page()는 “주소가 유효하게 매핑되어 있는가?”를 확인하는 동시에 “커널이 같은 바이트를 어떤 주소로 읽어야 하는가?”를 계산한다.

예시 mapping으로 값 계산하기

다음 mapping이 있다고 하자.

uaddr       = 0x0000000008048123
page size   = 0x1000
page offset = 0x123
user page   = 0x0000000008048000

PTE         = 0x0000000012345007
PTE_ADDR    = 0x0000000012345000
flags       = 0x007 = PTE_P | PTE_W | PTE_U

PintOS에서 커널 주소 공간의 시작점은 다음 상수로 정해진다.

KERN_BASE = LOADER_KERN_BASE = 0x8004000000

그러면 pml4_get_page()의 반환값은 다음과 같이 계산된다.

ptov(PTE_ADDR(PTE)) = 0x8004000000 + 0x12345000
                    = 0x8016345000

return address      = 0x8016345000 + 0x123
                    = 0x8016345123

따라서 0x8048123과 0x8016345123은 숫자로는 전혀 다르다. 하지만 현재 page table과 kernel direct mapping을 기준으로 보면, 두 주소는 같은 guest physical frame의 같은 offset을 가리킨다.

실제 운영체제와의 공통 원칙

실제 OS에서도 커널은 유저 포인터를 일반적인 C 포인터처럼 곧바로 신뢰하지 않는다.

Linux 커널은 유저 주소에 접근할 때 copy_from_user(), copy_to_user() 같은 전용 경로를 사용한다. 이 경로에서는 유저 주소 범위, page fault 가능성, 접근 권한을 고려한다. 실제 Linux에는 direct map, high memory, kmap 계열, page pinning, VMA 등 더 많은 층이 존재한다.

Windows에서도 커널은 Win32 API를 통해 전달된 user buffer를 바로 신뢰하지 않는다. 드라이버나 커널 경로에서는 probing, locking, MDL 같은 방식으로 유저 버퍼의 유효성과 접근 가능성을 다룬다.

두 운영체제에서 공통으로 드러나는 원칙은 다음과 같다.

유저 주소의 숫자는 커널이 직접 믿을 수 있는 포인터가 아니라, 현재 프로세스의 주소 공간을 기준으로 검증하고 변환해야 하는 입력값이다.

PintOS에서 변환을 구성하는 요소

PintOS에서 확인할 관련 파일은 세 곳이다.

  • SW_AI-W11-pintos/pintos/include/threads/vaddr.h
  • SW_AI-W11-pintos/pintos/include/threads/pte.h
  • SW_AI-W11-pintos/pintos/threads/mmu.c

먼저 vaddr.h는 물리 주소와 커널 가상 주소 사이의 단순한 변환 규칙을 제공한다.

#define KERN_BASE LOADER_KERN_BASE
#define ptov(paddr) ((void *) (((uint64_t) paddr) + KERN_BASE))
#define vtop(vaddr) ((uint64_t) (vaddr) - (uint64_t) KERN_BASE)

다음으로 pte.h는 PTE에서 frame 주소 부분만 꺼내는 규칙을 제공한다.

#define PTE_ADDR(pte) ((uint64_t) (pte) & ~0xFFF)

PTE의 낮은 12비트는 page offset이 아니라 flag 자리로 사용된다. 따라서 ~0xFFF로 낮은 12비트를 지우면 4KB 경계에 정렬된 frame base만 남는다.

마지막으로 mmu.c의 pml4_get_page()가 이 두 변환을 연결한다.

void *
pml4_get_page (uint64_t *pml4, const void *uaddr) {
    ASSERT (is_user_vaddr (uaddr));

    uint64_t *pte = pml4e_walk (pml4, (uint64_t) uaddr, 0);

    if (pte && (*pte & PTE_P))
        return ptov (PTE_ADDR (*pte)) + pg_ofs (uaddr);
    return NULL;
}

여기서 중요한 점은 create가 0이라는 사실이다. page table을 조회하는 함수가 존재하지 않는 중간 테이블을 새로 만들어서는 안 된다. 매핑이 없으면 NULL이어야 한다.

실제 PintOS 코드에서 쓰이는 곳

fork() 구현에서 page를 복사하는 흐름을 보면 반환값이 왜 커널 주소여야 하는지 분명해진다.

파일:

  • SW_AI-W11-pintos/pintos/userprog/process.c

핵심 흐름:

parent_page = pml4_get_page (parent->pml4, va);
newpage = palloc_get_page (PAL_USER);
memcpy (newpage, parent_page, PGSIZE);
pml4_set_page (current->pml4, va, newpage, writable);

memcpy()의 두 번째 인자인 parent_page는 커널이 읽을 수 있는 주소여야 한다. 만약 pml4_get_page()가 유저 VA인 va를 그대로 반환한다면, 커널은 부모 프로세스의 frame을 안정적으로 복사할 수 없다.

유저 포인터를 검증할 때도 pml4_get_page()가 사용된다.

파일:

  • SW_AI-W11-pintos/pintos/userprog/syscall.c

핵심 흐름:

if (!is_user_vaddr (addr)) {
    exit (-1);
}

if (pml4_get_page (curr->pml4, addr) == NULL) {
    exit (-1);
}

이 코드는 “주소의 숫자가 유저 영역에 속하는가?”와 “현재 page table에서 실제 present frame으로 이어지는가?”를 나누어 검사한다.

QEMU에서 바라본 주소 층

여기서 가장 혼동하기 쉬운 점은 guest의 커널 가상 주소와 host process의 포인터를 구분하는 것이다.

pml4_get_page()가 반환하는 0x8016345123 같은 값은 QEMU host process의 C 포인터가 아니다. 이 값은 PintOS guest 내부의 커널 가상 주소다.

QEMU에서는 다음 순서로 실제 host memory에 도달한다.

  1. guest CPU가 0x8016345123을 읽는 명령을 실행한다.
  2. guest page table과 guest CR3를 기준으로 guest virtual address를 guest physical address로 번역한다.
  3. 그 guest physical address가 QEMU memory region의 어느 offset에 해당하는지 찾는다.
  4. 실제 host memory에서는 RAMBlock.host + offset 같은 host pointer로 접근한다.

QEMU 코드에서도 각 층의 경계를 확인할 수 있다.

  • target/i386/emulate/x86_mmu.c
    • guest page table entry를 address_space_read(&address_space_memory, ...)로 읽는다.
  • system/memory_ldst.c.inc
    • RAM 접근이라면 qemu_map_ram_ptr(mr->ram_block, addr1)로 host pointer를 얻어 load/store를 수행한다.
  • include/system/ramblock.h
    • ramblock_ptr()는 block->host + offset을 반환한다.

따라서 주소 층을 다음과 같이 분리해야 한다.

PintOS user VA      = 0x0000000008048123
PintOS kernel VA    = 0x0000008016345123
guest physical addr = 0x0000000012345123
QEMU host pointer   = RAMBlock.host + 0x12345123

마지막 줄은 학습을 위한 단순화된 모델이다. 실제 QEMU는 memory region translation, RAMBlock, MMIO 분기, dirty tracking도 함께 처리한다.

구분 주소를 다루는 방식 이 문서에서 중요한 점
Linux / Windows 유저 포인터를 검증하고 커널 접근 경로를 통해 복사 실제 구현은 훨씬 복잡하지만 유저 주소를 바로 믿지 않는 원칙은 같다
PintOS pml4_get_page()가 PTE를 찾아 kernel virtual address를 반환 guest physical frame을 KERN_BASE 위쪽의 direct mapping으로 다시 본다
QEMU guest 주소 변환과 guest RAM 접근을 에뮬레이션 PintOS kernel VA는 host pointer가 아니다

pml4_get_page 코드의 양방향 변환

1. pml4_set_page()는 kernel VA를 PTE의 physical frame으로 바꾼다

파일:

  • SW_AI-W11-pintos/pintos/threads/mmu.c

핵심 코드:

*pte = vtop (kpage) | PTE_P | (rw ? PTE_W : 0) | PTE_U;

kpage는 palloc_get_page()가 반환한 커널 가상 주소다. PTE에는 커널 가상 주소가 아니라 guest physical frame base가 들어가야 하므로 vtop(kpage)를 사용한다.

2. pml4_get_page()는 PTE의 physical frame을 다시 kernel VA로 바꾼다

파일:

  • SW_AI-W11-pintos/pintos/threads/mmu.c

핵심 코드:

return ptov (PTE_ADDR (*pte)) + pg_ofs (uaddr);

PTE_ADDR(*pte)는 guest physical frame base다. ptov()는 이 frame을 커널이 접근할 수 있는 direct mapping 주소로 바꾼다. 여기에 pg_ofs(uaddr)를 더해야 page 내부의 정확한 byte 위치를 얻을 수 있다.

3. process.c는 반환값을 실제 복사 주소로 사용한다

파일:

  • SW_AI-W11-pintos/pintos/userprog/process.c

핵심 코드:

memcpy (newpage, parent_page, PGSIZE);

parent_page는 pml4_get_page(parent->pml4, va)에서 얻은 값이다. 이 값이 커널이 읽을 수 있는 주소라는 사실은 memcpy()의 사용 방식에서 드러난다.

pml4_get_page 값 추적

구체적인 값을 추적할 때는 frame base, page offset, kernel VA 순서로 계산한다.

1. PTE 값에서 frame base 분리 

PTE      = 0x0000000012345007
flags    = 0x007
PTE_ADDR = PTE & ~0xFFF
         = 0x0000000012345000

0x007은 다음 bit가 켜져 있다는 뜻이다.

0x001 PTE_P present
0x002 PTE_W writable
0x004 PTE_U user

2. user VA의 page offset 계산 

uaddr  = 0x0000000008048123
PGMASK = 0xFFF
offset = uaddr & PGMASK
       = 0x123

3. kernel VA 계산 

KERN_BASE  = 0x8004000000
frame base = 0x0012345000
offset     = 0x123

kaddr = KERN_BASE + frame base + offset
      = 0x8016345123

4. 같은 바이트를 두 주소로 보는 이유 

user VA 0x8048123
  -> page table
  -> guest physical 0x12345123

kernel VA 0x8016345123
  -> kernel direct mapping
  -> guest physical 0x12345123

두 가상 주소가 같은 숫자일 필요는 없다. 서로 다른 주소 변환 경로를 거쳐 같은 guest physical address에 도달한다면 같은 바이트를 가리킨다.

GDB로 pml4_get_page 확인하기

PintOS를 GDB에서 멈춘 뒤 pml4_get_page()에 breakpoint를 걸어 확인할 수 있다.

break pml4_get_page
continue

함수 안으로 들어오면 먼저 입력 주소와 PTE를 확인한다.

next
next
p/x uaddr
p/x pte
p/x *pte
p/x ((uint64_t)(*pte) & ~0xfff)
p/x ((uint64_t)uaddr & 0xfff)

그다음 반환 직전의 계산을 직접 대조한다.

p/x 0x8004000000 + (((uint64_t)(*pte) & ~0xfff)) + (((uint64_t)uaddr) & 0xfff)

이어서 반환된 커널 주소의 바이트를 확인한다.

finish
p/x $rax
x/16xb $rax

현재 실행 중인 address space가 같은 프로세스의 것이라면 유저 주소 쪽 바이트도 비교할 수 있다.

x/16xb uaddr

만약 x/16xb uaddr가 실패하거나 두 값이 다르게 보인다면, 먼저 현재 CR3, 현재 thread, 현재 process의 pml4가 모두 같은 주소 공간을 기준으로 하는지 확인해야 한다. 유저 VA의 의미는 현재 주소 공간에 의존하기 때문이다.

정리

  • pml4_get_page()는 user virtual address를 그대로 반환하지 않는다.
  • PTE에서 guest physical frame base를 꺼낸 뒤 ptov()로 PintOS kernel virtual address를 만든다.
  • 반환값은 커널이 memcpy()나 syscall buffer 검사에 사용할 수 있는 주소다.
  • QEMU 관점에서 이 값은 host pointer가 아니라 guest kernel virtual address다.
  • 실제 host memory 접근은 QEMU의 guest 주소 변환과 memory region/RAMBlock 경로를 거친다.

pml4_get_page 관련 문서

  • 주소 변환
    • VA, PA, frame, offset을 아우르는 전체 모델.
  • x86 64 page table walk
    • 주소를 PML4/PDPE/PDE/PTE index로 나누는 방법.
  • PTE bit
    • PTE의 주소 bit와 flag bit를 분리하는 방법.
  • guest physical memory
    • guest physical address가 QEMU host process memory에 backing되는 방식.
  • 유저 포인터 검증
    • syscall에서 유저 포인터를 검증하는 흐름.
  • 바이트 버퍼와 캐스팅
    • 같은 raw bytes를 주소와 타입에 따라 다르게 해석하는 실험.
