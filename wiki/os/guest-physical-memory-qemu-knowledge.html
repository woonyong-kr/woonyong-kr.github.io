Guest Physical Memory

Guest Physical Memory

확인 범위: 이 문서는 guest·host 환경의 주소 변환 계층과 각 주소의 의미를 설명하는 개념 자료이며, 제시된 PintOS·QEMU 코드 좌표와 수치는 특정 구현을 이해하기 위한 예시다. 실제 코드 동작, 버전별 세부 경로, 실행 결과와 성능 판단은 해당 환경의 소스·설정·실행 기록 및 측정을 통해 별도로 검증해야 한다.

한 줄 요약: PintOS가 보는 ‘물리 주소’는 host RAM이 아니라 guest physical address라는 점.

Guest Physical Memory 상태

PintOS page table entry에 들어가는 “물리 주소”는 host machine의 실제 RAM 주소가 아니다. QEMU 위에서 실행되는 PintOS가 보는 물리 주소는 guest physical address(GPA)이며, QEMU가 이를 자신의 프로세스 메모리(host virtual address)로 변환한다. “physical”이라는 단어가 어느 층의 물리 주소인지 구분하는 것이 이 문서의 목표다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

실제 하드웨어에서는 주소 층이 2개다: Virtual Address → Physical Address. MMU가 page table을 walk해서 VA를 PA로 변환하고, PA는 메모리 컨트롤러를 거쳐 DRAM 셀에 도달한다.

하지만 가상화 환경에서는 주소 층이 늘어난다:

%% Guest VA에서 Host PA까지 이어지는 주소 변환 층
flowchart LR
  gva["Guest VA<br/>PintOS process 주소<br/>예: 0x0000_0000_8048_0123"]
  gpa["Guest PA<br/>PintOS가 물리 메모리라고 믿는 주소<br/>PTE_ADDR(*pte) + offset"]
  hva["Host VA<br/>QEMU process 내부 포인터<br/>RAMBlock.host + ram_addr_t offset"]
  hpa["Host PA<br/>host OS가 관리하는 실제 DRAM frame<br/>PintOS/GDB에서는 직접 볼 수 없는 층"]
  guest_walk["guest page table"]
  qemu_map["RAMBlock / MemoryRegion"]
  host_walk["host page table"]
  gva --> guest_walk
  guest_walk --> gpa
  gpa --> qemu_map
  qemu_map --> hva
  hva --> host_walk
  host_walk --> hpa

Intel VT-x 하드웨어 가상화에서는 EPT(Extended Page Table)가 GPA→HPA 변환을 하드웨어로 수행한다. QEMU TCG(소프트웨어 에뮬레이션) 모드에서는 이 변환을 C 코드(RAMBlock + MemoryRegion)로 수행한다.

실제 OS (Linux/Windows)

실제 OS 커널은 하드웨어 위에서 직접 실행되므로 page table entry의 물리 주소가 곧 DRAM frame 주소다.

항목LinuxWindows
PA의 의미실제 DRAM frame number실제 DRAM frame number
커널 접근 방식direct map (PA + PAGE_OFFSET)HAL 관리
PA 할당buddy allocator (zone별)PFN database
PA 범위e820 memory mapfirmware memory map

핵심 차이: 실제 OS의 physical address는 bus 주소이자 DRAM 주소다. PintOS on QEMU의 physical address는 에뮬레이터가 만든 가상의 물리 주소 공간이다.

PintOS 구현

PintOS는 자신이 물리 메모리를 직접 소유한다고 믿는다. 이 믿음은 ptov()/vtop()에 잘 드러난다:

이 계산은 guest OS 내부 주소 배치 규칙이다. host physical address를 물어보는 시스템 호출이 아니다.

PTE 설치 시 guest PA가 들어가는 지점:

vtop(kpage) 결과는 guest physical frame address다. 이 값이 PTE에 기록되지만 host machine의 DRAM 주소가 아니다.

부팅 시 identity-like mapping:

PintOS가 guest physical page 전체를 kernel VA 영역에 직선 매핑하는 과정이다. 여기서 pa는 guest PA다.

QEMU 에뮬레이션

QEMU는 guest physical memory를 MemoryRegion + RAMBlock으로 backing한다.

  region["MemoryRegion type?"]

  gpa --> flatview
  flatview --> region
  region --> ramblock
  region --> dispatch
  ramblock --> hva
  hva --> copy
  dispatch --> handler

RAMBlock 구조:

host 필드가 핵심이다. guest RAM의 실제 바이트가 QEMU process의 host virtual memory에 있다.

Guest Physical Memory 값 추적

전체 변환 추적 예제

=== 유저 프로그램이 0x8048123 을 읽는다 ===

[1단계: Guest page table walk]
  Guest VA         = 0x0000_0000_8048_0123
  PML4[0] → PDPT[0] → PD[64] → PT[72]
  PTE              = 0x0123_4007 (present, writable, user)
  Guest PA frame   = PTE_ADDR(0x01234007) = 0x0123_4000
  offset           = 0x123
  Guest PA         = 0x0123_4000 + 0x123 = 0x0123_4123

[2단계: PintOS 내부 — vtop/ptov]
  kpage (kernel VA) = ptov(0x01234000) = 0x01234000 + 0x8004000000
                    = 0x80_0523_4000
  vtop(kpage)       = 0x80_0523_4000 - 0x80_0400_0000 = 0x0123_4000
  → 순환 관계: ptov(vtop(x)) = x

[3단계: QEMU memory layer]
  RAMBlock.host    = 0x0000_6000_0000_0000 (설명용)
  RAM offset       = 0x0123_4123  (= Guest PA)
  HVA              = 0x0000_6000_0000_0000 + 0x0123_4123
                   = 0x0000_6000_0123_4123

[4단계: Host OS]
  Host page table이 HVA 0x600001234123 을 실제 DRAM frame으로 변환
  → PintOS가 볼 수 없는 층

PintOS 메모리 크기와 RAMBlock

PintOS 기본 RAM    = 64 MB = 0x400_0000 bytes
RAMBlock.used_length = 0x400_0000
Guest PA 범위      = 0x0000_0000 ~ 0x03FF_FFFF
frame 수           = 64 MB / 4 KB = 16,384 frames

QEMU가 host에서 mmap하는 크기 ≈ 64 MB
→ host process의 RSS에 ~64 MB가 잡힌다

GDB 관찰 스크립트

아래 스크립트로 4층 주소 변환이 실제로 어떻게 일어나는지 관찰할 수 있다.

관찰 시나리오: 유저 프로그램 첫 page fault에서 4층 주소 전부 확인

# page_fault BP에서 정지 후:
(gdb) p/x $cr2
$1 = 0x400c10                    ← Guest VA (유저 프로그램 코드)
(gdb) trace_va_to_gpa 0x400c10
=== VA 0x400c10 변환 추적 ===
PML4[0] → PDPT[0] → PD[2] → PT[12] + offset 0xc10
PTE   = 0x01234007 (present=1, writable=1, user=1)
Guest PA = 0x01234c10
Frame KVA = 0x8005234c10
검증: x/1bx 0x400c10 == x/1bx 0x8005234c10   ← 같은 byte여야 함

# QEMU 내부에서는:
# RAMBlock.host + 0x01234c10 = HVA (host virtual address)
# → host OS가 이 HVA를 실제 DRAM(Host PA)으로 변환
# PintOS/GDB에서는 이 마지막 층을 직접 관찰할 수 없다

관찰 시나리오

시나리오 1: palloc_get_page 반환값의 주소 계층 추적

palloc_get_page(PAL_USER)가 반환한 frame이 4개 주소 층에서 각각 어떤 값인지 추적한다.

# palloc_get_page(PAL_USER) 반환 시:
(gdb) p/x $rax
$1 = 0x8005234000              ← kernel VA (= frame의 KVA)

# Guest PA 계산:
(gdb) p/x 0x8005234000 - 0x8004000000
$2 = 0x1234000                 ← Guest PA

# 이 Guest PA가 PTE에 들어가는 값:
# *pte = vtop(kpage) | PTE_P | PTE_W | PTE_U
#      = 0x1234000 | 0x7 = 0x1234007

# QEMU 내부에서는:
# RAMBlock.host + 0x1234000 = HVA
# 예: 0x600000000000 + 0x1234000 = 0x600001234000
# GDB에서 HVA는 볼 수 없음 — 이것은 host OS의 주소 공간

# 검증: Guest PA가 palloc pool 범위 안인지
(gdb) p/x init_ram_pages * 0x1000
$3 = 0x4000000                 ← 64MB = 16384 pages
(gdb) p 0x1234000 < 0x4000000
$4 = 1                         ← YES, 범위 안

시나리오 2: pml4_set_page에서 GPA가 PTE에 기록되는 순간

install_page → pml4_set_page에서 vtop(kpage)가 PTE에 들어가는 바로 그 순간을 포착한다.

b pml4_set_page
commands
  silent
  set $gpa = (uint64_t)kpage - 0x8004000000
  printf "[pml4_set_page] upage=%p, kpage=%p\n", upage, kpage
  printf "  Guest PA (vtop) = 0x%lx\n", $gpa
  printf "  PTE will be = 0x%lx\n", $gpa | 0x7
  continue
end

# 실행 결과 예:
# [pml4_set_page] upage=0x400000, kpage=0x8005234000
#   Guest PA (vtop) = 0x1234000
#   PTE will be = 0x1234007
# → 유저가 0x400000을 접근하면 MMU가 PTE에서 GPA 0x1234000을 읽고
# → QEMU SoftMMU가 이를 RAMBlock.host + 0x1234000 = HVA로 변환

시나리오 3: context switch 시 CR3 변경과 SoftMMU TLB flush

두 프로세스 간 context switch에서 CR3가 바뀌면 QEMU SoftMMU TLB가 전면 flush되는 것을 관찰한다.

b pml4_activate
commands
  silent
  set $old = $cr3 & 0xfffffffffffff000
  set $new = (uint64_t)thread_current()->pml4 - 0x8004000000
  printf "[cr3] old GPA=0x%lx → new GPA=0x%lx (%s)\n", \
    $old, $new, thread_current()->name
  if $old != $new
    printf "  → QEMU: tlb_flush(cpu) 호출됨, SoftMMU 캐시 전면 초기화\n"
    printf "  → 이후 모든 메모리 접근은 page table walk부터 시작\n"
  else
    printf "  → 같은 주소 공간, TLB flush 생략 가능\n"
  end
  continue
end

# 프로세스 A→B 전환 시:
# [cr3] old GPA=0x1240000 → new GPA=0x1280000 (process-B)
#   → QEMU: tlb_flush(cpu) 호출됨, SoftMMU 캐시 전면 초기화
# 커널 스레드 간 전환 시:
# [cr3] old GPA=0x1000 → new GPA=0x1000 (idle)
#   → 같은 주소 공간, TLB flush 생략 가능
