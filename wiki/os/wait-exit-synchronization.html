wait/exit 세마포어 동기화

부모가 먼저 기다릴 수도 있고, 자식이 먼저 끝날 수도 있다. wait/exit 동기화는 두 순서 모두에서 종료 코드를 잃지 않게 만드는 약속이다.

누가 먼저 와도 같은 결과가 나와야 한다

부모가 wait(child_tid)를 호출했는데 자식이 아직 실행 중이면 부모는 잠들어야 한다. 반대로 자식이 이미 exit()했다면 부모는 기다리지 않고 종료 코드를 바로 읽어야 한다. PintOS는 struct child_status 안의 wait_sema(초기값 0)와 exited 플래그로 이 두 순서를 모두 처리한다. 세마포어는 “아직 끝나지 않았으면 잠들기”를, 플래그는 “이미 끝났으면 바로 수거하기”를 맡는다.

두 가지 타이밍

부모가 먼저 기다리는 경우와 자식이 먼저 끝나는 경우

부모-자식 동기화에는 두 가지 경쟁 조건이 있다:

시나리오 A: 부모가 먼저 wait

부모: wait(child) → 블록
자식:                     → exit(42) → 부모 깨움
부모:                                        → status=42 수거

시나리오 B: 자식이 먼저 exit

자식: exit(42) → status 기록 → 종료
부모:                              → wait(child) → 즉시 status=42 수거

핵심 요구사항:

  1. 자식이 아직 살아있으면 부모가 블록되어야 한다
  2. 자식이 이미 죽었으면 부모가 블록 없이 즉시 결과를 받아야 한다
  3. exit status는 자식 thread가 소멸된 뒤에도 살아남아야 한다
  4. wait는 같은 자식에 대해 한 번만 가능해야 한다

실제 OS (Linux)

Linux는 wait4() syscall에서 task_struct → exit_state 필드를 확인한다. 자식이 EXIT_ZOMBIE 상태면 즉시 수거하고, 아직 살아있으면 wait_queue_head에 부모를 넣어 블록한다. 자식의 do_exit() → exit_notify()가 wake_up_parent()를 호출하여 부모를 깨운다. 좀비 프로세스(task_struct만 남은 상태)가 wait/exit 사이의 status 보존 역할을 한다.

PintOS 구현

PintOS는 Linux의 좀비 대신 struct child_status라는 별도 구조체로 동기화한다.

struct child_status 핵심 필드:

process_exit_with_status() + finish_self_status() — 자식 측:

두 시나리오의 세마포어 값 변화:

시점시나리오 A (부모 먼저)시나리오 B (자식 먼저)
초기wait_sema = 0wait_sema = 0
부모 wait 또는 자식 exitsema_down(0→블록)cs->exited = true, sema_up(0→1)
나머지 측 동작cs->exited = true, sema_up(→깨움)sema_down 안 함 (exited==true)
최종status 수거, cs 해제즉시 status 수거, cs 해제

child_status의 수명 관리

fork()에서 malloc   →   자식 thread 실행   →   exit()에서 status 기록
                                                     ↓
                                              wait()에서 free
                                              또는
                                              부모 exit → reparent_or_reap

child_status는 thread보다 오래 산다. 자식 thread가 소멸된 후에도 child_status는 부모의 child_status_list에 남아 있다가, 부모가 wait()을 호출하면 그때 free()된다.

부모가 wait하지 않고 먼저 죽으면? reparent_or_reap_children()이 orphaned = true로 표시하거나, 이미 exited된 child_status는 즉시 free한다.

wait/exit 세마포어 동기화 숫자 추적

struct child_status 메모리 사용량 (x86-64):

  • tid_t tid: 4 bytes
  • int exit_status: 4 bytes
  • bool waited: 1 byte
  • bool exited: 1 byte
  • bool orphaned: 1 byte
  • bool fork_success: 1 byte
  • struct semaphore wait_sema: ~40 bytes (value + waiters list)
  • struct semaphore fork_sema: ~40 bytes
  • struct list_elem elem: 16 bytes
  • padding 포함 약 120~128 bytes per child

자식 100개를 fork하면 child_status만 ~12 KB. 각 child의 커널 스택(4 KB) + thread struct보다는 훨씬 가볍다.

QEMU 에뮬레이션

QEMU는 wait/exit 동기화에 직접 관여하지 않는다. 세마포어의 sema_down()/sema_up()은 순수 소프트웨어 로직이며, QEMU가 하는 일은 cli/sti 명령어를 에뮬레이션하여 인터럽트 비활성화 구간을 재현하는 것뿐이다.

다만 디버깅 관점에서 QEMU GDB stub이 유용하다:

  • sema_down()에서 thread가 BLOCKED될 때, GDB로 thread_current()->status를 확인하면 guest OS 내부 상태를 직접 관찰 가능
  • 부모가 sema_down(&cs->wait_sema)에서 블록된 순간, QEMU는 timer interrupt로 다른 thread에게 CPU를 넘기므로, TCG 번역 블록이 자식 thread의 코드로 전환됨
  • sema_up()이 부모를 깨울 때 ready_list에 삽입하는 과정도 guest 메모리의 linked list 조작이므로 GDB로 ready_list 순회 확인 가능

관찰 시나리오

시나리오 1: 부모-먼저-wait 타이밍 확인

목적: 부모가 sema_down에서 실제로 BLOCKED되고, 자식의 sema_up으로 깨어나는 과정을 확인한다.

준비: exec-once 또는 비슷한 테스트에서 부모가 wait()을 호출하고 자식이 정상 종료하는 케이스.

기대 결과: 부모 thread가 BLOCKED 상태에서 자식의 sema_up 호출 후 READY로 전환.

시나리오 2: 자식-먼저-exit 즉시 수거 확인

목적: 자식이 먼저 exit한 후 부모의 wait()이 sema_down 없이 즉시 status를 수거하는지 확인한다.

기대 결과: cs->exited == true이므로 sema_down 호출 없이 바로 status = cs->exit_status → free(cs).
