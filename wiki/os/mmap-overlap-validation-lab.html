mmap은 왜 이미 쓰는 주소 범위를 덮으면 안 되나

mmap 주소 재사용

mmap()은 파일을 사용자 가상 주소에 연결한다.

그렇다면 같은 주소에 다시 mmap()을 호출하면 어떻게 처리해야 할까?

이 문서에서 다루는 PintOS 테스트는 두 번째 호출이 실패해야 한다고 기대한다. 이는 일반 운영체제 전체의 동작을 단정하는 설명이 아니라, 뒤에서 확인할 PintOS 테스트의 판정 기준이다.

여기서 핵심 질문은 다음과 같다.

첫 번째 mapping을 아직 실제로 읽지 않아 page table에 present PTE가 없을 수 있는데, 커널은 어떻게 “이미 쓰는 범위”라고 판단해야 할까?

먼저 살펴볼 질문

이 Lab에서는 mmap-overlap, mmap-over-code, mmap-over-data, mmap-over-stk 테스트를 한 묶음으로 살펴본다. 먼저 주소 범위가 겹치면 안 되는 이유를 이해하고, 그다음 PintOS의 SPT와 page table이 각각 무엇을 나타내는지 구분하면 다음 질문에 답하기 쉽다.

  • 왜 mmap은 시작 주소 하나가 아니라 page range 전체를 검사해야 할까?
  • code, data, stack page 위에 file-backed page를 붙이면 무엇이 깨질까?
  • lazy mapping은 page table에 아직 없어도 왜 이미 점유된 주소인가?
  • 실제 OS는 주소 범위 충돌을 어디에서 관리할까?
  • PintOS에서는 spt_find_page()와 pml4_get_page() 중 무엇을 봐야 할까?
  • QEMU는 두 mapping이 같은 사용자 VA를 요구했다는 사실을 알까?
  • 숫자를 넣으면 [addr, addr + length)가 어떤 page들로 바뀔까?
  • GDB로 어느 함수에서 실패 결정을 확인할 수 있을까?

mmap 주소 겹침을 막아야 하는 이유

가상 주소 공간이 안정적으로 동작하려면 각 주소 범위에는 한 가지 의미만 부여되어야 한다.

예를 들어 같은 page 0x10000000에 다음 두 약속이 동시에 등록되면 서로 충돌한다.

이 상태에서 page fault가 발생하면 커널은 어느 파일을 읽어야 하는지 결정할 수 없다.

더 위험한 경우는 code, data, stack 위에 mmap을 붙이는 것이다.

이 네 종류는 모두 사용자 가상 주소 공간의 page이지만 역할은 서로 다르다. mmap이 기존 page 위에 들어가면 instruction, 전역 변수, 지역 변수, file-backed data 가운데 하나의 의미가 다른 의미로 덮인다.

따라서 do_mmap()이 가장 먼저 확인해야 할 조건은 “파일을 읽을 수 있는가”가 아니라 “이 VA range가 비어 있는가”이다.

mmap 주소 겹침을 판단하는 흐름

mmap 범위는 half-open range로 해석하면 된다.

이때 page table과 SPT가 답하는 질문을 구분해야 한다.

표대답하는 질문
page table지금 이 VA가 frame으로 번역되는가?
SPT아직 frame이 없어도 이 VA가 원래 합법한 page인가?

lazy loading에서는 SPT에 page 정보가 먼저 나타날 수 있다.

따라서 overlap 검사를 pml4_get_page()만으로 수행해서는 부족하다. 아직 page-in되지 않은 mapping은 pml4_get_page()에서 보이지 않을 수 있기 때문이다.

mmap-overlap 테스트가 확인하는 빈틈

mmap-overlap 테스트는 바로 이 차이를 확인한다.

첫 번째 mmap()이 lazy 방식이라면 이 시점에는 파일을 아직 읽지 않는다.

그렇더라도 해당 주소 범위는 이미 예약되었으므로, 두 번째 mapping은 SPT 충돌로 MAP_FAILED가 되어야 한다.

mmap-over-code, mmap-over-data, mmap-over-stk는 같은 원리를 서로 다른 기존 영역에 적용한다.

테스트새 mmap이 덮으려는 기존 의미
mmap-over-codetest_main() instruction이 있는 code page
mmap-over-datastatic char x가 있는 data/bss page
mmap-over-stk지역 변수 handle이 있는 stack page
mmap-overlap직전에 만든 file-backed mapping page

실제 운영체제와의 비교

Linux는 프로세스 주소 공간을 VMA, 즉 virtual memory area 단위로 관리한다. 파일 mapping, anonymous mapping, stack, heap, executable segment는 모두 주소 범위 metadata로 표현된다.

일반적인 mmap(addr, length, ...)에서 addr는 힌트로 취급될 수 있으므로 커널이 다른 빈 주소를 선택할 수 있다. 반면 MAP_FIXED는 기존 mapping을 대체할 수 있어 위험하며, MAP_FIXED_NOREPLACE는 범위가 겹치면 실패한다.

Windows는 POSIX mmap() 대신 file mapping object와 view를 사용한다. MapViewOfFile 계열도 프로세스 주소 공간에 view 범위를 연결하며, 특정 base address를 요구하는 변형은 충돌할 때 실패할 수 있다.

두 운영체제의 공통된 핵심은 실제 page 접근보다 먼저 주소 범위 metadata를 관리한다는 점이다. 실제 운영체제는 protection, sharing, copy-on-write, page cache, ASLR까지 함께 다루므로 PintOS보다 훨씬 복잡하다.

PintOS에서 확인할 지점

PintOS user header에 정의된 실패값은 NULL이다.

따라서 mmap 실패 시에는 Linux식 (void *) -1이 아니라 NULL을 반환해야 한다.

현재 살펴보는 PintOS VM skeleton에서는 do_mmap()이 아직 비어 있다.

mmap-overlap은 첫 번째 mapping을 읽지 않은 채 곧바로 두 번째 mapping을 시도한다. page table만 보면 “아직 present mapping이 없으므로 비어 있다”고 잘못 판단할 수 있다. 그러나 SPT에는 이미 file-backed page를 만들겠다는 약속이 등록되어 있어야 한다.

QEMU가 아는 것과 모르는 것

QEMU는 PintOS의 mmap 정책을 알지 못한다.

QEMU가 관찰하는 것은 x86 하드웨어 관점의 page table walk다.

즉, QEMU는 “이 VA가 code였는지, stack이었는지, file-backed mmap이었는지”를 판단하지 않는다. 그 의미는 PintOS의 SPT와 page fault handler가 해석한다.

PintOS가 SPT overlap을 막지 않고 두 번째 mapping metadata로 기존 정보를 덮어써도 QEMU는 이를 막아주지 않는다. 이후 page fault가 발생하면 PintOS가 잘못된 file metadata를 바탕으로 frame을 채우게 된다.

QEMU에서 확인할 수 있는 근거는 x86 page bit와 page fault error code의 처리다.

  • target/i386/cpu.h
    • PG_PRESENT_MASK
    • PG_RW_MASK
    • PG_USER_MASK
    • PG_ERROR_P_MASK
    • PG_ERROR_W_MASK
    • PG_ERROR_U_MASK
  • target/i386/tcg/system/excp_helper.c
    • page table walk 중 present/user/write 권한을 검사한다.
    • 접근이 성립하면 TLB에 넣을 권한을 계산한다.
    • 접근이 실패하면 page fault error code를 만든다.

PintOS를 학습할 때는 “실제 운영체제의 mmap(addr)는 힌트일 수 있다”는 사실과 PintOS 테스트의 단순화된 규칙을 구분해야 한다. 여기서 다루는 PintOS 테스트는 사용자가 지정한 주소에 mapping하거나 실패하는 모델을 전제로 한다.

mmap 주소 겹침 값 추적

1. 한 page mapping

두 번째 mmap(0x10000000, 4096, ...)은 같은 page 0x10000000을 다시 요구하므로 실패해야 한다.

2. 두 page mapping

이 경우에는 두 page를 모두 검사해야 한다.

둘 중 하나라도 이미 점유되어 있으면 전체 mmap은 실패해야 한다. 일부 page만 등록한 뒤 실패하면 mapping metadata가 불완전하게 남는다.

3. 겹침 판단에는 half-open range를 사용한다

PintOS에서 page 단위로 순회하면 판단은 단순해진다. 새 mapping이 차지할 각 page base가 SPT나 page table에 이미 존재하는지 확인하면 된다.

정리

  • mmap은 파일을 연결하기 전에 요청한 VA range가 비어 있는지 먼저 확인해야 한다.
  • mmap-overlap은 lazy mapping이 page table에 아직 없어도 SPT에는 이미 존재해야 한다는 점을 확인한다.
  • mmap-over-code/data/stk는 executable segment, data segment, stack page를 file-backed mapping으로 덮어서는 안 된다는 테스트다.
  • PintOS의 실패값은 MAP_FAILED, 즉 NULL이다.
  • overlap 검사를 pml4_get_page()만으로 수행해서는 부족하며, SPT 점유 여부를 반드시 확인해야 한다.
  • QEMU는 mmap 정책을 모르며, guest page table의 present/write/user bit와 page fault를 하드웨어처럼 재현한다.

mmap 주소 겹침 관련 개념

  • mmap file backed page
    • file-backed mapping의 전체 모델을 이해하는 데 필요하다.
  • mmap syscall 흐름
    • SYS_MMAP 인자가 do_mmap()으로 전달되는 입구다.
  • mmap 인자 검증
    • overlap 검사에 앞서 fd, 주소, 길이, offset 자체가 유효한지 판정하는 기준이다.
  • munmap 범위
    • mapping range metadata가 해제 과정에서 다시 필요한 이유를 설명한다.
  • SPT
    • lazy page가 page table보다 SPT에 먼저 남는 이유와 연결된다.
  • file backed metadata
    • page별 file offset과 read bytes를 나타내는 metadata다.
  • mmap readonly 보호
    • 이미 허용된 mapping의 write 권한을 제한하는 별도의 문제다.
  • Page Fault Error Code
    • QEMU나 CPU가 전달한 page fault error code를 PintOS가 해석하는 방법과 연결된다.
