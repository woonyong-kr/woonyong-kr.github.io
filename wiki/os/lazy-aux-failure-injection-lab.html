lazy aux 실패 주입 Lab

lazy aux 실패 주입에서 먼저 헷갈리는 지점

lazy page aux cleanup 구현 체크리스트 Trace는 aux를 누가 정리해야 하는지 분기표로 정리했다.

이 Lab의 질문은 더 실험적이다.

vm_alloc_page_with_initializer() 실패, file_read_at() short read, never-faulted cleanup을 억지로 만들면 같은 aux와 reopened file이 정확히 한 번만 close/free되는가?

여기서 “실패 주입”은 production 코드를 망가뜨리는 구현이 아니라, 디버깅 중에만 켜는 임시 관찰 장치다.

lazy aux 실패 주입 혼동

VM 테스트는 보통 정상 page fault가 살아나는지 먼저 보여 준다. 하지만 aux ownership 버그는 정상 경로만으로는 잘 드러나지 않는다.

관찰하지 않은 경로숨어 있을 수 있는 버그
SPT 등록 실패SPT에 들어가지 못한 aux는 나중에 destroy될 기회가 없다
file_read_at() short readcallback이 false만 반환하면 reopened file과 heap block이 샌다
never-faulted UNINIT destroy접근하지 않은 lazy page의 aux가 process exit 뒤에도 남는다
callback 실패 뒤 claim rollbackPTE와 frame link가 남으면 덜 채워진 frame이 유저에게 노출될 수 있다

이 말은 즉, cleanup 코드는 성공 테스트가 아니라 실패 테스트로 증명해야 한다.

lazy aux 실패 주입 흐름

관찰 대상은 세 개다.

기대 규칙은 단순하다.

경로aux freeaux->file closePTE/frame rollback
등록 실패1회1회아직 없음

중요한 점은 “free 함수가 한 곳”이라는 말이 아니다. 성공, 실패, destroy 경로가 여러 함수에 있어도 같은 pointer에 대해 실제 소유자는 하나여야 한다.

lazy aux 실패 주입 사례

마지막 executable segment page가 다음 값으로 등록됐다고 하자.

정상 성공이면 frame은 이렇게 채워진다.

short read를 주입하면 기대 결과가 바뀐다.

frame bytes가 일부 채워졌는지는 핵심이 아니다. 핵심은 그 frame이 유저 주소로 노출되지 않고, 자원 소유권이 한 번만 닫히는가다.

실제 운영체제

Linux와 Windows도 file-backed demand paging 중 I/O 실패, 메모리 부족, mapping teardown 같은 실패 경로를 다룬다. 현실 OS는 VMA/VAD, section object, page cache, reference count 같은 더 큰 장부로 수명을 관리한다.

PintOS에서는 이 장부가 작고 노골적이다. UNINIT page의 aux, struct file_page, struct frame, SPT entry가 그 장부 역할을 나눠 가진다.

QEMU

QEMU는 aux를 모른다.

QEMU가 볼 수 있는 것은 x86 page fault 결과다. QEMU의 target/i386/tcg/system/excp_helper.c는 page translation 실패 때 EXCP0E_PAGE, error code, cr2 = addr를 만든다. 이후 guest CR2에 fault address가 들어간다.

따라서 QEMU 관찰은 보조 증거다.

QEMU가 보여 주는 것QEMU가 모르는 것
not-present pf가 발생했는가aux가 leak됐는가
write/read error code bitreopened file이 double close됐는가
handler가 돌아온 뒤 같은 instruction이 재시도되는가uninit_destroy()가 어떤 helper를 불렀는가

aux cleanup은 PintOS 커널 내부 장부이므로 GDB breakpoint와 임시 counter로 직접 봐야 한다.

실험 준비

먼저 구현 코드에 임시 로그 지점을 하나로 모은다. 이름은 예시다. 실제 구현의 aux 구조체 이름에 맞춰 바꾼다.

이 helper는 permanent code가 아니다. 관찰이 끝나면 제거한다.

GDB에서는 다음 breakpoint를 기본으로 둔다.

free는 너무 자주 멈출 수 있으므로 처음에는 helper breakpoint를 더 우선한다.

실험 1. SPT 등록 실패 cleanup

작은 질문:

aux를 만든 뒤 SPT 등록이 실패하면 누가 닫는가?

임시 실패 주입:

또는 같은 upage를 두 번 등록하도록 만들어 spt_insert_page()가 실패하는 경로를 탄다.

관찰 기준:

항목기대값

SPT lookup해당 upage entry 없음
이후 uninit_destroy()같은 aux로 다시 호출되지 않음

이 경로는 SPT에 page가 들어가기 전이다. 그래서 나중 cleanup에 맡기면 안 된다.

실험 3. never-faulted UNINIT cleanup

작은 질문:

등록은 됐지만 한 번도 접근하지 않은 lazy page의 aux는 어디서 닫히는가?

관찰용 user program은 mmap page가 가장 만들기 쉽다.

executable lazy page도 같은 원리다. 프로그램이 특정 segment page를 한 번도 접근하지 않고 exit하면 그 page는 UNINIT 상태로 SPT에 남을 수 있다.

GDB 관찰:

관찰 기준:

항목기대값
page->operations->typeVM_UNINIT
page->frameNULL
PTE없음
aux destroy1회
dirty write-back없음

never-faulted page는 frame bytes가 없다. 따라서 이 경로에서 file_write_at()이 호출되면 이상하다. write-back은 resident FILE page가 dirty일 때의 문제다.

실험 4. mmap file ownership 이동

작은 질문:

mmap page가 첫 fault에 성공한 뒤 file reference owner는 aux인가, page->file인가?

mmap-close와 mmap-remove는 이 질문을 확인하는 좋은 테스트다.

성공 기준:

시점기대 owner
first fault 전page->uninit.aux
first fault 성공 직후page->file 또는 region metadata
aux wrapper free 뒤aux->file = NULL 같은 ownership 이동 표시
munmap()/exitfile_backed_destroy() 또는 region cleanup이 file close

close(handle) 뒤 mapped data를 읽을 수 없으면 file_reopen() 또는 ownership 이동이 실패한 것이다. remove("sample.txt") 뒤 mapped data가 깨지면 file reference가 inode 수명과 분리되지 않았을 가능성이 크다.

정리

  • 등록 실패는 아직 SPT owner가 없으므로 등록자가 aux를 정리한다.
  • callback 실패는 aux cleanup과 PTE/frame rollback을 나누어 본다.
  • never-faulted UNINIT page는 uninit_destroy()가 cleanup owner다.
  • mmap 성공 경로는 aux를 없애되 file metadata를 page->file 또는 region으로 옮겨야 한다.
  • QEMU는 pf와 CR2만 보여 주며, aux leak과 double close는 PintOS 내부 계측으로 확인해야 한다.
