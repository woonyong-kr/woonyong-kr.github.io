mmap file page의 aux는 언제 struct file_page로 옮겨야 하나

한 줄 요약: mmap page의 aux는 첫 fault 전 VM_UNINIT page가 들고 있는 임시 작업 지시서다. 첫 fault가 발생하면 file·offset·read_bytes를 같은 union 자리의 page->file(struct file_page)로 옮기고, aux 자체는 성공·실패 경로를 통틀어 정확히 한 번만 정리해야 한다.

mmap file aux 전환의 쟁점

file backed page metadata에는 무엇을 저장해야 하나는 mmap() page가 file, offset, read bytes, zero bytes를 기억해야 한다고 설명한다.

그런데 PintOS VM 스켈레톤에서는 file-backed page도 처음에 VM_UNINIT page로 SPT에 들어갈 수 있다.

따라서 다음 질문을 해결해야 한다.

do_mmap()에서 만든 page별 작업 지시서 aux를 첫 page fault 뒤에도 그대로 보관해야 할까, 아니면 struct file_page로 옮겨야 할까?

짧은 답은 다음과 같다.

mmap file aux 전환 단계

mmap() page는 두 단계의 생명주기를 거친다.

첫 번째는 아직 frame이 없는 단계다.

두 번째는 첫 page fault가 발생한 뒤의 단계다.

여기서 주의할 점은 struct page 안의 uninit과 file이 같은 union의 멤버라는 사실이다.

따라서 page가 VM_FILE로 바뀐 뒤에도 page->uninit.aux를 계속 유효한 저장소로 간주하면 위험하다. 같은 메모리 자리를 이제는 page->file로 해석해야 하기 때문이다.

또한 aux는 보통 heap에 별도로 할당한 작은 구조체다. 첫 fault가 성공한 뒤에는 이를 UNINIT 작업 지시서로 남겨 둘 이유가 없다. 반대로 fault가 실패하거나, 한 번도 fault가 발생하지 않은 상태에서 munmap()/exit()이 호출되면 누군가 이를 정리해야 한다.

mmap file aux 전환 흐름

전체 흐름은 다음 두 단계로 이해할 수 있다.

단계page 상태metadata 위치주된 사용자

aux는 택배 송장에 비유할 수 있다.

첫 fault 뒤에도 계속 필요한 정보는 page->file에 남겨야 한다.

따라서 핵심 불변식은 다음과 같이 정리할 수 있다.

사용자가 파일의 두 번째 page를 메모리에 연결하는 경우

do_mmap()은 파일을 즉시 읽지 않고 SPT에 lazy page만 넣을 수 있다.

그 뒤 첫 접근에서 page fault가 발생한다.

이때 load_mmap_page() 같은 초기화 callback은 aux의 내용을 page->file으로 옮겨야 한다.

이 전환을 빠뜨리면 나중에 munmap(p)가 호출될 때 문제가 생긴다.

실제 운영체제에서는

Linux의 mmap()은 VMA와 file reference, page cache, fault handler를 통해 이 문제를 해결한다.

처음부터 모든 page를 읽지 않더라도 VMA가 “이 주소 범위가 어느 file의 어느 offset에서 왔는지”를 기억한다. 첫 fault가 발생하면 커널은 그 정보를 바탕으로 page cache/file page를 연결하고 PTE를 만든다.

Windows도 file mapping object와 mapped view, section object, VAD 같은 구조로 같은 종류의 문제를 처리한다. 사용자는 MapViewOfFile()로 주소 범위를 얻지만, 커널은 해당 view가 어떤 file object와 offset에 연결되는지 별도로 관리한다.

실제 OS와 PintOS 사이에는 큰 차이가 있다.

  • 실제 OS는 범위 단위 metadata, page cache, reference count, write-back 정책을 함께 다룬다.
  • PintOS에서는 학습을 위해 구현자가 struct page, SPT, struct file_page, 직접 만든 aux/region object에 이러한 의미를 명시적으로 담아야 한다.

그러나 공통된 결론은 같다.

PintOS에서는

W09 PintOS skeleton에는 이 전환과 관련된 세 가지 자리가 이미 마련되어 있다.

첫째, struct page는 type별 metadata를 union으로 둔다.

둘째, struct uninit_page는 future type과 aux를 가진다.

셋째, struct file_page는 아직 비어 있다.

이 구조의 의도는 “처음에는 uninit으로 생성되고, 첫 fault 때 file page로 전환된다”에 가깝다.

여기서 file_backed_initializer()의 인자를 주의해서 봐야 한다.

이 함수는 aux를 받지 않으므로 page별 file offset과 read bytes를 알 수 없다. 따라서 실제 metadata 복사는 보통 uninit_initialize()가 지역 변수에 보관한 aux를 전달받는 초기화 callback에서 수행해야 한다.

이 코드는 완성된 구현이 아니라 ownership 기준을 보여 주는 예시다. 실제 구현에서는 실패 경로의 file close, frame/PTE 정리, aux free가 각각 한 번만 일어나도록 더욱 주의해야 한다.

munmap()과 process_exit()의 관점에서 보면 상태마다 정리 방식도 달라진다.

특히 mmap-close와 mmap-remove는 file reference의 ownership을 직접 검증한다. 사용자가 원래 fd를 닫거나 파일 이름을 지워도 mapping은 기존 file 내용을 읽을 수 있어야 한다. 따라서 do_mmap()은 fd table의 원래 struct file *에 의존하지 않고 file_reopen() 또는 별도의 mapping reference를 가져야 한다.

QEMU의 역할

QEMU는 aux, struct file_page, mmap_region을 알지 못한다.

QEMU가 관찰하는 대상은 더 낮은 계층에 있다.

관련된 QEMU 단서는 다음과 같다.

  • target/i386/tcg/system/excp_helper.c
    • store access에서 PG_DIRTY_MASK를 set 후보에 넣는다.
    • page fault는 EXCP0E_PAGE와 err.cr2를 통해 guest에 전달된다.
  • hw/ide/core.c
    • ide_sector_write()가 sector_num << BDRV_SECTOR_BITS로 block backend offset을 만든다.

즉, QEMU는 “metadata를 aux에서 file_page로 옮겨야 한다”는 종류의 버그를 막아 주지 않는다. 이 전환은 PintOS 커널 자료구조를 설계하는 쪽의 책임이다.

핵심:

UNINIT일 때는 page->uninit을 읽고, VM_FILE이 된 뒤에는 page->file을 읽는 모델로 이해해야 한다.

2. uninit_initialize()는 aux를 지역 변수에 보관한다

파일:

  • pintos/vm/uninit.c

핵심:

이 순서가 중요하다. page_initializer()가 page->operations와 union의 해석을 바꾸더라도 지역 변수 aux는 callback에 전달할 수 있다.

3. file-backed page 함수들은 page->file을 사용한다

파일:

  • pintos/vm/file.c
  • pintos/include/vm/file.h

핵심:

현재 struct file_page는 비어 있으므로 구현자가 file, offset, read/zero bytes를 채워 넣어야 한다.

4. SPT kill은 never-faulted UNINIT도 정리한다

파일:

  • pintos/vm/vm.c
  • pintos/userprog/process.c

흐름:

한 번도 접근하지 않은 mmap page에는 frame과 PTE가 모두 없을 수 있다. 그래도 aux 안의 reopened file과 heap memory는 남아 있을 수 있으므로, uninit_destroy()가 정리 기준을 가져야 한다.

5. offset 기반 I/O는 file position을 바꾸지 않는다

파일:

  • pintos/filesys/file.c

핵심:

mmap page에는 page별 file offset이 고정되어 있다. 따라서 file_read()/file_write()처럼 file->pos를 움직이는 API보다 *_at() 계열이 적합하다.

파일:

  • pintos/tests/vm/mmap-remove.c

정리

  • aux는 UNINIT page가 첫 fault까지 들고 가는 임시 초기화 인자다.
  • struct file_page는 page가 VM_FILE이 된 뒤 swap_in/out, munmap, destroy에서 사용하는 지속 metadata다.
  • struct page의 uninit과 file은 union이므로, VM_FILE로 전환된 뒤에는 page->uninit.aux를 계속 의미 있는 저장소로 간주하면 안 된다.
  • uninit_initialize()는 aux를 지역 변수에 보관한 뒤 page_initializer()와 callback을 호출하므로, callback에서 aux -> page->file 전환을 수행할 수 있다.
  • 한 번도 fault가 발생하지 않은 mmap page는 uninit_destroy()가 aux와 file reference를 정리해야 한다.
  • fault가 성공한 page는 file_backed_destroy()나 region cleanup이 page->file metadata와 file reference를 정리해야 한다.
  • QEMU는 이 ownership 전환을 알지 못하며 page fault, dirty bit, IDE sector write 같은 하드웨어 효과만 재현한다.

mmap file aux 전환 관련 문서

  • file backed page metadata
    • struct file_page에 무엇을 저장해야 하는지 설명
  • lazy aux ownership
    • first fault 전후 aux owner를 한 곳으로 고정하는 공통 규칙
  • lazy aux cleanup
