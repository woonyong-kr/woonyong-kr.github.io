Program Header와 PT_LOAD

Program Header와 PT_LOAD

한 줄 요약: 파일 구간을 어느 주소에 어떤 권한으로 올릴지 알려주는 ELF Program Header 중 실제 적재되는 PT_LOAD.

Program Header와 PT_LOAD 차이

ELF 파일의 Program Header는 “파일의 어느 구간을 메모리 어느 주소에 어떤 권한으로 올릴지”를 OS 로더에게 알려주는 지시서다. 여러 타입의 program header 중 PT_LOAD는 실제로 메모리에 적재되는 세그먼트를 기술한다. 전형적인 실행 파일에는 읽기 전용 코드와 rodata를 담는 세그먼트, 읽기와 쓰기가 가능한 데이터와 BSS를 담는 세그먼트에 대응하는 PT_LOAD가 2개 있다. 로더는 각 PT_LOAD의 p_offset, p_vaddr, p_filesz, p_memsz, p_flags를 읽어 파일 바이트를 가상 주소에 매핑하고, p_memsz - p_filesz만큼의 영역을 0으로 채운다.

상세 설명

추상 개념 (ELF Program Header 구조)

ELF64의 Program Header는 Elf64_Phdr라는 56바이트 구조체로 표현된다.

p_type에 따라 Program Header의 역할과 메모리 적재 여부가 달라진다.

p_type값의미메모리 적재?
PT_NULL0빈 항목아니오
PT_LOAD1적재 가능 세그먼트예
PT_DYNAMIC2동적 링킹 정보아니오 (PintOS 미지원)
PT_INTERP3인터프리터 경로아니오 (PintOS 미지원)
PT_NOTE4부가 정보아니오
PT_PHDR6프로그램 헤더 테이블 자체아니오
PT_STACK0x6474e551스택 속성아니오 (GNU 확장)

PT_LOAD에서는 다섯 필드가 파일 구간과 가상 메모리 구간을 연결한다.

  virtual_memory["가상 메모리<br/>p_filesz bytes<br/>파일에서 읽기 &#124; p_memsz - p_filesz<br/>0으로 채움<br/>p_vaddr → p_vaddr + p_filesz &#124; p_vaddr + p_filesz → p_vaddr + p_memsz"]

p_memsz > p_filesz이면 두 크기의 차이가 BSS 영역에 해당한다. 전역 변수 int arr[1000] = {0}은 파일에 4000바이트를 저장하는 대신 p_memsz를 늘려 해당 영역을 0으로 채우는 방식으로 표현할 수 있다.

실제 OS (Linux)

이 문서에서는 Linux의 ELF 로더(fs/binfmt_elf.c)가 각 PT_LOAD 세그먼트를 mmap()으로 파일에 직접 매핑하고, 이후 page fault가 발생하면 해당 page를 파일에서 읽는 demand paging 방식으로 동작한다고 설명한다. 또한 BSS에 해당하는 p_memsz - p_filesz 영역은 anonymous mapping으로 0 page를 제공한다고 본다. 다만 입력에는 이를 확인할 Linux 소스 인용이나 실행 결과가 없으므로, 여기서는 PintOS 구현과 구분해 일반적인 동작 설명의 범위로 다룬다.

이 설명에 따른 전형적인 Linux ELF 실행 파일의 PT_LOAD 배치는 다음과 같다.

LOAD 0: p_flags=R-X  p_vaddr=0x400000  .text + .rodata  (코드)
LOAD 1: p_flags=RW-  p_vaddr=0x600000  .data + .bss     (데이터)

PintOS 구현

PintOS의 load() 함수(userprog/process.c)는 ELF header에서 e_phoff와 e_phnum을 읽는다. e_phoff는 program header table의 시작 오프셋이고, e_phnum은 program header의 개수다. load()는 이 두 값을 사용해 각 program header를 순회한다.

PT_LOAD를 만나면 다음 흐름으로 처리한다.

validate_segment()는 다음 다섯 조건으로 세그먼트를 검사한다.

검사조건이유
page 정렬 일치(p_offset & PGMASK) == (p_vaddr & PGMASK)파일과 메모리의 page 내 오프셋이 같아야 매핑 가능
파일 범위p_offset ≤ file_length파일 밖을 가리키면 안 됨
크기 관계p_memsz ≥ p_filesz메모리가 파일보다 작을 수 없음
유저 영역is_user_vaddr(p_vaddr) 및 끝 주소커널 영역 침범 방지
0번 page 금지p_vaddr ≥ PGSIZENULL 포인터 영역 보호

read_bytes와 zero_bytes를 계산할 때는 p_vaddr이 page 경계에 정렬되지 않을 가능성을 고려해야 한다. 이를 위해 page_offset으로 page 내부의 오프셋을 구해 보정한다.

예시:
  p_offset  = 0x1000
  p_vaddr   = 0x401000
  p_filesz  = 0x2345
  p_memsz   = 0x3000

계산:
  page_offset = 0x401000 & 0xFFF = 0x000
  file_page   = 0x1000 & ~0xFFF  = 0x1000
  mem_page    = 0x401000 & ~0xFFF = 0x401000
  read_bytes  = 0 + 0x2345       = 0x2345 (9029 bytes)
  total_mem   = ROUND_UP(0 + 0x3000, 0x1000) = 0x3000
  zero_bytes  = 0x3000 - 0x2345  = 0x0CBB (3259 bytes)

계산된 값은 load_segment()로 전달되고 page 단위로 나뉘어 적재된다. VM이 활성화된 경우에는 load_segment()가 파일을 즉시 읽지 않고 UNINIT page로 등록해 demand paging을 수행한다.

QEMU 에뮬레이션

이 문서에서 설명하는 역할 구분에서는 QEMU가 ELF header나 program header를 직접 해석하지 않는다. PintOS 커널이 disk_read()로 ELF 파일의 섹터를 읽고, 커널 코드가 그 바이트를 파싱해 program header를 해석한다. 따라서 QEMU의 관점에서는 IDE 디스크 섹터 읽기 요청이 연속으로 들어온다.

Program Header와 PT_LOAD 값 추적

다음은 전형적인 PintOS 유저 프로그램의 PT_LOAD 예시다.

$ readelf -l build/tests/userprog/args-single

Program Headers:
  Type   Offset    VirtAddr           FileSiz  MemSiz   Flg Align
  LOAD   0x001000  0x0000000000400000 0x001a30 0x001a30 R E 0x1000
  LOAD   0x003000  0x0000000000402000 0x000128 0x000130 RW  0x1000
세그먼트p_offsetp_vaddrp_fileszp_memsz권한read_byteszero_bytes
code0x10000x4000000x1a300x1a30R-X0x1a300x05d0
data0x30000x4020000x01280x0130RW-0x01280x0ed8

code 세그먼트는 p_filesz == p_memsz이므로 BSS가 없다. 다만 마지막 page에서 파일 데이터가 차지하지 않는 나머지 영역은 0으로 채운다. data 세그먼트에서는 p_memsz(0x130) - p_filesz(0x128) = 8 bytes가 BSS에 해당하며, 초기화되지 않은 전역 변수가 이 영역에 놓인다.

page별로 나누면 다음과 같다.

code 세그먼트 (0x1a30 bytes, page_offset = 0):

page 0: VA 0x400000, read 4096B from file offset 0x1000
page 1: VA 0x401000, read 2608B(0xa30) from file, zero 1488B(0x5d0)

data 세그먼트 (0x128 file bytes, 0x130 mem bytes):

page 0: VA 0x402000, read 296B(0x128) from file, zero 3800B(0xed8)
