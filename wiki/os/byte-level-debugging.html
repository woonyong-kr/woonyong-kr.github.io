Byte-level 디버깅 — 같은 바이트, 다른 해석

확인 범위: 이 문서는 같은 바이트가 해석 방식에 따라 다른 의미를 갖는 일반 원리와 GDB·PintOS·QEMU에서의 적용 기준을 설명한다. 제시된 구조체 offset, 코드 좌표, 명령 결과, swap I/O 일치 여부 등 구현·버전·실행 환경에 의존하는 내용은 특정 코드나 실행 기록으로 검증된 결과가 아니라 실제 대상 환경에서 별도로 확인해야 할 예시다.

한 줄 요약: 메모리의 바이트는 해석 방식에 따라 정수·포인터·명령어·구조체가 된다 — GDB x/x·x/d·x/i·x/s로 같은 바이트를 다르게 읽는 감각.

Byte-level 디버깅 구조

OS 디버깅에서 가장 중요한 감각은 “메모리에 있는 바이트는 그 자체로는 의미가 없고, 해석 방식에 따라 정수, 포인터, 명령어, 구조체 필드가 된다”는 인식이다. GDB에서 x/x, x/d, x/i, x/s 같은 포맷을 바꾸면 같은 바이트가 전혀 다르게 보인다. 이 감각이 없으면 page fault의 CR2, swap slot의 sector 번호, intr_frame의 필드를 디버깅할 때 “이 숫자가 무엇인가?”에서 막힌다.

상세 설명

추상 개념 (바이트 해석 규칙)

메모리의 모든 데이터는 바이트 시퀀스다. 의미는 해석자가 부여한다.

바이트정수 해석포인터 해석명령어 해석문자 해석
48 c7 c7 01 00 00 000x000001c7c748유효하지 않은 주소mov $1, %rdi의미 없음
68 65 6c 6c 6f0x6f6c6c6568유효하지 않은 주소push $0x6c6c6568…hello
00 10 00 00 00 00 00 0040960x1000 (1페이지)add %dl,(%rax) …\0\x10...

x86-64는 little-endian이다. 주소 0x1000에 8바이트 정수 0x0000000000001000이 저장되면:

addr:  0x1000  0x1001  0x1002  ...  0x1007
byte:    00      10      00    ...    00

GDB에서 x/1gx 0x1000은 0x0000000000001000을 보여주지만, x/8bx 0x1000은 00 10 00 00 00 00 00 00을 보여준다. 같은 바이트, 다른 표현.

실제 OS (Linux/Windows)

실제 OS 디버깅에서도 byte-level 감각은 동일하게 중요하다.

Linux 커널 디버깅에서의 예:

  • crash 도구로 커널 메모리를 직접 읽을 때, struct task_struct의 offset을 계산하여 특정 필드를 바이트로 확인
  • dmesg에 BUG: unable to handle page fault at 0xdead000000000108 같은 메시지가 나오면, 0xdead는 KASAN poison 패턴일 수 있고, 이것을 아는지 모르는지가 디버깅 속도를 결정

커널이 사용하는 디버깅 패턴 바이트:

패턴용도의미
0xdeadbeeffreed memory해제된 메모리를 읽으면 바로 눈에 띔
0xccccccccMSVC uninitialized stack초기화되지 않은 지역 변수
0x5a5a5a5aLinux SLUB freed objectslab allocator가 해제 표시
0xa5a5a5a5Linux SLUB poison유효하지 않은 데이터 표시
0x6b6b6b6bLinux SLUB freedk의 반복

PintOS + QEMU 디버깅 실전

PintOS 디버깅에서 byte-level 관점이 필요한 대표 상황:

1. page fault 디버깅 — CR2 해석

2. intr_frame 바이트 직접 읽기

3. swap slot 검증 — 디스크의 바이트와 메모리의 바이트 비교

4. PTE 바이트 직접 읽기

QEMU 관찰 계층

QEMU GDB stub을 통해 보는 값은 모두 guest 관점이다.

GDB 명령보이는 것실제 위치
info registersguest CPU 레지스터QEMU CPUX86State.regs[]
x/Nx addrguest 가상 메모리QEMU softmmu가 guest PT를 walk하여 host memory에서 읽음
x/Ni addrguest 명령어위와 같은 바이트를 x86 명령어로 디코드
monitor info memguest 페이지 테이블 매핑QEMU가 guest CR3 기반으로 요약
monitor xp/Nx paddrguest 물리 메모리QEMU RAMBlock에서 직접 읽음

x/Nx는 guest 가상 주소, monitor xp/Nx는 guest 물리 주소다. 둘의 차이를 이해하지 못하면 커널 VA와 유저 VA가 겹치는 상황에서 혼란이 생긴다.

Byte-level 디버깅 값 추적

GDB 포맷 문자 정리:

x/[개수][포맷][크기] [주소]

포맷:
  x = hex         d = decimal      u = unsigned
  o = octal       t = binary       i = instruction
  c = char        s = string       a = address

크기:
  b = 1 byte      h = 2 bytes (halfword)
  w = 4 bytes     g = 8 bytes (giant)

PintOS의 주요 구조체 크기와 offset:

struct thread:
  sizeof = 약 168 bytes (구현에 따라 다름)
  status offset: 일반적으로 +16 (tid 뒤)

struct intr_frame:
  sizeof = 약 184 bytes
  R.rax offset:    112
  R.rdi offset:     72
  rip offset:      152
  rsp offset:      176
  error_code offset: 144

struct page:
  va offset:       구현에 따라 다름
  frame offset:    va 뒤
  type offset:     union 앞

page table walk에서의 주소 비트 분할:

64-bit VA (48 usable bits):
  [63:48]  sign extension (canonical)
  [47:39]  PML4 index    (9 bits, 512 entries)
  [38:30]  PDPT index    (9 bits)
  [29:21]  PD index      (9 bits)
  [20:12]  PT index      (9 bits)
  [11:0]   page offset   (12 bits, 4096 bytes)

각 테이블: 512 entries × 8 bytes = 4096 bytes = 1 page
