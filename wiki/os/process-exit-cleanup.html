프로세스 종료 자원 회수

프로세스 종료 자원 회수

확인 범위: 이 문서는 프로세스 종료 시 자원 회수의 일반 원리와 Linux·PintOS·QEMU에서의 구현 및 관찰 지점을 설명한다. 다만 제시된 함수 호출 순서, 코드 좌표, 자원 크기·회수량, GDB 관찰 결과와 성능 관련 판단은 특정 코드·빌드 구성·버전 및 실제 실행 기록을 대조해야 검증할 수 있다.

프로세스가 끝나면 커널은 주소 공간, 열린 파일, 자식 상태 레코드처럼 프로세스가 붙잡고 있던 자원을 순서대로 놓아야 한다. 종료 처리는 단순히 실행을 멈추는 일이 아니라, 남은 참조를 정리하는 일이다.

프로세스 종료 자원 회수 상태

프로세스가 종료할 때 커널은 그 프로세스가 소유한 모든 자원을 체계적으로 회수해야 한다. 회수 대상은 가상 메모리(SPT, 페이지 테이블, frame, swap slot), 파일 시스템 자원(fd table, running executable), 프로세스 계층 구조(child status records)다. 회수 순서가 잘못되면 dangling pointer, 메모리 누수, 좀비 프로세스가 발생한다.

상세 설명

추상 개념 (OS 일반 원칙)

프로세스 종료 시 커널이 회수해야 하는 자원 범주:

범주자원회수하지 않으면
메모리물리 frame, swap slot, page table물리 메모리 고갈
파일열린 fd, inode 참조 카운트fd 누수, 파일 삭제 불가
프로세스 구조child status, wait semaphore좀비 프로세스, 부모 무한 대기
실행 파일write deny lock실행 중 파일 수정 가능 (보안 위반)

핵심 원칙: 역순 해제 — 자원은 할당의 역순으로 해제한다. 특히 가상 주소 공간(SPT)을 먼저 정리하고, 그 다음 페이지 테이블(PML4)을 파괴해야 한다.

실제 OS (Linux)

Linux에서 do_exit() → exit_mm() → exit_files() → exit_notify() 순서로 자원을 회수한다. mm_struct의 참조 카운트가 0이 되면 mmput()이 VMA를 순회하며 frame을 해제한다. fd table은 put_files_struct()가 모든 struct file을 fput()으로 닫는다.

PintOS 구현

PintOS에서 프로세스 종료는 두 계층으로 나뉜다:

1단계: thread_exit() (threads/thread.c:379)

2단계: process_exit() (userprog/process.c:613)

회수 순서 (VM/non-VM 분기):

%% process_exit() 자원 회수 흐름
flowchart TD
  start["thread_exit()"]
  exit["process_exit()"]

  finish["finish_self_status(curr)<br/>exit status 저장 + sema_up"]
  cleanup_after["VM 빌드?"]
  cleanup_non_vm["process_cleanup()<br/>non-VM: PML4만 파괴"]
  intr["intr_disable()"]
  schedule["do_schedule(THREAD_DYING)"]
  pml4_null["pml4_null"]

VM 빌드에서 순서가 중요한 이유:

process_cleanup()이 close_open_files()보다 먼저 호출된다. SPT에 file-backed page가 있으면 dirty page를 write-back해야 하는데, 이때 파일이 아직 열려 있어야 한다. SPT kill이 file close보다 먼저 실행되는 것은 이 때문이다.

non-VM 빌드에서 process_cleanup()이 맨 마지막인 이유: 파일 close가 PML4와 무관하므로 순서가 자유롭고, reparent/finish까지 끝낸 뒤 마지막에 PML4를 파괴해도 안전하다.

process_cleanup() 상세:

process_cleanup()은 process.c:29에 선언되어 있고, VM 빌드에서는 process_exit():620에서 호출된다. non-VM 빌드에서는 :632에서 호출된다.

curr->pml4 = NULL → pml4_activate(NULL) → pml4_destroy(pml4) 순서의 이유: 타이머 인터럽트가 process_activate()를 통해 이미 파괴된 PML4를 CR3에 로드하는 것을 방지한다.

reparent_or_reap_children() 상세 (process.c:535):

주의: list_next(e)를 remove 전에 호출해야 한다. remove 후에는 elem의 prev/next가 무효화되기 때문이다.

finish_self_status() 상세 (process.c:561):

process_exit_with_status() (process.c:585): process_exit()와 별도로 존재하는 진입점이다. printf("%s: exit(%d)\n", ...) 출력 → self_status->exit_status 설정 → thread_exit() 호출. thread_exit() 안에서 process_exit()가 다시 호출되어 실제 자원 회수가 이뤄진다.

QEMU 에뮬레이션

process_exit()은 순수 OS 소프트웨어 로직이므로 QEMU가 직접 관여하지 않지만, 자원 회수 과정에서 QEMU 하드웨어 에뮬레이션이 개입하는 지점이 있다:

  1. SPT kill → file-backed dirty writeback: mmap된 dirty page를 원본 파일에 쓸 때, file_write_at() → inode → IDE controller → QEMU block backend 경로를 탄다.
  2. swap slot 해제: anon_destroy()가 swap bitmap을 해제하지만 실제 디스크 I/O는 없다(bitmap만 false).
  3. PML4 destroy → CR3 전환: pml4_activate(NULL)이 커널 PML4의 물리 주소를 CR3에 로드한다. QEMU TCG는 이를 env->cr[3] 업데이트 + SoftTLB 전체 flush로 처리한다.

GDB에서 자원 회수 관찰 6단계:

  1. b process_exit — 종료 진입점 정지
  2. p thread_current()->name — 어떤 프로세스가 종료하는지 확인
  3. b supplemental_page_table_kill → hit 시 p thread_current()->spt — SPT 크기 확인
  4. b close_open_files → p curr->fd_table[2] ~ p curr->fd_table[10] — 열린 파일 확인
  5. b finish_self_status → p curr->self_status->exit_status — exit status 값 확인
  6. b pml4_destroy → p/x $cr3 — CR3가 커널 PML4로 전환되었는지 확인

race condition 관찰:

  • b process_cleanup 직후 p thread_current()->pml4 — NULL로 설정되었는지 확인
  • 타이머 인터럽트가 끼어들어 process_activate()를 호출해도 pml4=NULL이면 base_pml4를 사용

Linux vs PintOS exit 비교

항목Linux (do_exit)PintOS (process_exit)
진입점do_exit(code) → exit_mm, exit_files, exit_notifyprocess_exit_with_status → thread_exit → process_exit
메모리 회수 순서exit_mm() → mmput() → VMA 순회 → unmap_vmasprocess_cleanup() → spt_kill → pml4_destroy
fd 회수exit_files() → put_files_struct() → fput() per fdclose_open_files() → file_close() per fd
부모 통지exit_notify() → do_notify_parent() (SIGCHLD)finish_self_status() → sema_up(wait_sema)
orphan 처리find_new_reaper() → init(pid 1)이 입양reparent_or_reap_children → orphan_status_list
좀비 상태TASK_ZOMBIE → 부모 wait4()가 task_struct 해제exited=true → 부모 process_wait가 cs free
참조 카운트mm_struct.mm_count, files_struct.count, sighand.count없음 (단일 소유자 모델)
COW frame페이지별 mapcount— → 0이면 free_pagecow_pte의 frame_ref_cnt— → 0이면 palloc_free
실행 파일 보호 해제exe_file fput (deny_write 자동 해제)close_running_file → file_allow_write + file_close
스케줄러 제거finish_task_switch() → put_task_struct()do_schedule(THREAD_DYING) → thread_struct은 idle에서 해제

핵심 차이: Linux는 참조 카운트 기반으로 자원을 공유하고, 카운트가 0이 될 때만 실제 해제한다. PintOS는 단일 소유자 모델이라 exit 시점에 무조건 해제한다. Linux의 좀비 상태(task_struct이 유지됨)는 부모가 waitpid로 수거해야 소멸하지만, PintOS는 child_status 구조체만 남기고 thread_struct 자체는 idle thread의 palloc_free로 즉시 회수된다.

SPT kill 페이지 수 측정

(gdb) set $page_kill_count = 0
(gdb) b hash_destroy
(gdb) commands
  set $page_kill_count = $page_kill_count + 1
  c
end
(gdb) b pml4_destroy
(gdb) commands
  printf "SPT pages destroyed: %d\n", $page_kill_count
  set $page_kill_count = 0
  c
end

dirty mmap writeback 감지

(gdb) b file_write_at
(gdb) commands
  printf "file_write_at: inode=%p, offset=%d, size=%d, caller=%s\n", \
    file->inode, (int)ofs, (int)size, thread_current()->name
  c
end

→ process_exit 중 hit이 발생하면 dirty file-backed page writeback

fd 회수 관찰

(gdb) b close_open_files
(gdb) commands
  set $fd_count = 0
  set $i = 2
  while $i < 128
    if curr->fd_table[$i] != 0
      set $fd_count = $fd_count + 1
    end
    set $i = $i + 1
  end
  printf "Closing %d open files for %s\n", $fd_count, curr->name
  c
end

orphan/reparent 경로 관찰

(gdb) b reparent_or_reap_children
(gdb) commands
  printf "reparent: %s has %d children\n", curr->name, \
    (int)list_size(&curr->child_status_list)
  c
end

exit status 전달 관찰

(gdb) b finish_self_status
(gdb) commands
  printf "finish_self: %s, exit_status=%d, orphaned=%d\n", \

  c
end

관찰 시나리오: exit 후 메모리 실제 해제 확인

  1. b process_exit — 종료 시작
  2. p palloc_pool[1].used_map->bit_cnt — user pool 사용량 (before)
  3. b pml4_destroy → finish
  4. p palloc_pool[1].used_map->bit_cnt — user pool 사용량 (after)
  5. 감소량 × 4 KB = 해제된 물리 메모리
