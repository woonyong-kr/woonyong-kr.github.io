file-backed page metadata에는 무엇을 저장해야 하나

file-backed page metadata에는 무엇을 저장해야 하나

file-backed metadata 질문

PintOS VM 스켈레톤의 struct page에는 file-backed page를 위한 자리가 이미 마련되어 있다.

이 union에는 struct file_page가 들어가지만, 현재 구조체의 내부는 비어 있다.

여기서 다음 질문이 생긴다.

mmap()으로 만든 page가 첫 page fault 때 파일의 어느 바이트를 읽고, munmap() 때 어느 바이트를 다시 써야 하는지는 어디에 기억해야 할까?

page table만으로 부족한 이유

page table은 가상 주소를 실제 frame으로 빠르게 번역하기 위한 표다.

그러나 page table만으로는 다음 정보를 알 수 없다.

이 정보가 없으면 page fault를 처리하기 어렵다. 첫 접근에서 frame을 얻더라도, 커널은 그 frame에 어떤 파일 바이트를 채워야 하는지 알 수 없다. munmap()이나 eviction 때도 dirty frame을 어느 file offset으로 되돌려야 하는지 판단할 수 없다.

따라서 file-backed page에는 주소 번역 정보와 별개로 backing store 정보가 필요하다.

page와 파일 구간을 연결하는 metadata

처음에는 struct file_page를 한 VA page와 파일 구간을 연결하는 영수증처럼 생각할 수 있다.

각 정보가 필요한 이유는 다음과 같다.

의미왜 필요한가
filepage-in/write-back 대상 파일을 찾기 위해 필요
ofs이 page가 파일의 어느 위치와 연결되는지 기억
read_bytesframe 앞쪽에 실제로 읽을 파일 바이트 수
zero_bytesframe 뒤쪽에 0으로 채울 padding 수
writablepml4_set_page()와 write protection 판단에 필요

필드 이름은 구현마다 달라도 된다. 다만 이 다섯 의미는 page fault와 write-back이 일어날 때까지 유지되어야 한다.

구현 후보는 다음과 같은 형태가 될 수 있다.

파일 포인터의 소유권은 이 구조와 별도로 정해야 한다. 같은 reopened file을 여러 page가 함께 가리키면 file_close()는 한 번만 호출해야 한다. 반대로 page마다 file_reopen()을 따로 호출하면 각 page가 자기 파일 객체를 닫을 수 있지만, 열린 파일 객체가 많아진다.

두 page로 나뉘는 mapping

파일의 byte 0x1000부터 6000바이트를 주소 0x10000000에 매핑한다고 하자.

page size는 4096 = 0x1000이다. 이 mapping은 두 개의 VA page로 나뉜다.

나중에 두 번째 page가 dirty 상태라면 다음과 같이 파일로 되돌린다.

여기서 2192바이트의 zero padding은 page 안에서는 0이어야 하지만, 원본 파일에 대응되는 바이트는 아니다.

실제 운영체제와 PintOS의 차이

Linux에서 mmap()은 프로세스 주소 공간에 VMA를 만든다. VMA는 주소 범위, 권한, backing file, file offset 같은 의미를 담고 있으며, 실제 page fault 처리 과정에서 file page와 page cache를 연결한다.

Windows도 file mapping object와 mapped view를 통해 같은 종류의 문제를 푼다. user API 이름은 CreateFileMapping, MapViewOfFile이고, 커널에서는 section object와 view, modified page 처리를 포함한 더 큰 구조를 사용한다.

현실의 OS는 PintOS보다 훨씬 복잡하다.

  • 같은 파일 page를 여러 프로세스가 공유할 수 있다.
  • MAP_PRIVATE 계열에서는 copy-on-write가 들어간다.
  • page cache, truncate, 권한, write-back error, memory pressure를 함께 다룬다.
  • metadata는 단순히 page 구조체 하나에만 들어가지 않는다.

학습 단계에서는 실제 OS가 mapping 범위 단위 metadata와 page cache를 함께 사용하고, PintOS는 이 문제를 page별 metadata 중심으로 축소해 구현한다고 이해할 수 있다.

PintOS의 구현 자리

현재 저장소는 VM skeleton 상태다.

PintOS 저장소 상대 경로 pintos/include/vm/vm.h에는 struct page union 안에 struct file_page file 자리가 있다. pintos/include/vm/file.h의 struct file_page는 비어 있으며, pintos/vm/file.c에는 file-backed page용 함수 이름만 놓여 있다.

PintOS에서 예상할 수 있는 흐름은 다음과 같다.

이 흐름에서 file_reopen()은 mapping과 원래 fd의 생명주기를 분리한다. mmap-close 테스트에서는 사용자가 mmap() 직후 원래 fd를 close()하더라도 mapping을 통해 파일을 계속 읽을 수 있어야 한다. 따라서 mapping이 fd table entry가 보유하던 struct file *에 그대로 의존해서는 안 된다.

mmap-remove 테스트도 close/remove 이후 mapping을 통해 기존 파일 내용을 읽는 상황을 만든다. 이 동작을 이해하려면 fd 번호, 열린 file object, inode reference, mapping 생명주기를 구분해서 봐야 한다.

QEMU가 담당하는 범위

QEMU는 struct file_page를 알지 못한다. QEMU가 보는 것은 크게 두 가지 효과다.

첫째, guest CPU가 page fault와 page table update를 겪는다. QEMU x86 코드에는 dirty bit 자체가 있다.

  • target/i386/cpu.h
    • PG_DIRTY_BIT = 6
    • PG_DIRTY_MASK
  • target/i386/tcg/system/excp_helper.c
    • access_type == MMU_DATA_STORE이면 dirty bit set 후보에 PG_DIRTY_MASK를 포함한다.

둘째, PintOS가 파일 시스템 write-back을 수행하면 IDE sector write와 block backend write로 내려간다.

  • hw/ide/core.c
    • ide_sector_write()
    • blk_aio_pwritev(s->blk, sector_num << BDRV_SECTOR_BITS, ...)
  • include/block/block-common.h
    • BDRV_SECTOR_BITS = 9
    • BDRV_SECTOR_SIZE = 512

따라서 QEMU가 이 page가 mmap file-backed page다라는 의미를 처리하는 것은 아니다. 그 의미는 PintOS 커널의 struct page, struct file_page, SPT, 파일 시스템 코드가 만든다.

이 union은 page 종류에 따라 서로 다른 metadata를 담기 위한 자리다.

2. 현재 struct file_page는 비어 있다

파일:

  • PintOS 저장소 상대 경로 pintos/include/vm/file.h

구조체가 비어 있다는 사실만으로 file-backed page에 metadata가 필요 없다고 볼 수는 없다. 현재 skeleton에서는 구현자가 필요한 정보를 이 자리에 설계해야 한다.

3. file_backed_swap_in/out은 file_page를 사용한다

파일:

  • PintOS 저장소 상대 경로 pintos/vm/file.c

file_page가 비어 있으면 file_read_at()에 넘길 file, size, offset을 알 수 없다.

4. lazy page는 aux를 첫 fault까지 유지한다

파일:

  • PintOS 저장소 상대 경로 pintos/vm/uninit.c

첫 fault에서는 다음 순서로 호출된다.

이 구조를 사용하면 do_mmap()이 page별 metadata를 aux로 전달한 뒤 첫 fault에서 struct file_page로 옮길 수 있다. 또는 page를 만든 직후 page->file에 직접 채우는 방식으로 설계할 수도 있다.

5. VM용 load_segment()도 같은 계산을 요구한다

파일:

  • PintOS 저장소 상대 경로 pintos/userprog/process.c

현재는 aux = NULL인 TODO 상태다. 이 코드도 결국 이 page에서 파일을 몇 바이트 읽고 몇 바이트를 0으로 채울지 page fault 시점까지 전달해야 한다.

실행 파일 segment와 mmap file-backed page는 용도가 다르다. 그러나 둘 다 lazy loading 과정에서 file, offset, read bytes, zero bytes를 잃으면 안 된다는 점은 같다.

mmap에서는 이 전달 정보가 첫 fault 전에는 aux에 있다가, page가 VM_FILE로 전환된 뒤에는 struct file_page나 region metadata로 옮겨져야 한다. 이 전환 기준은 mmap file page의 aux는 언제 struct file page로 옮겨야 하나에서 별도로 본다.

6. offset 기반 파일 I/O 함수가 이미 있다

파일:

  • PintOS 저장소 상대 경로 pintos/filesys/file.c

이 함수들은 파일의 현재 위치를 바꾸지 않는다. 따라서 page별 offset이 정해진 mmap page-in/write-back에는 file_read()보다 file_read_at()이 맞다.

파일:

  • PintOS 저장소 상대 경로 pintos/tests/vm/lazy-file.c

기억해야 할 설계 기준

file-backed page metadata는 한 VA page가 어떤 파일 구간을 대표하는지 기억한다. page table에서는 frame 번역과 dirty bit를 확인할 수 있지만, 원본 파일과 file offset은 알 수 없다.

PintOS의 빈 struct file_page에는 최소한 file, ofs, read_bytes, zero_bytes, writable의 의미가 필요하다. fd를 닫은 뒤에도 mapping이 살아 있어야 하므로 file_reopen()이나 별도 mapping object를 통해 생명주기도 분리해야 한다.

마지막 page에서는 read_bytes만 원본 파일에 대응하며, zero_bytes는 page 내부 padding이다. writable은 dirty write-back 여부뿐 아니라 lazy read-only page에 첫 write가 들어왔을 때 claim을 거절하는 판단에도 필요하다.

QEMU는 이 metadata를 해석하지 않는다. guest의 page fault와 dirty bit, IDE sector write 같은 하드웨어 효과만 재현한다.
