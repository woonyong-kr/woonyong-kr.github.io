fork에서 swapped-out anonymous page는 어떻게 복사해야 하나

fork에서 swapped-out anonymous page는 어떻게 복사해야 하나

swapped anon fork 쟁점

fork 때 SPT는 왜 같이 복사해야 하나는 fork()가 부모의 SPT를 자식에게 복사해야 한다고 설명한다.

그 다음에 바로 생기는 질문이 있다.

부모의 anonymous page가 이미 RAM에서 쫓겨나 swap slot에만 있다면, 자식 SPT에는 그 slot 번호를 그대로 복사해도 될까?

아직 swap으로 내려가지 않은 lazy UNINIT page의 aux 복제 문제는 fork에서 lazy UNINIT page의 aux는 어떻게 복사해야 하나에서 따로 본다.

짧은 답은 이렇다.

swapped anon fork 필요성

anonymous page는 원본 파일이 없다. stack, heap, 전역 writable 배열처럼 실행 중에 만들어진 바이트는 RAM에서 밀려날 때 swap disk에 저장된다.

부모가 fork()하기 직전에 이런 상태라고 하자.

이 page는 page table에는 없지만 불법 주소가 아니다. 나중에 부모가 다시 0x8049000을 읽으면 page fault가 나고, PintOS는 SPT에서 page P를 찾아 slot 3에서 4096B를 읽어 올 수 있다.

문제는 fork()다.

자식에게도 fork 순간의 같은 bytes가 보여야 한다. 하지만 다음처럼 slot 번호만 복사하면 ownership이 꼬인다.

이 상태에서 부모가 먼저 swap-in하며 slot 3을 free하면, 자식의 metadata는 아직 slot 3을 가리키지만 slot allocator는 그 slot을 비었다고 생각할 수 있다. 다른 page가 slot 3을 재사용하면 자식은 부모의 fork 순간 bytes가 아니라 다른 page의 bytes를 읽게 된다.

이 말은 즉, fork()에서 swapped-out page를 복사한다는 말은 단순히 숫자 하나를 복사한다는 뜻이 아니다. 그 slot의 bytes를 누가 소유하고, 언제 해제하고, 자식이 어떤 snapshot을 읽어야 하는지까지 정해야 한다.

swapped anon fork 구조

swapped-out anonymous page의 fork()는 세 가지를 분리해서 봐야 한다.

대상질문잘못 복사하면 생기는 문제
SPT entry자식도 같은 VA를 합법 page로 보나?child fault가 SPT miss로 죽는다
page bytesfork 순간의 4096B snapshot을 자식이 얻나?child가 부모와 다른 값을 읽는다
swap slot ownershipslot을 누가 free하고 재사용하나?double free, leak, stale data read가 생긴다

따라서 안전한 모델은 둘 중 하나다. 이 중 child 전용 snapshot을 만드는 구현 흐름은 swapped anonymous page fork snapshot 흐름에서 Trace로 따로 따라간다.

전략의미장점주의점
독립 복사부모 slot의 4096B를 자식 전용 frame 또는 자식 전용 slot으로 복사구현 판단이 단순하다fork() 비용이 커질 수 있다
참조 카운트 공유부모와 자식이 같은 slot bytes를 공유하되 slot refcount를 둔다swap-in 전까지 복사를 미룰 수 있다slot free 조건, write 후 분리, destroy 경계가 복잡하다

학습용 PintOS에서 먼저 구현하기 쉬운 쪽은 보통 독립 복사다. COW나 slot refcount를 설계하지 않았다면, “slot 번호만 복사하고 각 page가 독립 소유한다고 믿는 설계”는 피해야 한다.

VA page = 0x8049000

부모가 20 MiB anonymous 배열을 sparse하게 썼고, frame이 부족해져 page 하나가 swap으로 내려갔다고 하자.

fork 직후 자식이 같은 주소를 읽으면 기대값은 fork 순간의 부모 bytes다.

하지만 slot 번호만 공유하면 다음 순서가 가능하다.

이 실패는 page table만 봐서는 잘 안 보인다. parent와 child 모두 not-present fault를 겪고, 둘 다 어떤 slot에서 sector read를 한다. 깨지는 것은 “slot 3이 누구의 snapshot인가”라는 PintOS metadata의 의미다.

실제 운영체제

Linux의 fork()는 일반적으로 private anonymous page를 copy-on-write로 다룬다. resident page라면 부모와 자식이 같은 physical page를 read-only로 공유하고, 한쪽이 write할 때 fault를 이용해 새 page를 만든다.

swapped-out page도 단순히 “디스크 위치 숫자만 복사하고 서로 독립 소유”로 끝나지 않는다. 실제 커널은 swap entry, page table entry, reverse mapping, page refcount, swap count 같은 metadata로 공유와 해제를 추적한다. 핵심은 backing bytes가 여러 주소 공간의 snapshot 역할을 할 수 있으면 그 수명을 참조로 관리해야 한다는 점이다.

Windows는 Unix식 fork()를 일반 API로 제공하지 않는다. CreateProcess는 새 주소 공간을 만들고 image section, pagefile-backed section, copy-on-write view 같은 다른 모델을 쓴다. 그래서 “fork의 swapped page 복사”라는 표현은 Linux/POSIX 쪽에 가깝다.

그래도 공통 판단 기준은 같다.

PintOS

현재 W09 PintOS VM 코드는 스켈레톤이다. TODO를 채울 때 놓치기 쉬운 설계 질문을 정리한다.

__do_fork()는 VM 빌드에서 supplemental_page_table_copy()를 호출한다.

supplemental_page_table_copy()가 swapped-out anonymous page를 만났을 때 선택지는 대략 셋이다.

선택지동작판단
slot 번호만 복사child anon.slot = parent.anon.slotrefcount 없으면 위험
slot bytes를 새 slot으로 복사parent slot 3을 읽어 child slot 7에 씀안전하지만 I/O 비용 있음
parent를 swap-in한 뒤 frame 복사parent bytes를 frame으로 복원하고 child frame 또는 COW로 연결구현은 단순할 수 있으나 memory pressure와 eviction 재진입을 조심해야 함

초기 구현에서는 다음 불변식을 목표로 잡는 것이 좋다.

tests/vm/swap-fork.c도 함께 읽어야 한다. 이 테스트는 이름 때문에 “부모의 swapped page를 자식이 직접 읽는 테스트”처럼 보일 수 있지만, 실제 child는 fork() 직후 곧바로 exec("child-swap")한다.

따라서 이 테스트가 주로 확인하는 것은 다음이다.

  • fork/exec 경계에서 옛 SPT와 새 SPT가 섞이지 않는가
  • 10개 child가 각자 1 MiB anonymous array를 쓰고 읽을 때 swap metadata가 독립인가
  • child exit 때 각 child의 swapped-out anonymous page가 정리되는가

부모의 swapped-out page snapshot을 자식이 exec 없이 직접 읽는 최소 질문은 이 문서처럼 별도로 떼어 보는 편이 정확하다.

QEMU

QEMU는 PintOS의 SPT나 struct anon_page를 모른다.

QEMU가 보는 것은 두 가지다.

QEMU는 “slot 3이 parent와 child에게 공유 중인지”, “이 slot을 free해도 되는지”를 판단하지 않는다. 그 판단은 PintOS의 slot bitmap, refcount, page metadata가 해야 한다.

swapped anon fork 코드

1. VM fork 경로는 SPT copy로 들어간다

파일:

  • PintOS 저장소 상대 경로 pintos/userprog/process.c

확인한 위치:

  • __do_fork()에서 VM 빌드는 supplemental_page_table_init(&curr->spt) 뒤 supplemental_page_table_copy(&curr->spt, &parent->spt)를 호출한다.
  • 같은 함수에서 자식의 syscall 반환값은 if_.R.rax = 0으로 바뀐다.

2. SPT copy와 anon page metadata는 아직

파일:

  • PintOS 저장소 상대 경로 pintos/vm/vm.c
  • PintOS 저장소 상대 경로 pintos/include/vm/anon.h
  • PintOS 저장소 상대 경로 pintos/vm/anon.c

확인한 위치:

  • supplemental_page_table_copy()는 스켈레톤 함수다.
  • struct anon_page는 비어 있다.
  • anon_swap_in(), anon_swap_out(), anon_destroy()도 TODO 자리다.

이 말은 즉, slot 번호, in-swap 상태, refcount 또는 ownership 정책은 구현자가 직접 넣어야 한다.

3. swap-fork는 direct inheritance

파일:

  • PintOS 저장소 상대 경로 pintos/tests/vm/swap-fork.c
  • PintOS 저장소 상대 경로 pintos/tests/vm/child-swap.c
  • PintOS 저장소 상대 경로 pintos/tests/vm/Make.tests

확인한 위치:

  • swap-fork.c는 child 10개를 만들고, child branch에서 바로 exec("child-swap")한다.
  • child-swap.c는 각 child가 자기 전역 배열 big_chunks 1 MiB를 page 단위로 쓰고 다시 읽는다.
  • Make.tests는 swap-fork에 SWAP_DISK = 200, MEMORY = 40, TIMEOUT = 600을 준다.

따라서 swap-fork는 child별 swap 격리에는 좋지만, 부모의 swapped-out page를 child가 exec 없이 읽는 최소 관찰과는 다르다.

4. QEMU는 pf와 sector I/O만 만든다

파일:

  • target/i386/tcg/system/excp_helper.c
  • hw/ide/core.c
  • block/block-backend.c

확인한 위치:

  • 주소 번역 실패는 EXCP0E_PAGE, error_code, cr2로 정리된다.
  • x86_cpu_tlb_fill()은 fault address를 env->cr[2]에 저장하고 예외를 올린다.
  • IDE DMA 경로는 offset = sector_num << BDRV_SECTOR_BITS로 sector를 block backend byte offset으로 바꾼다.
  • block backend는 blk_aio_preadv()와 blk_aio_pwritev()로 offset 기반 I/O를 실행한다.

QEMU 쪽에는 “parent slot”, “child slot”, “SPT copy”라는 정책 이름이 없다.

swapped anon fork 값 추적

slot 3을 예로 들자.

slot 3이 담는 byte 범위는 다음과 같다.

page byte rangedisk sectorQEMU block offset
0..5112424 << 9 = 0x3000
512..10232525 << 9 = 0x3200

3584..40953131 << 9 = 0x3e00

slot 번호만 복사했을 때 깨지는 지점은 이 byte 범위다.

page table과 CR2/error code는 이 상황을 “not-present page fault”로만 보여 준다. 실제로 잘못된 것은 disk sector 자체가 아니라, PintOS가 sector 24..31의 소유자를 잘못 기억한 것이다.

정리

  • VM 이후 fork()는 resident frame뿐 아니라 not-present page의 의미도 복사해야 한다.
  • swapped-out anonymous page는 특히 slot ownership이 중요하다.
  • refcount 없이 slot 번호만 복사하면 parent와 child가 서로 독립적으로 free한다고 믿는 순간 깨진다.
  • swap-fork는 fork/exec와 child별 swap 격리를 확인하지만, 부모의 swapped page 직접 상속 최소 실험은 아니다.
  • QEMU는 pf와 sector I/O를 재현할 뿐이고, slot 소유권은 PintOS VM metadata가 책임진다.

순서도

slot 번호만 복사했을 때 깨지는 시나리오

sequenceDiagram
    participant P as Parent
    participant Slot as Swap Slot 3
    participant C as Child
    participant Other as Other Page D

    Note over P,C: fork 시점
    P->>P: page P → slot 3 (swapped-out)
    P->>C: fork: child page C도 slot 3 가리킴

    Note over P,Slot: parent가 먼저 swap-in
    P->>Slot: anon_swap_in(slot 3) → 4096B 읽기
    P->>Slot: bitmap_reset(slot 3) → slot free

    Note over Other,Slot: 다른 page가 slot 3 재사용
    Other->>Slot: anon_swap_out → slot 3에 다른 bytes 쓰기

    Note over C,Slot: child가 뒤늦게 swap-in
    C->>Slot: anon_swap_in(slot 3) → page D의 bytes 읽음!
    Note over C: child는 fork snapshot이 아닌<br/>page D의 데이터를 보게 됨
