QEMU는 OS가 아니다

QEMU는 OS가 아니다

확인 범위: 이 문서는 QEMU가 재현하는 하드웨어 계층과 PintOS가 담당하는 OS 정책의 책임 경계를 설명하고, 디버깅 시 원인 계층을 구분하는 일반적인 판단 기준과 예시를 제시한다. 특정 QEMU·PintOS 버전의 실제 소스 상태, 코드 좌표, GDB 실행 결과, 오류 빈도와 TCG·KVM 성능 수치는 이 본문만으로 검증된 결과가 아니므로 해당 버전의 코드와 실행·측정 기록을 별도로 확인해야 한다.

한 줄 요약: QEMU는 하드웨어 에뮬레이터일 뿐 프로세스·파일 이름을 관리하지 않는 OS가 아니라는 구분.

QEMU는 OS가 아니다 상태

QEMU는 하드웨어 에뮬레이터이지 운영체제가 아니다. CPU가 명령어를 실행하고, 메모리 컨트롤러가 주소를 변환하고, 디스크 컨트롤러가 sector를 읽는 것처럼 동작하지만, 프로세스를 관리하거나 파일 이름을 해석하거나 syscall 번호의 의미를 아는 것은 OS의 일이다. PintOS 디버깅에서 “이 버그가 QEMU 문제인가, OS 문제인가”를 판단하려면 이 경계를 확실히 알아야 한다.

상세 설명

추상 개념 (하드웨어 vs OS의 책임 경계)

컴퓨터 시스템의 계층을 세 겹으로 나눌 수 있다:

계층역할예시
하드웨어전기 신호로 비트 조작CPU ALU, MMU, PIC, PIT, IDE 컨트롤러
OS하드웨어 위에서 추상화·정책 제공프로세스, 파일, 가상 메모리, 스케줄링
사용자 프로그램OS API를 통해 자원 사용shell, cat, echo

QEMU가 재현하는 것은 첫 번째 계층뿐이다. QEMU는 x86-64 CPU, 8259A PIC, 8254 PIT, IDE 디스크 컨트롤러를 소프트웨어로 모사한다. 그 위에서 돌아가는 OS 코드(PintOS)가 두 번째 계층을 구성한다.

핵심 구분:

%% QEMU와 PintOS의 책임 경계
flowchart LR
  qemu["하드웨어 (QEMU가 재현)<br/>명령어 실행<br/>주소 변환 (PML4 walk)<br/>인터럽트 전달<br/>sector I/O"]
  pintos["OS (PintOS가 구현)<br/>프로세스 생성·종료<br/>페이지 테이블 구축·관리<br/>인터럽트 핸들러 로직<br/>파일 시스템 정책"]
  qemu -->|전기적 효과와 바이트 상태 위에 OS 정책을 올림| pintos

QEMU가 모르는 OS 개념 5가지

1. 프로세스 (Process)

QEMU에게 struct thread는 guest 메모리의 바이트 덩어리일 뿐이다. PintOS가 palloc_get_page()로 페이지를 할당하고 그 안에 thread 구조체를 초기화해도, QEMU 입장에서는 “게스트가 물리 주소 X에 바이트를 썼다”만 인식한다.

PintOS 관점: tid=3인 프로세스가 생성되었다
QEMU 관점:  물리 주소 0x8004e000에 0x03 0x00 0x00 0x00이 쓰여졌다

QEMU의 CPUX86State에는 tid, pid, ppid 같은 필드가 전혀 없다. 레지스터 값과 플래그만 있다.

2. 스케줄링 (Scheduling)

QEMU는 PIT가 매 1193182 / 100 ≈ 11932 클럭마다 IRQ0을 발생시키는 것까지만 책임진다. 그 인터럽트를 받아서 thread_tick()을 호출하고, TIME_SLICE(=4 tick) 이상이면 intr_yield_on_return을 설정하고, schedule()에서 ready_list의 다음 스레드를 고르는 것은 전부 PintOS 코드의 일이다.

3. 가상 메모리 정책

QEMU는 CR3가 가리키는 PML4 테이블로 4단계 page table walk를 하고, PTE가 없으면 pf를 발생시킨다. 여기까지가 QEMU의 역할이다. pf 핸들러에서 lazy loading으로 물리 프레임을 할당할지, swap에서 복원할지, stack growth를 허용할지는 PintOS의 vm_try_handle_fault()가 결정한다.

4. 파일 이름

QEMU의 IDE 모델은 “sector 42를 읽어라”는 요청을 처리할 뿐, sector 42에 “hello.txt”라는 이름의 파일 데이터가 들어 있는지는 모른다. 파일 이름 → inode 번호 → sector 위치 매핑은 PintOS의 dir_lookup() → inode_open() → byte_to_sector()가 한다.

5. Syscall 의미

QEMU는 SYSCALL 명령어 실행 시 CPL 전환, LSTAR MSR → RIP 설정만 한다. RAX에 10이 들어 있을 때 그것이 SYS_WRITE인지 SYS_READ인지는 PintOS의 syscall_handler()가 switch (f->R.rax) 문으로 판단한다.

실제 OS (Linux/Windows)

실제 하드웨어에서도 동일한 경계가 존재한다:

OS 개념하드웨어가 하는 일Linux 커널이 하는 일
프로세스없음 (레지스터 상태만)task_struct 관리, fork(), schedule()
파일블록 장치: LBA sector I/OVFS → ext4/btrfs → block layer
가상 메모리MMU page walk, TLBmm_struct, vm_area_struct, page fault handler
syscallSYSCALL 명령어: CPL 전환sys_call_table[__NR_xxx] 디스패치

KVM 가상화에서도 마찬가지다. KVM은 하드웨어 가속으로 guest CPU를 실행하지만, guest의 프로세스 목록이나 파일 시스템은 전혀 관여하지 않는다.

TCG vs KVM: 에뮬레이션 방식의 차이

QEMU는 두 가지 실행 방식을 지원하며, 어느 쪽이든 OS 개념은 모른다:

항목TCG (Tiny Code Generator)KVM (Kernel-based VM)
실행 방식guest 명령어 → TCG IR → 호스트 명령어 (JIT 번역)guest 명령어를 호스트 CPU에서 직접 실행 (VT-x/AMD-V)
성능느림 (5~20x 오버헤드)빠름 (near-native)
I/O 처리번역 중 I/O 명령 감지 → helper 함수 호출VM Exit → QEMU 유저 공간에서 장치 에뮬레이션
PintOS 사용기본 (cross-architecture 가능)-enable-kvm 옵션 시 (같은 아키텍처만)
디버깅GDB stub 내장, breakpoint 쉬움GDB stub 사용 가능하나 하드웨어 breakpoint 필요
OS 개념 인식없음 — IR에 process/fd/file 없음없음 — VMCS에 process/fd/file 없음

TCG 번역 예시 (guest → host):

%% TCG 번역에서 사라지는 OS 의미
flowchart TD
  guest["Guest 명령어<br/>mov eax"]
  ir["TCG IR<br/>ld_i64 tmp0"]
  host["Host 명령어<br/>mov rax"]
  guest -->|guest 명령어 번역| ir
  ir -->|호스트 명령어 생성| host

TCG에게 rdi+0x10이 struct thread의 tid 필드인지, 배열의 세 번째 원소인지는 구별 불가능하다.

PintOS 디버깅에서의 실전 적용

버그를 만났을 때 “QEMU 문제인가, OS 문제인가”를 판단하는 체크리스트:

증상QEMU 문제 가능성확인 방법
page fault 발생거의 없음CR2 확인 → PTE 확인 → OS handler 로직 추적
syscall 반환값 이상없음syscall_handler() 분기와 내부 함수 확인
스케줄링 안 됨거의 없음ready_list 상태, thread_tick() 확인
디스크 데이터 깨짐드물게 가능sector 번호 계산 → IDE 모델이 올바른 offset 접근하는지 확인
타이머 동작 이상드물게 가능PIT 주파수 확인 → timer_interrupt() 핸들러 확인

99%의 PintOS 버그는 OS 레벨이다. QEMU의 하드웨어 에뮬레이션은 수천 명이 사용한 검증된 코드이므로, “QEMU 버그일 것이다”라는 가정은 거의 항상 틀리다.

QEMU 에뮬레이션

QEMU 소스 코드에서 OS 개념의 부재를 확인할 수 있다:

  • CPUX86State 구조체에 tid, process, file_table 같은 필드 없음
  • hw/ide/core.c에 파일 이름 파싱 코드 없음 — sector 번호만 처리
  • target/i386/ 전체에 SYS_WRITE, SYS_READ 상수 정의 없음
  • QEMU 프로세스 하나가 guest CPU 하나를 표현 — guest 안의 “프로세스 N개”는 QEMU가 모르는 개념
