E820 메모리 맵에서 palloc Pool까지의 Trace

E820 메모리 맵에서 palloc Pool까지의 Trace

한 줄 요약: QEMU의 e820 메모리 맵에서 PintOS palloc pool이 만들어지기까지의 추적.

E820 메모리 맵 쟁점

QEMU에서 PintOS를 실행할 때 e820 memory map이 나온다.

그렇다면 이 map은 “QEMU가 만든 20MB짜리 RAM 공간” 자체일까? 그리고 PintOS는 그중 코드, data, BSS, boot 영역을 제외한 나머지를 kernel_pool과 user_pool로 나누어 bitmap으로 관리하는 걸까?

짧은 답은 이렇다.

E820 palloc pool 혼동

운영체제는 부팅 직후부터 “어느 물리 page를 써도 되는가”를 알아야 한다.

하지만 낮은 주소에는 BIOS 자료, boot loader, multiboot 정보, 커널 이미지, page table, 장치 예약 영역 같은 것들이 섞여 있다. 그래서 OS가 그냥 0x0부터 끝까지 마음대로 쓰면 부팅에 필요한 자료를 덮어쓸 수 있다.

이 문제를 풀기 위해 부트 단계에서는 다음 순서가 필요하다.

  1. BIOS/QEMU가 어떤 guest physical memory 구간이 usable인지 알려준다.
  2. loader가 그 정보를 multiboot 형식의 e820 map으로 저장한다.
  3. PintOS palloc_init()이 map을 읽는다.
  4. 이미 사용 중인 커널 영역과 bitmap 영역을 제외한다.
  5. 남은 page를 kernel_pool과 user_pool로 나눈다.

이 말은 즉, palloc은 “RAM 전체를 새로 만드는 코드”가 아니라 “이미 존재한다고 보고된 guest RAM page를 빌려주고 회수하는 장부”다.

E820 palloc pool 구조

PintOS가 보는 메모리 층을 먼저 분리한다.

주의할 점은 “BBS”가 아니라 “BSS”다. BSS는 초기값이 0인 전역/static 변수가 놓이는 영역이다.

20MB인가

“20MB인가?”는 실행 방식에 따라 다르다.

상황메모리 크기 기준
PintOS 테스트 harnesspintos/tests/Make.tests의 MEMORY = 20
직접 pintos 실행pintos/utils/pintos의 기본 --memory 256
직접 overridepintos -m 20 ...처럼 지정한 값

QEMU에 -m 20이 들어가면 PintOS 입장에서는 대략 20MiB guest RAM이 있는 것처럼 보인다. 하지만 그 20MiB 전체가 곧바로 palloc free page가 되는 것은 아니다.

이 중 일부는 다음 이유로 빠진다.

  • BIOS/loader/multiboot 정보가 낮은 주소를 사용한다.
  • 커널 이미지가 0x200000부터 올라간다.
  • 커널의 .text, .rodata, .data, .bss가 이미 메모리를 차지한다.
  • palloc bitmap 자체도 RAM 안에 저장해야 한다.
  • e820 map에서 reserved로 표시된 영역은 allocator가 free로 풀면 안 된다.

PintOS 코드 흐름

1. QEMU memory 크기

테스트에서는 MEMORY = 20이 기본이다.

직접 실행 wrapper의 기본값은 256이다.

그래서 “PintOS는 항상 20MB로 돈다”라고 말하면 반만 맞다. 과제 테스트에서는 보통 20MB지만, wrapper 기본값이나 직접 -m 옵션에 따라 바뀐다.

2. loader가 e820 map을 받는다

PintOS loader는 BIOS interrupt int 0x15의 e820 기능을 호출한다.

이 결과가 MULTIBOOT_INFO 근처에 저장된다.

여기서 중요한 구분은 이렇다.

3. 커널은 2MB부터 올라간다

현재 PintOS 코드에서 커널 시작 물리 주소는 0x200000이다.

링커 스크립트는 커널 섹션을 다음 순서로 배치한다.

그래서 그림에서 kernel data, kernel BSS 위에 바로 pool이 시작된다고 생각하면 조금 부족하다. 실제로는 _end 다음에 palloc bitmap 공간이 먼저 들어간다.

4. palloc_init()이 e820을 읽는다

초기화 순서는 init.c:main()에서 볼 수 있다.

palloc_init()은 두 일을 한다.

5. 전체 page 수를 반으로 나눈다

populate_pools()의 첫 계산은 다음이다.

기본 정책은 단순하다.

다만 -ul 옵션으로 user_page_limit을 제한하면 user pool page 수가 더 작아질 수 있다.

6. bitmap은 pool의 “장부”다

각 pool은 다음 세 필드로 관리된다.

init_pool()은 bitmap을 만들고 처음에는 모든 bit를 true로 둔다.

여기서 true는 “사용 중이거나 사용 불가능”이라는 뜻이다. 아직 e820 usable 구간을 검증하기 전이므로 전부 막아 둔다.

그 다음 다시 e820 entry를 순회하면서 실제로 free로 풀 수 있는 page만 false로 바꾼다.

즉 bitmap의 의미는 다음이다.

bit 값의미
true사용 중 또는 사용 불가능
falsepalloc이 줄 수 있는 free page

7. _end 이전은 free로 풀지 않는다

핵심 경계는 이 줄이다.

그리고 bitmap 공간을 만들 때마다 free_start는 앞으로 이동한다.

이후 usable_bound보다 낮은 page는 free로 풀지 않는다.

이 말은 즉, 커널 code/data/BSS뿐 아니라 palloc bitmap 자체도 allocator가 다시 나눠주면 안 되는 영역이다.

palloc_get_page()로 이어지는 순간

초기화가 끝나면 page 할당은 단순한 bitmap 검색이 된다.

PAL_USER가 있으면 user_pool, 없으면 kernel_pool을 고른다.

반환값은 user virtual address가 아니다. PintOS 커널이 같은 frame을 만질 수 있는 kernel virtual address다. 이 구분은 palloc user frame과 주소 별칭과 연결된다.

실제 운영체제

Linux나 Windows도 부팅 중 firmware가 제공한 메모리 배치 정보를 읽고, usable physical frame을 관리한다. 하지만 실제 OS는 PintOS보다 훨씬 더 많은 상태를 둔다.

Linux의 경우:

  1. 부팅 초기에 BIOS e820 또는 UEFI memory map을 e820_table에 저장한다.
  2. memblock 단계에서 usable 영역을 등록하고, 커널/initrd가 점유한 영역을 reserve한다.
  3. buddy allocator가 초기화되면 free page를 zone별(DMA, DMA32, Normal, HighMem)로 나눠 관리한다.
  4. 각 physical page마다 struct page 디스크립터가 있어서 참조 카운트, LRU 위치, mapping 정보를 추적한다.
  5. NUMA 시스템에서는 node별로 zone이 따로 있고, page allocator가 가까운 node에서 먼저 할당한다.

Windows의 경우:

HAL이 firmware memory map을 읽고, PFN(Page Frame Number) database에 모든 physical page 상태를 기록한다. 상태는 Free, Zeroed, Standby, Modified, Active 등으로 나뉜다.

주제LinuxWindowsPintOS
메모리 발견e820 / UEFIHAL firmware queryloader.S → e820 → multiboot
자료구조struct page + buddy + zonePFN database + listsbitmap × 2 pools
할당 단위2^order pages (buddy)single page (PFN)bitmap scan (연속 bit)
영역 분리DMA/Normal/HighMem zone없음 (PFN 범위로 구분)kernel_pool / user_pool
page 회수kswapd, reclaim, compactionworking set trimmerVM 과제의 eviction
NUMAnode별 zonenode별 memory없음 (단일 node)

따라서 PintOS의 palloc은 실제 OS 물리 page allocator의 축소판으로 보면 된다. 핵심 개념(firmware에서 usable 영역 발견 → 커널이 점유한 영역 제외 → 나머지를 pool로 관리)은 같고, buddy/zone/NUMA 같은 복잡성이 빠져 있다.

QEMU

QEMU는 host OS 위의 프로세스다. QEMU가 -m 20으로 guest RAM을 만들면, PintOS가 보는 physical address는 host physical address가 아니라 guest physical memory다.

정리하면 층은 이렇게 된다.

e820 map도 이 guest 세계의 보고서다. PintOS는 그 보고서를 믿고 palloc 장부를 만든다. QEMU는 PintOS의 kernel_pool과 user_pool 의미를 알지 못한다.

확인 후보

나중에 코드 리뷰나 Lab으로 내릴 만한 지점이다.

  • populate_pools()의 ASSERT (rem == size)는 rem이 page count이고 size가 byte count로 보이므로 의미를 다시 확인할 후보로 남긴다.
  • 0x1000 ~ 0x200000 구간 TODO는 낮은 메모리와 커널 시작 전 영역을 palloc 장부에 어떻게 반영할지 확인할 지점이다.
  • 실제 boot log의 e820 출력과 kernel_pool.base, user_pool.base, _end, free_start를 GDB로 맞춰 보면 이 trace를 Lab으로 승격할 수 있다.

    • page table, frame, fault, swap으로 이어지는 상위 문서
