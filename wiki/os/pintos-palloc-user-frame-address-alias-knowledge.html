PintOS palloc과 User Frame 주소 별칭

PintOS palloc과 User Frame 주소 별칭

한 줄 요약: palloc_get_page(PAL_USER)는 user pool에서 프레임을 선택하지만 kernel virtual address(KVA)를 반환한다. 커널의 KVA와 유저의 VA는 같은 물리 프레임을 가리키는 별칭이며, page table에는 KVA가 아니라 vtop()으로 변환한 guest physical address가 들어간다.

먼저 구분할 주소와 질문

  • palloc 주소 별칭
    • 확인할 질문
      • palloc_get_page(PAL_USER)가 반환하는 값은 user virtual address인가?
      • user page table이 kernel virtual address를 가리키면 “가상의 가상 주소”가 되는가?
    • 주소별 역할
      • user virtual address: 유저 프로그램이 사용하는 주소
      • kernel virtual address: 커널 C 코드가 프레임을 읽고 쓰는 주소
      • guest physical address: PintOS page table entry에 기록되는 프레임 주소
      • host memory: QEMU 프로세스와 host OS가 실제로 backing하는 메모리
    • PintOS 코드의 큰 흐름
      • kernel_pool / user_pool: 물리 프레임 자원을 나누어 관리하는 풀
      • palloc_get_page(PAL_USER): user pool에서 프레임을 고르고 kernel virtual address를 반환
      • vtop(kpage): kernel virtual address를 guest physical frame address로 변환
      • pml4_set_page(t->pml4, upage, kpage, writable): user VA page를 해당 프레임에 연결
    • 두 가상 주소가 필요한 이유
      • 커널은 프레임을 초기화하고 데이터를 복사해야 한다.
      • 유저 프로세스는 자신의 주소 공간과 권한을 통해 같은 프레임에 접근해야 한다.
      • page table에는 kernel VA가 아니라 guest physical frame address가 들어간다.
    • 이어서 볼 문서
      • x86 64 page table walk
        • PML4에서 PTE까지 걷는 과정을 다룬다.
      • pml4 get page() Lab
        • user VA를 kernel VA로 되돌려 확인하는 실험을 다룬다.
      • guest physical memory
        • PintOS physical address와 QEMU host memory를 구분한다.

palloc frame 별칭의 핵심

palloc_get_page(PAL_USER)로 받은 값이 kernel virtual address라면, 겉보기에는 user virtual address가 kernel virtual address에 매핑되는 것처럼 보일 수 있다.

하지만 이는 “가상 주소가 다른 가상 주소를 한 번 더 가리키는 구조”가 아니다.

같은 프레임에 두 개의 가상 주소 별칭이 생기는 것은 맞다. 다만 user VA가 kernel VA를 거쳐 가는 것은 아니다. 두 주소는 각각 한 번의 MMU 번역을 거쳐 같은 프레임에 도착한다.

커널 주소와 유저 주소를 나누는 이유

유저 프로그램을 실행하려면 커널은 서로 다른 두 작업을 수행해야 한다.

첫째, 디스크에서 읽은 ELF segment의 byte를 실제 프레임에 채워야 한다. 이때 file_read_at(file, kpage, ...), memset(kpage, ...), memcpy(kpage, ...)처럼 커널 C 코드가 접근할 수 있는 주소가 필요하다.

둘째, 유저 프로그램은 그 byte를 자신의 주소 공간에서 보아야 한다. 예를 들어 프로그램은 코드가 0x401000, 스택이 0x4747f000 같은 user virtual address에 있다고 인식한다.

이 두 요구를 한 종류의 주소로 처리하면 커널과 프로세스의 주소 공간 및 권한 경계가 섞인다.

요구필요한 주소이유
커널이 프레임을 채움kernel virtual address커널 C 코드가 직접 읽고 쓸 수 있어야 한다
유저가 프로그램을 실행user virtual address프로세스마다 같은 숫자의 주소를 서로 다른 프레임에 연결할 수 있어야 한다
CPU/MMU가 최종 번역guest physical addresspage table entry에 프레임 번호와 permission bit를 기록해야 한다

따라서 PAL_USER는 “user virtual address를 반환하라”는 뜻이 아니다. 정확히는 “유저 프로세스의 data page로 사용할 프레임을 user pool에서 가져오라”는 뜻이다.

한 프레임을 보는 세 주소

머릿속에서는 “같은 프레임을 서로 다른 관점에서 본다”고 이해하면 된다.

  • upage: 유저 프로그램이 사용할 page base
  • kpage: 커널이 같은 프레임을 채울 때 사용하는 kernel virtual address
  • vtop(kpage): PTE에 기록할 guest physical frame base
  • PTE_U: 유저 모드 접근 허용 여부
  • PTE_W: 쓰기 가능 여부
  • PTE_P: 현재 RAM에 올라온 present page인지 여부

실제 운영체제와 비교

Linux와 Windows 같은 실제 OS에서도 user VA와 kernel VA가 같은 physical frame을 가리키는 구조는 일반적이다.

Linux에서는 물리 page를 struct page 같은 metadata로 추적한다. 커널이 해당 page에 접근할 때는 direct map, kmap 계열 mapping, copy_to_user() / copy_from_user() 같은 통제된 경로를 사용한다. 세부 구현은 CPU architecture, config, memory type에 따라 다르지만, 유저 포인터를 그대로 신뢰하지 않고 커널이 관리하는 mapping을 통해 접근한다는 원칙은 같다.

Windows에서도 user virtual address와 kernel address space는 분리된다. 커널은 physical page, section object, MDL, system mapping 같은 장치를 이용해 user buffer나 file-backed memory를 다룬다. API는 PintOS와 다르지만, 프로세스가 보는 주소와 커널이 page/frame을 관리하는 주소를 분리한다는 방향은 같다.

따라서 하나의 physical page에 여러 virtual mapping이 생기는 현상은 특별한 예외가 아니다. shared memory, file mapping, copy-on-write, kernel direct map도 이 원리를 활용한다.

QEMU에서 한 층 더 구분하기

QEMU 위에서 PintOS를 실행하면 guest와 host 사이의 메모리 변환 계층이 하나 더 생긴다.

PintOS 관점에서는 vtop(kpage) 결과를 physical address라고 불러도 된다. 그러나 QEMU 전체 관점에서 보면 이는 host physical address가 아니라 guest physical address다.

QEMU의 x86 page walk는 guest page table을 읽어 최종 guest physical address를 계산한다.

파일:

  • target/i386/tcg/system/excp_helper.c
  • target/i386/tcg/system/excp_helper.c

핵심 계산:

이 paddr가 PintOS 관점의 physical address, 즉 guest physical address다.

이후 QEMU memory layer는 guest physical address가 RAM인지 MMIO 장치인지 구분한다. RAM이라면 RAMBlock의 host pointer 쪽으로 연결되며, 이 계층은 Guest Physical Memory에서 더 자세히 다룬다.

핵심 코드로 다시 확인하기

1. pool 선택은 PAL_USER가 결정한다

파일:

  • palloc.c

PAL_USER는 user virtual address를 만든다는 뜻이 아니라 user pool을 선택한다는 뜻이다.

2. 반환값은 pool base에서 계산된다

파일:

  • palloc.c

pool base가 ptov(...)로 만든 kernel virtual address 영역에 있으므로 pages도 kernel virtual address다.

3. PTE에는 vtop(kpage)가 들어간다

파일:

  • mmu.c

이 코드가 핵심 결론을 보여 준다. user page table은 user VA를 kernel VA에 연결하지 않고, vtop(kpage)로 얻은 guest physical frame에 연결한다.

4. user VA에서 kernel VA를 다시 확인할 수도 있다

파일:

  • mmu.c

pml4_get_page()는 PTE에 있던 guest physical frame address를 ptov()로 다시 kernel virtual address로 바꾸어 반환한다. 이 덕분에 syscall buffer 검사나 fork copy 과정에서 커널이 user memory의 실제 byte에 접근할 수 있다.

예시 값으로 주소 추적하기

다음 값을 기준으로 변환을 직접 따라가 보자.

1. kpage를 guest physical frame으로 변환한다

2. PTE를 만든다

3. user access는 user VA에서 guest PA로 간다

4. kernel access도 같은 guest PA로 간다

따라서 두 접근은 같은 byte에 도착한다.

이 과정에서 MMU 번역이 연달아 두 번 일어나는 것은 아니다. user access는 user VA를 한 번 번역하고, kernel access는 kernel VA를 한 번 번역한다. 두 번역의 목적지가 같은 프레임일 뿐이다.

정리

  • palloc_get_page(PAL_USER)는 user virtual address를 반환하지 않는다.
  • PAL_USER는 user pool에서 프레임을 가져오도록 지정하는 flag다.
  • 반환값 kpage는 PintOS kernel virtual address다.
  • user page table의 PTE에는 kpage가 아니라 vtop(kpage)가 들어간다.
  • 따라서 user VA는 kernel VA를 가리키지 않는다. 두 가상 주소가 같은 guest physical frame을 각각 가리킨다.
  • QEMU 환경에서 이 프레임은 host physical address가 아니라 QEMU가 backing하는 guest physical memory에 속한다.
