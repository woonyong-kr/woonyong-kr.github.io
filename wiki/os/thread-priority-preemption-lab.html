Priority Preemption 실험: 높은 우선순위 스레드가 READY가 되는 순간

Priority Preemption 실험: 높은 우선순위 스레드가 READY가 되는 순간

한 줄 요약: thread_create로 만든 스레드는 곧장 실행되지 않고 ready_list에 READY 상태로 들어간다. 새 스레드의 우선순위가 현재 스레드보다 높으면(예: 32 > 31) 그 순간 선점이 일어나야 한다.

스레드를 만들었다 = 바로 실행된다

thread_create("high-priority", PRI_DEFAULT + 1, ...)를 호출하면 새 스레드는 언제 실행될까?

처음에는 스레드를 만드는 즉시 그 스레드가 실행된다고 생각하기 쉽다.

그러나 정확히는 그렇지 않다. 스레드를 만들면 새 struct thread가 생기고, 해당 스레드가 READY 상태로 ready_list에 들어간다. 그 뒤 실제로 CPU를 받을지는 스케줄러가 결정한다.

다만 우선순위 스케줄링에서는 한 가지 동작을 기대할 수 있다.

이 문서에서는 관련 PintOS 코드와 테스트를 따라가며 이러한 “즉시 양보”가 어느 지점에서 일어나도록 구현되어 있는지 확인한다.

Priority Preemption 필요성

priority scheduling의 핵심 약속은 “더 급한 일을 먼저 실행한다”는 것이다.

그런데 높은 우선순위 스레드가 READY 상태가 되었는데도 현재의 낮은 우선순위 스레드가 남은 time slice를 계속 사용한다면, priority는 사실상 “다음 스케줄링 때 참고하는 힌트”에 가까워진다.

이 차이는 테스트에서 바로 드러난다.

priority-preempt 테스트는 main thread가 위 메시지를 출력하기 전에 high-priority thread가 이미 실행을 마쳤어야 한다고 기대한다.

즉, 높은 priority 스레드가 READY 상태가 되는 사건 자체가 선점(preemption)의 기회가 되어야 한다.

Priority Preemption 흐름

PintOS의 priority preemption은 네 단계로 나누어 보면 이해하기 쉽다.

실제 운영체제

실제 OS도 “높은 우선순위 작업이 runnable 상태가 되었을 때 현재 실행 흐름을 계속 유지할 것인가”를 판단해야 한다.

Linux는 단순한 전역 ready_list 하나만으로 이를 결정하지 않는다. CPU별 run queue, scheduler class, wakeup preemption, realtime policy, fairness, SMP load balancing 같은 요소가 함께 작용한다. 따라서 높은 우선순위 또는 더 유리한 runnable task가 생긴 모든 상황을 PintOS처럼 한 번의 비교만으로 처리한다고 이해해서는 안 된다.

Windows 역시 priority와 quantum을 사용하지만, process priority class, thread priority, dynamic boost, dispatcher wait, interrupt/DPC 같은 정책이 함께 작동한다.

PintOS는 이 큰 개념을 교육용으로 단순화하여 ready_list와 priority의 비교로 보여준다.

PintOS

이 코드베이스에서 priority preemption이 드러나는 지점은 세 곳이다.

1) 새 스레드가 만들어질 때

PintOS: SW_AI-W11-pintos/pintos/threads/thread.c

thread_create()는 새 스레드를 초기화한 뒤 thread_unblock(t)를 통해 READY 상태로 만든다. 이어서 새 스레드의 priority가 현재 스레드보다 높으면 thread_yield()를 호출한다.

핵심 흐름만 정리하면 다음과 같다.

priority-preempt 테스트는 바로 이 지점을 검사한다.

2) 세마포어에서 스레드가 깨어날 때

PintOS: SW_AI-W11-pintos/pintos/threads/synch.c

sema_down()은 기다리는 스레드를 sema->waiters에 priority 순서로 넣는다. sema_up()은 waiter가 있으면 priority가 가장 높은 스레드를 깨우고, 마지막에 check_preemption()을 호출한다.

이 흐름을 바탕으로 priority-sema 테스트는 semaphore에서 스레드가 priority 순서대로 깨어나는지 확인한다.

3) 현재 스레드의 priority가 낮아질 때

PintOS: SW_AI-W11-pintos/pintos/threads/thread.c

thread_set_priority()는 현재 스레드의 base_priority를 변경하고 donation을 반영한 뒤 check_preemption()을 호출한다.

이 흐름을 바탕으로 priority-change 테스트는 thread 2가 자신의 priority를 낮추었을 때 main thread가 다시 실행되는 상황을 검사한다.

QEMU

QEMU는 PintOS의 priority 숫자가 지닌 의미를 해석하지 않는다.

QEMU가 관찰하는 것은 다음과 같다.

  • guest CPU가 thread_create(), thread_yield(), schedule() 같은 PintOS 커널 코드를 실행한다.
  • guest memory 안의 struct thread.priority, struct list_elem 바이트가 바뀐다.
  • timer 장치나 interrupt controller가 guest CPU에 interrupt pending 상태를 만든다.

예를 들어 timer preemption 경로에서는 QEMU의 가상 PIT/APIC가 “timer interrupt가 발생한 것처럼” guest에 사건을 전달한다.

  • hw/timer/i8254.c
    • pit_irq_timer_update()가 qemu_set_irq(s->irq, irq_level)를 통해 PIT 출력선을 바꾼다.
    • pit_realizefn()이 channel 0에 timer_new_ns(QEMU_CLOCK_VIRTUAL, pit_irq_timer, s)를 만든다.
  • hw/intc/apic.c
    • apic_timer()가 local APIC timer interrupt를 전달한다.
    • apic_update_irq()가 pending interrupt를 발견하면 cpu_interrupt(cpu, CPU_INTERRUPT_HARD)를 호출한다.

그러나 priority=32가 priority=31보다 더 급하다는 판단은 QEMU가 내리지 않는다. 이는 PintOS guest OS 내부의 정책에 따른 판단이다.

2) ready_list 정렬

PintOS: SW_AI-W11-pintos/pintos/threads/thread.c

thread_unblock()과 thread_yield()는 ready_list에 스레드를 넣을 때 thread_priority 비교 함수를 사용한다.

이 비교 함수는 priority가 큰 스레드를 앞쪽에 둔다.

따라서 next_thread_to_run()이 list_pop_front(&ready_list)를 호출하면 priority가 가장 높은 스레드가 선택된다.

3) 선점 판단

PintOS: SW_AI-W11-pintos/pintos/threads/thread.c

check_preemption()은 ready_list 맨 앞의 스레드와 현재 스레드를 비교한다.

단, interrupt context에서는 곧바로 thread_yield()를 실행하지 않는다. 이 코드베이스의 check_preemption()은 intr_context()이면 그대로 반환한다.

timer interrupt에서 time slice를 기준으로 선점하는 과정은 별도 경로를 따른다.

정리

  • priority preemption은 높은 priority 스레드가 READY 상태가 되는 순간 현재의 낮은 priority 스레드가 CPU를 양보하도록 하는 정책이다.
  • PintOS에서는 ready_list를 priority 내림차순으로 유지하고, thread_create(), sema_up(), thread_set_priority() 같은 지점에서 선점 여부를 다시 확인한다.
  • thread_unblock() 자체가 언제나 선점을 일으키는 것은 아니다. 호출한 쪽에서 atomic update 범위를 마친 뒤 적절한 시점에 양보 여부를 결정한다.
  • QEMU는 priority의 의미를 해석하지 않는다. QEMU는 PintOS가 사용하는 CPU, 메모리, timer/interrupt 장치를 에뮬레이션할 뿐이다.

Priority Preemption 관련 문서

  • thread scheduler
    • ready_list에서 선택된 스레드가 실제로 schedule()로 이어지는 흐름
  • priority donation
    • lock holder의 effective priority가 바뀌는 이유
  • condition
    • sema_up()이 waiter를 깨우는 구조
  • intrusive list Lab
    • ready_list의 list_elem 주소를 struct thread로 복원하는 방법
  • QEMU timer interrupt
    • time slice 선점과 QEMU timer interrupt의 연결
