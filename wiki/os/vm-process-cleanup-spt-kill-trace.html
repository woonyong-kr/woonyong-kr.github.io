process cleanup은 SPT page들을 어떤 순서로 해제하나

process cleanup은 SPT page들을 어떤 순서로 해제하나

확인 범위: 이 문서는 프로세스 종료·exec 시 SPT와 페이지 유형별 자원을 정리하는 일반 원리와 PintOS 구현 시 선택 기준을 설명한다. 제시된 호출 순서, 코드 좌표, 페이지·swap·write-back 예시는 구현 방향과 추적 방법이며, 특정 코드 버전에서의 동작이나 수치, 성능을 실제 실행으로 검증한 결과는 아니다.

process cleanup 쟁점

PintOS VM 구현 준비의 구현 체크리스트에는 이런 질문이 있다.

process exit 때 SPT, frame, swap slot, mmap metadata가 정리되는가?

처음에는 process_exit()이 열린 파일만 닫고 끝나는 것처럼 보인다. 하지만 VM을 구현한 뒤에는 프로세스가 끝날 때 주소 공간의 의미도 같이 사라져야 한다.

이 Trace는 process_exit() 또는 process_exec()가 process_cleanup()으로 들어간 뒤, SPT 안의 page들이 type별 destroy 경로로 내려가는 흐름을 따라간다.

꼬리 질문

  • 왜 pml4_destroy()만으로 VM page 정리가 끝나지 않을까?
  • 실제 OS에서는 process address space teardown이 무엇을 회수할까?
  • PintOS에서는 supplemental_page_table_kill()이 어떤 page들을 순회해야 할까?
  • UNINIT, ANON, FILE page의 destroy 책임은 어떻게 다를까?
  • swapped-out anonymous page가 process exit으로 사라지면 slot은 언제 free되어야 할까?
  • dirty file-backed mmap page는 exit 경로에서 어디로 write-back되어야 할까?
  • QEMU는 process cleanup이나 SPT kill을 알고 있을까?
  • GDB로 어디를 보면 page가 한 번만 destroy되는지 확인할 수 있을까?

process cleanup 필요성

VM 이후의 주소 공간은 단순한 page table이 아니다.

PML4는 CPU가 걷는 hardware page table이고, SPT는 PintOS가 “이 유저 VA는 원래 어떤 page인가”를 기억하는 커널 metadata다.

이 말은 즉, pml4_destroy()는 page table page들을 해제할 수 있지만, SPT가 들고 있는 backing 의미까지 자동으로 정리하지 않는다.

process teardown에서 SPT 정리가 빠지면 이런 버그가 생긴다.

빠진 정리결과
resident frame 해제user pool frame 누수
swapped-out anon slot freeswap slot 누수
dirty mmap write-back파일 수정 내용 손실
uninit lazy aux 해제file reference 또는 aux metadata 누수
SPT entry 제거종료한 process의 page metadata가 남음

process cleanup 흐름

process cleanup의 VM 부분은 이렇게 읽으면 된다.

process_exec()도 같은 cleanup 경로를 쓴다.

핵심은 supplemental_page_table_kill()이 pml4_destroy()보다 먼저 와야 한다는 점이다. page destructor가 현재 page의 frame, dirty bit, PTE 상태를 확인해야 할 수 있기 때문이다.

    B --> C["supplemental_page_table_kill(&spt)"]
    C --> D{"SPT 순회: 각 page"}
    D --> E["page type?"]
    E -->|UNINIT| F["uninit_destroy(page)\naux/file ref 정리"]
    E -->|ANON resident| G["anon_destroy(page)\nframe 반환"]
    E -->|ANON swapped| H["anon_destroy(page)\nswap slot free"]
    E -->|FILE dirty| I["file_backed_destroy(page)\nwrite-back + frame 반환"]
    E -->|FILE clean| J["file_backed_destroy(page)\nframe 반환만"]
    F --> K["vm_dealloc_page(page)\nfree(page)"]

한 프로세스가 다음 page들을 갖고 있다고 하자.

VA상태정리해야 할 것
0x400000lazy code page, 아직 접근 안 함lazy aux, reopened file reference
0x401000resident anonymous pageframe, PTE, page metadata

프로세스가 종료되면 유저 VA들은 더 이상 의미가 없다. 하지만 cleanup이 해야 할 일은 page 상태마다 다르다.

정리의 목표는 “종료한 process의 주소 공간을 다시 fault로 살릴 수 없게 하는 것”만이 아니다. 더 중요한 목표는 그 주소 공간이 잡고 있던 커널 자원을 정확히 한 번씩 회수하는 것이다.

실제 운영체제

Linux에서는 exit()나 execve()가 성공할 때 기존 mm_struct와 VMA, page table, file-backed mapping, anonymous page, swap entry 같은 자원을 정리한다. 실제 구현은 reference count, reverse mapping, page cache, TLB shootdown, file write-back 정책과 얽힌다.

Windows도 process address space를 구성하는 VAD, section object, prototype PTE, working set, pagefile-backed private page 같은 자원을 정리한다. Unix식 fork() 모델과는 다르지만, process가 소유한 private address space metadata를 teardown해야 한다는 점은 같다.

현실 OS는 PintOS보다 훨씬 복잡하다. 여러 CPU가 같은 process를 실행할 수 있고, mapping이 공유될 수 있으며, write-back과 page cache 정책도 포함된다. PintOS는 이 복잡도를 supplemental_page_table_kill()과 page operation table로 축소해 연습하게 한다.

PintOS

PintOS에서 cleanup 경로는 두 진입점에서 시작한다.

진입점의미
process_exit()process가 완전히 끝남
process_exec()같은 thread가 기존 주소 공간을 버리고 새 프로그램으로 바뀜

두 함수 모두 SW_AI-W11-pintos/pintos/userprog/process.c의 process_cleanup()으로 들어간다.

VM이 켜져 있으면 process_cleanup()은 먼저 supplemental_page_table_kill(&curr->spt)를 호출한다. 그 뒤 curr->pml4 = NULL, pml4_activate(NULL), pml4_destroy(pml4) 순서로 page table 자체를 파괴한다.

현재 기준 저장소의 VM 코드는 skeleton이다. SW_AI-W11-pintos/pintos/vm/vm.c의 supplemental_page_table_kill()에는 아직 TODO만 있다.

구현자가 채워야 할 큰 흐름은 다음이다.

SPT를 hash table로 구현했다면 SW_AI-W11-pintos/pintos/lib/kernel/hash.c의 hash_destroy(h, destructor) 패턴을 쓸 수 있다. destructor는 각 hash element를 받아 struct page로 되돌린 뒤 vm_dealloc_page(page)를 호출하는 식이 된다.

주의할 점은 destroy(page)와 free(page)를 섞지 않는 것이다. type별 destroy 함수는 page가 잡은 외부 자원을 정리하고, vm_dealloc_page()가 마지막에 struct page 메모리를 해제한다.

QEMU

QEMU는 PintOS process도, SPT도, struct page도 모른다.

QEMU가 제공하는 것은 더 낮은 층이다.

  • CPU가 page table walk를 하다가 실패하면 pf를 만든다.
  • guest store가 성공하면 x86 규칙에 따라 PTE dirty bit가 세팅될 수 있다.
  • PintOS가 disk sector read/write를 요청하면 IDE/block backend로 처리한다.
  • GDB stub을 통해 guest register와 memory를 관찰하게 해 준다.

예를 들어 dirty mmap page를 exit 때 파일로 write-back하면 PintOS 내부에서는 file_write_at() 계열 호출이 일어나고, 더 아래에서는 disk sector write가 발생할 수 있다. QEMU의 hw/ide/core.c는 ide_sector_write()에서 sector 번호를 얻고, blk_aio_pwritev()에 sector_num << BDRV_SECTOR_BITS byte offset을 넘긴다.

하지만 QEMU는 이것이 “process exit 때문에 dirty mmap page를 되돌리는 write-back”인지 모른다. QEMU 입장에서는 guest가 특정 sector에 write를 보낸 것이다.

process cleanup 코드

1. exec()와 exit()는 둘 다 process_cleanup()을 지난다

SW_AI-W11-pintos/pintos/userprog/process.c

exec()에서 cleanup이 먼저 나오는 이유는 새 ELF를 로드하기 전에 기존 주소 공간을 버려야 하기 때문이다.

2. VM cleanup은 PML4 destroy보다 먼저 호출된다

같은 파일의 process_cleanup()은 VM 빌드에서 먼저 SPT를 kill한다.

이 순서는 중요하다. page별 destroy가 PTE dirty bit나 frame 연결을 봐야 한다면 PML4가 먼저 사라지면 판단 근거가 줄어든다.

3. destroy(page)는 page operation table로 분기한다

SW_AI-W11-pintos/pintos/include/vm/vm.h

따라서 SPT kill은 page type을 직접 switch로 모두 알아도 되지만, 기본 설계는 page가 가진 operation table로 정리 책임을 위임하는 쪽이다.

4. type별 destroy 자리는 이미 나뉘어 있다

관련 파일:

  • SW_AI-W11-pintos/pintos/vm/uninit.c
    • uninit_destroy()
  • SW_AI-W11-pintos/pintos/vm/anon.c
    • anon_destroy()
  • SW_AI-W11-pintos/pintos/vm/file.c
    • file_backed_destroy()

이 함수들은 현재 TODO다. 그래서 VM 구현에서는 “page를 free한다”와 “page가 가진 외부 자원을 정리한다”를 분리해서 채워야 한다.

5. QEMU는 dirty bit와 disk sector write 효과만 본다

QEMU의 x86 MMU helper는 store 접근에서 dirty bit를 세울 수 있다.

  • target/i386/tcg/system/excp_helper.c
    • access_type == MMU_DATA_STORE이면 PG_DIRTY_MASK를 set 대상에 포함한다.
  • target/i386/cpu.h
    • PG_DIRTY_BIT = 6
    • PG_DIRTY_MASK

또한 hw/ide/core.c의 ide_sector_write()는 sector 번호를 byte offset으로 바꿔 block backend에 넘긴다.

BDRV_SECTOR_BITS는 include/block/block-common.h에서 9로 정의된다. 즉 sector 하나는 1 << 9 = 512B다.

process cleanup 값 추적

1. process cleanup 전후 page 수 감각

예를 들어 SPT에 page 4개가 있다고 하자.

정리 대상은 frame 개수와 다르다.

그래서 cleanup은 “PTE가 있는 page만” 보면 안 된다. 아직 resident가 아닌 page도 SPT에는 남아 있고, 그 page가 swap slot이나 lazy aux를 잡고 있을 수 있다.

2. swapped-out page의 slot 계산

slot 3이 차지하는 sector:

process exit에서 이 page가 RAM으로 돌아오지 않고 사라진다면, anon_destroy()는 slot 3을 free로 되돌려야 한다. disk bytes를 0으로 지우는 것이 핵심이 아니라, slot allocator가 다시 slot 3을 줄 수 있게 만드는 것이 핵심이다.

3. dirty file-backed page의 write-back 범위

이 page는 4096B frame을 갖지만, 파일에 되돌릴 수 있는 범위는 보통 read_bytes만큼이다.

정리

  • pml4_destroy()는 hardware page table 구조를 해제하지만, SPT가 기억한 VM backing 의미를 대신 정리하지 않는다.
  • supplemental_page_table_kill()은 process exit과 exec cleanup에서 SPT의 모든 page를 순회해야 한다.
  • page별 실제 정리는 destroy(page)를 통해 uninit_destroy(), anon_destroy(), file_backed_destroy()로 내려간다.
  • swapped-out anonymous page는 frame이 없어도 swap slot을 회수해야 한다.
  • dirty file-backed page는 process exit에서도 munmap()과 같은 write-back 의미를 가져야 한다.
  • QEMU는 이 정책을 모르고, page fault와 disk sector I/O 같은 하드웨어 효과만 제공한다.
