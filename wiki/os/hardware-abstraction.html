추상화

추상화

한 줄 요약: 물리 RAM·디스크 섹터·특권 비트를 직접 다루는 위험을 감추는 운영체제의 첫 책임 추상화.

추상화 상태

운영체제의 첫 번째 책임은 하드웨어를 감추는 것이다. 프로그램이 물리 RAM 주소, 디스크 섹터 번호, CPU 특권 비트를 직접 다루면 한 프로그램이 다른 프로그램의 메모리를 밟거나 디스크를 덮어쓸 수 있다. OS는 하드웨어 위에 가상 주소 공간, 파일 시스템, 프로세스/스레드라는 세 가지 추상화를 놓아 프로그램이 서로 간섭 없이 실행되게 한다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

추상화는 순수 소프트웨어 트릭이 아니다. CPU와 MMU가 하드웨어 수준에서 지원해야 가능하다.

추상화하드웨어 지원역할
가상 주소 공간MMU + 페이지 테이블 (CR3)프로그램마다 독립된 주소 공간, 물리 메모리 배치 은닉
파일 시스템디스크 컨트롤러 + DMA섹터 번호를 경로/파일/오프셋으로 변환
프로세스/스레드인터럽트 + TSS + 타이머CPU 시간을 분할, 각 실행 흐름에 독립 레지스터 상태 부여

MMU가 없으면 가상 주소를 물리 주소로 변환할 수 없으므로 모든 프로그램이 같은 물리 메모리를 공유해야 한다. 타이머 인터럽트가 없으면 OS가 CPU를 빼앗을 시점을 알 수 없으므로 선점형 스케줄링이 불가능하다.

가상 주소 공간. 각 프로세스는 0x0000000000000000 ~ 0x00007FFFFFFFFFFF (user 영역, 약 128 TB)을 자기만의 연속 공간처럼 사용한다. 실제로는 페이지 테이블이 4 KB 단위로 물리 프레임에 매핑하며, 프로세스마다 별도의 PML4 테이블을 가진다. 프로세스 전환 시 CR3를 교체하면 주소 공간 전체가 바뀐다.

파일 시스템. 디스크는 512 B 섹터의 배열일 뿐이다. OS는 inode, 디렉터리 트리, 파일 오프셋을 관리하여 프로그램이 open("/etc/passwd"), read(fd, buf, 128) 같은 인터페이스로 데이터를 다루게 한다.

프로세스/스레드. CPU는 하나(또는 소수)인데 프로그램은 많다. OS는 타이머 인터럽트로 CPU를 주기적으로 빼앗고, 레지스터 상태를 저장/복원하여 각 실행 흐름이 “자기만의 CPU”를 가진 것처럼 보이게 한다.

실제 OS (Linux/Windows)

Linux에서 세 추상화는 다음과 같이 구현된다.

추상화Linux 구현체핵심 자료구조
가상 주소 공간mm subsystemstruct mm_struct, struct vm_area_struct, 4단계 페이지 테이블
파일 시스템VFS + 구체 fs (ext4, btrfs 등)struct inode, struct file, struct dentry
프로세스/스레드task managementstruct task_struct, CFS scheduler

Windows에서는 Memory Manager가 가상 메모리를, NTFS/ReFS가 파일 시스템을, Process/Thread Manager가 프로세스 추상화를 담당한다. 핵심 원리는 같지만 자료구조 이름과 정책이 다르다.

실제 OS는 추상화 위에 최적화를 겹겹이 쌓는다. huge page (2 MB / 1 GB), copy-on-write, page cache, NUMA-aware allocation, I/O scheduler 등이 모두 기본 추상화 위의 확장이다.

PintOS 구현

PintOS는 세 추상화를 최소한으로 구현한다.

가상 주소 공간:

파일함수/구조체역할
threads/mmu.cpml4_create()프로세스용 PML4 테이블 생성
threads/mmu.cpml4_set_page()VA → PA 매핑 등록
threads/mmu.cpml4_activate()CR3에 새 PML4 주소 적재 → 주소 공간 전환
userprog/process.cprocess_activate()스레드 전환 시 pml4_activate() + TSS 갱신

PintOS 주소 공간 배치:

%% PintOS 주소 공간 배치
flowchart TD
  layout["주소 &#124; PintOS 주소 공간<br/>0xFFFFFFFFFFFFFFFF &#124;<br/>Kernel Space<br/>직접 매핑<br/>PA + KERN_BASE<br/>KERN_BASE = 0x8004000000<br/>0x8004000000 근처 &#124; 접근 불가 영역<br/>USER_STACK = 0x47480000 &#124;<br/>User Stack<br/>아래 방향으로 성장"]

기본 사용자 ELF의 text는 0x400000에서 적재되며 ELF program header에 따라 data와 BSS가 뒤따른다. 실제 경계는 실행 파일의 segment 크기와 정렬에 따라 달라지므로 0x400000을 data/BSS의 고정 주소로 해석하지 않는다.

파일 시스템: PintOS filesys/ 디렉터리에 단순한 파일 시스템이 있다. 저널링, 권한, 심볼릭 링크 없이 기본 create, open, read, write, close만 지원한다. 디스크 접근은 disk_read()/disk_write()로 섹터 단위 I/O를 수행한다.

프로세스/스레드: struct thread가 프로세스이자 스레드 역할을 겸한다. 별도의 struct process가 없고, 스레드 하나가 곧 하나의 실행 단위다.

QEMU 에뮬레이션

QEMU는 이 세 추상화에 관여하지 않는다. QEMU가 제공하는 것은 추상화의 전제 조건인 하드웨어다.

OS 추상화QEMU가 제공하는 하드웨어QEMU가 모르는 것
가상 주소 공간페이지 테이블 walk 효과 재현, CR3 전환어떤 프로세스에 어떤 페이지를 줄지
파일 시스템IDE 컨트롤러 모델, block backend파일 이름, 디렉터리, inode 구조
프로세스/스레드타이머 인터럽트 (i8254 PIT), 인터럽트 전달 (i8259 PIC)ready list, priority, time slice 정책

추상화 값 추적

페이지 테이블 매핑 예제:

User VA     = 0x0000000000400000
Page size   = 4096 (0x1000)
PML4 index  = (0x400000 >> 39) & 0x1FF = 0
PDPT index  = (0x400000 >> 30) & 0x1FF = 0
PD index    = (0x400000 >> 21) & 0x1FF = 2
PT index    = (0x400000 >> 12) & 0x1FF = 0
Offset      = 0x400000 & 0xFFF        = 0

만약 이 VA가 물리 프레임 0x200000에 매핑되어 있다면, 프로그램은 0x400000을 읽지만 실제 RAM 접근은 0x200000 + 0 = 0x200000이다.

파일 시스템 섹터 매핑 예제:

파일 오프셋      = 1024 bytes
섹터 크기        = 512 bytes
시작 섹터 번호   = inode가 가리키는 data block의 첫 섹터
필요 섹터        = 1024 / 512 = 2개 (섹터 0, 1)

    D --> E[디스크 드라이버: sector read]

    H --> I[MMU: VA → PA 변환]
    I --> J[물리 프레임에 기록]

파일 시스템VFS + ext4/btrfs/xfs, 저널링, ACL, 심볼릭 링크단순 inode, 저널링 없음, 권한 없음PintOS는 필수 CRUD만
프로세스struct task_struct, CFS, cgroup, namespacestruct thread (프로세스=스레드), 우선순위 스케줄링Linux는 격리·자원 제한 계층 있음
