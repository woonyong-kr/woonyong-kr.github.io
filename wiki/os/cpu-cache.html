CPU 캐시

CPU 캐시

확인 범위: 이 문서는 CPU 캐시의 일반 원리와 OS 설계에서의 고려 기준을 설명하고, PintOS·QEMU 관련 내용은 입력에 제시된 코드와 동작 설명을 바탕으로 구현별 차이를 구분한다. 구체적인 지연 시간·캐시 구성·성능 효과는 CPU와 버전, 실행 환경에 따라 달라질 수 있으므로 실제 코드·버전 확인과 실행 기록 또는 성능 측정 없이는 특정 구현의 검증 결과로 간주하지 않는다.

한 줄 요약: CPU 캐시는 자주 접근하는 메모리 내용을 CPU 가까이에 복사해 두는 소규모 고속 SRAM이다. 캐시가 없으면 CPU는 매 명령어마다 수십~수백 사이클을 메모리 대기에 낭비한다.

CPU 캐시 필요성

CPU는 매 사이클(0.3ns)마다 연산을 수행한다. 그런데 메인 메모리(DRAM, Dynamic RAM)에서 데이터를 가져오려면 약 50100ns가 걸린다. 비유하면 CPU가 1초에 한 번 일하는데, 재료를 가져오는 데 2~3분이 걸리는 셈이다.

이 속도 차이를 **메모리 벽(Memory Wall)**이라 부른다. 캐시가 없으면 CPU는 대부분의 시간을 메모리 응답을 기다리며 놀게 된다. CPU 캐시는 이 격차를 줄이기 위해 CPU와 메인 메모리 사이에 놓는 소규모 고속 SRAM(Static RAM)이다. 메인 메모리로 쓰는 DRAM보다 빠르지만, 셀 하나에 트랜지스터가 더 많이 들어가 같은 면적에 담을 수 있는 용량이 작다. 그래서 캐시는 항상 메모리보다 작다.

캐시가 동작하는 근거는 지역성(Locality) 원리다.

  • 시간 지역성(Temporal Locality): 한 번 접근한 데이터는 곧 다시 접근할 가능성이 높다. 반복문의 카운터 변수가 대표적이다.
  • 공간 지역성(Spatial Locality): 한 주소에 접근하면 인접 주소도 곧 접근할 가능성이 높다. 배열 순회가 대표적이다.

CPU 캐시 흐름

메모리 계층 구조

CPU에서 멀어질수록 용량은 커지고 속도는 느려진다.

%% 메모리 계층 구조
flowchart TD
  l1["L1 캐시 &#124; ~1 cycle &#124; 32~64 KB<br/>레지스터 바로 옆"]
  l2["L2 캐시 &#124; ~4~10 cycle &#124; 256 KB~1 MB"]
  l3["L3 캐시 &#124; ~20~40 cycle &#124; 8~64 MB<br/>코어 간 공유"]
  dram["메인 메모리 &#124; ~50~100 cycle &#124; 수 GB~수십 GB<br/>DRAM"]
  disk["디스크/SSD &#124; ~수만~수십만 cycle &#124; 수백 GB~수 TB"]
  l1 --> l2
  l2 --> l3
  l3 --> dram
  dram --> disk

L1은 코어마다 독립적으로 존재하고, 명령어 캐시(I-cache)와 데이터 캐시(D-cache)로 분리된다. L2는 코어별 또는 코어 쌍이 공유한다. L3는 모든 코어가 공유한다.

캐시 라인 (Cache Line)

캐시는 바이트 단위가 아니라 캐시 라인 단위로 데이터를 관리한다. x86-64에서 캐시 라인 크기는 64바이트다.

CPU가 주소 0x1004의 4바이트를 읽으면, 캐시는 0x1000~0x103F 64바이트 전체를 메모리에서 가져온다. 이것이 공간 지역성을 활용하는 핵심 메커니즘이다. 배열 int arr[16]을 순회하면 첫 원소 접근 시 64바이트(16개 int)가 한 번에 캐시에 올라오므로, 나머지 15번은 캐시 히트로 처리된다.

캐시 히트와 캐시 미스

  • 캐시 히트(Cache Hit): 요청한 데이터가 캐시에 있다. L1 히트면 ~1 사이클.
  • 캐시 미스(Cache Miss): 캐시에 없어서 하위 계층에서 가져와야 한다.

캐시 미스는 세 가지로 분류한다.

  • Cold miss (Compulsory miss): 처음 접근하는 데이터. 캐시에 한 번도 올라온 적 없다.
  • Capacity miss: 캐시 용량이 부족해서 이전에 캐시된 데이터가 밀려났다.
  • Conflict miss: 캐시 구조상 같은 위치에 매핑되는 다른 데이터와 충돌했다.

캐시 매핑 방식

메모리 주소를 캐시의 어느 위치에 저장할지 결정하는 방식이다.

  • 직접 매핑(Direct Mapped): 주소가 캐시의 한 곳에만 들어갈 수 있다. 빠르지만 충돌이 잦다.
  • 완전 연관(Fully Associative): 아무 위치에나 들어갈 수 있다. 충돌 없지만 검색이 느리다.
  • 집합 연관(Set Associative): 절충안. N-way set associative는 한 집합 안에 N개 라인을 둔다. 현대 CPU의 L1은 보통 8-way, L2는 4~16-way이다.

쓰기 정책

캐시에 쓸 때 메인 메모리와 어떻게 동기화할지 결정한다.

  • Write-through: 캐시에 쓸 때마다 메인 메모리에도 동시에 쓴다. 일관성은 보장되지만 느리다.
  • Write-back: 캐시에만 쓰고, 캐시 라인이 교체될 때 메인 메모리에 반영한다. dirty bit로 수정 여부를 표시한다. 현대 CPU 대부분이 이 방식이다.

교체 정책

캐시가 꽉 찼을 때 어떤 라인을 내보낼지 결정한다.

  • LRU(Least Recently Used): 가장 오래전에 접근한 라인을 교체. 구현 비용이 높아 현대 CPU는 pseudo-LRU를 쓴다.
  • Random: 무작위 교체. L3처럼 라인 수가 많으면 LRU와 성능 차이가 크지 않다.

왜 캐시 라인이 64바이트인가?

캐시 라인 크기 = 한 번의 메모리 버스 전송으로 효율적으로 가져올 수 있는 크기

라인이 너무 작으면 → 공간 지역성 활용 못 함, 메모리 접근 횟수 증가 라인이 너무 크면 → 불필요한 데이터까지 가져옴, 캐시 공간 낭비, 교체 빈도 증가

DDR 메모리 버스의 burst 전송 단위(8 × 8바이트 = 64바이트)와 맞추면 한 번의 burst로 캐시 라인 하나를 정확히 채울 수 있다. 64바이트는 버스 효율과 지역성 활용의 균형점이다.

OS가 캐시를 신경 써야 하는 이유

CPU 캐시는 하드웨어가 자동 관리하지만, OS 설계에서 캐시를 무시하면 성능이 크게 떨어진다.

  • 페이지 크기 선택: 4KB 페이지는 캐시 라인(64B)의 정수배다. 페이지 내 데이터는 연속 캐시 라인에 매핑된다.
  • 컨텍스트 스위칭 비용: 프로세스를 전환하면 캐시에 쌓인 데이터가 새 프로세스에 무의미해진다. 이것이 컨텍스트 스위칭의 숨은 비용이다.
  • TLB 미스와 캐시 미스 중첩: 가상 주소를 물리 주소로 변환하는 TLB도 캐시의 일종이다. TLB 미스가 나면 페이지 테이블 워크가 필요하고, 이 과정에서 추가 캐시 미스가 발생할 수 있다.
  • 캐시 라인 바운싱: 멀티코어에서 여러 코어가 같은 캐시 라인을 수정하면 일관성 프로토콜(MESI 등)로 인해 캐시 라인이 코어 간에 반복 전송된다. 이것이 경쟁 조건의 성능 측면 원인이기도 하다.

실제 OS · PintOS · QEMU에서 캐시는 누가 다루나

같은 CPU 캐시라도 어느 시스템을 기준으로 보느냐에 따라 다루는 주체가 다르다. 기준을 섞지 않고 분리한다.

  • 실제 OS (Linux / Windows) 기준
    • CPU 캐시 적재와 교체 자체는 하드웨어가 자동으로 한다. OS가 특정 데이터를 캐시에 “넣어라”라고 명령하지 않는다.
    • 대신 OS는 캐시 효율을 높이는 간접 제어를 한다. 페이지 컬러링(page coloring)으로 물리 페이지를 캐시 집합에 고르게 흩어 충돌 미스를 줄이고, clflush 명령어로 특정 캐시 라인을 비워 DMA(Direct Memory Access) 전후의 데이터 일관성을 맞춘다.
    • 멀티코어 일관성은 하드웨어 MESI(Modified-Exclusive-Shared-Invalid) 프로토콜이 담당하고, OS는 그 위에서 락과 메모리 배리어로 쓰기 가시성을 보장한다.
  • PintOS 기준
    • 페이지 컬러링도, clflush 호출도 없다. palloc_get_page()는 4KB 페이지를 비트맵 순서대로 나눠줄 뿐 캐시 집합 분산을 고려하지 않는다.
    • 즉 PintOS는 “4KB = 64 캐시 라인”이라는 정렬 이점만 자연히 얻고, 캐시를 적극적으로 제어하는 코드는 두지 않는다. 교육용 OS의 단순함이 드러나는 지점이다.
  • QEMU 기준
    • QEMU의 TCG(Tiny Code Generator)는 게스트 명령어를 호스트 명령어로 번역해 실행할 뿐, 게스트 CPU의 L1/L2/L3 캐시 계층을 모델링하지 않는다. 실행 루프는 accel/tcg/cpu-exec.c에 있다.
    • accel/tcg/cputlb.c에 있는 “TLB”는 게스트 메모리 접근을 빠르게 하기 위한 호스트 측 자료구조이지, 게스트 캐시의 히트/미스 타이밍을 흉내 내는 것이 아니다.
    • 결론: PintOS를 QEMU 위에서 돌리면 캐시 미스로 생기는 사이클 지연이 관측되지 않는다. 캐시 효과를 실험으로 재현하려면 실제 하드웨어나 사이클 정확(cycle-accurate) 시뮬레이터가 필요하다.

QEMU 소스: accel/tcg/cpu-exec.c, accel/tcg/cputlb.c

CPU 캐시 코드

PintOS는 교육용 OS이므로 CPU 캐시를 직접 다루지 않는다. 하드웨어(QEMU가 에뮬레이션하는 x86-64)가 캐시를 자동으로 관리한다. 하지만 PintOS의 메모리 관리 코드 곳곳에 캐시 친화적 설계가 녹아 있다.

페이지 단위 할당 — 캐시 라인 정렬

PGSIZE는 4096바이트다. 4096 / 64 = 64이므로, 한 페이지는 정확히 64개 캐시 라인으로 구성된다. palloc_get_page()로 할당받은 메모리는 항상 4KB 경계에 정렬되어 있으므로, 캐시 라인 경계와도 자연스럽게 정렬된다.

풀 기반 할당 — 연속 메모리와 공간 지역성

커널 풀과 유저 풀은 각각 연속된 물리 메모리 영역이다. 비트맵으로 관리하면 인접 페이지가 물리적으로도 인접할 가능성이 높아, 공간 지역성에 유리하다.

캐시의 세 가지 얼굴 — 메모리 계층에서 “캐시”라 불리는 것들

OS에서 “캐시”라는 이름은 세 곳에 등장한다. 각각 캐싱 대상과 관리 주체가 다르다.

%% 메모리 계층의 캐시 종류
flowchart LR
  cpu_cache["CPU 캐시<br/>이 문서<br/>대상: 데이터 + 명령어<br/>관리: 하드웨어 자동"]
  tlb["TLB<br/>주소 변환 캐시<br/>대상: 주소 변환 결과<br/>관리: HW + OS 무효화"]
  buffer_cache["버퍼 캐시<br/>디스크 I/O 캐시<br/>대상: 디스크 섹터 내용<br/>관리: OS 커널 코드"]
  cpu_cache --> tlb
  tlb --> buffer_cache
  • CPU 캐시: 하드웨어가 자동 관리. OS가 직접 제어하지 않지만 성능에 지대한 영향.
  • TLB: 주소 변환 결과를 캐싱. 하드웨어가 관리하지만 OS가 페이지 테이블 변경 시 무효화해야 한다.
  • 버퍼 캐시: 디스크 섹터를 RAM에 캐싱. 순수하게 OS 커널 코드로 구현한다.

정리

CPU 캐시는 CPU와 메인 메모리 사이의 속도 격차(~100배)를 줄이는 소규모 SRAM이다. 캐시 라인(64B) 단위로 데이터를 관리하며, 시간 지역성과 공간 지역성에 기반해 동작한다. L1/L2/L3 계층으로 나뉘고, 현대 CPU는 write-back + set-associative 방식을 주로 사용한다.

OS 개발자가 CPU 캐시를 직접 제어하지는 않지만, 페이지 크기 결정, 컨텍스트 스위칭 비용 이해, 멀티코어 동기화 설계에서 캐시 동작을 반드시 고려해야 한다. TLB와 버퍼 캐시는 같은 “캐시” 원리를 각각 주소 변환과 디스크 I/O에 적용한 것이다. 단, PintOS를 QEMU 위에서 실행하면 캐시 미스로 인한 지연은 관측되지 않는다. 캐시 효과는 PintOS 코드가 아니라 그 아래 하드웨어 규칙으로 이해해야 한다.
