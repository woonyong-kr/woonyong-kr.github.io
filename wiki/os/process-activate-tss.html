process_activate() — TSS rsp0 설정과 주소 공간 전환

process_activate()는 문맥 전환 때 새 스레드의 주소 공간을 CR3에 올리고, 다음 유저 모드 진입에서 사용할 커널 스택 꼭대기를 TSS rsp0에 적어 둔다.

문맥 전환에서 맞춰야 할 두 상태

스케줄러가 다음 스레드를 선택해도 CPU의 주소 공간과 커널 진입 스택이 이전 스레드를 가리키고 있으면 새 스레드를 안전하게 실행할 수 없다. process_activate()는 문맥 전환 때마다 이 두 상태를 새 스레드에 맞춘다. 먼저 PML4를 CR3에 로드해 주소 공간을 전환하고, 이어서 TSS의 rsp0을 새 스레드의 커널 스택 꼭대기로 갱신한다.

두 작업은 서로 다른 문제를 막는다. 유저 프로그램마다 독립된 가상 주소 공간을 사용하므로 CR3를 바꾸지 않으면 이전 프로세스의 주소 공간이 남아 잘못된 메모리에 접근할 수 있다. 또한 이 문서에서 다루는 PintOS의 인터럽트·trap gate 경로에서는 유저 모드(CPL 3)에서 커널 모드로 전환할 때 CPU가 TSS의 rsp0에 저장된 주소를 새 RSP로 사용한다. rsp0이 이전 스레드의 커널 스택을 가리키면 새 스레드의 전환 프레임이 그 스택에 쌓일 수 있다.

여기서 TSS가 시스템 전체에 하나라는 설명은 이 문서의 단일 CPU PintOS 구현에 해당한다. 스레드 A와 스레드 B가 서로 다른 커널 스택을 가지더라도 하나의 TSS를 공유하므로, 스레드가 바뀔 때마다 TSS.rsp0을 현재 스레드의 커널 스택으로 갱신해야 한다. 갱신하지 않으면 스레드 B가 유저 모드에서 인터럽트를 받았을 때 스레드 A의 커널 스택에 프레임이 쌓여 두 스레드의 커널 스택이 오염될 수 있다.

syscall 명령은 이 규칙과 구분해야 한다. 아래 QEMU 경로에서 설명하듯 syscall 명령 자체는 TSS를 참조해 스택을 자동 전환하지 않는다. PintOS는 syscall 대신 trap gate(IDT)를 사용하므로 이 문서의 process_activate()와 rsp0 설명은 해당 인터럽트 경로를 기준으로 한다.

PintOS 구현

PintOS의 process_activate() 함수는 다음 두 호출로 주소 공간과 커널 진입 스택을 차례로 설정한다.

process_activate() 함수 (userprog/process.c:659):

1단계 — pml4_activate(next->pml4)

  • next->pml4가 NULL이면 커널 스레드이므로 커널 기본 PML4인 base_pml4를 사용한다.
  • vtop()으로 가상 주소를 물리 주소로 변환한 뒤 lcr3()로 CR3 레지스터에 기록한다.
  • 이 문서의 PintOS와 QEMU 설명에서는 CR3 변경으로 이전 스레드의 주소 매핑 캐시가 무효화된다.

2단계 — tss_update(next)

userprog/tss.c:76의 구현은 다음과 같다.

PintOS에서 스레드의 struct thread는 4 KiB 페이지의 맨 아래에 있고, 커널 스택은 같은 페이지의 맨 위에서 아래로 자란다. 따라서 (uint64_t)next + PGSIZE가 커널 스택의 최상단 주소가 된다.

+------------------+ ← next + PGSIZE = tss->rsp0 (0x8004_5000)
|  커널 스택 성장 ↓ |
|                  |
|   (빈 공간)      |
|                  |
|  struct thread   |
+------------------+ ← next (0x8004_4000)

호출과 초기화 순서

schedule()은 다음 스레드를 실행 상태로 바꾼 뒤 process_activate(next)를 호출한다. 주소 공간과 rsp0을 새 스레드에 맞춘 다음 thread_launch 또는 do_iret 경로로 진행한다.

호출 시점 — schedule() 내부 (threads/thread.c:716):

process_activate()는 #ifdef USERPROG 안에 있으므로 userprog 프로젝트부터 활성화된다. threads 프로젝트에서는 모든 스레드가 커널 모드에서만 실행되므로 이 구현에서 주소 공간 전환과 TSS 갱신이 필요하지 않다.

TSS 자체는 부팅 과정에서 먼저 준비된다.

초기화 — tss_init() (userprog/tss.c:51):

palloc_get_page()로 4 KiB 페이지를 할당해 TSS 구조체로 사용한다. 부팅 시 main() → tss_init()에서 호출되며, 초기 스레드의 커널 스택 주소로 rsp0을 설정한다.

QEMU에서 보이는 하드웨어 경로

QEMU는 TSS를 target/i386/seg_helper.c의 switch_tss_ra() 등에서 에뮬레이션한다. Guest OS가 ltr 명령으로 TSS 셀렉터를 로드하면 QEMU가 GDT에서 TSS 디스크립터를 읽어 CPUX86State.tr 필드에 저장한다. 이 문서에서 다루는 유저 모드에서 커널 모드로의 인터럽트 전환에서는 QEMU가 env->tr.base를 기준으로 rsp0을 읽어 Guest RSP를 교체한다.

QEMU 내부 rsp0 사용 경로 (interrupt vs syscall):

[인터럽트 경로]
do_interrupt_all() → do_interrupt64()
  esp = get_rsp_from_tss(env, 0)    // IST=0이면 rsp0 사용
  → env->tr.base + 4 에서 8바이트 읽기
  → guest 메모리에서 rsp0 값 fetch
  → 이 값을 new RSP로 사용, 이전 SS/RSP를 guest 스택에 push

[syscall 경로 — MSR 기반, TSS 무관]
helper_syscall() → target/i386/seg_helper.c
  env->regs[R_ESP] = env->star >> 32  // LSTAR가 아닌 STAR.RSP는 아님
  → 실제로는 syscall은 스택을 자동 전환하지 않음
  → PintOS는 syscall이 아닌 int $0x80 또는 trap gate 사용

syscall 명령은 TSS를 참조하지 않는 MSR 기반 경로다. PintOS는 syscall 대신 trap gate(IDT)를 사용하므로 do_interrupt64() 경로에서 TSS의 rsp0을 읽는다. 이 경로가 올바른 스레드의 커널 스택을 사용하려면 tss_update()가 각 context switch에서 rsp0을 갱신해야 한다.

CR3 교체도 QEMU에서 별도의 경로로 에뮬레이션된다. Guest가 mov cr3, rax(lcr3)를 실행하면 QEMU TCG는 다음 순서로 상태를 바꾼다.

helper_write_crN() → target/i386/misc_helper.c
  → cpu_x86_update_cr3(env, val)
  → env->cr[3] = val
  → tlb_flush(cs)  // QEMU softmmu TLB 전체 무효화

QEMU softmmu의 TLB(CPUTLBEntry)는 guest 가상 주소에서 host 가상 주소로의 매핑을 캐시하며, 이 경로에서는 CR3 변경 시 전체 플러시된다. 이는 guest OS의 pml4_activate()에서 일어나는 TLB 플러시를 에뮬레이션한 것이다.

GDB로 process_activate() 관찰

다음 절차는 process_activate()의 두 호출 전후에서 CR3와 tss->rsp0을 비교하도록 구성되어 있다. 아래 값은 실행 결과가 아니라 관찰할 항목과 기대 관계다.

① breakpoint 설정:
   (gdb) b process_activate

② hit 후 next 스레드 확인:
   (gdb) p next->name
   (gdb) p/x next->pml4

③ CR3 변경 전후 비교:
   (gdb) p/x $cr3          # 변경 전
   (gdb) n                  # pml4_activate() 실행
   (gdb) p/x $cr3          # 변경 후 — next->pml4의 물리 주소

④ TSS rsp0 갱신 확인:
   (gdb) n                  # tss_update() 실행
   (gdb) p/x tss->rsp0
   (gdb) p/x (uint64_t)next + 0x1000
   → 두 값이 동일해야 함

⑤ schedule() 전체 흐름에서 관찰:
   (gdb) b schedule
   (gdb) commands
     > p curr->name
     > p next->name
     > continue
     > end

Linux와의 구현 범위 비교

Linux에서는 switch_to() 매크로와 switch_mm() 함수가 대응하는 역할을 나누어 수행한다. switch_mm()이 CR3를 교체하고, switch_to() 내부에서 per-CPU TSS의 sp0 필드를 갱신한다. Linux는 코어마다 독립된 TSS를 유지하므로 각 코어의 context switch에서는 해당 코어의 TSS를 갱신한다. 따라서 PintOS의 시스템 전체 TSS 하나라는 전제를 Linux에 그대로 적용할 수 없다.

비교 항목PintOSLinux
TSS 개수시스템 전체 1개per-CPU 1개 (cpu_tss_rw)
rsp0 갱신 함수tss_update(next)load_sp0(tss, next_p) via __switch_to()
CR3 전환pml4_activate() → lcr3()switch_mm_irqs_off() → load_new_mm_cr3()
KPTI (Meltdown 대응)없음CR3를 user/kernel PML4 쌍으로 전환

스레드 t가 물리 주소 0x8004_4000에 할당되었다고 두면 값의 관계는 다음과 같다.

  • struct thread *t = 0x8004_4000
  • tss->rsp0 = 0x8004_4000 + 0x1000 = 0x8004_5000
  • 커널 스택은 0x8004_5000에서 아래로 성장
