세마포어 up unblock (Sema Up Unblock)

세마포어 up unblock (Sema Up Unblock)

sema_up()은 세마포어 값을 1 증가시키고, waiters에서 잠든 스레드가 있으면 하나를 READY 상태로 깨운다. 이 문서에서 다루는 PintOS 구현은 우선순위가 가장 높은 스레드를 먼저 깨운 뒤 선점이 필요한지도 확인한다.

세마포어 up unblock 구조

이 문서의 목표는 sema_up()이 세마포어 값을 증가시키고 대기 중인 스레드를 깨우는 과정과, 그 결과 선점이 일어나는 조건을 이해하는 것이다. 대기 큐(waiters)에 스레드가 있으면 우선순위가 가장 높은 스레드를 BLOCKED에서 READY로 전환한다. 이는 sema_down()에 대응하는 연산이다. 또한 인터럽트 핸들러 안에서도 호출할 수 있다는 점에서 sema_down()과 중요한 차이가 있다. value++을 수행한 뒤 선점 검사(check_preemption())를 거쳐, 깨어난 스레드의 우선순위가 현재 스레드보다 높으면 CPU를 양보한다.

상세 설명

추상 개념 (Signaling Synchronization)

세마포어의 V 연산은 Dijkstra가 처음 사용한 명칭으로, 여기서는 다음 계약으로 설명한다.

핵심 특성은 다음과 같다.

  • 호출한 스레드를 블록하지 않는다: value를 증가시키는 연산이므로 ISR에서도 사용할 수 있다.
  • producer-consumer에서는 producer 쪽 연산이다: 생산자가 자원을 내놓으면 대기 중인 소비자를 깨운다.
  • binary semaphore에서는 Lock release에 대응한다: 이 구현에서는 lock_release() 내부에서 sema_up()을 호출한다.

핵심 설계 결정

1. list_sort()와 list_insert_ordered()의 역할

sema_down()은 삽입할 때 list_insert_ordered()을 사용해 정렬 상태를 유지하지만, sema_up()은 스레드를 꺼내기 직전에 list_sort()을 수행한다. 대기 중에 priority donation 등으로 스레드의 우선순위가 달라질 수 있기 때문이다. 따라서 삽입 당시의 순서가 스레드를 깨우는 시점에도 유효하다고 단정하지 않고, 깨우기 직전에 다시 정렬한다.

2. unblock 이후의 value++

깨어난 스레드가 sema_down()의 while 루프에서 조건을 다시 검사할 때는 value > 0이 성립한다. value++를 먼저 수행한 뒤 unblock해도 같은 동작을 한다는 설명이 제시되어 있지만, 여기서 코드 순서가 의미하는 설계 의도까지는 구현만으로 확정하기 어렵다. 확인할 수 있는 사실은 unblock과 value++가 인터럽트가 비활성화된 임계 구역 안에서 실행된다는 점이다.

3. check_preemption() — 인터럽트 복원 후 실행

intr_set_level() 이후에 check_preemption()을 호출한다. 이 구현은 인터럽트를 복원한 다음 선점 여부를 검사하도록 실행 순서를 구성한다.

4. ISR에서 호출 가능

sema_up()에는 ASSERT(!intr_context())가 없다. 따라서 timer_interrupt 핸들러에서 세마포어 값을 올려 대기 중인 스레드를 깨울 수 있으며, 이는 timer_sleep() 구현에서 활용된다. 반면 sema_down()은 thread_block()을 호출하므로 ISR에서 사용할 수 없다.

QEMU 에뮬레이션

QEMU 관점에서 sema_up()은 주로 메모리를 조작하지만, 다음 경로에서는 하드웨어 에뮬레이션과 연결된다.

  1. cli/sti 에뮬레이션: intr_disable()의 cli 명령을 실행하면 QEMU TCG는 CPUX86State.eflags의 IF 비트를 지운다. 이 시점부터 sti까지 QEMU는 cpu_exec() 루프에서 인터럽트 주입을 보류한다. 따라서 sema_up의 critical section 동안 timer interrupt가 발생해도 즉시 guest에 전달되지 않는다.

  2. 메모리 접근: sema->value++와 list_sort()의 포인터 조작은 모두 softmmu를 거친다. guest VA를 PML4 walk로 변환해 host VA를 얻은 뒤 실제 메모리에 접근한다. sema->waiters 리스트의 list_elem 포인터는 각 스레드의 4 KB 페이지 안에 있으므로, TLB에 캐시되어 있다면 빠르게 처리된다.

  3. 선점 경로: check_preemption() → thread_yield() → schedule() → do_iret() 경로를 거쳐 마지막에 iretq 명령을 실행한다. QEMU는 이를 helper_iret_protected()로 에뮬레이션하고, 깨어난 스레드의 intr_frame에서 CS/SS/RSP/RIP를 복원한다.

  4. ISR 경로(timer_sleep): timer interrupt 핸들러에서 sema_up()을 호출하는 경우를 살펴보자. QEMU의 i8254 PIT 모델이 IRQ0을 발생시키고 i8259 PIC를 거쳐 guest CPU에 인터럽트를 주입한 상태에서 해당 코드가 실행된다. 이때 check_preemption()은 intr_context()가 true이므로 즉시 반환하고, 이후 intr_yield_on_return 플래그를 통해 인터럽트 핸들러가 끝난 뒤 yield한다.

관찰 시나리오

시나리오 1: producer-consumer에서 sema_up 호출

조건: Consumer(priority 40)는 sema_down으로 BLOCKED 상태이고, Producer(priority 31)가 sema_up을 호출한다.

1. Producer가 sema_up() 진입 (value=0, waiters=[Consumer])
2. intr_disable() — QEMU eflags IF=0
3. list_sort() — waiter 1개이므로 O(1)
4. list_pop_front() → Consumer
5. thread_unblock(Consumer) → ready_list에 삽입 (priority 40)
6. value++ → value=1
7. intr_set_level(old) — sti, IF=1 복원
8. check_preemption()
   - ready_list 선두: Consumer(40) > Producer(31) → thread_yield()
9. Producer → READY, Consumer → RUNNING
10. Consumer의 sema_down while 재검사: value=1 > 0 → value-- → 진행

시나리오 2: ISR에서 sema_up 호출(timer_sleep)

조건: Thread A(priority 35)는 timer_sleep()의 sema_down으로 BLOCKED 상태이며, timer interrupt에서 sema_up을 호출한다.

1. QEMU PIT IRQ0 발생 → i8259 PIC → guest #0x20 인터럽트
2. timer_interrupt() 핸들러 실행 (intr_context() = true)
3. Thread A의 wake_tick 도달 → sema_up(&A->timer_sema)
4. list_sort → thread_unblock(A) → ready_list 삽입
5. value++
6. check_preemption() → intr_context() true → 즉시 리턴 (yield 안 함)
7. timer_interrupt 종료 → intr_handler()가 yield_on_return 검사
8. A(35) > 현재(31)이면 intr_yield_on_return → schedule()
9. A가 RUNNING, sema_down while 재검사: value=1 → value-- → 깨어남
