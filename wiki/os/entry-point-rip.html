e_entry와 RIP 설정

e_entry와 RIP 설정

확인 범위: 이 문서는 ELF의 e_entry가 RIP로 전달되어 실행이 시작되는 일반 원리와 Linux·Windows·PintOS·QEMU에서의 구현 흐름을 설명한다. 다만 구체적인 코드 위치, 구조체 배치, 주소값, 버전별 동작 및 GDB·readelf 실행 기록과 성능 관련 판단은 해당 소스와 실행 환경에서 별도로 검증해야 한다.

한 줄 요약: ELF 헤더의 e_entry(시작 가상 주소)를 로더가 intr_frame.rip에 기록해, do_iret()로 유저 모드에 진입시키는 과정.

e_entry와 RIP 설정 차이

ELF 헤더의 e_entry 필드는 프로그램이 실행을 시작할 가상 주소를 담고 있다. OS의 로더가 ELF를 메모리에 적재한 뒤, 이 값을 intr_frame.rip에 기록하면, do_iret()로 유저 모드에 진입하는 순간 CPU의 RIP 레지스터가 이 주소를 가리키게 되어 프로그램의 첫 명령어가 실행된다. 이것이 “프로그램 적재 → 실행 시작” 체인의 마지막 단계다.

상세 설명

추상 개념 (CPU/MMU 하드웨어 규칙)

x86-64 CPU의 **RIP(Instruction Pointer)**는 “다음에 실행할 명령어의 가상 주소”를 가리킨다. iretq 명령어가 실행되면 스택에서 RIP 값을 pop하여 CPU에 설정하고, 그 주소부터 fetch-decode-execute 사이클이 시작된다.

ELF 파일 자체는 하드웨어와 무관한 포맷이지만, e_entry에 적힌 주소가 결국 하드웨어 RIP로 전달되는 흐름이 핵심이다:

%% ELF e_entry가 intr_frame.rip를 거쳐 CPU RIP로 전달되는 흐름
flowchart LR
  elf["ELF 파일<br/>e_entry: 0x400078<br/>디스크의 시작 가상 주소"]
  frame["커널 메모리<br/>if_.rip = 0x400078<br/>intr_frame에 복사"]
  cpu["CPU 하드웨어<br/>RIP = 0x400078<br/>첫 명령어 fetch"]
  elf --> frame
  frame --> cpu

실제 OS (Linux/Windows)

Linux의 execve() 시스템 콜에서:

  1. load_elf_binary()가 ELF 헤더를 파싱하여 e_entry를 읽는다.
  2. PT_INTERP가 있으면 커널은 주 실행 파일의 e_entry를 덮어쓰는 것이 아니라 interpreter를 별도로 적재하고 그 진입점으로 먼저 제어를 넘긴다. 동적 링커가 relocation과 library 적재를 마친 뒤 주 실행 파일의 원래 e_entry로 점프한다.
  3. 정적 링크 바이너리면 e_entry가 곧바로 pt_regs->ip에 설정된다.

Windows의 PE 포맷에서는 AddressOfEntryPoint 필드가 동일한 역할을 한다. ImageBase + AddressOfEntryPoint가 최종 RIP가 된다.

PintOS 구현

PintOS의 load() 함수(userprog/process.c)에서 ELF 적재의 마지막 단계:

이 한 줄이 ELF 적재 체인의 종착점이다. 전체 흐름:

QEMU 에뮬레이션

QEMU는 e_entry를 직접 처리하지 않는다. OS가 iretq를 실행하면 QEMU의 TCG가 해당 명령어를 번역하여 CPUX86State.eip(RIP)를 갱신하고, 다음 translation block을 e_entry 주소부터 시작한다.

GDB에서 e_entry → RIP 전달 과정 관찰하기:

QEMU TCG 관점에서의 흐름:

단계TCG 동작CPUX86State 변화
iretq 실행gen_helper_iret_real → 스택 pop 시뮬레이션env->eip = 0x400c10
TB 종료현재 Translation Block 종료lookup_tb 요청
새 TB 시작e_entry 주소(0x400c10)에서 새 TB 생성fetch → decode → execute
CPL 전환CS selector의 RPL=3으로 변경env->hflags CPL=3 반영

e_entry와 RIP 설정 값 추적

PintOS에서 유저 프로그램의 e_entry 값 실측:

프로그램마다 e_entry가 다른 이유: _start 심볼의 위치가 코드 크기에 따라 달라진다. 그러나 모두 0x400000 대역에 있다 — PintOS 링커 스크립트가 .text 섹션을 0x400000부터 배치하기 때문이다.

항목값근거
유저 프로그램 시작 대역0x400000링커 스크립트 .text 시작
e_entry 예시 (args-single)0x400c10_start = CRT 초기화 코드
e_entry 예시 (halt)0x400b56코드가 적어 _start가 더 앞
ELF 헤더 내 오프셋0x18~0x1f (8 bytes)uint64_t
KERN_BASE0x8004000000e_entry가 이 이상이면 pf

e_entry가 KERN_BASE 이상이면: 유저 모드(CPL=3)에서 커널 주소 접근 시도 → PTE의 user bit = 0 → pf(page fault) → 프로세스 종료.
