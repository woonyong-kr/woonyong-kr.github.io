Resident Page 복사 (fork SPT copy)

Resident Page 복사 (fork SPT copy)

한 줄 요약: fork로 SPT를 복제할 때, 물리 frame을 점유한 resident page(page->frame != NULL)를 자식 주소 공간에 반영하는 방식을 설명한다.

Resident Page 복사 흐름

이 문서에서 resident page는 부모의 SPT에 속한 페이지 중 현재 물리 frame을 점유한 페이지(page->frame != NULL)를 뜻한다. fork가 이 페이지를 자식 주소 공간에 반영하는 방법은 eager copy와 Copy-on-Write(COW)로 나뉜다. eager copy는 자식용 frame을 확보해 내용을 즉시 복사한다. COW는 부모와 자식이 같은 frame을 공유하다가 쓰기가 발생할 때 복사한다.

아래의 eager copy 설명은 spt_copy_loaded_page()에 제시된 처리 흐름을 풀어 쓴 것이다. 이 문서가 현재 구현으로 제시하는 anon_copy()는 COW 방식이므로, eager copy의 단계와 수치가 그대로 적용된다고 해석해서는 안 된다. 먼저 두 방식에 공통인 주소 매핑을 살펴본 뒤, eager copy의 코드 흐름과 현재 COW 구현을 차례로 비교한다.

상세 설명

주소 공간 복제와 페이지 매핑

fork의 주소 공간 복제는 하드웨어가 직접 수행하는 기능이 아니다. 이 문서의 설명에서는 CPU/MMU가 CR3가 가리키는 페이지 테이블을 따라 주소를 변환하며, OS가 부모의 페이지 테이블 엔트리를 순회해 자식에게 필요한 매핑을 만든다.

이 문서에 제시된 eager copy 모델은 resident page 하나를 다음 순서로 처리한다.

  1. palloc으로 자식용 물리 frame을 확보해 새 PFN(Physical Frame Number)을 얻는다.
  2. 자식 PML4에 upage → 새 frame 매핑을 설치하기 위해 pml4_set_page()를 호출한다.
  3. 부모 frame의 내용을 자식 frame으로 복사한다.

Linux와 COW

이 문서에서는 Linux의 fork()가 일반적으로 resident page를 즉시 복사하지 않고 **Copy-on-Write(COW)**를 사용한다고 설명한다.

  • 부모와 자식의 PTE에서 writable 비트를 제거한다.
  • 두 프로세스가 같은 물리 frame을 read-only로 공유한다.
  • 어느 한쪽이 쓰기를 시도해 page fault가 발생하면 그때 새 frame을 할당하고 내용을 복사한다.
  • struct page의 _mapcount와 _refcount로 공유 상태를 추적한다.

이 방식은 fork() 직후 exec()가 호출되어 기존 주소 공간이 폐기되는 상황에서 즉시 복사할 페이지를 줄이는 데 목적이 있다.

PintOS에서 페이지 유형을 나누는 흐름

이 문서에 제시된 supplemental_page_table_copy() 설명에서는 부모 SPT를 순회하면서 페이지 타입에 따라 복제 방법을 선택한다. resident page를 eager copy하는 경로는 자식 page 생성, frame 확보와 매핑, 내용 복사의 순서로 읽을 수 있다. UNINIT page와 swapped page는 별도의 경로로 분기한다.

페이지와 frame의 관계는 다음 설계 메모로 남아 있다.

page->frame->kva는 커널 가상 주소이므로 memcpy의 src와 dst로 사용할 수 있다. 이 문서의 eager copy 코드에서 복사 범위는 한 페이지 전체인 4096바이트(PGSIZE)다.

부모 page가 코드 세그먼트처럼 read-only라면 자식도 read-only로 매핑해야 한다. 따라서 vm_do_claim_page() 또는 pml4_set_page()를 호출할 때 부모와 같은 writable 플래그를 사용한다.

PintOS eager copy 코드

이 문서가 eager copy 함수로 제시한 코드는 spt_copy_loaded_page()다 (vm/vm.c:503).

코드는 다음 순서로 읽을 수 있다.

  1. 타입 보존 — page_get_type(page)로 VM_ANON 또는 VM_FILE을 얻고, 자식 page를 같은 타입으로 생성한다.
  2. 가드 조건 — page->frame == NULL이면 resident page가 아니므로 이 함수의 처리 대상에서 제외한다. 제시된 흐름에서는 spt_copy_page()가 UNINIT 타입을 먼저 분기한다.
  3. 자식 page 생성 — vm_alloc_page가 자식 SPT의 hash에 새 struct page를 삽입한다. 이 시점에는 아직 frame이 연결되지 않았다. 이는 page 타입이 UNINIT이라는 뜻이 아니라 claim 전이라는 뜻이다.
  4. 생성한 page 조회 — spt_find_page로 방금 삽입한 page를 dst에서 찾는다. 이 설명은 vm_alloc_page가 내부적으로 thread_current()->spt에 삽입한다는 전제를 따른다.
  5. frame 확보와 매핑 — vm_do_claim_page가 새 frame을 할당해 page->frame = frame으로 연결하고, pml4_set_page()로 자식 PML4에 매핑한다. 매핑에는 부모에서 전달된 page->writable 값이 사용된다.
  6. 내용 복사 — memcpy가 부모 frame->kva에서 자식 frame->kva로 4096바이트를 복사한다.

처리 중 실패하면 이미 복사한 page가 남을 수 있다. 문서의 예처럼 supplemental_page_table_copy()가 100개 page 중 73번째에서 OOM으로 false를 반환하면 앞서 복사한 72개 page의 frame과 SPT 엔트리가 정리 대상이 된다. 제시된 호출 흐름에서는 __do_fork()가 supplemental_page_table_kill()을 호출해 이를 정리한다.

QEMU에서 관찰할 대상

이 문서가 제시한 QEMU TCG 관찰 흐름은 다음과 같다.

  1. pml4_set_page()가 자식 페이지 테이블에 frame의 kva를 매핑하면 QEMU guest의 PTE가 갱신된다.
  2. COW에서는 부모와 자식의 PTE가 같은 물리 frame을 가리키며 writable=false로 설정된다.
  3. 이후 쓰기로 page fault가 발생하면 memcpy로 frame을 복사한다. 문서에서는 이 과정에서 TCG가 rep movsb 등을 host 명령어로 번역하고 메모리 접근마다 softmmu TLB lookup을 수행한다고 설명한다.
  4. QEMU 내부의 src kva와 dst kva는 address_space_rw()를 통해 RAMBlock(pc.ram)의 서로 다른 offset에 접근하는 것으로 설명되어 있다.

GDB에서 pml4_get_page(부모pml4, va)와 pml4_get_page(자식pml4, va)가 같은 kva를 반환한다면, 이 문서의 COW 모델에서는 두 page가 같은 frame을 공유하는 상태로 해석한다. 이는 아래 스크립트로 직접 관찰할 수 있는 점검 기준이며, 이 문서 자체가 실행 결과를 제시하는 것은 아니다.

현재 PintOS 구현으로 제시된 COW 흐름

앞의 eager copy 경로와 달리, 이 문서가 현재 PintOS 코드로 제시한 anon_copy()는 COW 방식을 사용한다. fork 시점에는 새 frame을 만들고 내용을 복사하는 대신 기존 frame을 공유한다. 부모와 자식의 매핑을 read-only로 만들고, 이후 쓰기 시점의 page fault에서 새 frame을 확보해 복사한다.

비교Eager Copy (기본 템플릿)COW (현재 구현)
fork 시 동작palloc + memcpy 즉시PTE writable 해제 + frame 공유
frame 수부모 + 자식 각각 N개공유하므로 N개 유지
write 시이미 별도 framepage fault → 그때 palloc + memcpy
exec 후 fork 비용N × 4 KB 낭비거의 0 (exec이 전부 버림)
구현 복잡도낮음높음 (ref_count, PTE writable 관리)
rollback 복잡도spt_remove_page만pml4_clear_page + owner 제거 + writable 복원

표의 계산 조건대로 부모에게 resident page가 100개 있고 각 페이지가 4 KB라면, eager copy가 복사하는 양은 100 × 4 KB = 400 KB다. 같은 조건에서 COW는 fork 시점에 page 내용을 복사하지 않는다. 이 계산은 두 방식의 차이를 설명하기 위한 조건부 비교이며, 실제 실행을 측정한 결과는 아니다.

현재 구현 코드 — anon_copy() 상세

이 문서가 제시한 anon_copy() (vm/anon.c:190)의 resident page 처리 흐름은 다음과 같다.

이 코드 조각에서는 자식 page를 만든 뒤 swapped 상태를 분기하고, resident frame이라면 부모와 자식의 매핑을 read-only로 조정한 후 owner를 추가한다.

  • memcpy가 없으며 새 frame을 만드는 대신 기존 frame을 공유한다.
  • ref_count == 1일 때 부모의 writable을 끈다. 문서의 설명에 따르면 이미 공유 중인 frame은 앞선 처리에서 read-only로 바뀐 상태다.
  • 처리에 실패하면 부모의 writable 상태를 복원해야 한다.
  • vm_frame_add_owner()가 ref_count++를 담당한다.

GDB 관찰 스크립트

다음 스크립트는 frame 공유, read-only 매핑, 참조 수 변화와 COW 복사를 관찰하기 위한 것이다. 스크립트의 출력은 예상 관찰 지점을 나타내며, 이 문서에는 실제 실행 결과가 포함되어 있지 않다.

이 값들은 입력 문서가 제시한 eager copy 코드와 계산 조건을 설명한 것이다. 실제 실행을 측정한 결과로 보아서는 안 된다.

Eager copy에서는 자식이 받은 frame이 부모와 다른 새 물리 주소를 갖는다. 가상 주소(va)는 같게 매핑할 수 있지만 물리 주소는 서로 다르다.

  • 부모: va=0x400000 → PFN=0x1A3 → PA=0x1A3000
  • 자식: va=0x400000 → PFN=0x2F7 → PA=0x2F7000
  • memcpy 직후 두 frame의 4096바이트 내용은 같다.

이 주소는 eager copy의 관계를 설명하기 위한 예시다. 현재 COW 구현처럼 frame을 공유하는 동안에는 적용되지 않는다.

순서도

다음 순서도는 현재 COW 구현이 아니라 앞에서 설명한 eager copy 경로를 나타낸다.

flowchart TD
    A[supplemental_page_table_copy 시작] --> B[부모 SPT 순회: 다음 page]
    B --> C{page->frame != NULL?}
    C -->|YES: resident| D[자식 SPT에 page 구조체 생성]
    D --> E[vm_do_claim_page: palloc + PML4 매핑]
    E --> F{할당 성공?}
    F -->|YES| G["memcpy(child kva, parent kva, PGSIZE)"]
    G --> B
    F -->|NO| H[return false — OOM]
    C -->|NO: UNINIT| I[aux deep copy 또는 file reopen]
    I --> B
    C -->|NO: swapped| J[swap slot snapshot 복사]
    J --> B
    B -->|순회 완료| K[return true]
