프로세스 자원 정리

프로세스 자원 정리

확인 범위: 이 문서는 프로세스 종료 시 VM 자원을 회수하는 일반 원리와 순서 선택 기준을 설명하고 Linux와 PintOS의 구현 흐름을 비교한다. 제시된 코드 좌표, 버전별 자료구조, GDB·QEMU 관찰 예시, 자원 사용량과 장애 증상은 실제 소스와 실행 기록 또는 측정으로 별도 검증해야 한다.

프로세스가 끝날 때 VM 자원은 그냥 사라지지 않는다. process_cleanup()은 frame, swap slot, mmap dirty page, SPT entry, page table을 순서대로 회수해야 한다.

프로세스 자원 정리 상태

프로세스 종료 경로에는 열린 파일 닫기, 자식 상태 정리, exit status 보존도 함께 들어 있다. 그중 VM 자원 회수는 순서가 특히 중요하다. dirty mmap 페이지를 파일에 쓰기 전 PML4를 없애면 dirty bit를 확인할 수 없고, 현재 CR3가 가리키는 페이지 테이블을 먼저 해제하면 다음 메모리 접근에서 바로 무너진다.

상세 설명

추상 개념 (OS 일반 원칙)

흐름 UML — process_exit() → process_cleanup()이 1단계 supplemental_page_table_kill(&curr->spt)로 SPT의 각 struct page를 타입별(VM_ANON/VM_FILE/VM_UNINIT)로 destroy한 뒤, 2단계에서 curr->pml4 = NULL → pml4_activate(NULL) → pml4_destroy(pml4) 순으로 페이지 테이블을 해제한다.

핵심 질문: 왜 SPT kill이 PML4 destroy보다 먼저인가? dirty bit 확인과 file-backed writeback이 아직 PTE를 필요로 하기 때문이다.

회수 순서의 원칙: 참조자를 먼저 끊고, 자원을 해제한다.

  1. 먼저 SPT의 각 page를 순회하며 page 유형별 cleanup 수행
  2. file-backed dirty 페이지는 디스크에 writeback
  3. anonymous page의 swap slot 해제
  4. frame 반환 (palloc_free_page)
  5. 마지막으로 PML4 페이지 테이블 자체를 파괴

PML4를 먼저 파괴하면, 아직 writeback하지 않은 dirty mmap 페이지의 가상 주소를 통해 내용을 읽을 수 없다.

실제 OS (Linux)

Linux에서 exit_mm() → mmput() → exit_mmap() 순으로 VMA(Virtual Memory Area)를 순회한다:

단계함수동작
VMA 순회unmap_vmas()각 VMA의 PTE를 해제, dirty page writeback
anonymous pagefree_pages_and_swap_cache()frame 반환 + swap 엔트리 해제
file-backed pagepage_remove_rmap() → writebackdirty이면 파일에 기록
페이지 테이블free_pgtables()PML4/PUD/PMD/PTE 페이지 해제
mm_structmmdrop()참조 카운트 0이면 mm_struct 해제

Linux는 reverse-mapping(rmap)으로 frame→page table entry 역추적이 가능하므로, frame을 해제할 때 모든 PTE를 찾아 unmap할 수 있다.

PintOS 구현

PintOS의 VM 자원 회수는 process_exit() 안에서 두 단계로 진행된다:

1단계: supplemental_page_table_kill()

spt_kill()은 SPT에 등록된 모든 struct page를 순회하며 페이지 유형별 정리를 수행한다:

Anonymous Page (VM_ANON):

상태회수 동작
Resident (frame에 존재)palloc_free_page(frame->kva) → frame 반환
Swapped (swap slot에 존재)swap_free(slot_no) → swap bitmap에서 slot 해제
UNINIT (lazy, 아직 fault 안 됨)aux 메모리만 free, frame/swap 없음

File-backed Page (VM_FILE):

상태회수 동작
Resident + dirtyfile_write_at() → 파일에 writeback 후 frame 반환
Resident + cleanframe 반환만 (파일과 동일하므로 writeback 불필요)
UNINIT (lazy)aux만 free, 파일 I/O 없음

Dirty 판단:

pml4_is_dirty()는 PML4 → … → PTE를 걸어가서 dirty bit(bit 6)를 확인한다. 이것이 PML4를 SPT보다 나중에 파괴해야 하는 이유다 — dirty 검사를 위해 PTE가 아직 유효해야 한다.

2단계: PML4 파괴

(a)가 (c)보다 먼저인 이유: 타이머 인터럽트가 발생하면 process_activate()가 curr->pml4로 CR3를 재설정한다. 이미 파괴된 PML4를 CR3에 로드하면 즉시 page fault → 커널 패닉.

(b)가 (c)보다 먼저인 이유: 현재 CPU가 사용 중인 페이지 테이블을 해제하면, 다음 메모리 접근에서 TLB miss → 이미 해제된 PTE 참조 → 커널 패닉. pml4_activate(NULL)이 CR3를 base_pml4(커널 전용)로 전환하여 이를 방지.

최악의 경우 자원 사용량 예제

프로세스가 8 MB의 anonymous 메모리 + 4 MB mmap file을 사용한다면:

  • frame: (8MB + 4MB) / 4KB = 3072개 물리 페이지
  • swap slot: evict 시 최대 2048개 (anonymous만 swap)
  • PTE: 3072 엔트리 → 약 6~7 PT 페이지 + PDPT/PD/PML4
  • SPT entry: 3072개 struct page

QEMU 에뮬레이션

QEMU 관점에서 프로세스 종료의 VM 자원 회수는 다음과 같이 보인다:

  1. dirty mmap writeback: file_write_at() → inode_write_at() → disk_write() → IDE PIO → QEMU가 I/O port(0x1F0~0x1F7) 접근을 가로채 호스트 파일에 pwrite()

  2. swap slot 해제: bitmap 조작만 이루어지므로 QEMU 측에서는 일반 메모리 store로 보임. swap disk에 대한 추가 I/O는 없음(해제된 slot의 데이터를 지울 필요 없음)

  3. frame 반환: palloc_free_page()는 user pool bitmap의 비트를 clear. QEMU의 RAMBlock 메모리는 그대로 유지되며, 다음 palloc_get_page()에서 같은 guest PA가 재사용됨

  4. PML4 파괴: pml4_destroy()가 페이지 테이블 페이지를 palloc_free_page()로 반환. CR3 전환 시 QEMU TCG의 SoftMMU TLB가 flush됨

QEMU 관찰 포인트게스트 동작QEMU 측 동작
dirty writebackdisk_write(hd0:0, sector, buf)IDE model → pwrite(host_fd, buf, 512, sector×512)
CR3 전환pml4_activate(NULL) → lcr3(base_pml4)SoftMMU TLB 전체 flush
frame 재사용palloc_get_page(PAL_USER|PAL_ZERO)같은 GPA, memset 0으로 보임
