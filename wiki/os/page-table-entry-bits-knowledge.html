페이지 테이블 엔트리 비트 — CPU가 주소 변환 중에 읽고 쓰는 플래그들

한 줄 요약: 페이지 테이블 엔트리(PTE)의 하위 12비트에는 Present, Writable, User, Accessed, Dirty 플래그가 있다. CPU는 주소 변환 때 이 비트들을 읽고, OS는 이 비트를 설정·해제하여 메모리 보호와 페이지 교체 정책을 구현한다.

페이지 테이블 엔트리 비트 문제

x86-64 CPU는 가상 주소를 물리 주소로 변환할 때 4단계 페이지 테이블을 걸어간다. 각 단계의 엔트리는 64비트인데, 상위 비트는 다음 테이블(또는 물리 프레임)의 주소를 담고, 하위 12비트는 플래그다. CPU는 이 플래그만 보고 “이 페이지에 접근해도 되는가?”, “쓰기를 허용하는가?”, “유저 모드에서 접근 가능한가?”를 판단한다. 플래그가 규칙에 맞지 않으면 CPU는 즉시 pf(Page Fault) 예외를 발생시킨다.

이 비트들을 모르면 page fault가 왜 발생했는지, OS가 어떤 기준으로 페이지를 교체하는지 이해할 수 없다.

페이지 테이블 엔트리 비트 상태

PTE 64비트 구조

PTE 하나는 64비트다. 상위 비트에 물리 주소, 하위 12비트에 플래그를 담는다.

주소와 플래그를 손으로 분리하는 예시

4KB 페이지에서 다음 PTE를 해석해 보자.

0x067 = 0x040 + 0x020 + 0x004 + 0x002 + 0x001이므로, 이 엔트리는 Present, Writable, User, Accessed, Dirty 비트가 모두 설정된 0x12345000 프레임을 가리킨다.

가상 주소가 0x8048123이면 페이지 내부 offset은 0x123이다. 따라서 이 PTE가 최종 PT 엔트리일 때 물리 주소는 다음과 같다.

여기서 PTE의 하위 12비트는 플래그이고, 가상 주소의 하위 12비트는 페이지 내부 바이트 위치라는 점을 구분해야 한다.

5개 핵심 플래그

  • P (Present, 비트 0) — 이 엔트리가 유효한 매핑을 가지고 있는가?

    • 1이면 매핑 존재. CPU가 다음 단계로 진행한다.
    • 0이면 매핑 없음. CPU가 즉시 pf를 발생시킨다. 나머지 비트는 무시된다.
    • OS는 swap out한 페이지의 P 비트를 0으로 만들어 “물리 메모리에 없음”을 표시한다.

  • W (Writable, 비트 1) — 쓰기가 허용되는가?

    • 1이면 읽기/쓰기 모두 가능.
    • 0이면 읽기 전용. 쓰기 시도 시 pf 발생. error code에 write 플래그가 설정된다.
    • Copy-on-Write 구현에서 공유 페이지를 읽기 전용으로 매핑할 때 사용한다.

  • U (User, 비트 2) — 유저 모드(CPL 3)에서 접근 가능한가?

    • 1이면 유저/커널 모두 접근 가능.
    • 0이면 커널 전용. 유저 모드 접근 시 pf 발생.
    • 커널 주소 공간의 페이지는 U = 0으로 설정하여 유저 프로그램이 커널 메모리를 읽지 못하게 한다.

  • A (Accessed, 비트 5) — 이 페이지에 접근한 적이 있는가?

    • CPU가 읽기든 쓰기든 이 페이지에 접근하면 자동으로 1로 설정한다.
    • OS는 이 비트를 주기적으로 0으로 초기화하고, 다시 1이 되었는지 확인하여 “최근에 사용된 페이지”를 판별한다.
    • Clock 알고리즘이 교체 대상을 고를 때 이 비트를 참조한다.

  • D (Dirty, 비트 6) — 이 페이지에 쓰기가 발생했는가?

    • CPU가 이 페이지에 쓰기를 수행하면 자동으로 1로 설정한다.
    • OS가 페이지를 evict할 때, D = 1이면 디스크에 내용을 먼저 써야 한다(writeback). D = 0이면 그냥 버려도 된다.
    • file-backed 페이지에서 D 비트가 1이면 file_write_at()으로 원본 파일에 변경 사항을 반영해야 한다.

P 비트가 0이면 나머지는 의미 없다

이 규칙이 중요하다. P = 0인 엔트리에서 CPU는 W, U, A, D를 전혀 보지 않는다. 그래서 OS는 P = 0인 엔트리의 나머지 비트에 swap slot 번호 같은 커널 메타데이터를 저장하기도 한다.

계층별 적용

4단계 테이블(PML4 → PDPT → PD → PT)의 모든 엔트리에 같은 플래그 구조가 적용된다. 단, D(Dirty) 비트는 최종 PT 엔트리에서만 의미가 있다. CPU는 주소 변환 경로의 모든 단계에서 P, W, U를 확인하며, 어느 단계에서든 실패하면 pf가 발생한다.

왜 플래그가 하위 12비트에 들어가는가?

페이지 크기 = 4KB = 4096바이트 = 2의 12제곱 페이지 내부 오프셋을 표현하는 데 필요한 비트 수 = log2(4096) = 12비트

물리 프레임은 항상 4KB 경계에 정렬된다. 그래서 프레임 시작 주소의 하위 12비트는 언제나 0이다. 비어 있는 이 12비트를 버리지 않고 플래그 자리로 재사용한다.

PTE 하나에 “물리 프레임 주소 + 플래그”를 64비트 안에 함께 담을 수 있는 이유는, 4KB 정렬 덕분에 하위 12비트가 항상 0으로 남아 낭비되기 때문이다.

실제 OS와의 차이 (Linux/Windows vs PintOS)

같은 x86-64 하드웨어를 쓰므로 P, W, U, A, D 비트의 하드웨어 의미는 Linux, Windows, PintOS가 모두 동일하다. 차이는 OS가 나머지 비트까지 얼마나 활용하느냐다.

  • Linux 기준
    • 하드웨어 PTE 비트를 arch/x86/include/asm/pgtable_types.h에 _PAGE_PRESENT, _PAGE_RW, _PAGE_USER, _PAGE_ACCESSED, _PAGE_DIRTY로 정의한다.
    • 비트 63의 NX(No-Execute) 비트를 적극 사용해 데이터 페이지에서 코드 실행을 막는다(W^X 보호).
    • 커널 전역 페이지에 G(Global) 비트를 설정해 주소 공간 전환 때 TLB에서 지워지지 않게 한다.
    • A, D 비트는 LRU 기반 페이지 회수(active/inactive 리스트)에 쓴다.
  • Windows 기준
    • 동일한 하드웨어 비트를 쓰며 NX, G 비트도 사용한다.
    • PFN(Page Frame Number) 데이터베이스가 프레임 상태를 추적하고, P = 0인 PTE에 prototype PTE나 transition 상태 같은 소프트웨어 정보를 담는다.
  • PintOS 기준
    • P, W, U, A, D 다섯 비트만 쓴다. NX, G, PWT, PCD 비트는 다루지 않는다.
    • 페이지 교체가 단순 Clock 알고리즘이라 A 비트만 참조한다.
    • 보호 모델이 단순해 W^X 같은 정책이 없다.

하드웨어 비트의 의미는 셋 다 같지만, PintOS는 학습을 위해 최소 집합만 쓰고 실제 OS는 보안과 성능을 위해 NX, Global 같은 추가 비트까지 동원한다.

QEMU는 A, D 비트를 어떻게 설정하나

“CPU가 접근하면 A 비트를, 쓰면 D 비트를 자동으로 1로 만든다”는 동작은 실제 하드웨어에서는 MMU가 한다. PintOS는 QEMU 위에서 도므로, 이 자동 설정은 QEMU가 소프트웨어로 흉내 낸다.

QEMU TCG는 게스트 가상 주소를 변환할 때 게스트 페이지 테이블을 직접 걸어간다(page table walk). 이 과정에서 접근한 엔트리에 A 비트를, 쓰기 접근이면 D 비트를 써넣는다.

소스: excp_helper.c

PintOS의 pml4_is_accessed()가 읽는 A 비트는 이렇게 QEMU가 써넣은 값이다. PintOS 입장에서 “하드웨어가 설정한 것처럼 보이는” 비트의 실체는 QEMU ptw_setl() 호출이다.

페이지 테이블 엔트리 비트 코드

PTE 플래그 정의

PTE에서 물리 주소를 꺼내려면 PTE_ADDR(pte) 매크로로 하위 12비트를 잘라낸다. 물리 주소는 항상 4KB 정렬이므로 하위 12비트가 0이어야 하고, 그 자리에 플래그가 들어가는 것이다.

매핑 설정 — pml4_set_page()

새 매핑을 만들 때 물리 주소에 PTE_P | PTE_U를 OR로 합치고, rw가 true면 PTE_W도 추가한다. A, D 비트는 0으로 시작하며, CPU가 접근/쓰기 시점에 자동으로 1로 설정한다.

매핑 해제 — pml4_clear_page()

P 비트를 0으로 만들면 이 가상 주소에 대한 다음 접근 시 pf가 발생한다. invlpg는 TLB에 캐시된 이전 변환을 무효화한다. TLB에 옛 매핑이 남아있으면 CPU가 이미 P = 0인 엔트리를 무시하고 옛 물리 주소로 접근할 수 있기 때문이다.

A, D 비트 조회와 설정 — 페이지 교체에서의 활용

PintOS의 Clock 알고리즘(vm_get_victim())은 pml4_is_accessed()로 A 비트를 확인한다. A = 1이면 “최근 사용됨”이므로 A를 0으로 초기화하고 다음 프레임으로 넘어간다. A = 0이면 “최근 사용 안 됨”이므로 교체 대상으로 선택한다. D 비트도 같은 패턴으로 pml4_is_dirty() / pml4_set_dirty()로 조회·설정한다.

page fault에서 error code와 PTE 비트의 관계

%% page fault error code와 PTE 비트 관계
flowchart LR
  cpu_pte["CPU가 PTE를 읽음<br/>P = 0?<br/>W = 0 + 쓰기?<br/>U = 0 + 유저모드?"]
  error_code["error code 생성<br/>not_present = true<br/>write = true<br/>user = true"]
  vm_fault["vm_try_handle_fault()<br/>복구 가능한지 판단"]
  cpu_pte --> error_code
  error_code --> vm_fault

CPU는 pf 발생 시 error code를 스택에 push한다. PintOS의 page_fault() 함수는 이 error code를 분석하여 not_present, write, user 세 불리언을 vm_try_handle_fault()에 전달한다. not_present가 true면 아직 매핑이 없는 경우(lazy load, stack growth)이고, false면 매핑은 있지만 권한 위반(write protect fault)이다.

정리

PTE의 하위 12비트는 CPU가 주소 변환 중에 하드웨어적으로 검사하는 플래그다. P 비트가 매핑 존재 여부를, W 비트가 쓰기 권한을, U 비트가 유저 접근 권한을 결정한다. A, D 비트는 CPU가 자동으로 설정하며, OS는 이를 읽어 페이지 교체 정책을 수행한다. PintOS에서는 pte.h에 매크로로 정의하고, mmu.c의 함수들이 이 비트를 조작한다.
