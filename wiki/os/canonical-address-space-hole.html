x86-64 Canonical Address와 비정규 홀

x86-64 Canonical Address와 비정규 홀

확인 범위: 이 문서는 x86-64 canonical address의 일반 원리와 주소 공간 분할 기준을 설명하고, Linux·PintOS·QEMU에 관한 내용은 입력에 제시된 특정 구현 설명과 코드 좌표를 바탕으로 한 사례로 다룬다. 실제 적용 여부와 세부 동작, 버전별 차이, 실행 결과 및 성능에 관한 판단은 해당 코드·버전·실행 기록·측정 자료를 별도로 확인해야 한다.

한 줄 요약: x86-64 canonical 규칙은 유효한 주소 표현과 중간 hole을 정하고, 실제 유저/커널 격리는 OS의 매핑 정책과 PTE U/S 권한이 결정한다.

x86-64 Canonical 차이

PintOS가 사용하는 x86-64 4-level paging에서는 하위 48비트를 주소 변환에 사용하고 상위 bit[63:48]은 bit 47의 **부호 확장(sign extension)**이어야 한다. 이 규칙을 만족하는 주소를 canonical address라 한다. LA57 5-level paging에서는 기준이 bit 56으로 바뀐다. non-canonical 주소 접근은 gp(General Protection) 예외를 일으킨다.

상세 설명

추상 개념 (CPU 하드웨어 규칙)

x86-64에서 가상 주소의 구조:

%% x86-64 가상 주소의 bit 구획
flowchart LR
  address["63..48 &#124; 47..12 &#124; 11..0<br/>sign ext<br/>(16 bit) &#124; 실제 주소 변환 사용 (48 bit)<br/>PML4[9] PDPT[9] PD[9] PT[9] &#124; page ofs<br/>(12 bit)"]

Canonical 규칙: bit 63~48은 모두 bit 47과 같아야 한다.

  • bit 47 = 0 → bit 63~48 = 0x0000 → 유효 범위: 0x0000_0000_0000_0000 ~ 0x0000_7FFF_FFFF_FFFF
  • bit 47 = 1 → bit 63~48 = 0xFFFF → 유효 범위: 0xFFFF_8000_0000_0000 ~ 0xFFFF_FFFF_FFFF_FFFF

이 두 범위 사이의 0x0000_8000_0000_0000 ~ 0xFFFF_7FFF_FFFF_FFFF는 non-canonical hole이다. 이 영역은 어떤 페이지 테이블로도 매핑할 수 없다.

영역시작 주소끝 주소크기
하반부 (canonical low)0x0000_0000_0000_00000x0000_7FFF_FFFF_FFFF128 TB
non-canonical hole0x0000_8000_0000_00000xFFFF_7FFF_FFFF_FFFF~16 EB
상반부 (canonical high)0xFFFF_8000_0000_00000xFFFF_FFFF_FFFF_FFFF128 TB

많은 OS가 canonical low를 유저 영역, canonical high를 커널 영역으로 배치하지만 이는 OS의 선택이다. hole은 유효하지 않은 주소 표현에 gp를 일으킬 뿐 privilege 격리를 제공하지 않는다. 실제 접근 통제는 page mapping과 PTE의 U/S·R/W·NX 같은 권한 bit가 담당한다.

5-Level Paging (LA57)

최신 CPU는 5단계 페이지 테이블(PML5)을 지원하며, 이때 유효 비트가 57비트로 확장된다. canonical 규칙은 bit 63~57이 bit 56의 부호 확장이어야 하는 것으로 바뀌고, 각 반은 64 PB로 확장된다. PintOS와 현재 대부분의 OS는 4-level paging(48비트)을 사용한다.

실제 OS (Linux)

Linux는 canonical 주소 규칙에 기반하여 주소 공간을 분할한다:

%% Linux canonical 주소 공간 분할
flowchart TD
  low["0x0000_0000_0000_0000 .. 0x0000_7FFF_FFFF_FFFF<br/>유저 공간 (128 TB)<br/>코드·데이터·힙·mmap·스택<br/>TASK_SIZE_MAX = 0x0000_7FFF_FFFF_F000"]
  hole["0x0000_8000_0000_0000 .. 0xFFFF_7FFF_FFFF_FFFF<br/>non-canonical hole (~16 EB)<br/>접근 불가 영역"]
  high["0xFFFF_8000_0000_0000 .. 0xFFFF_FFFF_FFFF_FFFF<br/>커널 공간 (128 TB)<br/>direct mapping: PAGE_OFFSET = 0xFFFF_8880_0000_0000<br/>vmalloc·커널 text/data"]
  low -->|canonical 경계| hole
  hole -->|상위 canonical 영역| high

Linux에서 TASK_SIZE_MAX가 정확히 0x0000_7FFF_FFFF_F000인 이유: canonical low 영역의 끝에서 한 페이지를 빼서, 유저 코드가 실수로 canonical 경계를 넘어 non-canonical 주소에 접근하는 것을 방지한다.

Linux 커널의 직접 매핑 시작점 PAGE_OFFSET는 canonical high 영역 안에 있되, hole과 일정 거리를 둔다. 이 사이의 guard 영역이 커널 코드 버그로 인한 잘못된 포인터 역참조를 잡는다.

PintOS 구현

PintOS는 canonical 주소 규칙을 단순화하여 사용한다:

%% PintOS 주소 공간 단순화
flowchart TD
  user["0x0000_0000_0000_0000 .. KERN_BASE-1<br/>PintOS 정책상 유저 범위<br/>실제 코드·stack은 훨씬 낮은 일부만 사용"]
  kernel["KERN_BASE = 0x0000_0080_0400_0000<br/>같은 canonical low 안의 커널 1:1 mapping<br/>supervisor mapping으로 보호"]
  low_rest["남은 canonical low<br/>대부분 미매핑"]
  hole["non-canonical hole<br/>48비트 canonical 규칙에서 생기는 중간 공백"]
  high["canonical high<br/>PintOS에서는 사용하지 않음"]
  user -->|KERN_BASE 경계는 OS 정책| kernel
  kernel --> low_rest
  low_rest --> hole
  hole --> high

KERN_BASE = 0x8004000000의 의미:

0x8004000000은 canonical low 영역 안에 있다 (bit 47 = 1이 아님). 이것은 PintOS가 48비트 canonical 규칙과는 다르게, 더 낮은 주소에서 유저/커널을 나누기 때문이다.

분해하면:

  • 0x80_0000_0000 = 512 GB = PML4 index 1의 시작
  • 0x04_0000_0000 = 16 GB 오프셋

즉 KERN_BASE는 PML4[1] 영역의 16GB 지점이다. PML4[0]이 유저 영역, PML4[1] 이상이 커널 영역이라는 단순한 분할이다.

이 분할이 pml4_destroy()에서 pml4[0]만 처리하는 이유이기도 하다.

검사 함수판단 기준용도
is_user_vaddr()addr < 0x8004000000syscall에서 유저 포인터 검증
is_kernel_vaddr()addr >= 0x8004000000커널 전용 함수에서 인자 검증

PintOS가 canonical high 대신 canonical low 안에서 분할하는 이유: PintOS는 물리 메모리가 최대 ~512 MB이고, 단순한 1:1 매핑(PA + KERN_BASE = KVA)을 사용한다. 512 GB(PML4 index 1 시작)이면 물리 메모리 전체를 넉넉히 매핑할 수 있다. Linux처럼 128TB 유저 공간이 필요 없으므로, 복잡한 canonical high 매핑을 쓸 이유가 없다.

QEMU 에뮬레이션

QEMU TCG는 canonical address 검사를 x86 명령어 에뮬레이션의 일부로 수행한다:

  1. 메모리 접근 명령어 실행 시, 주소가 canonical인지 확인
  2. non-canonical이면 raise_exception(env, EXCP0D_GPF) → gp(0) 주입
  3. 이 검사는 SoftMMU TLB lookup 이전에 수행됨
%% QEMU non-canonical 주소 #GP 흐름
flowchart LR
  guest["Guest 명령어<br/>mov rax, [0x0001_0000_0000_0000]"]
  check["QEMU 주소 검사<br/>bit 47 = 0<br/>bit 48..63 != 0"]
  gpf["non-canonical 감지<br/>raise_exception(env, EXCP0D_GPF)"]
  inject["x86_cpu_do_interrupt()<br/>#GP(0) 주입"]
  handler["Guest OS GPF handler<br/>PintOS는 PANIC"]
  guest -->|메모리 접근| check
  check -->|canonical 위반| gpf
  gpf -->|#GP 준비| inject
  inject -->|예외 전달| handler

PintOS 유저 프로그램이 canonical 규칙을 위반할 일은 거의 없다. 유저 주소가 0x47480000 이하이므로 bit 47은 항상 0이고, 상위 비트도 0이라 canonical이 보장된다.

유저 프로그램은 128 TB의 0.0001%도 사용하지 않는다. 이 거대한 빈 공간은 미래 확장성을 위한 여유다.

PML4 index와 주소 범위

PML4 index는 가상 주소의 bit 47:39에서 추출된다:

PML4 index시작 주소끝 주소PintOS 용도
00x00_0000_00000x7F_FFFF_FFFF유저 영역 (512 GB)
10x80_0000_00000xFF_FFFF_FFFF커널 시작, KERN_BASE 포함
20x100_0000_00000x17F_FFFF_FFFF미사용
………미사용
2550x7F80_0000_00000x7FFF_FFFF_FFFFcanonical low 끝
2560xFFFF_8000_0000_00000xFFFF_807F_FFFF_FFFFcanonical high 시작
………canonical high; PintOS에서는 미사용
5110xFFFF_FF80_0000_00000xFFFF_FFFF_FFFF_FFFFcanonical high 마지막 512 GB

PML4 index는 9비트라 0511만 존재한다. index 256511은 bit 47이 1이므로 주소를 64비트로 표현할 때 상위 bit를 1로 부호 확장한다. non-canonical hole은 별도 PML4 index가 아니라 이 부호 확장 규칙을 어긴 64비트 표현들이다.
