AWS EC2, ALB, Auto Scaling 실습 재도전 가이드

AWS EC2, ALB, Auto Scaling 실습 재도전 가이드

수동으로 켜던 서버 한 대를 AMI와 launch template으로 재사용 가능한 이미지로 만들고, ALB와 Auto Scaling이 여러 대를 함께 운영하게 넘겨 보는 실습이다.

이 실습은 “서버 한 대를 수동으로 켜는 것”에서 “서버 이미지를 만들고, 부하분산기와 Auto Scaling이 같은 서버를 여러 대 운영하게 하는 것”으로 넘어가는 과정이다.

먼저 public subnet에 EC2 한 대를 띄워 웹 서버 이미지를 만든다. 그다음 AMI와 launch template을 이용해 private subnet의 Auto Scaling Group이 같은 웹 서버를 자동으로 만들게 한다. 사용자는 EC2에 직접 접근하지 않고 ALB DNS를 통해 웹 서버에 접속한다.

EC2, ALB, Auto Scaling이 필요한 이유

EC2만으로도 서버 한 대를 만들 수 있다. 하지만 이 구성만으로는 장애와 트래픽 증가에 대응하기 어렵다. ALB는 사용자의 HTTP 요청을 여러 target으로 나눠 보내고, Auto Scaling은 원하는 서버 수를 유지하면서 지표에 따라 서버 수를 늘리거나 줄인다.

AMI와 launch template은 새 서버의 구성을 반복할 수 있게 만든다. AMI에는 서버의 디스크 상태를 담고, launch template에는 사용할 AMI, instance type, security group, IAM Instance Profile과 같은 생성 설정을 지정한다.

AWS EC2, ALB, Auto Scaling 요청 흐름

ALB는 외부 HTTP 요청을 받는 지점이다. target group은 ALB가 요청을 보낼 대상 목록이고, Auto Scaling Group은 target group에 들어갈 EC2 인스턴스 수를 계속 유지한다. launch template은 Auto Scaling Group이 새 인스턴스를 만들 때 참고하는 설계도다.

1단계: 웹 서버용 EC2 만들기

  • EC2 인스턴스
    • 이름: Web server for custom AMI
    • 인스턴스 타입: t2.micro
    • 키 페어: 없음
    • VPC: VPC-Lab
    • subnet: public subnet VPC-Lab-subnet-public1-ap-northeast-2a
    • Auto-assign Public IP: enabled
    • IAM instance profile: 나중에 Systems Manager나 Secrets Manager 접근에 쓸 profile
  • Security Group
    • 이름: Immersion Day - Web Server
    • inbound: HTTP 80 from My IP
    • 운영 환경에서는 My IP도 최소화해야 하지만, 실습에서는 웹 서버 확인을 위해 쓴다.
  • Metadata
    • IMDSv2 only로 둔다.
    • 인스턴스 메타데이터 접근을 더 안전하게 만드는 기본 습관이다.
  • User data
    • 웹 서버 패키지를 설치한다.
    • 실습 애플리케이션 ZIP을 내려받는다.
    • Apache HTTP server를 시작한다.

user data가 실패하면 웹 서버가 떠 있어도 페이지가 열리지 않는다. 이때는 EC2의 system log, /var/log/cloud-init-output.log, HTTP server 상태를 확인한다.

2단계: AMI 만들기

  • AMI
    • 이름: Web Server v1
    • 설명: LAMP web server AMI

AMI는 현재 EC2의 디스크 상태를 이미지로 저장한 것이다. Auto Scaling은 매번 패키지를 새로 설치하는 대신 이 AMI를 바탕으로 같은 서버를 만든다.

3단계: ALB와 Target Group 만들기

  • Application Load Balancer
    • 이름: Web-ALB
    • scheme: internet-facing
    • subnet: public subnet 2개
    • listener: HTTP 80
  • ALB Security Group
    • 이름: web-ALB-SG
    • inbound: HTTP 80 from Anywhere IPv4
  • Target Group
    • 이름: Web-TG
    • target type: instances
    • protocol: HTTP
    • health check: HTTP

ALB는 public subnet에 놓지만, ALB가 요청을 보내는 target EC2는 private subnet에 둘 수 있다. 사용자는 ALB를 통해 접속하고 실제 웹 서버는 인터넷에 직접 노출하지 않는 구조다.

4단계: Launch Template 만들기

  • Launch Template
    • 이름: Web
    • 설명: Immersion Day Web Instances Template - Web only
    • AMI: Web Server v1
    • instance type: t2.micro
    • key pair: 없음
    • security group: ASG-Web-Inst-SG
    • tag: Name=Web Instance
    • IAM instance profile: SSMInstanceProfile

웹 인스턴스용 security group은 ALB에서 오는 트래픽만 받도록 범위를 좁힌다.

5단계: Auto Scaling Group 만들기

  • Auto Scaling Group
    • 이름: Web-ASG
    • launch template: Web
    • subnet: private subnet 2개
    • target group: Web-TG
    • desired capacity: 2
    • min capacity: 2
    • max capacity: 4
    • CloudWatch group metrics: enabled
    • scaling policy: target tracking, average CPU 30%
    • tag: Name=ASG-Web-Instance

Auto Scaling Group은 웹 서버를 직접 공개하지 않도록 private subnet에 둔다. 외부 요청은 ALB가 받고, ALB가 내부 IP를 통해 private subnet의 인스턴스로 보낸다.

EC2, Target Group, ALB, Auto Scaling 확인

EC2에서는 Auto Scaling Group이 만든 인스턴스가 2대인지, 각 인스턴스가 private subnet에 있는지 확인한다. Target Group에서는 target 상태가 healthy인지 본다. unhealthy라면 security group, health check path, web server 실행 상태를 확인한다.

이어서 ALB DNS name을 브라우저에 입력해 페이지가 열리는지 확인한다. Auto Scaling Group에는 desired, min, max 값이 의도대로 들어갔는지 보고, CPU target tracking 정책이 연결되어 있는지도 확인한다.

자주 막히는 지점

Target Group이 unhealthy인 경우

EC2의 HTTP server가 실행 중인지 먼저 확인한다. 이어서 EC2 security group inbound가 ALB security group을 허용하는지 보고, health check path가 애플리케이션에서 200을 반환하는지 확인한다.

ALB DNS는 열리지만 특정 인스턴스만 실패하는 경우

AMI를 만들기 전에 EC2 설정이 완성되지 않았을 수 있다. launch template이 최신 AMI 버전을 사용하는지도 확인한다.

Auto Scaling이 인스턴스를 계속 새로 만드는 경우

health check 실패로 인스턴스를 교체하고 있을 수 있다. target group의 health check reason을 먼저 확인한다.
