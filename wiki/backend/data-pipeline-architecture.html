데이터 파이프라인 아키텍처

데이터 파이프라인은 외부 원본에서 데이터를 꺼내고(Extract), 쓸 수 있는 형태로 바꾸고(Transform), 저장소에 싣는(Load) 과정을 자동화한 구조다. 핵심은 각 단계 사이에 검증을 두어 “틀린 데이터가 다음 단계로 넘어가지 못하게” 막는 데 있다.

요청 흐름에서 보이는 데이터 파이프라인 아키텍처

이해를 돕기 위해 공공 대기질 API의 데이터를 모델에 입력하는 상황을 가정해 보자. 첫날에는 데이터를 수동으로 받아 CSV로 저장한 뒤 분석할 수 있다. 그러나 이 방식을 며칠간 반복해서 운영하면 다음과 같은 문제가 생길 수 있다.

  • API가 어제는 pm10을 숫자로 주더니, 오늘은 "-" 문자열로 준다.
  • 측정소 한 곳이 응답에서 통째로 빠진다.
  • 같은 시각의 데이터가 두 번 들어와 행이 중복된다.
  • 한 달 뒤 “지난주 데이터를 다시 뽑아 달라”는 요청을 받았지만 당시 데이터를 어떻게 가져왔는지 기억나지 않는다.

이 사례는 특정 API에서 실제로 발생했다고 확인한 기록이 아니라, 반복 수집 과정에서 대비해야 할 대표적인 실패 상황을 설명하기 위한 예시다. 데이터를 한 번 수동으로 받는 일과 매일 또는 매시간 자동으로 수집하면서 신뢰성을 유지하는 일은 서로 다른 문제다. 전자는 간단한 스크립트로 처리할 수 있지만, 후자에는 실패를 감지하고 재실행해도 같은 결과를 만드는 파이프라인이 필요하다.

이 구조를 알아야 다음 내용을 이해할 수 있다.

  • 원본 데이터가 잘못되면 분석 결과도 신뢰하기 어려운 이유(garbage in, garbage out)
  • ETL(Extract·Transform·Load)과 ELT가 서로 다른 방식으로 발전한 이유
  • RAG의 임베딩 인덱스나 모델 학습 데이터가 어떤 과정을 거쳐 만들어지는지
  • “재현 가능한 데이터”가 포트폴리오에서 중요한 이유

따라서 핵심 질문은 하나다. 언제든 원본에 문제가 생길 수 있는 상황에서, 수집한 데이터를 어떻게 끝까지 신뢰할 수 있게 만들 것인가.

데이터 파이프라인 아키텍처 흐름

먼저 정수기 비유로 전체 역할을 이해하고, 이어서 ETL의 각 단계와 ETL·ELT의 차이를 살펴본다. 그다음 검증과 멱등 적재를 포함한 실제 처리 순서를 확인한다.

비유: 정수기

수돗물(원본)을 그대로 마시지 않고 정수기의 여러 필터를 통과시킨다고 생각해 보자. 굵은 이물질 거름 → 활성탄 → 미세 필터 → 깨끗한 물 탱크의 순서로 처리되며, 각 필터는 “이 단계를 통과한 물은 이 수준의 조건을 만족한다”는 기준을 제공한다.

데이터 파이프라인도 이와 비슷하다. 원본 데이터를 여러 단계에서 정제하고 검사해 다음 단계가 사용할 수 있는 품질로 만든다. 마지막 탱크에 해당하는 저장소에는 정해진 검증 조건을 통과한 데이터가 도착한다. 다만 이 비유에서 “믿고 쓸 수 있다”는 말은 데이터가 절대적으로 정확하다는 뜻이 아니라, 파이프라인이 정의한 품질 기준을 충족했다는 뜻이다.

정의: ETL 세 단계

파이프라인의 기본 뼈대는 ETL(Extract, Transform, Load)이라는 세 단계다.

  • Extract(추출): 외부 원본(API, 파일, DB, 웹)에서 raw 데이터를 가져온다. 재현성을 위해 이 단계에서는 가능한 한 원본을 가공하지 않고 보존한다.
  • Transform(변환): 데이터를 정제·표준화·결합한다. 타입을 맞추고, 결측을 처리하며, 단위를 통일하고, 중복을 제거한다.
  • Load(적재): 변환된 데이터를 데이터베이스, 데이터 웨어하우스, 파일 같은 최종 저장소에 싣는다.

ETL vs ELT — 변환을 어디서 하는가

기본 요소는 같지만, 변환을 수행하는 시점에 따라 ETL과 ELT로 나뉜다.

  • ETL: 적재 전에 변환한다. 저장소에는 정제된 데이터가 들어간다. 저장 공간이 비싸고 스키마가 고정된 전통적 관계형 DB에 적합하다.
  • ELT: raw 데이터를 먼저 저장소에 적재한 뒤 그 안에서 SQL 등으로 변환한다. 원본을 보존한 채 다양한 방식으로 다시 가공하기 좋으며, 저장 비용이 낮고 연산 능력이 강한 클라우드 웨어하우스 환경에서 널리 쓰인다.

판단 기준은 다음과 같다. 저장 비용이 높고 스키마가 고정되어 있다면 ETL이 적합하다. 저장 비용이 낮고 원본을 보존하면서 나중에 여러 방식으로 가공해야 한다면 ELT가 유리하다. 이 선택은 데이터를 담을 저장소를 결정하는 관계형 DB와 NoSQL 판단과도 직접 연결된다.

동작 순서: 검증을 끼운 파이프라인

ETL의 세 단계만으로는 운영 중 발생하는 오류와 재시도를 충분히 다루기 어렵다. 실제 파이프라인에서는 단계 사이에 검증(Validation)을 두고, 적재에는 멱등성을 적용하며, 마지막에 처리 이력을 기록한다. 흐름은 다음과 같다.

  1. Extract — 원본에서 데이터를 가져와 raw 상태로 스냅샷을 보관한다. 나중에 당시 입력을 재현하기 위한 단계다.
  2. Validate(raw) — 응답이 비어 있거나 필수 필드가 빠졌는지 1차로 점검한다.
  3. Transform — 타입·단위·결측·중복을 정리한다.
  4. Validate(clean) — 변환 결과가 정해진 스키마와 값의 범위를 만족하는지 2차로 점검한다.
  5. Load — 같은 작업을 두 번 실행해도 중복이 생기지 않도록 멱등하게 적재한다.
  6. Record — 언제 무엇을 몇 건 처리했는지 메타데이터와 계보를 남긴다.
%% 검증을 끼운 데이터 파이프라인 흐름
flowchart TD
  extract["Extract<br/>API 호출"]
  transform["Transform<br/>정제·표준화"]
  load["Load<br/>DB 적재"]
  validate_raw["검증 1<br/>비었나?"]
  validate_clean["검증 2<br/>범위 맞나?"]
  lineage["계보 기록<br/>건수·시각"]
  extract --> transform
  transform --> load
  extract --> validate_raw
  transform --> validate_clean
  load --> lineage

이제 이 흐름을 실제 값에 적용해 보자. “정제”는 추상적인 표현이 아니라 개별 값에 적용되는 구체적인 규칙을 뜻한다. 문자열 "-"로 들어온 pm10을 None으로 바꾸고, (station_id, measured_at)가 같은 행은 중복으로 판단해 하나만 남긴다. 측정값이 0~1000 범위를 벗어나면 적재를 중단한다. 여기서 범위는 이 예시의 검증 규칙이며, 실제 시스템에서는 데이터 정의와 업무 기준에 맞게 별도로 정해야 한다.

멱등성: 왜 INSERT가 아니라 UPSERT인가

배치 작업은 네트워크 단절, 서버 장애, 실행 일정 중복 등으로 실패하거나 재시도될 수 있다. 따라서 같은 배치를 두 번 실행해도 최종 결과가 같아야 한다. 이 성질을 멱등성이라고 한다.

INSERT만 사용하면 재실행할 때 같은 행이 다시 쌓여 중복이 생길 수 있다. 반면 (station_id, measured_at)를 유니크 키로 정하고 UPSERT하면, 같은 키의 행을 새로 추가하지 않고 갱신할 수 있다. 이때 멱등성이 실제로 보장되려면 중복을 식별하는 키가 데이터의 의미에 맞게 설계되어야 한다. 이러한 키 설계는 DB 인덱스의 유니크 인덱스와 직결된다.

데이터 파이프라인 아키텍처 코드

아래 참조 구현은 앞서 설명한 흐름을 단계별 코드로 옮긴 것이다. 원본 보존, 변환, 검증, 멱등 적재, 전체 실행 순서의 차례로 살펴보면 각 코드가 6단계 흐름에서 맡는 역할을 확인할 수 있다.

먼저 원본을 가공하지 않고 받아 스냅샷으로 남긴다.

Extract 단계에서 원본을 그대로 보존해야 나중에 “당시 데이터로 다시 실행해 달라”는 요청에 대응할 수 있다. 스냅샷은 이후 변환 결과가 잘못되었을 때 입력부터 다시 확인하는 근거이기도 하다.

다음으로 들쭉날쭉한 원본을 일정한 형태로 정제한다.

Transform 단계는 문자열 "-"이나 중복 행처럼 원본에 섞인 형식 차이를 흡수한다. 그 결과 "-"는 None이 되고, (station_id, measured_at) 중복은 제거된다.

정제가 끝나면 잘못된 데이터가 저장소로 넘어가지 않도록 검증한다.

검증은 정해진 품질 조건을 만족하지 않는 데이터의 적재를 막는 차단기다. assert가 깨지면 파이프라인을 중단해, 해당 데이터가 저장소에 들어가기 전에 문제를 드러낸다.

검증을 통과한 데이터는 두 번 실행해도 중복이 생기지 않도록 적재한다.

ON CONFLICT ... DO UPDATE가 멱등 적재의 핵심이다. 같은 배치를 재시도해도 키가 같은 행은 새로 쌓이지 않고 갱신되므로, 배치 실패 후에도 안전하게 다시 실행할 수 있다.

마지막으로 앞의 단계를 안전한 순서로 묶는다.

이 실행 순서 자체가 안전장치다. 검증(assert_clean)이 적재(upsert)보다 먼저 실행되므로, 검증 조건을 통과하지 못한 데이터는 저장소에 도달하지 않는다.

정리

데이터 파이프라인은 불안정한 원본을 받아 정해진 품질 기준을 만족하는 데이터로 만드는 구조다. ETL의 추출·변환·적재 단계 사이에 검증을 두고, 멱등 적재와 계보 기록을 더하면 원본에 문제가 생겼을 때 이를 감지하고 재현하며 안전하게 다시 처리할 수 있다.

판단 기준은 다음과 같이 정리할 수 있다.

  • 변환을 적재 전에 할지(ETL) 후에 할지(ELT)는 저장 비용, 스키마 제약, 원본 보존과 재가공의 필요성을 함께 고려해 정한다.
  • 적재는 INSERT보다 키 기반 UPSERT를 사용한다. 배치는 실패 후 재시도될 수 있으므로 중복을 막아야 한다.
  • raw 스냅샷과 계보 기록은 데이터의 수집 과정과 처리 결과를 재현하는 근거다. 이를 남기지 않으면 “어떻게 받은 데이터인지” 확인하기 어렵고 결과의 신뢰성을 설명하기도 어렵다.
