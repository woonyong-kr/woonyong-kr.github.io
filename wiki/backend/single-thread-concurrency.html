단일 스레드 동시성

확인 범위: 이 문서는 단일 스레드 동시성의 일반 원리와 I/O 바운드·CPU 바운드 작업을 구분하는 선택 기준을 설명하며, 포함된 코드와 수치는 동작을 이해하기 위한 예시다. 특정 JavaScript·Node.js·브라우저 버전의 구현을 검증하거나 실제 실행 기록과 성능 측정에 근거해 처리량·메모리 효율을 보장하는 문서는 아니다.

서버 하나에 클라이언트 1만 명이 동시에 접속해 있다고 하자. 각 클라이언트가 요청을 보낸 뒤 서버가 디스크나 다른 서버에서 데이터를 가져오는 동안에는 응답을 기다려야 한다. 자바스크립트는 실행 스레드가 하나뿐인데도 이런 연결을 여럿 다룬다. 여러 작업을 병렬로 실행해서가 아니라, 기다리는 작업을 운영체제나 런타임에 맡기고 그사이에 다른 작업을 진행하기 때문이다. 이것이 단일 스레드 동시성(concurrency)이다.

연결마다 스레드를 두면 생기는 문제

요청을 처리하는 가장 단순한 방법은 연결마다 스레드를 하나씩 두는 것이다. 클라이언트가 1만 명이면 스레드도 1만 개가 필요하다. 스레드 하나에 보통 1MB 안팎의 스택(stack)이 붙는다고 가정하면, 스택에만 약 10GB가 필요하다. 운영체제가 실행할 스레드를 바꾸는 컨텍스트 스위치(context switch)에도 비용이 든다. 스레드가 많아질수록 실제 작업보다 전환에 더 많은 시간을 쓸 수 있다.

자바스크립트의 메인 스레드는 하나다. 따라서 연결마다 실행 스레드를 붙잡아 두는 대신, 응답을 기다리는 동안 메인 스레드가 다른 요청을 처리하게 해야 한다. 이 구조를 이해하면 Node.js 서버가 여러 동시 접속을 다루는 방식, 무거운 for 루프 하나가 서버 전체를 멈추게 하는 이유, 동시성과 병렬성의 차이를 함께 설명할 수 있다.

한 명의 요리사가 여러 요리를 진행하는 방식

주방에 요리사가 한 명뿐인데 손님 세 명이 각각 스테이크, 파스타, 수프를 주문했다고 하자.

요리사는 스테이크를 불판에 올린 뒤 굽는 8분 동안 서서 기다리지 않는다. 굽는 일은 불판이 계속하므로 그사이에 파스타 물을 올리고 수프 재료를 썬다. 불판에서 다 익었다는 신호가 오면 다시 스테이크를 처리한다.

요리사는 한 명이어서 한순간에 한 가지 일만 직접 한다. 그러나 기다리는 시간을 다른 일에 사용하므로 세 요리를 함께 진행할 수 있다. 단일 스레드 동시성도 이처럼 기다림이 필요한 일을 외부 장치에 맡기고, 실행할 수 있는 다른 일을 번갈아 처리한다.

동시성(concurrency)은 실행 주체 하나가 여러 작업을 오가며 함께 진행하는 방식이다. 병렬성(parallelism)은 실행 주체 여러 개가 같은 순간에 작업을 실제로 나누어 실행하는 방식이다. 단일 스레드 자바스크립트는 동시성을 제공하지만, 자바스크립트 코드 자체를 여러 스레드에서 병렬로 실행하는 것은 아니다.

콜 스택에서 이벤트 루프까지

메인 스레드는 먼저 콜 스택(call stack)에 올라온 함수를 실행한다. 콜 스택에서는 한 번에 함수 하나만 실행된다. 실행 중 파일 읽기나 네트워크 응답처럼 기다림이 필요한 작업을 만나면, 그 작업을 운영체제 또는 런타임에 맡긴다. O를 사용하면 콜 스택은 완료를 기다리지 않고 다음 코드를 실행할 수 있다.

맡긴 작업이 끝나면 완료 콜백이 큐에 들어간다. 이벤트 루프(event loop)는 콜 스택이 비었는지 확인하고, 비어 있으면 큐에서 콜백 하나를 꺼내 콜 스택에 올린다. 메인 스레드는 이 과정을 반복하며 지금 실행할 수 있는 일을 계속 처리한다.

%% 단일 스레드 이벤트 루프 흐름
flowchart TD
  call_stack["콜 스택<br/>Call Stack<br/>한 번에 함수 하나만 실행"]
  event_loop["이벤트 루프<br/>Event Loop<br/>콜 스택이 비었는지 반복 확인"]
  callback_queue["콜백 큐<br/>Queue<br/>타이머와 I/O 완료 콜백 대기"]
  background["OS/런타임 백그라운드<br/>디스크"]
  call_stack --> background
  background --> callback_queue
  callback_queue --> event_loop
  event_loop --> call_stack

이 흐름은 기다리는 시간이 긴 작업에서 유리하다. 예를 들어 요청 하나가 CPU를 0.1밀리초 사용하고 응답을 50밀리초 기다린다고 하자. 스레드 하나가 요청 하나를 계속 붙잡으면 그 스레드는 기다리는 동안 다른 일을 하지 못한다. 단일 스레드 이벤트 루프는 같은 50밀리초 동안 다른 요청 500개의 CPU 작업을 0.1밀리초씩 처리할 수 있다. 이 수치는 동작을 설명하기 위한 예시이며 실제 처리량을 보장하지 않는다.

I/O 작업과 CPU 작업이 다른 이유

I/O 바운드(I/O-bound) 작업은 CPU 계산보다 디스크나 네트워크를 기다리는 시간이 길다. 이런 작업은 기다림을 외부에 맡길 수 있으므로, 메인 스레드가 그사이에 다른 요청을 처리할 수 있다.

CPU 바운드(CPU-bound) 작업은 외부 응답을 기다리지 않고 CPU를 오래 사용한다. 이 작업이 콜 스택을 차지하면 이벤트 루프는 다음 콜백을 올릴 수 없다. 큐에 들어온 요청과 이벤트도 콜 스택이 빌 때까지 기다려야 한다. 단일 스레드에서 무거운 계산 하나가 전체 처리를 멈추게 하는 이유다. 이런 계산은 Web Workers처럼 별도의 실행 주체로 빼야 한다.

코드로 보는 대기와 점유

동기 파일 읽기는 작업이 끝날 때까지 현재 실행 흐름을 붙잡는다.

readFileSync가 실행되는 동안 콜 스택은 이 작업에서 벗어나지 못한다. 큐에 다른 요청의 콜백이 있어도 실행할 수 없으므로 단일 스레드의 동시성이 막힌다.

비동기 파일 읽기는 기다리는 작업을 런타임에 맡긴 뒤 곧바로 반환한다.

readFile가 반환하면 콜 스택은 handleNextRequest()를 실행한다. 파일 읽기가 끝난 뒤에는 콜백이 큐에 들어간다. 이벤트 루프는 콜 스택이 빈 순간 그 콜백을 올린다. 같은 메인 스레드가 두 작업을 병렬로 실행하는 것이 아니라, 기다림을 사이에 두고 번갈아 처리하는 흐름이다.

반면 다음 while 루프에는 외부에 맡길 기다림이 없다.

이 코드는 CPU를 5초 동안 계속 사용한다. 그동안 콜 스택이 비지 않으므로 이벤트 루프는 큐의 콜백을 실행하지 못한다. 따라서 다른 콜백과 클릭, 요청도 5초 동안 대기한다. 이런 CPU 바운드 작업은 단일 스레드에 그대로 두기 어렵다.

브라우저와 Node.js에서의 차이

브라우저에서는 메인 스레드 하나가 자바스크립트 실행과 화면 렌더링을 함께 맡는다. 무거운 계산이 콜 스택을 차지하면 클릭과 스크롤도 함께 멈춘다.

Node.js에서도 자바스크립트 코드는 메인 스레드 하나에서 실행된다. 다만 파일 I/O 같은 일부 작업은 내부 라이브러리 libuv의 스레드 풀(기본 4개)이 백그라운드에서 처리한다. 백그라운드에 다른 스레드가 있더라도 자바스크립트 코드 자체가 메인 스레드 하나에서 실행된다는 원칙은 같다.

작업을 배치하는 판단 기준

작업이 주로 디스크나 네트워크 응답을 기다리는 I/O 바운드 작업이라면, 단일 스레드 이벤트 루프는 기다리는 시간을 다른 요청 처리에 사용할 수 있다. 연결마다 스레드를 두는 방식과 비교하면 예시의 스택 메모리와 컨텍스트 스위치 비용을 피할 수 있다. 다만 이 문서는 실제 측정을 바탕으로 메모리 효율이나 처리량을 보장하지 않는다.

작업이 기다림 없이 계산을 오래 수행하는 CPU 바운드 작업이라면, 메인 스레드에 두는 동안 다른 작업이 모두 밀린다. 따라서 작업을 어디에 둘지 판단할 때는 먼저 그 작업이 외부 응답을 기다리는지, 아니면 CPU 계산을 계속하는지 구분해야 한다.

CPU 계산을 별도 실행 주체로 옮기는 방법, 나중에 도착하는 값을 코드로 표현하는 방법, 운영체제 수준의 I/O 대기를 더 살펴보려면 다음 문서로 이어서 읽는다.

  • Web Workers
  • await
  • O
