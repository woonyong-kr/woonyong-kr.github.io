웹 서버와 프록시 학습 프로젝트

웹 서버와 프록시는 요청 하나가 socket fd, 버퍼, 파일 fd를 거쳐 응답으로 돌아오는 길을 따라가면 훨씬 덜 막힌다.

프로젝트 목적

웹 서버, 프록시, 소켓 프로그래밍을 따로 외우지 않고 요청 하나의 이동 경로로 묶어 본다. 브라우저가 보낸 HTTP 요청이 어디서 읽히고, 어떤 버퍼에 담기고, 언제 파일이나 원 서버 요청으로 이어지는지가 중심이다.

개념

  • 웹 서버와 프록시
  • 웹 서버와 프록시 서버 실행 구조

학습 경로

처음 볼 때는 fetch() 한 번이 서버 안에서 어떤 fd, 버퍼, 파싱 단계로 바뀌는지부터 따라간다. 그다음 Tiny Web Server와 프록시 과제를 보면서 같은 HTTP 메시지가 어느 지점에서 읽히고 다시 쓰이는지 확인한다.

  1. 웹 서버와 프록시에서 전체 범위를 확인한다.
  2. 웹 서버와 프록시 서버 실행 구조에서 socket -> bind -> listen -> accept -> read -> write 흐름을 잡는다.
  3. Tiny Web Server 구현을 보면서 listening socket과 connected socket을 구분한다.
  4. 프록시 과제에서는 브라우저가 보낸 request line을 원 서버용 request line으로 다시 만드는 지점을 찾는다.

자료를 나누는 기준

  • 자료 출처와 진행 기록은 여기에서 찾는다.
  • 개념 설명은 주제별 Wiki 문서로 옮긴다.
  • 실행 흐름을 코드 단위로 추적할 때는 별도 흐름 문서로 나눈다.
  • 직접 실행 로그나 요청/응답 관찰은 주제별 실험 문서로 분리한다.

학습 체크포인트

이 프로젝트를 끝냈다고 판단하려면 “웹 서버를 만들었다”가 아니라 다음 질문에 답할 수 있어야 한다.

  • accept()가 반환한 fd와 listen()에 쓰는 fd가 왜 다른가?
  • HTTP 요청에서 method, path, version은 어디서 분리되는가?
  • 정적 파일 응답과 동적 CGI 응답은 어떤 지점에서 갈라지는가?
  • 프록시는 클라이언트와 서버 양쪽에 대해 각각 어떤 역할을 하는가?
  • 순차 서버, 멀티프로세스 서버, 멀티스레드 서버는 병목이 어디서 달라지는가?

완료 기준

이 주제의 최종 산출물은 실행되는 코드 하나가 아니라, 요청 하나가 시스템 안에서 이동하는 경로를 설명할 수 있는 상태다. 예를 들어 브라우저가 /index.html을 요청했을 때 클라이언트 fd, 서버 fd, 파일 fd가 각각 언제 생기고 언제 닫히는지 말할 수 있어야 한다. 프록시까지 포함하면 같은 HTTP 메시지가 어느 지점에서 “클라이언트가 보낸 요청”에서 “원 서버에 다시 보낼 요청”으로 바뀌는지도 설명할 수 있어야 한다.

문서 정리는 이 완료 기준에 맞춰 진행한다. 원본 자료는 이 문서에 남기고, 개념 설명은 Wiki 문서로, 코드 추적은 별도 흐름 문서로, 직접 실행 결과는 실험 문서로 분리한다. 그래야 나중에 “웹 서버 공부”가 아니라 “소켓, HTTP, 프록시, 동시성” 중 필요한 축으로 다시 찾을 수 있다.

다음에 보강할 흐름

  • Tiny Web Server의 socket -> bind -> listen -> accept -> read -> write 흐름을 코드 위치와 함께 따라간다.
  • 프록시가 받은 HTTP request line을 origin server 요청으로 다시 만드는 과정을 요청 예시로 남긴다.
