웹 서버와 프록시 서버 실행 구조

브라우저의 fetch() 호출이 서버 쪽에서 어떻게 처리되는지, 웹 서버와 프록시의 실행 흐름을 소켓부터 따라간다.

fetch() 요청이 서버를 거쳐 응답으로 돌아오기까지

브라우저에서 fetch("http://localhost:8000/index.html")를 호출하면 서버는 요청을 받을 소켓을 준비하고 연결을 받아들인다. 이어서 HTTP 요청을 읽고, 요청 대상 자원을 찾은 뒤 응답을 작성한다. 웹 프레임워크는 이 과정을 감추지만, CS:APP의 Tiny Web Server를 C로 구현하면 요청을 받는 소켓부터 HTTP 응답을 쓰는 순간까지 서버의 뼈대를 직접 따라갈 수 있다.

이 문서에서는 이더넷, 라우팅, TCP 혼잡 제어, OSI 계층과 같은 네트워크 공학보다 서버 프로그램 안에서 일어나는 실행 흐름에 집중한다.

구분관심사
네트워크 프로그래밍socket, bind, listen, accept, read, write
네트워크 공학이더넷, 라우팅, TCP 혼잡 제어, OSI 계층

Tiny Web Server의 실행 흐름

서버는 먼저 socket()으로 소켓을 만들고, bind()로 주소를 연결한 다음, listen()으로 연결을 기다린다. accept()가 클라이언트와 연결된 소켓을 반환하면 그 소켓에서 요청을 읽는다. 서버는 HTTP 요청을 파싱하고 자원을 찾은 뒤 응답을 쓰고 연결을 닫는다.

이 흐름에서는 listening socket과 connected socket을 구분해야 한다. listening socket은 연결을 기다리고, accept()가 반환한 connected socket은 실제 요청을 읽고 응답을 보내는 데 사용된다. Flask나 FastAPI가 숨겨 주는 서버의 기본 골격도 이 데이터 흐름을 따라가면 확인할 수 있다.

브라우저 요청을 기준으로 로그를 남긴다면 다음 순서로 실행 위치를 확인할 수 있다.

로그를 읽을 때는 함수 이름만 보는 대신 fd와 HTTP 데이터가 어디에서 만들어지고 전달되는지 살핀다. request line을 파싱하는 위치, header와 body를 구분하는 위치, 파일 경로를 결정하는 위치가 이어져야 요청 하나의 처리 과정이 드러난다.

프록시가 요청을 중계하는 흐름

프록시는 브라우저와 원 서버 사이에 선다.

브라우저는 먼저 프록시에 요청을 보낸다. 프록시는 요청에서 원 서버 주소를 얻고, 원 서버로 보낼 요청을 다시 생성한다. 원 서버가 응답하면 프록시는 그 응답을 브라우저에 전달한다. 따라서 프록시에서는 같은 요청의 흐름이 두 번 나타난다. 첫 번째는 브라우저가 프록시에 보낸 요청이고, 두 번째는 프록시가 원 서버에 다시 보낸 요청이다.

두 요청의 host, path, connection header를 비교하면 프록시가 요청을 그대로 통과시키는 데서 그치지 않고 다시 구성한다는 점을 볼 수 있다. 이 중계 구조에 캐시, 필터링, 로깅, 인증, 로드밸런싱 같은 기능을 붙이면 실제 인프라에서 흔히 보는 구성으로 확장된다.

코드를 따라가는 순서

전체 흐름을 먼저 본 뒤 필요한 개념으로 돌아가면 각 함수가 요청 처리에서 맡는 역할을 연결하기 쉽다.

  1. CS:APP 11.5, 11.6의 Tiny 서버 구현을 먼저 본다.
  2. 모르는 함수가 나오면 11.1-11.4로 돌아가 개념을 채운다.
  3. 에코 서버와 Tiny 서버를 라인 단위로 추적한다.
  4. 프록시 과제에서 요청을 다시 생성하고 전달하는 부분을 구현한다.
  5. 이후 DBMS 서버화처럼 다른 프로젝트에 같은 흐름을 적용한다.

서버와 프록시 코드를 읽을 때는 다음 질문으로 데이터 흐름이 끊기는 지점을 찾을 수 있다.

  • 어떤 fd가 listening socket인가?
  • 어떤 fd가 connected socket인가?
  • HTTP request line은 어디서 파싱되는가?
  • header와 body는 어디서 구분되는가?
  • 프록시는 원 서버 주소를 어디서 얻는가?
  • 동시 요청이 오면 순차 처리, 프로세스, 스레드 중 무엇을 쓰는가?
