Web Workers

Web Workers

확인 범위: 이 문서는 Web Workers의 일반 개념과 CPU 바운드 작업에 적용할 때의 선택 기준을 설명하며, 포함된 코드는 동작 구조를 보여 주는 예시다. 특정 브라우저·Node.js 버전에서의 호환성이나 실제 실행 결과, UI 응답성 및 복사·전송 비용에 관한 성능 판단은 별도의 코드 실행과 측정으로 검증해야 한다.

이벤트 루프는 기다림을 활용할 뿐 무거운 계산은 못 나눈다. Web Worker는 별도 스레드를 띄워 CPU 작업을 메인 스레드 밖에서 진짜 병렬로 실행하고, 메모리를 공유하는 대신 메시지로만 통신한다.

Web Workers 필요성

단일 스레드 동시성은 기다림이 많은 작업에 강하다. 그런데 기다림이 전혀 없는 작업이 들어오면 무너진다. 예를 들어 100만 개 원소의 배열을 정렬하거나, 이미지 필터를 픽셀마다 계산하거나, 큰 데이터를 암호화하는 일은 CPU만 몇 초씩 붙잡는다.

이런 작업이 메인 스레드의 콜 스택을 점유하면 그동안 이벤트 루프가 멈춘다. 브라우저라면 그 몇 초 동안 버튼 클릭도 스크롤도 전부 얼어붙는다. 사용자는 “페이지가 죽었다”고 느낀다.

이벤트 루프로는 이걸 못 푼다. 이벤트 루프는 “기다리는 시간을 다른 일에 쓰는” 기술이지, “계산 자체를 둘로 쪼개는” 기술이 아니기 때문이다. 계산을 정말로 나누려면 실행 주체가 둘 이상, 즉 스레드가 더 필요하다. 이 진짜 병렬 실행을 자바스크립트(JavaScript)에 주는 도구가 Web Worker다.

이 개념을 모르면 다음을 설명할 수 없다.

  • 무거운 계산을 비동기로 감싸도 왜 화면이 여전히 얼어붙는가
  • 스레드를 늘렸는데 왜 변수를 직접 공유하지 못하고 메시지를 주고받아야 하는가
  • 워커 안에서는 왜 화면(document)을 건드릴 수 없는가

Web Workers 구조

비유: 주방에 보조 요리사 추가하기

단일 스레드 동시성에서 요리사는 한 명이었다. 그 요리사가 30분짜리 반죽을 손으로 치대기 시작하면, 그동안 새 주문을 받을 수 없다. 손이 반죽에 묶여 있기 때문이다.

해법은 보조 요리사(Worker)를 한 명 더 고용하는 것이다. 메인 요리사는 계속 주문을 받고(메인 스레드는 UI를 처리), 무거운 반죽은 보조에게 넘긴다. 단, 둘은 같은 도마를 동시에 쓰지 않는다. 메인 요리사가 “이 재료로 반죽해”라고 쪽지(메시지)와 함께 재료를 건네면, 보조가 다 만들어 “완성했어”라는 쪽지와 함께 돌려준다.

정의: 별도 스레드 + 메시지 통신

Web Worker는 메인 스레드와 분리된 별도의 운영체제 스레드에서 자바스크립트를 실행한다. 두 스레드는 같은 순간에 함께 돈다. 이게 동시성이 아니라 병렬성(parallelism)이다.

핵심 규칙은 메모리를 공유하지 않는다는 것이다. 메인과 워커는 변수를 직접 같이 쓰지 못한다. 대신 postMessage로 데이터를 보내고 onmessage로 받는다. 보낸 데이터는 공유가 아니라 복사(structured clone)로 전달된다.

왜 메모리를 공유하지 않게 만들었나

여러 스레드가 같은 메모리를 동시에 건드리면 경쟁 조건(race condition)이 생긴다. 두 스레드가 같은 변수를 동시에 더하면 한쪽 갱신이 사라지는 식이다. 이걸 막으려면 락(lock)을 걸어야 하고, 락은 데드락과 버그의 온상이다.

자바스크립트는 이 복잡함을 처음부터 피하기로 했다. “공유하지 말고 메시지로만 주고받아라”는 모델을 택했다. 각 워커는 자기 메모리만 본다. 그래서 락이 필요 없고, 경쟁 조건이 구조적으로 막힌다. 대신 데이터를 복사해 보내는 비용이 든다.

복사 비용이 부담되는 큰 데이터에는 두 가지 예외가 있다.

  • Transferable 객체: ArrayBuffer 같은 버퍼를 복사하지 않고 소유권만 넘긴다. 넘긴 쪽은 그 버퍼를 더 못 쓴다.
  • SharedArrayBuffer: 진짜로 메모리를 공유한다. 이때는 동기화를 직접 책임져야 한다.

제약: 워커가 못 하는 일

워커는 메인 스레드와 다른 환경에서 돈다. 그래서 화면을 직접 못 건드린다.

  • DOM 접근 불가: document, window로 화면 요소를 읽거나 바꿀 수 없다. 화면 갱신은 결과를 메인 스레드로 보내 거기서 한다.
  • 쓸 수 있는 것: 순수 계산, fetch로 네트워크 요청, 타이머, 그리고 self를 통한 워커 자신의 API.

화면은 메인 스레드만 만진다는 원칙이 깔려 있다. 그래야 여러 스레드가 화면을 동시에 고쳐 충돌하는 일이 없다.

런타임별 차이

  • 브라우저: Worker 객체를 쓴다. 주로 UI를 얼리지 않으려고 무거운 계산을 빼는 용도다.
  • Node.js: worker_threads 모듈의 Worker를 쓴다. API 이름은 다르지만 “별도 스레드 + 메시지 통신 + 메모리 비공유”라는 모델은 같다.

Web Workers 코드

메인 스레드: 워커에 일을 맡긴다

postMessage로 일을 넘긴 뒤 메인 스레드는 바로 다음 줄로 넘어간다. 무거운 계산은 워커가 병렬로 도므로 그동안에도 클릭과 스크롤이 살아 있다. 결과는 onmessage 콜백으로 메인 스레드에 돌아온다.

워커 스레드: 받은 일을 계산해 돌려준다

워커는 자기 메모리 안에서만 계산하고, 끝나면 결과를 postMessage로 돌려준다. 이 reduce가 5초를 잡아먹어도 메인 스레드의 이벤트 루프는 멈추지 않는다. 둘이 다른 스레드이기 때문이다.

큰 버퍼는 복사 대신 소유권 이전

두 번째 인자에 버퍼를 넘기면 데이터를 복사하지 않고 소유권만 워커로 옮긴다. 64MB를 복사하는 비용이 사라진다. 대신 넘긴 뒤에는 메인 쪽 buffer가 빈 껍데기가 되므로, 더 쓰지 않을 데이터에만 쓴다.

정리

Web Worker는 메인 스레드와 분리된 별도 스레드를 띄워 CPU 작업을 진짜 병렬로 실행한다. 두 스레드는 메모리를 공유하지 않고 메시지로만 통신하므로 락과 경쟁 조건의 복잡함을 피한다. 대신 데이터를 복사해 보내는 비용이 들고, 워커는 화면(DOM)을 직접 건드리지 못한다.

판단 기준: 작업이 CPU 바운드(기다림 없이 계산만 오래)이고 그 때문에 UI가 얼어붙는다면 워커로 빼라. 반대로 I/O 바운드(대부분 기다림)면 워커가 필요 없다. 그건 이벤트 루프와 비동기로 충분하다. 또 워커로 보내고 받는 데이터가 작업량에 비해 너무 크면 복사 비용이 이득을 깎아먹으니, “계산량이 통신 비용보다 충분히 큰가”를 함께 따진다.

워커가 왜 필요한지, 스레드를 늘릴 때 운영체제가 치르는 비용, 워커 없이 처리할 수 있는 I/O 바운드 작업은 다음 문서로 이어서 비교한다.
