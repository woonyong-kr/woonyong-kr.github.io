Obsidian을 학습 운영체제로 쓰기

확인 범위: 이 문서는 Obsidian 기반 학습 자료의 분류·연결·공개 범위를 설계하는 일반 원리와 이 볼트에 적용한 운영 기준을 설명한다. 실제 코드의 동작, 특정 버전과의 호환성, 실행 기록이나 성능 측정을 검증한 결과는 다루지 않는다.

Obsidian을 파일 창고로 두지 않고, 입력·원자료·정제·링크·공개 범위를 나눠 학습이 계속 굴러가게 만드는 방법.

파일 창고와 학습 운영체제의 차이

Obsidian에 Markdown 파일을 모으기만 하면 자료가 쌓여도 다시 찾고 설명하기 어렵다. 입력, 원자료, 정제 문서, 링크 구조, 공개 범위를 구분하면 새 자료를 받아들이고 설명 가능한 지식으로 다듬는 흐름을 계속 운영할 수 있다.

구요한 교수의 공개 자료에서는 노트 사이의 연결을 반복해서 강조한다. WikiDocs의 Obsidian 가이드도 노트 연결과 시각화가 생각을 정교하게 만드는 데 쓰인다고 설명한다. 노트 간 연결, 백링크, 아웃고잉 링크, 태그는 지식 구조를 확장하는 수단이다.

보존한 외부 근거

2026-08-28에 llm-wiki, claude-obsidian, garden-skills의 README와 라이선스를 Wiki 내부 source snapshot으로 가져왔다. 원격 링크는 발견과 갱신 확인에만 사용하며, 현재 운영 기준은 이 문서 안에 흡수한다.

  • llm-wiki에서는 세션 후보와 영구 지식의 분리, 명시적 승격, 범위가 제한된 조회를 가져왔다.
  • claude-obsidian에서는 local-first 검색, 입력 hash가 바뀐 stale 결과의 거부, transaction recovery와 deterministic lint를 가져왔다.
  • garden-skills에서는 trigger·절차·reference·검증을 하나의 skill 단위로 관리하는 패키징 방식을 가져왔다.

세 구현의 별도 vault, MOC, 검색 정본이나 플러그인 구조는 복제하지 않는다. Woon의 기존 source·claim·page·receipt와 skill catalog가 같은 책임을 이미 소유하기 때문이다.

이 볼트에 맞춘 최소 모델

이 볼트는 CMDS의 숫자 카테고리를 그대로 복사하지 않는다. 위키와 PintOS/OS/AI 정리, 창작 프로젝트 보존, Quartz 읽기 사이트 운영이라는 목적에 맞지 않기 때문이다. 대신 자료가 들어와 정제되고 공유되는 흐름을 가져온다.

  • Capture
    • 위치: inbox/capture/, inbox/daily/
    • 역할: 아직 분류하지 않은 생각과 작업 로그
  • Source
    • 위치: 비공개 원자료 보관 영역
    • 역할: 외부 원자료, 강의, 전사, 링크, 클리핑
  • Wiki
    • 위치: wiki/<domain>/
    • 역할: 처음 배우는 사람이 읽을 수 있는 설명 문서
  • Keywords
    • 위치: 같은 wiki/ 문서의 parent·하위 키워드 block
    • 역할: 학습 키워드와 대표 링크
  • Share
    • 위치: publish, access, Quartz
    • 역할: 읽기용 사이트 포함 여부와 공개 범위

자료가 Wiki 문서가 되는 흐름

새로운 자료를 발견해도 바로 wiki/에 넣지는 않는다. 먼저 비공개 원자료 보관 영역에 원자료로 저장한다. 원자료를 읽은 뒤, 자신의 언어로 설명할 수 있게 된 개념만 wiki/로 승격한다. 이렇게 해야 원자료와 독자를 위한 설명 문서가 섞이지 않는다.

새로운 질문은 inbox/capture/에 둔다. 질문이 반복되거나 설명할 가치가 생기면 templates/question-note.md로 형식을 정리하고, 이후 Wiki 문서로 바꾼다.

완성된 Wiki 문서는 대표 링크를 통해 접근할 수 있어야 한다. 독립된 중심 질문이 있는 설명만 Wiki child로 분리한다. 상위 문서에서는 Core가 전체 하위 키워드를 생성한다.

많은 원문을 적은 정본으로 바꾸는 성장 루프

2026-08-29 확장 대조에서는 8개 저장소의 활성 파일 17,645개를 먼저 catalog화하고, 실제 설명에 사용한 공개 원문 133개만 snapshot으로 보존했다. 원문 수와 Wiki 페이지 수가 같아야 하는 것은 아니다. 같은 질문에 답하는 자료는 한 정본에 병합하고, 독립적으로 다시 찾을 질문이 생길 때만 페이지를 분리한다.

  1. Inventory에서 모든 파일의 hash·role·변경 상태를 고정한다.
  2. Select에서 학습 claim과 설계 판단에 실제로 필요한 원문을 보존한다.
  3. Compare에서 기존 Wiki의 중심 질문과 중복을 찾는다.
  4. Promote에서 기존 페이지 병합 또는 새 정본 승격을 명시한다.
  5. Compile에서 page와 receipt를 재현한다.
  6. Audit에서 깨진 링크·중복·고아·stale 입력을 검사한다.

llm-wiki의 checkpoint·promotion, claude-obsidian의 provenance·transaction recovery, garden-skills의 information density·review checklist는 이 단계별 경계에 흡수했다. 별도 plugin이나 두 번째 vault는 만들지 않았다.

공개 범위를 나누는 기준

읽기용 사이트에 포함할지와 외부에 공개할 수 있는지는 서로 다른 판단이므로 publish와 access를 분리한다.

  • publish
    • publish: true: Quartz 읽기 사이트에 포함한다.
    • publish: false: Obsidian 로컬에서만 쓴다.
  • access
    • access: private: 인증 뒤에서만 보여줄 문서다.
    • access: public: 외부 공개가 가능하다.
    • access: local-only: Obsidian 내부 운영 문서다.

비공개 원자료 보관 영역, inbox/, templates/는 기본적으로 publish: false, access: local-only다.

Wiki 문서를 점검하는 기준

Wiki 문서는 독자가 용어를 만나기 전에 그 용어가 필요한 이유를 이해할 수 있어야 한다. 설명은 실제 예시, 코드, 값, 흐름 가운데 하나로 이어져야 하며, 최소 하나의 대표 링크 문서에서 접근할 수 있어야 한다.

공개 문서에서는 비공개 원자료를 직접 wikilink하지 않는다. 또한 문서를 읽은 사람이 다음에 무엇을 봐야 할지 알 수 있도록 연결 구조를 남긴다.

외부 도구를 받아들이는 기준

외부 도구는 기존 source → accepted claim → page spec → compiled Markdown → receipt 흐름을 보강할 때만 채택한다. 별도 vault, 별도 MOC, 별도 검색 정본을 요구하면 설치하지 않는다. retrieval index는 삭제 후 다시 만들 수 있어야 하고, 쓰기는 expected revision과 rollback 근거를 가져야 한다. 자세한 비교는 외부 지식 시스템을 Woon에 반영하는 기준에서 관리한다.
