HTTP — 웹 브라우저와 서버가 대화하는 규칙

HTTP(HyperText Transfer Protocol)는 클라이언트와 서버가 요청과 응답을 주고받기 위한 웹의 기본 통신 규약이다. HTTP/1.x 메시지는 텍스트로 표현되며, 이후 버전은 전송 형식이 달라져도 요청·응답의 의미를 이어 간다.

요청 흐름에서 보이는 HTTP

이 글의 목표는 실제 HTTP 메시지에서 요청 라인, 상태 라인, 헤더, 본문을 구분하고, 메서드와 상태 코드가 무엇을 뜻하는지 설명하는 것이다.

브라우저 주소창에 http://example.com/index.html을 입력하면 웹 페이지가 나타난다. 이때 브라우저는 서버에 무엇을 요청하고, 서버는 어떤 형식으로 결과를 돌려줄까?

TCP는 바이트 스트림을 신뢰성 있게 전달하지만, 그 바이트가 “어떤 파일을 달라”거나 “이 데이터를 저장해 달라”는 뜻인지는 해석하지 않는다. 따라서 TCP 위에는 요청의 의미와 응답의 형식을 정하는 별도의 약속이 필요하다. 그 약속이 HTTP다.

HTTP 메시지 구조를 알면 웹 서버가 요청을 해석하는 방식, 응답 코드 404가 자원을 찾지 못했다는 뜻인 이유, 브라우저가 받은 데이터의 형식을 판단하는 과정을 연결해 이해할 수 있다. 이는 웹 개발, API 설계, 프록시 서버 구현의 기초이기도 하다.

요청과 응답을 읽는 법

요청-응답 모델

HTTP 통신은 클라이언트가 요청(Request)을 보내고 서버가 그 요청에 대한 응답(Response)을 돌려주는 방식으로 설명할 수 있다. 이를 요청-응답 모델(Request-Response Model)이라고 한다. 여기서 핵심은 서버의 응답이 클라이언트가 시작한 요청과 연결된다는 점이다.

편지에 비유하면 클라이언트는 “이 파일을 보내 달라”고 적은 편지인 요청을 서버에 보낸다. 서버는 요청을 읽고 처리 결과를 응답으로 회신한다. 실제 연결에서는 버전이나 확장 기능에 따라 데이터 전달 방식이 달라질 수 있지만, HTTP 메시지를 읽을 때는 먼저 어떤 요청에 대한 어떤 응답인지 대응시키면 된다.

HTTP 메시지 구조: 시작 줄·헤더·본문

HTTP/1.x의 요청과 응답은 시작 줄, 헤더, 빈 줄, 선택적인 본문 순서로 읽는다.

요청 메시지:

요청 라인은 세 부분으로 나뉜다. 메서드(Method)는 “무엇을 할지”, URI(Uniform Resource Identifier)는 “어떤 자원을 대상으로 할지”, 버전은 “어떤 HTTP 규칙을 따를지”를 나타낸다.

응답 메시지:

응답 라인을 읽을 때는 상태 코드(Status Code)를 먼저 확인한다. 200은 요청이 성공했음을, 404는 요청한 자원을 찾지 못했음을 나타낸다.

HTTP/1.x 메시지에서 헤더와 본문을 구분하는 표지는 빈 줄(\r\n)이다. 헤더가 끝난 뒤 빈 줄이 나오고, 본문이 있다면 그다음에 이어진다.

HTTP 메서드: 자원에 수행할 동작

메서드는 클라이언트가 대상 자원에 어떤 동작을 원하는지 나타낸다. 대표적인 메서드는 다음과 같다.

  • GET — 자원을 조회한다. 브라우저 주소창에 URL을 입력할 때 일반적으로 이 요청이 사용된다.
  • POST — 데이터를 제출하거나 처리 결과로 새 자원을 만들 때 사용한다. 로그인 폼 제출이 대표적인 예다.
  • PUT — 대상 자원의 전체 상태를 전달한 표현으로 생성하거나 교체할 때 사용한다.
  • DELETE — 대상 자원을 삭제하도록 요청한다.

메서드의 의미를 단순히 본문 유무로만 구분해서는 안 된다. API를 설계하거나 읽을 때는 각 메서드가 자원에 요구하는 동작과 서버가 정의한 처리 방식을 함께 확인해야 한다.

상태 코드: 처리 결과의 범주

서버는 요청 처리 결과를 세 자리 상태 코드로 알린다. 첫 번째 숫자는 결과의 큰 범주를 나타낸다.

  • 1xx (정보) — 요청을 받았으며 처리가 계속 진행되고 있음을 알린다.
  • 2xx (성공) — 요청이 정상적으로 처리되었음을 나타낸다.
    • 200 OK — 요청이 성공했으며, 필요한 경우 응답 본문에 결과가 담긴다.
    • 201 Created — 요청이 성공해 새 자원이 생성되었다.
  • 3xx (리다이렉션) — 요청을 완료하려면 다른 위치나 추가 동작을 확인해야 함을 나타낸다.
    • 301 Moved Permanently — 자원이 영구적으로 이동했으므로 이후에는 새 URI를 사용해야 한다.
  • 4xx (클라이언트 오류) — 요청을 처리할 수 없는 원인이 클라이언트 측 요청에 있음을 나타낸다.
    • 400 Bad Request — 서버가 요청 형식이나 내용을 이해하거나 처리할 수 없다.
    • 403 Forbidden — 서버가 요청을 이해했지만 접근을 허용하지 않는다.
    • 404 Not Found — 서버에서 요청한 자원을 찾을 수 없다.
  • 5xx (서버 오류) — 서버가 요청을 처리하는 과정에서 실패했음을 나타낸다.
    • 500 Internal Server Error — 서버 내부에서 처리하지 못한 오류가 발생했다.
    • 501 Not Implemented — 현재 서버가 요청을 처리하는 데 필요한 기능을 지원하지 않는다.

헤더: 메시지의 부가 정보

헤더는 메시지를 해석하고 처리하는 데 필요한 부가 정보를 이름: 값 형식으로 전달한다. 요청과 응답 모두 헤더를 포함할 수 있다.

자주 쓰는 요청 헤더는 다음과 같다.

  • Host — 요청 대상 호스트를 나타낸다. HTTP/1.1 요청에서는 필수이며, 하나의 IP 주소에서 여러 도메인을 운영할 때 대상을 구분하는 데 쓰인다.
  • Content-Type — 요청 본문에 담긴 데이터의 형식을 나타낸다. 예를 들어 text/html, application/json 등을 지정할 수 있다.
  • Content-Length — 본문의 바이트 길이를 알려준다.
  • Connection — 연결에 적용할 제어 정보를 전달한다. keep-alive는 연결을 유지하려는 의도를, close는 응답 뒤 연결을 닫으려는 의도를 나타낸다.

자주 쓰는 응답 헤더는 다음과 같다.

  • Content-Type — 응답 본문의 데이터 형식을 나타낸다.
  • Content-Length — 응답 본문의 바이트 길이를 나타낸다.
  • Server — 서버가 공개하도록 설정한 서버 소프트웨어 정보를 나타낸다.

무상태(Stateless): 요청 사이의 상태

HTTP가 무상태 프로토콜이라는 말은 각 요청을 독립적으로 처리하며, 프로토콜 자체가 이전 요청의 애플리케이션 상태를 자동으로 이어 주지 않는다는 뜻이다. 따라서 첫 요청에서 로그인 절차를 마쳤더라도, 다음 요청에서 같은 사용자인지 식별할 정보를 별도로 전달해야 한다.

로그인 뒤 마이페이지를 보는 상황을 생각해 보자. 서버가 요청자를 식별하지 못하면 사용자별 화면을 제공할 수 없다. 이를 보완하기 위해 쿠키(Cookie)와 세션(Session)을 사용할 수 있다. 쿠키는 클라이언트가 저장한 정보를 요청과 함께 보내는 방식이고, 세션은 일반적으로 서버에 상태를 보관한 뒤 클라이언트가 전달하는 식별자와 연결하는 방식이다.

무상태성은 서버 확장을 단순하게 만드는 데 도움이 된다. 다만 실제로 여러 서버가 요청을 나누어 처리하려면 세션 저장 위치처럼 별도로 관리하는 상태도 함께 고려해야 한다.

HTTP 버전 변천

  • HTTP/1.0 — 기본적인 사용 방식에서는 요청마다 TCP 연결을 새로 맺고 닫아 연결 비용이 커질 수 있다.
  • HTTP/1.1 — 기본적으로 Connection: keep-alive를 사용해 하나의 TCP 연결을 여러 요청에 재사용한다. 파이프라이닝(Pipelining)도 정의하지만, 응답 순서가 요청 순서와 같아야 해서 HOL(Head-of-Line) 블로킹이 생길 수 있다.
  • HTTP/2 — 하나의 TCP 연결에서 여러 스트림을 다중화(Multiplexing)한다. 바이너리 프레이밍과 헤더 압축(HPACK)을 사용한다.
  • HTTP/3 — TCP 대신 QUIC 위에서 동작하며, 스트림별 전송을 통해 한 스트림의 손실이 다른 스트림의 진행까지 막는 문제를 줄인다.

아래 예시는 HTTP/1.0과 HTTP/1.1 메시지를 기준으로 한다. 시작 줄과 헤더가 텍스트로 표현되므로 메시지 구조를 직접 확인하기 좋다.

HTTP 코드로 확인하는 메시지 처리

HTTP 요청 파싱 — tiny.c의 doit()

Tiny Web Server는 CS:APP(Computer Systems: A Programmer’s Perspective) 교재에서 제공하는 교육용 HTTP/1.0 서버다. doit() 함수는 클라이언트의 HTTP 요청을 읽고 파싱하기 시작하는 지점이다.

먼저 확인할 부분은 HTTP 요청의 첫 줄인 요청 라인을 메서드 URI 버전 세 토큰으로 나누는 과정이다. 이 교육용 서버에서는 sscanf로 공백을 기준으로 분리해 기본 정보를 얻는다. 이는 HTTP/1.0 요청 라인이 텍스트로 표현되기 때문에 가능한 단순한 파싱 방식이다.

HTTP 응답 생성 — tiny.c의 정적 콘텐츠 전송

이 함수는 서버가 정적 파일을 찾은 뒤 HTTP 응답 메시지를 조립해 소켓에 쓰는 과정을 보여 준다.

여기서는 두 가지를 기억하면 된다. 첫째, 응답 메시지를 snprintf로 이어 붙여 만든다. HTTP/1.0의 시작 줄과 헤더가 텍스트이므로 printf 계열 함수로 조립할 수 있다. 둘째, 헤더를 먼저 보내고(Rio_writen(fd, buf, ...)) 본문을 이어서 보낸다(Rio_writen(fd, srcp, ...)). 두 영역의 경계는 빈 줄(\r\n)이다.

오류 응답 — tiny.c의 clienterror()

클라이언트가 서버에서 처리할 수 없는 요청을 보내거나 존재하지 않는 파일을 요청하면, 서버는 상태 코드와 간단한 HTML 본문으로 오류를 알린다.

clienterror(fd, filename, "404", "Not found", "Tiny couldn't find this file")로 호출하면 HTTP/1.0 404 Not found 응답이 만들어진다. 상태 코드와 사유 구문을 인자로 받아 상태 라인에 반영하는 구조다.

HTTP/1.0의 기본적인 처리에서는 요청과 응답이 끝난 뒤 TCP 연결을 닫는다. HTTP/1.1에서는 기본적으로 연결을 유지하므로, ⑥에서 연결을 닫는 대신 같은 연결로 다음 요청을 보낼 수 있다.

정리: HTTP 메시지를 다시 읽는 기준

HTTP는 요청과 응답으로 웹 통신의 의미를 표현한다. 클라이언트가 메서드 URI 버전 형식의 요청 라인을 보내면 서버는 버전 상태코드 사유구문 형식의 상태 라인으로 처리 결과를 알리고, 필요한 경우 본문을 돌려준다. HTTP/1.x에서 헤더와 본문은 빈 줄(\r\n)로 구분한다. 또한 각 요청은 독립적으로 처리되므로, 로그인처럼 요청 사이에 상태를 이어야 할 때는 쿠키와 세션 같은 별도의 상태 관리 수단이 필요하다.
