BSD 소켓 — 네트워크 통신을 파일처럼 다루는 표준 인터페이스

BSD 소켓은 네트워크 연결을 파일 디스크립터로 추상화해, read()/write()만으로 다른 컴퓨터와 데이터를 주고받게 해 주는 시스템 콜 묶음이다.

BSD 소켓 오해

두 컴퓨터가 네트워크로 연결되어 있다고 하자. 한쪽 프로그램이 다른 쪽 프로그램에게 “Hello”를 보내고 싶다. 그런데 프로그램이 직접 만질 수 있는 건 자기 메모리뿐이다. 랜 카드를 어떻게 건드려야 하는지, 패킷 헤더를 어떻게 붙이는지, TCP가 순서를 어떻게 맞추는지를 프로그램이 일일이 알아야 한다면 네트워크 프로그램은 아무도 못 만든다.

그래서 운영체제가 중간에 끼어든다. 복잡한 네트워크 동작을 전부 커널이 처리하고, 프로그램에는 단순한 손잡이 하나만 내준다. 이 손잡이가 소켓 (Socket)이다.

소켓의 핵심 아이디어는 “네트워크 연결을 파일처럼 보이게 한다”는 것이다. 유닉스에서 파일을 열면 open()이 작은 정수, 즉 파일 디스크립터 (File Descriptor)를 돌려준다. 소켓도 똑같이 정수 하나를 돌려준다. 그 정수에 read()를 하면 상대가 보낸 데이터가 들어오고, write()를 하면 상대에게 데이터가 나간다. 파일을 읽고 쓰는 것과 코드 모양이 거의 같다.

  • 소켓을 모르면: 웹 서버, 채팅 서버, 게임 서버가 어떤 시스템 콜 위에서 도는지 설명할 수 없다.
  • 파일 디스크립터와의 관계를 모르면: 왜 네트워크 연결에 read()/write()/close()를 그대로 쓰는지, 왜 select()/epoll()이 소켓과 파일을 같이 감시하는지 이해 못 한다.
  • 호출 순서를 모르면: bind()가 먼저인지 listen()이 먼저인지, 서버와 클라이언트가 어디서 갈라지는지 헷갈린다.

파일처럼 다루는 네트워크 연결

비유 — 가게 전화와 손님 전화

소켓은 전화기에 가깝다. 다만 가게(서버)와 손님(클라이언트)이 전화기를 쓰는 방식이 다르다.

  • 가게는 대표 번호를 받아(bind) 전화기를 “받을 준비” 상태로 둔다(listen). 전화가 오면 받는다(accept).
  • 손님은 전화기를 들고(socket) 가게 번호로 건다(connect).
  • 통화가 연결되면 양쪽 다 말하고 듣는다(read/write).
  • 용건이 끝나면 끊는다(close).

중요한 점이 하나 있다. 가게는 대표 번호로 직접 통화하지 않는다. 대표 번호는 “전화를 받는 창구”일 뿐이고, 실제 통화는 accept()가 새로 만들어 주는 별도 회선에서 이뤄진다. 그래서 서버에는 소켓이 두 종류 생긴다. 연결을 받기만 하는 듣기 소켓(listening socket)과, 손님 한 명과 실제로 대화하는 연결 소켓(connected socket)이다.

정의 — 소켓 = (IP 주소, 포트, 프로토콜)을 묶은 통신

소켓 하나는 통신의 한쪽 끝을 가리킨다. 그 끝을 특정하려면 세 가지가 필요하다.

  • IP 주소: 어느 컴퓨터인가
  • 포트 번호: 그 컴퓨터의 어느 프로그램인가
  • 프로토콜: TCP인가 UDP인가

socket()을 호출할 때 이 셋의 큰 틀을 정한다. 첫 인자 AF_INET은 IPv4 주소를, SOCK_STREAM은 연결 지향 바이트 스트림(즉 TCP)을, SOCK_DGRAM은 비연결 데이터그램(즉 UDP)을 뜻한다. TCP와 UDP의 차이는 IP와 UDP 문서에서 다룬다.

동작 순서 — 서버와 클라이언트가 갈라지는 지점

서버와 클라이언트는 모두 socket()으로 파일 디스크립터를 만드는 데서 시작한다. 서버는 이 소켓에 bind()로 IP와 포트를 붙인 다음, listen()으로 연결 요청을 기다리는 상태로 바꾼다. 이어서 accept()에서 클라이언트의 요청을 기다린다. 클라이언트는 서버처럼 대기하지 않고, socket() 다음에 connect()를 호출해 서버에 연결을 요청한다.

클라이언트의 connect() 요청과 서버의 accept()가 만나 연결이 성사된다. accept()는 요청이 들어올 때까지 블록되며, 연결이 성사되면 해당 클라이언트와 통신할 새 연결 소켓을 반환한다. 서버는 이 연결 소켓으로 read()와 write()를 수행하고, 기존 듣기 소켓은 다음 연결을 받을 수 있도록 남겨 둔다. 클라이언트도 연결 뒤에는 write()와 read()로 데이터를 교환한다. 양쪽은 통신을 마치면 각자의 연결 소켓을 close()한다.

따라서 호출 순서는 서버의 socket() → bind() → listen() → accept()와 클라이언트의 socket() → connect()로 나뉜다. 두 흐름이 갈라지는 지점은 서버가 bind()로 대기할 주소를 정하는 단계다.

구체적으로 — 주소를 바이트로 채운다

추상적으로 “IP와 포트를 붙인다”고 했지만, 실제로는 구조체 한 덩어리를 바이트 단위로 채우는 일이다. IPv4 주소는 struct sockaddr_in에 담는다.

  • sin_family: 주소 체계. AF_INET이면 IPv4. (2바이트)
  • sin_port: 포트 번호. 16비트라 0~65535. (2바이트)
  • sin_addr: IP 주소. 32비트. (4바이트)

여기서 함정이 하나 있다. 포트 9000을 그대로 넣으면 안 된다. 네트워크는 빅 엔디언(big-endian, 큰 자리부터 저장)을 표준으로 쓰는데, x86 CPU는 리틀 엔디언(little-endian, 작은 자리부터 저장)이다. 그래서 호스트 표기를 네트워크 표기로 바꾸는 변환이 필요하다.

  • htons(): host to network short. 포트(16비트) 변환.
  • htonl(): host to network long. IP 주소(32비트) 변환.

포트 9000(16진수 0x2328)을 예로 들면, 리틀 엔디언 메모리에는 28 23로 들어 있다. htons()가 이걸 네트워크 표준인 23 28 순서로 뒤집는다. 이 변환을 빠뜨리면 9000번이 아니라 엉뚱한 포트(0x2823 = 10275)에 연결을 시도한다.

BSD 소켓 코드

실제 코드는 이 볼트의 웹 프록시 랩에 있는 echo 서버/클라이언트로 확인한다. 두 프로그램은 한 줄을 받아 그대로 되돌려 보내는 가장 단순한 TCP 통신이다.

서버 1 — 소켓을 만들고 주소에 붙이기

서버는 먼저 소켓을 만들고, 재시작을 쉽게 하는 옵션을 켠 뒤, 주소 구조체를 채워 bind()한다.

INADDR_ANY는 “이 컴퓨터의 모든 IP에서 연결을 받겠다”는 뜻이다. bind()가 끝나면 이 소켓은 비로소 특정 포트에 묶인다. 여기까지는 아직 연결을 받지 않는다.

서버 2 — 대기하고 연결을 받기

listen()으로 소켓을 수동 대기 상태로 바꾸고, accept()로 들어오는 연결을 하나씩 꺼낸다.

여기서 listenfd와 connfd는 서로 다른 소켓이다. listenfd는 연결을 받는 창구로 계속 살아 있고, 실제 데이터 교환은 accept()가 돌려준 connfd에서만 일어난다.

서버 3 — 파일처럼 읽고 쓰기

연결 소켓에는 특별한 네트워크 함수가 따로 없다. 파일에 쓰던 read()/write()를 그대로 쓴다.

write() 한 번이 요청한 바이트를 다 보낸다는 보장이 없다. TCP는 바이트 스트림이라 중간까지만 쓰일 수 있다. 그래서 다 보낼 때까지 반복하는 짧은 루프가 네트워크 코드의 기본기다.

클라이언트 — 이름을 주소로 바꾸고 연결하기

클라이언트는 socket() 다음에 bind/listen/accept 없이 곧장 connect()로 간다. 그 전에 사람이 쓰는 이름(“127.0.0.1”, “example.com”)을 실제 소켓 주소로 바꿔 주는 getaddrinfo()를 거친다.

getaddrinfo()가 돌려준 주소 후보를 위에서부터 하나씩 connect()로 시도하고, 처음 성공한 소켓을 쓴다. 이름을 주소로 바꾸는 일은 DNS가 담당한다. 이 코드는 그 결과를 받아 소켓에 꽂는 자리다.

정리

  • 소켓은 네트워크 연결을 파일 디스크립터로 추상화한다. 그래서 연결을 만든 뒤에는 read()/write()/close()로 파일처럼 다룬다.
  • 서버는 socket() → bind() → listen() → accept() 순서로 수동 대기하고, 클라이언트는 socket() → connect()로 능동 연결한다. 갈라지는 지점은 bind()부터다.
  • 서버에는 소켓이 둘 생긴다. 연결을 받는 듣기 소켓(listenfd)과 손님 한 명과 대화하는 연결 소켓(connfd)이다. 이 둘을 섞으면 동작을 설명할 수 없다.
  • 주소는 구조체에 바이트로 채운다. 포트·IP는 htons()/htonl()로 네트워크 바이트 순서로 바꿔야 한다. 이 변환을 빠뜨리면 엉뚱한 포트로 간다.

판단 기준: “이 코드가 서버인가 클라이언트인가”는 bind()/listen()/accept()가 있는지로 가른다. “왜 소켓이 두 개인가”는 듣는 창구와 통화 회선을 분리했기 때문이라고 답하면 된다.

이어서 읽기

클라이언트 쪽 getaddrinfo()는 이름을 주소로 바꾸는 과정과 맞닿아 있고, SOCK_STREAM과 SOCK_DGRAM의 차이는 전송 계층 선택으로 이어진다. 소켓이 정수처럼 보이는 이유는 파일 디스크립터에서 다시 확인할 수 있다.
