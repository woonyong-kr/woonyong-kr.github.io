HTTP 메서드 — GET·POST·PUT·DELETE가 나누는 요청의 의미

확인 범위: 이 문서는 HTTP 메서드의 일반적인 의미와 안전성·멱등성에 따른 선택 기준을 개념적으로 설명하며, 포함된 프록시 코드는 요청 라인에서 메서드를 분리하고 GET 이외의 요청을 거절하는 특정 구현의 예시다. 실제 코드의 동작 범위와 버전별 세부 동작, 캐시·재전송 특성 및 성능에 관한 판단은 해당 구현과 실행 기록·측정을 별도로 확인해야 한다.

HTTP 메서드는 요청 라인의 첫 단어로, 같은 자원에 대해 “읽어라·만들어라·바꿔라·지워라” 중 무엇을 할지를 서버에 알려주는 동사다.

요청 흐름에서 보이는 HTTP 메서드

브라우저로 같은 주소 http://example.com/users/42에 접속한다고 하자. 어떤 때는 그 사용자의 정보를 화면에 보여주고, 어떤 때는 그 사용자를 삭제하고 싶다. 주소(URI)는 똑같이 /users/42인데, 서버는 둘을 어떻게 구분하는가?

URI는 “어떤 자원에 대해”만 가리킨다. “그 자원에 무엇을 할지”는 URI에 들어 있지 않다. 그래서 요청에는 동작을 나타내는 단어가 따로 필요하다. 그 단어가 HTTP 메서드 (HTTP Method)다. 요청 라인의 맨 앞에 온다.

메서드를 모르면 다음을 이해할 수 없다.

  • 같은 URI로 조회와 삭제가 어떻게 갈라지는지.
  • <form method="post">가 왜 주소창 입력과 다르게 동작하는지.
  • REST API에서 자원 하나에 여러 동작을 어떻게 매핑하는지.
  • 프록시·캐시·브라우저가 왜 GET 응답은 캐시하고 POST 응답은 캐시하지 않는지.

요청 첫 단어가 정하는 동작

메서드는 요청에 붙는 “동사”다

식당에 비유하면 이렇다. 자원(URI)이 “테이블 5번”이라는 명사라면, 메서드는 “안내해라(읽기)”, “주문 받아라(생성)”, “주문 바꿔라(수정)”, “치워라(삭제)“라는 동사다. 같은 테이블이라도 어떤 동사를 붙이느냐에 따라 직원이 하는 일이 완전히 달라진다.

HTTP 요청은 항상 동사(메서드) + 명사(URI) 꼴로 시작한다. 서버는 이 둘을 함께 보고 무엇을 할지 결정한다.

주요 메서드와 의미

  • GET — 자원을 조회한다. 서버 상태를 바꾸지 않는다.
  • POST — 새 자원을 만들거나, 분류되지 않는 처리를 요청한다. 보통 본문(body)에 데이터를 담는다.
  • PUT — 자원을 통째로 교체한다. 그 자리에 자원이 없으면 새로 만들 수도 있다. CRUD의 “수정”은 HTTP에서는 보통 PUT이나 PATCH로 나뉜다.
  • PATCH — 자원의 일부 필드만 부분 수정한다.
  • DELETE — 자원을 삭제한다.
  • HEAD — GET과 같지만 본문 없이 헤더만 받는다. 파일 크기나 존재 여부 확인용.
  • OPTIONS — 해당 자원이 어떤 메서드를 허용하는지 묻는다. CORS 사전 요청에 쓰인다.

안전성과 멱등성 — 메서드를 가르는 두 기준

메서드를 고를 때 판단 기준이 되는 두 성질이 있다.

  • 안전성 (Safe): 서버 상태를 바꾸지 않는가. GET, HEAD, OPTIONS가 안전하다. 안전한 메서드는 몇 번을 호출해도 데이터가 변하지 않으므로 캐시·프리페치 대상이 된다.
  • 멱등성 (Idempotent): 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은가. GET, PUT, DELETE가 멱등하다.

PUT /users/42로 이름을 “김”으로 세 번 바꿔도 최종 상태는 “이름=김” 하나다. 그래서 멱등하다. 반면 POST /users는 호출할 때마다 사용자가 한 명씩 늘어난다. 그래서 멱등하지 않다.

이 성질이 중요한 이유는 네트워크 재전송 때문이다. 응답이 유실되어 클라이언트가 같은 요청을 다시 보낼 때, 멱등한 메서드는 안전하게 재시도할 수 있지만 POST는 중복 생성 위험이 있다.

GET과 POST — 데이터를 싣는 위치가 다르다

  • GET은 데이터를 URI의 질의 문자열 (Query String)에 싣는다. 예: /search?q=cat&page=2. 주소창에 그대로 노출되고 길이 제한이 있으며 브라우저 기록·서버 로그에 남는다.
  • POST는 데이터를 메시지 본문(body)에 싣는다. URI에 드러나지 않고 길이 제한이 사실상 없으며, 로그인 비밀번호처럼 노출되면 안 되는 값에 적합하다.

HTTP 메서드 코드

서버는 메서드를 어떻게 읽어낼까. 추상적으로 “요청 라인의 첫 단어”라고 했는데, 실제 코드에서는 바이트로 들어온 요청 줄을 공백으로 쪼개 첫 토큰을 메서드로 꺼낸다.

요청 라인에서 메서드를 파싱한다

아래는 웹 프록시 학습 프로젝트에서 클라이언트 요청의 첫 줄을 읽어 메서드를 분리하는 실제 코드다.

요청 라인 GET /index.html HTTP/1.1은 공백으로 나뉜 세 토큰이다. sscanf의 %s %s %s가 각각 method, uri, version에 담는다. 첫 토큰이 곧 HTTP 메서드다. 이 프록시는 GET만 구현했으므로 다른 메서드는 501 Not Implemented로 거절한다. 서버 코드에서 메서드는 요청 첫 줄의 첫 단어, 즉 짧은 문자열로 출발한다.

같은 URI, 다른 메서드 — 실제 요청 바이트

URI는 둘 다 /users/42로 같다. 다른 것은 첫 단어(GET vs PUT)와 본문의 유무뿐이다. 서버는 이 첫 단어를 보고 분기한다.

정리

HTTP 메서드는 요청 라인 첫 단어로, URI가 가리키는 자원에 무엇을 할지를 정하는 동사다. GET은 조회, POST는 생성, PUT/PATCH는 수정, DELETE는 삭제를 뜻한다. 메서드를 고를 때 판단 기준은 두 가지다. 서버 상태를 바꾸는가(안전성), 여러 번 호출해도 결과가 같은가(멱등성). 이 기준이 캐시 가능 여부와 재전송 안전성을 결정한다. 서버 입장에서 메서드는 거창한 것이 아니라, 공백으로 쪼갠 요청 첫 줄의 첫 문자열일 뿐이다.

이어서 읽기

메서드가 어떤 자원 URI와 만나는지 보면 REST API 설계가 보이고, 요청 라인 전체 구조를 보면 HTTP 메시지 파싱이 더 분명해진다.
