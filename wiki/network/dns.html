DNS 이름 해석

DNS 이름 해석

확인 범위: 이 문서는 DNS 이름 해석의 계층 구조, 위임, 캐시·TTL, 레코드와 전송 방식 및 getaddrinfo() 사용을 일반 원리와 선택·진단 기준 중심으로 설명한다. 제시된 코드와 dig 출력은 개념을 보여 주는 예시이며, 특정 구현·버전에서의 동작이나 실제 실행 기록·성능 측정을 검증한 결과로 보아서는 안 된다.

DNS(Domain Name System)는 example.com 같은 사람이 외우는 이름을 93.184.216.34 같은 컴퓨터가 쓰는 IP 주소로 바꿔 주는, 전 세계에 분산된 이름 해석 시스템이다.

DNS 이름 해석 혼동

네트워크에서 실제로 통신할 때 컴퓨터는 IP 주소만 안다. 패킷에는 “어느 IP로 보낼지”가 적히지, “어느 이름으로 보낼지”가 적히지 않는다. 앞서 본 소켓 코드도 결국 connect()에 IP 주소가 담긴 구조체를 넘긴다.

그런데 사람은 93.184.216.34를 외우지 못한다. 숫자 주소는 외우기 어렵고, 서버를 옮기면 주소가 바뀌며, 한 서비스가 여러 주소를 쓰기도 한다. 그래서 사람은 example.com 같은 이름을 쓰고, 어딘가에서 그 이름을 주소로 바꿔 줘야 한다.

이 변환을 한 군데 거대한 표에 몰아넣으면 곧 무너진다. 전 세계 수억 개 도메인을 한 서버가 다 관리하면, 그 서버가 멈추는 순간 인터넷 전체의 이름 해석이 멈춘다. 갱신도 병목이 된다. 그래서 DNS는 표를 전 세계에 잘게 쪼개 나눠 맡기고, 질문을 위에서 아래로 넘겨 가며 답을 찾는 분산 구조로 설계됐다.

  • DNS를 모르면: 브라우저에 주소를 쳤을 때 실제 연결이 시작되기 전에 무슨 일이 일어나는지 설명할 수 없다.
  • 분산 구조를 모르면: 왜 한 회사가 인터넷 전체의 이름을 관리하지 않는지, 도메인을 사면 왜 전파에 시간이 걸리는지 이해 못 한다.
  • 캐시를 모르면: 같은 사이트를 두 번째 열 때 왜 더 빠른지, DNS 변경이 왜 바로 반영되지 않는지 감이 안 잡힌다.

이름을 주소로 찾는 계층 구조

비유 — 모르는 번호를 단계별로 물어보기

DNS는 한 권의 전화번호부가 아니라, 여러 안내소가 단계별로 떠넘기는 구조다. www.example.com의 주소를 찾는 과정은 이렇게 비유할 수 있다.

  • 먼저 동네 안내소(로컬 DNS, 보통 통신사나 8.8.8.8)에게 묻는다.
  • 동네 안내소가 모르면, 최상위 안내소(루트 서버)에게 “.com 담당이 누구냐”고 묻는다.
  • 루트는 “.com은 저쪽 TLD 안내소에 물어봐”라고 알려 준다.
  • TLD 안내소는 “example.com은 저쪽 권한 있는 서버가 안다”고 알려 준다.
  • 마지막 권한 있는 서버(authoritative)가 실제 주소를 답한다.

각 안내소는 자기 담당만 알고, 나머지는 “다음에 누구한테 물어보라”고 길만 알려 준다. 이렇게 책임을 나눴기 때문에 어느 한 곳이 모든 이름을 알 필요가 없다.

정의 — 계층적 이름 공간과 위임

도메인 이름은 점으로 나뉜 계층이다. 오른쪽이 위, 왼쪽이 아래다.

  • . (루트, 보통 생략)
  • .com (TLD, Top-Level Domain)
  • example.com (2차 도메인, 등록자가 소유)
  • www.example.com (하위 도메인, 등록자가 자유롭게 만듦)

각 계층은 아래 계층의 관리를 “위임(delegation)“한다. 루트는 .com을 누가 관리하는지만 알고, .com은 example.com을 누가 관리하는지만 안다. 실제 www의 주소는 example.com을 소유한 쪽의 권한 있는 서버만 안다.

동작 순서 — 재귀 질의의 흐름

로컬 DNS가 사용자를 대신해 위에서 아래로 물어 가는 과정을 재귀 질의(recursive query)라 한다.

%% DNS 재귀 질의 — 로컬 DNS가 루트, TLD, 권한 서버를 차례로 물어 주소를 찾는 과정
flowchart TD
  s1["① 클라이언트 → Resolver<br/>www.example.com 주소?"]
  s2["② Resolver ↔ Root<br/>.com 담당 누구? → TLD 서버 주소"]
  s3["③ Resolver ↔ TLD(.com)<br/>example.com 담당? → 권한 서버 주소"]
  s4["④ Resolver ↔ 권한 서버<br/>www.example.com 주소? → 93.184.216.34 (A 레코드)"]
  s5["⑤ Resolver → 클라이언트<br/>93.184.216.34 응답, TTL 동안 캐시 저장"]
  s1 --> s2
  s2 --> s3
  s3 --> s4
  s4 --> s5

사용자 PC는 로컬 DNS에 한 번만 묻는다. 위로 올라가며 여러 번 묻는 수고는 로컬 DNS가 대신한다. 그래서 사용자 입장에서는 “물어봤더니 주소가 왔다”로 끝난다.

구체적으로 — 레코드 타입과 TTL

DNS가 돌려주는 답은 단순한 IP 하나가 아니라 “레코드(record)“라는 항목이다. 자주 쓰는 종류는 다음과 같다.

  • A: 이름 → IPv4 주소 (예: example.com → 93.184.216.34)
  • AAAA: 이름 → IPv6 주소
  • CNAME: 이름 → 다른 이름 (별칭. www.example.com → example.com)
  • MX: 메일 서버 지정
  • NS: 이 도메인을 관리하는 권한 서버 지정

각 레코드에는 TTL(Time To Live)이 붙는다. 초 단위 숫자이며 “이 답을 몇 초 동안 믿고 캐시해도 되는가”를 뜻한다. TTL이 300이면 로컬 DNS와 PC는 5분 동안 다시 묻지 않고 캐시된 주소를 쓴다.

이 캐시가 두 가지를 동시에 설명한다. 같은 사이트를 두 번째 열 때 빠른 이유는 답이 캐시에 있어 위로 묻지 않기 때문이고, 도메인 주소를 바꿔도 한동안 옛 주소로 가는 이유는 TTL이 끝나기 전까지 캐시가 옛 답을 들고 있기 때문이다.

dig 명령으로 실제 응답을 직접 볼 수 있다.

응답 한 줄에 이름, TTL(86400초 = 24시간), 클래스(IN = 인터넷), 타입(A), 그리고 실제 주소가 들어 있다. 위 동작 순서 다이어그램의 마지막 단계에서 권한 서버가 돌려준 것이 바로 이 A 레코드다. (주소 값은 예시이며 실제 값은 시점에 따라 다르다.)

전송 계층 관점 — DNS는 보통 UDP를 쓴다

DNS 질의는 대개 짧은 한 번의 질문과 답이다. 매번 TCP로 연결을 맺고 끊으면 느리다. 그래서 DNS는 기본적으로 포트 53번에서 UDP를 쓴다. 응답이 너무 커서 한 패킷에 안 들어가거나(예: DNSSEC) 영역 전송 같은 특수한 경우에만 TCP로 넘어간다. UDP와 TCP의 차이는 IP와 UDP에서 다룬다.

DNS 이름 해석 코드

프로그램은 보통 DNS 패킷을 직접 만들지 않는다. 표준 라이브러리의 getaddrinfo()를 부르면 그 안에서 로컬 DNS 질의와 캐시 조회가 일어나고, 결과로 바로 소켓에 꽂을 수 있는 주소 구조체가 나온다. 앞의 BSD 소켓 문서에서 본 클라이언트 코드가 그 자리다.

getaddrinfo()가 후보 주소를 여러 개 돌려주는 이유는 한 이름에 A 레코드가 여러 개이거나 IPv4와 IPv6가 함께 있을 수 있기 때문이다. 그래서 코드는 후보를 순서대로 시도한다. DNS의 분산·다중 응답 특성이 코드의 반복문 모양으로 그대로 드러난다.

정리

  • DNS는 사람이 쓰는 이름을 컴퓨터가 쓰는 IP 주소로 바꾼다. 통신 자체는 항상 IP로 하므로, 연결 전에 반드시 이름 해석이 먼저 일어난다.
  • 표를 한 곳에 두지 않고 루트 → TLD → 권한 서버로 위임해 나눈다. 그래서 어느 한 서버도 모든 이름을 알 필요가 없고, 한 곳이 멈춰도 전체가 멈추지 않는다.
  • 답에는 TTL이 붙고 캐시된다. 두 번째 접속이 빠른 것도, 주소 변경이 바로 반영되지 않는 것도 모두 이 캐시와 TTL로 설명된다.
  • 프로그램은 getaddrinfo()로 이름 해석을 위임받는다. 결과는 소켓에 바로 꽂을 수 있는 주소 후보 목록이다.

판단 기준: “주소가 바뀌었는데 왜 아직 옛 사이트로 가지” 같은 문제는 거의 항상 TTL과 캐시로 설명된다. “이름 해석이 실패했나 연결이 실패했나”는 getaddrinfo()가 실패했는지 connect()가 실패했는지로 가른다.

이어서 읽기

getaddrinfo()가 돌려준 주소는 소켓 연결에 바로 쓰이고, DNS 질의가 짧은 요청과 응답으로 끝나는 이유는 전송 계층 선택과 이어진다. 이름 해석과 연결이 끝난 뒤에는 HTTP 요청이 그 위에 올라간다.

  • IP와 UDP
