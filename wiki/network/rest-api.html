REST API — 자원과 HTTP 메서드로 설계하는 웹 인터페이스

REST는 서버의 데이터를 “자원(URI)“으로 보고, 그 자원에 대한 동작을 HTTP 메서드로 표현하기로 약속한 API 설계 스타일이다.

요청 흐름에서 보이는 REST API

서버에 “게시글 목록을 달라”, “새 글을 써라”, “3번 글을 고쳐라”, “3번 글을 지워라” 같은 요청을 보내야 한다고 하자. 각 팀이 제멋대로 주소를 지으면 다음처럼 된다.

동작마다 새 주소가 생기고, 이름 짓는 규칙이 사람마다 다르다. API를 쓰는 쪽은 주소 하나하나를 외워야 하고, 같은 “삭제”가 delete인지 remove인지 추측해야 한다. 동사가 URI 안에 섞여 들어가 URI가 폭발한다.

여기서 관점을 바꾼다. 주소는 “동작”이 아니라 “대상(자원)“만 가리키게 하고, 동작은 이미 표준으로 정해진 HTTP 메서드에 맡기면 어떨까. 그러면 위 다섯 줄이 자원 하나 /posts와 메서드 조합으로 줄어든다. 이 발상이 REST(REpresentational State Transfer)다.

REST를 모르면 다음을 이해할 수 없다.

  • 왜 잘 만든 API는 /users, /users/42처럼 명사만 쓰고 동사를 안 쓰는지.
  • 같은 /users 주소가 GET이면 목록, POST면 생성이 되는 이유.
  • 상태 코드 201, 404, 409가 왜 그 상황에 쓰이는지.

자원과 동작을 나누는 방식

자원 — 동작이 아니라 대상에 이름을 붙인다

REST의 출발점은 “모든 것을 자원(Resource)으로 본다”는 것이다. 사용자, 게시글, 주문 같은 데이터 하나하나가 자원이고, 각 자원에는 고유한 주소(URI)가 있다.

도서관에 비유하면 이렇다. 책 한 권 한 권에 청구기호(URI)가 붙어 있다. “빌려라”, “반납해라”, “버려라”는 책 제목에 적지 않는다. 그 동작은 사서에게 표준 절차(메서드)로 요청한다. 청구기호는 오직 “어떤 책인가”만 가리킨다.

URI 설계 규칙은 단순하다.

  • 명사를 쓴다: /users, /posts. 동사 /getUsers는 쓰지 않는다.
  • 컬렉션은 복수형: /users는 사용자 전체, /users/42는 그중 42번 한 명.
  • 계층은 경로로: /users/42/posts는 42번 사용자의 게시글들.

동작은 HTTP 메서드로 — CRUD 매핑

자원에 대한 네 가지 기본 동작(생성·조회·수정·삭제, 줄여서 CRUD)을 HTTP 메서드에 대응시킨다.

  • 목록 조회: GET /users → 사용자 전체
  • 단건 조회: GET /users/42 → 42번 사용자
  • 생성: POST /users → 새 사용자 추가
  • 전체 수정: PUT /users/42 → 42번 사용자 통째로 교체
  • 부분 수정: PATCH /users/42 → 42번 사용자 일부 필드만
  • 삭제: DELETE /users/42 → 42번 사용자 제거

URI는 단 두 개(/users, /users/42)지만 메서드 조합으로 여섯 동작이 나온다. 메서드의 안전성·멱등성 성질이 여기서 그대로 의미를 가진다. 자세한 메서드 성질은 HTTP 메서드에 정리되어 있다.

상태 코드로 결과를 알린다

REST는 동작의 결과도 표준 HTTP 상태 코드로 돌려준다. 본문 메시지로 “성공했어요”를 적는 대신, 숫자 코드로 기계가 판단할 수 있게 한다.

  • 200 OK — 조회·수정 성공.
  • 201 Created — 생성 성공. 보통 Location 헤더에 새 자원 URI를 담는다.
  • 204 No Content — 성공했지만 돌려줄 본문이 없음. 삭제 응답에 자주 쓰인다.
  • 400 Bad Request — 요청 형식이 잘못됨.
  • 404 Not Found — 그 URI의 자원이 없음.
  • 409 Conflict — 중복 생성 등 현재 상태와 충돌.

무상태(Stateless) — 서버는 이전 요청을 기억하지 않는다

REST에서는 무상태성도 중요하다. 각 요청은 그 자체로 처리에 필요한 정보를 모두 담아야 하고, 서버는 “이 클라이언트가 직전에 무엇을 했는지”를 저장하지 않는다.

왜 이렇게 설계하는가. 서버가 클라이언트별 대화 상태를 기억하지 않으면, 요청을 아무 서버 인스턴스로나 보내도 똑같이 처리된다. 그래서 서버를 여러 대로 늘려 부하를 나누기(수평 확장) 쉽다. 대신 인증 토큰처럼 매 요청에 필요한 정보는 클라이언트가 매번 함께 보내야 한다.

REST API 코드

추상적으로 “자원 + 메서드”라고 했는데, 실제 주고받는 바이트와 서버의 라우팅 테이블로 내려가 본다.

자원 하나에 대한 CRUD 요청·응답

생성은 201과 함께 새 자원 주소 /users/42를 Location에 담아 돌려준다. 조회는 200과 자원의 현재 표현(JSON)을, 삭제는 돌려줄 내용이 없으므로 204만 보낸다. REST 요청을 읽을 때는 URI가 자원만, 메서드가 동작을, 상태 코드가 결과를 맡는다고 나눠 보면 된다.

서버의 라우팅 — 메서드+경로를 핸들러에 매핑

REST 서버는 “메서드 + URI 패턴”을 받아 해당 핸들러로 분기한다. 의사 코드로 보면 매핑 구조가 드러난다.

같은 경로 /users라도 (메서드, 경로) 쌍이 키이므로 GET과 POST가 서로 다른 핸들러로 간다. 메서드를 동작으로 쓰는 REST의 핵심이 이 매핑 한 줄에 담겨 있다. 요청 첫 줄을 파싱해 method와 path를 꺼내는 실제 코드는 HTTP 메서드 문서의 프록시 예시에서 확인할 수 있다.

정리

REST는 서버의 데이터를 자원으로 보고 URI로 가리키되, 그 자원에 대한 동작은 URI에 동사를 넣는 대신 HTTP 메서드로 표현하는 설계 스타일이다. URI는 명사(대상), 메서드는 동사(동작), 상태 코드는 결과를 각각 분담한다. 무상태성 덕분에 서버를 수평으로 늘리기 쉽다. API를 설계하거나 평가할 때 판단 기준은 분명하다. URI에 동사가 섞여 있으면 REST답지 않은 신호이고, 같은 자원의 서로 다른 동작이 메서드로 깔끔하게 갈라지면 잘 설계된 것이다.
