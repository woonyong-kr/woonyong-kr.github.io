CDN — 전 세계에 흩어진 서버로 콘텐츠를 사용자 가까이에서 전달하는 구조

확인 범위: 이 문서는 CDN의 요청 흐름, 캐시·TTL의 일반 원리와 콘텐츠별 선택 기준을 설명하며, 제시된 거리·지연·적중률 계산과 코드·응답 헤더는 개념 이해를 위한 가정 및 예시다. 특정 CDN 구현이나 서비스 버전에서 실행·측정해 검증한 결과는 아니므로, 실제 동작과 성능은 해당 환경의 코드, 설정, 실행 기록과 측정으로 별도 확인해야 한다.

CDN(Content Delivery Network)은 같은 콘텐츠의 사본을 세계 곳곳의 서버에 미리 복제해 두고, 사용자에게 가장 가까운 서버가 응답하게 만들어 거리에서 오는 지연을 줄이는 분산 전달망이다.

요청 흐름에서 보이는 CDN

웹 서버 한 대가 서울에 있다고 하자. 서울 사용자가 접속하면 빠르다. 그런데 브라질 상파울루 사용자가 같은 서버에 접속하면 어떨까.

데이터는 빛보다 빠를 수 없다. 서울과 상파울루는 직선 거리로 약 18,000km 떨어져 있다. 광케이블 안에서 빛은 진공보다 느려 초속 약 20만 km로 움직인다. 한 번 가는 데만 18,000 / 200,000 = 0.09초, 즉 90ms가 걸린다. 왕복(RTT)이면 180ms다.

문제는 한 번 왕복으로 끝나지 않는다는 점이다. TCP 연결을 세우는 3-way handshake가 1회 왕복, TLS 협상이 추가 왕복, 그리고 실제 HTTP 요청·응답이 또 왕복이다. 합치면 페이지 하나 여는 데 왕복만 서너 번 쌓인다. 180ms × 4 ≈ 0.7초가 거리 때문에 그냥 날아간다. 서버가 아무리 빨라도 이 지연은 줄지 않는다.

서버를 늘려도 같은 문제다. 상파울루 사용자를 위해 서울 서버를 더 강하게 만들어 봐야 거리는 그대로다. 필요한 것은 더 강한 서버가 아니라 더 가까운 서버다.

  • CDN을 모르면: 같은 이미지·동영상·JS 파일이 왜 여러 나라에서 빠르게 열리는지, 트래픽이 몰려도 원본 서버가 왜 안 죽는지 설명할 수 없다.
  • 캐시(Cache)를 모르면: 한 번 받은 콘텐츠를 왜 다시 원본까지 가서 받지 않는지, 파일을 바꿨는데 왜 바로 안 바뀌는지 이해 못 한다.
  • DNS 기반 라우팅을 모르면: 같은 주소를 입력했는데 사람마다 다른 서버로 연결되는 이유를 놓친다.

가까운 엣지가 대신 응답하는 구조

비유 — 편의점 체인

본사 창고가 하나만 있으면 모든 손님이 창고까지 가야 한다. 대신 동네마다 편의점을 두고 잘 팔리는 물건을 미리 채워 두면, 손님은 걸어서 몇 분 거리 편의점에서 바로 산다. 편의점에 없는 특이한 물건만 본사 창고에 주문한다.

CDN이 이 구조다. 본사 창고가 원본 서버(Origin), 동네 편의점이 **엣지 서버(Edge Server)**다. 잘 팔리는 물건이 이미지·CSS·동영상 같은 정적 콘텐츠이고, “편의점에 채워 두는 것”이 캐시다.

정의 — 엣지 서버와 PoP

CDN은 전 세계 주요 도시에 서버 무리를 배치한다. 한 지역에 모인 엣지 서버 무리를 **PoP(Point of Presence, 접속 거점)**라 부른다. 큰 CDN 업체는 전 세계에 수백 개 PoP를 둔다.

각 엣지 서버는 원본 서버의 콘텐츠 사본을 보관한다. 사용자는 원본 서버가 아니라 자기에게 가장 가까운 PoP의 엣지 서버와 통신한다. 앞에서 본 180ms 왕복이, 엣지가 같은 도시 안에 있으면 5ms 수준으로 줄어든다.

동작 순서 — 요청이 어디로 가는가

처음 배우는 사람을 위해 한 요청이 흐르는 순서를 본다.

  1. 사용자가 img.example.com/logo.png를 연다.
  2. DNS가 이 이름을 풀 때, 일반 서버 IP 하나를 주는 대신 사용자 위치에 가장 가까운 엣지 서버 IP를 돌려준다. 그래서 서울 사용자와 상파울루 사용자는 같은 이름을 입력해도 다른 IP를 받는다.
  3. 사용자는 그 엣지 서버에 HTTP 요청을 보낸다.
  4. 엣지 서버가 logo.png 사본을 이미 가지고 있으면(캐시 적중, Cache HIT) 즉시 응답한다. 원본 서버까지 가지 않는다.
  5. 사본이 없으면(캐시 미스, Cache MISS) 엣지 서버가 원본 서버에서 한 번 받아 와 사용자에게 주고, 동시에 자기 디스크에 저장한다. 다음 사용자부터는 이 사본으로 응답한다.

캐시는 언제까지 유효한가 — TTL과 Cache-Control

엣지 서버가 사본을 영원히 들고 있으면 원본이 바뀌어도 옛날 파일을 계속 준다. 반대로 매번 원본에 물어보면 CDN을 쓰는 의미가 없다. 그래서 “이 사본은 며칠/몇 초까지 신선하다”는 유효 기간을 둔다. 이 기간을 **TTL(Time To Live)**이라 한다.

TTL은 원본 서버가 HTTP 응답 헤더로 알려 준다. 대표 헤더가 Cache-Control이다.

  • Cache-Control: max-age=86400 → 이 응답은 86,400초(=24시간) 동안 신선하다. 그동안 엣지는 원본에 다시 묻지 않는다.
  • Cache-Control: no-store → 캐시에 저장하지 말라. 매번 원본으로 가라.

그래서 로고·CSS처럼 잘 안 바뀌는 파일은 max-age를 길게, 로그인 후 개인화된 페이지는 no-store로 둔다.

추상에서 구체로 — 숫자로 본 효과

서울↔상파울루 왕복 180ms, 엣지가 같은 도시면 왕복 5ms라 하자. 캐시 적중률(원본까지 안 가도 되는 비율)이 95%면, 평균 응답 거리 지연은 다음과 같이 계산된다.

평균 지연 = (적중 95% × 5ms) + (미스 5% × (5ms + 180ms)) = 4.75ms + 9.25ms = 14ms

CDN 없이 매번 180ms이던 것이 평균 14ms로 떨어진다. 약 13배 빨라진다. 적중률을 높이는 것(긴 TTL, 자주 쓰이는 파일)이 CDN 튜닝에서 중요한 이유가 여기서 나온다.

실제 OS·서비스에서는 — 정적 vs 동적

CDN은 본래 정적 콘텐츠(이미지, 동영상, JS/CSS)를 위해 만들어졌다. 같은 파일을 수많은 사용자가 똑같이 받기 때문에 캐시가 잘 맞는다. 반면 사용자마다 다른 동적 응답(예: 내 장바구니, 내 타임라인)은 캐시하기 어렵다. 최근 CDN은 엣지에서 코드를 실행하는 엣지 컴퓨팅으로 동적 영역까지 넓히고 있으나, 기본 모델은 “잘 안 바뀌고 모두가 같은 것을 받는 콘텐츠를 가까이 둔다”이다.

CDN 코드

CDN은 응답 헤더에 흔적을 남긴다. curl -I로 헤더만 받아 보면 이 요청이 엣지 서버에서 캐시로 처리됐는지 확인할 수 있다. 아래는 CDN을 거친 정적 파일 응답의 전형적인 헤더다.

x-cache: HIT은 엣지 서버가 사본으로 바로 응답했다는 뜻이다. age: 312는 캐시된 지 312초 지났다는 뜻이고, max-age=86400이므로 아직 86,088초 더 신선하다. 즉 이 요청은 원본 서버를 건드리지 않았다.

원본 서버 쪽 코드는 “이 파일을 얼마나 캐시해도 되는지”를 헤더로 선언하는 게 전부다. 정적 파일 서버에서 캐시 정책을 주는 최소 예시다.

원본은 TTL을 헤더로 알려 줄 뿐, 실제 캐시 저장·재사용은 엣지 서버가 한다. 캐시 수명을 길게 줄수록 적중률이 오르지만, 그만큼 콘텐츠 변경이 늦게 반영된다.

요청이 흐르는 경로를 그림으로 보면 다음과 같다.

  a["① 사용자 → 엣지(PoP)<br/>GET logo.png"]
  b["② 캐시 HIT?<br/>예 → 200 OK (5ms) 즉시 응답"]
  c["③ 캐시 MISS일 때만: 엣지 → 원본(Origin)<br/>GET logo.png → 200 OK (+180ms)"]
  d["④ 엣지가 사본 저장 후 사용자에 전달"]
  a --> b
  b --> c
  c --> d

캐시 적중이면 화살표가 엣지에서 끊긴다. 원본 서버까지 가는 긴 왕복은 캐시 미스일 때만 일어난다.

정리

  • CDN은 더 강한 서버가 아니라 더 가까운 서버로 거리 지연을 푸는 구조다. 같은 콘텐츠 사본을 세계 곳곳 엣지 서버에 두고, 사용자에게 가장 가까운 PoP가 응답한다.
  • 어디로 보낼지는 DNS가 사용자 위치에 맞는 엣지 IP를 돌려주며 정한다. 같은 주소라도 사람마다 다른 엣지로 간다.
  • 엣지는 캐시로 동작한다. 적중이면 원본까지 안 가고 즉시 응답하고, 미스면 원본에서 한 번 받아 와 저장한다. 신선도는 Cache-Control: max-age로 정한 TTL이 결정한다.
  • 판단 기준: 잘 안 바뀌고 모두가 같은 것을 받는 정적 콘텐츠일수록 CDN 효과가 크다. 사용자마다 다른 동적 응답은 캐시하기 어려워 효과가 작다. “이 콘텐츠는 캐시해도 되는가, TTL을 얼마로 줄까”가 CDN 설계의 첫 질문이다.

이어서 읽기

CDN이 사용자마다 다른 엣지 서버로 보내는 일은 DNS 단계에서 시작된다. 엣지가 캐시 여부를 판단할 때 보는 Cache-Control, Age 같은 값은 HTTP 헤더이고, 가까운 서버가 빨라지는 이유는 결국 전송 계층의 왕복 시간과 이어진다.
