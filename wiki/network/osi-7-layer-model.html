OSI 7계층 모델

OSI 7계층 모델

확인 범위: 이 문서는 OSI 7계층의 책임 분리, 캡슐화, TCP/IP 모델과의 관계, 계층별 디버깅 기준을 설명하는 개념 중심의 학습 자료다. 제시된 BSD 소켓 코드와 명령은 개념을 연결하기 위한 예시이며, 특정 운영체제·버전에서의 실행 결과나 실제 네트워크 환경의 동작·성능을 검증한 기록은 아니다.

OSI 모델은 네트워크 통신을 물리 → 데이터 링크 → 네트워크 → 전송 → 세션 → 표현 → 응용의 7계층으로 나눠, 각 계층이 하나의 책임만 지도록 설계한 참조 모델이다.

OSI 7계층 모델 혼동

컴퓨터 A에서 B로 “Hello”를 보내는 일은 단순해 보인다. 그런데 실제로는 이런 일이 동시에 벌어진다.

  • 비트를 전기 신호로 바꿔 케이블에 실어야 한다.
  • 같은 네트워크 안에서 어떤 장비가 수신자인지 구분해야 한다.
  • 서로 다른 네트워크를 거쳐 경로를 찾아야 한다.
  • 데이터가 유실되면 재전송할지 말지 결정해야 한다.
  • 데이터를 압축하거나 암호화할 수도 있다.
  • 어떤 응용 프로그램이 데이터를 받을지 정해야 한다.

이 모든 것을 하나의 소프트웨어에 밀어 넣으면 어떻게 되는가? 한 가지를 고치려면 전부를 뒤져야 한다. 이더넷을 Wi-Fi로 바꿨을 뿐인데 TCP 코드까지 수정해야 하고, HTTP를 고쳤는데 IP 라우팅이 깨진다.

OSI(Open Systems Interconnection) 모델은 이 문제를 “계층 분리”로 해결한다. 각 계층은 자기 책임만 지고, 아래 계층이 제공하는 서비스를 사용하며, 위 계층에 서비스를 제공한다. 이더넷을 Wi-Fi로 바꿔도 그 위 계층은 영향을 받지 않는다.

OSI 모델을 모르면:

  • “라우터는 3계층 장비다”라는 말이 무슨 뜻인지 이해할 수 없다.
  • 네트워크 문제를 계층별로 분리해서 디버깅하지 못한다.
  • TCP/IP 모델과의 관계를 설명하지 못한다.

책임을 나누는 방식

계층화 — 왜 나누는가

건물을 짓는 과정을 생각하자. 기초 공사, 골조, 배관, 전기, 인테리어는 각각 전문가가 다르다. 배관 업체가 바뀌어도 골조는 건드리지 않는다. 네트워크도 마찬가지다. 물리적 전송 방식(이더넷 vs Wi-Fi)이 바뀌어도 그 위에서 동작하는 IP, TCP, HTTP는 바꿀 필요가 없다.

이것을 가능하게 하는 원리:

  • 각 계층은 아래 계층의 서비스를 사용한다.
  • 각 계층은 위 계층에 서비스를 제공한다.
  • 같은 계층끼리는 프로토콜(규약)로 통신한다.

외우는 것보다 각 계층이 “어떤 문제를 해결하는가”를 이해하는 것이 중요하다.

각 계층이 해결하는 문제

1계층: 물리 계층 (Physical Layer)

문제: 0과 1을 상대방에게 어떻게 물리적으로 전달하는가?

이 계층은 비트를 전기 신호, 빛, 전파 같은 물리적 형태로 바꿔 전송 매체에 실는다. 케이블의 종류(UTP, 광섬유), 핀 배치, 전압 수준, 주파수 등이 이 계층의 관심사다.

  • 단위: 비트 (bit)
  • 장비: 허브 (Hub), 리피터 (Repeater)
  • 예: 이더넷 케이블에서 전기 신호의 전압 변화로 0과 1을 구분한다

허브는 들어온 신호를 모든 포트로 복사한다. 누가 수신자인지 판단하지 않는다. 그건 2계층의 일이다.

2계층: 데이터 링크 계층 (Data Link Layer)

문제: 같은 물리 네트워크(LAN) 안에서 어떤 장비가 수신자인지 어떻게 구분하는가?

물리 계층은 비트를 전달할 뿐이다. 허브가 모든 장비에 신호를 뿌리면, 각 장비가 “이건 내 거다” 또는 “내 거 아니다”를 판단해야 한다. 데이터 링크 계층이 MAC 주소(Media Access Control Address)로 이 판단을 한다.

MAC 주소는 네트워크 카드(NIC, Network Interface Card)에 하드웨어로 새겨진 48비트 주소다. 00:1A:2B:3C:4D:5E 같은 형식이다. 세상에 존재하는 모든 NIC가 고유한 MAC 주소를 가진다.

이 계층의 데이터 단위는 프레임(Frame)이다. 프레임에는 출발지 MAC, 목적지 MAC, 상위 계층 데이터, 오류 검출용 FCS(Frame Check Sequence)가 들어간다.

  • 단위: 프레임 (Frame)
  • 장비: 스위치 (Switch), 브리지 (Bridge)
  • 프로토콜: Ethernet, Wi-Fi (802.11)

스위치는 허브와 달리 MAC 주소 테이블을 가지고 있다. 어떤 MAC 주소가 어떤 포트에 연결되어 있는지 학습해서, 프레임을 해당 포트에만 전달한다.

3계층: 네트워크 계층 (Network Layer)

문제: 서로 다른 네트워크에 있는 장비에게 데이터를 어떻게 전달하는가?

MAC 주소는 같은 LAN 안에서만 의미가 있다. 서울의 컴퓨터가 뉴욕의 서버에 접속하려면 여러 네트워크를 거쳐야 한다. 네트워크 계층은 논리 주소(IP 주소)와 라우팅으로 이 문제를 해결한다.

IP 주소는 네트워크 + 호스트를 식별하는 논리 주소다. 물리적으로 어디에 있든 IP 주소로 찾아갈 수 있다. IPv4는 32비트(예: 192.168.1.1), IPv6는 128비트다.

라우팅은 패킷이 출발지에서 목적지까지 어떤 경로로 갈지 결정하는 과정이다. 라우터가 패킷의 목적지 IP를 보고 “다음 홉(next hop)“을 결정한다.

  • 단위: 패킷 (Packet)
  • 장비: 라우터 (Router)
  • 프로토콜: IP(IPv4, IPv6), ICMP, ARP

“라우터는 3계층 장비다”라는 말의 의미는 이것이다. 라우터는 프레임(2계층)을 열어 IP 헤더(3계층)를 확인하고 라우팅 결정을 내린다. 4계층 이상의 내용은 보지 않는다.

4계층: 전송 계층 (Transport Layer)

문제: 호스트까지 도착한 데이터를 어떤 프로세스에 전달할지, 신뢰성을 보장할지 말지 어떻게 결정하는가?

3계층은 호스트를 찾아준다. 그런데 호스트 안에는 여러 프로세스가 동시에 통신한다. 웹 브라우저, 메일 클라이언트, DNS 리졸버가 동시에 네트워크를 쓴다. 전송 계층은 포트 번호(Port Number)로 프로세스를 구분하고, 선택적으로 신뢰성을 제공한다.

  • TCP: 연결 지향, 신뢰성 보장, 순서 보장, 흐름/혼잡 제어
  • UDP: 비연결, 신뢰성 없음, 빠르고 단순

상세 내용은 IP와 UDP 문서를 참고한다.

  • 단위: 세그먼트(TCP) / 데이터그램(UDP)
  • 프로토콜: TCP, UDP

5계층: 세션 계층 (Session Layer)

문제: 통신의 시작, 유지, 종료를 어떻게 관리하는가?

두 호스트 사이의 대화(세션)를 설정하고, 동기화하고, 끝내는 역할이다. 파일 전송 중간에 끊어졌을 때 처음부터 다시 보내지 않고 중간부터 재개하려면, 어디까지 보냈는지 체크포인트를 관리하는 계층이 필요하다.

현실에서는 TCP/IP 모델에서 이 기능이 응용 계층이나 전송 계층에 흡수되어 있다. 별도의 세션 계층 프로토콜을 명시적으로 구현하는 경우는 드물다.

6계층: 표현 계층 (Presentation Layer)

문제: 데이터의 형식(인코딩, 암호화, 압축)을 어떻게 통일하는가?

송신 측과 수신 측이 서로 다른 데이터 표현 방식을 쓸 수 있다. 한쪽은 EBCDIC(Extended Binary Coded Decimal Interchange Code), 다른 쪽은 ASCII를 쓴다면 변환이 필요하다. SSL/TLS 암호화, JPEG/MPEG 압축, 문자 인코딩 변환 등이 이 계층의 역할이다.

현실에서는 이 기능 역시 응용 계층에 흡수되어 있다. TLS는 HTTP와 TCP 사이에서 동작하지만, 별도의 “표현 계층 프로토콜”이라기보다 응용 계층의 일부로 취급된다.

7계층: 응용 계층 (Application Layer)

문제: 사용자와 네트워크를 어떻게 연결하는가?

사용자가 직접 접하는 네트워크 서비스를 제공한다. 웹 브라우저가 HTTP로 페이지를 요청하고, 메일 클라이언트가 SMTP로 메일을 보내고, nslookup이 DNS로 도메인을 조회하는 것이 모두 이 계층이다.

  • 프로토콜: HTTP, HTTPS, DNS, FTP, SSH, SMTP, POP3, IMAP

캡슐화와 역캡슐화

데이터가 송신 측의 7계층에서 1계층으로 내려갈 때, 각 계층이 자기 헤더를 붙인다. 이것을 캡슐화(Encapsulation)라 한다. 수신 측에서는 1계층에서 7계층으로 올라가면서 각 계층이 자기 헤더를 벗긴다. 이것을 역캡슐화(Decapsulation)라 한다.

  c["[ NH &#124; TH &#124; 데이터 ]<br/>3. 네트워크 — NH(IP 헤더) 추가"]

  c --> d
  d --> e

각 계층은 바로 위 계층에서 받은 전체를 “데이터”로 취급하고 자기 헤더를 앞에 붙인다. 3계층의 IP 헤더는 4계층 세그먼트 전체를 페이로드(payload)로 본다. 2계층은 IP 패킷 전체를 페이로드로 본다.

OSI 7계층 vs TCP/IP 4계층

OSI는 국제표준화기구(ISO, International Organization for Standardization)가 만든 “이론적 참조 모델”이다. 실제 인터넷은 OSI가 아니라 TCP/IP 모델을 기반으로 구현되었다. TCP/IP 모델은 OSI의 5·6·7계층을 하나의 응용 계층으로 합치고, 1·2계층을 네트워크 접근 계층으로 합쳤다.

%% OSI 7계층과 TCP/IP 4계층 대응 — 5·6·7은 응용, 1·2는 네트워크 접근으로 합쳐짐
flowchart TD
  t["OSI 7계층 &#124; TCP/IP 4계층<br/>7. 응용 &#124; 응용 계층 (Application)<br/>6. 표현<br/>5. 세션<br/>4. 전송 &#124; 전송 계층 (Transport)<br/>3. 네트워크 &#124; 인터넷 계층 (Internet)<br/>2. 데이터 링크 &#124; 네트워크 접근 (Link)<br/>1. 물리"]

왜 차이가 나는가? OSI는 “이론적으로 완전한 분리”를 추구했다. 모든 기능을 빠짐없이 7개 층으로 나눴다. TCP/IP는 “실제로 구현 가능한 분리”를 추구했다. 세션·표현 계층의 기능은 실제로 별도 프로토콜로 구현되는 경우가 드물어서 응용 계층에 합쳤다.

현실에서 OSI 7계층은 네트워크를 설명하고 디버깅하는 공통 언어로 쓰인다. “이 문제는 몇 계층 문제인가?”라고 물으면 OSI 모델이 기준이다. 실제 프로토콜 구현은 TCP/IP 모델을 따른다.

OSI 7계층 모델 코드

네트워크 프로그래밍에서 OSI 계층이 어떻게 드러나는지, BSD 소켓 API를 기준으로 확인한다.

socket() 호출에서 계층이 드러나는 방식

socket() 함수의 인자가 OSI 계층을 반영한다. AF_INET은 3계층(IP)을 선택하고, SOCK_STREAM/SOCK_DGRAM은 4계층(TCP/UDP)을 선택한다. 대부분의 응용 프로그램은 4계층 위에서 동작하므로 1~3계층을 직접 다룰 일이 없다. 패킷 캡처 도구(tcpdump, Wireshark)는 AF_PACKET으로 2계층까지 내려간다.

네트워크 문제 디버깅 — 계층별 점검

네트워크가 안 될 때 아래 계층에서 위로 점검하는 것이 표준 디버깅 흐름이다.

1계층부터 순서대로 확인하면 문제가 어느 계층에서 발생했는지 좁힐 수 있다. ping이 되는데 curl이 안 되면 47계층 문제다. ping도 안 되면 13계층부터 의심한다. 이것이 OSI 모델이 디버깅 프레임워크로서 가치를 갖는 이유다.

정리

OSI 7계층 모델은 네트워크 통신을 물리(1) → 데이터 링크(2) → 네트워크(3) → 전송(4) → 세션(5) → 표현(6) → 응용(7)으로 나눈다. 각 계층은 하나의 문제만 해결하고, 아래 계층의 서비스 위에서 동작한다. 데이터는 송신 시 위에서 아래로 캡슐화되고, 수신 시 아래에서 위로 역캡슐화된다.

실제 인터넷은 TCP/IP 4계층 모델로 구현되었고, 5·6·7계층은 응용 계층으로 합쳐져 있다. OSI 모델의 가치는 구현이 아니라 “네트워크 문제를 계층별로 분리해서 생각하는 프레임워크”를 제공한다는 점이다.

네트워크 문제를 만나면 “이건 몇 계층 문제인가?”를 먼저 떠올려야 한다. 그것이 OSI 모델이 존재하는 이유다.
