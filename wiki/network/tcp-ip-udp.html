TCP/IP와 UDP — 인터넷에서 데이터를 주고받는 두 가지 방식

TCP/IP와 UDP — 인터넷에서 데이터를 주고받는 두 가지 방식

TCP는 신뢰성을 보장하는 연결 기반 전송 프로토콜이고, UDP는 신뢰성을 포기하는 대신 빠르고 단순한 비연결 전송 프로토콜이다.

TCP/IP와 UDP 혼동

컴퓨터 두 대가 네트워크로 연결되어 있다고 하자. A가 B에게 “Hello”라는 메시지를 보내고 싶다. 그런데 이 메시지는 곧바로 B에 도착하지 않는다. 수십 개의 라우터를 거치고, 패킷이 쪼개지고, 순서가 뒤바뀌고, 중간에 유실될 수도 있다.

IP(Internet Protocol)는 패킷을 목적지까지 라우팅하는 역할만 한다. “이 패킷이 제대로 도착했는지”, “순서가 맞는지”, “빠진 건 없는지”는 IP의 관심사가 아니다. IP는 최선을 다하지만 보장하지 않는다. 이것을 최선 노력 전달 (Best-effort Delivery)이라 한다.

그래서 IP 위에 전송 계층 (Transport Layer) 프로토콜이 필요하다. 이 계층에서 “신뢰성을 어떻게 처리할 것인가”에 대한 두 가지 선택지가 TCP와 UDP다.

  • TCP를 모르면: 웹 브라우저가 왜 페이지를 정확히 받아오는지, connect() → send() → recv()가 왜 이 순서인지 이해할 수 없다.
  • UDP를 모르면: 실시간 게임이나 DNS가 왜 TCP 대신 UDP를 쓰는지, 왜 “빠르지만 불안정”하다고 하는지 감이 안 잡힌다.
  • 둘의 차이를 모르면: 소켓 프로그래밍에서 SOCK_STREAM과 SOCK_DGRAM 중 무엇을 써야 하는지 판단할 수 없다.

전송 계층이 고르는 두 가지 태도

TCP/IP 모델 — 4계층 구조

인터넷의 프로토콜 스택은 4계층으로 나뉜다. OSI 7계층보다 실제 구현에 가깝다.

%% TCP/IP 4계층 스택 — 각 계층과 대표 프로토콜
flowchart TD
  stack["응용 계층 (Application) &#124; HTTP, DNS, FTP, SSH<br/>전송 계층 (Transport) &#124; TCP, UDP ← 이 문서의 주인공<br/>인터넷 계층 (Internet) &#124; IP, ICMP, ARP<br/>네트워크 접근 (Link) &#124; Ethernet, Wi-Fi"]

응용 계층의 데이터는 전송 계층에서 세그먼트(TCP) 또는 데이터그램(UDP)으로 포장된다. 인터넷 계층에서 IP 헤더가 붙어 패킷이 되고, 링크 계층에서 프레임으로 감싸져 물리 네트워크를 탄다.

IP — 주소 지정과 라우팅

IP는 두 가지 일을 한다.

  • 주소 지정: 모든 호스트에 고유한 IP 주소를 부여한다. IPv4는 32비트(예: 192.168.1.1), IPv6는 128비트다.
  • 라우팅: 패킷을 출발지에서 목적지까지 중간 라우터를 거쳐 전달한다.

IP가 하지 않는 일이 중요하다.

  • 패킷 도착을 보장하지 않는다 (유실 가능).
  • 순서를 보장하지 않는다 (뒤바뀔 수 있다).
  • 중복 전달을 막지 않는다 (같은 패킷이 두 번 올 수 있다).

이 한계를 전송 계층에서 해결할지 말지가 TCP와 UDP의 갈림길이다.

포트 — 같은 호스트 안에서 프로세스를 구분하는 번호

IP 주소는 호스트(컴퓨터)를 식별한다. 그런데 한 컴퓨터에서 웹 브라우저, 메일 클라이언트, 게임이 동시에 네트워크를 쓴다. 어떤 패킷이 어떤 프로세스로 가야 하는지 어떻게 구분하는가?

포트 번호 (Port Number)가 이 역할을 한다. 16비트 정수(0~65535)다.

  • 0~1023: 잘 알려진 포트 (Well-known). HTTP는 80, HTTPS는 443, SSH는 22, DNS는 53.
  • 1024~49151: 등록된 포트 (Registered). 특정 서비스가 예약.
  • 49152~65535: 동적/임시 포트 (Ephemeral). 클라이언트가 연결할 때 OS가 자동 할당.

IP 주소 + 포트 번호의 조합을 소켓 주소라 한다. 192.168.1.1:80은 “해당 호스트의 80번 포트로 가라”는 뜻이다.

TCP — 신뢰할 수 있는 바이트 스트림

TCP(Transmission Control Protocol)는 IP 위에서 신뢰성을 보장하는 연결 지향 프로토콜이다.

비유: 전화 통화와 비슷하다. 먼저 전화를 걸어 상대방이 받아야(연결 수립) 대화가 시작된다. 대화 도중 상대방이 못 알아들으면 다시 말해준다(재전송). 통화가 끝나면 “끊을게” 하고 끊는다(연결 해제).

TCP가 보장하는 것:

  • 신뢰성: 데이터가 유실되면 재전송한다. 수신 측이 확인 응답(ACK)을 보내고, ACK가 없으면 송신 측이 다시 보낸다.
  • 순서 보장: 각 바이트에 시퀀스 번호 (Sequence Number)를 매긴다. 수신 측이 순서대로 재조립한다.
  • 흐름 제어 (Flow Control): 수신 측이 처리할 수 있는 속도보다 빠르게 보내지 않는다. 수신 윈도우 (Receive Window) 크기를 알려주는 방식이다.
  • 혼잡 제어 (Congestion Control): 네트워크가 과부하 상태면 전송 속도를 줄인다. Slow Start, Congestion Avoidance 등의 알고리즘을 사용한다.

3-way Handshake — TCP 연결 수립

TCP 연결은 세 번의 패킷 교환으로 시작된다.

%% TCP 3-way handshake — SYN, SYN+ACK, ACK 순서
flowchart TD
  s1["① SYN (seq=x)<br/>Client → Server · &quot;연결하고 싶다&quot;"]
  s2["② SYN+ACK (seq=y, ack=x+1)<br/>Server → Client · &quot;나도 연결하자&quot;"]
  s3["③ ACK (ack=y+1)<br/>Client → Server · &quot;확인했다&quot;"]
  done["연결 수립 완료"]
  s1 --> s2
  s2 --> s3
  s3 --> done

왜 세 번인가? 두 번이면 안 되는가?

두 번만 하면 클라이언트는 서버가 응답한 걸 알지만, 서버는 클라이언트가 자신의 응답을 받았는지 모른다. 세 번째 ACK가 있어야 양쪽 모두 “상대방이 내 메시지를 받았다”는 확신을 가진다. 또한 오래된 SYN 패킷이 지연 도착해서 잘못된 연결이 생기는 것을 막는다.

4-way Handshake — TCP 연결 해제

연결을 끊을 때는 네 번의 패킷을 교환한다.

%% TCP 4-way 연결 해제 — FIN, ACK, FIN, ACK와 TIME_WAIT
flowchart TD
  a["① FIN<br/>Client → Server · &quot;더 보낼 게 없다&quot;"]
  b["② ACK<br/>Server → Client · &quot;알겠다&quot;"]
  c["③ FIN<br/>Server → Client · &quot;나도 없다&quot;"]
  d["④ ACK<br/>Client → Server · &quot;알겠다&quot;"]
  tw["TIME_WAIT (2MSL 대기)"]
  a --> b
  b --> c
  c --> d
  d --> tw

왜 네 번인가? 연결 수립은 SYN+ACK를 하나로 합칠 수 있지만, 해제는 한쪽이 FIN을 보내도 상대방은 아직 보낼 데이터가 남아 있을 수 있다. 그래서 각자 독립적으로 FIN을 보내고 ACK를 받는다.

TIME_WAIT는 클라이언트가 마지막 ACK를 보낸 뒤 일정 시간(2 × MSL, 보통 60초) 동안 소켓을 유지하는 상태다. 마지막 ACK가 유실되었을 때 서버가 FIN을 재전송하면 다시 ACK를 보낼 수 있도록 하기 위함이다.

TCP 세그먼트 헤더

TCP 세그먼트의 헤더는 최소 20바이트다. 핵심 필드만 보면:

  • 출발지 포트 (Source Port): 16비트
  • 목적지 포트 (Destination Port): 16비트
  • 시퀀스 번호 (Sequence Number): 32비트. 이 세그먼트의 첫 바이트 번호.
  • 확인 응답 번호 (Acknowledgment Number): 32비트. 다음에 받기를 기대하는 바이트 번호.
  • 플래그: SYN, ACK, FIN, RST, PSH, URG 등.
  • 윈도우 크기 (Window Size): 16비트. 수신 측이 현재 받을 수 있는 바이트 수.
  • 체크섬 (Checksum): 16비트. 헤더와 데이터의 무결성 검증.

UDP — 빠르고 단순한 데이터그램

UDP(User Datagram Protocol)는 IP 위에 포트 번호와 체크섬만 얹은 최소한의 프로토콜이다.

비유: 편지와 비슷하다. 봉투에 주소를 쓰고 우체통에 넣는다. 상대방이 받았는지 확인하지 않는다. 여러 통을 보내면 도착 순서가 보장되지 않는다. 대신 우체국에서 처리하는 시간이 짧다.

UDP의 특징:

  • 비연결: 핸드셰이크 없이 바로 데이터를 보낸다.
  • 비신뢰: 패킷이 유실되어도 재전송하지 않는다.
  • 순서 미보장: 패킷이 보낸 순서대로 도착하지 않을 수 있다.
  • 경량: 헤더가 8바이트뿐이다 (TCP는 최소 20바이트).
  • 메시지 경계 보존: TCP는 바이트 스트림이라 메시지 경계가 없지만, UDP는 보낸 데이터그램 단위 그대로 수신 측에 전달된다.

UDP 데이터그램 헤더

UDP 헤더는 단 8바이트다.

  • 출발지 포트 (Source Port): 16비트
  • 목적지 포트 (Destination Port): 16비트
  • 길이 (Length): 16비트. 헤더 + 데이터 전체 길이.
  • 체크섬 (Checksum): 16비트. 선택 사항(IPv4), 필수(IPv6).

TCP 헤더와 비교하면 시퀀스 번호, ACK 번호, 윈도우 크기, 플래그가 전부 없다. 연결 관리와 신뢰성 보장에 필요한 필드를 모두 뺐기 때문이다.

TCP vs UDP — 언제 무엇을 쓰는가

기준TCPUDP
연결 방식연결 지향 (3-way handshake)비연결
신뢰성보장 (ACK, 재전송)보장하지 않음
순서보장 (시퀀스 번호)보장하지 않음
흐름/혼잡 제어있음없음
헤더 크기최소 20바이트8바이트
전송 단위바이트 스트림데이터그램 (메시지 경계 보존)
지연핸드셰이크 + 재전송 오버헤드낮음

TCP를 쓰는 경우:

  • 웹 (HTTP/HTTPS): 페이지 데이터가 하나라도 빠지면 안 된다.
  • 이메일 (SMTP): 메일 본문이 깨지면 안 된다.
  • 파일 전송 (FTP): 파일 1바이트라도 틀리면 안 된다.
  • SSH: 명령어가 순서대로 도착해야 한다.

UDP를 쓰는 경우:

  • DNS: 질의 하나, 응답 하나. 짧은 교환에 연결 수립은 낭비다.
  • 실시간 스트리밍/VoIP: 1초 전 프레임이 유실되어도 재전송보다 다음 프레임을 보여주는 게 낫다.
  • 온라인 게임: 0.1초 전 위치 정보보다 지금 위치 정보가 더 중요하다.
  • DHCP: 아직 IP 주소가 없는 호스트가 IP를 요청하는 과정이므로 연결 수립이 불가능하다.

TCP/IP와 UDP 코드

BSD 소켓 API로 TCP와 UDP의 차이를 본다. 소켓 프로그래밍에서 두 프로토콜의 흐름이 어떻게 갈라지는지가 핵심이다.

TCP 서버 — 연결 수립 후 바이트 스트림 송수신

TCP 서버는 socket() → bind() → listen() → accept() → recv()/send() → close() 순서를 따른다. accept()가 3-way handshake를 완료하고, close()가 4-way handshake를 시작한다. listen_fd는 연결 요청을 받는 문지기이고, conn_fd는 실제 데이터를 주고받는 통로다.

UDP 서버 — 연결 없이 데이터그램 송수신

UDP 서버는 socket() → bind() → recvfrom()/sendto() → close()다. listen()과 accept()가 없다. 연결이라는 개념 자체가 없기 때문이다. recvfrom()은 데이터와 함께 보낸 쪽의 주소를 돌려주고, sendto()는 매번 목적지 주소를 지정한다.

소켓 API 흐름 비교

%% TCP와 UDP 소켓 호출 순서 비교 — listen/accept 유무
flowchart LR
  tcp["TCP · SOCK_STREAM<br/>socket()<br/>bind()<br/>listen()<br/>accept() ← 3-way handshake<br/>recv() / send()<br/>close() ← 4-way handshake"]
  udp["UDP · SOCK_DGRAM<br/>socket()<br/>bind()<br/>(listen 없음)<br/>(accept 없음)<br/>recvfrom() / sendto()<br/>close()"]
  tcp --> udp

둘을 가르는 차이는 연결의 존재다. TCP는 accept()로 연결별 전용 소켓을 만든다. 여러 클라이언트가 동시에 접속하면 accept()가 클라이언트마다 별도의 conn_fd를 반환한다. UDP는 하나의 소켓으로 모든 클라이언트의 데이터그램을 처리한다.

정리

IP는 패킷을 목적지까지 보내지만 도착을 보장하지 않는다. TCP는 3-way handshake로 연결을 수립하고, 시퀀스 번호와 ACK로 신뢰성과 순서를 보장하며, 흐름 제어와 혼잡 제어까지 수행한다. 그 대가로 연결 수립과 재전송에 따른 지연이 생긴다. UDP는 연결도 재전송도 없이 8바이트 헤더만 붙여 데이터그램을 바로 보낸다. 빠르지만 유실과 순서 뒤바뀜을 응용이 직접 감수해야 한다.

프로토콜을 고를 때 판단 기준은 하나다. “데이터 하나가 빠지면 치명적인가, 아니면 최신 데이터만 있으면 되는가?” 전자면 TCP, 후자면 UDP다.
