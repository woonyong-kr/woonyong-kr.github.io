HTTP/2 — 한 연결에 여러 요청을 동시에 흘려보내는 바이너리 프로토콜

HTTP/2는 HTTP/1.1과 같은 의미(메서드·헤더·상태 코드)를 유지하면서, 텍스트를 바이너리 프레임으로 바꾸고 하나의 TCP 연결 위에 여러 요청을 스트림으로 다중화해 응답이 서로를 기다리지 않게 만든 프로토콜이다.

여러 자원을 받는 요청 흐름에서 HTTP/2가 바꾸는 것

웹 페이지 하나를 열면 HTML뿐 아니라 CSS, 자바스크립트, 이미지, 폰트까지 작은 파일 수십에서 수백 개를 받아야 화면이 완성된다. 이때 HTTP/1.1의 요청이 어디에서 기다리고 HTTP/2가 그 대기를 어떻게 줄이는지 이해하면, 프레임·스트림·다중화가 필요한 이유와 남아 있는 TCP 계층의 한계를 함께 설명할 수 있다.

1.1은 keep-alive로 하나의 TCP 연결을 재사용한다. 그런데 그 연결에서 요청은 한 번에 하나씩, 순서대로만 처리된다. 앞 요청의 응답이 다 와야 다음 응답이 시작된다. 1번 요청이 큰 이미지라서 느리면, 그 뒤에 줄 선 2번·3번 응답은 작은 파일인데도 1번이 끝날 때까지 묶여 기다린다. 이것이 응용 계층의 머리 줄 막힘(Head-of-Line Blocking, HOL 블로킹)이다.

브라우저는 이 문제를 우회하려고 한 출처(origin)에 여러 TCP 연결을 동시에 연다. 여기서는 그 상한을 6개 안팎으로 설명한다. 연결을 여섯 줄로 나누더라도 파일이 100개라면 요청이 각 연결에 계속 대기한다. 연결마다 TCP 3-way handshake와 느린 시작(slow start) 비용도 따로 발생하며, 서버가 유지할 소켓·메모리·혼잡 제어 상태도 늘어난다. 따라서 연결 수를 늘리는 방법은 병렬성을 높이지만 별도의 비용도 만든다.

이 흐름을 알면 HTTP/1.1에서 파일을 합치는 번들링, 이미지를 하나로 붙이는 스프라이트, 도메인을 나누는 도메인 샤딩을 사용한 이유를 이해할 수 있다. HTTP/2에서는 한 연결의 여러 스트림이 이 역할을 대신하므로, 그런 최적화가 불필요하거나 오히려 손해가 될 수 있는 이유도 이어서 판단할 수 있다.

출처당 연결 수가 제한되는 이유

연결을 늘리면 여러 요청을 병렬로 보낼 수 있지만, 연결마다 초기화와 유지 비용이 생긴다.

연결 1개당 비용 = TCP handshake 1.5 RTT + TLS handshake 1~2 RTT + slow start 동안 낮은 전송량

연결을 N개로 늘리면 → 서버는 N배의 소켓·메모리·혼잡 제어 상태를 유지 연결이 너무 많으면 → 네트워크 전체가 혼잡해져 오히려 느려짐

이 문서에서는 브라우저가 출처당 6개 안팎을 상한으로 잡은 이유를 병렬성과 연결 비용 사이의 경험적 타협으로 설명한다. 여기서 6은 모든 브라우저와 환경에 고정된 규칙이라기보다 그 타협을 보여 주는 기준이다. HTTP/2는 여러 연결로 병렬성을 확보하는 대신, 연결 하나에서 여러 스트림을 함께 처리한다.

프레임과 스트림으로 나누는 연결

비유: 계산대 한 줄 vs 번호표 한 통로

HTTP/1.1 연결은 계산대 한 줄과 비슷하다. 앞사람의 계산이 끝나지 않으면 뒷사람은 물건이 한 개뿐이어도 지나갈 수 없다.

HTTP/2 연결에서는 각 주문에 번호표를 붙이고, 주문을 잘게 나눈 뒤 한 통로에 섞어 흘려보낸다. 1번 손님의 큰 주문과 2번 손님의 작은 주문이 같은 통로를 나누어 사용하므로 작은 주문이 먼저 끝날 수 있다. 통로는 하나지만 주문은 서로 다른 흐름으로 구분된다.

이 번호표가 스트림 식별자(Stream ID)이고, 주문을 잘게 나눈 조각이 프레임(Frame)이다.

바이너리 프레이밍 — 텍스트를 버린 이유

HTTP/1.1 메시지는 사람이 읽는 텍스트다. GET /index.html HTTP/1.1\r\n 같은 줄을 파서가 한 글자씩 읽어 경계를 찾는다. 경계가 \r\n이라는 약속뿐이라 한 메시지가 끝나야 다음 메시지를 읽을 수 있고, 여러 요청을 한 연결에 섞으면 각 부분이 어느 요청에 속하는지 구분하기 어렵다.

HTTP/2는 메시지를 프레임이라는 고정 구조의 바이너리 조각으로 쪼갠다. 모든 프레임은 9바이트 헤더로 시작하며, 헤더에는 길이·종류·소속 스트림 번호가 들어 있다. 수신자는 길이와 스트림 번호를 보고 섞여 도착한 프레임을 각 스트림으로 다시 모을 수 있다.

Length가 24비트이므로 한 프레임 페이로드는 최대 2^24 - 1 = 16,777,215바이트(약 16MB)다. 단, 기본 최대 프레임 크기는 16,384바이트(16KB)이고, 더 키우려면 SETTINGS 프레임으로 양쪽이 합의해야 한다.

프레임의 종류

자주 등장하는 프레임은 다음과 같다. Type 필드의 1바이트 값으로 구분한다.

  • HEADERS (0x1) — 요청·응답의 헤더. HTTP/1.1의 요청 라인·상태 라인·헤더가 여기에 압축돼 담긴다.
  • DATA (0x0) — 본문. HTML, JSON, 이미지 바이트가 여기에 실린다.
  • SETTINGS (0x4) — 연결 시작 시 양쪽이 주고받는 설정. 최대 동시 스트림 수와 프레임 크기 등이 포함된다.
  • WINDOW_UPDATE (0x8) — 흐름 제어(flow control). 받는 쪽이 더 받을 수 있는 양을 알린다.
  • RST_STREAM (0x3) — 특정 스트림 하나만 취소하고 연결 전체는 유지한다.
  • GOAWAY (0x7) — 연결을 정상 종료하겠다고 통보한다.
  • PING (0x6) — 연결이 살아 있는지 확인한다.

하나의 요청·응답은 보통 HEADERS 프레임 한 개와 DATA 프레임 여러 개로 표현된다.

스트림과 다중화(Multiplexing)

스트림(Stream)은 하나의 연결 안에서 독립적으로 흐르는 양방향 메시지 흐름이다. 요청·응답 한 쌍이 스트림 하나에 대응하며, 각 스트림은 번호(Stream ID)를 가진다.

  • 클라이언트가 시작하는 스트림은 홀수 번호: 1, 3, 5, 7 …
  • 서버가 시작하는 스트림은 짝수 번호: 2, 4, 6 …

번호를 홀짝으로 나누면 양쪽이 동시에 새 스트림을 열어도 번호가 겹치지 않는다. 클라이언트와 서버가 같은 번호 공간을 사용하면서도 별도의 합의 없이 충돌을 피할 수 있다.

다중화는 여러 스트림의 프레임을 한 연결에 시간순으로 섞어 보내는 방식이다. 1번 스트림 HEADERS → 3번 스트림 HEADERS → 1번 DATA → 3번 DATA → 1번 DATA 순서로 도착해도, 수신자는 각 프레임의 Stream ID를 보고 1번과 3번을 따로 모은다. 따라서 큰 응답인 1번이 작은 응답인 3번을 응용 계층에서 막지 않는다. HTTP/2는 이 방식으로 HTTP/1.1의 응용 계층 HOL 블로킹을 없앤다.

HPACK — 헤더 압축

HTTP 요청은 User-Agent, Accept, Cookie처럼 비슷한 헤더를 반복해서 보낸다. 요청마다 같은 문자열을 다시 보내면 중복이 생긴다.

HPACK은 이 중복을 줄이는 헤더 전용 압축 방식이다.

  • 정적 테이블(static table): 자주 쓰는 헤더 61개에 미리 번호를 매긴다. 예를 들어 :method: GET은 인덱스 2번이며, GET을 보낼 때 문자열 대신 이 인덱스를 사용할 수 있다.
  • 동적 테이블(dynamic table): 현재 연결에서 처음 본 헤더(Cookie: session=... 등)를 양쪽의 테이블에 추가하고, 다음 요청부터 인덱스로 참조한다.

문자열로 보내야 하는 값은 허프만 코딩(Huffman coding)으로 추가 압축한다. 이 구조에서는 같은 연결의 뒤쪽 요청일수록 이미 공유한 헤더를 인덱스로 나타낼 수 있다.

서버 푸시(Server Push)와 그 퇴장

HTTP/2 스펙에는 서버 푸시가 있다. 클라이언트가 index.html을 요청하면 서버가 이후에 필요할 것으로 예상한 style.css를 PUSH_PROMISE 프레임으로 미리 보내는 기능이다.

하지만 서버가 클라이언트의 캐시 상태를 알 수 없어 이미 가진 파일을 다시 보내는 낭비가 생길 수 있다. 이 문서가 설명하는 현재 상태에서는 크롬이 HTTP/2 서버 푸시 지원을 제거했고, Link: rel=preload 같은 힌트가 그 자리를 대신한다. 따라서 서버 푸시는 스펙에 존재하지만 실무에서는 거의 사용하지 않는 기능으로 이해할 수 있다.

실제 OS·서버 관점에서의 전제 조건

  • 브라우저는 사실상 HTTPS 위에서 HTTP/2를 사용한다. 평문 HTTP/2(h2c)도 스펙에는 있지만 브라우저는 지원하지 않는다. 사용할 프로토콜은 TLS 핸드셰이크 중 ALPN(Application-Layer Protocol Negotiation)으로 합의한다. 클라이언트가 h2를 제안하고 서버가 받아들이면 HTTP/2를 사용한다.
  • 서버 소프트웨어(nginx, Apache, Caddy)는 설정 한 줄(listen 443 ssl http2; 등)로 HTTP/2를 켠다. 메서드·상태 코드·헤더로 구성된 의미 계층은 유지되므로 애플리케이션 코드를 바꿀 필요가 없다.

남은 한계: TCP 머리 줄 막힘

HTTP/2는 응용 계층의 HOL 블로킹을 없애지만, 더 아래 TCP 계층의 HOL 블로킹은 남는다.

TCP는 바이트를 순서대로 전달한다. 중간 패킷 하나가 유실되면 그 뒤에 도착한 패킷이 정상이어도, 유실된 부분이 재전송될 때까지 운영체제 버퍼에서 기다린다. HTTP/2에서 스트림 3번의 데이터가 도착했더라도 스트림 1번에 해당하는 앞선 패킷이 빠졌다면 TCP가 3번 데이터까지 전달하지 못할 수 있다. 여러 스트림이 연결 하나를 공유하므로 이 지연이 함께 드러난다.

이 문제는 HTTP/2의 응용 계층 다중화만으로 풀 수 없다. 전송 계층을 TCP에서 QUIC(UDP 기반)으로 바꾼 HTTP/3은 이 한계를 겨냥한다.

HTTP/2 프레임을 코드와 출력으로 읽기

연결 시작 — 클라이언트 연결 서문(connection preface)

HTTP/2 연결은 클라이언트가 고정된 24바이트 매직 문자열을 먼저 보내면서 시작한다. 서버는 이 바이트열을 보고 상대가 HTTP/2로 통신하려 한다는 것을 식별한다.

PRI와 SM을 세로로 읽으면 PRISM이다. HTTP/1.1 파서가 이 문자열을 정상 요청으로 오해하지 않도록 어떤 HTTP/1.1 요청과도 겹치지 않는 형태를 사용한다. 이 서문 직후 양쪽은 SETTINGS 프레임을 교환하며 연결을 연다.

다중화 — 한 연결에 섞여 흐르는 프레임

다음은 요청 두 개인 스트림 1번과 3번이 한 연결을 나누어 쓰는 모습을 시간순으로 나타낸 것이다.

스트림 3번의 작은 CSS는 스트림 1번의 큰 이미지 프레임 사이에 들어가 먼저 완성된다. 프레임마다 붙은 Stream ID가 있으므로 수신자는 섞여 온 조각을 각 스트림으로 다시 모을 수 있다.

눈으로 확인 — curl로 프레임 보기

curl에 --http2와 -v를 주면 ALPN 합의와 프레임 송수신을 확인할 수 있다.

이 예시 출력에서는 HTTP/2에서도 GET과 200의 의미가 HTTP/1.1과 같고 전송 방식이 달라졌다는 점을 읽을 수 있다. Host 헤더가 :authority라는 의사 헤더(pseudo-header, :로 시작)로 바뀐 것도 표면에 드러나는 차이다. 다만 이 문서는 명령을 실제로 실행한 결과를 보고하는 것이 아니라, 제시된 출력에서 무엇을 확인할지 설명한다.

서버에서 켜기 — nginx 설정 한 줄

이 설정 예시에서는 http2 on;으로 해당 가상 호스트의 HTTP/2를 활성화한다. 백엔드 애플리케이션은 같은 메서드·헤더·상태 코드를 사용하므로, HTTP/2가 바꾸는 범위는 HTTP의 의미가 아니라 그 의미를 실어 나르는 방식이다.

HTTP/2를 설명하고 판단하는 기준

HTTP/2는 HTTP의 메서드·헤더·상태 코드를 유지하면서 메시지를 바이너리 프레임으로 나눈다. 각 프레임의 Stream ID를 이용해 여러 요청을 한 TCP 연결에 섞어 보내므로 HTTP/1.1의 응용 계층 HOL 블로킹을 줄인다. HPACK은 반복되는 헤더를 정적·동적 테이블의 인덱스로 나타낸다.

이 구조를 기준으로 보면 HTTP/1.1의 번들링과 도메인 샤딩 같은 우회 최적화가 HTTP/2에서 불필요하거나 손해가 될 수 있는 이유를 설명할 수 있다. 반면 TCP의 순서 보장 때문에 생기는 전송 계층 HOL 블로킹은 남는다. 따라서 HTTPS를 사용하고 여러 자원을 전송하는 서비스에서는 HTTP/2를 기본 선택으로 볼 수 있지만, 패킷 손실이 잦은 망에서는 하나의 TCP 연결을 공유하는 특성이 약점이 될 수 있다.

이어서 읽기

HTTP/2가 유지한 메서드·헤더·상태 코드의 의미를 다시 확인하려면 HTTP를 함께 본다. 남은 한계는 TCP의 순서 보장에서 나오므로 TCP/IP와 UDP를 연결해 보면 HTTP/3이 QUIC을 사용하는 이유까지 이어서 설명할 수 있다.

  • HTTP
  • IP와 UDP
