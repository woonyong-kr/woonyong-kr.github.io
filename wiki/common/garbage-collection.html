가비지 컬렉션

가비지 컬렉션

확인 범위: 이 문서는 가비지 컬렉션의 일반 원리와 주요 방식, 수동 메모리 관리와의 선택 기준을 설명하는 개념 개요이며, 포함된 CPython·PintOS 코드는 이해를 돕기 위한 예시다. 특정 버전의 실제 동작, 출력값·임계값, 구현 세부와 성능·정지 시간에 관한 판단은 해당 코드와 실행 기록 또는 측정 결과를 별도로 확인해야 한다.

가비지 컬렉션(Garbage Collection, GC)은 프로그램이 더 이상 참조하지 않는 힙 메모리를 런타임이 자동으로 찾아 해제하는 메커니즘이다.

가비지 컬렉션 필요성

C에서 malloc()으로 메모리를 할당하면, 반드시 free()로 돌려줘야 한다. 그런데 현실의 프로그램은 수천 개의 객체를 만들고, 함수 사이로 포인터를 넘기고, 조건에 따라 다른 경로로 실행된다. 이 과정에서 두 가지 문제가 반복된다.

  • 메모리 누수 (Memory Leak): free()를 빠뜨려서 더 이상 쓰지 않는 메모리가 쌓인다. 프로그램이 오래 실행될수록 메모리 사용량이 끝없이 증가한다.
  • Use After Free: 이미 free()한 메모리를 다시 읽거나 쓴다. 비결정적 버그와 보안 취약점의 대표적 원인이다.

수동 메모리 관리는 이 두 실수를 프로그래머의 주의력에만 의존한다. 코드가 수만 줄을 넘어가면 사람이 모든 할당-해제 쌍을 추적하는 것은 사실상 불가능하다.

가비지 컬렉션은 이 문제를 런타임 시스템이 대신 해결한다. “이 메모리를 아직 누군가 쓰고 있는가?”를 자동으로 판단하고, 아무도 쓰지 않는 메모리를 회수한다. Java, Python, Go, JavaScript 같은 언어가 GC를 채택한 이유다.

먼저 구분할 항목은 다음과 같다.

  • GC가 “쓰레기”를 어떤 기준으로 판별하는지 (도달 가능성)
  • 레퍼런스 카운팅과 추적 기반 GC의 차이
  • GC가 있는 언어에서도 메모리 누수가 발생할 수 있는 이유

도달 가능한 객체와 버려진 객체

쓰레기란 무엇인가 — 도달 가능성 (Reachability)

비유: 도서관에 책이 1만 권 있다. 서가에 꽂혀 있지만, 카탈로그에도 없고 어떤 대출 기록에도 없는 책이 있다면 — 아무도 그 책을 찾을 방법이 없다. 이것이 “쓰레기”다.

메모리에서도 마찬가지다. 프로그램이 실행 중에 접근할 수 있는 출발점을 **루트 (Root)**라 한다.

  • 루트의 예: 전역 변수, 스택 프레임의 지역 변수, CPU 레지스터에 들어 있는 포인터
  • 루트에서 포인터 체인을 따라가서 도달할 수 있는 객체는 살아 있다 (Live).
  • 어떤 루트에서도 도달할 수 없는 객체는 **쓰레기 (Garbage)**다.
%% 루트에서 도달 가능한 객체와 도달 불가능한 객체
flowchart LR
  root["루트<br/>전역 변수, 스택, 레지스터"]
  a["객체 A<br/>Live"]
  b["객체 B<br/>Live"]
  c["객체 C<br/>Live"]
  d["객체 D<br/>Garbage"]
  e["객체 E<br/>Garbage"]
  root --> a
  a --> b
  root --> c
  d -.-> e

GC의 핵심 질문은 “이 객체에 도달할 수 있는 경로가 남아 있는가?”이다. 이 질문에 답하는 방식이 GC 알고리즘을 나눈다.

방식 1: 레퍼런스 카운팅 (Reference Counting)

가장 직관적인 방법이다. 각 객체에 “나를 가리키는 포인터가 몇 개인가”를 세는 카운터를 붙인다.

동작 규칙:

  • 새 참조가 생기면 카운터를 1 증가시킨다.
  • 참조가 사라지면 카운터를 1 감소시킨다.
  • 카운터가 0이 되면 그 객체는 쓰레기다. 즉시 해제한다.

장점: 객체가 죽는 순간 바로 해제된다. 지연이 없다.

치명적 약점 — 순환 참조 (Circular Reference): 두 객체가 서로를 가리키면, 외부에서 아무도 접근할 수 없어도 refcount가 0이 되지 않는다.

%% 루트에서 끊어진 순환 참조와 남아 있는 refcount
flowchart LR
  root["루트<br/>참조 끊김"]
  x["객체 X<br/>refcount = 1"]
  y["객체 Y<br/>refcount = 1"]
  unreachable["루트에서 도달 불가<br/>하지만 refcount는 0이 아님"]
  root -.-> x
  x --> y
  y --> x
  x --> unreachable
  y --> unreachable

CPython은 레퍼런스 카운팅을 기본으로 쓰되, 순환 참조를 잡기 위해 별도의 순환 탐지기 (Cycle Detector)를 추가로 돌린다.

방식 2: Mark and Sweep (표시하고 쓸기)

추적 기반 GC(Tracing GC)의 가장 기본적인 형태다. 도달 가능성을 직접 확인한다.

동작 순서:

  1. Mark (표시): 모든 루트에서 출발하여 포인터 체인을 따라간다. 도달한 객체마다 “살아 있음” 비트를 켠다.
  2. Sweep (쓸기): 힙 전체를 순회하면서 “살아 있음” 비트가 꺼진 객체를 해제한다.
%% Mark 단계에서 도달 객체를 표시하고 Sweep 단계에서 미표시 객체를 해제하는 흐름
flowchart TD
  root["루트"]
  a["A<br/>mark"]
  b["B<br/>mark"]
  c["C<br/>mark"]
  d["D<br/>mark 없음"]
  e["E<br/>mark 없음"]
  heap["힙 순회<br/>A(mark), B(mark), C(mark), D(없음), E(없음)"]
  free["D, E 해제<br/>A, B, C의 mark 비트 초기화"]
  root --> a
  a --> b
  root --> c
  d -.-> e
  heap --> free
  c --> heap

장점: 순환 참조를 정확히 찾아낸다. 루트에서 도달 못 하면 refcount와 무관하게 쓰레기다.

단점 — Stop-the-World (STW): Mark 단계에서 객체 그래프가 변하면 안 되므로, 프로그램 실행을 일시 정지해야 한다. 힙이 클수록 정지 시간이 길어진다.

방식 3: 세대별 GC (Generational GC)

대부분의 객체는 만들어진 직후 곧 쓰레기가 된다. 함수 안에서 임시로 만든 리스트, 문자열 연결 중간 결과 등이 대표적이다. 이것을 **세대 가설 (Generational Hypothesis)**이라 한다.

이 관찰을 이용해서, 힙을 세대별로 나눈다.

  • Young Generation (젊은 세대): 새로 생성된 객체가 들어간다. 크기가 작으므로 GC가 빠르다. 자주 수집한다.
  • Old Generation (오래된 세대): Young에서 여러 번 GC를 살아남은 객체가 승격(Promotion)된다. 크기가 크므로 GC가 느리다. 드물게 수집한다.
%% Young Generation에서 Old Generation으로 승격되는 세대별 힙 구조
flowchart LR
  new_object["새 객체"]
  young["Young Generation<br/>자주 GC<br/>새 객체가 먼저 들어오는 곳"]
  old["Old Generation<br/>드물게 GC<br/>오래 살아남은 객체"]
  new_object --> young
  young --> old

Java의 HotSpot JVM이 대표적인 세대별 GC를 사용한다. Young을 다시 Eden + Survivor 0 + Survivor 1로 나누어, 새 객체는 Eden에 할당하고, Minor GC 때 살아남은 객체를 Survivor 사이로 복사하며, 일정 횟수 이상 살아남으면 Old로 승격한다.

GC가 있어도 메모리 누수가 생기는 이유

GC는 “도달 불가능한” 객체만 수거한다. 프로그램이 실수로 컬렉션(리스트, 맵)에 객체를 넣어 놓고 빼지 않으면, 루트에서 해당 컬렉션을 통해 여전히 도달 가능하므로 GC가 수거하지 않는다. 이것을 **논리적 메모리 누수 (Logical Memory Leak)**라 한다.

예: Java에서 static List<Object> cache = new ArrayList<>()에 객체를 계속 추가하기만 하면, 프로그램이 끝날 때까지 모든 객체가 살아 있다.

수동 관리 vs GC 비교

  • 수동 (malloc/free)
    • 해제 시점: 프로그래머가 결정
    • 성능 오버헤드: 없음 (해제 비용만)
    • 위험: Use After Free, 이중 해제, 메모리 누수
    • 대표 언어: C, C++, Rust(소유권 시스템으로 컴파일 타임에 해결)
  • GC
    • 해제 시점: 런타임이 결정
    • 성능 오버헤드: Mark/Sweep 비용 + STW 일시 정지
    • 위험: 논리적 메모리 누수, GC 지연(Latency)
    • 대표 언어: Java, Python, Go, JavaScript, C#

PintOS는 C로 작성된 교육용 OS이므로 GC가 없다. malloc()과 free()를 직접 호출해야 하며, 누수나 이중 해제를 방지하는 것은 전적으로 코드 작성자의 책임이다.

가비지 컬렉션 코드

CPython의 레퍼런스 카운팅 확인

Python에서 sys.getrefcount()로 객체의 현재 참조 카운트를 확인할 수 있다.

sys.getrefcount()의 결과가 예상보다 1 큰 이유: 함수 인자로 전달하는 순간 임시 참조가 하나 추가되기 때문이다.

CPython의 순환 참조 탐지

CPython은 세대별로 순환 탐지를 수행한다. gc.get_threshold()로 세대별 수집 임계값을 확인할 수 있다. 기본값은 (700, 10, 10) — Generation 0에서 할당 카운트가 700을 넘으면 수집을 시작한다.

PintOS에 GC가 없는 이유 — 수동 해제의 예

이 코드가 하는 일: 프로세스 종료 시 가상 메모리 자원, 열린 파일, 자식 프로세스 상태를 명시적으로 해제한다. 각 close_* 함수 안에서 file_close()와 free()를 직접 호출한다. GC가 있다면 이 정리 코드의 상당 부분이 불필요하겠지만, C 기반 OS에서는 프로그래머가 직접 모든 할당-해제 쌍을 관리해야 한다.

정리

가비지 컬렉션은 “누가 이 메모리를 아직 쓰고 있는가?”를 런타임이 자동으로 판단하여, 아무도 쓰지 않는 메모리를 회수하는 메커니즘이다. 레퍼런스 카운팅은 참조 수를 세어 0이 되면 즉시 해제하지만 순환 참조를 처리하지 못하고, Mark and Sweep은 도달 가능성을 추적하여 순환을 포함한 모든 쓰레기를 찾아내지만 Stop-the-World 비용이 든다. 세대별 GC는 “젊은 객체가 일찍 죽는다”는 관찰을 활용해 STW 시간을 줄인다. GC가 있어도 도달 가능한 채로 방치된 객체는 수거되지 않으므로, 논리적 메모리 누수를 방지하는 것은 여전히 프로그래머의 몫이다.
