AWS Immersion Day 재실습 로드맵

여러 서비스가 한 번에 연결되어 어려운 AWS Immersion Day를 단계별로 다시 실습하는 로드맵.

AWS Immersion Day에서는 VPC 안에 EC2를 띄우고 ALB와 Auto Scaling을 붙인다. 여기에 DB와 S3를 연결하고, 다른 축에서는 Bedrock Knowledge Base와 Agent를 만든다. 개별 개념보다 여러 서비스의 관계를 한꺼번에 따라가야 한다는 점이 실습을 어렵게 만든다.

이 로드맵은 다시 실습할 때 지금 무엇을 만들고 있으며 다음 단계가 왜 필요한지 구분하는 데 초점을 둔다. 세부 버튼과 설정값은 각 실습 가이드에서 확인하고, 여기서는 서비스의 의존 순서와 실패했을 때 돌아갈 지점을 살펴본다.

재실습 로드맵이 필요한 이유

콘솔 화면만 따라가면 VPC, subnet, security group, IAM role, endpoint, Bedrock role이 어떻게 연결되는지 놓치기 쉽다. 실습이 실패했을 때 어느 리소스까지 지우고 다시 시작해야 하는지도 판단하기 어렵다. 개인 계정에서는 남은 리소스가 비용을 만들 수 있으므로, 시작 전에 비용 안전장치와 삭제 순서도 정해야 한다.

재실습을 마친 뒤에는 네트워크, 컴퓨트, 데이터베이스, 스토리지, 생성형 AI 실습이 어떤 순서로 의존하는지 설명할 수 있어야 한다. 실패한 계층을 찾아 어느 단계로 되돌아갈지도 판단해야 한다. 이를 위해 리소스를 만들기 전에 삭제 계획부터 세운다.

전체 의존 순서

AWS 실습은 격리된 네트워크 안에 서비스를 배치하고, 필요한 통로만 연 뒤, 사용량과 삭제를 관리하는 과정으로 볼 수 있다.

이 순서는 리소스 사이의 의존성을 따른다. EC2를 배치하려면 VPC가 필요하다. Auto Scaling을 만들려면 AMI와 launch template이 먼저 있어야 한다. RDS를 안전하게 연결하려면 DB subnet group과 DB security group이 필요하다. Bedrock Knowledge Base도 S3 원문, embedding model, vector store, service role을 한 묶음으로 준비해야 한다.

다시 시작하기 전 확인할 것

행사 실습 계정을 사용한다면 Padlet의 lab account 링크로 들어가 콘솔에서 제공된 역할을 사용한다. 개인 계정으로 진행한다면 비용 알림과 Budgets를 먼저 만든다.

워크숍이 지정한 리전 하나를 고정해서 사용한다. 이미 만든 리소스가 보이지 않을 때는 리소스를 다시 만들기 전에 현재 리전이 다른지 확인한다. 개인 AWS 계정과 실습 계정이 섞이지 않도록 실습은 한 브라우저 프로필 안에서만 진행한다.

리소스 이름은 가이드에 나온 이름을 그대로 쓴다. 같은 이름의 리소스가 이미 있다면 이전 실습의 리소스가 남아 있을 수 있으므로 cleanup 문서를 먼저 확인한다.

실습을 중간에 멈출 경우에는 비용이 생기는 리소스부터 지운다. 삭제 우선순위는 RDS, NAT Gateway, EC2/ALB/ASG, S3 public/static hosting, Bedrock vector store, VPC 순서다.

권장 재실습 순서

1회차: Compute & Network

먼저 AWS VPC 실습과 EC2·ALB·Auto Scaling 실습을 완주한다. ALB DNS로 접속했을 때 웹 페이지가 열리고, Auto Scaling Group의 private subnet 인스턴스가 target group에서 healthy로 보이는지 확인한다.

2회차: 데이터 계층

Aurora RDS 실습과 S3 정적 웹 호스팅 실습을 이어서 진행한다. 웹 앱이 DB 연결 정보를 Secrets Manager에서 읽을 수 있어야 한다. S3 정적 웹 페이지에서는 ALB 주소로 이동할 수 있어야 한다.

3회차: 비용과 정리 루틴

AWS 비용 안전장치를 따라 Budgets와 비용 알림을 만든다. 실습 리소스를 의존성 순서대로 지울 수 있는지도 확인한다.

4회차: Bedrock RAG

Bedrock Knowledge Base에서 Knowledge Base가 S3 문서를 sync하는지 확인한다. 검색 근거 chunk와 생성 답변은 각각 나누어 살펴본다.

5회차: Bedrock Agent 운영 확장

Bedrock Agent Flow와 Guardrails에서 Agent가 Knowledge Base와 Lambda action group을 함께 사용하는지 확인한다. trace에서는 어떤 도구와 지식이 쓰였는지 살펴본다. Guardrail을 연결한 뒤에는 차단과 민감정보 처리를 테스트한다.

실패한 계층부터 되돌아가기

웹 페이지가 열리지 않을 때

먼저 ALB target group의 health check 상태를 본다. target이 unhealthy라면 EC2 security group, user data 실행, instance subnet을 확인한다. ALB 자체가 열리지 않는다면 ALB security group이 HTTP 80을 허용하는지 살펴본다.

private subnet 인스턴스가 인터넷 패키지를 받지 못할 때

private route table이 NAT Gateway로 나가는지 확인한다. 이어서 NAT Gateway가 public subnet에 있고 Elastic IP를 가졌는지 본다. 마지막으로 public route table이 internet gateway로 나가는지 확인한다.

RDS에 연결되지 않을 때

DB security group inbound가 웹 인스턴스 security group을 source로 허용하는지 확인한다. Secrets Manager secret의 dbname, username, password가 실습 값과 맞는지도 살펴본다. 웹 인스턴스의 IAM role에는 secret read 권한이 있어야 한다.

Bedrock Knowledge Base가 sync되지 않을 때

S3 data source 경로와 service role 권한을 확인한다. embedding model과 vector store의 생성이 끝나지 않았다면 완료될 때까지 기다린다. 문제 범위를 나누려면 먼저 Generate responses를 끄고 검색 chunk만 확인한다.

Agent가 도구를 사용하지 못할 때

action group의 Lambda와 API schema S3 경로를 확인한다. Agent를 수정했다면 Prepare를 다시 눌렀는지도 살펴본다. trace에서는 Knowledge Base 조회 실패와 Lambda 호출 실패를 나누어 확인한다.
