B-Tree와 B+Tree

B-Tree와 B+Tree

범위: 이 문서는 B-Tree와 B+Tree가 디스크 접근 비용을 줄이는 일반 원리와 구조 선택 기준을 설명하며, minidb의 코드·페이지 크기·엔트리 수·탐색 및 삽입 동작은 특정 구현을 전제로 한 사례다. 구체적인 수치와 동작 여부, 성능 판단은 실제 코드와 버전, 실행 기록 및 성능 측정을 별도로 확인해야 한다.

B-Tree는 한 노드에 여러 개의 키를 담아 트리 높이를 낮춘 정렬 구조다. B+Tree는 거기서 한 발 더 나아가 실제 데이터를 리프에만 두고 리프끼리 연결해, 디스크 기반 DB 인덱스에 가장 잘 맞는 형태가 된다.

B-Tree와 B+Tree가 비용을 줄이는 자리

100만 개의 행이 들어 있는 테이블에서 id = 742301인 행 하나를 찾는다고 하자. 아무 구조도 없으면 행을 처음부터 끝까지 하나씩 비교해야 한다. 최악의 경우 100만 번 비교다. 이걸 풀 스캔(full scan)이라 부른다.

그러면 정렬해 두고 이진 탐색(binary search)을 쓰면 되지 않을까. 메모리 위 배열이라면 맞다. log₂(1,000,000) ≈ 20번이면 찾는다. 그런데 DB의 데이터는 메모리가 아니라 디스크에 있다. 디스크는 바이트 단위로 읽지 않고 페이지(page, 보통 4KB 또는 16KB) 단위로 통째로 읽는다. 이진 탐색은 비교할 때마다 멀리 떨어진 위치로 점프하는데, 그 점프 하나하나가 디스크 페이지를 새로 읽는 비용이다. 20번 비교가 곧 20번의 디스크 접근이 된다.

여기서 질문이 바뀐다. 비교 횟수보다 디스크 접근 횟수 자체를 줄이려면 어떻게 해야 할까. 한 번 읽은 페이지 안에서 최대한 많은 갈림길을 처리하면 된다. 이 발상이 B-Tree다. 이걸 모르면 “왜 DB 인덱스가 이진 트리가 아니라 B+Tree로 되어 있는가”를 이해하기 어렵다.

디스크 접근을 줄이는 트리

이진 탐색 트리(BST, Binary Search Tree)는 노드 하나에 키 1개, 자식 2개를 둔다. 한 번 내려갈 때 갈림길이 2개뿐이다. 그래서 데이터가 많아지면 트리가 깊어진다. 깊이가 곧 디스크 접근 횟수다.

B-Tree의 발상은 단순하다. 노드 하나에 키를 수백 개 담는다. 그러면 자식도 수백 개가 된다. 한 페이지를 읽으면 수백 갈래 중 하나를 고를 수 있다. 갈림길이 2개에서 수백 개로 늘면, 같은 데이터를 담아도 트리가 훨씬 얕아진다.

비유하자면 BST는 두 갈래 길만 있는 미로이고, B-Tree는 한 층마다 수백 개의 문이 달린 건물이다. 같은 방을 찾아도 후자가 층을 적게 오르내린다.

왜 트리가 얕아지는가?

트리 높이 = log_(분기 수)(전체 키 수)

분기 수(한 노드의 자식 수)를 b, 전체 키 수를 N이라 하면 높이는 약 log_b(N)이다.

  • BST: b = 2 → log₂(1,000,000) ≈ 20층
  • B+Tree (한 노드 약 300 분기): log₃₀₀(1,000,000) = ln(1,000,000) / ln(300) ≈ 13.8 / 5.7 ≈ 2.4층

100만 행을 3층 이내에 담는다는 뜻이다. 디스크 접근이 20번에서 3번으로 줄어든다. 분기 수를 키워 높이를 깎는 것, 이것이 B-Tree 계열의 전부다.

B-Tree와 B+Tree의 차이

같은 다방향 트리지만 데이터를 어디에 두느냐가 다르다.

  • B-Tree
    • 모든 노드(내부 노드 포함)가 키와 실제 데이터를 함께 가진다.
    • 운이 좋으면 내부 노드에서 바로 찾고 끝난다.
    • 단점: 내부 노드가 데이터까지 안고 있어 한 노드에 담기는 키 수가 줄고, 범위 검색(BETWEEN, ORDER BY)이 까다롭다.
  • B+Tree
    • 내부 노드는 길 안내(라우팅)만 한다. 키만 두고 데이터는 두지 않는다.
    • 실제 데이터(또는 데이터 위치)는 전부 리프(leaf) 노드에만 둔다.
    • 리프 노드끼리 양방향 연결 리스트로 이어 둔다.
    • 장점: 내부 노드가 가벼워져 분기 수가 더 커지고, 리프를 따라가면 범위 검색이 순차 읽기로 끝난다.

DB 인덱스가 거의 전부 B+Tree인 이유가 여기 있다. WHERE age BETWEEN 20 AND 30 같은 범위 조회가 흔한데, B+Tree는 시작 리프를 찾은 뒤 옆 리프로 줄줄이 따라가면 된다.

B+Tree의 모양을 그림으로 보면 다음과 같다. 내부 노드는 갈림길의 경계값(separator)만 들고, 리프는 정렬된 실제 키와 데이터 위치를 들고 옆으로 연결된다.

%% B+Tree 구조 — 내부 노드는 separator만, 리프는 정렬된 키와 행 위치를 들고 양방향 연결
flowchart TD
  root["내부 노드 (라우팅)<br/>separator 키: [30 &#124; 60]"]
  l1["리프 [10, 20]<br/>+ 행 위치(row_ref)"]
  l2["리프 [30, 45]<br/>+ 행 위치(row_ref)"]
  l3["리프 [60, 80]<br/>+ 행 위치(row_ref)"]
  root -->|key &lt; 30| l1
  root -->|30 ≤ key &lt; 60| l2
  root -->|key ≥ 60| l3
  l1 <-->|정렬 연결| l2
  l2 <--> l3

리프끼리 양방향으로 연결돼 있어, 범위 검색은 시작 리프를 찾은 뒤 옆으로 따라가기만 하면 된다.

내부 노드의 키 30, 60은 데이터가 아니라 “30보다 작으면 왼쪽, 60 이상이면 오른쪽”이라는 경계값일 뿐이다. 실제 데이터는 전부 맨 아래 리프 줄에 있고, 그 리프들이 정렬 순서대로 연결되어 있다.

B-Tree와 B+Tree 코드

이 볼트의 기준 코드인 minidb(직접 구현한 디스크 기반 DB)에는 실제 동작하는 B+Tree가 있다. 노드 하나가 디스크 페이지 하나에 그대로 대응한다. 자식 참조는 메모리 포인터가 아니라 페이지 ID(page_id)다. 디스크에 저장하려면 포인터 주소가 아니라 파일 안의 위치 번호여야 하기 때문이다.

먼저 리프 노드 한 칸이 어떤 바이트로 생겼는지 본다.

리프 한 칸은 키 8바이트와 행 위치 6바이트, 합쳐서 14바이트다. __attribute__((packed))로 패딩을 없애 디스크 바이트와 정확히 일치시킨다.

이제 “한 노드에 키가 수백 개”라는 말이 실제 숫자로 확인된다. 4096바이트 페이지에서 헤더 20바이트를 빼고 14바이트로 나누면 리프 한 장에 키가 몇 개 들어가는지 나온다.

리프 한 장에 약 291개, 내부 노드는 엔트리가 12바이트라 약 340개의 갈림길을 담는다. 분기 수 약 300이 코드에서 그대로 나온다. 앞의 높이 계산에 쓴 숫자가 가공이 아니라 이 구현의 실제 값이다.

탐색은 루트에서 리프까지 내부 노드의 경계값을 보며 자식을 골라 내려가는 일이다. 리프에 도착하면 그 안에서 이진 탐색으로 키를 찾는다.

find_leaf()로 리프 페이지까지 내려간 뒤, 그 페이지 안에서 leaf_find()(이진 탐색)로 키 위치를 찾는다. 찾으면 row_ref(힙 페이지 ID + 슬롯 번호)를 돌려준다. 즉 인덱스가 직접 주는 것은 데이터가 아니라 데이터가 있는 위치다.

삽입할 때 리프가 가득 차면 어떻게 균형을 유지하는지도 코드 주석에 흐름이 정리되어 있다. 넘치면 둘로 쪼개고, 가운데 키를 부모로 올린다.

트리가 자라는 방향이 위가 아니라 아래라는 점이 중요하다. 높이는 루트가 쪼개질 때만 1 증가한다. 그래서 모든 리프가 항상 같은 깊이에 놓이고, 어떤 키를 찾든 디스크 접근 횟수가 같다. 이 균형이 B+Tree가 최악의 경우에도 O(log N)을 보장하는 이유다.

정리

  • B-Tree는 노드 하나에 키를 수백 개 담아 분기 수를 키우고, 그만큼 트리 높이(=디스크 접근 횟수)를 낮춘 정렬 구조다.
  • B+Tree는 내부 노드를 라우팅 전용으로 비우고 데이터를 리프에만 모은 뒤 리프끼리 연결한다. 그래서 분기 수가 더 커지고 범위 검색이 순차 읽기로 끝난다.
  • 디스크는 페이지 단위로 읽으므로, “한 번 읽은 페이지에서 최대한 많은 갈림길을 처리한다”가 설계의 판단 기준이다. DB 인덱스가 이진 트리가 아닌 B+Tree인 이유가 이것이다.
  • 삽입은 넘칠 때 쪼개고 가운데 키를 위로 올려, 모든 리프를 같은 깊이로 유지한다.
