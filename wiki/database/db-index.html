DB 인덱스

DB 인덱스

확인 범위: 이 문서는 DB 인덱스의 일반 원리와 선택 기준을 설명하고 minidb 코드로 그 구조를 예시하지만, 특정 DB 제품·버전의 동작이나 제시된 페이지 접근 횟수와 성능 효과를 실제 실행 기록 또는 측정으로 검증한 결과는 아니다.

인덱스는 테이블 본문과 별도로, 특정 컬럼을 정렬해 둔 보조 자료구조(보통 B+Tree)다. 검색을 행 전수 비교에서 트리 탐색으로 바꿔 주지만, 쓰기와 저장 공간을 대가로 치른다. 책 뒤의 ‘찾아보기’와 같다.

DB 인덱스 혼동

회원 100만 명이 있는 users 테이블에서 SELECT * FROM users WHERE email = 'a@b.com'을 실행한다고 하자. email 인덱스가 없으면 DB는 조건과 일치하는 행을 찾기 위해 테이블을 처음부터 끝까지 확인할 수 있다. 이 접근을 풀 테이블 스캔(full table scan)이라 한다. 실제 비교 횟수와 페이지 읽기 수는 실행 계획, 저장 구조, 캐시 상태에 따라 달라진다.

데이터가 늘어나면 풀 스캔이 확인해야 할 행도 함께 늘어날 수 있다. 실제 지연 시간은 DB 제품, 하드웨어, 캐시와 쿼리 조건을 같은 기준으로 측정해 확인해야 한다.

책으로 비유하면 이렇다. 500쪽짜리 책에서 ‘B+Tree’라는 단어를 찾으려고 1쪽부터 넘기는 것이 풀 스캔이다. 반면 책 뒤의 ‘찾아보기(index)‘를 펴면 ‘B+Tree … 312쪽’이라고 적혀 있다. 찾아보기는 단어를 가나다순으로 정렬해 두고 쪽 번호만 가리킨다. DB 인덱스가 정확히 이것이다. 이 개념을 모르면 “쿼리는 똑같은데 왜 어떤 건 즉시 나오고 어떤 건 멈추는가”를 설명할 수 없다.

풀 스캔을 피하는 구조

인덱스는 테이블 본문을 건드리지 않는다. 대신 특정 컬럼의 값을 뽑아 정렬해 두고, 그 값이 “어느 행에 있는지” 위치만 같이 적은 별도 자료구조다. 정렬되어 있으니 이진 탐색이나 트리 탐색이 가능해진다.

흐름은 두 단계다.

  1. 인덱스에서 찾는 값의 위치를 알아낸다. (정렬된 구조라 빠르다)
  2. 그 위치로 점프해서 테이블 본문의 실제 행을 읽는다.

많은 관계형 DB의 기본 인덱스는 B Tree 또는 B+Tree 계열이다. 한 노드에 여러 키를 담아 트리 높이를 낮추지만, 제품에 따라 hash·bitmap·inverted·spatial index 같은 다른 구조도 제공한다. 따라서 CREATE INDEX가 항상 B+Tree 하나를 만든다고 단정하지 말고, 선택한 index method와 실행 계획을 확인해야 한다.

리프가 가리키는 대상은 제품과 저장 구조에 따라 다르다

인덱스 리프가 행 자체를 담는지, primary key를 담는지, heap tuple 위치를 담는지는 DB 제품과 table storage에 따라 달라진다. 이 차이를 하나의 보편적인 clustered 대 non-clustered 규칙으로 외우면 실제 실행 계획을 잘못 읽기 쉽다.

  • SQL Server의 clustered index처럼 리프가 data page인 구조가 있다.
  • MySQL InnoDB는 primary key를 기준으로 clustered storage를 구성하고, secondary index 리프에는 대상 행의 primary key를 둔다.
  • PostgreSQL의 일반 index는 heap tuple 위치를 가리킨다. CLUSTER는 지정한 index 순서로 table을 한 번 재배치하지만 이후 변경까지 그 순서를 계속 보장하지 않는다.
  • index-organized table처럼 table 자체가 index 구조인 제품 기능도 있다.

그러므로 “인덱스를 탔는데도 왜 table을 다시 읽는가”는 제품명, table storage, index 종류, covering 여부를 함께 보고 답해야 한다. 아래 그림과 minidb 코드는 리프가 row_ref를 보관하고 heap page를 다시 읽는 보조 인덱스 예시다.

flowchart TD
  q["SQL: WHERE id = 742301"]
  leaf["보조 인덱스 리프<br/>key 742301 → row_ref {page 14, slot 3}"]
  heap["heap page 14, slot 3<br/>row: (742301, 'a@b.com', ...)"]
  q -->|"1. index method로 탐색"| leaf
  leaf -->|"2. row_ref로 heap 조회"| heap

이 예시에서 index가 직접 반환하는 값은 행이 아니라 row_ref다. 반면 covering index이거나 리프가 행을 소유하는 저장 구조라면 별도 table lookup이 생략될 수 있다.

비용도 함께 본다

인덱스는 공짜가 아니다. 판단 기준을 위해 대가를 분명히 한다.

  • 쓰기가 느려진다. INSERT/UPDATE/DELETE 때마다 본문뿐 아니라 인덱스 B+Tree도 정렬을 유지하며 갱신해야 한다. 인덱스가 5개면 쓰기 1번에 트리 5개를 손본다.
  • 저장 공간을 더 쓴다. 인덱스는 별도 자료구조라 디스크를 추가로 차지한다.
  • 그래서 “읽기가 많고 쓰기가 적은 컬럼, 그리고 검색 조건으로 자주 쓰는 컬럼”에만 인덱스를 거는 것이 원칙이다. 모든 컬럼에 인덱스를 거는 것은 손해다.

논클러스터드 인덱스의 2단계 점프를 그림으로 보면 이렇다.

%% DB 인덱스 조회 흐름 — 논클러스터드 인덱스의 2단계 점프
flowchart TD
  q["SQL: WHERE id = 742301"]
  leaf["인덱스 리프 (B+Tree)<br/>key 742301 → row_ref {page 14, slot 3}"]
  heap["힙 페이지 14, slot 3<br/>row: (742301, 'a@b.com', ...)"]
  q -->|"1단계: 인덱스 탐색 O(log n)"| leaf
  leaf -->|"2단계: row_ref로 점프"| heap

인덱스가 직접 주는 것은 행이 아니라 행의 위치다. 위치를 받아 본문으로 한 번 더 가는 것이 논클러스터드 인덱스의 본질이다.

DB 인덱스 코드

이 볼트의 기준 코드인 minidb는 id 컬럼에 B+Tree 인덱스를 둔다. 인덱스 리프 한 칸의 정의를 보면, 위에서 설명한 “키 → 행 위치” 구조가 그대로 바이트로 나타난다.

리프는 데이터 본문이 아니라 row_ref(힙 페이지 ID + 슬롯 번호)를 들고 있다. 전형적인 논클러스터드 인덱스의 모양이다. 인덱스가 위치를 알려주면, 그 위치로 힙 페이지를 다시 읽어야 진짜 행이 나온다.

검색은 인덱스 B+Tree를 타고 내려가 위치를 회수하는 한 줄로 끝난다.

bptree_search()가 끝났을 때 손에 쥔 것은 데이터가 아니라 row_ref다. 이 코드로 확인할 수 있는 사실은 B+Tree 탐색 뒤 호출자가 heap page를 다시 읽어야 한다는 점이다. 실제 page access 수와 full scan 대비 성능은 tree height, cache, data distribution, storage 상태를 측정하기 전에는 숫자로 단정하지 않는다.

정리

  • 인덱스는 테이블 본문과 별개로 특정 컬럼을 정렬해 둔 보조 자료구조다. 검색을 행 전수 비교(풀 스캔)에서 트리 탐색으로 바꾼다.
  • 대부분 B+Tree로 구현된다. 디스크 접근 횟수를 트리 높이로 묶기 때문이다.
  • 리프가 행, primary key, heap 위치 중 무엇을 담는지는 제품과 저장 구조에 따라 다르다. covering 여부와 실행 계획까지 확인해야 별도 table lookup이 필요한지 판단할 수 있다.
  • 인덱스는 읽기를 빠르게 하는 대신 쓰기를 느리게 하고 공간을 더 쓴다. 그래서 “자주 검색하고 덜 바뀌는 컬럼”에만 거는 것이 판단 기준이다.
