AWS Aurora RDS 실습 재도전 가이드

Aurora RDS 실습에서는 데이터베이스를 private subnet에 두고, 웹 서버가 Secrets Manager와 IAM role을 통해 접속 정보를 읽게 만든다.

RDS 실습은 웹 서버가 직접 데이터베이스 비밀번호를 들고 있지 않게 만들고, DB는 private subnet 안에서 웹 계층만 접근하게 제한하는 과정이다.

DB를 만들었는지보다 먼저 확인할 기준은 “누가 DB에 접근할 수 있는가”다. Aurora MySQL 클러스터, DB security group, Secrets Manager, IAM instance profile이 한 묶음으로 연결된다.

AWS Aurora RDS 실습 필요성

  • DB를 public으로 열면
    • 인터넷에서 직접 접근 가능한 공격면이 생긴다.
  • 비밀번호를 코드에 박아 넣으면
    • 배포 파일과 로그를 통해 secret이 새어 나갈 수 있다.
  • security group을 IP로 넓게 열면
    • 웹 서버가 바뀔 때마다 규칙이 깨지고, 실수로 과하게 열기 쉽다.
  • 재실습 때 남길 판단 기준
    • DB security group source를 웹 인스턴스 security group으로 제한한다.
    • secret은 Secrets Manager에 저장하고, EC2 role에 읽기 권한을 준다.
    • RDS 삭제 시 deletion protection과 snapshot 옵션을 확인한다.

접속 흐름

애플리케이션은 DB endpoint, username, password, dbname이 필요하다. 이 정보를 코드에 직접 두지 않고 secret으로 보관하면, 서버가 늘어나도 같은 권한 모델을 반복해서 쓸 수 있다.

1단계: DB Security Group 만들기

  • Security Group
    • 이름: DB-SG
    • 설명: Database Security Group
    • VPC: VPC-Lab
    • inbound
      • type: MySQL/Aurora
      • port: 3306
      • source: ASG-Web-Inst-SG

여기서는 source를 IP 대역이 아니라 security group으로 둔다. Auto Scaling Group이 인스턴스를 새로 만들어도, 그 인스턴스가 ASG-Web-Inst-SG를 가지면 DB 접근이 허용된다.

2단계: Aurora MySQL 만들기

  • Engine
    • Amazon Aurora
    • MySQL compatible
    • 예시 버전: Aurora MySQL 3 계열
  • Template
    • 실습에서는 workshop이 지정한 template을 따른다.
    • 개인 계정에서는 비용을 보고 가장 작은 옵션과 정리 계획을 먼저 확인한다.
  • 식별자와 계정
    • cluster identifier: rdscluster
    • master username: awsuser
    • password: 실습용 값은 교육 환경에서만 사용한다. 개인 계정에서는 새 강한 비밀번호를 만든다.
    • initial database name: immersionday
  • Network
    • VPC: VPC-Lab
    • DB subnet group: private subnet 기반
    • public access: No
    • security group: DB-SG
    • port: 3306

Aurora는 클러스터와 인스턴스를 나눠 생각한다. 클러스터는 데이터와 endpoint의 단위이고, writer/reader 인스턴스는 실제 요청을 처리하는 compute 단위다.

3단계: Secrets Manager에 접속 정보 저장

  • Secret
    • 이름: mysecret
    • 종류: RDS credentials
    • host: Aurora endpoint
    • username: DB username
    • password: DB password
    • dbname: immersionday

중요한 점은 애플리케이션이 secret 안에서 dbname까지 읽어야 한다는 것이다. DB 이름이 빠지면 접속은 되어도 사용할 schema를 못 찾는 식으로 실패할 수 있다.

4단계: EC2 IAM role에 secret 읽기 권한 붙이기

  • IAM policy
    • 이름: ReadSecrets
    • action: secretsmanager:GetSecretValue
    • resource: 실습 secret ARN
  • IAM instance profile
    • SSMInstanceProfile에 policy를 attach한다.

이렇게 하면 EC2 웹 서버는 access key를 파일로 들고 있지 않아도, 자신의 IAM role을 통해 secret 값을 읽을 수 있다.

5단계: 웹 앱 연결 확인

  • ALB DNS로 웹 앱 접속
    • DB 연결이 필요한 화면을 연다.
    • 실패하면 애플리케이션 로그를 먼저 본다.
  • 확인 순서
    • secret 값이 맞는가
    • EC2 role에 GetSecretValue 권한이 있는가
    • DB security group이 웹 인스턴스 security group을 허용하는가
    • DB endpoint와 port가 맞는가

자주 막히는 지점

  • “DB가 만들어졌는데 웹 앱이 연결 못 한다”
    • 가장 먼저 DB security group inbound source를 본다.
    • 다음으로 EC2 role의 secret 읽기 권한을 본다.
  • “콘솔에서 endpoint가 여러 개다”
    • writer endpoint와 reader endpoint가 있다.
    • 쓰기가 필요한 앱은 writer endpoint를 사용한다.
  • “삭제가 안 된다”
    • deletion protection이 켜져 있을 수 있다.
    • cluster보다 instance를 먼저 삭제해야 하는 흐름일 수 있다.
