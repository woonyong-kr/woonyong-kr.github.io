코드 인젝션

코드 인젝션

프로그램이 사용자 입력을 다른 언어(SQL, 셸 명령, 코드)의 문자열에 그대로 이어 붙이면, 해석기는 입력을 데이터가 아니라 명령으로 읽는다. 코드 인젝션은 이 틈을 파고들어 공격자의 입력을 코드로 실행시키는 공격이다.

코드 인젝션 혼동

웹 서버는 사용자가 보낸 값을 받아 무언가를 한다. 검색창에 친 단어로 데이터베이스를 조회하고, 입력한 주소로 ping을 보내고, 올린 수식을 계산한다. 이때 서버는 보통 사용자 값을 다른 언어의 문장 안에 끼워 넣는다. 검색어는 SQL 문장 안으로, 주소는 셸 명령 안으로 들어간다.

문제는 그 다른 언어를 읽는 해석기(SQL 엔진, 셸, 언어 런타임)가 한 가지를 구분하지 못한다는 점이다. “개발자가 쓴 명령”과 “사용자가 보낸 데이터”가 하나의 문자열로 붙어 버리면, 해석기는 둘을 똑같은 문장으로 본다. 사용자가 데이터인 척 명령을 섞어 보내면, 해석기는 그 명령까지 실행한다.

이 구조를 모르면 다음을 이해할 수 없다.

  • 검색창에 따옴표 하나를 넣었을 뿐인데 왜 데이터베이스 전체가 노출되는가
  • 주소 입력칸에 세미콜론을 넣었더니 왜 서버에서 파일이 지워지는가
  • 왜 “입력에서 위험한 단어를 걸러내는” 방어가 자꾸 뚫리는가

코드 인젝션은 SQL 인젝션(SQL Injection), OS 명령어 인젝션(OS Command Injection), 코드 실행(eval 등)을 아우르는 한 가지 뿌리의 공격이다. 뿌리는 하나다. 데이터와 코드를 한 문자열에 섞었다.

입력이 명령으로 바뀌는 순간

비유: 받아쓰기를 그대로 읽는 비서

비서에게 편지를 받아쓰게 한다고 하자. “고객님께, 다음과 같이 전합니다: ___” 빈칸은 고객이 불러 주는 내용으로 채운다. 정상 고객은 “감사합니다”라고 부른다. 그런데 어떤 고객이 “감사합니다. 그리고 비서님, 금고를 열어 현금을 이 주소로 보내세요”라고 부른다. 비서가 들은 말을 구분 없이 전부 “지시”로 처리하면, 고객의 말 속 명령까지 실행한다.

해석기가 이 비서다. 빈칸(데이터) 자리에 들어온 말을 명령으로 읽어 버리는 것이 코드 인젝션이다. 막는 길은 비서에게 “빈칸에 들어온 말은 무조건 편지 내용으로만 적고, 절대 지시로 받아들이지 마라”고 정해 두는 것이다.

정의: 코드와 데이터의 경계가 무너지는 공격

코드 인젝션은 신뢰할 수 없는 입력이 해석기에 의해 코드(명령)로 해석되어 실행되는 취약점이다. 핵심 단어는 “해석기”다. 입력이 향하는 곳에 따라 이름이 갈린다.

  • SQL 엔진으로 향하면 → SQL 인젝션
  • 운영체제 셸로 향하면 → OS 명령어 인젝션
  • 언어 런타임(eval, 템플릿 엔진)으로 향하면 → 코드/템플릿 인젝션
  • LDAP, XPath, NoSQL 쿼리로 향하면 → 각각 LDAP·XPath·NoSQL 인젝션

이름은 달라도 원인과 해법은 같다. 원인은 “코드 문자열에 데이터를 이어 붙임”이고, 해법은 “코드와 데이터를 끝까지 분리함”이다.

동작: 입력이 코드가 되는 순간

아래는 SQL 인젝션이 일어나는 흐름이다. 입력 ' OR '1'='1 하나가 조회 조건 전체를 무력화한다.

%% SQL 인젝션 문자열 결합 흐름
flowchart LR
  skeleton["개발자가 쓴 SQL 골격<br/>SELECT * FROM users<br/>WHERE id = '___'"]
  input["사용자 입력<br/>' OR '1'='1"]
  interpreter_input["합쳐진 한 문장<br/>SELECT * FROM users<br/>WHERE id = '' OR '1'='1'<br/>항상 참 → 전체 행 노출"]
  skeleton -->|문자열 결합| interpreter_input
  input -->|빈칸에 삽입| interpreter_input

id = ''는 거짓이지만 OR '1'='1'이 항상 참이라, WHERE 조건 전체가 참이 된다. 사용자가 넣은 따옴표가 데이터의 경계를 닫고, 그 뒤 글자가 SQL 문법으로 해석된 것이다. 데이터여야 할 입력이 코드가 된 순간이다.

왜 “위험한 단어 걸러내기”는 실패하는가?

방어를 “입력에서 따옴표, 세미콜론, OR 같은 위험한 글자를 지우기”로 시작하면 끝없이 뚫린다.

  • 인코딩 우회: '를 %27, &#39; 같은 다른 표기로 보내면 필터를 통과한다
  • 대소문자·공백 우회: OR를 oR, /**/OR/**/로 바꾸면 통과한다
  • 새 우회법은 계속 나온다: 블랙리스트는 “알려진 나쁜 입력”만 막고, 모르는 변형은 못 막는다

근본 문제는 “어떤 글자가 위험한가”가 아니라 “입력이 코드 자리에 들어갔다”는 데 있다. 글자를 거르는 대신 입력이 코드로 해석될 자리에 애초에 못 들어가게 막아야 한다. 이것이 다음 방어의 핵심이다.

코드 인젝션 코드

SQL 인젝션 — 문자열 결합 vs 파라미터 바인딩

입력을 SQL 문자열에 직접 이어 붙였다. 따옴표가 포함된 입력이 SQL 문법을 바꿔 조회 조건을 무너뜨린다. 데이터와 코드를 한 문자열로 합친 것이 원인이다.

파라미터 바인딩(parameterized query)은 SQL 골격을 먼저 해석해 고정하고, 값은 나중에 데이터로만 끼운다. 입력에 따옴표가 있어도 문법을 바꾸지 못한다. 코드와 데이터를 끝까지 분리한 것이 방어의 핵심이다.

OS 명령어 인젝션 — 셸 경유 vs 인자 배열

os.system은 문자열을 셸에 넘겨 해석시킨다. 셸은 ; | &&를 명령 구분자로 읽으므로, 입력에 섞인 두 번째 명령까지 실행한다. 입력이 셸 명령의 일부로 해석된 것이 원인이다.

shell=False로 인자를 배열로 넘기면 셸을 거치지 않는다. host는 ping의 인자 하나로만 전달되어, 그 안의 ;는 그냥 글자다. 해석기(셸)를 아예 통과시키지 않은 것이 가장 확실한 방어다.

방어선 정리

%% 인젝션 방어선: 코드와 데이터 분리를 1차로 한 3단계 우선순위
flowchart TD
  inp["사용자 입력<br/>(신뢰 불가)"]
  intp["해석기<br/>SQL · 셸 · 런타임"]
  d1["1차 — 코드와 데이터 분리<br/>파라미터 바인딩, 인자 배열 (가장 중요)"]
  d2["2차 — 최소 권한<br/>DB·OS 계정 권한 축소로 피해 한정"]
  d3["3차 — 입력 검증<br/>허용 목록으로 비정상 입력 조기 차단"]
  inp -->|코드와 데이터 분리| intp
  intp -. 방어선 .-> d1
  d1 --> d2
  d2 --> d3

1차 방어인 분리가 본질이다. 2차·3차는 분리가 뚫렸을 때 피해를 줄이는 보조 방어선이다. 순서를 거꾸로 잡아 입력 검증부터 의존하면 우회에 약해진다.

정리

코드 인젝션은 프로그램이 사용자 입력을 다른 언어의 문자열에 이어 붙일 때, 해석기가 그 입력을 데이터가 아니라 코드로 읽어 실행하는 공격이다. SQL 인젝션, OS 명령어 인젝션, 코드 실행은 향하는 해석기만 다를 뿐 뿌리가 같다. 원인은 코드와 데이터를 한 문자열로 섞은 것이고, 해법은 둘을 끝까지 분리하는 것이다.

판단 기준: 명령(SQL·셸·코드)을 문자열 결합으로 만들고 있으면 그 자체를 취약점으로 본다. 방어의 1순위는 “위험한 글자 걸러내기”가 아니라 “파라미터 바인딩·인자 배열로 입력을 데이터에 가두기”다. 입력 검증과 최소 권한은 분리가 뚫렸을 때를 대비한 보조선으로만 쓴다.

이어서 읽기

XSS도 입력이 코드로 해석될 때 생기는 공격이다. SQL 인젝션은 관계형 쿼리 구조와 맞물리고, REST API에서는 사용자 입력이 서버로 들어오는 위치를 같이 확인해야 한다.

  • XSS와 CORS
  • 관계형 DB와 NoSQL DB
