무료 TLS/SSL 인증서 — Let's Encrypt와 ACM은 어떻게 공짜로 신뢰를 발급하나

무료 TLS/SSL 인증서 — Let’s Encrypt와 ACM은 어떻게 공짜로 신뢰를 발급하나

범위: 이 문서는 도메인 소유 검증 자동화의 일반 원리와 Let’s Encrypt·AWS ACM의 선택 기준을 설명한다. 제시된 명령, 인증서 값, DNS 레코드는 특정 환경과 시점의 예시이며, 실제 동작과 버전별 차이, 인증서 상태, 성능을 검증한 결과로 일반화하지 않는다.

TLS 인증서는 “이 도메인의 공개키는 이것”이라는 CA의 서명이다. 예전엔 이 서명을 돈 주고 샀지만, Let’s Encrypt와 AWS ACM은 “도메인 소유 확인”을 기계가 자동으로 검증하게 만들어 그 서명을 무료로, 자동으로 발급한다.

무료 TLS/SSL 인증서 문제

암호 응용에서 TLS 인증서가 무엇인지 봤다. “이 도메인의 공개키는 이것이 맞다”를 인증 기관(CA)이 디지털 서명한 문서다. 그리고 자기 서명 인증서는 발급자(issuer)를 믿을 근거가 없어서 브라우저가 경고한다는 것도 봤다.

그러면 경고 없는 진짜 인증서를 받으려면 CA의 서명이 필요한데, 여기서 두 가지 현실적 장벽이 생긴다.

  • 돈: 과거에는 CA가 인증서 한 장에 연 수만 원에서 수십만 원을 받았다. 작은 사이트나 개인 프로젝트에는 부담이었다.
  • 손: 인증서를 받으려면 CSR을 만들어 제출하고, 도메인 소유를 메일이나 전화로 증명하고, 받은 인증서를 서버에 설치하고, 만료 전에 갱신하는 과정을 사람이 직접 해야 했다. 갱신을 깜빡해 사이트 전체가 멈추는 사고가 흔했다.

이 두 장벽 때문에 “HTTPS는 돈 있고 손 많은 곳만 쓰는 것”이라는 분위기가 오래 갔다. 이걸 모르면 왜 2015년 이후에야 갑자기 인터넷 거의 전부가 https://로 바뀌었는지, Let’s Encrypt가 왜 “인터넷을 암호화했다”는 평가를 받는지 설명할 수 없다.

  • 이 문서에서 얻을 판단 기준
    • “도메인 소유 검증”을 기계가 어떻게 자동으로 하는지 구분한다
    • 내 서버에 직접 깔 때(Let’s Encrypt)와 클라우드에 맡길 때(ACM)의 차이를 고른다

무료 발급을 가능하게 한 검증 자동화

비싸고 손이 많이 갔던 진짜 이유

인증서 발급에서 어려운 부분은 암호 연산이 아니다. 서명 자체는 디지털 서명에서 봤듯 한순간에 끝난다. 진짜 어려운 건 그 앞 단계, **도메인 소유 검증(domain validation)**이다.

CA는 아무에게나 서명해 주면 안 된다. example.com의 인증서를 example.com을 실제로 소유한 사람에게만 줘야 한다. 그렇지 않으면 공격자가 남의 도메인 인증서를 받아 가짜 사이트를 진짜처럼 꾸밀 수 있다. 과거에는 이 “정말 네 도메인이 맞냐”를 사람이 메일을 주고받으며 확인했다. 느리고, 사람 손이 들고, 그래서 비쌌다.

Let’s Encrypt의 발상은 단순하다. 이 검증을 사람이 아니라 기계가, 프로토콜로 자동으로 하게 만들자.

Let’s Encrypt — 검증을 자동화하는 프로토콜(ACME)

Let’s Encrypt는 무료 CA다. 중심에는 ACME(Automatic Certificate Management Environment)라는 프로토콜이 있다. “네가 정말 이 도메인을 통제하는지”를 기계가 확인하는 절차를 표준화했다.

비유는 집 소유 증명이다. 부동산 등기를 일일이 떼지 않아도, “지금 그 집 우편함에 내가 보낸 쪽지가 있냐”를 확인하면 그 집을 통제한다는 걸 알 수 있다. ACME는 도메인에 대해 똑같은 일을 한다.

대표적인 검증 방식(challenge)은 두 가지다.

  • HTTP-01: CA가 준 토큰을 http://<도메인>/.well-known/acme-challenge/<토큰> 경로에 올려 둔다. CA가 그 주소에 접속해 토큰이 있으면 “이 웹 서버를 통제하는군” 하고 인정한다.
  • DNS-01: CA가 준 값을 도메인의 TXT 레코드에 등록한다. CA가 DNS를 조회해 그 값이 있으면 “이 도메인의 DNS를 통제하는군” 하고 인정한다. 와일드카드(*.example.com) 인증서에 쓴다.

검증이 끝나면 CA가 서명한 인증서가 자동으로 발급되고, certbot 같은 클라이언트가 서버에 설치까지 한다.

왜 유효 기간이 90일인가?

Let’s Encrypt 인증서는 90일짜리다. 상용 CA의 1~2년보다 훨씬 짧다. 이유는 두 가지다.

키가 유출됐을 때 위험 노출 기간 = 인증서 유효 기간 90일이면 → 유출돼도 최대 90일 뒤 자동 폐기 1년이면 → 유출이 1년간 악용될 수 있음

게다가 갱신이 자동이라 사람이 짧은 주기를 부담스러워할 이유가 없다. 보통 만료 30일 전(60일째)에 자동 갱신한다. 짧은 수명은 자동화를 전제로 했기에 가능한 선택이다.

AWS ACM — 클라우드가 인증서를 통째로 관리한다

ACM(AWS Certificate Manager)도 무료로 인증서를 발급하지만 결이 다르다. Let’s Encrypt는 “인증서를 받아 내 서버에 직접 깐다”이고, ACM은 “AWS가 인증서를 발급·보관·갱신까지 다 하고, 나는 AWS 서비스에 붙여 쓰기만 한다”이다.

비유는 직접 요리 대 호텔 룸서비스다. Let’s Encrypt는 재료를 받아 내 주방에서 요리한다. ACM은 주문만 하면 완성된 음식이 방으로 온다. 대신 그 음식을 호텔 밖으로 들고 나갈 수는 없다.

  • 검증: 보통 DNS 검증을 쓴다. AWS가 알려준 CNAME 레코드를 도메인에 등록하면 자동 확인한다. Route 53을 쓰면 등록까지 자동이다.
  • 갱신: 완전 자동이다. 만료 전 AWS가 알아서 새 인증서로 교체한다.
  • 제약: 발급된 인증서의 개인키는 AWS 밖으로 빼낼 수 없다. ELB, CloudFront, API Gateway 같은 AWS 서비스에 붙여 쓰는 용도다. 내 EC2 안의 nginx에 직접 파일로 깔고 싶다면 ACM 대신 Let’s Encrypt가 맞다.

Let’s Encrypt와 ACM의 차이를 한 축(인증서를 누가 들고 있나)으로 비교한다. 비교가 목적이므로 표가 적합하다.

항목Let’s EncryptAWS ACM
발급 주체공개 무료 CAAWS 내부 CA
인증서 위치내 서버에 설치AWS가 보관 (반출 불가)
검증 방식HTTP-01 / DNS-01주로 DNS (CNAME)

무료 TLS/SSL 인증서 코드

추상적인 “자동 검증”을 실제 명령과 인증서 값으로 내려본다. 아래 인증서 값은 실제 운영 중인 사이트에서 직접 뽑은 결과다.

먼저 certbot으로 Let’s Encrypt 인증서를 받는 명령이다. nginx가 깔린 서버에서 한 줄이면 발급·설치·갱신 설정까지 끝난다.

이 한 줄 안에서 ACME 검증이 자동으로 돈다. HTTP-01 방식이면 certbot이 토큰 파일을 잠깐 웹 루트에 올리고, Let’s Encrypt가 그 주소에 접속해 확인한다.

# CA가 확인하는 경로 (certbot이 잠시 올려두는 토큰)
http://example.com/.well-known/acme-challenge/9f8s...토큰...

CA가 이 주소에서 올바른 토큰을 읽으면 “이 웹 서버를 통제하는군” 하고 서명해 준다. 이 코드에서 기억할 것: 발급의 본질은 암호가 아니라 “이 도메인을 정말 통제하느냐”의 자동 증명이다.

발급된 인증서가 자기 서명이 아니라 진짜 CA 서명인지 확인한다. 운영 중인 letsencrypt.org의 실제 인증서를 들여다본다.

issuer=C = US, O = Let's Encrypt, CN = E7     # 발급자가 Let's Encrypt
subject=CN = letsencrypt.org                  # 주체가 도메인
notBefore=May  7 16:14:37 2026 GMT
notAfter=Aug  5 16:14:36 2026 GMT             # 5월 7일 → 8월 5일 = 정확히 90일

암호 응용에서 본 자기 서명 인증서는 issuer와 subject가 같았다. 여기서는 issuer가 Let's Encrypt, subject가 letsencrypt.org로 다르다. 제3자 CA가 보증했다는 뜻이라 브라우저가 경고 없이 받아들인다. 유효 기간도 5월 7일부터 8월 5일까지 정확히 90일이다. 이 코드에서 기억할 것: issuer가 자기 자신이 아닌 신뢰받는 CA로 찍혀 있고, 그 CA가 브라우저 루트 저장소에 있어야 경고가 사라진다.

ACM은 명령이 아니라 DNS 레코드 등록으로 검증한다. AWS가 알려준 값을 도메인에 한 번 넣으면 끝난다.

이 CNAME이 DNS에 보이면 AWS가 자동으로 소유를 확인하고 인증서를 발급한다. 그 뒤 갱신도 AWS가 알아서 한다. 이 코드에서 기억할 것: ACM에서는 인증서 파일을 손에 쥐지 않는다. DNS 레코드 하나만 넣고, 인증서는 AWS 서비스에 “붙여 쓴다”.

정리

  • TLS 인증서는 “이 도메인의 공개키는 이것”이라는 CA의 디지털 서명이다. 발급이 비쌌던 이유는 암호 연산이 아니라 “도메인 소유 검증”을 사람이 했기 때문이다.
  • Let’s Encrypt는 이 검증을 ACME 프로토콜로 자동화했다. HTTP-01(토큰 파일)이나 DNS-01(TXT 레코드)로 기계가 소유를 확인하고, certbot이 발급·설치·갱신을 자동으로 한다.
  • 유효 기간 90일은 자동 갱신을 전제로 한 선택이다. 키 유출 시 노출 기간을 짧게 줄인다.
  • AWS ACM도 무료지만 결이 다르다. AWS가 인증서를 보관·갱신하고 개인키는 반출되지 않는다. ELB·CloudFront 같은 AWS 서비스에 붙여 쓸 때 맞다.
  • 판단 기준: 내 VM의 nginx/apache에 직접 인증서를 깔아야 하면 Let’s Encrypt, AWS 서비스 앞단에 붙이고 관리까지 맡기고 싶으면 ACM을 고른다. 둘 다 무료이고, 가른 기준은 “인증서 파일을 내가 직접 들고 있어야 하느냐”다.

이어서 읽기

무료 인증서가 해결한 문제는 TLS의 신뢰 앵커를 자동으로 발급하는 일이다. 인증서가 TLS 안에서 어떤 역할을 하는지, 그 위에 인증·인가가 어떻게 얹히는지는 아래 흐름으로 이어진다.
