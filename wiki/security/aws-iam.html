AWS IAM

AWS IAM

확인 범위: 이 문서는 AWS IAM의 주체·정책·자원, 권한 평가와 최소 권한에 관한 일반 개념과 선택 기준을 예시로 설명한다. 제시된 정책과 접근 흐름은 특정 환경·버전에서 실제 실행하거나 검증한 결과가 아니다. 실제 적용 가능성과 동작·보안·성능을 판단하려면 대상 코드와 설정, 버전, 실행 기록 및 측정 결과를 별도로 확인해야 한다.

AWS IAM(Identity and Access Management)은 “누가(주체), 무엇에(자원), 어떤 행동을(액션) 해도 되는가”를 JSON 정책으로 선언하는 클라우드 권한 시스템이다. 요청이 들어오면 해당 정책을 기준으로 허용하거나 거부한다.

하나의 AWS 계정을 함께 쓸 때 생기는 문제

회사가 AWS 계정 하나에 서버, 데이터베이스, 파일 저장소(S3), 결제 정보를 모두 올렸다. 이제 개발자 다섯 명과 자동 배포 스크립트 하나가 이 계정을 함께 써야 한다.

가장 단순한 방법은 계정을 만들 때 받은 최고 권한 로그인인 루트 계정을 공유하는 것이다. 그러나 이 방법으로는 사람과 프로그램마다 권한을 구분할 수 없다.

  • 인턴이 실수로 운영 데이터베이스를 통째로 지워도 막을 방법이 없다. 모두가 모든 것을 할 수 있기 때문이다.
  • 배포 스크립트의 비밀키가 깃허브에 실수로 올라가면, 그 키 하나로 계정 전체가 털린다.
  • 누가 무엇을 했는지 구분이 안 된다. 로그를 봐도 전부 “루트 계정”으로 찍힌다.

이 문제는 “계정에 로그인할 수 있다”와 “이 자원에 이 행동을 해도 된다”가 분리되어 있지 않다는 데서 생긴다. 로그인 수단을 넘기는 순간 모든 권한까지 통째로 넘기게 된다.

AWS IAM은 로그인할 신원과 그 신원이 행사할 권한을 분리한다. 사람과 스크립트마다 별도 신원을 만들고, 각 신원에는 “S3의 이 버킷만 읽기”처럼 필요한 권한만 정책으로 붙인다. 이 구조를 알아야 클라우드에서 권한이 왜 거부되는지(AccessDenied), 역할(Role)과 사용자(User)가 왜 다른지, 서버가 비밀키 없이 어떻게 S3에 접근하는지를 이해할 수 있다.

로그인과 권한을 분리하는 구조

회사 출입증으로 이해하기

대기업 출입 시스템에서는 정문에서 신원을 확인한 뒤 사원증에 부서별 출입 권한을 부여한다. 신원을 확인하는 과정은 인증이고, 확인된 신원에 허용할 범위를 정하는 과정은 인가다.

  • 신원과 권한은 분리되어 있다. 사원증에는 그 사람이 어디까지 들어갈 수 있는지가 정해진다.
  • 권한은 직무에 따라 다르다. 개발팀은 서버실, 회계팀은 금고실에 들어갈 수 있고, 필요 없는 문은 열리지 않는다.
  • 외부 협력사 직원에게는 사원증 대신 하루짜리 임시 출입증에 해당하는 역할을 빌려준다.

IAM도 같은 방식으로 신원별 접근 범위를 통제한다. 누가 요청했는지 확인한 뒤, 그 신원이 어디에서 무엇을 할 수 있는지를 정책으로 판단한다.

요청을 판단하는 세 요소

IAM의 판단에는 주체, 정책, 자원이 등장한다.

  • 주체(Principal): 요청을 보내는 신원. 사람용 사용자(User), 사람 묶음(Group), 임시로 빌리는 역할(Role)이 있다.
  • 정책(Policy): “무엇을 허용하거나 거부하는가”를 적은 JSON 문서. 주체나 자원에 붙는다.
  • 자원(Resource): 행동의 대상. S3 버킷, EC2 인스턴스, DynamoDB 테이블 등이다.

요청이 들어오면 IAM은 이 요소를 연결해 판단한다. 확인할 질문은 “이 주체가 이 자원에 이 액션을 하도록 허용한 정책이 있는가?”이다.

사용자(User)와 역할(Role)의 차이

User와 Role은 모두 권한을 담지만, 수명과 비밀키 보관 방식이 다르다.

  • 사용자(User): 사람에게 영구히 귀속된다. 긴 수명의 비밀키인 액세스 키를 가지며, 이 키를 저장해 두고 계속 쓴다.
  • 역할(Role): 누구에게도 영구 귀속되지 않는다. 필요할 때 잠깐 “맡아서(assume)” 쓰며, 자동으로 만료되는 임시 자격증명을 받는다. 영구 비밀키는 없다.

영구 비밀키가 유출되면 만료되기 전까지 계속 악용될 수 있다. 그래서 서버나 스크립트에는 User의 영구 키를 넣지 않고 Role을 맡긴다. 서버나 스크립트는 필요할 때마다 짧은 수명의 임시 키를 받고, 이 키는 유출되더라도 곧 만료된다. 이 발상은 OAuth 2.0에서 access token을 짧게, refresh token을 길게 나누는 이유와 같다.

명시적으로 허용하지 않으면 거부한다

IAM은 다음 순서로 요청을 평가한다.

요청 평가 순서:
1. 명시적 Deny가 하나라도 있으면 → 거부 (가장 강함)
2. 명시적 Allow가 하나라도 있으면 → 허용
3. 아무것도 없으면 → 거부 (암묵적 거부)

아무 정책도 행동을 명시적으로 허용하지 않으면 요청은 거부된다. 명시적 Deny가 있다면 Allow가 있어도 Deny가 우선한다.

이 규칙에서는 막아야 할 권한을 빠뜨리더라도 해당 요청이 허용되지 않는다. 기본이 허용이면 빠뜨린 권한이 열린 채로 남지만, 기본이 거부이면 닫힌 채로 남는다. 필요한 권한만 부여해 접근 범위를 줄이는 방식을 최소 권한 원칙(least privilege)이라고 한다.

다른 클라우드 서비스와의 용어 차이

  • AWS IAM 기준: 위에서 설명한 User / Group / Role / Policy 구조와 JSON 정책 문법(Effect, Action, Resource)을 사용한다.
  • Azure 기준: 같은 개념을 Microsoft Entra ID(옛 Azure AD)와 RBAC(Role-Based Access Control)로 부른다. “사용자에게 역할을 범위(scope)에 할당한다”는 모델이며, AWS의 JSON 정책 대신 역할 정의(Role Definition)를 쓴다.
  • GCP 기준: IAM이라는 이름은 같지만, 멤버인 주체에게 역할(role)을 자원에 바인딩한다. 따라서 AWS의 정책 문서 모델과 세부 방식이 다르다.
  • 공통점: 셋 모두 “기본 거부 + 명시적 허용 + 최소 권한”이라는 원칙을 공유한다. 정책을 표현하는 문법과 용어에는 차이가 있다.

JSON 정책 읽기

IAM 정책은 권한을 선언하는 JSON 문서다. 정책에서 어떤 행동을 어떤 자원에 허용하거나 거부하는지 읽을 수 있어야 요청의 평가 과정을 이해할 수 있다.

1단계: 정책 한 장 읽기

다음 정책은 특정 S3 버킷의 객체를 읽는 행동만 허용한다.

정책을 읽을 때는 Effect, Action, Resource를 차례로 본다. Effect는 허용할지 거부할지, Action은 어떤 행동인지, Resource는 어떤 대상인지 나타낸다. 이 정책에는 객체 쓰기(s3:PutObject)와 삭제를 허용하는 내용이 없다. 따라서 기본 거부 규칙에 따라 해당 행동은 막히고, 이 정책을 가진 주체는 파일을 읽을 수만 있다.

2단계: ARN으로 자원 범위 읽기

Resource에 있는 arn:aws:s3:::my-bucket/*는 ARN(Amazon Resource Name) 형식의 자원 주소다.

%% ARN이 자원 주소를 조각으로 나누는 방식
flowchart TD
  arn["arn &#124; aws &#124; s3 &#124; 비어 있음 &#124; 비어 있음 &#124; my-bucket/*<br/>전체 값: arn:aws:s3:::my-bucket/*"]
  prefix["고정 접두사<br/>ARN 형식의 시작"]
  partition["파티션<br/>aws"]
  service["서비스<br/>s3"]
  scope["리전·계정<br/>S3는 전역이라 비어 있음"]
  resource["자원 경로<br/>이 버킷의 모든 객체"]
  arn --> prefix
  arn --> partition
  arn --> service
  arn --> scope
  arn --> resource

ARN은 AWS 자원을 가리키는 고유 주소다. 정책은 이 주소로 권한이 적용될 자원을 나타낸다. *는 와일드카드이며 여기서는 “이 버킷 아래의 모든 객체”를 뜻한다. 버킷 하나나 경로 하나처럼 자원을 좁게 지정할수록 권한의 범위도 좁아진다.

3단계: 겹치는 정책 평가하기

다음 두 정책은 모든 S3 객체 읽기를 허용하면서 secret-bucket의 객체 읽기만 명시적으로 거부한다.

주체가 두 정책을 모두 가졌다고 하자. secret-bucket을 읽는 요청에는 A의 Allow와 B의 Deny가 함께 적용된다. 명시적 Deny가 우선하므로 결과는 거부다. 다른 버킷은 B의 대상이 아니므로 A의 Allow에 따라 읽을 수 있다. 이처럼 Deny는 예외적으로 허용해서는 안 되는 범위를 명시하는 안전장치가 된다.

4단계: 서버가 비밀키 없이 S3에 접근하기

EC2 서버가 영구 비밀키를 코드에 넣지 않고 Role을 맡아 임시 자격증명을 받는 흐름이다.

%% EC2 서버가 임시 자격증명으로 S3에 접근하는 순서
flowchart TD
  iam_role_temp_credential_flow["EC2 서버가 임시 자격증명으로 S3에 접근하는 순서"]

이 방식에서는 서버 코드에 비밀키를 넣지 않는다. 서버에 Role을 연결하고 그 Role에 필요한 정책을 부여한다. 서버가 받는 임시 키는 몇 시간 뒤 자동으로 만료되므로, 유출되더라도 피해 범위가 제한된다. 따라서 서버나 스크립트에는 영구 키를 넣는 대신 Role을 사용한다.

요청이 거부될 때 확인할 순서

AWS IAM의 권한 문제를 살필 때는 먼저 요청을 보낸 주체가 User인지 Role인지 확인한다. 그다음 요청한 액션과 대상 자원의 ARN을 찾고, 이 조합을 허용하는 정책이 있는지 본다. 명시적 Deny가 있다면 Allow보다 먼저 적용되며, Allow도 Deny도 없다면 암묵적으로 거부된다.

사람에게 영구히 귀속되는 신원과 서버·스크립트가 잠시 맡는 신원을 구분하는 것도 중요하다. 사람은 User를 사용하고, 서버와 스크립트는 Role을 통해 임시 자격증명을 받는다. 어느 경우든 필요한 액션과 자원만 좁게 허용해야 최소 권한 원칙을 지킬 수 있다.

이어서 읽기

IAM의 Role과 임시 자격증명은 웹의 권한 위임 및 짧은 수명 토큰과 닮아 있다. AWS ACM처럼 클라우드가 관리하는 신뢰 체계와 서명·검증을 떠받치는 암호 부품까지 함께 보면 권한 시스템의 아래층을 연결해서 이해할 수 있다.

  • OAuth 2.0
  • SSL 인증서
  • 암호 응용
