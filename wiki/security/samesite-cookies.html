SameSite 쿠키 — 다른 사이트가 시작한 요청에 쿠키를 붙일지 정하는 빗장

SameSite 쿠키 — 다른 사이트가 시작한 요청에 쿠키를 붙일지 정하는 빗장

확인 범위: 이 문서는 SameSite 쿠키의 일반 원리와 Strict·Lax·None의 선택 기준을 설명하며, 포함된 HTTP·Django·Spring Boot 코드는 동작을 보여 주는 예시다. 특정 브라우저·프레임워크 버전에서의 실제 동작과 설정 호환성은 실행 기록이나 성능 측정으로 검증한 결과를 제시하지 않는다.

쿠키는 같은 도메인으로 가는 모든 요청에 자동으로 따라붙는다. 이 자동 첨부가 CSRF 공격의 통로가 되는데, SameSite 속성은 “다른 사이트에서 시작된 요청에는 쿠키를 붙이지 마라”고 브라우저에 지시해 그 통로를 막는다.

SameSite 쿠키 구분

쿠키에는 편리하지만 위험한 성질이 하나 있다. 브라우저는 어떤 도메인으로 요청을 보낼 때, 그 도메인의 쿠키를 자동으로 Cookie 헤더에 실어 보낸다. 개발자가 코드를 쓰지 않아도 알아서 붙는다.

문제는 “누가 그 요청을 시작했는지”를 따지지 않는다는 점이다. 내가 bank.com에 로그인해 세션 쿠키를 받았다고 하자. 이 상태에서 공격자가 만든 evil.com에 접속하면, 그 페이지 안에 숨겨진 코드가 내 브라우저를 시켜 bank.com으로 송금 요청을 보낼 수 있다. 이때 브라우저는 “bank.com으로 가는 요청이네” 하고 내 세션 쿠키를 자동으로 붙인다. 서버 입장에서는 정상 로그인한 내가 보낸 요청과 구별되지 않는다.

이것이 사이트 간 요청 위조 (Cross-Site Request Forgery, CSRF)다. 공격자는 내 쿠키 값을 훔칠 필요조차 없다. 그저 내 브라우저가 쿠키를 자동으로 붙인다는 성질을 이용해, 내 권한으로 요청을 대신 보내게 만든다.

SameSite를 모르면 “왜 로그인 쿠키만으로는 부족해서 CSRF 토큰을 따로 쓰는지”, “요즘 브라우저가 왜 갑자기 일부 외부 요청에서 쿠키를 빼버리는지”를 설명할 수 없다. SameSite는 CSRF의 근원인 “출처를 묻지 않는 자동 첨부”에 직접 빗장을 거는 속성이다.

쿠키 자동 전송을 제어하는 법

비유: 자동으로 보여주는 신분증

쿠키는 브라우저가 해당 도메인에 갈 때마다 자동으로 내미는 신분증이다. 편리하다. 매번 다시 로그인하지 않아도 된다.

하지만 신분증이 너무 고분고분하면 곤란하다. 낯선 사람이 “저기 은행 가서 이 서류 좀 내줘”라고 시켰는데, 신분증이 군말 없이 따라가 버리면 내 이름으로 일이 처리된다. SameSite는 신분증에 “내가 직접 그 사이트에 들어갈 때만 보여주고, 남이 시킨 심부름에는 따라가지 마라”는 규칙을 새기는 것이다.

”same site”는 정확히 무엇인가

이름이 SameSite이므로 “같은 사이트”의 기준을 정확히 알아야 한다. 여기서 사이트(site)는 출처(origin)보다 넓은 개념이다.

  • 사이트(site)의 기준 = 등록 가능 도메인(eTLD+1). example.com이 사이트 단위다.
  • 따라서 app.example.com과 api.example.com은 서브도메인이 달라도 같은 사이트다.
  • example.com과 evil.com은 다른 사이트다(cross-site).

요청이 “같은 사이트”인지 “다른 사이트”인지는 두 가지로 갈린다.

  • 요청을 시작한 페이지의 사이트(요청 맥락) = 도착지의 사이트 → same-site
  • 요청을 시작한 페이지의 사이트 ≠ 도착지의 사이트 → cross-site

evil.com에 떠 있는 페이지가 bank.com으로 요청을 보내면 cross-site다. SameSite는 바로 이 cross-site 요청에 쿠키를 붙일지 말지를 통제한다.

세 가지 값: Strict, Lax, None

SameSite는 세 값 중 하나를 가진다. cross-site 요청에 쿠키를 얼마나 붙이느냐가 다르다.

  • Strict: cross-site 요청에는 어떤 경우에도 쿠키를 붙이지 않는다. 가장 엄격하다.
  • Lax: cross-site여도 “안전한 이동”에만 붙인다. 안전한 이동 = 사용자가 직접 링크를 클릭해 페이지를 통째로 옮기는 최상위 탐색(top-level navigation)의 GET 요청. 그 외(폼 POST, 이미지·iframe 내부 요청, 자바스크립트 fetch)에는 붙이지 않는다.
  • None: cross-site든 아니든 항상 붙인다. 단 반드시 Secure(HTTPS 전용)와 함께 써야 한다. 안 그러면 브라우저가 쿠키를 거부한다.

Lax에서 헷갈리는 지점은 “안전한 이동” 예외다. CSRF 공격은 대부분 폼 자동 제출(POST)이나 백그라운드 요청으로 일어난다. Lax는 바로 그 위험한 요청들에서 쿠키를 빼버린다. 반면 사용자가 외부 검색 결과에서 내 사이트 링크를 클릭해 들어오는 정상 이동(GET)에는 쿠키를 유지해, 로그인이 풀리지 않게 한다.

왜 Lax가 요즘 기본값이 되었나

과거 브라우저는 SameSite를 지정하지 않은 쿠키를 None처럼(항상 첨부) 다뤘다. 즉 모든 쿠키가 기본적으로 CSRF에 노출돼 있었다. 2020년부터 크롬을 시작으로 주요 브라우저는 SameSite를 명시하지 않은 쿠키를 Lax로 간주하도록 기본값을 바꿨다.

명시 안 함 → 과거: None처럼 동작(모든 cross-site 요청에 첨부) → CSRF에 무방비 명시 안 함 → 현재: Lax로 동작(위험한 cross-site 요청에서 제외) → CSRF 기본 방어

Lax를 기본값으로 고른 이유는 균형이다. Strict를 기본으로 하면 외부 링크로 들어온 사용자가 매번 로그아웃 상태로 보여 불편하다. None을 기본으로 두면 CSRF에 무방비다. Lax는 “정상적인 링크 이동은 살리되, 공격에 쓰이는 폼·백그라운드 요청은 막는” 중간값이다.

동작 비교 한눈에 보기

각 시나리오에서 쿠키가 붙는지 비교한다. 비교가 판단 기준이므로 표를 쓴다.

외부 링크 클릭으로 들어오는 GET안 붙음붙음붙음
외부 사이트의 폼 POST안 붙음안 붙음붙음

외부 사이트의 자바스크립트 fetch안 붙음안 붙음붙음

Strict와 Lax의 유일한 차이는 둘째 줄(외부 링크 클릭 GET)뿐이다. 나머지 위험한 요청은 둘 다 막는다.

SameSite 쿠키 코드

CSRF 공격이 작동하는 모습

공격자 페이지(evil.com)에 숨겨진 자동 제출 폼이다. 피해자가 이 페이지를 열기만 하면 폼이 스스로 제출된다.

피해자가 bank.com에 로그인된 상태라면, 이 폼이 만든 POST 요청에 브라우저가 세션 쿠키를 자동으로 붙인다. 서버는 정상 요청으로 받아들여 송금을 실행한다. 공격자는 쿠키 값을 본 적도 없다.

SameSite가 그 요청을 막는 법

bank.com이 세션 쿠키를 SameSite=Lax(또는 Strict)로 내렸다고 하자.

이제 위 공격의 cross-site POST 요청이 나갈 때 브라우저는 이렇게 판단한다.

세션 쿠키가 빠지므로 서버는 이 요청을 “로그인 안 된 익명 요청”으로 보고 거부한다. 공격의 통로였던 “자동 첨부”가 cross-site POST에서 끊겼다.

백엔드에서 SameSite 쿠키 설정하기

대부분의 프레임워크는 세션 쿠키 설정에서 SameSite를 직접 지정한다.

두 코드 모두 결과는 같은 Set-Cookie 헤더다. 기억할 것은 SameSite를 HttpOnly·Secure와 한 묶음으로 거는 것이 표준이라는 점이다. HttpOnly는 XSS로 인한 쿠키 탈취를, Secure는 도청을, SameSite는 CSRF를 각각 막는다. 셋이 막는 공격이 다르므로 함께 쓴다.

SameSite만으로 충분한가

SameSite=Lax는 강력하지만 만능은 아니다. 한계가 있다.

  • 같은 사이트 안에서 일어나는 공격(예: XSS로 주입된 스크립트가 같은 사이트로 요청)은 cross-site가 아니므로 막지 못한다.
  • 오래된 브라우저는 SameSite를 무시할 수 있다.
  • None이 꼭 필요한 정당한 cross-site 시나리오(외부 결제 위젯, 일부 SSO 흐름)에서는 SameSite로 막을 수 없다.

그래서 민감한 상태 변경 요청에는 SameSite에 더해 CSRF 토큰(서버가 발급한 예측 불가능한 값을 요청 본문/헤더로 함께 검증)을 병행하는 것이 표준이다. SameSite는 1차 방어선이고, CSRF 토큰은 그 방어선을 보강하는 2차 방어선이다.

정리

  • 쿠키는 같은 도메인으로 가는 요청에 자동으로 붙는다. 이 자동 첨부가 출처를 묻지 않기 때문에 CSRF, 즉 “내 권한으로 남이 요청을 대신 보내는” 공격이 가능하다.
  • SameSite는 “다른 사이트에서 시작된 요청에 쿠키를 붙일지”를 통제한다. Strict는 cross-site에 절대 안 붙이고, Lax(현재 기본값)는 외부 링크 클릭 GET에만 붙이며, None은 항상 붙이되 Secure가 필수다.
  • Lax가 기본값이 된 이유는 균형이다. 정상적인 외부 링크 이동은 살리고, 공격에 쓰이는 폼 POST·백그라운드 요청에서는 쿠키를 빼 CSRF를 기본 차단한다.
  • 판단 기준: 로그인 세션 쿠키는 최소 Lax로 두고, 외부에서 내 사이트로 진입하는 흐름이 거의 없다면 Strict까지 올린다. cross-site가 꼭 필요할 때만 None+Secure를 쓴다. 그리고 민감한 요청은 SameSite만 믿지 말고 CSRF 토큰을 함께 검증한다.

이어서 읽기

SameSite는 쿠키의 자동 전송 성질 위에 얹히는 속성이다. 저장소의 차이를 먼저 구분하고, 같은 출처 정책과 XSS/CORS의 경계까지 이어서 보면 CSRF가 어디에 놓이는지 선명해진다.
