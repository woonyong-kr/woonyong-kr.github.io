HTTPS와 Mixed Content — 평문 HTTP를 암호화하고, 섞이면 왜 막는가

확인 범위: 이 문서는 HTTPS와 Mixed Content의 일반 원리와 판단 기준을 개념적으로 설명하며, 제시된 명령어·설정·출력은 동작을 이해하기 위한 예시다. 특정 OS·브라우저·서버·TLS 버전에서의 실제 차단·승급 동작이나 인증서 검증 결과는 해당 환경의 코드, 버전, 실행 기록으로 별도 확인해야 한다.

HTTPS는 HTTP 메시지를 그대로 두고 그 아래에 TLS라는 암호화 계층을 끼워, 가로채기·위조·신원 사칭을 막는 방식이다. Mixed Content는 그렇게 보호한 HTTPS 페이지가 일부 자원을 평문 HTTP로 불러올 때 생기는 구멍이고, 브라우저는 이를 등급에 따라 막거나 올린다.

HTTPS와 Mixed Content 문제

웹에서 주소창에 http://bank.example.com/login 을 치고 비밀번호를 보낸다고 하자. 이 요청은 내 노트북에서 출발해 공유기, 통신사 장비, 여러 라우터를 거쳐 은행 서버까지 간다. HTTP는 이 모든 구간을 평문으로 흐른다. 즉 중간의 누구든 패킷을 들여다보면 password=1234 가 글자 그대로 보인다.

평문 HTTP에는 세 가지 약점이 동시에 있다.

  • 도청(eavesdropping): 같은 와이파이에 붙은 사람이 내 요청 내용을 그대로 읽는다.
  • 변조(tampering): 중간 장비가 응답 HTML에 광고나 악성 스크립트를 끼워 넣어도 받는 쪽은 모른다.
  • 위장(impersonation): 공격자가 가짜 서버를 bank.example.com 인 척 내세워도, 평문 HTTP에는 “이 서버가 진짜인지” 확인할 수단이 없다.

HTTPS(HyperText Transfer Protocol Secure)는 이 세 가지를 한꺼번에 막으려고 HTTP 아래에 TLS(Transport Layer Security)라는 보안 계층을 끼운다. 이걸 모르면 “왜 로그인 페이지는 무조건 https:// 여야 하는지”, “주소창 자물쇠 아이콘이 무엇을 보장하고 무엇은 보장하지 않는지”, “왜 HTTPS 페이지인데도 브라우저가 ‘안전하지 않음’을 띄우는지(=Mixed Content)“를 설명할 수 없다.

왜 굳이 HTTP를 그대로 두고 아래에 끼우는가?

HTTP 자체를 암호화 기능이 있는 새 프로토콜로 다시 만들 수도 있었다. 그러나 그렇게 하지 않았다.

기존 HTTP 자산 = 수십 년치 서버·브라우저·라이브러리·도구 HTTP를 새로 설계 → 위 자산을 전부 다시 만들어야 함 HTTP는 그대로 + 아래에 TLS 한 겹 → 기존 자산을 그대로 재사용

그래서 HTTPS는 새 프로토콜이 아니다. “HTTP over TLS”다. 애플리케이션은 여전히 같은 메서드·헤더·상태 코드를 주고받고, 단지 그 바이트가 TLS로 암호화된 통로를 지날 뿐이다. 이 설계 덕분에 2도 같은 방식으로 TLS 위에 그대로 얹혔다.

HTTPS가 만드는 세 가지 보장

비유: 봉인된 외교 행낭

평문 HTTP는 엽서다. 우편함을 거치는 모두가 내용을 읽을 수 있고, 누군가 글자를 고쳐 써도 받는 사람은 모른다.

HTTPS는 봉인된 외교 행낭이다. 세 가지가 동시에 보장된다.

  • 자물쇠로 잠겨 있어 운반하는 사람이 내용을 못 본다 → 기밀성(암호화).
  • 봉인이 뜯기면 즉시 표가 난다 → 무결성(변조 감지).
  • 발신처 인장이 찍혀 있어 누가 보냈는지 검증된다 → 인증(서버 신원).

이 세 보장을 만들어 내는 절차가 TLS 핸드셰이크다.

포트부터 다르다: 80 vs 443

평문 HTTP는 기본 포트 80, HTTPS는 기본 포트 443을 쓴다. 브라우저는 https:// 를 보면 443으로 TCP 연결을 맺고, 연결이 되면 곧바로 HTTP 요청을 보내지 않는다. 먼저 TLS 핸드셰이크부터 한다. 핸드셰이크가 끝나 암호 통로가 생긴 다음에야 그 안으로 평소의 GET / HTTP/1.1 을 흘려보낸다.

TLS 핸드셰이크 — 자물쇠를 만드는 4단계

처음 보는 두 컴퓨터가, 도청당하는 통로 위에서, 둘만 아는 비밀 열쇠를 만들어야 한다. 모순처럼 들리지만 공개키 암호로 풀린다. 동작 순서는 다음과 같다(TLS 1.3 기준 요약).

  1. ClientHello — 클라이언트가 “이런 암호 방식들을 쓸 수 있다”는 목록과 자기 쪽 키 교환 재료(임시 공개값)를 보낸다. 동시에 ALPN으로 h2(HTTP/2) 같은 상위 프로토콜도 제안한다.
  2. ServerHello + 인증서 — 서버가 암호 방식 하나를 고르고, 자기 키 교환 재료와 함께 인증서(certificate)를 보낸다. 인증서 안에는 서버의 공개키와 도메인 이름, 그리고 발급 기관(CA, Certificate Authority)의 디지털 서명이 들어 있다.
  3. 키 합의 — 양쪽이 서로의 키 교환 재료를 합쳐 같은 세션 키(session key)를 각자 계산해 낸다. 이 값은 통로로 직접 보내지 않으므로 도청자는 알 수 없다.
  4. 검증과 완료 — 클라이언트가 인증서의 CA 서명을 자기 안에 내장된 신뢰 CA 목록으로 검증한다. 통과하면 이후 모든 HTTP 메시지를 세션 키로 대칭 암호화해 주고받는다.

여기서 중요한 점은 역할 분담이다. 신원 확인과 키 합의에는 느리지만 안전한 공개키 암호를 쓰고, 실제 대량 데이터 전송에는 빠른 대칭키 암호를 쓴다. 공개키로 “둘만의 대칭키”를 안전하게 만들고, 그다음부터는 그 대칭키로 빠르게 나르는 구조다. 암호 갈래의 차이는 암호 알고리즘에서 더 깊게 다룬다.

인증서는 무엇을 증명하나

자물쇠 아이콘이 보장하는 것은 딱 두 가지다.

  • 이 연결이 암호화되어 있다(도청·변조 방지).
  • 이 서버가 인증서에 적힌 도메인의 소유자임을 신뢰받는 CA가 보증했다(신원).

보장하지 않는 것: “이 사이트가 착한 사이트다”는 뜻은 아니다. 피싱 사이트도 자기 도메인에 대한 정식 인증서를 발급받을 수 있다. 자물쇠는 “통신이 안전하다”이지 “상대가 선하다”가 아니다. 이 구분을 놓치면 보안 사고가 난다.

Mixed Content — HTTPS 안에 섞여 들어온 평문

여기서 본론이다. 페이지를 https://shop.example.com 으로 안전하게 받았다고 하자. 그런데 그 HTML 안에 이런 줄이 있다.

  • <img src="http://cdn.example.com/logo.png">
  • <script src="http://cdn.example.com/app.js">

페이지 본체는 HTTPS로 보호받았지만, 이 자원들은 평문 http:// 로 따로 불러온다. 이렇게 HTTPS 페이지가 일부 자원을 평문 HTTP로 가져오는 상태를 혼합 콘텐츠(Mixed Content)라고 한다.

문제는 명확하다. 페이지 본문을 아무리 암호화해도, 그 안의 app.js 가 평문으로 오면 중간자가 그 자바스크립트를 바꿔치기할 수 있다. 바꿔치기된 스크립트는 같은 페이지 안에서 실행되므로 쿠키를 훔치고 화면을 조작한다. 자물쇠 하나가 잠겨 있어도 옆 창문이 열려 있으면 집은 안전하지 않다.

브라우저는 위험도에 따라 혼합 콘텐츠를 두 등급으로 나눈다.

  • 능동 혼합 콘텐츠(active mixed content): <script>, <link>(CSS), <iframe>, fetch()/XHR 처럼 페이지를 조작할 수 있는 자원. 변조되면 페이지 전체를 장악당한다. → 브라우저가 무조건 차단(block)한다. 로드되지 않는다.
  • 수동 혼합 콘텐츠(passive mixed content): <img>, <audio>, <video> 처럼 표시만 하는 자원. 변조돼도 피해 범위가 좁다. → 과거에는 경고만 했으나, 현재 최신 브라우저는 대부분 자동으로 HTTPS로 올려(upgrade) 시도하고, 실패하면 막는다.

판단 기준은 “이 자원이 변조되면 페이지를 조종할 수 있는가”다. 조종 가능하면 능동, 표시만 하면 수동이다.

실제 OS·브라우저 관점에서의 처리 기준

  • 브라우저 기준: 혼합 콘텐츠 판정은 서버가 아니라 브라우저가 한다. 같은 HTML이라도 브라우저가 자원 요청 시점에 스킴을 보고 차단/승급을 결정한다.
  • 서버 기준: 서버는 Content-Security-Policy: upgrade-insecure-requests 응답 헤더로 “이 페이지의 모든 http:// 요청을 https:// 로 올려서 보내라”를 브라우저에 지시할 수 있다. 일일이 링크를 고치지 않고 한 번에 승급시키는 안전망이다.
  • 운영체제·네트워크 기준: TLS 암호화 자체는 전송 계층 위(애플리케이션과 TCP 사이)에서 일어난다. 운영체제의 소켓은 암호화된 바이트를 그대로 운반할 뿐, 내용 해석에는 관여하지 않는다.

HTTPS와 Mixed Content 코드

핸드셰이크 들여다보기 — openssl s_client

openssl 로 443 포트에 직접 TLS 연결을 맺으면 어떤 프로토콜과 인증서로 합의했는지 그대로 보인다.

Verify return code: 0 (ok) 가 핵심이다. 클라이언트가 내장 CA 목록으로 인증서 서명을 검증해 통과했다는 뜻이다. 이 값이 0이 아니면 브라우저는 “안전하지 않은 연결” 경고를 띄운다.

평문과 HTTPS의 차이 — curl로 비교

여기서 볼 점은 두 경우 모두 보내는 HTTP 요청(GET /)의 의미가 같다는 것이다. HTTPS는 그 요청을 TLS 통로 안에 넣어 보낼 뿐이다. HTTP를 바꾼 게 아니라 아래에 한 겹을 깐 것이라는 설계가 출력에 그대로 드러난다.

혼합 콘텐츠를 막고 승급시키기 — 서버 헤더

이 헤더 한 줄이면 브라우저는 페이지 안의 http:// 자원 요청을 전송 직전에 https:// 로 바꾼다. 다만 원본 서버가 HTTPS를 지원하지 않으면 승급 후 연결이 실패하므로, 근본 해결은 자원 URL 자체를 https:// 로 고치는 것이다.

페이지 본체는 TLS로 안전했지만, 평문으로 끌어온 app.js 한 줄이 전체를 무너뜨린다. 브라우저가 능동 혼합 콘텐츠를 아예 차단하는 이유가 이 그림에 있다.

정리

  • HTTP는 평문이라 도청·변조·위장에 노출된다. HTTPS는 HTTP를 그대로 두고 아래에 TLS 한 겹을 끼워 기밀성·무결성·인증을 동시에 얻는다. 포트는 80이 아니라 443을 쓴다.
  • TLS 핸드셰이크는 공개키로 신원을 확인하고 둘만의 대칭 세션 키를 합의한 뒤, 본 데이터는 빠른 대칭키로 암호화한다. 자물쇠 아이콘은 “통신이 안전하다”는 보장이지 “상대가 선하다”는 보장이 아니다.
  • Mixed Content는 HTTPS 페이지가 자원을 평문 HTTP로 불러올 때 생긴다. 페이지를 조작할 수 있는 능동 콘텐츠(script, css, iframe)는 차단되고, 표시용 수동 콘텐츠(img 등)는 승급 후 실패 시 차단된다.
  • 판단 기준: HTTPS는 로그인·결제뿐 아니라 모든 페이지의 기본값이다. 그리고 HTTPS로 만들었다면 페이지가 부르는 모든 자원도 빠짐없이 HTTPS여야 한다. 한 자원이라도 평문이면 자물쇠는 의미를 잃는다.

이어서 읽기

혼합 콘텐츠의 위험은 결국 신뢰받는 페이지 안에서 스크립트가 실행될 때 커진다. TLS가 내부에서 어떤 암호 부품을 조합하는지는 암호 알고리즘 쪽으로 이어진다.
