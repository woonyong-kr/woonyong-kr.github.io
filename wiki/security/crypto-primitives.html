암호 프리미티브

암호 프리미티브

확인 범위: 이 문서는 암호 프리미티브의 일반 원리와 선택 기준을 설명하며, 포함된 수치·명령 결과·성능 관련 판단은 제시된 RSA-2048, SHA-256, OpenSSL 및 Python 예시에 한정된 검증 내용이다. 다른 알고리즘·키 길이·패딩·버전·실행 환경에 적용하려면 실제 코드와 실행 기록, 성능 측정을 별도로 확인해야 한다.

암호 알고리즘(AES, RSA, SHA)은 원자재다. 그 원자재를 조합해 실무 문제를 푸는 부품이 프리미티브다. 메시지 암호는 “남이 못 읽게”를, 디지털 서명은 “내가 보냈고 안 바뀜”을 보장하며, 두 부품은 키를 정반대 방향으로 쓴다.

암호 프리미티브 문제

암호 알고리즘에서 대칭키, 공개키, 보안 해시라는 세 가지 원자재를 봤다. 그런데 원자재 하나만으로는 현실의 일이 끝나지 않는다. 상황을 하나 그려본다.

앨리스(Alice)가 밥(Bob)에게 "send 1000 to bob"이라는 메시지를 보낸다. 이때 서로 다른 두 가지 요구가 동시에 생긴다.

  • “이 내용을 중간에서 아무도 못 읽게 하고 싶다” → 메시지 암호(message encryption) 문제
  • “이 메시지를 진짜 앨리스가 보냈고, 도중에 한 글자도 안 바뀌었음을 밥이 확인하고 싶다” → 디지털 서명(digital signature) 문제

두 요구는 비슷해 보이지만 정반대다. 암호는 “받는 사람만 풀 수 있게” 만들고, 서명은 “보낸 사람만 만들 수 있게” 만든다. 그래서 공개키를 쓰는 방향이 거꾸로다. 이 방향 차이를 모르면 “공개키로 서명한다” 같은 말이 왜 틀린 표현인지 알 수 없고, HTTPS 인증서가 왜 서명되어 있는지, JWT 토큰이 왜 위조 불가능한지도 설명할 수 없다.

여기서는 알고리즘 자체보다, 알고리즘을 조합해 만든 두 부품에 초점을 둔다. 부품 단위로 이해해야 실제 프로토콜(TLS, SSH, OAuth)이 어떤 부품을 어디에 끼웠는지 보인다.

알고리즘을 부품으로 쓰는 법

프리미티브가 뭔가

프리미티브(primitive)는 “더 큰 보안 시스템을 짤 때 그대로 가져다 쓰는 최소 단위 부품”이다. 비유하면 알고리즘은 철강·고무 같은 원자재이고, 프리미티브는 그 원자재로 찍어낸 볼트·베어링이다. 엔지니어는 베어링 내부를 매번 다시 설계하지 않고 규격 부품을 끼운다.

  • 원자재(알고리즘): AES, RSA, SHA-256
  • 부품(프리미티브): 메시지 암호, 디지털 서명, 메시지 인증 코드(MAC)
  • 완제품(프로토콜): TLS, SSH, GPG

여기서 볼 층은 가운데, 즉 부품이다.

메시지 암호 — 공개키로 직접 암호화하지 않는다

가장 단순한 생각은 “받는 사람 공개키로 메시지를 통째로 암호화한다”이다. 그런데 이게 안 된다. 두 가지 벽이 있다.

첫째, 길이 제한이다. RSA는 키 길이(모듈러스)보다 긴 데이터를 한 번에 못 다룬다.

왜 RSA-2048로 한 번에 190바이트뿐인가?

RSA 출력 한 덩어리 = 모듈러스 크기 = 2048비트 = 256바이트 OAEP 패딩이 잡아먹는 공간 = 2 × 해시 길이 + 2 = 2 × 32 + 2 = 66바이트 실제로 담을 수 있는 평문 = 256 − 66 = 190바이트

이메일 한 통, 이미지 한 장은 190바이트를 훌쩍 넘는다. 둘째 벽은 속도다. 공개키 연산은 대칭키보다 수백 배 느리다. 1메가바이트 파일을 통째로 RSA로 돌리는 건 현실적이지 않다.

그래서 실제로는 하이브리드 암호(hybrid encryption), 다른 이름으로 디지털 봉투(digital envelope)를 쓴다. 짧은 대칭키만 공개키로 감싸고, 본문은 빠른 대칭키로 암호화한다.

%% 하이브리드 암호에서 공개키와 대칭키가 나뉘는 흐름
flowchart LR
  alice["앨리스<br/>① 1회용 대칭키 생성<br/>32바이트 랜덤 키"]
  aes_body["본문 암호화<br/>② 본문을 AES로 암호화<br/>큰 데이터는 빠른 대칭키가 처리"]
  wrapped_key["대칭키 감싸기<br/>③ 대칭키를 밥의 공개키로 암호화<br/>공개키는 짧은 열쇠만 운반"]
  envelope["디지털 봉투<br/>RSA로 감싼 대칭키<br/>AES로 암호화한 본문"]
  bob["밥<br/>④ 개인키로 대칭키 복호화<br/>⑤ 대칭키로 본문 복호화"]
  alice --> aes_body
  alice --> wrapped_key
  aes_body --> envelope
  wrapped_key --> envelope
  envelope --> bob

공개키는 “열쇠 하나(대칭키)“만 안전하게 나르고, 무거운 본문은 대칭키가 맡는다. 이 구조가 암호 알고리즘에서 본 “공개키로 대칭키만 건넨다”의 실제 모습이다.

디지털 서명 — 키 방향이 거꾸로다

암호화는 받는 사람의 공개키로 잠그고 그 사람의 개인키로 푼다. 서명은 정확히 반대다. 보내는 사람의 개인키로 잠그고(서명), 누구나 그 사람의 공개키로 푼다(검증).

비유는 봉인 도장이다. 도장(개인키)은 한 사람만 갖는다. 그 도장이 찍힌 무늬(서명)는 누구나 보고 진위를 확인할 수 있다(공개키). 무늬를 똑같이 만들려면 도장 자체가 있어야 하므로, 위조가 불가능하다.

서명이 보장하는 것은 세 가지다.

  • 무결성(integrity): 메시지가 한 글자라도 바뀌면 검증이 실패한다.
  • 인증(authentication): 개인키 소유자만 만들 수 있으므로, 발신자가 확정된다.
  • 부인 방지(non-repudiation): 나중에 “난 안 보냈다”라고 발뺌할 수 없다.

여기서 암호 알고리즘에서 본 HMAC(Hash-based Message Authentication Code)과의 차이가 갈린다. HMAC도 무결성과 인증은 준다. 하지만 HMAC은 양쪽이 같은 비밀 키를 공유한다. 그래서 밥도 같은 태그를 만들 수 있고, “이건 앨리스가 아니라 밥이 만든 것일 수도 있다”는 반박이 성립한다. 부인 방지가 안 된다. 디지털 서명은 개인키가 앨리스에게만 있으므로 이 반박이 막힌다.

암호화와 서명에서 키가 어느 방향으로 쓰이는지 정리한다. 이 표는 키 방향이라는 한 축으로 두 부품을 비교하므로 표가 적합하다.

부품만들 때(잠금)풀 때누가 할 수 있나
메시지 암호받는 사람의 공개키받는 사람의 개인키누구나 암호화, 받는 사람만 복호화
디지털 서명보내는 사람의 개인키보내는 사람의 공개키보내는 사람만 서명, 누구나 검증

왜 메시지 전체가 아니라 해시에 서명하나?

RSA 서명도 암호화처럼 한 번에 256바이트(모듈러스 크기)밖에 못 다룬다. 1메가바이트 문서에 직접 서명할 수 없다.

해법은 먼저 해시로 줄이는 것이다. SHA-256(아무리 긴 메시지) = 항상 32바이트 지문 그 32바이트 지문에만 개인키로 서명 = 256바이트 서명 한 덩어리

해시는 한 글자만 바뀌어도 지문 전체가 달라진다(쇄도 효과). 따라서 “지문에 서명”해도 “원본에 서명”한 것과 같은 변조 탐지력을 갖는다. 길이는 메시지 크기와 무관하게 고정된다. 그래서 실무의 모든 서명은 서명 = Sign(개인키, SHA-256(메시지)) 형태다.

암호 프리미티브 코드

추상적인 “도장”과 “검증”을 실제 바이트로 내려본다. 아래 명령은 직접 실행해 검증한 값이다.

먼저 서명과 검증의 전체 흐름을 본다. openssl dgst는 메시지를 SHA-256으로 해시한 뒤 그 해시에 서명한다.

실행 결과는 다음과 같다.

# wc -c < msg.txt  → 16    (평문 16바이트)
# wc -c < sig.bin  → 256   (RSA-2048 서명은 항상 모듈러스 크기 256바이트)
Verified OK

16바이트 메시지든 1기가바이트 파일이든 서명은 항상 256바이트다. 해시로 줄인 뒤 서명하기 때문이다. 이 코드에서 기억할 것: 서명은 개인키로 만들고 공개키로 검증한다. 암호화와 키 방향이 반대다.

변조가 일어나면 검증이 실패하는지 확인한다.

# 결과: Verification failure  (bad signature)

금액 한 군데를 바꿨더니 서명이 무효가 됐다. 해시의 쇄도 효과 때문에 지문이 완전히 달라졌고, 그 지문에 맞춰 만든 서명과 더는 들어맞지 않는다. 이 코드에서 기억할 것: 서명 검증 실패는 곧 “내용이 바뀌었거나 가짜 발신자”라는 신호다.

다음은 하이브리드 암호(디지털 봉투)다. 대칭키만 공개키로 감싼다.

# wc -c < aeskey.bin → 32    (대칭키 32바이트)
# wc -c < key.enc    → 256   (RSA로 감싼 키는 모듈러스 크기로 부풂)
# wc -c < body.enc   → 48    (16바이트 솔트 + 한 블록 32바이트)

본문(body.enc)은 빠른 AES가, 열쇠(key.enc)는 RSA가 맡았다. 받는 쪽은 개인키로 key.enc를 풀어 대칭키를 얻고, 그 키로 본문을 복호화한다. 이 코드에서 기억할 것: 공개키 암호는 “데이터”가 아니라 “데이터를 푸는 열쇠”를 나르는 데 쓴다.

마지막으로 서명과 HMAC의 차이를 코드로 대조한다.

HMAC 태그도 무결성과 인증을 준다. 하지만 b"shared-key"를 아는 쪽이면 누구나 같은 태그를 재현한다. 그래서 “둘 중 누가 만들었는지”는 못 가린다. 이 코드에서 기억할 것: 부인 방지가 필요하면 공유 키 HMAC이 아니라 개인키 서명을 써야 한다.

정리

  • 프리미티브는 알고리즘(AES, RSA, SHA)을 조합해 만든 보안 부품이다. 핵심 둘은 메시지 암호와 디지털 서명이다.
  • 메시지 암호는 받는 사람 공개키로 잠근다. 단 공개키는 길이·속도 한계(RSA-2048은 한 번에 190바이트) 때문에 데이터를 직접 다루지 않고, 대칭키만 감싸는 하이브리드 암호로 쓴다.
  • 디지털 서명은 키 방향이 반대다. 보내는 사람 개인키로 서명하고 누구나 공개키로 검증한다. 무결성·인증에 더해 부인 방지까지 준다. 이것이 공유 키 HMAC과의 결정적 차이다.
  • 길이를 맞추려고 메시지 전체가 아니라 SHA-256 해시에 서명한다. 쇄도 효과 덕에 변조 탐지력은 그대로 유지된다.
  • 판단 기준: “받는 사람만 읽게 할까(암호), 보낸 사람을 증명할까(서명)“를 먼저 물어라. 그다음 “둘이 키를 공유하나(HMAC), 한쪽만 개인키를 갖나(서명)“로 인증 방식을 고른다.
