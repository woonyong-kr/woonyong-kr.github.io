OAuth 2.0 권한 위임

OAuth 2.0 권한 위임

확인 범위: 이 문서는 OAuth 2.0 권한 위임의 일반 원리와 주요 흐름, 토큰 설계의 선택 기준을 설명하며, 제시된 HTTP·JSON·JWT 예시는 개념 이해를 위한 예시다. 특정 제공자·버전의 실제 구현 적합성이나 만료 시간·발급 조건·보안 및 성능 판단은 실제 코드, 공식 문서와 실행·측정 결과를 별도로 확인해야 한다.

OAuth 2.0은 사용자가 비밀번호를 제3의 앱에 넘기지 않고도, “내 데이터 중 이만큼만 접근해도 좋다”는 권한(access token)만 안전하게 위임하는 표준 절차다.

OAuth 2.0 권한 위임 필요성

어떤 사진 인화 앱이 “구글 포토에 있는 사진을 가져와 인쇄해 드립니다”라고 한다. 사진을 가져오려면 그 앱이 내 구글 계정에 접근해야 한다.

가장 단순한 방법은 앱에 구글 아이디와 비밀번호를 그대로 입력하는 것이다. 그런데 이렇게 하면 문제가 한둘이 아니다.

  • 앱은 내 비밀번호를 알게 된다. 사진만 보면 되는데 메일, 캘린더, 결제 정보까지 전부 열 수 있다.
  • 비밀번호를 바꾸면 앱이 동작을 멈춘다. 권한을 회수할 방법이 “비밀번호 변경”밖에 없다.
  • 앱 서버가 털리면 내 비밀번호가 그대로 유출된다.

여기서 문제가 생긴다. “누구인지 증명하는 수단(비밀번호)“과 “무엇을 할 수 있는지(권한)“가 분리되어 있지 않다. 비밀번호를 넘기는 순간 모든 권한을 통째로 넘기게 된다.

OAuth 2.0은 이 둘을 분리한다. 앱에는 비밀번호 대신 “구글 포토 읽기 권한만 담긴 토큰”을 준다. 이 개념을 모르면 소셜 로그인(“구글로 로그인”, “카카오로 로그인”)이 내부에서 무슨 일을 하는지, access token과 refresh token이 왜 따로 있는지를 이해할 수 없다.

비밀번호 대신 권한을 건네는 흐름

비유: 호텔 카드키

호텔 체크인을 생각하면 된다. 프런트(인증 서버)에서 신분증으로 본인 확인을 한 뒤, 객실 카드키(access token)를 받는다.

  • 카드키는 비밀번호가 아니다. 카드키를 주워도 내가 누구인지는 알 수 없다.
  • 카드키는 권한이 제한된다. 내 방과 헬스장 문은 열리지만, 다른 손님 방은 안 열린다.
  • 카드키는 만료된다. 체크아웃 날 자정이 지나면 안 열린다.

OAuth의 access token이 바로 이 카드키다. “누구인지”가 아니라 “어디까지 열 수 있는지”를 담은 임시 출입증이다.

등장인물 네 명

OAuth 흐름에는 항상 네 역할이 나온다. 이름부터 정리한다.

  • 자원 소유자(Resource Owner): 데이터의 주인. 보통 사용자 본인.
  • 클라이언트(Client): 데이터에 접근하려는 앱. 위 예시의 사진 인화 앱.
  • 인증 서버(Authorization Server): 로그인을 받고 토큰을 발급하는 서버. 구글의 accounts.google.com.
  • 자원 서버(Resource Server): 실제 데이터를 들고 있는 서버. 구글 포토 API.

권한 부여 방식(Grant Type)

토큰을 받는 절차는 상황에 따라 여러 종류가 있다. 가장 중요한 것이 **Authorization Code Grant(인가 코드 방식)**다. 웹/모바일 앱의 소셜 로그인이 거의 다 이 방식이다.

핵심 아이디어: 토큰을 브라우저(주소창, 화면)에 직접 노출하지 않는다. 대신 한 번 쓰고 버리는 짧은 **인가 코드(authorization code)**를 먼저 받고, 그 코드를 클라이언트 서버가 뒤에서 토큰으로 교환한다. 토큰이 사용자 화면을 거치지 않으므로 가로채기가 어렵다.

왜 코드를 한 번 거치나? (토큰 직접 전달과 비교)

토큰을 곧장 브라우저로 주는 옛 방식(Implicit Grant)과 비교하면 이유가 보인다.

  • 토큰 직접 전달: 인증 서버 → 브라우저 주소창에 토큰. 주소창, 브라우저 기록, 리퍼러 헤더에 토큰이 남는다.
  • 인가 코드 방식: 인증 서버 → 브라우저에는 코드만. 코드 → 클라이언트 서버 뒤편에서 토큰 교환.

코드는 1회용이고 수명이 짧다(보통 10분 이내). 설령 주소창에서 코드가 새어 나가도, 토큰 교환에는 클라이언트만 아는 비밀(client secret) 또는 PKCE 검증값이 필요해서 공격자가 코드만으로 토큰을 못 만든다. 그래서 “한 단계 더 거치는” 번거로움을 감수한다.

access token과 refresh token을 왜 나누나?

access token 하나만 쓰면 딜레마가 생긴다. 수명을 길게 하면 유출 시 오래 악용되고, 짧게 하면 사용자가 자꾸 다시 로그인해야 한다.

그래서 둘로 나눈다.

  • access token: 수명이 짧다(예: 1시간). 매 API 요청에 실어 보낸다. 자주 노출되므로 새어 나가도 곧 만료된다.
  • refresh token: 수명이 길다(예: 30일). 오직 새 access token을 받을 때만, 인증 서버에만 보낸다. 노출 빈도가 낮다.

access token이 만료되면 refresh token으로 조용히 새 access token을 받는다. 사용자는 다시 로그인하지 않는다. 짧은 수명으로 유출 위험을 줄이고, 재로그인 없이 사용성을 유지하는 설계다.

실제 OS/서비스에서의 차이

  • 표준 자체는 토큰의 형식을 강제하지 않는다. 토큰은 의미 없는 임의 문자열(opaque token)일 수도 있고, 자체에 정보를 담은 JWT일 수도 있다.
  • 구글, 카카오, 깃허브 등은 세부 구현이 조금씩 다르다. scope 이름, 만료 시간, refresh token 발급 조건이 제각각이다. 항상 각 제공자 문서를 확인해야 한다.
  • 인증(Authentication, 너 누구냐)과 인가(Authorization, 너 뭘 할 수 있냐)는 다르다. OAuth 2.0은 본래 인가 프로토콜이다. “로그인”(신원 확인)까지 표준화한 것은 그 위에 얹은 **OpenID Connect(OIDC)**이며, 이때 신원 정보를 담은 id_token(JWT)이 추가로 발급된다.

OAuth 2.0 권한 위임 코드

1단계: 인증 서버로 보내는 요청

클라이언트는 사용자를 인증 서버로 redirect한다. 쿼리 파라미터에 무엇을 요청하는지 담는다.

scope가 권한의 범위다. 여기서는 사진 읽기 전용만 요청했다. state는 응답이 내가 보낸 요청에 대한 것인지 확인하는 난수로, CSRF 같은 변조 공격을 막는다.

2단계: 인가 코드를 토큰으로 교환

사용자가 동의하면 인증 서버는 redirect_uri?code=ABC123&state=xyz789로 돌려보낸다. 클라이언트 서버는 이 코드를 뒤에서(서버 대 서버) 토큰으로 바꾼다.

client_secret은 절대 브라우저에 노출되면 안 되는 값이다. 그래서 이 교환은 사용자 화면이 아니라 클라이언트 서버에서 일어난다. 코드만 훔쳐도 secret이 없으면 토큰을 못 만든다.

3단계: 토큰 응답

token_type: Bearer는 “이 토큰을 가진 자(bearer)에게 권한을 준다”는 뜻이다. 그래서 토큰 자체가 곧 출입증이며, 유출되면 그대로 악용된다. 토큰을 어디에 저장하느냐가 보안에서 중요한 이유가 여기 있다.

4단계: 토큰으로 자원 서버 호출

Authorization: Bearer <token> 헤더에 access token을 실으면 자원 서버가 권한을 확인하고 데이터를 내준다. 이 코드에서 기억할 것: 토큰은 매 요청 헤더에 들어가고, 자원 서버는 토큰만 보고 판단한다. 비밀번호는 어디에도 등장하지 않는다.

JWT 토큰 뜯어보기

access token이나 OIDC의 id_token이 JWT라면, 점(.)으로 나뉜 세 조각이다. 각 조각은 Base64URL로 인코딩되어 있다.

%% JWT 토큰의 header, payload, signature 구조
flowchart LR
  header["header<br/>alg"]
  payload["payload<br/>sub"]
  signature["signature<br/>sign(header.payload)<br/>위조 여부 검증"]
  header -->|.| payload
  payload -->|.| signature

서명(signature)은 인증 서버의 비밀키로 만든다. 자원 서버는 공개키로 서명을 검증해 “이 토큰이 위조되지 않았다”를 확인한다. payload는 누구나 디코드해 읽을 수 있으므로, JWT에 비밀번호 같은 민감 정보를 넣으면 안 된다. JWT의 가치는 “숨김”이 아니라 “위조 불가”에 있다.

정리

  • OAuth 2.0은 비밀번호 대신 권한만 담은 토큰을 위임하는 표준이다. “누구인가”와 “무엇을 할 수 있는가”를 분리한다.
  • 웹/앱 소셜 로그인은 대부분 Authorization Code 방식이다. 1회용 코드를 먼저 받고, 클라이언트 서버가 secret과 함께 토큰으로 교환한다.
  • access token은 짧게(자주 노출), refresh token은 길게(드물게 사용) 두어 유출 위험과 재로그인 부담을 함께 줄인다.
  • 토큰은 Bearer 출입증이라 유출되면 그대로 악용된다. 그래서 다음 질문이 자연스럽게 따라온다 — 토큰을 브라우저 어디에 저장해야 안전한가?

이어서 읽기

토큰 저장 위치에 따라 XSS와 CSRF 노출이 달라진다. OAuth 흐름을 이해한 뒤에는 브라우저 저장소와 웹 공격 경계를 함께 보면 토큰 관리 판단이 쉬워진다.

  • 브라우저 저장소
  • XSS와 CORS
