쿠키·로컬스토리지·세션스토리지 — 브라우저가 데이터를 보관하는 세 장소

쿠키·로컬스토리지·세션스토리지 — 브라우저가 데이터를 보관하는 세 장소

확인 범위: 이 문서는 쿠키·로컬스토리지·세션스토리지의 일반적인 동작 차이와 보안 관점의 선택 기준을 설명하며, 포함된 코드는 개념을 보여 주는 예시다. 특정 브라우저·버전이나 실제 애플리케이션에서의 동작, 저장 용량, 보안 효과와 성능은 실행 기록이나 측정으로 검증한 결과가 아니다.

브라우저는 데이터를 세 곳에 보관할 수 있다. 쿠키는 서버와 자동으로 주고받는 작은 메모, 로컬스토리지는 브라우저에 남는 영구 창고, 세션스토리지는 탭을 닫으면 사라지는 임시 창고다. 어디에 저장하느냐가 보안과 동작을 바꾼다.

쿠키·로컬스토리지·세션스토리지 혼동

HTTP는 상태가 없다(stateless). 요청 하나가 끝나면 서버는 방금 누가 왔는지 잊는다. 그런데 로그인은 상태가 필요하다. “이 사람은 1분 전에 로그인한 그 사람”이라는 사실을 어딘가 기억해야, 페이지를 옮길 때마다 다시 로그인하지 않는다.

그 “어딘가”가 브라우저의 저장소다. 로그인 토큰, 장바구니, 다크 모드 설정 같은 것을 브라우저에 두고 다음 요청에 다시 꺼내 쓴다.

문제는 저장 방식이 한 가지가 아니라는 점이다. 셋 중 무엇을 고르느냐에 따라 서버로 자동 전송되는지, 탭을 닫으면 사라지는지, 자바스크립트로 읽을 수 있는지가 전부 달라진다. 이 차이를 모르면 OAuth 토큰을 엉뚱한 곳에 저장해 XSS 공격에 그대로 노출시키게 된다.

세 저장소를 구분하는 기준

비유: 메모를 어디에 붙이나

세 저장소는 메모를 붙이는 위치가 다르다.

  • 쿠키: 택배 상자에 붙여 매번 같이 보내는 송장. 내가 요청을 보낼 때마다 서버에 자동으로 따라간다.
  • 로컬스토리지: 책상 서랍. 내가 직접 열어 꺼내야 하고, 치우기 전까지 계속 남는다.
  • 세션스토리지: 포스트잇. 자리(탭)를 뜨면 버려진다.

세 저장소 비교

비교가 판단 기준이 되므로 여기서는 표를 쓴다.

서버로 자동 전송되는가

셋을 가르는 가장 중요한 차이는 “서버로 자동으로 가느냐”다.

  • 쿠키는 같은 도메인으로 요청을 보낼 때마다 브라우저가 알아서 Cookie 헤더에 실어 보낸다. 그래서 로그인 세션 유지에 잘 맞는다. 반대로, 내 의도와 무관하게 자동 전송되기 때문에 CSRF 공격의 표적이 된다.
  • 로컬스토리지/세션스토리지는 절대 자동 전송되지 않는다. 보내려면 자바스크립트가 직접 값을 읽어 요청에 넣어야 한다. 그래서 CSRF에는 안전하지만, 자바스크립트로 항상 읽히므로 XSS에는 약하다.

그래서 토큰은 어디에 저장하나? (보안 판단)

OAuth access token 저장 위치를 고를 때 이 갈림길이 그대로 적용된다.

  • 로컬스토리지에 토큰을 두면: XSS로 스크립트가 한 번 주입되면 localStorage.getItem('token') 한 줄로 토큰이 통째로 털린다.
  • HttpOnly 쿠키에 두면: 자바스크립트가 쿠키를 읽지 못하므로(document.cookie에 안 보임) XSS로도 토큰 값을 빼내기 어렵다. 대신 자동 전송되니 CSRF 대비로 SameSite 속성을 함께 건다.

그래서 민감한 인증 토큰은 가능하면 HttpOnly + Secure + SameSite 쿠키에 두는 편이 안전하다. 로컬스토리지는 토큰처럼 털리면 안 되는 값이 아니라, 다크 모드 설정 같은 비민감 데이터에 적합하다.

쿠키 보안 속성

쿠키는 단순한 문자열이 아니라 속성을 붙여 통제한다. 속성마다 막는 공격이 다르다.

  • HttpOnly: 자바스크립트의 document.cookie 접근 차단 → XSS로 인한 탈취 방어
  • Secure: HTTPS 연결에서만 전송 → 중간자 도청 방어
  • SameSite=Strict|Lax|None: 다른 사이트에서 시작된 요청에 쿠키를 붙일지 통제 → CSRF 방어
    • Strict: 외부 사이트에서 온 요청에는 절대 안 붙음
    • Lax: 링크 클릭 같은 안전한 이동에만 붙음 (요즘 기본값)
    • None: 항상 붙음. 단 Secure 필수

쿠키·로컬스토리지·세션스토리지 코드

서버가 쿠키를 심는 법 (Set-Cookie 헤더)

서버는 응답 헤더로 쿠키를 내려보낸다. 보안 속성을 함께 붙인 모습이다.

이 응답은 session 쿠키를 심고, 자바스크립트 접근을 막고(HttpOnly), HTTPS에서만 보내고(Secure), 외부 사이트 요청에는 제한적으로만 붙이고(SameSite=Lax), 1시간 뒤 만료시킨다(Max-Age). OAuth 토큰을 안전하게 보관하는 표준 형태다.

브라우저가 쿠키를 자동으로 돌려보내는 법

개발자가 코드를 쓰지 않아도 브라우저가 Cookie 헤더를 알아서 붙인다. 이 “자동”이 쿠키의 편리함이자 CSRF 위험의 근원이다.

자바스크립트로 다루는 세 저장소

이 코드에서 기억할 것: HttpOnly 쿠키는 document.cookie에 나타나지 않는다. 로컬/세션 스토리지는 항상 자바스크립트로 읽히므로, 거기 둔 값은 XSS에 그대로 노출된다.

XSS가 로컬스토리지 토큰을 터는 한 줄

같은 토큰이 HttpOnly 쿠키에 있었다면 이 스크립트는 토큰 값을 읽지 못한다. 저장 위치 선택이 곧 공격 표면의 크기를 정한다.

정리

  • 쿠키는 서버와 자동으로 오가는 메모, 로컬스토리지는 영구 창고, 세션스토리지는 탭 단위 임시 창고다.
  • 가장 중요한 갈림길은 “서버 자동 전송 여부”다. 쿠키는 자동(→ CSRF 주의), 스토리지는 수동(→ XSS 주의)이다.
  • 인증 토큰처럼 털리면 안 되는 값은 HttpOnly + Secure + SameSite 쿠키가 안전하다. 비민감 설정값은 로컬스토리지가 편하다.
  • 저장 위치를 고르는 일은 곧 어떤 공격을 감수할지 고르는 일이다. 그래서 다음 두 문서를 이어 읽는다.
    • XSS와 CORS: 토큰을 노리는 공격의 작동 원리.
    • OAuth 2.0: 여기서 저장하는 토큰이 애초에 어떻게 발급되는지.
